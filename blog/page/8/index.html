PostgreSQL Course — 05 · Transactions, MVCC, Isolation and Locking
Created2026-06-29|Database PostgreSQL
A transaction is the unit in which a database promises to be correct. PostgreSQL implements that promise with MVCC — multi-version concurrency control — where writers never block readers and readers never block writers, because every row can exist in several versions at once. That design explains almost everything else in this post: why an writes a new row instead of editing one, why exists at all, why an idle transaction can quietly break your cluster, and why hands you an error instead of a lock. This post covers the mechanics, the four isolation levels as PostgreSQL actually implements them, explicit locking, deadlocks, and the vacuum consequences. > Series map: 00 Foundations & Setup → 01 SQL Fundamentals & Data Types → 02 Joins, Aggregation & Window Functions → 03 Indexes & the Query Planner → 04 Query Optimization & Statistics → 05 Transactions, MVCC, Isolation & Locking (this post) → 06 Schema Design, Normalization & JSONB → 07 Operations, Backup, Replication & Security. This is the application's and the schema's property; the database enforces it through constraints, not by magic.- Isolation — concurrent transactions produce a result consistent with some acceptable ordering. Snapshots and visibility A snapshot records: the next unassigned transaction ID, and the list of transactions in flight. SERIALIZABLE and SSI PostgreSQL 9.1 and later implement with Serializable Snapshot Isolation (SSI). It runs on top of snapshot isolation and tracks read/write dependencies between concurrent transactions with predicate locks (SIREAD locks). When it detects a dependency cycle that could not occur in any serial ordering, it aborts one of the transactions with SQLSTATE . Properties worth internalising: - It does not block. Rules for the retry body: - Retry the whole transaction, not the failing statement. The snapshot is gone; re-reading is the point.- Never leave side effects outside the transaction inside the retried block — no emails, no queue publishes, no HTTP calls. PostgreSQL detects it after (default ) and aborts one transaction with SQLSTATE . The fix: consistent lock ordering Deadlocks come from two transactions acquiring the same set of locks in different orders. Impose a global order — sorting by primary key is the standard choice — and the cycle becomes impossible. Other reliable mitigations: keep transactions short, do not interleave user think-time inside a transaction, and touch tables in the same order everywhere in the codebase. Chapter 7 — Long transactions, wraparound, and "idle in transaction" Why long transactions are expensive Vacuum can only remove a dead tuple if no snapshot in the entire cluster could still see it. One transaction that started an hour ago and is still open pins the global horizon at its own snapshot. For that hour, no dead tuple newer than it can be removed anywhere in the database — even in tables that transaction has never touched. The result is bloat everywhere, slowly, invisibly, until someone notices the disk. is the worst state on that list: the client issued , did some work, and then went off to call an external API or wait on a user. It holds its snapshot, holds any locks it took, and consumes a connection slot, while doing nothing. Defences, all of which should be set in production: Set them per role rather than globally when a reporting user legitimately needs longer. Transaction ID wraparound Transaction IDs are 32-bit. PostgreSQL treats them as a circle: from any XID, roughly 2 billion are "in the past" and 2 billion are "in the future". A tuple whose fell more than 2 billion transactions behind would suddenly appear to be from the future — invisible. To prevent that, old tuples are frozen: marked as unconditionally visible, so their no longer matters. Chapter 7 — Client-Side Field-Level Encryption (CSFLE) Sensitive fields are encrypted by the driver before they leave the application. The server only ever sees ciphertext. Algorithm matters: - Deterministic — same plaintext → same ciphertext. Allows equality lookups ().- Random — same plaintext → different ciphertext each time. Hides distribution + frequency but no equality lookups. The driver intercepts queries + writes, encrypts/decrypts as needed. Server, admins, backups, replicas all see ciphertext only. Key Management: data keys are encrypted by a master key held in your KMS (AWS KMS, Azure Key Vault, GCP KMS, KMIP). The key vault collection stores encrypted data keys; the master key never leaves the KMS. Constraints with CSFLE: - Only equality queries on deterministically-encrypted fields.- No range / sort / aggregation on encrypted fields.- For "range queries on encrypted data" → use Queryable Encryption. Chapter 8 — Queryable Encryption (GA in 7.0) Queryable Encryption extends field-level encryption to support equality + range + prefix queries on encrypted data — without ever decrypting on the server. Use cases: - PII fields needing search (email lookup for password reset).- Salaries, balances, ages — range queries while keeping plaintext invisible to DBAs.- Compliance (HIPAA, GDPR) — data is encrypted to ops staff but still queryable to apps with the right key. Hash Equality only. WAL-logged and crash-safe since PostgreSQL 10 (before that they were not replicated and had to be rebuilt after a crash, which is why old advice says "never use hash indexes"). Narrower than a B-tree for long keys, since it stores a 32-bit hash rather than the value. In exchange it cannot do ranges, cannot sort, cannot be unique, and cannot be multicolumn. The niche is genuinely narrow: very long keys, equality-only access, no ordering requirement. Benchmark against a B-tree on your own data before committing. GIN — Generalized Inverted Index For values that contain multiple searchable items: array elements, keys and values, full-text lexemes, trigrams. GIN reads fast and writes slowly, because one row update can touch many index entries. The mechanism buffers changes in a pending list and flushes them in batches — good for write throughput, but it means a query may have to scan the unflushed pending list, producing occasional latency spikes. Tune with or set for read-latency-sensitive workloads. GiST — Generalized Search Tree A framework for indexing things without a natural total order: geometry, ranges, nearest-neighbour search, and the exclusion constraints from Post 01. GiST is lossy: it returns candidate rows that the executor must recheck. That is why a GiST plan shows a . SP-GiST — Space-Partitioned GiST For naturally hierarchical, non-balanced partitionings: quadtrees, k-d trees, radix trees. In practice: / containment, points, and text prefix search where a radix tree beats a B-tree on space. BRIN — Block Range INdex Stores a summary (by default min/max) for each range of heap pages — 128 pages by default. Consequently it is minuscule: an index over a billion-row table can be a few megabytes. BRIN only works when the physical row order correlates with the indexed value — append-only time-series data, log tables, tables loaded in key order. If rows are scattered, every block range spans the whole value domain and the index eliminates nothing. Check before building: PostgreSQL 14 added opclasses (tolerant of a few outliers that would otherwise ruin a range's summary) and opclasses (equality on uncorrelated columns). When a sequential scan is correct This bears stating plainly, because a great deal of wasted tuning effort comes from trying to force an index scan that would be slower. A sequential scan is the right plan when: 1. The predicate matches a large fraction of the table — beyond roughly 5–10%, random heap fetches through an index exceed the cost of reading everything sequentially. The exact crossover depends on and physical correlation.2. The table is small. Under a few hundred pages, one sequential read beats index descent plus heap fetch. The planner knows this and is right.3. No index covers the predicate, and creating one is not justified by the query's frequency.4. The query is an aggregate over most of the table — genuinely must look at everything (or at least at the whole visibility map, via a parallel index-only scan).5. Parallelism applies. A parallel sequential scan across four workers can beat a single-threaded index scan outright.
