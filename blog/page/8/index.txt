Chapter 1 — How the scheduler works

Terminology

- Scheduling — assigning an unscheduled Pod to a node by writing . The kubelet on that node then starts it.- Filter (predicate) — a check that eliminates nodes a Pod cannot run on.- Score (priority) — a ranking of the surviving nodes by how good a fit they are.- Binding — persisting the chosen node back to the API server.- Feasible node — a node that survived every filter.

The two phases

For each Pod in the scheduling queue,  runs a scheduling cycle and then a binding cycle. The scheduling cycle has two halves:

1. Filter. Every node is tested against a series of predicates. Any failure removes the node from consideration:

- Does the node have enough allocatable CPU, memory and ephemeral storage to satisfy the Pod's requests?- Do the Pod's  and required node affinity match the node's labels?- Are the node's taints tolerated by the Pod?- Are the requested host ports free?- Can the Pod's volumes be attached here (zone, node affinity of the PV, attach limits)?- Do required pod affinity and anti-affinity rules hold?- Is the node  and not under ,  or ?

If zero nodes survive, the Pod stays  and the scheduler records an event naming the failing predicate — . That event is the answer to almost every "why is my Pod Pending" question.

2. Score. Each feasible node is scored 0-100 by several plugins and the totals are weighted:

-  — spread load (, the default) or pack it tight (, better for autoscaler-driven cost savings).-  — prefer nodes that already have the image cached.- , , ,  — the preferred (soft) forms of each rule.

The highest-scoring node wins; ties are broken at random. The scheduler then reserves the resources, runs any  plugins, and binds asynchronously.

Two properties matter operationally:

- The scheduler decides once, at admission. It does not move a running Pod because the cluster later became unbalanced. Rebalancing requires deleting Pods (the  project automates this).- The scheduler reasons about requests, never about actual usage. A node can be 95 % idle and still reject a Pod because its requests are fully committed — and it can be 100 % CPU-saturated and happily accept more Pods whose requests fit.

Chapter 2 — Controlling placement

nodeSelector — the simple case

Exact-match labels only, hard requirement. Fine for small, unambiguous rules; it cannot express preferences, negation, or set membership.

Node affinity — the expressive case

Read the long field names literally.  is a filter;  is a score contribution.  is the important half: an already-running Pod is never evicted because the node's labels changed. There is no  — if you need eviction on a condition change, use a taint with .

Pod affinity and anti-affinity

These place Pods relative to other Pods, using a  to define what "together" means.

> Common pitfall: hard  on  caps your replica count at the node count. Scale to 10 replicas on a 6-node cluster and 4 Pods sit  forever. Use the preferred form, or topology spread constraints, unless the co-location really is unacceptable.

Pod affinity is also computationally expensive — the scheduler must evaluate every Pod in the matched topology for every candidate node. On large clusters, prefer topology spread constraints.

Taints and tolerations — the inverse

Affinity is a Pod attracting a node. A taint is a node repelling Pods. Only Pods with a matching toleration may land there.

| Effect | Meaning ||--------|---------||  | no new Pod without a toleration ||  | soft version — avoid if possible ||  | as , plus evict already-running Pods that do not tolerate it (optionally after ) |

Taints are how you reserve expensive hardware (GPU nodes, high-memory nodes) for the workloads that need it, how control-plane nodes stay free of user workloads, and how the node lifecycle controller cordons off unhealthy nodes —  and  are  taints applied automatically.

Note that a toleration does not attract. Tolerating the GPU taint lets a Pod run on GPU nodes; it does not make it prefer them. Pair a toleration with node affinity to get both halves.

Topology spread constraints — the modern way to spread

is the maximum permitted difference between the most-populated and least-populated domain. With  across three zones, nine replicas land 3/3/3 and ten land 4/3/3. This expresses "spread evenly" directly, instead of approximating it with anti-affinity, and it is far cheaper for the scheduler to evaluate.

Chapter 3 — Requests, limits and QoS

The one sentence that matters

Requests drive scheduling. Limits drive enforcement.

- A request is a reservation. The scheduler subtracts it from the node's allocatable capacity and guarantees the Pod that much. It is also the number that decides whether the Pod fits at all.- A limit is a ceiling enforced at runtime by the kernel through cgroups. Exceed the CPU limit and you are throttled. Exceed the memory limit and you are killed.

Everything else in this chapter follows from that distinction.

CPU is compressible: exceeding your share means running slower. Memory is incompressible: there is no "slower", only "killed".

QoS classes

The kubelet assigns each Pod a class based purely on how its requests and limits are written:

| Class | Condition | Consequence ||-------|-----------|-------------|| Guaranteed | every container sets both CPU and memory, and request == limit for each | evicted last; eligible for exclusive CPUs under the static CPU manager policy || Burstable | at least one request is set, but not the Guaranteed pattern | evicted after BestEffort, in order of how far usage exceeds requests || BestEffort | no requests or limits anywhere in the Pod | evicted first, always |

Under node memory pressure the kubelet evicts in that order: BestEffort first, then Burstable Pods that are using more than they requested (ranked by the excess), then Guaranteed. The kernel's own OOM killer uses a parallel mechanism, , derived from the same classes.

> Common pitfall: BestEffort Pods look thrifty and are actually hazardous. They are the first thing evicted when a node fills up, they contribute nothing to autoscaler capacity calculations, and they can starve neighbours. Set requests on everything, including the small "unimportant" jobs.

CPU limits and CFS throttling

A CPU limit is implemented as a CFS quota: the cgroup is granted quota microseconds of CPU time per period (100 ms by default). A limit of  means 50 ms of CPU per 100 ms window. When the quota is exhausted, every thread in the cgroup is stopped until the next period begins.

This produces a failure mode that is invisible in average CPU graphs. An application averaging 30 % of its limit can still be throttled hard, because the work is not spread evenly: a request arrives, several threads wake, the quota is consumed in 15 ms, and the container sleeps for the remaining 85 ms. The result is tail latency in whole multiples of 100 ms while the dashboard shows a comfortable average.

Multithreaded runtimes make it worse. A JVM or Go program that sees 32 host CPUs will happily run 32 threads, burning the quota 32× faster than a single thread would.

Measure it — do not guess:

Sustained values above roughly 5-10 % on a latency-sensitive service are worth acting on. Confirm on your own workload rather than trusting any published threshold.

The genuine argument for omitting CPU limits

Set memory limits always; consider omitting CPU limits on latency-sensitive services.

The case for omitting: CPU is compressible and already fairly shared. When several containers on a node contend, the kernel divides CPU time in proportion to their requests (cgroup CPU shares) — so requests alone already provide isolation under contention. A limit adds nothing during contention and actively hurts when the node is idle, because it forbids a container from using spare capacity it could have had for free. Throttling a service that could have run faster, on a machine that is 60 % idle, is pure loss.

The case for keeping them: limits make behaviour reproducible and capacity predictable, they stop one runaway process from degrading its neighbours' latency (fair sharing is fair, but a busy neighbour still slows you down), some regulated or multi-tenant environments require hard ceilings, and Guaranteed QoS — which requires a CPU limit — is needed for exclusive CPU pinning.

A defensible policy: memory limit always set and equal to a measured peak plus headroom; CPU request set from measured usage; CPU limit omitted for latency-sensitive services, set generously (well above the request) for batch and untrusted workloads. Whatever you choose, also set  (Go) or the container-aware JVM flags so the runtime sizes its thread pools to the cgroup, not to the host.

OOMKill and exit code 137

Exceed the memory limit and the kernel's OOM killer terminates the process with . The container exits with 137 — the shell convention of , and  is SIGKILL.

- Exit 137 with  — the container exceeded its own memory limit. Chapter 4 — Probes

Three probes, three completely different jobs. Confusing them is the most common cause of self-inflicted outages in Kubernetes.

| Probe | Question | Action on failure ||-------|----------|-------------------|| liveness | "Is this process wedged beyond recovery?" | kill and restart the container || readiness | "Should this Pod receive traffic right now?" | remove the Pod from Service endpoints (no restart) || startup | "Has the process finished booting?" | kill the container; while it runs, liveness and readiness are suspended |

The classic outage

A team writes one  endpoint that checks the database, and wires it to both the readiness and the liveness probe. The database has a 30-second hiccup.

1. Every replica's liveness probe fails.2. The kubelet kills and restarts every replica simultaneously.3. The database recovers — and is immediately hit by the full fleet reconnecting and re-warming caches at once.4. The probes fail again. Restart storm. . The blast radius of a 30-second dependency blip is now a total outage that outlives it by many minutes.

The rule that prevents it: a liveness probe must never test anything outside the process. If the dependency is down, restarting your container does not help — it makes recovery harder by discarding warm state and multiplying reconnection load.

- Liveness → shallow. "Is the event loop running, can I serve a trivial response?" Many mature services are better off with no liveness probe at all; a process that crashes on a fatal fault is restarted by the Pod restart policy anyway.- Readiness → may be deep. Failing readiness removes the Pod from load balancing and is reversible with no state loss. If every replica fails readiness the Service has no endpoints and clients get connection errors — bad, but strictly better than a restart storm, and it recovers the instant the dependency does.- Startup → the correct tool for slow-starting applications. Without it you must inflate  or  on liveness, which weakens liveness forever to accommodate one slow boot.

Graceful shutdown and the endpoint-removal race

When a Pod is deleted, two things happen concurrently, and this is the subtle part:

Path B is a distributed propagation across every node in the cluster; path A is local and immediate. Cluster Autoscaler and Karpenter

The HPA adds Pods. Something has to add nodes when those Pods do not fit.

| | Cluster Autoscaler | Karpenter ||---|---|---|| Model | scales pre-defined node groups / ASGs up and down | provisions individual nodes chosen to fit the pending Pods || Instance choice | fixed per node group | picks instance type, size, zone and capacity type per batch of Pods || Speed | minutes (ASG-mediated) | typically faster; talks to the cloud API directly || Consolidation | scale-down of under-used nodes | active consolidation and bin-packing; replaces nodes with cheaper ones || Availability | all major clouds | AWS-native origin, now with other providers |

Both react to unschedulable Pods, which means both depend entirely on your requests being accurate. Requests that are too high make the autoscaler buy capacity nobody uses; requests that are too low let it under-provision and then evict. Note also that Karpenter-style consolidation deliberately churns nodes, so PodDisruptionBudgets and correct graceful shutdown (Chapter 5) stop being optional.

Right-sizing methodology

A repeatable procedure, in order:

1. Instrument first. Without  and a metrics store you are guessing. Collect at least two weeks, covering a weekly cycle and any peak event.2. Set memory request at P95 of observed working set; set the memory limit at the observed peak plus 25-50 %. Memory is incompressible, so the limit is a safety fuse, not a target.3. Set CPU request at P90 of observed usage. This is the scheduling reservation and the HPA's denominator, so it should reflect typical, not peak.4. Decide the CPU limit by policy (Chapter 3), then verify with the throttling ratio.5. Check the QoS class you ended up with —  — and confirm it matches the workload's importance.6. Compare requests against actual usage cluster-wide. The ratio of total requests to total usage is your headline waste number, and it is usually far worse than anyone expects.7. Re-measure after every significant release. Right-sizing is not a one-off project.

Read those two together: a memory ratio consistently near 1.0 predicts OOMKills; a CPU ratio consistently near 0.05 is money on fire.

The shared-context leak

V8 (like other engines) does not give each closure its own copy of the variables it uses. Variables captured by any closure in a scope go into one context object for that scope, and every closure created in that scope keeps the whole context alive:

Chapter 1 — The model

Terminology

- Agent — a call stack, a set of queues and one event loop. A window (with its same-origin iframes), each worker, and each Node  worker are separate agents.- Task (often "macrotask") — a unit of work queued by the host: a timer firing, an input event, a network response, a . Browsers keep several task queues (by task source) and may choose which queue to serve next — this is how input can be prioritised over timers.- Microtask — a smaller unit queued by promise reactions, , and . There is one microtask queue per agent.- Microtask checkpoint — the step that runs microtasks until the queue is empty, including microtasks queued by microtasks.- Rendering opportunity — a moment when the browser can present a new frame, typically aligned with the display refresh (about every 16.7 ms at 60 Hz). Browsers may skip frames or throttle hidden pages.

One turn of the browser loop

1. Pick the oldest task from a task queue the browser chooses, and run it to completion. The call stack empties.2. Perform a microtask checkpoint: run microtasks until none remain.3. If this is a rendering opportunity and there is something to render, update the rendering (Chapter 3).4. Repeat.

Two rules produce nearly every "surprising" order:

- Microtasks run whenever the JavaScript stack becomes empty, not only between tasks. The HTML spec's "clean up after running script" step performs a microtask checkpoint whenever the JavaScript execution context stack becomes empty — after a task, but also after each event listener the browser invokes and after each  callback.- The checkpoint drains the queue completely. A microtask that queues another microtask keeps the loop in step 2. An infinite chain of microtasks freezes the page as surely as  — rendering and input never get a turn.

> Watch out:  is not "run next". HTML clamps the delay to at least 4 ms once timers are nested more than 5 levels deep, browsers throttle timers in background tabs heavily, and a timer is only a task — everything already queued, and the rendering step, can run first.

Chapter 3 — Rendering and

When the loop decides to render, the HTML standard's update the rendering step runs, per document, in this order (abridged):

1. Run the resize steps (fire ), then the scroll steps (fire ).2. Evaluate media queries; update animations and send animation events; fullscreen steps.3. Run the animation frame callbacks — every  callback registered before this frame began.4. Recalculate styles and update layout, then deliver  callbacks; if they changed layout, recalculate and deliver again (to a depth limit, after which the browser reports a "ResizeObserver loop" error).5. Run the  update steps.6. Paint — "update the rendering or user interface".

Consequences for engineers:

- rAF is the place for visual writes. Code in a rAF callback runs just before style and layout, so the frame shows its result. A  animation drifts against the display's refresh and may run twice or zero times per frame.- A rAF callback that calls rAF schedules for the next frame, not the current one. That is what makes rAF loops work.- Microtasks run between rAF callbacks (the stack empties after each one), so a promise resolved in one rAF callback settles before the next callback runs.- Layout thrashing: reading layout (, ) after writing styles forces the browser to do style and layout synchronously, in the middle of your task. Doing it in a loop — write, read, write, read — can force a layout per iteration. Batch all reads first, then all writes.

> Common pitfall: using rAF in a background tab to keep "real-time" work going. Browsers stop or heavily throttle rAF in hidden documents (the HTML spec removes hidden documents from rendering). Anything that must keep running — a WebSocket heartbeat, a timer for session expiry — belongs in a timer or a worker, not rAF.

Chapter 7 — Long tasks, INP and yielding

Terminology

- Long task — any task that occupies the main thread for more than 50 ms. Input that arrives during it waits.- INP (Interaction to Next Paint) — the Core Web Vital for responsiveness: roughly the worst latency from a user interaction to the next frame, across the page's life. Good is 200 ms or less; poor is above 500 ms.- Yielding — ending the current task deliberately so the browser can handle input and render, then continuing in a new task.

Chapter 2 — The V8 pipeline

V8 has one interpreter and three compilers. Each tier trades compile time for code quality:

| Tier | Kind | Shipped | Input → output | Why it exists ||---|---|---|---|---|| Ignition | Interpreter | V8 5.9 / Chrome 59 (with TurboFan) | Source → bytecode, then executes it | Fast start, small memory, collects type feedback || Sparkplug | Baseline (non-optimising) compiler | Chrome 91 | Bytecode → machine code in one linear pass, no IR | Removes interpreter dispatch cost almost for free || Maglev | Mid-tier optimising compiler | Chrome 117 | Bytecode + feedback → SSA/CFG IR → machine code | Good code quickly: about 10× slower to compile than Sparkplug, about 10× faster than TurboFan (V8 team's figure) || TurboFan | Top-tier optimising compiler | V8 5.9 | Bytecode + feedback → heavily optimised machine code | Peak speed for truly hot code; its JavaScript backend now runs on the CFG-based Turboshaft IR |

Parsing: most functions are parsed twice

Full parsing is expensive, and most functions in a large bundle never run. V8 therefore pre-parses inner functions: it checks syntax and records which variables they capture, but builds no AST and no bytecode. The full parse and bytecode generation happen on the first call ("lazy compilation"). A function that is called immediately pays twice, so V8 uses heuristics — for example a function expression wrapped in parentheses () is compiled eagerly.

Consequences:

- Startup cost is dominated by how much code is parsed, not how much exists. Code splitting and lazy  help because unparsed code costs nothing.- Compiled bytecode can be cached. Chrome caches it for scripts it sees repeatedly; Node offers a module compile cache (, added in v22.1.0) that persists it to disk between runs, useful for CLIs.

The bracketed numbers after each operation are feedback slots. Every property access, call and arithmetic operation records what it saw — which object shapes, whether the operands were small integers or doubles — into the function's feedback vector. Everything the optimising tiers do is built on this record. Code that never ran has no feedback, and the optimisers cannot specialise it.

Tiering up and OSR

V8 counts how much a function runs (invocations and loop iterations, weighted by bytecode size) and promotes it when budgets run out. The exact thresholds are internal heuristics that change between releases; do not design around numbers.

A long-running loop inside a function that is called only once would never tier up by call count, so V8 performs on-stack replacement (OSR): it compiles an optimised version while the loop is running and jumps into it mid-loop.

Speculation is the whole trick

An optimising compiler for a dynamic language cannot know that  is a small integer. It speculates from feedback: "every  seen so far had shape M1, and  was always a Smi". It emits a cheap check (a guard) followed by a fast path — a load at a fixed offset, an integer add. If the guard fails at run time, the optimised code cannot continue; it deoptimizes (Chapter 5). Chapter 7 — The Orinoco garbage collector

Terminology

- Generational hypothesis — most objects die young. A GC that collects young objects often and cheaply wins.- Young generation — where new objects are allocated. In V8 it is split into a nursery and an intermediate generation.- Old generation — objects that survived two young collections.- Scavenge (minor GC) — copying collection of the young generation.- Mark-Compact (major GC) — marking live objects in the whole heap, sweeping dead ones, compacting fragmented pages.- Write barrier — a small piece of code the engine runs on every pointer store into the heap, so concurrent or incremental marking does not miss new references, and old-to-young pointers are remembered.- Stop-the-world pause — time the main thread spends in GC instead of running JavaScript.

Young generation: the scavenger

New objects go into the nursery with bump-pointer allocation (very cheap). When the young space fills, a scavenge copies live objects out: survivors of their first scavenge become intermediate; survivors of a second are promoted to the old generation. The young generation uses a semi-space design, so half of it is always empty to receive the copies. Cost is proportional to the number of live objects, not the garbage — dying young is nearly free.

The scavenger runs in parallel on helper threads; the V8 team measured a 20–50% reduction in main-thread young-generation GC time from parallel scavenging.

Node exposes the size knob:  (MiB). The Node docs note that the young generation is three times the semi-space size, so +1 MiB of semi-space adds 3 MiB of heap. Raising it can cut scavenges for allocation-heavy servers; benchmark before and after.

Old generation: concurrent mark-compact

- Marking finds everything reachable from the roots (stack, globals, handles). V8 does most of it concurrently on background threads while JavaScript runs, plus incremental steps on the main thread. Write barriers keep it correct while your code mutates the heap.- Sweeping frees dead objects' memory into free lists, concurrently.- Compaction moves objects out of fragmented pages, in parallel, during a pause.- Large objects (above a size threshold) live in a separate large-object space and are never moved.- Idle-time GC: the browser tells V8 when a frame finished early, and V8 uses the idle slice for GC work.

Concurrent marking and sweeping reduced pause times in heavy WebGL games by up to 50%, per the V8 team.

In Chrome, Blink's C++ DOM objects are managed by Oilpan () and traced together with the JavaScript heap, so a cycle between a DOM node and a JavaScript closure is still collectable.

Chapter 1 — Field extensions and degree

Terminology

- Extension — a pair of fields $F \subseteq E$, written $E/F$ ("$E$ over $F$"). $F$ is the base field.- Degree — $[E : F] = \dimF E$, the dimension of $E$ as a vector space over $F$. The extension is finite if the degree is finite.- Generated extension — for $\alpha \in E$, $F(\alpha)$ is the smallest subfield of $E$ containing $F$ and $\alpha$. Likewise $F(\alpha1, \dots, \alphan)$. An extension $F(\alpha)/F$ is simple and $\alpha$ is a primitive element.- Intermediate field — a field $K$ with $F \subseteq K \subseteq E$.

Examples: $[\mathbb{C} : \mathbb{R}] = 2$ with basis $1, i$. $[\mathbb{Q}(\sqrt2) : \mathbb{Q}] = 2$ with basis $1, \sqrt2$, since $\mathbb{Q}(\sqrt2) = \{a + b\sqrt2 : a, b \in \mathbb{Q}\}$ and $\sqrt2 \notin \mathbb{Q}$. $[\mathbb{R} : \mathbb{Q}]$ is infinite (a countable field cannot span the uncountable $\mathbb{R}$ with finitely many vectors). A field with $q$ elements that contains $\mathbb{F}p$ has $q = p^n$ where $n = [E : \mathbb{F}p]$, because an $n$-dimensional vector space over $\mathbb{F}p$ has $p^n$ elements.

The tower law

Theorem (tower law). If $F \subseteq K \subseteq E$ are fields, then

$$[E : F] = [E : K]\,[K : F],$$

in the sense that the left side is finite exactly when both factors are, and then equality holds.

Proof (finite case). Let $\alpha1, \dots, \alpham$ be a basis of $K$ over $F$ and $\beta1, \dots, \betan$ a basis of $E$ over $K$. The claim is that the $mn$ products $\alphai\betaj$ form a basis of $E$ over $F$.

- Spanning. Any $e \in E$ is $\sumj kj \betaj$ with $kj \in K$, and each $kj = \sumi f{ij}\alphai$ with $f{ij} \in F$. So $e = \sum{i,j} f{ij}\,\alphai\betaj$.- Independence. If $\sum{i,j} f{ij}\alphai\betaj = 0$, regroup as $\sumj \big(\sumi f{ij}\alphai\big)\betaj = 0$. The inner sums are in $K$ and the $\betaj$ are independent over $K$, so each inner sum is $0$. The $\alphai$ are independent over $F$, so every $f{ij} = 0$. ∎

Corollaries. (1) If $K$ is intermediate in a finite extension $E/F$, then $[K : F]$ divides $[E : F]$. (2) If $[E : F]$ is prime, there is no intermediate field other than $F$ and $E$. (3) If $\alpha \in E$, then $[F(\alpha) : F]$ divides $[E : F]$.

> Trick: most degree computations are "bound above by a tower, bound below by divisibility". If $[K : F] = 2$ and $[L : F] = 3$ are both inside $E$, then $6 \mid [E : F]$.

Chapter 2 — Algebraic elements and minimal polynomials

Terminology

- Algebraic — $\alpha \in E$ is algebraic over $F$ if $f(\alpha) = 0$ for some nonzero $f \in F[x]$. Otherwise $\alpha$ is transcendental over $F$.- Algebraic extension — every element of $E$ is algebraic over $F$.- Minimal polynomial — the monic polynomial $m\alpha \in F[x]$ of least degree with $m\alpha(\alpha) = 0$.

$\sqrt2$, $i$, $\sqrt[3]{2}$ and $e^{2\pi i/5}$ are algebraic over $\mathbb{Q}$. Hermite proved in 1873 that $e$ is transcendental and Lindemann in 1882 that $\pi$ is transcendental; both proofs are analytic and are not needed below.

The minimal polynomial

Theorem. Let $\alpha$ be algebraic over $F$. Then:

1. $m\alpha$ exists, is unique, and is irreducible over $F$;2. for $f \in F[x]$: $f(\alpha) = 0$ if and only if $m\alpha \mid f$;3. $F(\alpha) \cong F[x]/(m\alpha)$, so $[F(\alpha) : F] = \deg m\alpha$, with basis $1, \alpha, \dots, \alpha^{n-1}$ where $n = \deg m\alpha$.

Proof. Evaluation $\mathrm{ev}\alpha : F[x] \to E$, $f \mapsto f(\alpha)$, is a ring homomorphism. Its kernel $I$ is nonzero because $\alpha$ is algebraic, and $F[x]$ is a PID (post 04), so $I = (m)$ for a unique monic $m$; this $m$ has least degree among nonzero elements of $I$, so $m = m\alpha$, and statement 2 is "$f \in I \iff m\alpha \mid f$". The image of $\mathrm{ev}\alpha$ is a subring of the field $E$, hence a domain, so by the First Isomorphism Theorem $F[x]/(m\alpha)$ is a domain: $(m\alpha)$ is prime, so $m\alpha$ is irreducible. Then $(m\alpha)$ is maximal (post 04, Chapter 6), so the image $F[\alpha]$ is a field containing $F$ and $\alpha$; it is therefore $F(\alpha)$. The basis claim is the division algorithm: every class has a unique representative of degree $< n$. ∎

So to find $[F(\alpha) : F]$: find a polynomial with root $\alpha$ and prove it irreducible with the tests of post 04.

> Common pitfall: the minimal polynomial depends on the base field. $m{\sqrt2}$ over $\mathbb{Q}$ is $x^2 - 2$; over $\mathbb{R}$ it is $x - \sqrt2$.

Arithmetic in $\mathbb{Q}(\sqrt[3]{2})$. Let $a = \sqrt[3]{2}$, with $ma = x^3 - 2$ (Eisenstein at 2), so $[\mathbb{Q}(a) : \mathbb{Q}] = 3$ with basis $1, a, a^2$. To invert $1 + a$, use $(1 + a)(1 - a + a^2) = 1 + a^3 = 3$:

$$\frac{1}{1 + \sqrt[3]{2}} = \frac{1 - \sqrt[3]{2} + \sqrt[3]{4}}{3}.$$

Finite implies algebraic. If $[E : F] = n$ and $\alpha \in E$, the $n + 1$ elements $1, \alpha, \dots, \alpha^n$ are linearly dependent over $F$, and a dependence relation is a nonzero polynomial with root $\alpha$. Consequently, if $\alpha$ and $\beta$ are algebraic then $F(\alpha, \beta)$ is finite (tower law), so $\alpha \pm \beta$, $\alpha\beta$ and $\alpha/\beta$ are algebraic too: the algebraic numbers form a field.

Worked example: Q(√2, √3)

Degree. $[\mathbb{Q}(\sqrt2) : \mathbb{Q}] = 2$. Next, $\sqrt3 \notin \mathbb{Q}(\sqrt2)$: if $(a + b\sqrt2)^2 = 3$ with $a, b \in \mathbb{Q}$, then $a^2 + 2b^2 = 3$ and $2ab = 0$. $b = 0$ gives $a^2 = 3$ and $a = 0$ gives $b^2 = 3/2$, neither possible in $\mathbb{Q}$. So $x^2 - 3$ stays irreducible over $\mathbb{Q}(\sqrt2)$, and by the tower law

$$[\mathbb{Q}(\sqrt2, \sqrt3) : \mathbb{Q}] = [\mathbb{Q}(\sqrt2, \sqrt3) : \mathbb{Q}(\sqrt2)]\,[\mathbb{Q}(\sqrt2) : \mathbb{Q}] = 2 \cdot 2 = 4,$$

with basis $1, \sqrt2, \sqrt3, \sqrt6$ (products of the two bases, as in the proof of the tower law).

A primitive element. Let $\theta = \sqrt2 + \sqrt3$. Then $\theta^2 = 5 + 2\sqrt6$, so $(\theta^2 - 5)^2 = 24$, that is

$$\theta^4 - 10\theta^2 + 1 = 0.$$

Also $\theta^3 = 11\sqrt2 + 9\sqrt3$, which gives $\sqrt2 = (\theta^3 - 9\theta)/2$ and $\sqrt3 = (11\theta - \theta^3)/2$. So $\mathbb{Q}(\theta)$ contains $\sqrt2$ and $\sqrt3$, hence $\mathbb{Q}(\theta) = \mathbb{Q}(\sqrt2, \sqrt3)$ has degree 4. A degree-4 monic polynomial with root $\theta$ must then be the minimal polynomial: $m\theta = x^4 - 10x^2 + 1$, irreducible over $\mathbb{Q}$ (its four roots are $\pm\sqrt2 \pm \sqrt3$).

This is an instance of the primitive element theorem: every finite separable extension (Chapter 5; in particular every finite extension of $\mathbb{Q}$) is simple.

Chapter 3 — Ruler and compass

Start with the points $0$ and $1$ in the plane $\mathbb{C}$. A ruler draws the line through two constructed points; a compass draws a circle with a constructed centre through a constructed point. New points are intersections of lines and circles. A real number is constructible if it is a coordinate of a constructible point.

Key observation. If all points so far have coordinates in a field $K$, then:

- the intersection of two lines solves a linear system, so it has coordinates in $K$;- an intersection involving a circle solves a quadratic equation over $K$, so it has coordinates in $K$ or in some $K(\sqrt d)$ with $d \in K$, an extension of degree 2.

Theorem. If $\alpha$ is constructible, then $[\mathbb{Q}(\alpha) : \mathbb{Q}]$ is a power of 2.

Proof. By the observation, $\alpha$ lies in the top field of a tower $\mathbb{Q} = K0 \subset K1 \subset \cdots \subset Kr$ with each $[K{i+1} : Ki] = 2$. By the tower law $[Kr : \mathbb{Q}] = 2^r$, and $[\mathbb{Q}(\alpha) : \mathbb{Q}]$ divides it. ∎

Doubling the cube. A cube of volume 2 needs side $\sqrt[3]{2}$, whose minimal polynomial $x^3 - 2$ has degree 3. Not a power of 2, so impossible.

Trisecting 60°. A 60° angle is constructible (equilateral triangle). Trisecting it means constructing $c = \cos 20^\circ$. From $\cos 3\theta = 4\cos^3\theta - 3\cos\theta$ with $\theta = 20^\circ$ and $\cos 60^\circ = \tfrac12$:

$$4c^3 - 3c = \tfrac12 \quad\Longleftrightarrow\quad 8c^3 - 6c - 1 = 0.$$

By the rational root test, a rational root would be one of $\pm1, \pm\tfrac12, \pm\tfrac14, \pm\tfrac18$; substituting gives $1, -3, -3, 1, -\tfrac{19}{8}, \tfrac38, -\tfrac{111}{64}, -\tfrac{17}{64}$, never $0$. A cubic without rational roots is irreducible, so $[\mathbb{Q}(c) : \mathbb{Q}] = 3$ and the trisection is impossible. (Some angles, such as 90°, can be trisected; the theorem is that no method works for every angle.)

Squaring the circle. A square of area $\pi$ needs side $\sqrt\pi$. If $\sqrt\pi$ were constructible it would be algebraic, so $\pi$ would be algebraic, contradicting Lindemann.

> Watch out: "degree a power of 2" is necessary, not sufficient. The exact criterion is that the splitting field of the minimal polynomial has degree a power of 2. The Gauss–Wantzel theorem answers the polygon question: a regular $n$-gon is constructible if and only if $n$ is a power of 2 times a product of distinct Fermat primes $3, 5, 17, 257, 65537$.

Chapter 4 — Splitting fields and finite fields

Splitting fields

A splitting field of a nonconstant $f \in F[x]$ is an extension $E/F$ in which $f$ factors into linear factors, $f = c(x - \alpha1)\cdots(x - \alphan)$, and which is generated by the roots: $E = F(\alpha1, \dots, \alphan)$.

Theorem. Every nonconstant $f \in F[x]$ has a splitting field $E$, with $[E : F] \le n!$ where $n = \deg f$. Any two splitting fields of $f$ over $F$ are isomorphic by an isomorphism that fixes $F$.

(Existence: take an irreducible factor $p$ of $f$; in $F[x]/(p)$ it has a root (post 04), so $f$ gains a linear factor over an extension of degree $\le n$; repeat on the quotient, whose degree is $n - 1$. Uniqueness is proved by the same induction, extending an isomorphism one root at a time.)

Examples:

- $x^2 - 2$ over $\mathbb{Q}$: splitting field $\mathbb{Q}(\sqrt2)$, degree 2.- $x^4 - 10x^2 + 1$: roots $\pm\sqrt2 \pm \sqrt3$, splitting field $\mathbb{Q}(\sqrt2, \sqrt3)$, degree 4.- $x^3 - 2$: roots $\alpha$, $\alpha\omega$, $\alpha\omega^2$ with $\alpha = \sqrt[3]{2}$ and $\omega = e^{2\pi i/3}$, a root of $x^2 + x + 1$. The splitting field is $E = \mathbb{Q}(\alpha, \omega)$ (it contains $\omega = \alpha\omega/\alpha$). $[\mathbb{Q}(\alpha) : \mathbb{Q}] = 3$, and $\omega \notin \mathbb{Q}(\alpha) \subset \mathbb{R}$, so $[E : \mathbb{Q}(\alpha)] = 2$. Hence $[E : \mathbb{Q}] = 6 = 3!$, the maximum.

Finite fields

Let $E$ be a finite field. Its characteristic is a prime $p$ (post 04), so it contains $\mathbb{F}p$ and has $p^n$ elements, $n = [E : \mathbb{F}p]$.

Lemma (freshman's dream). In a commutative ring of characteristic $p$, $(a + b)^p = a^p + b^p$.

Proof. Expand with the binomial theorem. For $0 < k < p$, $\binom{p}{k} = \frac{p!}{k!(p-k)!}$ is divisible by $p$: $p$ divides the numerator but not the denominator. So all middle terms vanish. ∎

Hence the Frobenius map $\mathrm{Fr}(a) = a^p$ is a ring homomorphism. On a field it is injective (post 04: homomorphisms out of fields are injective), so on a finite field it is an automorphism, and it fixes exactly the elements of $\mathbb{F}p$ (the roots of $x^p - x$; there are at most $p$ of them, and all of $\mathbb{F}p$ qualifies by Fermat's little theorem from post 00).

Theorem (existence and uniqueness of finite fields). For every prime $p$ and $n \ge 1$ there is a field with $q = p^n$ elements, and any two such fields are isomorphic. It is written $\mathbb{F}q$.

Proof. Existence. Let $E$ be a splitting field of $g = x^q - x$ over $\mathbb{F}p$, and $S$ the set of roots of $g$ in $E$. The derivative $g' = qx^{q-1} - 1 = -1$ has no common root with $g$, so the roots are distinct and $|S| = q$. $S$ is a subfield: if $a^q = a$ and $b^q = b$, then $(a + b)^q = a^q + b^q = a + b$ (apply the lemma $n$ times), $(ab)^q = ab$, and $(a^{-1})^q = a^{-1}$. A subfield containing all roots is the whole splitting field, so $E = S$ has $q$ elements.

Uniqueness. In any field $K$ with $q$ elements, the multiplicative group has order $q - 1$, so $a^{q-1} = 1$ for $a \ne 0$ by Lagrange, and $a^q = a$ for all $a$. So $K$ consists of the $q$ roots of $x^q - x$, and is a splitting field of $x^q - x$ over $\mathbb{F}p$. Splitting fields are unique up to isomorphism. ∎

Two further facts, stated without proof: the multiplicative group $\mathbb{F}q^\times$ is cyclic (post 04's $\mathbb{F}8$ table showed a generator), and $\mathbb{F}{p^d}$ sits inside $\mathbb{F}{p^n}$ exactly when $d \mid n$.

Worked example. Over $\mathbb{F}2$:

$$\begin{aligned}x^4 - x &= x\,(x + 1)\,(x^2 + x + 1), \\x^8 - x &= x\,(x + 1)\,(x^3 + x + 1)\,(x^3 + x^2 + 1).\end{aligned}$$

The first line lists the minimal polynomials of the 4 elements of $\mathbb{F}4$; the second those of the 8 elements of $\mathbb{F}8$. The two cubics are the two irreducible cubics over $\mathbb{F}2$, each with three roots in $\mathbb{F}8$. No quadratic appears in the second line, matching $2 \nmid 3$: $\mathbb{F}4 \not\subseteq \mathbb{F}8$.

Chapter 5 — Galois extensions and the Galois group

Terminology

- $F$-automorphism of $E$ — a field automorphism $\sigma : E \to E$ with $\sigma(a) = a$ for every $a \in F$. They form a group $\operatorname{Aut}(E/F)$.- Fixed field — for a subgroup $H \le \operatorname{Aut}(E)$, $E^H = \{ e \in E : \sigma(e) = e \text{ for all } \sigma \in H \}$.- Separable polynomial — one with no repeated root in its splitting field. An algebraic extension is separable if every minimal polynomial is separable.- Normal extension — an algebraic $E/F$ such that every irreducible polynomial in $F[x]$ with one root in $E$ splits completely in $E$.- Galois extension — a finite extension that is normal and separable. Its Galois group is $\operatorname{Gal}(E/F) = \operatorname{Aut}(E/F)$.- Galois group of a polynomial — $\operatorname{Gal}(E/F)$ for $E$ a splitting field of the (separable) polynomial.

Separability is automatic in the cases you meet most. Over a field of characteristic 0, and over any finite field, every irreducible polynomial is separable. (An irreducible $f$ has a repeated root only if $\gcd(f, f') \ne 1$, which forces $f' = 0$; in characteristic 0 that is impossible for nonconstant $f$.) The standard inseparable example is $x^p - t$ over the field $\mathbb{F}p(t)$ of rational functions: it is irreducible (Eisenstein at the prime $t$), but over its splitting field it equals $(x - t^{1/p})^p$.

Automorphisms permute roots

Lemma. If $f \in F[x]$, $\alpha \in E$ is a root of $f$, and $\sigma \in \operatorname{Aut}(E/F)$, then $\sigma(\alpha)$ is a root of $f$.

Proof. If $f = \sum ck x^k$ with $ck \in F$, then $f(\sigma(\alpha)) = \sum ck \sigma(\alpha)^k = \sigma\big(\sum ck\alpha^k\big) = \sigma(0) = 0$, since $\sigma$ fixes each $ck$. ∎

So if $E = F(\alpha1, \dots, \alphan)$ is a splitting field of $f$, an $F$-automorphism is determined by how it permutes $\alpha1, \dots, \alphan$, and $\operatorname{Aut}(E/F)$ is (isomorphic to) a subgroup of $Sn$, an action on the roots in the sense of post 03.

Theorem (characterisations of Galois extensions). For a finite extension $E/F$ the following are equivalent:

1. $E/F$ is Galois (normal and separable);2. $E$ is the splitting field over $F$ of a separable polynomial;3. $\lvert\operatorname{Aut}(E/F)\rvert = [E : F]$;4. the fixed field of $\operatorname{Aut}(E/F)$ is exactly $F$.

In general $\lvert\operatorname{Aut}(E/F)\rvert \le [E : F]$ and equality is what "Galois" means in practice.

Examples.

- $\operatorname{Gal}(\mathbb{C}/\mathbb{R}) = \{\mathrm{id}, \text{complex conjugation}\} \cong \mathbb{Z}/2\mathbb{Z}$.- $\mathbb{Q}(\sqrt[3]{2})/\mathbb{Q}$ is not Galois. An automorphism must send $\sqrt[3]{2}$ to a root of $x^3 - 2$ inside $\mathbb{Q}(\sqrt[3]{2}) \subset \mathbb{R}$, and the only real root is $\sqrt[3]{2}$ itself. So $\operatorname{Aut}$ is trivial, of order $1 < 3$. It fails normality: $x^3 - 2$ has one root in the field but does not split there.- $\operatorname{Gal}(\mathbb{F}{p^n}/\mathbb{F}p)$ is cyclic of order $n$, generated by Frobenius. ($\mathrm{Fr}^k$ fixes exactly the roots of $x^{p^k} - x$, so $\mathrm{Fr}$ has order exactly $n$; and the group has order $[\mathbb{F}{p^n} : \mathbb{F}p] = n$ because $\mathbb{F}{p^n}$ is the splitting field of the separable $x^{p^n} - x$.)

Chapter 6 — The Fundamental Theorem of Galois Theory

Theorem (Fundamental Theorem of Galois Theory). Let $E/F$ be a finite Galois extension with group $G = \operatorname{Gal}(E/F)$. Then the maps

$$H \longmapsto E^H \qquad\text{and}\qquad K \longmapsto \operatorname{Gal}(E/K)$$

are mutually inverse bijections between subgroups $H \le G$ and intermediate fields $F \subseteq K \subseteq E$, and:

1. they reverse inclusion: $H1 \le H2$ if and only if $E^{H1} \supseteq E^{H2}$;2. degrees match indices: $[E : E^H] = |H|$ and $[E^H : F] = [G : H]$;3. $K/F$ is Galois if and only if $\operatorname{Gal}(E/K)$ is a normal subgroup of $G$, and then $\operatorname{Gal}(K/F) \cong G / \operatorname{Gal}(E/K)$.

So the lattice of intermediate fields is the lattice of subgroups turned upside down: the big field $E$ matches the trivial group, the base $F$ matches all of $G$. Part 3 is where normal subgroups and quotient groups (post 02) acquire their original meaning.

Worked example 1: Q(√2, √3)

$E = \mathbb{Q}(\sqrt2, \sqrt3)$ is the splitting field of the separable $(x^2 - 2)(x^2 - 3)$, so it is Galois of degree 4 and $G$ has 4 elements. Each automorphism sends $\sqrt2 \mapsto \pm\sqrt2$ and $\sqrt3 \mapsto \pm\sqrt3$, and all four sign choices occur. Let

$$\sigma : \sqrt2 \mapsto -\sqrt2,\ \sqrt3 \mapsto \sqrt3, \qquad \tau : \sqrt2 \mapsto \sqrt2,\ \sqrt3 \mapsto -\sqrt3.$$

Each has order 2 and they commute, so $G = \{\mathrm{id}, \sigma, \tau, \sigma\tau\} \cong \mathbb{Z}/2 \times \mathbb{Z}/2$. The subgroups and their fixed fields:

| Subgroup | Order | Fixed field | Degree over $\mathbb{Q}$ ||---|---|---|---|| $\{\mathrm{id}\}$ | 1 | $\mathbb{Q}(\sqrt2, \sqrt3)$ | 4 || $\langle\sigma\rangle$ | 2 | $\mathbb{Q}(\sqrt3)$ | 2 || $\langle\tau\rangle$ | 2 | $\mathbb{Q}(\sqrt2)$ | 2 || $\langle\sigma\tau\rangle$ | 2 | $\mathbb{Q}(\sqrt6)$ | 2 || $G$ | 4 | $\mathbb{Q}$ | 1 |

($\sigma\tau(\sqrt6) = (-\sqrt2)(-\sqrt3) = \sqrt6$.) By the theorem these are all the intermediate fields: exactly three quadratic subfields, which is not obvious without Galois theory. $G$ is abelian, so every subgroup is normal and every intermediate field is Galois over $\mathbb{Q}$.

Worked example 2: the splitting field of x³ − 2

$E = \mathbb{Q}(\alpha, \omega)$ with $\alpha = \sqrt[3]{2}$, of degree 6 (Chapter 4). It is Galois, so $|G| = 6$, and $G$ acts on the three roots $\alpha, \alpha\omega, \alpha\omega^2$, so $G$ is a subgroup of $S3$ of order 6: $G \cong S3$. Concretely an automorphism is fixed by $\alpha \mapsto \alpha\omega^a$ ($a \in \{0, 1, 2\}$) and $\omega \mapsto \omega$ or $\omega^2$. Let

$$\sigma : \alpha \mapsto \alpha\omega,\ \omega \mapsto \omega \quad(\text{order } 3), \qquad \tau : \alpha \mapsto \alpha,\ \omega \mapsto \omega^2 \quad(\text{complex conjugation, order } 2).$$

Composing right to left (apply $\tau$ first in $\sigma\tau$): $\sigma\tau$ sends $\alpha \mapsto \alpha\omega$ and $\omega \mapsto \omega^2$, so $\sigma\tau(\alpha\omega^2) = \alpha\omega \cdot \omega^4 = \alpha\omega^2$. Similarly $\sigma^2\tau$ fixes $\alpha\omega$. The six subgroups of $S3$ and their fixed fields:

| Subgroup | Order | Normal? | Fixed field | Degree over $\mathbb{Q}$ ||---|---|---|---|---|| $\{\mathrm{id}\}$ | 1 | yes | $\mathbb{Q}(\alpha, \omega)$ | 6 || $\langle\tau\rangle$ | 2 | no | $\mathbb{Q}(\alpha)$ | 3 || $\langle\sigma\tau\rangle$ | 2 | no | $\mathbb{Q}(\alpha\omega^2)$ | 3 || $\langle\sigma^2\tau\rangle$ | 2 | no | $\mathbb{Q}(\alpha\omega)$ | 3 || $\langle\sigma\rangle = A3$ | 3 | yes | $\mathbb{Q}(\omega)$ | 2 || $S3$ | 6 | yes | $\mathbb{Q}$ | 1 |

Each order-2 subgroup fixes one real or complex cube root, so its fixed field contains that root; the degree count $[G : H] = 3 = [\mathbb{Q}(\alpha\omega^k) : \mathbb{Q}]$ makes it equal to $\mathbb{Q}(\alpha\omega^k)$. $\sigma$ fixes $\omega$, and $[G : \langle\sigma\rangle] = 2 = [\mathbb{Q}(\omega) : \mathbb{Q}]$.

Part 3 of the theorem, checked on this example: $A3 = \langle\sigma\rangle$ is normal, and $\mathbb{Q}(\omega)$ is Galois over $\mathbb{Q}$ (it is the splitting field of $x^2 + x + 1$), with $\operatorname{Gal}(\mathbb{Q}(\omega)/\mathbb{Q}) \cong S3/A3 \cong \mathbb{Z}/2$. The three subgroups of order 2 are not normal (they are conjugate, like the three Sylow 2-subgroups of $S3$ in post 03), and correspondingly $\mathbb{Q}(\sqrt[3]{2})$ and its two conjugate fields are not Galois over $\mathbb{Q}$.

> Common pitfall: the correspondence reverses order. A bigger subgroup fixes more conditions and so has a smaller fixed field. Draw the two lattices with $E$ at the top and $\{\mathrm{id}\}$ at the top.

Chapter 7 — Solvable groups and the quintic

Solvable groups

A group $G$ is solvable if there is a chain of subgroups

$$\{e\} = G0 \trianglelefteq G1 \trianglelefteq \cdots \trianglelefteq Gk = G$$

with each $Gi$ normal in $G{i+1}$ and each quotient $G{i+1}/Gi$ abelian.

- Abelian groups are solvable ($k = 1$).- $S3$: $\{e\} \trianglelefteq A3 \trianglelefteq S3$ with quotients $\mathbb{Z}/3$ and $\mathbb{Z}/2$.- $S4$: $\{e\} \trianglelefteq V4 \trianglelefteq A4 \trianglelefteq S4$ with quotients $\mathbb{Z}/2 \times \mathbb{Z}/2$, $\mathbb{Z}/3$, $\mathbb{Z}/2$. So every subgroup of $S4$ is solvable too (subgroups and quotients of solvable groups are solvable).- $S5$ is not solvable. Its only normal subgroups are $\{e\}$, $A5$, $S5$, and $A5$ is simple and non-abelian (post 02). A chain would have to pass through $A5$, and the step below $A5$ would need a normal subgroup of $A5$ with abelian quotient; the only candidates are $A5$ itself (quotient trivial, no progress) and $\{e\}$ (quotient $A5$, not abelian). Equivalently, the commutator subgroup of $A5$ is $A5$, so the derived series $S5 \supset A5 \supset A5 \supset \cdots$ never reaches $\{e\}$.

Radicals

A polynomial $f \in \mathbb{Q}[x]$ is solvable by radicals if its roots can be written starting from rational numbers using $+, -, \times, \div$ and $k$-th roots. The quadratic formula shows this for degree 2; Cardano's and Ferrari's formulas do it for degrees 3 and 4.

Theorem (Galois, characteristic 0). $f$ is solvable by radicals if and only if its Galois group is solvable.

(Idea of "only if": adjoining a $k$-th root to a field that already contains the $k$-th roots of unity gives a Galois extension with cyclic group; adjoining roots of unity gives an abelian group. A tower of such steps gives, through part 3 of the Fundamental Theorem, a chain of normal subgroups with abelian quotients.)

Since $S4$ is solvable and the Galois group of a degree-$n$ polynomial embeds in $Sn$, every polynomial of degree $\le 4$ is solvable by radicals. The Abel–Ruffini theorem says the general quintic is not: the generic polynomial $x^5 + a4x^4 + \cdots + a0$ with independent indeterminate coefficients has Galois group $S5$ over $\mathbb{Q}(a0, \dots, a4)$, which is not solvable, so there is no formula in radicals valid for all quintics. Galois theory gives more: specific quintics with rational coefficients have unsolvable roots.

A concrete unsolvable quintic

Lemma. Let $p$ be prime and $f \in \mathbb{Q}[x]$ irreducible of degree $p$ with exactly two non-real roots. Then $\operatorname{Gal}(f) \cong Sp$.

Proof. View $G = \operatorname{Gal}(f)$ as a subgroup of $Sp$ acting on the $p$ roots. For a root $\alpha$, $[\mathbb{Q}(\alpha) : \mathbb{Q}] = p$ divides $[E : \mathbb{Q}] = |G|$, so by Cauchy's theorem (post 03) $G$ has an element of order $p$; in $Sp$ the elements of order $p$ are the $p$-cycles. Complex conjugation restricts to an element of $G$ that swaps the two non-real roots and fixes the $p - 2$ real ones: a transposition. For prime $p$, a $p$-cycle and a transposition generate all of $Sp$. ∎

Theorem. $f(x) = x^5 - 4x + 2$ is not solvable by radicals over $\mathbb{Q}$.

Proof. Irreducible: Eisenstein at $p = 2$ ($2 \mid -4$, $2 \mid 2$, $4 \nmid 2$, leading coefficient 1).

Exactly three real roots: $f'(x) = 5x^4 - 4$ vanishes only at $x = \pm c$ with $c = (4/5)^{1/4} \approx 0.9457$. So $f$ increases, then decreases on $[-c, c]$, then increases. The local maximum $f(-c) \approx 5.03 > 0$ and the local minimum $f(c) \approx -1.03 < 0$, while $f \to -\infty$ as $x \to -\infty$ and $f \to +\infty$ as $x \to +\infty$. So $f$ crosses zero once on each of the three monotone pieces: three real roots, approximately $-1.5185$, $0.5085$ and $1.2436$, and the other two roots are a complex-conjugate pair.

By the lemma with $p = 5$, $\operatorname{Gal}(f) \cong S5$, which is not solvable. By Galois's theorem, $f$ is not solvable by radicals. ∎

> Watch out: "not solvable by radicals" does not mean the roots are hard to compute. Numerically they are easy (the values above). It means there is no finite expression in $+, -, \times, \div, \sqrt[k]{\ }$ for them.

Practice Exercises

1. Find $[\mathbb{Q}(\sqrt2, \sqrt[3]{2}) : \mathbb{Q}]$.

<details><summary>Solution</summary>

$\mathbb{Q}(\sqrt2)$ has degree 2 and $\mathbb{Q}(\sqrt[3]{2})$ has degree 3, both intermediate, so 2 and 3 divide the degree, and so does 6. On the other hand $[\mathbb{Q}(\sqrt2, \sqrt[3]{2}) : \mathbb{Q}(\sqrt[3]{2})] \le 2$ (root of $x^2 - 2$), so the degree is at most $2 \cdot 3 = 6$. Hence it is exactly 6.

</details>

2. Find the minimal polynomial of $\sqrt2 + i$ over $\mathbb{Q}$.

<details><summary>Solution</summary>

Let $\theta = \sqrt2 + i$. Then $\theta^2 = 1 + 2\sqrt2\,i$, so $(\theta^2 - 1)^2 = -8$, giving $\theta^4 - 2\theta^2 + 9 = 0$. As in the $\sqrt2 + \sqrt3$ example, $\mathbb{Q}(\theta) = \mathbb{Q}(\sqrt2, i)$, which has degree 4 ($i \notin \mathbb{Q}(\sqrt2) \subset \mathbb{R}$). So $m\theta = x^4 - 2x^2 + 9$.

</details>

3. Show that the regular 7-gon is not constructible, using that $2\cos(2\pi/7)$ is a root of $x^3 + x^2 - 2x - 1$.

<details><summary>Solution</summary>

Rational roots could only be $\pm 1$, which give $-1$ and $1$, so the cubic has no rational root and is irreducible. Then $[\mathbb{Q}(2\cos(2\pi/7)) : \mathbb{Q}] = 3$, not a power of 2, so $\cos(2\pi/7)$ is not constructible, and neither is the 7-gon. (Consistent with Gauss–Wantzel: 7 is prime but not a Fermat prime.)

</details>

4. List all subfields of $\mathbb{F}{64}$ and draw their inclusions. What is $\operatorname{Gal}(\mathbb{F}{64}/\mathbb{F}2)$?

<details><summary>Solution</summary>

$64 = 2^6$ and the divisors of 6 are 1, 2, 3, 6, so the subfields are $\mathbb{F}2, \mathbb{F}4, \mathbb{F}8, \mathbb{F}{64}$. Inclusions: $\mathbb{F}2 \subset \mathbb{F}4 \subset \mathbb{F}{64}$ and $\mathbb{F}2 \subset \mathbb{F}8 \subset \mathbb{F}{64}$, while $\mathbb{F}4 \not\subseteq \mathbb{F}8$. The Galois group is cyclic of order 6, generated by Frobenius; its subgroups (orders 1, 2, 3, 6) match the subfields $\mathbb{F}{64}, \mathbb{F}8, \mathbb{F}4, \mathbb{F}2$ in that order.

</details>

5. In $\mathbb{Q}(\sqrt2, \sqrt3)$, which automorphism fixes $\sqrt6$, and what is the fixed field of $\{\mathrm{id}, \sigma\}$? Why does the Fundamental Theorem guarantee that $\mathbb{Q}(\sqrt2 + \sqrt3)$ is the whole field without computing $\theta^3$?

<details><summary>Solution</summary>

$\sigma\tau$ fixes $\sqrt6$ (both signs flip). $\sigma$ fixes $\sqrt3$, so $E^{\langle\sigma\rangle} \supseteq \mathbb{Q}(\sqrt3)$, and both have degree 2, so they are equal. For $\theta = \sqrt2 + \sqrt3$: the non-identity automorphisms send $\theta$ to $-\sqrt2 + \sqrt3$, $\sqrt2 - \sqrt3$, $-\sqrt2 - \sqrt3$, all different from $\theta$. So only the trivial subgroup fixes $\theta$, and $\mathbb{Q}(\theta)$ corresponds to $\{\mathrm{id}\}$, i.e. it is all of $E$.

</details>

6. Explain why every polynomial of degree at most 4 over $\mathbb{Q}$ is solvable by radicals, but this argument says nothing about degree 5.

<details><summary>Solution</summary>

The Galois group of a degree-$n$ polynomial is a subgroup of $Sn$. For $n \le 4$, $Sn$ is solvable (chains above), and subgroups of solvable groups are solvable, so Galois's theorem applies. For $n = 5$ the group may be a solvable subgroup of $S5$ (for example $x^5 - 2$ is solvable by radicals, since $\sqrt[5]{2}$ is already a radical), or all of $S5$, as for $x^5 - 4x + 2$. The degree alone does not decide.

</details>

Chapter 1 — Pick the right data store

Quick decision tree:

The biggest mistake is choosing by familiarity rather than fit. Postgres on RDS is a fine default; DynamoDB is a much better fit for high-write key-value patterns. Picking wrong locks you into a costly migration later.

Chapter 2 — RDS

RDS (Relational Database Service) runs PostgreSQL, MySQL, MariaDB, Oracle, or SQL Server on EC2 + EBS, managed by AWS. You get:

- Daily automated backups + point-in-time recovery (1-35 days).- Multi-AZ failover (synchronous replica in another AZ; automatic promotion).- Up to 15 read replicas for read scaling.- Maintenance windows for patching.- IAM authentication, KMS encryption at rest, TLS in transit.

What you give up: full OS access. You can't run  on an RDS host or install custom Postgres extensions outside AWS's approved list.

Engines and versions

| Engine | Typical use ||--------|-------------|| Postgres | most modern apps; richest feature set || MySQL | legacy or compatibility || MariaDB | MySQL drop-in || Oracle / SQL Server | licensed workloads |

Pick the most recent LTS major version for production unless a specific older feature is needed.

Multi-AZ vs read replica

| Feature | Multi-AZ | Read replica ||---------|----------|---------------|| Purpose | HA: automatic failover | Read scaling || Replication | synchronous | asynchronous || Visible? | invisible standby | endpoint queryable || Failover time | 60-120 sec | manual promote || Cost | 2× the instance | 1× per replica |

Production = always Multi-AZ. Heavy-read workloads = also one or more read replicas.

Backups

- Automated snapshots — every day, retained 1-35 days, free for active DBs.- Manual snapshots — kept until you delete them.- Point-in-time restore — recover to any second within the retention window (writes go to transaction logs in S3).

> Trick: RDS lets you spin up a new DB from a snapshot in seconds for testing. Great for "show me prod data from yesterday in a sandbox" workflows. Just remember to delete it after.

Chapter 3 — Aurora

Aurora is AWS's cloud-native rewrite of MySQL and PostgreSQL. Compatible at the wire level, but with a custom storage engine that:

- Replicates data across 6 copies in 3 AZs automatically.- Keeps working for writes after losing up to 2 copies, and for reads after losing up to 3.- Auto-grows storage in 10 GB chunks up to 128 TB.- Provides up to 15 read replicas that share the same storage layer (lag in single-digit ms).

Aurora vs RDS

| Trait | RDS | Aurora ||-------|-----|--------|| Engines | many | Postgres / MySQL compatible only || Storage | EBS (provisioned) | shared cluster volume, auto-grow || Throughput vs vanilla | baseline | up to 3-5× MySQL, 2-3× Postgres || Cost | cheaper at small scale | costlier baseline, cheaper at scale || Best for | low-traffic apps, small teams | production OLTP at scale, SaaS |

Aurora Serverless V2

Aurora Serverless V2 scales the compute capacity ( — Aurora Capacity Units) up and down with load, in fractions of an ACU. Used to be best for unpredictable workloads; in 2026 it's mature enough to be a viable default for new Aurora clusters.

Chapter 4 — DynamoDB

DynamoDB is a fully managed NoSQL key-value + document store. Single-digit millisecond latency at any scale. No servers to provision, no AZ design — AWS handles all of it.

Trade-offs vs SQL:- No joins (denormalise instead).- Limited transactional support (single-region transactions OK; multi-region eventual).- Query patterns must be designed first — DynamoDB tables are not "queried like SQL"; you access by key.

Table schema

A table has:- A partition key (mandatory) — determines which physical partition stores the item.- An optional sort key — orders items within a partition.- Items are JSON-like documents with arbitrary attributes.- Secondary indexes (Global or Local) let you query by other attributes.

Capacity modes

| Mode | When ||------|------|| On-demand | unpredictable traffic, dev, low-traffic | pay per request || Provisioned + auto-scaling | steady traffic with daily curve | cheaper at predictable scale |

Start with on-demand; switch to provisioned once you have a stable traffic profile and the cost gap matters.

Streams + change capture

DynamoDB Streams publishes every item-level change for 24 hours. Wire to Lambda for:- replication to another store (S3, OpenSearch, another region),- audit trails,- triggering downstream workflows.

Single-table design

Power users put multiple entity types in one table with carefully designed key patterns. Higher learning curve but lower cost and faster queries. Worth reading Alex DeBrie's The DynamoDB Book when ready.

Chapter 5 — ElastiCache

ElastiCache runs Redis or Memcached as a managed service. Two flavours:

| Engine | Best for ||--------|----------|| Redis (ElastiCache for Redis) | rich data structures, pub/sub, persistence, replicas, cluster mode | most use cases || Memcached | pure cache, multi-threaded, simpler | rarely chosen now |

Modern AWS also offers MemoryDB for Redis — Redis-compatible with multi-AZ durable storage (effectively Redis-as-a-database). Use when you need Redis semantics plus durability.

Cache patterns

- Cache-aside (lazy loading) — app reads from cache first; on miss, query DB and populate.- Write-through — every DB write also updates the cache.- TTL eviction — auto-expire entries after a duration.- Session store — sticky-session alternative for stateless app servers.- Rate limiting / leaderboards — natural Redis use cases.

> Trick: when adding a cache to fix a slow query, set a short TTL (60-300 sec) at first. Lets you measure hit rate and roll back without stale-data risk. Expand TTL once you're confident the data tolerates it.

Chapter 6 — Choosing between RDS, Aurora, DynamoDB

| Scenario | Pick ||----------|------|| Small SaaS, < 1k req/s, SQL | RDS Postgres Multi-AZ || Larger SaaS, 5k+ req/s, SQL | Aurora Postgres || Mobile app backend, key-value | DynamoDB on-demand || User-session store | ElastiCache Redis || Time-series IoT writes | DynamoDB or TimeStream || Reporting / analytics | Redshift or S3 + Athena || Search | OpenSearch || Caching API responses | ElastiCache Redis |

There is no universal best. Match the access pattern.

Chapter 7 — Costs and gotchas

| Item | Typical cost driver | Saver ||------|---------------------|-------|| RDS / Aurora instance | per-hour by class | reserved instance / 1-3 yr commit || RDS storage | per GB-month gp3 | rightsize; gp3 not gp2 || RDS backup beyond DB size | per GB-month | shorter retention or move old to S3 || RDS Multi-AZ | 2× the instance | required for production || DynamoDB on-demand | per request (read + write units) | provisioned + auto-scale at scale || DynamoDB storage | per GB-month | TTL old items || DynamoDB GSI | extra reads/writes | only create needed indexes || ElastiCache nodes | per-hour by class | reserved nodes; right-size || Cross-AZ traffic | per GB | keep app + DB in same AZ where safe |

Watch out: turning on performance insights, enhanced monitoring, automated backups at long retention, and many secondary indexes adds line items that double a small DB's bill quietly.

Chapter 8 — Migration shortcuts

- DMS (Database Migration Service) — continuous replication from one DB to another (on-prem → RDS, MySQL → Aurora, RDS → DynamoDB).- AWS Schema Conversion Tool (SCT) — convert schemas + stored procedures between engines.-  /  still work fine for small one-shot loads.

For production cut-overs, the DMS "ongoing-replication then cut" pattern is the safe playbook.

This is the textbook "3-tier" shape — load balancer in front, Auto Scaling Group across AZs, optional managed data behind. The patterns here form the spine of nearly every classical AWS workload.

Learning Outcome

- Pick between ALB, NLB, GLB, and the legacy CLB.- Configure target groups with sane health checks.- Build an Auto Scaling Group across multiple AZs.- Write scaling policies: target tracking, step, scheduled.- Apply the "warm pool" + "instance refresh" pattern for safe rollouts.- Combine ALB + ASG + private subnets into the textbook 3-tier reference architecture.

Chapter 1 — The load balancer family

| LB | Layer | Protocols | When ||----|-------|-----------|------|| Application LB (ALB) | 7 | HTTP, HTTPS, WebSocket, gRPC | web APIs, microservices, host/path routing || Network LB (NLB) | 4 | TCP, UDP, TLS | extreme throughput, static IP, non-HTTP || Gateway LB (GLB) | 3 | IP via GENEVE | inserting 3rd-party network appliances || Classic LB (CLB) | 4 + 7 (legacy) | HTTP, TCP | only existing deployments |

Most workloads use ALB. Reach for NLB when you need raw TCP, sub-millisecond latency, or a static IP that doesn't change. GLB is niche (firewall/IDS vendors). CLB is deprecated for new use.

ALB headline features

- Host-based routing —  → service A,  → service B.- Path-based routing —  → service A,  → service B.- Header / query-param matching in listener rules.- WebSocket and gRPC support.- TLS termination with certs from ACM.- AWS WAF integration.- Cognito / OIDC authentication at the listener.- Sticky sessions via cookies.

NLB headline features

- Static per-AZ IP (or your own Elastic IPs).- Millions of requests/sec with sub-millisecond added latency.- Preserves the client source IP at the backend.- Supports the  protocol for backends that want the original peer IP.

Chapter 2 — Target groups

A target group is a registered list of "things that can serve traffic". A listener forwards based on rules to one or more target groups.

Target types:- instance — by EC2 instance ID- ip — for ECS tasks, on-prem hosts via Direct Connect- lambda — invoke a Lambda per request (ALB only)- alb — chain an ALB behind an NLB (advanced)

Health checks (the make-or-break setting)

| Setting | Reasonable default ||---------|---------------------|| Protocol | HTTP / HTTPS || Path |  (your app implements) || Interval | 15-30 sec || Timeout | 5 sec || Healthy threshold | 2 || Unhealthy threshold | 2-3 |

Watch out: an overly aggressive check (1 second, 1 failure → unhealthy) marks healthy targets bad during minor blips. An overly relaxed check (60 seconds, 5 failures) lets bad targets serve traffic for minutes.

Three common health-check mistakes

1. The  endpoint also checks a downstream DB → a single DB hiccup marks every target unhealthy → outage. Make  a shallow liveness check; add  for dependency health.2. The endpoint requires auth. The LB has no credentials → 401 → all targets appear unhealthy.3. The endpoint runs an expensive query. ALB poll × target count multiplies the load.

Chapter 3 — Listeners and routing rules

Common patterns:

- HTTP → HTTPS redirect — a port 80 listener with a single redirect rule to 443.- Canary — header/cookie-based routing to a small target group running a new version.- Maintenance page — fixed-response rule returning a static 503 + HTML.- Weighted target groups — split a percentage of traffic for blue/green.

Chapter 4 — Auto Scaling Group (ASG)

An ASG maintains a fleet of EC2 instances at a target capacity, replaces unhealthy ones automatically, and scales up/down based on policies.

Anatomy

- Launch template — AMI, instance type, key, SGs, user data. (Replaces older "launch configuration".)- Min / Desired / Max — capacity bounds.- VPC zone identifier — list of subnets (one per AZ).- Health-check type —  (instance status) or  (target-group health). Always pick  if the ASG is behind a load balancer.- Target groups — the ASG registers / deregisters instances automatically as they come and go.

A minimal ASG

runs on first boot — install your app, fetch config, register with discovery.

Chapter 5 — Scaling policies

Target tracking (start here)

Pick a metric and a target; AWS adds/removes instances to keep the metric there.

- "Average CPU = 50%" → scale out when > 50, in when < 50.- "ALB requests per target = 200" → scale to meet load.

Step scaling

Trigger at thresholds; add/remove a configurable count per step. Use when target tracking can't express the logic — e.g., asymmetric scale-out vs scale-in speeds.

Scheduled

Predictable patterns deserve scheduled scaling — flash sale, market open, weekday morning ramp.

Trick: schedule warm-up 15 minutes before a known spike. EC2 + ASG instances take 1-3 minutes from request to "in service".

Chapter 6 — Cooldowns, warm pools, instance refresh

Cooldown

A waiting period after a scaling action before evaluating again — prevents oscillation when metrics dip slightly post-action.

Warm pool

A pool of pre-initialised but stopped instances. When the ASG needs to scale, it starts (rather than provisions) one — seconds vs minutes. Cost: EBS storage of the warm instances.

Instance refresh

When you publish a new launch-template version (new AMI, new user-data),  rolls existing instances out in batches.

Pair with ALB weighted target groups or canary listener rules for safe rollouts.

Chapter 7 — The textbook 3-tier reference

Tier rules:- ALB lives in public subnets across ≥ 2 AZs.- App tier lives in private subnets across the same AZs.- DB tier lives in isolated subnets, accessible only from the app SG.- Each tier's security group only accepts traffic from the tier above's SG.- Outbound from app tier to internet via NAT (only for pulling packages, calling external APIs).

This shape survives:- a single instance failure (ASG replaces it)- a single AZ failure (other AZs absorb traffic)- a deploy with bad code (canary catches it; instance refresh rolls back)- a traffic spike (ASG scales out)

Chapter 8 — Cost considerations

| Item | Approx (us-east-1) ||------|---------------------|| ALB | USD 16 / month base + LCU hours || NLB | USD 16 / month + NLCU || Data transfer out | USD 0.09/GB after 100 GB free || EC2 t3.micro | USD 7.50 / month at 24/7 on-demand || NAT gateway | USD 32 / month + USD 0.045 / GB processed || RDS db.t4g.micro multi-AZ | USD 25-30 / month |

A minimal 3-tier shop: ASG of 2 × t3.micro + ALB + RDS Multi-AZ + 1 NAT ≈ USD 100 / month before traffic. Per-AZ NATs add USD 32 each for HA.

Watch out: ALB LCU (Load Balancer Capacity Units) is metered on connections, requests, processed bytes, and rule evaluations. A high-traffic ALB can cost more than the EC2 behind it.

Chapter 9 — Beyond EC2 + ASG

Modern compute alternatives to consider for the app tier:

- ECS Fargate — containers without managing EC2 hosts.- EKS — Kubernetes managed control plane.- App Runner — push a container, AWS does the rest.- Lambda behind ALB — short-lived, infrequent endpoints (Post 05).

EC2 + ASG remains right when you need OS access, GPU, NVMe, or want the lowest level of abstraction. Otherwise consider going up the stack — Post 05 covers serverless, future posts cover containers.
