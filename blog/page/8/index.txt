PostgreSQL implements that promise with MVCC — multi-version concurrency control — where writers never block readers and readers never block writers, because every row can exist in several versions at once. Chapter 1 — ACID, stated precisely

Terminology

- Atomicity — a transaction's effects are all applied or none are. PostgreSQL gets this from the commit record in the WAL: until the commit record is durable, the transaction's tuples are simply invisible.- Consistency — the database moves from one state satisfying all declared constraints to another. This is the application's and the schema's property; the database enforces it through constraints, not by magic.- Isolation — concurrent transactions produce a result consistent with some acceptable ordering. How strong that guarantee is depends on the isolation level (Chapter 3).- Durability — once  returns, the effects survive a crash. Provided by write-ahead logging plus ; weakened deliberately by .- Anomaly — a concurrency outcome that a given isolation level permits: dirty read, non-repeatable read, phantom read, lost update, write skew.

Chapter 3 — Isolation levels, as PostgreSQL implements them

The SQL standard defines four levels by which anomalies they may permit. PostgreSQL's implementations are strictly stronger than the minimum in two important places.

| Level | Dirty read | Non-repeatable read | Phantom read | Serialization anomaly (write skew) ||-------|-----------|---------------------|--------------|-------------------------------------|| READ UNCOMMITTED | not possible | possible | possible | possible || READ COMMITTED (default) | not possible | possible | possible | possible || REPEATABLE READ | not possible | not possible | not possible | possible || SERIALIZABLE | not possible | not possible | not possible | not possible |

What  still allows is write skew: two transactions each read a set of rows, each decides its write is safe based on what it read, and the combined result violates an invariant that neither transaction alone broke.

SERIALIZABLE and SSI

PostgreSQL 9.1 and later implement  with Serializable Snapshot Isolation (SSI). It runs on top of snapshot isolation and tracks read/write dependencies between concurrent transactions with predicate locks (SIREAD locks). When it detects a dependency cycle that could not occur in any serial ordering, it aborts one of the transactions with SQLSTATE .

Properties worth internalising:

- It does not block. There is no extra waiting; the cost is aborts and the memory used for predicate locks.- The guarantee is real: if every transaction runs at  and every serialization failure is retried, the outcome is equivalent to some serial execution. No hand-written locking required.- It is all-or-nothing per workload. A transaction at  running alongside serializable ones is not protected and can break their guarantee.- Read-only transactions can be marked to reduce false positives:  waits until a safe snapshot exists, then never aborts.

The retry loop is mandatory

Any code path that uses  or  must be prepared to run the whole transaction again. This is not optional error handling; it is part of the contract.

Rules for the retry body:

- Retry the whole transaction, not the failing statement. The snapshot is gone; re-reading is the point.- Never leave side effects outside the transaction inside the retried block — no emails, no queue publishes, no HTTP calls. Chapter 5 — Deadlocks

A deadlock is a cycle in the wait-for graph: A holds a lock B wants and B holds a lock A wants. PostgreSQL detects it after  (default ) and aborts one transaction with SQLSTATE .

Reading the log entry

The fix: consistent lock ordering

Deadlocks come from two transactions acquiring the same set of locks in different orders. Impose a global order — sorting by primary key is the standard choice — and the cycle becomes impossible.

Other reliable mitigations: keep transactions short, do not interleave user think-time inside a transaction, and touch tables in the same order everywhere in the codebase. And keep the retry loop from Chapter 3 — a deadlock abort is retryable by definition.

Chapter 6 — Advisory locks

Advisory locks are application-defined mutexes stored in PostgreSQL's lock manager. The database attaches no meaning to them; you choose the key.

Typical uses: making a cron job single-instance across many app servers, serialising a migration, or guarding a per-tenant critical section keyed by tenant ID.

> Trick: prefer  over . Transaction-scoped locks cannot be leaked by a crashed code path — they disappear at the end of the transaction.

> Common pitfall: advisory locks are per session, and PgBouncer in transaction pooling mode hands your session to someone else between statements. Session-scoped advisory locks are unusable there; transaction-scoped ones are fine. Post 07 covers this.

Chapter 7 — Long transactions, wraparound, and "idle in transaction"

Why long transactions are expensive

Vacuum can only remove a dead tuple if no snapshot in the entire cluster could still see it. One transaction that started an hour ago and is still open pins the global horizon at its own snapshot. For that hour, no dead tuple newer than it can be removed anywhere in the database — even in tables that transaction has never touched.

The result is bloat everywhere, slowly, invisibly, until someone notices the disk.

Transaction IDs are 32-bit. PostgreSQL treats them as a circle: from any XID, roughly 2 billion are "in the past" and 2 billion are "in the future". Chapter 7 — Client-Side Field-Level Encryption (CSFLE)

Sensitive fields are encrypted by the driver before they leave the application. The server only ever sees ciphertext.

Algorithm matters:

- Deterministic — same plaintext → same ciphertext. Allows equality lookups ().- Random — same plaintext → different ciphertext each time. Hides distribution + frequency but no equality lookups.

The driver intercepts queries + writes, encrypts/decrypts as needed. Server, admins, backups, replicas all see ciphertext only.

Key Management: data keys are encrypted by a master key held in your KMS (AWS KMS, Azure Key Vault, GCP KMS, KMIP). The key vault collection stores encrypted data keys; the master key never leaves the KMS.

Constraints with CSFLE:

- Only equality queries on deterministically-encrypted fields.- No range / sort / aggregation on encrypted fields.- For "range queries on encrypted data" → use Queryable Encryption.

Chapter 8 — Queryable Encryption (GA in 7.0)

Queryable Encryption extends field-level encryption to support equality + range + prefix queries on encrypted data — without ever decrypting on the server.

Use cases:

- PII fields needing search (email lookup for password reset).- Salaries, balances, ages — range queries while keeping plaintext invisible to DBAs.- Compliance (HIPAA, GDPR) — data is encrypted to ops staff but still queryable to apps with the right key.

Caveats: slower than unencrypted queries; some index types unsupported; key management complexity. Plan carefully.

Atlas: Queryable Encryption is supported on dedicated tiers + recent Mongo versions.

Chapter 9 — Materialized views

A materialized view stores the query result on disk. It is the right tool when an expensive aggregate is read far more often than the underlying data changes, and slightly stale results are acceptable.

computes the new contents into a temporary relation and applies the difference, so readers are never blocked. Its requirements: a unique index covering all rows, and a view that has already been populated once. It is slower in wall-clock terms than a plain refresh — it trades throughput for availability.

PostgreSQL has no built-in incremental view maintenance; if refresh cost becomes the bottleneck, the usual answer is a summary table updated by triggers or by a scheduled job that only recomputes recent partitions.

Chapter 3 — Shard key — the most important decision

A shard key is one or more fields whose value decides which shard each document lives on.

Three properties to evaluate

| Property | Good | Bad ||----------|------|-----|| Cardinality | many distinct values | few values || Frequency | values appear with similar frequency | one value dominates || Monotonicity | random-looking distribution | always-increasing (, timestamps) |

Why each matters

- Low cardinality — too few values to spread across many shards. A  shard key over  gives 2 chunks max; can't scale beyond 2 shards.- Skewed frequency — one tenant or one product dominates → one shard takes all writes (hot shard).- Monotonic key (auto-increment ID, timestamp) → all new writes hit the chunk holding the max value → that chunk's shard becomes hot.

The ideal

A field that's:- many distinct values,- writes spread evenly,- frequently appears in queries' filters so  can route to one shard.

Chapter 4 — Ranged vs hashed sharding

Ranged (default)

Documents with shard-key values in a range live on the same chunk.

- Pro: range queries on the shard key only hit shards in that range.- Con: monotonic inserts hot-spot the max-range chunk.

Hashed

The shard key is hashed before placement.

- Pro: writes always spread evenly across shards, even for monotonic / sequential keys.- Con: range queries on the shard key become scatter-gather (visit every shard).

Chapter 5 — Chunks + the balancer

A chunk is a range of shard-key values. Each chunk lives entirely on one shard. Chunk size defaults to 128 MB in modern versions.

The balancer is a background process on the primary config server that moves chunks between shards to keep distribution roughly even. Runs continuously; can be scheduled to a window:

Inspect chunk distribution:

Jumbo chunks

A chunk exceeding the chunk size that can't be split (because all its documents have the same shard-key value) is called jumbo and is marked unmovable. The balancer skips it.

Cause: too few distinct values for the shard key (low cardinality) — usually a sign the shard key was wrong.

Fix: re-shard the collection (Chapter 7); or pre-split with care.

Chapter 6 — Zones (formerly tags)

Pin specific shard-key ranges to specific shards. Used for:

- Region pinning — APAC users on APAC shards (low-latency reads + compliance).- Tiered storage — recent data on SSD shards, archive on cheap shards.

The balancer respects zones — chunks in a tagged range move only to shards with the matching tag.

Chapter 7 — Resharding (5.0+)

Pre-5.0, changing a shard key meant dumping the collection, dropping, and reinserting under a new shard key — multi-hour outage for big collections.

5.0+ introduced online resharding:

The new shard key is computed; chunks rebalance in the background; clients keep reading + writing throughout. Final cutover is brief.

Constraints:

- Disk + I/O cost is high; plan for a slower-than-usual period.- Some prerequisites on indexes + collection size.- The new shard key must have an index.

This dramatically lowered the cost of "I chose the wrong shard key" — but a good initial choice still saves time + money.

Scatter-gather scales poorly as the cluster grows — adding a shard makes scatter-gather queries slower, not faster.

Chapter 11 — When to shard (and when not)

Shard when

- Single replica set's CPU / disk / RAM is the bottleneck and vertical scaling is exhausted.- Working-set (hot indexes + frequently-accessed docs) exceeds RAM, even at maximum instance size.- Write throughput needed exceeds what one primary can sustain.- Data set exceeds biggest available single-instance storage.- Regulatory / latency requirement to keep data in specific regions.

Don't shard when

- Single replica set still handles your load (most apps' entire lifecycle).- Working-set fits in RAM on a larger instance.- Sharding overhead (extra hops via , complexity, cost) doesn't pay back.

Vertical scaling beats horizontal scaling until you have no choice — modern Atlas tiers go to many TB of RAM. Most apps never shard.

Chapter 1 — Why replication

Three things at once:

1. Durability — N copies of the data; loss of one server doesn't lose data.2. High availability — automatic failover; clients reconnect to a new primary in seconds.3. Read scaling (optional) — secondaries serve eventual-consistent reads.

Replication doesn't scale writes — every write still goes through one primary. For write scaling, you shard (Post 11) on top of replica sets.

Chapter 2 — Member roles

| Role | Receives writes | Serves reads | Votes in election | Holds data ||------|------------------|---------------|--------------------|-------------|| PRIMARY | yes (only one at a time) | yes | yes | yes || SECONDARY | replicates from primary's oplog | yes (with  etc.) | yes | yes || ARBITER | no | no | yes | no — voting only || HIDDEN | no | no (invisible to drivers) | yes | yes (backups, analytics) || DELAYED | no | no | yes | yes (lags primary by N seconds — disaster recovery) |

A typical minimal production set: 3 data-bearing members (1 primary + 2 secondaries). Loss of any one keeps a majority alive.

Avoid:

- Even number of voting members without an arbiter → election can split. Always odd.- Arbiter-only failover safety in 2026 → arbiters can't vote on majority writes; prefer a 3-data-member setup unless cost-constrained. (See "election + write concern" pitfall in Chapter 8.)

Chapter 5 — The oplog

The oplog is a capped collection () on every replica-set member that records every write applied. Secondaries tail it and replay it to stay in sync.

Each entry: timestamp, operation type (insert/update/delete), namespace, document or update spec.

Oplog size matters

Default size: 5 % of free disk (with a 50 GB upper cap on most platforms). If a secondary falls behind by more oplog entries than fit, it goes STALE and must do a full resync — slow.

Tune via  at start, or  admin command. Atlas auto-sizes.

> Trick: if you regularly run multi-hour ingest jobs while secondaries catch up, increase oplog size. The "1 day of writes fits" rule of thumb prevents most stale-member surprises.

Chapter 6 — Replication mechanics + lag

1. Client writes to PRIMARY.2. PRIMARY records the write to its own oplog and applies it.3. Each SECONDARY tails the primary's oplog and applies in order.4. Once a majority of voters have applied the write, it's "majority committed".

Replication lag = how far behind the primary a secondary is in oplog time.

Inspect:

Causes of lag:

- Big write spike (secondaries can't keep up).- Slow disk on a secondary.- Network latency (especially across regions).- Long oplog entries (huge updates).

Persistent lag > a few seconds = warning. Lag growing unbounded = crisis (eventually goes STALE).

Chapter 7 — Elections

If the PRIMARY becomes unreachable, voting members hold an election (under the hood: Raft-like protocol Version 1, "PV1").

Steps:

1. A secondary that hasn't heard from the primary for  (default 10 s) calls an election.2. Other voting members vote yes if the candidate's oplog is up-to-date enough.3. Majority of votes → new PRIMARY.4. Drivers detect the change via heartbeats; subsequent writes go to the new primary.

Typical failover: 10-20 seconds for clients to reconnect; retryable writes (Post 08) hide most of the disruption.

Structure

A PostgreSQL B-tree is a Lehman–Yao B-link tree, built from 8 KB pages:

Numbers worth internalising:

- Each page holds on the order of a few hundred entries for typical key widths, so fanout is a few hundred.- Three levels therefore index roughly a hundred million rows; four levels index far more. Depth grows logarithmically and stays small.- A single-row lookup costs about depth + 1 page reads: one per level down, plus one heap page fetch — and the upper levels are almost always cached.- The maximum index entry is about one third of a page (roughly 2704 bytes at the default 8 KB ). Indexing a long  column fails at insert time when a value exceeds it; index a hash or a truncation instead.- Leaf pages are doubly linked, which is why a range scan (, , ) is cheap once positioned, and why a B-tree can also satisfy  without a sort — in either direction, since it can be walked backwards.

Two modern optimisations that matter operationally:

- Deduplication (PostgreSQL 13+): repeated keys are stored once with a posting list of TIDs. Indexes on low-cardinality columns became dramatically smaller.- Bottom-up index deletion (PostgreSQL 14+): before splitting a page, the index opportunistically removes entries pointing at dead tuples. This substantially slows bloat growth on tables with heavy non- updates.

Chapter 2 — The six index types

B-tree

The default and the right answer for perhaps 90% of indexes: any type with a total order, equality and range predicates, sorting, uniqueness.

Hash

Equality only. WAL-logged and crash-safe since PostgreSQL 10 (before that they were not replicated and had to be rebuilt after a crash, which is why old advice says "never use hash indexes").

Narrower than a B-tree for long keys, since it stores a 32-bit hash rather than the value. In exchange it cannot do ranges, cannot sort, cannot be unique, and cannot be multicolumn. The niche is genuinely narrow: very long keys, equality-only access, no ordering requirement. Benchmark against a B-tree on your own data before committing.

GIN — Generalized Inverted Index

For values that contain multiple searchable items: array elements,  keys and values, full-text lexemes, trigrams.

GIN reads fast and writes slowly, because one row update can touch many index entries. The  mechanism buffers changes in a pending list and flushes them in batches — good for write throughput, but it means a query may have to scan the unflushed pending list, producing occasional latency spikes. Tune with  or set  for read-latency-sensitive workloads.

GiST — Generalized Search Tree

A framework for indexing things without a natural total order: geometry, ranges, nearest-neighbour search, and the exclusion constraints from Post 01.

GiST is lossy: it returns candidate rows that the executor must recheck. That is why a GiST plan shows a .

SP-GiST — Space-Partitioned GiST

For naturally hierarchical, non-balanced partitionings: quadtrees, k-d trees, radix trees. In practice: / containment, points, and text prefix search where a radix tree beats a B-tree on space.

BRIN — Block Range INdex

Stores a summary (by default min/max) for each range of heap pages — 128 pages by default. Consequently it is minuscule: an index over a billion-row table can be a few megabytes.

BRIN only works when the physical row order correlates with the indexed value — append-only time-series data, log tables, tables loaded in key order. If rows are scattered, every block range spans the whole value domain and the index eliminates nothing. Check before building:

Ordering the columns

The rule PostgreSQL practitioners use is the same shape as MongoDB's:

> Equality columns first, then the column you sort by, then the range column last.

That is exactly the ESR rule — Equality, Sort, Range — from the MongoDB indexes post. The reasoning is identical in both engines: a B-tree can only continue using subsequent columns while preceding ones are pinned to single values. Once a range predicate opens up a span of the tree, everything after it in the index is no longer in useful order.

Where PostgreSQL and MongoDB genuinely diverge:

The bitmap difference is the practical one. In MongoDB the guidance is firmly "build the compound index that matches the query". When a sequential scan is correct

This bears stating plainly, because a great deal of wasted tuning effort comes from trying to force an index scan that would be slower.

A sequential scan is the right plan when:

1. The predicate matches a large fraction of the table — beyond roughly 5–10%, random heap fetches through an index exceed the cost of reading everything sequentially. The exact crossover depends on  and physical correlation.2. The table is small. Under a few hundred pages, one sequential read beats index descent plus heap fetch. The planner knows this and is right.3. No index covers the predicate, and creating one is not justified by the query's frequency.4. The query is an aggregate over most of the table —  genuinely must look at everything (or at least at the whole visibility map, via a parallel index-only scan).5. Parallelism applies. A parallel sequential scan across four workers can beat a single-threaded index scan outright.

To diagnose — never to fix in production code:

If the forced index plan is slower, the planner was right and the investigation is over. If it is much faster, you have found a cost-model or statistics problem — which is Post 04's subject.

Chapter 7 — Building and maintaining indexes in production

A plain  takes a lock that blocks all writes to the table for the entire build. On a large busy table that is an outage.

What it costs you:

- Two table scans instead of one, plus a wait for all transactions that could see the table to finish. Substantially slower in wall-clock terms.- It cannot run inside a transaction block — which means migration frameworks that wrap each migration in a transaction need an explicit escape (Rails: ; Django: ; plain SQL: run it as its own statement).- If it fails — a deadlock, a unique violation discovered during the second pass, a cancelled session — it leaves behind an invalid index that is maintained on writes but never used by queries.

(PostgreSQL 12+) rebuilds an existing index without blocking writes, and  removes one the same way. On a replicated setup, build indexes on standbys first only if you are using logical replication — with physical streaming replication the index arrives automatically through WAL.

Index bloat

MVCC leaves dead entries behind;  reclaims space for reuse but does not return it to the operating system, and a B-tree that has churned heavily can end up substantially larger than a freshly built equivalent. Bottom-up index deletion (PG 14+) reduced this markedly, but it did not eliminate it.

The fix is . Do not schedule blanket reindexing "just in case" — it is expensive I/O, and a healthy index does not need it.

Chapter 1 — Pixel ratio (the biggest free win)

A modern phone may report  — meaning a 400×800 logical viewport renders at 1200×2400 actual pixels. That's 9× the pixels of a desktop running the same canvas at DPR=1.

Capping at 2 is the standard. The visual difference between DPR=2 and DPR=3 is essentially invisible; the performance difference is dramatic.

For aggressive optimisation, cap at 1.5 or 1 on detected low-end devices. Combine with a quality slider in your UI.

Chapter 8 — Postprocess discipline on mobile
