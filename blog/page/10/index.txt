Chapter 1 — What PostgreSQL is (and is not)

Terminology

- RDBMS — Relational Database Management System: data lives in tables of typed columns, related by keys, queried with SQL.- Cluster — one PostgreSQL server instance and the set of databases it manages, all sharing one data directory, one port, and one set of processes. Nothing to do with a distributed cluster.- Data directory () — the on-disk home of a cluster: table files, WAL, config, everything.- WAL — Write-Ahead Log. Every change is written to the log before it is written to the data files. WAL is the foundation of crash recovery, replication, and point-in-time recovery.- MVCC — Multi-Version Concurrency Control. Writers create new row versions instead of overwriting, so readers never block writers and writers never block readers. Covered in depth in Post 05.- Extension — a packaged bundle of SQL objects, types, functions, or index methods loadable with . PostGIS, , and  are extensions.- psql — the official terminal client. Not just a query runner: it has its own meta-command language, scripting, and formatting.

Where it fits

PostgreSQL is an object-relational database: standard SQL plus a type system you can extend. The design bias is correctness first, then features, then raw speed. It will refuse to silently truncate your string, silently coerce  to , or silently accept February 30th.

| Property | PostgreSQL | MySQL / MariaDB | SQLite | MongoDB ||---|---|---|---|---|| Model | Relational + extensible types | Relational | Relational | Document || Process model | Process per connection | Thread per connection | In-process library | Thread per connection || Concurrency | MVCC, readers never block writers | MVCC (InnoDB) | File lock / WAL mode | MVCC-ish, document-level || Strict typing | Strong, will error on bad input | Historically lenient | Dynamic ("type affinity") | Schema-optional || Window functions, CTEs | Full, since 8.4 / 9.4 | Since 8.0 | Since 3.25 | Aggregation framework || JSON |  with GIN indexing |  column |  extension | Native || Extensibility | Custom types, operators, index AMs | Limited | Limited | N/A || Best at | Anything relational, mixed workloads | Simple high-read web workloads | Embedded, single-file, tests | Document-shaped, flexible schema |

When PostgreSQL is the wrong choice

Being honest about this early saves grief:

- Embedded / single-file / zero-admin. Use SQLite. A PostgreSQL cluster is a server with a lifecycle.- Petabyte analytical scans. PostgreSQL is row-oriented. A columnar warehouse (ClickHouse, BigQuery, DuckDB for local work) will beat it by an order of magnitude on wide aggregate scans. A key-value store will win.

Everything else — the overwhelming majority of application back-ends — is squarely PostgreSQL territory.

Chapter 4 — Process and memory architecture

PostgreSQL is multi-process, not multi-threaded. Understanding the process map explains most of its operational behaviour: why connections are expensive, why  exists, why a checkpoint can cause an I/O spike.

Terminology

- Postmaster — the supervisor process (). It listens on the port, authenticates, and forks one child per connection. It never executes queries itself.- Backend — one OS process serving exactly one client connection, for the lifetime of that connection.- Shared buffers — the cluster-wide page cache in shared memory. All backends read and write pages here.- Background worker — an auxiliary process: WAL writer, checkpointer, autovacuum, background writer, and (18+) I/O workers.

Why connections are expensive

Each connection is a forked OS process with its own memory context — measurably heavier than a thread. A few hundred idle connections consume real RAM and add contention. The answer is a connection pooler (PgBouncer, pgcat, or a pool in your application driver), covered in Post 07. Rule of thumb: keep  moderate (100–300) and pool in front of it rather than raising it to thousands.

Chapter 3 — IXSCAN vs COLLSCAN — the binary signal

IXSCAN = used an index. Cost: O(log n) for the seek + O(matches) for the scan.

COLLSCAN = scanned every document. Cost: O(n) for n documents in the collection.

A COLLSCAN on a 10k-row collection is fast (a few ms). A COLLSCAN on a 10M-row collection is a multi-second outage.

Means: no index helped; the server read every document and filtered in memory. Add an index on  (or a compound covering this + other filters).

Acceptable COLLSCANs

- Tiny collections (< few thousand docs).- Analytical jobs running off-peak.- One-time admin queries.

For user-facing endpoints, never accept COLLSCAN.

Chapter 1 — What MongoDB is

Terminology

- MongoDB — distributed document database; open-source core + commercial Atlas service.- Document — a BSON object: ordered key-value pairs, nested arrays + sub-documents. Conceptually a JSON object with extra types (ObjectId, Date, Binary, Decimal128).- Collection — a group of documents (analogous to a SQL table; no enforced schema by default).- Database — a group of collections.- BSON — Binary JSON, the on-disk + on-wire format. Adds types JSON lacks (ObjectId, Date, Binary, etc.) and length-prefixes for fast traversal.-  — every document has one. Auto-generated  (12 bytes: timestamp + machine + pid + counter) unless you supply your own.- Replica set — a group of  processes that maintain the same data; provides HA + read scaling.- Sharded cluster — multiple replica sets partitioned by a shard key; provides horizontal write scaling.

Document example

One document holds the user, their tags array, and a nested address — no joins, no separate tables.

Chapter 2 — Document vs relational mental model

| Relational | MongoDB ||------------|---------|| Database | Database || Table | Collection || Row | Document || Column | Field || Primary key |  || Foreign key | Reference (manual or ) || Join |  aggregation stage || Schema enforced by DDL | Optional schema validation () || Transactions | Multi-document transactions (since 4.0) || Index | Index (B-tree, hashed, text, geo, vector) |

The shift in thinking:

- Relational: normalise first, denormalise for performance.- Document: denormalise first (embed related data) for read locality; reference only when reuse + size dictate.

Post 07 (Schema Design) covers this decision deeply.

When MongoDB fits

- Document-shaped data (catalogue items, user profiles, content items).- High write throughput with sharding.- Flexible / evolving schema (early product, multi-tenant SaaS with per-tenant variation).- Geographic + full-text + vector queries on the same data.- Real-time change streams.

When MongoDB doesn't fit (consider alternatives)

- Heavy multi-row ACID transactions → Postgres / CockroachDB.- Complex relational reporting + ad-hoc joins → relational + warehouse.- Pure key-value at giant scale → Redis / DynamoDB.- Strict tabular columnar analytics → ClickHouse / BigQuery.
