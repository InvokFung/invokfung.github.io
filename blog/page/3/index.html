Created2026-08-11|Programming Web
Caching is the part of Next.js that changed the most between versions, and the part most likely to produce a production incident: a price page that serves yesterday's number, a dashboard that shows another tenant's data because a cached function closed over the wrong variable, or a Server Action that anyone on the internet can call because the page that renders it was protected and the action was not. This post covers how to fetch data in Server Components without waterfalls, the four caching layers of Next.js 14, what 15 changed, how Next.js 16 replaced implicit caching with the explicit model (Cache Components), the revalidation APIs and their exact semantics, Server Actions (forms, progressive enhancement, the single-roundtrip response, the security model), and Route Handlers. Chapter 1 — Who are you, and what may you do? Two questions sit behind every protected request: 1. Authentication (AuthN) — who are you? The user proves an identity, for example with a password plus a code.2. Authorization (AuthZ) — what may you do? The app checks whether this identity may read or change this thing. They fail in different ways. A perfect login does not help if any logged-in user can open that belongs to someone else. That second bug is authorization, and Dev Essentials 12 · OWASP Top 10 shows it as "Broken Access Control". HTTP has a status code for each. means "I do not know who you are" (not logged in, or a bad token). means "I know who you are, and you may not do this". A is also fine for "not yours" when you do not want to reveal that the thing exists. Terminology - Credential — the thing that proves identity: a password, a private key, a code.- Factor — a kind of proof: something you know (password), have (phone, security key), or are (fingerprint). MFA means two or more different kinds.- Session — the server remembers "this browser is logged in as Ada" after the login step.- Token — a string the client sends with each request to show it is logged in. It can be a random ID (a reference) or a signed document such as a JWT (a value).- Identity provider (IdP) — a service that logs users in for other apps (Google, Microsoft Entra ID, Okta, Keycloak). Chapter 2 — Storing passwords Never plain text, never reversible encryption If you store passwords as plain text, one database leak exposes every user — and most users reuse passwords on other sites. Encryption is not the answer either. Encrypted data can be decrypted, so whoever steals the key gets every password back. You want a one-way function: easy to check a guess, impossible to reverse. That is a hash. But not any hash. Why SHA-256 is the wrong hash SHA-256 and MD5 are built to be fast. A modern GPU can compute billions of them per second. If an attacker steals your table of SHA-256 password hashes, they hash every word from a big list of leaked passwords and compare. Password hashing functions are built to be slow and memory-hungry on purpose. One login costs your server a fraction of a second. For an attacker trying billions of guesses, the same cost becomes enormous. Being memory-hard matters too: GPUs have many cores but little memory per core, so a hash that needs many MiB per guess slows them down. Salt and pepper - Salt — a random value, different for every password, stored next to the hash. Two users with the same password get different hashes, and precomputed tables ("rainbow tables") become useless. Modern libraries make and store the salt for you.- Pepper — one secret value shared by all passwords, stored outside the database (a secrets manager or an HSM). OWASP says a pepper "should not be stored along with the generated hash". If only the database leaks, the hashes cannot be cracked without it. A pepper is defence in depth, not a replacement for a slow hash. The algorithms and the current OWASP parameters The OWASP Password Storage Cheat Sheet (checked September 2026) gives this order of preference. The quotes are exact: | Algorithm | When | OWASP parameters ||-----------|------|------------------|| Argon2id | First choice | "a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism" || scrypt | If Argon2id is not available | "a minimum CPU/memory cost parameter of (2^17), a minimum block size of 8 (1024 bytes), and a parallelization parameter of 1" || bcrypt | Legacy systems | "a work factor of 10 or more and with a password limit of 72 bytes" || PBKDF2 | When FIPS-140 compliance is required | "PBKDF2-HMAC-SHA256: 600,000 iterations"; "PBKDF2-HMAC-SHA512: 220,000 iterations" | OWASP also lists Argon2id settings that give about the same protection. Chapter 4 — Password rules from NIST SP 800-63B-4 NIST SP 800-63B-4 is the US government guideline on authentication. The final version was published on 31 July 2025. Chapter 5 — Hardening the login Rate limiting Without a limit, an attacker can try thousands of passwords per minute. NIST requires that the verifier "SHALL limit consecutive failed authentication attempts using a specific authenticator on a single subscriber account to no more than 100". Most apps choose a much lower number, plus a limit per IP address. The app in Chapter 7 allows 5 failures per account per 15 minutes. Dev Essentials 14 · API Reliability covers rate-limit algorithms in depth. > Watch out: a hard lockout per account lets anyone lock a real user out on purpose. Prefer growing delays or a temporary block, and give the real user a way to recover. Generic error messages Say "Invalid username or password" in both cases. If "no such user" and "wrong password" give different messages, attackers can find which accounts exist (user enumeration). Watch the timing too. If unknown users return instantly while real users take 50 ms to hash, the delay leaks the same fact. The Chapter 7 code hashes a dummy value for unknown users to keep the timing close. Registration and "forgot password" pages leak the same way, so give them neutral replies such as "If that account exists, we sent an email". MFA with TOTP (RFC 6238) A Time-based One-Time Password is the 6-digit code in an authenticator app. Server and app share a secret. Both compute and cut the result down to 6 digits. RFC 6238 builds on HOTP (RFC 4226) and recommends a 30-second time step. It needs only the standard library: Real systems also remember the last accepted time step, so the same code cannot be used twice, and they rate-limit code guesses. In production you would use a tested library such as . NIST marks SMS codes as a "restricted" authenticator because of risks such as SIM swaps and number porting. Passkeys and WebAuthn TOTP codes can still be phished: a fake site asks for the code and replays it within 30 seconds. Passkeys fix this. A passkey is a key pair created by the user's device or password manager through the WebAuthn browser API. The server stores only the public key. At login, the device signs a random challenge with the private key. The browser ties each credential to the site's origin, so a look-alike domain cannot use it. WebAuthn Level 3 became a W3C Recommendation in 2026, and NIST 800-63B-4 requires phishing-resistant authenticators at its highest level (AAL3). Use a maintained WebAuthn server library rather than writing the checks yourself. Chapter 6 — Sessions and cookies After a good login, the server must remember the user.
