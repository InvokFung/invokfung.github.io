MongoDB's native time-series collections (Post 17 Ch 9) cover small-to-medium telemetry workloads beautifully — IoT fleets in the thousands of devices, observability for a single product, financial ticks for a few symbols. Past that, dedicated columnar / time-series engines pull ahead by an order of magnitude on price-performance. This post is the comparative guide: how Mongo time-series collections actually work internally, where their limits are, and how they compare to ClickHouse, TimescaleDB, InfluxDB, QuestDB, Druid. The goal — give you the decision matrix so you know when to stay on Mongo and when to add (or move to) something else. > Series map: 26 OpenTelemetry → 27 Geo → 28 Time-series extreme (this post) → 29 K8s + mongosync + cost. Learning Outcome - Explain how MongoDB time-series collections store + query data.- Recognise the workload ceiling — when Mongo time-series stops scaling.- Compare with ClickHouse, TimescaleDB, InfluxDB, QuestDB, Druid on the dimensions that matter.- Pick a stack — pure Mongo / Mongo + hot analytics engine / replace Mongo for this workload.- Design hybrid architectures (Mongo OLTP + external OLAP). Chapter 1 — How Mongo time-series collections work You create a TS collection with a , optional , and : Under the hood: - Documents you insert are invisibly bucketed by + time window. The visible API is one-doc-per-event, but on disk it's many events per bucket document.- Buckets use columnar compression — much smaller than 1-doc-per-event.- Queries by time range + metaField are fast because they touch only matching buckets. Trade-offs vs hand-rolled bucket pattern (Post 07 Ch 5): - No manual schema to maintain.- Better compression than naive.- TTL works out of the box. For most telemetry use cases this is fine. Workloads where Mongo TS starts to crack: 100k+ writes/sec sustained on a single node, deep aggregations over years of data, sub-100 ms query latency on billions of rows. The operational simplicity wins. Chapter 3 — Where Mongo TS struggles - Very high write throughput — single primary saturates around 50-100k writes/sec on a strong shard. Beyond that, sharding helps but costs grow.- Very deep aggregations — averaging across billions of rows with cardinality-heavy is slower than columnar engines built for it.- Sub-50ms p99 on huge ranges — columnar formats with vectorised execution win.- Compression at extreme scale — ClickHouse / Parquet typically achieves 5-20× the compression ratio of Mongo TS for time-series-shape data.- Cost per TB of cold data — Atlas hot storage isn't cheap; archive helps but specialist engines compress more aggressively. When the workload hits any of these, look at alternatives below. Strengths for time-series: - Sub-second aggregation over billions of rows.- 10-50× compression vs row-store.- Materialized views update incrementally.- Native S3 + Parquet integration for cold storage. Inserts: millions of rows / second per node.Queries: tens of milliseconds over millions of rows. Chapter 6 — Hybrid — Mongo for OLTP, ClickHouse for OLAP The common 2026 pattern for serious scale: Mongo handles user-facing reads + writes with rich queries on recent data. Events flow to ClickHouse via Kafka (Post 24) or a periodic batch ( + S3 → ClickHouse). Dashboards / BI hit ClickHouse for big analytics. Each tool does what it's best at; you pay the cost of running two systems but neither is asked to do the other's job poorly. Chapter 7 — When TimescaleDB fits better If your team is already deep on Postgres + your analytical queries are still SQL-shape (joins, complex predicates, transactions over recent slices), TimescaleDB keeps you on one engine. Strengths: - Full Postgres feature set + PostGIS + extensions.- Multi-tier storage (recent on SSD, old compressed to columnar).- Familiar to SQL teams. Weaknesses: - Not as fast as pure columnar for huge analytics.- Scaling horizontally still harder than Atlas + Mongo or ClickHouse. Pick when: SQL-first team, mixed transactional + analytical SQL workload, < 1 TB per dataset. Chapter 8 — InfluxDB v3 — metrics-focused InfluxDB v3 (formerly IOx) is rebuilt on Apache Arrow + Parquet. Strengths for metrics: - Native to monitoring workflows (Prometheus-compat ingest, Grafana plugin).- Fast on time-series math (rates, moving averages, derivatives).- Self-managed or cloud. Weaknesses: - Less general-purpose than ClickHouse.- Schema evolution gotchas inherited from earlier versions. Pick when: pure monitoring workload + you want a metrics-first DB rather than a general analytical engine. Chapter 9 — QuestDB — fast + small QuestDB is a young, fast columnar TS database. Strengths: - Tiny footprint; runs on a laptop and on a server.- Very fast ingest + SQL queries.- Compatible with Postgres wire protocol. Weaknesses: - Smaller community + ecosystem than ClickHouse.- Fewer enterprise features. Pick when: greenfield project, dev-friendliness > ecosystem. Chapter 10 — Druid / Pinot — sub-second dashboards over huge data For ad-tech, real-time analytics, leaderboard-style dashboards over billions of rows with millisecond response: - Apache Druid — operational complexity high; sub-second analytical queries shine.- Apache Pinot — similar story; LinkedIn / Uber heritage. Not the first choice for general workloads; reserve for when you genuinely need that latency at that scale. Chapter 1 — Why state machines A workflow is a graph of steps with branches, parallelism, error handling, and (sometimes) human approval. Hand-rolled, this turns into a tangle of Lambdas invoking other Lambdas, with retry logic copied in each, error-handling baked into each step, and no central view of "where is this execution right now?". Step Functions externalises the orchestration: - The state machine definition is a JSON document — version-controlled, auditable.- Step Functions runs each execution: tracks position, retries, errors, history.- The console shows a visual diagram of every execution — which step succeeded, which failed, what data flowed where.- Each step is small and stateless (your Lambdas or AWS service calls); orchestration logic lives in one place. Express suits per-request orchestration (an API call that needs to fan out, gather, return). Chapter 6 — The Saga pattern In a distributed system, you can't have ACID across services. The Saga pattern fakes it: every step has a compensating action, and if a later step fails, the workflow runs the prior compensating actions in reverse. Example: order placement. If fails, the workflow: 1. Cancels delivery (n/a, never scheduled).2. Refunds the card.3. Releases the inventory.4. Returns the user a coherent failure response. In Step Functions, model it as a block with that routes to a compensating sub-workflow. Chapter 7 — Express vs Standard pricing | Standard | Express ||----------|---------|| USD 0.025 per 1,000 state transitions | USD 1 per 1M executions + GB-second compute time | A long-running workflow with 50 transitions costs USD 0.00125 per execution on Standard. A 200-ms Express execution at 100 MB costs USD 0.0000004 per execution. Express wins for high-volume; Standard wins for long-running / fewer / audit-required. Many production systems use both: Standard for the business workflow, Express for inner high-frequency loops. Chapter 8 — When NOT to use Step Functions | Scenario | Better fit ||----------|------------|| Single Lambda, no branching | just use Lambda || Pure pub/sub fanout | SNS or EventBridge || Pure queue + worker | SQS + Lambda || Stream processing | Kinesis + Lambda || Simple event chain across AWS services without transformations | EventBridge Pipes (newer, lighter than Step Functions for source → enrich → target) || Always-on long-running daemon | ECS / EC2 | EventBridge Pipes deserves a special mention: launched 2022, ideal for "read from queue/stream → optional Lambda enrich → write to target". For pure pipelines without branching, Pipes is cheaper and simpler than Step Functions. Chapter 9 — A worked example: image-processing pipeline Workflow: user uploads photo → resize multiple variants in parallel → run ML classifier → store metadata → notify user. What this gains over hand-wired Lambdas:- Visual diagram for every execution.- Built-in retries with backoff.- Direct SDK integration for DynamoDB + SNS — no Lambda wrappers.- Full execution history queryable in the console.- Easy modification — add a step in JSON, no code change. Chapter 10 — Standard workflow + human approval A common pattern: wait for a human approval mid-workflow. Step Functions supports callback tokens — pause until an out-of-band call resumes. The workflow pauses (up to a year on Standard). A human (or webhook) calls / with the token to resume.
