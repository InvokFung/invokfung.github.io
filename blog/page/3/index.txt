e:T24ca,MongoDB has had multi-document ACID transactions since 4.0 (replica sets) and 4.2 (sharded clusters). They look like SQL transactions (), behave like SQL transactions (snapshot isolation), and carry SQL-like costs (locking, latency, contention). This post covers how to use them safely ??sessions, retry on transient errors, abort vs commit, the limits ??and the more important question: when NOT to reach for a transaction (in MongoDB, the answer is "more often than you think").

Chapter 1 ??Why transactions in MongoDB

Single-document updates are already atomic in MongoDB ??that's true for any update operator on one document, no transaction needed.

Transactions matter when you need atomicity across multiple documents (possibly across multiple collections, possibly across multiple shards):

- Transfer money between two accounts.- Decrement stock + insert an order line.- Update a parent + add to its children collection consistently.

Before 4.0, the workaround was the two-phase commit pattern in application code ??verbose and error-prone. Transactions replaced that for most use cases.

Chapter 5 ??Limits and gotchas

| Limit | Default ||-------|---------|| Transaction lifetime | 60 seconds (server ) || Total oplog size per transaction | 16 MB || Operations per transaction | unlimited in count, capped by oplog size || Read preference | primary only (replica set) || Cross-shard transactions | supported since 4.2; slower than single-shard || DDL inside transaction | limited (no  in some versions; check current docs) || Capped collections | can't be written inside a transaction |

> Watch out: the 60-second default kills long-running transactions. For bulk operations, chunk into many small transactions rather than one huge one.

Performance impact

A transaction holds locks for its duration. Other writers to the same documents queue or conflict. The longer the transaction, the worse the contention.

Rule of thumb:- Sub-100 ms transactions are usually fine.- 100 ms-1 s transactions add measurable lag at scale.- Multi-second transactions almost always indicate a design problem.

Chapter 6 ??Read-then-write inside transactions

The double safeguard (in-app check + filter condition) handles the race where another transaction modifies stock between your read and your write.

Without a transaction, you could still do this with optimistic check on the filter ??the transaction adds atomicity across the insert and the decrement plus a snapshot view.

Chapter 7 ??When NOT to use transactions

Transactions are powerful + tempting, but expensive. Cheaper alternatives:

Single-document atomicity (free)

The whole update is atomic. If the filter doesn't match (balance < 100), nothing changes. Most "decrement counter, reject if would go negative" problems collapse to this one statement.

Embed instead of reference

If you find yourself in a transaction across  + , ask whether the children should be embedded in the parent (Post 07). A single update on an embedded array is atomic, no transaction needed.

Idempotent retries

If the operation is idempotent, just retry on failure. No transaction needed ??eventual consistency settles.

Choreography (sagas) for distributed flows

For long-running cross-service flows (order ??payment ??shipping), use a saga / compensating action pattern. Transactions don't help across systems.

Compute + materialise

Materialised views via  (Post 06) or change-stream-driven sync (Post 12) replace many "update two collections at once" cases.

> Trick: before reaching for a transaction, ask: "Can a single-document update with a filter condition serve this?" Answer is yes 70-80 % of the time.

Chapter 8 ??Sharded transactions

Cross-shard transactions work since 4.2. They use a two-phase commit under the hood, so they're slower than single-shard.

Performance tips:

- Design schema so transactions hit one shard whenever possible.- Choose the shard key carefully ??a transaction touching docs on the same shard key value stays single-shard.- Distributed transactions across many shards multiply latency by the number of shards.

If your design requires frequent cross-shard transactions, the schema or shard-key choice may be wrong.

Chapter 1 ??The mental shift

SQL: design schema first, query later.MongoDB: start from the queries you want to run, design schema to make them efficient.

Two principles:

1. Data that's accessed together should live together. Embed it.2. Data that grows unboundedly or is shared across many parents should be separated. Reference it.

That's it. The named patterns below are corollaries.

Chapter 2 ??Embed vs reference

Embed (sub-document or array)

Pros:- One document fetch returns the whole thing.- Atomic writes across the whole document.- No joins.

Cons:- Duplication if the same sub-document is shared by many parents.- Document size cap: 16 MB.- Updating a deeply nested value can be awkward.

Reference (foreign key style)

Pros:- Each entity is the single source of truth.- No size limit (each is its own document).- Many parents can reference the same entity.

Cons:- Reads need a join ( or two round-trips).- No atomic writes across the reference unless using transactions.

Decision matrix

| | Embed | Reference ||---|-------|-----------|| Always read together | ??| || Independent reads dominant | | ??|| Few items per parent (< 100) | ??| || Many items per parent (> 1000) | | ??|| Item shared by many parents | | ??|| Item grows unbounded | | ??|| Item updated often, on its own | | ??|| Items rarely change once written | ??| |

> Trick: when undecided, embed first. Schema migration from embedded to referenced is mechanical. The reverse usually requires re-engineering query paths. Embedding is the cheap default.

Chapter 3 ??IXSCAN vs COLLSCAN ??the binary signal

IXSCAN = used an index. Cost: O(log n) for the seek + O(matches) for the scan.

COLLSCAN = scanned every document. Cost: O(n) for n documents in the collection.

A COLLSCAN on a 10k-row collection is fast (a few ms). A COLLSCAN on a 10M-row collection is a multi-second outage.

Means: no index helped; the server read every document and filtered in memory. Add an index on  (or a compound covering this + other filters).

Acceptable COLLSCANs

- Tiny collections (< few thousand docs).- Analytical jobs running off-peak.- One-time admin queries.

For user-facing endpoints, never accept COLLSCAN.

Chapter 1 ??What MongoDB is

Terminology

- MongoDB ??distributed document database; open-source core + commercial Atlas service.- Document ??a BSON object: ordered key-value pairs, nested arrays + sub-documents. Conceptually a JSON object with extra types (ObjectId, Date, Binary, Decimal128).- Collection ??a group of documents (analogous to a SQL table; no enforced schema by default).- Database ??a group of collections.- BSON ??Binary JSON, the on-disk + on-wire format. Adds types JSON lacks (ObjectId, Date, Binary, etc.) and length-prefixes for fast traversal.-  ??every document has one. Auto-generated  (12 bytes: timestamp + machine + pid + counter) unless you supply your own.- Replica set ??a group of  processes that maintain the same data; provides HA + read scaling.- Sharded cluster ??multiple replica sets partitioned by a shard key; provides horizontal write scaling.

Chapter 2 ??Document vs relational mental model

| Relational | MongoDB ||------------|---------|| Database | Database || Table | Collection || Row | Document || Column | Field || Primary key |  || Foreign key | Reference (manual or ) || Join |  aggregation stage || Schema enforced by DDL | Optional schema validation () || Transactions | Multi-document transactions (since 4.0) || Index | Index (B-tree, hashed, text, geo, vector) |

The shift in thinking:

- Relational: normalise first, denormalise for performance.- Document: denormalise first (embed related data) for read locality; reference only when reuse + size dictate.

Post 07 (Schema Design) covers this decision deeply.

When MongoDB fits

- Document-shaped data (catalogue items, user profiles, content items).- High write throughput with sharding.- Flexible / evolving schema (early product, multi-tenant SaaS with per-tenant variation).- Geographic + full-text + vector queries on the same data.- Real-time change streams.

When MongoDB doesn't fit (consider alternatives)

- Heavy multi-row ACID transactions ??Postgres / CockroachDB.- Complex relational reporting + ad-hoc joins ??relational + warehouse.- Pure key-value at giant scale ??Redis / DynamoDB.- Strict tabular columnar analytics ??ClickHouse / BigQuery.
