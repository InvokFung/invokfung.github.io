Chapter 1 — Two component worlds

Terminology

- React Server Components (RSC) — a React architecture in which some components run only in a server environment (at build time or per request) and never ship their code to the browser.- Server Component — the default for every component under . Can be , can read files, databases and secrets. Cannot use state, effects, or browser APIs.- Client Component — a component in the client module graph. Rendered to HTML on the server for the first load, then hydrated and interactive in the browser. Can use hooks and event handlers.- RSC payload (also called the Flight payload) — the serialised result of rendering the Server Component tree: rendered output, placeholders for Client Components with references to their JavaScript, and the props passed to them.- Hydration — React attaching event handlers and state to server-rendered HTML so it becomes interactive.- Boundary — the point in the module graph where a server module imports a  module.

Server Components are not SSR

SSR is an old idea: run the whole React tree on the server, emit HTML, then ship all of the same code to the browser and hydrate it. Every component exists twice, once on each side.

Server Components change the second half. A Server Component runs only on the server; its code is never sent to the browser, so it has nothing to hydrate. Only Client Components are both server-rendered (for the first HTML) and shipped (for hydration).

The first-load pipeline

On a first visit to a dynamic route, three things happen in order:

1. RSC render. The server renders the Server Component tree. Wherever it meets a Client Component, it does not run it; it writes a placeholder plus a module reference and the serialised props. The result is the RSC payload.2. SSR of the client parts. The server then renders the Client Components to HTML, using the payload as input, so the first response is complete HTML.3. Browser. The HTML paints immediately (non-interactive). The client JavaScript loads, React reads the payload (inlined in the HTML) to reconcile the tree, and hydrates only the Client Components.

On a later client navigation, step 2 and the HTML are skipped. The router fetches only the RSC payload for the segments that change and merges it into the existing tree.

> Trick: when asking "does this code run in the browser?", ignore the file name and folder. Follow the imports from the nearest  file. That is the only rule the bundler uses.

Chapter 4 — The RSC payload

What it contains

From the Next.js glossary, the payload carries three things:

1. The rendered result of the Server Components (host elements such as  and , with their props and text).2. Placeholders where Client Components should render, with references to their JavaScript chunks.3. The props passed from Server Components to Client Components.

It is a streamed, line-oriented format, not one JSON document. Rows can arrive out of order: a Suspense boundary's content is written as a later row that fills a hole left earlier. That is what makes streaming work for client navigations as well as for HTML.

Chapter 2 — DNS: from name to IP address

Packets are routed by IP address, not by name. DNS (RFC 1034/1035) is the distributed phone book that turns names into addresses.

There are 13 named root server identities ( to ), each served from many sites by anycast. The authoritative server holds the real records, and is usually run by your DNS host or CDN.

Every answer carries a TTL (time to live) in seconds. Caches may reuse the answer until the TTL runs out. That is why a DNS change takes time to reach everyone: old answers live until their TTL ends.

> Trick: before you move a site to a new IP, lower the TTL (for example to 300 s) a day ahead. After the move, raise it again.

Chapter 4 — The TLS 1.3 handshake

TLS (Transport Layer Security) gives three things: confidentiality (only the two ends can read), integrity (changes on the way are detected), and authentication (you reached the real ).

TLS 1.3 was defined in RFC 8446 (August 2018). In July 2026 the IETF published RFC 9846, which obsoletes RFC 8446. It calls itself a minor update that keeps the version number 1.3 and stays backward compatible. It also obsoletes RFC 5246, the TLS 1.2 spec.

1. ClientHello. The client guesses which key-exchange group the server accepts and sends a public key for it at once. This guess is what saves a round trip compared with TLS 1.2.2. ServerHello. The server sends its own public key. Both sides now run ECDHE (Elliptic-Curve Diffie-Hellman, Ephemeral): each mixes its private key with the other's public key and gets the same shared secret. Someone watching the wire cannot compute it.3. Keys are derived from that secret. Everything after ServerHello is encrypted, including the certificate.4. CertificateVerify. The server signs a hash of all handshake messages so far with the private key of its certificate. This proves it owns the certificate, not just a copy.5. Finished. Each side sends a MAC over the whole transcript. If an attacker changed any earlier message, the MACs do not match and the connection dies.6. The client sends its HTTP request together with its Finished. Total: one round trip (1-RTT).

The key pairs are ephemeral: new for each connection, then thrown away. So stealing the server's certificate key later does not decrypt recorded old sessions. This is forward secrecy.

After a handshake the server can send a session ticket. Next time the client presents it as a pre-shared key (PSK) and may send data in its very first flight: 0-RTT early data.

Chapter 5 — Certificates and the chain of trust

Key exchange gives encryption, but encryption with whom? The certificate answers that. It is a statement, "this public key belongs to ", signed by a Certificate Authority (CA).

- Subject Alternative Name (SAN) — the host names the certificate is valid for. Clients check the SAN, not the old Common Name.- notBefore / notAfter — the validity window. Outside it, the certificate is rejected.- Issuer — who signed it. The issuer has its own certificate, and so on up the chain.

How long a certificate may live — the rules today

Public TLS certificates follow the CA/Browser Forum Baseline Requirements. Ballot SC-081v3, adopted on April 11, 2025, shrinks the maximum validity in steps (Baseline Requirements, section 6.3.2):

| Certificate issued on or after | Issued before | Maximum validity ||--------------------------------|---------------|------------------|| — | 2026-03-15 | 398 days || 2026-03-15 | 2027-03-15 | 200 days ← applies now || 2027-03-15 | 2029-03-15 | 100 days || 2029-03-15 | — | 47 days |

The same ballot cuts how long a CA may reuse a domain-validation result: 200 days from 2026-03-15, 100 days from 2027-03-15, 10 days from 2029-03-15. So a certificate issued today lives at most 200 days, and yearly manual renewal is already gone.

Revocation. If a key leaks, the CA can revoke the certificate and publish that in a CRL (signed list of revoked serial numbers) or via OCSP (ask about one certificate). Let's Encrypt turned off its OCSP service on August 6, 2025, and now publishes revocation data only through CRLs. Short lifetimes also limit damage: a leaked short-lived certificate soon stops working anyway.

> Trick: every publicly trusted certificate is recorded in public Certificate Transparency logs. Search your domain on a CT search site such as crt.sh to see every certificate ever issued for it.

Where they came from

On a typewriter or an old teleprinter, two separate motions start a new line. The carriage return moves the print head back to the left margin. The line feed rolls the paper up one line. Teleprinters needed both codes, so early systems stored both.

The choice then split:

| System | Line ending ||--------|-------------|| CP/M, MS-DOS, Windows | CRLF || Unix, Linux, macOS (since Mac OS X) | LF || Classic Mac OS (before Mac OS X) | CR |

Unix stores only LF in files and lets the terminal driver add the CR when printing. Windows kept the CP/M and MS-DOS habit of storing both.

Many internet protocols still use CRLF on the wire, whatever the operating system. HTTP/1.1 (RFC 9112) defines a message as , and CSV (RFC 4180) ends each record with CRLF. That is the protocol's business; your library handles it. This post is about files in your repository.

> Watch out: Windows Notepad only understood CRLF until 2018. Microsoft then added support for LF and CR files. New files in Notepad still use CRLF by default.

Chapter 4 — Static caching and stringification

Hoisting became caching in 3.5

The same  compiled by 3.4 and by 3.5:

In 3.4 a static vnode was hoisted to module scope and shared by every instance of the component. In 3.5 it is created on first render and kept in the instance's  array. The flag name changed from  to  with the same value (−1). Static props objects () are still hoisted to module scope, because a plain object with no DOM reference is safe to share.

The practical effect is the same — static nodes are created once and skipped by the diff — but nothing is shared between instances any more. A hoisted vnode kept a reference () to the DOM element it was last mounted to, which was a known way to retain detached DOM trees (vuejs/core issue #5256). A per-instance cache avoids that shared state.

Stringification

When enough static content sits together, the compiler goes further and emits it as an HTML string that the runtime inserts with :

Stringified chunks create no vnodes per element at all, which matters for large static sections such as documentation pages and legal text.

What is never static

Anything with a binding, a directive, a component, a , or a child that is dynamic. A single  inside a large block makes that element dynamic, but its static siblings and static descendants are still cached separately. Keep dynamic bits in small leaf elements and the static structure around them stays free.

Chapter 8 — Vapor mode

What it is

Vapor mode is an alternative compilation target for SFCs. Chapter 1 — The mental model

Four ideas explain almost every rescue.

1. A commit is a snapshot. It stores the full state of the tracked files, a message, an author, and the ID of its parent commit(s). The ID is a hash of all of that, so a commit can never change. "Changing" a commit always means making a new one.2. A branch is a movable pointer.  is only a name that holds one commit ID. When you commit, Git moves that pointer forward. Deleting a branch deletes the name, not the commits.3.  means "where you are". Normally  points to a branch, and the branch points to a commit. If  points straight at a commit, you are in detached HEAD (Chapter 6).4. The index is the next commit, in draft.  copies a file version into the index (also called the staging area).  turns the index into a snapshot.

Each commit points back to its parent, and each branch points at one commit. The key word is reachable. A commit is reachable if you can walk to it from a branch, a tag, or another ref. Git's garbage collector only deletes objects that are unreachable and old. The reflog (Chapter 3) keeps recently left commits reachable for weeks. That is why most mistakes can be undone.

Chapter 10 — Worktrees

A worktree is an extra working folder attached to the same repository. Each worktree has its own , its own index and its own files on disk. All worktrees share one object database, the branches and tags, the config — and, as Chapter 5 showed, the stash. Good uses: review a pull request while your own branch is half-edited; run a long test on one branch while you keep editing another; build an old release.

Pitfalls

1. One branch, one worktree. A branch that is checked out in one worktree cannot be checked out in another. Current Git refuses with ; older versions word it as . The same rule blocks deleting the branch (). The reason: two checkouts moving one branch pointer would leave one of them with a stale index. Fix it by using a different branch there, using , or removing the other worktree first.

2. Ignored files do not come along. A new worktree is a fresh checkout of tracked files only.  files, virtual environments (), , build caches — anything in  — are missing. The app often will not start there until you reinstall dependencies and copy local config. Budget for that, or do the work in the main checkout.

3. GUI tools show every worktree. For example, VS Code (since version 1.103) scans the repository for worktrees and lists each one in the Source Control Repositories view; the  setting turns this off. Other Git GUIs list them too. Many leftover worktrees mean a cluttered sidebar, and it becomes easy to open a file from the wrong checkout.

Chapter 2 — UTC, offsets and IANA zones

Offsets

An offset says how far a clock is from UTC at one moment.  and  are the same instant. To convert to UTC, subtract the offset: 15:00 − 8 h = 07:00.

Zones are more than offsets

The IANA time zone database (also called tzdata or the Olson database) names zones as : , , . Each zone stores every offset change in that region's history, plus the current rules for the future.

Today  is shared by several zones. Their histories differ. From the tzdata files:

| Zone | Offset today | History that  alone cannot tell you ||------|--------------|---------------------------------------------||  | +08:00 | Used summer time until 1979; the last change was on 1979-10-21. ||  | +08:00 | Was +07:30 until 1982-01-01. ||  | +08:00 | Ran a DST trial from 2006-12-03 to 2009-03-29 (+09:00 in summer). |

So an offset tells you about one moment. A zone tells you about every moment, including next year. Governments change the rules, and tzdata is updated when they do, so keep your OS, language runtime and  packages current.

Chapter 3 — DST gaps and overlaps

When clocks jump forward, one hour of wall-clock time does not exist (a gap). When clocks go back, one hour happens twice (an overlap).

Real 2026 transitions

| Zone | Change | Local clock | Result ||------|--------|-------------|--------||  | Sun 2026-03-08 | 02:00 EST → 03:00 EDT | Gap: 02:00–02:59 never happens ||  | Sun 2026-11-01 | 02:00 EDT → 01:00 EST | Overlap: 01:00–01:59 happens twice ||  | Sun 2026-03-29 | 01:00 GMT → 02:00 BST | Gap: 01:00–01:59 never happens ||  | Sun 2026-10-25 | 02:00 BST → 01:00 GMT | Overlap: 01:00–01:59 happens twice |

Chapter 8 — Cron jobs and DST

Classic cron runs jobs by the machine's local clock. On a machine in a DST zone, a job at  meets the gap in spring and the overlap in autumn. The Debian  manual describes its behaviour for clock changes of less than 3 hours:

- Moving forward: "those jobs which would have run in the time that was skipped will be run soon after the change."- Moving back: "those jobs that fall into the repeated time will not be re-run."- Jobs with  in the hour or minute field "are run based on the new time immediately".

Other schedulers behave differently, so check yours. Safe habits:

- Run servers in UTC. Then there is no DST at all.- If a job must follow local time, avoid 01:00–03:00 local in zones with DST.- GitHub Actions:  cron runs in UTC by default. You can add an IANA ; for zones with DST, GitHub's docs say a schedule inside the skipped hour advances to the next valid time (a 2:30 AM schedule runs at 3:00 AM).
