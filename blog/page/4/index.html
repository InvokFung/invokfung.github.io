AWS Course — 05 · Serverless & Events — Lambda, API Gateway, SQS, SNS, EventBridge

Most modern AWS architectures are not all-server, all-the-time — large parts of them run as events flowing through serverless glue. This post covers the building blocks: Lambda (run code on demand), API Gateway / Function URLs (turn Lambda into HTTP), SQS (queues for decoupling), SNS (pub/sub fanout), and EventBridge (the bus for routed events). Combined, they let you build entire services with no servers to manage and bills proportional to traffic. > Series map: 00 Foundations → 01 Network First → 02 Compute & Storage → 03 Scale & Survive → 04 Managed Data → 05 Serverless & Events (this post) → 06 Workflow Orchestration → 07 Observability & Security → 08 IaC. Chapter 1 — Lambda essentials A Lambda function is a piece of code (handler) plus configuration (memory, timeout, role, env vars) that AWS runs in response to an event. Billing is per-request plus per-GB-second of execution time. Minimal Python Lambda Package and deploy: Knobs that matter | Knob | Range | Note ||------|-------|------|| Memory | 128 MB - 10,240 MB | CPU scales with memory — doubling memory ≈ doubles speed || Timeout | 1 sec - 15 min | killed if exceeded || Ephemeral storage | 512 MB - 10 GB at | persists across warm invocations || Concurrency | up to 1000+ by default | reserved / provisioned controls || VPC | none (default) or attached | only attach if you need VPC resources | Trick: memory is the most important tuning knob. Tools like Lambda Power Tuning test multiple memory sizes and recommend the sweet spot — usually faster AND cheaper than the 128 MB default. Chapter 2 — Cold starts When AWS provisions a fresh container for a function, the cold start cost is:1. Download the zip / image.2. Initialise the runtime.3. Run module-level / static code.4. Chapter 3 — Event sources Lambdas don't run on a schedule by default — they're invoked by event sources. | Source | Pattern ||--------|---------|| API Gateway / Function URL / ALB | sync HTTP → Lambda → HTTP response || S3 | new object created / deleted → Lambda || EventBridge schedule | cron / rate → Lambda || EventBridge events | AWS API event → Lambda || SQS | poll a queue → Lambda || SNS | publish → Lambda || DynamoDB Streams | row change → Lambda || Kinesis | stream record → Lambda || CloudWatch Logs subscription | log line → Lambda || Direct invoke (SDK / CLI) | sync or async call | Sync vs async vs polling - Sync — caller waits for response (API Gateway, Function URL, direct invoke).- Async — Lambda returns immediately, processes in background; failures retried twice + optional DLQ (S3, SNS, EventBridge).- Polling — Lambda runtime polls SQS / Kinesis / DynamoDB Streams in batches. Chapter 4 — API Gateway and Function URLs Two ways to put HTTP in front of Lambda: API Gateway HTTP API - Custom domain + TLS via ACM.- Authn (JWT, Cognito, IAM, Lambda authoriser).- Throttling, usage plans, API keys.- Per-route Lambda integration or HTTP/private integration.- USD 1 per million requests + data transfer. Lambda Function URL - One HTTPS endpoint per Lambda.- No API Gateway in between (cheaper, simpler).- No built-in WAF, custom domain (manual via CloudFront), or throttling.- Best for internal tools, webhooks, prototypes. REST API (older) The older "REST API" flavour exists for compatibility (request validation, models, X-Ray detail). For new projects in 2026, HTTP API is the right default. Chapter 5 — SQS (Simple Queue Service) SQS is a managed message queue. Producers , consumers (often Lambda) + after success. Two queue types: | Type | Order | Duplicates | Use ||------|-------|------------|-----|| Standard | best-effort | possible | most async work || FIFO | strict per group | exactly-once | order-sensitive workflows | Lambda + SQS pattern Benefits:- Decoupling — A returns immediately; processing runs in background.- Back-pressure — if Lambda concurrency caps, messages sit in queue (no data loss).- Retries — Lambda errors keep message visible; goes to DLQ after N attempts.- Batch processing — Lambda receives up to 10 messages at once. CQRS (Command Query Responsibility Segregation) separates write models from read models. Event Sourcing treats the immutable event log as the source of truth — current state is a projection of replayed events. Both are architectural patterns, not Mongo features — but MongoDB fits them especially well: change streams as the projection bus (Post 12), for materialised views (Post 06), aggregation for replaying events, transactions for atomic event-store appends (Post 09). Chapter 1 — CQRS in one paragraph A normal CRUD app uses one model for reads and writes — same schema, same indexes, same database. CQRS splits them: command side handles writes (often normalised, validated, transactional), query side holds one or more read models optimised per use case (denormalised, fast). The read models are updated by events the command side publishes — usually asynchronously. Benefit: - Read models match exactly the queries they serve → simple + fast.- Read + write scale independently.- Multiple read models per command model (one for search, one for analytics, one for a mobile API). Cost: - More moving parts.- Read-after-write delay (eventual consistency).- Operational complexity. Use CQRS when one of: read volume >> write volume; queries diverge wildly from write shape; you already need an outbox + projections. Chapter 2 — Event Sourcing in one paragraph Instead of storing current state, store every change as an immutable event. Current state is computed by replaying events. Events are append-only — the most reliable storage primitive in databases. Benefits: - Full audit trail for free.- New projections retroactively built from history.- Bug fixes can replay events through corrected code.- Time-travel debugging. Costs: - Reads must aggregate events (use snapshots + projections).- Schema evolution of events is forever — versioning matters.- Higher mental + ops load than CRUD. Use ES when one of: regulatory audit trail mandatory; the domain is genuinely event-shaped (orders, payments, IoT, ledger systems); you need to replay history for new analytics or bug correction. ES + CQRS combine naturally — ES is the command-side event log, CQRS is the read-side projections. Chapter 3 — When NOT to use CQRS / ES - A CRUD app with simple reads + writes — KISS.- Small team / small product — overhead > benefit.- Tight read-after-write requirements with no tolerance for eventual consistency.- "Because it sounds modern" — biggest reason teams regret it.
