MongoDB Course — 20 · Outbox Pattern + Transactional Event Publishing
Created2026-07-18|Database MongoDB
You write to the database. You also need to publish an event ("order placed → send confirmation email"). If those two steps aren't atomic, you'll either lose events (DB committed, queue publish failed) or send duplicates (publish succeeded, DB rolled back). The outbox pattern solves this by treating the event as part of the same DB transaction, then publishing from the outbox to your message bus asynchronously. With MongoDB change streams (Post 12), the publisher is one process tailing the outbox collection — no Kafka Connect, no extra infrastructure. This post covers the full pattern, retry + idempotency + ordering, and the deduplication strategies downstream consumers need. > Series map: 18 Mongoose → 19 Beanie+FastAPI → 20 Outbox (this post) → 21 CQRS + ES → 22 RAG → ... → 29 K8s + mongosync + cost. Learning Outcome - Recognise the dual-write problem.- Build an outbox collection alongside business writes inside one transaction.- Build a change-stream-driven publisher with resume tokens.- Handle at-least-once delivery + downstream idempotency.- Pick between outbox + change streams vs Debezium / Kafka Connect. Chapter 1 — The dual-write problem Two failure modes: - DB insert succeeds, Kafka publish fails → lost event.- Kafka publish succeeds, DB insert fails → phantom event (consumers act on data that doesn't exist). Neither is acceptable for systems that need consistency between their database state + downstream consumers. Naive fixes that don't work - Try-catch + retry: same race, just longer odds.- 2-phase commit across MongoDB + Kafka: not supported across systems.- Eventual consistency + reconciliation: complex; high latency. The outbox Write the event as a row in the same database, same transaction as the business mutation. A separate process publishes from the outbox to Kafka / RabbitMQ / SQS / SNS, marking each event as published (or deleting it). Because the business write + outbox write are in one transaction, they're atomic. The publisher is async + retryable; downstream consumers handle duplicates idempotently. Chapter 2 — Outbox schema means unprocessed. The publisher claims, processes, marks. Chapter 3 — Producer side — transactional write Both writes commit together or neither does. The business state and the to-be-published event are forever consistent. Chapter 4 — Publisher — change-stream-driven (the cheap option) Properties: - At-least-once delivery — on crash before token persist, we replay.- Resume token persisted after successful publish + mark.- Network blip → retried with backoff, attempts incremented. This pattern needs no external infrastructure beyond your existing MongoDB. The publisher can run anywhere — a sidecar, a long-running container, a dedicated tiny pod. Chapter 5 — Publisher — polling fallback If change streams aren't available (standalone Mongo, very old versions, or a multi-region setup with restricted secondary access): Higher latency (poll interval) + more DB queries; rock-solid. Use change streams when available, polling as fallback. Chapter 6 — At-least-once → consumer must be idempotent Once a publisher delivers at-least-once, consumers will eventually see duplicates (publisher crashed mid-ack, network duplicate, replay after rebuild). Idempotency patterns: 1. Event ID dedup Every outbox event has a unique . Consumers track processed IDs (in a "consumedevents" collection, Redis set, etc.). Skip if already processed. 2. Idempotent operations Make the consumer's side-effect itself idempotent: , upsert by key, "set status to X" rather than increment. 3. Optimistic versioning Event carries ; consumer rejects updates with . Combine 1 + 2 for belt-and-braces. Chapter 7 — Ordering guarantees Kafka topics + partitions preserve order within a partition. Choose your partition key to match the ordering you need. For "all events on this order, in order" → key on .For "every event in occurrence order globally" → single-partition topic (low throughput). Most outbox usage cares about per-aggregate ordering — keying by is the right default. What if you don't have Kafka? SQS doesn't preserve order across the queue (unless FIFO with ). SNS doesn't (FIFO topics do). RabbitMQ exchanges + queues do preserve order per queue. Match destination to the ordering requirement. Chapter 8 — Backpressure + DLQ When the downstream is down for hours: - Outbox grows. Disk usage climbs.- If you have TTL on , you'll lose unpublished events — don't TTL the unpublished portion.- The publisher must implement exponential backoff to avoid hammering a downed downstream. Dead Letter Queue pattern: Alert + investigate. Don't silently drop. Chapter 9 — Outbox + sagas (cross-service workflows) For workflows spanning services (order → payment → inventory → shipping), combine outbox events with a saga orchestrator. Each step is one service's local transaction + outbox publication. The next service's consumer triggers its step. If a step fails, the orchestrator publishes a compensating action event → previous services undo. Outbox makes each step atomic + reliable. The saga adds the cross-step orchestration. Together they're the standard pattern for distributed workflows on document databases. AWS Course — 01 · Network First — VPC, Subnets, Routing, Security Groups
Created2026-07-16|Cloud AWS
Real AWS workloads start with the network, not the server. Where a workload lives — which VPC, which subnet, behind which gateway, allowed by which security rules — decides far more about its security posture, cost, and failure behaviour than the choice of instance type. This post is the deep dive on VPC, the virtual data centre that hosts almost everything else in the series. > Series map: 00 Foundations → 01 Network First (this post) → 02 Compute & Storage → 03 Scale & Survive → 04 Managed Data → 05 Serverless & Events → 06 Workflow Orchestration → 07 Observability & Security → 08 Infrastructure as Code. Why network before compute A tempting shortcut is to "just launch an EC2" and figure out the network later. The cost: every later change (adding a database, fronting with a load balancer, going multi-AZ, locking down for security review) becomes a re-architecture. Network-first means picking a small set of decisions once and reusing them for the next decade. The decisions:- Which region.- VPC CIDR range (which private IPs you'll own).- Subnet layout (how many AZs, public/private/isolated).- Internet egress path (IGW + NAT or VPC endpoints).- Security group baseline (who can talk to whom). Learning Outcome - Design a VPC CIDR that won't collide with other accounts you might peer with.- Lay out public / private / isolated subnets across 3 AZs.- Configure route tables, internet gateways, NAT gateways, and VPC endpoints.- Write security groups and (rarely) NACLs that are tight without being painful.- Recognise the cost levers: NAT gateway, cross-AZ traffic, data egress. Chapter 1 — VPC anatomy A VPC is a software-defined private network inside one AWS region. Each AWS account gets a default VPC per region (); production accounts almost always create custom ones. | Construct | What ||-----------|------|| VPC | the boundary; one or more CIDR ranges (IPv4 + optional IPv6) || Subnet | a CIDR slice of the VPC, lives in exactly one AZ || Route table | per-subnet (or default) rules: "for destination X, next hop is Y" || Internet Gateway (IGW) | one per VPC; enables inbound + outbound public internet || NAT Gateway | enables outbound-only public internet from private subnets || VPC endpoint | reach AWS services privately, no IGW/NAT needed || Security group | stateful per-ENI firewall || NACL | stateless per-subnet firewall | CIDR sizing A (e.g., ) gives 65,536 addresses — enough for a serious production environment. Conventional starting layouts: - Account —- Account —- Account —- Account —- On-prem — or Chapter 2 — The 3-AZ subnet layout Three reasons this shape is the industry default: 1. Failure isolation. An AZ outage takes down at most a third of capacity. Combined with a load balancer (Post 03), the service stays up.2. Blast radius for security. Public subnets only host things designed to face the internet. Application servers and data live one or two hops inward.3. Cost vs availability tradeoff. One NAT gateway is cheaper but a single point of failure; one per AZ doubles or triples cost but removes the SPoF. Production prefers per-AZ. A subnet is "public" because its route table sends to an Internet Gateway. There is no checkbox — it is the routing that defines the type. Chapter 4 — Internet egress: IGW vs NAT vs VPC endpoints | Path | Where allowed | Inbound from internet? | Outbound to internet? ||------|---------------|------------------------|------------------------|| IGW | public subnets only | yes (with public IP) | yes || NAT Gateway | private subnets | no | yes || VPC endpoint (Gateway) | S3, DynamoDB | n/a | private to those services || VPC endpoint (Interface) | most AWS services | n/a | private to those services | VPC endpoints — the cost saver By default, an EC2 in a private subnet calling routes out via the NAT gateway — and you pay NAT data charges (USD 0.045 / GB). With a Gateway VPC endpoint for S3, the traffic stays inside AWS, free. Watch out: Interface endpoints cost about USD 7 / endpoint / AZ / month plus per-GB. Chapter 5 — Security groups (your everyday firewall) A security group is stateful: if a request matches an outbound rule, the reply is automatically allowed (and vice versa). You only configure one direction, not both. Default behaviour: no inbound, all outbound. Rules contain:- Protocol (TCP / UDP / ICMP / all)- Port range- Source / destination (CIDR, another security group, or a prefix list) Reference SGs by ID, not by IP When both ends are AWS resources, reference the other side's security group rather than its IP range. As IPs change (autoscaling, recreation), the SG reference stays correct. Chapter 6 — NACLs (the backup layer) A Network ACL is stateless and applied per subnet. Default rules allow all inbound + outbound. Custom NACLs default to deny. NACLs are evaluated in order (rule numbers); the first match wins. In practice most teams don't touch NACLs — security groups do all the real work. Reserve NACLs for blanket per-subnet rules (e.g., "isolated subnets reject any outbound traffic at all") or defence-in-depth against compromised SG state. Chapter 4 — Document-level locking + MVCC WiredTiger uses multi-version concurrency control (MVCC): - Readers see a consistent snapshot at their start time.- Writers create new versions; old versions linger until no reader needs them.- Locking is at the document level — different documents in the same collection don't block each other.
