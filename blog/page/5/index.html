Containers Course — 05 · Config, Storage and Stateful Workloads
Created2026-08-03|Containers Kubernetes
Post 04 built the stateless half of Kubernetes: a Deployment of identical, interchangeable, disposable Pods behind a Service. Real systems are not that. They need configuration that differs per environment, credentials that must not leak, disks that survive a Pod being rescheduled onto another node, members with stable names that peer with each other, and batch work that runs once and stops. This post covers all of it — and closes with the question everyone eventually asks: should the database be in the cluster at all? > Series map: 00 Containers from First Principles → 01 Images and Dockerfiles → 02 Networking, Volumes and Compose → 03 Registries, Supply Chain and Security → 04 Kubernetes Architecture and Core Objects → 05 Config, Storage and Stateful Workloads (this post) → 06 Scheduling, Resources, Probes and Rollouts → 07 Ingress, Observability, RBAC and GitOps. Learning Outcome - Inject configuration as environment variables or mounted files, and predict exactly which of the two updates without a restart.- State precisely what a Kubernetes Secret does and does not protect, and choose between encryption at rest, an external secret manager, and the Secrets Store CSI driver.- Force a deliberate rollout when configuration changes, using immutable objects plus a checksum annotation.- Distinguish Volume, PersistentVolume, PersistentVolumeClaim and StorageClass, and choose access modes, reclaim policies and binding modes correctly.- Deploy a StatefulSet with stable identity and per-Pod storage, and explain what happens to its PVCs when it is deleted.- Use DaemonSets, Jobs and CronJobs, including the concurrency and missed-schedule traps.- Decide, with reasons, whether a given database belongs on Kubernetes. Chapter 1 — ConfigMaps and Secrets Terminology - ConfigMap — a namespaced API object holding non-confidential key/value data, consumed by Pods as environment variables, command-line arguments, or files.- Projection — the act of a kubelet rendering a ConfigMap or Secret into a Pod's filesystem.- Hot reload — the application noticing a configuration change without being restarted.- Immutable object — a ConfigMap or Secret marked , which can never be updated, only replaced. Two ways to consume it, with very different behaviour The difference is the single most useful fact in this chapter: | Consumption | Updates when the ConfigMap changes? ||-------------|-------------------------------------|| / | No. Environment variables are set once at container start. Editing the ConfigMap changes nothing until the Pod is recreated. || Volume mount | Yes, eventually — the kubelet re-projects the files in place. || Volume mount with | No. A mount is resolved once and never refreshed. | The propagation delay Mounted files do not update instantly. The kubelet refreshes projected volumes on its periodic sync, using a locally cached copy of the object. The worst-case delay is therefore roughly the kubelet sync period (, default 1 minute) plus the ConfigMap/Secret cache propagation delay (watch-based by default; the TTL-based strategy defaults to another minute). In practice, budget for changes appearing within about two minutes, not immediately. Three further caveats: - Updates are atomic per volume. The kubelet writes a new timestamped directory and swings a symlink, so an application never reads a half-updated set of files. Watch the directory, not the file inode — many file watchers miss the symlink swap.- The application still has to do something. A file changing on disk is not a reload; something must re-read it. Either implement a watcher, or accept a restart.- is the classic trap. It is used to drop a single file into a directory that already has other content (), and it silently opts you out of updates entirely. > Common pitfall: "I edited the ConfigMap and nothing happened." Check which of the three consumption forms you used. If it is or , nothing will happen. Roll the Deployment. Secrets, and what they actually protect A Secret looks exactly like a ConfigMap with a different and a convenience field. The blunt truth A Secret is base64-encoded, not encrypted. Base64 is an encoding, not a cipher; prints the password, and anyone with permission in that namespace can do it. By default the value also sits in etcd in plain text, which means an etcd backup, a stolen disk snapshot, or a compromised control-plane node exposes it. What a Secret actually buys you over a ConfigMap: - It is a distinct resource kind, so RBAC can be written against it separately (Post 07). This is the real benefit.- Its values are not printed by .- The kubelet stores projected Secret volumes in , so they do not touch the node's disk.- It is only distributed to nodes running a Pod that requests it. What it does not buy you: encryption, audit of reads by the application, rotation, or safety from anyone who can into the Pod. A secret that is never issued cannot leak. > Watch out: enabling encryption at rest does not retroactively encrypt existing Secrets. After changing the , rewrite every Secret () so they are re-persisted through the new provider. Chapter 2 — Forcing a rollout when configuration changes Because -injected values do not hot-reload, and because most applications cannot reload files anyway, the honest default is: treat a configuration change as a deployment. Two patterns make that reliable. Immutable ConfigMaps and Secrets Set (stable since Kubernetes 1.21). The object can then never be edited — only deleted and recreated under a new name. This removes an entire class of "someone edited the live ConfigMap and half the fleet is now on different config", and it also lets the kubelet stop watching the object, which measurably reduces API server load on large clusters. Kustomize's and Helm both have idioms for hash-suffixed names; a new hash produces a new object name, the Deployment template references the new name, and the template change triggers a rollout automatically. The checksum annotation When the ConfigMap name is fixed, put a hash of its content in the Pod template annotations. Changing an annotation on the template changes the template, which is exactly what makes the Deployment controller create a new ReplicaSet. Outside Helm, compute it in CI: > Trick: annotate the Pod template, not the Deployment's own . An annotation on the Deployment object changes nothing about the Pods and triggers no rollout. This is a very common and very confusing mistake. Chapter 3 — Storage Terminology - Volume — a directory available to the containers in a Pod, with a lifetime tied to the Pod. is scratch space that vanishes with the Pod; , , and are read-only data sources.- PersistentVolume (PV) — a cluster-scoped object representing a real piece of storage (an EBS volume, a Ceph RBD image, an NFS export).- PersistentVolumeClaim (PVC) — a namespaced request for storage: size, access mode, class. Pods reference PVCs, never PVs.- StorageClass — a named recipe describing how to provision a PV on demand: which provisioner, which parameters, which reclaim and binding policy.- CSI (Container Storage Interface) — the standard gRPC contract between Kubernetes and a storage vendor's driver. The indirection exists so that a workload author can ask for "20 GiB, fast, exclusive" without knowing whether the cluster runs on AWS, on-prem Ceph, or a laptop. Static versus dynamic provisioning Static: an administrator creates PVs by hand and users claim them. Necessary for pre-existing storage (an NFS export, a restored snapshot). Dynamic: the user creates a PVC naming a StorageClass, and the CSI driver provisions a matching PV automatically. Dynamic is the default in every managed cloud and is what you should use unless you have a specific reason not to. Access modes — and the mistake everyone makes | Mode | Short | Meaning ||------|-------|---------|| ReadWriteOnce | RWO | mounted read-write by one node (several Pods on that node may share it) || ReadOnlyMany | ROX | mounted read-only by many nodes || ReadWriteMany | RWX | mounted read-write by many nodes || ReadWriteOncePod | RWOP | mounted read-write by exactly one Pod (GA in Kubernetes 1.29) | The mistake: assuming RWX is available. It usually is not. Block storage — EBS, GCE PD, Azure Disk, most on-prem SANs — is RWO only, because a block device cannot safely be mounted read-write on two machines at once. RWX requires a file protocol: NFS, EFS, Azure Files, CephFS, Filestore. If your design has three replicas of a Deployment all writing to one shared volume, either budget for a networked filesystem (slower, more expensive, another thing to operate) or redesign so each replica owns its own volume — which is what a StatefulSet gives you. Note also that RWO is per node, not per Pod. Two Pods of the same Deployment that happen to land on the same node can both write to one RWO volume and corrupt each other. RWOP exists precisely to prevent that. Reclaim policy Set on the StorageClass (inherited by dynamically provisioned PVs) or directly on a static PV: - Delete — deleting the PVC deletes the PV and the underlying disk. The default for dynamic provisioning. Convenient; also how data gets destroyed by a careless .- Retain — the PV survives in state, the data stays, and an administrator must manually clean up or re-bind. The correct choice for anything you would be upset to lose.- Recycle — deprecated, do not use. > Watch out: for production databases, either use or make sure the StorageClass's behaviour is compensated by real, tested, off-cluster backups. "The PVC was deleted" should not be an unrecoverable event. volumeBindingMode and the zone-mismatch bug This setting fixes a failure that is baffling the first time you hit it. - — the PV is provisioned as soon as the PVC is created, before any Pod exists. In a multi-zone cluster the provisioner has to guess a zone. If the scheduler later places the Pod in a different zone, the Pod cannot mount the volume and stays forever with a event. Zonal block storage cannot cross zones.- — provisioning is deferred until a Pod that uses the PVC is scheduled. The scheduler picks a node first, considering all its normal constraints, and then the volume is created in that node's zone. Use on every zonal block-storage class. It is the default on modern managed clusters for exactly this reason. CSI in one paragraph Every storage integration is now an out-of-tree CSI driver: a controller Deployment that handles create/delete/attach and a node DaemonSet that handles mount/unmount, both speaking a standard gRPC interface. The in-tree cloud provider volume plugins have been migrated to CSI and removed. Practical consequences: driver features arrive on the vendor's schedule rather than Kubernetes releases; snapshots (, ), cloning, expansion (, then edit the PVC's requested size) and topology awareness are all standard CSI capabilities you can rely on if the driver advertises them. Chapter 4 — StatefulSets A Deployment's Pods are interchangeable and get random names. Some workloads cannot work that way: a Postgres replica must know it is the replica, a Kafka broker must keep its broker ID and its log directory, a Zookeeper ensemble must have stable peer addresses. Chapter 5 — DaemonSets, Jobs and CronJobs DaemonSet Runs exactly one Pod per node (optionally a filtered subset), and automatically adds a Pod when a node joins the cluster. This is the right shape for anything that is a property of the node rather than of the application: log collectors, metrics exporters (), CNI agents, CSI node plugins, security agents. Without the , a DaemonSet skips tainted nodes — usually the opposite of what a node agent wants. Taints and tolerations are covered in Post 06. Job Runs Pods until a specified number complete successfully, then stops. - + express a work queue or a fixed fan-out. With , each Pod knows which slice of work is its own — the cleanest way to shard a batch job without an external queue.- counts Pod failures, with exponential back-off between retries (10s, 20s, 40s, capped). Set it deliberately: on a job that fails deterministically wastes six retries and twenty minutes.- is the difference between a tidy cluster and 4,000 Pods.- The Pod-level must be or . > Trick: a Job with a sidecar used to hang forever, because the Job only completes when all containers exit and the sidecar never did. Use a native sidecar ( with , stable since 1.33 — Post 04): Kubernetes terminates it automatically once the main container finishes. CronJob Creates a Job on a schedule. matters more than it looks: - Allow (default) — a run that overruns its interval simply overlaps with the next one. Fine for idempotent work, catastrophic for a job that takes a lock or writes a shared file.- Forbid — skip the new run if the previous one is still going. The safe default for most reporting and maintenance jobs.- Replace — kill the running Job and start a fresh one. The missed-schedule trap The CronJob controller does not have perfect memory. When it wakes up, it counts the schedules it missed since it last ran. If it finds more than 100 missed schedules, it gives up entirely, schedules nothing, and records an event saying so — the CronJob then silently never fires again until it is edited or recreated. This happens after a long control-plane outage, after restoring an old cluster backup, or after a CronJob is created with a schedule in the past. interacts with this: if set, the controller only counts misses within that window, which keeps the count small and avoids the lockout — but it also means a run more than that many seconds late is dropped rather than started. Setting it to a value shorter than the controller's own check interval can cause runs to be missed altogether. > Watch out: always alert on "expected CronJob has not produced a successful Job in N intervals". Do not alert on the CronJob object being healthy — it looks perfectly healthy while firing nothing at all. Chapter 6 — Worked example: a stateful database with a headless Service Putting the pieces together: a three-member Postgres with per-Pod storage, stable DNS names, credentials from a Secret, and tuning from a ConfigMap. Two details in there are load-bearing and routinely omitted: - points at a subdirectory of the mount, not the mount root. Many block-storage volumes arrive with a directory, and Postgres refuses to initialise into a non-empty directory.- makes the kubelet chown the volume so the non-root database user can write to it. Without it the container starts and immediately dies on a permission error. What this manifest still does not give you: replication between the three members, promotion of a new primary when dies, backups, or point-in-time recovery. Those need an operator (CloudNativePG, Zalando Postgres Operator, Percona, or the vendor's own) or a managed service. A StatefulSet is the substrate, not the database platform. Chapter 7 — Should the database be on Kubernetes at all? The honest answer is "sometimes", and the reasoning matters more than the verdict. The case against - The failure modes are unfamiliar. A node drain, a spot-instance reclaim, a memory limit hit, an eviction under disk pressure, a CNI hiccup — each is routine for a stateless service and each is a potential data event for a database.- You are now operating two hard systems. Kubernetes upgrades every few months; the database has its own upgrade path. The intersection is where the incidents live.- Managed services are genuinely good. RDS, Aurora, Cloud SQL, Atlas and their peers give you backups, PITR, failover, patching and a support contract for a price that is usually less than the engineer-time you would spend replicating them badly.- Storage performance is a layer deeper. Network-attached block storage under a CSI driver under a container runtime has more moving parts and more tail latency than a local NVMe device. The case for - You already run Kubernetes for everything else, and the operational uniformity — same deploy pipeline, same secrets, same observability, same RBAC — is worth real money.- On-prem, sovereign or air-gapped requirements rule out managed services entirely.- A mature operator exists for your database. This is the pivotal question. CloudNativePG for Postgres, Strimzi for Kafka, the MongoDB and Percona operators, Vitess for MySQL — these encode failover, backup and upgrade as controllers. Running a database on Kubernetes with a mature operator is a different activity from running one with a hand-written StatefulSet.- Many identical database instances. Per-tenant or per-environment databases are exactly where declarative provisioning pays off. A decision rule | Situation | Reasonable call ||-----------|-----------------|| Managed service available, no sovereignty constraint, small team | Use the managed service. || Already deep in Kubernetes, mature operator exists, platform team on call | On Kubernetes, via the operator. || On-prem or air-gapped | On Kubernetes — it is likely the best option available || Small dataset, low QPS, one instance | plain VM or managed; the cluster adds cost without benefit || Hand-written StatefulSet, no operator, no runbook, production data | Do not. | For a fuller treatment of this exact trade-off in one ecosystem — operator choice, production checklist, cost and compliance — see , which covers the same decision for MongoDB with the concrete numbers and the operator landscape spelled out. Whatever you choose, the non-negotiables are the same: tested restores (not just backups), storage with a reclaim policy or an equivalent guard, a PodDisruptionBudget so a node drain cannot take quorum (Post 06), anti-affinity so replicas are not co-located, and monitoring that alerts on replication lag rather than on Pod count. MongoDB Course — 26 · OpenTelemetry Observability — Traces, Metrics, Logs, Correlation

When a request is slow, "is it Mongo?" is the question that wastes the most production time. OpenTelemetry (OTel) makes the answer obvious — every Mongo operation becomes a span attached to the request trace, with query shape, duration, target collection, and the surrounding service spans on the same timeline. Chapter 5 — Pods, ReplicaSets and Deployments Why the Pod, not the container A Pod is one or more containers that are scheduled together, share a network namespace and an IP address, can share volumes, and live and die as a unit. Chapter 5 — SBOMs, provenance, and signing SBOM A Software Bill of Materials lists every component in an artifact — OS packages, language dependencies, versions, licences. Two mainstream formats: SPDX (ISO standard, licence-focused) and CycloneDX (OWASP, security-focused). Either is fine; pick one and be consistent. Why it matters: when the next widely-exploited library CVE lands, the question "are we affected, and where?" becomes a query over stored SBOMs instead of a week of archaeology. It is also increasingly a procurement and compliance requirement. Provenance Provenance answers how the artifact was built: which source commit, which builder, which parameters. BuildKit emits it as an in-toto attestation (), and the SLSA framework defines levels for how tamper-resistant that claim is. Provenance produced by your CI, signed by your CI's identity, is what lets a policy say "only images built by this pipeline from this repository may run". Signing with cosign Classic key-based signing works, but key management is the hard part. Keyless signing (Sigstore) removes the long-lived key: your CI job authenticates with an OIDC token, Fulcio issues a short-lived certificate bound to that identity, the signature is recorded in the Rekor transparency log, and the certificate expires minutes later. > Watch out: with no identity flags checks only that a signature exists. Chapter 1 — Should you migrate? Honest answer first: most SQL workloads should stay on SQL. Migration is expensive + risky. Strong reasons to move: - Schema flexibility required (per-tenant custom fields, fast product iteration, polymorphic items).- Write throughput beyond what Postgres can vertical-scale.- Hierarchical / document-shaped data (forms, content, configs, complex products) that's painful to join.- Horizontal scaling + multi-region + sharding required.- Operational simplicity at low ops headcount (Atlas managed > self-hosted Postgres cluster). Weak reasons: - "NoSQL is modern."- "We want to avoid joins" (you'll write joins as either way).- "We need higher performance" (often a Postgres index would have fixed it). Often the right answer is migrate a subset — the parts where the document model genuinely fits — and keep the rest in Postgres. The two coexist via outbox / CDC / app-side composition. Always pick if the ASG is behind a load balancer.- Target groups — the ASG registers / deregisters instances automatically as they come and go. A minimal ASG runs on first boot — install your app, fetch config, register with discovery. Chapter 5 — Scaling policies Target tracking (start here) Pick a metric and a target; AWS adds/removes instances to keep the metric there. - "Average CPU = 50%" → scale out when > 50, in when < 50.- "ALB requests per target = 200" → scale to meet load. Step scaling Trigger at thresholds; add/remove a configurable count per step. Use when target tracking can't express the logic — e.g., asymmetric scale-out vs scale-in speeds. Scheduled Predictable patterns deserve scheduled scaling — flash sale, market open, weekday morning ramp. Trick: schedule warm-up 15 minutes before a known spike. EC2 + ASG instances take 1-3 minutes from request to "in service". Chapter 6 — Cooldowns, warm pools, instance refresh Cooldown A waiting period after a scaling action before evaluating again — prevents oscillation when metrics dip slightly post-action. Warm pool A pool of pre-initialised but stopped instances. When the ASG needs to scale, it starts (rather than provisions) one — seconds vs minutes. Cost: EBS storage of the warm instances. Instance refresh When you publish a new launch-template version (new AMI, new user-data), rolls existing instances out in batches. Pair with ALB weighted target groups or canary listener rules for safe rollouts. Chapter 7 — The textbook 3-tier reference Tier rules:- ALB lives in public subnets across ≥ 2 AZs.- App tier lives in private subnets across the same AZs.- DB tier lives in isolated subnets, accessible only from the app SG.- Each tier's security group only accepts traffic from the tier above's SG.- Outbound from app tier to internet via NAT (only for pulling packages, calling external APIs). This shape survives:- a single instance failure (ASG replaces it)- a single AZ failure (other AZs absorb traffic)- a deploy with bad code (canary catches it; instance refresh rolls back)- a traffic spike (ASG scales out) Chapter 8 — Cost considerations | Item | Approx (us-east-1) ||------|---------------------|| ALB | USD 16 / month base + LCU hours || NLB | USD 16 / month + NLCU || Data transfer out | USD 0.09/GB after 100 GB free || EC2 t3.micro | USD 7.50 / month at 24/7 on-demand || NAT gateway | USD 32 / month + USD 0.045 / GB processed || RDS db.t4g.micro multi-AZ | USD 25-30 / month | A minimal 3-tier shop: ASG of 2 × t3.micro + ALB + RDS Multi-AZ + 1 NAT ≈ USD 100 / month before traffic. Per-AZ NATs add USD 32 each for HA. Watch out: ALB LCU (Load Balancer Capacity Units) is metered on connections, requests, processed bytes, and rule evaluations. A high-traffic ALB can cost more than the EC2 behind it. Chapter 9 — Beyond EC2 + ASG Modern compute alternatives to consider for the app tier: - ECS Fargate — containers without managing EC2 hosts.- EKS — Kubernetes managed control plane.- App Runner — push a container, AWS does the rest.- Lambda behind ALB — short-lived, infrequent endpoints (Post 05). EC2 + ASG remains right when you need OS access, GPU, NVMe, or want the lowest level of abstraction. Otherwise consider going up the stack — Post 05 covers serverless, future posts cover containers.
