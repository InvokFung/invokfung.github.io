MongoDB Course — 11 · Sharding — mongos, Shard Keys, Chunks, Balancer, Resharding
Created2025-04-19|Database MongoDB
A single replica set scales reads (Post 10) and stores as much data as fits on one machine. To scale writes and store more data than one machine can hold, MongoDB shards — partitions a collection across multiple replica sets ("shards") by a chosen shard key. Get the shard key right and the cluster scales linearly. Get it wrong and you get hot shards, jumbo chunks, scatter-gather queries, and an expensive resharding project. This post covers the architecture, the shard-key decision (the most important one), ranged vs hashed sharding, chunks + balancer, zones, resharding (5.0+), and query targeting vs scatter-gather. > Series map: 00 Foundations → … → 10 Replica Sets → 11 Sharding (this post) → 12 Change Streams → … → 17 Drivers & Case Studies. Learning Outcome - Explain , config servers, shards.- Choose a shard key by cardinality, frequency, monotonicity.- Pick between ranged and hashed sharding.- Read chunk + balancer state; understand jumbo chunks.- Use zone sharding for region pinning / tiered storage.- Recognise when to use resharding (5.0+).- Recognise query targeting vs scatter-gather. Chapter 1 — Sharded-cluster architecture - — stateless router. Clients connect to it. Routes operations to the right shard(s) by reading metadata.- Config servers — a dedicated replica set storing the chunk map, shard list, indexes metadata.- Shards — each shard is itself a full replica set (HA at the shard level). Atlas: when you scale a cluster to "sharded", it builds all of this for you. Chapter 2 — Sharding a database + collection Once sharded, the chunk map ranges are built on the shard key. What gets sharded - Per collection. Different collections can have different shard keys (or none).- Some collections often stay unsharded — small, infrequently-written ones. Chapter 3 — Shard key — the most important decision A shard key is one or more fields whose value decides which shard each document lives on. Three properties to evaluate | Property | Good | Bad ||----------|------|-----|| Cardinality | many distinct values | few values || Frequency | values appear with similar frequency | one value dominates || Monotonicity | random-looking distribution | always-increasing (, timestamps) | Why each matters - Low cardinality — too few values to spread across many shards. A shard key over gives 2 chunks max; can't scale beyond 2 shards.- Skewed frequency — one tenant or one product dominates → one shard takes all writes (hot shard).- Monotonic key (auto-increment ID, timestamp) → all new writes hit the chunk holding the max value → that chunk's shard becomes hot. The ideal A field that's:- many distinct values,- writes spread evenly,- frequently appears in queries' filters so can route to one shard. Common shard-key choices | Workload | Good shard key ||----------|----------------|| Multi-tenant SaaS | (tenant-aware queries route to one shard) || User-centric (orders per user) | || IoT telemetry, write-heavy | (even distribution) || Time-series append | hashed on + ranged on time secondary; OR native time-series collection || Geo-partitioned | + zone sharding | A compound shard key () gives tenant-aware routing (tenantid used by queries) while keeping cardinality high (via tiebreaker). Chapter 4 — Ranged vs hashed sharding Ranged (default) Documents with shard-key values in a range live on the same chunk. - Pro: range queries on the shard key only hit shards in that range.- Con: monotonic inserts hot-spot the max-range chunk. Hashed The shard key is hashed before placement. - Pro: writes always spread evenly across shards, even for monotonic / sequential keys.- Con: range queries on the shard key become scatter-gather (visit every shard). Modern compound hashed (4.4+): Hashed on , ranged on as secondary — combines distribution + time-range-by-device queries. Chapter 5 — Chunks + the balancer A chunk is a range of shard-key values. Each chunk lives entirely on one shard. Chunk size defaults to 128 MB in modern versions. The balancer is a background process on the primary config server that moves chunks between shards to keep distribution roughly even. Runs continuously; can be scheduled to a window: Inspect chunk distribution: Jumbo chunks A chunk exceeding the chunk size that can't be split (because all its documents have the same shard-key value) is called jumbo and is marked unmovable. The balancer skips it. Cause: too few distinct values for the shard key (low cardinality) — usually a sign the shard key was wrong. Fix: re-shard the collection (Chapter 7); or pre-split with care. Chapter 6 — Zones (formerly tags) Pin specific shard-key ranges to specific shards. Used for: - Region pinning — APAC users on APAC shards (low-latency reads + compliance).- Tiered storage — recent data on SSD shards, archive on cheap shards. The balancer respects zones — chunks in a tagged range move only to shards with the matching tag. Chapter 7 — Resharding (5.0+) Pre-5.0, changing a shard key meant dumping the collection, dropping, and reinserting under a new shard key — multi-hour outage for big collections. 5.0+ introduced online resharding: The new shard key is computed; chunks rebalance in the background; clients keep reading + writing throughout. Final cutover is brief. Constraints: - Disk + I/O cost is high; plan for a slower-than-usual period.- Some prerequisites on indexes + collection size.- The new shard key must have an index. This dramatically lowered the cost of "I chose the wrong shard key" — but a good initial choice still saves time + money. Chapter 8 — Query targeting vs scatter-gather When a query includes the shard key, can route to one (or few) specific shards. Otherwise it has to ask every shard ("scatter") and merge results ("gather"). Scatter-gather scales poorly as the cluster grows — adding a shard makes scatter-gather queries slower, not faster. Check with explain (sharded version): > Trick: the hot path of every endpoint should include the shard key in its filter. Reports + admin queries can scatter-gather. Plan your access patterns accordingly when picking a shard key. Chapter 9 — Aggregation + sharding Most aggregation stages run per shard, then merges. Some stages must run after the merge (, final , against an unsharded collection). Implications: - early — lets shards drop docs before pulling them to mongos.- foreign collection should be unsharded (sharded works but is slower).- / to a sharded target — supported since 4.4 / 5.0. shows the split between stages and stages. You pick a shard key in the UI; resharding is a one-click operation. Connection string remains — routing is invisible to clients. Chapter 11 — When to shard (and when not) Shard when - Single replica set's CPU / disk / RAM is the bottleneck and vertical scaling is exhausted.- Working-set (hot indexes + frequently-accessed docs) exceeds RAM, even at maximum instance size.- Write throughput needed exceeds what one primary can sustain.- Data set exceeds biggest available single-instance storage.- Regulatory / latency requirement to keep data in specific regions. Don't shard when - Single replica set still handles your load (most apps' entire lifecycle).- Working-set fits in RAM on a larger instance.- Sharding overhead (extra hops via , complexity, cost) doesn't pay back. Vertical scaling beats horizontal scaling until you have no choice — modern Atlas tiers go to many TB of RAM. Most apps never shard. MongoDB Course — 10 · Replica Sets — Primary, Secondary, Oplog, Elections
Created2025-04-13|Database MongoDB
A single is a single point of failure. A replica set is a group of processes that maintain copies of the same data and automatically elect a new primary when one fails. Three or more members get you durability, automatic failover, optional read scaling on secondaries, and zero-downtime maintenance. This post covers the architecture, the oplog, election protocol, write-concern interaction with replication, secondary read trade-offs, and the canonical 3-member + arbiter topologies. > Series map: 00 Foundations → … → 09 Transactions → 10 Replica Sets (this post) → 11 Sharding → 12 Change Streams → … → 17 Drivers & Case Studies. Learning Outcome - Explain PRIMARY / SECONDARY / ARBITER roles.- Initiate a replica set and inspect .- Read the oplog and understand replication lag.- Force an election + observe automatic failover.- Configure priorities, hidden members, delayed members.- Pick the right topology for your durability + cost target. Chapter 1 — Why replication Three things at once: 1. Durability — N copies of the data; loss of one server doesn't lose data.2. High availability — automatic failover; clients reconnect to a new primary in seconds.3. Read scaling (optional) — secondaries serve eventual-consistent reads. Replication doesn't scale writes — every write still goes through one primary. For write scaling, you shard (Post 11) on top of replica sets. Chapter 2 — Member roles | Role | Receives writes | Serves reads | Votes in election | Holds data ||------|------------------|---------------|--------------------|-------------|| PRIMARY | yes (only one at a time) | yes | yes | yes || SECONDARY | replicates from primary's oplog | yes (with etc.) | yes | yes || ARBITER | no | no | yes | no — voting only || HIDDEN | no | no (invisible to drivers) | yes | yes (backups, analytics) || DELAYED | no | no | yes | yes (lags primary by N seconds — disaster recovery) | A typical minimal production set: 3 data-bearing members (1 primary + 2 secondaries). Loss of any one keeps a majority alive. Avoid: - Even number of voting members without an arbiter → election can split. Always odd.- Arbiter-only failover safety in 2026 → arbiters can't vote on majority writes; prefer a 3-data-member setup unless cost-constrained. (See "election + write concern" pitfall in Chapter 8.) Chapter 3 — Initiate a replica set (local) Connect to one + initiate: Within a second or two, one member is PRIMARY, the other two are SECONDARY. In Atlas, every cluster is already a replica set — you don't initiate manually. Chapter 4 — Connection string for a replica set The driver:- Reads the seed list (your hosts).- Polls each to discover the full topology and the current primary.- Re-discovers automatically on failover. You only need to list a few seed hosts — the driver finds the rest. The SRV form (Atlas) returns the full member list via DNS, so the URI stays short. Chapter 5 — The oplog The oplog is a capped collection () on every replica-set member that records every write applied. Secondaries tail it and replay it to stay in sync. Each entry: timestamp, operation type (insert/update/delete), namespace, document or update spec. Oplog size matters Default size: 5 % of free disk (with a 50 GB upper cap on most platforms). If a secondary falls behind by more oplog entries than fit, it goes STALE and must do a full resync — slow. Tune via at start, or admin command. Atlas auto-sizes. > Trick: if you regularly run multi-hour ingest jobs while secondaries catch up, increase oplog size. The "1 day of writes fits" rule of thumb prevents most stale-member surprises. Chapter 6 — Replication mechanics + lag 1. Client writes to PRIMARY.2. PRIMARY records the write to its own oplog and applies it.3. Each SECONDARY tails the primary's oplog and applies in order.4. Once a majority of voters have applied the write, it's "majority committed". Replication lag = how far behind the primary a secondary is in oplog time. Inspect: Causes of lag: - Big write spike (secondaries can't keep up).- Slow disk on a secondary.- Network latency (especially across regions).- Long oplog entries (huge updates). Persistent lag > a few seconds = warning. Lag growing unbounded = crisis (eventually goes STALE). Chapter 7 — Elections If the PRIMARY becomes unreachable, voting members hold an election (under the hood: Raft-like protocol Version 1, "PV1"). Steps: 1. A secondary that hasn't heard from the primary for (default 10 s) calls an election.2. Other voting members vote yes if the candidate's oplog is up-to-date enough.3. Majority of votes → new PRIMARY.4. Drivers detect the change via heartbeats; subsequent writes go to the new primary. Typical failover: 10-20 seconds for clients to reconnect; retryable writes (Post 08) hide most of the disruption. Force a manual failover (test) A useful production drill — practise failover under controlled conditions. Chapter 8 — Write concern + replica sets Recap from Post 08 — write concern interacts with replication: | | Meaning ||-----|---------|| 0 | fire-and-forget || 1 | primary acked || | majority of voters acked || N | exactly N members acked | is the production-correct default — guarantees the write survives the primary failing (because at least one surviving voter has it). Arbiter pitfall If you have a 2-data + 1-arbiter set (total 3 voters, majority = 2), arbiters can vote in elections but don't store data. A write reaching only the primary + the arbiter (waiting for the second data member) can be lost in failover. Modern guidance: avoid arbiters in 2026 for any system where data loss isn't acceptable. Use 3 data-bearing members.
