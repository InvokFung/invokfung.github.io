MongoDB Course — 09 · Multi-Document Transactions
Created2026-06-18|Database MongoDB
MongoDB has had multi-document ACID transactions since 4.0 (replica sets) and 4.2 (sharded clusters). They look like SQL transactions (), behave like SQL transactions (snapshot isolation), and carry SQL-like costs (locking, latency, contention). This post covers how to use them safely — sessions, retry on transient errors, abort vs commit, the limits — and the more important question: when NOT to reach for a transaction (in MongoDB, the answer is "more often than you think"). > Series map: 00 Foundations → … → 08 Connection Pool & Concurrency → 09 Transactions (this post) → 10 Replica Sets → … → 17 Drivers & Case Studies. Learning Outcome - Start, commit, and abort a multi-document transaction.- Handle transient transaction errors with a retry loop.- Understand snapshot isolation + transaction limits (60 s, 16 MB).- Recognise when a transaction is the right tool — and when single-doc atomicity or schema redesign is better. Chapter 1 — Why transactions in MongoDB Single-document updates are already atomic in MongoDB — that's true for any update operator on one document, no transaction needed. Transactions matter when you need atomicity across multiple documents (possibly across multiple collections, possibly across multiple shards): - Transfer money between two accounts.- Decrement stock + insert an order line.- Update a parent + add to its children collection consistently. Before 4.0, the workaround was the two-phase commit pattern in application code — verbose and error-prone. Transactions replaced that for most use cases. Chapter 6 — Read-then-write inside transactions The double safeguard (in-app check + filter condition) handles the race where another transaction modifies stock between your read and your write. Without a transaction, you could still do this with optimistic check on the filter — the transaction adds atomicity across the insert and the decrement plus a snapshot view. Chapter 7 — When NOT to use transactions Transactions are powerful + tempting, but expensive. Cheaper alternatives: Single-document atomicity (free) The whole update is atomic. If the filter doesn't match (balance < 100), nothing changes. Most "decrement counter, reject if would go negative" problems collapse to this one statement. Embed instead of reference If you find yourself in a transaction across + , ask whether the children should be embedded in the parent (Post 07). A single update on an embedded array is atomic, no transaction needed. Idempotent retries If the operation is idempotent, just retry on failure. No transaction needed — eventual consistency settles. Choreography (sagas) for distributed flows For long-running cross-service flows (order → payment → shipping), use a saga / compensating action pattern. Transactions don't help across systems. Compute + materialise Materialised views via (Post 06) or change-stream-driven sync (Post 12) replace many "update two collections at once" cases. > Trick: before reaching for a transaction, ask: "Can a single-document update with a filter condition serve this?" Answer is yes 70-80 % of the time. Chapter 8 — Sharded transactions Cross-shard transactions work since 4.2. They use a two-phase commit under the hood, so they're slower than single-shard. Performance tips: - Design schema so transactions hit one shard whenever possible.- Choose the shard key carefully — a transaction touching docs on the same shard key value stays single-shard.- Distributed transactions across many shards multiply latency by the number of shards. If your design requires frequent cross-shard transactions, the schema or shard-key choice may be wrong. MongoDB Course — 08 · Connection Pool, Concurrency, Write/Read Concern

A MongoDB driver doesn't open a connection per query — it holds a pool and checks them out. How big the pool is, how long checkouts wait, what write durability you ask for (write concern), what read freshness you tolerate (read concern), and where reads go (read preference) — these settings decide whether your app sustains 100 req/sec or 100k req/sec, and whether a failover costs you data. Chapter 1 — The MongoClient lifecycle A is thread-safe, long-lived, and pooled. Create once per process; reuse for every operation. Wrong pattern (anti-pattern): per request. Each instantiation opens new sockets, runs handshakes, and exhausts server-side connection limits. Across a fleet this is a #1 outage cause. Same rule across languages — (Node, Python sync), (Python async), (Go), (.NET) — all are pooled + thread-safe singletons. Chapter 1 — The draw-call budget Every in the scene typically produces one draw call. Each draw call has CPU overhead: bind shader, set uniforms, set attribute pointers, issue the GPU command.
