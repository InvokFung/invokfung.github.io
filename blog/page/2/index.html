Dev Essentials — 17 · How LLMs Work in Practice — Tokens, Context, Sampling and Embeddings
Created2026-08-12|Dev Essentials
A large language model (LLM) reads text as tokens and predicts the next token, again and again. That one idea explains most of the surprises developers meet: why a prompt costs what it costs, why a long chat "forgets" how it started, why the same question gets two different answers, and why a model can state a false fact with full confidence. This post builds the mental model step by step: tokens, the transformer, training, the context window, sampling and embeddings. Then it covers hallucinations and three API features you will meet everywhere. It opens Part D, and the next two posts build on it. The ideas apply to every vendor; the runnable examples use Python, NumPy, and the Anthropic Python SDK. > Series map: 01 Text Encoding → … → 16 CI/CD → 17 How LLMs Work (this post) → 18 Coding with AI Agents → … → 24 Desk Health. Part D · AI tools. Learning Outcome - Explain what a token is, why tokens are not words, and why code and non-English text often cost more.- Train a toy BPE tokenizer, and count real tokens with Anthropic's token-counting endpoint.- Describe next-token prediction and attention at an intuition level.- Name the training stages: pretraining, instruction tuning, and preference training (RLHF, AI feedback).- Explain the context window, what fills it, and what happens when a request is too big.- Use temperature, top-k and top-p correctly, and know which current models still accept them.- Turn text into embeddings and compare them with cosine similarity.- Explain why hallucinations happen, and reduce them.- Recognise prompt caching, tool use and extended thinking in an API. Chapter 1 — Tokens and tokenizers Setup You need Python 3.10 or newer (the 1.x SDK requires it) and, for the API examples, a key from the Anthropic Console. Terminology | Term | Meaning ||------|---------|| Token | One chunk of text from the model's fixed list: a word, part of a word, a space plus a word, a symbol, or a byte. || Vocabulary | The fixed list of all tokens a model knows. Each token has an integer ID. || Tokenizer | The program that turns text into token IDs and back. It is fixed before training. || BPE | Byte Pair Encoding: build a vocabulary by merging the most frequent neighbouring pieces, over and over. | Tokens are not words The model never sees letters or words. It sees a list of integers. A common word may be one token; a rare word may be three or four. Spaces, punctuation and line breaks use tokens too. A rule of thumb from Anthropic's models page (vendor spec, September 2026): on the tokenizer Claude has used since Claude Opus 4.7, 1M tokens is roughly 555k English words, or 2.5M Unicode characters. Earlier models fit about 750k words in 1M tokens. So the same text gives a different count on a different model. Tokens matter because almost every limit uses them: price (per million input and output tokens), the context window (Chapter 4), (the cap on what the model writes) and rate limits. BPE in one example Byte Pair Encoding was brought into neural machine translation by Sennrich, Haddow and Birch (ACL 2016) to handle rare words as sequences of smaller units. Training: split every word into characters, count every neighbouring pair, merge the most frequent pair, repeat. Tokenizing: replay the merges in the same order. Many modern tokenizers run the same idea on UTF-8 bytes, so any text can be encoded (see Dev Essentials 01 · Text Encoding). Output: is common, so it becomes one token. never appeared, so it breaks into known pieces plus single letters. Common text becomes few tokens. Rare text becomes many. Why code and non-English text often cost more Merges are learned from the tokenizer's training data. Whatever is common there gets long tokens. - Non-English text. Petrov et al. (NeurIPS 2023) tokenized the same text translated into many languages and found lengths that differ by up to 15 times in some cases (independent measurement). A Chinese character is also 3 bytes in UTF-8, so a byte-level tokenizer starts from more pieces.- Code. The Codex paper (Chen et al., 2021) found the GPT-3 text tokenizer "not very effective for representing code", with whitespace the largest waste. Adding tokens for runs of spaces cut code token counts by about 30% (vendor research paper). Measure your own data instead of trusting a rule of thumb. Anthropic's token-counting endpoint is free (rate-limited by usage tier) and returns an estimate for the exact model you name: A higher means that kind of text is packed more tightly. Each count includes a few tokens of message framing, which is why the samples repeat 20 times. For scale, the docs show a tiny request (system "You are a scientist", message "Hello, Claude") counting as on . > Trick: count with both model IDs before you switch models. Anthropic's docs say Claude 4.7 and later models use a newer tokenizer that produces about 30% more tokens for the same text (vendor spec). Budgets and cost estimates move with it. Chapter 2 — Next-token prediction and the transformer Every LLM answer comes from the same loop: 1. Turn the prompt into token IDs.2. Run them through the network. It returns one score (a logit) per vocabulary token.3. Turn the scores into probabilities and pick one token (Chapter 5).4. Append it and repeat. Stop at an end token, a stop sequence or . Attention, at intuition level Almost every modern LLM is a transformer, from "Attention Is All You Need" (Vaswani et al., 2017). Its key part is self-attention: for each token, the model decides how much each earlier token matters right now. In "The animal didn't cross the street because it was tired", attention lets "it" pull in information from "animal". Each token makes a query (what am I looking for?), a key (what do I contain?) and a value (what do I pass on?): $$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{dk}}\right)V$$ For text generation, a causal mask stops each token from looking at later tokens. Real models stack many such layers, each with several attention "heads". What this means for you: - Output is written one token at a time, which is why APIs offer streaming. On Anthropic's current price list, output tokens cost five times as much as input tokens.- The model cannot go back. An early wrong token shapes everything after it. Reasoning before answering helps (Chapter 8).- Long inputs cost more compute. The paper lists self-attention cost per layer as $O(n^2 \cdot d)$ for sequence length $n$. Preference training. InstructGPT (Ouyang et al., 2022) describes classic RLHF: supervised fine-tuning on labeller demonstrations, then a reward model trained on rankings of model outputs, then reinforcement learning against it. Constitutional AI (Bai et al., 2022) replaces much human labelling for harmlessness: the model critiques and revises its own answers against written principles, and a preference model trained on AI comparisons gives the reward (RLAIF). Chapter 4 — The context window The context window is everything the model can read while writing a response, including the response itself. Anthropic's docs call it the model's "working memory". It counts the system prompt, every message (including tool results, images and documents), tool definitions, and this turn's output including any thinking. The API is stateless. The model does not remember your last request, so a chat app resends the whole history every turn. Turn 10 pays for turns 1 to 9 again (Exercise 4 does the maths). Sizes change often. As of September 2026 (vendor spec), current Claude Opus, Sonnet and Fable models have a 1M-token window and up to 128k output tokens per request; Claude Haiku 4.5 has 200k and 64k. Temperature $T$ divides the logits first: $$pi = \frac{e^{zi / T}}{\sumj e^{zj / T}}$$ $T < 1$ sharpens the distribution, $T > 1$ flattens it, and as $T$ approaches 0 sampling approaches greedy decoding (always the top token). Why the same prompt gives different answers: above temperature 0 every token is a random draw, and one different early token changes everything after it. Even at 0, Anthropic's API reference says results will not be fully deterministic. Chapter 7 — Why hallucinations happen and how to reduce them A hallucination is fluent, confident text that is false or not supported by the given sources. Causes: - The goal is a plausible next token, not a true statement. A made-up citation can look very plausible.- Training and tests reward guessing. Kalai et al. (2025, "Why Language Models Hallucinate") argue that training and evaluation reward guessing over admitting uncertainty, like an exam with no penalty for wrong answers.- Missing knowledge: after the cutoff, private, or rare.- Missing or buried context: not in the prompt, or lost in a very long one. Fixes. Chapter 2 — Storing passwords Never plain text, never reversible encryption If you store passwords as plain text, one database leak exposes every user — and most users reuse passwords on other sites. Encryption is not the answer either. Encrypted data can be decrypted, so whoever steals the key gets every password back. You want a one-way function: easy to check a guess, impossible to reverse. That is a hash. But not any hash. Why SHA-256 is the wrong hash SHA-256 and MD5 are built to be fast. A modern GPU can compute billions of them per second. If an attacker steals your table of SHA-256 password hashes, they hash every word from a big list of leaked passwords and compare. Password hashing functions are built to be slow and memory-hungry on purpose. One login costs your server a fraction of a second. For an attacker trying billions of guesses, the same cost becomes enormous. Being memory-hard matters too: GPUs have many cores but little memory per core, so a hash that needs many MiB per guess slows them down. Salt and pepper - Salt — a random value, different for every password, stored next to the hash. Two users with the same password get different hashes, and precomputed tables ("rainbow tables") become useless. Modern libraries make and store the salt for you.- Pepper — one secret value shared by all passwords, stored outside the database (a secrets manager or an HSM). OWASP says a pepper "should not be stored along with the generated hash". If only the database leaks, the hashes cannot be cracked without it. A pepper is defence in depth, not a replacement for a slow hash.
