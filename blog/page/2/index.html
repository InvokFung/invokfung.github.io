Dev Essentials — 14 · API Reliability — Timeouts, Retries with Backoff, Idempotency, Rate Limits and Queues

Every call over a network can be slow, can fail, or can fail in a way where you do not know if it worked. Chapter 1 — How remote calls fail A function call inside one process either returns or throws. A call over a network has more outcomes: | Failure | What you see | Example ||---------|--------------|---------|| Slow | The call takes 30 s instead of 30 ms | Database is overloaded, a GC pause, a long queue || Down | Connection refused, DNS error, connect timeout | Service crashed, wrong port, network cut || Partial failure | Some calls work, some fail | One of five servers is broken; one region is down || Unknown outcome | A timeout after the request was sent | timed out. Was the card charged? | The last one is the hard case. The request may have reached the server and run. Only the reply was lost. If you retry blindly, you may do the action twice. If you do not retry, the action may never happen. Most of this post is about handling this case safely. Chapter 8 — Queues, at-least-once delivery and the outbox Load levelling If work does not need an answer right now (send an email, resize an image), put it on a queue. The API replies at once; workers take jobs at their own pace. A traffic spike makes the queue longer, not the servers slower. On AWS this is SQS (see AWS Course 05 · Serverless & Events). At-least-once means duplicates SQS standard queues keep copies of each message on several servers. The SQS docs say you may rarely receive a message again, and tell you to design your application to be idempotent. Many queues work this way. A worker can also crash after doing the work but before it deletes the message, so the message comes back. So every consumer must be idempotent. The usual method: each message carries a unique ID; the consumer records processed IDs and skips any ID it has seen. Exercise 6 builds this with SQLite. > Watch out: the side effect and the "processed" record must be saved together, in one database transaction. If you save the effect, crash, and never save the ID, the redelivered message runs again. Dead-letter queues Some messages always fail (bad data, a bug). Without a limit, they loop forever. The outbox pattern A classic bug: save an order to the database, then publish an "order created" event. If the process dies between the two steps, the event is lost. The outbox pattern writes the event into an table in the same transaction as the order. A separate relay reads the outbox and publishes. The relay may publish twice, so consumers must still be idempotent. MongoDB Course 20 · Outbox Pattern builds this step by step. A cache keeps a copy of something that was expensive to get, so the next request is fast. Caches sit everywhere between a user and your database: in the browser, on a CDN, in a reverse proxy, in your process, in Redis, and inside the database itself. This post shows what each layer is for, how HTTP cache headers really work (with demos against a tiny local server), the standard application patterns, how to invalidate safely, and how to stop a cache stampede. Chapter 1 — Why cache, and what it costs Without a cache, every request pays the full price: a network round trip, a database query, a template render. With a cache, most requests pay a lookup instead. The share of requests answered from the cache is the hit ratio (). A cache with a 95% hit ratio sends only 1 request in 20 to the slow system behind it. Caching is never free: | Cost | What goes wrong ||------|-----------------|| Staleness | The copy is older than the truth. Chapter 2 — Storing passwords Never plain text, never reversible encryption If you store passwords as plain text, one database leak exposes every user — and most users reuse passwords on other sites. Encryption is not the answer either. Encrypted data can be decrypted, so whoever steals the key gets every password back. You want a one-way function: easy to check a guess, impossible to reverse. That is a hash. But not any hash. Why SHA-256 is the wrong hash SHA-256 and MD5 are built to be fast. A modern GPU can compute billions of them per second. If an attacker steals your table of SHA-256 password hashes, they hash every word from a big list of leaked passwords and compare. Password hashing functions are built to be slow and memory-hungry on purpose. One login costs your server a fraction of a second. For an attacker trying billions of guesses, the same cost becomes enormous. Being memory-hard matters too: GPUs have many cores but little memory per core, so a hash that needs many MiB per guess slows them down. Salt and pepper - Salt — a random value, different for every password, stored next to the hash. Two users with the same password get different hashes, and precomputed tables ("rainbow tables") become useless. Modern libraries make and store the salt for you.- Pepper — one secret value shared by all passwords, stored outside the database (a secrets manager or an HSM). OWASP says a pepper "should not be stored along with the generated hash". If only the database leaks, the hashes cannot be cracked without it. A pepper is defence in depth, not a replacement for a slow hash.
