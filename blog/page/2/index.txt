That one idea explains most of the surprises developers meet: why a prompt costs what it costs, why a long chat "forgets" how it started, why the same question gets two different answers, and why a model can state a false fact with full confidence. This post builds the mental model step by step: tokens, the transformer, training, the context window, sampling and embeddings. Then it covers hallucinations and three API features you will meet everywhere. It opens Part D, and the next two posts build on it. The ideas apply to every vendor; the runnable examples use Python, NumPy,  and the Anthropic Python SDK.

Chapter 1 — Tokens and tokenizers

Setup

You need Python 3.10 or newer (the  1.x SDK requires it) and, for the API examples, a key from the Anthropic Console.

Terminology

| Term | Meaning ||------|---------|| Token | One chunk of text from the model's fixed list: a word, part of a word, a space plus a word, a symbol, or a byte. || Vocabulary | The fixed list of all tokens a model knows. Each token has an integer ID. || Tokenizer | The program that turns text into token IDs and back. It is fixed before training. || BPE | Byte Pair Encoding: build a vocabulary by merging the most frequent neighbouring pieces, over and over. |

Tokens are not words

The model never sees letters or words. It sees a list of integers. A common word may be one token; a rare word may be three or four. Spaces, punctuation and line breaks use tokens too.

A rule of thumb from Anthropic's models page (vendor spec, September 2026): on the tokenizer Claude has used since Claude Opus 4.7, 1M tokens is roughly 555k English words, or 2.5M Unicode characters. Earlier models fit about 750k words in 1M tokens. So the same text gives a different count on a different model.

Tokens matter because almost every limit uses them: price (per million input and output tokens), the context window (Chapter 4),  (the cap on what the model writes) and rate limits.

BPE in one example

Byte Pair Encoding was brought into neural machine translation by Sennrich, Haddow and Birch (ACL 2016) to handle rare words as sequences of smaller units. Training: split every word into characters, count every neighbouring pair, merge the most frequent pair, repeat. Tokenizing: replay the merges in the same order. Many modern tokenizers run the same idea on UTF-8 bytes, so any text can be encoded (see Dev Essentials 01 · Text Encoding).

Why code and non-English text often cost more

Merges are learned from the tokenizer's training data. Whatever is common there gets long tokens.

- Non-English text. Petrov et al. (NeurIPS 2023) tokenized the same text translated into many languages and found lengths that differ by up to 15 times in some cases (independent measurement). A Chinese character is also 3 bytes in UTF-8, so a byte-level tokenizer starts from more pieces.- Code. The Codex paper (Chen et al., 2021) found the GPT-3 text tokenizer "not very effective for representing code", with whitespace the largest waste. Adding tokens for runs of spaces cut code token counts by about 30% (vendor research paper).

Chapter 2 — Next-token prediction and the transformer

Every LLM answer comes from the same loop:

1. Turn the prompt into token IDs.2. Run them through the network. It returns one score (a logit) per vocabulary token.3. Turn the scores into probabilities and pick one token (Chapter 5).4. Append it and repeat. Stop at an end token, a stop sequence or .

A real LLM looks at all earlier tokens, its probabilities come from billions of learned parameters, and it works on subword tokens. The loop is the same.

Attention, at intuition level

Almost every modern LLM is a transformer, from "Attention Is All You Need" (Vaswani et al., 2017). Its key part is self-attention: for each token, the model decides how much each earlier token matters right now. In "The animal didn't cross the street because it was tired", attention lets "it" pull in information from "animal". Each token makes a query (what am I looking for?), a key (what do I contain?) and a value (what do I pass on?):

$$\text{Attention}(Q, K, V) = \text{softmax}\left(\frac{QK^T}{\sqrt{dk}}\right)V$$

For text generation, a causal mask stops each token from looking at later tokens. Real models stack many such layers, each with several attention "heads".

What this means for you:

- Output is written one token at a time, which is why APIs offer streaming. On Anthropic's current price list, output tokens cost five times as much as input tokens.- The model cannot go back. An early wrong token shapes everything after it. Reasoning before answering helps (Chapter 8).- Long inputs cost more compute. The paper lists self-attention cost per layer as $O(n^2 \cdot d)$ for sequence length $n$.

Chapter 3 — Training stages (high level)

| Term | Meaning ||------|---------|| Pretraining | Next-token prediction on a huge text corpus. Produces a base model. || Instruction tuning (SFT) | Supervised fine-tuning on example requests with good answers. || Reward model | A model trained to score answers, from human rankings. || RLHF / RLAIF | Reinforcement learning from human / AI feedback. |

This is deliberately high level: labs combine and change these steps, and full recipes are not published.

1. Pretraining. The model learns to predict the next token over a very large text collection. It picks up grammar, facts, code patterns and reasoning habits, but does not reliably follow instructions yet.2. Instruction tuning. Fine-tuning on demonstrations: a request, then a good response.3. Preference training. InstructGPT (Ouyang et al., 2022) describes classic RLHF: supervised fine-tuning on labeller demonstrations, then a reward model trained on rankings of model outputs, then reinforcement learning against it. Constitutional AI (Bai et al., 2022) replaces much human labelling for harmlessness: the model critiques and revises its own answers against written principles, and a preference model trained on AI comparisons gives the reward (RLAIF).

In practice:

- Knowledge has a cutoff. Anthropic lists a "reliable knowledge cutoff" per model (vendor spec): for example Feb 2025 for Claude Haiku 4.5 and Jun 2026 for Claude Opus 5.5.- The model knows nothing about your private code or data. You supply it through context: prompts, files, retrieved documents (post 19), tool results (post 18).

Chapter 4 — The context window

The context window is everything the model can read while writing a response, including the response itself. Anthropic's docs call it the model's "working memory". It counts the system prompt, every message (including tool results, images and documents), tool definitions, and this turn's output including any thinking.

The API is stateless. The model does not remember your last request, so a chat app resends the whole history every turn. Turn 10 pays for turns 1 to 9 again (Exercise 4 does the maths).

Sizes change often. As of September 2026 (vendor spec), current Claude Opus, Sonnet and Fable models have a 1M-token window and up to 128k output tokens per request; Claude Haiku 4.5 has 200k and 64k. When a request does not fit, the Anthropic API does this (vendor spec):

| Situation | Result ||-----------|--------|| Input alone is bigger than the window |  ("prompt is too long") || Input fits, but input +  does not (Claude 4.5 and newer) | Accepted; if generation hits the limit it stops with  || Chat apps such as claude.ai | May drop the oldest turns ("first in, first out") |

Other vendors differ, and some truncate silently. Check your API's docs.

> Watch out: bigger is not automatically better. Anthropic's docs describe context rot: as the token count grows, accuracy and recall degrade. Choose what goes in with care.

Chapter 5 — Sampling: temperature, top-k and top-p

Softmax turns logits $zi$ into probabilities. Temperature $T$ divides the logits first:

$$pi = \frac{e^{zi / T}}{\sumj e^{zj / T}}$$

$T < 1$ sharpens the distribution, $T > 1$ flattens it, and as $T$ approaches 0 sampling approaches greedy decoding (always the top token). Watch it with made-up logits for the word after "The cat sat on the":

Output:

Two filters cut the unlikely tail before sampling: top-k keeps the $k$ most likely tokens; top-p (nucleus sampling, Holtzman et al., ICLR 2020) keeps the smallest set of top tokens whose probabilities add up to at least $p$.

Why the same prompt gives different answers: above temperature 0 every token is a random draw, and one different early token changes everything after it. Even at 0, Anthropic's API reference says results will not be fully deterministic.

Chapter 7 — Why hallucinations happen and how to reduce them

A hallucination is fluent, confident text that is false or not supported by the given sources. Causes:

- The goal is a plausible next token, not a true statement. A made-up citation can look very plausible.- Training and tests reward guessing. Kalai et al. (2025, "Why Language Models Hallucinate") argue that training and evaluation reward guessing over admitting uncertainty, like an exam with no penalty for wrong answers.- Missing knowledge: after the cutoff, private, or rare.- Missing or buried context: not in the prompt, or lost in a very long one.

Fixes. The first five follow Anthropic's "Reduce hallucinations" guide and work with any model:

| Technique | How ||-----------|-----|| Allow "I don't know" | "If the documents do not contain the answer, say so." || Ground in sources | Put the documents in the prompt; tell the model to use only them. || Quote first | For long documents, extract word-for-word quotes, then answer from them. || Cite and check | One citation per claim; retract any claim without a supporting quote. || Compare several runs | Answers that disagree across runs are a warning sign. || Verify with tools | Run the code and tests; check official docs for any API or flag you do not know. |

The AI Prompting post covers prompt structure and evaluation in depth; post 18 applies "verify with tools" to coding.

Vocabulary

React calls any function marked  a Server Function. When it is used through React's action mechanisms (, , or called inside ), it is a Server Action. Next.js docs use both terms; they describe the same compiled artefact.

At build time,  tells the compiler to replace the function in client bundles with a reference: an action ID plus a dispatcher that POSTs to the route of the page that invokes it. Chapter 2 — Pyramid or trophy?

Both are models, not laws. They are opinions about where to spend effort.

| Layer (top to bottom) | Test pyramid (Cohn) | Testing trophy (Dodds) ||-----------------------|---------------------|------------------------|| End-to-end / UI | very few | few || Service / integration | some | most effort || Unit | most tests | some || Static (types, lint) | not part of the model | the base layer |

- Test pyramid. Mike Cohn described it in Succeeding with Agile (2009); Martin Fowler's 2012 "TestPyramid" article is a common reference. Many fast unit tests at the bottom, fewer service tests, very few slow UI tests on top.- Testing trophy. Kent C. Dodds sketched it in 2018, building on Guillermo Rauch's line: "Write tests. Not too many. Mostly integration." Its layers are static analysis, unit, integration and E2E, with the biggest share on integration, because those tests are closest to how the software is used while still being fairly fast.

Both agree on the important parts: E2E tests are few and precious, static checks (types, lint) are cheap wins, and every test must earn its cost. The trophy fits web apps where most bugs live between components. The pyramid fits libraries and logic-heavy code. Testcontainers (Chapter 6) makes integration tests cheaper than they used to be, which pushes many teams toward the trophy shape.

A good test is:

A reader sees the setup, the action and the expected result without jumping around.

Chapter 7 — Flaky tests

A flaky test passes and fails on the same code. It is worse than no test, because people learn to ignore red. One large-scale data point (Google, 2016, one company's measurement): about 1.5% of all test runs gave a flaky result, almost 16% of tests showed some flakiness, and about 84% of observed pass-to-fail transitions involved a flaky test.

The report lists, per file, the percentage of lines and branches that ran, plus the missing line numbers. Missing lines are the useful part: they show code no test even executes.

Coverage cannot tell you whether anything was checked:

Chapter 11 — TDD in brief

Test-driven development (Kent Beck, Test-Driven Development: By Example) is a short loop:

1. Red: write one small failing test for the next bit of behaviour.2. Green: write the simplest code that makes it pass.3. Refactor: clean up while all tests stay green.

It works best when the behaviour is clear and the code is logic-heavy (parsers, pricing rules, state machines). It is harder for exploratory UI work. Even if you do not use TDD all the time, one habit is always worth it: when you fix a bug, first write the test that fails because of it (see Dev Essentials 10 · Debugging).

Chapter 1 — How remote calls fail

A function call inside one process either returns or throws. A call over a network has more outcomes:

| Failure | What you see | Example ||---------|--------------|---------|| Slow | The call takes 30 s instead of 30 ms | Database is overloaded, a GC pause, a long queue || Down | Connection refused, DNS error, connect timeout | Service crashed, wrong port, network cut || Partial failure | Some calls work, some fail | One of five servers is broken; one region is down || Unknown outcome | A timeout after the request was sent |  timed out. Was the card charged? |

The last one is the hard case. The request may have reached the server and run. Only the reply was lost. If you retry blindly, you may do the action twice. If you do not retry, the action may never happen. Most of this post is about handling this case safely.

Terminology

| Term | Meaning ||------|---------|| Timeout | The longest you wait for one step (connect, read) before giving up || Deadline | The total time budget for the whole operation, including retries || Backoff | Waiting longer before each new retry || Jitter | Adding randomness to the wait, so clients do not retry at the same moment || Safe method | A method the client does not expect to change anything (, ) || Idempotent | Doing it twice has the same intended effect as doing it once || Idempotency key | A unique ID the client sends so the server can spot a repeat || Rate limit | A cap on how many requests a client may send per time window || Circuit breaker | A switch that stops calls to a failing service for a while || At-least-once | A message is delivered one or more times — duplicates are possible || Dead-letter queue (DLQ) | A side queue for messages that failed too many times |

Chapter 2 — Timeouts on every network call

A timeout limits one attempt. A deadline limits the whole job. If a user request has 2 seconds in total, and 1.5 s are already spent, the next downstream call should get at most 0.5 s. Pass the remaining time down (as an argument or a header) so inner calls never outlive the outer request.

Chapter 7 — Circuit breakers

When a dependency is down, each call waits for a timeout before failing. A circuit breaker notices repeated failures and fails fast for a while. The pattern was made popular by Michael Nygard's book Release It!; Martin Fowler's "CircuitBreaker" article (2014) is a clear short summary.

| State | Behaviour ||-------|-----------|| Closed | Normal. Calls go through. Count failures || Open | Too many failures. Fail at once without calling. Wait  || Half-open | After the wait, let a trial call through. Success → closed. Failure → open again |

A breaker and retries work together: retries handle short blips, the breaker stops retries from hammering a service that is clearly down. Exercise 4 builds a small one. Real breakers also add a lock, count failures over a time window, and often use a failure rate instead of a count.

> Trick: when the breaker is open, return something useful if you can — a cached value, a default, or a clear "try again later" message — instead of a stack trace.

Chapter 8 — Queues, at-least-once delivery and the outbox

Load levelling

If work does not need an answer right now (send an email, resize an image), put it on a queue. The API replies  at once; workers take jobs at their own pace. A traffic spike makes the queue longer, not the servers slower. On AWS this is SQS (see AWS Course 05 · Serverless & Events).

At-least-once means duplicates

SQS standard queues keep copies of each message on several servers. The SQS docs say you may rarely receive a message again, and tell you to design your application to be idempotent. Many queues work this way. A worker can also crash after doing the work but before it deletes the message, so the message comes back.

So every consumer must be idempotent. The usual method: each message carries a unique ID; the consumer records processed IDs and skips any ID it has seen. Exercise 6 builds this with SQLite.

> Watch out: the side effect and the "processed" record must be saved together, in one database transaction. If you save the effect, crash, and never save the ID, the redelivered message runs again.

Dead-letter queues

Some messages always fail (bad data, a bug). Without a limit, they loop forever. In SQS, a redrive policy sets : after that many receives, the message moves to the dead-letter queue. AWS advises setting it high enough to allow real retries, and giving the DLQ a longer retention period than the source queue. Put an alarm on DLQ depth — a message there means a person must look.

The outbox pattern

A classic bug: save an order to the database, then publish an "order created" event. If the process dies between the two steps, the event is lost. The outbox pattern writes the event into an  table in the same transaction as the order. A separate relay reads the outbox and publishes. The relay may publish twice, so consumers must still be idempotent. MongoDB Course 20 · Outbox Pattern builds this step by step.

Chapter 1 — Why cache, and what it costs

Without a cache, every request pays the full price: a network round trip, a database query, a template render. With a cache, most requests pay a lookup instead. The share of requests answered from the cache is the hit ratio (). A cache with a 95% hit ratio sends only 1 request in 20 to the slow system behind it.

Caching is never free:

| Cost | What goes wrong ||------|-----------------|| Staleness | The copy is older than the truth. A user changes a price and still sees the old one. || Memory | Every copy takes RAM or disk. Full caches must evict something. || Complexity | New failure modes: invalidation bugs, stampedes, one user's page served to another. || Debugging | "It works on my machine" becomes "it works after a hard refresh". |

A good rule: add a cache when you have measured a slow, repeated read, and you can say how stale the data is allowed to be.

Terminology

- Hit / miss — the value was in the cache / it had to be fetched from the source (the origin).- TTL (time to live) — how long an entry counts as fresh.- Fresh / stale — younger / older than its TTL. Stale entries may still be used in some cases.- Eviction — removing entries to make room, often LRU (least recently used first).- Invalidation — removing or updating an entry because the source changed.- Cache key — what identifies an entry: a URL, or a string like . A cold cache is empty (just started); a warm one is full of useful entries.

| Pattern | Read path | Write path | Good for ||---------|-----------|------------|----------|| Cache-aside (lazy loading) | App checks cache; on miss, reads DB and fills cache | App writes DB, then deletes the key | The default choice; the cache can fail without losing data || Read-through | App asks the cache; the cache library loads from DB on a miss | Same as cache-aside | Hides loading logic in one place || Write-through | Always a hit after a write | App (or cache) writes cache and DB together | Data that is read right after it is written || Write-behind (write-back) | Always a hit | Write goes to the cache; DB is updated later in batches | Very high write rates, if you can accept losing recent writes |

TTLs

Every entry should have a TTL, even if you also invalidate on writes. The TTL is your safety net: if an invalidation is missed, the wrong value lives for at most one TTL. Choose it from the business question "how stale may this be?", not from performance alone. Add jitter (a small random extra) so that entries created together do not all expire together.

Invalidation strategies

1. Expire only — rely on the TTL. Simplest; data is up to one TTL old.2. Delete on write — after the DB write succeeds,  the key. The next read reloads it. Prefer delete over "set the new value", because two concurrent writers can set values in the wrong order.3. Versioned keys — put a version in the key () and bump the version on change. Old keys simply age out.4. Event-driven — the database emits change events and a worker deletes the matching keys. MongoDB Course 12 · Change Streams shows the event source.

> Watch out: cache-aside has a known race. Reader A misses and loads the old row. Writer B updates the row and deletes the key. Reader A then writes the old value into the cache. It stays wrong until its TTL ends. Short TTLs keep the damage small; for critical data, add a version check or do not cache.

Chapter 9 — Cache stampede and how to stop it

A cache stampede (or thundering herd, or dog-piling) happens when a popular key expires and hundreds of requests miss at the same moment. They all run the same slow query, the database slows down, requests pile up, and the cache never gets refilled. It often follows a deploy or restart (cold cache) or a batch of keys that were all created with the same TTL.

shows the problem in miniature. With 20 threads asking for the same missing key at once, the slow function ran 20 times. The fixes:

| Fix | Idea ||-----|------|| Jittered TTL |  so keys created together expire at different times. || Locking | Only the request that wins a lock recomputes; the others wait briefly and read the new value (Chapter 8). || Request coalescing (single-flight) | In one process, concurrent callers for the same key share one in-flight computation. || Early refresh | Recompute before expiry, so the key is never missing. Either a background job, or a random early refresh per request. || Serve stale | Keep serving the old value while one worker refreshes (the idea behind ). |

Chapter 2 — Storing passwords

Never plain text, never reversible encryption

If you store passwords as plain text, one database leak exposes every user — and most users reuse passwords on other sites. Encryption is not the answer either. Encrypted data can be decrypted, so whoever steals the key gets every password back. You want a one-way function: easy to check a guess, impossible to reverse. That is a hash. But not any hash.

Why SHA-256 is the wrong hash

SHA-256 and MD5 are built to be fast. A modern GPU can compute billions of them per second. If an attacker steals your table of SHA-256 password hashes, they hash every word from a big list of leaked passwords and compare. Password hashing functions are built to be slow and memory-hungry on purpose. One login costs your server a fraction of a second. For an attacker trying billions of guesses, the same cost becomes enormous. Being memory-hard matters too: GPUs have many cores but little memory per core, so a hash that needs many MiB per guess slows them down.

Salt and pepper

- Salt — a random value, different for every password, stored next to the hash. Two users with the same password get different hashes, and precomputed tables ("rainbow tables") become useless. Modern libraries make and store the salt for you.- Pepper — one secret value shared by all passwords, stored outside the database (a secrets manager or an HSM). OWASP says a pepper "should not be stored along with the generated hash". If only the database leaks, the hashes cannot be cracked without it. A pepper is defence in depth, not a replacement for a slow hash.

The algorithms and the current OWASP parameters

The OWASP Password Storage Cheat Sheet (checked September 2026) gives this order of preference. The quotes are exact:

| Algorithm | When | OWASP parameters ||-----------|------|------------------|| Argon2id | First choice | "a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism" || scrypt | If Argon2id is not available | "a minimum CPU/memory cost parameter of (2^17), a minimum block size of 8 (1024 bytes), and a parallelization parameter of 1" || bcrypt | Legacy systems | "a work factor of 10 or more and with a password limit of 72 bytes" || PBKDF2 | When FIPS-140 compliance is required | "PBKDF2-HMAC-SHA256: 600,000 iterations"; "PBKDF2-HMAC-SHA512: 220,000 iterations" |

OWASP also lists Argon2id settings that give about the same protection. You can trade memory for iterations: , , , , .

> Watch out: bcrypt only uses the first 72 bytes of the input in most implementations. Longer passwords are silently cut, so two different long passwords can match. OWASP says to "enforce a maximum password length of 72 bytes". Note that 72 bytes can be fewer than 72 characters in UTF-8 (see Dev Essentials 01 · Text Encoding). Pre-hashing the password before bcrypt has its own traps (null bytes, "password shucking"), so for new systems just choose Argon2id.

The work factor (or cost) is how much CPU time, and for Argon2 and scrypt how much memory, one hash takes. You raise it as hardware gets faster.

Chapter 4 — Password rules from NIST SP 800-63B-4

NIST SP 800-63B-4 is the US government guideline on authentication. The final version was published on 31 July 2025. It supersedes SP 800-63B (revision 3). Many companies follow it, and it drops several old habits. The key rules, quoted:

| Rule | NIST 800-63B-4 text ||------|---------------------|| Minimum length, password alone | "SHALL require passwords that are used as a single-factor authentication mechanism to be a minimum of 15 characters in length" || Minimum length, with MFA | may be shorter "but SHALL require them to be a minimum of eight characters in length" || Maximum length | "SHOULD permit a maximum password length of at least 64 characters" || Composition rules | "SHALL NOT impose other composition rules (e.g., requiring mixtures of different character types)" || Rotation | "SHALL NOT require subscribers to change passwords periodically" — but "SHALL force a change if there is evidence that the authenticator has been compromised" || Blocklist | compare new passwords "against a blocklist that contains known commonly used, expected, or compromised passwords" || Unicode | "Each Unicode code point SHALL be counted as a single character" || Password managers | "SHALL allow the use of password managers and autofill functionality"; "SHOULD permit" paste || No truncation | "SHALL verify the entire submitted password (e.g., not truncate it)" |

Chapter 5 — Hardening the login

Rate limiting

Without a limit, an attacker can try thousands of passwords per minute. NIST requires that the verifier "SHALL limit consecutive failed authentication attempts using a specific authenticator on a single subscriber account to no more than 100". Most apps choose a much lower number, plus a limit per IP address. The app in Chapter 7 allows 5 failures per account per 15 minutes. Dev Essentials 14 · API Reliability covers rate-limit algorithms in depth.

> Watch out: a hard lockout per account lets anyone lock a real user out on purpose. Prefer growing delays or a temporary block, and give the real user a way to recover.

Generic error messages

Say "Invalid username or password" in both cases. If "no such user" and "wrong password" give different messages, attackers can find which accounts exist (user enumeration). Watch the timing too. If unknown users return instantly while real users take 50 ms to hash, the delay leaks the same fact. The Chapter 7 code hashes a dummy value for unknown users to keep the timing close. Registration and "forgot password" pages leak the same way, so give them neutral replies such as "If that account exists, we sent an email".

MFA with TOTP (RFC 6238)

A Time-based One-Time Password is the 6-digit code in an authenticator app. Server and app share a secret. Both compute  and cut the result down to 6 digits. RFC 6238 builds on HOTP (RFC 4226) and recommends a 30-second time step. It needs only the standard library:

Passkeys and WebAuthn

TOTP codes can still be phished: a fake site asks for the code and replays it within 30 seconds. Passkeys fix this. A passkey is a key pair created by the user's device or password manager through the WebAuthn browser API. The server stores only the public key. At login, the device signs a random challenge with the private key. The browser ties each credential to the site's origin, so a look-alike domain cannot use it. WebAuthn Level 3 became a W3C Recommendation in 2026, and NIST 800-63B-4 requires phishing-resistant authenticators at its highest level (AAL3). Use a maintained WebAuthn server library rather than writing the checks yourself.

Chapter 8 — JWT: signed tokens without a session store

A JSON Web Token (RFC 7519) is three base64url parts joined by dots: . The payload holds claims such as  (subject, the user),  (expiry time),  (issued at),  (issuer) and  (audience). The revocation problem

Stateless has a price. Once a JWT is issued, it stays valid until . Logout, a password change, or "block this account" cannot cancel it, unless you add a denylist, and then you have a server-side store again. The usual answer is short-lived access tokens (minutes) plus a long-lived refresh token that is tracked server-side, so it can be revoked. With refresh token rotation, each use returns a new refresh token and invalidates the old one. If an old one shows up again, revoke the whole chain.

Chapter 9 — OAuth 2.0 and OpenID Connect

What OAuth 2.0 is for

OAuth 2.0 (RFC 6749) is about delegated authorization. It answers: "may this app act on my behalf at that API?" For example, a printing site asks to read your photos from a cloud drive, without ever seeing your cloud password. The four roles are the resource owner (you), the client (the printing site, a mobile app or a single-page app), the authorization server (the cloud's login and consent service, which issues tokens) and the resource server (the photo API, which accepts access tokens).

Chapter 1 — The debugging loop

Most wasted debugging time comes from changing things at random. The fix is a loop borrowed from the scientific method:

1. Observe. What exactly happened? Copy the full error text. Note the input, the time, the version.2. Hypothesize. Make one specific guess: "one order item has no  key".3. Test one change. Design a check that proves or kills the guess. Change one thing only.4. Record. Write down what you tried and what happened. Then loop.

A tiny log in a text file is enough. It stops you testing the same idea twice, and it becomes your bug report or commit message:

> Watch out: if you change two things and the bug vanishes, you learn nothing. You do not know which change fixed it, or if one of them only hid it.

The special meaning of 0.x. SemVer item 4 says major version zero is for initial development: "Anything MAY change at any time." So  →  may break you. The FAQ adds that software already used in production "should probably already be 1.0.0". Treat every  minor bump like a major one.

SemVer is a promise, not a proof. The maintainer decides what counts as "breaking". A patch that fixes a bug you relied on still breaks you. Version numbers tell you where to look first; tests tell you whether it works.

Chapter 7 — Supply-chain attacks: how they really happen

An attacker who cannot break into your app can break into something your app installs. The main patterns:

- Typosquatting — a malicious package whose name is one typo away from a popular one.- Dependency confusion — a public package with the same name as your private internal one, which a misconfigured installer prefers.- Compromised maintainer account — a stolen password or token, or a phished 2FA code, followed by a malicious release of a real, trusted package.- Malicious install scripts —  /  code runs on your laptop or CI runner the moment you install, before you import anything.- Takeover of an abandoned asset — a domain, CDN or package that passes to a new owner.

Chapter 8 — Mitigations you can apply today

1. Lock, and install exactly

Commit lockfiles, and use ,  or  in CI (Chapter 3). A malicious new release cannot enter a build that installs only locked, hashed versions.

2. Wait before adopting new versions

Most malicious releases are found and removed within hours or days. A minimum release age makes your tools ignore anything newer than a set age. Names and units differ, so be careful:

| Tool | Setting | Unit | Available since ||------|---------|------|-----------------|| npm |  in  | days | npm 11.10.0 || pnpm |  in  | minutes | 10.16; default  from 11.0 || Yarn (Berry) |  in  | duration (a plain number means minutes) | 4.10.0 || Bun |  in  | seconds | see Bun docs || uv |  under  | timestamp or duration (, ) | see uv docs || pip |  | ISO 8601 timestamp, or a duration like  | 26.0; durations from 26.1 || Renovate |  | duration () | — || Dependabot |  (, …) | days | — |

> Watch out: a release-age delay also delays security fixes. Keep an exclude list for urgent patches; Dependabot's cooldown already skips security updates. For Yarn, check your version's default with , because recent releases changed it.

3. Do not run install scripts you did not approve

- npm 12+: dependency scripts are blocked by default. Approve the ones you need with , which records them in the root  policy, then run .- Older npm:  in  stops all scripts. Packages with native parts may then need a manual .- pnpm 10+: scripts are off by default.  adds the packages you approve to  in .

4. Check where packages came from

Provenance links a published package to the source repository and the CI build that produced it, signed through Sigstore. As a consumer, run . As a maintainer, publish from CI with trusted publishing, or with  and the  permission in GitHub Actions. PyPI supports trusted publishing too. npm's docs are careful here: provenance shows where a package came from, but it does not promise the code is free of malware.

5. Know what you ship: SBOMs

A Software Bill of Materials lists every component and version in a build, in a standard format (CycloneDX or SPDX). When the next xz-style advisory appears, you search your SBOMs instead of guessing.

6. Protect your own publishing

Use passkeys or hardware keys, which resist phishing, instead of TOTP codes on registry accounts. Prefer trusted publishing to long-lived tokens, and give CI tokens the smallest scope.

7. Add fewer dependencies

Before adding a package, check who maintains it, when it last released, whether it has install scripts, and how many transitive packages it brings. A 10-line helper you write yourself has no supply chain.
