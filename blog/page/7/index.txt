e:T2e80,A MongoDB driver doesn't open a connection per query — it holds a pool and checks them out. How big the pool is, how long checkouts wait, what write durability you ask for (write concern), what read freshness you tolerate (read concern), and where reads go (read preference) — these settings decide whether your app sustains 100 req/sec or 100k req/sec, and whether a failover costs you data. This post covers every knob with sensible production defaults.

Chapter 3 — Sizing the pool — the right answer is "not larger"

A common mistake: bump  to 500 or 1000 hoping for more throughput. The opposite usually happens — more connections = more context switches on server + WiredTiger ticket contention + memory bloat.

Useful starting numbers

| Workload |  ||----------|---------------|| Small web app, dozens of QPS | 10-20 || Medium API, 1k-5k QPS | 50-100 (default) || High concurrency, mostly fast queries | 100-200 || Heavy aggregations / long queries | smaller pool + more app instances |

Math — Little's Law

Avg concurrent ops needed = .

Example: 200 QPS × 0.05 s avg latency = 10 concurrent ops needed. A pool of 20 is plenty; 100 is wasted resources.

If your driver pool is much larger than the math suggests, the bottleneck is elsewhere (server, network, lock contention) and pool growth won't help.

Per process vs per fleet

Each Node process / each Python worker has its own pool. A web fleet of 20 instances ×  = up to 1000 connections to the server. The MongoDB server has its own ceiling (, default 65,536). Don't accidentally exceed it.

Atlas tier limits

- M0 / M2 / M5 (shared): 500 connections.- M10: 1500.- M20: 3000.- M30+: 6000+ (scales with tier).

Symptoms: server logs flooded with ,  climbing, app sees timeouts.

Chapter 11 — Server-side concurrency — WiredTiger tickets

uses read + write tickets to limit concurrent storage-engine operations. Default: 128 each. Once exhausted, requests queue.

Symptoms of ticket exhaustion: high  near 0 in ; query latency spikes that can't be explained by individual queries; lock contention in metrics.

Causes: slow queries holding tickets too long, sudden write storms, bad index plans.

Fix order:

1. Find + fix slow queries (Post 04 profiler).2. Add indexes; reduce work per ticket.3. Lower app-side concurrency (smaller pool).4. Scale up the instance (more cache, more I/O).

Tickets aren't tunable in modern versions — they're sized internally based on the storage engine. Treat them as a signal rather than a knob.

Chapter 1 — The draw-call budget

Every  in the scene typically produces one draw call. Each draw call has CPU overhead: bind shader, set uniforms, set attribute pointers, issue the GPU command. Modern GPUs draw millions of triangles per frame easily; CPUs choke on thousands of draw calls per frame.

Rough targets for 60 fps:

| Device | Safe draw-call count ||--------|----------------------|| Desktop / high-end laptop | ≤ 1,000 || Mid-range mobile (mid-2020s) | ≤ 100-200 || Low-end mobile / older hardware | ≤ 50-100 |

Triangle counts matter much less than draw-call counts. 1 mesh with 500k triangles renders fine; 5,000 meshes with 100 triangles each will not.

Chapter 1 — The mental shift

SQL: design schema first, query later.MongoDB: start from the queries you want to run, design schema to make them efficient.

Two principles:

1. Data that's accessed together should live together. Embed it.2. Data that grows unboundedly or is shared across many parents should be separated. Reference it.

That's it. The named patterns below are corollaries.

Chapter 2 — Embed vs reference

Embed (sub-document or array)

Pros:- One document fetch returns the whole thing.- Atomic writes across the whole document.- No joins.

Cons:- Duplication if the same sub-document is shared by many parents.- Document size cap: 16 MB.- Updating a deeply nested value can be awkward.

Reference (foreign key style)

Pros:- Each entity is the single source of truth.- No size limit (each is its own document).- Many parents can reference the same entity.

Cons:- Reads need a join ( or two round-trips).- No atomic writes across the reference unless using transactions.

Decision matrix

Chapter 3 — The three compressions you should enable

A typical 5 MB glTF can shrink to 500 KB with the right compression — and load 5× faster.

| Layer | What it compresses | Decoder bytes | Ratio ||-------|--------------------|---------------|-------|| Draco | mesh geometry | 250 KB (lazy loaded) | up to 10× || Meshopt | mesh geometry + animations + morph targets | tiny (no separate decoder) | similar to Draco, sometimes better || KTX2 / Basis | textures (GPU + disk) | 700 KB transcoder | 10× GPU memory |

You'll usually pick either Draco or Meshopt for geometry (not both), plus KTX2 for textures.

Chapter 3 — IXSCAN vs COLLSCAN — the binary signal

IXSCAN = used an index. Cost: O(log n) for the seek + O(matches) for the scan.

COLLSCAN = scanned every document. Cost: O(n) for n documents in the collection.

A COLLSCAN on a 10k-row collection is fast (a few ms). A COLLSCAN on a 10M-row collection is a multi-second outage.

Means: no index helped; the server read every document and filtered in memory. Add an index on  (or a compound covering this + other filters).

Acceptable COLLSCANs

- Tiny collections (< few thousand docs).- Analytical jobs running off-peak.- One-time admin queries.

For user-facing endpoints, never accept COLLSCAN.

This post covers loading textures, the colour-space rules every modern Three.js project must follow, mipmaps + anisotropy, the full PBR map set, environment maps and image-based lighting (IBL), and KTX2 compressed textures for shipping mobile-friendly builds.

Chapter 2 — Colour space (the bug that ruins your scene)

PBR shading does its math in linear light space. Image files (JPG, PNG) are stored in sRGB (gamma-encoded for storage efficiency, perception-uniform on monitors).

If you load an sRGB image without telling Three.js, the shader treats the gamma-encoded values as linear → washed-out, oversaturated, wrong-coloured result.

A mipmap is a chain of pre-downscaled copies of the texture (1024 → 512 → 256 → 128 → ... → 1). The GPU samples the right level for the distance, avoiding flicker and improving cache use.

Chapter 6 — Normal maps (the detail multiplier)

Chapter 8 — KTX2 / Basis Universal (the cost saver)

JPG / PNG textures decompress fully on the GPU. A 1024² PNG = 4 MB of GPU memory regardless of file size on disk. A scene with 50 textures can blow the GPU budget on phones.

Chapter 9 — Texture atlases

Combining many small textures into one big "atlas" saves texture-binding overhead. With UV remapping per object, you can render many meshes that share the atlas in fewer draw calls.

Authoring tools (Blender → UV Editor, gltf-transform , custom packers like ) generate atlases. At runtime, every mesh references the same atlas texture with different UV ranges.

Pairs naturally with InstancedMesh (Post 07) and texture arrays (one texture sampler, N layers).

17:T258b,An index is a B-tree (or specialised structure) on one or more fields that lets MongoDB find documents without scanning the whole collection. Indexes turn a 60-second query into a 5-millisecond one — and turn an undertuned cluster into a poorly-running mess if used wrong (too many, too wide, wrong order). This post covers every index type, the ESR rule (Equality, Sort, Range) for compound-index ordering, partial / sparse / TTL / wildcard / hashed variants, index intersection, covered queries, and the build options (, , ).

Chapter 1 — Index basics

Every MongoDB collection has at least one index — on  (unique, auto-created, can't drop). All others are user-created.

Naming: auto-generated as  joined by . Use  option for custom.

Cost trade-off

- Indexes speed reads that filter / sort / project on indexed fields.- Indexes slow writes — every insert / update / delete must update every relevant index.- Indexes use RAM — frequently accessed parts of indexes must fit in the WiredTiger cache for speed (Post 15).- Indexes use disk — typically 10-30% of collection data size each.

Rule: index for the queries you actually run, drop indexes never used (Post 04 covers  to find unused).

Chapter 3 — Compound index + the ESR rule

A compound index is on multiple fields:

The order of fields in the index matters enormously. The ESR rule:

> E — Equality fields first.> S — Sort fields second.> R — Range fields last.

Why: B-trees can serve range scans only on the trailing indexed prefix once equality fields have been matched. Out-of-order indexes do partial work then full scans.

Chapter 4 — Multikey index (arrays)

When indexed field is an array, MongoDB creates one index entry per array element. This is called a multikey index — automatic, no special syntax.

Limits:

Chapter 11 — TTL index — auto-delete after N seconds

A background thread deletes documents whose indexed date is older than  ago. Runs roughly every 60 s — TTL is approximate, not exact.

Chapter 12 — Wildcard index — index unknown fields

Useful when documents have heterogeneous / unknown fields and the app queries arbitrary attributes — common in multi-tenant SaaS where each tenant has custom fields.

Costs: big indexes, expensive writes. Reach for only when access patterns truly vary.

Chapter 13 — Covered queries

A query is covered when:

1. Every queried field is in an index.2. Every projected field is in the same index.3. Query doesn't return  unless  is in the index.

Covered queries return results straight from the index — no document fetch — extremely fast.

(Post 04) shows  with no following  stage when a query is covered.

Chapter 14 — Index intersection (use sparingly)

MongoDB can intersect two single-field indexes to satisfy a multi-field query, but it's usually slower than a single compound index that matches the query.

Rule: design compound indexes for the queries you run, not single-field per-column indexes.

Chapter 15 — Build options

Build in background (5.0+: always)

Index builds since 5.0 use a hybrid foreground/background protocol that doesn't block writes. No special flag needed. (Older versions used  — still accepted, no-op.)

Collation — case + locale-aware

Without matching collation on the query, the index is not used.

Hiding (test removal without dropping)

Safe pattern for "is this index needed?": hide for a week, observe query performance, drop if no regression.

Chapter 16 — Production rules of thumb

1. Index every field used in a frequent filter, sort, or join. Not more.2. Compound indexes follow ESR.3. Sort direction in the index matches your most common sort.4. Use partial indexes to shrink indexes for filtered subsets (active users, open tickets).5. Use TTL for inherently temporary data.6. Index size + frequently-accessed entries should fit in RAM — Post 15.7. Drop unused indexes —  shows usage (Post 04).8. Build new indexes in off-peak windows for large collections, even with hybrid background builds — backfill is I/O heavy.9. Don't index every field "just in case" — write amplification + RAM waste.10. Test with  before shipping any new query — Post 04.
