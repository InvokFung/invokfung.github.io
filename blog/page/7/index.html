MongoDB Course — 08 · Connection Pool, Concurrency, Write/Read Concern
Created2026-06-15|Database MongoDB
A MongoDB driver doesn't open a connection per query — it holds a pool and checks them out. How big the pool is, how long checkouts wait, what write durability you ask for (write concern), what read freshness you tolerate (read concern), and where reads go (read preference) — these settings decide whether your app sustains 100 req/sec or 100k req/sec, and whether a failover costs you data. Chapter 1 — The MongoClient lifecycle A is thread-safe, long-lived, and pooled. Create once per process; reuse for every operation. Wrong pattern (anti-pattern): per request. Each instantiation opens new sockets, runs handshakes, and exhausts server-side connection limits. Across a fleet this is a #1 outage cause. Same rule across languages — (Node, Python sync), (Python async), (Go), (.NET) — all are pooled + thread-safe singletons. Three.js Course — 07 · Instancing & Batching for Large Scenes
Created2026-06-15|Programming 3D
The single biggest performance trick in real-time 3D is don't issue one draw call per object. The CPU side of WebGL/WebGPU spends most of its budget setting up state for each draw call; reducing 9,000 draw calls to 300 takes a slideshow back to 60 fps without changing visual quality. This post covers the four standard tools — (the "clone trick" for many copies of one shape), (many different shapes, one material), geometry merging (one giant mesh), and LOD (less detail for distant objects) — and the draw-call budget rules to know when to reach for each. > Series map: 00 Foundations → 01 Geometry & Materials → 02 Cameras & Controls → 03 Lighting & Shadows → 04 Textures & PBR → 05 Asset Pipeline → 06 Animation → 07 Instancing & Batching (this post) → 08 Low-End Perf → 09 Shaders → 10 Post-Processing → 11 Physics → 12 R3F → 13 AI 3D. Learning Outcome - Recognise the draw-call budget and how to measure it.- Use to render N copies of one geometry with per-instance transforms + colours.- Use (since r156) when geometries differ but the material is shared.- Merge static geometries into one with .- Use (Level of Detail) so distant objects render simplified versions.- Pick the right tool for "10,000 trees", "1,000 unique buildings", "a city of 50,000 windows". Chapter 1 — The draw-call budget Every in the scene typically produces one draw call. Each draw call has CPU overhead: bind shader, set uniforms, set attribute pointers, issue the GPU command. Modern GPUs draw millions of triangles per frame easily; CPUs choke on thousands of draw calls per frame. Rough targets for 60 fps: | Device | Safe draw-call count ||--------|----------------------|| Desktop / high-end laptop | ≤ 1,000 || Mid-range mobile (mid-2020s) | ≤ 100-200 || Low-end mobile / older hardware | ≤ 50-100 | Triangle counts matter much less than draw-call counts. 1 mesh with 500k triangles renders fine; 5,000 meshes with 100 triangles each will not. Measure with If ≫ 200 and the scene is laggy, the problem is the draw-call count, not GPU rasterisation. The fix is one of the patterns in this post. Chapter 2 — — the "clone trick" draws N copies of one geometry with one material in one draw call, each copy with its own 4×4 matrix (transform) and optionally its own colour. This is the answer to "I have 10,000 trees / rocks / windows / grass blades / particles". That entire scene = 1 draw call regardless of . Per-instance colour The material respects per-instance colour automatically. Animating instances Reading/writing every instance every frame is fine up to 10k instances on the main thread. For 100k+ instances, move the update to a Web Worker or use a vertex shader (Post 09) that computes positions from a base attribute + instance id. Per-instance picking + visibility (Three.js doesn't have first-class per-instance visibility; scale = 0 is the common trick.) Chapter 3 — — many shapes, one material requires every instance to share the same geometry. (added in r156) lifts that restriction — many different geometries can be rendered in one draw call as long as they share a material. Use when: a city of unique buildings, a furniture catalogue, a forest with several tree species. 200 different-shape objects, 1 draw call. The original cube/cone/torus geometries are merged into the batch's internal buffer. When BatchedMesh underperforms The current Three.js BatchedMesh emulates instancing via rather than . For workloads of "many copies of the same geometry", InstancedMesh is faster. For "many different geometries, same material", BatchedMesh wins. Decision: - All instances identical geometry → InstancedMesh.- Different geometries, same material → BatchedMesh.- Different materials → can't batch directly; merge materials (Chapter 6) or accept separate draw calls. Chapter 4 — Geometry merging (one big mesh) For static scenery where you don't need per-object updates, merge geometries into a single big mesh: 1 draw call, fully baked. No per-object animation possible — to move one cube, you'd modify the whole merged geometry. Use for static decoration (walls, ground details, fixed environment). Multi-material merge Groups define which sub-range uses which material — still one geometry but multiple draw calls (one per group). Useful for merging objects that genuinely need different materials while keeping vertex data shared. Chapter 5 — LOD (Level of Detail) A model 100 m away doesn't need 50k triangles. swaps to a simpler version automatically: Each tier is a different mesh (different geometry). Three.js picks based on camera distance per frame. Impostor billboards For very distant objects: replace the 3D model with a (textured 2D billboard) of a pre-rendered angle. Used heavily in open-world games for forests / cities. Chapter 6 — Merging materials with a texture atlas To batch objects that look different (different colours, different decals), pack their textures into a single atlas + remap UVs. Then they share one material → can be merged or instanced. Tools: Blender bake to atlas; ; manual UV editing. Chapter 7 — Frustum culling + occlusion culling Three.js culls per-mesh: meshes whose bounding sphere is outside the camera frustum are skipped. For and , frustum culling tests the entire batch's bounding sphere — if any part is in view, the whole batch renders. To get per-instance culling, you have two choices: 1. Manual chunking — split a 10k-instance forest into 100 chunks of 100 instances. Each chunk has its own InstancedMesh with a tighter bounding sphere.2. Libraries like three-mesh-bvh can accelerate visibility queries; production engines often use a custom hierarchical-Z buffer approach. MongoDB Course — 07 · Schema Design — Embed vs Reference, Patterns, Trees, Versioning
Created2026-06-13|Database MongoDB
The biggest leap from SQL to MongoDB is the way you model data. There's no "right" normalisation — schema is chosen per access pattern. Get it right and a single document satisfies the hot read with one disk seek. Get it wrong and you're stitching together with on every page load. This post covers the canonical design patterns: embed vs reference, 1:1 / 1:few / 1:many / many:many, plus the named patterns the MongoDB community has codified — Polymorphic, Bucket, Computed, Extended Reference, Attribute, Tree (4 variants), Outlier, Schema Versioning. > Series map: 00 Foundations → 01 CRUD → 02 Query Operators → 03 Indexes → 04 Query Optimization → 05 Aggregation Basics → 06 Aggregation Advanced → 07 Schema Design (this post) → 08 Connection Pool & Concurrency → … → 17 Drivers & Case Studies. Learning Outcome - Decide between embedding and referencing for each relationship.- Recognise the canonical access patterns for 1:1, 1:few, 1:many, many:many.- Apply the named patterns: Polymorphic, Bucket, Computed, Extended Reference, Attribute, Tree, Outlier, Schema Versioning.- Store hierarchies four ways (parent ref / child ref / array of ancestors / materialised path).- Plan schema evolution without downtime. Chapter 1 — The mental shift SQL: design schema first, query later.MongoDB: start from the queries you want to run, design schema to make them efficient. Two principles: 1. Data that's accessed together should live together. Embed it.2. Data that grows unboundedly or is shared across many parents should be separated. Reference it. That's it. The named patterns below are corollaries. Chapter 2 — Embed vs reference Embed (sub-document or array) Pros:- One document fetch returns the whole thing.- Atomic writes across the whole document.- No joins. Cons:- Duplication if the same sub-document is shared by many parents.- Document size cap: 16 MB.- Updating a deeply nested value can be awkward. Reference (foreign key style) Pros:- Each entity is the single source of truth.- No size limit (each is its own document).- Many parents can reference the same entity. Cons:- Reads need a join ( or two round-trips).- No atomic writes across the reference unless using transactions. Schema migration from embedded to referenced is mechanical. The reverse usually requires re-engineering query paths. Embedding is the cheap default. Chapter 3 — Cardinality patterns 1:1 — always embed 1:few — embed (bounded array) A user's emails (≤ 10), a product's color variants (≤ 20). 1:many — embed if bounded, reference if not A blog post's comments (could be 1 or 10,000) → reference.A user's purchase history (could be 1 or 10,000) → reference (separate collection).A book's chapters (10-50 typically) → embed. Never try to embed millions of children into the parent — the 16 MB cap kicks in. Chapter 4 — Polymorphic pattern When documents in the same collection have different shapes (different fields per type): Common base fields (, , ) + a discriminator () + type-specific fields. Index for filtering. When to use: catalogue with many product kinds; events with type-specific payloads; logs with varied formats. In code, a switch on decides how to render / process. Trade richer schema for fewer collections + simpler queries. Chapter 5 — Bucket pattern (pre-time-series collections, still useful) Instead of one document per event, group events into "buckets" of N (by time or count): One bucket per hour per device → 24 docs/day/device instead of 86,400. MongoDB 5.0+ ships native time-series collections that automate the bucket pattern + add columnar compression — Post 17 walks through them. Hand-rolled buckets are still useful when you need custom grouping (e.g., per session) or pre-5.0 clusters. Chapter 6 — Computed pattern Pre-compute aggregates and store them on the parent document — avoid repeating expensive aggregations on every read. Update via the same write that creates the related event (transaction or ) or via change-stream-driven background updates. Trade-off: write amplification for read speed. Worth it when the read is hot and the computation expensive. Chapter 7 — Extended Reference pattern Reference an entity by ID plus duplicate a few stable fields on the referencing side — saves the join for the most common read. Reads listing orders don't need to users for name + email. Drawback: if the user changes their name, orders show stale. Use when:- The denormalised fields rarely change.- Read frequency >> write frequency.- Stale data for hours/days is acceptable until a background job catches up. Chapter 8 — Attribute pattern When documents have many similar fields you need to query over arbitrary subsets: A single multikey compound index serves all attribute-based queries. Trade-offs: more rigid query syntax (), unfamiliar to SQL background. Choose when products / items have hundreds of possible attributes only some of which apply per item. Chapter 10 — Outlier pattern A few documents in a collection are atypically large (a celebrity user with 50k followers; a viral post with 1M comments). Embedding fails the 16 MB limit for them. Mark them as outliers + store the overflow elsewhere: App reads check and fetch from the side collection if true. Avoids pathological queries on average users while still scaling for outliers. An index is a B-tree (or specialised structure) on one or more fields that lets MongoDB find documents without scanning the whole collection.
