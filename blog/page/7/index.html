Containers Course — 00 · Containers from First Principles
Created2026-07-10|Infrastructure Containers
Containers are the packaging and isolation unit that most modern deployment runs on: CI pipelines, Kubernetes clusters, serverless container platforms, and local development environments all assume them. The trouble is that the popular one-line explanation — "a container is a lightweight VM" — is wrong in a way that produces bad decisions later, especially around security and state. This first post builds the correct model from the Linux primitives upward: a container is an ordinary process whose view of the system has been narrowed by namespaces, whose resource usage has been capped by cgroups, and whose root filesystem has been swapped for an image. Everything else in this course — Dockerfiles, Compose, registries, Kubernetes pods — is machinery layered on top of that one sentence. > Series map: 00 Containers from First Principles (this post) → 01 Images and Dockerfiles → 02 Networking, Volumes and Compose → 03 Registries, Supply Chain and Security → 04 Kubernetes Architecture and Core Objects → 05 Config, Storage and Stateful Workloads → 06 Scheduling, Resources, Probes and Rollouts → 07 Ingress, Observability, RBAC and GitOps. Learning Outcome - Define a container in terms of namespaces, cgroups, and a root filesystem — and state precisely where the "lightweight VM" analogy breaks.- Name the Linux namespaces and what each one virtualises, and read a process's namespace set from .- Explain how cgroups v2 enforces CPU, memory, and I/O limits, and read those limits from inside a running container.- Describe overlayfs and copy-on-write layering, and predict what happens to a file written inside a container.- Compare containers and VMs on startup, density, and isolation, including the shared-kernel security caveat.- Place the OCI specifications and the Docker CLI → dockerd → containerd → runc stack, and say where Podman fits.- Install Docker on Linux, macOS, or Windows and run, inspect, and remove your first container. Chapter 1 — What a container actually is Terminology - Container — a process (or small process tree) running on the host kernel with a restricted view of the system: its own namespaces, a cgroup limiting its resources, and a root filesystem taken from an image.- Image — a read-only, layered filesystem plus metadata (entrypoint, environment, exposed ports). The template.- Namespace — a kernel feature that gives a process a private instance of a global resource (process IDs, mounts, network stack, hostname, …).- cgroup (control group) — a kernel mechanism that accounts for and limits a group of processes' CPU, memory, I/O, and process count.- Container runtime — the software that turns an image plus a config into a running process. Low-level: , . High-level: , .- Host kernel — the single Linux kernel that every container on a machine shares. There is no second kernel. The one-sentence definition On Linux, this is a container: Nothing is emulated. Nothing is virtualised in the hardware sense. results in an process visible in the host's process table. Prove it on a Linux host: Inside the container that same process believes it is PID 1. Outside, it is just another entry in . Both views are true; they differ only by namespace. Where "lightweight VM" fails The analogy is seductive because both give you "a box that looks like its own machine". It fails on four concrete points, and every one of them bites in production: 1. There is no guest kernel. A VM boots its own kernel on virtual hardware. A container calls the host's kernel directly. A kernel panic, a kernel CVE, or a that must differ per workload is therefore not isolated by a container.2. There is no boot. A VM boots firmware → bootloader → kernel → init → services, in seconds to a minute. A container is + in milliseconds. That is why "one container per process" is normal and "one VM per process" is absurd.3. The isolation boundary is a kernel API surface, not a hardware boundary. A VM escape requires defeating the hypervisor's narrow virtual-device interface. A container escape requires defeating one of 300-plus syscalls, plus every cgroup, namespace, and filesystem interface the kernel exposes. The attack surface is orders of magnitude wider.4. The filesystem is layered and disposable by default. A VM has a disk that persists. A container's writable layer is thrown away with unless you explicitly mount a volume. Treating a container like a small server — SSH in, edit a config, restart — loses your edit the moment the container is replaced. > Watch out: the fourth point is the most common beginner failure. Anything a container writes that is not on a mounted volume is temporary storage attached to that container instance, not to the image and not to the service. Container isolation is enforced by the same kernel that a compromised container is talking to. A kernel privilege-escalation bug that a container can reach is, in the worst case, a host compromise — and from the host, every other container on that machine. VM escapes exist too, but the interface an attacker must break is far narrower. Practical consequences: - Do not treat containers as a hard multi-tenant boundary for untrusted code. Chapter 1 — The write-ahead log Terminology - WAL — the write-ahead log. Every change to a data page is described in a WAL record that is flushed to durable storage before the page itself is written.- LSN — Log Sequence Number, a monotonically increasing byte position in the WAL stream (). The universal currency of replication and recovery.- WAL segment — a WAL file, 16 MB by default.- Checkpoint — a point at which all dirty shared buffers are flushed to the data files, allowing WAL before that point to be recycled.- Full page write — the first change to a page after a checkpoint writes the entire 8 KB page into the WAL, not just the delta. The write-ahead rule is what makes crash recovery possible: after a crash, PostgreSQL replays WAL from the last checkpoint forward, reconstructing every committed change. returns only once the commit record is durably flushed — this is exactly the D in ACID, and it is why is a data-loss setting, not a performance setting. Full page writes Operating systems and storage do not guarantee that an 8 KB page write is atomic. A crash mid-write can leave a torn page: half old, half new — a page WAL deltas cannot be applied to, because the base is corrupt. (the default) solves this by writing a complete image of the page the first time it is modified after each checkpoint, giving recovery a known-good base to replay from. The cost is WAL volume, and it is the reason WAL generation spikes immediately after every checkpoint. It is also the reason random-write workloads (see UUIDv4 keys in post 06) generate far more WAL than sequential ones: they touch more distinct pages, so more of them need full images. Chapter 3 — Streaming replication A standby connects to the primary over the replication protocol, receives WAL as it is generated, and replays it continuously. It is physical, byte-for-byte identical replication of the whole cluster. Setup On the primary: On the standby: Replication slots A slot makes the primary retain WAL until the standby has confirmed consuming it. That removes the classic failure where a standby falls behind, the primary recycles the WAL it still needed, and the standby is permanently broken. The slot's danger is symmetrical: a forgotten or dropped standby leaves an active slot, the primary retains WAL forever, and fills the disk. Bound it: Synchronous vs asynchronous Asynchronous (the default) means returns as soon as the primary has flushed locally. A primary failure can lose the last few transactions. Synchronous replication waits for a standby: The trade is unambiguous: synchronous replication buys zero data loss on failover and costs one network round trip on every commit. Configure rather than a single named standby — with one synchronous standby and no alternative, losing that standby stalls every commit on the primary. Hot standby and read scaling lets the standby serve read-only queries. Two conflicts follow: - A long query on the standby can be cancelled when WAL replay needs to remove rows it is reading (, default 30 s, controls how long replay waits first).- tells the primary to hold back vacuum for the standby's oldest snapshot, which prevents those cancellations — and reintroduces the long-transaction bloat problem from post 05, now caused remotely. Monitoring lag Alert on replay lag in bytes, not on the time figure alone: on an idle primary, grows simply because nothing has been committed, which produces false alarms. Failover and split brain Promotion itself is trivial: The danger is split brain: the old primary is not actually dead — it was unreachable — and it keeps accepting writes while the new primary also accepts writes. Two divergent timelines, both containing real customer data, and no automatic way to merge them. Automatic failover therefore requires more than a health check: - Fencing / STONITH — make certain the old primary cannot accept writes: kill the instance, revoke its network path, or detach its storage.- Quorum — the decision to promote must be made by a majority of an odd-numbered set of observers, not by one watcher that may itself be the partitioned party.- A single write endpoint — clients must reach the primary through a VIP, a proxy, or in a multi-host connection string, so promotion actually redirects them. Use Patroni (with etcd/Consul/Kubernetes for consensus) or repmgr. Hand-rolled failover scripts are the classic source of split-brain incidents, and — which can resynchronise a diverged old primary — only helps if the divergence is small and or data checksums were enabled beforehand. Chapter 4 — Logical replication Streaming replication copies bytes. Logical replication decodes the WAL into row-level changes and applies them as ordinary inserts, updates and deletes on the subscriber. That makes it selective and cross-version. What it can do that physical replication cannot: replicate a subset of tables, replicate between different major versions, replicate into a differently-indexed target, filter rows ( clauses on publications, PostgreSQL 15+) and columns (15+), and support two-way or many-to-one topologies. What it does not do, and these bite: - DDL is not replicated. Schema changes must be applied on both sides, subscriber first for additive changes.- Sequence values are not replicated (through PostgreSQL 17). At cutover you must advance every sequence on the subscriber manually with .- Every replicated table needs a replica identity — a primary key, or (which makes updates and deletes far more expensive), otherwise updates and deletes cannot be applied.- Large objects are not replicated. Truncate is (11+), but only for tables in the publication. Logical replication is right when downtime is measured in seconds and you want a live rollback path. Chapter 5 — Connection pooling PostgreSQL forks one operating-system process per connection. Each backend carries its own memory ( allocations, catalogue caches, prepared statement plans), typically several megabytes at rest and much more under load. Consequences: - Establishing a connection costs a plus catalogue loading — milliseconds, which is enormous compared to a 0.3 ms query.- Idle connections are not free; they hold memory and appear in every snapshot computation.- Throughput peaks at a fairly small number of active backends — roughly in the neighbourhood of the core count plus effective spindle count — and declines beyond it as lock contention and context switching dominate. Raising to 2000 does not raise throughput; it lowers it. This is why a pooler is near-mandatory for any application with more than a handful of application servers, and why serverless platforms that open a connection per request need one absolutely. Chapter 3 — Keys: natural, surrogate, and index locality Terminology - Natural key — a key drawn from the data itself: ISBN, ISO country code, email address.- Surrogate key — a meaningless generated identifier: a sequence or a UUID.- Index locality — how close together in the btree consecutive inserts land. High locality means new entries pack into the same few rightmost pages. Natural keys are excellent when the value is genuinely immutable, short, and externally defined — ISO country codes, currency codes, ISBNs. They are dangerous when the "obviously stable" value turns out to be mutable: email addresses change, national ID formats get reissued, SKUs get renumbered in an acquisition. A natural key that changes forces a cascading update across every referencing table. Default to a surrogate primary key and a constraint on the natural key. The rule for JSONB vs a real column Make it a real column when any of these is true: - You filter, sort, join, or group by it regularly.- It must be , unique, checked, or a foreign key.- Every row has it.- Its type matters (dates, money, booleans). Make it JSONB when all of these are true: - The shape is genuinely open-ended or supplied by an external system you do not control.- It is read as a whole blob far more often than it is queried by an inner field.- The set of keys varies by row and enumerating them would produce a wide sparse table. Chapter 8 — Migration discipline Every schema change happens against a running system. The rule is that a migration must never require the application and the database to change at the same instant. Expand / contract Split every breaking change into phases that are individually backwards-compatible: 1. Expand — add the new structure. Nullable column, new table, new index built . Old code keeps working.2. Backfill — populate the new structure in batches, committing as you go so no single transaction holds a snapshot for hours.3. Dual-write — deploy application code that writes both old and new. Reads still come from old.4. Migrate reads — deploy code that reads from new. Verify.5. Contract — stop writing the old structure, then drop it, once you are certain no rollback will need it. Renaming a column becomes: add → backfill → dual-write → switch reads → drop . Five deployments instead of one, and zero downtime at every step.
