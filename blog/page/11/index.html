Chapter 4 — Mipmaps + anisotropy A mipmap is a chain of pre-downscaled copies of the texture (1024 → 512 → 256 → 128 → ... → 1). MongoDB Course — 21 · CQRS + Event Sourcing on MongoDB
Created2025-07-08|Database MongoDB
CQRS (Command Query Responsibility Segregation) separates write models from read models. Event Sourcing treats the immutable event log as the source of truth — current state is a projection of replayed events. Both are architectural patterns, not Mongo features — but MongoDB fits them especially well: change streams as the projection bus (Post 12), for materialised views (Post 06), aggregation for replaying events, transactions for atomic event-store appends (Post 09). This post covers when each pays off, the canonical models, the trade-offs vs CRUD, and a worked order-management example end-to-end. > Series map: 19 Beanie+FastAPI → 20 Outbox → 21 CQRS + Event Sourcing (this post) → 22 RAG → ... → 29 K8s + mongosync + cost. Learning Outcome - Define CQRS and recognise when it earns its complexity.- Define Event Sourcing and the event-store schema in MongoDB.- Project events into read models via change streams.- Replay history for new projections + bug fixes.- Handle snapshots + projection rebuilds.- Combine outbox + CQRS + ES into a clean architecture. Chapter 1 — CQRS in one paragraph A normal CRUD app uses one model for reads and writes — same schema, same indexes, same database. CQRS splits them: command side handles writes (often normalised, validated, transactional), query side holds one or more read models optimised per use case (denormalised, fast). The read models are updated by events the command side publishes — usually asynchronously. Benefit: - Read models match exactly the queries they serve → simple + fast.- Read + write scale independently.- Multiple read models per command model (one for search, one for analytics, one for a mobile API). Cost: - More moving parts.- Read-after-write delay (eventual consistency).- Operational complexity. Use CQRS when one of: read volume >> write volume; queries diverge wildly from write shape; you already need an outbox + projections. Chapter 2 — Event Sourcing in one paragraph Instead of storing current state, store every change as an immutable event. Current state is computed by replaying events. Events are append-only — the most reliable storage primitive in databases. Benefits: - Full audit trail for free.- New projections retroactively built from history.- Bug fixes can replay events through corrected code.- Time-travel debugging. Costs: - Reads must aggregate events (use snapshots + projections).- Schema evolution of events is forever — versioning matters.- Higher mental + ops load than CRUD. Use ES when one of: regulatory audit trail mandatory; the domain is genuinely event-shaped (orders, payments, IoT, ledger systems); you need to replay history for new analytics or bug correction. ES + CQRS combine naturally — ES is the command-side event log, CQRS is the read-side projections. Chapter 3 — When NOT to use CQRS / ES - A CRUD app with simple reads + writes — KISS.- Small team / small product — overhead > benefit.- Tight read-after-write requirements with no tolerance for eventual consistency.- "Because it sounds modern" — biggest reason teams regret it. Default = CRUD. Add CQRS only when reads + writes genuinely diverge. Add ES only when the audit-or-replay property is mandatory. Chapter 4 — Event-store schema Constraints: - unique — prevents concurrent appends with the same version. Acts as optimistic concurrency control.- Append-only — never update or delete events. Use TTL only on very long-term retention if regulation allows. Most ES systems keep events forever (or in cold storage after N years). Chapter 5 — Command handlers (write side) A command handler: 1. Loads the aggregate by replaying its events.2. Validates the command against current state.3. Generates new events.4. Appends them with the next sequential . Concurrency: two handlers trying to append for the same aggregate → one wins, the other gets . The losing handler retries by re-loading the aggregate (now at version N+1) + reapplying validation. Chapter 6 — Projections (read side) A projection is a read model derived from events. One projection per query pattern. Projection: current order view A projection process change-streams (Post 12) and updates the view: The read endpoint: Read side never touches the event log directly. Fast. Indexed. Schema designed for the read pattern. Multiple projections Add a keyed by , an view, a Atlas Search index — each is a different consumer of the event stream. To add a new view: write the projection code, replay events from the beginning (no resume token), let it catch up, switch reads over. Chapter 7 — Snapshots Replaying thousands of events per command load is slow. Periodically write a snapshot of the aggregate state, then load . Take snapshots every N events (e.g., every 50) or on a schedule. Command handler loads snapshot + events with . Snapshots are derived data — disposable. Wipe + rebuild from events if your apply logic changes. Chapter 8 — Rebuilding projections Bug in projection code? Wrote bad state? Rebuild from scratch: Or use + sort by (events sorted naturally by ObjectId time) instead of change stream for a one-shot rebuild. This retroactive correctness is one of the headline benefits of ES — no other persistence model lets you "just rerun history with the new code". Chapter 9 — Event versioning Events live forever. Their schema must evolve gracefully. Patterns: 1. Add a field per event type + handle each version in the projection.2. Upcast old events to the new shape at read time.3. Migration events — emit a new event ("schema migrated to v2") rather than mutating history. Never mutate old events. The event log is sacred — modifying it breaks every projection's correctness. Chapter 10 — Worked end-to-end architecture Three deployables: 1. Command service — accepts commands, validates against loaded aggregate, appends events.2. Query service — reads from projection collections.3. Projection workers — one or many, each tail change stream + update one view. Optional: outbox alongside events for publishing to Kafka (Post 20) — events going to external systems. MongoDB Course — 20 · Outbox Pattern + Transactional Event Publishing
Created2025-07-06|Database MongoDB
You write to the database. You also need to publish an event ("order placed → send confirmation email"). If those two steps aren't atomic, you'll either lose events (DB committed, queue publish failed) or send duplicates (publish succeeded, DB rolled back). The outbox pattern solves this by treating the event as part of the same DB transaction, then publishing from the outbox to your message bus asynchronously. With MongoDB change streams (Post 12), the publisher is one process tailing the outbox collection — no Kafka Connect, no extra infrastructure. This post covers the full pattern, retry + idempotency + ordering, and the deduplication strategies downstream consumers need. > Series map: 18 Mongoose → 19 Beanie+FastAPI → 20 Outbox (this post) → 21 CQRS + ES → 22 RAG → ... → 29 K8s + mongosync + cost. Learning Outcome - Recognise the dual-write problem.- Build an outbox collection alongside business writes inside one transaction.- Build a change-stream-driven publisher with resume tokens.- Handle at-least-once delivery + downstream idempotency.- Pick between outbox + change streams vs Debezium / Kafka Connect. Chapter 1 — The dual-write problem Two failure modes: - DB insert succeeds, Kafka publish fails → lost event.- Kafka publish succeeds, DB insert fails → phantom event (consumers act on data that doesn't exist). Neither is acceptable for systems that need consistency between their database state + downstream consumers. Naive fixes that don't work - Try-catch + retry: same race, just longer odds.- 2-phase commit across MongoDB + Kafka: not supported across systems.- Eventual consistency + reconciliation: complex; high latency. The outbox Write the event as a row in the same database, same transaction as the business mutation. A separate process publishes from the outbox to Kafka / RabbitMQ / SQS / SNS, marking each event as published (or deleting it). Because the business write + outbox write are in one transaction, they're atomic. The publisher is async + retryable; downstream consumers handle duplicates idempotently. Chapter 2 — Outbox schema means unprocessed. The publisher claims, processes, marks. Chapter 3 — Producer side — transactional write Both writes commit together or neither does. The business state and the to-be-published event are forever consistent. Chapter 4 — Publisher — change-stream-driven (the cheap option) Properties: - At-least-once delivery — on crash before token persist, we replay.- Resume token persisted after successful publish + mark.- Network blip → retried with backoff, attempts incremented. This pattern needs no external infrastructure beyond your existing MongoDB. The publisher can run anywhere — a sidecar, a long-running container, a dedicated tiny pod. Chapter 5 — Publisher — polling fallback If change streams aren't available (standalone Mongo, very old versions, or a multi-region setup with restricted secondary access): Higher latency (poll interval) + more DB queries; rock-solid. Use change streams when available, polling as fallback. Chapter 6 — At-least-once → consumer must be idempotent Once a publisher delivers at-least-once, consumers will eventually see duplicates (publisher crashed mid-ack, network duplicate, replay after rebuild). Idempotency patterns: 1. Event ID dedup Every outbox event has a unique . Consumers track processed IDs (in a "consumedevents" collection, Redis set, etc.). Skip if already processed. 2. Idempotent operations Make the consumer's side-effect itself idempotent: , upsert by key, "set status to X" rather than increment. 3. Optimistic versioning Event carries ; consumer rejects updates with . Combine 1 + 2 for belt-and-braces. Chapter 7 — Ordering guarantees Kafka topics + partitions preserve order within a partition. Choose your partition key to match the ordering you need. For "all events on this order, in order" → key on .For "every event in occurrence order globally" → single-partition topic (low throughput). Most outbox usage cares about per-aggregate ordering — keying by is the right default. What if you don't have Kafka? SQS doesn't preserve order across the queue (unless FIFO with ). SNS doesn't (FIFO topics do). RabbitMQ exchanges + queues do preserve order per queue. Match destination to the ordering requirement. Chapter 8 — Backpressure + DLQ When the downstream is down for hours: - Outbox grows. Disk usage climbs.- If you have TTL on , you'll lose unpublished events — don't TTL the unpublished portion.- The publisher must implement exponential backoff to avoid hammering a downed downstream. Dead Letter Queue pattern: Alert + investigate. Don't silently drop. Chapter 9 — Outbox + sagas (cross-service workflows) For workflows spanning services (order → payment → inventory → shipping), combine outbox events with a saga orchestrator. Each step is one service's local transaction + outbox publication. The next service's consumer triggers its step. If a step fails, the orchestrator publishes a compensating action event → previous services undo. Outbox makes each step atomic + reliable. The saga adds the cross-step orchestration. Together they're the standard pattern for distributed workflows on document databases.
