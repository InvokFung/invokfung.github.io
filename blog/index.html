Chapter 1 — Smart pointers std::uniqueptr — sole ownership is move-only — there's exactly one owner at a time: Use for almost all heap-allocated objects. Costs nothing at runtime vs a raw pointer. std::sharedptr — shared ownership (reference count) Use when you genuinely have multiple owners — usually in observer-style or graph structures. Has reference-counting overhead, so prefer when one owner is enough. std::weakptr — non-owning observer Use to break reference cycles in graphs, or to observe without prolonging life. > Rule: never write or in new code. If you find yourself reaching for them, your design needs a smart pointer or a container. Chapter 2 — Move semantics in practice A move transfers a resource's ownership instead of copying it. The compiler optimises returns automatically (NRVO + implicit move). You don't have to do anything for the common case. When to call explicitly Use when:- You're passing a local variable to a sink (container, constructor) and won't use it afterward.- You're transferring ownership in an assignment or parameter. Don't move objects — moving requires modifying the source. The compiler silently falls back to copy. Pass-by-value + move idiom The parameter is constructed (one copy or move depending on the caller). Then transfers into with zero extra allocation. Modern idiomatic style. C++ classes are how you bundle data + behaviour and enforce invariants. Chapter 1 — class vs struct and are nearly identical — they differ only in default access: defaults to , to . Chapter 2 — Constructors and the initialiser list The syntax is the member initialiser list. It runs before the body — and is the only way to initialise:- members,- reference members,- base classes,- members with no default constructor. Always prefer the initialiser list over assignments inside the body. Default constructor If you declare any constructor, the compiler stops generating the default. Add if you want both your custom one and a default. Explicit Mark single-argument constructors to prevent surprise conversions. Standard advice. Chapter 3 — Destructor The destructor runs automatically when the object's lifetime ends:- For stack objects: end of scope.- For heap objects: when you call .- For class members: after the enclosing object's destructor body runs. In modern code, most classes don't need an explicit destructor — the Rule of Zero (Chapter 7). Chapter 4 — Member functions and const Mark methods whenever they don't mutate. Lets callers use the class with references — better safety, more places usable. this pointer Inside a member function, is a pointer to the current object. Chapter 5 — Copy semantics The compiler generates a copy constructor and copy assignment operator by default. They do member-wise copy. For most classes this is fine. For classes that own raw memory, you must define them. The default member-wise copy would have copied the pointer — both objects would point to the same memory, and the second destructor would double-free. Classic bug. Chapter 6 — Move semantics (C++11+) Moving = transferring ownership of resources without copying. Crucial for performance when you want a new object to take over what an old one had. When does move happen?- Returning a local from a function.- cast.- Passing a temporary (rvalue) to a constructor. > Trick: if you implement copy + dtor by hand, also implement move. Otherwise the compiler won't generate move automatically, and your class falls back to copies in performance-critical places. The Rule of Five If you write any of: destructor, copy ctor, copy assign, move ctor, move assign — you should write (or / ) all five. The Rule of Zero If your class only owns members that already handle their own copy/move/destruction (smart pointers, standard containers), write none of the five. Let the compiler default everything. This is the modern way. Reach for explicit Rule-of-Five only when wrapping a C library or hand-managing memory.
