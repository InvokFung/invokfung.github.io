<h1 id="Chapter-1-—-Why-write-design-docs"><a href="#Chapter-1-—-Why-write-design-docs" class="headerlink" title="Chapter 1 — Why write design docs"></a>Chapter 1 — Why write design docs</h1>
<p>A design doc is a short document written <strong>before</strong> coding that describes the plan and, most of all, the <strong>trade-offs</strong>. Changing a paragraph is cheaper than changing a service.</p>
<p>Malte Ubl's article &quot;Design Docs at Google&quot; (2020) describes the practice there:</p>
<ul>
<li>Design docs are <strong>informal</strong> documents. Authors write them before coding starts, to record the high-level plan and key design decisions, with a focus on trade-offs.</li>
<li>Common sections: context and scope, goals and non-goals, the actual design (including system-context diagrams, APIs, data storage), alternatives considered, and cross-cutting concerns such as security, privacy and observability.</li>
<li>Length: about <strong>10-20 pages</strong> for a larger project; <strong>&quot;mini design docs&quot; of 1-3 pages</strong> for smaller, incremental work.</li>
<li>A lifecycle: write and iterate quickly, get a wider review, update the doc during implementation when reality differs, then keep it as a record.</li>
<li><strong>Skip it</strong> when the solution is obvious and there are no real trade-offs to discuss, or when fast prototyping matters more.</li>
</ul>
<p>What it buys you: colleagues find the flaw before you write 3,000 lines; everyone reads the same plan; non-goals stop the scope from growing in secret; six months later the &quot;why&quot; is still written down; and the breakdown and risks feed straight into an estimate (see Dev Essentials 21 · Estimating).</p>

<h1 id="Chapter-3-—-ADRs-one-decision-one-file"><a href="#Chapter-3-—-ADRs-one-decision-one-file" class="headerlink" title="Chapter 3 — ADRs: one decision, one file"></a>Chapter 3 — ADRs: one decision, one file</h1>
<p>A design doc covers a project. An <strong>Architecture Decision Record</strong> covers one decision. Michael Nygard proposed the format in &quot;Documenting Architecture Decisions&quot; (2011):</p>
<ul>
<li><strong>Title</strong> — a short noun phrase, numbered: &quot;ADR 7: Use PostgreSQL for billing records&quot;.</li>
<li><strong>Status</strong> — proposed, accepted, deprecated, or superseded (with a link to the replacement).</li>
<li><strong>Context</strong> — the forces at play, described as neutral facts.</li>
<li><strong>Decision</strong> — in active voice, starting with &quot;We will…&quot;.</li>
<li><strong>Consequences</strong> — everything that follows, good <strong>and</strong> bad.</li>
</ul>
<p>Other points from the same article:</p>
<ul>
<li>Keep ADRs in the repository, for example <code>doc/arch/adr-NNN.md</code>, numbered in order. Numbers are never reused.</li>
<li>Each ADR is one or two pages, in full sentences.</li>
<li>When a decision is reversed, do not delete the old ADR. Mark it <strong>superseded</strong> and keep it — the history is the point.</li>
</ul>

<p><strong>Trick:</strong> write the ADR when you make the decision, not later. It takes 20 minutes then; it takes a day of archaeology in a year.</p>
</blockquote>

<h1 id="Chapter-4-—-Real-world-RFC-processes"><a href="#Chapter-4-—-Real-world-RFC-processes" class="headerlink" title="Chapter 4 — Real-world RFC processes"></a>Chapter 4 — Real-world RFC processes</h1>
<p>Big open-source projects run design docs in public. They are free lessons in how to argue for a change.</p>
<p><strong>Rust RFCs.</strong> Substantial changes to Rust go through an RFC in the <code>rust-lang/rfcs</code> repository. The template's sections are: Summary, Motivation, Guide-level explanation, Reference-level explanation, Drawbacks, Rationale and alternatives, Prior art, Unresolved questions, Future possibilities. Note the two explanation levels: one for users (&quot;how would I teach this?&quot;), one for implementers.</p>
<p><strong>Python PEPs.</strong> PEP 1 defines a PEP as a design document that gives information to the Python community or describes a new feature, process or environment change. There are three types: Standards Track, Informational and Process. The Python Steering Council makes the final decision, or a PEP-Delegate it approves. A PEP's sections include Abstract, Motivation, Rationale, Specification, Backwards Compatibility, Security Implications, How to Teach This, Reference Implementation, Rejected Ideas and Open Issues.</p>
<p>Both map onto the Chapter 2 template: Motivation → context and goals; Specification / reference-level explanation → proposal; Rationale, Rejected Ideas, alternatives → alternatives considered; Drawbacks, Backwards Compatibility → trade-offs and risks; Open Issues / Unresolved questions → open questions.</p>
<blockquote>
<p><strong>Trick:</strong> before writing your first design doc, read one accepted PEP and one accepted Rust RFC end to end. Notice how much space goes to alternatives and drawbacks.</p>
</blockquote>

<h1 id="Chapter-5-—-READMEs"><a href="#Chapter-5-—-READMEs" class="headerlink" title="Chapter 5 — READMEs"></a>Chapter 5 — READMEs</h1>
<p>A README is the front door of a repository. GitHub's docs say a README typically covers what the project does, why it is useful, how to get started, where to get help, and who maintains it. GitHub looks for the file in <code>.github/</code>, then the repository root, then <code>docs/</code>.</p>
<p>A structure that works:</p>
<ol>
<li><strong>Name + one-line description</strong> — what it is.</li>
<li><strong>Why</strong> — the problem it solves, in 2-3 sentences.</li>
<li><strong>Quickstart</strong> — the shortest path to a working result. Copy-paste commands.</li>
<li><strong>Usage</strong> — common tasks with examples.</li>
<li><strong>Configuration</strong> — every option, its default, and an example.</li>
<li><strong>Troubleshooting</strong> — the top 3-5 errors and their fixes.</li>
<li><strong>Contributing</strong> — how to set up, test and send changes.</li>
<li><strong>License.</strong></li>
</ol>

<h1 id="Chapter-6-—-Diátaxis-four-kinds-of-docs"><a href="#Chapter-6-—-Diátaxis-four-kinds-of-docs" class="headerlink" title="Chapter 6 — Diátaxis: four kinds of docs"></a>Chapter 6 — Diátaxis: four kinds of docs</h1>
<p>A README cannot hold everything. <strong>Diátaxis</strong>, created by Daniele Procida, says documentation serves four different needs, and each needs its own kind of page:</p>
<table>
<thead>
<tr>
<th>Type</th>
<th>Oriented to</th>
<th>Reader is…</th>
<th>Example for a CSV tool</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Tutorial</strong></td>
<td>Learning</td>
<td>New, following along</td>
<td>&quot;Clean your first CSV in 5 minutes&quot;</td>
</tr>
<tr>
<td><strong>How-to guide</strong></td>
<td>A task</td>
<td>Working, has a goal</td>
<td>&quot;How to clean every file in a folder&quot;</td>
</tr>
<tr>
<td><strong>Reference</strong></td>
<td>Information</td>
<td>Looking something up</td>
<td>&quot;All command-line options&quot;</td>
</tr>
<tr>
<td><strong>Explanation</strong></td>
<td>Understanding</td>
<td>Thinking, wants the why</td>
<td>&quot;Why encoding is detected before parsing&quot;</td>
</tr>
</tbody>
</table>
<p>The four sit on two axes: <strong>learning vs doing</strong> (study vs work) and <strong>action vs cognition</strong> (practical steps vs theory). The most common mistake is mixing them — a tutorial that stops to explain theory, or a reference page that tries to teach. Keep each page one type, and link between them.</p>
<p>A good README is a small <strong>tutorial</strong> (quickstart) plus links to the other three.</p>
<hr>
<h1 id="Chapter-7-—-Writing-clearly"><a href="#Chapter-7-—-Writing-clearly" class="headerlink" title="Chapter 7 — Writing clearly"></a>Chapter 7 — Writing clearly</h1>
<p>Two useful public guides:</p>
<ul>
<li>The <strong>Google developer documentation style guide</strong>. Its highlights include: be conversational without being frivolous; use second person (&quot;you&quot;); use active voice; put conditions <strong>before</strong> instructions; use sentence case for headings; use numbered lists for steps; write descriptive link text.</li>
<li>The US government's plain-language guidance. <code>plainlanguage.gov</code> now redirects to a set of <strong>plain language guides on <a href="http://digital.gov" target="_blank" rel="noopener external nofollow noreferrer">digital.gov</a></strong>, adapted from the old site. They advise: write for your audience, summarise long documents up front, use active voice and present tense, prefer short words and short sections, and avoid &quot;hidden verbs&quot; (say &quot;we analyse&quot;, not &quot;we conduct an analysis&quot;).</li>
</ul>
<p>Rules with before/after examples:</p>
<table>
<thead>
<tr>
<th>Rule</th>
<th>Before</th>
<th>After</th>
</tr>
</thead>
<tbody>
<tr>
<td>Conclusion first</td>
<td>&quot;After evaluating several options over two weeks, and considering…, we propose Redis.&quot;</td>
<td>&quot;We propose Redis for sessions. It cuts login latency from 180 ms to 20 ms. Details below.&quot;</td>
</tr>
<tr>
<td>Active voice</td>
<td>&quot;The config file is read by the server at startup.&quot;</td>
<td>&quot;The server reads the config file at startup.&quot;</td>
</tr>
<tr>
<td>Short sentences</td>
<td>One 45-word sentence with three commas and a semicolon</td>
<td>Three sentences of 15 words</td>
</tr>
<tr>
<td>Condition first</td>
<td>&quot;Run <code>setup.ps1</code> if you are on Windows.&quot;</td>
<td>&quot;On Windows, run <code>setup.ps1</code>.&quot;</td>
</tr>
<tr>
<td>No hidden verbs</td>
<td>&quot;Perform an installation of the package.&quot;</td>
<td>&quot;Install the package.&quot;</td>
</tr>
<tr>
<td>Descriptive links</td>
<td>&quot;Click <a href="#">here</a> for the API.&quot;</td>
<td>&quot;See the <a href="#">API reference</a>.&quot;</td>
</tr>
<tr>
<td>Concrete</td>
<td>&quot;The system is slow.&quot;</td>
<td>&quot;p95 latency is 2.4 s; the goal is 300 ms.&quot;</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>Trick:</strong> read your text aloud. Wherever you run out of breath or stumble, split the sentence.</p>
</blockquote>

<h1 id="Chapter-8-—-Diagrams-as-text"><a href="#Chapter-8-—-Diagrams-as-text" class="headerlink" title="Chapter 8 — Diagrams as text"></a>Chapter 8 — Diagrams as text</h1>
<p>Diagrams in image files go stale because nobody can edit them. Diagrams as <strong>text</strong> live next to the code, get reviewed in pull requests, and show clean diffs.</p>

<h2 id="The-C4-model"><a href="#The-C4-model" class="headerlink" title="The C4 model"></a>The C4 model</h2>
<p>Simon Brown's <strong>C4 model</strong> is a set of zoom levels for software architecture, like a map app:</p>
<table>
<thead>
<tr>
<th>Level</th>
<th>Diagram</th>
<th>Shows</th>
<th>Audience</th>
</tr>
</thead>
<tbody>
<tr>
<td>1</td>
<td>System context</td>
<td>Your system as one box, its users, and other systems it talks to</td>
<td>Everyone</td>
</tr>
<tr>
<td>2</td>
<td>Container</td>
<td>Apps and data stores inside the system (web app, API, database, queue)</td>
<td>Developers, ops</td>
</tr>
<tr>
<td>3</td>
<td>Component</td>
<td>Main parts inside one container</td>
<td>Developers</td>
</tr>
<tr>
<td>4</td>
<td>Code</td>
<td>Classes or functions (often generated, often skipped)</td>
<td>Developers</td>
</tr>
</tbody>
</table>
<p>C4 is notation- and tool-independent. Mermaid has C4 diagram syntax (<code>C4Context</code>, <code>C4Container</code>, …), but its docs mark it <strong>experimental</strong>, so the syntax may change. A plain flowchart with clear labels is often enough.</p>
<blockquote>
<p><strong>Trick:</strong> a design doc usually needs a level 1 (context) and a level 2 (container) diagram. Level 3 only where the change is.</p>
</blockquote>

<pre><code class="language-markdown"><figure class="highlight markdown"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span><br><span class="line">17</span><br><span class="line">18</span><br><span class="line">19</span><br><span class="line">20</span><br><span class="line">21</span><br><span class="line">22</span><br><span class="line">23</span><br><span class="line">24</span><br><span class="line">25</span><br><span class="line">26</span></pre></td><td class="code"><pre><code class="markdown"><span class="line"><span class="hljs-section"># ADR 007: Use PostgreSQL for billing records</span></span><br><span class="line"> </span><br><span class="line">Status: Accepted</span><br><span class="line">Date: 2026-09-24</span><br><span class="line"> </span><br><span class="line"><span class="hljs-section">## Context</span></span><br><span class="line">The billing service stores invoices, payments and refunds. <h2 id="Exercise-3-—-Goals-and-non-goals"><a href="#Exercise-3-—-Goals-and-non-goals" class="headerlink" title="Exercise 3 — Goals and non-goals"></a>Exercise 3 — Goals and non-goals</h2>

<details>
<summary>Solution</summary>
