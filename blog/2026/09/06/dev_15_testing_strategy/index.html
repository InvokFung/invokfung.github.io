Dev Essentials — 15 · Testing Strategy — Unit, Integration, End-to-End, Mocks and Testcontainers

Created2026-09-06|Updated2026-09-06|Dev Essentials
|Post View:

Tests are how you change code without fear. But more tests is not the goal; the right tests are. This post gives you a strategy: which kinds of tests to write, what makes a test good, and the tools that make it practical. It covers pytest in depth (fixtures, parametrize, tmp_path, monkeypatch), JUnit briefly, test doubles and when not to mock, real databases in tests with Testcontainers, flaky tests, coverage, property-based testing with Hypothesis, end-to-end tests with Playwright, and a short look at TDD. The next post runs all of this automatically in CI.

Series map: 01 Text Encoding → … → 14 API Reliability → 15 Testing (this post) → 16 CI/CD → … → 24 Desk Health. Part C · Building safely.

Learning Outcome

  • Tell unit, integration and end-to-end tests apart, and explain the test pyramid and the testing trophy as models.
  • Write fast, deterministic tests with one reason to fail, in Arrange-Act-Assert form.
  • Use pytest fixtures, parametrize, tmp_path, monkeypatch and markers; read a JUnit 5/6 test.
  • Choose between dummy, stub, fake, spy and mock, and wrap code you do not own.
  • Test against a real PostgreSQL or MongoDB with Testcontainers.
  • Find and fix flaky tests, read coverage as a signal, and add property-based and end-to-end tests.

Chapter 1 — Three kinds of tests

Kind What it checks Speed Typical tool
Unit One function or class, with no network, disk or database milliseconds pytest, JUnit
Integration Your code together with a real neighbour: a database, a queue, the file system, another module seconds pytest + Testcontainers
End-to-end (E2E) The whole system through its real interface, usually a browser or public API seconds to minutes Playwright

The names are fuzzy in practice. Agree on meanings inside your team, and focus on the real question: how much confidence does this test give, for how much time and maintenance?

Terminology

Term Meaning
SUT System under test: the code the test is about.
Test double Any object that stands in for a real one in a test (Chapter 5).
Fixture Setup that a test needs: data, objects, a temp folder, a database.
Flaky test A test that passes and fails on the same code.
Coverage Which lines or branches ran during the tests.
Regression test A test written for a bug you fixed, so it cannot come back.

Chapter 2 — Pyramid or trophy?

Both are models, not laws. They are opinions about where to spend effort.

Layer (top to bottom) Test pyramid (Cohn) Testing trophy (Dodds)
End-to-end / UI very few few
Service / integration some most effort
Unit most tests some
Static (types, lint) not part of the model the base layer

  • Test pyramid. Mike Cohn described it in Succeeding with Agile (2009); Martin Fowler's 2012 "TestPyramid" article is a common reference. Many fast unit tests at the bottom, fewer service tests, very few slow UI tests on top.
  • Testing trophy. Kent C. Dodds sketched it in 2018, building on Guillermo Rauch's line: "Write tests. Not too many. Mostly integration." Its layers are static analysis, unit, integration and E2E, with the biggest share on integration, because those tests are closest to how the software is used while still being fairly fast.

Both agree on the important parts: E2E tests are few and precious, static checks (types, lint) are cheap wins, and every test must earn its cost. The trophy fits web apps where most bugs live between components. The pyramid fits libraries and logic-heavy code. Testcontainers (Chapter 6) makes integration tests cheaper than they used to be, which pushes many teams toward the trophy shape.

Chapter 3 — What makes a good test

A good test is:

  1. Fast. Milliseconds for unit tests. Slow suites stop being run.
  2. Deterministic. Same code, same result, every time. No real clock, random seed, network or shared state.
  3. One reason to fail. When it goes red, the name tells you what broke.
  4. Independent. It passes alone, in any order, and in parallel.
  5. Readable. A reader sees the setup, the action and the expected result without jumping around.

The shape that gives you readability is Arrange-Act-Assert (named by Bill Wake in 2001). A bad test mixes everything; a good one has three clear parts:

Trick: name tests as sentences about behaviour: test_negative_amount_is_rejected, not test_with_tax_2. The test report then reads like a specification.

What each tool does:

Tool Use
plain assert pytest rewrites it to show both sides when it fails.
pytest.raises(E, match=...) The block must raise E with a matching message.
@pytest.mark.parametrize One test function, many cases; each case is reported separately (test_with_tax_table[typical]).
tmp_path A unique pathlib.Path folder per test. No clean-up code, no clashes.
monkeypatch setenv, delenv, setattr, chdir, all undone after the test.
pytest.approx Compare floats with a tolerance: assert 0.1 + 0.2 == pytest.approx(0.3).

Fixtures

A fixture is a function that builds what tests need. Tests ask for it by parameter name. Code after yield is the tear-down:

  • scope="function" (default) builds it fresh for every test. scope="session" builds it once for the whole run, which is useful for an expensive database container.
  • Put shared fixtures in tests/conftest.py; pytest finds them without imports.

Configuration and markers

pytest 9 reads native TOML from [tool.pytest] in pyproject.toml. Older versions use [tool.pytest.ini_options], where addopts is one string instead of a list.

Mark slow tests with @pytest.mark.integration, then choose: python -m pytest -m "not integration" for the fast inner loop, everything in CI.

Chapter 5 — JUnit briefly, and test doubles

JUnit in one screen

On the Java side, the current release is JUnit 6 (6.1.3 in August 2026; it needs Java 17+). The Jupiter API you write tests with keeps the org.junit.jupiter.api package from JUnit 5, so JUnit 5 tutorials still apply. Setup is in Java Development p1 / p2.

assertThrows(IllegalArgumentException.class, () -> ...) is the Java version of pytest.raises.

Test doubles

A test double replaces a real collaborator. The names come from Gerard Meszaros (xUnit Test Patterns, 2007), and Martin Fowler's article "Mocks Aren't Stubs" explains them:

Double What it is Example
Dummy Passed around, never used None for a logger the code path never touches
Stub Returns canned answers an exchange-rate function that always returns 1.1
Fake A working but simple implementation an in-memory repository instead of PostgreSQL
Spy A stub that also records how it was called a mailer that stores sent messages in a list
Mock Pre-programmed with expected calls that the test verifies "send must be called once with these arguments"

The service under test takes its collaborators as parameters, including the clock:

Fowler calls these two styles state verification (check the result) and behaviour verification (check the calls). Prefer state: behaviour checks break when you refactor how the work is done, even if the result is still right. Use a mock when the call is the result, as with sending an e-mail.

Common pitfall: Mock() accepts any attribute, so mailer.sned(...) (a typo) passes silently. Use create_autospec(RealMailer) so the mock has the same methods and signatures as the real class.

"Don't mock what you don't own"

This rule comes from the paper "Mock Roles, not Objects" (Freeman, Mackinnon, Pryce and Walnes, OOPSLA 2004) and the book Growing Object-Oriented Software, Guided by Tests. If you mock requests.get or a database driver directly, your test encodes your guess about how that library behaves. When the library changes, your mocks keep passing and production breaks.

Instead:

  1. Wrap the third-party code in a small class you own, such as PaymentGateway with charge(amount).
  2. Mock or fake your wrapper in unit tests of the business logic.
  3. Test the wrapper itself with an integration test against the real thing, or a real container of it (next chapter).

Chapter 6 — Real databases with Testcontainers

Fakes are fast, but they cannot catch a wrong SQL query, a missing index or a driver quirk. Testcontainers starts a real database in Docker for your tests and removes it afterwards. You need Docker running (Docker Desktop on Windows).

Python

  • In the current release (testcontainers-python 4.15, July 2026), modules live under testcontainers.community.*. The old from testcontainers.postgres import PostgresContainer still works but prints a DeprecationWarning.
  • get_connection_url() includes a SQLAlchemy driver name (postgresql+psycopg2://…) by default; driver=None gives a plain URL that psycopg accepts.
  • Pin the image tag (postgres:18), never latest, so a new major version does not surprise you.

Java

Watch out: the first run downloads the image, which can take a minute. In CI, keep these tests in their own job (Dev Essentials 16 · CI/CD) so the fast unit tests report first.

Chapter 7 — Flaky tests

A flaky test passes and fails on the same code. It is worse than no test, because people learn to ignore red. One large-scale data point (Google, 2016, one company's measurement): about 1.5% of all test runs gave a flaky result, almost 16% of tests showed some flakiness, and about 84% of observed pass-to-fail transitions involved a flaky test.

Cause Symptom Fix
Time Fails near midnight, month end, DST Inject a clock (below); store and compare in UTC (see Dev Essentials 02 · Dates & Time Zones)
Order Passes alone, fails in the full run Remove shared state; find it with pytest-randomly, which shuffles order and prints the seed
Network Fails when a remote API is slow or down Fake the client you own; use a local container instead of a shared server
Shared state Tests leak rows, files, env vars, globals tmp_path, monkeypatch, a fresh table per test (TRUNCATE), no module-level caches
Async / waits sleep(1) is sometimes not enough Wait for a condition, not a time (Playwright's auto-waiting does this)
Randomness Fails 1 run in 50 Fix the seed, or use Hypothesis, which reports the failing input

Inject the clock instead of reading the real one:

To reproduce an order bug that pytest-randomly found, run again with the seed it printed at the start: python -m pytest --randomly-seed=1234.

Common pitfall: automatic retries (pytest --reruns 3 from pytest-rerunfailures) hide flakiness instead of fixing it. Use them only as a short quarantine with a ticket and a deadline.

Chapter 8 — Coverage is a signal, not a goal

The report lists, per file, the percentage of lines and branches that ran, plus the missing line numbers. Missing lines are the useful part: they show code no test even executes.

Coverage cannot tell you whether anything was checked:

This test raises coverage and catches no bugs. Once a number becomes a target, people write tests like this (Goodhart's law).

Practical guidance:

  • Look at coverage of changed lines in each pull request more than the project total.
  • For a feel of scale, Google's testing blog (2020) gave its internal guideline as 60% "acceptable", 75% "commendable" and 90% "exemplary", and warned against top-down mandates. Treat it as one company's rule of thumb.
  • A red flag is high coverage and many production bugs: the tests run code without checking results.

Chapter 9 — Property-based testing with Hypothesis

Example tests check the cases you thought of. Property-based tests state a rule that must hold for all inputs, and a library generates the inputs. By default Hypothesis tries 100 generated examples per test, and when one fails it shrinks it to a minimal failing case.

A run-length encoder with a hidden bug:

Example tests like decode(encode("aaab")) == "aaab" pass. The property test does not:

Hypothesis soon reports a tiny input such as text='0': encode("0") is "10", and decode reads both characters as one count. The fix is a format that does not mix counts and data, such as a list of (char, count) pairs.

Good properties to look for:

Property Example
Round trip decode(encode(x)) == x, json.loads(json.dumps(x)) == x
Invariant sorted(xs) is in order and has the same items as xs (Counter(result) == Counter(xs))
Oracle a fast function agrees with a slow, obviously correct one
Idempotence normalise(normalise(x)) == normalise(x)

Chapter 10 — End-to-end tests with Playwright

E2E tests drive a real browser through your real app. Keep them few: the main user journeys (sign in, buy, publish), not every edge case.

  • The page fixture gives each test a fresh, isolated browser context.
  • Locate elements the way users see them (get_by_role, get_by_label, get_by_text), not by CSS classes that change with every redesign.
  • Playwright auto-waits: actions wait until the element is visible, stable and enabled, and expect(...) assertions retry until they pass or time out. Never add time.sleep.
  • --base-url http://localhost:3000 lets tests use page.goto("/") against your own dev server.

Chapter 11 — TDD in brief

Test-driven development (Kent Beck, Test-Driven Development: By Example) is a short loop:

  1. Red: write one small failing test for the next bit of behaviour.
  2. Green: write the simplest code that makes it pass.
  3. Refactor: clean up while all tests stay green.

It works best when the behaviour is clear and the code is logic-heavy (parsers, pricing rules, state machines). It is harder for exploratory UI work. Even if you do not use TDD all the time, one habit is always worth it: when you fix a bug, first write the test that fails because of it (see Dev Essentials 10 · Debugging).

Exercise 1 — Name the kind

Classify each test: (a) with_tax(100) returns 108.00; (b) PgOrderRepo saves and loads a row in a Testcontainers PostgreSQL; (c) a browser signs in and sees "Welcome"; (d) OrderService.place with a fake repo and a mock mailer.

Solution

(a) unit, (b) integration, (c) end-to-end, (d) unit: the fake and the mock replace all real neighbours, so it tests one class alone.

Exercise 4 — Pick the double

Which double fits? (a) A function needs a logger argument, but the tested path never logs. (b) You need get_rate("EUR") to return 1.1. (c) You must prove exactly one SMS is sent. (d) You want repository behaviour without a database.

Solution

(a) dummy, (b) stub, (c) mock (or a spy you assert on), (d) fake.

Exercise 5 — Wrap what you do not own

Your code calls requests.get(url, timeout=5).json()["rate"] in three places, and the tests mock requests.get. Refactor for testability.

Solution

Business code takes a RateClient (or anything with get_rate) as a parameter. Its unit tests pass a stub: a tiny class whose get_rate always returns 1.1. RateClient itself gets one integration test against a local test server or a container. When requests changes, only that one test needs attention.
