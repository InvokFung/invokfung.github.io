<h1 id="Chapter-2-—-Pyramid-or-trophy"><a href="#Chapter-2-—-Pyramid-or-trophy" class="headerlink" title="Chapter 2 — Pyramid or trophy?"></a>Chapter 2 — Pyramid or trophy?</h1>
<p>Both are <strong>models</strong>, not laws. They are opinions about where to spend effort.</p>
<table>
<thead>
<tr>

<td>few</td>

<td>some</td>
<td><strong>most effort</strong></td>

<tr>
<td>Unit</td>
<td><strong>most tests</strong></td>
<td>some</td>

<td>not part of the model</td>

<ul>
<li><strong>Test pyramid.</strong> Mike Cohn described it in <em>Succeeding with Agile</em> (2009); Martin Fowler's 2012 &quot;TestPyramid&quot; article is a common reference. Many fast unit tests at the bottom, fewer service tests, very few slow UI tests on top.</li>
<li><strong>Testing trophy.</strong> Kent C. Dodds sketched it in 2018, building on Guillermo Rauch's line: &quot;Write tests. Not too many. Mostly integration.&quot; Its layers are static analysis, unit, integration and E2E, with the biggest share on <strong>integration</strong>, because those tests are closest to how the software is used while still being fairly fast.</li>
</ul>
<p>Both agree on the important parts: E2E tests are few and precious, static checks (types, lint) are cheap wins, and every test must earn its cost. The trophy fits web apps where most bugs live between components. The pyramid fits libraries and logic-heavy code. Testcontainers (Chapter 6) makes integration tests cheaper than they used to be, which pushes many teams toward the trophy shape.</p>
<hr>
<h1 id="Chapter-3-—-What-makes-a-good-test"><a href="#Chapter-3-—-What-makes-a-good-test" class="headerlink" title="Chapter 3 — What makes a good test"></a>Chapter 3 — What makes a good test</h1>
<p>A good test is:</p>
<ol>
<li><strong>Fast.</strong> Milliseconds for unit tests. Slow suites stop being run.</li>
<li><strong>Deterministic.</strong> Same code, same result, every time. No real clock, random seed, network or shared state.</li>
<li><strong>One reason to fail.</strong> When it goes red, the name tells you what broke.</li>
<li><strong>Independent.</strong> It passes alone, in any order, and in parallel.</li>
<li><strong>Readable.</strong> A reader sees the setup, the action and the expected result without jumping around.</li>
</ol>
<p>The shape that gives you readability is <strong>Arrange-Act-Assert</strong> (named by Bill Wake in 2001). A bad test mixes everything; a good one has three clear parts:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">test_everything</span>():                       <span class="hljs-comment"># BAD: which part broke? you cannot tell</span></span><br><span class="line">    <span class="hljs-keyword">assert</span> with_tax(<span class="hljs-number">100</span>) == Decimal(<span class="hljs-string">&quot;108.00&quot;</span>)</span><br><span class="line">    <span class="hljs-keyword">assert</span> load_prices(Path(<span class="hljs-string">&quot;prices.csv&quot;</span>))   <span class="hljs-comment"># depends on a real file in the repo</span></span><br><span class="line">    <span class="hljs-keyword">assert</span> send_invoice(customer_id=<span class="hljs-number">42</span>)      <span class="hljs-comment"># sends a real e-mail</span></span><br><span class="line"> </span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">test_with_tax_adds_eight_percent</span>():      <span class="hljs-comment"># GOOD</span></span><br><span class="line">    amount = <span class="hljs-number">100</span>                             <span class="hljs-comment"># Arrange</span></span><br><span class="line">    result = with_tax(amount)                <span class="hljs-comment"># Act</span></span><br><span class="line">    <span class="hljs-keyword">assert</span> result == Decimal(<span class="hljs-string">&quot;108.00&quot;</span>)       <span class="hljs-comment"># Assert</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Trick:</strong> name tests as sentences about behaviour: <code>test_negative_amount_is_rejected</code>, not <code>test_with_tax_2</code>. The test report then reads like a specification.</p>
</blockquote>

<p>A <strong>test double</strong> replaces a real collaborator. The names come from Gerard Meszaros (<em>xUnit Test Patterns</em>, 2007), and Martin Fowler's article &quot;Mocks Aren't Stubs&quot; explains them:</p>

<tr>
<td>Stub</td>
<td>Returns canned answers</td>

<p>Fowler calls these two styles <strong>state verification</strong> (check the result) and <strong>behaviour verification</strong> (check the calls). Prefer state: behaviour checks break when you refactor how the work is done, even if the result is still right. Use a mock when the call <strong>is</strong> the result, as with sending an e-mail.</p>
<blockquote>
<p><strong>Common pitfall:</strong> <code>Mock()</code> accepts any attribute, so <code>mailer.sned(...)</code> (a typo) passes silently. Use <code>create_autospec(RealMailer)</code> so the mock has the same methods and signatures as the real class.</p>
</blockquote>
<h2 id="Dont-mock-what-you-dont-own"><a href="#Dont-mock-what-you-dont-own" class="headerlink" title="&quot;Don't mock what you don't own&quot;"></a>&quot;Don't mock what you don't own&quot;</h2>
<p>This rule comes from the paper &quot;Mock Roles, not Objects&quot; (Freeman, Mackinnon, Pryce and Walnes, OOPSLA 2004) and the book <em>Growing Object-Oriented Software, Guided by Tests</em>. If you mock <code>requests.get</code> or a database driver directly, your test encodes <strong>your guess</strong> about how that library behaves. When the library changes, your mocks keep passing and production breaks.</p>
<p>Instead:</p>
<ol>
<li>Wrap the third-party code in a small class <strong>you own</strong>, such as <code>PaymentGateway</code> with <code>charge(amount)</code>.</li>
<li>Mock or fake <strong>your</strong> wrapper in unit tests of the business logic.</li>
<li>Test the wrapper itself with an <strong>integration test</strong> against the real thing, or a real container of it (next chapter).</li>
</ol>
<hr>
<h1 id="Chapter-6-—-Real-databases-with-Testcontainers"><a href="#Chapter-6-—-Real-databases-with-Testcontainers" class="headerlink" title="Chapter 6 — Real databases with Testcontainers"></a>Chapter 6 — Real databases with Testcontainers</h1>
<p>Fakes are fast, but they cannot catch a wrong SQL query, a missing index or a driver quirk. <strong>Testcontainers</strong> starts a real database in Docker for your tests and removes it afterwards. You need Docker running (Docker Desktop on Windows).</p>

<h1 id="Chapter-7-—-Flaky-tests"><a href="#Chapter-7-—-Flaky-tests" class="headerlink" title="Chapter 7 — Flaky tests"></a>Chapter 7 — Flaky tests</h1>
<p>A flaky test passes and fails on the same code. It is worse than no test, because people learn to ignore red. One large-scale data point (Google, 2016, one company's measurement): about 1.5% of all test runs gave a flaky result, almost 16% of tests showed some flakiness, and about 84% of observed pass-to-fail transitions involved a flaky test.</p>
<table>
<thead>
<tr>
<th>Cause</th>
<th>Symptom</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Time</strong></td>
<td>Fails near midnight, month end, DST</td>
<td>Inject a clock (below); store and compare in UTC (see Dev Essentials 02 · Dates &amp; Time Zones)</td>
</tr>
<tr>
<td><strong>Order</strong></td>
<td>Passes alone, fails in the full run</td>
<td>Remove shared state; find it with <code>pytest-randomly</code>, which shuffles order and prints the seed</td>
</tr>
<tr>
<td><strong>Network</strong></td>
<td>Fails when a remote API is slow or down</td>
<td>Fake the client you own; use a local container instead of a shared server</td>
</tr>
<tr>
<td><strong>Shared state</strong></td>
<td>Tests leak rows, files, env vars, globals</td>
<td><code>tmp_path</code>, <code>monkeypatch</code>, a fresh table per test (<code>TRUNCATE</code>), no module-level caches</td>
</tr>
<tr>
<td><strong>Async / waits</strong></td>
<td><code>sleep(1)</code> is sometimes not enough</td>
<td>Wait for a condition, not a time (Playwright's auto-waiting does this)</td>
</tr>
<tr>
<td><strong>Randomness</strong></td>
<td>Fails 1 run in 50</td>
<td>Fix the seed, or use Hypothesis, which reports the failing input</td>
</tr>
</tbody>
</table>

<h1 id="Chapter-8-—-Coverage-is-a-signal-not-a-goal"><a href="#Chapter-8-—-Coverage-is-a-signal-not-a-goal" class="headerlink" title="Chapter 8 — Coverage is a signal, not a goal"></a>Chapter 8 — Coverage is a signal, not a goal</h1>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">pip install pytest-cov</span><br><span class="line">python -m pytest --cov=shop --cov-branch --cov-report=term-missing</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The report lists, per file, the percentage of lines and branches that ran, plus the <strong>missing</strong> line numbers. Missing lines are the useful part: they show code no test even executes.</p>
<p>Coverage cannot tell you whether anything was <strong>checked</strong>:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">test_with_tax_runs</span>():</span><br><span class="line">    with_tax(<span class="hljs-number">100</span>)          <span class="hljs-comment"># runs every line on the happy path, asserts nothing</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>This test raises coverage and catches no bugs. Once a number becomes a target, people write tests like this (Goodhart's law).</p>
<p>Practical guidance:</p>
<ul>
<li>Look at coverage of <strong>changed lines</strong> in each pull request more than the project total.</li>
<li>For a feel of scale, Google's testing blog (2020) gave its <strong>internal</strong> guideline as 60% &quot;acceptable&quot;, 75% &quot;commendable&quot; and 90% &quot;exemplary&quot;, and warned against top-down mandates. Treat it as one company's rule of thumb.</li>
<li>A red flag is high coverage <strong>and</strong> many production bugs: the tests run code without checking results.</li>
</ul>

<h1 id="Chapter-11-—-TDD-in-brief"><a href="#Chapter-11-—-TDD-in-brief" class="headerlink" title="Chapter 11 — TDD in brief"></a>Chapter 11 — TDD in brief</h1>
<p><strong>Test-driven development</strong> (Kent Beck, <em>Test-Driven Development: By Example</em>) is a short loop:</p>
<ol>
<li><strong>Red:</strong> write one small failing test for the next bit of behaviour.</li>
<li><strong>Green:</strong> write the simplest code that makes it pass.</li>
<li><strong>Refactor:</strong> clean up while all tests stay green.</li>
</ol>
<p>It works best when the behaviour is clear and the code is logic-heavy (parsers, pricing rules, state machines). It is harder for exploratory UI work. Even if you do not use TDD all the time, one habit is always worth it: <strong>when you fix a bug, first write the test that fails because of it</strong> (see Dev Essentials 10 · Debugging).</p>
