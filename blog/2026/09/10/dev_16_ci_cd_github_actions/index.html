Dev Essentials — 16 · CI/CD with GitHub Actions — Build, Test and Deploy a Static Blog

Created2026-09-10|Updated2026-09-10|Dev Essentials
|Post View:

A pipeline that builds, tests and deploys on every push turns "it works on my machine" into "it works on a clean machine, every time". This post teaches GitHub Actions from the ground up: workflows, events, jobs, runners, secrets, artifacts, environments, concurrency and permissions. You build a Python CI pipeline with a version matrix and caching, then deploy a static site to GitHub Pages with the official Pages actions. The case study is this blog's own 2022-era workflow: what aged badly, and a modern replacement. The last chapter covers the security traps, including the 2025 tj-actions/changed-files compromise. This post ends Part C.

Series map: 01 Text Encoding → … → 15 Testing → 16 CI/CD (this post) → 17 How LLMs Work → … → 24 Desk Health. Part C · Building safely.

Learning Outcome

  • Explain CI, continuous delivery and continuous deployment, and the GitHub Actions building blocks.
  • Write a Python CI workflow: lint, a test matrix across Python versions, dependency caching, artifacts.
  • Use secrets, environments, concurrency and least-privilege permissions: correctly.
  • Deploy a static site to GitHub Pages with configure-pages, upload-pages-artifact and deploy-pages.
  • Read an old workflow, list what is outdated, and modernise it.
  • Avoid pull_request_target "pwn requests", script injection and compromised third-party actions.

Chapter 1 — CI, CD and the building blocks

Continuous integration (CI) means everyone merges small changes often, and every push or pull request is built and tested automatically. Continuous delivery means every change that passes is ready to release with one click. Continuous deployment goes one step further: it releases automatically.

GitHub Actions runs these pipelines from YAML files in .github/workflows/.

Terminology

Term Meaning
Workflow One YAML file in .github/workflows/.
Event What starts a workflow: push, pull_request, schedule, workflow_dispatch (manual button), and more.
Job A group of steps that runs on one runner. Jobs run in parallel unless one needs another.
Step One command (run:) or one action (uses:), run in order inside a job.
Runner The machine that runs a job. GitHub-hosted runners are fresh VMs, thrown away after the job.
Action A reusable step, referenced as owner/repo@ref, such as actions/checkout@v7.
Secret An encrypted value, read as ${{ secrets.NAME }}.
Artifact Files a job uploads to keep after the run, or to pass to a later job.
Environment A named deploy target (production, github-pages) with its own secrets and protection rules.
concurrency A group name; only one run in the group is active at a time.
permissions What the automatic GITHUB_TOKEN may do in this workflow or job.

Chapter 2 — Anatomy of a workflow

  • ${{ ... }} is an expression. It reads contexts such as github, matrix, secrets, steps and env.
  • run: uses bash on Linux and macOS runners and PowerShell (pwsh) on Windows runners. Set shell: bash or shell: pwsh to choose.
  • Runner labels (checked September 2026): ubuntu-latest is Ubuntu 24.04 (ubuntu-26.04 also exists), windows-latest is Windows Server 2025, macos-latest is macOS 26 on Arm. -latest moves over time; pin a version like ubuntu-24.04 when you need stability.

Watch out: YAML reads 3.10 as the number 3.1. Always quote versions: python-version: "3.10".

Chapter 3 — CI for a Python project

A small project:

The workflow: one fast lint job, then a test matrix.

How it works:

  • The matrix makes 5 test jobs: 4 Python versions on Ubuntu plus 1 on Windows. fail-fast is true by default, which cancels the others on the first failure.
  • cache: pip saves pip's download cache between runs. The key comes from the file in cache-dependency-path, so a changed pin gives a fresh cache.
  • Artifact names must be unique in a run, so the name includes the matrix values.
  • Why 3.11–3.14: Python 3.10 reaches end of life in October 2026, and 3.15 is scheduled for 2026-10-01. To try a pre-release, add "3.15" to the list and allow-prereleases: true to setup-python.

Then make the checks required: in the repository settings, add a branch ruleset for main that requires the lint and test status checks. Now a red build blocks the merge button.

Trick: keep CI fast. Put cheap checks (lint, type check) first with needs:, so a typo fails in 30 seconds instead of after a 10-minute matrix. Put slow integration tests (Dev Essentials 15 · Testing) in their own job.

Common pitfall: a cache is a speed-up, never a source of truth. A job must still pass with an empty cache.

Chapter 4 — Secrets, artifacts, environments and permissions

The GITHUB_TOKEN and permissions:

At the start of every job, GitHub creates a fresh GITHUB_TOKEN for that repository. It expires when the job finishes (at most 6 hours on GitHub-hosted runners). What it may do is set by permissions::

  • As soon as you list any permission, every permission you did not list becomes none.
  • permissions: {} gives no permissions at all.
  • Set the default at the top to read-only, and raise it only in the job that needs more.

Secrets

Add secrets in the repository settings, then pass them to steps through env::

  • Values are masked in logs, but GitHub says redaction is not guaranteed: a secret that is transformed (base64, split, JSON) may appear in clear text.
  • Anyone with write access to the repo can write a workflow that reads the secrets.
  • Except for GITHUB_TOKEN, secrets are not passed to workflows triggered by pull requests from forks, and the token is read-only there.

Chapter 5 — CD: deploy a static site to GitHub Pages

GitHub Pages hosts static files. A project site is served at https://<owner>.github.io/<repository>/; a user site comes from a repository named <owner>.github.io and is served at the root. There are two ways to publish:

Source How it works
Deploy from a branch Pages serves (or builds with Jekyll) a branch such as gh-pages.
GitHub Actions Your workflow builds the site, uploads it as a Pages artifact, and deploys it.

To use the second way: Settings → Pages → Build and deployment → Source: GitHub Actions. Then the workflow has two jobs:

  1. build: check out, build, then actions/upload-pages-artifact@v5 packs the folder into an artifact named github-pages (a gzip tar; kept 1 day by default).
  2. deploy: actions/deploy-pages@v5 publishes that artifact. It needs pages: write (to create the deployment) and id-token: write (to get an OIDC token that proves which workflow and branch the deployment comes from). It runs in the github-pages environment.

actions/configure-pages@v6 is optional. It reads the site's metadata (for example base_path, such as /my-repo) and can adjust a few generators' configs. It needs pages: read.

Usage limits (GitHub docs): the published site may be at most 1 GB, a deployment times out after 10 minutes, and there is a soft bandwidth limit of 100 GB per month.

Watch out: with branch publishing, Jekyll skips folders that start with _, such as Next.js's _next/, unless the branch has a .nojekyll file. With the GitHub Actions source, your workflow does the build and the artifact is published as it is. Also, upload-pages-artifact v4 and later leave out dotfiles unless you set include-hidden-files: true (added in v5).

The full workflow is in the next chapter, applied to this blog.

Chapter 6 — Case study: modernising this blog's workflow

The 2022-era Hexo workflow

The Hexo source repository of this blog still runs this workflow (name and email replaced by placeholders):

hexo cl && hexo g && hexo d is clean, generate, deploy. The deploy step uses the SSH key to push the generated site into a separate GitHub Pages repository.

What aged badly

# Problem Why it matters
1 actions/checkout@v3, actions/setup-node@v3 Both declare the node16 runtime. Runners have used Node 24 for actions by default since 2026-06-16, and Node 20 was removed on 2026-09-23. So these old majors now run on a runtime they were not built for. Current majors are checkout@v7 and setup-node@v7.
2 node-version: "16" Node.js 16 reached end of life on 2023-09-11: three years without security fixes.
3 npm install May update the lockfile and pick new versions. npm ci installs exactly the lockfile and fails if it does not match package.json.
4 npm install hexo-cli -g An unpinned global tool, fresh on every run. Use the project's own local binary via npx.
5 SSH private key in a secret A long-lived key with push rights to another repository. If it leaks, someone can deface the site until the key is rotated by hand.
6 ssh-keyscan github.com Trusts whatever host key the network returns at run time. GitHub publishes its fingerprints; GitHub also replaced its RSA host key on 2023-03-24 after it was exposed.
7 No permissions: The GITHUB_TOKEN gets the repository's default permissions, which may be read-write.
8 No concurrency Two quick pushes can deploy out of order; the older build may win.
9 Name and email in the file Personal data in a public file; not needed at all with the Pages actions.
10 No timeout-minutes, no checks A hung step can burn up to 6 hours; nothing verifies the build before it goes live.

The Next.js port: a static export

The Next.js version of the blog does a static export when the variable NEXT_EXPORT=1 is set (next.config.mjs, abridged):

  • output: "export" makes next build write plain HTML, CSS and JS (the old next export command was removed in Next.js 14).
  • distDir: "out" is where the files go (out is also the default for exports).
  • basePath: "/blog" prefixes every link, because the site is served under /blog/, exactly like a project site at https://<owner>.github.io/<repository>/.

Today that out/ folder is copied into a blog/ folder of the Pages repository by a local script. A workflow can do the same job on every push.

The modern workflow

What changed, point by point: current action majors; an LTS Node line; npm ci with the npm cache; no SSH key, no personal data, no global installs; read-only default token and job-level extra rights only where needed; a pages concurrency group; timeouts; and a manual "Run workflow" button. The repository that runs this workflow must have Source: GitHub Actions in its Pages settings.

Watch out: basePath must match the path the site is served from. A project site lives at /<repository>/, so /blog only fits a repository named blog (or a custom domain set up that way). If CSS and JS return 404 after a deploy, check this first. configure-pages outputs the real base_path, which you could pass to the build instead of hard-coding it.

For the Hexo source, only the build steps change: npx hexo generate instead of the Next.js build, and path: public (Hexo's default public_dir). Check that your Hexo version supports the Node line you choose.

Node.js release lines on 2026-09-25 (from the Node.js release schedule):

Line Status Moves on
20 end of life since 2026-04-30 —
22 Maintenance LTS end of life 2027-04-30
24 Active LTS Maintenance from 2026-10-20, end of life 2028-04-30
26 Current becomes LTS on 2026-10-28

Pin the major (24) for repeatable builds, or use node-version: lts/* to always get the newest LTS. Either way, plan an upgrade every October.

Chapter 7 — Security: the traps

pull_request vs pull_request_target

Event Runs code from Secrets GITHUB_TOKEN for fork PRs
pull_request the PR's merge commit not passed for fork PRs read-only
pull_request_target the base repository's default branch available can have write access

pull_request_target exists so a workflow can, for example, label or comment on PRs from forks. It is safe only if it never runs the PR's code. The classic "pwn request" does exactly that: it checks out the fork's head commit and runs npm install or a test script in a job that holds secrets and a write token. The attacker's package.json then runs with those rights.

GitHub has tightened this twice. Since 2025-12-08, pull_request_target always takes the workflow file and checkout ref from the default branch. And actions/checkout@v7 (backported to older majors on 2026-07-20) refuses to check out fork PR code in pull_request_target and workflow_run workflows unless you set allow-unsafe-pr-checkout: true, a name meant to stand out in review. Workflows pinned to an older SHA or exact version do not get the backport.

Watch out: workflow_run has the same problem: it runs with secrets after a PR workflow finishes. Treat any artifact it downloads from that PR as untrusted data.

Third-party actions: the tj-actions/changed-files compromise

On 2025-03-14 and 15, an attacker who had obtained a token with access to the popular tj-actions/changed-files action moved its version tags (v1 up to v45.0.7) to a malicious commit (CVE-2025-30066). The injected code read the runner's memory and printed secrets into the build logs, which are public for public repositories. More than 23,000 repositories used the action. CISA's alert covers it together with a compromise of reviewdog/action-setup@v1 (CVE-2025-30154) around the same time, which may have enabled it. The fixed release is v46.0.1. Workflows pinned to the full SHA of an earlier clean commit kept running that clean code, because moving a tag does not change an existing commit.

Defences, in order of effort:

  1. Least privilege: read-only default permissions:, secrets only in the jobs that need them, environments with reviewers for deploy keys.
  2. Fewer third-party actions: a few lines of shell or an official action are often enough.
  3. Pin by full SHA and let Dependabot propose updates you review.
  4. Organisation policy: allow-lists of actions; since August 2025 policies can also require SHA pinning (unpinned workflows fail) and block a named action with a ! prefix during an incident.
  5. Lint your workflows: actionlint finds syntax and expression bugs; zizmor is a static analyser for Actions security issues.
  6. If an action you use is compromised: stop using it, search your logs for leaked values, and rotate every secret the workflow could see.

Practice Exercises

Exercise 1 — Read a workflow

In the CI workflow of Chapter 3: how many jobs run on a push to main, and in which order? What happens to a running CI job when you push again to the same PR?

Solution

Six jobs: lint first, then five test jobs (4 Python versions on Ubuntu + 1 on Windows) in parallel, because test has needs: lint. A new push to the same PR has the same concurrency group (ci-refs/pull/<n>/merge), and cancel-in-progress: true cancels the older run.

Exercise 2 — The YAML number trap

A teammate writes python-version: [3.9, 3.10, 3.11]. The 3.10 job fails with "version 3.1 not found". Why, and how do you fix it?

Solution

YAML parses unquoted 3.10 as the float 3.1. Quote every version: python-version: ["3.10", "3.11", "3.12"]. Also drop 3.9: it reached end of life in October 2025.

Exercise 3 — Least privilege

A workflow has no permissions: key. Job test runs pytest; job release creates a GitHub Release. Add the smallest permissions.

Solution

Remember: a job-level permissions: block replaces the workflow default for that job.

Exercise 4 — Fix the injection

This step posts a greeting on new issues. Make it safe.

Solution

The title now reaches bash as the value of a variable, not as script text. Quoting inside run: does not help without this, because the expression is pasted in before bash parses anything.
