<h1 id="Chapter-1-—-How-remote-calls-fail"><a href="#Chapter-1-—-How-remote-calls-fail" class="headerlink" title="Chapter 1 — How remote calls fail"></a>Chapter 1 — How remote calls fail</h1>
<p>A function call inside one process either returns or throws. A call over a network has more outcomes:</p>
<table>
<thead>
<tr>
<th>Failure</th>
<th>What you see</th>
<th>Example</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Slow</strong></td>
<td>The call takes 30 s instead of 30 ms</td>
<td>Database is overloaded, a GC pause, a long queue</td>
</tr>
<tr>
<td><strong>Down</strong></td>

<td>Some calls work, some fail</td>

<p>The last one is the hard case. The request may have reached the server and run. Only the reply was lost. If you retry blindly, you may do the action twice. If you do not retry, the action may never happen. Most of this post is about handling this case safely.</p>

<h1 id="Chapter-2-—-Timeouts-on-every-network-call"><a href="#Chapter-2-—-Timeouts-on-every-network-call" class="headerlink" title="Chapter 2 — Timeouts on every network call"></a>Chapter 2 — Timeouts on every network call</h1>
<p>A call with no timeout can hang forever. One hung call holds a thread, a connection and memory. Enough of them and the whole service stops. <strong>Rule: every network call gets a timeout.</strong></p>
<h2 id="Connect-vs-read-timeouts"><a href="#Connect-vs-read-timeouts" class="headerlink" title="Connect vs read timeouts"></a>Connect vs read timeouts</h2>
<ul>
<li><strong>Connect timeout</strong> — how long to wait to open the TCP connection. If it fails, the request was never sent, so a retry is always safe.</li>
<li><strong>Read timeout</strong> — how long to wait for the server's reply after sending. If it fails, the server <strong>may have done the work</strong>.</li>
</ul>

<h2 id="Deadlines"><a href="#Deadlines" class="headerlink" title="Deadlines"></a>Deadlines</h2>
<p>A timeout limits one attempt. A <strong>deadline</strong> limits the whole job. If a user request has 2 seconds in total, and 1.5 s are already spent, the next downstream call should get at most 0.5 s. Pass the remaining time down (as an argument or a header) so inner calls never outlive the outer request.</p>
<blockquote>
<p><strong>Trick:</strong> pick timeouts from real latency data. A common starting point is a bit above the downstream's p99 latency. Too long and a slow dependency blocks you; too short and you fail healthy calls.</p>
</blockquote>

<h1 id="Chapter-3-—-What-is-safe-to-retry"><a href="#Chapter-3-—-What-is-safe-to-retry" class="headerlink" title="Chapter 3 — What is safe to retry"></a>Chapter 3 — What is safe to retry</h1>
<h2 id="Method-rules-from-RFC-9110"><a href="#Method-rules-from-RFC-9110" class="headerlink" title="Method rules from RFC 9110"></a>Method rules from RFC 9110</h2>
<p>RFC 9110 (HTTP Semantics) defines two properties:</p>
<table>
<thead>
<tr>
<th>Method</th>
<th>Safe</th>
<th>Idempotent</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>GET</code>, <code>HEAD</code>, <code>OPTIONS</code>, <code>TRACE</code></td>
<td>yes</td>
<td>yes</td>
</tr>
<tr>
<td><code>PUT</code>, <code>DELETE</code></td>
<td>no</td>
<td>yes</td>
</tr>
<tr>
<td><code>POST</code>, <code>PATCH</code></td>
<td>no</td>
<td><strong>no</strong></td>
</tr>
</tbody>
</table>
<p>(<code>PATCH</code> is defined in RFC 5789, which says it is neither safe nor idempotent.)</p>
<p><strong>Idempotent</strong> means: the intended effect of sending the request once is the same as sending it many times. <code>PUT /users/7 {&quot;name&quot;: &quot;Ada&quot;}</code> twice leaves the same state. <code>POST /orders</code> twice may create two orders.</p>
<p>RFC 9110 is direct about retries: a client <strong>SHOULD NOT</strong> automatically retry a non-idempotent request unless it knows the request is really idempotent, or knows the original was never received. That is exactly what idempotency keys (Chapter 5) give you.</p>
<blockquote>
<p><strong>Watch out:</strong> these are promises your server must keep. A <code>GET /reset-password</code> that sends an email is not safe, whatever the RFC says. A <code>DELETE</code> that returns <code>404</code> the second time is still idempotent — the <strong>state</strong> is the same, even if the reply differs.</p>
</blockquote>

<h1 id="Chapter-4-—-Retries-with-exponential-backoff-and-jitter"><a href="#Chapter-4-—-Retries-with-exponential-backoff-and-jitter" class="headerlink" title="Chapter 4 — Retries with exponential backoff and jitter"></a>Chapter 4 — Retries with exponential backoff and jitter</h1>
<p>If a server is overloaded and every client retries at once, the retries keep it overloaded. Two fixes:</p>
<ol>
<li><strong>Exponential backoff</strong> — wait longer after each failure: <code>base * 2**attempt</code>, up to a <code>cap</code>.</li>
<li><strong>Jitter</strong> — add randomness, so clients spread out instead of retrying in waves.</li>
</ol>
<p>Marc Brooker's AWS Architecture Blog post &quot;Exponential Backoff And Jitter&quot; (2015) compared several variants. Its formulas:</p>
<table>
<thead>
<tr>
<th>Variant</th>
<th>Sleep</th>
</tr>
</thead>
<tbody>
<tr>
<td>No jitter</td>
<td><code>min(cap, base * 2 ** attempt)</code></td>
</tr>
<tr>
<td><strong>Full Jitter</strong></td>
<td><code>random(0, min(cap, base * 2 ** attempt))</code></td>
</tr>
<tr>
<td>Equal Jitter</td>
<td><code>half + random(0, half)</code> where <code>half = base * 2 ** attempt / 2</code></td>
</tr>
<tr>
<td>Decorrelated Jitter</td>
<td><code>min(cap, random(base, sleep * 3))</code></td>
</tr>
</tbody>
</table>
<p>In that simulation, Full Jitter used the least total client work, Decorrelated Jitter was close, and both beat no jitter by a wide margin. Its conclusion: jittered backoff should be the standard approach for remote clients.</p>

<h2 id="Retry-budgets"><a href="#Retry-budgets" class="headerlink" title="Retry budgets"></a>Retry budgets</h2>
<p>Retries multiply. Google's <em>Site Reliability Engineering</em> book (&quot;Addressing Cascading Failures&quot;) gives the example of three layers that each make 4 attempts: one user action becomes 4 × 4 × 4 = <strong>64</strong> attempts on the database — while it is already overloaded. So pick <strong>one</strong> layer to own retries. The chapter &quot;Handling Overload&quot; adds two limits:</p>
<ul>
<li>a <strong>per-request</strong> budget of up to three attempts, then the error goes up to the caller;</li>
<li>a <strong>per-client</strong> budget: retry only while retries are below <strong>10%</strong> of requests.</li>
</ul>
<p>And stop retrying when the deadline is near.</p>
<blockquote>
<p><strong>Common pitfall:</strong> retrying <code>POST</code> with the <code>urllib3</code> recipe from the <code>requests</code> docs, which sets <code>allowed_methods={'POST'}</code>. That is only correct if the endpoint is idempotent or uses idempotency keys.</p>
</blockquote>

<h1 id="Chapter-5-—-Idempotency-keys"><a href="#Chapter-5-—-Idempotency-keys" class="headerlink" title="Chapter 5 — Idempotency keys"></a>Chapter 5 — Idempotency keys</h1>
<p>An idempotency key turns a risky <code>POST</code> into a safe retry. The client makes a unique ID (a UUID v4) for one logical operation and sends it on the first try <strong>and every retry</strong>. The server remembers the key and the result. A repeat gets the saved result instead of running again.</p>
<h2 id="How-Stripe-does-it"><a href="#How-Stripe-does-it" class="headerlink" title="How Stripe does it"></a>How Stripe does it</h2>
<p>Stripe's API docs describe a widely copied design:</p>
<ul>
<li>Header: <code>Idempotency-Key</code>. All <code>POST</code> requests accept it. <code>GET</code> and <code>DELETE</code> do not need it — they are idempotent already.</li>
<li>Keys are up to <strong>255 characters</strong>; Stripe suggests <strong>V4 UUIDs</strong>. Do not put personal data in a key.</li>
<li>Stripe saves the status code and body of the first request that <strong>started executing</strong> — success or failure, even <code>500</code>.</li>
<li>If parameters differ from the original, Stripe returns an error.</li>
<li>Requests that fail validation, or that clash with a request still running, are <strong>not</strong> saved, so you can retry them.</li>
<li>Keys can be removed once they are at least <strong>24 hours</strong> old; a reused key after that is a new request.</li>
</ul>
<h2 id="The-IETF-draft"><a href="#The-IETF-draft" class="headerlink" title="The IETF draft"></a>The IETF draft</h2>
<p>The IETF HTTPAPI working group wrote &quot;The Idempotency-Key HTTP Header Field&quot; (<code>draft-ietf-httpapi-idempotency-key-header</code>). As of September 2026, the latest version is <strong>-07 (October 2025)</strong> and the Datatracker lists it as an <strong>expired</strong> Internet-Draft — not an RFC. It is still a useful reference. It suggests:</p>
<table>
<thead>
<tr>
<th>Situation</th>
<th>Status</th>
</tr>
</thead>
<tbody>
<tr>
<td>Key missing on an endpoint that requires it</td>
<td><code>400 Bad Request</code></td>
</tr>
<tr>
<td>Same key, different request payload</td>
<td><code>422 Unprocessable Content</code></td>
</tr>
<tr>
<td>Same key while the first request is still running</td>
<td><code>409 Conflict</code></td>
</tr>
</tbody>
</table>
<p>It also recommends a UUID or a similar random value, and says the server should publish its key expiry policy.</p>
<h2 id="Server-design"><a href="#Server-design" class="headerlink" title="Server design"></a>Server design</h2>
<ol>
<li>Scope the key to the caller: store <code>client_id + key</code>, so two customers cannot collide.</li>
<li>Store a <strong>fingerprint</strong> (hash of method, path and body) to catch reuse with a different payload.</li>
<li>Mark the key <strong>in progress</strong> before running the handler. A second request with the same key gets <code>409</code>.</li>
<li>Save the final status and body. Replays return the saved response.</li>
<li>Expire keys after a TTL (for example 24 hours).</li>
<li>The &quot;insert if absent&quot; in step 3 must be atomic. In one process a dict is enough. With many servers, use Redis <code>SET key value NX EX 86400</code> or a unique index in a database (see Dev Essentials 13 · Caching for Redis).</li>
</ol>

<h1 id="Chapter-6-—-Rate-limiting"><a href="#Chapter-6-—-Rate-limiting" class="headerlink" title="Chapter 6 — Rate limiting"></a>Chapter 6 — Rate limiting</h1>
<p>A rate limit protects a server from too much traffic — from bugs, abuse, or one noisy customer. Four common algorithms:</p>
<table>
<thead>
<tr>
<th>Algorithm</th>
<th>How it works</th>
<th>Good at</th>
<th>Weak at</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Token bucket</strong></td>
<td>Bucket holds up to <code>capacity</code> tokens, refills at <code>rate</code>/s. Each request takes one</td>
<td>Allows short bursts, smooth long-run limit</td>
<td>Needs care to share across servers</td>
</tr>
<tr>
<td><strong>Leaky bucket</strong></td>
<td>Requests join a queue that drains at a fixed rate</td>
<td>Very smooth output</td>
<td>Bursts wait or are dropped</td>
</tr>
<tr>
<td><strong>Fixed window</strong></td>
<td>Count per clock window (e.g. per minute)</td>
<td>Simplest; one counter</td>
<td>Up to 2× the limit around a window edge</td>
</tr>
<tr>
<td><strong>Sliding window</strong></td>
<td>Count over the last N seconds (log or weighted counters)</td>
<td>Fixes the edge problem</td>
<td>More memory or maths</td>
</tr>
</tbody>
</table>

<h1 id="Chapter-7-—-Circuit-breakers"><a href="#Chapter-7-—-Circuit-breakers" class="headerlink" title="Chapter 7 — Circuit breakers"></a>Chapter 7 — Circuit breakers</h1>
<p>When a dependency is down, each call waits for a timeout before failing. A <strong>circuit breaker</strong> notices repeated failures and fails fast for a while. The pattern was made popular by Michael Nygard's book <em>Release It!</em>; Martin Fowler's &quot;CircuitBreaker&quot; article (2014) is a clear short summary.</p>
<table>
<thead>
<tr>
<th>State</th>
<th>Behaviour</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Closed</strong></td>
<td>Normal. Calls go through. Count failures</td>
</tr>
<tr>
<td><strong>Open</strong></td>
<td>Too many failures. Fail at once without calling. Wait <code>reset_timeout</code></td>
</tr>
<tr>
<td><strong>Half-open</strong></td>
<td>After the wait, let a trial call through. Success → closed. Failure → open again</td>
</tr>
</tbody>
</table>
<p>A breaker and retries work together: retries handle short blips, the breaker stops retries from hammering a service that is clearly down. Exercise 4 builds a small one. Real breakers also add a lock, count failures over a time window, and often use a failure <strong>rate</strong> instead of a count.</p>
<blockquote>
<p><strong>Trick:</strong> when the breaker is open, return something useful if you can — a cached value, a default, or a clear &quot;try again later&quot; message — instead of a stack trace.</p>
</blockquote>

<h1 id="Chapter-8-—-Queues-at-least-once-delivery-and-the-outbox"><a href="#Chapter-8-—-Queues-at-least-once-delivery-and-the-outbox" class="headerlink" title="Chapter 8 — Queues, at-least-once delivery and the outbox"></a>Chapter 8 — Queues, at-least-once delivery and the outbox</h1>
<h2 id="Load-levelling"><a href="#Load-levelling" class="headerlink" title="Load levelling"></a>Load levelling</h2>
<p>If work does not need an answer right now (send an email, resize an image), put it on a queue. The API replies <code>202 Accepted</code> at once; workers take jobs at their own pace. A traffic spike makes the queue longer, not the servers slower. On AWS this is SQS (see AWS Course 05 · Serverless &amp; Events).</p>
<h2 id="At-least-once-means-duplicates"><a href="#At-least-once-means-duplicates" class="headerlink" title="At-least-once means duplicates"></a>At-least-once means duplicates</h2>
<p>SQS standard queues keep copies of each message on several servers. The SQS docs say you may rarely receive a message again, and tell you to <strong>design your application to be idempotent</strong>. Many queues work this way. A worker can also crash after doing the work but before it deletes the message, so the message comes back.</p>
<p>So every consumer must be <strong>idempotent</strong>. The usual method: each message carries a unique ID; the consumer records processed IDs and skips any ID it has seen. Exercise 6 builds this with SQLite.</p>
<blockquote>
<p><strong>Watch out:</strong> the side effect and the &quot;processed&quot; record must be saved together, in one database transaction. If you save the effect, crash, and never save the ID, the redelivered message runs again.</p>
</blockquote>
<h2 id="Dead-letter-queues"><a href="#Dead-letter-queues" class="headerlink" title="Dead-letter queues"></a>Dead-letter queues</h2>
<p>Some messages always fail (bad data, a bug). Without a limit, they loop forever. In SQS, a <strong>redrive policy</strong> sets <code>maxReceiveCount</code>: after that many receives, the message moves to the dead-letter queue. AWS advises setting it high enough to allow real retries, and giving the DLQ a longer retention period than the source queue. Put an alarm on DLQ depth — a message there means a person must look.</p>
<h2 id="The-outbox-pattern"><a href="#The-outbox-pattern" class="headerlink" title="The outbox pattern"></a>The outbox pattern</h2>
<p>A classic bug: save an order to the database, then publish an &quot;order created&quot; event. If the process dies between the two steps, the event is lost. The <strong>outbox pattern</strong> writes the event into an <code>outbox</code> table in the <strong>same transaction</strong> as the order. A separate relay reads the outbox and publishes. The relay may publish twice, so consumers must still be idempotent. MongoDB Course 20 · Outbox Pattern builds this step by step.</p>

<h2 id="Exercise-1-—-Classify-the-failure"><a href="#Exercise-1-—-Classify-the-failure" class="headerlink" title="Exercise 1 — Classify the failure"></a>Exercise 1 — Classify the failure</h2>
<p>For each case, say &quot;retry&quot;, &quot;retry with idempotency key only&quot;, or &quot;do not retry&quot;: (a) <code>GET /users/7</code> → connect timeout; (b) <code>POST /payments</code> → read timeout; (c) <code>PUT /users/7</code> → <code>503</code> with <code>Retry-After: 2</code>; (d) <code>POST /orders</code> → <code>422</code>.</p>
<details>
<summary>Solution</summary>
<p>(a) Retry — the request never reached the server, and <code>GET</code> is safe anyway. (b) Retry <strong>only</strong> with the same idempotency key — the charge may have happened. (c) Retry after at least 2 seconds — <code>PUT</code> is idempotent and <code>503</code> is temporary. (d) Do not retry — the request itself is wrong; the same body will fail again.</p>
</details>
<h2 id="Exercise-2-—-Worst-case-wait"><a href="#Exercise-2-—-Worst-case-wait" class="headerlink" title="Exercise 2 — Worst-case wait"></a>Exercise 2 — Worst-case wait</h2>
<p>With <code>base = 0.2</code>, <code>cap = 5</code> and <code>max_attempts = 5</code>, what is the longest total sleep with full jitter?</p>
<details>
<summary>Solution</summary>
<p>There are 4 sleeps (after attempts 0-3). The upper bounds are <code>min(5, 0.2 * 2**n)</code> for n = 0..3: 0.2 + 0.4 + 0.8 + 1.6 = <strong>3.0 s</strong>. The average is half of that, 1.5 s, because full jitter is uniform from 0.</p>
</details>

<h2 id="Exercise-5-—-Fixed-window-edge"><a href="#Exercise-5-—-Fixed-window-edge" class="headerlink" title="Exercise 5 — Fixed window edge"></a>Exercise 5 — Fixed window edge</h2>
<p>A fixed-window limiter allows 100 requests per minute. How many requests can a client get through in 2 seconds, and how?</p>
<details>
<summary>Solution</summary>
<p>Up to <strong>200</strong>: 100 in the last second of one window (e.g. 12:00:59) and 100 in the first second of the next (12:01:00). A token bucket with <code>capacity = 100</code> or a sliding window avoids this.</p>
</details>

<h1 id="Cheat-sheet"><a href="#Cheat-sheet" class="headerlink" title="Cheat-sheet"></a>Cheat-sheet</h1>
<table>
<thead>
<tr>
<th>Topic</th>
<th>Rule of thumb</th>
</tr>
</thead>
<tbody>
<tr>
<td>Timeouts</td>
<td>Every call. <code>requests</code>: <code>timeout=(3.05, 10)</code>. <code>httpx</code>: <code>httpx.Timeout(10, connect=3)</code></td>
</tr>
<tr>
<td>requests default</td>
<td>No timeout at all — always pass one</td>
</tr>
<tr>
<td>httpx default</td>
<td>5 s</td>
</tr>
<tr>
<td>Safe to retry</td>
<td>Connect errors; idempotent methods (<code>GET</code>, <code>HEAD</code>, <code>OPTIONS</code>, <code>PUT</code>, <code>DELETE</code>)</td>
</tr>
<tr>
<td>Not safe</td>
<td><code>POST</code>/<code>PATCH</code> after a read timeout — unless it has an idempotency key</td>
</tr>
<tr>
<td>Retryable statuses</td>
<td><code>408</code>, <code>429</code>, <code>502</code>, <code>503</code>, <code>504</code> (maybe <code>500</code>)</td>
</tr>
<tr>
<td>Never retry</td>
<td><code>400</code>, <code>401</code>, <code>403</code>, <code>404</code>, <code>409</code>, <code>422</code></td>
</tr>
<tr>
<td>Full jitter</td>
<td><code>sleep = random(0, min(cap, base * 2 ** attempt))</code></td>
</tr>
<tr>
<td>Retry budget</td>
<td>≤ 3 attempts per request; retries &lt; 10% of traffic; retry at one layer only</td>
</tr>
<tr>
<td>Idempotency key</td>
<td>UUID v4 per logical action; same key on every retry</td>
</tr>
<tr>
<td>Server store</td>
<td><code>client + key</code> → fingerprint, status, body; TTL ~24 h; atomic insert</td>
</tr>
<tr>
<td>Draft status codes</td>
<td>Missing key <code>400</code>, different payload <code>422</code>, still running <code>409</code></td>
</tr>
<tr>
<td>Rate limit reply</td>
<td><code>429</code> + <code>Retry-After</code> (seconds or HTTP date)</td>
</tr>
<tr>
<td>Token bucket</td>
<td><code>rate</code> = long-run limit, <code>capacity</code> = burst size</td>
</tr>
<tr>
<td>Circuit breaker</td>
<td>Closed → Open (fail fast) → Half-open (one trial)</td>
</tr>
<tr>
<td>Queues</td>
<td>At-least-once → idempotent consumers; DLQ via <code>maxReceiveCount</code></td>
</tr>
<tr>
<td>Outbox</td>
<td>Write event + data in one transaction; relay publishes later</td>
</tr>
</tbody>
</table>
