Dev Essentials — 14 · API Reliability — Timeouts, Retries with Backoff, Idempotency, Rate Limits and Queues

Created2026-09-04|Updated2026-09-04|Dev Essentials
|Post View:

Every call over a network can be slow, can fail, or can fail in a way where you do not know if it worked. This post is a practical kit for those cases: timeouts on every call, retries that do not make an outage worse, idempotency keys so a retry never charges a card twice, rate limits that protect a server, circuit breakers, and queues. All code is runnable Python. It sits in Part C of the series, after Caching and before Testing.

Series map: 01 Text Encoding → … → 13 Caching → 14 API Reliability (this post) → 15 Testing → … → 24 Desk Health. Part C · Building safely.

Learning Outcome

  • Name the four ways a remote call fails, and why "unknown outcome" is the hard one.
  • Put a connect timeout and a read timeout on every call in requests and httpx.
  • Decide what is safe to retry, using HTTP method rules from RFC 9110 and the status code.
  • Write a retry decorator with exponential backoff and full jitter, and respect Retry-After.
  • Make POST safe to retry with an Idempotency-Key header and a server-side store with a TTL.
  • Build a token-bucket rate limiter that returns 429 Too Many Requests with Retry-After.
  • Explain circuit-breaker states, queue load levelling, dead-letter queues and idempotent consumers.

Chapter 1 — How remote calls fail

A function call inside one process either returns or throws. A call over a network has more outcomes:

Failure What you see Example
Slow The call takes 30 s instead of 30 ms Database is overloaded, a GC pause, a long queue
Down Connection refused, DNS error, connect timeout Service crashed, wrong port, network cut
Partial failure Some calls work, some fail One of five servers is broken; one region is down
Unknown outcome A timeout after the request was sent POST /payments timed out. Was the card charged?

The last one is the hard case. The request may have reached the server and run. Only the reply was lost. If you retry blindly, you may do the action twice. If you do not retry, the action may never happen. Most of this post is about handling this case safely.

Terminology

Term Meaning
Timeout The longest you wait for one step (connect, read) before giving up
Deadline The total time budget for the whole operation, including retries
Backoff Waiting longer before each new retry
Jitter Adding randomness to the wait, so clients do not retry at the same moment
Safe method A method the client does not expect to change anything (GET, HEAD)
Idempotent Doing it twice has the same intended effect as doing it once
Idempotency key A unique ID the client sends so the server can spot a repeat
Rate limit A cap on how many requests a client may send per time window
Circuit breaker A switch that stops calls to a failing service for a while
At-least-once A message is delivered one or more times — duplicates are possible
Dead-letter queue (DLQ) A side queue for messages that failed too many times

Chapter 2 — Timeouts on every network call

A call with no timeout can hang forever. One hung call holds a thread, a connection and memory. Enough of them and the whole service stops. Rule: every network call gets a timeout.

Connect vs read timeouts

  • Connect timeout — how long to wait to open the TCP connection. If it fails, the request was never sent, so a retry is always safe.
  • Read timeout — how long to wait for the server's reply after sending. If it fails, the server may have done the work.

requests

The requests library has no default timeout. Its docs say requests do not time out unless you set one.

Watch out: the requests read timeout is the time between bytes from the server, not the total download time. A server that sends one byte every 9 seconds never trips a 10-second read timeout. Neither timeout is a wall-clock limit. For a hard total limit, use a deadline (below).

The requests docs suggest a connect timeout slightly larger than a multiple of 3 (for example 3.05), because 3 seconds is the classic TCP retransmission window.

httpx

httpx has a default timeout of 5 seconds and four separate settings: connect, read, write and pool (waiting for a free connection). Each raises its own exception: ConnectTimeout, ReadTimeout, WriteTimeout, PoolTimeout.

From the shell

In Windows PowerShell 5.1, curl is an alias for Invoke-WebRequest. Type curl.exe to get real curl.

Deadlines

A timeout limits one attempt. A deadline limits the whole job. If a user request has 2 seconds in total, and 1.5 s are already spent, the next downstream call should get at most 0.5 s. Pass the remaining time down (as an argument or a header) so inner calls never outlive the outer request.

Trick: pick timeouts from real latency data. A common starting point is a bit above the downstream's p99 latency. Too long and a slow dependency blocks you; too short and you fail healthy calls.

Chapter 3 — What is safe to retry

Method rules from RFC 9110

RFC 9110 (HTTP Semantics) defines two properties:

Method Safe Idempotent
GET, HEAD, OPTIONS, TRACE yes yes
PUT, DELETE no yes
POST, PATCH no no

(PATCH is defined in RFC 5789, which says it is neither safe nor idempotent.)

Idempotent means: the intended effect of sending the request once is the same as sending it many times. PUT /users/7 {"name": "Ada"} twice leaves the same state. POST /orders twice may create two orders.

RFC 9110 is direct about retries: a client SHOULD NOT automatically retry a non-idempotent request unless it knows the request is really idempotent, or knows the original was never received. That is exactly what idempotency keys (Chapter 5) give you.

Watch out: these are promises your server must keep. A GET /reset-password that sends an email is not safe, whatever the RFC says. A DELETE that returns 404 the second time is still idempotent — the state is the same, even if the reply differs.

Status codes (common practice)

Response Retry? Why
Connect error / connect timeout Yes Request never reached the server
Read timeout, connection reset Only if idempotent or has an idempotency key Server may have run it
408, 429, 502, 503, 504 Yes, with backoff Temporary. For 429/503 read Retry-After
500 Maybe, a few times, idempotent only Could be a bug that will fail again
400, 401, 403, 404, 409, 422 No Retrying the same request gives the same error

The popular urllib3 Retry class (requests uses urllib3 under the hood) follows the method rule by default: its DEFAULT_ALLOWED_METHODS are DELETE, GET, HEAD, OPTIONS, PUT, TRACE — no POST. It also respects Retry-After by default for status codes 413, 429 and 503.

Chapter 4 — Retries with exponential backoff and jitter

If a server is overloaded and every client retries at once, the retries keep it overloaded. Two fixes:

  1. Exponential backoff — wait longer after each failure: base * 2**attempt, up to a cap.
  2. Jitter — add randomness, so clients spread out instead of retrying in waves.

Marc Brooker's AWS Architecture Blog post "Exponential Backoff And Jitter" (2015) compared several variants. Its formulas:

Variant Sleep
No jitter min(cap, base * 2 ** attempt)
Full Jitter random(0, min(cap, base * 2 ** attempt))
Equal Jitter half + random(0, half) where half = base * 2 ** attempt / 2
Decorrelated Jitter min(cap, random(base, sleep * 3))

In that simulation, Full Jitter used the least total client work, Decorrelated Jitter was close, and both beat no jitter by a wide margin. Its conclusion: jittered backoff should be the standard approach for remote clients.

Retry budgets

Retries multiply. Google's Site Reliability Engineering book ("Addressing Cascading Failures") gives the example of three layers that each make 4 attempts: one user action becomes 4 × 4 × 4 = 64 attempts on the database — while it is already overloaded. So pick one layer to own retries. The chapter "Handling Overload" adds two limits:

  • a per-request budget of up to three attempts, then the error goes up to the caller;
  • a per-client budget: retry only while retries are below 10% of requests.

And stop retrying when the deadline is near.

Common pitfall: retrying POST with the urllib3 recipe from the requests docs, which sets allowed_methods={'POST'}. That is only correct if the endpoint is idempotent or uses idempotency keys.

Chapter 5 — Idempotency keys

An idempotency key turns a risky POST into a safe retry. The client makes a unique ID (a UUID v4) for one logical operation and sends it on the first try and every retry. The server remembers the key and the result. A repeat gets the saved result instead of running again.

How Stripe does it

Stripe's API docs describe a widely copied design:

  • Header: Idempotency-Key. All POST requests accept it. GET and DELETE do not need it — they are idempotent already.
  • Keys are up to 255 characters; Stripe suggests V4 UUIDs. Do not put personal data in a key.
  • Stripe saves the status code and body of the first request that started executing — success or failure, even 500.
  • If parameters differ from the original, Stripe returns an error.
  • Requests that fail validation, or that clash with a request still running, are not saved, so you can retry them.
  • Keys can be removed once they are at least 24 hours old; a reused key after that is a new request.

The IETF draft

The IETF HTTPAPI working group wrote "The Idempotency-Key HTTP Header Field" (draft-ietf-httpapi-idempotency-key-header). As of September 2026, the latest version is -07 (October 2025) and the Datatracker lists it as an expired Internet-Draft — not an RFC. It is still a useful reference. It suggests:

Situation Status
Key missing on an endpoint that requires it 400 Bad Request
Same key, different request payload 422 Unprocessable Content
Same key while the first request is still running 409 Conflict

It also recommends a UUID or a similar random value, and says the server should publish its key expiry policy.

Server design

  1. Scope the key to the caller: store client_id + key, so two customers cannot collide.
  2. Store a fingerprint (hash of method, path and body) to catch reuse with a different payload.
  3. Mark the key in progress before running the handler. A second request with the same key gets 409.
  4. Save the final status and body. Replays return the saved response.
  5. Expire keys after a TTL (for example 24 hours).
  6. The "insert if absent" in step 3 must be atomic. In one process a dict is enough. With many servers, use Redis SET key value NX EX 86400 or a unique index in a database (see Dev Essentials 13 · Caching for Redis).

Chapter 6 — Rate limiting

A rate limit protects a server from too much traffic — from bugs, abuse, or one noisy customer. Four common algorithms:

Algorithm How it works Good at Weak at
Token bucket Bucket holds up to capacity tokens, refills at rate/s. Each request takes one Allows short bursts, smooth long-run limit Needs care to share across servers
Leaky bucket Requests join a queue that drains at a fixed rate Very smooth output Bursts wait or are dropped
Fixed window Count per clock window (e.g. per minute) Simplest; one counter Up to 2× the limit around a window edge
Sliding window Count over the last N seconds (log or weighted counters) Fixes the edge problem More memory or maths

A token bucket

Requests 0-4 pass (the burst), 5-7 are rejected with about 0.5 s to wait, and after one second a request passes again. Use time.monotonic(), not time.time() — the wall clock can jump.

429 and Retry-After

429 Too Many Requests is defined in RFC 6585. The response MAY include Retry-After. RFC 9110 defines Retry-After as either an HTTP date or a number of seconds.

Add any route and call it five times quickly with TestClient as alice: you get [200, 200, 200, 429, 429] with Retry-After: 1, while bob still gets 200 — each key has its own bucket.

The RateLimit header fields (draft)

Many APIs send their own X-RateLimit-* headers. The IETF HTTPAPI working group is standardising two fields in draft-ietf-httpapi-ratelimit-headers. The latest version is -11 (May 2026), still an active draft, so names may change:

q is the quota, w the window in seconds, r the remaining quota, t the seconds until it resets. The draft says that if Retry-After is also present, Retry-After takes precedence.

Chapter 7 — Circuit breakers

When a dependency is down, each call waits for a timeout before failing. A circuit breaker notices repeated failures and fails fast for a while. The pattern was made popular by Michael Nygard's book Release It!; Martin Fowler's "CircuitBreaker" article (2014) is a clear short summary.

State Behaviour
Closed Normal. Calls go through. Count failures
Open Too many failures. Fail at once without calling. Wait reset_timeout
Half-open After the wait, let a trial call through. Success → closed. Failure → open again

A breaker and retries work together: retries handle short blips, the breaker stops retries from hammering a service that is clearly down. Exercise 4 builds a small one. Real breakers also add a lock, count failures over a time window, and often use a failure rate instead of a count.

Trick: when the breaker is open, return something useful if you can — a cached value, a default, or a clear "try again later" message — instead of a stack trace.

Chapter 8 — Queues, at-least-once delivery and the outbox

Load levelling

If work does not need an answer right now (send an email, resize an image), put it on a queue. The API replies 202 Accepted at once; workers take jobs at their own pace. A traffic spike makes the queue longer, not the servers slower. On AWS this is SQS (see AWS Course 05 · Serverless & Events).

At-least-once means duplicates

SQS standard queues keep copies of each message on several servers. The SQS docs say you may rarely receive a message again, and tell you to design your application to be idempotent. Many queues work this way. A worker can also crash after doing the work but before it deletes the message, so the message comes back.

So every consumer must be idempotent. The usual method: each message carries a unique ID; the consumer records processed IDs and skips any ID it has seen. Exercise 6 builds this with SQLite.

Watch out: the side effect and the "processed" record must be saved together, in one database transaction. If you save the effect, crash, and never save the ID, the redelivered message runs again.

Dead-letter queues

Some messages always fail (bad data, a bug). Without a limit, they loop forever. In SQS, a redrive policy sets maxReceiveCount: after that many receives, the message moves to the dead-letter queue. AWS advises setting it high enough to allow real retries, and giving the DLQ a longer retention period than the source queue. Put an alarm on DLQ depth — a message there means a person must look.

The outbox pattern

A classic bug: save an order to the database, then publish an "order created" event. If the process dies between the two steps, the event is lost. The outbox pattern writes the event into an outbox table in the same transaction as the order. A separate relay reads the outbox and publishes. The relay may publish twice, so consumers must still be idempotent. MongoDB Course 20 · Outbox Pattern builds this step by step.

Practice Exercises

Exercise 1 — Classify the failure

For each case, say "retry", "retry with idempotency key only", or "do not retry": (a) GET /users/7 → connect timeout; (b) POST /payments → read timeout; (c) PUT /users/7 → 503 with Retry-After: 2; (d) POST /orders → 422.

Solution

(a) Retry — the request never reached the server, and GET is safe anyway. (b) Retry only with the same idempotency key — the charge may have happened. (c) Retry after at least 2 seconds — PUT is idempotent and 503 is temporary. (d) Do not retry — the request itself is wrong; the same body will fail again.

Exercise 2 — Worst-case wait

With base = 0.2, cap = 5 and max_attempts = 5, what is the longest total sleep with full jitter?

Solution

There are 4 sleeps (after attempts 0-3). The upper bounds are min(5, 0.2 * 2**n) for n = 0..3: 0.2 + 0.4 + 0.8 + 1.6 = 3.0 s. The average is half of that, 1.5 s, because full jitter is uniform from 0.

Cheat-sheet

Topic Rule of thumb
Timeouts Every call. requests: timeout=(3.05, 10). httpx: httpx.Timeout(10, connect=3)
requests default No timeout at all — always pass one
httpx default 5 s
Safe to retry Connect errors; idempotent methods (GET, HEAD, OPTIONS, PUT, DELETE)
Not safe POST/PATCH after a read timeout — unless it has an idempotency key
Retryable statuses 408, 429, 502, 503, 504 (maybe 500)
Never retry 400, 401, 403, 404, 409, 422
Full jitter sleep = random(0, min(cap, base * 2 ** attempt))
Retry budget ≤ 3 attempts per request; retries < 10% of traffic; retry at one layer only
Idempotency key UUID v4 per logical action; same key on every retry
Server store client + key → fingerprint, status, body; TTL ~24 h; atomic insert
Draft status codes Missing key 400, different payload 422, still running 409
Rate limit reply 429 + Retry-After (seconds or HTTP date)
Token bucket rate = long-run limit, capacity = burst size
Circuit breaker Closed → Open (fail fast) → Half-open (one trial)
Queues At-least-once → idempotent consumers; DLQ via maxReceiveCount
Outbox Write event + data in one transaction; relay publishes later
