Vue Deep Dive — 01 · Composition API at Scale

Created2026-09-11|Updated2026-09-11|Programming > Web
|Post View:

The Composition API is easy to start with and easy to misuse at scale. In a codebase with two hundred components and forty composables, the questions change: which inputs should a composable accept, who stops its watchers, how does a deeply nested component get a typed service without prop drilling, what exactly does defineProps compile to, and how do you type a generic table component so that its slot props know the row type. This post answers those questions with the reactivity model from Post 00 as the foundation. It covers composable design (refs and getters as inputs, toValue, cleanup, shared state), typed provide/inject, every <script setup> macro including reactive props destructure and defineModel, generic components, useTemplateRef, and async components with Suspense and lazy hydration. Examples target Vue 3.5; compiled output shown in this post was produced by @vue/compiler-sfc 3.5.

Series map: 00 Reactivity Internals → 01 Composition API at Scale (this post) → 02 Compiler, Virtual DOM & Vapor Mode → 03 Ecosystem & Production (Pinia, Router, Nuxt). Future: see the extensions table in 03.

Learning Outcome

  • Write composables that accept refs, getters or plain values through MaybeRefOrGetter and toValue(), and explain why the read must happen inside an effect.
  • Decide what a composable returns (refs, readonly refs, functions) so that callers can destructure it safely.
  • Attach cleanup with onScopeDispose and build a shared, reference-counted composable with a detached effectScope.
  • Type provide/inject with InjectionKey, expose read-only state plus mutation functions, and fail loudly on a missing provider.
  • Explain what each <script setup> macro compiles to: defineProps (with destructure), defineEmits, defineModel, defineSlots, defineExpose, defineOptions.
  • Build a generic component with the generic attribute and typed slots.
  • Use useTemplateRef for element and component refs.
  • Configure defineAsyncComponent, Suspense and the 3.5 lazy hydration strategies, and know which parts are still experimental.

Chapter 1 — What a composable is

Terminology

  • Composable — a function that uses Composition API features to encapsulate stateful logic. By convention named useX. A pure helper (formatPrice) is not a composable.
  • Setup context — the synchronous window in which Vue knows the "current instance": setup() or <script setup>. Lifecycle hooks, inject() and automatic effect collection depend on it.
  • MaybeRef<T> — T | Ref<T> | ShallowRef<T> | WritableComputedRef<T>.
  • MaybeRefOrGetter<T> — MaybeRef<T> | ComputedRef<T> | (() => T). The type for "any reactive or plain input".
  • toValue(x) (3.3+) — normalises a MaybeRefOrGetter: calls a getter, unwraps a ref, returns anything else as-is.
  • InjectionKey<T> — a typed Symbol used as a provide/inject key.
  • Compiler macro — a function like defineProps that exists only at compile time inside <script setup>. It needs no import and cannot be called at run time.

The contract

A composable called inside setup gets three things for free:

  1. Every computed, watch and watchEffect it creates is collected by the component's effect scope and stopped on unmount (Post 00, Chapter 7).
  2. Lifecycle hooks it registers (onMounted, onUnmounted) attach to the calling component.
  3. inject() resolves against the calling component's ancestors.

All three depend on the current instance, which Vue sets while setup runs synchronously. That gives the first rule: call composables synchronously at the top of setup, not in event handlers, setTimeout callbacks or after an arbitrary await.

<script setup> softens the await part. The compiler wraps each top-level await so the instance is restored afterwards. This source:

The top-level await also turns the component into an async dependency that needs a <Suspense> ancestor (Chapter 8).

Return refs, not a reactive object

Returning reactive({ count, double }) would make every caller that destructures lose reactivity (Post 00, Chapter 8). If a caller wants the object form, it can wrap the result itself: const counter = reactive(useCounter()) unwraps the refs.

Trick: return readonly(ref) for state the composable owns and a function for each allowed mutation. Callers cannot bypass your invariants, and a code search for inc( finds every writer.

  • onWatcherCleanup aborts the previous request when url changes and when the component unmounts, so a slow old response can never overwrite a newer one.
  • shallowRef for data: API responses are replaced, not mutated, and a deep proxy over a large JSON tree is wasted work. Nuxt 4 made the same choice for useFetch (Post 03).

Options objects

For more than two parameters, take an options object and make only the fields that may change at run time MaybeRefOrGetter (interval?: MaybeRefOrGetter<number>), keeping set-once flags plain (immediate?: boolean).

Common pitfall: usePoll({ interval: props.ms }) passes a snapshot of the prop. Pass { interval: () => props.ms }.

Chapter 3 — Cleanup, ownership and shared state

onScopeDispose over onUnmounted

onScopeDispose runs when the component unmounts and when a standalone effectScope stops, so the composable also works in a store, a test, or another composable's scope. The getCurrentScope() guard avoids a development warning when the function is called outside any scope; returning stop gives such callers a way to clean up by hand.

Watch out: window does not exist during SSR. A composable that touches browser APIs at call time crashes the server render. Do browser work in onMounted (which never runs on the server) or guard with typeof window !== 'undefined'.

A shared composable with reference counting

Some state should exist once for all components that use it: one resize listener, one WebSocket, one media-query watcher. A detached scope owns it, and reference counting disposes it when the last user unmounts:

Without effectScope(true), the listener and any watchers would be collected by the first component that called useWindowWidth, and would stop when that component unmounted even though others still use them. VueUse ships a production version of this helper under the same name.

Global state: module scope vs provide

A ref at module scope is fine in a client-only SPA, but in SSR it is shared by every request on the server (Post 00, Chapter 8). Per-user state goes through app.provide, Pinia or Nuxt's useState; module scope holds only constants and truly global caches.

InjectionKey<T>

Defaults and factories

inject(ThemeKey, 'light') gives a plain default. inject(LoggerKey, () => new ConsoleLogger(), true) treats the default as a factory (third argument), so the expensive object is built only when no provider exists; without true, a function default is returned as-is, not called.

Where injection works

  • Inside setup / <script setup> of a descendant, including after a <script setup> top-level await (Chapter 1).
  • app.provide(key, value) makes a value available to every component in the app, and to app.runWithContext(fn) (3.3+), which router guards and plugins use to call inject() outside components.
  • hasInjectionContext() (3.3+) returns whether inject() can be called right now without a warning. Libraries use it to support both component and non-component callers; useRoute() in Vue Router is the example the Vue type definitions give.

Watch out: a component can inject from ancestors only. A sibling or a component in another subtree cannot see the value, and Teleport does not change this: injection follows the component tree, not the DOM.

Chapter 5 — The <script setup> macros

defineProps and reactive destructure (3.5)

Since 3.5, destructuring defineProps() is stable and enabled by default, with native default values:

So count is not a local variable at run time; it is __props.count, read inside the computed getter and tracked. Two consequences:

  • Passing the name itself to watch(count, …) would pass a number. The compiler rejects it: "count" is a destructured prop and should not be passed directly to watch(). Pass a getter () => count instead.
  • Passing it to a composable passes a snapshot. Use useThing(() => count); with MaybeRefOrGetter inputs (Chapter 2) this is free.

withDefaults(defineProps<…>(), { … }) still works and remains the way to declare defaults without destructuring.

defineEmits

The 3.3+ named-tuple syntax is the most readable typed form:

Watch out: a default on defineModel is used when the parent does not bind v-model. The child then works as local state while the parent's own value (if it has one but did not bind it) stays different. The Vue docs warn about this desynchronisation. Give a default only to models that are genuinely optional.

defineSlots, defineExpose, defineOptions

defineSlots (3.3+) is type-only: it types useSlots() and the slot props that parents receive. defineExpose matters because <script setup> components are closed by default: a parent holding a template ref to the child sees only what was exposed. defineOptions (3.3+) is spread into the component definition; in the output it appears as ...{ inheritAttrs: false }.

Chapter 6 — Generic components and TypeScript

The generic attribute (3.3+)

A table, a select or a virtual list should know the row type from its items prop. The generic attribute on <script setup> declares type parameters, with constraints and defaults written as in TypeScript:

At run time there are no types: the compiled props option is { items: { type: Array, required: true }, selected: { type: null, required: false } }. All the checking happens in vue-tsc and the editor (Vue - Official extension), which is why CI should run vue-tsc --noEmit; the Vite build does not type-check.

Typing refs to generic or exposed components

InstanceType<typeof Comp> does not work for generic components, because their default export is a function type. The vue-component-type-helpers package (from the Vue language tools) provides ComponentExposed<typeof Comp> for exactly this.

Trick: type-based defineProps generates runtime options only from types it can resolve; a union of object shapes becomes type: Object or null, so runtime validation is weaker than the type. Keep prop interfaces local or in a .ts file imported by relative path — the SFC compiler resolves imported types itself (3.3+), but complex conditional or mapped types from third-party packages can fail to resolve and stop the build.

Chapter 7 — Template refs with useTemplateRef (3.5)

Why it replaced the old pattern of a ref(null) whose variable name matched the ref attribute:

  • The ref name is a string, so it can be dynamic (:ref="row-${id}") and can come from a composable that does not own the template.
  • A composable can accept the key: useElementSize(useTemplateRef('panel')).
  • The returned ref is read-only, which prevents accidental writes.

Timing: template refs are set in the post-flush phase (Post 00, Chapter 6). They are null before mount and during a pre watcher that runs before the first render; read them in onMounted or a flush: 'post' watcher. A ref on a v-for element holds an array, and the docs note that its order is not guaranteed to match the source array.

A ref on a component gives the instance's exposed surface only — whatever defineExpose listed.

Chapter 8 — Async components, Suspense and lazy hydration

defineAsyncComponent

The loader becomes a separate chunk. The 200 ms delay exists so fast loads do not flash a skeleton. If the async component is inside a <Suspense>, it is controlled by that boundary by default (suspensible: true) and its own loading, error, delay and timeout options are ignored.

Suspense (still experimental)

<Suspense> waits for async dependencies in its subtree — components with an async setup() (including any <script setup> with a top-level await) and suspensible async components — and shows its #fallback slot until all resolve:

  • On the first render, the fallback shows until everything resolves. On later changes, Suspense keeps showing the previous content until the new branch resolves, and only switches to the fallback after timeout ms.
  • Events: pending, resolve, fallback.
  • Errors in async setup are not handled by Suspense. Catch them with onErrorCaptured in a parent or with the app-level errorHandler.
  • Nested <Suspense> boundaries need the suspensible prop (3.3+) on the inner one to join the parent's resolution.

The Vue docs still mark <Suspense> as experimental, with an API that may change. Nuxt relies on it for every page, which is a practical sign that it is dependable, but in a plain Vue app keep its use to route-level boundaries.

Lazy hydration (3.5)

In an SSR app, every component normally hydrates as soon as the client bundle runs. 3.5 lets an async component delay its hydration:

Practice Exercises

Exercise 1 — Fix the composable signature

function useTitle(title: string) sets document.title once. Rewrite it so that useTitle('Home'), useTitle(titleRef) and useTitle(() => ${n.value} new) all work and stay in sync.

Solution

toValue reads inside the effect, so a ref or getter is tracked; a plain string is simply read once. In SSR, move the body into onMounted or use Unhead / Nuxt's useHead.

Exercise 2 — Who stops the watcher?

A composable is called from a Pinia setup store instead of a component. Its watch never stops, and its onUnmounted logs a warning. Explain both, and fix the composable.

Solution

There is no component instance, so onUnmounted has nothing to attach to (warning). The store's setup runs inside Pinia's own effect scope, so the watch is collected by that scope and lives as long as the store — usually the app. Replace onUnmounted with onScopeDispose, which attaches to whichever scope is active: the component, the store, or a test's effectScope.
