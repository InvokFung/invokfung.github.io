11:Te3bc,<p>Shipping a Next.js app is easy; running one for years is a different skill. Between March 2025 and August 2026 the framework and its React Server Components layer produced an authorisation bypass that ignored middleware entirely, a CVSS 10.0 unauthenticated remote code execution in the RSC protocol, a run of follow-up denial-of-service and source-exposure bugs, and critical fixes in the image optimiser's native dependencies. Teams that had layered defences, a patch process, and observability shrugged; teams whose only auth check lived in middleware, or who ran a year-old minor, did not. This post covers authentication patterns that survive a bypass, the incidents themselves and what each teaches, <code>next/image</code> and <code>next/font</code> in production, bundle analysis, self-hosting with <code>output: 'standalone'</code> and Docker versus a managed platform, <code>instrumentation.ts</code> with OpenTelemetry, and environment-variable leaks. It ends with the planned extensions of this series.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Design authentication in layers (Proxy, Data Access Layer, per-page and per-action checks) so that no single bypass exposes data.</li>
<li>Explain CVE-2025-29927 and CVE-2025-55182 (React2Shell): mechanism, affected versions, fixed versions, and the lessons.</li>
<li>Run a patch process that matches the Next.js LTS policy.</li>
<li>Configure <code>next/image</code> safely for Next.js 16, and use <code>next/font</code> without layout shift or third-party requests.</li>
<li>Find client-bundle bloat with the bundle analyzer and fix it at the server/client boundary.</li>
<li>Self-host with <code>output: 'standalone'</code> in Docker, including shared caching, the Server Actions key, version skew and graceful shutdown.</li>
<li>Instrument the server with <code>instrumentation.ts</code>, <code>onRequestError</code> and OpenTelemetry.</li>
<li>Prevent secret leaks through <code>NEXT_PUBLIC_</code>, <code>next.config</code> <code>env</code>, props and action return values.</li>

<h1 id="Chapter-1-—-Authentication-in-layers"><a href="#Chapter-1-—-Authentication-in-layers" class="headerlink" title="Chapter 1 — Authentication in layers"></a>Chapter 1 — Authentication in layers</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Authentication</strong> — who is the caller? (a valid session)</li>
<li><strong>Authorisation</strong> — may this caller do this to this resource? (ownership, role)</li>
<li><strong>Optimistic check</strong> — a cheap check on the presence of a session cookie, without a database or full verification; good for redirects, never enough for data.</li>
<li><strong>Secure check</strong> — full session verification plus an authorisation decision, next to the data access.</li>
<li><strong>IDOR</strong> — Insecure Direct Object Reference: the caller changes an id and gets someone else's record because only authentication was checked.</li>
</ul>

<p>Every DAL function starts with <code>await verifySession()</code> and scopes its query to the caller (<code>where: { id, ownerId: userId }</code>). A page, an action and a Route Handler then get the same guarantees without remembering to write them.</p>
<h2 id="Sessions"><a href="#Sessions" class="headerlink" title="Sessions"></a>Sessions</h2>
<ul>
<li><strong>Stateless</strong> (a signed and encrypted token in a cookie): no session store, but revocation before expiry needs extra machinery (short lifetimes, a deny-list).</li>
<li><strong>Database sessions</strong> (an opaque id in the cookie, state server-side): revocable instantly, one lookup per request (cheap with <code>React.cache</code>).</li>
<li>Either way the cookie is <code>HttpOnly</code>, <code>Secure</code>, <code>SameSite=Lax</code> (or <code>Strict</code>), with a sensible <code>Max-Age</code>, and is set or deleted only in Server Actions or Route Handlers: setting cookies during render is not allowed.</li>
</ul>
<p>Prefer a maintained auth library over hand-rolled crypto; the layering above applies whichever library you choose.</p>
<h2 id="Auth-with-Cache-Components"><a href="#Auth-with-Cache-Components" class="headerlink" title="Auth with Cache Components"></a>Auth with Cache Components</h2>
<p>Under <code>cacheComponents</code> (Post 02), per-user data must never sit in a <code>'use cache'</code> scope keyed only by public inputs. Read the session outside the cached scope and pass the user id in as an argument, so it becomes part of the key; or keep per-user parts as uncached dynamic holes inside Suspense. Since 15.1, <code>forbidden()</code> and <code>unauthorized()</code> (behind <code>experimental.authInterrupts</code>, still experimental as of 16.3) render <code>forbidden.tsx</code> / <code>unauthorized.tsx</code> with 403 / 401 status, as long as they run before streaming starts.</p>
<blockquote>
<p><strong>Common pitfall:</strong> &quot;the dashboard layout checks the session, so all dashboard pages are safe.&quot; The layout's check runs on the first load; on soft navigation between child pages the layout is not re-rendered, and the child pages' actions are separate endpoints. Check in the DAL.</p>
</blockquote>

<h1 id="Chapter-2-—-The-incidents-and-what-they-teach"><a href="#Chapter-2-—-The-incidents-and-what-they-teach" class="headerlink" title="Chapter 2 — The incidents, and what they teach"></a>Chapter 2 — The incidents, and what they teach</h1>
<h2 id="CVE-2025-29927-middleware-bypass-March-2025"><a href="#CVE-2025-29927-middleware-bypass-March-2025" class="headerlink" title="CVE-2025-29927: middleware bypass (March 2025)"></a>CVE-2025-29927: middleware bypass (March 2025)</h2>
<p>Next.js used an internal header, <code>x-middleware-subrequest</code>, to stop middleware from recursing into itself. The server trusted that header on incoming requests, so an attacker who sent it with the right value made the server <strong>skip middleware entirely</strong>: authentication redirects, authorisation checks, security headers, everything.</p>
<ul>
<li><strong>Severity:</strong> critical, CVSS 9.1.</li>
<li><strong>Affected:</strong> self-hosted apps using <code>next start</code> (including <code>output: 'standalone'</code>). Vercel, Netlify, Cloudflare Workers and static exports were not affected (Vercel's routing is decoupled from the Next.js server; exports have no server).</li>
<li><strong>Fixed in:</strong> 15.2.3, 14.2.25, and backports 13.5.9 and 12.3.5.</li>
<li><strong>Timeline:</strong> reported late February 2025, patched March 17–18, disclosed March 21.</li>
<li><strong>Workaround:</strong> strip <code>x-middleware-subrequest</code> at the load balancer or reverse proxy before it reaches Next.js.</li>
</ul>
<p><strong>Lesson:</strong> an app whose only authorisation lived in middleware had none. Apps that re-checked in the DAL lost a redirect, not their data.</p>
<h2 id="CVE-2025-55182-React2Shell-RSC-remote-code-execution-December-2025"><a href="#CVE-2025-55182-React2Shell-RSC-remote-code-execution-December-2025" class="headerlink" title="CVE-2025-55182 &quot;React2Shell&quot;: RSC remote code execution (December 2025)"></a>CVE-2025-55182 &quot;React2Shell&quot;: RSC remote code execution (December 2025)</h2>
<p>A deserialisation flaw in how React decodes payloads sent to <strong>Server Function endpoints</strong> let a crafted HTTP request execute code on the server, without authentication.</p>
<ul>
<li><strong>Severity:</strong> critical, <strong>CVSS 10.0</strong>. Reported November 29, disclosed December 3, 2025 (reporter: Lachlan Davidson).</li>
<li><strong>Affected React packages:</strong> <code>react-server-dom-webpack</code>, <code>react-server-dom-parcel</code>, <code>react-server-dom-turbopack</code> at 19.0, 19.1.0, 19.1.1 and 19.2.0; fixed in 19.0.1, 19.1.2 and 19.2.1. Frameworks affected included Next.js, React Router, Waku, <code>@parcel/rsc</code>, <code>@vitejs/plugin-rsc</code> and rwsdk.</li>
<li><strong>Not only apps with actions:</strong> React's advisory states that an app <strong>without</strong> any Server Functions of its own may still be vulnerable if it supports React Server Components.</li>
<li><strong>Next.js impact</strong> (tracked as CVE-2025-66478): App Router apps on <strong>15.x, 16.x, and 14.3.0-canary.77 or later canaries</strong>. Next.js 13.x, <strong>14.x stable</strong>, the Pages Router and the Edge runtime were not affected.</li>
<li><strong>Next.js fixed versions:</strong> 15.0.5, 15.1.9, 15.2.6, 15.3.6, 15.4.8, 15.5.7, 16.0.7. No workaround; upgrade was required. <code>npx fix-react2shell-next</code> performed the version bumps.</li>
<li><strong>Exploitation:</strong> exploited in the wild within days; AWS reported China-nexus threat groups using it.</li>
<li><strong>Secrets:</strong> Vercel advised that any app online and unpatched as of December 4, 2025, 1:00 PM PT should <strong>rotate its secrets</strong>, most critical first.</li>
</ul>

<h2 id="nextimage"><a href="#nextimage" class="headerlink" title="next/image"></a><code>next/image</code></h2>
<p><code>&lt;Image&gt;</code> wraps <code>&lt;img&gt;</code> with: lazy loading by default, a <code>srcset</code> generated from width lists, format negotiation through the <code>Accept</code> header (<code>formats</code>, default <code>['image/webp']</code>; add <code>'image/avif'</code> to prefer AVIF), and required <code>width</code>/<code>height</code> (or <code>fill</code>) so the browser reserves space and avoids layout shift.</p>

<p>Production notes:</p>

<h2 id="nextfont"><a href="#nextfont" class="headerlink" title="next/font"></a><code>next/font</code></h2>
<p><code>next/font</code> downloads Google Font files (or uses your local files) <strong>at build time</strong> and serves them with your static assets, so the browser never contacts Google. <h1 id="Chapter-5-—-Self-hosting-vs-a-managed-platform"><a href="#Chapter-5-—-Self-hosting-vs-a-managed-platform" class="headerlink" title="Chapter 5 — Self-hosting vs a managed platform"></a>Chapter 5 — Self-hosting vs a managed platform</h1>
<h2 id="Standalone-output"><a href="#Standalone-output" class="headerlink" title="Standalone output"></a>Standalone output</h2>
<p><code>output: 'standalone'</code> uses output file tracing (<code>@vercel/nft</code>) to copy only the files each route needs, including the needed parts of <code>node_modules</code>, into <code>.next/standalone</code>, with a minimal <code>server.js</code> that replaces <code>next start</code>. It does <strong>not</strong> copy <code>public/</code> or <code>.next/static</code>, which are expected to go to a CDN; copy them in if the server should serve them. <code>PORT</code> and <code>HOSTNAME</code> set the listen address. In a monorepo, set <code>outputFileTracingRoot</code> so files outside the app folder are traced.</p>

<h1 id="Chapter-6-—-instrumentationts-and-OpenTelemetry"><a href="#Chapter-6-—-instrumentationts-and-OpenTelemetry" class="headerlink" title="Chapter 6 — instrumentation.ts and OpenTelemetry"></a>Chapter 6 — <code>instrumentation.ts</code> and OpenTelemetry</h1>
<p><code>instrumentation.ts</code> in the project root (or in <code>src/</code>) is stable since Next.js 15. Its <code>register()</code> runs once when a new server instance starts, before your code. Its <code>onRequestError()</code> (added in 15) receives every error thrown on the server with context: which router, and whether it came from a Server Component, Server Action, Route Handler or Proxy.</p>

<p>Next.js is instrumented out of the box. The spans it emits by default include the root request span (<code>next.span_type</code> <code>BaseServer.handleRequest</code>), App Router rendering (<code>AppRender.getBodyResult</code>), each <code>fetch</code> (<code>AppRender.fetch</code>, disabled with <code>NEXT_OTEL_FETCH_DISABLED=1</code>), Route Handler execution (<code>AppRouteRouteHandlers.runHandler</code>), <code>generateMetadata</code>, and a zero-length <code>start response</code> span at first byte. <p>What to put on dashboards: p95 of <code>start response</code> (time to first byte) per <code>next.route</code>, error counts from <code>onRequestError</code> by <code>routeType</code>, <code>fetch</code> span durations per upstream host, and prefetch (<code>next.rsc</code>) volume after a navigation change.</p>
<blockquote>
<p><strong>Watch out:</strong> error payloads are a leak vector too. Do not ship full request headers (cookies, <code>authorization</code>) to a third-party sink; pick the fields you need, as above.</p>
</blockquote>

<h1 id="Chapter-7-—-Environment-variables-and-NEXT_PUBLIC_-leaks"><a href="#Chapter-7-—-Environment-variables-and-NEXT_PUBLIC_-leaks" class="headerlink" title="Chapter 7 — Environment variables and NEXT_PUBLIC_ leaks"></a>Chapter 7 — Environment variables and <code>NEXT_PUBLIC_</code> leaks</h1>
<h2 id="How-loading-works"><a href="#How-loading-works" class="headerlink" title="How loading works"></a>How loading works</h2>
<p>Lookup order, stopping at the first hit: <code>process.env</code>, <code>.env.$(NODE_ENV).local</code>, <code>.env.local</code> (skipped when <code>NODE_ENV</code> is <code>test</code>), <code>.env.$(NODE_ENV)</code>, <code>.env</code>. Variables can reference others with <code>$VAR</code>. Outside Next.js (an ORM config, a test runner), <code>loadEnvConfig</code> from <code>@next/env</code> loads them the same way.</p>
<h2 id="The-inlining-rule"><a href="#The-inlining-rule" class="headerlink" title="The inlining rule"></a>The inlining rule</h2>
<p>Only variables prefixed <code>NEXT_PUBLIC_</code> reach the browser, and they are <strong>inlined as literals at <code>next build</code></strong>. Consequences:</p>
<ul>
<li>One Docker image promoted from staging to production keeps <strong>staging's</strong> <code>NEXT_PUBLIC_</code> values. Runtime values must be read on the server during dynamic rendering (<code>await connection()</code> first) or served by an endpoint.</li>
<li>Only direct references are replaced: <code>process.env[name]</code> or <code>const env = process.env; env.NEXT_PUBLIC_X</code> are <strong>not</strong> inlined.</li>
<li>The <code>env</code> key in <code>next.config</code> inlines values into the bundle the same way. This blog uses it for <code>NEXT_PUBLIC_BASE_PATH</code>, which is public by nature.</li>
</ul>
<h2 id="How-secrets-actually-leak"><a href="#How-secrets-actually-leak" class="headerlink" title="How secrets actually leak"></a>How secrets actually leak</h2>
<table>
<thead>
<tr>
<th>Leak</th>
<th>Example</th>
<th>Prevention</th>
</tr>
</thead>
<tbody>
<tr>
<td>Wrong prefix</td>
<td><code>NEXT_PUBLIC_STRIPE_SECRET_KEY</code></td>
<td>Code review rule and a CI grep: no <code>SECRET</code>, <code>TOKEN</code>, <code>KEY</code> after <code>NEXT_PUBLIC_</code> unless explicitly public</td>
</tr>
<tr>
<td><code>next.config</code> <code>env</code></td>

</blockquote>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Survive-a-Proxy-bypass"><a href="#Exercise-1-—-Survive-a-Proxy-bypass" class="headerlink" title="Exercise 1 — Survive a Proxy bypass"></a>Exercise 1 — Survive a Proxy bypass</h2>
<p>An app's only protection for <code>/admin</code> is a <code>proxy.ts</code> redirect when the <code>role</code> cookie is not <code>admin</code>. Describe an attack even without a framework CVE, and redesign the checks.</p>
<details>
<summary>Solution</summary>
<p>The cookie is client-controlled: set <code>role=admin</code> and the redirect passes. Even with a signed cookie, any bypass or matcher gap exposes everything. Redesign: Proxy only checks that a session cookie exists; <code>verifySession()</code> in the DAL decrypts and verifies the session and loads the role from the session store; every admin DAL function checks <code>role === 'admin'</code>; every admin Server Action calls those DAL functions.</p>
</details>
<h2 id="Exercise-2-—-Triage-an-advisory"><a href="#Exercise-2-—-Triage-an-advisory" class="headerlink" title="Exercise 2 — Triage an advisory"></a>Exercise 2 — Triage an advisory</h2>
<p>A new critical advisory lists &quot;Next.js 15.x and 16.x App Router, fixed in 15.5.x and 16.3.x&quot;. You run 15.2.4 self-hosted and a static-export marketing site on 14.2. What do you do for each?</p>
<details>
<summary>Solution</summary>
<p>15.2.4 is inside the affected range and on an old minor: upgrade to the latest 15.5.x patch (the Maintenance LTS line), deploy, and if the advisory is remote code execution and you were exposed, rotate secrets. Then plan the move to 16.x. The static export has no Next.js server, so server-side advisories do not apply; note that 14.x is outside the LTS policy and schedule an upgrade.</p>
</details>
<h2 id="Exercise-3-—-Fix-the-image-config"><a href="#Exercise-3-—-Fix-the-image-config" class="headerlink" title="Exercise 3 — Fix the image config"></a>Exercise 3 — Fix the image config</h2>
<p>A Next.js 16 upgrade makes every product image look slightly different and a designer complains <code>quality={90}</code> is ignored. Explain and fix.</p>
<details>
<summary>Solution</summary>
<p>In 16, <code>images.qualities</code> defaults to <code>[75]</code> and <code>quality</code> is coerced to the nearest allowed value, so 90 becomes 75. Add the needed values: <code>images: { qualities: [75, 90] }</code>. Keep the list short: each allowed quality is another variant attackers can request and the server must cache.</p>
</details>
<h2 id="Exercise-4-—-Two-pods-stale-pages"><a href="#Exercise-4-—-Two-pods-stale-pages" class="headerlink" title="Exercise 4 — Two pods, stale pages"></a>Exercise 4 — Two pods, stale pages</h2>
<p>After scaling from one to two pods, users see a product page flip between old and new prices for minutes after an edit. List the causes and fixes.</p>
<details>
<summary>Solution</summary>
<p>Each pod has its own ISR and data cache on local disk and memory, and <code>revalidateTag</code> / <code>updateTag</code> on one pod does not reach the other. Configure a shared <code>cacheHandler</code> (and <code>cacheHandlers</code> for <code>'use cache: remote'</code>), set <code>cacheMaxMemorySize: 0</code>, and implement <code>refreshTags()</code> so each pod syncs tag invalidations before serving. Also make sure both pods run the same build and share <code>NEXT_SERVER_ACTIONS_ENCRYPTION_KEY</code>.</p>
</details>
<h2 id="Exercise-5-—-Find-the-leak"><a href="#Exercise-5-—-Find-the-leak" class="headerlink" title="Exercise 5 — Find the leak"></a>Exercise 5 — Find the leak</h2>
<p>A Server Component renders <code>&lt;Checkout config={config} /&gt;</code> where <code>config = { currency: 'EUR', stripeSecret: process.env.STRIPE_SECRET_KEY, publishableKey: process.env.NEXT_PUBLIC_STRIPE_KEY }</code>. What leaks, how would you detect it, and how do you prevent it structurally?</p>
<details>
<summary>Solution</summary>
<p><code>stripeSecret</code> is serialised into the RSC payload and visible in page source, even if <code>Checkout</code> never renders it. Detect it by searching the HTML and <code>_rsc</code> responses for the key prefix, or with <code>experimental_taintUniqueValue</code> on the secret, which makes React throw when it is passed to the client. Prevent it by reading the secret only in the DAL, giving <code>Checkout</code> a narrow props type (<code>{ currency, publishableKey }</code>), and marking the config module <code>server-only</code>.</p>
</details>
<h2 id="Exercise-6-—-Instrument-a-slow-route"><a href="#Exercise-6-—-Instrument-a-slow-route" class="headerlink" title="Exercise 6 — Instrument a slow route"></a>Exercise 6 — Instrument a slow route</h2>
<p>Users report slow <code>/products/[id]</code> pages. Using only the default Next.js spans, how do you find whether the time goes to rendering, to upstream <code>fetch</code> calls, or before the first byte?</p>
<details>
<summary>Solution</summary>
<p>Filter traces by <code>next.route = /products/[id]</code>. Compare the root <code>BaseServer.handleRequest</code> duration with the <code>start response</code> span (time to first byte), the <code>AppRender.getBodyResult</code> render span, and the child <code>AppRender.fetch</code> spans grouped by host. Long fetch spans in sequence point to a waterfall (Post 01); a late <code>start response</code> with short fetches points to blocking work outside Suspense (Post 02).</p>
</details>
