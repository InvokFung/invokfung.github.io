11:T14b8f,<p>An AI coding agent is a language model that can read your files, run commands and edit code in a loop until a task is done. Used well, it removes hours of routine work. Used carelessly, it produces a confident mess, pushes it, and leaves you to find out later. This post explains what an agent really is, then tours one real tool in depth: Claude Code, with its project memory (<code>CLAUDE.md</code>), skills, hooks, subagents, permission modes, MCP servers and cloud sessions. It maps the same ideas onto <code>AGENTS.md</code>, GitHub Copilot and Cursor, gives a workflow that keeps you in charge, and ends with a review checklist and a real case study: the <code>CLAUDE.md</code> that runs this blog. Feature details were checked against the official docs in September 2026. These tools change monthly, so check the docs again before you rely on a detail.</p>

<p>Run it from inside any small project folder. Three details carry over to every real agent:</p>
<ul>
<li><strong>The loop has a hard cap.</strong> An agent that never stops burns money.</li>
<li><strong>Tools check their inputs.</strong> <code>inside_project</code> refuses paths like <code>../../secrets</code>. The model's arguments are untrusted input.</li>
<li><strong>The whole assistant turn goes back into the history</strong>, including any <code>thinking</code> blocks, and all tool results go back in one user message.</li>
</ul>
<p>Now add a <code>write_file</code> tool and a <code>run_command</code> tool, and you have a real coding agent. You also have a real risk. A production harness exists to manage exactly that risk: which actions need a human's approval, what fits in the context, and how to recover from mistakes. The rest of this post is about using those controls well.</p>

<h1 id="Chapter-2-—-Claude-Code-project-memory-with-CLAUDEmd"><a href="#Chapter-2-—-Claude-Code-project-memory-with-CLAUDEmd" class="headerlink" title="Chapter 2 — Claude Code: project memory with CLAUDE.md"></a>Chapter 2 — Claude Code: project memory with <a href="http://CLAUDE.md" target="_blank" rel="noopener external nofollow noreferrer">CLAUDE.md</a></h1>
<p>Claude Code is Anthropic's coding agent. It runs in the terminal, in IDEs, in a desktop app and in the cloud. Each session starts with a fresh context window, so knowledge that must survive between sessions lives in files.</p>

<p>How they load (official docs, September 2026):</p>
<ul>
<li>At launch, Claude Code reads <code>CLAUDE.md</code> and <code>CLAUDE.local.md</code> from the working directory <strong>and every directory above it</strong>.</li>
<li>Files are <strong>joined together, not overridden</strong>. Content runs from the filesystem root down to the working directory, so the closest instructions are read last.</li>
<li>A <code>CLAUDE.md</code> inside a <strong>subdirectory</strong> loads later, when Claude reads files in that subdirectory.</li>
<li><code>@path/to/file</code> inside a <code>CLAUDE.md</code> imports another file (up to four hops deep).</li>
<li><code>/init</code> generates a starting file; <code>/memory</code> and <code>/context</code> show which files actually loaded.</li>
</ul>
<h2 id="What-to-write"><a href="#What-to-write" class="headerlink" title="What to write"></a>What to write</h2>
<p>The docs suggest staying <strong>under 200 lines</strong>: every line costs context in every session, and long files reduce how well rules are followed. Write down what Claude cannot guess by reading the code:</p>
<ul>
<li>build, test and lint commands,</li>
<li>style rules that differ from the language defaults,</li>
<li>project layout and naming conventions,</li>
<li>&quot;never do X&quot; rules, each with the <strong>reason</strong>,</li>
<li>known traps in this repository.</li>
</ul>
<p>Leave out what the code already shows, long tutorials, and file-by-file descriptions. For every line, ask: &quot;Would removing this cause a mistake?&quot;</p>
<blockquote>
<p><strong>Trick:</strong> block-level HTML comments (<code>&lt;!-- note for humans --&gt;</code>) in a <code>CLAUDE.md</code> are stripped before the text reaches the model. Use them for notes to maintainers.</p>
</blockquote>
<h2 id="Rules-and-memory-Claude-writes-itself"><a href="#Rules-and-memory-Claude-writes-itself" class="headerlink" title="Rules, and memory Claude writes itself"></a>Rules, and memory Claude writes itself</h2>
<ul>
<li><strong><code>.claude/rules/*.md</code></strong> splits instructions by topic. A rule with a <code>paths:</code> list in its frontmatter (for example <code>&quot;src/api/**/*.ts&quot;</code>) only loads when Claude works on matching files.</li>
<li><strong>Auto memory</strong> is a separate store of notes Claude writes about your corrections and preferences. It is loaded every session (the first 200 lines or 25KB).</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> <code>CLAUDE.md</code> is <strong>context, not configuration</strong>. The docs are explicit: Claude treats it as guidance, and to block an action no matter what the model decides, you need a hook or a permission rule (Chapters 3 and 4).</p>
</blockquote>

<h1 id="Chapter-3-—-Skills-hooks-and-subagents"><a href="#Chapter-3-—-Skills-hooks-and-subagents" class="headerlink" title="Chapter 3 — Skills, hooks and subagents"></a>Chapter 3 — Skills, hooks and subagents</h1>
<h2 id="Skills-knowledge-and-workflows-loaded-on-demand"><a href="#Skills-knowledge-and-workflows-loaded-on-demand" class="headerlink" title="Skills: knowledge and workflows loaded on demand"></a>Skills: knowledge and workflows loaded on demand</h2>
<p>A skill is a folder with a <code>SKILL.md</code> file. Project skills live in <code>.claude/skills/&lt;name&gt;/SKILL.md</code>, personal ones in <code>~/.claude/skills/&lt;name&gt;/SKILL.md</code>. Only each skill's <strong>description</strong> sits in context all the time. The full body loads when you type <code>/&lt;name&gt;</code> or when Claude decides the description matches the task.</p>

<h2 id="Hooks-things-that-must-happen-every-time"><a href="#Hooks-things-that-must-happen-every-time" class="headerlink" title="Hooks: things that must happen every time"></a>Hooks: things that must happen every time</h2>
<p>A hook is a command that Claude Code runs at a lifecycle event, such as <code>SessionStart</code>, <code>UserPromptSubmit</code>, <code>PreToolUse</code> (before a tool call, can block it), <code>PostToolUse</code> (after a tool call succeeds) or <code>Stop</code> (when Claude finishes). Hooks are <strong>deterministic</strong>: they fire whether or not the model remembers a rule. They live in <code>~/.claude/settings.json</code> (all your projects), <code>.claude/settings.json</code> (the project, can be committed) or <code>.claude/settings.local.json</code> (the project, just you).</p>

<p>MCP servers give Claude new tools: your issue tracker, a database, a browser. Add one with <code>claude mcp add</code>:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">claude mcp add --transport http docs-search https://example.com/mcp                  <span class="hljs-comment"># just you, this project</span></span><br><span class="line">claude mcp add --transport http docs-search --scope project https://example.com/mcp  <span class="hljs-comment"># writes .mcp.json for the team</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-6-—-A-workflow-that-keeps-you-in-charge"><a href="#Chapter-6-—-A-workflow-that-keeps-you-in-charge" class="headerlink" title="Chapter 6 — A workflow that keeps you in charge"></a>Chapter 6 — A workflow that keeps you in charge</h1>
<h2 id="Plan-then-small-steps-then-verify-each-one"><a href="#Plan-then-small-steps-then-verify-each-one" class="headerlink" title="Plan, then small steps, then verify each one"></a>Plan, then small steps, then verify each one</h2>
<p>The Claude Code best-practices guide describes four phases, and they fit any agent:</p>
<ol>
<li><strong>Explore.</strong> In plan mode, ask the agent to read the relevant code and explain it. No edits yet.</li>
<li><strong>Plan.</strong> Ask for a written plan: files to change, order of steps, tests to add. Edit the plan yourself. Skip planning only when you could describe the diff in one sentence.</li>
<li><strong>Implement in small steps.</strong> One step, then a check, then the next step.</li>
<li><strong>Commit.</strong> Small commits with real messages, so any step can be reverted (see Dev Essentials 03 · Git Rescue Kit).</li>
</ol>
<p>The most useful single habit: <strong>give the agent a check it can run.</strong> Tests, a build, a linter, a script that compares output. The guide puts it plainly: without a check, &quot;looks done&quot; is the only signal, and you become the verification loop.</p>
<h2 id="Give-context-the-way-you-would-to-a-new-colleague"><a href="#Give-context-the-way-you-would-to-a-new-colleague" class="headerlink" title="Give context the way you would to a new colleague"></a>Give context the way you would to a new colleague</h2>

<th>Strong prompt</th>
</tr>
</thead>
<tbody>

<td>&quot;Users are logged out after a session timeout. Check the token refresh in <code>src/auth/</code>. Write a failing test that shows it, then fix it.&quot;</td>
</tr>
<tr>
<td>&quot;add tests for <a href="http://foo.py" target="_blank" rel="noopener external nofollow noreferrer">foo.py</a>&quot;</td>

<p>Name the files, paste real errors, state the constraints (versions, &quot;do not change the public API&quot;), and say what &quot;done&quot; means.</p>
<h2 id="Keep-the-human-in-charge-of-irreversible-actions"><a href="#Keep-the-human-in-charge-of-irreversible-actions" class="headerlink" title="Keep the human in charge of irreversible actions"></a>Keep the human in charge of irreversible actions</h2>
<p>Pushing, deploying, deleting data, running migrations, sending messages, and changing CI secrets are one-way doors. Let the agent <strong>prepare</strong> them. You <strong>do</strong> them. Enforce that with deny or ask rules (Chapter 4), not only with a sentence in <code>CLAUDE.md</code>.</p>
<h2 id="Manage-context-like-a-scarce-resource"><a href="#Manage-context-like-a-scarce-resource" class="headerlink" title="Manage context like a scarce resource"></a>Manage context like a scarce resource</h2>
<ul>
<li><code>/clear</code> between unrelated tasks. A clean session with a better prompt usually beats a long one full of failed attempts.</li>
<li>After two failed corrections on the same issue, stop, <code>/clear</code>, and rewrite the prompt with what you learned.</li>
<li>Send research to a subagent so only the summary enters your context.</li>
<li>Checkpoints (<code>Esc</code> <code>Esc</code> or <code>/rewind</code>) can undo Claude's file edits, but not changes made by shell commands. They are not a replacement for git.</li>
</ul>

<h1 id="Chapter-7-—-Reviewing-AI-output"><a href="#Chapter-7-—-Reviewing-AI-output" class="headerlink" title="Chapter 7 — Reviewing AI output"></a>Chapter 7 — Reviewing AI output</h1>
<p>You own every line you merge, whoever typed it. Review AI-written changes at least as strictly as a new colleague's.</p>
<h2 id="The-checklist"><a href="#The-checklist" class="headerlink" title="The checklist"></a>The checklist</h2>
<ol>
<li><strong>Read the whole diff.</strong> <code>git diff</code> and <code>git diff --staged</code>, every file. Look for changes outside the task.</li>
<li><strong>Run the tests yourself</strong>, and check the tests were not weakened: deleted assertions, new <code>skip</code> or <code>xfail</code> markers, loosened expected values, <code>.only</code> left in (see Dev Essentials 15 · Testing).</li>
<li><strong>Check every API, flag and config key you do not know.</strong> Open the official docs, run <code>--help</code>, or import it in a REPL. Invented functions and flags look perfectly plausible.</li>
<li><strong>Check every new dependency.</strong> Does the package exist, is it the one you meant, is it maintained? Spracklen et al. (USENIX Security 2025) found code models suggesting packages that do not exist: at least 5.2% of suggested packages for commercial models and 21.7% for open-source models (independent measurement). Attackers can register those names (see Dev Essentials 09 · Versions &amp; Dependencies).</li>
<li><strong>Security.</strong> Injection, missing authorisation checks, disabled TLS verification, unsafe deserialisation, overly broad CORS (see Dev Essentials 12 · OWASP Top 10). Claude Code has a <code>/security-review</code> command for a first pass, but it does not replace your own review.</li>
<li><strong>Secrets.</strong> No keys, tokens or passwords in code, tests, logs or fixtures. A quick scan:</li>
</ol>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git diff --staged | grep -inE <span class="hljs-string">&quot;api[_-]?key|secret|token|password|BEGIN .*PRIVATE KEY&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="powershell"><span class="line">git <span class="hljs-built_in">diff</span> <span class="hljs-literal">--staged</span> | <span class="hljs-built_in">Select-String</span> <span class="hljs-literal">-Pattern</span> <span class="hljs-string">&#x27;api[_-]?key|secret|token|password|BEGIN .*PRIVATE KEY&#x27;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ol start="7">
<li><strong>Licensing.</strong> Large blocks that look copied from elsewhere, removed license headers, new dependencies with incompatible licenses.</li>
<li><strong>Text hygiene.</strong> Encoding, line endings and bulk reformatting noise (see Dev Essentials 01 · Text Encoding and 04 · Line Endings).</li>

<p><strong>Trick:</strong> use a second, fresh reviewer. A new session or subagent that sees only the diff and your criteria is not biased by the reasoning that produced the change. Claude Code's bundled <code>/code-review</code> skill runs such a review in a fresh subagent.</p>

<h2 id="The-encoding-incident"><a href="#The-encoding-incident" class="headerlink" title="The encoding incident"></a>The encoding incident</h2>
<p>A helper script once rewrote 44 posts through Windows PowerShell 5.1 and saved them in the system's ANSI code page instead of UTF-8. About 2,700 characters were destroyed: <code>—</code> became a literal <code>??</code>, and <code>·</code> became a stray CJK character, U+7E5A. Microsoft's docs confirm the trap: in Windows PowerShell 5.1, <code>Set-Content</code> and <code>Add-Content</code> use the <code>Default</code> encoding, which is the active ANSI code page, when the file is new or empty. Also, <code>-Encoding utf8</code> in 5.1 writes UTF-8 <strong>with</strong> a byte order mark (PowerShell 7 defaults to UTF-8 without one). The <code>CLAUDE.md</code> therefore shows the right way to write files, and a one-line check that searches every post for U+7E5A and must print nothing after any bulk edit. Written so that it does not depend on the shell's locale, the check looks like this:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="bash"><span class="line">grep -l <span class="hljs-string">&quot;<span class="hljs-subst">$(printf &#x27;\347\271\232&#x27;)</span>&quot;</span> content/posts/*.md    <span class="hljs-comment"># the three UTF-8 bytes of U+7E5A</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="powershell"><span class="line"><span class="hljs-built_in">Select-String</span> <span class="hljs-literal">-Path</span> content\posts\*.md <span class="hljs-literal">-Pattern</span> ([<span class="hljs-built_in">char</span>]<span class="hljs-number">0</span>x7E5A) <span class="hljs-literal">-List</span> | <span class="hljs-built_in">ForEach-Object</span> Path</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> check the checker. A shorter form using bash's <code>$'\uXXXX'</code> quoting only turns into the real character when bash runs in a UTF-8 locale. In a shell with no locale set, it stays plain text, and grep then searches for the wrong thing. In a quick test in such a shell, that form flagged a clean file and missed the corrupted one. The <code>printf</code> version above passes the raw UTF-8 bytes, so it works in any locale. Run any verify command once against a known-bad and a known-good file.</p>
</blockquote>
<h2 id="Why-the-rules-live-in-the-root-CLAUDEmd"><a href="#Why-the-rules-live-in-the-root-CLAUDEmd" class="headerlink" title="Why the rules live in the root CLAUDE.md"></a>Why the rules live in the root <a href="http://CLAUDE.md" target="_blank" rel="noopener external nofollow noreferrer">CLAUDE.md</a></h2>
<p>In this repository the whole <code>.claude/</code> folder is gitignored. That has a direct consequence (Chapter 4): nothing inside <code>.claude/</code>, not settings, not hooks, not skills, reaches a cloud session or a fresh clone. The only instruction file every session is guaranteed to see is the committed root <code>CLAUDE.md</code>. So the durable rules had to go there, in plain words, with the reason for each.</p>
<h2 id="A-trimmed-generic-version-you-can-adapt"><a href="#A-trimmed-generic-version-you-can-adapt" class="headerlink" title="A trimmed, generic version you can adapt"></a>A trimmed, generic version you can adapt</h2>
<pre><code class="language-markdown"><figure class="highlight markdown"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span><br><span class="line">17</span><br><span class="line">18</span><br><span class="line">19</span><br><span class="line">20</span></pre></td><td class="code"><pre><code class="markdown"><span class="line"><span class="hljs-section"># Project instructions</span></span><br><span class="line"> </span><br><span class="line">Static blog. <p>Lessons that transfer to any project:</p>
<ol>
<li><strong>Write a rule after an incident, and include the reason.</strong> A reason lets the agent handle cases the rule did not foresee.</li>
<li><strong>Give a verify command, not just a warning</strong>, and test the command itself. A check the agent can run beats a sentence it may skim.</li>
<li><strong>Put durable rules where every session can see them.</strong> Committed and at the root.</li>
<li><strong>Keep it short</strong>, so the important rules do not get lost.</li>
<li><strong>Back prose rules with enforcement where you can.</strong> A <code>Bash(git push *)</code> deny rule in your user settings stops pushes locally even though the project's <code>.claude/</code> folder is not shared.</li>
</ol>

<h2 id="Exercise-4-—-One-file-for-three-tools"><a href="#Exercise-4-—-One-file-for-three-tools" class="headerlink" title="Exercise 4 — One file for three tools"></a>Exercise 4 — One file for three tools</h2>

<details>
<summary>Solution</summary>
<p>Put the shared rules in <code>AGENTS.md</code> at the repo root. Copilot and Cursor both read <code>AGENTS.md</code>. <h2 id="Exercise-5-—-Review-this-diff"><a href="#Exercise-5-—-Review-this-diff" class="headerlink" title="Exercise 5 — Review this diff"></a>Exercise 5 — Review this diff</h2>
<p>An agent produced this change to &quot;add retries to the payment client&quot;. Find at least four problems.</p>
<pre><code class="language-diff"><figure class="highlight diff"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="diff"><span class="line"><span class="hljs-addition">+import requests_retry_helper</span></span><br><span class="line"><span class="hljs-addition">+API_KEY = &quot;sk_live_51H...&quot;</span></span><br><span class="line"> def charge(amount, card):</span><br><span class="line"><span class="hljs-deletion">-    resp = requests.post(URL, json={&quot;amount&quot;: amount, &quot;card&quot;: card}, timeout=10)</span></span><br><span class="line"><span class="hljs-addition">+    resp = requests.post(URL, json={&quot;amount&quot;: amount, &quot;card&quot;: card},</span></span><br><span class="line"><span class="hljs-addition">+                         verify=False, retries=3, headers={&quot;Authorization&quot;: API_KEY})</span></span><br><span class="line">     return resp.json()</span><br><span class="line"><span class="hljs-deletion">-def test_charge_rejects_negative():</span></span><br><span class="line"><span class="hljs-deletion">-    with pytest.raises(ValueError):</span></span><br><span class="line"><span class="hljs-deletion">-        charge(-5, CARD)</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<ol>
<li><strong>Hardcoded live secret</strong> (<code>API_KEY = &quot;sk_live_...&quot;</code>): remove it, rotate the key, load it from the environment.</li>
<li><strong>Invented argument:</strong> <code>requests.post</code> has no <code>retries</code> parameter. Retries in <code>requests</code> are configured through an <code>HTTPAdapter</code> with <code>urllib3</code>'s <code>Retry</code>.</li>
<li><strong>Unknown dependency</strong> <code>requests_retry_helper</code>: check that it exists and is trustworthy; it may be a hallucinated name.</li>
<li><strong><code>verify=False</code></strong> turns off TLS certificate checks on a payment call.</li>
<li><strong><code>timeout=10</code> was removed</strong>, so a hung server now blocks forever.</li>
<li><strong>A test was deleted</strong> instead of fixed.</li>
<li><strong>Retrying a charge</strong> without an idempotency key can charge the customer twice (see Dev Essentials 14 · API Reliability).</li>
</ol>
</details>
<h2 id="Exercise-6-—-What-reaches-the-cloud"><a href="#Exercise-6-—-What-reaches-the-cloud" class="headerlink" title="Exercise 6 — What reaches the cloud?"></a>Exercise 6 — What reaches the cloud?</h2>
<p>Your repo gitignores <code>.claude/</code>. You have a project hook in <code>.claude/settings.json</code>, a personal skill in <code>~/.claude/skills/</code>, a committed root <code>CLAUDE.md</code>, and a committed <code>.mcp.json</code>. Which of these does a single-repository cloud session see?</p>
<details>
<summary>Solution</summary>
<p>Only the root <code>CLAUDE.md</code> and <code>.mcp.json</code>, because only committed files are in the clone. The project hook lives in the ignored <code>.claude/</code> folder, so it never reaches the clone. The personal skill lives on your machine. To make the hook travel, stop ignoring <code>.claude/settings.json</code> (for example, ignore only <code>.claude/settings.local.json</code> and other personal files) and commit it.</p>
</details>
