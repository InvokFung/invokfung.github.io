11:T13e4a,<p>Most Vue bugs that reach production are not template bugs. They are reactivity bugs: a value that stopped updating after a refactor, a watcher that fires three times or never, a list that re-renders on every keystroke, a store that leaks between SSR requests. All of them come from one small engine — <code>@vue/reactivity</code> — and all of them become obvious once its model is clear. This post takes the engine apart: how <code>reactive()</code> builds on <code>Proxy</code>, how <code>track</code> and <code>trigger</code> build a dependency graph, why <code>computed</code> is lazy and when it recomputes, what <code>flush: 'pre'</code> really means, how the scheduler batches updates into one microtask, and how Vue's model compares with the signals in Solid, Preact, Angular and the TC39 proposal. Examples target <strong>Vue 3.5</strong> (3.5.42 at the time of writing). Where the <strong>3.6</strong> release candidate (3.6.0-rc.7) differs, it is called out. Every behaviour claim with an output comment was checked by running it against 3.5.</p>

<h1 id="Chapter-1-—-The-model-effects-deps-triggers"><a href="#Chapter-1-—-The-model-effects-deps-triggers" class="headerlink" title="Chapter 1 — The model: effects, deps, triggers"></a>Chapter 1 — The model: effects, deps, triggers</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Effect (subscriber)</strong> — a function that reads reactive state and must re-run when that state changes. A component's render, a <code>watchEffect</code>, a <code>watch</code> getter and a <code>computed</code> getter are all effects.</li>
<li><strong>Dep</strong> — the list of subscribers attached to one reactive property (one key of one object, or the <code>.value</code> of one ref).</li>
<li><strong>Track</strong> — during an effect run, record &quot;this effect read this property&quot; by linking the effect to the property's dep.</li>
<li><strong>Trigger</strong> — on a write, notify every subscriber in the property's dep.</li>
<li><strong>Active subscriber</strong> — the effect currently running. <code>track</code> only does something while one exists; a read outside any effect is invisible to the system.</li>
<li><strong>Dirty</strong> — a subscriber whose dependencies changed since its last run.</li>
<li><strong>Scheduler</strong> — the function an effect calls instead of re-running itself directly. Components and watchers use it to queue work.</li>
</ul>

<p>Three properties fall out of this design and explain most of Vue's behaviour:</p>
<ol>
<li><strong>Dependencies are discovered at run time.</strong> An effect depends on exactly what it read during its last run. A branch that was not taken creates no dependency.</li>
<li><strong>Reads outside an effect are not tracked.</strong> <code>const n = state.count</code> in plain <code>setup()</code> code reads once and never updates.</li>
<li><strong>Tracking is synchronous.</strong> Only reads made while the effect is on the stack count. A read after an <code>await</code> happens after the effect returned, so it is not tracked (Chapter 5).</li>
</ol>
<h2 id="The-real-data-structures-35"><a href="#The-real-data-structures-35" class="headerlink" title="The real data structures (3.5)"></a>The real data structures (3.5)</h2>
<p>In 3.5 the storage is a <code>WeakMap&lt;target, Map&lt;key, Dep&gt;&gt;</code> called <code>targetMap</code>. Because the outer map is weak, an object that nobody references any more can be garbage-collected together with its deps.</p>
<p>The 3.5 release rewrote the internals around two ideas taken from Preact signals: <strong>version counting</strong> and <strong>doubly-linked lists</strong>. Each <code>Dep</code> has a <code>version</code> that increases on every trigger. Each subscriber keeps a linked list of <code>Link</code> nodes, one per dep it read; each <code>Link</code> also sits in the dep's list of subscribers, and records the dep version seen at the last run. On a re-run, links that were not visited again are removed, so a dependency from a branch no longer taken is dropped in O(1) per link rather than by clearing and rebuilding sets.</p>
<p>The Vue 3.5 announcement reports <strong>56% lower memory use</strong> for the reactivity system with no behaviour change, and up to 10x faster operations on large, deeply reactive arrays in some cases. The pull request that did this measured 1,426k down to 631k in a test of 1,000 refs, 2,000 computeds and 1,000 effects.</p>
<p><strong>Vue 3.6</strong> (release candidate at the time of writing) replaces this core again with a refactor based on <strong>alien-signals</strong>, a signals library by a Vue core team member. The shape changes — the 3.6 package exposes internal functions such as <code>link</code>, <code>unlink</code>, <code>propagate</code> and <code>checkDirty</code> — but the public API (<code>ref</code>, <code>reactive</code>, <code>computed</code>, <code>watch</code>, <code>effectScope</code>) is the same. The rc release notes list no breaking change to the reactivity API.</p>
<p><img src="/blog/assets/vue/diagram_00_write_to_dom.svg" alt="How a Vue write becomes a DOM update: a ref and a computed linked by track and trigger to four subscribers (a component render and pre, post and sync watchers), then one tick in which sync watchers run at once, and pre watchers, component updates and post watchers run in one microtask flush before nextTick resolves."></p>

</blockquote>
<h2 id="Arrays-and-length"><a href="#Arrays-and-length" class="headerlink" title="Arrays and length"></a>Arrays and length</h2>
<p>Mutating array methods (<code>push</code>, <code>pop</code>, <code>shift</code>, <code>unshift</code>, <code>splice</code>) read and write <code>length</code>. If they tracked it, an effect that pushes into an array it also reads would trigger itself forever, so Vue pauses tracking inside those methods. Checked: <code>watchEffect(() =&gt; { runs++; if (runs &lt; 5) list.push(1) }, { flush: 'sync' })</code> runs once, not five times.</p>
<h2 id="What-reactive-refuses-to-wrap"><a href="#What-reactive-refuses-to-wrap" class="headerlink" title="What reactive() refuses to wrap"></a>What <code>reactive()</code> refuses to wrap</h2>
<ul>
<li><strong>Primitives</strong> — a proxy needs an object. This is the reason <code>ref()</code> exists.</li>
<li><strong>Frozen or non-extensible objects</strong> — <code>reactive(Object.freeze({ a: 1 }))</code> returns the frozen object unchanged; <code>isReactive()</code> is <code>false</code>.</li>
<li><strong>Objects marked with <code>markRaw()</code></strong> — useful for class instances from third-party libraries (map SDKs, editors, Three.js scenes) that should never be proxied.</li>
<li><strong>Classes with <code>#private</code> fields</strong>, in practice. The proxy wraps fine, but a method called through the proxy runs with <code>this</code> set to the proxy, and the private-field check fails:</li>
</ul>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">class</span> <span class="hljs-title class_">Counter</span> { #n = <span class="hljs-number">0</span>; <span class="hljs-title function_">inc</span>(<span class="hljs-params"></span>) { <span class="hljs-variable language_">this</span>.#n++ } }</span><br><span class="line"><span class="hljs-keyword">const</span> c = <span class="hljs-title function_">reactive</span>(<span class="hljs-keyword">new</span> <span class="hljs-title class_">Counter</span>())</span><br><span class="line">c.<span class="hljs-title function_">inc</span>()</span><br><span class="line"><span class="hljs-comment">// TypeError: Cannot read private member #n from an object whose class did not declare it</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-3-—-ref-reactive-shallowRef-and-friends"><a href="#Chapter-3-—-ref-reactive-shallowRef-and-friends" class="headerlink" title="Chapter 3 — ref, reactive, shallowRef and friends"></a>Chapter 3 — <code>ref</code>, <code>reactive</code>, <code>shallowRef</code> and friends</h1>
<h2 id="ref-is-an-object-with-a-tracked-value"><a href="#ref-is-an-object-with-a-tracked-value" class="headerlink" title="ref() is an object with a tracked .value"></a><code>ref()</code> is an object with a tracked <code>.value</code></h2>
<p>A ref is an object whose <code>value</code> getter calls <code>track(ref, 'value')</code> and whose setter calls <code>trigger(ref, 'value')</code>; the real <code>RefImpl</code> class holds its own <code>Dep</code> instead of going through <code>targetMap</code>. A ref works for any value, including primitives, and replacing <code>.value</code> is always reactive. When the value is an object, <code>ref()</code> passes it through <code>reactive()</code>, so <code>ref({ n: 1 }).value.n++</code> is tracked too.</p>

<h1 id="Chapter-4-—-computed-lazy-cached-and-quiet-when-nothing-changed"><a href="#Chapter-4-—-computed-lazy-cached-and-quiet-when-nothing-changed" class="headerlink" title="Chapter 4 — computed: lazy, cached, and quiet when nothing changed"></a>Chapter 4 — <code>computed</code>: lazy, cached, and quiet when nothing changed</h1>
<h2 id="Laziness-and-caching"><a href="#Laziness-and-caching" class="headerlink" title="Laziness and caching"></a>Laziness and caching</h2>
<p>A computed is both a subscriber (it reads deps) and a dep (effects read it). It does not run until someone reads <code>.value</code>, and after that it re-runs only when a dependency changed <strong>and</strong> someone reads it again:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">let</span> calls = <span class="hljs-number">0</span></span><br><span class="line"><span class="hljs-keyword">const</span> n = <span class="hljs-title function_">ref</span>(<span class="hljs-number">1</span>)</span><br><span class="line"><span class="hljs-keyword">const</span> double = <span class="hljs-title function_">computed</span>(<span class="hljs-function">() =&gt;</span> { calls++; <span class="hljs-keyword">return</span> n.<span class="hljs-property">value</span> * <span class="hljs-number">2</span> })</span><br><span class="line">                               <span class="hljs-comment">// calls === 0: nothing read yet</span></span><br><span class="line">double.<span class="hljs-property">value</span>; double.<span class="hljs-property">value</span>     <span class="hljs-comment">// calls === 1: cached after the first read</span></span><br><span class="line">n.<span class="hljs-property">value</span> = <span class="hljs-number">2</span>                    <span class="hljs-comment">// calls === 1: marked dirty, not recomputed</span></span><br><span class="line">double.<span class="hljs-property">value</span>                   <span class="hljs-comment">// calls === 2: recomputed on demand</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>This is a <strong>push-pull</strong> design. A write pushes a &quot;maybe dirty&quot; notice down the graph; the actual recomputation is pulled by a read. Expensive computeds that nobody reads cost nothing.</p>
<p>Since <strong>3.5</strong>, a computed subscribes to its own dependencies only while it has at least one subscriber, and unsubscribes when it loses the last one. A computed read only from plain code (no effect reading it) is never registered as a subscriber of its dependencies, so writes never notify it. On each read it first checks a global version counter, which skips recomputation outright when nothing reactive has changed anywhere, and otherwise compares the versions of its own deps. The same refactor removed the ability to &quot;stop&quot; a computed, which fixed old bugs where a computed could return a stale value after its component unmounted.</p>
<h2 id="A-computed-that-returns-the-same-value-does-not-wake-its-dependents"><a href="#A-computed-that-returns-the-same-value-does-not-wake-its-dependents" class="headerlink" title="A computed that returns the same value does not wake its dependents"></a>A computed that returns the same value does not wake its dependents</h2>
<p>Since <strong>3.4</strong>, when a computed recomputes and gets a value equal to the previous one (<code>Object.is</code>), its subscribers are not triggered:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> n = <span class="hljs-title function_">ref</span>(<span class="hljs-number">1</span>)</span><br><span class="line"><span class="hljs-keyword">const</span> parity = <span class="hljs-title function_">computed</span>(<span class="hljs-function">() =&gt;</span> n.<span class="hljs-property">value</span> % <span class="hljs-number">2</span>)</span><br><span class="line"><span class="hljs-keyword">let</span> runs = <span class="hljs-number">0</span></span><br><span class="line"><span class="hljs-title function_">watchEffect</span>(<span class="hljs-function">() =&gt;</span> { parity.<span class="hljs-property">value</span>; runs++ })   <span class="hljs-comment">// runs === 1 (initial run)</span></span><br><span class="line"> </span><br><span class="line">n.<span class="hljs-property">value</span> = <span class="hljs-number">3</span>; <span class="hljs-keyword">await</span> <span class="hljs-title function_">nextTick</span>()   <span class="hljs-comment">// parity recomputes: 1 → 1, runs === 1</span></span><br><span class="line">n.<span class="hljs-property">value</span> = <span class="hljs-number">4</span>; <span class="hljs-keyword">await</span> <span class="hljs-title function_">nextTick</span>()   <span class="hljs-comment">// parity 1 → 0, runs === 2</span></span><br><span class="line">n.<span class="hljs-property">value</span> = <span class="hljs-number">6</span>; <span class="hljs-keyword">await</span> <span class="hljs-title function_">nextTick</span>()   <span class="hljs-comment">// parity 0 → 0, runs === 2</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The write to <code>n</code> marks <code>parity</code> as possibly dirty and notifies the effect. Before re-running, the effect asks <code>parity</code> whether it really changed; <code>parity</code> recomputes, compares with <code>Object.is</code>, and answers no. The effect is skipped. The rule: <strong>a computed whose new value is <code>Object.is</code>-equal to the old one does not trigger its subscribers.</strong> The practical corollary:</p>

<h2 id="Rules-for-computed-getters"><a href="#Rules-for-computed-getters" class="headerlink" title="Rules for computed getters"></a>Rules for computed getters</h2>
<ul>
<li><strong>No side effects.</strong> No writes to other state, no requests, no DOM work. Use a watcher.</li>
<li><strong>Do not mutate the returned value.</strong> It is a derived snapshot; mutating it changes nothing upstream and the next recompute throws the change away.</li>
<li><strong>Writable computed</strong> (<code>computed({ get, set })</code>) is for adapters, typically <code>v-model</code> on a transformed value. The setter should write the source, never the computed itself.</li>
<li>Writing to a read-only computed does not throw: Vue logs <code>[Vue warn] Write operation failed: computed value is readonly</code> in development and ignores the write.</li>
</ul>

<h1 id="Chapter-6-—-The-scheduler-and-nextTick"><a href="#Chapter-6-—-The-scheduler-and-nextTick" class="headerlink" title="Chapter 6 — The scheduler and nextTick"></a>Chapter 6 — The scheduler and <code>nextTick</code></h1>
<h2 id="Why-writes-do-not-re-render-immediately"><a href="#Why-writes-do-not-re-render-immediately" class="headerlink" title="Why writes do not re-render immediately"></a>Why writes do not re-render immediately</h2>
<p>A component's render effect does not re-run on each trigger. Its scheduler <strong>queues</strong> a job, and the queue is flushed in a microtask. Three synchronous writes cost one render and one <code>pre</code> watcher callback:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> c = <span class="hljs-title function_">ref</span>(<span class="hljs-number">0</span>)</span><br><span class="line"><span class="hljs-title function_">watch</span>(c, <span class="hljs-function">(<span class="hljs-params">v, o</span>) =&gt;</span> <span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(v, o))</span><br><span class="line">c.<span class="hljs-property">value</span>++; c.<span class="hljs-property">value</span>++; c.<span class="hljs-property">value</span>++</span><br><span class="line"><span class="hljs-comment">// nothing logged yet</span></span><br><span class="line"><span class="hljs-keyword">await</span> <span class="hljs-title function_">nextTick</span>()</span><br><span class="line"><span class="hljs-comment">// logs once: 3 0</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The watcher sees <code>oldValue</code> 0 and <code>value</code> 3; the intermediate values never exist from its point of view.</p>
<h2 id="One-flush-in-order"><a href="#One-flush-in-order" class="headerlink" title="One flush, in order"></a>One flush, in order</h2>
<p>The queue is flushed by a function scheduled with <code>Promise.resolve().then(flushJobs)</code>. Inside one flush:</p>
<ol>
<li><strong><code>flush: 'pre'</code> watcher callbacks and component update jobs</strong>, in one queue sorted by component id. A parent is created before its children, so it has a lower id and updates first. That guarantees a child is never rendered with props its parent is about to change, and lets the queue skip a child update that its parent's re-render already covered. Pre jobs for a component run just before that component's own update.</li>
<li><strong>Post-flush callbacks</strong>: <code>flush: 'post'</code> watchers, <code>onMounted</code> / <code>onUpdated</code> hooks and template ref updates. At this point the DOM is patched.</li>
<li>If any of those queued more work, the flush loops.</li>
</ol>
<p><code>flush: 'sync'</code> watchers are outside the queue: they run inside <code>trigger</code>, before the write statement even returns. Checked on 3.5 with three watchers on the same ref:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line">a.<span class="hljs-property">value</span>++</span><br><span class="line">log.<span class="hljs-title function_">push</span>(<span class="hljs-string">&#x27;after set&#x27;</span>)</span><br><span class="line"><span class="hljs-keyword">await</span> <span class="hljs-title function_">nextTick</span>()</span><br><span class="line"><span class="hljs-comment">// sync, after set, pre, post</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<table>
<thead>
<tr>
<th>Flush</th>
<th>Runs</th>
<th>DOM state</th>
<th>Use for</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>'sync'</code></td>
<td>Inside the write</td>
<td>Not updated</td>
<td>Rare: invariants that must hold immediately. Defeats batching.</td>
</tr>
<tr>

<p><code>watchPostEffect</code> and <code>watchSyncEffect</code> are aliases for <code>watchEffect</code> with <code>flush</code> set.</p>
<h2 id="nextTick"><a href="#nextTick" class="headerlink" title="nextTick()"></a><code>nextTick()</code></h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">nextTick</span>(<span class="hljs-params">fn</span>) {</span><br><span class="line">  <span class="hljs-keyword">const</span> p = currentFlushPromise || resolvedPromise</span><br><span class="line">  <span class="hljs-keyword">return</span> fn ? p.<span class="hljs-title function_">then</span>(fn) : p</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>That is the actual 3.5 implementation, minus a <code>this</code> binding. <code>nextTick()</code> returns the promise of the flush that is pending or running, so awaiting it means &quot;after this round of DOM updates&quot;. When no flush is pending, it resolves after an already-resolved promise — one microtask.</p>
<blockquote>
<p><strong>Common pitfall:</strong> <code>await nextTick()</code> inside a <code>flush: 'pre'</code> watcher to &quot;wait for the DOM&quot;. It works, but <code>flush: 'post'</code> says what you mean and avoids an extra hop.</p>
</blockquote>
<h2 id="Infinite-loops"><a href="#Infinite-loops" class="headerlink" title="Infinite loops"></a>Infinite loops</h2>
<p>A job that re-queues itself — a watcher that writes its own source, an <code>onUpdated</code> hook that changes state the template reads — is caught in development after <strong>100</strong> recursive runs (<code>RECURSION_LIMIT</code> in the scheduler), with a &quot;Maximum recursive updates exceeded&quot; warning naming the component. In production the check is compiled out and the page simply spins.</p>

<h1 id="Chapter-7-—-effectScope-owning-effects-outside-components"><a href="#Chapter-7-—-effectScope-owning-effects-outside-components" class="headerlink" title="Chapter 7 — effectScope: owning effects outside components"></a>Chapter 7 — <code>effectScope</code>: owning effects outside components</h1>
<p>Inside <code>setup()</code>, every <code>computed</code>, <code>watch</code> and <code>watchEffect</code> is collected into the component's scope and stopped on unmount. Outside a component — a shared composable, a store, a test — nothing collects them, and they leak. <code>effectScope()</code> is the public version of that collector:</p>
<pre><code class="language-ts"><figure class="highlight ts"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="ts"><span class="line"><span class="hljs-keyword">const</span> scope = <span class="hljs-title function_">effectScope</span>()</span><br><span class="line">scope.<span class="hljs-title function_">run</span>(<span class="hljs-function">() =&gt;</span> {</span><br><span class="line">  <span class="hljs-keyword">const</span> q = <span class="hljs-title function_">ref</span>(<span class="hljs-string">&#x27;&#x27;</span>)</span><br><span class="line">  <span class="hljs-title function_">watch</span>(q, search)                               <span class="hljs-comment">// collected by scope</span></span><br><span class="line">  <span class="hljs-keyword">const</span> off = <span class="hljs-title function_">listen</span>(<span class="hljs-string">&#x27;resize&#x27;</span>, onResize)</span><br><span class="line">  <span class="hljs-title function_">onScopeDispose</span>(off)                            <span class="hljs-comment">// cleanup for non-reactive resources</span></span><br><span class="line">})</span><br><span class="line">scope.<span class="hljs-title function_">stop</span>()                                     <span class="hljs-comment">// stops every effect created in run()</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Useful details:</p>
<ul>
<li><code>getCurrentScope()</code> returns the active scope, or <code>undefined</code>. A composable can use it to decide whether it is safe to register cleanup.</li>
<li><code>onScopeDispose(fn)</code> works in components too, where it is equivalent to <code>onUnmounted</code> for the setup scope. Prefer it in composables: it also works inside a standalone <code>effectScope</code>.</li>
<li><code>effectScope(true)</code> creates a <strong>detached</strong> scope that is not collected by the parent scope. Use it for state that must outlive the component that first created it.</li>
<li>Since 3.5 a scope can be paused and resumed (<code>scope.pause()</code> / <code>scope.resume()</code>), which pauses every effect it owns.</li>
</ul>
<p>The main consumer of <code>effectScope(true)</code> is the <strong>shared composable</strong>: state created by the first caller, kept alive by a detached scope, and disposed when the last caller unmounts. Post 01 builds one with reference counting.</p>

<p>Every item below was a real production bug somewhere. The fix is always the same idea: keep a <strong>reference to the container</strong> (the proxy or the ref), not a copy of the value.</p>

<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-title function_">useTitle</span>(title.<span class="hljs-property">value</span>)      <span class="hljs-comment">// passes a string snapshot</span></span><br><span class="line"><span class="hljs-title function_">useTitle</span>(title)            <span class="hljs-comment">// passes the ref</span></span><br><span class="line"><span class="hljs-title function_">useTitle</span>(<span class="hljs-function">() =&gt;</span> <span class="hljs-string">`<span class="hljs-subst">${page.value}</span> · Shop`</span>)   <span class="hljs-comment">// passes a getter</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Post 01 shows how to write composables that accept all three via <code>MaybeRefOrGetter</code> and <code>toValue()</code>.</p>
<h2 id="3-Replacing-a-reactive-object"><a href="#3-Replacing-a-reactive-object" class="headerlink" title="3. Replacing a reactive() object"></a>3. Replacing a <code>reactive()</code> object</h2>
<p><code>state = reactive({ items: fresh })</code> rebinds a local variable; the template still holds the old proxy. <code>Object.assign(state, { items: fresh })</code> mutates the same proxy and works. With a <code>ref</code>, <code>state.value = { items: fresh }</code> is reactive by design.</p>
<h2 id="4-Destructuring-props-before-35-and-stores"><a href="#4-Destructuring-props-before-35-and-stores" class="headerlink" title="4. Destructuring props (before 3.5) and stores"></a>4. Destructuring props (before 3.5) and stores</h2>
<p>Since 3.5, <code>const { count } = defineProps()</code> is compiled to <code>__props.count</code> and stays reactive (Post 01). Passing that destructured name straight to <code>watch(count, …)</code> is a <strong>compile error</strong> in 3.5; the compiler tells you to pass <code>() =&gt; count</code>. Pinia stores are <code>reactive</code> objects: <code>const { total } = useCart()</code> breaks, <code>const { total } = storeToRefs(useCart())</code> works (Post 03).</p>
<h2 id="5-Reads-after-await-identity-checks-unproxyable-objects"><a href="#5-Reads-after-await-identity-checks-unproxyable-objects" class="headerlink" title="5. Reads after await, identity checks, unproxyable objects"></a>5. Reads after <code>await</code>, identity checks, unproxyable objects</h2>
<p>Only reads before the first <code>await</code> of an effect are tracked (Chapter 5). <code>reactive([item])[0] !== item</code>, so <code>Map</code>/<code>Set</code> keys, <code>===</code> checks and <code>WeakMap</code> caches see the proxy: compare ids or <code>toRaw()</code> values. Frozen and <code>markRaw</code> objects are returned as-is, and classes with <code>#private</code> fields break through the proxy (Chapter 2): all three usually belong in a <code>shallowRef</code>.</p>
<h2 id="6-State-created-at-module-scope-in-SSR"><a href="#6-State-created-at-module-scope-in-SSR" class="headerlink" title="6. State created at module scope in SSR"></a>6. State created at module scope in SSR</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// store.js</span></span><br><span class="line"><span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> cart = <span class="hljs-title function_">reactive</span>({ <span class="hljs-attr">items</span>: [] })   <span class="hljs-comment">// one instance per server process</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>On the server, a module is evaluated once and shared by every request, so this leaks one user's cart into another user's page. Per-request state belongs in <code>app.provide</code>, Pinia (which creates a store per app instance) or Nuxt's <code>useState</code> (Post 03).</p>
<blockquote>
<p><strong>Trick:</strong> when a value &quot;stops updating&quot;, ask one question: at the moment the effect ran, did it read a <strong>proxy property or a ref's <code>.value</code></strong>? If it read a plain variable holding a copy, nothing can ever trigger it.</p>
</blockquote>

<h1 id="Chapter-9-—-Vue-and-signals"><a href="#Chapter-9-—-Vue-and-signals" class="headerlink" title="Chapter 9 — Vue and signals"></a>Chapter 9 — Vue and signals</h1>
<h2 id="Same-idea-different-surface"><a href="#Same-idea-different-surface" class="headerlink" title="Same idea, different surface"></a>Same idea, different surface</h2>
<p>A <strong>signal</strong> is a value container that tracks reads and notifies on writes. By that definition <code>shallowRef</code> is a signal, and the Vue docs compare it directly with Preact and Qwik signals. The frameworks differ mostly in API shape and in what re-runs:</p>

<p>The TC39 Signals proposal (<code>Signal.State</code>, <code>Signal.Computed</code>, <code>Signal.subtle.Watcher</code>) is at <strong>Stage 1</strong>. It standardises the graph, not the rendering. Nothing in Vue depends on it.</p>
<h2 id="Where-Vue-is-different"><a href="#Where-Vue-is-different" class="headerlink" title="Where Vue is different"></a>Where Vue is different</h2>
<ul>
<li><strong>Deep reactivity by default.</strong> <code>ref(obj)</code> makes the whole object reactive via proxies. Most signal libraries are shallow and expect immutable updates. Vue gives you both (<code>ref</code> and <code>shallowRef</code>).</li>
<li><strong>Coarse re-render in the VDOM model.</strong> In classic Vue, fine-grained tracking decides <em>which component</em> re-renders; within the component, the virtual DOM diff (helped by the compiler's patch flags, Post 02) decides what changes. Solid and Svelte 5 skip the component level and update DOM nodes directly.</li>
<li><strong>Vapor mode closes that gap.</strong> A Vapor component compiles its template into direct DOM operations, each wrapped in a small render effect, so a change to <code>count</code> updates one text node. Post 02 shows the compiled output.</li>
<li><strong>3.6's alien-signals core.</strong> The 3.6 refactor changes the engine, not the model: the same push-pull graph, a leaner implementation. The code you write in this post is unchanged.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> if you are coming from Solid or Preact, map <code>createSignal</code> to <code>shallowRef</code>, <code>createMemo</code> to <code>computed</code>, <code>createEffect</code> to <code>watchEffect</code>, and <code>createRoot</code> to <code>effectScope</code>. The model transfers directly; the deep <code>ref</code> is the only extra concept.</p>
</blockquote>

<h2 id="Exercise-1-—-Draw-the-graph"><a href="#Exercise-1-—-Draw-the-graph" class="headerlink" title="Exercise 1 — Draw the graph"></a>Exercise 1 — Draw the graph</h2>
<p>For this component, list every dep and every subscriber, then say what re-runs when <code>filter</code> changes and when one item's <code>done</code> flag changes.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> items = <span class="hljs-title function_">ref</span>([{ <span class="hljs-attr">id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">text</span>: <span class="hljs-string">&#x27;a&#x27;</span>, <span class="hljs-attr">done</span>: <span class="hljs-literal">false</span> }])</span><br><span class="line"><span class="hljs-keyword">const</span> filter = <span class="hljs-title function_">ref</span>(<span class="hljs-string">&#x27;all&#x27;</span>)</span><br><span class="line"><span class="hljs-keyword">const</span> visible = <span class="hljs-title function_">computed</span>(<span class="hljs-function">() =&gt;</span></span><br><span class="line">  filter.<span class="hljs-property">value</span> === <span class="hljs-string">&#x27;all&#x27;</span> ? items.<span class="hljs-property">value</span> : items.<span class="hljs-property">value</span>.<span class="hljs-title function_">filter</span>(<span class="hljs-function"><span class="hljs-params">i</span> =&gt;</span> i.<span class="hljs-property">done</span> === (filter.<span class="hljs-property">value</span> === <span class="hljs-string">&#x27;done&#x27;</span>)))</span><br><span class="line"><span class="hljs-comment">// template: &lt;li v-for=&quot;i in visible&quot; :key=&quot;i.id&quot;&gt;{{ i.text }}&lt;/li&gt;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p>Deps: <code>filter.value</code>, <code>items.value</code>, the array's iteration/length, and each item's <code>done</code> (only read when <code>filter</code> is not <code>'all'</code>) and <code>text</code> and <code>id</code> (read by the render). Subscribers: <code>visible</code> (reads <code>filter</code>, <code>items</code>, and <code>done</code> when filtering) and the component render (reads <code>visible.value</code>, each <code>i.text</code>, each <code>i.id</code>). Changing <code>filter</code> dirties <code>visible</code>; the render re-runs and pulls a new array. Changing <code>done</code> while <code>filter === 'all'</code> triggers nothing that reads <code>done</code> — <code>visible</code> never read it in that branch — so nothing re-renders, which is correct because nothing visible changed. With <code>filter === 'done'</code>, it dirties <code>visible</code> and the render.</p>
</details>
<h2 id="Exercise-2-—-Predict-the-log"><a href="#Exercise-2-—-Predict-the-log" class="headerlink" title="Exercise 2 — Predict the log"></a>Exercise 2 — Predict the log</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> a = <span class="hljs-title function_">ref</span>(<span class="hljs-number">0</span>)</span><br><span class="line"><span class="hljs-title function_">watch</span>(a, <span class="hljs-function">() =&gt;</span> log.<span class="hljs-title function_">push</span>(<span class="hljs-string">&#x27;pre&#x27;</span>))</span><br><span class="line"><span class="hljs-title function_">watch</span>(a, <span class="hljs-function">() =&gt;</span> log.<span class="hljs-title function_">push</span>(<span class="hljs-string">&#x27;post&#x27;</span>), { <span class="hljs-attr">flush</span>: <span class="hljs-string">&#x27;post&#x27;</span> })</span><br><span class="line"><span class="hljs-title function_">watch</span>(a, <span class="hljs-function">() =&gt;</span> log.<span class="hljs-title function_">push</span>(<span class="hljs-string">&#x27;sync&#x27;</span>), { <span class="hljs-attr">flush</span>: <span class="hljs-string">&#x27;sync&#x27;</span> })</span><br><span class="line">a.<span class="hljs-property">value</span>++; a.<span class="hljs-property">value</span>++</span><br><span class="line">log.<span class="hljs-title function_">push</span>(<span class="hljs-string">&#x27;end&#x27;</span>)</span><br><span class="line"><span class="hljs-keyword">await</span> <span class="hljs-title function_">nextTick</span>()</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p><code>sync, sync, end, pre, post</code>. The sync watcher runs inside each write (twice). The pre and post watchers are queued once each, because a queued job is not queued again, and run in the flush: pre first, then post-flush callbacks.</p>
</details>
<h2 id="Exercise-3-—-Fix-the-composable-call"><a href="#Exercise-3-—-Fix-the-composable-call" class="headerlink" title="Exercise 3 — Fix the composable call"></a>Exercise 3 — Fix the composable call</h2>
<p><code>useFormatted(price.value)</code> shows the first price forever. Fix it without changing the composable's callers more than necessary, and state what signature the composable should have.</p>
<details>
<summary>Solution</summary>
<p>Pass the ref or a getter: <code>useFormatted(price)</code> or <code>useFormatted(() =&gt; price.value)</code>. The composable should accept <code>MaybeRefOrGetter&lt;number&gt;</code> and read it with <code>toValue()</code> inside a <code>computed</code> or <code>watchEffect</code>, so the read happens inside an effect every time.</p>
</details>
<h2 id="Exercise-4-—-Choose-the-primitive"><a href="#Exercise-4-—-Choose-the-primitive" class="headerlink" title="Exercise 4 — Choose the primitive"></a>Exercise 4 — Choose the primitive</h2>
<p>For each, pick <code>ref</code>, <code>reactive</code>, <code>shallowRef</code> or <code>markRaw</code>: (a) a 50,000-row report you replace on each fetch; (b) a Mapbox map instance; (c) a login form with six fields; (d) a counter.</p>
<details>
<summary>Solution</summary>
<p>(a) <code>shallowRef</code>: no per-row proxies, and you replace rather than mutate. (b) <code>markRaw</code> (or a <code>shallowRef</code> holding it): the SDK must never be proxied. (c) <code>reactive</code> or a <code>ref</code> of an object: grouped, mutated in place, never replaced. (d) <code>ref</code>.</p>
</details>
