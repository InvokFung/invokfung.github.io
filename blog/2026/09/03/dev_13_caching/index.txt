11:T12f83,<p>A cache keeps a copy of something that was expensive to get, so the next request is fast. Caches sit everywhere between a user and your database: in the browser, on a CDN, in a reverse proxy, in your process, in Redis, and inside the database itself. This post shows what each layer is for, how HTTP cache headers really work (with <code>curl</code> demos against a tiny local server), the standard application patterns, how to invalidate safely, and how to stop a <strong>cache stampede</strong>. It ends with a Redis cache-aside example in Python.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Explain what a cache buys you and what it costs: staleness, memory, complexity.</li>
<li>Name the cache layers from browser to database, and who controls each one.</li>
<li>Write correct <code>Cache-Control</code> headers (RFC 9111): <code>max-age</code>, <code>s-maxage</code>, <code>no-cache</code> vs <code>no-store</code>, <code>private</code>, <code>public</code>, <code>immutable</code>, <code>stale-while-revalidate</code>.</li>
<li>Use <code>ETag</code> / <code>If-None-Match</code> and <code>Last-Modified</code> to get cheap <code>304 Not Modified</code> answers, and check them with <code>curl -I</code>.</li>
<li>Bust caches with content-hashed file names.</li>
<li>Use <code>functools.lru_cache</code>, and implement <strong>cache-aside</strong> with Redis or Valkey, plus TTL jitter.</li>
<li>Prevent a <strong>cache stampede</strong> with locking, request coalescing and early refresh.</li>
</ul>

<h1 id="Chapter-1-—-Why-cache-and-what-it-costs"><a href="#Chapter-1-—-Why-cache-and-what-it-costs" class="headerlink" title="Chapter 1 — Why cache, and what it costs"></a>Chapter 1 — Why cache, and what it costs</h1>
<p>Without a cache, every request pays the full price: a network round trip, a database query, a template render. With a cache, most requests pay a lookup instead. The share of requests answered from the cache is the <strong>hit ratio</strong> (<code>hits / (hits + misses)</code>). A cache with a 95% hit ratio sends only 1 request in 20 to the slow system behind it.</p>
<p>Caching is never free:</p>
<table>
<thead>
<tr>
<th>Cost</th>
<th>What goes wrong</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Staleness</strong></td>
<td>The copy is older than the truth. A user changes a price and still sees the old one.</td>
</tr>
<tr>
<td><strong>Memory</strong></td>
<td>Every copy takes RAM or disk. Full caches must <strong>evict</strong> something.</td>
</tr>
<tr>
<td><strong>Complexity</strong></td>
<td>New failure modes: invalidation bugs, stampedes, one user's page served to another.</td>
</tr>
<tr>
<td><strong>Debugging</strong></td>
<td>&quot;It works on my machine&quot; becomes &quot;it works after a hard refresh&quot;.</td>
</tr>
</tbody>
</table>
<p>A good rule: add a cache when you have measured a slow, repeated read, and you can say how stale the data is allowed to be.</p>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Hit / miss</strong> — the value was in the cache / it had to be fetched from the source (the <strong>origin</strong>).</li>
<li><strong>TTL (time to live)</strong> — how long an entry counts as fresh.</li>
<li><strong>Fresh / stale</strong> — younger / older than its TTL. Stale entries may still be used in some cases.</li>
<li><strong>Eviction</strong> — removing entries to make room, often <strong>LRU</strong> (least recently used first).</li>
<li><strong>Invalidation</strong> — removing or updating an entry because the source changed.</li>
<li><strong>Cache key</strong> — what identifies an entry: a URL, or a string like <code>product:42</code>. A <strong>cold</strong> cache is empty (just started); a <strong>warm</strong> one is full of useful entries.</li>
</ul>

<p>A request can pass many caches on its way to the data. Each one is closer to the user (faster) or closer to the data (fresher).</p>
<table>
<thead>
<tr>

<p>The database layer works on its own. MongoDB's WiredTiger engine, for example, keeps an internal cache that by default is the larger of 50% of (RAM − 1 GB) or 256 MB, and also relies on the operating system's file cache. MongoDB Course 15 · Performance Deep explains the working set and WiredTiger cache in detail. The rest of this post is about the layers you control.</p>

<h1 id="Chapter-3-—-HTTP-caching-with-Cache-Control-RFC-9111"><a href="#Chapter-3-—-HTTP-caching-with-Cache-Control-RFC-9111" class="headerlink" title="Chapter 3 — HTTP caching with Cache-Control (RFC 9111)"></a>Chapter 3 — HTTP caching with Cache-Control (RFC 9111)</h1>
<p>HTTP caching is defined by <strong>RFC 9111</strong> &quot;HTTP Caching&quot; (June 2022). It separates two ideas:</p>
<ul>
<li><strong>Freshness</strong> — &quot;may I use my copy without asking?&quot; controlled mainly by <code>Cache-Control: max-age</code>.</li>
<li><strong>Validation</strong> — &quot;my copy is stale; is it still good?&quot; done with <code>ETag</code> or <code>Last-Modified</code> (next chapter).</li>
</ul>
<p>It also separates two kinds of cache. A <strong>private cache</strong> belongs to one user (the browser). A <strong>shared cache</strong> serves many users (a CDN or proxy).</p>
<p>The response directives you will actually use:</p>
<table>
<thead>
<tr>
<th>Directive</th>
<th>Meaning</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>max-age=N</code></td>
<td>Fresh for N seconds. RFC 9111: &quot;The response is to be considered stale after its age is greater than the specified number of seconds.&quot;</td>
</tr>
<tr>
<td><code>s-maxage=N</code></td>
<td>Like <code>max-age</code>, but only for <strong>shared</strong> caches, and it overrides <code>max-age</code> there.</td>
</tr>
<tr>
<td><code>no-cache</code></td>
<td><strong>May</strong> be stored, but must be revalidated with the origin before <strong>every</strong> use. It does <em>not</em> mean &quot;do not cache&quot;.</td>
</tr>
<tr>
<td><code>no-store</code></td>
<td>Must <strong>not</strong> be stored at all, by any cache. Use it for sensitive data.</td>
</tr>
<tr>
<td><code>private</code></td>
<td>Only the user's own browser may store it; shared caches must not.</td>
</tr>
<tr>
<td><code>public</code></td>
<td>Any cache may store it, even when it normally would not (for example, a response to a request with <code>Authorization</code>).</td>
</tr>
<tr>
<td><code>must-revalidate</code></td>
<td>Once stale, never use it without a successful revalidation.</td>
</tr>
<tr>
<td><code>immutable</code></td>
<td>(RFC 8246) The body will never change while fresh, so do not even revalidate on reload.</td>
</tr>
<tr>
<td><code>stale-while-revalidate=N</code></td>
<td>(RFC 5861) After expiry, a cache may keep serving the stale copy for up to N more seconds while it refetches in the background.</td>
</tr>
<tr>
<td><code>stale-if-error=N</code></td>
<td>(RFC 5861) If the origin fails, a stale copy may be served for up to N seconds.</td>
</tr>
</tbody>
</table>
<p>Other headers you will meet:</p>
<ul>
<li><code>Age: 42</code> — added by shared caches: how many seconds the copy has been in a cache.</li>
<li><code>Expires: &lt;date&gt;</code> — the old way to say &quot;fresh until&quot;. If <code>max-age</code> is present, it wins.</li>
<li>No <code>Cache-Control</code> and no <code>Expires</code>, but a <code>Last-Modified</code>? Caches may <strong>guess</strong> a lifetime. RFC 9111 says a typical guess is 10% of the time since the last change. This is a classic source of &quot;why is this page stale?&quot;. Always send explicit headers.</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> using <code>no-cache</code> for a bank statement. The browser still writes it to disk; it just asks before showing it. For sensitive pages use <code>no-store</code> (and usually <code>private</code>).</p>
</blockquote>

<h1 id="Chapter-4-—-Validation-ETag-Last-Modified-and-304"><a href="#Chapter-4-—-Validation-ETag-Last-Modified-and-304" class="headerlink" title="Chapter 4 — Validation: ETag, Last-Modified and 304"></a>Chapter 4 — Validation: ETag, Last-Modified and 304</h1>
<p>When a cached copy is stale (or marked <code>no-cache</code>), the cache sends a <strong>conditional request</strong>:</p>
<ol>
<li>The first response carried a validator: <code>ETag: &quot;b5099f092335ab78&quot;</code> (a fingerprint of the body) and/or <code>Last-Modified: &lt;date&gt;</code>.</li>
<li>Later, the client asks <code>If-None-Match: &quot;b5099f092335ab78&quot;</code> (or <code>If-Modified-Since: &lt;date&gt;</code>).</li>
<li>If nothing changed, the server answers <strong><code>304 Not Modified</code></strong> with no body. The client reuses its copy. Only headers cross the network.</li>
</ol>
<p>An ETag starting with <code>W/</code> is a <strong>weak</strong> validator: &quot;the same meaning&quot;, not byte-for-byte equal. If both <code>If-None-Match</code> and <code>If-Modified-Since</code> arrive, <code>If-None-Match</code> wins (RFC 9110). ETags are more precise, because dates only have one-second resolution.</p>
<p><strong><code>Vary</code></strong> tells caches which request headers change the response. With <code>Vary: Accept-Encoding</code>, the gzip and brotli versions are cached separately. Be careful with <code>Vary: Cookie</code> or <code>Vary: User-Agent</code>: they split the cache into so many versions that almost nothing hits.</p>

<h2 id="Pick-a-policy-per-kind-of-content"><a href="#Pick-a-policy-per-kind-of-content" class="headerlink" title="Pick a policy per kind of content"></a>Pick a policy per kind of content</h2>
<table>
<thead>
<tr>
<th>Content</th>
<th><code>Cache-Control</code></th>
<th>Why</th>
</tr>
</thead>
<tbody>
<tr>
<td>Hashed static files (<code>app.3f9a2c1b.js</code>, fonts, images)</td>
<td><code>public, max-age=31536000, immutable</code></td>
<td>The name changes when the content changes, so the old copy can live forever.</td>

<tr>
<td>HTML pages</td>
<td><code>no-cache</code> (plus an <code>ETag</code>)</td>

<tr>

</tr>
<tr>

<td><code>private, no-cache</code> or <code>private, no-store</code></td>
<td>Must never land in a shared cache.</td>
</tr>
<tr>
<td>Secrets (statements, tokens, admin pages)</td>
<td><code>no-store</code></td>
<td>Never written anywhere.</td>
</tr>
</tbody>

<h2 id="CDNs-and-shared-caches"><a href="#CDNs-and-shared-caches" class="headerlink" title="CDNs and shared caches"></a>CDNs and shared caches</h2>
<p>A CDN is a shared cache in many cities. Three extra points:</p>
<ul>
<li>Use <code>s-maxage</code> to give the CDN a longer life than browsers: <code>Cache-Control: public, max-age=60, s-maxage=3600</code>. <strong>RFC 9213</strong> also defines <code>CDN-Cache-Control</code>, a header that only CDNs read.</li>
<li>Most CDNs offer a <strong>purge</strong> API, and many can purge by tag. The details (and support for <code>stale-while-revalidate</code>) are vendor-specific, so check your CDN's docs.</li>
<li><strong>Never let a shared cache store personal data.</strong> If <code>/account</code> is cached publicly, the next visitor sees the previous user's page. That is a Broken Access Control bug (see Dev Essentials 12 · OWASP Top 10). Mark per-user responses <code>private</code>, and be careful with any response that sets a cookie.</li>
</ul>
<h2 id="Cache-busting-with-hashed-file-names"><a href="#Cache-busting-with-hashed-file-names" class="headerlink" title="Cache busting with hashed file names"></a>Cache busting with hashed file names</h2>
<p>The long-lived policy above only works if each new version of a file gets a <strong>new URL</strong>. Build tools do this by putting a hash of the content in the file name. Next.js is a common example. Its docs say that it sets &quot;<code>public, max-age=31536000, immutable</code>&quot; for truly immutable assets, that these files &quot;contain a SHA-hash in the file name&quot;, and that this header &quot;cannot be overridden&quot;. The HTML then points to the new names, and the HTML itself is revalidated on each visit.</p>
<p>The idea in a few lines of Python:</p>

Change one byte of <code>app.js</code> and the name changes, so every cache fetches it fresh. A hash in the path beats a manual <code>?v=42</code> query string: it never needs a version bump, and some caches ignore query strings.</p>

<p>Know the limits before you use them for real data:</p>
<ul>
<li><strong>No TTL.</strong> An entry stays until it is evicted or you call <code>cache_clear()</code>. Fine for pure functions like <code>fib</code>; wrong for exchange rates.</li>
<li><strong>Arguments must be hashable.</strong> A <code>list</code> or <code>dict</code> argument raises <code>TypeError</code>.</li>
<li><strong>Shared mutable results.</strong> If the function returns a list and a caller changes it, every later caller sees the change.</li>
<li><strong>Per process.</strong> With 8 web workers you have 8 separate caches, and invalidating one does not touch the others.</li>
<li><strong>Not stampede-proof.</strong> The docs note the wrapped function may be &quot;called more than once if another thread makes an additional call before the initial call has been completed and cached&quot;. Chapter 9 measures this.</li>
</ul>

<h1 id="Chapter-7-—-Application-caching-patterns"><a href="#Chapter-7-—-Application-caching-patterns" class="headerlink" title="Chapter 7 — Application caching patterns"></a>Chapter 7 — Application caching patterns</h1>
<p>When the cache is a separate system (Redis, Valkey, Memcached), there are four classic ways to wire it to the database:</p>
<table>
<thead>
<tr>
<th>Pattern</th>
<th>Read path</th>
<th>Write path</th>
<th>Good for</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Cache-aside</strong> (lazy loading)</td>
<td>App checks cache; on miss, reads DB and fills cache</td>
<td>App writes DB, then <strong>deletes</strong> the key</td>
<td>The default choice; the cache can fail without losing data</td>
</tr>
<tr>
<td><strong>Read-through</strong></td>
<td>App asks the cache; the cache library loads from DB on a miss</td>
<td>Same as cache-aside</td>
<td>Hides loading logic in one place</td>
</tr>
<tr>
<td><strong>Write-through</strong></td>
<td>Always a hit after a write</td>
<td>App (or cache) writes cache <strong>and</strong> DB together</td>
<td>Data that is read right after it is written</td>
</tr>
<tr>
<td><strong>Write-behind</strong> (write-back)</td>
<td>Always a hit</td>
<td>Write goes to the cache; DB is updated later in batches</td>
<td>Very high write rates, if you can accept losing recent writes</td>
</tr>
</tbody>
</table>
<h2 id="TTLs"><a href="#TTLs" class="headerlink" title="TTLs"></a>TTLs</h2>
<p>Every entry should have a TTL, even if you also invalidate on writes. The TTL is your <strong>safety net</strong>: if an invalidation is missed, the wrong value lives for at most one TTL. Choose it from the business question &quot;how stale may this be?&quot;, not from performance alone. Add <strong>jitter</strong> (a small random extra) so that entries created together do not all expire together.</p>
<h2 id="Invalidation-strategies"><a href="#Invalidation-strategies" class="headerlink" title="Invalidation strategies"></a>Invalidation strategies</h2>
<ol>
<li><strong>Expire only</strong> — rely on the TTL. Simplest; data is up to one TTL old.</li>
<li><strong>Delete on write</strong> — after the DB write succeeds, <code>DEL</code> the key. The next read reloads it. Prefer delete over &quot;set the new value&quot;, because two concurrent writers can set values in the wrong order.</li>
<li><strong>Versioned keys</strong> — put a version in the key (<code>user:42:v7</code>) and bump the version on change. Old keys simply age out.</li>
<li><strong>Event-driven</strong> — the database emits change events and a worker deletes the matching keys. MongoDB Course 12 · Change Streams shows the event source.</li>
</ol>
<blockquote>
<p><strong>Watch out:</strong> cache-aside has a known race. Reader A misses and loads the old row. Writer B updates the row and deletes the key. Reader A then writes the <em>old</em> value into the cache. It stays wrong until its TTL ends. Short TTLs keep the damage small; for critical data, add a version check or do not cache.</p>
</blockquote>

<h1 id="Chapter-9-—-Cache-stampede-and-how-to-stop-it"><a href="#Chapter-9-—-Cache-stampede-and-how-to-stop-it" class="headerlink" title="Chapter 9 — Cache stampede and how to stop it"></a>Chapter 9 — Cache stampede and how to stop it</h1>
<p>A <strong>cache stampede</strong> (or thundering herd, or dog-piling) happens when a popular key expires and hundreds of requests miss at the same moment. They all run the same slow query, the database slows down, requests pile up, and the cache never gets refilled. It often follows a deploy or restart (cold cache) or a batch of keys that were all created with the same TTL.</p>
<p><code>lru_cache</code> shows the problem in miniature. With 20 threads asking for the same missing key at once, the slow function ran <strong>20 times</strong>. The fixes:</p>
<table>
<thead>
<tr>
<th>Fix</th>
<th>Idea</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Jittered TTL</strong></td>
<td><code>ttl = base + random</code> so keys created together expire at different times.</td>
</tr>
<tr>
<td><strong>Locking</strong></td>
<td>Only the request that wins a lock recomputes; the others wait briefly and read the new value (Chapter 8).</td>
</tr>
<tr>
<td><strong>Request coalescing</strong> (single-flight)</td>
<td>In one process, concurrent callers for the same key share one in-flight computation.</td>
</tr>
<tr>
<td><strong>Early refresh</strong></td>
<td>Recompute <em>before</em> expiry, so the key is never missing. Either a background job, or a random early refresh per request.</td>
</tr>
<tr>
<td><strong>Serve stale</strong></td>
<td>Keep serving the old value while one worker refreshes (the idea behind <code>stale-while-revalidate</code>).</td>
</tr>
</tbody>
</table>

<h2 id="Probabilistic-early-refresh"><a href="#Probabilistic-early-refresh" class="headerlink" title="Probabilistic early refresh"></a>Probabilistic early refresh</h2>
<p>Vattani, Chierichetti and Lowenstein (&quot;Optimal Probabilistic Cache Stampede Prevention&quot;, VLDB 2015) propose that each reader flips a biased coin. The closer the key is to expiry, and the longer the recompute takes, the more likely the reader refreshes it early:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> math, random, time</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">should_refresh_early</span>(<span class="hljs-params">expires_at: <span class="hljs-built_in">float</span>, delta: <span class="hljs-built_in">float</span>, beta: <span class="hljs-built_in">float</span> = <span class="hljs-number">1.0</span></span>) -&gt; <span class="hljs-built_in">bool</span>:</span><br><span class="line">    <span class="hljs-comment"># delta: seconds the last recompute took; beta &gt; 1 refreshes earlier</span></span><br><span class="line">    <span class="hljs-keyword">return</span> time.time() - delta * beta * math.log(<span class="hljs-number">1.0</span> - random.random()) &gt;= expires_at</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>With <code>delta = 1</code> second, a quick simulation of 10,000 readers gives about 0% refreshes 10 s before expiry, about 5% at 3 s, about 37% at 1 s and about 83% at 0.2 s. Usually one reader refreshes the key shortly before it expires, and nobody ever sees a miss. Store <code>delta</code> next to the value so every reader can use it. (<code>1.0 - random.random()</code> avoids <code>log(0)</code>.)</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Choose-the-headers"><a href="#Exercise-1-—-Choose-the-headers" class="headerlink" title="Exercise 1 — Choose the headers"></a>Exercise 1 — Choose the headers</h2>
<p>Write a <code>Cache-Control</code> value for each: (a) <code>logo.8c1f2e7a.svg</code>, (b) the home page HTML, (c) <code>GET /api/account</code> for the logged-in user, (d) a public list of exchange rates updated every minute.</p>
<details>
<summary>Solution</summary>
<p>(a) <code>public, max-age=31536000, immutable</code> — the hash in the name changes with the content. (b) <code>no-cache</code>, plus an <code>ETag</code>, so every visit revalidates and usually gets a <code>304</code>. (c) <code>private, no-store</code> (or <code>private, no-cache</code> if the data is not sensitive) — never in a shared cache. (d) <code>public, max-age=60, stale-while-revalidate=30</code>, or add <code>s-maxage=60</code> if browsers should keep it shorter than the CDN.</p>
</details>
<h2 id="Exercise-2-—-no-cache-or-no-store"><a href="#Exercise-2-—-no-cache-or-no-store" class="headerlink" title="Exercise 2 — no-cache or no-store?"></a>Exercise 2 — no-cache or no-store?</h2>
<p>A bank shows monthly statements at <code>/statements/2026-08</code>. The page is sent with <code>Cache-Control: no-cache</code>. Is that safe?</p>
<details>
<summary>Solution</summary>
<p>No. <code>no-cache</code> allows storing; it only forces revalidation before reuse. The statement can sit in the browser's disk cache on a shared computer. Use <code>Cache-Control: no-store</code> (with <code>private</code> as well for older caches).</p>
</details>
<h2 id="Exercise-3-—-Prove-the-304"><a href="#Exercise-3-—-Prove-the-304" class="headerlink" title="Exercise 3 — Prove the 304"></a>Exercise 3 — Prove the 304</h2>
<p>Using <code>cache_server.py</code>, show with <code>curl</code> that a second request for <code>/</code> can be answered with <code>304</code> and no body. Then change the body of <code>/</code> in <code>PAGES</code>, restart, and repeat with the old ETag. What happens and why?</p>
<details>
<summary>Solution</summary>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">ETAG=$(curl -sI localhost:8000/ | grep -i <span class="hljs-string">&#x27;^etag&#x27;</span> | <span class="hljs-built_in">cut</span> -d<span class="hljs-string">&#x27; &#x27;</span> -f2 | <span class="hljs-built_in">tr</span> -d <span class="hljs-string">&#x27;\r&#x27;</span>)</span><br><span class="line">curl -s -o /dev/null -w <span class="hljs-string">&quot;%{http_code} %{size_download}\n&quot;</span> -H <span class="hljs-string">&quot;If-None-Match: <span class="hljs-variable">$ETAG</span>&quot;</span> localhost:8000/</span><br><span class="line"><span class="hljs-comment"># 304 0</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>After changing the body, the server computes a new ETag from the new bytes, so the old tag no longer matches and it returns <code>200</code> with the new body. That is exactly how a revalidating cache picks up changes.</p>
</details>
<h2 id="Exercise-4-—-Find-the-invalidation-bug"><a href="#Exercise-4-—-Find-the-invalidation-bug" class="headerlink" title="Exercise 4 — Find the invalidation bug"></a>Exercise 4 — Find the invalidation bug</h2>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">update_price</span>(<span class="hljs-params">pid, cents</span>):</span><br><span class="line">    r.delete(<span class="hljs-string">f&quot;product:<span class="hljs-subst">{pid}</span>&quot;</span>)</span><br><span class="line">    db.execute(<span class="hljs-string">&quot;UPDATE products SET price_cents = ? WHERE id = ?&quot;</span>, (cents, pid))</span><br><span class="line">    db.commit()</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p>The key is deleted <strong>before</strong> the write. Between the delete and the commit, another request can miss, read the <strong>old</strong> row and put it back in the cache, where it stays for a full TTL. Also, if the update fails, the cache was cleared for nothing. Write first, commit, then delete. Keep a TTL as the safety net for the remaining race.</p>
</details>
<h2 id="Exercise-5-—-Measure-a-stampede"><a href="#Exercise-5-—-Measure-a-stampede" class="headerlink" title="Exercise 5 — Measure a stampede"></a>Exercise 5 — Measure a stampede</h2>
<p>Decorate a function that sleeps 0.3 s with <code>functools.lru_cache</code>, call it from 20 threads at once with the same argument, and count the calls. Then swap in <code>ttl_cache(seconds=60)</code> from Chapter 9.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> threading, time</span><br><span class="line"><span class="hljs-keyword">from</span> functools <span class="hljs-keyword">import</span> lru_cache</span><br><span class="line"> </span><br><span class="line">n = <span class="hljs-number">0</span></span><br><span class="line"><span class="hljs-meta">@lru_cache</span></span><br><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">slow</span>(<span class="hljs-params">x</span>):</span><br><span class="line">    <span class="hljs-keyword">global</span> n; <p>With <code>@ttl_cache(seconds=60)</code> instead of <code>@lru_cache</code>, <code>n</code> is <code>1</code>: the other 19 threads wait on the per-key lock and then read the stored value.</p>
</details>
<h2 id="Exercise-6-—-Early-refresh-odds"><a href="#Exercise-6-—-Early-refresh-odds" class="headerlink" title="Exercise 6 — Early-refresh odds"></a>Exercise 6 — Early-refresh odds</h2>
<p>In <code>should_refresh_early</code>, the chance of refreshing is <code>exp(-time_left / (delta * beta))</code>. With <code>delta = 1</code> and <code>beta = 1</code>, what is the chance 2 seconds before expiry? What does <code>beta = 2</code> do?</p>
<details>
<summary>Solution</summary>
<p><code>exp(-2) ≈ 0.135</code>, so about 13.5% of readers at that moment trigger a refresh. With <code>beta = 2</code> the chance becomes <code>exp(-1) ≈ 0.37</code>: refreshes start earlier. Larger <code>beta</code> means fewer misses but more total recomputes.</p>
</details>
