11:T11835,<p>The App Router is not &quot;React with file-based routing&quot;. It is a two-environment application model: one component tree that is split, at compile time, into a server module graph and a client module graph, glued together by a streamed wire format called the RSC payload. Most production bugs in App Router codebases (a 400 KB client bundle from one stray import, a secret that ends up in page source, a layout that &quot;does not update&quot;, a modal route that 404s on refresh) come from an inaccurate picture of where each piece of code runs and what crosses the wire. Examples target <strong>Next.js 16.3</strong> (the Active LTS line as of September 2026), with the 14 and 15 differences called out where they matter.</p>

<h1 id="Chapter-1-—-Two-component-worlds"><a href="#Chapter-1-—-Two-component-worlds" class="headerlink" title="Chapter 1 — Two component worlds"></a>Chapter 1 — Two component worlds</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>React Server Components (RSC)</strong> — a React architecture in which some components run only in a server environment (at build time or per request) and never ship their code to the browser.</li>
<li><strong>Server Component</strong> — the default for every component under <code>app/</code>. Can be <code>async</code>, can read files, databases and secrets. Cannot use state, effects, or browser APIs.</li>
<li><strong>Client Component</strong> — a component in the client module graph. Rendered to HTML on the server for the first load, then hydrated and interactive in the browser. Can use hooks and event handlers.</li>
<li><strong>RSC payload</strong> (also called the Flight payload) — the serialised result of rendering the Server Component tree: rendered output, placeholders for Client Components with references to their JavaScript, and the props passed to them.</li>
<li><strong>Hydration</strong> — React attaching event handlers and state to server-rendered HTML so it becomes interactive.</li>
<li><strong>Boundary</strong> — the point in the module graph where a server module imports a <code>'use client'</code> module.</li>
</ul>
<h2 id="Server-Components-are-not-SSR"><a href="#Server-Components-are-not-SSR" class="headerlink" title="Server Components are not SSR"></a>Server Components are not SSR</h2>
<p>SSR is an old idea: run the whole React tree on the server, emit HTML, then ship all of the same code to the browser and hydrate it. Every component exists twice, once on each side.</p>
<p>Server Components change the second half. A Server Component runs <strong>only</strong> on the server; its code is never sent to the browser, so it has nothing to hydrate. Only Client Components are both server-rendered (for the first HTML) and shipped (for hydration).</p>

<h2 id="The-first-load-pipeline"><a href="#The-first-load-pipeline" class="headerlink" title="The first-load pipeline"></a>The first-load pipeline</h2>
<p>On a first visit to a dynamic route, three things happen in order:</p>
<ol>
<li><strong>RSC render.</strong> The server renders the Server Component tree. Wherever it meets a Client Component, it does not run it; it writes a placeholder plus a module reference and the serialised props. The result is the RSC payload.</li>
<li><strong>SSR of the client parts.</strong> The server then renders the Client Components to HTML, using the payload as input, so the first response is complete HTML.</li>
<li><strong>Browser.</strong> The HTML paints immediately (non-interactive). The client JavaScript loads, React reads the payload (inlined in the HTML) to reconcile the tree, and hydrates only the Client Components.</li>
</ol>
<p>On a later <strong>client navigation</strong>, step 2 and the HTML are skipped. The router fetches only the RSC payload for the segments that change and merges it into the existing tree.</p>
<blockquote>
<p><strong>Trick:</strong> when asking &quot;does this code run in the browser?&quot;, ignore the file name and folder. Follow the imports from the nearest <code>'use client'</code> file. That is the only rule the bundler uses.</p>
</blockquote>

<h1 id="Chapter-2-—-The-use-client-boundary"><a href="#Chapter-2-—-The-use-client-boundary" class="headerlink" title="Chapter 2 — The 'use client' boundary"></a>Chapter 2 — The <code>'use client'</code> boundary</h1>
<h2 id="What-the-directive-actually-marks"><a href="#What-the-directive-actually-marks" class="headerlink" title="What the directive actually marks"></a>What the directive actually marks</h2>
<p><code>'use client'</code> marks a <strong>module entry point into the client graph</strong>. It does not mark a single component, and it is not a runtime switch. From react.dev: the directive marks the module <strong>and all of its transitive dependencies</strong> as client code. When a server module imports that file, the import is the boundary.</p>
<p>Consequences that surprise people:</p>
<ul>
<li>You only need <code>'use client'</code> at the entry points. A file imported only by client modules is client code even without the directive.</li>
<li>Every module a client entry imports is bundled for the browser, including utilities you meant to keep server-side. One <code>import { db } from '@/lib/db'</code> in a client file tries to put your database driver in the bundle.</li>
<li>A component can still be client-evaluated without the directive, simply because a client module imported it.</li>
<li>The directive must be the first statement (comments allowed), with single or double quotes, never backticks.</li>
</ul>

<h2 id="Context-providers"><a href="#Context-providers" class="headerlink" title="Context providers"></a>Context providers</h2>
<p>React context needs state, so a provider is a Client Component. The usual pattern is a thin client wrapper that takes <code>children</code>:</p>
<pre><code class="language-tsx"><figure class="highlight tsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="tsx"><span class="line"><span class="hljs-comment">// app/providers.tsx</span></span><br><span class="line"><span class="hljs-string">&#x27;use client&#x27;</span></span><br><span class="line"><span class="hljs-keyword">import</span> { <span class="hljs-title class_">ThemeProvider</span> } <span class="hljs-keyword">from</span> <span class="hljs-string">&#x27;some-theme-lib&#x27;</span></span><br><span class="line"><span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">Providers</span>(<span class="hljs-params">{ children }: { children: React.ReactNode }</span>) {</span><br><span class="line">  <span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">ThemeProvider</span> <span class="hljs-attr">attribute</span>=<span class="hljs-string">&quot;class&quot;</span>&gt;</span>{children}<span class="hljs-tag">&lt;/<span class="hljs-name">ThemeProvider</span>&gt;</span></span></span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The root layout stays a Server Component and renders <code>&lt;Providers&gt;{children}&lt;/Providers&gt;</code>. The pages under it stay Server Components, because they arrive as <code>children</code> (a slot), not as imports of the provider file.</p>
<blockquote>
<p><strong>Common pitfall:</strong> putting <code>'use client'</code> at the top of <code>app/layout.tsx</code> &quot;to make the error go away&quot;. Every page is still passed as <code>children</code>, so pages are not converted, but everything the layout imports becomes client code, and the layout can no longer read cookies or data on the server. Push the directive down to the smallest interactive leaf.</p>
</blockquote>
<p>A library component that uses hooks but ships no <code>'use client'</code> fails when rendered from a Server Component. Re-export it from your own client file: a <code>components/carousel.tsx</code> containing <code>'use client'</code> and <code>export { Carousel } from 'acme-carousel'</code>.</p>
<h2 id="Guarding-the-graphs-server-only-and-client-only"><a href="#Guarding-the-graphs-server-only-and-client-only" class="headerlink" title="Guarding the graphs: server-only and client-only"></a>Guarding the graphs: <code>server-only</code> and <code>client-only</code></h2>
<p>Nothing stops a developer from importing a data module into a client file by accident. Poison the module instead:</p>
<pre><code class="language-ts"><figure class="highlight ts"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="ts"><span class="line"><span class="hljs-comment">// data/products.ts</span></span><br><span class="line"><span class="hljs-keyword">import</span> <span class="hljs-string">&#x27;server-only&#x27;</span>   <span class="hljs-comment">// build error if this module ever enters the client graph</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Next.js handles <code>server-only</code> and <code>client-only</code> internally, so the import works even without installing the npm package (install it anyway if a lint rule flags extraneous imports).</p>
<blockquote>
<p><strong>Watch out:</strong> <code>'use server'</code> is <strong>not</strong> the opposite of <code>'use client'</code>. It marks Server Functions (callable endpoints, Post 01), not Server Components. A Server Component needs no directive at all. Adding <code>'use server'</code> to a component file turns every export into a public POST endpoint.</p>
</blockquote>

<p>Practical effects:</p>
<ul>
<li>An ORM row that is a class instance (with methods, getters, or a custom prototype) fails. Map it to a plain object first.</li>
<li><code>onClick={() =&gt; …}</code> from a Server Component fails. The handler must live in the client file, or be a Server Function passed as <code>action</code>.</li>
<li>A <code>Date</code> arrives as a <code>Date</code>, a <code>Map</code> as a <code>Map</code>. JSON is not the format; the payload has richer encodings.</li>
</ul>

<h2 id="Everything-you-pass-is-public"><a href="#Everything-you-pass-is-public" class="headerlink" title="Everything you pass is public"></a>Everything you pass is public</h2>
<p>The payload is delivered to the browser. Every prop you give a Client Component is readable in page source or in the network panel, <strong>including fields the component never renders</strong>.</p>
<pre><code class="language-tsx"><figure class="highlight tsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="tsx"><span class="line"><span class="hljs-comment">// BAD: the whole user row (email, password hash, internal flags) is now in the page</span></span><br><span class="line"><span class="hljs-keyword">const</span> user = <span class="hljs-keyword">await</span> db.<span class="hljs-property">user</span>.<span class="hljs-title function_">findUnique</span>({ <span class="hljs-attr">where</span>: { id } })</span><br><span class="line"><span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">ProfileCard</span> <span class="hljs-attr">user</span>=<span class="hljs-string">{user}</span> /&gt;</span></span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// GOOD: pass a minimal object built for the UI</span></span><br><span class="line"><span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">ProfileCard</span> <span class="hljs-attr">user</span>=<span class="hljs-string">{{</span> <span class="hljs-attr">name:</span> <span class="hljs-attr">user.name</span>, <span class="hljs-attr">avatarUrl:</span> <span class="hljs-attr">user.avatarUrl</span> }} /&gt;</span></span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Next.js recommends a server-only <strong>Data Access Layer</strong> that returns minimal Data Transfer Objects, and offers React's taint APIs (<code>experimental_taintObjectReference</code>, <code>experimental_taintUniqueValue</code>, behind <code>experimental.taint</code>) as a second line of defence. Post 01 builds the DAL; Post 03 covers the environment-variable side of leaks.</p>
<blockquote>
<p><strong>Watch out:</strong> broad prop types make leaks easy. A client component typed <code>({ user }: { user: User })</code>, where <code>User</code> is the database type, invites callers to pass the full row. Type client props as the narrow shape the component renders.</p>
</blockquote>

<h1 id="Chapter-4-—-The-RSC-payload"><a href="#Chapter-4-—-The-RSC-payload" class="headerlink" title="Chapter 4 — The RSC payload"></a>Chapter 4 — The RSC payload</h1>
<h2 id="What-it-contains"><a href="#What-it-contains" class="headerlink" title="What it contains"></a>What it contains</h2>
<p>From the Next.js glossary, the payload carries three things:</p>
<ol>
<li>The rendered result of the Server Components (host elements such as <code>div</code> and <code>h1</code>, with their props and text).</li>
<li>Placeholders where Client Components should render, with references to their JavaScript chunks.</li>
<li>The props passed from Server Components to Client Components.</li>
</ol>
<p>It is a streamed, line-oriented format, not one JSON document. Rows can arrive out of order: a Suspense boundary's content is written as a later row that fills a hole left earlier. That is what makes streaming work for client navigations as well as for HTML.</p>
<h2 id="Where-to-see-it"><a href="#Where-to-see-it" class="headerlink" title="Where to see it"></a>Where to see it</h2>
<ul>
<li><strong>First load:</strong> the payload is inlined in the HTML as a series of <code>&lt;script&gt;</code> tags that push chunks into <code>self.__next_f</code>. React on the client reads them to hydrate without a second request.</li>
<li><strong>Client navigation:</strong> the router requests the target URL with an <code>RSC: 1</code> request header (and a <code>_rsc</code> query parameter so caches do not mix it with the HTML response). The response body is the payload for the segments that change.</li>
<li><strong>Static export:</strong> each route's payload is written as a file next to its HTML. This blog is a Next.js 14 static export, and with <code>trailingSlash: true</code> each post folder holds an <code>index.html</code> and an <code>index.txt</code>; the <code>.txt</code> is the payload fetched when you navigate to the post from another page.</li>
</ul>
<h2 id="Why-its-size-matters"><a href="#Why-its-size-matters" class="headerlink" title="Why its size matters"></a>Why its size matters</h2>
<p>The payload is not free:</p>
<ul>
<li>Data passed to Client Components appears <strong>twice</strong> on first load: once rendered in the HTML, once as props in the inlined payload. A 300 KB JSON prop costs roughly 600 KB before compression.</li>
<li>Server Component output is also in the payload (it has to be, to reconcile). A long server-rendered list is sent as HTML and again as payload rows.</li>
<li>Deserialisation costs CPU. Next.js 16.2 shipped a React change that made payload deserialisation up to 350% faster by replacing a <code>JSON.parse</code> reviver callback (which crosses the C++/JavaScript boundary in V8 for every key) with a plain <code>JSON.parse</code> followed by a walk in JavaScript. The Next.js team reports 25% to 60% faster rendering to HTML in real apps, depending on payload size. To find bloat, filter the network panel by <code>_rsc</code> and read the response: whole database rows are the usual find.</li>
</ul>

<p>A folder named <code>@slot</code> becomes a prop of the parent layout, rendered alongside <code>children</code>:</p>
<pre><code class="language-tsx"><figure class="highlight tsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="tsx"><span class="line"><span class="hljs-comment">// app/dashboard/layout.tsx</span></span><br><span class="line"><span class="hljs-keyword">export</span> <span class="hljs-keyword">default</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">Layout</span>(<span class="hljs-params">{ children, team, analytics }: {</span><br><span class="line">  children: React.ReactNode; team: React.ReactNode; analytics: React.ReactNode</span><br><span class="line">}</span>) {</span><br><span class="line">  <span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;&gt;</span>{children}<span class="hljs-tag">&lt;<span class="hljs-name">div</span> <span class="hljs-attr">className</span>=<span class="hljs-string">&quot;cols&quot;</span>&gt;</span>{team}{analytics}<span class="hljs-tag">&lt;/<span class="hljs-name">div</span>&gt;</span><span class="hljs-tag">&lt;/&gt;</span></span></span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Each slot navigates independently and can have its own <code>loading.tsx</code> and <code>error.tsx</code>. On a soft navigation, a slot with no match for the new URL keeps its current content. On a hard load (refresh), Next.js cannot know that previous state, so it renders the slot's <code>default.tsx</code>, or a 404 if there is none.</p>
<p><strong>Next.js 16 made this strict:</strong> every parallel-route slot must have an explicit <code>default.js</code>, and the build fails without one. To keep the old behaviour, add a <code>default.tsx</code> that returns <code>null</code> or calls <code>notFound()</code>.</p>
<h2 id="Intercepting-routes-and-the-modal-pattern"><a href="#Intercepting-routes-and-the-modal-pattern" class="headerlink" title="Intercepting routes and the modal pattern"></a>Intercepting routes and the modal pattern</h2>
<p>Intercepting routes render another route's content inside the current layout on a <strong>soft</strong> navigation, while a hard load of the same URL shows the full page. Prefixes are relative to <strong>route segments</strong> (not the file system, so <code>@slot</code> folders do not count): <code>(.)</code> same level, <code>(..)</code> one level up, <code>(..)(..)</code> two levels up, <code>(...)</code> from the root.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="text"><span class="line">app/</span><br><span class="line">  layout.tsx                 renders {children} and {modal}</span><br><span class="line">  @modal/</span><br><span class="line">    default.tsx              returns null (required in 16)</span><br><span class="line">    (.)photo/[id]/page.tsx   the modal version, shown on soft navigation</span><br><span class="line">  photo/[id]/page.tsx        the full page, shown on refresh or shared link</span><br><span class="line">  page.tsx                   the gallery with &lt;Link href=&quot;/photo/1&quot;&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Clicking a thumbnail opens the modal with the gallery still behind it and the URL set to <code>/photo/1</code>. Refreshing shows the full photo page. Closing the modal is <code>router.back()</code>.</p>
<blockquote>
<p><strong>Common pitfall:</strong> forgetting <code>@modal/default.tsx</code>. Before 16 the symptom was a 404 on refresh of unrelated routes; in 16 the build fails, which is the better failure.</p>
</blockquote>

<h1 id="Chapter-6-—-Navigation-and-prefetching"><a href="#Chapter-6-—-Navigation-and-prefetching" class="headerlink" title="Chapter 6 — Navigation and prefetching"></a>Chapter 6 — Navigation and prefetching</h1>
<h2 id="Soft-navigation-and-partial-rendering"><a href="#Soft-navigation-and-partial-rendering" class="headerlink" title="Soft navigation and partial rendering"></a>Soft navigation and partial rendering</h2>
<p><code>&lt;Link&gt;</code> and <code>router.push()</code> perform a <strong>soft navigation</strong>: no document reload, only the RSC payload for the segments that differ. Layouts shared by the old and new route are not re-rendered, so their client state (an open sidebar, a scroll position inside it, an input's value) survives. This is <strong>partial rendering</strong>.</p>
<p>It has a security-relevant side effect: a check written in a shared layout does <strong>not</strong> re-run when the user navigates between its child pages. Put authorisation checks next to the data they protect (Post 03).</p>
<p><code>router.refresh()</code> re-requests the current route's payload from the server and merges it, preserving client state. It is the tool for &quot;server data changed, redraw without losing the form input&quot;.</p>
<h2 id="prefetching"><a href="#prefetching" class="headerlink" title="&lt;Link> prefetching"></a><code>&lt;Link&gt;</code> prefetching</h2>

<h1 id="Chapter-7-—-Failure-modes-worth-recognising"><a href="#Chapter-7-—-Failure-modes-worth-recognising" class="headerlink" title="Chapter 7 — Failure modes worth recognising"></a>Chapter 7 — Failure modes worth recognising</h1>
<h2 id="Hydration-mismatches"><a href="#Hydration-mismatches" class="headerlink" title="Hydration mismatches"></a>Hydration mismatches</h2>
<p>The HTML rendered on the server must match the first client render. Classic causes:</p>
<ul>
<li><code>Date.now()</code>, <code>new Date().toLocaleString()</code>, <code>Math.random()</code> rendered directly (server and browser disagree on time, locale and randomness).</li>
<li><code>typeof window !== 'undefined'</code> branches in render.</li>
<li>Invalid HTML nesting (<code>&lt;div&gt;</code> inside <code>&lt;p&gt;</code>), which the browser's parser rewrites.</li>
<li>Browser extensions injecting attributes into <code>&lt;html&gt;</code> or <code>&lt;body&gt;</code>.</li>
</ul>
<p>Fixes: compute the value on the server and pass it down; move browser-only values into <code>useEffect</code> and render a placeholder first; for a single known-unstable text node (a timestamp), <code>suppressHydrationWarning</code> on that element. Next.js 16.2's error overlay labels the diff with <code>+ Client</code> / <code>- Server</code>, which makes the source obvious.</p>
<h2 id="My-layout-does-not-update"><a href="#My-layout-does-not-update" class="headerlink" title="&quot;My layout does not update&quot;"></a>&quot;My layout does not update&quot;</h2>
<p>A layout is not re-rendered on navigation between its children (partial rendering). If it shows data that a child action changed, call <code>router.refresh()</code>, revalidate in a Server Action (Post 01), or move the data into the page.</p>
<h2 id="Bundle-bloat-and-browser-only-widgets"><a href="#Bundle-bloat-and-browser-only-widgets" class="headerlink" title="Bundle bloat and browser-only widgets"></a>Bundle bloat and browser-only widgets</h2>
<p>A <code>'use client'</code> file that imports a large library (a markdown parser, a date library with all locales) pulls it into the browser even if the component uses it for one string: do that work in a Server Component and pass the result down (Post 03 covers the bundle analyzer). For a widget that touches <code>window</code> at import time, <code>dynamic(() =&gt; import('./chart'), { ssr: false })</code> must be called from a <code>'use client'</code> file; since Next.js 15, <code>ssr: false</code> is not allowed in Server Components.</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Find-the-boundary"><a href="#Exercise-1-—-Find-the-boundary" class="headerlink" title="Exercise 1 — Find the boundary"></a>Exercise 1 — Find the boundary</h2>
<p>Given this graph, list every module that ends up in the client bundle: <code>page.tsx</code> (server) imports <code>Header.tsx</code> and <code>Cart.tsx</code>; <code>Cart.tsx</code> starts with <code>'use client'</code> and imports <code>format.ts</code> and <code>Badge.tsx</code>; <code>Header.tsx</code> imports <code>Badge.tsx</code>; <code>Badge.tsx</code> has no directive.</p>
<details>
<summary>Solution</summary>
<p>Client bundle: <code>Cart.tsx</code>, <code>format.ts</code>, <code>Badge.tsx</code>. <code>Cart.tsx</code> is a client entry, and everything it imports transitively is client code. <code>Badge.tsx</code> also stays a Server Component when <code>Header.tsx</code> (server) renders it: the same module can be evaluated in both graphs. <code>page.tsx</code> and <code>Header.tsx</code> are server-only.</p>
</details>
<h2 id="Exercise-2-—-Fix-the-serialisation-error"><a href="#Exercise-2-—-Fix-the-serialisation-error" class="headerlink" title="Exercise 2 — Fix the serialisation error"></a>Exercise 2 — Fix the serialisation error</h2>
<p>A Server Component renders <code>&lt;PriceChart series={rows} onPointClick={(p) =&gt; console.log(p)} /&gt;</code> where <code>rows</code> comes from an ORM that returns class instances. List both errors and fix them.</p>
<details>
<summary>Solution</summary>
<p>(1) <code>onPointClick</code> is a plain function, which cannot be serialised. Move the handler into the client component (or pass a Server Function if it must run on the server). (2) Class instances are not serialisable. Map to plain objects: <code>rows.map(r =&gt; ({ t: r.timestamp, v: Number(r.value) }))</code>. Also check the mapped shape contains only what the chart draws.</p>
</details>

<h2 id="Exercise-4-—-Modal-route"><a href="#Exercise-4-—-Modal-route" class="headerlink" title="Exercise 4 — Modal route"></a>Exercise 4 — Modal route</h2>
<p>Build the file tree for a <code>/login</code> modal that opens over any page on soft navigation and shows a full login page on refresh. The app uses Next.js 16.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="text"><span class="line">app/</span><br><span class="line">  layout.tsx               ({ children, auth }) =&gt; &lt;&gt;{children}{auth}&lt;/&gt;</span><br><span class="line">  @auth/default.tsx        export default function Default() { return null }</span><br><span class="line">  @auth/(.)login/page.tsx  &lt;Modal&gt;&lt;LoginForm /&gt;&lt;/Modal&gt;</span><br><span class="line">  login/page.tsx           &lt;LoginForm /&gt; as a full page</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Exercise-5-—-Predict-the-error-boundary"><a href="#Exercise-5-—-Predict-the-error-boundary" class="headerlink" title="Exercise 5 — Predict the error boundary"></a>Exercise 5 — Predict the error boundary</h2>
<p><code>app/shop/layout.tsx</code> throws during render. There is an <code>app/shop/error.tsx</code> and an <code>app/error.tsx</code>. Which one renders, and why?</p>
<details>
<summary>Solution</summary>
<p><code>app/error.tsx</code>. The boundary from <code>app/shop/error.tsx</code> sits <strong>inside</strong> <code>app/shop/layout.tsx</code>, so it cannot catch errors from that layout. The next boundary outward is the root segment's <code>error.tsx</code>.</p>
</details>

<td>Marks Server Functions (endpoints), not Server Components</td>

<td>Client Component; does not catch its own segment's layout</td>
