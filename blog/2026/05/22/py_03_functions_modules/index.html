Python Course — 03 · Functions, Scope, Modules, and Packages

Created2026-05-22|Updated2026-05-21|Programming
|Post View:

Functions are how you turn 50 lines of scripted code into reusable building blocks. Modules and packages are how you split a 500-line file into a project. This post covers everything you need to write professional-shaped Python: def, argument styles, scope, lambda, modules, packages, import, and pip-installable libraries.

Series map: 00 Setup → 01 Syntax → 02 Data Structures → 03 Functions & Modules (this post) → 04 OOP → 05 Files & Exceptions → (future).

Learning Outcome

  • Define functions with positional, keyword, default, *args, **kwargs.
  • Understand scope (LEGB rule) and the global / nonlocal keywords.
  • Use lambda for short anonymous functions.
  • Organise code into modules + packages with __init__.py.
  • Use import, from ... import, and aliasing.
  • Understand if __name__ == "__main__".
  • Install and use third-party packages from PyPI.

Chapter 2 — Variadic arguments

Inside the function, nums is a tuple.

**kwargs — extra keyword args

Inside, options is a dict.

Combining everything

Order: positional → *args → keyword-only → **kwargs.

Keyword-only and positional-only

  • Before / — must be positional.
  • After * — must be keyword.

Trick: using * to force keyword-only args (def f(*, debug=False)) prevents callers from passing True mysteriously without context. Great for boolean flags.

Chapter 3 — Scope (LEGB rule)

When Python looks up a name, it checks in this order:

  1. Local — inside the current function.
  2. Enclosing — outer functions (if nested).
  3. Global — at the module's top level.
  4. Built-in — print, len, etc.

Modifying outer scope

global and nonlocal are escape hatches. Prefer returning values to mutating outer state.

Chapter 6 — The if __name__ == "__main__" block

When you run python script.py, Python sets __name__ == "__main__" inside that file. When you import script from elsewhere, __name__ == "script".

This lets the file be both importable (no side effects on import) and runnable (executes when run directly).

Trick: every executable script should have this block. Tests and other modules can then import its functions without triggering the whole script.

Chapter 9 — Function design tips

  1. One purpose per function. If you can't name it cleanly, it does too much.
  2. Return values, don't print (except for genuinely user-facing functions). Lets the caller decide what to do.
  3. Keep parameter count low. 5+ args = it's time to wrap them in a dataclass or dict.
  4. Document with a docstring. Even one line beats nothing.
  5. Avoid hidden side effects. A function called calculate_total shouldn't write to the DB.

Where I got stuck: I once wrote a 200-line function that did 12 things. Refactoring it to 12 small functions took 30 minutes and the test failures dropped 80% because each piece was independently testable.
