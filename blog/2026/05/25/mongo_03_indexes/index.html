MongoDB Course ??03 · Indexes ??Single, Compound, Multikey, Text, Geo, TTL, Wildcard, Hashed

Created2026-05-25|Updated2026-05-25|Database > MongoDB
|Post View:

An index is a B-tree (or specialised structure) on one or more fields that lets MongoDB find documents without scanning the whole collection. Indexes turn a 60-second query into a 5-millisecond one ??and turn an undertuned cluster into a poorly-running mess if used wrong (too many, too wide, wrong order). This post covers every index type, the ESR rule (Equality, Sort, Range) for compound-index ordering, partial / sparse / TTL / wildcard / hashed variants, index intersection, covered queries, and the build options (background, unique, collation).

Learning Outcome

  • Create single-field, compound, multikey, text, geospatial, hashed indexes.
  • Apply the ESR rule to compound index ordering.
  • Use partial, sparse, TTL, wildcard, unique indexes correctly.
  • Recognise covered queries.
  • Understand index intersection and when not to rely on it.
  • List, hint, drop, hide indexes.
  • Build indexes in production without downtime.

Chapter 1 ??Index basics

Every MongoDB collection has at least one index ??on _id (unique, auto-created, can't drop). All others are user-created.

Naming: auto-generated as <field>_<dir> joined by _. Use { name: "my_idx" } option for custom.

Cost trade-off

  • Indexes speed reads that filter / sort / project on indexed fields.
  • Indexes slow writes ??every insert / update / delete must update every relevant index.
  • Indexes use RAM ??frequently accessed parts of indexes must fit in the WiredTiger cache for speed (Post 15).
  • Indexes use disk ??typically 10-30% of collection data size each.

Rule: index for the queries you actually run, drop indexes never used (Post 04 covers $indexStats to find unused).

Chapter 2 ??Single-field index

The simplest:

Direction (1 vs -1) doesn't matter for a single-field index ??the B-tree can be walked either way. It matters for compound indexes when sorting on multiple fields.

Chapter 3 ??Compound index + the ESR rule

A compound index is on multiple fields:

The order of fields in the index matters enormously. The ESR rule:

E ??Equality fields first.
S ??Sort fields second.
R ??Range fields last.

Why: B-trees can serve range scans only on the trailing indexed prefix once equality fields have been matched. Out-of-order indexes do partial work then full scans.

Example

Query: "Most recent paid orders for user 1, sorted desc by date."

Best index:

The index serves:

  • find({ user_id: 1 }) ??uses prefix.
  • find({ user_id: 1, status: "paid" }) ??uses prefix.
  • find({ user_id: 1 }).sort({ at: -1 }) ??equality + sort.
  • find({ user_id: 1, status: "paid", at: { $gte: D } }).sort({ at: -1 }) ??full use.

Doesn't serve:

  • find({ status: "paid" }) ??user_id is the prefix; can't skip it.
  • find({ user_id: 1 }).sort({ status: 1 }) ??sort doesn't match index order.

Prefix rule

A compound index { a: 1, b: 1, c: 1 } can serve:

  • { a }
  • { a, b }
  • { a, b, c }

But not:

  • { b } alone ??a is the required prefix.

Trick: if you frequently query by b alone, you need a separate index { b: 1 }. Don't try to make one mega-index do everything.

Direction matters for sort

Index { at: 1, user_id: 1 }:

  • .sort({ at: 1, user_id: 1 }) ??uses it directly.
  • .sort({ at: -1, user_id: -1 }) ??uses it in reverse scan (also OK).
  • .sort({ at: 1, user_id: -1 }) ??can't use it (mixed direction).

Build the index to match your most common sort direction.

Chapter 4 ??Multikey index (arrays)

When indexed field is an array, MongoDB creates one index entry per array element. This is called a multikey index ??automatic, no special syntax.

Limits:

  • Only one array field in a compound multikey index. { tags: 1, scores: 1 } where both are arrays is forbidden (would explode entries quadratically).
  • Multikey indexes are larger than single-value indexes.

For arrays of sub-documents, use full-path field names:

Chapter 5 ??Text index

One text index per collection. Use only when "real" search (Atlas Search, Lucene, ES) isn't available. Coverage of operators in Post 02 Chapter 6.

Chapter 6 ??Geospatial index

Required for $near, $geoWithin, $geoIntersects on GeoJSON points/polygons. Post 02 Chapter 8.

Chapter 7 ??Hashed index

Used for:

  • Sharding with a hashed shard key ??distributes writes evenly (Post 11).
  • Equality lookups on fields where you don't need range queries.

Doesn't support range queries ($gt, etc.). Don't combine with sort on the hashed field.

Chapter 8 ??Partial index ??index only some documents

The index contains only docs where active: true. Queries that include active: true can use it; others can't.

Use cases:

  • Index only "open" tickets / "active" users / non-deleted records ??smaller index, faster builds.
  • Conditional uniqueness (next).

Chapter 9 ??Sparse index ??index only docs that have the field

Skips documents missing the field entirely. Smaller index when the field is optional.

Partial vs sparse:

  • Sparse ??only checks field presence.
  • Partial ??checks arbitrary partialFilterExpression.

Partial is the modern superset. New work: use partial.

Chapter 10 ??Unique index

Attempts to insert a duplicate raise E11000 duplicate key error.

Unique + partial ??conditional uniqueness

Common pattern: soft-deleted users may share an email with a new active user.

Unique + multikey

{ tags: 1 } unique applies per array element across documents ??usually not what you want. Use a separate dedicated collection for tag uniqueness.

Chapter 11 ??TTL index ??auto-delete after N seconds

A background thread deletes documents whose indexed date is older than expireAfterSeconds ago. Runs roughly every 60 s ??TTL is approximate, not exact.

Field must be a Date (or array of Dates ??uses earliest).

Common uses:

  • Sessions, OTP codes, password-reset tokens.
  • Short-term caches.
  • Rate-limit counters.

To expire at a specific instant: store the desired expiry timestamp directly, set expireAfterSeconds: 0:

Watch out: TTL deletes generate write load + replication traffic ??a large TTL cleanup spike can saturate a small instance.

Chapter 12 ??Wildcard index ??index unknown fields

Useful when documents have heterogeneous / unknown fields and the app queries arbitrary attributes ??common in multi-tenant SaaS where each tenant has custom fields.

Costs: big indexes, expensive writes. Reach for only when access patterns truly vary.

Chapter 13 ??Covered queries

A query is covered when:

  1. Every queried field is in an index.
  2. Every projected field is in the same index.
  3. Query doesn't return _id unless _id is in the index.

Covered queries return results straight from the index ??no document fetch ??extremely fast.

explain() (Post 04) shows IXSCAN with no following FETCH stage when a query is covered.

Chapter 14 ??Index intersection (use sparingly)

MongoDB can intersect two single-field indexes to satisfy a multi-field query, but it's usually slower than a single compound index that matches the query.

Rule: design compound indexes for the queries you run, not single-field per-column indexes.

Chapter 15 ??Build options

Build in background (5.0+: always)

Index builds since 5.0 use a hybrid foreground/background protocol that doesn't block writes. No special flag needed. (Older versions used { background: true } ??still accepted, no-op.)

Collation ??case + locale-aware

Without matching collation on the query, the index is not used.

Hiding (test removal without dropping)

Safe pattern for "is this index needed?": hide for a week, observe query performance, drop if no regression.

Chapter 16 ??Production rules of thumb

  1. Index every field used in a frequent filter, sort, or join. Not more.
  2. Compound indexes follow ESR.
  3. Sort direction in the index matches your most common sort.
  4. Use partial indexes to shrink indexes for filtered subsets (active users, open tickets).
  5. Use TTL for inherently temporary data.
  6. Index size + frequently-accessed entries should fit in RAM ??Post 15.
  7. Drop unused indexes ??$indexStats shows usage (Post 04).
  8. Build new indexes in off-peak windows for large collections, even with hybrid background builds ??backfill is I/O heavy.
  9. Don't index every field "just in case" ??write amplification + RAM waste.
  10. Test with explain() before shipping any new query ??Post 04.

Practice Exercises

Exercise 1 ??Create + verify

In the shop dataset, create an index on users.email and confirm with getIndexes().

Exercise 2 ??ESR design

Given query find({ user_id, status: "paid" }).sort({ at: -1 }), design the compound index. Explain why each field is in its position.

Answer

{ user_id: 1, status: 1, at: -1 }. user_id and status are equality ??first two. at is sort + range candidate ??last. Direction -1 matches the desc sort.
