<h1 id="Chapter-1-—-What-MongoDB-is"><a href="#Chapter-1-—-What-MongoDB-is" class="headerlink" title="Chapter 1 — What MongoDB is"></a>Chapter 1 — What MongoDB is</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>MongoDB</strong> — distributed document database; open-source core + commercial Atlas service.</li>
<li><strong>Document</strong> — a BSON object: ordered key-value pairs, nested arrays + sub-documents. Conceptually a JSON object with extra types (ObjectId, Date, Binary, Decimal128).</li>
<li><strong>Collection</strong> — a group of documents (analogous to a SQL table; no enforced schema by default).</li>
<li><strong>Database</strong> — a group of collections.</li>
<li><strong>BSON</strong> — Binary JSON, the on-disk + on-wire format. Adds types JSON lacks (ObjectId, Date, Binary, etc.) and length-prefixes for fast traversal.</li>
<li><strong><code>_id</code></strong> — every document has one. Auto-generated <code>ObjectId</code> (12 bytes: timestamp + machine + pid + counter) unless you supply your own.</li>
<li><strong>Replica set</strong> — a group of <code>mongod</code> processes that maintain the same data; provides HA + read scaling.</li>
<li><strong>Sharded cluster</strong> — multiple replica sets partitioned by a shard key; provides horizontal write scaling.</li>
</ul>

<td>Foreign key</td>
<td>Reference (manual or <code>$lookup</code>)</td>
</tr>
<tr>
<td>Join</td>
<td><code>$lookup</code> aggregation stage</td>
</tr>
<tr>
<td>Schema enforced by DDL</td>
<td>Optional schema validation (<code>$jsonSchema</code>)</td>
</tr>
<tr>
<td>Transactions</td>
<td>Multi-document transactions (since 4.0)</td>
</tr>
<tr>
<td>Index</td>
<td>Index (B-tree, hashed, text, geo, vector)</td>
</tr>
</tbody>
</table>
<p>The shift in thinking:</p>
<ul>
<li>Relational: normalise first, denormalise for performance.</li>
<li>Document: <strong>denormalise first</strong> (embed related data) for read locality; reference only when reuse + size dictate.</li>
</ul>
<p>Post 07 (Schema Design) covers this decision deeply.</p>
<h2 id="When-MongoDB-fits"><a href="#When-MongoDB-fits" class="headerlink" title="When MongoDB fits"></a>When MongoDB fits</h2>
<ul>
<li>Document-shaped data (catalogue items, user profiles, content items).</li>
<li>High write throughput with sharding.</li>
<li>Flexible / evolving schema (early product, multi-tenant SaaS with per-tenant variation).</li>
<li>Geographic + full-text + vector queries on the same data.</li>
<li>Real-time change streams.</li>
</ul>
<h2 id="When-MongoDB-doesnt-fit-consider-alternatives"><a href="#When-MongoDB-doesnt-fit-consider-alternatives" class="headerlink" title="When MongoDB doesn't fit (consider alternatives)"></a>When MongoDB doesn't fit (consider alternatives)</h2>
<ul>
<li>Heavy multi-row ACID transactions → Postgres / CockroachDB.</li>
<li>Complex relational reporting + ad-hoc joins → relational + warehouse.</li>
<li>Pure key-value at giant scale → Redis / DynamoDB.</li>
<li>Strict tabular columnar analytics → ClickHouse / BigQuery.</li>
</ul>
