11:T610e,<p>Real AWS workloads start with the network, not the server. Where a workload lives — which VPC, which subnet, behind which gateway, allowed by which security rules — decides far more about its security posture, cost, and failure behaviour than the choice of instance type. This post is the deep dive on <strong>VPC</strong>, the virtual data centre that hosts almost everything else in the series.</p>

<h1 id="Why-network-before-compute"><a href="#Why-network-before-compute" class="headerlink" title="Why network before compute"></a>Why network before compute</h1>
<p>A tempting shortcut is to &quot;just launch an EC2&quot; and figure out the network later. The cost: every later change (adding a database, fronting with a load balancer, going multi-AZ, locking down for security review) becomes a re-architecture. Network-first means picking a small set of decisions once and reusing them for the next decade.</p>
<p>The decisions:</p>
<ul>
<li>Which <strong>region</strong>.</li>
<li>VPC <strong>CIDR range</strong> (which private IPs you'll own).</li>
<li><strong>Subnet layout</strong> (how many AZs, public/private/isolated).</li>
<li><strong>Internet egress</strong> path (IGW + NAT or VPC endpoints).</li>
<li><strong>Security group baseline</strong> (who can talk to whom).</li>
</ul>
<hr>
<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Design a VPC CIDR that won't collide with other accounts you might peer with.</li>
<li>Lay out public / private / isolated subnets across 3 AZs.</li>
<li>Configure route tables, internet gateways, NAT gateways, and VPC endpoints.</li>
<li>Write security groups and (rarely) NACLs that are tight without being painful.</li>
<li>Recognise the cost levers: NAT gateway, cross-AZ traffic, data egress.</li>
</ul>
<hr>
<h1 id="Chapter-1-—-VPC-anatomy"><a href="#Chapter-1-—-VPC-anatomy" class="headerlink" title="Chapter 1 — VPC anatomy"></a>Chapter 1 — VPC anatomy</h1>
<p>A <strong>VPC</strong> is a software-defined private network inside one AWS region. Each AWS account gets a default VPC per region (<code>172.31.0.0/16</code>); production accounts almost always create custom ones.</p>

<h2 id="CIDR-sizing"><a href="#CIDR-sizing" class="headerlink" title="CIDR sizing"></a>CIDR sizing</h2>
<p>A <code>/16</code> (e.g., <code>10.0.0.0/16</code>) gives 65,536 addresses — enough for a serious production environment. A <code>/24</code> subnet (e.g., <code>10.0.1.0/24</code>) gives 256 addresses minus 5 reserved by AWS → 251 usable.</p>
<p><strong>Trick:</strong> pick non-overlapping ranges across all your AWS accounts and on-prem networks. Once you peer two VPCs or set up a Transit Gateway / Direct Connect, overlapping CIDRs become an immediate migration project. Conventional starting layouts:</p>
<ul>
<li>Account <code>prod</code> — <code>10.0.0.0/16</code></li>
<li>Account <code>staging</code> — <code>10.1.0.0/16</code></li>
<li>Account <code>dev</code> — <code>10.2.0.0/16</code></li>
<li>Account <code>tools / shared services</code> — <code>10.10.0.0/16</code></li>
<li>On-prem — <code>192.168.0.0/16</code> or <code>172.16.0.0/12</code></li>
</ul>
<hr>

<p>Three reasons this shape is the industry default:</p>
<ol>
<li><strong>Failure isolation.</strong> An AZ outage takes down at most a third of capacity. Combined with a load balancer (Post 03), the service stays up.</li>
<li><strong>Blast radius for security.</strong> Public subnets only host things designed to face the internet. Application servers and data live one or two hops inward.</li>
<li><strong>Cost vs availability tradeoff.</strong> One NAT gateway is cheaper but a single point of failure; one per AZ doubles or triples cost but removes the SPoF. Production prefers per-AZ.</li>
</ol>
<p>A subnet is &quot;public&quot; because <strong>its route table sends <code>0.0.0.0/0</code> to an Internet Gateway</strong>. There is no checkbox — it is the routing that defines the type.</p>
<hr>

<h2 id="VPC-endpoints-—-the-cost-saver"><a href="#VPC-endpoints-—-the-cost-saver" class="headerlink" title="VPC endpoints — the cost saver"></a>VPC endpoints — the cost saver</h2>
<p>By default, an EC2 in a private subnet calling <code>s3.ap-east-1.amazonaws.com</code> routes <strong>out via the NAT gateway</strong> — and you pay NAT data charges (~USD 0.045 / GB). With a <strong>Gateway VPC endpoint for S3</strong>, the traffic stays inside AWS, free.</p>
<p><strong>Watch out:</strong> Interface endpoints cost about USD 7 / endpoint / AZ / month plus per-GB. Useful when bandwidth is high; not always cheaper than NAT for occasional access. Always estimate before adding.</p>
<hr>
<h1 id="Chapter-5-—-Security-groups-your-everyday-firewall"><a href="#Chapter-5-—-Security-groups-your-everyday-firewall" class="headerlink" title="Chapter 5 — Security groups (your everyday firewall)"></a>Chapter 5 — Security groups (your everyday firewall)</h1>
<p>A security group is <strong>stateful</strong>: if a request matches an outbound rule, the reply is automatically allowed (and vice versa). You only configure one direction, not both.</p>
<p>Default behaviour: no inbound, all outbound.</p>
<p>Rules contain:</p>
<ul>
<li><strong>Protocol</strong> (TCP / UDP / ICMP / all)</li>
<li><strong>Port range</strong></li>
<li><strong>Source / destination</strong> (CIDR, another security group, or a prefix list)</li>
</ul>
<h2 id="Reference-SGs-by-ID-not-by-IP"><a href="#Reference-SGs-by-ID-not-by-IP" class="headerlink" title="Reference SGs by ID, not by IP"></a>Reference SGs by ID, not by IP</h2>
<p>When both ends are AWS resources, <strong>reference the other side's security group rather than its IP range</strong>. As IPs change (autoscaling, recreation), the SG reference stays correct.</p>

<h1 id="Chapter-6-—-NACLs-the-backup-layer"><a href="#Chapter-6-—-NACLs-the-backup-layer" class="headerlink" title="Chapter 6 — NACLs (the backup layer)"></a>Chapter 6 — NACLs (the backup layer)</h1>
<p>A Network ACL is <strong>stateless</strong> and applied per subnet. Default rules allow all inbound + outbound. Custom NACLs default to deny.</p>
<p>NACLs are evaluated in order (rule numbers); the first match wins.</p>
<p>In practice most teams <strong>don't touch NACLs</strong> — security groups do all the real work. Reserve NACLs for blanket per-subnet rules (e.g., &quot;isolated subnets reject any outbound traffic at all&quot;) or defence-in-depth against compromised SG state.</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Pick-a-CIDR"><a href="#Exercise-1-—-Pick-a-CIDR" class="headerlink" title="Exercise 1 — Pick a CIDR"></a>Exercise 1 — Pick a CIDR</h2>
<p>Design CIDR blocks for these accounts so they can all peer without overlap:</p>
<ul>
<li><code>prod</code> (large)</li>
<li><code>staging</code> (medium)</li>
<li><code>dev</code> (small)</li>
<li><code>shared-tools</code> (medium)</li>
</ul>
<details>
<summary>Solution</summary>
<ul>
<li>prod: <code>10.0.0.0/16</code></li>
<li>staging: <code>10.1.0.0/16</code></li>
<li>dev: <code>10.2.0.0/16</code></li>
<li>shared-tools: <code>10.10.0.0/16</code></li>
</ul>
<p>Or use <code>/20</code> slices of a single <code>/12</code> (<code>10.0.0.0/12</code>) if you want larger headroom.</p>
</details>
<h2 id="Exercise-2-—-Build-the-3-AZ-VPC"><a href="#Exercise-2-—-Build-the-3-AZ-VPC" class="headerlink" title="Exercise 2 — Build the 3-AZ VPC"></a>Exercise 2 — Build the 3-AZ VPC</h2>
<p>Recreate Chapter 8's CLI build for <strong>all three AZs</strong> of your default region. Verify by launching a t3.micro into a private subnet and confirming <code>curl https://example.com</code> works (proves NAT egress).</p>
<h2 id="Exercise-3-—-Cut-the-NAT-bill"><a href="#Exercise-3-—-Cut-the-NAT-bill" class="headerlink" title="Exercise 3 — Cut the NAT bill"></a>Exercise 3 — Cut the NAT bill</h2>
<p>Add an S3 Gateway endpoint to the private route tables of the VPC from Exercise 2. Run <code>aws s3 cp</code> from the private instance. Confirm in CloudWatch that the NAT gateway's outbound bytes did <strong>not</strong> increase.</p>
<h2 id="Exercise-4-—-Security-group-chain"><a href="#Exercise-4-—-Security-group-chain" class="headerlink" title="Exercise 4 — Security-group chain"></a>Exercise 4 — Security-group chain</h2>
<p>Build three SGs:</p>
<ul>
<li><code>sg-web</code>  → 443 from <code>0.0.0.0/0</code></li>
<li><code>sg-app</code>  → 8080 from <code>sg-web</code></li>
<li><code>sg-db</code>   → 5432 from <code>sg-app</code></li>
</ul>
<p>Verify the chain works end-to-end and that nothing else can reach the DB.</p>
