AWS Course — 06 · Workflow Orchestration — Step Functions and Patterns

Created2026-05-19|Updated2026-05-19|Cloud > AWS
|Post View:

Once you have many Lambdas + events (Post 05), the next problem is coordination: "run A, then B in parallel with C, then if A succeeded do D, retry B up to 3 times, and if anything fails roll back". Wiring this with raw Lambdas and SQS is possible but quickly turns into spaghetti. AWS Step Functions provides a managed state-machine service exactly for this purpose. This post covers the basics of Step Functions, the two workflow types (Standard vs Express), the common patterns (sequence, parallel, choice, map, wait, retry, catch), the Saga pattern for distributed transactions, and when to reach for Step Functions vs simpler alternatives.

Series map: 00 Foundations → 01 Network First → 02 Compute & Storage → 03 Scale & Survive → 04 Managed Data → 05 Serverless & Events → 06 Workflow Orchestration (this post) → 07 Observability & Security → 08 IaC.

Learning Outcome

  • Write a state machine in Amazon States Language (ASL).
  • Pick between Standard and Express workflows.
  • Use the core state types: Task, Pass, Choice, Wait, Parallel, Map, Succeed, Fail.
  • Configure retries, catches, and timeouts.
  • Implement a Saga (compensating-action rollback) for distributed transactions.
  • Decide between Step Functions, EventBridge Pipes, and SQS-chained Lambdas.

Chapter 1 — Why state machines

A workflow is a graph of steps with branches, parallelism, error handling, and (sometimes) human approval. Hand-rolled, this turns into a tangle of Lambdas invoking other Lambdas, with retry logic copied in each, error-handling baked into each step, and no central view of "where is this execution right now?".

Step Functions externalises the orchestration:

  • The state machine definition is a JSON document — version-controlled, auditable.
  • Step Functions runs each execution: tracks position, retries, errors, history.
  • The console shows a visual diagram of every execution — which step succeeded, which failed, what data flowed where.
  • Each step is small and stateless (your Lambdas or AWS service calls); orchestration logic lives in one place.

Chapter 2 — Workflow types

Type Duration Pricing Execution history Use
Standard up to 1 year per state transition full history, queryable long-running, audit-required, occasional
Express up to 5 min per execution time CloudWatch Logs only high-throughput, short

Standard suits business workflows (order fulfilment, ETL, approvals). Express suits per-request orchestration (an API call that needs to fan out, gather, return).

Chapter 4 — Core state types

Task

Invokes an AWS service action. The most common is a Lambda, but Step Functions can call > 200 AWS service actions directly without a Lambda:

The .$ suffix tells the engine "use the value from the execution state at this JSONPath". This service integration avoids a Lambda hop entirely — faster + cheaper + simpler.

Pass

Manipulates the state (filter, add, rename fields) without invoking anything.

Choice

Conditional branching.

Wait

Pauses for a duration or until a timestamp.

Parallel

Runs multiple branches at once; collects all results into an array.

Map

Like Parallel, but for a dynamic-size array — the same workflow runs once per item.

The 2023+ Distributed Map scales Map up to 10,000 parallel iterations (good for fanning out over big S3 lists, large arrays).

Succeed / Fail

Terminal states. Fail records an error + cause that the parent can Catch.

Chapter 5 — Retry and Catch

Every Task can declare retries and error catchers:

Retries multiply: first the most specific error block runs, then States.ALL as a catch-all.

Trick: put exponential backoff (BackoffRate: 2.0) on Retries that hit external APIs — the third-party will recover; instant retries waste your throttling budget.

Chapter 6 — The Saga pattern

In a distributed system, you can't have ACID across services. The Saga pattern fakes it: every step has a compensating action, and if a later step fails, the workflow runs the prior compensating actions in reverse.

Example: order placement.

If Schedule Delivery fails, the workflow:

  1. Cancels delivery (n/a, never scheduled).
  2. Refunds the card.
  3. Releases the inventory.
  4. Returns the user a coherent failure response.

In Step Functions, model it as a Try block with Catch that routes to a compensating sub-workflow.

Chapter 7 — Express vs Standard pricing

Standard Express
USD 0.025 per 1,000 state transitions USD 1 per 1M executions + GB-second compute time

A long-running workflow with 50 transitions costs ~USD 0.00125 per execution on Standard. A 200-ms Express execution at 100 MB costs ~USD 0.0000004 per execution. Express wins for high-volume; Standard wins for long-running / fewer / audit-required.

Many production systems use both: Standard for the business workflow, Express for inner high-frequency loops.

Chapter 8 — When NOT to use Step Functions

Scenario Better fit
Single Lambda, no branching just use Lambda
Pure pub/sub fanout SNS or EventBridge
Pure queue + worker SQS + Lambda
Stream processing Kinesis + Lambda
Simple event chain across AWS services without transformations EventBridge Pipes (newer, lighter than Step Functions for source → enrich → target)
Always-on long-running daemon ECS / EC2

EventBridge Pipes deserves a special mention: launched 2022, ideal for "read from queue/stream → optional Lambda enrich → write to target". For pure pipelines without branching, Pipes is cheaper and simpler than Step Functions.

Chapter 9 — A worked example: image-processing pipeline

Workflow: user uploads photo → resize multiple variants in parallel → run ML classifier → store metadata → notify user.

What this gains over hand-wired Lambdas:

  • Visual diagram for every execution.
  • Built-in retries with backoff.
  • Direct SDK integration for DynamoDB + SNS — no Lambda wrappers.
  • Full execution history queryable in the console.
  • Easy modification — add a step in JSON, no code change.

Chapter 10 — Standard workflow + human approval

A common pattern: wait for a human approval mid-workflow. Step Functions supports callback tokens — pause until an out-of-band call resumes.

The workflow pauses (up to a year on Standard). A human (or webhook) calls SendTaskSuccess / SendTaskFailure with the token to resume.

Practice Exercises

Exercise 1 — Hello state machine

Create a Standard workflow with three Lambdas in sequence: A → B → C. Start an execution; watch the visual diagram in the console.

Exercise 2 — Choice branch

Add a Choice state after A:

  • if $.priority == "high" → Lambda X
  • else → Lambda Y

Test both inputs.

Exercise 3 — Retry + Catch

Make Lambda B fail intermittently (raise an exception 50% of the time). Add Retry (3 attempts, backoff 2) and Catch (→ a "Notify failure" Lambda). Observe behaviour.

Exercise 4 — Saga

Implement the order-placement Saga from Chapter 6 with three real Lambdas (each can be a stub that prints + returns). Force the third step to fail; verify compensating actions run in reverse.

Exercise 5 — Direct service integration

Replace one of your Task Lambdas with a direct DynamoDB putItem. Confirm the workflow shrinks by one Lambda and runs faster.

Exercise 6 — Express vs Standard

Convert a workflow that runs 1000+ times/day to Express. Compare costs over a week.
