<h1 id="Chapter-1-—-Why-state-machines"><a href="#Chapter-1-—-Why-state-machines" class="headerlink" title="Chapter 1 — Why state machines"></a>Chapter 1 — Why state machines</h1>
<p>A workflow is a graph of steps with branches, parallelism, error handling, and (sometimes) human approval. Hand-rolled, this turns into a tangle of Lambdas invoking other Lambdas, with retry logic copied in each, error-handling baked into each step, and no central view of &quot;where is this execution right now?&quot;.</p>
<p>Step Functions externalises the orchestration:</p>
<ul>
<li>The <strong>state machine definition</strong> is a JSON document — version-controlled, auditable.</li>
<li>Step Functions runs each execution: tracks position, retries, errors, history.</li>
<li>The console shows a <strong>visual diagram</strong> of every execution — which step succeeded, which failed, what data flowed where.</li>
<li>Each step is small and stateless (your Lambdas or AWS service calls); orchestration logic lives in one place.</li>
</ul>

<h1 id="Chapter-6-—-The-Saga-pattern"><a href="#Chapter-6-—-The-Saga-pattern" class="headerlink" title="Chapter 6 — The Saga pattern"></a>Chapter 6 — The Saga pattern</h1>
<p>In a distributed system, you can't have ACID across services. The Saga pattern fakes it: every step has a <strong>compensating action</strong>, and if a later step fails, the workflow runs the prior compensating actions in reverse.</p>
<p>Example: order placement.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="text"><span class="line">Reserve Inventory  →  Charge Card  →  Schedule Delivery  →  Done</span><br><span class="line">        │                  │                  │</span><br><span class="line">   (compensate:       (compensate:       (compensate:</span><br><span class="line">   release inv)         refund)         cancel delivery)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If <code>Schedule Delivery</code> fails, the workflow:</p>
<ol>
<li>Cancels delivery (n/a, never scheduled).</li>
<li>Refunds the card.</li>
<li>Releases the inventory.</li>
<li>Returns the user a coherent failure response.</li>
</ol>
<p>In Step Functions, model it as a <code>Try</code> block with <code>Catch</code> that routes to a compensating sub-workflow.</p>

</table>
<p>A long-running workflow with 50 transitions costs ~USD 0.00125 per execution on Standard. A 200-ms Express execution at 100 MB costs ~USD 0.0000004 per execution. Express wins for high-volume; Standard wins for long-running / fewer / audit-required.</p>
<p>Many production systems use <strong>both</strong>: Standard for the business workflow, Express for inner high-frequency loops.</p>

<h1 id="Chapter-8-—-When-NOT-to-use-Step-Functions"><a href="#Chapter-8-—-When-NOT-to-use-Step-Functions" class="headerlink" title="Chapter 8 — When NOT to use Step Functions"></a>Chapter 8 — When NOT to use Step Functions</h1>

<thead>
<tr>
<th>Scenario</th>
<th>Better fit</th>
</tr>
</thead>
<tbody>
<tr>

</tr>

</tr>

</table>
<p>EventBridge Pipes deserves a special mention: launched 2022, ideal for &quot;read from queue/stream → optional Lambda enrich → write to target&quot;. For pure pipelines without branching, Pipes is cheaper and simpler than Step Functions.</p>
