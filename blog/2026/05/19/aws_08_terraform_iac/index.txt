11:Tc04c,<p>Posts 01-07 used the AWS CLI and console to build a real workload. Both are fine for learning; both are wrong for production. The final base post covers <strong>Infrastructure as Code (IaC)</strong>: declarative, version-controlled, repeatable definitions of every resource. The series uses <strong>Terraform</strong> as the primary tool — the de facto industry standard at present — with a fair comparison against CloudFormation, CDK, and Pulumi. By the end of this post, the entire 3-tier architecture from Post 03 fits in ~150 lines of HCL anyone on the team can read, review, and redeploy.</p>

<p>Series map: 00 Foundations → 01 Network First → 02 Compute &amp; Storage → 03 Scale &amp; Survive → 04 Managed Data → 05 Serverless &amp; Events → 06 Workflow Orchestration → 07 Observability &amp; Security → <strong>08 Infrastructure as Code</strong> (this post). <pre><code class="language-hcl"><figure class="highlight hcl"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="hcl"><span class="line">terraform {</span><br><span class="line">  backend <span class="hljs-string">&quot;s3&quot;</span> {</span><br><span class="line">    bucket         <span class="hljs-operator">=</span> <span class="hljs-string">&quot;myorg-tfstate&quot;</span></span><br><span class="line">    key            <span class="hljs-operator">=</span> <span class="hljs-string">&quot;prod/network/terraform.tfstate&quot;</span></span><br><span class="line">    region         <span class="hljs-operator">=</span> <span class="hljs-string">&quot;us-east-1&quot;</span></span><br><span class="line">    encrypt        <span class="hljs-operator">=</span> true</span><br><span class="line">    dynamodb_table <span class="hljs-operator">=</span> <span class="hljs-string">&quot;myorg-tfstate-lock&quot;</span></span><br><span class="line">  }</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Setup once: create the bucket + lock table by hand (or with a tiny bootstrap Terraform run). Then every subsequent project uses the backend.</p>
<p><strong>Watch out:</strong> the state file contains every value — including secrets you passed to resources. Encrypt the bucket, restrict access tightly, and treat state with the same care as a database backup.</p>

<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="bash"><span class="line">terraform <span class="hljs-built_in">fmt</span>           <span class="hljs-comment"># canonical formatting</span></span><br><span class="line">terraform validate      <span class="hljs-comment"># syntax check</span></span><br><span class="line">terraform plan -out plan.tfplan</span><br><span class="line"><span class="hljs-comment"># review carefully — every change shown</span></span><br><span class="line">terraform apply plan.tfplan</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Rules everyone in the team should follow:</p>
<ol>
<li><strong>Always review the plan before apply.</strong> Terraform happily replaces a database if the configuration says so.</li>
<li><strong>Use <code>prevent_destroy = true</code></strong> on stateful resources (RDS, S3 buckets with data).</li>
<li><strong>Workspaces or directories</strong> isolate envs — never one state file for dev + prod.</li>
<li><strong>Lock files (<code>.terraform.lock.hcl</code>) are committed</strong> — pins provider versions.</li>
<li><strong>Pin module + provider versions.</strong> Floating versions break builds quietly.</li>
</ol>
<pre><code class="language-hcl"><figure class="highlight hcl"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="hcl"><span class="line"><span class="hljs-keyword">lifecycle</span> {</span><br><span class="line">  prevent_destroy <span class="hljs-operator">=</span> <span class="hljs-literal">true</span></span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Trick:</strong> when you see <code># forces replacement</code> in a <code>plan</code> for a resource you don't want destroyed (an RDS, an EBS volume with data), <strong>stop</strong>. Either the change is wrong, or you need <code>lifecycle { create_before_destroy = true }</code>, or you need a migration approach. Never just apply through it.</p>
</blockquote>

<h1 id="Chapter-10-—-CICD-for-Terraform"><a href="#Chapter-10-—-CICD-for-Terraform" class="headerlink" title="Chapter 10 — CI/CD for Terraform"></a>Chapter 10 — CI/CD for Terraform</h1>
<p>A typical pipeline (GitHub Actions / GitLab CI / CodePipeline):</p>
<ol>
<li>PR opened with <code>.tf</code> changes.</li>
<li>CI runs <code>terraform fmt -check</code>, <code>terraform validate</code>, <code>terraform plan</code>.</li>
<li>The plan is posted as a PR comment for review.</li>
<li>On merge to <code>main</code>, CI runs <code>terraform apply</code> against the target env.</li>
<li>Optionally run <code>tflint</code>, <code>tfsec</code>, <code>checkov</code> for static security analysis.</li>
</ol>
<p>Use <a href="https://www.runatlantis.io/" target="_blank" rel="noopener external nofollow noreferrer">Atlantis</a> or AWS-managed alternatives like CodePipeline + CodeBuild for centralised Terraform automation.</p>
<p>For high-stakes envs, <strong>gate apply behind manual approval</strong> in the pipeline. Belt-and-braces: even with a perfect plan, a second pair of eyes catches the case where the plan and the intent diverge.</p>

<h1 id="Chapter-11-—-Common-Terraform-pitfalls"><a href="#Chapter-11-—-Common-Terraform-pitfalls" class="headerlink" title="Chapter 11 — Common Terraform pitfalls"></a>Chapter 11 — Common Terraform pitfalls</h1>
<table>
<thead>
<tr>
<th>Pitfall</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>State file lost or corrupted</td>
<td>use remote backend; backup the bucket</td>
</tr>
<tr>
<td>Two people apply simultaneously</td>
<td>DynamoDB lock table</td>
</tr>
<tr>
<td>Drift (resource changed in console)</td>
<td>run <code>terraform plan</code> regularly; <code>terraform import</code> to reconcile</td>
</tr>
<tr>
<td>Provider version floats and breaks</td>
<td>pin versions in <code>required_providers</code></td>
</tr>
<tr>
<td>Secrets in <code>.tfvars</code> committed to git</td>
<td>use SSM / Secrets Manager, fetch via data sources</td>
</tr>
<tr>
<td>Big monolith refactors</td>
<td>split into modules + per-env directories</td>
</tr>
<tr>
<td>Resource destroyed accidentally</td>
<td><code>lifecycle { prevent_destroy = true }</code> on stateful things</td>
</tr>
<tr>
<td>Drift you can't reconcile</td>
<td>as a last resort, <code>terraform state rm</code> then <code>terraform import</code> to re-attach</td>
</tr>
</tbody>
</table>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Hello-Terraform"><a href="#Exercise-1-—-Hello-Terraform" class="headerlink" title="Exercise 1 — Hello Terraform"></a>Exercise 1 — Hello Terraform</h2>
<p>Install Terraform; write a minimal <code>main.tf</code> that creates a single S3 bucket; run <code>init → plan → apply → destroy</code>.</p>
<h2 id="Exercise-2-—-Variables-outputs"><a href="#Exercise-2-—-Variables-outputs" class="headerlink" title="Exercise 2 — Variables + outputs"></a>Exercise 2 — Variables + outputs</h2>
<p>Parameterise the bucket name with a variable; add an output for the bucket ARN. Use <code>-var=&quot;bucket=...&quot;</code>.</p>
<h2 id="Exercise-3-—-Remote-backend"><a href="#Exercise-3-—-Remote-backend" class="headerlink" title="Exercise 3 — Remote backend"></a>Exercise 3 — Remote backend</h2>
<p>Create an S3 bucket + DynamoDB lock table (by hand or with a tiny bootstrap module). Configure your Exercise 1 module to use the S3 backend. Confirm <code>terraform.tfstate</code> no longer appears locally.</p>
<h2 id="Exercise-4-—-VPC-module"><a href="#Exercise-4-—-VPC-module" class="headerlink" title="Exercise 4 — VPC module"></a>Exercise 4 — VPC module</h2>
<p>Use the public <code>terraform-aws-modules/vpc/aws</code> module to recreate the 3-AZ VPC from Post 01. Compare line count vs the CLI walkthrough.</p>
<h2 id="Exercise-5-—-Full-3-tier-stack"><a href="#Exercise-5-—-Full-3-tier-stack" class="headerlink" title="Exercise 5 — Full 3-tier stack"></a>Exercise 5 — Full 3-tier stack</h2>
<p>Wire up Chapter 9's example end-to-end. Apply to a fresh AWS account, hit the ALB DNS, confirm responses come from the EC2 instances. Destroy.</p>
<h2 id="Exercise-6-—-Pipeline"><a href="#Exercise-6-—-Pipeline" class="headerlink" title="Exercise 6 — Pipeline"></a>Exercise 6 — Pipeline</h2>
<p>Push your Terraform repo to GitHub. Add a GitHub Actions workflow that runs <code>terraform fmt</code> + <code>validate</code> + <code>plan</code> on PRs and <code>apply</code> on merge. Bonus: add <code>tflint</code> + <code>tfsec</code>.</p>
