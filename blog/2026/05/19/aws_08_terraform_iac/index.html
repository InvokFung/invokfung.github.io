AWS Course — 08 · Infrastructure as Code — Terraform on AWS

Created2026-05-19|Updated2026-05-19|Cloud > AWS
|Post View:

Posts 01-07 used the AWS CLI and console to build a real workload. Both are fine for learning; both are wrong for production. The final base post covers Infrastructure as Code (IaC): declarative, version-controlled, repeatable definitions of every resource. The series uses Terraform as the primary tool — the de facto industry standard at present — with a fair comparison against CloudFormation, CDK, and Pulumi. By the end of this post, the entire 3-tier architecture from Post 03 fits in ~150 lines of HCL anyone on the team can read, review, and redeploy.

Series map: 00 Foundations → 01 Network First → 02 Compute & Storage → 03 Scale & Survive → 04 Managed Data → 05 Serverless & Events → 06 Workflow Orchestration → 07 Observability & Security → 08 Infrastructure as Code (this post). Future extensions: containers (ECS/EKS), edge (CloudFront/Route53), CI/CD pipelines, multi-account organisations, FinOps deep dive.

Learning Outcome

  • Understand why IaC matters and the trade-offs between tools.
  • Install Terraform and set up an AWS provider.
  • Write resources, variables, outputs, modules.
  • Use a remote backend (S3 + DynamoDB) for state.
  • Apply Terraform's plan / apply / destroy cycle safely.
  • Structure a real repository: envs (dev/staging/prod), modules, secrets, CI/CD.
  • Compare Terraform vs CloudFormation vs CDK vs Pulumi.

Chapter 1 — Why IaC

Without IaC With IaC
Resources created by clicking — no record of how Every resource in a git-tracked file
Re-creating in another region/account = pain terraform apply in a new workspace
Drift between environments Same code, parameterised
Code review for app code only Code review for infrastructure too
Recovery from incident = guesswork Re-apply from version control

In serious organisations, clicking in the console for production is an audit finding. Even small projects benefit: the second time you destroy and rebuild a test environment is when IaC pays for itself.

Chapter 2 — Tool comparison

Tool Language Vendor When
Terraform / OpenTofu HCL HashiCorp / Linux Foundation most multi-cloud, most ops teams, default in 2026
CloudFormation YAML / JSON AWS AWS-only stacks that benefit from native rollback + drift detection
AWS CDK TypeScript / Python / Java / Go AWS teams comfortable with code-defined infra, complex constructs
Pulumi TypeScript / Python / Go / C# Pulumi multi-cloud with general-purpose language preferred
AWS SAM YAML AWS serverless-first projects (extends CloudFormation)
Ansible / Chef / Puppet YAML / Ruby various config management of existing servers, not IaC

Terraform's hegemony comes from:

  • Multi-cloud + huge provider ecosystem (AWS, Azure, GCP, Datadog, GitHub, Cloudflare, etc.).
  • Mature module ecosystem (the registry).
  • Clear state model + plan/apply workflow.

For pure AWS shops, CDK is increasingly popular — it generates CloudFormation under the hood but lets you write in familiar code with constructs that bundle common patterns.

Note: in 2023 HashiCorp changed Terraform's licence; the OpenTofu fork (Linux Foundation, MPL-2.0) is a drop-in replacement many teams now prefer. The HCL syntax + provider plugins are compatible.

Chapter 6 — Remote state

By default Terraform stores state locally in terraform.tfstate. For teams, store it in S3 + a DynamoDB lock table:

Setup once: create the bucket + lock table by hand (or with a tiny bootstrap Terraform run). Then every subsequent project uses the backend.

Watch out: the state file contains every value — including secrets you passed to resources. Encrypt the bucket, restrict access tightly, and treat state with the same care as a database backup.

Chapter 8 — The plan / apply discipline

Rules everyone in the team should follow:

  1. Always review the plan before apply. Terraform happily replaces a database if the configuration says so.
  2. Use prevent_destroy = true on stateful resources (RDS, S3 buckets with data).
  3. Workspaces or directories isolate envs — never one state file for dev + prod.
  4. Lock files (.terraform.lock.hcl) are committed — pins provider versions.
  5. Pin module + provider versions. Floating versions break builds quietly.

Trick: when you see # forces replacement in a plan for a resource you don't want destroyed (an RDS, an EBS volume with data), stop. Either the change is wrong, or you need lifecycle { create_before_destroy = true }, or you need a migration approach. Never just apply through it.

Chapter 10 — CI/CD for Terraform

A typical pipeline (GitHub Actions / GitLab CI / CodePipeline):

  1. PR opened with .tf changes.
  2. CI runs terraform fmt -check, terraform validate, terraform plan.
  3. The plan is posted as a PR comment for review.
  4. On merge to main, CI runs terraform apply against the target env.
  5. Optionally run tflint, tfsec, checkov for static security analysis.

Use Atlantis or AWS-managed alternatives like CodePipeline + CodeBuild for centralised Terraform automation.

For high-stakes envs, gate apply behind manual approval in the pipeline. Belt-and-braces: even with a perfect plan, a second pair of eyes catches the case where the plan and the intent diverge.

Chapter 11 — Common Terraform pitfalls

Pitfall Fix
State file lost or corrupted use remote backend; backup the bucket
Two people apply simultaneously DynamoDB lock table
Drift (resource changed in console) run terraform plan regularly; terraform import to reconcile
Provider version floats and breaks pin versions in required_providers
Secrets in .tfvars committed to git use SSM / Secrets Manager, fetch via data sources
Big monolith refactors split into modules + per-env directories
Resource destroyed accidentally lifecycle { prevent_destroy = true } on stateful things
Drift you can't reconcile as a last resort, terraform state rm then terraform import to re-attach

Practice Exercises

Exercise 1 — Hello Terraform

Install Terraform; write a minimal main.tf that creates a single S3 bucket; run init → plan → apply → destroy.

Exercise 2 — Variables + outputs

Parameterise the bucket name with a variable; add an output for the bucket ARN. Use -var="bucket=...".

Exercise 3 — Remote backend

Create an S3 bucket + DynamoDB lock table (by hand or with a tiny bootstrap module). Configure your Exercise 1 module to use the S3 backend. Confirm terraform.tfstate no longer appears locally.

Exercise 4 — VPC module

Use the public terraform-aws-modules/vpc/aws module to recreate the 3-AZ VPC from Post 01. Compare line count vs the CLI walkthrough.

Exercise 5 — Full 3-tier stack

Wire up Chapter 9's example end-to-end. Apply to a fresh AWS account, hit the ALB DNS, confirm responses come from the EC2 instances. Destroy.

Exercise 6 — Pipeline

Push your Terraform repo to GitHub. Add a GitHub Actions workflow that runs terraform fmt + validate + plan on PRs and apply on merge. Bonus: add tflint + tfsec.

Cheat-sheet

What How
Init terraform init
Plan terraform plan -out plan.tfplan
Apply terraform apply plan.tfplan
Destroy terraform destroy
Format terraform fmt -recursive
Validate terraform validate
Workspace terraform workspace select staging
Variable file -var-file=prod.tfvars
Remote state S3 bucket + DynamoDB lock table
Public modules terraform-aws-modules/*
Prevent destroy lifecycle { prevent_destroy = true }
Replace one resource terraform apply -replace=aws_instance.web
Import existing terraform import aws_s3_bucket.x bucket-name
Tools tflint, tfsec, checkov for static analysis
Alternative OpenTofu (drop-in OSS fork)
