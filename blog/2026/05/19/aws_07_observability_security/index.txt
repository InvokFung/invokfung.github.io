<h1 id="Chapter-1-—-CloudWatch-metrics"><a href="#Chapter-1-—-CloudWatch-metrics" class="headerlink" title="Chapter 1 — CloudWatch metrics"></a>Chapter 1 — CloudWatch metrics</h1>
<p>Every AWS service publishes metrics to CloudWatch automatically:</p>
<ul>
<li>EC2 — CPU, network in/out, status checks.</li>
<li>ALB — request count, target response time, 5XX count, healthy host count.</li>
<li>Lambda — invocations, errors, throttles, duration, concurrent executions.</li>
<li>RDS — CPU, free memory, IOPS, replica lag.</li>
<li>DynamoDB — consumed read/write capacity, throttles.</li>
</ul>
<p>Metrics are stored per namespace (e.g., <code>AWS/Lambda</code>) with dimensions (e.g., <code>FunctionName=hello</code>). Each is a time series of values.</p>

<h1 id="Chapter-2-—-CloudWatch-Logs"><a href="#Chapter-2-—-CloudWatch-Logs" class="headerlink" title="Chapter 2 — CloudWatch Logs"></a>Chapter 2 — CloudWatch Logs</h1>
<p>Every Lambda, ECS task, EC2 (with CloudWatch Agent), API Gateway, RDS (optional), and ALB (optional) writes logs to <strong>log groups</strong>.</p>
<ul>
<li>Group: <code>/aws/lambda/&lt;function&gt;</code> or <code>/aws/ecs/&lt;service&gt;</code>.</li>
<li>Stream: one per execution / container / day.</li>
<li>Each log event has a timestamp + message.</li>
</ul>
<h2 id="Retention"><a href="#Retention" class="headerlink" title="Retention"></a>Retention</h2>
<p>The default retention is <strong>forever</strong> — costly over time. Set retention on every log group: 7, 14, 30, or 90 days are typical.</p>

<h1 id="Chapter-3-—-Alarms"><a href="#Chapter-3-—-Alarms" class="headerlink" title="Chapter 3 — Alarms"></a>Chapter 3 — Alarms</h1>
<p>A CloudWatch alarm watches a metric and notifies (usually via SNS) when a threshold is breached.</p>
<p>Minimum production alarms:</p>
<table>
<thead>
<tr>
<th>Resource</th>
<th>Alarm</th>
</tr>
</thead>
<tbody>
<tr>
<td>Every Lambda</td>
<td><code>Errors &gt; 0 over 1 min</code></td>
</tr>
<tr>
<td>Every Lambda</td>
<td><code>Throttles &gt; 0 over 1 min</code></td>
</tr>
<tr>
<td>Every ALB</td>
<td><code>HTTPCode_Target_5XX_Count &gt; N over 5 min</code></td>
</tr>
<tr>
<td>Every ALB</td>
<td><code>UnHealthyHostCount &gt; 0</code></td>
</tr>
<tr>
<td>Every RDS</td>
<td><code>CPUUtilization &gt; 80 over 10 min</code></td>
</tr>
<tr>
<td>Every RDS</td>
<td><code>FreeableMemory &lt; 100 MB</code></td>
</tr>
<tr>
<td>Every RDS</td>
<td><code>DatabaseConnections &gt; limit*0.8</code></td>
</tr>
<tr>
<td>Every DLQ</td>
<td><code>ApproximateNumberOfMessagesVisible &gt; 0</code></td>
</tr>
<tr>
<td>Every NAT gateway</td>
<td><code>ErrorPortAllocation &gt; 0</code></td>
</tr>

</tr>
</tbody>
</table>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="bash"><span class="line">aws cloudwatch put-metric-alarm \</span><br><span class="line">  --alarm-name lambda-hello-errors \</span><br><span class="line">  --metric-name Errors --namespace AWS/Lambda \</span><br><span class="line">  --statistic Sum --period 60 --threshold 0 \</span><br><span class="line">  --comparison-operator GreaterThanThreshold \</span><br><span class="line">  --evaluation-periods 1 \</span><br><span class="line">  --dimensions Name=FunctionName,Value=hello \</span><br><span class="line">  --alarm-actions arn:aws:sns:...</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The SNS topic typically subscribes email + a Slack/Teams webhook + PagerDuty.</p>
<hr>
<h1 id="Chapter-4-—-Dashboards"><a href="#Chapter-4-—-Dashboards" class="headerlink" title="Chapter 4 — Dashboards"></a>Chapter 4 — Dashboards</h1>
<p>CloudWatch dashboards combine metrics + logs widgets into a single page. Reasonable starter set:</p>
<ul>
<li>Service KPI tile: request rate, p50 / p95 latency, 5xx count.</li>
<li>Resource utilisation row: CPU, memory, errors per service.</li>
<li>Cost tile: estimated charges + month-over-month.</li>
<li>Dependency row: DB CPU, queue depth, cache hit rate.</li>
</ul>
<p>For multi-account visibility, <strong>CloudWatch cross-account observability</strong> lets one monitoring account aggregate metrics + logs from many workload accounts.</p>
<h2 id="Alternatives"><a href="#Alternatives" class="headerlink" title="Alternatives"></a>Alternatives</h2>
<p>Datadog, Grafana / Prometheus, New Relic, Honeycomb — all integrate with CloudWatch. Pick whichever your team uses if it's already paid for. Pure-AWS dashboards are fine to start.</p>
<hr>
<h1 id="Chapter-5-—-X-Ray-distributed-tracing"><a href="#Chapter-5-—-X-Ray-distributed-tracing" class="headerlink" title="Chapter 5 — X-Ray (distributed tracing)"></a>Chapter 5 — X-Ray (distributed tracing)</h1>
<p>X-Ray traces a request as it hops between services (API Gateway → Lambda → DynamoDB → SNS). For each segment: start time, end time, latency, errors. Find bottlenecks in seconds.</p>
<p>Enable per service:</p>
<ul>
<li>Lambda: tick &quot;Active tracing&quot; or <code>--tracing-config Mode=Active</code>.</li>
<li>API Gateway: enable in stage settings.</li>
<li>ECS: add the X-Ray daemon container.</li>
</ul>
<p>In the SDK, instrument client calls:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">from</span> aws_xray_sdk.core <span class="hljs-keyword">import</span> patch_all</span><br><span class="line">patch_all()   <span class="hljs-comment"># auto-instruments boto3, requests, sqlalchemy, etc.</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>X-Ray is being superseded by the newer <strong>AWS Distro for OpenTelemetry (ADOT)</strong> for cross-cloud + OSS compatibility. For pure AWS, X-Ray is still the simplest start.</p>
<hr>
<h1 id="Chapter-6-—-CloudTrail-audit-log"><a href="#Chapter-6-—-CloudTrail-audit-log" class="headerlink" title="Chapter 6 — CloudTrail (audit log)"></a>Chapter 6 — CloudTrail (audit log)</h1>
<p>CloudTrail records every API call in your account: who, when, what, from where.</p>
<p>By default, a free 90-day <strong>event history</strong> is available in the console. For longer retention and analytical use, configure a <strong>trail</strong> that writes to S3 + optionally CloudWatch Logs.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="bash"><span class="line">aws cloudtrail create-trail \</span><br><span class="line">  --name account-trail \</span><br><span class="line">  --s3-bucket-name my-audit-bucket-2026 \</span><br><span class="line">  --is-multi-region-trail \</span><br><span class="line">  --enable-log-file-validation</span><br><span class="line"> </span><br><span class="line">aws cloudtrail start-logging --name account-trail</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="What-CloudTrail-tells-you"><a href="#What-CloudTrail-tells-you" class="headerlink" title="What CloudTrail tells you"></a>What CloudTrail tells you</h2>
<ul>
<li>Who created / deleted resources.</li>
<li>Who assumed a role.</li>
<li>Failed authentication attempts.</li>
<li>Console logins (with MFA status).</li>
<li>Source IPs of API calls.</li>
</ul>
<p>Couple with <strong>Athena</strong> to query CloudTrail logs in S3 cheaply.</p>

<p>Specialised for credentials with <strong>automatic rotation</strong>. AWS rotates RDS / DocumentDB / Redshift passwords without app-code changes when wired correctly.</p>

<thead>
<tr>
<th>Trait</th>
<th>Parameter Store SecureString</th>
<th>Secrets Manager</th>
</tr>

<tbody>
<tr>

<td>free</td>

<h1 id="Chapter-9-—-KMS-encryption-keys"><a href="#Chapter-9-—-KMS-encryption-keys" class="headerlink" title="Chapter 9 — KMS (encryption keys)"></a>Chapter 9 — KMS (encryption keys)</h1>
<p><strong>KMS (Key Management Service)</strong> manages cryptographic keys for AWS services + your own code. Two key kinds:</p>
<table>
<thead>
<tr>
<th>Kind</th>
<th>Use</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>AWS-managed</strong></td>
<td>each service has a default (<code>aws/s3</code>, <code>aws/rds</code>, etc.); free</td>
</tr>
<tr>
<td><strong>Customer-managed (CMK)</strong></td>
<td>you control rotation, key policy, deletion; USD 1 / month / key</td>
</tr>
</tbody>
</table>
<p>For most workloads, the default AWS-managed key is enough. Move to CMKs when:</p>
<ul>
<li>Compliance demands it (HIPAA, FedRAMP).</li>
<li>You want to deny access to specific principals via key policy.</li>
<li>You want to enforce annual rotation.</li>
</ul>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">aws kms create-key --description <span class="hljs-string">&quot;prod app data&quot;</span></span><br><span class="line">aws kms enable-key-rotation --key-id &lt;key-id&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Then use the key when creating an S3 bucket, RDS instance, EBS volume, etc., via the <code>--kms-key-id</code> flag.</p>

<h2 id="Minimum-WAF-setup"><a href="#Minimum-WAF-setup" class="headerlink" title="Minimum WAF setup"></a>Minimum WAF setup</h2>
<p>A WebACL with these managed rule groups attached:</p>
<ul>
<li><code>AWSManagedRulesCommonRuleSet</code> — OWASP top 10 staples.</li>
<li><code>AWSManagedRulesKnownBadInputsRuleSet</code> — known exploit payloads.</li>
<li><code>AWSManagedRulesAmazonIpReputationList</code> — known bad IPs.</li>
<li><code>AWSManagedRulesBotControlRuleSet</code> (paid) — bot detection.</li>
<li>A per-IP rate-based rule (e.g., block IP at 2000 req / 5 min).</li>
</ul>
<p>Cost: USD 5 / WebACL + USD 1 / rule + USD 0.60 / million requests + USD 10 / rule for Bot Control. Affordable for most production sites.</p>

<h1 id="Chapter-12-—-The-production-observability-security-checklist"><a href="#Chapter-12-—-The-production-observability-security-checklist" class="headerlink" title="Chapter 12 — The production observability + security checklist"></a>Chapter 12 — The production observability + security checklist</h1>
<p>For each new workload:</p>
<p><strong>Observability</strong></p>
<ul>
<li>[ ] Every Lambda / service writes structured logs with correlation IDs.</li>
<li>[ ] Every log group has retention ≤ 90 days.</li>
<li>[ ] Every service has dashboards for KPI + utilisation.</li>
<li>[ ] Every critical metric has an alarm with paging SNS subscribers.</li>
<li>[ ] X-Ray (or OpenTelemetry) is on across the request path.</li>
<li>[ ] Cost alarms exist at account level.</li>
</ul>
<p><strong>Security</strong></p>
<ul>
<li>[ ] Root user MFA enabled; root credentials in a vault.</li>
<li>[ ] CloudTrail multi-region trail to encrypted S3, log validation on.</li>
<li>[ ] GuardDuty enabled in all regions.</li>
<li>[ ] Security Hub aggregating findings.</li>
<li>[ ] No long-lived IAM access keys for code; everything uses roles.</li>
<li>[ ] Secrets in Secrets Manager, not in env vars or code.</li>
<li>[ ] S3 buckets: Block Public Access on, encryption on.</li>
<li>[ ] WAF in front of every internet-facing ALB / API Gateway.</li>
<li>[ ] Critical resources protected with deletion-protection / S3 Object Lock for backups.</li>
<li>[ ] Backup retention reviewed (RDS, EBS snapshots, DynamoDB PITR, S3 versioning).</li>
</ul>
