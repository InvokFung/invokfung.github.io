Most modern AWS architectures are not all-server, all-the-time — large parts of them run as <strong>events flowing through serverless glue</strong>. <td>0.5 - 3 s</td>
</tr>

<h2 id="Mitigation"><a href="#Mitigation" class="headerlink" title="Mitigation"></a>Mitigation</h2>
<ul>
<li><strong>Provisioned Concurrency</strong> — keep N warm containers ready; always-on cost.</li>
<li><strong>SnapStart</strong> (Java) — snapshot init state; restore in ~1/10 the time.</li>
<li><strong>Smaller package</strong> — fewer dependencies, faster init.</li>
<li><strong>Avoid VPC unless needed</strong> — ENI attach adds 100-500 ms.</li>
<li><strong>Move heavy setup to module level</strong> — reused across warm invocations.</li>
</ul>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> boto3</span><br><span class="line"><span class="hljs-comment"># initialised once per cold start, reused on warm calls</span></span><br><span class="line">s3 = boto3.client(<span class="hljs-string">&quot;s3&quot;</span>)</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">lambda_handler</span>(<span class="hljs-params">event, context</span>):</span><br><span class="line">    s3.get_object(...)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Sync-vs-async-vs-polling"><a href="#Sync-vs-async-vs-polling" class="headerlink" title="Sync vs async vs polling"></a>Sync vs async vs polling</h2>
<ul>
<li><strong>Sync</strong> — caller waits for response (API Gateway, Function URL, direct <code>RequestResponse</code> invoke).</li>
<li><strong>Async</strong> — Lambda returns immediately, processes in background; failures retried twice + optional DLQ (S3, SNS, EventBridge).</li>
<li><strong>Polling</strong> — Lambda runtime polls SQS / Kinesis / DynamoDB Streams in batches.</li>
</ul>

<h1 id="Chapter-4-—-API-Gateway-and-Function-URLs"><a href="#Chapter-4-—-API-Gateway-and-Function-URLs" class="headerlink" title="Chapter 4 — API Gateway and Function URLs"></a>Chapter 4 — API Gateway and Function URLs</h1>
<p>Two ways to put HTTP in front of Lambda:</p>
<h2 id="API-Gateway-HTTP-API"><a href="#API-Gateway-HTTP-API" class="headerlink" title="API Gateway HTTP API"></a>API Gateway HTTP API</h2>
<ul>
<li>Custom domain + TLS via ACM.</li>
<li>Authn (JWT, Cognito, IAM, Lambda authoriser).</li>
<li>Throttling, usage plans, API keys.</li>
<li>Per-route Lambda integration or HTTP/private integration.</li>
<li>~USD 1 per million requests + data transfer.</li>
</ul>
<p>Minimal wire-up: create HTTP API → add route <code>ANY /{proxy+}</code> → Lambda integration → deploy → get an <code>execute-api.amazonaws.com</code> URL.</p>
<h2 id="Lambda-Function-URL"><a href="#Lambda-Function-URL" class="headerlink" title="Lambda Function URL"></a>Lambda Function URL</h2>
<ul>
<li>One HTTPS endpoint per Lambda.</li>
<li>No API Gateway in between (cheaper, simpler).</li>
<li>No built-in WAF, custom domain (manual via CloudFront), or throttling.</li>
<li>Best for internal tools, webhooks, prototypes.</li>
</ul>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">aws lambda create-function-url-config \</span><br><span class="line">  --function-name hello \</span><br><span class="line">  --auth-type NONE</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="REST-API-older"><a href="#REST-API-older" class="headerlink" title="REST API (older)"></a>REST API (older)</h2>
<p>The older &quot;REST API&quot; flavour exists for compatibility (request validation, models, X-Ray detail). For new projects in 2026, <strong>HTTP API</strong> is the right default.</p>

<h1 id="Chapter-5-—-SQS-Simple-Queue-Service"><a href="#Chapter-5-—-SQS-Simple-Queue-Service" class="headerlink" title="Chapter 5 — SQS (Simple Queue Service)"></a>Chapter 5 — SQS (Simple Queue Service)</h1>
<p>SQS is a managed message queue. Producers <code>send-message</code>, consumers (often Lambda) <code>receive-message</code> + <code>delete-message</code> after success.</p>
<p>Two queue types:</p>
<table>
<thead>
<tr>
<th>Type</th>
<th>Order</th>
<th>Duplicates</th>
<th>Use</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Standard</strong></td>
<td>best-effort</td>
<td>possible</td>
<td>most async work</td>
</tr>
<tr>
<td><strong>FIFO</strong></td>
<td>strict per group</td>
<td>exactly-once</td>
<td>order-sensitive workflows</td>
</tr>
</tbody>
</table>
<h2 id="Lambda-SQS-pattern"><a href="#Lambda-SQS-pattern" class="headerlink" title="Lambda + SQS pattern"></a>Lambda + SQS pattern</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">[API or Service A] → SQS Standard → [Lambda processes in batches]</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Benefits:</p>
<ul>
<li><strong>Decoupling</strong> — A returns immediately; processing runs in background.</li>
<li><strong>Back-pressure</strong> — if Lambda concurrency caps, messages sit in queue (no data loss).</li>
<li><strong>Retries</strong> — Lambda errors keep message visible; goes to <strong>DLQ</strong> after N attempts.</li>
<li><strong>Batch processing</strong> — Lambda receives up to 10 messages at once.</li>
</ul>
<h2 id="Visibility-timeout"><a href="#Visibility-timeout" class="headerlink" title="Visibility timeout"></a>Visibility timeout</h2>
<p>When a consumer receives a message, it becomes invisible to others for the <strong>visibility timeout</strong> (default 30 sec). If not deleted by then, the message reappears for another consumer. Set this to at least 2× your processing time.</p>
<h2 id="Dead-Letter-Queue-DLQ"><a href="#Dead-Letter-Queue-DLQ" class="headerlink" title="Dead Letter Queue (DLQ)"></a>Dead Letter Queue (DLQ)</h2>
<p>Configure a DLQ on a source queue. After N receive attempts (typical: 3-5), the message moves to the DLQ for inspection. Alarm on DLQ message count &gt; 0 — that means production has a stuck pattern.</p>

<h1 id="Chapter-6-—-SNS-Simple-Notification-Service"><a href="#Chapter-6-—-SNS-Simple-Notification-Service" class="headerlink" title="Chapter 6 — SNS (Simple Notification Service)"></a>Chapter 6 — SNS (Simple Notification Service)</h1>
<p>SNS is <strong>pub/sub fanout</strong> — a publisher sends one message to a topic; AWS delivers a copy to every subscriber.</p>
<p>Subscriber types:</p>
<ul>
<li>SQS queue</li>
<li>Lambda</li>
<li>HTTPS endpoint</li>
<li>Email / SMS</li>
<li>Mobile push</li>
<li>Kinesis Firehose</li>
</ul>
<h2 id="Common-fanout-pattern"><a href="#Common-fanout-pattern" class="headerlink" title="Common fanout pattern"></a>Common fanout pattern</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="text"><span class="line">[Order Service]</span><br><span class="line">      │ publish &quot;order_placed&quot;</span><br><span class="line">      ▼</span><br><span class="line">   [SNS topic]</span><br><span class="line">      ├── → SQS for inventory service</span><br><span class="line">      ├── → SQS for email service</span><br><span class="line">      ├── → Lambda for analytics</span><br><span class="line">      └── → SQS for fulfilment service</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p><strong>Trick:</strong> SNS for simple fanout (one source → many same-message subscribers). <h1 id="Chapter-10-—-When-NOT-to-use-serverless"><a href="#Chapter-10-—-When-NOT-to-use-serverless" class="headerlink" title="Chapter 10 — When NOT to use serverless"></a>Chapter 10 — When NOT to use serverless</h1>
<ul>
<li>Long-running CPU jobs (&gt; 15 min) — use Step Functions (Post 06), ECS Fargate, or AWS Batch.</li>
<li>Steady high-throughput services where always-on EC2 / Fargate is cheaper than per-request Lambda billing.</li>
<li>Cold-start-sensitive workloads where even 100 ms hurts and Provisioned Concurrency cost wipes the savings.</li>
<li>Heavy WebSocket / persistent connections — use API Gateway WebSocket + Lambda or ECS.</li>
</ul>
<p>Serverless wins when traffic is spiky, glue-shaped, or genuinely event-driven. Steady-state high-CPU workloads belong on Fargate / EC2.</p>
