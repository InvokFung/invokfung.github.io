<h2 id="ALB-headline-features"><a href="#ALB-headline-features" class="headerlink" title="ALB headline features"></a>ALB headline features</h2>
<ul>
<li><strong>Host-based routing</strong> — <code>api.example.com</code> → service A, <code>app.example.com</code> → service B.</li>
<li><strong>Path-based routing</strong> — <code>/v1/*</code> → service A, <code>/v2/*</code> → service B.</li>
<li><strong>Header / query-param matching</strong> in listener rules.</li>
<li><strong>WebSocket</strong> and <strong>gRPC</strong> support.</li>
<li><strong>TLS termination</strong> with certs from ACM.</li>
<li><strong>AWS WAF</strong> integration.</li>
<li><strong>Cognito / OIDC authentication</strong> at the listener.</li>
<li><strong>Sticky sessions</strong> via cookies.</li>
</ul>
<h2 id="NLB-headline-features"><a href="#NLB-headline-features" class="headerlink" title="NLB headline features"></a>NLB headline features</h2>
<ul>
<li>Static <strong>per-AZ IP</strong> (or your own Elastic IPs).</li>
<li>Millions of requests/sec with sub-millisecond added latency.</li>
<li>Preserves the <strong>client source IP</strong> at the backend.</li>
<li>Supports the <strong><code>PROXY</code> protocol</strong> for backends that want the original peer IP.</li>
</ul>

<h1 id="Chapter-2-—-Target-groups"><a href="#Chapter-2-—-Target-groups" class="headerlink" title="Chapter 2 — Target groups"></a>Chapter 2 — Target groups</h1>
<p>A target group is a registered list of &quot;things that can serve traffic&quot;. A listener forwards based on rules to one or more target groups.</p>
<p>Target types:</p>
<ul>
<li><strong>instance</strong> — by EC2 instance ID</li>
<li><strong>ip</strong> — for ECS tasks, on-prem hosts via Direct Connect</li>
<li><strong>lambda</strong> — invoke a Lambda per request (ALB only)</li>
<li><strong>alb</strong> — chain an ALB behind an NLB (advanced)</li>
</ul>

<p><strong>Watch out:</strong> an overly aggressive check (1 second, 1 failure → unhealthy) marks healthy targets bad during minor blips. An overly relaxed check (60 seconds, 5 failures) lets bad targets serve traffic for minutes.</p>
<h2 id="Three-common-health-check-mistakes"><a href="#Three-common-health-check-mistakes" class="headerlink" title="Three common health-check mistakes"></a>Three common health-check mistakes</h2>
<ol>
<li>The <code>/health</code> endpoint also checks a downstream DB → a single DB hiccup marks every target unhealthy → outage. Make <code>/health</code> a <strong>shallow liveness</strong> check; add <code>/ready</code> for dependency health.</li>
<li>The endpoint requires auth. The LB has no credentials → 401 → all targets appear unhealthy.</li>
<li>The endpoint runs an expensive query. ALB poll × target count multiplies the load.</li>
</ol>

<h1 id="Chapter-3-—-Listeners-and-routing-rules"><a href="#Chapter-3-—-Listeners-and-routing-rules" class="headerlink" title="Chapter 3 — Listeners and routing rules"></a>Chapter 3 — Listeners and routing rules</h1>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line">ALB</span><br><span class="line">└── Listener: HTTPS 443  (cert from ACM)</span><br><span class="line">    ├── Rule 1: Host = api.example.com           → forward to tg-api</span><br><span class="line">    ├── Rule 2: Path = /admin/*                  → forward to tg-admin</span><br><span class="line">    ├── Rule 3: Header X-Canary = true           → forward to tg-canary</span><br><span class="line">    └── Default                                   → forward to tg-web</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Common patterns:</p>
<ul>
<li><strong>HTTP → HTTPS redirect</strong> — a port 80 listener with a single redirect rule to 443.</li>
<li><strong>Canary</strong> — header/cookie-based routing to a small target group running a new version.</li>
<li><strong>Maintenance page</strong> — fixed-response rule returning a static 503 + HTML.</li>
<li><strong>Weighted target groups</strong> — split a percentage of traffic for blue/green.</li>
</ul>
<hr>
<h1 id="Chapter-4-—-Auto-Scaling-Group-ASG"><a href="#Chapter-4-—-Auto-Scaling-Group-ASG" class="headerlink" title="Chapter 4 — Auto Scaling Group (ASG)"></a>Chapter 4 — Auto Scaling Group (ASG)</h1>
<p>An ASG maintains a fleet of EC2 instances at a target capacity, replaces unhealthy ones automatically, and scales up/down based on policies.</p>
<h2 id="Anatomy"><a href="#Anatomy" class="headerlink" title="Anatomy"></a>Anatomy</h2>
<ul>
<li><strong>Launch template</strong> — AMI, instance type, key, SGs, user data. (Replaces older &quot;launch configuration&quot;.)</li>
<li><strong>Min / Desired / Max</strong> — capacity bounds.</li>
<li><strong>VPC zone identifier</strong> — list of subnets (one per AZ).</li>
<li><strong>Health-check type</strong> — <code>EC2</code> (instance status) or <code>ELB</code> (target-group health). Always pick <code>ELB</code> if the ASG is behind a load balancer.</li>
<li><strong>Target groups</strong> — the ASG registers / deregisters instances automatically as they come and go.</li>
</ul>
<h2 id="A-minimal-ASG"><a href="#A-minimal-ASG" class="headerlink" title="A minimal ASG"></a>A minimal ASG</h2>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span><br><span class="line">17</span><br><span class="line">18</span><br><span class="line">19</span><br><span class="line">20</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># launch template</span></span><br><span class="line">aws ec2 create-launch-template \</span><br><span class="line">  --launch-template-name web-template \</span><br><span class="line">  --launch-template-data <span class="hljs-string">&#x27;{</span><br><span class="line">    &quot;ImageId&quot;:&quot;ami-XXXXXXXX&quot;,</span><br><span class="line">    &quot;InstanceType&quot;:&quot;t3.micro&quot;,</span><br><span class="line">    &quot;SecurityGroupIds&quot;:[&quot;sg-XXXXXXXX&quot;],</span><br><span class="line">    &quot;UserData&quot;:&quot;&#x27;</span>$(<span class="hljs-built_in">base64</span> -w0 user-data.sh)<span class="hljs-string">&#x27;&quot;,</span><br><span class="line">    &quot;IamInstanceProfile&quot;:{&quot;Name&quot;:&quot;web-instance-profile&quot;}</span><br><span class="line">  }&#x27;</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># the ASG itself</span></span><br><span class="line">aws autoscaling create-auto-scaling-group \</span><br><span class="line">  --auto-scaling-group-name web-asg \</span><br><span </span></code></pre></td></tr></table></figure></code></pre>
<p><code>user-data.sh</code> runs on first boot — install your app, fetch config, register with discovery.</p>
<hr>
<h1 id="Chapter-5-—-Scaling-policies"><a href="#Chapter-5-—-Scaling-policies" class="headerlink" title="Chapter 5 — Scaling policies"></a>Chapter 5 — Scaling policies</h1>
<h2 id="Target-tracking-start-here"><a href="#Target-tracking-start-here" class="headerlink" title="Target tracking (start here)"></a>Target tracking (start here)</h2>
<p>Pick a metric and a target; AWS adds/removes instances to keep the metric there.</p>
<ul>
<li>&quot;Average CPU = 50%&quot; → scale out when &gt; 50, in when &lt; 50.</li>
<li>&quot;ALB requests per target = 200&quot; → scale to meet load.</li>
</ul>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="bash"><span class="line">aws autoscaling put-scaling-policy \</span><br><span class="line">  --auto-scaling-group-name web-asg \</span><br><span class="line">  --policy-name cpu-target \</span><br><span class="line">  --policy-type TargetTrackingScaling \</span><br><span class="line">  --target-tracking-configuration <span class="hljs-string">&#x27;{</span><br><span class="line">    &quot;PredefinedMetricSpecification&quot;: { &quot;PredefinedMetricType&quot;: &quot;ASGAverageCPUUtilization&quot; },</span><br><span class="line">    &quot;TargetValue&quot;: 50.0</span><br><span class="line">  }&#x27;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Step-scaling"><a href="#Step-scaling" class="headerlink" title="Step scaling"></a>Step scaling</h2>
<p>Trigger at thresholds; add/remove a configurable count per step. Use when target tracking can't express the logic — e.g., asymmetric scale-out vs scale-in speeds.</p>
<h2 id="Scheduled"><a href="#Scheduled" class="headerlink" title="Scheduled"></a>Scheduled</h2>
<p>Predictable patterns deserve scheduled scaling — flash sale, market open, weekday morning ramp.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="bash"><span class="line">aws autoscaling put-scheduled-update-group-action \</span><br><span class="line">  --auto-scaling-group-name web-asg \</span><br><span class="line">  --scheduled-action-name morning-warmup \</span><br><span class="line">  --recurrence <span class="hljs-string">&quot;0 9 * * 1-5&quot;</span> \</span><br><span class="line">  --desired-capacity 20 --min-size 20</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Trick:</strong> schedule warm-up <strong>15 minutes before</strong> a known spike. EC2 + ASG instances take 1-3 minutes from request to &quot;in service&quot;.</p>
<hr>
<h1 id="Chapter-6-—-Cooldowns-warm-pools-instance-refresh"><a href="#Chapter-6-—-Cooldowns-warm-pools-instance-refresh" class="headerlink" title="Chapter 6 — Cooldowns, warm pools, instance refresh"></a>Chapter 6 — Cooldowns, warm pools, instance refresh</h1>
<h2 id="Cooldown"><a href="#Cooldown" class="headerlink" title="Cooldown"></a>Cooldown</h2>
<p>A waiting period after a scaling action before evaluating again — prevents oscillation when metrics dip slightly post-action.</p>
<h2 id="Warm-pool"><a href="#Warm-pool" class="headerlink" title="Warm pool"></a>Warm pool</h2>
<p>A pool of pre-initialised but <strong>stopped</strong> instances. When the ASG needs to scale, it starts (rather than provisions) one — seconds vs minutes. Cost: EBS storage of the warm instances.</p>
<h2 id="Instance-refresh"><a href="#Instance-refresh" class="headerlink" title="Instance refresh"></a>Instance refresh</h2>
<p>When you publish a new launch-template version (new AMI, new user-data), <code>start-instance-refresh</code> rolls existing instances out in batches.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">aws autoscaling start-instance-refresh \</span><br><span class="line">  --auto-scaling-group-name web-asg \</span><br><span class="line">  --preferences <span class="hljs-string">&#x27;{&quot;MinHealthyPercentage&quot;:90,&quot;InstanceWarmup&quot;:120}&#x27;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Pair with ALB weighted target groups or canary listener rules for safe rollouts.</p>
<hr>
<h1 id="Chapter-7-—-The-textbook-3-tier-reference"><a href="#Chapter-7-—-The-textbook-3-tier-reference" class="headerlink" title="Chapter 7 — The textbook 3-tier reference"></a>Chapter 7 — The textbook 3-tier reference</h1>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span></pre></td><td class="code"><pre><code class="text"><span class="line">              ┌─────────────────────────────┐</span><br><span class="line">              │         Route 53            │   DNS</span><br><span class="line">              └────────────┬────────────────┘</span><br><span class="line">                           │</span><br><span class="line">              ┌────────────┴────────────────┐</span><br><span class="line">              │   ALB (public subnets)      │   HTTPS, WAF attached</span><br><span class="line">              └────────────┬────────────────┘</span><br><span class="line">                           │  http → 8080</span><br><span class="line">              ┌────────────┴────────────────┐</span><br><span class="line">              │  ASG of EC2 (private subnets)│   app tier, multi-AZ</span><br><span class="line">              └────────────┬────────────────┘</span><br><span class="line">                           │  tcp → 5432</span><br><span class="line">              ┌────────────┴────────────────┐</span><br><span class="line">              │   RDS multi-AZ (isolated)   │   data tier</span><br><span class="line">              └─────────────────────────────┘</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Tier rules:</p>
<ul>
<li>ALB lives in public subnets across ≥ 2 AZs.</li>
<li>App tier lives in private subnets across the same AZs.</li>
<li>DB tier lives in isolated subnets, accessible only from the app SG.</li>
<li>Each tier's security group only accepts traffic from the tier above's SG.</li>
<li>Outbound from app tier to internet via NAT (only for pulling packages, calling external APIs).</li>
</ul>
<p>This shape survives:</p>
<ul>
<li>a single instance failure (ASG replaces it)</li>
<li>a single AZ failure (other AZs absorb traffic)</li>
<li>a deploy with bad code (canary catches it; instance refresh rolls back)</li>
<li>a traffic spike (ASG scales out)</li>
</ul>

<h1 id="Chapter-9-—-Beyond-EC2-ASG"><a href="#Chapter-9-—-Beyond-EC2-ASG" class="headerlink" title="Chapter 9 — Beyond EC2 + ASG"></a>Chapter 9 — Beyond EC2 + ASG</h1>
<p>Modern compute alternatives to consider for the app tier:</p>
<ul>
<li><strong>ECS Fargate</strong> — containers without managing EC2 hosts.</li>
<li><strong>EKS</strong> — Kubernetes managed control plane.</li>
<li><strong>App Runner</strong> — push a container, AWS does the rest.</li>
<li><strong>Lambda behind ALB</strong> — short-lived, infrequent endpoints (Post 05).</li>
</ul>
<p>EC2 + ASG remains right when you need OS access, GPU, NVMe, or want the lowest level of abstraction. Otherwise consider going up the stack — Post 05 covers serverless, future posts cover containers.</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Two-EC2-ALB-by-hand"><a href="#Exercise-1-—-Two-EC2-ALB-by-hand" class="headerlink" title="Exercise 1 — Two EC2 + ALB by hand"></a>Exercise 1 — Two EC2 + ALB by hand</h2>
<ol>
<li>Launch 2 EC2 instances in 2 AZs, each serving a tiny HTTP &quot;hello from <code>&lt;hostname&gt;</code>&quot;.</li>
<li>Create a target group; register both.</li>
<li>Create an ALB on port 80 → target group.</li>
<li>Hit the ALB DNS name 10 times; observe both hostnames in responses.</li>
<li>Stop one instance; verify it's marked unhealthy in ≤ 2 minutes and only the survivor receives traffic.</li>
</ol>
<h2 id="Exercise-2-—-Convert-to-ASG"><a href="#Exercise-2-—-Convert-to-ASG" class="headerlink" title="Exercise 2 — Convert to ASG"></a>Exercise 2 — Convert to ASG</h2>
<p>Tear down Exercise 1; rebuild with:</p>
<ul>
<li>a launch template producing the same web instance,</li>
<li>ASG min 2 / desired 2 / max 6 across the same AZs,</li>
<li>the target group attached to the ASG,</li>
<li>a target-tracking policy on CPU 50%.</li>
</ul>
<p>Run <code>stress</code> on one instance to push CPU &gt; 70% and watch the ASG add an instance.</p>
<h2 id="Exercise-3-—-Host-based-routing"><a href="#Exercise-3-—-Host-based-routing" class="headerlink" title="Exercise 3 — Host-based routing"></a>Exercise 3 — Host-based routing</h2>
<p>Add a second target group with a different <code>/health</code> payload. Add an ALB listener rule:</p>
<ul>
<li><code>api.&lt;your-domain&gt;</code> → tg-api,</li>
<li>default → tg-web.</li>
</ul>
<p>Then test canary routing with <code>X-Canary: true</code> header.</p>
<h2 id="Exercise-4-—-Failure-drill"><a href="#Exercise-4-—-Failure-drill" class="headerlink" title="Exercise 4 — Failure drill"></a>Exercise 4 — Failure drill</h2>
<p>Terminate the ASG's instances manually (<code>aws ec2 terminate-instances</code>). Observe the ASG replace them. Note total recovery time end-to-end.</p>
<h2 id="Exercise-5-—-Cost-audit"><a href="#Exercise-5-—-Cost-audit" class="headerlink" title="Exercise 5 — Cost audit"></a>Exercise 5 — Cost audit</h2>
<p>Pull last month's bill for ALB + ASG + NAT + data transfer. Sum the components; identify the largest line item. Suggest one concrete change to shrink it (smaller types, Spot, fewer AZs, S3 endpoint for NAT-bypass).</p>
