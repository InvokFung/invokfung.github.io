<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Choose between RDS, Aurora, DynamoDB, ElastiCache for a given workload.</li>
<li>Configure RDS Multi-AZ for HA and read replicas for read scaling.</li>
<li>Use Aurora's storage layer and serverless V2 mode.</li>

<h1 id="Chapter-2-—-RDS"><a href="#Chapter-2-—-RDS" class="headerlink" title="Chapter 2 — RDS"></a>Chapter 2 — RDS</h1>
<p><strong>RDS (Relational Database Service)</strong> runs PostgreSQL, MySQL, MariaDB, Oracle, or SQL Server on EC2 + EBS, managed by AWS. You get:</p>
<ul>
<li>Daily automated backups + point-in-time recovery (1-35 days).</li>
<li>Multi-AZ failover (synchronous replica in another AZ; automatic promotion).</li>
<li>Up to 15 <strong>read replicas</strong> for read scaling.</li>
<li>Maintenance windows for patching.</li>
<li>IAM authentication, KMS encryption at rest, TLS in transit.</li>
</ul>
<p>What you give up: full OS access. You can't run <code>sudo</code> on an RDS host or install custom Postgres extensions outside AWS's approved list.</p>

<h2 id="Backups"><a href="#Backups" class="headerlink" title="Backups"></a>Backups</h2>
<ul>
<li><strong>Automated snapshots</strong> — every day, retained 1-35 days, free for active DBs.</li>
<li><strong>Manual snapshots</strong> — kept until you delete them.</li>
<li><strong>Point-in-time restore</strong> — recover to any second within the retention window (writes go to transaction logs in S3).</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> RDS lets you spin up a <strong>new DB from a snapshot in seconds</strong> for testing. Great for &quot;show me prod data from yesterday in a sandbox&quot; workflows. Just remember to delete it after.</p>
</blockquote>

<h1 id="Chapter-3-—-Aurora"><a href="#Chapter-3-—-Aurora" class="headerlink" title="Chapter 3 — Aurora"></a>Chapter 3 — Aurora</h1>
<p><strong>Aurora</strong> is AWS's cloud-native rewrite of MySQL and PostgreSQL. Compatible at the wire level, but with a custom storage engine that:</p>
<ul>
<li>Replicates data across <strong>6 copies in 3 AZs</strong> automatically.</li>
<li>Can survive losing 2 copies without data loss, 3 without losing read.</li>
<li>Auto-grows storage in 10 GB chunks up to 128 TB.</li>
<li>Provides up to 15 read replicas that share the same storage layer (lag in single-digit ms).</li>
</ul>
<h2 id="Aurora-vs-RDS"><a href="#Aurora-vs-RDS" class="headerlink" title="Aurora vs RDS"></a>Aurora vs RDS</h2>
<table>
<thead>
<tr>
<th>Trait</th>
<th>RDS</th>
<th>Aurora</th>
</tr>
</thead>
<tbody>
<tr>
<td>Engines</td>
<td>many</td>
<td>Postgres / MySQL compatible only</td>
</tr>
<tr>
<td>Storage</td>
<td>EBS (provisioned)</td>
<td>shared cluster volume, auto-grow</td>
</tr>
<tr>
<td>Throughput vs vanilla</td>
<td>baseline</td>
<td>up to 3-5× MySQL, 2-3× Postgres</td>
</tr>
<tr>
<td>Cost</td>
<td>cheaper at small scale</td>
<td>costlier baseline, cheaper at scale</td>
</tr>
<tr>
<td>Best for</td>
<td>low-traffic apps, small teams</td>
<td>production OLTP at scale, SaaS</td>
</tr>
</tbody>
</table>
<h2 id="Aurora-Serverless-V2"><a href="#Aurora-Serverless-V2" class="headerlink" title="Aurora Serverless V2"></a>Aurora Serverless V2</h2>
<p>Aurora Serverless V2 scales the compute capacity (<code>ACU</code> — Aurora Capacity Units) up and down with load, in fractions of an ACU. Used to be best for unpredictable workloads; in 2026 it's mature enough to be a viable default for new Aurora clusters.</p>
<hr>
<h1 id="Chapter-4-—-DynamoDB"><a href="#Chapter-4-—-DynamoDB" class="headerlink" title="Chapter 4 — DynamoDB"></a>Chapter 4 — DynamoDB</h1>
<p><strong>DynamoDB</strong> is a fully managed NoSQL key-value + document store. Single-digit millisecond latency at any scale. No servers to provision, no AZ design — AWS handles all of it.</p>
<p>Trade-offs vs SQL:</p>
<ul>
<li>No joins (denormalise instead).</li>
<li>Limited transactional support (single-region transactions OK; multi-region eventual).</li>
<li>Query patterns must be <strong>designed first</strong> — DynamoDB tables are not &quot;queried like SQL&quot;; you access by key.</li>
</ul>
<h2 id="Table-schema"><a href="#Table-schema" class="headerlink" title="Table schema"></a>Table schema</h2>
<p>A table has:</p>
<ul>
<li>A <strong>partition key</strong> (mandatory) — determines which physical partition stores the item.</li>
<li>An optional <strong>sort key</strong> — orders items within a partition.</li>
<li>Items are JSON-like documents with arbitrary attributes.</li>
<li><strong>Secondary indexes</strong> (Global or Local) let you query by other attributes.</li>
</ul>

<p>Start with on-demand; switch to provisioned once you have a stable traffic profile and the cost gap matters.</p>
<h2 id="Streams-change-capture"><a href="#Streams-change-capture" class="headerlink" title="Streams + change capture"></a>Streams + change capture</h2>
<p><strong>DynamoDB Streams</strong> publishes every item-level change for 24 hours. Wire to Lambda for:</p>
<ul>
<li>replication to another store (S3, OpenSearch, another region),</li>
<li>audit trails,</li>
<li>triggering downstream workflows.</li>
</ul>
<h2 id="Single-table-design"><a href="#Single-table-design" class="headerlink" title="Single-table design"></a>Single-table design</h2>
<p>Power users put <strong>multiple entity types in one table</strong> with carefully designed key patterns. Higher learning curve but lower cost and faster queries. Worth reading Alex DeBrie's <em>The DynamoDB Book</em> when ready.</p>
<hr>
<h1 id="Chapter-5-—-ElastiCache"><a href="#Chapter-5-—-ElastiCache" class="headerlink" title="Chapter 5 — ElastiCache"></a>Chapter 5 — ElastiCache</h1>
<p><strong>ElastiCache</strong> runs Redis or Memcached as a managed service. Two flavours:</p>
<table>
<thead>
<tr>
<th>Engine</th>
<th>Best for</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Redis (ElastiCache for Redis)</strong></td>
<td>rich data structures, pub/sub, persistence, replicas, cluster mode</td>
</tr>
<tr>
<td><strong>Memcached</strong></td>
<td>pure cache, multi-threaded, simpler</td>
</tr>
</tbody>
</table>
<p>Modern AWS also offers <strong>MemoryDB for Redis</strong> — Redis-compatible with multi-AZ durable storage (effectively Redis-as-a-database). Use when you need Redis semantics plus durability.</p>
<h2 id="Cache-patterns"><a href="#Cache-patterns" class="headerlink" title="Cache patterns"></a>Cache patterns</h2>
<ul>
<li><strong>Cache-aside (lazy loading)</strong> — app reads from cache first; on miss, query DB and populate.</li>
<li><strong>Write-through</strong> — every DB write also updates the cache.</li>
<li><strong>TTL eviction</strong> — auto-expire entries after a duration.</li>
<li><strong>Session store</strong> — sticky-session alternative for stateless app servers.</li>
<li><strong>Rate limiting / leaderboards</strong> — natural Redis use cases.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> when adding a cache to fix a slow query, set a short TTL (60-300 sec) at first. Lets you measure hit rate and roll back without stale-data risk. Expand TTL once you're confident the data tolerates it.</p>
</blockquote>

<hr>
<h1 id="Chapter-8-—-Migration-shortcuts"><a href="#Chapter-8-—-Migration-shortcuts" class="headerlink" title="Chapter 8 — Migration shortcuts"></a>Chapter 8 — Migration shortcuts</h1>
<ul>
<li><strong>DMS (Database Migration Service)</strong> — continuous replication from one DB to another (on-prem → RDS, MySQL → Aurora, RDS → DynamoDB).</li>
<li><strong>AWS Schema Conversion Tool (SCT)</strong> — convert schemas + stored procedures between engines.</li>
<li><strong><code>pg_dump</code> / <code>mysqldump</code></strong> still work fine for small one-shot loads.</li>
</ul>
<p>For production cut-overs, the DMS &quot;ongoing-replication then cut&quot; pattern is the safe playbook.</p>

<h2 id="Exercise-1-—-RDS-Postgres-Multi-AZ"><a href="#Exercise-1-—-RDS-Postgres-Multi-AZ" class="headerlink" title="Exercise 1 — RDS Postgres Multi-AZ"></a>Exercise 1 — RDS Postgres Multi-AZ</h2>
<p>Create an RDS Postgres <code>db.t4g.micro</code> Multi-AZ in the isolated subnets of the VPC from Post 01. Confirm:</p>
<ul>
<li>the standby in another AZ exists,</li>
<li>the master endpoint resolves to the active node,</li>
<li>a forced failover (<code>reboot-db-instance --force-failover</code>) flips traffic within 60-120 sec.</li>
</ul>
<h2 id="Exercise-2-—-Read-replica"><a href="#Exercise-2-—-Read-replica" class="headerlink" title="Exercise 2 — Read replica"></a>Exercise 2 — Read replica</h2>
<p>Add a read replica to the Exercise 1 DB. Point a read-only client (e.g., <code>psql --readonly</code>) at the replica endpoint. Verify writes fail on the replica, succeed on the primary.</p>
<h2 id="Exercise-3-—-DynamoDB-design"><a href="#Exercise-3-—-DynamoDB-design" class="headerlink" title="Exercise 3 — DynamoDB design"></a>Exercise 3 — DynamoDB design</h2>
<p>Design a DynamoDB table for a simple URL shortener:</p>
<ul>
<li>partition key: <code>short_code</code> (string)</li>
<li>attributes: <code>long_url</code>, <code>created_at</code>, <code>hits</code></li>
<li>secondary requirement: list 100 most recent short codes</li>
</ul>
<p>What partition/sort key and (if needed) GSI satisfies both access patterns?</p>
<details>
<summary>One valid answer</summary>
<ul>
<li>Table partition key: <code>short_code</code> (for direct lookup).</li>
<li>GSI: partition key <code>gsi_pk</code> (always literal <code>&quot;ALL&quot;</code>), sort key <code>created_at</code>. Query the GSI with <code>pk = &quot;ALL&quot;</code>, sorted descending, limit 100.</li>
</ul>
<p>Note the GSI pattern: cramming everything into one partition is fine at low scale but won't scale to massive write throughput; that's where you'd shard <code>gsi_pk</code> (e.g., by date).</p>
</details>
<h2 id="Exercise-4-—-Cache-aside"><a href="#Exercise-4-—-Cache-aside" class="headerlink" title="Exercise 4 — Cache-aside"></a>Exercise 4 — Cache-aside</h2>
<p>Add ElastiCache Redis in front of the RDS from Exercise 1. Implement a simple Python service that:</p>
<ul>
<li>on <code>GET /user/{id}</code> checks Redis first,</li>
<li>on miss, queries Postgres, populates Redis with TTL 60 sec,</li>
<li>on <code>POST /user/{id}</code> writes Postgres and invalidates the Redis key.</li>
</ul>
<p>Measure hit-rate after warm-up.</p>
<h2 id="Exercise-5-—-DynamoDB-Streams-to-Lambda"><a href="#Exercise-5-—-DynamoDB-Streams-to-Lambda" class="headerlink" title="Exercise 5 — DynamoDB Streams to Lambda"></a>Exercise 5 — DynamoDB Streams to Lambda</h2>
<p>Enable Streams on the table from Exercise 3. Hook up a Lambda that logs every change. Confirm in CloudWatch Logs.</p>
