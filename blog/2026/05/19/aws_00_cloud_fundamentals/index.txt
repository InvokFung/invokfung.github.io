<h1 id="Chapter-1-—-What-the-cloud-is"><a href="#Chapter-1-—-What-the-cloud-is" class="headerlink" title="Chapter 1 — What the cloud is"></a>Chapter 1 — What the cloud is</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Cloud computing</strong> — renting compute, storage, network, and services from a provider on-demand, billed by usage rather than capital purchase.</li>
<li><strong>Region</strong> — a geographic area (e.g., <code>us-east-1</code> in Northern Virginia, <code>ap-east-1</code> in Hong Kong). Each region is fully independent.</li>
<li><strong>Availability Zone (AZ)</strong> — one or more isolated data centres inside a region, connected by low-latency links. Each region has ≥ 3 AZs.</li>
<li><strong>Edge location</strong> — smaller PoPs (point of presence) used by CloudFront (CDN) and Route 53 (DNS). Hundreds worldwide.</li>
<li><strong>Service</strong> — a single AWS product. EC2, S3, Lambda are services.</li>
<li><strong>API</strong> — every AWS service is driven by an HTTPS API. Console, CLI, SDKs, and IaC tools all call the same APIs underneath.</li>
</ul>

<h1 id="Chapter-2-—-Regions-and-AZs"><a href="#Chapter-2-—-Regions-and-AZs" class="headerlink" title="Chapter 2 — Regions and AZs"></a>Chapter 2 — Regions and AZs</h1>
<p>Each AWS service runs in a particular region. Resources in <code>us-east-1</code> are <em>not visible</em> from <code>eu-west-1</code> by default — they're separate accounts of the same service.</p>
<h2 id="Choosing-a-region"><a href="#Choosing-a-region" class="headerlink" title="Choosing a region"></a>Choosing a region</h2>
<table>
<thead>
<tr>
<th>Criterion</th>
<th>Example</th>
</tr>
</thead>
<tbody>
<tr>
<td>Latency to users</td>
<td>Hong Kong users → <code>ap-east-1</code></td>
</tr>
<tr>
<td>Data sovereignty / regulation</td>
<td>EU customer data → <code>eu-central-1</code> (Frankfurt)</td>
</tr>
<tr>
<td>Service availability</td>
<td>newest services launch first in <code>us-east-1</code>, <code>us-west-2</code></td>
</tr>
<tr>
<td>Price</td>
<td><code>us-east-1</code> and <code>us-west-2</code> are usually cheapest</td>
</tr>

<p><strong>Watch out:</strong> <code>us-east-1</code> is the &quot;default region&quot; for many global services (IAM, CloudFront, Route 53 hosted-zone APIs). Many tutorials assume <code>us-east-1</code> implicitly.</p>
<h2 id="Multi-AZ-for-high-availability"><a href="#Multi-AZ-for-high-availability" class="headerlink" title="Multi-AZ for high availability"></a>Multi-AZ for high availability</h2>
<p>A region has at least 3 AZs (e.g., <code>us-east-1a</code>, <code>us-east-1b</code>, <code>us-east-1c</code>). Each AZ is a separate building with separate power. <strong>Production workloads spread across ≥ 2 AZs</strong> so a single-AZ outage doesn't take down the system.</p>

<h1 id="Chapter-3-—-Account-billing-and-the-root-user"><a href="#Chapter-3-—-Account-billing-and-the-root-user" class="headerlink" title="Chapter 3 — Account, billing, and the root user"></a>Chapter 3 — Account, billing, and the root user</h1>
<p>When you sign up at <a href="https://aws.amazon.com" target="_blank" rel="noopener external nofollow noreferrer">aws.amazon.com</a>, you create the <strong>root user</strong> — an account-wide super-admin tied to your email + credit card.</p>
<h2 id="The-rules-everyone-learns-the-hard-way"><a href="#The-rules-everyone-learns-the-hard-way" class="headerlink" title="The rules everyone learns the hard way"></a>The rules everyone learns the hard way</h2>
<ol>
<li><strong>Never use the root user for daily work.</strong> Log in once, set up MFA, create an IAM admin user, then log out.</li>
<li><strong>Enable MFA on the root user immediately</strong> — preferably a hardware key or a TOTP app.</li>
<li><strong>Set a billing alert</strong> before deploying anything. AWS has no built-in spending cap; you can rack up $5,000 in a misconfigured stack overnight.</li>
<li><strong>Tag every resource</strong> with at least an owner and environment tag — for cost allocation later.</li>
</ol>
<h2 id="Billing-alert-5-minute-setup"><a href="#Billing-alert-5-minute-setup" class="headerlink" title="Billing alert (5-minute setup)"></a>Billing alert (5-minute setup)</h2>
<ol>
<li>Console → <em>Billing</em> → <em>Billing preferences</em> → enable &quot;Receive Billing Alerts&quot;.</li>
<li>CloudWatch → <em>Alarms</em> → create a billing alarm at, say, USD 10 / month.</li>
<li>Subscribe your email to the SNS topic.</li>
</ol>
<p>The alarm needs to be created in <code>us-east-1</code> (billing metrics live there).</p>
<hr>
<h1 id="Chapter-4-—-IAM-Identity-and-Access-Management"><a href="#Chapter-4-—-IAM-Identity-and-Access-Management" class="headerlink" title="Chapter 4 — IAM (Identity and Access Management)"></a>Chapter 4 — IAM (Identity and Access Management)</h1>
<p>IAM is <strong>how AWS knows who you are and what you're allowed to do</strong>. Five concepts:</p>
<table>
<thead>
<tr>
<th>Concept</th>
<th>What</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>User</strong></td>
<td>A human (or app key pair). Has a password and/or access keys.</td>
</tr>
<tr>
<td><strong>Group</strong></td>
<td>A bag of users sharing permissions (e.g., <code>developers</code>, <code>auditors</code>).</td>
</tr>
<tr>
<td><strong>Role</strong></td>
<td>An identity that a service (EC2, Lambda, etc.) or a federated user assumes temporarily. <strong>The modern way.</strong></td>
</tr>
<tr>
<td><strong>Policy</strong></td>
<td>A JSON document listing allowed/denied actions. Attached to users, groups, or roles.</td>
</tr>
<tr>
<td><strong>Permission boundary</strong></td>
<td>A meta-policy that caps what a user/role can be granted, regardless of inline policies.</td>
</tr>
</tbody>
</table>

<p>Parts:</p>
<ul>
<li><code>Effect</code> — <code>Allow</code> or <code>Deny</code>.</li>
<li><code>Action</code> — service:operation. Wildcards allowed (<code>s3:Get*</code>).</li>
<li><code>Resource</code> — ARN(s) the actions apply to. <code>*</code> means &quot;all resources&quot;.</li>
<li>Optional: <code>Condition</code>, <code>Principal</code>, <code>NotAction</code>, <code>NotResource</code>.</li>
</ul>
<h2 id="Roles-vs-users-—-modern-guidance"><a href="#Roles-vs-users-—-modern-guidance" class="headerlink" title="Roles vs users — modern guidance"></a>Roles vs users — modern guidance</h2>
<p>Use <strong>roles</strong> for code (EC2, Lambda, ECS tasks). The service automatically gets short-lived credentials via the EC2 instance metadata service or the Lambda runtime; you never store access keys on disk.</p>
<p>Use <strong>users</strong> only for humans, and prefer federation (SSO, Okta, Azure AD) over local IAM users in serious accounts.</p>
<p><strong>Common pitfall:</strong> committing long-lived AWS access keys to a public repo. Bots scan GitHub for keys constantly; expect crypto-mining within minutes. Never commit <code>AKIA...</code> strings. If exposed, rotate immediately and audit.</p>

</tr>

<p><strong>Surprise-bill traps to avoid:</strong></p>
<ol>
<li><strong>NAT Gateway</strong> — runs 24/7 at ≈ USD 32 / month, charges for data through it. Easy to leave running.</li>
<li><strong>Elastic IPs not attached</strong> — costs while idle.</li>
<li><strong>EBS volumes not deleted with their instances</strong> — keep paying for storage.</li>
<li><strong>CloudWatch Logs without retention</strong> — defaults to <em>forever</em>. Set retention to 7 or 30 days.</li>
<li><strong>Cross-region data transfer</strong> — between regions costs around USD 0.02 / GB. Adds up.</li>
<li><strong>Public S3 traffic</strong> — if your bucket goes viral, you pay for the egress.</li>
</ol>
<blockquote>
<p><strong>Trick:</strong> create a separate AWS account for <em>learning</em> — nothing else lives there. When done with a tutorial, run <code>aws ec2 terminate-instances ...</code> or use <a href="https://github.com/rebuy-de/aws-nuke" target="_blank" rel="noopener external nofollow noreferrer">AWS Nuke</a> to wipe everything.</p>
</blockquote>

<p>Audit your account:</p>
<ol>
<li>Are there any unused Elastic IPs (<code>aws ec2 describe-addresses</code>)?</li>
