<h1 id="Chapter-1-—-Elements-components-and-instances"><a href="#Chapter-1-—-Elements-components-and-instances" class="headerlink" title="Chapter 1 — Elements, components and instances"></a>Chapter 1 — Elements, components and instances</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Element</strong> — a plain, immutable object that describes what should be on screen: <code>{ type, props, key, ... }</code>. Cheap to create, thrown away after each render.</li>
<li><strong>Component</strong> — a function (or class) that takes props and returns elements. It is a <em>description of a description</em>.</li>
<li><strong>Instance</strong> — the thing that holds state for one mounted use of a component. For function components React does not expose an instance object; the state lives on an internal <strong>fiber</strong>.</li>
<li><strong>Host component</strong> — a platform element such as <code>'div'</code> or <code>'button'</code> (a string <code>type</code>). The renderer (<code>react-dom</code>, React Native) turns it into a real node.</li>
<li><strong>Renderer</strong> — the package that owns the host environment. <code>react</code> holds the component model; <code>react-dom</code> owns the DOM.</li>
</ul>
<h2 id="What-JSX-becomes"><a href="#What-JSX-becomes" class="headerlink" title="What JSX becomes"></a>What JSX becomes</h2>
<p>With the automatic JSX runtime (the default in Vite, Next.js and TypeScript's <code>&quot;jsx&quot;: &quot;react-jsx&quot;</code>), this:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="jsx"><span class="line">&lt;<span class="hljs-title class_">Button</span> kind=<span class="hljs-string">&quot;primary&quot;</span> onClick={save}&gt;<span class="hljs-title class_">Save</span>&lt;/<span class="hljs-title class_">Button</span>&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>compiles to roughly:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">import</span> { jsx <span class="hljs-keyword">as</span> _jsx } <span class="hljs-keyword">from</span> <span class="hljs-string">&quot;react/jsx-runtime&quot;</span>;</span><br><span class="line"><span class="hljs-title function_">_jsx</span>(<span class="hljs-title class_">Button</span>, { <span class="hljs-attr">kind</span>: <span class="hljs-string">&quot;primary&quot;</span>, <span class="hljs-attr">onClick</span>: save, <span class="hljs-attr">children</span>: <span class="hljs-string">&quot;Save&quot;</span> });</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The result is an ordinary object (<code>el.type === Button</code>, <code>el.props.kind === &quot;primary&quot;</code>). Nothing has rendered yet; <code>Button</code> has not even been called. The element only records <em>which</em> component to call and <em>with which</em> props. React decides later whether to call it at all.</p>
<h2 id="Where-state-lives"><a href="#Where-state-lives" class="headerlink" title="Where state lives"></a>Where state lives</h2>
<p>State does not live &quot;in the function&quot;. A function component is called again on every render, and its local variables are new each time. The state lives on the fiber that React created when it first mounted that element <strong>at that position in the tree</strong>. <code>useState</code> reads from and writes to that fiber.</p>
<p>This has one big consequence that the rest of the post keeps returning to: <strong>identity is decided by position and type (and key), not by the component's name or by which variable held the element.</strong></p>
<blockquote>
<p><strong>Trick:</strong> say &quot;React calls my component&quot; instead of &quot;my component runs&quot;. It keeps the right model in mind: React owns the call, the timing, and how many times it happens.</p>
</blockquote>

<h1 id="Chapter-2-—-Trigger-render-commit"><a href="#Chapter-2-—-Trigger-render-commit" class="headerlink" title="Chapter 2 — Trigger, render, commit"></a>Chapter 2 — Trigger, render, commit</h1>
<p>Every screen update goes through the same three steps.</p>
<ol>
<li><strong>Trigger.</strong> Something schedules an update: the initial <code>root.render(&lt;App /&gt;)</code>, or a <code>setState</code> / <code>dispatch</code> call, or a change in an external store read with <code>useSyncExternalStore</code>.</li>
<li><strong>Render.</strong> React calls the components that may have changed and builds the next tree of elements. It compares that tree with the previous one (reconciliation) and records which host nodes need changes.</li>
<li><strong>Commit.</strong> React applies the recorded changes to the DOM in one go, attaches refs, and runs effects.</li>
</ol>
<p><img src="/blog/assets/react/diagram_00_render_commit.svg" alt="The three steps of a React update: trigger schedules work on a fiber, the render phase calls components and builds the workInProgress tree and can be paused or thrown away, the commit phase applies DOM mutations, runs layout effects and attaches refs, then the browser paints and passive effects run."></p>
<h2 id="Render-phase-pure-and-interruptible"><a href="#Render-phase-pure-and-interruptible" class="headerlink" title="Render phase: pure and interruptible"></a>Render phase: pure and interruptible</h2>
<p>In the render phase React only <em>calculates</em>. It calls your components and compares results. Because of concurrent rendering (Post 02), the render phase can be <strong>paused</strong> to let the browser handle input, <strong>restarted</strong> when a more urgent update arrives, or <strong>thrown away</strong> if the result is no longer needed.</p>
<p>That is why components must be <strong>pure</strong> during render: same props, state and context in, same elements out, and no side effects. An <code>analytics.track()</code> call, a render counter in a module variable, a write to a ref — any of these can run twice, or run for a render that never commits.</p>
<h2 id="Commit-phase-synchronous-and-never-partial"><a href="#Commit-phase-synchronous-and-never-partial" class="headerlink" title="Commit phase: synchronous and never partial"></a>Commit phase: synchronous and never partial</h2>
<p>The commit phase is not interruptible. Once React starts committing, the whole tree is applied in one synchronous pass, so the user never sees half an update. Inside the commit, the order is:</p>
<table>
<thead>
<tr>
<th>Step</th>
<th>What happens</th>
</tr>
</thead>
<tbody>
<tr>
<td>Before mutation</td>
<td><code>getSnapshotBeforeUpdate</code> for classes</td>
</tr>
<tr>
<td>Mutation</td>
<td>DOM nodes inserted, updated, removed; old ref detached; layout-effect cleanups of changed components</td>
</tr>
<tr>
<td>Layout</td>
<td>refs attached; <code>useLayoutEffect</code> setups; <code>componentDidMount</code> / <code>componentDidUpdate</code></td>
</tr>
<tr>
<td>(browser paints)</td>
<td></td>
</tr>
<tr>
<td>Passive</td>
<td><code>useEffect</code> cleanups then setups</td>
</tr>
</tbody>
</table>
<p><code>useLayoutEffect</code> runs after the DOM is changed but <strong>before</strong> the browser paints, so it can measure layout and set state without a visible flicker. <code>useEffect</code> normally runs <strong>after</strong> paint. The React docs add one detail: when the update came from a discrete interaction such as a click, React may run the effects before paint. Do not depend on either timing for correctness; use <code>useLayoutEffect</code> when you need &quot;before paint&quot;.</p>
<blockquote>
<p><strong>Watch out:</strong> &quot;render&quot; in React does not mean &quot;paint to the screen&quot;. A component can render many times with zero DOM changes, and the DOM only changes in the commit. Profilers (Post 03) show render time and commit time separately for this reason.</p>
</blockquote>

<h1 id="Chapter-3-—-The-Fiber-tree-and-the-work-loop"><a href="#Chapter-3-—-The-Fiber-tree-and-the-work-loop" class="headerlink" title="Chapter 3 — The Fiber tree and the work loop"></a>Chapter 3 — The Fiber tree and the work loop</h1>
<p>This chapter describes internals. They are not public API and they change between versions, but the shape has been stable since React 16 and it explains most observable behaviour.</p>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Fiber</strong> — an internal object, one per element in the tree (components and host nodes). It is both the &quot;instance&quot; and a unit of work.</li>
<li><strong><code>current</code> tree</strong> — the fibers that match what is on screen now.</li>
<li><strong><code>workInProgress</code> tree</strong> — the tree being built during a render.</li>
<li><strong>Alternate</strong> — each fiber points to its twin in the other tree. React reuses the pair instead of allocating new objects (double buffering).</li>
<li><strong>Lanes</strong> — a bit mask on each fiber that says which priorities of pending work it has. Post 02 covers them.</li>
<li><strong>Flags</strong> — bits on a fiber that say what the commit must do: place, update, delete, run effects.</li>
</ul>
<h2 id="What-a-fiber-holds"><a href="#What-a-fiber-holds" class="headerlink" title="What a fiber holds"></a>What a fiber holds</h2>
<p>A simplified view of the fields that matter for understanding behaviour:</p>
<pre><code class="language-ts"><figure class="highlight ts"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span></pre></td><td class="code"><pre><code class="ts"><span class="line"><span class="hljs-keyword">interface</span> <span class="hljs-title class_">Fiber</span> {</span><br><span class="line">  <span class="hljs-attr">type</span>: <span class="hljs-built_in">any</span>;              <span class="hljs-comment">// the component function, or &#x27;div&#x27;</span></span><br><span class="line">  <span class="hljs-attr">key</span>: <span class="hljs-built_in">string</span> | <span class="hljs-literal">null</span>;</span><br><span class="line">  <span class="hljs-attr">stateNode</span>: <span class="hljs-built_in">any</span>;          <span class="hljs-comment">// effects the commit must apply</span></span><br><span class="line">  <span class="hljs-attr">alternate</span>: <span class="hljs-title class_">Fiber</span> | <span class="hljs-literal">null</span>;</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Two fields explain a lot:</p>
<ul>
<li><code>memoizedState</code> of a function component points to a <strong>linked list of hooks</strong> in call order. That is the real reason hooks must be called in the same order every render (Post 01).</li>
<li><code>childLanes</code> lets React skip whole subtrees. If a fiber has no own work and <code>childLanes</code> is empty, React reuses the whole subtree from <code>current</code> without calling any component in it.</li>
</ul>
<h2 id="The-work-loop"><a href="#The-work-loop" class="headerlink" title="The work loop"></a>The work loop</h2>
<p>The tree is a linked list (<code>child</code>, <code>sibling</code>, <code>return</code>), so React can walk it with a plain loop instead of recursion. That is what makes pausing possible: the loop can stop after any fiber and resume later from a saved pointer.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// Very simplified shape of the loop</span></span><br><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">workLoopConcurrent</span>(<span class="hljs-params"></span>) {</span><br><span class="line">  <span class="hljs-keyword">while</span> (workInProgress !== <span class="hljs-literal">null</span> &amp;&amp; !<span class="hljs-title function_">shouldYield</span>()) {</span><br><span class="line">    <span class="hljs-title function_">performUnitOfWork</span>(workInProgress);</span><br><span class="line">  }</span><br><span class="line">}</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">performUnitOfWork</span>(<span class="hljs-params">fiber</span>) {</span><br><span class="line">  <span class="hljs-keyword">const</span> next = <span class="hljs-title function_">beginWork</span>(fiber);      <span class="hljs-comment">// call the component, reconcile its children</span></span><br><span class="line">  <span class="hljs-keyword">if</span> (next === <span class="hljs-literal">null</span>) <span class="hljs-title function_">completeUnitOfWork</span>(fiber); <span class="hljs-comment">// no child: complete, go to sibling or parent</span></span><br><span class="line">  <span class="hljs-keyword">else</span> workInProgress = next;</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><strong><code>beginWork</code></strong> goes down: it calls the component (or bails out), then reconciles the returned children into child fibers.</li>
<li><strong><code>completeWork</code></strong> goes back up: for host fibers it creates or prepares DOM nodes (not yet attached) and bubbles flags upward so the commit knows where to look.</li>
<li><strong><code>shouldYield</code></strong> asks the Scheduler whether the current time slice is used up. Synchronous updates use a loop without this check; transitions use the one above. The slice is only a few milliseconds long, so the browser gets regular chances to handle input.</li>
</ul>
<p>When the root completes, React swaps the pointer: the <code>workInProgress</code> tree becomes <code>current</code>. That swap happens during the commit, which is why a half-finished render is never visible.</p>
<blockquote>
<p><strong>Trick:</strong> the React DevTools &quot;Components&quot; tab shows the fiber tree (host and component fibers), not the DOM. When a DevTools tree and the Elements panel disagree about nesting, the fiber tree is what React reconciles.</p>
</blockquote>
<hr>
<h1 id="Chapter-4-—-Reconciliation-heuristics"><a href="#Chapter-4-—-Reconciliation-heuristics" class="headerlink" title="Chapter 4 — Reconciliation heuristics"></a>Chapter 4 — Reconciliation heuristics</h1>
<p>Comparing two arbitrary trees optimally is expensive; the general algorithms are roughly O(n³). React uses two heuristics that make it O(n):</p>
<ol>
<li><strong>Different element types produce different trees.</strong> If the <code>type</code> at a position changes (<code>div</code> → <code>section</code>, <code>UserCard</code> → <code>AdminCard</code>), React unmounts the old subtree — destroying its DOM <strong>and its state</strong> — and mounts a new one.</li>
<li><strong>Keys mark stable identity among siblings.</strong> Within one list of children, React matches old and new children by key (or by index when there is no key).</li>
</ol>
<p>When the type and key match, React keeps the fiber, keeps the state, and updates the props.</p>
<h2 id="Same-position-same-type-state-survives"><a href="#Same-position-same-type-state-survives" class="headerlink" title="Same position, same type: state survives"></a>Same position, same type: state survives</h2>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">Page</span>(<span class="hljs-params">{ isAdmin }</span>) {</span><br><span class="line">  <span class="hljs-keyword">return</span> isAdmin ? <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">Profile</span> <span class="hljs-attr">role</span>=<span class="hljs-string">&quot;admin&quot;</span> /&gt;</span></span> : <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">Profile</span> <span class="hljs-attr">role</span>=<span class="hljs-string">&quot;user&quot;</span> /&gt;</span></span>;</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Both branches produce a <code>Profile</code> at the same position. React sees the same type, so it <strong>keeps</strong> the state of <code>Profile</code> and only changes the <code>role</code> prop. This surprises people who expect &quot;a different branch&quot; to mean &quot;a fresh component&quot;.</p>
<h2 id="Different-type-state-is-lost"><a href="#Different-type-state-is-lost" class="headerlink" title="Different type: state is lost"></a>Different type: state is lost</h2>
<p>Change it to <code>isAdmin ? &lt;AdminProfile /&gt; : &lt;UserProfile /&gt;</code> and the type at that position changes, so the subtree is remounted and its state is gone.</p>
<h2 id="The-component-inside-component-bug"><a href="#The-component-inside-component-bug" class="headerlink" title="The component-inside-component bug"></a>The component-inside-component bug</h2>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">List</span>(<span class="hljs-params">{ items }</span>) {</span><br><span class="line">  <span class="hljs-comment">// A new function object on every render of List</span></span><br><span class="line">  <span class="hljs-keyword">function</span> <span class="hljs-title function_">Row</span>(<span class="hljs-params">{ item }</span>) {</span><br><span class="line">    <span class="hljs-keyword">const</span> [open, setOpen] = <span class="hljs-title function_">useState</span>(<span class="hljs-literal">false</span>);</span><br><span class="line">    <span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">li</span> <span class="hljs-attr">onClick</span>=<span class="hljs-string">{()</span> =&gt;</span> setOpen(!open)}&gt;{item.name} {open &amp;&amp; <span class="hljs-tag">&lt;<span class="hljs-name">Row</span> <span class="hljs-attr">key</span>=<span class="hljs-string">{i.id}</span> <span class="hljs-attr">item</span>=<span class="hljs-string">{i}</span> /&gt;</span>)}<span class="hljs-tag">&lt;/<span class="hljs-name">ul</span>&gt;</span></span>;</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Every render of <code>List</code> creates a new <code>Row</code> function. The element type is compared by reference, so <code>Row</code> from this render is a <em>different type</em> from <code>Row</code> last render. Every row is unmounted and remounted on every render: state resets, focus is lost, effects re-run, and it is slow. Define components at module level. The <code>react-hooks/static-components</code> lint rule in <code>eslint-plugin-react-hooks</code> v6 reports this pattern.</p>
<blockquote>
<p><strong>Common pitfall:</strong> conditional wrappers change the tree shape. <code>{loading ? &lt;Spinner /&gt; : null}&lt;Form /&gt;</code> keeps <code>Form</code> in slot 2 either way, but <code>{loading ? &lt;div&gt;&lt;Form /&gt;&lt;/div&gt; : &lt;Form /&gt;}</code> moves <code>Form</code> to a different depth and resets its state every time <code>loading</code> flips.</p>
</blockquote>

<h1 id="Chapter-5-—-Keys-identity-and-state-preservation"><a href="#Chapter-5-—-Keys-identity-and-state-preservation" class="headerlink" title="Chapter 5 — Keys, identity and state preservation"></a>Chapter 5 — Keys, identity and state preservation</h1>
<h2 id="What-keys-do"><a href="#What-keys-do" class="headerlink" title="What keys do"></a>What keys do</h2>
<p>A key is an identity <strong>among siblings</strong>. React uses it to match children between two renders. With keys, moving an item moves its fiber (state and DOM included). Without keys, React matches by index.</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-comment">// Bug: index as key in a list that can be reordered or filtered</span></span><br><span class="line">{todos.<span class="hljs-title function_">map</span>(<span class="hljs-function">(<span class="hljs-params">todo, i</span>) =&gt;</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">TodoRow</span> <span class="hljs-attr">key</span>=<span class="hljs-string">{i}</span> <span class="hljs-attr">todo</span>=<span class="hljs-string">{todo}</span> /&gt;</span></span>)}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>TodoRow</code> holds local state (say, an &quot;editing&quot; flag and an uncontrolled <code>&lt;input&gt;</code>). Sort the list, and the row at index 0 now receives a different <code>todo</code> prop but keeps the <strong>old</strong> state and the old input text. The data moved; the identity did not.</p>
<p>Rules:</p>
<ul>
<li>Keys must be stable, unique among siblings, and come from the data (<code>todo.id</code>). Not <code>Math.random()</code> — that remounts every row on every render.</li>
<li>Index keys are fine only for lists that are never reordered, filtered or inserted into, and whose rows hold no state.</li>
<li>Keys do not need to be globally unique; two different lists can reuse the same keys.</li>
<li><code>key</code> is not a prop. The child cannot read <code>props.key</code>; pass the id again as a separate prop if the child needs it.</li>
</ul>
<h2 id="Keys-to-reset-state-on-purpose"><a href="#Keys-to-reset-state-on-purpose" class="headerlink" title="Keys to reset state on purpose"></a>Keys to reset state on purpose</h2>
<p>Because a new key means a new identity, a key is the cleanest way to reset a subtree:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-comment">// Reset the whole editor when the user switches documents</span></span><br><span class="line">&lt;<span class="hljs-title class_">Editor</span> key={documentId} documentId={documentId} /&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The alternative — an effect that watches <code>documentId</code> and resets five pieces of state — renders once with stale state, then again with the reset state, and is easy to get wrong when a new piece of state is added.</p>
<p>A key can go on a <code>Fragment</code> when each item renders several siblings (<code>&lt;Fragment key={row.id}&gt;&lt;dt/&gt;&lt;dd/&gt;&lt;/Fragment&gt;</code>); the short <code>&lt;&gt;...&lt;/&gt;</code> syntax cannot take a key.</p>
<blockquote>
<p><strong>Watch out:</strong> the &quot;missing key&quot; warning only covers arrays. Unstable identity from a changing type or a changing tree depth (Chapter 4) produces no warning at all.</p>
</blockquote>
<hr>
<h1 id="Chapter-6-—-When-a-component-renders-and-when-it-does-not"><a href="#Chapter-6-—-When-a-component-renders-and-when-it-does-not" class="headerlink" title="Chapter 6 — When a component renders, and when it does not"></a>Chapter 6 — When a component renders, and when it does not</h1>
<h2 id="The-four-reasons-a-component-renders"><a href="#The-four-reasons-a-component-renders" class="headerlink" title="The four reasons a component renders"></a>The four reasons a component renders</h2>
<ol>
<li><strong>Initial mount.</strong></li>
<li><strong>Its own state changed</strong> (<code>useState</code>, <code>useReducer</code>), or an external store it subscribes to with <code>useSyncExternalStore</code> changed.</li>
<li><strong>Its parent rendered.</strong> By default, when a component renders, React renders all of its children, whether their props changed or not.</li>
<li><strong>A context it reads changed</strong> (<code>useContext</code> or <code>use(Context)</code>), compared with <code>Object.is</code>.</li>
</ol>
<p>What is <strong>not</strong> on the list: &quot;its props changed&quot;. Props are an input to a render that already happens because the parent rendered. A parent can pass identical props and the child still renders; <code>memo</code> is what makes React compare them.</p>
<h2 id="Bailouts"><a href="#Bailouts" class="headerlink" title="Bailouts"></a>Bailouts</h2>
<p>React skips work in these cases:</p>
<table>
<thead>
<tr>
<th>Case</th>
<th>What React does</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>setState(x)</code> where <code>Object.is(x, current)</code></td>
<td>Usually skips the update. React may still call the component once before it can tell the result is the same, but it does not go on into the children or commit.</td>
</tr>
<tr>
<td>Fiber has no pending work and its props object is the same reference as last time</td>
<td>Reuses the fiber and skips calling it; checks <code>childLanes</code> to decide whether to go deeper.</td>
</tr>
<tr>
<td><code>memo(Component)</code> and every prop is <code>Object.is</code> equal</td>
<td>Skips the render (unless its own state or a read context changed).</td>
</tr>
<tr>
<td>Subtree has no pending lanes</td>
<td>Whole subtree reused from <code>current</code>.</td>
</tr>
</tbody>
</table>
<p>The second row is the basis of the <strong>children-as-props</strong> pattern:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">ScrollTracker</span>(<span class="hljs-params">{ children }</span>) {</span><br><span class="line">  <span class="hljs-keyword">const</span> [y, setY] = <span class="hljs-title function_">useState</span>(<span class="hljs-number">0</span>);</span><br><span class="line">  <span class="hljs-title function_">useScrollListener</span>(setY);          <span class="hljs-comment">// calls setY on every scroll</span></span><br><span class="line">  <span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">div</span> <span class="hljs-attr">data-y</span>=<span class="hljs-string">{y}</span>&gt;</span>{children}<span class="hljs-tag">&lt;/<span class="hljs-name">div</span>&gt;</span></span>;</span><br><span class="line">}</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// In the parent:</span></span><br><span class="line">&lt;<span class="hljs-title class_">ScrollTracker</span>&gt;<span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">ExpensiveDashboard</span> /&gt;</span></span>&lt;/<span class="hljs-title class_">ScrollTracker</span>&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>&lt;ExpensiveDashboard /&gt;</code> was created by the parent, not by <code>ScrollTracker</code>. When <code>ScrollTracker</code> re-renders on every scroll, <code>children</code> is the same element object as before, so React bails out of <code>ExpensiveDashboard</code> without any <code>memo</code>. Moving state down, or lifting content up into <code>children</code>, often beats memoisation.</p>
<h2 id="Context-is-not-a-bailout-friendly-channel"><a href="#Context-is-not-a-bailout-friendly-channel" class="headerlink" title="Context is not a bailout-friendly channel"></a>Context is not a bailout-friendly channel</h2>
<p>Every component that reads a context renders when the provided value changes, and <code>memo</code> does not stop that. A provider whose value is a new object on each render makes every consumer render on every parent render:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-comment">// Every render of App creates a new object -&gt; every consumer renders</span></span><br><span class="line">&lt;<span class="hljs-title class_">AuthContext</span> value={{ user, login, logout }}&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Post 01 covers the fixes (stable values, splitting contexts, selectors via external stores). In React 19 you can write <code>&lt;AuthContext value={...}&gt;</code> directly; <code>&lt;AuthContext.Provider&gt;</code> still works.</p>
<h2 id="Adjusting-state-when-a-prop-changes"><a href="#Adjusting-state-when-a-prop-changes" class="headerlink" title="Adjusting state when a prop changes"></a>Adjusting state when a prop changes</h2>
<p>Sometimes state must follow a prop. The effect version renders twice with a stale frame in between. React supports setting state <strong>during render</strong> for the component that is rendering, guarded by a comparison:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">Selection</span>(<span class="hljs-params">{ items }</span>) {</span><br><span class="line">  <span class="hljs-keyword">const</span> [prevItems, setPrevItems] = <span class="hljs-title function_">useState</span>(items);</span><br><span class="line">  <span class="hljs-keyword">const</span> [selected, setSelected] = <span class="hljs-title function_">useState</span>(<span class="hljs-literal">null</span>);</span><br><span class="line"> </span><br><span class="line">  <span class="hljs-keyword">if</span> (items !== prevItems) {        <span class="hljs-comment">// allowed: updates this component during its own render</span></span><br><span class="line">    <span class="hljs-title function_">setPrevItems</span>(items);</span><br><span class="line">    <span class="hljs-title function_">setSelected</span>(<span class="hljs-literal">null</span>);</span><br><span class="line">  }</span><br><span class="line">  <span class="hljs-comment">// ...</span></span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>React throws away the JSX of the first pass and re-runs the component immediately, before children render. Prefer a <code>key</code> reset or deriving the value; use this only when those do not fit.</p>
<blockquote>
<p><strong>Common pitfall:</strong> &quot;I wrapped the child in <code>memo</code> and it still renders.&quot; Check, in order: a new object/array/function prop created in the parent's render; a context the child reads; the child's own state; <code>children</code> passed as JSX (a new element object every render, so <code>memo</code> never matches).</p>
</blockquote>

<h1 id="Chapter-7-—-Batching-and-state-snapshots"><a href="#Chapter-7-—-Batching-and-state-snapshots" class="headerlink" title="Chapter 7 — Batching and state snapshots"></a>Chapter 7 — Batching and state snapshots</h1>
<h2 id="State-is-a-snapshot"><a href="#State-is-a-snapshot" class="headerlink" title="State is a snapshot"></a>State is a snapshot</h2>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">const</span> [n, setN] = <span class="hljs-title function_">useState</span>(<span class="hljs-number">0</span>);</span><br><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">handleClick</span>(<span class="hljs-params"></span>) {</span><br><span class="line">  <span class="hljs-title function_">setN</span>(n + <span class="hljs-number">1</span>); <span class="hljs-title function_">setN</span>(n + <span class="hljs-number">1</span>); <span class="hljs-title function_">setN</span>(n + <span class="hljs-number">1</span>);</span><br><span class="line">  <span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(n); <span class="hljs-comment">// still 0</span></span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>One click shows 1, not 3. <code>n</code> is a constant for this render; each call queues &quot;replace with 0 + 1&quot;. An <strong>updater function</strong> reads the queued value instead:</p>
<p><code>setN(prev =&gt; prev + 1)</code> three times gives 3. The <code>console.log</code> still prints 0. The new value exists only in the next render.</p>
<h2 id="Automatic-batching-React-18"><a href="#Automatic-batching-React-18" class="headerlink" title="Automatic batching (React 18+)"></a>Automatic batching (React 18+)</h2>
<p>React groups several state updates into a single render. Before React 18 this happened only inside React event handlers; updates in <code>setTimeout</code>, promises or native listeners each caused their own render. With <code>createRoot</code> (React 18+), batching is automatic everywhere:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-title function_">fetch</span>(<span class="hljs-string">&quot;/api/user&quot;</span>).<span class="hljs-title function_">then</span>(<span class="hljs-function"><span class="hljs-params">r</span> =&gt;</span> r.<span class="hljs-title function_">json</span>()).<span class="hljs-title function_">then</span>(<span class="hljs-function"><span class="hljs-params">user</span> =&gt;</span> {</span><br><span class="line">  <span class="hljs-title function_">setUser</span>(user);</span><br><span class="line">  <span class="hljs-title function_">setLoading</span>(<span class="hljs-literal">false</span>);  <span class="hljs-comment">// one render in React 18+, two in React 17</span></span><br><span class="line">});</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Apps still on the legacy <code>ReactDOM.render</code> root kept the old behaviour in React 18; React 19 removed <code>ReactDOM.render</code>, so every React 19 app batches automatically.</p>
<h2 id="Opting-out-with-flushSync"><a href="#Opting-out-with-flushSync" class="headerlink" title="Opting out with flushSync"></a>Opting out with <code>flushSync</code></h2>
<p>Rarely you need the DOM to be updated <strong>now</strong>, for example to scroll to a newly added item:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">import</span> { flushSync } <span class="hljs-keyword">from</span> <span class="hljs-string">&quot;react-dom&quot;</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">addMessage</span>(<span class="hljs-params">msg</span>) {</span><br><span class="line">  <span class="hljs-title function_">flushSync</span>(<span class="hljs-function">() =&gt;</span> <span class="hljs-title function_">setMessages</span>(<span class="hljs-function"><span class="hljs-params">m</span> =&gt;</span> [...m, msg]));</span><br><span class="line">  listRef.<span class="hljs-property">current</span>.<span class="hljs-property">lastElementChild</span>.<span class="hljs-title function_">scrollIntoView</span>();</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>flushSync</code> forces a synchronous render and commit. It is expensive and it defeats concurrent features for that update, so keep it for DOM-measurement cases.</p>
<blockquote>
<p><strong>Trick:</strong> batching also explains why a click handler that calls three different <code>setX</code> functions produces one entry, not three, in the Profiler.</p>
</blockquote>

<h1 id="Chapter-8-—-StrictMode"><a href="#Chapter-8-—-StrictMode" class="headerlink" title="Chapter 8 — StrictMode"></a>Chapter 8 — StrictMode</h1>
<p><code>&lt;StrictMode&gt;</code> changes nothing in production. In development it runs extra checks by doing things twice, to expose code that is not pure or not cleaned up.</p>
<table>
<thead>
<tr>
<th>What is doubled (development only)</th>
<th>What it catches</th>
</tr>
</thead>
<tbody>
<tr>
<td>Component function bodies</td>
<td>Side effects during render, mutation of props or state</td>
</tr>
<tr>
<td><code>useState</code> initialisers and updaters, <code>useReducer</code> reducers</td>
<td>Impure initialisers and reducers</td>
</tr>
<tr>
<td>Class <code>constructor</code>, <code>render</code>, <code>shouldComponentUpdate</code></td>
<td>Same, for classes</td>
</tr>
<tr>
<td>Effects: setup → cleanup → setup on mount</td>
<td>Missing cleanup (duplicate subscriptions, leaked timers, double connections)</td>
</tr>
<tr>
<td>Ref callbacks on mount (React 19)</td>
<td>Missing ref cleanup</td>
</tr>
</tbody>
</table>
<p>React 19 changes two details: during the double render, <code>useMemo</code> and <code>useCallback</code> <strong>reuse</strong> the result of the first call; and ref callbacks are also run twice on mount, to simulate a component being hidden and shown again (for example by a Suspense fallback).</p>
<p>The effect double-run is the one people fight. It is a simulation of what really happens in production when a component is unmounted and mounted again: route changes with cached screens, <code>&lt;Activity&gt;</code> hiding and showing (Post 02), Fast Refresh. If an effect breaks when run twice, it will break there too.</p>

</blockquote>

<h1 id="Chapter-9-—-Refs"><a href="#Chapter-9-—-Refs" class="headerlink" title="Chapter 9 — Refs"></a>Chapter 9 — Refs</h1>
<h2 id="useRef-a-box-that-survives-renders"><a href="#useRef-a-box-that-survives-renders" class="headerlink" title="useRef: a box that survives renders"></a><code>useRef</code>: a box that survives renders</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> ref = <span class="hljs-title function_">useRef</span>(initialValue); <span class="hljs-comment">// { current: initialValue }, same object every render</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Writing <code>ref.current</code> does <strong>not</strong> schedule a render. That makes refs right for values the UI does not display: timer ids, the previous value, an <code>AbortController</code>, a DOM node, a third-party widget instance.</p>
<p>Rules that keep refs safe:</p>
<ul>
<li><strong>Do not read or write <code>ref.current</code> during render</strong> (except lazy initialisation, below). The render would depend on a value React does not track, and concurrent rendering can run that render more than once. The <code>react-hooks/refs</code> lint rule flags this.</li>
<li>Read and write them in event handlers and effects.</li>
<li>In React 19 with TypeScript, <code>useRef</code> needs an argument (<code>useRef&lt;HTMLDivElement&gt;(null)</code>), and all refs are mutable.</li>
<li>Lazy initialisation is the one allowed render-time access: <code>if (ref.current === null) ref.current = new VideoPlayer();</code>.</li>
</ul>
<h2 id="DOM-refs-and-callback-refs-with-cleanup"><a href="#DOM-refs-and-callback-refs-with-cleanup" class="headerlink" title="DOM refs and callback refs with cleanup"></a>DOM refs and callback refs with cleanup</h2>
<p>React sets <code>ref.current</code> to the DOM node in the commit and back to <code>null</code> when it is removed. For logic that must run when a node appears or goes away, use a callback ref. React 19 lets it return a cleanup function:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="jsx"><span class="line">&lt;div</span><br><span class="line">  ref={<span class="hljs-function"><span class="hljs-params">node</span> =&gt;</span> {</span><br><span class="line">    <span class="hljs-keyword">const</span> observer = <span class="hljs-keyword">new</span> <span class="hljs-title class_">ResizeObserver</span>(<span class="hljs-function">(<span class="hljs-params">[entry]</span>) =&gt;</span> <span class="hljs-title function_">setWidth</span>(entry.<span class="hljs-property">contentRect</span>.<span class="hljs-property">width</span>));</span><br><span class="line">    observer.<span class="hljs-title function_">observe</span>(node);</span><br><span class="line">    <span class="hljs-keyword">return</span> <span class="hljs-function">() =&gt;</span> observer.<span class="hljs-title function_">disconnect</span>();   <span class="hljs-comment">// React 19: called on detach</span></span><br><span class="line">  }}</span><br><span class="line">/&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>With a cleanup returned, React calls the cleanup on detach instead of calling the callback with <code>null</code>. Because the arrow function above is a new function every render, React detaches and re-attaches it on every render; wrap it in <code>useCallback</code> (or let the React Compiler memoise it) if that is costly.</p>
<h2 id="ref-as-a-prop-React-19"><a href="#ref-as-a-prop-React-19" class="headerlink" title="ref as a prop (React 19)"></a><code>ref</code> as a prop (React 19)</h2>
<p>Function components now receive <code>ref</code> as a normal prop. <code>forwardRef</code> is no longer needed and the React team plans to deprecate it:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">TextField</span>(<span class="hljs-params">{ label, ref, ...rest }</span>) {</span><br><span class="line">  <span class="hljs-keyword">return</span> (</span><br><span class="line">    <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">label</span>&gt;</span></span><br><span class="line">      {label}</span><br><span class="line">      <span class="hljs-tag">&lt;<span class="hljs-name">input</span> <span class="hljs-attr">ref</span>=<span class="hljs-string">{ref}</span> {<span class="hljs-attr">...rest</span>} /&gt;</span></span><br><span class="line">    <span class="hljs-tag">&lt;/<span class="hljs-name">label</span>&gt;</span></span></span><br><span class="line">  );</span><br><span class="line">}</span><br><span class="line"> </span><br><span class="line">&lt;<span class="hljs-title class_">TextField</span> label=<span class="hljs-string">&quot;Email&quot;</span> ref={emailRef} /&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>To expose a small imperative API instead of the raw node, combine the <code>ref</code> prop with <code>useImperativeHandle(ref, () =&gt; ({ play, pause }), [])</code>.</p>
<blockquote>
<p><strong>Trick:</strong> keep imperative handles small and verb-shaped (<code>focus</code>, <code>play</code>, <code>scrollToRow</code>). Exposing the whole DOM node lets every parent reach in and couple itself to your markup.</p>
</blockquote>

<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">App</span>(<span class="hljs-params">{ flag }</span>) {</span><br><span class="line">  <span class="hljs-keyword">return</span> flag ? <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">Counter</span> <span class="hljs-attr">label</span>=<span class="hljs-string">&quot;A&quot;</span> /&gt;</span></span> : <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">Counter</span> <span class="hljs-attr">label</span>=<span class="hljs-string">&quot;B&quot;</span> /&gt;</span></span>;</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Exercise-2-—-The-index-key-bug"><a href="#Exercise-2-—-The-index-key-bug" class="headerlink" title="Exercise 2 — The index-key bug"></a>Exercise 2 — The index-key bug</h2>
<p>Build a list of three rows, each with an uncontrolled <code>&lt;input defaultValue={item.name} /&gt;</code>, keyed by index. Type into row 0, then prepend an item. Explain what you see, then fix it.</p>
<details>
<summary>Solution</summary>
<p>The typed text stays in the first input, which now belongs to the new item. React matched children by index, so the fiber (and its DOM input) at index 0 was kept and given new props; <code>defaultValue</code> only applies on mount. Fix: <code>key={item.id}</code>, so the existing row's fiber moves to index 1 together with its DOM node.</p>
</details>
<h2 id="Exercise-3-—-Count-the-renders"><a href="#Exercise-3-—-Count-the-renders" class="headerlink" title="Exercise 3 — Count the renders"></a>Exercise 3 — Count the renders</h2>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">Parent</span>(<span class="hljs-params"></span>) {</span><br><span class="line">  <span class="hljs-keyword">const</span> [n, setN] = <span class="hljs-title function_">useState</span>(<span class="hljs-number">0</span>);</span><br><span class="line">  <span class="hljs-keyword">return</span> (</span><br><span class="line">    <span class="language-xml"><span class="hljs-tag">&lt;&gt;</span></span><br><span class="line">      <span class="hljs-tag">&lt;<span class="hljs-name">button</span> <span class="hljs-attr">onClick</span>=<span class="hljs-string">{()</span> =&gt;</span> setN(n + 1)}&gt;+<span class="hljs-tag">&lt;/<span class="hljs-name">button</span>&gt;</span></span><br><span class="line">      <span class="hljs-tag">&lt;<span class="hljs-name">Child</span> /&gt;</span></span><br><span class="line">      <span class="hljs-tag">&lt;<span class="hljs-name">MemoChild</span> <span class="hljs-attr">style</span>=<span class="hljs-string">{{</span> <span class="hljs-attr">color:</span> &quot;<span class="hljs-attr">red</span>&quot; }} /&gt;</span></span><br><span class="line">    <span class="hljs-tag">&lt;/&gt;</span></span></span><br><span class="line">  );</span><br><span class="line">}</span><br><span class="line"><span class="hljs-keyword">const</span> <span class="hljs-title class_">MemoChild</span> = <span class="hljs-title function_">memo</span>(<span class="hljs-keyword">function</span> <span class="hljs-title function_">MemoChild</span>(<span class="hljs-params">{ style }</span>) { <span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">p</span> <span class="hljs-attr">style</span>=<span class="hljs-string">{style}</span>&gt;</span>hi<span class="hljs-tag">&lt;/<span class="hljs-name">p</span>&gt;</span></span>; });</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>After one click, which components render?</p>
<details>
<summary>Solution</summary>
<p><code>Parent</code>, <code>Child</code> and <code>MemoChild</code> all render. <code>Child</code> renders because its parent rendered. <code>MemoChild</code> renders because <code>style</code> is a new object literal on every render, so the <code>Object.is</code> comparison fails. Hoist the object to module scope (or <code>useMemo</code> it, or let the React Compiler do it) and <code>MemoChild</code> bails out.</p>
</details>
<h2 id="Exercise-4-—-Make-it-StrictMode-safe"><a href="#Exercise-4-—-Make-it-StrictMode-safe" class="headerlink" title="Exercise 4 — Make it StrictMode-safe"></a>Exercise 4 — Make it StrictMode-safe</h2>
<p>This effect sends two &quot;join&quot; messages in development. Fix it without disabling StrictMode.</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-title function_">useEffect</span>(<span class="hljs-function">() =&gt;</span> {</span><br><span class="line">  chat.<span class="hljs-title function_">send</span>({ <span class="hljs-attr">type</span>: <span class="hljs-string">&quot;join&quot;</span>, roomId });</span><br><span class="line">}, [roomId]);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p>Pair the setup with a cleanup so that setup → cleanup → setup leaves the server in the right state:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-title function_">useEffect</span>(<span class="hljs-function">() =&gt;</span> {</span><br><span class="line">  chat.<span class="hljs-title function_">send</span>({ <span class="hljs-attr">type</span>: <span class="hljs-string">&quot;join&quot;</span>, roomId });</span><br><span class="line">  <span class="hljs-keyword">return</span> <span class="hljs-function">() =&gt;</span> chat.<span class="hljs-title function_">send</span>({ <span class="hljs-attr">type</span>: <span class="hljs-string">&quot;leave&quot;</span>, roomId });</span><br><span class="line">}, [roomId]);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If the protocol cannot express &quot;leave&quot;, the join belongs in the event that caused it (for example the click that opened the room), not in an effect.</p>
</details>
<h2 id="Exercise-5-—-Batching"><a href="#Exercise-5-—-Batching" class="headerlink" title="Exercise 5 — Batching"></a>Exercise 5 — Batching</h2>
<p>What does one click show and log? <code>setN(n + 5); setN(prev =&gt; prev + 1); setTimeout(() =&gt; console.log(n), 0);</code></p>
<details>
<summary>Solution</summary>
<p>The button shows <code>n + 6</code> (the queue is &quot;replace with n + 5&quot;, then &quot;add 1&quot;). The log prints the old <code>n</code>: the timeout's closure captured this render's constant.</p>
</details>
