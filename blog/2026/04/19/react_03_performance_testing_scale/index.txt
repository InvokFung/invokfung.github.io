11:T137b0,<p>The first three posts built the model: how React renders, how hooks and state fit together, and how concurrent React schedules work. This last core post is about keeping a large React codebase fast, correct and usable as it grows. It starts with measurement — the Profiler, DevTools and React 19.2 Performance Tracks — because most React performance work fails by fixing the wrong thing. Then it covers the fixes in order of how often they matter: fewer renders (memoisation, with and without React Compiler), less rendered (virtualisation), less shipped (code splitting). The second half covers the parts that keep a big app healthy: error boundaries, a testing strategy with Vitest, React Testing Library and Playwright, accessibility, and the architecture of reusable component libraries — compound components, headless UI and polymorphism. Examples target <strong>React 19.2</strong>.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Profile a slow interaction and classify the cause before changing code.</li>
<li>Read the React DevTools Profiler (flame graph, ranked view, &quot;why did this render&quot;) and the <code>&lt;Profiler&gt;</code> API.</li>

<h1 id="Chapter-1-—-Measure-first"><a href="#Chapter-1-—-Measure-first" class="headerlink" title="Chapter 1 — Measure first"></a>Chapter 1 — Measure first</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Render time</strong> — time spent calling components and reconciling (the render phase, Post 00).</li>
<li><strong>Commit time</strong> — time spent applying DOM changes and running layout effects.</li>
<li><strong><code>actualDuration</code></strong> — time spent rendering a subtree for this commit, after memoisation.</li>
<li><strong><code>baseDuration</code></strong> — estimated time to render the whole subtree with no memoisation. The gap between the two shows how much memoisation is saving.</li>
<li><strong>INP (Interaction to Next Paint)</strong> — the Core Web Vital for responsiveness since March 2024. &quot;Good&quot; is 200 ms or less at the 75th percentile.</li>
</ul>
<h2 id="The-workflow"><a href="#The-workflow" class="headerlink" title="The workflow"></a>The workflow</h2>
<ol>
<li><strong>Reproduce</strong> the slow interaction with a production-like build and realistic data. Development builds are several times slower and StrictMode doubles renders; do not judge speed there.</li>
<li><strong>Record</strong> it: React DevTools Profiler for components, the browser Performance panel for everything else.</li>
<li><strong>Classify</strong> the cost (table below).</li>
<li><strong>Fix</strong> the one thing the profile points at.</li>
<li><strong>Profile again.</strong> A fix that does not move the number is reverted.</li>
</ol>
<table>
<thead>
<tr>

<th>Cause</th>
<th>Fix</th>
</tr>
</thead>

<td>Too many renders</td>

<h2 id="Performance-Tracks-React-192"><a href="#Performance-Tracks-React-192" class="headerlink" title="Performance Tracks (React 19.2)"></a>Performance Tracks (React 19.2)</h2>
<p>React 19.2 adds custom tracks to the Chrome Performance panel: <strong>Scheduler</strong> (work by priority — blocking, transition — Post 02) and <strong>Components</strong> (which components rendered and ran effects). They put React's view next to network, layout and paint on one timeline, which is the fastest way to see whether a long task is React work at all.</p>
<blockquote>
<p><strong>Watch out:</strong> &quot;it re-renders a lot&quot; is not a performance problem until it shows up in a profile as time the user waits for. A component that renders 50 times in 0.1 ms each is fine; one that renders once in 180 ms is not.</p>
</blockquote>

<p>Before memoising, try the structural fixes from Post 00 — they cost nothing at runtime and cannot go stale:</p>
<ul>
<li><strong>Move state down</strong> into the component that uses it, so its siblings stop rendering.</li>
<li><strong>Lift content up</strong> into <code>children</code>, so a stateful wrapper does not re-render its content.</li>
<li><strong>Split contexts</strong> so a fast-changing value does not re-render every consumer.</li>
</ul>
<h2 id="With-React-Compiler"><a href="#With-React-Compiler" class="headerlink" title="With React Compiler"></a>With React Compiler</h2>
<p>React Compiler 1.0 (Post 02) memoises JSX, objects, callbacks and computations automatically, at a finer grain than hand-written hooks. In a compiled codebase:</p>
<ul>
<li>New code rarely needs <code>memo</code>, <code>useMemo</code> or <code>useCallback</code>. Write plain code.</li>
<li><strong>Keep</strong> manual memoisation where a value's identity is part of correctness — an effect dependency that must not change — so the intent is explicit.</li>
<li><strong>Do not bulk-delete</strong> existing memoisation; the React team advises leaving it or removing it carefully with tests, because removal can change the compiled output.</li>
<li>Components the compiler <strong>skips</strong> (Rules of React violations) get no help. The <code>eslint-plugin-react-hooks</code> compiler rules list them; fixing them is usually the real performance work.</li>
<li>The compiler does not fix expensive algorithms, huge DOM trees or big bundles. Chapters 3 and 4 still apply.</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> <code>useMemo(() =&gt; items.filter(...), [items])</code> where <code>items</code> is rebuilt by the parent on every render. The memo recomputes every time and adds overhead. Memoisation has to start at the source of the value.</p>
</blockquote>

<p>Trade-offs to plan for:</p>
<ul>
<li><strong>Find in page</strong> (Ctrl+F) cannot find rows that are not rendered.</li>
<li><strong>Accessibility</strong>: screen readers see only rendered rows. Set <code>aria-rowcount</code> / <code>aria-rowindex</code> on grids, or offer pagination.</li>
<li><strong>Variable heights</strong> need measurement, which can cause scroll jumps.</li>
<li><strong>Scroll restoration</strong> needs the virtualiser's offset, not <code>window.scrollY</code>.</li>
</ul>

It saves browser work, not React render work.</p>

<p>Rules and techniques:</p>
<ul>
<li><strong>Declare <code>lazy</code> at module level.</strong> Calling <code>lazy</code> inside a component creates a new component type every render — the remount bug from Post 00.</li>
<li><strong>Split by route first</strong>, then by heavy interaction-only features (editors, charts, maps, date pickers).</li>
<li><strong>Preload on intent</strong>: start the <code>import()</code> on hover or focus of the link, so the chunk is ready at click time. Keep the loader function in a variable and call it in both places; the module cache makes the second call free.</li>
<li><strong>Navigate in a Transition</strong> so the current page stays visible while the next chunk loads (Post 02), instead of showing the top-level fallback.</li>

</ul>

</blockquote>

<p>What error boundaries <strong>do not</strong> catch:</p>
<ul>
<li>errors in <strong>event handlers</strong> (use <code>try/catch</code>, or show the error through state),</li>
<li>errors in async code that is not part of rendering (<code>setTimeout</code>, a promise in a handler),</li>
<li>errors in the boundary itself,</li>
<li>errors during server rendering.</li>
</ul>
<p>Promises rejected through <code>use()</code> and errors thrown by Actions (Post 02) do reach the nearest boundary.</p>
<h2 id="Placement"><a href="#Placement" class="headerlink" title="Placement"></a>Placement</h2>
<ul>
<li><strong>Root</strong>: a last-resort &quot;something went wrong&quot; page with a reload button.</li>
<li><strong>Per route</strong>: one broken page does not take the navigation down.</li>
<li><strong>Per widget</strong> for independent panels (a dashboard card, a third-party embed).</li>
<li><strong>Reset on navigation</strong>: pass <code>resetKeys={[location.pathname]}</code> (or key the boundary) so moving away clears the error.</li>

<p>Principles that keep these tests valuable:</p>
<ul>
<li><strong>Query like a user.</strong> Prefer <code>getByRole</code> with an accessible name, then <code>getByLabelText</code>, <code>getByText</code>; use <code>getByTestId</code> last. Role queries double as accessibility checks: if the test cannot find the button by role and name, neither can a screen reader.</li>
<li><strong>Use <code>user-event</code></strong>, not <code>fireEvent</code>: it simulates the full sequence of browser events (focus, keydown, input, keyup).</li>
<li><strong>Wait for async UI</strong> with <code>findBy…</code> or <code>waitFor</code>, not with timers.</li>
<li><strong>Mock the network, not your modules.</strong> MSW intercepts requests, so the component, its hooks and the data library all run for real.</li>
<li><strong>Do not test implementation details</strong> — internal state, hook call counts, component names. Tests that survive refactors are the ones worth keeping.</li>
</ul>
<p>For components that depend on real layout, CSS or browser APIs that jsdom lacks, Vitest's <strong>Browser Mode</strong> (stable since Vitest 4.0) runs the same tests in a real browser through Playwright or WebdriverIO.</p>

<h1 id="Chapter-8-—-Component-library-architecture"><a href="#Chapter-8-—-Component-library-architecture" class="headerlink" title="Chapter 8 — Component-library architecture"></a>Chapter 8 — Component-library architecture</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Compound components</strong> — a set of components that work together and share state through context: <code>&lt;Tabs&gt;</code>, <code>&lt;Tabs.List&gt;</code>, <code>&lt;Tabs.Tab&gt;</code>, <code>&lt;Tabs.Panel&gt;</code>.</li>
<li><strong>Headless component</strong> — behaviour, state and accessibility without styling, delivered as hooks or unstyled components (Radix UI Primitives, React Aria, Headless UI, TanStack Table).</li>
<li><strong>Controlled / uncontrolled</strong> — the parent owns the value (<code>value</code> + <code>onChange</code>) or the component does (<code>defaultValue</code>).</li>
<li><strong>Polymorphism</strong> — one component that can render as different elements (<code>&lt;Button as=&quot;a&quot;&gt;</code>) or merge its behaviour into a child (<code>asChild</code>).</li>
</ul>

<h2 id="Headless-first"><a href="#Headless-first" class="headerlink" title="Headless first"></a>Headless first</h2>
<p>Splitting behaviour from appearance lets one design system serve many products. The behaviour layer — keyboard handling, focus management, ARIA attributes, positioning — is the hard, bug-prone part; the visual layer is the part each product wants to change. Mature headless libraries implement the ARIA patterns and test them across browsers and screen readers. Wrapping one with your design tokens is usually cheaper and more accessible than building from divs.</p>
<h2 id="Polymorphism-as-vs-asChild"><a href="#Polymorphism-as-vs-asChild" class="headerlink" title="Polymorphism: as vs asChild"></a>Polymorphism: <code>as</code> vs <code>asChild</code></h2>

<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-comment">// `asChild`: merge props into the single child (Radix Slot pattern)</span></span><br><span class="line">&lt;<span class="hljs-title class_">Button</span> asChild&gt;</span><br><span class="line">  <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">Link</span> <span class="hljs-attr">href</span>=<span class="hljs-string">&quot;/docs&quot;</span>&gt;</span>Docs<span class="hljs-tag">&lt;/<span class="hljs-name">Link</span>&gt;</span></span></span><br><span class="line">&lt;/<span class="hljs-title class_">Button</span>&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The <code>as</code> prop gets complicated in TypeScript (generic props, refs, conflicting prop names) and type-checks slowly in big unions. <code>asChild</code> keeps the child's own types and works with any router's <code>Link</code>, at the cost of a merging step (class names, event handlers, refs). Many design systems now prefer <code>asChild</code> or a render prop.</p>
<blockquote>
<p><strong>Trick:</strong> keep library components free of data fetching and app state. A component library that imports your API client cannot be reused, tested in isolation, or shown in Storybook.</p>
</blockquote>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Classify-the-profile"><a href="#Exercise-1-—-Classify-the-profile" class="headerlink" title="Exercise 1 — Classify the profile"></a>Exercise 1 — Classify the profile</h2>
<p>A table re-renders all 300 rows when a user types in a header search box. Each row takes 0.4 ms. What do you do first?</p>
<details>
<summary>Solution</summary>
<p>Classify: many components render with the same output, total about 120 ms per keystroke. First try structure: keep the search box state in the header component (move state down) so the table does not render on keystrokes; filter with <code>useDeferredValue</code> so typing stays urgent. Memoise rows (<code>memo</code>, or the compiler) only if the table must still re-render. Profile again after each change.</p>
</details>
<h2 id="Exercise-2-—-Why-is-memo-useless-here"><a href="#Exercise-2-—-Why-is-memo-useless-here" class="headerlink" title="Exercise 2 — Why is memo useless here?"></a>Exercise 2 — Why is <code>memo</code> useless here?</h2>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="jsx"><span class="line">&lt;<span class="hljs-title class_">MemoRow</span> item={item} onSelect={<span class="hljs-function">() =&gt;</span> <span class="hljs-title function_">select</span>(item.<span class="hljs-property">id</span>)} style={{ <span class="hljs-attr">padding</span>: <span class="hljs-number">8</span> }} /&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p><code>onSelect</code> and <code>style</code> are new on every render, so the prop comparison always fails. Hoist <code>style</code> to a module constant; pass <code>onSelect={select}</code> (stable via <code>useCallback</code> or <code>useReducer</code> dispatch) and let the row call <code>onSelect(item.id)</code>. Or enable React Compiler, which memoises both.</p>
</details>
<h2 id="Exercise-3-—-Boundary-placement"><a href="#Exercise-3-—-Boundary-placement" class="headerlink" title="Exercise 3 — Boundary placement"></a>Exercise 3 — Boundary placement</h2>
<p>A dashboard has a navigation bar and six independent widgets. One widget's third-party chart throws on bad data and the whole page goes white. Design the boundaries.</p>
<details>
<summary>Solution</summary>
<p>A root boundary with a reload page; a route-level boundary under the navigation bar so navigation survives; one boundary per widget with a small &quot;This widget failed — retry&quot; fallback and <code>resetKeys</code> tied to the widget's inputs. Report from <code>componentDidCatch</code> (or <code>onError</code>) and from the root's <code>onCaughtError</code> / <code>onUncaughtError</code>.</p>
</details>
<h2 id="Exercise-4-—-Rewrite-a-brittle-test"><a href="#Exercise-4-—-Rewrite-a-brittle-test" class="headerlink" title="Exercise 4 — Rewrite a brittle test"></a>Exercise 4 — Rewrite a brittle test</h2>

<details>
<summary>Solution</summary>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">const</span> user = userEvent.<span class="hljs-title function_">setup</span>();</span><br><span class="line"><span class="hljs-title function_">render</span>(<span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">Login</span> /&gt;</span></span>);</span><br><span class="line"><span class="hljs-keyword">await</span> user.<span class="hljs-title function_">type</span>(screen.<span class="hljs-title function_">getByLabelText</span>(<span class="hljs-regexp">/email/i</span>), <span class="hljs-string">&quot;a@b.co&quot;</span>);</span><br><span class="line"><span class="hljs-keyword">await</span> user.<span class="hljs-title function_">click</span>(screen.<span class="hljs-title function_">getByRole</span>(<span class="hljs-string">&quot;button&quot;</span>, { <span class="hljs-attr">name</span>: <span class="hljs-regexp">/sign in/i</span> }));</span><br><span class="line"><span class="hljs-title function_">expect</span>(<span class="hljs-keyword">await</span> screen.<span class="hljs-title function_">findByText</span>(<span class="hljs-regexp">/welcome back/i</span>)).<span class="hljs-title function_">toBeInTheDocument</span>();</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>It queries by what the user sees (and proves the label and button name exist), uses real event sequences, mocks the network with MSW instead of the module, and asserts the visible result.</p>
</details>
<h2 id="Exercise-5-—-Make-a-compound-component"><a href="#Exercise-5-—-Make-a-compound-component" class="headerlink" title="Exercise 5 — Make a &lt;Disclosure> compound component"></a>Exercise 5 — Make a <code>&lt;Disclosure&gt;</code> compound component</h2>
<p>Design <code>&lt;Disclosure&gt;</code>, <code>&lt;Disclosure.Button&gt;</code> and <code>&lt;Disclosure.Panel&gt;</code> that work controlled and uncontrolled and are accessible.</p>
<details>
<summary>Solution</summary>
<p>The root holds <code>open</code> (controlled via <code>open</code> / <code>onOpenChange</code>, uncontrolled via <code>defaultOpen</code>) and a <code>useId()</code> id in context. <code>Disclosure.Button</code> renders a <code>&lt;button aria-expanded={open} aria-controls={id}&gt;</code> that toggles. <code>Disclosure.Panel</code> renders <code>&lt;div id={id} hidden={!open}&gt;</code>. Test it with role queries: <code>getByRole(&quot;button&quot;, { name })</code>, then assert <code>aria-expanded</code> and panel visibility after <code>user.click</code>.</p>
</details>
