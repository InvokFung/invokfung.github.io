<h1 id="Chapter-1-—-Semantic-Versioning-200"><a href="#Chapter-1-—-Semantic-Versioning-200" class="headerlink" title="Chapter 1 — Semantic Versioning 2.0.0"></a>Chapter 1 — Semantic Versioning 2.0.0</h1>
<p>SemVer 2.0.0 (<a href="http://semver.org" target="_blank" rel="noopener external nofollow noreferrer">semver.org</a>) gives a version three numbers, <code>MAJOR.MINOR.PATCH</code>:</p>
<table>
<thead>
<tr>
<th>Bump</th>
<th>When</th>
<th>Example</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>MAJOR</strong></td>
<td>An incompatible change to the public API</td>
<td><code>2.4.1</code> → <code>3.0.0</code></td>
</tr>
<tr>
<td><strong>MINOR</strong></td>
<td>New functionality, backward compatible</td>
<td><code>2.4.1</code> → <code>2.5.0</code></td>
</tr>
<tr>
<td><strong>PATCH</strong></td>
<td>Backward-compatible bug fixes</td>
<td><code>2.4.1</code> → <code>2.4.2</code></td>
</tr>
</tbody>
</table>
<p>Two optional parts can follow:</p>
<ul>
<li><strong>Pre-release</strong>, after a hyphen: <code>1.0.0-alpha.1</code>, <code>1.0.0-rc.2</code>. A pre-release sorts <strong>before</strong> the normal release.</li>
<li><strong>Build metadata</strong>, after a plus: <code>1.0.0+build.5</code>, <code>1.0.0+sha.5114f85</code>. It is <strong>ignored</strong> when comparing versions.</li>
</ul>
<p>The spec's own precedence example (npm's <code>semver</code> library sorts it the same way):</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">1.0.0-alpha &lt; 1.0.0-alpha.1 &lt; 1.0.0-beta &lt; 1.0.0-beta.2 &lt; 1.0.0-beta.11 &lt; 1.0.0-rc.1 &lt; 1.0.0</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Note <code>beta.2 &lt; beta.11</code>: identifiers made only of digits compare as numbers, not as text.</p>
<p><strong>The special meaning of 0.x.</strong> SemVer item 4 says major version zero is for initial development: &quot;Anything MAY change at any time.&quot; So <code>0.4.0</code> → <code>0.5.0</code> may break you. The FAQ adds that software already used in production &quot;should probably already be 1.0.0&quot;. Treat every <code>0.x</code> minor bump like a major one.</p>
<p><strong>SemVer is a promise, not a proof.</strong> The maintainer decides what counts as &quot;breaking&quot;. A patch that fixes a bug you relied on still breaks you. Version numbers tell you <strong>where to look first</strong>; tests tell you whether it works.</p>
<p><strong>Python is not SemVer.</strong> Python packages follow <strong>PEP 440</strong> (now the &quot;Version specifiers&quot; spec on <a href="http://packaging.python.org" target="_blank" rel="noopener external nofollow noreferrer">packaging.python.org</a>). It looks similar but is spelled differently: <code>1.0.0a1</code>, <code>1.0.0b2</code>, <code>1.0.0rc1</code> (pre-releases), <code>1.0.0.post1</code> (post-release), <code>1.0.0.dev3</code> (development). Tools normalise other spellings, so <code>1.0.0-alpha.1</code> becomes <code>1.0.0a1</code>.</p>

<h2 id="npm-ci-vs-npm-install"><a href="#npm-ci-vs-npm-install" class="headerlink" title="npm ci vs npm install"></a><code>npm ci</code> vs <code>npm install</code></h2>
<p>According to the npm docs, <code>npm ci</code>:</p>
<ul>
<li>needs an existing <code>package-lock.json</code>;</li>
<li><strong>fails</strong> if <code>package.json</code> and the lock disagree, instead of updating the lock;</li>
<li>deletes <code>node_modules</code> first, then installs;</li>
<li>never writes to <code>package.json</code> or the lockfile.</li>
</ul>
<p>Use <code>npm install</code> when you <strong>change</strong> dependencies on your machine, and <code>npm ci</code> in CI and deployment. uv has the same split: <code>uv add</code> and <code>uv lock</code> change the lock, <code>uv sync --locked</code> fails if the lock is out of date, and <code>uv sync --frozen</code> uses the lock without checking it.</p>

<h1 id="Chapter-5-—-A-safe-upgrade-workflow"><a href="#Chapter-5-—-A-safe-upgrade-workflow" class="headerlink" title="Chapter 5 — A safe upgrade workflow"></a>Chapter 5 — A safe upgrade workflow</h1>
<ol>
<li><strong>See what is behind.</strong> <code>npm outdated</code>, <code>pnpm outdated</code>, <code>uv tree --outdated</code>, <code>pip list --outdated</code>.</li>
<li><strong>Read the changelog</strong> or release notes, and the migration guide for majors. Search for &quot;breaking&quot;, &quot;removed&quot;, &quot;deprecated&quot;, &quot;minimum Node&quot;, &quot;minimum Python&quot;.</li>
<li><strong>One major at a time</strong>, on its own branch. Patch and minor updates can be grouped.</li>
<li><strong>Let the tool change the lock:</strong> <code>npm install foo@^5</code>, <code>uv lock --upgrade-package foo</code>.</li>
<li><strong>Run the tests, the build and a quick manual check.</strong> Read the lockfile diff. An upgrade that adds 40 new transitive packages deserves a second look.</li>
<li><strong>Merge small, deploy, watch.</strong> One small change is easy to revert or bisect (see Dev Essentials 10 · Debugging).</li>
</ol>

<p>The Hexo build workflow behind this blog still says:</p>

<p>Two separate things have aged here:</p>

</ul>
<p>Today (September 2026), per Node's release schedule, Node 24 is Active LTS until 2026-10-20 and then in maintenance until 2028-04-30. Node 22 is in maintenance until 2027-04-30, and Node 26 becomes LTS on 2026-10-28. A safe plan is to move the build to Node 24 and the action to its current major in <strong>one small branch</strong>. Run the Hexo build, compare the generated site, then merge. <h2 id="The-cost-of-an-exact-pin"><a href="#The-cost-of-an-exact-pin" class="headerlink" title="The cost of an exact pin"></a>The cost of an exact pin</h2>
<p>The Next.js pin from Chapter 2, <code>&quot;next&quot;: &quot;14.2.18&quot;</code>, is inside the affected range of <strong>CVE-2025-29927</strong>. That is a critical (CVSS 9.1) authorization bypass in Next.js middleware, published March 21, 2025. It affects 14.0 up to but not including 14.2.25, and 14.2.25 fixes it. Whether it matters depends on use: only apps that rely on middleware for authorization are exposed. A static export (<code>output: &quot;export&quot;</code>) produces plain files and does not support middleware at all, so a statically exported site like this blog is not exposed — but the pin would still carry the bug into any future server deployment. The lesson is general, though. An exact pin never moves by itself, so pair it with a bot that proposes updates and an audit in CI.</p>

<p>GitHub's docs state that <code>cooldown</code> applies to <strong>version</strong> updates only, not <strong>security</strong> updates, so security fixes still arrive at once.</p>

<p><code>renovate.json</code>:</p>
<pre><code class="language-json"><figure class="highlight json"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="json"><span class="line"><span class="hljs-punctuation">{</span></span><br><span class="line">  <span class="hljs-attr">&quot;$schema&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-string">&quot;https://docs.renovatebot.com/renovate-schema.json&quot;</span><span class="hljs-punctuation">,</span></span><br><span class="line">  <span class="hljs-attr">&quot;extends&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">[</span><span class="hljs-string">&quot;config:recommended&quot;</span><span class="hljs-punctuation">]</span><span class="hljs-punctuation">,</span></span><br><span class="line">  <span class="hljs-attr">&quot;minimumReleaseAge&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-string">&quot;3 days&quot;</span></span><br><span class="line"><span class="hljs-punctuation">}</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>minimumReleaseAge</code> makes Renovate wait until a release is that old before it opens a PR. The default is <code>null</code> (no wait).</p>
<h2 id="Audits"><a href="#Audits" class="headerlink" title="Audits"></a>Audits</h2>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="bash"><span class="line">npm audit                        <span class="hljs-comment"># known advisories for the installed tree</span></span><br><span class="line">npm audit --omit=dev             <span class="hljs-comment"># only what ships to production</span></span><br><span class="line">npm audit signatures             <span class="hljs-comment"># verify registry signatures and provenance attestations</span></span><br><span class="line">pip install pip-audit &amp;&amp; pip-audit -r requirements.txt    <span class="hljs-comment"># PyPA tool; PyPI or OSV data</span></span><br><span class="line">osv-scanner scan -L package-lock.json                     <span class="hljs-comment"># OSV-Scanner v2, many ecosystems</span></span><br><span class="line">osv-scanner scan -r .</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>These tools compare your exact versions with advisory databases such as the GitHub Advisory Database and <strong>OSV</strong> (osv.dev). Read the results with judgement. A vulnerable function you never call, in a dev-only tool, matters less than a vulnerable web framework in production. Still, fix or document every finding rather than muting the scanner.</p>
<blockquote>
<p><strong>Common pitfall:</strong> running <code>npm audit fix --force</code> blindly. It can jump major versions to reach a fixed release, which is the &quot;big bang upgrade&quot; Chapter 5 warns against.</p>
</blockquote>

<h1 id="Chapter-7-—-Supply-chain-attacks-how-they-really-happen"><a href="#Chapter-7-—-Supply-chain-attacks-how-they-really-happen" class="headerlink" title="Chapter 7 — Supply-chain attacks: how they really happen"></a>Chapter 7 — Supply-chain attacks: how they really happen</h1>
<p>An attacker who cannot break into your app can break into something your app installs. The main patterns:</p>
<ul>
<li><strong>Typosquatting</strong> — a malicious package whose name is one typo away from a popular one.</li>
<li><strong>Dependency confusion</strong> — a public package with the same name as your private internal one, which a misconfigured installer prefers.</li>
<li><strong>Compromised maintainer account</strong> — a stolen password or token, or a phished 2FA code, followed by a malicious release of a real, trusted package.</li>
<li><strong>Malicious install scripts</strong> — <code>preinstall</code> / <code>postinstall</code> code runs on your laptop or CI runner the moment you install, before you import anything.</li>
<li><strong>Takeover of an abandoned asset</strong> — a domain, CDN or package that passes to a new owner.</li>
</ul>

<h2 id="How-the-platforms-responded"><a href="#How-the-platforms-responded" class="headerlink" title="How the platforms responded"></a>How the platforms responded</h2>
<ul>

<h1 id="Chapter-8-—-Mitigations-you-can-apply-today"><a href="#Chapter-8-—-Mitigations-you-can-apply-today" class="headerlink" title="Chapter 8 — Mitigations you can apply today"></a>Chapter 8 — Mitigations you can apply today</h1>
<h2 id="1-Lock-and-install-exactly"><a href="#1-Lock-and-install-exactly" class="headerlink" title="1. Lock, and install exactly"></a>1. Lock, and install exactly</h2>
<p>Commit lockfiles, and use <code>npm ci</code>, <code>pnpm install --frozen-lockfile</code> or <code>uv sync --locked</code> in CI (Chapter 3). A malicious new release cannot enter a build that installs only locked, hashed versions.</p>

<h2 id="3-Do-not-run-install-scripts-you-did-not-approve"><a href="#3-Do-not-run-install-scripts-you-did-not-approve" class="headerlink" title="3. Do not run install scripts you did not approve"></a>3. Do not run install scripts you did not approve</h2>
<ul>
<li><strong>npm 12+:</strong> dependency scripts are blocked by default. Approve the ones you need with <code>npm install-scripts approve</code>, which records them in the root <code>allowScripts</code> policy, then run <code>npm rebuild</code>.</li>
<li><strong>Older npm:</strong> <code>ignore-scripts=true</code> in <code>.npmrc</code> stops all scripts. Packages with native parts may then need a manual <code>npm rebuild &lt;pkg&gt;</code>.</li>
<li><strong>pnpm 10+:</strong> scripts are off by default. <code>pnpm approve-builds</code> adds the packages you approve to <code>allowBuilds</code> in <code>pnpm-workspace.yaml</code>.</li>
</ul>
<h2 id="4-Check-where-packages-came-from"><a href="#4-Check-where-packages-came-from" class="headerlink" title="4. Check where packages came from"></a>4. Check where packages came from</h2>
<p><strong>Provenance</strong> links a published package to the source repository and the CI build that produced it, signed through <strong>Sigstore</strong>. As a consumer, run <code>npm audit signatures</code>. As a maintainer, publish from CI with trusted publishing, or with <code>npm publish --provenance</code> and the <code>id-token: write</code> permission in GitHub Actions. PyPI supports trusted publishing too. npm's docs are careful here: provenance shows <strong>where</strong> a package came from, but it does not promise the code is free of malware.</p>
<h2 id="5-Know-what-you-ship-SBOMs"><a href="#5-Know-what-you-ship-SBOMs" class="headerlink" title="5. Know what you ship: SBOMs"></a>5. Know what you ship: SBOMs</h2>
<p>A <strong>Software Bill of Materials</strong> lists every component and version in a build, in a standard format (<strong>CycloneDX</strong> or <strong>SPDX</strong>). When the next xz-style advisory appears, you search your SBOMs instead of guessing.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">npm sbom --sbom-format cyclonedx &gt; sbom.cdx.json</span><br><span class="line">npm sbom --sbom-format spdx      &gt; sbom.spdx.json</span><br><span class="line">uv <span class="hljs-built_in">export</span> --format cyclonedx1.5 -o sbom.cdx.json</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="6-Protect-your-own-publishing"><a href="#6-Protect-your-own-publishing" class="headerlink" title="6. Protect your own publishing"></a>6. Protect your own publishing</h2>
<p>Use passkeys or hardware keys, which resist phishing, instead of TOTP codes on registry accounts. Prefer trusted publishing to long-lived tokens, and give CI tokens the smallest scope.</p>
<h2 id="7-Add-fewer-dependencies"><a href="#7-Add-fewer-dependencies" class="headerlink" title="7. Add fewer dependencies"></a>7. Add fewer dependencies</h2>
<p>Before adding a package, check who maintains it, when it last released, whether it has install scripts, and how many transitive packages it brings. A 10-line helper you write yourself has no supply chain.</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Which-versions-match"><a href="#Exercise-1-—-Which-versions-match" class="headerlink" title="Exercise 1 — Which versions match?"></a>Exercise 1 — Which versions match?</h2>
<p>For each range, which of <code>0.2.9</code>, <code>0.3.0</code>, <code>1.2.9</code>, <code>1.3.0</code> match: <code>^0.2.3</code>, <code>~1.2.3</code>, <code>^1.2.3</code>? And which of <code>2.2</code>, <code>2.9</code>, <code>3.0</code> match pip's <code>~=2.2</code>?</p>
<details>
<summary>Solution</summary>
<table>
<thead>
<tr>
<th>Range</th>
<th>Matches</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>^0.2.3</code></td>
<td><code>0.2.9</code> only (the left-most non-zero number is the minor, so <code>&lt;0.3.0</code>)</td>
</tr>
<tr>
<td><code>~1.2.3</code></td>
<td><code>1.2.9</code> only</td>
</tr>
<tr>
<td><code>^1.2.3</code></td>
<td><code>1.2.9</code>, <code>1.3.0</code></td>
</tr>
<tr>
<td><code>~=2.2</code></td>
<td><code>2.2</code>, <code>2.9</code> (it means <code>&gt;=2.2, ==2.*</code>)</td>
</tr>
</tbody>
</table>
<p>Check with <code>npx semver -r &quot;^0.2.3&quot; 0.2.9 0.3.0 1.2.9 1.3.0</code>.</p>
</details>
<h2 id="Exercise-2-—-Pick-the-bump"><a href="#Exercise-2-—-Pick-the-bump" class="headerlink" title="Exercise 2 — Pick the bump"></a>Exercise 2 — Pick the bump</h2>
<p>A library is at <code>3.4.2</code>. Give the next version for: (a) a fix for a crash on empty input; (b) a new optional <code>timeout</code> parameter; (c) renaming <code>connect()</code> to <code>open()</code>; (d) the same rename when the library is at <code>0.9.2</code>.</p>
<details>
<summary>Solution</summary>
<p>(a) <code>3.4.3</code> (PATCH). (b) <code>3.5.0</code> (MINOR, backward compatible). (c) <code>4.0.0</code> (MAJOR, breaking). (d) <code>0.10.0</code> by convention. Under 0.x anything may change, and the SemVer FAQ suggests bumping the minor for each release. Users of <code>^0.9.2</code> will not get it automatically, which is what you want.</p>
</details>
<h2 id="Exercise-3-—-It-works-on-my-machine"><a href="#Exercise-3-—-It-works-on-my-machine" class="headerlink" title="Exercise 3 — &quot;It works on my machine&quot;"></a>Exercise 3 — &quot;It works on my machine&quot;</h2>
<p>CI runs <code>npm install</code> and sometimes fails with errors nobody sees locally. <code>package-lock.json</code> is listed in <code>.gitignore</code>. Explain the cause and the fix.</p>
<details>
<summary>Solution</summary>
<p>Without a committed lock, every CI run resolves the ranges again and may pick newer transitive versions than your machine has. Fix: remove <code>package-lock.json</code> from <code>.gitignore</code>, run <code>npm install</code> once, commit the lockfile, and change CI to <code>npm ci</code>. Now CI fails loudly when <code>package.json</code> and the lock disagree, instead of quietly installing something new.</p>
</details>
<h2 id="Exercise-4-—-Why-is-it-here"><a href="#Exercise-4-—-Why-is-it-here" class="headerlink" title="Exercise 4 — Why is it here?"></a>Exercise 4 — Why is it here?</h2>
<p>An audit flags <code>vulnerable-child@1.0.2</code>, which is not in your <code>package.json</code>. Find who brings it in, and fix it if the parent has no update yet.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">npm explain vulnerable-child      <span class="hljs-comment"># e.g. your-dep &gt; some-parent &gt; vulnerable-child</span></span><br><span class="line">npm view vulnerable-child versions --json</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>First try upgrading the parent (read its changelog). If no fixed parent exists, add an override and test:</p>
<pre><code class="language-json"><figure class="highlight json"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="json"><span class="line"><span class="hljs-punctuation">{</span> <span class="hljs-attr">&quot;overrides&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span> <span class="hljs-attr">&quot;some-parent&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span> <span class="hljs-attr">&quot;vulnerable-child&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-string">&quot;1.0.3&quot;</span> <span class="hljs-punctuation">}</span> <span class="hljs-punctuation">}</span> <span class="hljs-punctuation">}</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Run <code>npm install</code>, confirm with <code>npm ls vulnerable-child</code>, and leave a note to remove the override later. In Python: <code>uv tree --invert --package vulnerable-child</code>, then <code>override-dependencies</code> under <code>[tool.uv]</code>.</p>
</details>
<h2 id="Exercise-5-—-A-calm-update-bot"><a href="#Exercise-5-—-A-calm-update-bot" class="headerlink" title="Exercise 5 — A calm update bot"></a>Exercise 5 — A calm update bot</h2>
<p>Write a Dependabot config for a repo with npm and GitHub Actions. It should check weekly, wait 7 days before proposing npm releases (14 days for majors), and still deliver security fixes at once.</p>
<details>
<summary>Solution</summary>
<p>The <code>dependabot.yml</code> in Chapter 6 does exactly this. The <code>cooldown</code> block gives the 7- and 14-day waits. Security updates ignore <code>cooldown</code>, so they still arrive at once, as long as Dependabot security updates are turned on in the repository settings.</p>
</details>
<h2 id="Exercise-6-—-Plan-the-Node-upgrade-for-the-Hexo-CI"><a href="#Exercise-6-—-Plan-the-Node-upgrade-for-the-Hexo-CI" class="headerlink" title="Exercise 6 — Plan the Node upgrade for the Hexo CI"></a>Exercise 6 — Plan the Node upgrade for the Hexo CI</h2>
<p>The workflow uses <code>actions/setup-node@v3</code> with <code>node-version: 16</code>. Write the steps to bring it up to date safely.</p>
<details>
<summary>Solution</summary>
<ol>
<li>Create a branch: <code>git switch -c ci/node-24</code>.</li>
<li>Read the setup-node release notes from v3 up to the current major (v7) for changed inputs. Check that Hexo and its plugins support Node 24 (their <code>engines</code> fields and changelogs).</li>
<li>Change the step:</li>
</ol>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-bullet">-</span> <span class="hljs-attr">uses:</span> <span class="hljs-string">actions/setup-node@v7</span></span><br><span class="line">  <span class="hljs-attr">with:</span></span><br><span class="line">    <span class="hljs-attr">node-version:</span> <span class="hljs-number">24</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ol start="4">
<li>Locally, install Node 24 (for example with nvm-windows), delete <code>node_modules</code>, run <code>npm ci</code>, then <code>npx hexo clean &amp;&amp; npx hexo generate</code>. Compare the <code>public/</code> output with a build from the old setup.</li>
<li>Push the branch and let CI run. Merge only when the build passes and the site looks the same.</li>
<li>Add the <code>github-actions</code> ecosystem to Dependabot so the action does not drift again.</li>
