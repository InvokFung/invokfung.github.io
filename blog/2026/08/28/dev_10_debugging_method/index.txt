<h1 id="Chapter-1-—-The-debugging-loop"><a href="#Chapter-1-—-The-debugging-loop" class="headerlink" title="Chapter 1 — The debugging loop"></a>Chapter 1 — The debugging loop</h1>
<p>Most wasted debugging time comes from changing things at random. The fix is a loop borrowed from the scientific method:</p>
<ol>
<li><strong>Observe.</strong> What exactly happened? Copy the full error text. Note the input, the time, the version.</li>
<li><strong>Hypothesize.</strong> Make one specific guess: &quot;one order item has no <code>qty</code> key&quot;.</li>
<li><strong>Test one change.</strong> Design a check that proves or kills the guess. Change <strong>one</strong> thing only.</li>
<li><strong>Record.</strong> Write down what you tried and what happened. Then loop.</li>
</ol>
<p>A tiny log in a text file is enough. It stops you testing the same idea twice, and it becomes your bug report or commit message:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="text"><span class="line">14:05  Symptom: report crashes with KeyError: &#x27;qty&#x27; on orders.json (prod copy).</span><br><span class="line">14:08  Guess: one item uses a different key name.  Test: print keys of each item.</span><br><span class="line">14:10  Result: order A-2, item 2 has &quot;quantity&quot; not &quot;qty&quot;. Confirmed.</span><br><span class="line">14:12  Next: where does &quot;quantity&quot; come from? Check the export script.</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> if you change two things and the bug vanishes, you learn nothing. You do not know which change fixed it, or if one of them only hid it.</p>
</blockquote>

<ol>
<li><strong>Start at the last line.</strong> <code>KeyError: 'qty'</code> is the exception type and message. &quot;Most recent call last&quot; means the newest call is at the <strong>bottom</strong>.</li>
<li><strong>Walk up</strong> to the lowest frame that is <strong>your</strong> code: line 10 of <code>orders.py</code>.</li>
<li>The <code>~~~^^^</code> markers (fine-grained error locations, Python 3.11+, PEP 657) point at the exact sub-expression: <code>item[&quot;qty&quot;]</code>.</li>
<li>Walk further up only to learn <strong>how</strong> you got there.</li>
</ol>
<p>Since Python 3.13, tracebacks are coloured in the terminal. <code>NO_COLOR=1</code> or <code>PYTHON_COLORS=0</code> turns that off before you paste output into a bug report.</p>
<p>A <strong>chained</strong> exception prints two tracebacks with a line between them. &quot;The above exception was the <strong>direct cause</strong> of the following exception&quot; comes from <code>raise NewError(...) from exc</code>: the <strong>first</strong> traceback is the root cause. &quot;<strong>During handling</strong> of the above exception, another exception occurred&quot; means a second error happened inside an <code>except</code> block, often a bug in the error handling itself.</p>
<h2 id="Java-stack-traces"><a href="#Java-stack-traces" class="headerlink" title="Java stack traces"></a>Java stack traces</h2>
<p>Java prints the <strong>newest call at the top</strong>, the opposite of Python. Wrapped exceptions follow as <code>Caused by:</code> blocks (shortened example):</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="text"><span class="line">Exception in thread &quot;main&quot; java.lang.IllegalStateException: Could not load settings</span><br><span class="line">        at app.Settings.load(Settings.java:41)</span><br><span class="line">        at app.Main.main(Main.java:12)</span><br><span class="line">Caused by: java.io.UncheckedIOException: settings.json unreadable</span><br><span class="line">        at app.Settings.readFile(Settings.java:58)</span><br><span class="line">        at app.Settings.load(Settings.java:38)</span><br><span class="line">        ... 1 more</span><br><span class="line">Caused by: java.nio.file.NoSuchFileException: /etc/app/settings.json</span><br><span class="line">        at java.base/sun.nio.fs.UnixException.translateToIOException(UnixException.java:92)</span><br><span class="line">        at app.Settings.readFile(Settings.java:55)</span><br><span class="line">        ... 2 more</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<li>The <strong>last</strong> <code>Caused by:</code> is usually the root cause: the file does not exist.</li>

</ul>

<h1 id="Chapter-3-—-Reproduce-then-shrink"><a href="#Chapter-3-—-Reproduce-then-shrink" class="headerlink" title="Chapter 3 — Reproduce, then shrink"></a>Chapter 3 — Reproduce, then shrink</h1>
<p>You cannot fix what you cannot trigger. First get a repro, then make it small.</p>
<p><strong>Minimal reproducible example.</strong> Copy the failing case into a new file or a failing test. Delete code, data and settings one piece at a time, checking after each delete that the bug is still there. Stop when every line is needed. You often find the bug while shrinking. If not, you now have a perfect thing to share.</p>
<p><strong>&quot;What changed?&quot;</strong> Most bugs in code that used to work come from a change:</p>
<table>
<thead>
<tr>
<th>Layer</th>
<th>Questions</th>
</tr>
</thead>
<tbody>
<tr>
<td>Code</td>
<td>Which commits went in since it last worked? (<code>git log --since=&quot;3 days ago&quot;</code>)</td>
</tr>
<tr>
<td>Dependencies</td>
<td>Did the lockfile change? A new major version? (see Dev Essentials 09 · Versions &amp; Dependencies)</td>
</tr>
<tr>
<td>Config</td>
<td>New env vars, feature flags, secrets, paths?</td>
</tr>
<tr>
<td>Data</td>
<td>New kinds of input? Empty values, huge files, non-ASCII text?</td>
</tr>
<tr>
<td>Environment</td>
<td>New OS, runtime, container image, time zone, locale?</td>
</tr>
<tr>
<td>Time and load</td>
<td>Only at month end? Only under many users? Only after midnight UTC?</td>
</tr>
</tbody>
</table>
<p><strong>Binary search on inputs and config.</strong> Bisection works on more than commits. If a 1,000-line file crashes the parser, test each half and keep the half that fails:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">shrink</span>(<span class="hljs-params">lines, fails</span>):</span><br><span class="line">    <span class="hljs-string">&quot;&quot;&quot;Halve the input until one small piece still fails.&quot;&quot;&quot;</span></span><br><span class="line">    <span class="hljs-keyword">assert</span> fails(lines), <span class="hljs-string">&quot;start from an input that fails&quot;</span></span><br><span class="line">    <span class="hljs-keyword">while</span> <span class="hljs-built_in">len</span>(lines) &gt; <span class="hljs-number">1</span>:</span><br><span class="line">        half = <span class="hljs-built_in">len</span>(lines) // <span class="hljs-number">2</span></span><br><span class="line">        left, right = lines[:half], lines[half:]</span><br><span class="line">        <span class="hljs-keyword">if</span> fails(left):</span><br><span class="line">            lines = left</span><br><span class="line">        <span class="hljs-keyword">elif</span> fails(right):</span><br><span class="line">            lines = right</span><br><span class="line">        <span class="hljs-keyword">else</span>:</span><br><span class="line">            <span class="hljs-keyword">break</span>          <span class="hljs-comment"># the bug needs lines from both halves</span></span><br><span class="line">    <span class="hljs-keyword">return</span> lines</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>With 1,000 lines this finds a single bad line in about 10 rounds. The same idea works for config: turn off half the plugins or settings, check, repeat. A smarter version is called <strong>delta debugging</strong> (see the Debugging Book in References).</p>

<h1 id="Chapter-4-—-Logging-instead-of-print"><a href="#Chapter-4-—-Logging-instead-of-print" class="headerlink" title="Chapter 4 — Logging instead of print"></a>Chapter 4 — Logging instead of print</h1>
<p><code>print</code> is fine for a two-minute check you delete right away. For anything that stays, use <code>logging</code>: it adds levels, timestamps and module names, and you turn detail on or off without editing code.</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> logging</span><br><span class="line"> </span><br><span class="line">logging.basicConfig(</span><br><span class="line">    level=logging.DEBUG,</span><br><span class="line">    <span class="hljs-built_in">format</span>=<span class="hljs-string">&quot;%(asctime)s %(levelname)-8s %(name)s: %(message)s&quot;</span>,</span><br><span class="line">)</span><br><span class="line">log = logging.getLogger(<span class="hljs-string">&quot;shop.orders&quot;</span>)</span><br><span class="line"> </span><br><span class="line">log.debug(<span class="hljs-string">&quot;loaded %d orders&quot;</span>, <span class="hljs-number">2</span>)</span><br><span class="line"><span class="hljs-keyword">try</span>:</span><br><span class="line">    {}[<span class="hljs-string">&quot;qty&quot;</span>]</span><br><span class="line"><span class="hljs-keyword">except</span> KeyError:</span><br><span class="line">    log.exception(<span class="hljs-string">&quot;order %s has no qty&quot;</span>, <span class="hljs-string">&quot;A-2&quot;</span>)   <span class="hljs-comment"># logs at ERROR and adds the traceback</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>Put <code>breakpoint()</code> in your code (Python 3.7+) and run the program. You get a <code>(Pdb)</code> prompt. <h2 id="py-spy-a-sampling-profiler"><a href="#py-spy-a-sampling-profiler" class="headerlink" title="py-spy: a sampling profiler"></a><code>py-spy</code>: a sampling profiler</h2>
<p><code>py-spy</code> samples a running Python process from the outside, many times per second. It does not change your code and adds little overhead, so it is safe to point at a live service.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">pip install py-spy</span><br><span class="line">py-spy record -o profile.svg -- python slow.py     <span class="hljs-comment"># flame graph of a new process</span></span><br><span class="line">py-spy top --pid 12345                             <span class="hljs-comment"># live &quot;top&quot; view of a running process</span></span><br><span class="line">py-spy dump --pid 12345                            <span class="hljs-comment"># current stack of every thread</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>py-spy dump</code> is the fastest way to see where a <strong>hung</strong> program is stuck. On Linux and macOS, attaching to an existing PID usually needs <code>sudo</code>. The README (checked September 2026, release 0.4.2) lists CPython 2.3–2.7 and 3.3–3.14 as supported. Python 3.15 (scheduled for 2026-10-01) adds a standard <code>profiling</code> package: <code>profiling.tracing</code> (the new home of <code>cProfile</code>, which stays as an alias) and <code>profiling.sampling</code> (PEP 799).</p>

<h1 id="Chapter-8-—-Heisenbugs-and-race-conditions"><a href="#Chapter-8-—-Heisenbugs-and-race-conditions" class="headerlink" title="Chapter 8 — Heisenbugs and race conditions"></a>Chapter 8 — Heisenbugs and race conditions</h1>
<p>A <strong>heisenbug</strong> changes when you observe it: a log line, a debugger or a debug build changes the timing, and the bug hides. The usual cause is a <strong>race condition</strong>, where the result depends on which thread runs first.</p>

<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="python"><span class="line">lock = threading.Lock()</span><br><span class="line"><span class="hljs-comment"># inside the loop:</span></span><br><span class="line"><span class="hljs-keyword">with</span> lock:</span><br><span class="line">    current = balance</span><br><span class="line">    time.sleep(<span class="hljs-number">0</span>)</span><br><span class="line">    balance = current + <span class="hljs-number">1</span>           <span class="hljs-comment"># now always 4000</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>How to hunt these bugs:</p>
<ul>
<li><strong>Make it happen more often:</strong> run the test in a loop (commands below), add threads, or add <code>time.sleep(0)</code> at suspect spots.</li>
<li><strong>Log with thread names and timestamps</strong> (<code>%(threadName)s</code>). Logging disturbs timing less than a debugger that pauses one thread.</li>
<li><strong>Look for shared mutable state:</strong> globals, class attributes, caches, files, database rows.</li>
<li><strong>Fix the design, not the timing:</strong> a lock, a queue, an atomic database update, or no sharing. A <code>sleep</code> that &quot;fixes&quot; it only makes the window smaller.</li>
<li><strong>For hangs</strong>, dump every thread's stack: <code>py-spy dump --pid &lt;PID&gt;</code>, or <code>faulthandler.dump_traceback_later(60)</code> in the program.</li>
</ul>

<h1 id="Chapter-10-—-Case-study-44-corrupted-posts"><a href="#Chapter-10-—-Case-study-44-corrupted-posts" class="headerlink" title="Chapter 10 — Case study: 44 corrupted posts"></a>Chapter 10 — Case study: 44 corrupted posts</h1>
<p>A real bug from this blog, told with the loop from Chapter 1. The encoding background is in Dev Essentials 01 · Text Encoding.</p>
<p><strong>Observe.</strong> Many posts showed two question marks where an em dash <code>—</code> should be, and the odd character 繚 (U+7E5A) where a middle dot <code>·</code> should be. In total 44 posts were damaged and about 2,700 characters destroyed. (This page writes that character as an HTML entity, so the blog's own marker check below does not flag this post.)</p>
<p><strong>Hypothesize.</strong> Such a regular pattern suggests one <strong>bulk rewrite</strong> with the wrong encoding, not 44 separate typos.</p>
<p><strong>Test.</strong> The strange character is a perfect marker. First, list every affected file:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="bash"><span class="line">grep -l $<span class="hljs-string">&#x27;\u7E5A&#x27;</span> content/posts/*.md</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="powershell"><span class="line"><span class="hljs-built_in">Select-String</span> <span class="hljs-literal">-Path</span> content\posts\*.md <span class="hljs-literal">-Pattern</span> ([<span class="hljs-built_in">string</span>][<span class="hljs-built_in">char</span>]<span class="hljs-number">0</span>x7E5A) <span class="hljs-literal">-Encoding</span> UTF8 <span class="hljs-literal">-List</span> |</span><br><span class="line">    <span class="hljs-built_in">Select-Object</span> <span class="hljs-literal">-ExpandProperty</span> Path</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Then ask Git which commit <strong>added</strong> the marker. One way is the &quot;pickaxe&quot;, <code>git log -S&lt;text&gt;</code>, which lists commits that change how many times a string appears:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git <span class="hljs-built_in">log</span> -S $<span class="hljs-string">&#x27;\u7E5A&#x27;</span> --oneline -- content/posts/</span><br><span class="line">git show --<span class="hljs-built_in">stat</span> &lt;sha&gt;        <span class="hljs-comment"># which files did that commit touch?</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> in Windows PowerShell 5.1, non-ASCII arguments to native programs can get mangled. Run the pickaxe search from Git Bash.</p>
</blockquote>
<p>The history pointed to one commit: a cover-image script had rewritten the posts with the system ANSI code page instead of UTF-8. The bytes confirm it: <code>·</code> in UTF-8 is <code>C2 B7</code>, and in code page 950 (the ANSI code page of Traditional Chinese Windows) those two bytes are the character 繚 (U+7E5A).</p>
<p><strong>Fix.</strong> The parent of the bad commit still has the good text:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git <span class="hljs-built_in">log</span> --oneline &lt;sha&gt;..HEAD -- content/posts/     <span class="hljs-comment"># did anything touch these files later?</span></span><br><span class="line">git restore --<span class="hljs-built_in">source</span>=&lt;sha&gt;^ -- content/posts/a.md content/posts/b.md</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If later commits edited the same files, re-apply those edits. If the bad commit also made wanted changes, redo them with a tool that writes UTF-8.</p>
<p><strong>Record and prevent.</strong> The marker search became a standing check after every bulk edit: it must return nothing. The project notes now warn that Windows PowerShell 5.1 <code>Set-Content</code> defaults to the ANSI code page, and show the UTF-8-safe way to write files.</p>
<p>What made this fast: a <strong>unique marker</strong>, a <strong>search over files</strong>, a <strong>search over history</strong>, and a <strong>known-good parent</strong> to restore from.</p>

<h2 id="Exercise-1-—-Read-a-traceback"><a href="#Exercise-1-—-Read-a-traceback" class="headerlink" title="Exercise 1 — Read a traceback"></a>Exercise 1 — Read a traceback</h2>
<p>For the <code>KeyError: 'qty'</code> traceback in Chapter 2: which line failed, what was the exception, and what is your first hypothesis? Then do the same for the Java trace: which file is missing, and which line of your code tried to read it?</p>
<details>
<summary>Solution</summary>
<p>Python: line 10 of <code>orders.py</code> raised <code>KeyError: 'qty'</code> at <code>item[&quot;qty&quot;]</code>. Hypothesis: one item has no <code>qty</code> key, maybe a different spelling. Test: break at line 10 with the condition <code>&quot;qty&quot; not in item</code>.</p>

<p>Git runs <code>check.py</code> six or seven times and names <code>build 27</code> as the first bad commit. Its first test lands in the middle, on a build that does not compile; <code>check.py</code> exits <code>125</code>, so bisect skips it and tries a neighbour.</p>
<p>Now change <code>sys.exit(125)</code> to <code>sys.exit(1)</code> and bisect again. The broken builds now count as <strong>bad</strong>, and bisect blames <code>build 19</code>, the first one that does not compile. That is the wrong answer to &quot;when did <code>with_tax</code> break?&quot;, and it is why exit code <code>125</code> exists.</p>

</details>
<h2 id="Exercise-4-—-Profile-and-fix"><a href="#Exercise-4-—-Profile-and-fix" class="headerlink" title="Exercise 4 — Profile and fix"></a>Exercise 4 — Profile and fix</h2>
<p>Profile <code>slow.py</code> from Chapter 7, fix the hot spot, and measure again.</p>
<details>
<summary>Solution</summary>
<p>The profile puts almost all the time in the <code>tottime</code> of <code>find_common</code> itself. The cost is <code>x in b</code>: <code>b</code> is a list, so each check scans up to 20,000 items. A <code>set</code> lookup takes about constant time:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">find_common</span>(<span class="hljs-params">a, b</span>):</span><br><span class="line">    b_set = <span class="hljs-built_in">set</span>(b)</span><br><span class="line">    <span class="hljs-keyword">return</span> [x <span class="hljs-keyword">for</span> x <span class="hljs-keyword">in</span> a <span class="hljs-keyword">if</span> x <span class="hljs-keyword">in</span> b_set]</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>On one test machine (anecdotal measurement) this went from about 2.5 s to about 3 ms, with the same 439 results.</p>
</details>
<h2 id="Exercise-5-—-Reproduce-a-race"><a href="#Exercise-5-—-Reproduce-a-race" class="headerlink" title="Exercise 5 — Reproduce a race"></a>Exercise 5 — Reproduce a race</h2>
<p>Turn the race from Chapter 8 into a pytest test that fails, then fix it. Why is <code>assert balance == 4000</code> a poor test <strong>before</strong> the fix?</p>
<details>
<summary>Solution</summary>
<p>Put the thread code in a function <code>run()</code> that returns <code>balance</code>, and write <code>def test_deposit(): assert run() == 4000</code>. Before the fix it fails most runs but may pass sometimes, so a green run proves nothing. Loop it (Chapter 8) to see the failure rate. After adding the lock it passes every time. Keep the loop test in your notes, not in CI: tests must be fast and deterministic (see Dev Essentials 15 · Testing).</p>
</details>
