11:T11f13,<p>Hooks look like ordinary function calls, which is exactly why they are misused. <code>useEffect</code> becomes a general &quot;when X changes, do Y&quot; tool, context becomes a global store, and every piece of data — server records, form drafts, the selected tab, the page number — ends up in the same <code>useState</code> soup with effects copying values between them. The result is extra renders, race conditions, and state that disagrees with itself. This post first explains hooks from the inside (the linked list on the fiber from Post 00), then works through effects done right, the less common hooks that solve real problems (<code>useLayoutEffect</code>, <code>useSyncExternalStore</code>, <code>useReducer</code>, <code>useEffectEvent</code>), and context performance. The second half steps up to architecture: sorting state by where its truth lives, and choosing between TanStack Query, Zustand and Redux Toolkit. Examples target <strong>React 19.2</strong>.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Explain the Rules of Hooks from the implementation: a per-fiber linked list read in call order.</li>
<li>Decide whether logic belongs in render, an event handler, or an effect, using &quot;You Might Not Need an Effect&quot;.</li>
<li>Write effects with correct cleanup, and without race conditions on fast-changing inputs.</li>
<li>Choose between <code>useEffect</code>, <code>useLayoutEffect</code> and <code>useInsertionEffect</code>.</li>
<li>Subscribe to external stores safely with <code>useSyncExternalStore</code>, including the snapshot-caching rule.</li>

<li>Diagnose and fix context re-render storms.</li>
<li>Classify state as server, client, URL or form state, and pick a tool for each.</li>
<li>Compare TanStack Query, Zustand and Redux Toolkit on the trade-offs that matter at scale.</li>

<h1 id="Chapter-1-—-How-hooks-are-stored-and-why-the-rules-exist"><a href="#Chapter-1-—-How-hooks-are-stored-and-why-the-rules-exist" class="headerlink" title="Chapter 1 — How hooks are stored, and why the rules exist"></a>Chapter 1 — How hooks are stored, and why the rules exist</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Hook</strong> — a function whose name starts with <code>use</code> and that reads or writes per-component data kept by React.</li>
<li><strong>Hook list</strong> — for a function component, <code>fiber.memoizedState</code> points at the first hook object; each hook object has a <code>next</code> pointer. React walks the list in call order.</li>
<li><strong>Dispatcher</strong> — the internal object that decides what <code>useState</code> means right now: the &quot;mount&quot; version creates hook objects, the &quot;update&quot; version walks existing ones.</li>
<li><strong>Reactive value</strong> — props, state, context, and anything computed from them during render. These can change between renders.</li>
</ul>
<h2 id="The-linked-list"><a href="#The-linked-list" class="headerlink" title="The linked list"></a>The linked list</h2>
<p>On mount, each hook call appends a node to the list. On update, each hook call takes the <strong>next</strong> node:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="text"><span class="line">fiber.memoizedState</span><br><span class="line">   │</span><br><span class="line">   ▼</span><br><span class="line">[useState: count] ──next──▶ [useEffect: subscribe] ──next──▶ [useMemo: filtered] ──▶ null</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>React has no names for these nodes. The only thing that connects &quot;the second hook call in this render&quot; to &quot;the effect from last render&quot; is <strong>position</strong>. That is the whole reason for the two rules:</p>
<ol>
<li><strong>Call hooks only at the top level</strong> — not in conditions, loops, after an early <code>return</code>, or in nested functions.</li>
<li><strong>Call hooks only from components or other hooks.</strong></li>
</ol>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">Profile</span>(<span class="hljs-params">{ userId }</span>) {</span><br><span class="line">  <span class="hljs-keyword">if</span> (!userId) <span class="hljs-keyword">return</span> <span class="hljs-literal">null</span>;          <span class="hljs-comment">// early return BEFORE a hook</span></span><br><span class="line">  <span class="hljs-keyword">const</span> [tab, setTab] = <span class="hljs-title function_">useState</span>(<span class="hljs-string">&quot;posts&quot;</span>); <span class="hljs-comment">// breaks: hook count differs between renders</span></span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>When <code>userId</code> goes from <code>null</code> to a value, render 1 made zero hook calls and render 2 makes one; React throws &quot;Rendered more hooks than during the previous render&quot;. Worse cases do not throw: if two <code>useState</code> calls swap order, each reads the other's value silently.</p>
<p><code>use()</code> from React 19 is the documented exception: it can be called inside <code>if</code> and loops, because it does not store a hook node (Post 02).</p>
<blockquote>
<p><strong>Trick:</strong> custom hooks are not a runtime concept. A custom hook's hooks are inlined into the caller's list. Two components calling <code>useWindowWidth()</code> get two independent sets of state; nothing is shared unless the hook reads a shared store.</p>
</blockquote>

<h2 id="What-an-effect-is-for"><a href="#What-an-effect-is-for" class="headerlink" title="What an effect is for"></a>What an effect is for</h2>
<p>An effect <strong>synchronises a component with an external system</strong>: a network connection, a browser API, a third-party widget, a subscription. It is not a general &quot;on change&quot; callback. The React docs article &quot;You Might Not Need an Effect&quot; gives a decision rule worth memorising:</p>

<h2 id="Cleanup-is-part-of-the-contract"><a href="#Cleanup-is-part-of-the-contract" class="headerlink" title="Cleanup is part of the contract"></a>Cleanup is part of the contract</h2>
<p>Every setup needs a matching cleanup (<code>setInterval</code> → <code>clearInterval</code>, <code>subscribe</code> → <code>unsubscribe</code>, <code>connect</code> → <code>disconnect</code>) so that setup → cleanup → setup is equivalent to one setup. StrictMode tests exactly this in development (Post 00). React runs the cleanup before the next setup (when dependencies change) and on unmount. Cleanup reads the values from <strong>its own</strong> render — the closure it was created in — not the latest ones.</p>
<h2 id="Race-conditions-in-data-effects"><a href="#Race-conditions-in-data-effects" class="headerlink" title="Race conditions in data effects"></a>Race conditions in data effects</h2>
<p>A naive <code>useEffect(() =&gt; { fetch(url(query)).then(r =&gt; r.json()).then(setData); }, [query])</code> has a race. Type &quot;re&quot;, then &quot;react&quot;. If the &quot;re&quot; request is slower, its response arrives last and overwrites the correct result. Two fixes, often combined:</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-title function_">useEffect</span>(<span class="hljs-function">() =&gt;</span> {</span><br><span class="line">  <span class="hljs-keyword">const</span> controller = <span class="hljs-keyword">new</span> <span class="hljs-title class_">AbortController</span>();</span><br><span class="line">  <span class="hljs-keyword">let</span> ignore = <span class="hljs-literal">false</span>;</span><br><span class="line"> </span><br><span class="line">  <span class="hljs-title function_">fetch</span>(<span class="hljs-string">`/api/search?q=<span class="hljs-subst">${<span class="hljs-built_in">encodeURIComponent</span>(query)}</span>`</span>, { <span class="hljs-attr">signal</span>: controller.<span class="hljs-property">signal</span> })</span><br><span class="line">    .<span class="hljs-title function_">then</span>(<span class="hljs-function"><span class="hljs-params">r</span> =&gt;</span> r.<span class="hljs-title function_">json</span>())</span><br><span class="line">    .<span class="hljs-title function_">then</span>(<span class="hljs-function"><span class="hljs-params">json</span> =&gt;</span> { <span class="hljs-keyword">if</span> (!ignore) <span class="hljs-title function_">setData</span>(json); <h2 id="Dependencies-are-not-a-choice"><a href="#Dependencies-are-not-a-choice" class="headerlink" title="Dependencies are not a choice"></a>Dependencies are not a choice</h2>
<p>The dependency array must list every reactive value the effect reads. It is a description of what the effect uses, not a setting for &quot;when it runs&quot;. If an effect re-runs too often, change the code so it reads fewer reactive values:</p>
<ul>
<li>Move objects and functions that do not depend on props <strong>inside</strong> the effect or <strong>outside</strong> the component.</li>
<li>Use the updater form <code>setCount(c =&gt; c + 1)</code> so the effect does not read <code>count</code>.</li>
<li>Split an effect that does two unrelated things into two effects.</li>
<li>Move non-reactive logic into an Effect Event (Chapter 4).</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> <code>// eslint-disable-next-line react-hooks/exhaustive-deps</code> is almost always a stale-closure bug waiting to happen. The code will read a value from the render the effect was created in, forever.</p>
</blockquote>

<h2 id="useSyncExternalStore"><a href="#useSyncExternalStore" class="headerlink" title="useSyncExternalStore"></a><code>useSyncExternalStore</code></h2>

A paused render can show part of the tree with the old store value and part with the new one. <code>useSyncExternalStore</code> is the supported fix:</p>

<ol>
<li><strong><code>getSnapshot</code> must return the same value while the store has not changed.</strong> React compares with <code>Object.is</code>. <h2 id="Context-performance"><a href="#Context-performance" class="headerlink" title="Context performance"></a>Context performance</h2>
<p>Context is a way to pass a value down without props. It is not a state manager, and it has no selectors: every consumer of a context renders when the value changes (<code>Object.is</code>), and <code>memo</code> does not stop it.</p>
<p>Three fixes, from cheapest to strongest:</p>

<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-comment">// 2. <ol start="3">
<li><strong>Use a store with selectors</strong> when many components each need a small slice of a fast-changing value (a document, a canvas, a live dashboard). Put the store object in context (it never changes) and read slices with <code>useSyncExternalStore</code>-based selectors — which is what Zustand and React-Redux do.</li>
</ol>
<blockquote>
<p><strong>Trick:</strong> context is excellent for values that change rarely: theme, locale, the current user, a store instance, a feature-flag client. It is poor for values that change on every keystroke.</p>
</blockquote>

<h1 id="Chapter-5-—-Classifying-state"><a href="#Chapter-5-—-Classifying-state" class="headerlink" title="Chapter 5 — Classifying state"></a>Chapter 5 — Classifying state</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Server state</strong> — a cached copy of data whose truth lives on a server: users, orders, search results. It can go stale, can be changed by other people, and needs fetching, caching, invalidation and retries.</li>
<li><strong>Client (UI) state</strong> — data that exists only in this browser tab: an open modal, a selected row, a draft, a multi-step wizard position.</li>
<li><strong>URL state</strong> — state that should survive reload, back/forward, and sharing a link: filters, sort, page, selected tab, search query.</li>
<li><strong>Form state</strong> — in-progress user input, its validation and submission status.</li>
<li><strong>Derived state</strong> — anything computable from the above. It should not be stored at all.</li>
</ul>
<h2 id="Why-the-classification-matters"><a href="#Why-the-classification-matters" class="headerlink" title="Why the classification matters"></a>Why the classification matters</h2>
<p>Most &quot;state management&quot; pain comes from putting server state into a client store. Many older Redux codebases held <code>users</code>, <code>usersLoading</code>, <code>usersError</code> and hand-written thunks for every entity, reinventing a cache without invalidation. Once server state moves to a query cache, the remaining client state is usually small enough that <code>useState</code>, <code>useReducer</code> and a little context cover most of it.</p>
<p>A practical sort for each piece of state:</p>
<ol>
<li><strong>Can it be computed from other state?</strong> Compute it. Do not store it.</li>
<li><strong>Is the truth on a server?</strong> Query cache.</li>
<li><strong>Should a copied link or the back button restore it?</strong> URL.</li>
<li><strong>Is it user input before submit?</strong> Form state (uncontrolled inputs, a form library, or React 19 <code>useActionState</code> — Post 02).</li>
<li><strong>Is it used by one component or a small subtree?</strong> <code>useState</code> / <code>useReducer</code>, placed as low as possible.</li>
<li><strong>Is it shared across distant parts and changes often?</strong> A client store.</li>
</ol>
<p>Ask the questions in order; the first yes decides.</p>
<p><img src="/blog/assets/react/diagram_01_state_kinds.svg" alt="Six questions asked in order sort each piece of state: derived state is computed during render and never stored, server state goes to a query cache such as TanStack Query or framework loaders, URL state to router search params, form state to uncontrolled inputs, a form library or useActionState, client state to useState or useReducer placed low, and shared client state to Zustand or Redux Toolkit."></p>
<h2 id="URL-state-in-practice"><a href="#URL-state-in-practice" class="headerlink" title="URL state in practice"></a>URL state in practice</h2>

</blockquote>

<p>Status fields: <code>isPending</code> means &quot;no data yet&quot; (v5 renamed the old <code>isLoading</code>), <code>isFetching</code> means &quot;a request is in flight&quot;, which is also true during background refetches. <p>Key design points at scale:</p>
<ul>
<li><strong>Query key factories</strong> keep keys consistent: <code>todoKeys.detail(id)</code> returns <code>[&quot;todos&quot;, &quot;detail&quot;, id]</code>, so <code>invalidateQueries({ queryKey: [&quot;todos&quot;] })</code> hits every todo query by prefix.</li>
<li>Set a realistic <strong><code>staleTime</code></strong> per resource. <code>0</code> is safe but chatty; reference data can be minutes or <code>Infinity</code>.</li>
<li><code>useSuspenseQuery</code> integrates with Suspense (Post 02) and guarantees <code>data</code> is defined.</li>
<li>In a framework with server rendering, prefetch on the server and hydrate the cache, or let the framework's own loaders own server state (Next.js Deep Dive).</li>
</ul>

</blockquote>

<p>Rules of thumb:</p>
<ul>
<li>Start with <strong>TanStack Query for server state and local state for the rest</strong>. Many apps never need a client store after that.</li>
<li>Reach for <strong>Zustand</strong> when a few pieces of client state are shared widely and change often.</li>
<li>Choose <strong>Redux Toolkit</strong> when the team is large, needs strong conventions, action logging or time-travel debugging, or already runs Redux.</li>
<li>Keep derived data out of every store; compute it with selectors (memoised with <code>createSelector</code> when expensive).</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> a selector like <code>state =&gt; state.items.filter(i =&gt; i.done)</code> returns a new array every time, so the component renders on every store change. Select the raw data and derive it in the component with <code>useMemo</code>, or use a memoised selector.</p>
</blockquote>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Hook-order"><a href="#Exercise-1-—-Hook-order" class="headerlink" title="Exercise 1 — Hook order"></a>Exercise 1 — Hook order</h2>
<p>Why does this crash when <code>user</code> changes from <code>null</code> to an object? Fix it.</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">Greeting</span>(<span class="hljs-params">{ user }</span>) {</span><br><span class="line">  <span class="hljs-keyword">if</span> (!user) <span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">p</span>&gt;</span>Please sign in<span class="hljs-tag">&lt;/<span class="hljs-name">p</span>&gt;</span></span>;</span><br><span class="line">  <span class="hljs-keyword">const</span> [wave, setWave] = <span class="hljs-title function_">useState</span>(<span class="hljs-literal">false</span>);</span><br><span class="line">  <span class="hljs-keyword">return</span> <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">p</span> <span class="hljs-attr">onClick</span>=<span class="hljs-string">{()</span> =&gt;</span> setWave(true)}&gt;Hi {user.name}{wave &amp;&amp; &quot;!&quot;}<span class="hljs-tag">&lt;/<span class="hljs-name">p</span>&gt;</span></span>;</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p>The first render calls zero hooks, the next calls one; React reads the hook list by position and detects the mismatch. Move the hook above the early return (or split into two components: <code>Greeting</code> returns <code>&lt;SignedInGreeting user={user} /&gt;</code>).</p>
</details>
<h2 id="Exercise-2-—-The-frozen-counter"><a href="#Exercise-2-—-The-frozen-counter" class="headerlink" title="Exercise 2 — The frozen counter"></a>Exercise 2 — The frozen counter</h2>
<p>The display sticks at 1. Why? Fix it without adding <code>count</code> to the dependencies.</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="jsx"><span class="line"><span class="hljs-keyword">const</span> [count, setCount] = <span class="hljs-title function_">useState</span>(<span class="hljs-number">0</span>);</span><br><span class="line"><span class="hljs-title function_">useEffect</span>(<span class="hljs-function">() =&gt;</span> {</span><br><span class="line">  <span class="hljs-keyword">const</span> id = <span class="hljs-built_in">setInterval</span>(<span class="hljs-function">() =&gt;</span> <span class="hljs-title function_">setCount</span>(count + <span class="hljs-number">1</span>), <span class="hljs-number">1000</span>);</span><br><span class="line">  <span class="hljs-keyword">return</span> <span class="hljs-function">() =&gt;</span> <span class="hljs-built_in">clearInterval</span>(id);</span><br><span class="line">}, []);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p>The interval callback closed over <code>count</code> from the first render, which is always 0, so it sets 1 forever. Use the updater form, <code>setCount(c =&gt; c + 1)</code>: the effect no longer reads <code>count</code>, the empty dependency list is now honest, and the interval never restarts.</p>
</details>
<h2 id="Exercise-3-—-Snapshot-caching"><a href="#Exercise-3-—-Snapshot-caching" class="headerlink" title="Exercise 3 — Snapshot caching"></a>Exercise 3 — Snapshot caching</h2>
<p>This hook causes &quot;Maximum update depth exceeded&quot;. Why, and how do you fix it?</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> pos = <span class="hljs-title function_">useSyncExternalStore</span>(store.<span class="hljs-property">subscribe</span>, <span class="hljs-function">() =&gt;</span> ({ <span class="hljs-attr">x</span>: store.<span class="hljs-property">x</span>, <span class="hljs-attr">y</span>: store.<span class="hljs-property">y</span> }));</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p><code>getSnapshot</code> returns a new object on every call, so <code>Object.is</code> says the store changed every time React checks, and React re-renders forever. Keep an immutable snapshot object in the store and replace it only on change (<code>store.snapshot = { x, y }</code> inside the setter), then <code>() =&gt; store.snapshot</code>. Or read two primitives with two separate subscriptions.</p>
</details>
<h2 id="Exercise-4-—-Context-storm"><a href="#Exercise-4-—-Context-storm" class="headerlink" title="Exercise 4 — Context storm"></a>Exercise 4 — Context storm</h2>
<p>A <code>SettingsContext</code> value is <code>{ settings, updateSetting }</code>, rebuilt on each render of the provider. A slider updates a setting 60 times a second, and 400 consumers re-render. Give two fixes.</p>
<details>
<summary>Solution</summary>
<p>(1) Split: put <code>updateSetting</code> (stable, via <code>useCallback</code> or <code>useReducer</code>'s <code>dispatch</code>) in its own context, so action-only consumers never render; and memoise the settings value. (2) Move settings into a store (Zustand, or a small <code>useSyncExternalStore</code> store in context) and have each consumer select only the field it shows; only consumers of the changed field render.</p>
</details>
<h2 id="Exercise-5-—-Classify"><a href="#Exercise-5-—-Classify" class="headerlink" title="Exercise 5 — Classify"></a>Exercise 5 — Classify</h2>
<p>Classify each and name where it should live: the logged-in user's profile; the &quot;sort by&quot; dropdown on a product list; whether the sidebar is collapsed; an unsent comment draft; the number of items in the cart shown in the header; the total price of the cart.</p>
<details>
<summary>Solution</summary>
<p>Profile — server state (query cache). Sort — URL state (search params), so links and back button work. Sidebar collapsed — client state (<code>useState</code> near the layout, or <code>localStorage</code> if it should persist). Comment draft — form state (uncontrolled input or form state; optionally persisted). Cart items — server state if the cart is stored on the server, otherwise shared client state (a store). Total price — derived: compute from cart items; never store it.</p>
</details>
