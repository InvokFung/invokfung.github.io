<h1 id="Chapter-1-—-The-mental-model"><a href="#Chapter-1-—-The-mental-model" class="headerlink" title="Chapter 1 — The mental model"></a>Chapter 1 — The mental model</h1>
<p>Four ideas explain almost every rescue.</p>
<ol>
<li><strong>A commit is a snapshot.</strong> It stores the full state of the tracked files, a message, an author, and the ID of its parent commit(s). The ID is a hash of all of that, so a commit can never change. &quot;Changing&quot; a commit always means making a new one.</li>
<li><strong>A branch is a movable pointer.</strong> <code>main</code> is only a name that holds one commit ID. When you commit, Git moves that pointer forward. Deleting a branch deletes the name, not the commits.</li>
<li><strong><code>HEAD</code> means &quot;where you are&quot;.</strong> Normally <code>HEAD</code> points to a branch, and the branch points to a commit. If <code>HEAD</code> points straight at a commit, you are in <em>detached HEAD</em> (Chapter 6).</li>
<li><strong>The index is the next commit, in draft.</strong> <code>git add</code> copies a file version into the index (also called the staging area). <code>git commit</code> turns the index into a snapshot.</li>
</ol>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="text"><span class="line">C1 ◄── C2 ◄── C3 ◄── C4   ◄── main ◄── HEAD</span><br><span class="line">               ▲</span><br><span class="line">               └──── C5   ◄── feature</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Each commit points back to its parent, and each branch points at one commit. The key word is <strong>reachable</strong>. A commit is reachable if you can walk to it from a branch, a tag, or another ref. Git's garbage collector only deletes objects that are unreachable <em>and</em> old. The reflog (Chapter 3) keeps recently left commits reachable for weeks. That is why most mistakes can be undone.</p>

<h1 id="Chapter-3-—-First-aid-with-git-reflog"><a href="#Chapter-3-—-First-aid-with-git-reflog" class="headerlink" title="Chapter 3 — First aid with git reflog"></a>Chapter 3 — First aid with <code>git reflog</code></h1>
<p>Every time <code>HEAD</code> or a branch moves — commit, reset, rebase, checkout, merge, pull — Git adds a line to that ref's <strong>reflog</strong>. The reflog is local to your clone and is never pushed. By default, entries are kept for 90 days, and entries for commits that are no longer reachable are kept for 30 days (<code>gc.reflogExpire</code> and <code>gc.reflogExpireUnreachable</code>).</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git reflog              <span class="hljs-comment"># same as: git reflog show HEAD</span></span><br><span class="line">git reflog show main    <span class="hljs-comment"># the reflog of one branch</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Sample output (your hashes will differ):</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="text"><span class="line">3f2c1a9 (HEAD -&gt; main) HEAD@{0}: reset: moving to HEAD~2</span><br><span class="line">8d7e6f5 HEAD@{1}: commit: Add line 4</span><br><span class="line">b4c3d2e HEAD@{2}: commit: Add line 3</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>HEAD@{1}</code> means &quot;where <code>HEAD</code> was one move ago&quot;. Other forms work too: <code>main@{2.hours.ago}</code>, and <code>@{-1}</code> for &quot;the branch I was on before&quot;.</p>
<h2 id="Recipe-31-—-Undo-a-bad-reset-hard"><a href="#Recipe-31-—-Undo-a-bad-reset-hard" class="headerlink" title="Recipe 3.1 — Undo a bad reset --hard"></a>Recipe 3.1 — Undo a bad <code>reset --hard</code></h2>
<p><strong>Symptom.</strong> You ran <code>git reset --hard HEAD~2</code>, and two commits disappeared from <code>git log</code>.</p>
<p><strong>Command.</strong></p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git reflog -5</span><br><span class="line">git reset --hard <span class="hljs-string">&#x27;HEAD@{1}&#x27;</span>     <span class="hljs-comment"># or the hash from the reflog line you want</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Why it works.</strong> <code>reset</code> only moved the <code>main</code> pointer. The two commits still exist. The reflog remembers the old position, and a second <code>reset --hard</code> moves the pointer back.</p>
<blockquote>
<p><strong>Watch out:</strong> the reflog stores <em>commits</em>, not loose edits. Changes that were never committed and never staged are gone after <code>reset --hard</code>. If you had run <code>git add</code> on them, their contents may still exist as dangling blobs — see Chapter 9.</p>
</blockquote>
<h2 id="Recipe-32-—-Undo-a-rebase"><a href="#Recipe-32-—-Undo-a-rebase" class="headerlink" title="Recipe 3.2 — Undo a rebase"></a>Recipe 3.2 — Undo a rebase</h2>
<p><strong>Symptom.</strong> A rebase finished, but the result is wrong: lost changes or a bad conflict fix.</p>
<p><strong>Command.</strong></p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git reflog show feature            <span class="hljs-comment"># the branch&#x27;s own reflog</span></span><br><span class="line">git reset --hard <span class="hljs-string">&#x27;feature@{1}&#x27;</span>     <span class="hljs-comment"># the branch tip before the rebase</span></span><br><span class="line">git reset --hard ORIG_HEAD         <span class="hljs-comment"># also works, but only directly after the rebase</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Why it works.</strong> A rebase writes <em>new</em> commits, then moves the branch pointer once, at the end. The old commits are untouched, and the branch's previous reflog entry is the old tip — Git's rebase docs point to exactly this <code>@{1}</code> entry. <code>ORIG_HEAD</code> is set when the rebase starts, but commands such as <code>reset</code> overwrite it, so trust the reflog first. If the rebase is still running, simply stop it: <code>git rebase --abort</code>.</p>
<h2 id="Recipe-33-—-Get-a-deleted-branch-back"><a href="#Recipe-33-—-Get-a-deleted-branch-back" class="headerlink" title="Recipe 3.3 — Get a deleted branch back"></a>Recipe 3.3 — Get a deleted branch back</h2>
<p><strong>Symptom.</strong> You ran <code>git branch -D feature</code>, then realized it held unmerged work.</p>
<p><strong>Command.</strong> Git printed the old tip when it deleted the branch — <code>Deleted branch feature (was 5e6f7a8).</code> — so:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git branch feature 5e6f7a8</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If that line has scrolled away, search the <code>HEAD</code> reflog:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git reflog | grep <span class="hljs-string">&quot;feature&quot;</span>               <span class="hljs-comment"># Git Bash</span></span><br><span class="line">git reflog | Select-String <span class="hljs-string">&quot;feature&quot;</span>      <span class="hljs-comment"># PowerShell</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Look for a line like <code>checkout: moving from feature to main</code>. The entry just <em>below</em> it (one step older) is the last commit you had on <code>feature</code>. A commit message you remember works as a search term too.</p>
<p><strong>Why it works.</strong> Deleting a branch also deletes that branch's own reflog. But the <code>HEAD</code> reflog still lists every commit you checked out or created.</p>
<blockquote>
<p><strong>Common pitfall:</strong> <code>git branch -d</code> (lowercase) refuses to delete unmerged work with <code>error: the branch 'feature' is not fully merged</code>. That error is a safety net. Use <code>-D</code> only when you are sure.</p>
</blockquote>

<h2 id="Revert-for-shared-history"><a href="#Revert-for-shared-history" class="headerlink" title="Revert for shared history"></a>Revert for shared history</h2>
<p><strong>Symptom.</strong> A commit that is already on the shared <code>main</code> broke something. <strong>Command:</strong></p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git revert --no-edit 8d7e6f5    <span class="hljs-comment"># new commit that undoes 8d7e6f5, default message</span></span><br><span class="line">git revert -m 1 &lt;merge-sha&gt;     <span class="hljs-comment"># revert a merge; keep parent 1&#x27;s side</span></span><br><span class="line">git push</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Why it works.</strong> <code>revert</code> adds a <em>new</em> commit that applies the opposite change. History only grows, so nobody else has to repair their clone.</p>
<blockquote>
<p><strong>Common pitfall:</strong> running <code>reset --hard</code> on a pushed branch and then force-pushing. Everyone who already pulled now holds commits that &quot;no longer exist&quot;. Rewrite only what nobody else has.</p>
</blockquote>

<h1 id="Chapter-5-—-Stash-without-surprises"><a href="#Chapter-5-—-Stash-without-surprises" class="headerlink" title="Chapter 5 — Stash without surprises"></a>Chapter 5 — Stash without surprises</h1>
<p><code>git stash</code> saves your uncommitted changes and cleans the working tree. Under the hood, each stash entry is a special commit. The newest one is <code>refs/stash</code>; older ones live in that ref's reflog as <code>stash@{1}</code>, <code>stash@{2}</code>, and so on.</p>
<p><strong>The problem.</strong> There is <strong>one stash stack per repository</strong>. Git's worktree docs state that refs under <code>refs/</code> are shared by all worktrees, and <code>refs/stash</code> is one of them. If two terminals, two tools, an editor extension and an AI agent all work in one repository, they all push to and pop from the same stack. <code>stash@{0}</code> means &quot;whoever stashed last&quot; — maybe not you. A bare <code>git stash pop</code> can apply someone else's changes <em>and remove them from the list</em>.</p>
<h2 id="The-safe-pattern"><a href="#The-safe-pattern" class="headerlink" title="The safe pattern"></a>The safe pattern</h2>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># 1. Stash with a unique tag. -u also saves untracked files.</span></span><br><span class="line">git stash push -u -m <span class="hljs-string">&quot;wip-login-form-0925&quot;</span></span><br><span class="line"><span class="hljs-comment"># 2. Capture the entry&#x27;s full SHA right away.</span></span><br><span class="line">git stash list --format=<span class="hljs-string">&#x27;%H %gd %gs&#x27;</span></span><br><span class="line"><span class="hljs-comment">#    9c1e0b7...  stash@{0}  On main: wip-login-form-0925</span></span><br><span class="line"><span class="hljs-comment"># 3. Later: apply by SHA, not by position.</span></span><br><span class="line">git stash apply 9c1e0b7</span><br><span class="line"><span class="hljs-comment"># 4. When your changes are safely back, find the entry again by tag, then drop it.</span></span><br><span class="line">git stash list --format=<span class="hljs-string">&#x27;%gd %gs&#x27;</span> | grep <span class="hljs-string">&quot;wip-login-form-0925&quot;</span>            <span class="hljs-comment"># Git Bash</span></span><br><span class="line">git stash list --format=<span class="hljs-string">&#x27;%gd %gs&#x27;</span> | Select-String <span class="hljs-string">&quot;wip-login-form-0925&quot;</span>   <span class="hljs-comment"># PowerShell</span></span><br><span class="line">git stash drop <span class="hljs-string">&#x27;stash@{2}&#x27;</span>      <span class="hljs-comment"># the position the tag has *now*</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Why each step matters:</p>
<ul>
<li><strong><code>-u</code></strong> (<code>--include-untracked</code>): without it, new files are not saved and stay in the working tree.</li>
<li><strong><code>-m</code></strong>: Git stores the message as <code>On &lt;branch&gt;: &lt;message&gt;</code>, so you can find it later.</li>
<li><strong><code>apply &lt;sha&gt;</code></strong>: <code>apply</code> accepts any stash-like commit, so a SHA always means <em>your</em> entry, even if others stashed on top.</li>
<li><strong>Drop by position, found fresh</strong>: <code>drop</code> does not accept a raw SHA (<code>'&lt;sha&gt;' is not a stash reference</code>). It needs <code>stash@{n}</code>, so look up the current position by tag just before you drop. (Dropped the wrong one? See Chapter 9.)</li>
<li><strong><code>apply</code>, not <code>pop</code></strong>: <code>pop</code> removes the entry as soon as it applies. <code>apply</code> leaves it until you have checked the result.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> if <code>pop</code> or <code>apply</code> hits a conflict, the entry stays in the list. Fix the conflict, then drop the entry yourself.</p>
</blockquote>
<blockquote>
<p><strong>Trick:</strong> for a short break, skip the stash. Make a work-in-progress commit (<code>git add -A</code>, then <code>git commit -m &quot;WIP&quot;</code>) and later undo it with <code>git reset HEAD~1</code>, which keeps the changes. A commit lives on <em>your</em> branch, so no other session can take it.</p>
</blockquote>

<h1 id="Chapter-6-—-Detached-HEAD"><a href="#Chapter-6-—-Detached-HEAD" class="headerlink" title="Chapter 6 — Detached HEAD"></a>Chapter 6 — Detached HEAD</h1>
<p><strong>What it is.</strong> <code>HEAD</code> points straight at a commit instead of a branch. You get there with <code>git checkout &lt;sha&gt;</code>, <code>git switch --detach &lt;sha&gt;</code>, by checking out a tag, or during a rebase or bisect. Git tells you with the line <code>You are in 'detached HEAD' state.</code> and a hint to use <code>git switch -c</code>.</p>
<p>Looking around is harmless. Committing is allowed too — but no branch points to those new commits. When you switch away, they become unreachable, and garbage collection may delete them later.</p>
<p><strong>Symptom.</strong> &quot;I committed, switched branches, and my commit is gone.&quot; Git even warned you: <code>Warning: you are leaving 1 commit behind, not connected to any of your branches</code>, followed by a <code>git branch &lt;new-branch-name&gt; &lt;sha&gt;</code> hint.</p>
<p><strong>Command.</strong></p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git switch -c experiment        <span class="hljs-comment"># still detached: new branch here, HEAD attaches to it</span></span><br><span class="line">git reflog -10                  <span class="hljs-comment"># already switched away: find the commit...</span></span><br><span class="line">git branch experiment 7a8b9c0   <span class="hljs-comment"># ...and give it a name</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Why it works.</strong> A commit is safe as soon as a ref points to it. Creating a branch or a tag creates that ref. <code>git switch -</code> takes you back to the branch you were on before.</p>

<h1 id="Chapter-7-—-Moving-and-cleaning-commits"><a href="#Chapter-7-—-Moving-and-cleaning-commits" class="headerlink" title="Chapter 7 — Moving and cleaning commits"></a>Chapter 7 — Moving and cleaning commits</h1>
<h2 id="Cherry-pick-copy-one-commit"><a href="#Cherry-pick-copy-one-commit" class="headerlink" title="Cherry-pick: copy one commit"></a>Cherry-pick: copy one commit</h2>
<p><strong>Symptom.</strong> A fix landed on the wrong branch, or a release branch needs one fix from <code>main</code>.</p>
<p><strong>Command.</strong></p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git switch release-1.2</span><br><span class="line">git cherry-pick -x 4d5e6f7      <span class="hljs-comment"># -x adds &quot;(cherry picked from commit ...)&quot; to the message</span></span><br><span class="line"><span class="hljs-comment"># on conflict: fix the files, git add them, then</span></span><br><span class="line">git cherry-pick --<span class="hljs-built_in">continue</span>      <span class="hljs-comment"># or give up: git cherry-pick --abort</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Why it works.</strong> Cherry-pick takes the <em>change</em> that a commit introduced and applies it as a new commit on the current branch, with a new SHA. To <em>move</em> a commit you made on the wrong branch (and never pushed), cherry-pick it onto the right branch, then run <code>git reset --hard HEAD~1</code> on the wrong one.</p>
<h2 id="Fixup-commits-autosquash-tidy-history-before-review"><a href="#Fixup-commits-autosquash-tidy-history-before-review" class="headerlink" title="Fixup commits + autosquash: tidy history before review"></a>Fixup commits + autosquash: tidy history before review</h2>
<p><strong>Symptom.</strong> Review found a typo in a commit three steps back. You want the fix <em>inside</em> that commit, not as &quot;fix typo&quot; on top.</p>
<p><strong>Command.</strong></p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git commit -a --fixup=b4c3d2e            <span class="hljs-comment"># message: &quot;fixup! &lt;title of b4c3d2e&gt;&quot;</span></span><br><span class="line">git rebase -i --autosquash b4c3d2e~1     <span class="hljs-comment"># editor opens with the list pre-sorted; save and close</span></span><br><span class="line">git rebase --autosquash b4c3d2e~1        <span class="hljs-comment"># Git 2.44+: same result, no editor</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Why it works.</strong> The <code>fixup!</code> prefix tells rebase which commit the fix belongs to. Rebase moves the fixup right after its target and changes its action from <code>pick</code> to <code>fixup</code>, which merges the change and keeps the target's message. Variants: <code>--fixup=amend:&lt;sha&gt;</code> also replaces the message; <code>--fixup=reword:&lt;sha&gt;</code> changes only the message.</p>
<blockquote>
<p><strong>Watch out:</strong> <code>git rebase -i</code> opens an editor and waits for you. Scripts, CI jobs and AI coding agents have no one to close that editor, so they hang or fail. Use the non-interactive form (Git 2.44+), and set an editor you know for yourself: <code>git config --global core.editor &quot;code --wait&quot;</code>. Remember that rewriting gives commits new SHAs — do it only on commits nobody else has, or push with care (next chapter).</p>
</blockquote>
<hr>
<h1 id="Chapter-8-—-Force-push-without-wiping-others-work"><a href="#Chapter-8-—-Force-push-without-wiping-others-work" class="headerlink" title="Chapter 8 — Force-push without wiping others' work"></a>Chapter 8 — Force-push without wiping others' work</h1>
<p>After a rebase or <code>--amend</code>, your local branch and the remote branch have split apart, and a normal push is rejected. <code>--force</code> overwrites the remote branch no matter what is there — including commits a teammate pushed five minutes ago.</p>
<p><code>--force-with-lease</code> adds a check: &quot;overwrite only if the remote branch is still where my remote-tracking ref (<code>origin/feature</code>) says it is&quot;. If someone pushed in between, the push is rejected with <code>stale info</code>, and you fetch and look before deciding.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git push --force-with-lease                                  <span class="hljs-comment"># protect every ref being pushed</span></span><br><span class="line">git push --force-with-lease=feature:5e6f7a8 origin feature   <span class="hljs-comment"># remote feature must be exactly 5e6f7a8</span></span><br><span class="line">git push --force-with-lease --force-if-includes              <span class="hljs-comment"># Git 2.30+; safe with background fetch</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>The catch.</strong> The lease compares against your remote-tracking ref. Many editors run <code>git fetch</code> in the background. A background fetch moves <code>origin/feature</code> to include the teammate's commit <em>without you ever looking at it</em> — and then the lease passes. Git's push docs warn about exactly this. <code>--force-if-includes</code> closes the gap: it also checks that the remote tip appears in your local branch's reflog, meaning you actually integrated it. If not, the push is rejected with <code>remote ref updated since checkout</code>.</p>
<blockquote>
<p><strong>Trick:</strong> make the safe form your default with an alias: <code>git config --global alias.pushf &quot;push --force-with-lease --force-if-includes&quot;</code>, then use <code>git pushf</code>.</p>
</blockquote>

<h1 id="Chapter-9-—-Last-resort-git-fsck-for-dangling-objects"><a href="#Chapter-9-—-Last-resort-git-fsck-for-dangling-objects" class="headerlink" title="Chapter 9 — Last resort: git fsck for dangling objects"></a>Chapter 9 — Last resort: <code>git fsck</code> for dangling objects</h1>
<p>When the reflog has nothing — a dropped stash, an expired reflog, staged content lost to <code>reset --hard</code> — ask Git's checker which objects no ref points to.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git fsck --lost-found</span><br><span class="line"><span class="hljs-comment"># dangling commit 3c4d5e6f...</span></span><br><span class="line"><span class="hljs-comment"># dangling blob 9a8b7c6d...</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>--lost-found</code> also copies them into <code>.git/lost-found/commit/</code> and <code>.git/lost-found/other/</code>. For blobs it writes the file <em>contents</em>, so you can open them in an editor. For a commit, inspect it with <code>git show 3c4d5e6</code> and keep it with <code>git branch rescued 3c4d5e6</code>.</p>
<ul>
<li>By default, <code>fsck</code> treats reflog entries as roots, so a commit that is still in a reflog is <strong>not</strong> listed as dangling. Add <code>--no-reflogs</code> to see those too.</li>
<li>A dropped stash is a merge-like commit. Git's stash docs suggest searching unreachable commits for it. With a tagged stash (Chapter 5), search for the tag:</li>
</ul>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git fsck --unreachable | grep commit | <span class="hljs-built_in">cut</span> -d<span class="hljs-string">&#x27; &#x27;</span> -f3 |</span><br><span class="line">  xargs git <span class="hljs-built_in">log</span> --merges --no-walk --oneline --grep=<span class="hljs-string">&quot;wip-login-form&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="powershell"><span class="line">git fsck <span class="hljs-literal">--unreachable</span> |</span><br><span class="line">  <span class="hljs-built_in">Where-Object</span> { <span class="hljs-variable">$_</span> <span class="hljs-operator">-like</span> <span class="hljs-string">&#x27;unreachable commit *&#x27;</span> } |</span><br><span class="line">  <span class="hljs-built_in">ForEach-Object</span> { (<span class="hljs-variable">$_</span> <span class="hljs-operator">-split</span> <span class="hljs-string">&#x27; &#x27;</span>)[<span class="hljs-number">2</span>] } |</span><br><span class="line">  <span class="hljs-built_in">ForEach-Object</span> { git log <span class="hljs-literal">--merges</span> <span class="hljs-literal">--no-walk</span> <span class="hljs-literal">--oneline</span> <span class="hljs-literal">--grep</span>=<span class="hljs-string">&quot;wip-login-form&quot;</span> <span class="hljs-variable">$_</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Then <code>git stash apply &lt;sha&gt;</code> brings it back. Dangling objects survive until garbage collection prunes them; by default, <code>git gc</code> prunes loose unreachable objects older than two weeks (<code>gc.pruneExpire</code> = <code>2.weeks.ago</code>).</p>
<blockquote>
<p><strong>Watch out:</strong> never run <code>git gc --prune=now</code> in the middle of a rescue. It deletes exactly the objects you are looking for.</p>
</blockquote>

<h1 id="Chapter-10-—-Worktrees"><a href="#Chapter-10-—-Worktrees" class="headerlink" title="Chapter 10 — Worktrees"></a>Chapter 10 — Worktrees</h1>
<p>A <strong>worktree</strong> is an extra working folder attached to the same repository. Each worktree has its own <code>HEAD</code>, its own index and its own files on disk. All worktrees share one object database, the branches and tags, the config — and, as Chapter 5 showed, the stash. Good uses: review a pull request while your own branch is half-edited; run a long test on one branch while you keep editing another; build an old release.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git worktree list                                 <span class="hljs-comment"># all worktrees, main one first</span></span><br><span class="line">git worktree add -b hotfix ../lab-hotfix main     <span class="hljs-comment"># new branch &quot;hotfix&quot; from main, in ../lab-hotfix</span></span><br><span class="line">git worktree add ../lab-review feature            <span class="hljs-comment"># existing branch, new folder</span></span><br><span class="line">git worktree remove ../lab-hotfix                 <span class="hljs-comment"># delete the folder and its registration</span></span><br><span class="line">git worktree prune                                <span class="hljs-comment"># forget worktrees whose folder is gone</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Pitfalls"><a href="#Pitfalls" class="headerlink" title="Pitfalls"></a>Pitfalls</h2>
<p><strong>1. One branch, one worktree.</strong> A branch that is checked out in one worktree cannot be checked out in another. Current Git refuses with <code>fatal: 'main' is already used by worktree at '/work/rescue-lab'</code>; older versions word it as <code>is already checked out at …</code>. The same rule blocks deleting the branch (<code>cannot delete branch 'hotfix' used by worktree at …</code>). The reason: two checkouts moving one branch pointer would leave one of them with a stale index. Fix it by using a different branch there, using <code>--detach</code>, or removing the other worktree first.</p>
<p><strong>2. Ignored files do not come along.</strong> A new worktree is a fresh checkout of <em>tracked</em> files only. <code>.env</code> files, virtual environments (<code>.venv</code>), <code>node_modules</code>, build caches — anything in <code>.gitignore</code> — are missing. The app often will not start there until you reinstall dependencies and copy local config. Budget for that, or do the work in the main checkout.</p>
<p><strong>3. GUI tools show every worktree.</strong> For example, VS Code (since version 1.103) scans the repository for worktrees and lists each one in the Source Control Repositories view; the <code>git.detectWorktrees</code> setting turns this off. Other Git GUIs list them too. Many leftover worktrees mean a cluttered sidebar, and it becomes easy to open a file from the wrong checkout.</p>
<p><strong>4. Deleting the folder by hand leaves a stale entry.</strong> Git keeps admin files for each worktree inside the main repository. If you delete the folder in Explorer, <code>git worktree list</code> marks it <code>prunable</code>, and its branch can still count as &quot;in use&quot; until you run <code>git worktree prune</code>. Prefer <code>git worktree remove</code>. It refuses when there is unsaved work: <code>'../lab-hotfix' contains modified or untracked files, use --force to delete it</code>.</p>
<p><strong>5. Shared state still leaks across.</strong> Stash, config and hooks are shared. A <code>git stash pop</code> in one worktree can take an entry that was made in another.</p>
<h2 id="Case-study-the-posts-that-disappeared"><a href="#Case-study-the-posts-that-disappeared" class="headerlink" title="Case study: the posts that &quot;disappeared&quot;"></a>Case study: the posts that &quot;disappeared&quot;</h2>
<p>On this blog, a batch of drafts was once written into a worktree folder instead of the main checkout. The files were real and correct. But the dev server and the editor were running from the main checkout, so the new posts did not show up there, and it looked like the work was lost. Nothing was lost — it was simply in the other folder. The fix was plain: write content in the main checkout, and keep worktrees for short, clearly named, throwaway tasks. Before you hunt for &quot;missing&quot; files, run <code>git worktree list</code> and check which folder the file was written to.</p>

<h1 id="Chapter-11-—-git-bisect-in-one-paragraph"><a href="#Chapter-11-—-git-bisect-in-one-paragraph" class="headerlink" title="Chapter 11 — git bisect in one paragraph"></a>Chapter 11 — <code>git bisect</code> in one paragraph</h1>
<p>When something worked last month and is broken now, <code>git bisect</code> does a binary search over the commits in between. Run <code>git bisect start</code>, mark the broken commit with <code>git bisect bad</code> and a known-good one with <code>git bisect good v1.4.0</code>; Git checks out the middle commit; you test it and answer <code>good</code> or <code>bad</code>; repeat. About 1,000 commits need only about 10 steps. Automate it with <code>git bisect run &lt;command&gt;</code>: exit code 0 means good, 125 means &quot;cannot test, skip&quot;, and any other code from 1 to 127 means bad. Finish with <code>git bisect reset</code>. Dev Essentials 10 · Debugging covers bisect as part of a full debugging method.</p>

<h1 id="Cheat-sheet"><a href="#Cheat-sheet" class="headerlink" title="Cheat-sheet"></a>Cheat-sheet</h1>
<table>
<thead>
<tr>
<th>Symptom</th>
<th>Command</th>
</tr>
</thead>
<tbody>
<tr>
<td>Commits vanished after <code>reset --hard</code></td>
<td><code>git reflog</code> → <code>git reset --hard 'HEAD@{1}'</code></td>
</tr>
<tr>
<td>Rebase went wrong</td>
<td><code>git reset --hard 'branch@{1}'</code> (or <code>ORIG_HEAD</code> right after)</td>
</tr>
<tr>
<td>Deleted a branch</td>
<td><code>git branch name &lt;sha&gt;</code> (sha from &quot;Deleted branch … (was …)&quot; or reflog)</td>
</tr>
<tr>
<td>Discard edits / unstage a file</td>
<td><code>git restore file</code> / <code>git restore --staged file</code></td>
</tr>
<tr>
<td>Undo last local commit, keep work</td>
<td><code>git reset --soft HEAD~1</code></td>
</tr>
<tr>
<td>Undo a pushed commit</td>
<td><code>git revert &lt;sha&gt;</code></td>
</tr>
<tr>
<td>Stash safely</td>
<td><code>git stash push -u -m &quot;tag&quot;</code> → <code>git stash apply &lt;sha&gt;</code> → drop by re-found index</td>
</tr>
<tr>
<td>Commits made in detached HEAD</td>
<td><code>git switch -c name</code> (or <code>git branch name &lt;sha&gt;</code> from reflog)</td>
</tr>
<tr>
<td>Copy a commit to another branch</td>
<td><code>git cherry-pick -x &lt;sha&gt;</code></td>
</tr>
<tr>
<td>Fold a fix into an older commit</td>
<td><code>git commit --fixup=&lt;sha&gt;</code> → <code>git rebase --autosquash &lt;base&gt;</code></td>
</tr>
<tr>
<td>Force-push safely</td>
<td><code>git push --force-with-lease --force-if-includes</code></td>
</tr>
<tr>
<td>Nothing in the reflog</td>
<td><code>git fsck --lost-found</code> (add <code>--no-reflogs</code> to widen)</td>
</tr>
<tr>
<td>Branch &quot;already used by worktree&quot;</td>
<td><code>git worktree list</code> → work elsewhere or <code>git worktree remove</code></td>
</tr>
<tr>
<td>Stale worktree entry</td>
<td><code>git worktree prune</code></td>
</tr>
<tr>
<td>Find the commit that broke it</td>
<td><code>git bisect start</code> / <code>good</code> / <code>bad</code> / <code>run</code> / <code>reset</code></td>
</tr>
</tbody>
</table>
