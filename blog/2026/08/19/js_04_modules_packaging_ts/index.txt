<h1 id="Chapter-1-—-ES-modules-as-the-spec-defines-them"><a href="#Chapter-1-—-ES-modules-as-the-spec-defines-them" class="headerlink" title="Chapter 1 — ES modules as the spec defines them"></a>Chapter 1 — ES modules as the spec defines them</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Module record</strong> — the engine's parsed representation of one module: its imports, exports and code.</li>
<li><strong>Linking</strong> — connecting every import to the exporting module's binding, before any code runs.</li>
<li><strong>Binding</strong> — a named slot in a module's environment. An import is a <em>read-only view</em> of the exporter's binding, not a copy of its value.</li>
<li><strong>Module namespace object</strong> — the object you get from <code>import * as ns</code> or <code>await import()</code>: a frozen-shaped, live view of all exports.</li>
<li><strong>TDZ (temporal dead zone)</strong> — the window between a <code>let</code>/<code>const</code>/<code>class</code> binding being created and being initialised. Reading it throws <code>ReferenceError</code>.</li>
</ul>
<h2 id="Three-phases"><a href="#Three-phases" class="headerlink" title="Three phases"></a>Three phases</h2>
<p>A module graph is loaded in three separate phases:</p>
<ol>
<li><strong>Construction</strong> — fetch and parse every module reachable through static <code>import</code>/<code>export … from</code> declarations. The whole graph is known before anything runs. This is why static imports must be at top level with string-literal specifiers.</li>
<li><strong>Linking</strong> — create each module's bindings and wire imports to exports. A missing named export is a <code>SyntaxError</code> at this point, before any code runs.</li>
<li><strong>Evaluation</strong> — run each module body once, in <strong>post-order depth-first</strong> order: dependencies before dependents, siblings in source order. If <code>main.js</code> imports <code>a.js</code> and then <code>b.js</code>, and both import <code>c.js</code>, the bodies run in the order <code>c.js</code>, <code>a.js</code>, <code>b.js</code>, <code>main.js</code>.</li>
</ol>
<p>Consequences:</p>
<ul>
<li><strong>Imports are hoisted.</strong> An <code>import</code> on line 50 is linked before line 1 runs.</li>
<li><strong>Each module runs once per realm</strong>, keyed by its resolved URL. <code>./a.js?v=2</code> is a different module from <code>./a.js</code>.</li>
<li><strong>Modules are strict mode</strong>, top-level <code>this</code> is <code>undefined</code>, and top-level declarations are module-scoped, not global.</li>
</ul>

<h2 id="Cycles"><a href="#Cycles" class="headerlink" title="Cycles"></a>Cycles</h2>
<p>Both systems allow cycles and both can surprise you, in different ways.</p>
<table>
<thead>
<tr>
<th></th>
<th>ESM</th>
<th>CommonJS</th>
</tr>
</thead>
<tbody>
<tr>
<td>Module in the cycle not finished yet</td>
<td>Its bindings exist but are uninitialised: reading a <code>let</code>/<code>const</code>/<code>class</code> export throws <code>ReferenceError</code> (TDZ). <code>function</code> declarations are hoisted and usable.</td>
<td><code>require</code> returns the <em>partial</em> <code>module.exports</code> object as it is at that moment. Missing properties are <code>undefined</code>, and no error is raised.</td>
</tr>
<tr>
<td>Typical symptom</td>
<td><code>ReferenceError: Cannot access 'X' before initialization</code></td>
<td><code>TypeError: x is not a function</code> far from the cause</td>
</tr>
<tr>
<td>Fix</td>
<td>Break the cycle, move shared code into a third module, or only use cyclic imports inside functions called later</td>
<td>Same, or <code>require</code> inside the function that needs it</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>Trick:</strong> <code>madge --circular src/</code> or <code>dpdm</code> lists cycles. Run one in CI. Cycles through barrel files (<code>index.ts</code> re-exporting a whole folder) are the most common source in large apps.</p>
</blockquote>
<h2 id="Top-level-await"><a href="#Top-level-await" class="headerlink" title="Top-level await"></a>Top-level await</h2>
<p>A module that uses top-level <code>await</code> (ES2022) makes its evaluation asynchronous. Every module that imports it, directly or indirectly, waits for it. Siblings that do not depend on it can still evaluate. The cost is easy to miss: one <code>await fetchConfig()</code> in a shared <code>config.js</code> delays the start of every module above it in the graph.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// db.js</span></span><br><span class="line"><span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> pool = <span class="hljs-keyword">await</span> <span class="hljs-title function_">createPool</span>(process.<span class="hljs-property">env</span>.<span class="hljs-property">DATABASE_URL</span>);  <span class="hljs-comment">// importers wait for this</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Use it for real start-up dependencies (config, WASM instantiation, a connection pool) in <em>applications</em>. Avoid it in <em>libraries</em>. It forces an async graph on every consumer, and in Node it makes the module impossible to <code>require()</code> (Chapter 2).</p>
<h2 id="Dynamic-import-and-importmeta"><a href="#Dynamic-import-and-importmeta" class="headerlink" title="Dynamic import and import.meta"></a>Dynamic import and <code>import.meta</code></h2>
<p><code>import(specifier)</code> works in both module systems. It returns a promise of the namespace object and is how code-splitting points are expressed. <code>import.meta.url</code> is the module's own URL. Node adds <code>import.meta.dirname</code> and <code>import.meta.filename</code> (Node 20.11+), which replace <code>__dirname</code>/<code>__filename</code> in ESM, and <code>import.meta.resolve(specifier)</code>.</p>

<h2 id="ESM-importing-CommonJS"><a href="#ESM-importing-CommonJS" class="headerlink" title="ESM importing CommonJS"></a>ESM importing CommonJS</h2>
<p><code>import x from './legacy.cjs'</code> always works: the default export is <code>module.exports</code>. Named imports (<code>import { a } from './legacy.cjs'</code>) work only if Node's static analyser (<code>cjs-module-lexer</code>) can see the names in the source, for example as <code>exports.a = …</code> or <code>module.exports = { a, b }</code>. Exports computed at runtime are invisible to it, so you get a <code>SyntaxError</code> at link time.</p>
<h2 id="CommonJS-requiring-ESM-requireesm"><a href="#CommonJS-requiring-ESM-requireesm" class="headerlink" title="CommonJS requiring ESM: require(esm)"></a>CommonJS requiring ESM: <code>require(esm)</code></h2>
<p>For years <code>require()</code> of an ES module threw <code>ERR_REQUIRE_ESM</code>, and that single error drove a decade of dual-publishing. That has changed:</p>
<table>
<thead>
<tr>
<th>Node version</th>

</tr>
</thead>
<tbody>
<tr>

<td>Added behind <code>--experimental-require-module</code></td>

<td>Enabled by default (no flag)</td>
</tr>
<tr>

</tr>
<tr>

<td>No longer experimental</td>
</tr>
</tbody>
</table>
<p>Rules:</p>
<ul>
<li>The ES module graph must be <strong>fully synchronous</strong>: no top-level <code>await</code> anywhere in it. Otherwise you get <code>ERR_REQUIRE_ASYNC_MODULE</code>.</li>
<li><code>require()</code> returns the <strong>namespace object</strong>. If it has a default export, the namespace also includes <code>__esModule: true</code>, so transpiled CJS consumers see the default export correctly.</li>
<li>An ES module can choose what <code>require()</code> returns with <code>export { thing as 'module.exports' }</code>.</li>
<li>Detect it with <code>process.features.require_module</code>. Disable it with <code>--no-require-module</code>.</li>
</ul>

<h1 id="Chapter-3-—-packagejson-exports-imports-and-conditions"><a href="#Chapter-3-—-packagejson-exports-imports-and-conditions" class="headerlink" title="Chapter 3 — package.json: exports, imports and conditions"></a>Chapter 3 — <code>package.json</code>: <code>exports</code>, <code>imports</code> and conditions</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Entry point</strong> — the file a bare specifier (<code>import 'pkg'</code>) or subpath (<code>import 'pkg/utils'</code>) resolves to.</li>
<li><strong><code>exports</code></strong> — the public map from subpaths to files. Once present, <strong>only</strong> listed subpaths can be imported. Anything else throws <code>ERR_PACKAGE_PATH_NOT_EXPORTED</code>.</li>
<li><strong>Condition</strong> — a key inside an <code>exports</code> entry that matches the environment (<code>import</code>, <code>require</code>, <code>node</code>, <code>browser</code>, <code>types</code>, …).</li>
<li><strong>Subpath pattern</strong> — a <code>*</code> in both key and target, e.g. <code>&quot;./features/*&quot;: &quot;./dist/features/*.js&quot;</code>.</li>
<li><strong><code>imports</code></strong> — a private map for the package's own code. Keys must start with <code>#</code>.</li>
</ul>

<h1 id="Chapter-4-—-Dual-packages-and-the-hazard"><a href="#Chapter-4-—-Dual-packages-and-the-hazard" class="headerlink" title="Chapter 4 — Dual packages and the hazard"></a>Chapter 4 — Dual packages and the hazard</h1>
<p>A <strong>dual package</strong> ships both an ESM build and a CJS build. The <strong>dual-package hazard</strong>: in one process, some code <code>import</code>s the package and some <code>require</code>s it. Node then loads <strong>both</strong> files, creating two module instances with two copies of every piece of module state.</p>
<p>Symptoms:</p>
<ul>
<li><code>err instanceof SdkError</code> is <code>false</code> for an error thrown by &quot;the same&quot; class.</li>
<li>A singleton registry, cache or plugin list exists twice, and registrations go missing.</li>
<li>Two copies of a framework runtime complain that hooks or context are being called from a different copy.</li>
</ul>
<p>Strategies, from most to least preferred in 2026:</p>
<table>
<thead>
<tr>
<th>Strategy</th>
<th>How</th>
<th>Trade-off</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>ESM-only</strong></td>
<td>Ship ESM; CJS consumers use <code>require(esm)</code></td>
<td>Needs Node 20.19+ / 22.12+ for CJS consumers; no top-level <code>await</code> in the graph</td>
</tr>
<tr>
<td><strong>One ESM file for everyone</strong></td>
<td><code>&quot;module-sync&quot;</code> and <code>&quot;import&quot;</code> point at the ESM file, <code>&quot;require&quot;</code> points at a fallback only for old Node</td>
<td>Old Node still gets two copies, which is acceptable if old Node never mixes the two</td>
</tr>
<tr>
<td><strong>CJS core + thin ESM wrapper</strong></td>
<td><code>index.mjs</code> does <code>import cjs from './index.cjs'; export const { a, b } = cjs;</code></td>
<td>One instance of state; ESM consumers lose tree-shaking</td>
</tr>
<tr>
<td><strong>Stateless dual build</strong></td>
<td>Two full builds, no module-level state, no <code>instanceof</code> across the API</td>

This survives two copies and even two different versions in <code>node_modules</code>.</p>
</blockquote>

<h1 id="Chapter-6-—-Tree-shaking-and-bundlers"><a href="#Chapter-6-—-Tree-shaking-and-bundlers" class="headerlink" title="Chapter 6 — Tree-shaking and bundlers"></a>Chapter 6 — Tree-shaking and bundlers</h1>
<h2 id="What-tree-shaking-needs"><a href="#What-tree-shaking-needs" class="headerlink" title="What tree-shaking needs"></a>What tree-shaking needs</h2>
<p>Tree-shaking removes exports nobody imports. It relies on ESM being <strong>static</strong>: the bundler can see every import and export without running code. It fails when:</p>
<ul>
<li><strong>Code is CommonJS.</strong> <code>module.exports</code> is a runtime object, so bundlers must keep all of it (with a few heuristics).</li>
<li><strong>A module might have side effects.</strong> A top-level <code>polyfill()</code>, a <code>class</code> with static initialisers, or <code>Object.defineProperty(window, …)</code> must be kept even if nothing is imported from the module. The bundler has to assume that side effects exist unless told otherwise.</li>
<li><strong>The code uses namespace objects dynamically.</strong> <code>ns[key]</code> with a computed key keeps the whole namespace.</li>
</ul>
<p>Tell the bundler what is safe:</p>
<pre><code class="language-json"><figure class="highlight json"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="json"><span class="line"><span class="hljs-punctuation">{</span> <span class="hljs-attr">&quot;sideEffects&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">[</span><span class="hljs-string">&quot;*.css&quot;</span><span class="hljs-punctuation">,</span> <span class="hljs-string">&quot;./dist/polyfills.js&quot;</span><span class="hljs-punctuation">]</span> <span class="hljs-punctuation">}</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> theme = <span class="hljs-comment">/*#__PURE__*/</span> <span class="hljs-title function_">createTheme</span>({ … });   <span class="hljs-comment">// this call may be dropped if unused</span></span><br><span class="line"><span class="hljs-comment">/*#__NO_SIDE_EFFECTS__*/</span> <span class="hljs-keyword">export</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">defineComponent</span>(<span class="hljs-params">o</span>) { <span class="hljs-keyword">return</span> o; } <span class="hljs-comment">// every call is droppable</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>&quot;sideEffects&quot;: false</code> claims that <em>no</em> file in the package does anything on import, so the bundler may skip whole modules. Lying here breaks CSS imports and polyfills silently.</p>
<blockquote>
<p><strong>Watch out:</strong> barrel files (<code>index.ts</code> that re-exports 300 components) are cheap in production builds with correct <code>sideEffects</code>, but expensive everywhere else. The dev server, test runner and type checker all load and transform every re-exported module. Large codebases import from the leaf module (<code>@acme/ui/button</code>), and expose subpath <code>exports</code> to allow it.</p>
</blockquote>

<h1 id="Chapter-7-—-TypeScript-at-scale"><a href="#Chapter-7-—-TypeScript-at-scale" class="headerlink" title="Chapter 7 — TypeScript at scale"></a>Chapter 7 — TypeScript at scale</h1>
<h2 id="Where-TypeScript-is-in-2026"><a href="#Where-TypeScript-is-in-2026" class="headerlink" title="Where TypeScript is in 2026"></a>Where TypeScript is in 2026</h2>
<ul>
<li><strong>TypeScript 6.0</strong> (March 2026) is the last release built on the JavaScript codebase. It changed defaults: <code>strict: true</code>, <code>module: esnext</code>, <code>target: es2025</code>, <code>types: []</code> (no more automatic inclusion of every <code>@types</code> package), and <code>rootDir: &quot;.&quot;</code>. It also deprecated a long list of legacy options: <code>moduleResolution: node</code>/<code>node10</code> and <code>classic</code>, <code>target: es5</code>, <code>--downlevelIteration</code>, <code>--outFile</code>, <code>baseUrl</code> as a lookup root, and the <code>amd</code>/<code>umd</code>/<code>systemjs</code> module formats.</li>
<li><strong>TypeScript 7.0</strong> (July 2026) is the native port, written in Go. The announcement reports typical full-build speed-ups of 8–12×. It still installs as <code>typescript</code> and runs as <code>tsc</code>. The deprecated 6.0 options are now hard errors. 7.0 ships <strong>without a programmatic API</strong>, which is planned for 7.1. So tools that drive the compiler through its API (Vue, Svelte, Astro and MDX language tooling, some lint rules) may need to stay on 6.0 for now.</li>
</ul>

<h2 id="Declaration-files"><a href="#Declaration-files" class="headerlink" title="Declaration files"></a>Declaration files</h2>
<p>Libraries publish <code>.d.ts</code> files (<code>&quot;declaration&quot;: true</code>, plus <code>&quot;declarationMap&quot;: true</code> so that &quot;go to definition&quot; lands in the source). <code>isolatedDeclarations</code> (TS 5.5) requires explicit return and export types, so that each file's declarations can be produced <strong>without the type checker</strong>. Fast tools such as Oxc can then emit <code>.d.ts</code> files in parallel. In a monorepo this removes the slowest step from the build graph.</p>

<h1 id="Chapter-8-—-Type-level-programming-essentials"><a href="#Chapter-8-—-Type-level-programming-essentials" class="headerlink" title="Chapter 8 — Type-level programming essentials"></a>Chapter 8 — Type-level programming essentials</h1>
<p>Types are a small functional language that runs at compile time. Four features cover most real code.</p>

<p>Two operators that keep type-level code small:</p>
<ul>
<li><strong><code>satisfies</code></strong> checks a value against a type without widening it: <code>const routes = { home: '/', user: '/u/:id' } satisfies Record&lt;string, string&gt;;</code> keeps the literal keys.</li>
<li><strong><code>const</code> type parameters</strong> (<code>function f&lt;const T&gt;(x: T)</code>) infer <code>['a', 'b']</code> as a readonly tuple instead of <code>string[]</code>.</li>

<blockquote>
<p><strong>Watch out:</strong> deep recursive conditional types slow down the checker for everyone who imports them. If <code>tsc --extendedDiagnostics</code> shows check time dominated by one file, or <code>tsc --generateTrace</code> points at one type, simplify that type. <h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Live-binding-or-copy"><a href="#Exercise-1-—-Live-binding-or-copy" class="headerlink" title="Exercise 1 — Live binding or copy?"></a>Exercise 1 — Live binding or copy?</h2>
<p>Given <code>export let n = 1; export function bump() { n++; }</code>, what do an ESM importer and a CJS consumer using <code>require(esm)</code> each see after calling <code>bump()</code>?</p>
<details>
<summary>Solution</summary>
<p>Both see <code>2</code> through <code>ns.n</code> or a named import. <code>require(esm)</code> returns the <strong>module namespace object</strong>, which is a live view. The CJS consumer loses liveness only if it destructures: <code>const { n, bump } = require('./m.mjs')</code> copies <code>n</code> at that moment, and it stays <code>1</code>.</p>
</details>
<h2 id="Exercise-2-—-Fix-the-exports-map"><a href="#Exercise-2-—-Fix-the-exports-map" class="headerlink" title="Exercise 2 — Fix the exports map"></a>Exercise 2 — Fix the exports map</h2>
<p>A package has <code>&quot;exports&quot;: { &quot;.&quot;: { &quot;import&quot;: &quot;./dist/index.mjs&quot;, &quot;types&quot;: &quot;./dist/index.d.ts&quot;, &quot;require&quot;: &quot;./dist/index.cjs&quot; } }</code>. TypeScript users with <code>moduleResolution: nodenext</code> who <code>import</code> it report missing types, while <code>require</code> users are fine. Why, and what is the fix?</p>
<details>
<summary>Solution</summary>
<p>Key order is priority. For an ESM consumer, TypeScript matches <code>import</code> first and never reaches <code>types</code>. It resolves <code>./dist/index.mjs</code> and looks for the sibling declaration file <code>./dist/index.d.mts</code>, which does not exist. A <code>require</code> consumer skips <code>import</code>, so it reaches <code>types</code>. Put <code>types</code> first. If the ESM and CJS builds need different declarations, nest them: <code>&quot;import&quot;: { &quot;types&quot;: &quot;./dist/index.d.ts&quot;, &quot;default&quot;: &quot;./dist/index.js&quot; }, &quot;require&quot;: { &quot;types&quot;: &quot;./dist/index.d.cts&quot;, &quot;default&quot;: &quot;./dist/index.cjs&quot; }</code>. Verify with <code>npx @arethetypeswrong/cli --pack</code>.</p>
</details>
<h2 id="Exercise-3-—-Diagnose-the-double-singleton"><a href="#Exercise-3-—-Diagnose-the-double-singleton" class="headerlink" title="Exercise 3 — Diagnose the double singleton"></a>Exercise 3 — Diagnose the double singleton</h2>
<p>An app registers plugins with <code>@acme/sdk</code>, but plugins registered from a CJS config file never show up. The app code uses <code>import</code>. Explain the bug and give two fixes.</p>
<details>
<summary>Solution</summary>
<p>This is the dual-package hazard. The app loads <code>dist/index.js</code> and the config loads <code>dist/index.cjs</code>: two module instances, two registries. Fixes: (1) publish ESM-only, or point <code>module-sync</code>/<code>require</code> at the ESM file, so that <code>require(esm)</code> loads the same instance; (2) store the registry on <code>globalThis</code> under <code>Symbol.for('@acme/sdk.registry')</code> so that both copies share it.</p>
</details>
<h2 id="Exercise-4-—-Why-is-it-in-the-bundle"><a href="#Exercise-4-—-Why-is-it-in-the-bundle" class="headerlink" title="Exercise 4 — Why is it in the bundle?"></a>Exercise 4 — Why is it in the bundle?</h2>
<p>A 3 KB feature ships 180 KB. The bundle visualiser shows all of <code>@acme/icons</code>, imported as <code>import { Check } from '@acme/icons'</code>. List three possible causes.</p>
<details>
<summary>Solution</summary>
<p>(1) <code>@acme/icons</code> ships CommonJS only, so it cannot be tree-shaken. (2) It has no <code>&quot;sideEffects&quot;: false</code>, so the bundler keeps every module the barrel re-exports. (3) Its icons are built by top-level calls (<code>createIcon(…)</code>) without <code>/*#__PURE__*/</code>, so each call counts as a possible side effect. Fix at the source, or import from a subpath (<code>@acme/icons/check</code>) if the package exports one.</p>
</details>
<h2 id="Exercise-5-—-Strip-types-readiness"><a href="#Exercise-5-—-Strip-types-readiness" class="headerlink" title="Exercise 5 — Strip-types readiness"></a>Exercise 5 — Strip-types readiness</h2>
<p>Which of these lines fail under Node's type stripping, and why? <code>enum Color { Red }</code>, <code>import { User } from './types.ts'</code> (User is a type), <code>class A { constructor(private x: number) {} }</code>, <code>const x = y as unknown as Z;</code></p>
<details>
<summary>Solution</summary>
<p>The <code>enum</code> fails: it needs code generation. The parameter property <code>private x</code> fails for the same reason. The <code>import { User }</code> fails at runtime because it is treated as a value import of a name that <code>types.ts</code> does not export at runtime. Write <code>import type { User }</code>. The <code>as</code> casts are erasable and fine. <code>erasableSyntaxOnly</code> plus <code>verbatimModuleSyntax</code> catch all three failures at compile time.</p>
</details>
<h2 id="Exercise-6-—-Write-a-type"><a href="#Exercise-6-—-Write-a-type" class="headerlink" title="Exercise 6 — Write a type"></a>Exercise 6 — Write a type</h2>
<p>Write <code>DeepReadonly&lt;T&gt;</code> that makes nested objects and arrays readonly, but leaves functions alone.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-ts"><figure class="highlight ts"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="ts"><span class="line"><span class="hljs-keyword">type</span> <span class="hljs-title class_">DeepReadonly</span>&lt;T&gt; =</span><br><span class="line">  T <span class="hljs-title function_">extends</span> (...<span class="hljs-attr">args</span>: <span class="hljs-built_in">any</span>[]) =&gt; <span class="hljs-built_in">unknown</span> ? <p>The function check comes first, because functions are objects and would otherwise be mapped. Arrays are handled before plain objects, so that they become <code>ReadonlyArray</code> rather than objects with numeric keys.</p>
</details>
