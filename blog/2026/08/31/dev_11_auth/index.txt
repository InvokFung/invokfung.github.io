<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Tell <strong>authentication</strong> from <strong>authorization</strong>, and pick 401 vs 403 correctly.</li>
<li>Store passwords with <strong>Argon2id</strong> (or scrypt / bcrypt / PBKDF2) and the current OWASP parameters; explain <strong>salt</strong> vs <strong>pepper</strong>.</li>
<li>Apply the password rules of <strong>NIST SP 800-63B-4</strong>: length, no composition rules, no forced rotation, blocklists.</li>
<li>Harden a login: rate limits, generic errors, <strong>TOTP</strong> (RFC 6238) and <strong>passkeys</strong> (WebAuthn).</li>
<li>Build <strong>server-side sessions</strong> with safe cookie flags, and know when a <strong>JWT</strong> is the better tool.</li>
<li>Describe the OAuth 2.0 <strong>authorization code flow with PKCE</strong>, and the difference between an <strong>ID token</strong> and an <strong>access token</strong>.</li>

<h1 id="Chapter-1-—-Who-are-you-and-what-may-you-do"><a href="#Chapter-1-—-Who-are-you-and-what-may-you-do" class="headerlink" title="Chapter 1 — Who are you, and what may you do?"></a>Chapter 1 — Who are you, and what may you do?</h1>
<p>Two questions sit behind every protected request:</p>
<ol>
<li><strong>Authentication (AuthN)</strong> — <em>who are you?</em> The user proves an identity, for example with a password plus a code.</li>
<li><strong>Authorization (AuthZ)</strong> — <em>what may you do?</em> The app checks whether this identity may read or change this thing.</li>
</ol>
<p>They fail in different ways. A perfect login does not help if any logged-in user can open <code>/invoices/42</code> that belongs to someone else. That second bug is authorization, and Dev Essentials 12 · OWASP Top 10 shows it as &quot;Broken Access Control&quot;.</p>
<p>HTTP has a status code for each. <code>401 Unauthorized</code> means &quot;I do not know who you are&quot; (not logged in, or a bad token). <code>403 Forbidden</code> means &quot;I know who you are, and you may not do this&quot;. A <code>404</code> is also fine for &quot;not yours&quot; when you do not want to reveal that the thing exists.</p>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Credential</strong> — the thing that proves identity: a password, a private key, a code.</li>
<li><strong>Factor</strong> — a kind of proof: something you <em>know</em> (password), <em>have</em> (phone, security key), or <em>are</em> (fingerprint). <strong>MFA</strong> means two or more different kinds.</li>
<li><strong>Session</strong> — the server remembers &quot;this browser is logged in as Ada&quot; after the login step.</li>
<li><strong>Token</strong> — a string the client sends with each request to show it is logged in. It can be a random ID (a <em>reference</em>) or a signed document such as a JWT (a <em>value</em>).</li>
<li><strong>Identity provider (IdP)</strong> — a service that logs users in for other apps (Google, Microsoft Entra ID, Okta, Keycloak).</li>
</ul>
<hr>
<h1 id="Chapter-2-—-Storing-passwords"><a href="#Chapter-2-—-Storing-passwords" class="headerlink" title="Chapter 2 — Storing passwords"></a>Chapter 2 — Storing passwords</h1>
<h2 id="Never-plain-text-never-reversible-encryption"><a href="#Never-plain-text-never-reversible-encryption" class="headerlink" title="Never plain text, never reversible encryption"></a>Never plain text, never reversible encryption</h2>
<p>If you store passwords as plain text, one database leak exposes every user — and most users reuse passwords on other sites. Encryption is not the answer either. Encrypted data can be decrypted, so whoever steals the key gets every password back. You want a <strong>one-way</strong> function: easy to check a guess, impossible to reverse. That is a hash. But not any hash.</p>
<h2 id="Why-SHA-256-is-the-wrong-hash"><a href="#Why-SHA-256-is-the-wrong-hash" class="headerlink" title="Why SHA-256 is the wrong hash"></a>Why SHA-256 is the wrong hash</h2>
<p>SHA-256 and MD5 are built to be <strong>fast</strong>. A modern GPU can compute billions of them per second. If an attacker steals your table of SHA-256 password hashes, they hash every word from a big list of leaked passwords and compare. Password hashing functions are built to be <strong>slow and memory-hungry on purpose</strong>. One login costs your server a fraction of a second. For an attacker trying billions of guesses, the same cost becomes enormous. Being <strong>memory-hard</strong> matters too: GPUs have many cores but little memory per core, so a hash that needs many MiB per guess slows them down.</p>
<h2 id="Salt-and-pepper"><a href="#Salt-and-pepper" class="headerlink" title="Salt and pepper"></a>Salt and pepper</h2>
<ul>
<li><strong>Salt</strong> — a random value, different for every password, stored next to the hash. Two users with the same password get different hashes, and precomputed tables (&quot;rainbow tables&quot;) become useless. Modern libraries make and store the salt for you.</li>
<li><strong>Pepper</strong> — one secret value shared by all passwords, stored <strong>outside</strong> the database (a secrets manager or an HSM). OWASP says a pepper &quot;should not be stored along with the generated hash&quot;. If only the database leaks, the hashes cannot be cracked without it. A pepper is defence in depth, not a replacement for a slow hash.</li>
</ul>

<td>When FIPS-140 compliance is required</td>
<td>&quot;PBKDF2-HMAC-SHA256: 600,000 iterations&quot;; &quot;PBKDF2-HMAC-SHA512: 220,000 iterations&quot;</td>
</tr>
</tbody>
</table>
<p>OWASP also lists Argon2id settings that give about the same protection. You can trade memory for iterations: <code>m=47104 (46 MiB), t=1, p=1</code>, <code>m=19456 (19 MiB), t=2, p=1</code>, <code>m=12288 (12 MiB), t=3, p=1</code>, <code>m=9216 (9 MiB), t=4, p=1</code>, <code>m=7168 (7 MiB), t=5, p=1</code>.</p>
<blockquote>
<p><strong>Watch out:</strong> bcrypt only uses the first <strong>72 bytes</strong> of the input in most implementations. Longer passwords are silently cut, so two different long passwords can match. OWASP says to &quot;enforce a maximum password length of 72 bytes&quot;. Note that 72 <em>bytes</em> can be fewer than 72 characters in UTF-8 (see Dev Essentials 01 · Text Encoding). Pre-hashing the password before bcrypt has its own traps (null bytes, &quot;password shucking&quot;), so for new systems just choose Argon2id.</p>
</blockquote>
<p>The <strong>work factor</strong> (or cost) is how much CPU time, and for Argon2 and scrypt how much memory, one hash takes. You raise it as hardware gets faster.</p>

<p>The output is an <strong>encoded hash</strong>: one string that holds the algorithm, parameters, salt and hash. Store the whole string. <code>hash</code> returns a different string each time for the same password; that is the salt at work. <code>verify</code> reads the parameters and salt back out of the string. <code>check_needs_rehash</code> tells you when a stored hash used older, weaker parameters. The only moment you have the plain password is during login, so that is when you upgrade it.</p>
<p>The library default is the <strong>RFC 9106 &quot;low memory&quot; profile</strong>: <code>time_cost=3</code>, <code>memory_cost=65536</code> (KiB, so 64 MiB), <code>parallelism=4</code>. <blockquote>
<p><strong>Trick:</strong> measure before you choose. Run <code>python -m timeit -s &quot;from argon2 import PasswordHasher; ph=PasswordHasher()&quot; &quot;ph.hash('x')&quot;</code> on the real server. Pick the strongest setting whose time and memory your login traffic can afford.</p>
</blockquote>
<blockquote>
<p><strong>Common pitfall:</strong> comparing hashes yourself with <code>==</code>. Always call the library's <code>verify</code>. It does the constant-time compare and handles every parameter set that is stored in the string.</p>
</blockquote>

<h1 id="Chapter-5-—-Hardening-the-login"><a href="#Chapter-5-—-Hardening-the-login" class="headerlink" title="Chapter 5 — Hardening the login"></a>Chapter 5 — Hardening the login</h1>
<h2 id="Rate-limiting"><a href="#Rate-limiting" class="headerlink" title="Rate limiting"></a>Rate limiting</h2>
<p>Without a limit, an attacker can try thousands of passwords per minute. NIST requires that the verifier &quot;SHALL limit consecutive failed authentication attempts using a specific authenticator on a single subscriber account to no more than 100&quot;. Most apps choose a much lower number, plus a limit per IP address. The app in Chapter 7 allows 5 failures per account per 15 minutes. Dev Essentials 14 · API Reliability covers rate-limit algorithms in depth.</p>
<blockquote>
<p><strong>Watch out:</strong> a hard lockout per account lets anyone lock a real user out on purpose. Prefer growing delays or a temporary block, and give the real user a way to recover.</p>
</blockquote>
<h2 id="Generic-error-messages"><a href="#Generic-error-messages" class="headerlink" title="Generic error messages"></a>Generic error messages</h2>
<p>Say &quot;Invalid username or password&quot; in <strong>both</strong> cases. If &quot;no such user&quot; and &quot;wrong password&quot; give different messages, attackers can find which accounts exist (<strong>user enumeration</strong>). Watch the timing too. If unknown users return instantly while real users take 50 ms to hash, the delay leaks the same fact. The Chapter 7 code hashes a dummy value for unknown users to keep the timing close. Registration and &quot;forgot password&quot; pages leak the same way, so give them neutral replies such as &quot;If that account exists, we sent an email&quot;.</p>

<h2 id="Passkeys-and-WebAuthn"><a href="#Passkeys-and-WebAuthn" class="headerlink" title="Passkeys and WebAuthn"></a>Passkeys and WebAuthn</h2>
<p>TOTP codes can still be phished: a fake site asks for the code and replays it within 30 seconds. <strong>Passkeys</strong> fix this. A passkey is a key pair created by the user's device or password manager through the <strong>WebAuthn</strong> browser API. The server stores only the <strong>public key</strong>. At login, the device signs a random challenge with the private key. The browser ties each credential to the site's origin, so a look-alike domain cannot use it. WebAuthn Level 3 became a W3C Recommendation in 2026, and NIST 800-63B-4 requires phishing-resistant authenticators at its highest level (AAL3). Use a maintained WebAuthn server library rather than writing the checks yourself.</p>
<hr>
<h1 id="Chapter-6-—-Sessions-and-cookies"><a href="#Chapter-6-—-Sessions-and-cookies" class="headerlink" title="Chapter 6 — Sessions and cookies"></a>Chapter 6 — Sessions and cookies</h1>
<p>After a good login, the server must remember the user. The classic way is a <strong>server-side session</strong>. Make a long random session ID (<code>secrets.token_urlsafe(32)</code> gives 256 random bits). Store <code>{session_id: {user, created, last_seen}}</code> on the server, in memory, Redis or a database table. Send only the ID to the browser, in a cookie. On each request, look up the ID. On logout, <strong>delete the server record</strong>: the session is gone at once, even if someone copied the cookie.</p>
<p>The cookie flags matter:</p>
<table>
<thead>
<tr>
<th>Flag</th>
<th>What it does</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>HttpOnly</code></td>
<td>JavaScript cannot read the cookie, so an XSS bug cannot steal it directly.</td>
</tr>
<tr>
<td><code>Secure</code></td>
<td>Sent only over HTTPS. Most browsers and curl allow it on <code>http://localhost</code> for development.</td>
</tr>
<tr>
<td><code>SameSite=Lax</code></td>
<td>Not sent on most cross-site requests (cross-site POSTs, images, iframes), which blocks most CSRF. It is still sent when the user follows a link to your site.</td>
</tr>
<tr>
<td><code>SameSite=Strict</code></td>
<td>Never sent cross-site, not even on links. Safest, but the user looks logged out when arriving from another site.</td>
</tr>
<tr>
<td><code>SameSite=None</code></td>
<td>Always sent. Must be combined with <code>Secure</code>. Only for real cross-site needs.</td>
</tr>
<tr>
<td><code>__Host-</code> name prefix</td>
<td>The browser rejects the cookie unless it has <code>Secure</code> and <code>Path=/</code> and no <code>Domain</code>. This locks it to one host.</td>
</tr>
</tbody>
</table>
<p>Some browsers treat a missing <code>SameSite</code> as <code>Lax</code>, others do not. Always set it yourself.</p>
<p>Two session rules that stop real attacks:</p>
<ul>
<li><strong>Rotate the ID at login.</strong> Never keep a session ID that existed before login. Otherwise an attacker who planted an ID in the victim's browser shares the logged-in session. This attack is called <strong>session fixation</strong>.</li>
<li><strong>Two timeouts.</strong> An idle timeout (for example 30 minutes without activity) and an absolute timeout (for example 8 hours after login).</li>
</ul>

<h1 id="Chapter-8-—-JWT-signed-tokens-without-a-session-store"><a href="#Chapter-8-—-JWT-signed-tokens-without-a-session-store" class="headerlink" title="Chapter 8 — JWT: signed tokens without a session store"></a>Chapter 8 — JWT: signed tokens without a session store</h1>
<p>A <strong>JSON Web Token</strong> (RFC 7519) is three base64url parts joined by dots: <code>header.payload.signature</code>. The payload holds <strong>claims</strong> such as <code>sub</code> (subject, the user), <code>exp</code> (expiry time), <code>iat</code> (issued at), <code>iss</code> (issuer) and <code>aud</code> (audience). The server signs it. Any service with the key can check the signature and trust the claims without a database lookup. That is the whole appeal: it is <strong>stateless</strong>.</p>
<p>The payload is <strong>encoded, not encrypted</strong>. For example, the middle part <code>eyJzdWIiOiJhZGEiLCJyb2xlIjoidXNlciIsImV4cCI6MTc5MDAwMDAwMH0</code> decodes with <code>base64.urlsafe_b64decode(part + &quot;==&quot;)</code> to <code>{&quot;sub&quot;:&quot;ada&quot;,&quot;role&quot;:&quot;user&quot;,&quot;exp&quot;:1790000000}</code>. Anyone can read it, so never put secrets in a JWT payload.</p>
<h2 id="The-revocation-problem"><a href="#The-revocation-problem" class="headerlink" title="The revocation problem"></a>The revocation problem</h2>
<p>Stateless has a price. Once a JWT is issued, it stays valid until <code>exp</code>. Logout, a password change, or &quot;block this account&quot; cannot cancel it, unless you add a denylist, and then you have a server-side store again. The usual answer is <strong>short-lived access tokens</strong> (minutes) plus a long-lived <strong>refresh token</strong> that is tracked server-side, so it <em>can</em> be revoked. With <strong>refresh token rotation</strong>, each use returns a new refresh token and invalidates the old one. If an old one shows up again, revoke the whole chain.</p>
<h2 id="Validate-it-properly-RFC-8725-the-JWT-BCP"><a href="#Validate-it-properly-RFC-8725-the-JWT-BCP" class="headerlink" title="Validate it properly (RFC 8725, the JWT BCP)"></a>Validate it properly (RFC 8725, the JWT BCP)</h2>
<p>Most JWT bugs come from trusting the token's own header. RFC 8725 &quot;JSON Web Token Best Current Practices&quot; (BCP 225, February 2020) lists the traps:</p>
<ul>
<li><strong><code>alg: none</code></strong> — an unsigned token. Some old libraries accepted it if the header asked for it. Your code must decide the allowed algorithms, not the token.</li>
<li><strong>Key confusion</strong> — the server expects RS256 (RSA public key). The attacker sends <code>alg: HS256</code> and signs with the <em>public</em> key as an HMAC secret. A library that picks the algorithm from the header then &quot;verifies&quot; it. Pin one algorithm per key.</li>
<li><strong>Missing <code>aud</code> / <code>iss</code> checks</strong> — a token issued for service A gets accepted by service B.</li>
<li><strong>Weak HMAC secrets</strong> — HS256 secrets can be brute-forced offline. Use at least 256 random bits.</li>
</ul>
<p>With PyJWT (<code>pip install pyjwt</code>), all of this fits in one call:</p>

<h1 id="Chapter-9-—-OAuth-20-and-OpenID-Connect"><a href="#Chapter-9-—-OAuth-20-and-OpenID-Connect" class="headerlink" title="Chapter 9 — OAuth 2.0 and OpenID Connect"></a>Chapter 9 — OAuth 2.0 and OpenID Connect</h1>
<h2 id="What-OAuth-20-is-for"><a href="#What-OAuth-20-is-for" class="headerlink" title="What OAuth 2.0 is for"></a>What OAuth 2.0 is for</h2>
<p>OAuth 2.0 (RFC 6749) is about <strong>delegated authorization</strong>. It answers: &quot;may this app act on my behalf at that API?&quot; For example, a printing site asks to read your photos from a cloud drive, without ever seeing your cloud password. The four roles are the <strong>resource owner</strong> (you), the <strong>client</strong> (the printing site, a mobile app or a single-page app), the <strong>authorization server</strong> (the cloud's login and consent service, which issues tokens) and the <strong>resource server</strong> (the photo API, which accepts access tokens).</p>
<h2 id="The-authorization-code-flow-with-PKCE"><a href="#The-authorization-code-flow-with-PKCE" class="headerlink" title="The authorization code flow with PKCE"></a>The authorization code flow with PKCE</h2>
<p>This is the flow to use for web apps, single-page apps and mobile apps:</p>
<ol>
<li>The client makes a random <strong>code verifier</strong> and its hash, the <strong>code challenge</strong>.</li>
<li>The client sends the browser to the authorization server with <code>response_type=code</code>, <code>client_id</code>, the exact <code>redirect_uri</code>, <code>scope</code>, a random <code>state</code>, and <code>code_challenge</code> + <code>code_challenge_method=S256</code>.</li>
<li>The user logs in there and agrees.</li>
<li>The authorization server redirects back to <code>redirect_uri?code=...&amp;state=...</code>. The client checks that <code>state</code> matches what it sent (this blocks CSRF on the callback).</li>
<li>The client posts the <code>code</code> <strong>plus the original <code>code_verifier</code></strong> to the token endpoint.</li>
<li>The server hashes the verifier, compares it with the challenge from step 2, and returns an <strong>access token</strong> (and maybe a refresh token).</li>
</ol>
<p><img src="/blog/assets/dev/diagram_11_oauth_pkce.svg" alt="Sequence diagram of the OAuth 2.0 authorization code flow with PKCE across the client, the browser, the authorization server and the resource server"></p>
<p>PKCE (RFC 7636) means a stolen <code>code</code> is useless without the verifier, which never left the client. The verifier is 43–128 characters, and <code>code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))</code>:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-comment"># pkce.py</span></span><br><span class="line"><span class="hljs-keyword">import</span> base64, hashlib, secrets</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">b64url</span>(<span class="hljs-params">data: <span class="hljs-built_in">bytes</span></span>) -&gt; <span class="hljs-built_in">str</span>:</span><br><span class="line">    <span class="hljs-keyword">return</span> base64.urlsafe_b64encode(data).rstrip(<span class="hljs-string">b&quot;=&quot;</span>).decode()</span><br><span class="line"> </span><br><span class="line">verifier = b64url(secrets.token_bytes(<span class="hljs-number">32</span>))                   <span class="hljs-comment"># 43 characters</span></span><br><span class="line">challenge = b64url(hashlib.sha256(verifier.encode(<span class="hljs-string">&quot;ascii&quot;</span>)).digest())</span><br><span class="line"><span class="hljs-built_in">print</span>(verifier, challenge)</span><br><span class="line"><span class="hljs-comment"># RFC 7636 Appendix B check, prints E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM</span></span><br><span class="line"><span class="hljs-built_in">print</span>(b64url(hashlib.sha256(<span class="hljs-string">b&quot;dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk&quot;</span>).digest()))</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="The-rules-today-RFC-9700-and-OAuth-21"><a href="#The-rules-today-RFC-9700-and-OAuth-21" class="headerlink" title="The rules today: RFC 9700 and OAuth 2.1"></a>The rules today: RFC 9700 and OAuth 2.1</h2>
<p><strong>RFC 9700, &quot;Best Current Practice for OAuth 2.0 Security&quot;</strong> (BCP 240, January 2025), updates the old advice:</p>
<ul>
<li>Public clients <strong>MUST use PKCE</strong>; it is recommended for confidential clients too.</li>
<li>Do not use the <strong>implicit grant</strong> (<code>response_type=token</code>). Use the code flow.</li>
<li>The <strong>resource owner password credentials grant</strong> &quot;MUST NOT be used&quot;. Apps should never collect the user's password for another service.</li>
<li>Authorization servers <strong>MUST</strong> use <strong>exact string matching</strong> for redirect URIs (with a port exception for localhost in native apps).</li>
<li>Refresh tokens for public clients must be <strong>sender-constrained or rotated</strong>.</li>
<li>Do not put access tokens in URL query strings.</li>
</ul>
<p><strong>OAuth 2.1</strong> gathers these rules into one document. As of September 2026 it is still an <strong>IETF Internet-Draft</strong> (<code>draft-ietf-oauth-v2-1</code>), not an RFC. Treat it as a strong guide, not a final standard.</p>
<h2 id="OpenID-Connect-login-on-top-of-OAuth"><a href="#OpenID-Connect-login-on-top-of-OAuth" class="headerlink" title="OpenID Connect: login on top of OAuth"></a>OpenID Connect: login on top of OAuth</h2>
<p>OAuth alone does not tell the client <em>who</em> the user is. <strong>OpenID Connect (OIDC)</strong> adds that. The client asks for the <code>openid</code> scope and gets an extra <strong>ID token</strong>:</p>
<table>
<thead>
<tr>
<th></th>
<th>ID token</th>
<th>Access token</th>
</tr>
</thead>
<tbody>
<tr>
<td>Defined by</td>
<td>OpenID Connect Core 1.0</td>
<td>OAuth 2.0</td>
</tr>
<tr>
<td>Format</td>
<td>Always a JWT</td>
<td>Opaque string or JWT; the client should not care</td>
</tr>
<tr>
<td>Audience</td>
<td>The <strong>client</strong> (<code>aud</code> = your <code>client_id</code>)</td>
<td>The <strong>API</strong> (resource server)</td>
</tr>
<tr>
<td>Purpose</td>
<td>&quot;Ada logged in at 13:02 via this IdP&quot;</td>
<td>&quot;The bearer may call these APIs with these scopes&quot;</td>
</tr>
<tr>
<td>Send it to APIs?</td>
<td><strong>No</strong></td>
<td>Yes, in <code>Authorization: Bearer ...</code></td>
</tr>
</tbody>
</table>
<p>The client validates the ID token like any JWT (signature from the IdP's published keys, <code>iss</code>, <code>aud</code>, <code>exp</code>) and checks the <code>nonce</code> it sent. Then it usually starts its <strong>own session</strong> (Chapter 6). In practice you use a certified OIDC client library and a hosted or self-hosted IdP, not hand-written flows.</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Spot-the-storage-bug"><a href="#Exercise-1-—-Spot-the-storage-bug" class="headerlink" title="Exercise 1 — Spot the storage bug"></a>Exercise 1 — Spot the storage bug</h2>
<p>A team stores <code>hashlib.sha256(password.encode()).hexdigest()</code>. List two problems and the fix.</p>
<details>
<summary>Solution</summary>
<p>SHA-256 is fast, so a stolen table can be cracked with billions of guesses per second on GPUs. And there is no salt, so equal passwords get equal hashes and precomputed tables work. Fix: use Argon2id through <code>argon2-cffi</code> (<code>PasswordHasher().hash(pw)</code>), which is slow, memory-hard and salts every hash. Migrate old users at their next login: verify with SHA-256 once, then store the Argon2id hash.</p>
</details>
<h2 id="Exercise-2-—-Upgrade-parameters-safely"><a href="#Exercise-2-—-Upgrade-parameters-safely" class="headerlink" title="Exercise 2 — Upgrade parameters safely"></a>Exercise 2 — Upgrade parameters safely</h2>
<p>Your app used <code>PasswordHasher(time_cost=2, memory_cost=19456, parallelism=1)</code>. You now want the library defaults. How do you upgrade existing users without a password reset?</p>
<details>
<summary>Solution</summary>
<p>Switch <code>ph</code> to <code>PasswordHasher()</code>. <code>verify</code> still works on old hashes because the parameters are stored in each hash string. After a successful <code>verify</code>, call <code>ph.check_needs_rehash(stored)</code>. If it is <code>True</code>, save <code>ph.hash(password)</code>. Users upgrade one by one as they log in. This is exactly what <code>check_password</code> does in Chapter 7.</p>
</details>
<h2 id="Exercise-3-—-Fix-the-policy"><a href="#Exercise-3-—-Fix-the-policy" class="headerlink" title="Exercise 3 — Fix the policy"></a>Exercise 3 — Fix the policy</h2>
<p>A login page requires &quot;8+ characters, one uppercase, one digit, one symbol, change every 90 days&quot;. Rewrite it to match NIST SP 800-63B-4 for a site where the password is the only factor.</p>
<details>
<summary>Solution</summary>
<p>Require at least <strong>15</strong> characters (8 is only allowed when the password is part of MFA). Allow at least 64 characters, spaces, Unicode, paste and password managers. Drop the composition rules. Drop the 90-day change; force a change only when there is evidence of compromise. Reject passwords found in a blocklist of breached and common passwords, dictionary words, and the site name or username.</p>
</details>
<h2 id="Exercise-4-—-Why-is-this-JWT-check-wrong"><a href="#Exercise-4-—-Why-is-this-JWT-check-wrong" class="headerlink" title="Exercise 4 — Why is this JWT check wrong?"></a>Exercise 4 — Why is this JWT check wrong?</h2>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="python"><span class="line">header = jwt.get_unverified_header(token)</span><br><span class="line">claims = jwt.decode(token, KEY, algorithms=[header[<span class="hljs-string">&quot;alg&quot;</span>]])</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<p>It lets the attacker choose the algorithm. With <code>alg: none</code>, or <code>HS256</code> signed with a public RSA key, a weak library can accept a forged token. Pin the list in code, for example <code>algorithms=[&quot;RS256&quot;]</code>, and also pass <code>audience=</code> and <code>issuer=</code>. RFC 8725 says libraries must let callers choose the allowed algorithms and must check that the key fits the algorithm.</p>
</details>
<h2 id="Exercise-5-—-Session-fixation"><a href="#Exercise-5-—-Session-fixation" class="headerlink" title="Exercise 5 — Session fixation"></a>Exercise 5 — Session fixation</h2>
<p>In Chapter 7, imagine login did not drop the old ID and instead <em>reused</em> the incoming cookie value as the session ID. Describe the attack this allows.</p>
<details>
<summary>Solution</summary>
<p>An attacker gets a session ID (or picks one) and plants it in the victim's browser, for example through a subdomain that can set cookies. The victim logs in, and the server marks <em>that same ID</em> as logged in. The attacker, who knows the ID, is now logged in as the victim. Always issue a fresh random ID at login and drop the old one.</p>
</details>
