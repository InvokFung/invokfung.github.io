<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Ingress</strong> — a built-in API object describing HTTP/HTTPS routing rules (host, path, backend Service, TLS).</li>
<li><strong>Ingress controller</strong> — the component that actually implements those rules. Kubernetes ships the API, not an implementation.</li>
<li><strong>Gateway API</strong> — the newer, role-oriented, extensible routing API that supersedes Ingress. Installed as CRDs, not built in.</li>
<li><strong>TLS termination</strong> — decrypting HTTPS at the edge so backends receive plain HTTP.</li>
<li><strong>ACME</strong> — the protocol (used by Let's Encrypt) for automated certificate issuance.</li>
</ul>
<h2 id="Ingress"><a href="#Ingress" class="headerlink" title="Ingress"></a>Ingress</h2>
<p>A <code>LoadBalancer</code> Service per application means one cloud load balancer per application, each with its own IP, its own bill and its own certificate. Ingress collapses that into <strong>one</strong> entry point that routes by hostname and path.</p>

<p>The controller watches Ingress objects and reconfigures its own proxy. Note what the API does <strong>not</strong> cover: rate limiting, header rewriting, request mirroring, timeouts, retries, authentication. Every controller exposes those through <strong>vendor-specific annotations</strong>, which is precisely why Ingress manifests are not portable between controllers and why the Gateway API exists.</p>

<p>The practical reading: <strong>new clusters should start on the Gateway API</strong>; existing Ingress deployments keep working and should be migrated deliberately, prioritising any cluster still running ingress-nginx. <h1 id="Chapter-2-—-East-west-traffic-CNI-NetworkPolicy-and-meshes"><a href="#Chapter-2-—-East-west-traffic-CNI-NetworkPolicy-and-meshes" class="headerlink" title="Chapter 2 — East-west traffic: CNI, NetworkPolicy and meshes"></a>Chapter 2 — East-west traffic: CNI, NetworkPolicy and meshes</h1>
<h2 id="The-CNI-model"><a href="#The-CNI-model" class="headerlink" title="The CNI model"></a>The CNI model</h2>
<p>Kubernetes does not implement Pod networking. It defines a contract — <strong>CNI (Container Network Interface)</strong> — and requires that every Pod gets its own IP, that any Pod can reach any other Pod without NAT, and that nodes can reach all Pods. A plugin (Calico, Cilium, Flannel, AWS VPC CNI, Azure CNI, Weave) fulfils it, with very different implementations: overlay tunnels (VXLAN, Geneve), native routing (BGP), or cloud-native IP allocation from the VPC.</p>
<p>Two consequences: the default posture is <strong>completely flat</strong> — every Pod in every namespace can reach every other Pod, on every port — and <strong>NetworkPolicy is enforced by the CNI plugin, not by Kubernetes</strong>. A NetworkPolicy applied on a cluster whose plugin does not implement it is silently accepted and does nothing at all. Verify enforcement before you rely on it.</p>
<h2 id="Default-deny-then-open-what-is-needed"><a href="#Default-deny-then-open-what-is-needed" class="headerlink" title="Default-deny, then open what is needed"></a>Default-deny, then open what is needed</h2>

<p>Rules to internalise:</p>
<ul>
<li>Policies are <strong>additive whitelists</strong>. A Pod selected by <em>any</em> policy denies everything not explicitly allowed by <em>some</em> policy that selects it. A Pod selected by <em>no</em> policy allows everything.</li>
<li><code>podSelector: {}</code> with both <code>policyTypes</code> and no rules is the idiomatic default-deny.</li>
<li><strong>Always allow DNS egress explicitly.</strong> Forgetting it is the single most common NetworkPolicy incident: name resolution fails, every outbound call breaks, and the errors point everywhere except the network policy.</li>
<li>Policies are namespace-scoped and select by label. Cross-namespace rules need <code>namespaceSelector</code>; the automatic <code>kubernetes.io/metadata.name</code> label makes that convenient.</li>
<li>Standard NetworkPolicy is <strong>L3/L4 only</strong> — IPs, ports, protocols. It cannot express &quot;GET but not DELETE&quot; or &quot;only with a valid identity&quot;. CNI-specific CRDs (Cilium's <code>CiliumNetworkPolicy</code>, Calico's <code>NetworkPolicy</code>) add L7 rules, and the emerging <code>AdminNetworkPolicy</code> API adds cluster-wide rules that individual namespaces cannot override.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> roll out default-deny in <em>audit</em> mode first if your CNI supports it, or apply the deny policy to one low-risk namespace and watch the errors. Applying default-deny to a busy production namespace on a Friday is a well-documented way to spend a weekend.</p>
</blockquote>
<h2 id="Service-mesh-honestly"><a href="#Service-mesh-honestly" class="headerlink" title="Service mesh, honestly"></a>Service mesh, honestly</h2>
<p>A service mesh (Istio, Linkerd, Cilium's mesh mode) puts a proxy in the path of every Pod-to-Pod call — historically a sidecar, increasingly a per-node or ambient component. In exchange for that you get <strong>automatic mTLS between all workloads</strong>, <strong>L7 traffic control</strong> (retries, timeouts, circuit breaking, canary splitting by header or weight), <strong>uniform golden-signal telemetry</strong> for every service without touching application code, and <strong>identity-based authorisation policy</strong> rather than IP-based.</p>
<p>The costs are real and routinely understated: an extra network hop and a few milliseconds on every call; noticeable CPU and memory per Pod for sidecar deployments; a substantial new control plane to upgrade in lockstep with the cluster; failure modes that are genuinely hard to debug because the proxy is now between you and every symptom; and a body of concepts (VirtualService, DestinationRule, PeerAuthentication, or their equivalents) the whole team must learn. <strong>Most clusters do not need one.</strong> If you have a handful of services, NetworkPolicy plus TLS at the ingress plus a decent HTTP client library covers the same ground for a fraction of the operational cost. Reach for a mesh when you have a real, specific driver — a compliance requirement for encryption in transit everywhere, dozens of teams needing uniform traffic policy, or progressive delivery you cannot express any other way — and when you have someone who will own it. Linkerd is the smaller, simpler option; Istio ambient mode and Cilium remove the per-Pod sidecar cost; a mesh chosen because it was on a conference slide is a liability.</p>

<h2 id="Prometheus-and-kube-state-metrics"><a href="#Prometheus-and-kube-state-metrics" class="headerlink" title="Prometheus and kube-state-metrics"></a>Prometheus and kube-state-metrics</h2>
<p>The <code>kube-prometheus-stack</code> chart is the conventional starting point. It brings four things that are easy to confuse:</p>
<ul>
<li><strong>Prometheus</strong> — scrapes and stores time series; discovers targets from the Kubernetes API.</li>
<li><strong>node-exporter</strong> (DaemonSet) — <em>node</em> metrics: CPU, memory, disk, filesystem, network.</li>
<li><strong>cAdvisor</strong> (inside the kubelet) — <em>container</em> resource metrics: <code>container_cpu_usage_seconds_total</code>, <code>container_memory_working_set_bytes</code>.</li>
<li><strong>kube-state-metrics</strong> — <em>object state</em> metrics generated from the API server: <code>kube_deployment_status_replicas_available</code>, <code>kube_pod_container_status_restarts_total</code>, <code>kube_pod_status_phase</code>. Not resource usage — the <em>declared and observed state of objects</em>.</li>
</ul>
<p>That last distinction matters constantly: &quot;is the container using too much memory&quot; is cAdvisor; &quot;have the desired replicas been available for ten minutes&quot; is kube-state-metrics. Note also that <strong>metrics-server</strong> is a separate, minimal component that exists only to serve <code>kubectl top</code> and the HPA — it is not a monitoring system and does not store history.</p>
<h2 id="Alert-on-symptoms-not-causes"><a href="#Alert-on-symptoms-not-causes" class="headerlink" title="Alert on symptoms, not causes"></a>Alert on symptoms, not causes</h2>
<p>The discipline that separates a usable on-call rotation from an ignored one: <strong>page on what users experience; make everything else a dashboard or a ticket.</strong></p>
<p>Cause-based alerts (&quot;CPU above 80 %&quot;, &quot;a Pod restarted&quot;, &quot;disk 70 % full&quot;, &quot;replica count below desired&quot;) fire constantly, are usually harmless, and train people to ignore the pager. Symptom-based alerts describe a violated expectation:</p>
<ul>
<li>Error rate on <code>shop.example.com</code> exceeded 1 % of requests over 5 minutes.</li>
<li>p99 latency for checkout exceeded 2 s over 10 minutes.</li>
<li>The nightly export CronJob has not produced a successful Job in 26 hours.</li>
<li>The service is consuming its error budget fast enough to exhaust the month's allowance in under a day (multi-window, multi-burn-rate SLO alerting).</li>
</ul>
<p>Useful frameworks: <strong>RED</strong> (Rate, Errors, Duration) for request-driven services, <strong>USE</strong> (Utilisation, Saturation, Errors) for resources, and the four golden signals (latency, traffic, errors, saturation). A small number of genuinely paging alerts beats a hundred noisy ones.</p>
<p>A short list of Kubernetes-specific conditions genuinely worth paging on: a Deployment with zero available replicas; <code>CrashLoopBackOff</code> persisting beyond a few minutes; Pods <code>Pending</code> for more than N minutes (capacity); a node <code>NotReady</code> beyond the eviction timeout; PersistentVolume nearly full; certificate expiring within a week; API server error rate or latency elevated.</p>
<h2 id="Logging-when-Pods-are-ephemeral"><a href="#Logging-when-Pods-are-ephemeral" class="headerlink" title="Logging when Pods are ephemeral"></a>Logging when Pods are ephemeral</h2>
<p><code>kubectl logs</code> reads from the node's log files for a <em>currently existing</em> Pod. Delete the Pod — as every rollout, eviction and node scale-down does — and the logs are gone. <code>--previous</code> reaches exactly one container generation back, and rotation discards the rest. That is not a logging strategy.</p>
<p>The standard architecture is a <strong>node-level agent</strong> (Fluent Bit or Vector as a DaemonSet) that tails <code>/var/log/containers/*.log</code>, enriches each line with Kubernetes metadata (namespace, Pod, container, labels) from the API, and ships it to a store — Loki, OpenSearch, or a managed service. Requirements that pay for themselves:</p>
<ul>
<li><strong>Log to stdout/stderr as structured JSON.</strong> Writing to a file inside the container means the agent never sees it. Unstructured text means you cannot query by field.</li>
<li><strong>Carry the trace ID</strong> in every line. It is what joins the three signals.</li>
<li><strong>Set retention by value, not by default.</strong> Logs are usually the largest line in an observability bill; 7 days hot plus 90 days in cheap object storage is a common shape.</li>
<li><strong>Do not log secrets or personal data.</strong> Once shipped, it is in someone else's index and in their backups.</li>
</ul>
<h2 id="OpenTelemetry"><a href="#OpenTelemetry" class="headerlink" title="OpenTelemetry"></a>OpenTelemetry</h2>
<p>OpenTelemetry is the vendor-neutral standard for producing and shipping all three signals: one set of APIs and SDKs, one wire protocol (OTLP), and the <strong>OpenTelemetry Collector</strong> as a pipeline of receivers, processors and exporters. On Kubernetes it is typically deployed twice — as a DaemonSet for node-local collection and enrichment, and as a Deployment (gateway) for aggregation, sampling and fan-out to backends. The OpenTelemetry Operator adds auto-instrumentation by injecting language agents into Pods via an annotation, which gets you traces from a Java, Python, Node or .NET service without editing its code.</p>
<p>The reason to standardise on it is portability: instrument once, and changing backends becomes a Collector configuration change instead of a re-instrumentation project. For a full worked treatment of OpenTelemetry — spans, context propagation, sampling strategy, collector configuration and correlating traces with database telemetry — see <code>content/posts/mongo_26_opentelemetry_observability.md</code>.</p>

<h1 id="Chapter-4-—-Security-RBAC-Pod-Security-and-admission-control"><a href="#Chapter-4-—-Security-RBAC-Pod-Security-and-admission-control" class="headerlink" title="Chapter 4 — Security: RBAC, Pod Security and admission control"></a>Chapter 4 — Security: RBAC, Pod Security and admission control</h1>
<h2 id="RBAC"><a href="#RBAC" class="headerlink" title="RBAC"></a>RBAC</h2>
<p>Four object types, one simple model.</p>
<ul>
<li><strong>Role</strong> — a set of permissions, <strong>namespaced</strong>.</li>
<li><strong>ClusterRole</strong> — the same, but <strong>cluster-scoped</strong>; also the only way to grant access to cluster-scoped resources (nodes, PVs, CRDs) or to non-resource URLs.</li>
<li><strong>RoleBinding</strong> — grants a Role <em>or a ClusterRole</em> to subjects <strong>within one namespace</strong>.</li>
<li><strong>ClusterRoleBinding</strong> — grants a ClusterRole across the whole cluster.</li>
</ul>
<p>Binding a ClusterRole with a RoleBinding is the most useful idiom: define the permission set once, grant it namespace by namespace.</p>

<p>Verbs: <code>get</code>, <code>list</code>, <code>watch</code>, <code>create</code>, <code>update</code>, <code>patch</code>, <code>delete</code>, <code>deletecollection</code>, plus <code>impersonate</code>, <code>bind</code> and <code>escalate</code>. RBAC is <strong>purely additive</strong> — there is no deny rule. If you need denial, that is admission control's job.</p>
<p>Three permissions deserve special caution, because each is effectively cluster-admin in disguise: <code>create pods</code> in a namespace whose ServiceAccounts are privileged (you can mount any Secret and run as any identity); <code>escalate</code> or <code>bind</code> on roles (you can grant yourself more); and <code>get secrets</code> at cluster scope (you can read every credential in the cluster).</p>
<h2 id="ServiceAccounts-and-their-tokens"><a href="#ServiceAccounts-and-their-tokens" class="headerlink" title="ServiceAccounts and their tokens"></a>ServiceAccounts and their tokens</h2>
<p>Every Pod runs as a <strong>ServiceAccount</strong> — <code>default</code> in its namespace unless told otherwise, and <code>default</code> should have no permissions at all. Give each workload its own:</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">spec:</span></span><br><span class="line">  <span class="hljs-attr">serviceAccountName:</span> <span class="hljs-string">api</span></span><br><span class="line">  <span class="hljs-attr">automountServiceAccountToken:</span> <span class="hljs-literal">false</span>    <span class="hljs-comment"># if the workload never calls the API, do not mount one</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Token handling changed and the modern behaviour matters. Since Kubernetes <strong>1.24</strong>, creating a ServiceAccount no longer auto-creates a non-expiring Secret token. Pods receive a <strong>projected, time-bound, audience-scoped token</strong> that the kubelet rotates automatically. For an out-of-cluster consumer, mint one explicitly with <code>kubectl create token api --duration=1h</code> rather than creating a long-lived Secret. Long-lived static tokens are exactly the credential that ends up in a CI variable and never gets rotated.</p>
<p>On managed clusters, bind ServiceAccounts to cloud identity (IRSA on EKS, Workload Identity on GKE and AKS) so Pods obtain short-lived cloud credentials without any stored secret.</p>

<p>A concrete, repeatable procedure:</p>

<h2 id="Pod-Security-Admission"><a href="#Pod-Security-Admission" class="headerlink" title="Pod Security Admission"></a>Pod Security Admission</h2>
<p>PodSecurityPolicy was deprecated in 1.21 and <strong>removed in Kubernetes 1.25</strong>. Its replacement, <strong>Pod Security Admission</strong>, is a built-in admission controller — stable since 1.25 — configured with namespace labels rather than cluster-wide policy objects.</p>
<p>Three levels: <code>privileged</code> (no restrictions), <code>baseline</code> (blocks known privilege escalations: host namespaces, privileged containers, most host paths), and <code>restricted</code> (baseline plus hardening: run as non-root, drop all capabilities, seccomp <code>RuntimeDefault</code>, no privilege escalation, restricted volume types). Three modes: <code>enforce</code> (reject), <code>audit</code> (record in the audit log), <code>warn</code> (return a warning to the client).</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">apiVersion:</span> <span class="hljs-string">v1</span></span><br><span class="line"><span class="hljs-attr">kind:</span> <span class="hljs-string">Namespace</span></span><br><span class="line"><span class="hljs-attr">metadata:</span></span><br><span class="line">  <span class="hljs-attr">name:</span> <span class="hljs-string">shop</span></span><br><span class="line">  <span class="hljs-attr">labels:</span></span><br><span class="line">    <span class="hljs-attr">pod-security.kubernetes.io/enforce:</span> <span class="hljs-string">baseline</span></span><br><span class="line">    <span class="hljs-attr">pod-security.kubernetes.io/enforce-version:</span> <span class="hljs-string">v1.33</span></span><br><span class="line">    <span class="hljs-attr">pod-security.kubernetes.io/audit:</span> <span class="hljs-string">restricted</span>     <span class="hljs-comment"># see what would break</span></span><br><span class="line">    <span class="hljs-attr">pod-security.kubernetes.io/warn:</span> <span class="hljs-string">restricted</span>      <span class="hljs-comment"># tell authors now</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The migration path is exactly that shape: enforce <code>baseline</code>, audit and warn on <code>restricted</code>, fix what the warnings reveal, then raise enforcement. Pin <code>enforce-version</code> so a cluster upgrade cannot tighten policy underneath you unannounced.</p>
<p>PSA is deliberately limited — it checks Pod security context fields and nothing else. It cannot say &quot;images must come from our registry&quot; or &quot;every Deployment must set resource requests&quot;. That needs a policy engine.</p>
<h2 id="Admission-control-and-policy-engines"><a href="#Admission-control-and-policy-engines" class="headerlink" title="Admission control and policy engines"></a>Admission control and policy engines</h2>
<p>Every request to the API server passes through authentication, then authorisation (RBAC), then <strong>admission</strong>: first mutating admission (which can modify the object — inject sidecars, set defaults), then validating admission (which can only accept or reject), then schema validation, then persistence.</p>
<p>You extend it three ways:</p>
<ul>
<li><strong>MutatingAdmissionWebhook</strong> — an HTTPS service you run that patches objects. Powerful, and a liability: if it is down and <code>failurePolicy: Fail</code>, the API server rejects the requests it intercepts. Always scope webhooks narrowly with <code>namespaceSelector</code> and <code>objectSelector</code>, and exclude <code>kube-system</code>.</li>
<li><strong>ValidatingAdmissionPolicy</strong> — in-tree validation expressed in CEL, evaluated by the API server itself, GA since 1.30. No webhook to run or fail. The right first choice for simple rules.</li>
<li><strong>Policy engines</strong> — <strong>Kyverno</strong> (policies are Kubernetes resources written in YAML; validate, mutate, generate and verify image signatures; a gentle learning curve) or <strong>OPA Gatekeeper</strong> (constraint templates written in Rego; more expressive, steeper curve, shared with non-Kubernetes OPA deployments).</li>
</ul>

<h1 id="Chapter-5-—-Packaging-and-delivery"><a href="#Chapter-5-—-Packaging-and-delivery" class="headerlink" title="Chapter 5 — Packaging and delivery"></a>Chapter 5 — Packaging and delivery</h1>
<h2 id="Helm"><a href="#Helm" class="headerlink" title="Helm"></a>Helm</h2>
<p>Helm is a package manager: a <strong>chart</strong> is a directory of Go-templated manifests plus a <code>values.yaml</code> of defaults; installing it produces a <strong>release</strong> whose state Helm stores in a Secret in the cluster.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="bash"><span class="line">helm repo add bitnami https://charts.bitnami.com/bitnami</span><br><span class="line">helm install shop ./charts/shop -n shop --values values-prod.yaml</span><br><span class="line">helm upgrade shop ./charts/shop -n shop --values values-prod.yaml --atomic --<span class="hljs-built_in">timeout</span> 5m</span><br><span class="line">helm template shop ./charts/shop --values values-prod.yaml   <span class="hljs-comment"># render locally, no cluster</span></span><br><span class="line">helm diff upgrade shop ./charts/shop                          <span class="hljs-comment"># via the helm-diff plugin</span></span><br><span class="line">helm rollback shop 3</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Helm's strengths are real: one command installs a complex third-party system, versioned and parameterised; conditionals and loops express genuine variation; the ecosystem of charts is enormous.</p>
<p>The sharp edges are equally real and worth stating before you commit:</p>
<ul>
<li><strong>It is text templating over YAML.</strong> Indentation is your problem; <code>nindent</code> and <code>toYaml</code> are load-bearing; a template that produces valid text can produce invalid YAML. Error messages point at rendered lines you never wrote.</li>
<li><strong>Charts become unreadable.</strong> A generic chart with forty conditionals serving five environments is harder to reason about than five explicit manifests.</li>
<li><strong>Release state lives in the cluster</strong>, not in Git. Two operators, two laptops, two versions of the chart, and the state is whatever the last <code>helm upgrade</code> wrote.</li>
<li><strong><code>--atomic</code> is not optional.</strong> Without it a failed upgrade leaves the release half-applied. Also set <code>--timeout</code> deliberately.</li>
<li><strong>CRDs in <code>crds/</code> are installed but never upgraded or deleted</strong> by Helm. Chart upgrades that change a CRD require manual work; this surprises everyone once.</li>
<li><strong>Values sprawl.</strong> Deeply nested values files across environments drift, and nothing type-checks them. Schema-validate with <code>values.schema.json</code>.</li>
</ul>

<h2 id="GitOps"><a href="#GitOps" class="headerlink" title="GitOps"></a>GitOps</h2>
<p>GitOps inverts the direction of deployment. Instead of CI pushing to the cluster with credentials, an <strong>agent inside the cluster pulls</strong> the desired state from Git and reconciles continuously. Git is the source of truth; the cluster converges on it.</p>
<p><strong>Argo CD</strong> models this with an <code>Application</code> CRD, a strong UI, sync waves and hooks for ordering, and an &quot;app of apps&quot; pattern for managing many. <strong>Flux</strong> is a set of focused controllers (source, kustomize, helm, image automation, notification) driven entirely by CRDs, with no UI of its own. Both do the same job well; Argo CD suits teams who want the dashboard, Flux suits teams who want everything in the API.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span <p>What you actually gain:</p>
<ul>
<li><strong>Drift detection and correction.</strong> <code>selfHeal</code> means a manual <code>kubectl edit</code> is reverted within seconds. The cluster cannot silently diverge from the repository.</li>
<li><strong>The audit trail is the Git history.</strong> Who changed what, when, reviewed by whom, and how to revert — for free, in a system everyone already knows.</li>
<li><strong>Rollback is <code>git revert</code>.</strong> No special tooling, no remembering which Helm revision was good.</li>
<li><strong>Disaster recovery becomes re-pointing an agent</strong> at the repository rather than reconstructing state from memory.</li>
</ul>
<p>And the consequence that matters most: <strong>human access to the cluster should shrink once GitOps is in place.</strong> If every change arrives through a reviewed pull request, engineers do not need <code>apply</code>, <code>edit</code> or <code>delete</code> in production. Reduce them to read plus <code>logs</code>, <code>port-forward</code> and <code>exec</code> where justified, with break-glass elevation that is time-bound and alerted on. This is the point at which the RBAC work in Chapter 4 becomes genuinely easy — most people simply do not need write access any more.</p>
<p>Two caveats worth planning for: secrets still cannot be committed in plaintext, so pair GitOps with Sealed Secrets, SOPS, or the External Secrets Operator (Post 05); and image tags in Git must be updated by something — a CI step that commits the new tag, or an image-automation controller — otherwise &quot;GitOps&quot; quietly becomes &quot;someone edits the tag by hand&quot;.</p>

<h1 id="Chapter-6-—-Managed-Kubernetes-and-cost-control"><a href="#Chapter-6-—-Managed-Kubernetes-and-cost-control" class="headerlink" title="Chapter 6 — Managed Kubernetes and cost control"></a>Chapter 6 — Managed Kubernetes and cost control</h1>
<h2 id="The-managed-offerings"><a href="#The-managed-offerings" class="headerlink" title="The managed offerings"></a>The managed offerings</h2>
<p>EKS (AWS), GKE (Google) and AKS (Azure) all run and upgrade the control plane, manage etcd and its backups, and integrate with the cloud's IAM, load balancers and storage. What differs is the amount of remaining work: GKE Autopilot removes node management almost entirely; EKS gives you the most control and the most assembly; AKS sits between them. All charge for the control plane on a per-cluster-hour basis (with a free tier on some), and all charge normally for the worker nodes, load balancers, storage and data transfer — which is where the money actually goes. Check current pricing pages rather than trusting any figure quoted in a blog post, including this one.</p>
<p>The genuinely important decisions are the same everywhere: how many clusters (each has a control-plane cost and an operational cost — resist one per team until you have a reason), what your upgrade cadence is (Kubernetes releases roughly three times a year and support windows are finite), and whether your workloads can tolerate the node churn that spot instances and consolidation require.</p>

<h2 id="Exercise-4-—-Debug-a-shell-less-Pod"><a href="#Exercise-4-—-Debug-a-shell-less-Pod" class="headerlink" title="Exercise 4 — Debug a shell-less Pod"></a>Exercise 4 — Debug a shell-less Pod</h2>
<p>Build a distroless image with no shell that fails a readiness probe. Diagnose it end to end using only <code>describe</code>, <code>events</code>, <code>logs --previous</code>, an ephemeral debug container and <code>port-forward</code>. Write down which step actually revealed the cause.</p>
<h2 id="Exercise-5-—-Policy-in-audit-then-enforce"><a href="#Exercise-5-—-Policy-in-audit-then-enforce" class="headerlink" title="Exercise 5 — Policy in audit, then enforce"></a>Exercise 5 — Policy in audit, then enforce</h2>
<p>Install Kyverno. Write a policy requiring CPU and memory requests on every Pod, in <code>Audit</code> mode. Count the violations in your cluster. Fix them, switch to <code>Enforce</code>, and confirm a non-compliant Pod is now rejected with a readable message.</p>
<h2 id="Exercise-6-—-Helm-and-Kustomize-same-result"><a href="#Exercise-6-—-Helm-and-Kustomize-same-result" class="headerlink" title="Exercise 6 — Helm and Kustomize, same result"></a>Exercise 6 — Helm and Kustomize, same result</h2>
<p>Package one application twice: once as a Helm chart with staging and prod values, once as a Kustomize base with two overlays. Render both with <code>helm template</code> and <code>kubectl kustomize</code>, diff the outputs, and argue which you would choose here and why.</p>
<h2 id="Exercise-7-—-GitOps-with-self-heal"><a href="#Exercise-7-—-GitOps-with-self-heal" class="headerlink" title="Exercise 7 — GitOps with self-heal"></a>Exercise 7 — GitOps with self-heal</h2>
<p>Install Argo CD, point an Application at your Kustomize overlay with <code>prune</code> and <code>selfHeal</code> enabled, and confirm it syncs. Then <code>kubectl scale</code> the Deployment by hand and time how long the change survives. Finally, <code>git revert</code> a change and confirm the cluster follows.</p>

<h1 id="Course-base-complete-—-whats-next"><a href="#Course-base-complete-—-whats-next" class="headerlink" title="Course base complete — what's next"></a>Course base complete — what's next</h1>
<p>That is the base course. Across eight posts you have gone from a process isolated by namespaces and cgroups on a single host to a multi-node platform with declarative delivery: <strong>00-03</strong> covered what a container actually is, how images are built and layered, networking and volumes and Compose, and image supply-chain security; <strong>04</strong> the reconciliation model, cluster components, Pods, Deployments, Services and DNS; <strong>05</strong> configuration and secrets, the storage stack from Volume to CSI, StatefulSets, DaemonSets, Jobs and CronJobs; <strong>06</strong> scheduling and placement, requests versus limits, QoS and eviction, probes, rollouts, disruption budgets, graceful shutdown and autoscaling; and <strong>07</strong> ingress and the Gateway API, NetworkPolicy, observability, RBAC and admission control, Helm and Kustomize, GitOps and cost.</p>
<p>That is enough to run production services on Kubernetes competently and to read the documentation for anything not covered here without getting lost. The most valuable next step is not another post — it is to operate something real, break it in a non-production cluster on purpose, and practise the failure drills in the exercises until they are boring.</p>
