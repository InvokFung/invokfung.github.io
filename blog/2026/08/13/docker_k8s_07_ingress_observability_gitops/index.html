Containers Course — 07 · Ingress, Observability, RBAC and GitOps

Created2026-08-13|Updated2026-08-13|Containers > Kubernetes
|Post View:

The workloads run, they are scheduled sensibly, and they survive a rollout. What remains is everything around them: how external traffic reaches the cluster, how Pods are prevented from talking to each other, how you find out what is wrong at three in the morning, who is allowed to do what, and how manifests get from a Git repository into a cluster without a human running kubectl apply from a laptop. This is the last post of the base course, and it is the one that turns a working cluster into an operable platform.

Series map: 00 Containers from First Principles → 01 Images and Dockerfiles → 02 Networking, Volumes and Compose → 03 Registries, Supply Chain and Security → 04 Kubernetes Architecture and Core Objects → 05 Config, Storage and Stateful Workloads → 06 Scheduling, Resources, Probes and Rollouts → 07 Ingress, Observability, RBAC and GitOps (this post — final base post).

Learning Outcome

  • Route external HTTP traffic, terminate TLS, and automate certificates with cert-manager.
  • State the current status of the Gateway API and decide whether to start there instead of Ingress.
  • Write a default-deny NetworkPolicy, and judge honestly whether a service mesh is worth its cost.
  • Assemble the metrics/logs/traces triad on Kubernetes and alert on symptoms rather than causes.
  • Debug a broken Pod with describe, previous logs, events and ephemeral debug containers.
  • Design least-privilege RBAC, apply Pod Security Admission, and enforce policy with an admission controller.
  • Choose between Helm and Kustomize, run delivery with Argo CD or Flux, and control managed-cluster cost.

Chapter 1 — Getting traffic in

Terminology

  • Ingress — a built-in API object describing HTTP/HTTPS routing rules (host, path, backend Service, TLS).
  • Ingress controller — the component that actually implements those rules. Kubernetes ships the API, not an implementation.
  • Gateway API — the newer, role-oriented, extensible routing API that supersedes Ingress. Installed as CRDs, not built in.
  • TLS termination — decrypting HTTPS at the edge so backends receive plain HTTP.
  • ACME — the protocol (used by Let's Encrypt) for automated certificate issuance.

Ingress

A LoadBalancer Service per application means one cloud load balancer per application, each with its own IP, its own bill and its own certificate. Ingress collapses that into one entry point that routes by hostname and path.

The controller watches Ingress objects and reconfigures its own proxy. Note what the API does not cover: rate limiting, header rewriting, request mirroring, timeouts, retries, authentication. Every controller exposes those through vendor-specific annotations, which is precisely why Ingress manifests are not portable between controllers and why the Gateway API exists.

The ingress controller landscape, as of 2026

This changed materially and you need the current picture. The long-time default, ingress-nginx, was retired in March 2026: maintenance ceased, the repository was archived, and the planned successor project (InGate) was abandoned before reaching maturity. The Kubernetes SIG Network and Security Response Committee guidance is to migrate to the Gateway API or to another actively maintained controller.

Option Notes
Gateway API with a conformant implementation (Envoy Gateway, Traefik, Istio, Cilium, kgateway, cloud-native gateways) the recommended direction for new clusters
Traefik actively maintained, supports both Ingress and Gateway API, good developer ergonomics
HAProxy / F5 NGINX (commercial) / Envoy-based controllers maintained Ingress implementations if you must stay on the Ingress API
Cloud-native — AWS Load Balancer Controller, GKE Ingress, AGIC provisions the cloud's own L7 load balancer; least to operate, most vendor-coupled
ingress-nginx retired — running it means running unmaintained, unpatched edge software

If you are on ingress-nginx today, treat migration as a scheduled project, not an emergency: inventory your annotations first (that is where the work is), then use the ingress2gateway conversion tool as a starting point and review everything it emits.

TLS with cert-manager

cert-manager is a controller that turns a certificate request into a Kubernetes Secret and keeps it renewed.

With the cert-manager.io/cluster-issuer annotation on an Ingress, cert-manager notices the tls block, solves the ACME challenge, writes shop-tls, and renews it automatically before expiry.

Common pitfall: developing against letsencrypt-prod and burning through Let's Encrypt's rate limits in an afternoon. Use the ACME staging endpoint until the whole chain works, then switch. The staging certificate will not validate in a browser — that is the point.

The Gateway API

Gateway API replaces one overloaded object with a set of role-separated ones:

Resource Owned by Purpose
GatewayClass infrastructure provider which implementation, cluster-scoped
Gateway platform / cluster operator a listener: ports, protocols, TLS, which namespaces may attach
HTTPRoute / GRPCRoute / TLSRoute / TCPRoute application team the routing rules themselves

Current status, stated plainly. Gateway API is a set of CRDs versioned independently of Kubernetes and installed separately. Its Standard (GA) channel has carried GatewayClass, Gateway and HTTPRoute since v1.0 in late 2023, with GRPCRoute following, and v1.5 (early 2026) promoted a further six features from Experimental to Standard. Several conformant implementations exist. The Ingress API remains GA and supported but is feature-frozen — all active development happens in Gateway API. Meanwhile the most widely deployed Ingress controller has been retired.

The practical reading: new clusters should start on the Gateway API; existing Ingress deployments keep working and should be migrated deliberately, prioritising any cluster still running ingress-nginx. Check the conformance report for your chosen implementation rather than assuming a feature is available — extended features are genuinely optional.

Chapter 2 — East-west traffic: CNI, NetworkPolicy and meshes

The CNI model

Kubernetes does not implement Pod networking. It defines a contract — CNI (Container Network Interface) — and requires that every Pod gets its own IP, that any Pod can reach any other Pod without NAT, and that nodes can reach all Pods. A plugin (Calico, Cilium, Flannel, AWS VPC CNI, Azure CNI, Weave) fulfils it, with very different implementations: overlay tunnels (VXLAN, Geneve), native routing (BGP), or cloud-native IP allocation from the VPC.

Two consequences: the default posture is completely flat — every Pod in every namespace can reach every other Pod, on every port — and NetworkPolicy is enforced by the CNI plugin, not by Kubernetes. A NetworkPolicy applied on a cluster whose plugin does not implement it is silently accepted and does nothing at all. Verify enforcement before you rely on it.

Default-deny, then open what is needed

Rules to internalise:

  • Policies are additive whitelists. A Pod selected by any policy denies everything not explicitly allowed by some policy that selects it. A Pod selected by no policy allows everything.
  • podSelector: {} with both policyTypes and no rules is the idiomatic default-deny.
  • Always allow DNS egress explicitly. Forgetting it is the single most common NetworkPolicy incident: name resolution fails, every outbound call breaks, and the errors point everywhere except the network policy.
  • Policies are namespace-scoped and select by label. Cross-namespace rules need namespaceSelector; the automatic kubernetes.io/metadata.name label makes that convenient.
  • Standard NetworkPolicy is L3/L4 only — IPs, ports, protocols. It cannot express "GET but not DELETE" or "only with a valid identity". CNI-specific CRDs (Cilium's CiliumNetworkPolicy, Calico's NetworkPolicy) add L7 rules, and the emerging AdminNetworkPolicy API adds cluster-wide rules that individual namespaces cannot override.

Trick: roll out default-deny in audit mode first if your CNI supports it, or apply the deny policy to one low-risk namespace and watch the errors. Applying default-deny to a busy production namespace on a Friday is a well-documented way to spend a weekend.

Service mesh, honestly

A service mesh (Istio, Linkerd, Cilium's mesh mode) puts a proxy in the path of every Pod-to-Pod call — historically a sidecar, increasingly a per-node or ambient component. In exchange for that you get automatic mTLS between all workloads, L7 traffic control (retries, timeouts, circuit breaking, canary splitting by header or weight), uniform golden-signal telemetry for every service without touching application code, and identity-based authorisation policy rather than IP-based.

The costs are real and routinely understated: an extra network hop and a few milliseconds on every call; noticeable CPU and memory per Pod for sidecar deployments; a substantial new control plane to upgrade in lockstep with the cluster; failure modes that are genuinely hard to debug because the proxy is now between you and every symptom; and a body of concepts (VirtualService, DestinationRule, PeerAuthentication, or their equivalents) the whole team must learn. Most clusters do not need one. If you have a handful of services, NetworkPolicy plus TLS at the ingress plus a decent HTTP client library covers the same ground for a fraction of the operational cost. Reach for a mesh when you have a real, specific driver — a compliance requirement for encryption in transit everywhere, dozens of teams needing uniform traffic policy, or progressive delivery you cannot express any other way — and when you have someone who will own it. Linkerd is the smaller, simpler option; Istio ambient mode and Cilium remove the per-Pod sidecar cost; a mesh chosen because it was on a conference slide is a liability.

Chapter 3 — Observability

The triad

Signal Answers Typical stack
Metrics "is something wrong, and how wrong?" — cheap, aggregatable, alertable Prometheus, Thanos/Mimir/Cortex, cloud-native metrics
Logs "what exactly happened in this request?" — high detail, high volume Fluent Bit or Vector → Loki, OpenSearch, or a managed backend
Traces "where did the latency go across N services?" OpenTelemetry → Jaeger, Tempo, or a vendor

Metrics tell you that; traces tell you where; logs tell you why. You need all three, in that order of priority for a small team.

Prometheus and kube-state-metrics

The kube-prometheus-stack chart is the conventional starting point. It brings four things that are easy to confuse:

  • Prometheus — scrapes and stores time series; discovers targets from the Kubernetes API.
  • node-exporter (DaemonSet) — node metrics: CPU, memory, disk, filesystem, network.
  • cAdvisor (inside the kubelet) — container resource metrics: container_cpu_usage_seconds_total, container_memory_working_set_bytes.
  • kube-state-metrics — object state metrics generated from the API server: kube_deployment_status_replicas_available, kube_pod_container_status_restarts_total, kube_pod_status_phase. Not resource usage — the declared and observed state of objects.

That last distinction matters constantly: "is the container using too much memory" is cAdvisor; "have the desired replicas been available for ten minutes" is kube-state-metrics. Note also that metrics-server is a separate, minimal component that exists only to serve kubectl top and the HPA — it is not a monitoring system and does not store history.

Alert on symptoms, not causes

The discipline that separates a usable on-call rotation from an ignored one: page on what users experience; make everything else a dashboard or a ticket.

Cause-based alerts ("CPU above 80 %", "a Pod restarted", "disk 70 % full", "replica count below desired") fire constantly, are usually harmless, and train people to ignore the pager. Symptom-based alerts describe a violated expectation:

  • Error rate on shop.example.com exceeded 1 % of requests over 5 minutes.
  • p99 latency for checkout exceeded 2 s over 10 minutes.
  • The nightly export CronJob has not produced a successful Job in 26 hours.
  • The service is consuming its error budget fast enough to exhaust the month's allowance in under a day (multi-window, multi-burn-rate SLO alerting).

Useful frameworks: RED (Rate, Errors, Duration) for request-driven services, USE (Utilisation, Saturation, Errors) for resources, and the four golden signals (latency, traffic, errors, saturation). A small number of genuinely paging alerts beats a hundred noisy ones.

A short list of Kubernetes-specific conditions genuinely worth paging on: a Deployment with zero available replicas; CrashLoopBackOff persisting beyond a few minutes; Pods Pending for more than N minutes (capacity); a node NotReady beyond the eviction timeout; PersistentVolume nearly full; certificate expiring within a week; API server error rate or latency elevated.

Logging when Pods are ephemeral

kubectl logs reads from the node's log files for a currently existing Pod. Delete the Pod — as every rollout, eviction and node scale-down does — and the logs are gone. --previous reaches exactly one container generation back, and rotation discards the rest. That is not a logging strategy.

The standard architecture is a node-level agent (Fluent Bit or Vector as a DaemonSet) that tails /var/log/containers/*.log, enriches each line with Kubernetes metadata (namespace, Pod, container, labels) from the API, and ships it to a store — Loki, OpenSearch, or a managed service. Requirements that pay for themselves:

  • Log to stdout/stderr as structured JSON. Writing to a file inside the container means the agent never sees it. Unstructured text means you cannot query by field.
  • Carry the trace ID in every line. It is what joins the three signals.
  • Set retention by value, not by default. Logs are usually the largest line in an observability bill; 7 days hot plus 90 days in cheap object storage is a common shape.
  • Do not log secrets or personal data. Once shipped, it is in someone else's index and in their backups.

OpenTelemetry

OpenTelemetry is the vendor-neutral standard for producing and shipping all three signals: one set of APIs and SDKs, one wire protocol (OTLP), and the OpenTelemetry Collector as a pipeline of receivers, processors and exporters. On Kubernetes it is typically deployed twice — as a DaemonSet for node-local collection and enrichment, and as a Deployment (gateway) for aggregation, sampling and fan-out to backends. The OpenTelemetry Operator adds auto-instrumentation by injecting language agents into Pods via an annotation, which gets you traces from a Java, Python, Node or .NET service without editing its code.

The reason to standardise on it is portability: instrument once, and changing backends becomes a Collector configuration change instead of a re-instrumentation project. For a full worked treatment of OpenTelemetry — spans, context propagation, sampling strategy, collector configuration and correlating traces with database telemetry — see content/posts/mongo_26_opentelemetry_observability.md.

Chapter 4 — Security: RBAC, Pod Security and admission control

RBAC

Four object types, one simple model.

  • Role — a set of permissions, namespaced.
  • ClusterRole — the same, but cluster-scoped; also the only way to grant access to cluster-scoped resources (nodes, PVs, CRDs) or to non-resource URLs.
  • RoleBinding — grants a Role or a ClusterRole to subjects within one namespace.
  • ClusterRoleBinding — grants a ClusterRole across the whole cluster.

Binding a ClusterRole with a RoleBinding is the most useful idiom: define the permission set once, grant it namespace by namespace.

Verbs: get, list, watch, create, update, patch, delete, deletecollection, plus impersonate, bind and escalate. RBAC is purely additive — there is no deny rule. If you need denial, that is admission control's job.

Three permissions deserve special caution, because each is effectively cluster-admin in disguise: create pods in a namespace whose ServiceAccounts are privileged (you can mount any Secret and run as any identity); escalate or bind on roles (you can grant yourself more); and get secrets at cluster scope (you can read every credential in the cluster).

ServiceAccounts and their tokens

Every Pod runs as a ServiceAccount — default in its namespace unless told otherwise, and default should have no permissions at all. Give each workload its own:

Token handling changed and the modern behaviour matters. Since Kubernetes 1.24, creating a ServiceAccount no longer auto-creates a non-expiring Secret token. Pods receive a projected, time-bound, audience-scoped token that the kubelet rotates automatically. For an out-of-cluster consumer, mint one explicitly with kubectl create token api --duration=1h rather than creating a long-lived Secret. Long-lived static tokens are exactly the credential that ends up in a CI variable and never gets rotated.

On managed clusters, bind ServiceAccounts to cloud identity (IRSA on EKS, Workload Identity on GKE and AKS) so Pods obtain short-lived cloud credentials without any stored secret.

Pod Security Admission

PodSecurityPolicy was deprecated in 1.21 and removed in Kubernetes 1.25. Its replacement, Pod Security Admission, is a built-in admission controller — stable since 1.25 — configured with namespace labels rather than cluster-wide policy objects.

Three levels: privileged (no restrictions), baseline (blocks known privilege escalations: host namespaces, privileged containers, most host paths), and restricted (baseline plus hardening: run as non-root, drop all capabilities, seccomp RuntimeDefault, no privilege escalation, restricted volume types). Three modes: enforce (reject), audit (record in the audit log), warn (return a warning to the client).

The migration path is exactly that shape: enforce baseline, audit and warn on restricted, fix what the warnings reveal, then raise enforcement. Pin enforce-version so a cluster upgrade cannot tighten policy underneath you unannounced.

PSA is deliberately limited — it checks Pod security context fields and nothing else. It cannot say "images must come from our registry" or "every Deployment must set resource requests". That needs a policy engine.

Admission control and policy engines

Every request to the API server passes through authentication, then authorisation (RBAC), then admission: first mutating admission (which can modify the object — inject sidecars, set defaults), then validating admission (which can only accept or reject), then schema validation, then persistence.

You extend it three ways:

  • MutatingAdmissionWebhook — an HTTPS service you run that patches objects. Powerful, and a liability: if it is down and failurePolicy: Fail, the API server rejects the requests it intercepts. Always scope webhooks narrowly with namespaceSelector and objectSelector, and exclude kube-system.
  • ValidatingAdmissionPolicy — in-tree validation expressed in CEL, evaluated by the API server itself, GA since 1.30. No webhook to run or fail. The right first choice for simple rules.
  • Policy engines — Kyverno (policies are Kubernetes resources written in YAML; validate, mutate, generate and verify image signatures; a gentle learning curve) or OPA Gatekeeper (constraint templates written in Rego; more expressive, steeper curve, shared with non-Kubernetes OPA deployments).

Policies worth having early: require resource requests; require images from an approved registry and by digest (Post 03); forbid latest tags; require runAsNonRoot; require ownership and cost-centre labels; forbid hostNetwork and hostPath outside named namespaces. Run everything in Audit mode first — enforcing a policy that most existing workloads violate blocks deploys immediately.

Chapter 5 — Packaging and delivery

Helm

Helm is a package manager: a chart is a directory of Go-templated manifests plus a values.yaml of defaults; installing it produces a release whose state Helm stores in a Secret in the cluster.

Helm's strengths are real: one command installs a complex third-party system, versioned and parameterised; conditionals and loops express genuine variation; the ecosystem of charts is enormous.

The sharp edges are equally real and worth stating before you commit:

  • It is text templating over YAML. Indentation is your problem; nindent and toYaml are load-bearing; a template that produces valid text can produce invalid YAML. Error messages point at rendered lines you never wrote.
  • Charts become unreadable. A generic chart with forty conditionals serving five environments is harder to reason about than five explicit manifests.
  • Release state lives in the cluster, not in Git. Two operators, two laptops, two versions of the chart, and the state is whatever the last helm upgrade wrote.
  • --atomic is not optional. Without it a failed upgrade leaves the release half-applied. Also set --timeout deliberately.
  • CRDs in crds/ are installed but never upgraded or deleted by Helm. Chart upgrades that change a CRD require manual work; this surprises everyone once.
  • Values sprawl. Deeply nested values files across environments drift, and nothing type-checks them. Schema-validate with values.schema.json.

Kustomize

Kustomize takes the opposite approach: no templating language, only overlays that patch plain YAML. It is built into kubectl (kubectl apply -k).

Every file is valid Kubernetes YAML that your editor, linter and kubectl explain all understand. The configMapGenerator hash-suffix behaviour implements the rollout-on-config-change pattern from Post 05 for free. The limits: no conditionals or loops, so genuinely divergent environments mean duplication; deep patch hierarchies get hard to follow; and it does not package or distribute anything.

Helm Kustomize
Mechanism Go templating + values patch plain YAML
Best at distributing third-party software, wide parameterisation your own manifests across a few environments
Readability rendered output differs from source source is the output
Distribution repositories, versioned charts, OCI registries Git directories
State release history in-cluster none — the output is applied
Common practice use Helm for other people's software, Kustomize for your own (or Kustomize's helmCharts field for both)

GitOps

GitOps inverts the direction of deployment. Instead of CI pushing to the cluster with credentials, an agent inside the cluster pulls the desired state from Git and reconciles continuously. Git is the source of truth; the cluster converges on it.

Argo CD models this with an Application CRD, a strong UI, sync waves and hooks for ordering, and an "app of apps" pattern for managing many. Flux is a set of focused controllers (source, kustomize, helm, image automation, notification) driven entirely by CRDs, with no UI of its own. Both do the same job well; Argo CD suits teams who want the dashboard, Flux suits teams who want everything in the API.

What you actually gain:

  • Drift detection and correction. selfHeal means a manual kubectl edit is reverted within seconds. The cluster cannot silently diverge from the repository.
  • The audit trail is the Git history. Who changed what, when, reviewed by whom, and how to revert — for free, in a system everyone already knows.
  • Rollback is git revert. No special tooling, no remembering which Helm revision was good.
  • Disaster recovery becomes re-pointing an agent at the repository rather than reconstructing state from memory.

And the consequence that matters most: human access to the cluster should shrink once GitOps is in place. If every change arrives through a reviewed pull request, engineers do not need apply, edit or delete in production. Reduce them to read plus logs, port-forward and exec where justified, with break-glass elevation that is time-bound and alerted on. This is the point at which the RBAC work in Chapter 4 becomes genuinely easy — most people simply do not need write access any more.

Two caveats worth planning for: secrets still cannot be committed in plaintext, so pair GitOps with Sealed Secrets, SOPS, or the External Secrets Operator (Post 05); and image tags in Git must be updated by something — a CI step that commits the new tag, or an image-automation controller — otherwise "GitOps" quietly becomes "someone edits the tag by hand".

Chapter 6 — Managed Kubernetes and cost control

The managed offerings

EKS (AWS), GKE (Google) and AKS (Azure) all run and upgrade the control plane, manage etcd and its backups, and integrate with the cloud's IAM, load balancers and storage. What differs is the amount of remaining work: GKE Autopilot removes node management almost entirely; EKS gives you the most control and the most assembly; AKS sits between them. All charge for the control plane on a per-cluster-hour basis (with a free tier on some), and all charge normally for the worker nodes, load balancers, storage and data transfer — which is where the money actually goes. Check current pricing pages rather than trusting any figure quoted in a blog post, including this one.

The genuinely important decisions are the same everywhere: how many clusters (each has a control-plane cost and an operational cost — resist one per team until you have a reason), what your upgrade cadence is (Kubernetes releases roughly three times a year and support windows are finite), and whether your workloads can tolerate the node churn that spot instances and consolidation require.

Where the money goes, and what to do about it

Lever Action Typical effect
Over-requested resources right-size from measured usage (Post 06) usually the single largest win; requests are often multiples of real usage
Idle nodes Cluster Autoscaler scale-down or Karpenter consolidation reclaims capacity nobody is using
On-demand everything spot/preemptible for stateless and batch, with PDBs and graceful shutdown large discount, in exchange for interruption handling
Oversized instance types let Karpenter choose per workload rather than one node group for all better bin-packing
Cross-AZ traffic topology-aware routing; keep chatty pairs in one zone inter-zone transfer is metered and adds up quietly
Orphaned resources audit unbound PVCs, unused LoadBalancers, old snapshots, dangling images recurring, always finds something
Logs and metrics retention tiers; drop high-cardinality labels observability bills can rival compute
Cluster count consolidate with namespaces + RBAC + quotas instead of new clusters removes whole control planes

Make it visible and enforceable: OpenCost or Kubecost attribute spend to namespaces, labels and teams; a ResourceQuota and LimitRange per namespace stop one team consuming the cluster; and mandatory cost-centre labels (enforced by the Kyverno policy in Chapter 4) are what makes attribution possible at all. A monthly review of the top ten namespaces by cost against their requests-versus-usage ratio takes half an hour and consistently pays for itself.

Practice Exercises

Exercise 1 — Ingress or Gateway, end to end

On a local cluster, install a Gateway API implementation and expose two services on one hostname — /api to one, / to another — with TLS from a self-signed issuer. Then express the same routing as an Ingress and list every difference, including which features required controller-specific annotations.

Solution

Exercise 2 — Default-deny without breaking DNS

Apply a default-deny NetworkPolicy to a namespace running a two-tier app. Confirm everything breaks. Then restore it with exactly three policies: DNS egress, frontend→backend, backend→database. Verify with a debug Pod that nothing else is reachable.

Solution

Exercise 3 — Audit and shrink RBAC

For your own cluster: list every subject bound to cluster-admin, every Role using a wildcard verb or resource, and every ServiceAccount that can read Secrets cluster-wide. Then write a replacement Role for one over-privileged workload and verify with kubectl auth can-i --list --as=....

Solution

Exercise 4 — Debug a shell-less Pod

Build a distroless image with no shell that fails a readiness probe. Diagnose it end to end using only describe, events, logs --previous, an ephemeral debug container and port-forward. Write down which step actually revealed the cause.

Exercise 5 — Policy in audit, then enforce

Install Kyverno. Write a policy requiring CPU and memory requests on every Pod, in Audit mode. Count the violations in your cluster. Fix them, switch to Enforce, and confirm a non-compliant Pod is now rejected with a readable message.

Exercise 6 — Helm and Kustomize, same result

Package one application twice: once as a Helm chart with staging and prod values, once as a Kustomize base with two overlays. Render both with helm template and kubectl kustomize, diff the outputs, and argue which you would choose here and why.

Exercise 7 — GitOps with self-heal

Install Argo CD, point an Application at your Kustomize overlay with prune and selfHeal enabled, and confirm it syncs. Then kubectl scale the Deployment by hand and time how long the change survives. Finally, git revert a change and confirm the cluster follows.

Course base complete — what's next

That is the base course. Across eight posts you have gone from a process isolated by namespaces and cgroups on a single host to a multi-node platform with declarative delivery: 00-03 covered what a container actually is, how images are built and layered, networking and volumes and Compose, and image supply-chain security; 04 the reconciliation model, cluster components, Pods, Deployments, Services and DNS; 05 configuration and secrets, the storage stack from Volume to CSI, StatefulSets, DaemonSets, Jobs and CronJobs; 06 scheduling and placement, requests versus limits, QoS and eviction, probes, rollouts, disruption budgets, graceful shutdown and autoscaling; and 07 ingress and the Gateway API, NetworkPolicy, observability, RBAC and admission control, Helm and Kustomize, GitOps and cost.
