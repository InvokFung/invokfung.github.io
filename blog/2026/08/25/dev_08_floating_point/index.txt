11:T12ebb,<p>Sooner or later every developer types <code>0.1 + 0.2</code> and gets <code>0.30000000000000004</code>. This is not a bug in Python or JavaScript. It is how almost every computer stores fractional numbers: in binary, with a fixed number of bits. This post opens up that format (IEEE 754 binary64), shows exactly where the error comes from, and gives you the practical rules: how to compare floats, where integers stop being exact, how to add many numbers, how to store money, which rounding rule your language uses, and why 3D scenes jitter far from the origin.</p>

<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-meta">&gt;&gt;&gt; </span><span class="hljs-number">0.1</span> + <span class="hljs-number">0.2</span></span><br><span class="line"><span class="hljs-number">0.30000000000000004</span></span><br><span class="line"><span class="hljs-meta">&gt;&gt;&gt; </span><span class="hljs-number">0.1</span> + <span class="hljs-number">0.2</span> == <span class="hljs-number">0.3</span></span><br><span class="line"><span class="hljs-literal">False</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>JavaScript prints the same <code>0.30000000000000004</code>, and <code>0.1 + 0.2 === 0.3</code> is <code>false</code>. Both languages use the same number format, so both give the same answer.</p>
<h2 id="Why-01-cannot-be-stored-exactly"><a href="#Why-01-cannot-be-stored-exactly" class="headerlink" title="Why 0.1 cannot be stored exactly"></a>Why 0.1 cannot be stored exactly</h2>
<p>In decimal, <code>1/3</code> never ends: <code>0.3333…</code>. The reason is that 3 does not divide any power of 10. Binary has the same problem with any fraction whose denominator has a factor other than 2. And <code>1/10 = 1/(2 × 5)</code> has a 5, so in binary it repeats forever:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">0.1 (decimal) = 0.0001100110011001100110011… (binary, &quot;0011&quot; repeats)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A float keeps only 53 significant bits, so the computer stores the <strong>nearest</strong> representable number. You can see that number exactly:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">from</span> decimal <span class="hljs-keyword">import</span> Decimal</span><br><span class="line"><span class="hljs-keyword">from</span> fractions <span class="hljs-keyword">import</span> Fraction</span><br><span class="line"> </span><br><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-string">f&quot;<span class="hljs-subst">{<span class="hljs-number">0.1</span>:<span class="hljs-number">.20</span>f}</span>&quot;</span>)    <span class="hljs-comment"># 0.10000000000000000555</span></span><br><span class="line"><span class="hljs-built_in">print</span>(Decimal(<span class="hljs-number">0.1</span>))     <span class="hljs-comment"># 0.1000000000000000055511151231257827021181583404541015625</span></span><br><span class="line"><span class="hljs-built_in">print</span>(Fraction(<span class="hljs-number">0.1</span>))    <span class="hljs-comment"># 3602879701896397/36028797018963968   (the denominator is 2**55)</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>So <code>0.1</code> is really a bit more than 0.1, <code>0.2</code> is a bit more than 0.2, and their sum lands on a different double than the one nearest to 0.3.</p>
<p>Why does <code>print(0.1)</code> show <code>0.1</code> then? Python and JavaScript print the <strong>shortest</strong> decimal string that reads back to the same double. <code>0.1</code> is shorter than the long exact value and maps to the same bits, so it is chosen. The stored value did not change; only the printout is short.</p>
<p>Fractions whose denominator is a power of two <strong>are</strong> exact: <code>0.5</code>, <code>0.25</code>, <code>0.375</code>. Therefore <code>0.5 + 0.25 == 0.75</code> is <code>True</code>.</p>

<h1 id="Chapter-2-—-The-IEEE-754-binary64-layout"><a href="#Chapter-2-—-The-IEEE-754-binary64-layout" class="headerlink" title="Chapter 2 — The IEEE 754 binary64 layout"></a>Chapter 2 — The IEEE 754 binary64 layout</h1>
<p>Python <code>float</code>, JavaScript <code>number</code>, Java/C/C++ <code>double</code> and MongoDB <code>double</code> all use <strong>binary64</strong> from IEEE 754 (current edition: IEEE 754-2019). It has 64 bits:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line"> 1 bit   11 bits      52 bits</span><br><span class="line">[sign][ exponent ][          fraction          ]</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For normal numbers the value is:</p>

<ul>
<li><strong>sign</strong> <code>s</code>: 0 is positive, 1 is negative.</li>
<li><strong>exponent</strong> <code>e</code>: stored with a <strong>bias</strong> of 1023, so stored 1023 means 2^0.</li>

<h1 id="Chapter-3-—-Epsilon-ULP-and-comparing-floats"><a href="#Chapter-3-—-Epsilon-ULP-and-comparing-floats" class="headerlink" title="Chapter 3 — Epsilon, ULP and comparing floats"></a>Chapter 3 — Epsilon, ULP and comparing floats</h1>
<p>Doubles are not evenly spaced. The gap between neighbours grows with the size of the number:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> math, sys</span><br><span class="line"><span class="hljs-built_in">print</span>(sys.float_info.epsilon)   <span class="hljs-comment"># 2.220446049250313e-16  (= math.ulp(1.0))</span></span><br><span class="line"><span class="hljs-built_in">print</span>(math.ulp(<span class="hljs-number">1.0</span>))            <span class="hljs-comment"># 2.220446049250313e-16</span></span><br><span class="line"><span class="hljs-built_in">print</span>(math.ulp(<span class="hljs-number">1e6</span>))            <span class="hljs-comment"># 1.1641532182693481e-10</span></span><br><span class="line"><span class="hljs-built_in">print</span>(math.ulp(<span class="hljs-number">1e16</span>))           <span class="hljs-comment"># 2.0   -&gt; above 1e16 you cannot even store odd integers</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>JavaScript has the same epsilon (<code>Number.EPSILON</code>). Because every operation may round, <strong>never compare computed floats with <code>==</code></strong>. Compare with a tolerance:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> math</span><br><span class="line">math.isclose(<span class="hljs-number">0.1</span> + <span class="hljs-number">0.2</span>, <span class="hljs-number">0.3</span>)                 <span class="hljs-comment"># True</span></span><br><span class="line">math.isclose(<span class="hljs-number">1e-10</span>, <span class="hljs-number">0.0</span>)                     <span class="hljs-comment"># False  (!)</span></span><br><span class="line">math.isclose(<span class="hljs-number">1e-10</span>, <span class="hljs-number">0.0</span>, abs_tol=<span class="hljs-number">1e-9</span>)       <span class="hljs-comment"># True</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>math.isclose(a, b, *, rel_tol=1e-09, abs_tol=0.0)</code> returns <code>abs(a-b) &lt;= max(rel_tol * max(abs(a), abs(b)), abs_tol)</code>.</p>
<ul>
<li><strong>Relative tolerance</strong> scales with the size of the numbers. The default <code>1e-09</code> means &quot;same to about 9 significant digits&quot;. Use it for values of any size.</li>
<li><strong>Absolute tolerance</strong> is a fixed band. You need it near zero: a relative tolerance of anything times 0 is 0, so <code>isclose(x, 0)</code> is <code>False</code> for every non-zero <code>x</code> unless you pass <code>abs_tol</code>.</li>
</ul>
<p>JavaScript has no built-in, so write the same rule:</p>
<pre><code class="language-javascript"><figure class="highlight javascript"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="javascript"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">isClose</span>(<span class="hljs-params">a, b, relTol = <span class="hljs-number">1e-9</span>, absTol = <span class="hljs-number">0</span></span>) {</span><br><span class="line">  <span class="hljs-keyword">return</span> <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">abs</span>(a - b) &lt;= <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">max</span>(relTol * <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">max</span>(<span class="hljs-title class_">Math</span>.<span class="hljs-title function_">abs</span>(a), <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">abs</span>(b)), absTol);</span><br><span class="line">}</span><br><span class="line"><span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-title function_">isClose</span>(<span class="hljs-number">0.1</span> + <span class="hljs-number">0.2</span>, <span class="hljs-number">0.3</span>));           <span class="hljs-comment">// true</span></span><br><span class="line"><span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-title function_">isClose</span>(<span class="hljs-number">1e-10</span>, <span class="hljs-number">0</span>, <span class="hljs-number">1e-9</span>, <span class="hljs-number">1e-9</span>));     <span class="hljs-comment">// true</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Trick:</strong> in tests, use your framework's helper instead of <code>==</code>: <code>pytest.approx</code> in Python, <code>toBeCloseTo</code> in Jest/Vitest (see Dev Essentials 15 · Testing). Pick the tolerance from the problem, not from habit: sensor readings in metres might need <code>abs_tol=1e-3</code>.</p>

<h1 id="Chapter-4-—-Integers-past-253"><a href="#Chapter-4-—-Integers-past-253" class="headerlink" title="Chapter 4 — Integers past 2^53"></a>Chapter 4 — Integers past 2^53</h1>
<p>A double has 53 significant bits, so every integer up to 2^53 = 9,007,199,254,740,992 is exact. Past that, the gap between doubles is 2, then 4, and so on:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-meta">&gt;&gt;&gt; </span><span class="hljs-number">2</span>**<span class="hljs-number">53</span></span><br><span class="line"><span class="hljs-number">9007199254740992</span></span><br><span class="line"><span class="hljs-meta">&gt;&gt;&gt; </span><span class="hljs-built_in">float</span>(<span class="hljs-number">2</span>**<span class="hljs-number">53</span>) + <span class="hljs-number">1</span> == <span class="hljs-built_in">float</span>(<span class="hljs-number">2</span>**<span class="hljs-number">53</span>)</span><br><span class="line"><span class="hljs-literal">True</span></span><br><span class="line"><span class="hljs-meta">&gt;&gt;&gt; </span><span class="hljs-built_in">int</span>(<span class="hljs-built_in">float</span>(<span class="hljs-number">9007199254740993</span>))</span><br><span class="line"><span class="hljs-number">9007199254740992</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Python <code>int</code> has arbitrary precision, so this only bites when an integer passes through <code>float</code> (division with <code>/</code>, <code>float()</code>, JSON parsers, NumPy, pandas). In JavaScript every plain number is a double, so it bites all the time:</p>
<pre><code class="language-javascript"><figure class="highlight javascript"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="javascript"><span class="line"><span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-title class_">Number</span>.<span class="hljs-property">MAX_SAFE_INTEGER</span>); <p><strong>Common pitfall:</strong> 64-bit database IDs sent as JSON numbers. A browser silently changes <code>1234567890123456789</code> to <code>1234567890123456800</code>, and then you update the wrong record. <h1 id="Chapter-5-—-NaN-negative-zero-and-infinity"><a href="#Chapter-5-—-NaN-negative-zero-and-infinity" class="headerlink" title="Chapter 5 — NaN, negative zero and infinity"></a>Chapter 5 — NaN, negative zero and infinity</h1>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> math</span><br><span class="line">nan = <span class="hljs-built_in">float</span>(<span class="hljs-string">&quot;nan&quot;</span>)</span><br><span class="line"><span class="hljs-built_in">print</span>(nan == nan, nan != nan, math.isnan(nan))   <span class="hljs-comment"># False True True</span></span><br><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-built_in">sorted</span>([<span class="hljs-number">3.0</span>, nan, <span class="hljs-number">1.0</span>, <span class="hljs-number">2.0</span>]))              <span class="hljs-comment"># [3.0, nan, 1.0, 2.0]  -- not sorted!</span></span><br><span class="line"><span class="hljs-built_in">print</span>(-<span class="hljs-number">0.0</span> == <span class="hljs-number">0.0</span>, math.copysign(<span class="hljs-number">1</span>, -<span class="hljs-number">0.0</span>))       <span class="hljs-comment"># True -1.0</span></span><br><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-string">f&quot;<span class="hljs-subst">{-<span class="hljs-number">0.4</span>:<span class="hljs-number">.0</span>f}</span>&quot;</span>)                             <span class="hljs-comment"># -0</span></span><br><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-number">1e308</span> * <span class="hljs-number">10</span>, <span class="hljs-built_in">float</span>(<span class="hljs-string">&quot;inf&quot;</span>) - <span class="hljs-built_in">float</span>(<span class="hljs-string">&quot;inf&quot;</span>))   <span class="hljs-comment"># inf nan</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><strong>NaN is not equal to anything, including itself.</strong> Test with <code>math.isnan(x)</code> (Python) or <code>Number.isNaN(x)</code> (JavaScript). Any comparison with NaN is <code>False</code>, so sorting a list that contains NaN gives garbage without an error.</li>
<li><strong>Negative zero</strong> equals <code>0.0</code>, but it keeps its sign: <code>1 / -0</code> is <code>-Infinity</code> in JavaScript, and formatting <code>-0.4</code> with no decimals prints <code>-0</code>. Use <code>Object.is(x, -0)</code> in JavaScript or <code>math.copysign(1, x)</code> in Python to detect it.</li>
<li><strong>Overflow</strong> gives <code>inf</code>, not an error. <code>inf - inf</code> and <code>0 * inf</code> give NaN.</li>
<li><strong>Division by zero differs by language:</strong> Python raises <code>ZeroDivisionError</code> for <code>1 / 0.0</code>; JavaScript returns <code>Infinity</code>.</li>
</ul>

<p>Two things to learn from this table:</p>
<ol>
<li><strong><code>math.fsum</code></strong> tracks exact partial sums and returns the correctly rounded total. Use it when accuracy matters.</li>
<li><strong><code>sum()</code> changed in Python 3.12.</strong> The 3.12 &quot;What's New&quot; says <code>sum()</code> now uses Neumaier summation, a refined form of Kahan. So <code>sum([0.1] * 10)</code> is <code>0.9999999999999999</code> on 3.11 but <code>1.0</code> on 3.12 and later. Code that &quot;worked&quot; can change results on upgrade, in either direction. Know your version.</li>
</ol>
<p>Kahan has a known weak spot: when a huge value cancels out, as in <code>[1e16, 1.0, -1e16]</code>, plain Kahan still returns <code>0.0</code>. Neumaier (Python 3.12+ <code>sum</code>) and <code>fsum</code> both return <code>1.0</code>.</p>
<p>In JavaScript, <code>[0.1, 0.2, 0.3].reduce((a, b) =&gt; a + b, 0)</code> gives <code>0.6000000000000001</code>. <code>Math.sumPrecise</code> fixes this. It is a finished TC39 proposal (ES2026), and MDN marks it &quot;Baseline 2026, newly available since April 2026&quot;. Older runtimes such as Node 20 do not have it, so check before you rely on it:</p>

<h1 id="Chapter-7-—-Storing-money"><a href="#Chapter-7-—-Storing-money" class="headerlink" title="Chapter 7 — Storing money"></a>Chapter 7 — Storing money</h1>
<p><strong>Rule: never store or calculate money in binary floating point.</strong> Amounts like 19.99 cannot be stored exactly, and the errors show up as cents that do not add up. There are two safe designs.</p>
<h2 id="Option-A-—-integer-minor-units"><a href="#Option-A-—-integer-minor-units" class="headerlink" title="Option A — integer minor units"></a>Option A — integer minor units</h2>
<p>Store the amount as an integer count of the smallest unit: 19.99 → <code>1999</code> cents. Integers are exact, and addition is exact.</p>
<ul>
<li>Store the <strong>currency</strong> next to the amount. Currencies have different minor units under ISO 4217: JPY has 0 decimal places, USD and EUR have 2, and KWD and BHD have 3.</li>
<li>Division needs a remainder policy. Splitting 100.00 three ways must still add up to 100.00:</li>
</ul>

<p>PostgreSQL rounds <code>numeric</code> ties away from zero, but <code>double precision</code> ties to even (&quot;on most machines&quot;, says its manual): <code>round(2.5::numeric)</code> is 3, <code>round(2.5::float8)</code> is 2. The same <code>ROUND()</code> call can give different answers depending on the <strong>column type</strong>.</p>

<h1 id="Chapter-9-—-Formatting-is-not-the-stored-value"><a href="#Chapter-9-—-Formatting-is-not-the-stored-value" class="headerlink" title="Chapter 9 — Formatting is not the stored value"></a>Chapter 9 — Formatting is not the stored value</h1>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="python"><span class="line">x = <span class="hljs-number">0.1</span> + <span class="hljs-number">0.2</span></span><br><span class="line"><span class="hljs-built_in">print</span>(x)            <span class="hljs-comment"># 0.30000000000000004  (repr: shortest round-trip string)</span></span><br><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-string">f&quot;<span class="hljs-subst">{x:<span class="hljs-number">.2</span>f}</span>&quot;</span>)   <span class="hljs-comment"># 0.30                  (display only)</span></span><br><span class="line"><span class="hljs-built_in">print</span>(x == <span class="hljs-number">0.3</span>)     <span class="hljs-comment"># False                 (the stored value did not change)</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Formatting with <code>.2f</code> or <code>toFixed(2)</code> changes the <strong>text</strong>, not the number. Some rules:</p>
<ul>
<li>Round <strong>on purpose, at boundaries</strong>: when you store, when you send to an API, when you show to a user. Do not round in the middle of a calculation &quot;to clean it up&quot;.</li>
<li>Never compare formatted strings, and never parse your own display output back into numbers. Keep the raw value.</li>
<li>Formatting for humans is locale-dependent (<code>1,234.50</code> vs <code>1.234,50</code>). Use <code>Intl.NumberFormat</code> or Python's <code>locale</code> / Babel for display, and a fixed machine format (<code>&quot;1234.50&quot;</code>) in files and APIs.</li>
</ul>
<hr>
<h1 id="Chapter-10-—-float32-on-GPUs"><a href="#Chapter-10-—-float32-on-GPUs" class="headerlink" title="Chapter 10 — float32 on GPUs"></a>Chapter 10 — float32 on GPUs</h1>
<p>GPUs mostly compute in <strong>binary32</strong> (&quot;float32&quot;): 1 sign bit, 8 exponent bits, 23 fraction bits, so 24 significant bits and about 7 decimal digits. WebGL vertex buffers are usually <code>Float32Array</code>. The gap between neighbouring values grows fast:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> math, struct</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">f32</span>(<span class="hljs-params">x</span>):                       <span class="hljs-comment"># round a Python float to the nearest float32</span></span><br><span class="line">    <span class="hljs-keyword">return</span> struct.unpack(<span class="hljs-string">&quot;&lt;f&quot;</span>, struct.pack(<span class="hljs-string">&quot;&lt;f&quot;</span>, x))[<span class="hljs-number">0</span>]</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">f32_step</span>(<span class="hljs-params">x</span>):                  <span class="hljs-comment"># gap to the next float32 above x</span></span><br><span class="line">    bits = struct.unpack(<span class="hljs-string">&quot;&lt;I&quot;</span>, struct.pack(<span class="hljs-string">&quot;&lt;f&quot;</span>, x))[<span class="hljs-number">0</span>]</span><br><span class="line">    <span class="hljs-keyword">return</span> struct.unpack(<span class="hljs-string">&quot;&lt;f&quot;</span>, struct.pack(<span class="hljs-string">&quot;&lt;I&quot;</span>, bits + <span class="hljs-number">1</span>))[<span class="hljs-number">0</span>] - <pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line">           1  float32 step = 1.192092896e-07   float64 step = 2.22e-16</span><br><span class="line">       1,000  float32 step = 6.103515625e-05   float64 step = 1.14e-13</span><br><span class="line">     100,000  float32 step = 0.0078125   float64 step = 1.46e-11</span><br><span class="line">   1,000,000  float32 step = 0.0625   float64 step = 1.16e-10</span><br><span class="line">   6,371,000  float32 step = 0.5   float64 step = 9.31e-10</span><br><span class="line">  10,000,000  float32 step = 1   float64 step = 1.86e-09</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If one unit is one metre, an object 6,371 km from the origin (Earth's radius) can only sit on a <strong>0.5 m grid</strong> in float32. The camera and models snap between grid points, and you see <strong>jitter</strong>. The usual fixes:</p>
<ul>
<li><strong>Keep the action near the origin.</strong> Move the world instead of the camera (&quot;floating origin&quot;), or rebase coordinates when the camera travels far.</li>
<li><strong>Camera-relative rendering.</strong> Compute positions relative to the camera in float64 on the CPU (JavaScript numbers are float64), then send small float32 offsets to the GPU.</li>
</ul>

<p>The depth buffer has the same problem in the depth direction. With a perspective camera most depth precision sits near the <strong>near</strong> plane. Far away, two nearly touching surfaces get the same depth value and flicker through each other: <strong>z-fighting</strong>. In Three.js:</p>
<pre><code class="language-javascript"><figure class="highlight javascript"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="javascript"><span class="line"><span class="hljs-comment">// Rule 1: keep near as large and far as small as the scene allows.</span></span><br><span class="line"><span class="hljs-keyword">const</span> camera = <span class="hljs-keyword">new</span> <span class="hljs-variable constant_">THREE</span>.<span class="hljs-title class_">PerspectiveCamera</span>(<span class="hljs-number">50</span>, innerWidth / innerHeight, <span class="hljs-number">0.5</span>, <span class="hljs-number">5000</span>);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// Rule 2: for huge scale ranges, change how depth is stored.</span></span><br><span class="line"><span class="hljs-keyword">const</span> renderer = <span class="hljs-keyword">new</span> <span class="hljs-variable constant_">THREE</span>.<span class="hljs-title class_">WebGLRenderer</span>({ <span class="hljs-attr">logarithmicDepthBuffer</span>: <span class="hljs-literal">true</span> });</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The Three.js docs say <code>logarithmicDepthBuffer</code> &quot;may be necessary&quot; for &quot;huge differences in scale&quot;. The <code>near</code>/<code>far</code> rule of thumb is covered in Three.js Course 02 · Cameras, Controls, and Coordinate Systems.</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Predict-then-run"><a href="#Exercise-1-—-Predict-then-run" class="headerlink" title="Exercise 1 — Predict, then run"></a>Exercise 1 — Predict, then run</h2>
<p>Which of these print <code>True</code>? <code>0.1 * 3 == 0.3</code>, <code>0.5 + 0.25 == 0.75</code>, <code>0.1 + 0.7 == 0.8</code>, <code>1.1 * 3 == 3.3</code>.</p>
<details>
<summary>Solution</summary>
<p>Only <code>0.5 + 0.25 == 0.75</code>, because 0.5, 0.25 and 0.75 are exact binary fractions. The others give <code>0.30000000000000004</code>, <code>0.7999999999999999</code> and <code>3.3000000000000003</code>.</p>
</details>
<h2 id="Exercise-2-—-Find-253-yourself"><a href="#Exercise-2-—-Find-253-yourself" class="headerlink" title="Exercise 2 — Find 2^53 yourself"></a>Exercise 2 — Find 2^53 yourself</h2>
<p>Without typing 2**53, write a loop that finds the smallest power of two <code>n</code> (as a float) where <code>n + 1.0 == n</code>.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="python"><span class="line">n = <span class="hljs-number">1.0</span></span><br><span class="line"><span class="hljs-keyword">while</span> n + <span class="hljs-number">1.0</span> != n:</span><br><span class="line">    n *= <span class="hljs-number">2</span></span><br><span class="line"><span class="hljs-built_in">print</span>(n, <span class="hljs-built_in">int</span>(n) == <span class="hljs-number">2</span>**<span class="hljs-number">53</span>)    <span class="hljs-comment"># 9007199254740992.0 True</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>At 2^53 the gap between doubles becomes 2, so adding 1 rounds back to <code>n</code> (ties go to even).</p>
</details>

<p>Split a bill of 250.00 among 7 people using integer cents. Every share must be within 1 cent of every other, and the shares must add up to exactly 25000.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">def</span> <span class="hljs-title function_">split_cents</span>(<span class="hljs-params">total_cents, people</span>):</span><br><span class="line">    base, extra = <span class="hljs-built_in">divmod</span>(total_cents, people)</span><br><span class="line">    <span class="hljs-keyword">return</span> [base + <span class="hljs-number">1</span> <span class="hljs-keyword">if</span> i &lt; extra <span class="hljs-keyword">else</span> base <span class="hljs-keyword">for</span> i <span class="hljs-keyword">in</span> <span class="hljs-built_in">range</span>(people)]</span><br><span class="line"> </span><br><span class="line">s = split_cents(<span class="hljs-number">25000</span>, <span class="hljs-number">7</span>)</span><br><span class="line"><span class="hljs-built_in">print</span>(s, <span class="hljs-built_in">sum</span>(s))   <span class="hljs-comment"># [3572, 3572, 3572, 3571, 3571, 3571, 3571] 25000</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Exercise-4-—-Why-is-this-invoice-off-by-one-cent"><a href="#Exercise-4-—-Why-is-this-invoice-off-by-one-cent" class="headerlink" title="Exercise 4 — Why is this invoice off by one cent?"></a>Exercise 4 — Why is this invoice off by one cent?</h2>
<p>A system stores prices as <code>float</code>, computes <code>round(price * qty * 1.0825, 2)</code> per line, and the total differs from the accountant's figure by 0.01. List two separate causes.</p>
<details>
<summary>Solution</summary>
<ol>
<li><strong>Binary floats:</strong> <code>price * qty * 1.0825</code> is not exact, so a value that &quot;should&quot; be a tie like <code>x.xx5</code> may be stored a hair below it, and then it rounds down.</li>
<li><strong>Rounding mode and place:</strong> Python <code>round()</code> uses half-to-even, while accounting rules often want half-up. Rounding per line vs once on the total can also differ (the Chapter 7 example: 5.88 vs 5.87).</li>
</ol>
<p>Fix: <code>Decimal</code> built from strings, an explicit <code>ROUND_HALF_UP</code> (or whatever the rules say), and one agreed place to round.</p>
</details>
