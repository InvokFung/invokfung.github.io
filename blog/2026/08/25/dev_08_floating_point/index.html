Dev Essentials — 08 · Floating Point — Why 0.1 + 0.2 Is Not 0.3 and How to Store Money

Created2026-08-25|Updated2026-08-25|Dev Essentials
|Post View:

Sooner or later every developer types 0.1 + 0.2 and gets 0.30000000000000004. This is not a bug in Python or JavaScript. It is how almost every computer stores fractional numbers: in binary, with a fixed number of bits. This post opens up that format (IEEE 754 binary64), shows exactly where the error comes from, and gives you the practical rules: how to compare floats, where integers stop being exact, how to add many numbers, how to store money, which rounding rule your language uses, and why 3D scenes jitter far from the origin.

Series map: 01 Text Encoding → … → 07 HTTPS → 08 Floating Point (this post) → 09 Versions & Dependencies → … → 24 Desk Health. Part B · Everyday skills.

Learning Outcome

  • Explain why 0.1 has no exact binary form, and read the bits of a float in Python.
  • Describe the IEEE 754 binary64 layout: 1 sign bit, 11 exponent bits, 52 fraction bits.
  • Compare floats with a tolerance (math.isclose), and know when absolute vs relative tolerance fits.
  • Know the 2^53 limit for exact integers, and handle NaN, -0.0 and infinities without surprises.
  • Reduce summation error with math.fsum or Kahan summation.
  • Store money as integer minor units or a decimal type, and pick a rounding mode on purpose.
  • Explain float32 precision loss on GPUs and the Three.js depth-buffer options.

Chapter 1 — The famous result

JavaScript prints the same 0.30000000000000004, and 0.1 + 0.2 === 0.3 is false. Both languages use the same number format, so both give the same answer.

Why 0.1 cannot be stored exactly

In decimal, 1/3 never ends: 0.3333…. The reason is that 3 does not divide any power of 10. Binary has the same problem with any fraction whose denominator has a factor other than 2. And 1/10 = 1/(2 × 5) has a 5, so in binary it repeats forever:

A float keeps only 53 significant bits, so the computer stores the nearest representable number. You can see that number exactly:

So 0.1 is really a bit more than 0.1, 0.2 is a bit more than 0.2, and their sum lands on a different double than the one nearest to 0.3.

Why does print(0.1) show 0.1 then? Python and JavaScript print the shortest decimal string that reads back to the same double. 0.1 is shorter than the long exact value and maps to the same bits, so it is chosen. The stored value did not change; only the printout is short.

Fractions whose denominator is a power of two are exact: 0.5, 0.25, 0.375. Therefore 0.5 + 0.25 == 0.75 is True.

Chapter 2 — The IEEE 754 binary64 layout

Python float, JavaScript number, Java/C/C++ double and MongoDB double all use binary64 from IEEE 754 (current edition: IEEE 754-2019). It has 64 bits:

For normal numbers the value is:

x=(−1)s×1.f2×2 e−1023x = (-1)^{s} \times 1.f_2 \times 2^{\,e - 1023} x=(−1)s×1.f2​×2e−1023

  • sign s: 0 is positive, 1 is negative.
  • exponent e: stored with a bias of 1023, so stored 1023 means 2^0.
  • fraction f: the bits after the binary point. The leading 1. is implied and not stored, so you get 53 significant bits from 52 stored ones.

Look at real bits:

For 0.1 the exponent bits are 01111111011 = 1019, and 1019 − 1023 = −4. The fraction is the repeating 1001 pattern, and the last bits …1010 show it was rounded up. So 0.1 is stored as about 1.6 × 2^−4, just a little high.

Special exponent values

Exponent bits Fraction Meaning
all 0 0 +0.0 or -0.0
all 0 not 0 Subnormal: tiny numbers near zero, with less precision
all 1 0 +inf or -inf
all 1 not 0 NaN (not a number)

sys.float_info in Python lists the limits: max is 1.7976931348623157e+308, the smallest normal positive value min is 2.2250738585072014e-308, mant_dig is 53 bits, and dig is 15 (decimal digits that always survive a round trip). Rule of thumb: a double carries about 15 to 17 significant decimal digits.

Terminology

Term Meaning
Significand (mantissa) The 1.f part: the significant bits.
Exponent / bias Power of two, stored as e + 1023.
ULP "Unit in the last place": the gap between a float and the next one up.
Machine epsilon ULP of 1.0: 2**-52 ≈ 2.22e-16.
Round-to-nearest-even Default IEEE rounding for every arithmetic result.

Chapter 3 — Epsilon, ULP and comparing floats

Doubles are not evenly spaced. The gap between neighbours grows with the size of the number:

JavaScript has the same epsilon (Number.EPSILON). Because every operation may round, never compare computed floats with ==. Compare with a tolerance:

math.isclose(a, b, *, rel_tol=1e-09, abs_tol=0.0) returns abs(a-b) <= max(rel_tol * max(abs(a), abs(b)), abs_tol).

  • Relative tolerance scales with the size of the numbers. The default 1e-09 means "same to about 9 significant digits". Use it for values of any size.
  • Absolute tolerance is a fixed band. You need it near zero: a relative tolerance of anything times 0 is 0, so isclose(x, 0) is False for every non-zero x unless you pass abs_tol.

Chapter 4 — Integers past 2^53

A double has 53 significant bits, so every integer up to 2^53 = 9,007,199,254,740,992 is exact. Past that, the gap between doubles is 2, then 4, and so on:

Python int has arbitrary precision, so this only bites when an integer passes through float (division with /, float(), JSON parsers, NumPy, pandas). In JavaScript every plain number is a double, so it bites all the time:

Common pitfall: 64-bit database IDs sent as JSON numbers. A browser silently changes 1234567890123456789 to 1234567890123456800, and then you update the wrong record. Send large IDs as strings, and convert them to BigInt only if you must do arithmetic.

Chapter 5 — NaN, negative zero and infinity

  • NaN is not equal to anything, including itself. Test with math.isnan(x) (Python) or Number.isNaN(x) (JavaScript). Any comparison with NaN is False, so sorting a list that contains NaN gives garbage without an error.
  • Negative zero equals 0.0, but it keeps its sign: 1 / -0 is -Infinity in JavaScript, and formatting -0.4 with no decimals prints -0. Use Object.is(x, -0) in JavaScript or math.copysign(1, x) in Python to detect it.
  • Overflow gives inf, not an error. inf - inf and 0 * inf give NaN.
  • Division by zero differs by language: Python raises ZeroDivisionError for 1 / 0.0; JavaScript returns Infinity.

Chapter 6 — Summation error

Each + rounds. Add many numbers and the small errors pile up:

Method Python 3.11 Python 3.13
plain loop total += x 100000.00000133288 100000.00000133288
Kahan (above) 100000.0 100000.0
built-in sum() 100000.00000133288 100000.0
math.fsum() 100000.0 100000.0

Two things to learn from this table:

  1. math.fsum tracks exact partial sums and returns the correctly rounded total. Use it when accuracy matters.
  2. sum() changed in Python 3.12. The 3.12 "What's New" says sum() now uses Neumaier summation, a refined form of Kahan. So sum([0.1] * 10) is 0.9999999999999999 on 3.11 but 1.0 on 3.12 and later. Code that "worked" can change results on upgrade, in either direction. Know your version.

Kahan has a known weak spot: when a huge value cancels out, as in [1e16, 1.0, -1e16], plain Kahan still returns 0.0. Neumaier (Python 3.12+ sum) and fsum both return 1.0.

In JavaScript, [0.1, 0.2, 0.3].reduce((a, b) => a + b, 0) gives 0.6000000000000001. Math.sumPrecise fixes this. It is a finished TC39 proposal (ES2026), and MDN marks it "Baseline 2026, newly available since April 2026". Older runtimes such as Node 20 do not have it, so check before you rely on it:

Chapter 7 — Storing money

Rule: never store or calculate money in binary floating point. Amounts like 19.99 cannot be stored exactly, and the errors show up as cents that do not add up. There are two safe designs.

Option A — integer minor units

Store the amount as an integer count of the smallest unit: 19.99 → 1999 cents. Integers are exact, and addition is exact.

  • Store the currency next to the amount. Currencies have different minor units under ISO 4217: JPY has 0 decimal places, USD and EUR have 2, and KWD and BHD have 3.
  • Division needs a remainder policy. Splitting 100.00 three ways must still add up to 100.00:

Option B — decimal types

A decimal type stores base-10 digits, so 0.1 is exact.

Java BigDecimal — the Javadoc warns that new BigDecimal(0.1) equals 0.1000000000000000055511151231257827021181583404541015625. Use the String constructor or BigDecimal.valueOf(double):

Common pitfall: using BigDecimal.equals or putting BigDecimal keys in a HashMap. 2.0 and 2.00 are not equals. Compare with compareTo. (Java basics: Java Development [Basic] Part 1.)

MongoDB Decimal128 — IEEE 754 decimal128, with 34 decimal digits of precision. MongoDB's "Model Monetary Data" guide recommends it, and its mongosh examples build values from strings:

The same guide also describes the integer "scale factor" option (store 9.99 as 9990 with a scale of 1000). Types are introduced in MongoDB Course 00 · Foundations.

SQL NUMERIC(p, s) — p total digits, s digits after the point, so amount NUMERIC(12, 2) holds up to 9,999,999,999.99. Add a currency char(3) column for the ISO 4217 code. PostgreSQL's docs say numeric "is especially recommended for storing monetary amounts".

JavaScript has no built-in decimal type. Keep integer cents (use BigInt for very large totals) or use a well-maintained decimal library. Format only for display with Intl.NumberFormat:

Chapter 8 — Rounding modes

"Round 2.5" has more than one right answer. It depends on the rounding mode:

Mode (Python decimal name) 2.5 −2.5 2.4 Typical use
ROUND_HALF_EVEN ("banker's") 2 −2 2 IEEE default, Python round(), Decimal default
ROUND_HALF_UP (ties away from zero) 3 −3 2 School rounding, many invoices, SQL numeric
ROUND_HALF_DOWN 2 −2 2 Rare
ROUND_UP (away from zero) 3 −3 3 "Never undercharge" rules
ROUND_DOWN (toward zero, truncate) 2 −2 2 Truncating fees
ROUND_CEILING / ROUND_FLOOR 3 / 2 −2 / −3 3 / 2 Toward +∞ / −∞

Half-to-even sends ties up half the time and down half the time, so a long column of rounded numbers does not drift upward. That is why it is the IEEE default.

What your language actually does

Python's docs confirm: ties go "toward the even choice". And round(2.675, 2) gives 2.67, which the docs note "is not a bug": the stored double is 2.67499999999999982236431605997495353221893310546875, which is below the tie. When you need a specific mode, use Decimal built from a string:

JavaScript is different again:

PostgreSQL rounds numeric ties away from zero, but double precision ties to even ("on most machines", says its manual): round(2.5::numeric) is 3, round(2.5::float8) is 2. The same ROUND() call can give different answers depending on the column type.

Chapter 9 — Formatting is not the stored value

Formatting with .2f or toFixed(2) changes the text, not the number. Some rules:

  • Round on purpose, at boundaries: when you store, when you send to an API, when you show to a user. Do not round in the middle of a calculation "to clean it up".
  • Never compare formatted strings, and never parse your own display output back into numbers. Keep the raw value.
  • Formatting for humans is locale-dependent (1,234.50 vs 1.234,50). Use Intl.NumberFormat or Python's locale / Babel for display, and a fixed machine format ("1234.50") in files and APIs.

Chapter 10 — float32 on GPUs

GPUs mostly compute in binary32 ("float32"): 1 sign bit, 8 exponent bits, 23 fraction bits, so 24 significant bits and about 7 decimal digits. WebGL vertex buffers are usually Float32Array. The gap between neighbouring values grows fast:

If one unit is one metre, an object 6,371 km from the origin (Earth's radius) can only sit on a 0.5 m grid in float32. The camera and models snap between grid points, and you see jitter. The usual fixes:

  • Keep the action near the origin. Move the world instead of the camera ("floating origin"), or rebase coordinates when the camera travels far.
  • Camera-relative rendering. Compute positions relative to the camera in float64 on the CPU (JavaScript numbers are float64), then send small float32 offsets to the GPU.

Depth precision and z-fighting

The depth buffer has the same problem in the depth direction. With a perspective camera most depth precision sits near the near plane. Far away, two nearly touching surfaces get the same depth value and flicker through each other: z-fighting. In Three.js:

The Three.js docs say logarithmicDepthBuffer "may be necessary" for "huge differences in scale". They also note that it uses gl_FragDepth, which turns off the early fragment test and can cost performance. The docs list a newer reversedDepthBuffer option too. It needs the EXT_clip_control extension, and the docs call it faster and more accurate than the logarithmic buffer. The near/far rule of thumb is covered in Three.js Course 02 · Cameras, Controls, and Coordinate Systems.

Practice Exercises

Exercise 1 — Predict, then run

Which of these print True? 0.1 * 3 == 0.3, 0.5 + 0.25 == 0.75, 0.1 + 0.7 == 0.8, 1.1 * 3 == 3.3.

Solution

Only 0.5 + 0.25 == 0.75, because 0.5, 0.25 and 0.75 are exact binary fractions. The others give 0.30000000000000004, 0.7999999999999999 and 3.3000000000000003.

Exercise 2 — Find 2^53 yourself

Without typing 2**53, write a loop that finds the smallest power of two n (as a float) where n + 1.0 == n.

Solution

At 2^53 the gap between doubles becomes 2, so adding 1 rounds back to n (ties go to even).

Exercise 3 — Split a restaurant bill

Split a bill of 250.00 among 7 people using integer cents. Every share must be within 1 cent of every other, and the shares must add up to exactly 25000.

Solution

With floats, 250 / 7 rounded to cents is 35.71, and 7 × 35.71 = 249.97: three cents vanish.

Exercise 4 — Why is this invoice off by one cent?

A system stores prices as float, computes round(price * qty * 1.0825, 2) per line, and the total differs from the accountant's figure by 0.01. List two separate causes.

Solution
  1. Binary floats: price * qty * 1.0825 is not exact, so a value that "should" be a tie like x.xx5 may be stored a hair below it, and then it rounds down.
  2. Rounding mode and place: Python round() uses half-to-even, while accounting rules often want half-up. Rounding per line vs once on the total can also differ (the Chapter 7 example: 5.88 vs 5.87).

Fix: Decimal built from strings, an explicit ROUND_HALF_UP (or whatever the rules say), and one agreed place to round.

Exercise 5 — GPU grid size

A flight-simulator scene uses metres with the origin at the airport. At what distance does float32 spacing reach 1 cm, 10 cm and 1 m? Use f32_step from Chapter 10.

Solution

At 131 km from the origin a vertex can only move in 1.5 cm steps, which is enough to see a cockpit shake. Use a floating origin or camera-relative coordinates.
