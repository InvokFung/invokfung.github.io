11:Td669,<p>&quot;Is this page static or dynamic?&quot; used to be a per-route yes/no question in Next.js, answered implicitly by whatever APIs the route happened to touch. One <code>cookies()</code> call in a shared header could turn a whole marketing site into per-request rendering, and nothing warned you. Next.js 16's Cache Components turn the question into a per-component one: every route gets a prerendered static shell, and only the parts that genuinely need request data stream in afterwards. This post works through the whole rendering spectrum: how the classic static/dynamic decision is made, streaming with Suspense and what it does to status codes, ISR and <code>generateStaticParams</code>, Partial Prerendering and its Cache Components form, <code>proxy.ts</code> (formerly <code>middleware.ts</code>), the Node.js versus Edge runtime decision, and the hard limits of <code>output: 'export'</code>, using this blog, a Next.js 14 static export, as the worked example.</p>

<h1 id="Chapter-1-—-Static-vs-dynamic-the-classic-model"><a href="#Chapter-1-—-Static-vs-dynamic-the-classic-model" class="headerlink" title="Chapter 1 — Static vs dynamic, the classic model"></a>Chapter 1 — Static vs dynamic, the classic model</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Prerendering</strong> — rendering a route at build time (or at revalidation time) and storing the HTML and RSC payload for reuse.</li>
<li><strong>Dynamic rendering</strong> — rendering a route per request.</li>
<li><strong>Request-time APIs</strong> (earlier docs: &quot;dynamic APIs&quot;) — APIs whose value depends on the incoming request: <code>cookies()</code>, <code>headers()</code>, <code>searchParams</code>, <code>connection()</code>, <code>draftMode()</code>.</li>
<li><strong>Static shell</strong> — the prerendered part of a route that can be sent before any request-specific work runs (Cache Components term).</li>
<li><strong>Dynamic hole</strong> — a Suspense boundary whose content is rendered at request time and streamed into the shell.</li>
</ul>
<h2 id="How-a-route-became-static-or-dynamic-14-and-15"><a href="#How-a-route-became-static-or-dynamic-14-and-15" class="headerlink" title="How a route became static or dynamic (14 and 15)"></a>How a route became static or dynamic (14 and 15)</h2>
<p>Without Cache Components, <code>next build</code> tries to prerender every route. A route switches to dynamic rendering for the whole route when, anywhere in its tree, it:</p>
<ul>
<li>calls a request-time API (<code>cookies()</code>, <code>headers()</code>, <code>searchParams</code>, <code>connection()</code>, <code>draftMode()</code>),</li>
<li>runs a <code>fetch</code> with <code>cache: 'no-store'</code> or <code>revalidate: 0</code> (or calls <code>unstable_noStore()</code>),</li>
<li>or sets <code>export const dynamic = 'force-dynamic'</code>.</li>
</ul>
<p>The route segment config can force the decision:</p>
<table>
<thead>
<tr>
<th>Export</th>
<th>Effect</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>dynamic = 'auto'</code></td>
<td>Default: decided by what the route uses</td>
</tr>
<tr>
<td><code>dynamic = 'force-dynamic'</code></td>
<td>Always per request (in 15 also sets <code>no-store</code> on fetch)</td>
</tr>
<tr>
<td><code>dynamic = 'force-static'</code></td>
<td>Prerender; request-time APIs return empty values</td>
</tr>
<tr>
<td><code>dynamic = 'error'</code></td>
<td>Prerender, and fail the build if anything dynamic is used</td>
</tr>
<tr>
<td><code>revalidate = n</code></td>
<td>ISR interval in seconds for the route</td>
</tr>
<tr>
<td><code>dynamicParams = false</code></td>
<td>Params not returned by <code>generateStaticParams</code> return 404</td>
</tr>
</tbody>
</table>
<p><code>next build</code> prints a route table with a symbol per route: <code>○</code> static, <code>●</code> prerendered with <code>generateStaticParams</code> (SSG), <code>ƒ</code> dynamic. Reading it after every significant change is the cheapest regression test for rendering mode.</p>
<p>Response headers follow the decision when self-hosting: dynamic pages get <code>Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate</code>; ISR pages get <code>s-maxage=&lt;revalidate&gt;, stale-while-revalidate</code>; hashed static assets get <code>public, max-age=31536000, immutable</code>.</p>
<blockquote>
<p><strong>Common pitfall:</strong> reading <code>cookies()</code> in the root layout (for a theme or locale) makes <strong>every</strong> route dynamic, because the layout is in every route's tree. Read it in a small Suspense-wrapped component instead, or set the attribute before paint with an inline script.</p>
</blockquote>

<h1 id="Chapter-2-—-Streaming-with-Suspense"><a href="#Chapter-2-—-Streaming-with-Suspense" class="headerlink" title="Chapter 2 — Streaming with Suspense"></a>Chapter 2 — Streaming with Suspense</h1>
<h2 id="What-streaming-does"><a href="#What-streaming-does" class="headerlink" title="What streaming does"></a>What streaming does</h2>
<p>The App Router streams HTML. React sends the shell first with Suspense fallbacks in place, keeps the connection open, and later sends each boundary's content with a small inline script that swaps it in. The same happens for the RSC payload on client navigations. The user sees useful content as soon as the fastest part is ready instead of when the slowest is.</p>
<p><code>loading.tsx</code> is a shortcut: it wraps the segment's <code>page</code> in a Suspense boundary with the file's component as fallback. For finer control, place <code>&lt;Suspense&gt;</code> yourself around each slow region:</p>

<p><strong>Push dynamic access down.</strong> The smaller the component that awaits slow or request-bound data, the more of the page lands in the first flush.</p>
<h2 id="Status-codes-after-the-first-byte"><a href="#Status-codes-after-the-first-byte" class="headerlink" title="Status codes after the first byte"></a>Status codes after the first byte</h2>
<p>Once the first chunk is sent, the HTTP status line and headers are gone. If <code>notFound()</code>, <code>redirect()</code>, <code>forbidden()</code> or <code>unauthorized()</code> runs inside a boundary that already streamed, the response status stays <strong>200</strong>. Next.js handles the UI (and inserts a <code>noindex</code> robots meta tag for a streamed not-found), but monitoring that counts 404s by status code will miss them.</p>
<blockquote>
<p><strong>Trick:</strong> call <code>notFound()</code> for a missing resource <strong>before</strong> any Suspense boundary (at the top of the page, after the lookup), so the real 404 status is sent. Only data that is allowed to fail softly belongs inside the streamed parts.</p>
</blockquote>
<h2 id="Streaming-needs-every-hop-to-cooperate"><a href="#Streaming-needs-every-hop-to-cooperate" class="headerlink" title="Streaming needs every hop to cooperate"></a>Streaming needs every hop to cooperate</h2>
<p>Buffering anywhere between the server and the browser collapses a stream into one late response. Self-hosted, disable Nginx buffering (Next.js docs suggest the <code>X-Accel-Buffering: no</code> header) and check that load balancers support chunked transfer or HTTP/2 streaming. Some cloud load balancers buffer by default.</p>

<h1 id="Chapter-3-—-ISR-and-generateStaticParams"><a href="#Chapter-3-—-ISR-and-generateStaticParams" class="headerlink" title="Chapter 3 — ISR and generateStaticParams"></a>Chapter 3 — ISR and <code>generateStaticParams</code></h1>

On-demand ISR is <code>revalidatePath</code> / <code>revalidateTag</code> from Post 01.</p>
<p>Operational facts:</p>
<ul>
<li>The ISR cache is on the <strong>local file system of each server instance</strong> by default (plus a 50 MB in-memory layer). Two pods have two caches; a custom <code>cacheHandler</code> fixes it (Post 03).</li>
<li><code>expireTime</code> (Next.js 15) sets the <code>stale-while-revalidate</code> window in the <code>Cache-Control</code> header; its default is one year so CDNs can apply SWR properly.</li>
<li>The Edge runtime does not support ISR.</li>
</ul>
<h2 id="generateStaticParams-in-detail"><a href="#generateStaticParams-in-detail" class="headerlink" title="generateStaticParams in detail"></a><code>generateStaticParams</code> in detail</h2>
<ul>
<li>It returns an array of objects whose keys are the dynamic segment names and whose values are strings (or string arrays for catch-alls: <code>{ slug: ['a', 'b'] }</code> for <code>[...slug]</code>).</li>
<li>For nested dynamic segments, a child's <code>generateStaticParams</code> receives the parent's <code>params</code>, or a single function at the deepest level can return all segments at once.</li>
<li>It runs at build time, before the pages it lists are rendered.</li>
</ul>
<p>This blog's post route is <code>app/[year]/[month]/[day]/[slug]/page.tsx</code>. Its <code>generateStaticParams</code> returns one object with all four segments per post from <code>getAllPostPaths()</code>, and the paginated index at <code>app/page/[n]/page.tsx</code> sets <code>dynamicParams = false</code>, so <code>/page/999/</code> is a 404 rather than a server render the static host could never perform.</p>
<h2 id="ISR-under-Cache-Components-16"><a href="#ISR-under-Cache-Components-16" class="headerlink" title="ISR under Cache Components (16)"></a>ISR under Cache Components (16)</h2>
<p>With <code>cacheComponents</code>, two rules change:</p>
<ul>
<li><code>generateStaticParams</code> <strong>must return at least one param</strong>. Returning <code>[]</code> raises <code>empty-generate-static-params</code>, because Next.js needs one real render to validate the static shell. Unlisted paths still work: they get the shell at once and stream the rest.</li>
<li><code>dynamicParams</code> is not allowed. To reject unknown params, call <code>notFound()</code> when the lookup fails.</li>
</ul>
<p>Next.js 16.3 improved this further: a path you did not prerender serves an instant loading shell to its first visitor, then is upgraded to the fully prerendered page in the background, and later visitors get the final content from the cache.</p>

<h1 id="Chapter-4-—-Partial-Prerendering-and-Cache-Components"><a href="#Chapter-4-—-Partial-Prerendering-and-Cache-Components" class="headerlink" title="Chapter 4 — Partial Prerendering and Cache Components"></a>Chapter 4 — Partial Prerendering and Cache Components</h1>
<h2 id="From-static-or-dynamic-to-both-per-component"><a href="#From-static-or-dynamic-to-both-per-component" class="headerlink" title="From &quot;static or dynamic&quot; to &quot;both, per component&quot;"></a>From &quot;static or dynamic&quot; to &quot;both, per component&quot;</h2>
<p>Partial Prerendering (PPR) was introduced as an experiment in Next.js 14 (2023), offered as an incremental opt-in (<code>experimental_ppr</code> per route) in 15, and <strong>folded into Cache Components in 16</strong>, which removed the <code>experimental.ppr</code> flag. With <code>cacheComponents: true</code>, PPR is simply how the App Router renders.</p>
<p>The model: at build time Next.js renders every route as far as it can. Everything that is static or cached (<code>'use cache'</code>) becomes the <strong>static shell</strong>. Every Suspense boundary whose content needs request data or uncached data becomes a <strong>dynamic hole</strong>. At request time, the shell is sent immediately (it can come from a CDN) and the holes are rendered and streamed into the same response.</p>

<h2 id="The-three-errors-you-will-meet"><a href="#The-three-errors-you-will-meet" class="headerlink" title="The three errors you will meet"></a>The three errors you will meet</h2>
<p>With Cache Components, Next.js validates every route in development and at build time. Every piece of data must be one of: <strong>cached</strong> (<code>'use cache'</code>), <strong>inside a Suspense boundary</strong> (a dynamic hole), or <strong>static</strong>. The errors map to those rules:</p>
<table>
<thead>
<tr>
<th>Symptom</th>
<th>Cause</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>Blocking-route insight / error on <code>cookies()</code>, <code>headers()</code>, <code>searchParams</code></td>
<td>Runtime data read outside any Suspense boundary</td>
<td>Move the read into a Suspense-wrapped child; pass the <code>params</code> / <code>searchParams</code> promise down and await it there</td>
</tr>
<tr>
<td>Uncached data accessed outside Suspense</td>
<td>An uncached <code>fetch</code> or DB query at the top of a page or layout</td>
<td>Add <code>'use cache'</code> near the data access, or wrap the component in Suspense</td>
</tr>
<tr>
<td>Synchronous IO during prerender</td>
<td><code>new Date()</code>, <code>Date.now()</code>, <code>Math.random()</code>, <code>crypto.randomUUID()</code> in the shell</td>
<td>Wrap the part in Suspense and <code>await connection()</code> first, or compute it in a Client Component</td>
</tr>
</tbody>
</table>
<p>Two more rules from the 16 migration guide:</p>
<ul>
<li>Client hooks that read the route (<code>usePathname</code>, <code>useParams</code>, <code>useSelectedLayoutSegment(s)</code>) suspend when the route has unknown dynamic params, and <code>useSearchParams</code> always needs a Suspense boundary. A breadcrumb in a shared layout is the classic offender.</li>
<li>Reading a cookie to set <code>&lt;html lang&gt;</code> or <code>data-theme</code> in the root layout makes the whole tree request-bound. Next.js recommends an inline <code>&lt;head&gt;</code> script that sets the attribute before paint instead.</li>
</ul>
<p>As of 16.3, a segment can export <code>instant = false</code> to defer validation while you migrate incrementally. It does not clear synchronous-IO errors.</p>
<blockquote>
<p><strong>Watch out:</strong> a build that passes can still fail at request time. Calling <code>cookies()</code> through a helper inside a <code>'use cache'</code> function on a dynamically rendered route surfaces only when the route runs under <code>next start</code>. Exercise dynamic routes in a production build before shipping.</p>
</blockquote>

<h2 id="Writing-it-correctly"><a href="#Writing-it-correctly" class="headerlink" title="Writing it correctly"></a>Writing it correctly</h2>

<p>Rules worth memorising:</p>
<ul>
<li>Without a <code>matcher</code>, Proxy runs on <strong>every</strong> request, including <code>_next/static</code>, <code>_next/image</code> and <code>public/</code> files. An auth redirect without a negative matcher blocks CSS and JS.</li>
<li><code>matcher</code> values must be <strong>constants</strong>; they are statically analysed at build time and variables are ignored.</li>
<li>Execution order: <code>headers</code> from <code>next.config</code>, <code>redirects</code> from <code>next.config</code>, <strong>Proxy</strong>, <code>beforeFiles</code> rewrites, file-system routes, <code>afterFiles</code> rewrites, dynamic routes, <code>fallback</code> rewrites.</li>
<li><code>NextResponse.next({ request: { headers } })</code> passes headers <strong>upstream to the app</strong>; <code>NextResponse.next({ headers })</code> sends them <strong>to the client</strong>. Confusing the two leaks internal headers.</li>
<li>Flight headers (<code>rsc</code>, <code>next-router-state-tree</code>, <code>next-router-prefetch</code>) are stripped from <code>request.headers</code> in Proxy so RSC and HTML requests are handled alike.</li>
<li><code>fetch</code> cache options (<code>cache</code>, <code>next.revalidate</code>, <code>next.tags</code>) have no effect in Proxy.</li>
<li><code>event.waitUntil(promise)</code> (second argument, <code>NextFetchEvent</code>) keeps the invocation alive for logging after the response.</li>
<li>Since 15.1, <code>unstable_doesProxyMatch</code> from <code>next/experimental/testing/server</code> unit-tests matchers.</li>
</ul>
<h2 id="What-Proxy-is-not"><a href="#What-Proxy-is-not" class="headerlink" title="What Proxy is not"></a>What Proxy is not</h2>
<p>Next.js docs are explicit: Proxy is for <strong>optimistic</strong> checks (is there a session cookie at all?) and redirects/rewrites, not a full session-management or authorisation solution, and not for slow data fetching. Two structural reasons:</p>
<ol>
<li><strong>Server Functions are POSTs to the page route.</strong> A matcher that excludes a path also skips every action on it, and moving an action to another route silently changes coverage.</li>
<li><strong>A bypass is total.</strong> In March 2025, CVE-2025-29927 let an attacker skip middleware entirely by sending a crafted <code>x-middleware-subrequest</code> header on self-hosted deployments. Any app whose only auth check lived in middleware was open. Post 03 covers the incident.</li>
</ol>
<blockquote>
<p><strong>Trick:</strong> treat Proxy as a performance optimisation for the happy path (redirect obviously logged-out users early), and put the real check in the Data Access Layer that every page, action and Route Handler goes through.</p>
</blockquote>
<hr>
<h1 id="Chapter-6-—-Nodejs-vs-Edge-runtime"><a href="#Chapter-6-—-Nodejs-vs-Edge-runtime" class="headerlink" title="Chapter 6 — Node.js vs Edge runtime"></a>Chapter 6 — Node.js vs Edge runtime</h1>
<p>The Edge runtime is a restricted, Web-API-only environment (no <code>fs</code>, no native Node.js modules, no <code>require</code>, no <code>eval</code> or <code>new Function</code>, no ISR) designed to start fast and run close to users. The Node.js runtime has the full Node.js API and is the default.</p>
<p>By 2026 the balance has moved decisively to Node.js:</p>
<ul>
<li><code>proxy.ts</code> runs only on Node.js (16.0).</li>
<li>Cache Components requires the Node.js runtime (16.0).</li>
<li>The route segment option <code>export const runtime = 'edge'</code> is marked <strong>deprecated</strong> in the docs (as of 16.3), with the advice to remove it; the error page <code>edge-runtime-deprecated</code> says the Node.js runtime needs no replacement.</li>
<li>Next.js 16.3 replaced web streams with native Node.js streams in the App Router rendering layer and reports up to 22% more requests handled under load.</li>
</ul>

<thead>
<tr>

</tr>
</thead>

<td>Web APIs subset + <code>AsyncLocalStorage</code> polyfill</td>

<p>The latency row is the one people forget: a function at the edge that makes three sequential queries to a database in one region pays the long round trip three times. Rendering next to the data and caching the output at the CDN usually wins.</p>

<h1 id="Chapter-7-—-Static-export-and-its-limits"><a href="#Chapter-7-—-Static-export-and-its-limits" class="headerlink" title="Chapter 7 — Static export and its limits"></a>Chapter 7 — Static export and its limits</h1>
<h2 id="What-output-export-produces"><a href="#What-output-export-produces" class="headerlink" title="What output: 'export' produces"></a>What <code>output: 'export'</code> produces</h2>
<p><code>output: 'export'</code> makes <code>next build</code> write plain files to <code>out/</code>: one HTML file per route, the RSC payload per route for client navigation, and the static assets. Server Components run <strong>at build time</strong>, like classic static-site generation. Any static host can serve the result.</p>
<p>This blog is exactly that. Its <code>next.config.mjs</code>, reduced to the export branch:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> nextConfig = {</span><br><span class="line">  <span class="hljs-attr">images</span>: { <span class="hljs-attr">unoptimized</span>: <span class="hljs-literal">true</span> },          <span class="hljs-comment">// no image optimiser at runtime</span></span><br><span class="line">  <span class="hljs-attr">reactStrictMode</span>: <span class="hljs-literal">true</span>,</span><br><span class="line">  <span class="hljs-attr">trailingSlash</span>: <span class="hljs-literal">true</span>,                    <span class="hljs-comment">// /2026/09/14/slug/index.html</span></span><br><span class="line">  <span class="hljs-attr">env</span>: { <span class="hljs-attr">NEXT_PUBLIC_BASE_PATH</span>: <span class="hljs-string">&#x27;/blog&#x27;</span> },</span><br><span class="line">  <span class="hljs-attr">output</span>: <span class="hljs-string">&#x27;export&#x27;</span>, <span class="hljs-attr">distDir</span>: <span class="hljs-string">&#x27;out&#x27;</span>, <span class="hljs-attr">basePath</span>: <span class="hljs-string">&#x27;/blog&#x27;</span>, <span class="hljs-attr">assetPrefix</span>: <span class="hljs-string">&#x27;/blog/&#x27;</span>,</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>It runs Next.js 14.2 with React 18.3, prerenders every post through <code>generateStaticParams</code>, and is served by GitHub Pages under <code>/blog</code>. <code>basePath</code> is why in-post image paths are rewritten at build time: a root-relative <code>/assets/...</code> link would 404 without the <code>/blog</code> prefix.</p>
<h2 id="What-it-cannot-do"><a href="#What-it-cannot-do" class="headerlink" title="What it cannot do"></a>What it cannot do</h2>
<p>From the Next.js static export guide, these need a server and are <strong>not supported</strong>:</p>
<ul>
<li>Dynamic routes with <code>dynamicParams: true</code>, or without <code>generateStaticParams()</code></li>
<li>Route Handlers that read the <code>Request</code> (only <code>GET</code> handlers that prerender, with <code>dynamic = 'force-static'</code>)</li>
<li><code>cookies()</code>, Server Actions, Draft Mode, ISR</li>
<li><code>rewrites</code>, <code>redirects</code>, <code>headers</code> from <code>next.config</code>, and Proxy</li>
<li>Image Optimization with the default loader (use <code>unoptimized</code> or a custom <code>loader</code>)</li>
<li>Intercepting Routes</li>
</ul>
<p><code>'use cache'</code> is also listed as not supported for static export. In <code>next dev</code>, using any of these on an export build errors as if <code>dynamic = 'error'</code> were set on the root layout.</p>
<p>A security side effect: an export has no Next.js server, so server-side vulnerabilities in the framework (the middleware bypass, the React Server Components remote code execution of December 2025) have nothing to attack. The trade is that every page must be knowable at build time and every &quot;dynamic&quot; feature becomes client-side JavaScript or a separate service.</p>
<blockquote>
<p><strong>Watch out:</strong> <code>NEXT_PUBLIC_</code> values and the <code>env</code> key in <code>next.config</code> are <strong>inlined into the JavaScript at build time</strong>. That is fine for a base path; it is a leak for anything secret (Post 03).</p>
</blockquote>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Predict-the-rendering-mode"><a href="#Exercise-1-—-Predict-the-rendering-mode" class="headerlink" title="Exercise 1 — Predict the rendering mode"></a>Exercise 1 — Predict the rendering mode</h2>
<p>In Next.js 15 without Cache Components, which of these routes are static? (a) a page that <code>await fetch(url)</code> with no options; (b) a page that reads <code>searchParams</code>; (c) a page with no data whose root layout reads <code>cookies()</code>; (d) a page with <code>export const revalidate = 60</code>.</p>
<details>
<summary>Solution</summary>
<p>(a) Static: prerendered at build, the fetch runs once. (b) Dynamic. (c) Dynamic: the layout is part of the route's tree. (d) Static with ISR every 60 seconds (unless something else makes it dynamic).</p>
</details>
<h2 id="Exercise-2-—-Real-404-while-streaming"><a href="#Exercise-2-—-Real-404-while-streaming" class="headerlink" title="Exercise 2 — Real 404 while streaming"></a>Exercise 2 — Real 404 while streaming</h2>
<p>A product page streams its details inside Suspense and calls <code>notFound()</code> inside the streamed component when the product is missing. Crawlers see status 200. Restructure it.</p>
<details>
<summary>Solution</summary>
<p>Do a cheap existence lookup at the top of the page, before any Suspense boundary: <code>const exists = await productExists(id); if (!exists) notFound()</code>. Then render the Suspense-wrapped details. The 404 status is sent before streaming starts. With <code>React.cache</code> or <code>'use cache'</code> on the lookup, the details component reuses the result.</p>
</details>
<h2 id="Exercise-3-—-Migrate-to-Cache-Components"><a href="#Exercise-3-—-Migrate-to-Cache-Components" class="headerlink" title="Exercise 3 — Migrate to Cache Components"></a>Exercise 3 — Migrate to Cache Components</h2>
<p>A Next.js 15 page has <code>export const revalidate = 3600</code>, fetches a product list, and reads <code>cookies()</code> for a currency. Migrate it for <code>cacheComponents: true</code>.</p>
<details>
<summary>Solution</summary>
<p>Remove <code>revalidate</code>. Put the product query in a function with <code>'use cache'</code> and <code>cacheLife('hours')</code>. Move the cookie read into a <code>&lt;Suspense&gt;</code>-wrapped <code>Prices</code> component that reads the currency and passes it as an argument to a cached <code>getPrices(currency)</code>. The list is in the shell; prices stream as a dynamic hole.</p>
</details>
<h2 id="Exercise-4-—-Fix-the-matcher"><a href="#Exercise-4-—-Fix-the-matcher" class="headerlink" title="Exercise 4 — Fix the matcher"></a>Exercise 4 — Fix the matcher</h2>
<p>A <code>proxy.ts</code> redirects users without a session cookie to <code>/login</code>. After deploying, the login page renders unstyled and the logo is missing. Explain and fix.</p>
<details>
<summary>Solution</summary>
<p>With no <code>matcher</code> (or an over-broad one), Proxy also runs for <code>_next/static</code>, <code>_next/image</code> and <code>public/</code> files, and redirects those requests to <code>/login</code>. Add a negative matcher that excludes <code>_next/static</code>, <code>_next/image</code> and static files, and exclude <code>/login</code> itself to avoid a redirect loop.</p>
</details>
<h2 id="Exercise-5-—-Runtime-choice"><a href="#Exercise-5-—-Runtime-choice" class="headerlink" title="Exercise 5 — Runtime choice"></a>Exercise 5 — Runtime choice</h2>
<p>A team wants <code>export const runtime = 'edge'</code> on a dashboard route that runs four Postgres queries per request, to &quot;make it faster&quot;. Advise them for Next.js 16.3.</p>
<details>
<summary>Solution</summary>
<p>Do not. <code>runtime = 'edge'</code> is deprecated, incompatible with Cache Components, and puts the function far from a single-region database, so four sequential round trips get slower. Keep the Node.js runtime near the database, cache what can be cached with <code>'use cache'</code>, stream the rest, and let the CDN serve the static shell.</p>
</details>
<h2 id="Exercise-6-—-Static-export-audit"><a href="#Exercise-6-—-Static-export-audit" class="headerlink" title="Exercise 6 — Static export audit"></a>Exercise 6 — Static export audit</h2>
<p>List which of these features would break if this blog added them: a search page reading <code>?q=</code> on the server, an RSS feed as a <code>GET</code> Route Handler, a comment form using a Server Action, <code>next/image</code> with default settings.</p>
<details>
<summary>Solution</summary>
<p>Breaks: server-side <code>?q=</code> (needs a request; do the search in a Client Component over a prebuilt index), Server Action (no server), <code>next/image</code> default loader (needs the optimiser; keep <code>unoptimized</code> or use a custom loader). Works: the RSS <code>GET</code> handler with <code>dynamic = 'force-static'</code>, which is written to a file at build time.</p>
</details>
