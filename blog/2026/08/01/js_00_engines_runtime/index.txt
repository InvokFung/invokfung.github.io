11:Te3b7,<p>JavaScript is not &quot;interpreted&quot; and not &quot;compiled&quot; — in a modern engine it is both, several times over, and the engine changes its mind while your code runs. A function starts as bytecode, gets promoted to machine code when it turns hot, gets thrown back to bytecode when one of the guesses behind that machine code turns out wrong, and all the while a garbage collector moves its objects around in memory. Almost every &quot;mysterious&quot; performance cliff in a senior engineer's career — the loop that is fast on Monday and five times slower after a harmless refactor, the service whose p99 latency spikes every few seconds — comes from this machinery. This first post of the series opens up V8, the engine behind Chrome, Edge, Node.js and Deno: its compiler tiers, hidden classes, inline caches, deoptimization, elements kinds and the Orinoco garbage collector, then places the engine inside the runtimes that host it.</p>

<h1 id="Chapter-1-—-Engine-vs-host"><a href="#Chapter-1-—-Engine-vs-host" class="headerlink" title="Chapter 1 — Engine vs host"></a>Chapter 1 — Engine vs host</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Engine</strong> — implements the ECMAScript specification: parsing, the object model, built-ins such as <code>Array</code> and <code>Promise</code>, and the job queue for promise reactions. V8, SpiderMonkey and JavaScriptCore are engines.</li>
<li><strong>Host (embedder)</strong> — the program that embeds the engine and gives it a world: the event loop, timers, networking, the DOM, the file system. Chrome's Blink, Node.js, Deno, Bun and Cloudflare's <code>workerd</code> are hosts.</li>
<li><strong>Isolate</strong> — one independent V8 heap with its own garbage collector. A browser tab's main thread, each Web Worker and each Node <code>worker_threads</code> worker run in separate isolates. Isolates share no JavaScript objects.</li>
<li><strong>Realm</strong> — one set of global objects and built-ins (<code>globalThis</code>, <code>Array</code>, <code>Object.prototype</code>). An <code>&lt;iframe&gt;</code> is a new realm in the same isolate, which is why <code>arr instanceof Array</code> fails for an array from another frame while <code>Array.isArray(arr)</code> does not.</li>
<li><strong>Job</strong> — the specification's word for a queued unit of work. The engine asks the host to schedule promise jobs (<code>HostEnqueuePromiseJob</code>); the host decides <em>when</em> they run. That is why microtask timing is defined by HTML and Node, not by ECMAScript alone.</li>
</ul>
<p>The split matters in practice because the specification says nothing about <code>setTimeout</code>, <code>fetch</code>, <code>process.nextTick</code>, <code>require</code> or the DOM. When behaviour differs between Chrome and Node, the engine is usually identical (both V8) and the host is the difference.</p>

<h2 id="Parsing-most-functions-are-parsed-twice"><a href="#Parsing-most-functions-are-parsed-twice" class="headerlink" title="Parsing: most functions are parsed twice"></a>Parsing: most functions are parsed twice</h2>
<p>Full parsing is expensive, and most functions in a large bundle never run. V8 therefore <strong>pre-parses</strong> inner functions: it checks syntax and records which variables they capture, but builds no AST and no bytecode. The full parse and bytecode generation happen on the first call (&quot;lazy compilation&quot;). A function that is called immediately pays twice, so V8 uses heuristics — for example a function expression wrapped in parentheses (<code>(function () { … })()</code>) is compiled eagerly.</p>
<p>Consequences:</p>
<ul>
<li>Startup cost is dominated by <em>how much code is parsed</em>, not how much exists. Code splitting and lazy <code>import()</code> help because unparsed code costs nothing.</li>
<li>Compiled bytecode can be cached. Chrome caches it for scripts it sees repeatedly; Node offers a module compile cache (<code>NODE_COMPILE_CACHE=dir</code>, added in v22.1.0) that persists it to disk between runs, useful for CLIs.</li>
</ul>

<p>The bracketed numbers after each operation are <strong>feedback slots</strong>. Every property access, call and arithmetic operation records what it saw — which object shapes, whether the operands were small integers or doubles — into the function's <strong>feedback vector</strong>. Everything the optimising tiers do is built on this record. Code that never ran has no feedback, and the optimisers cannot specialise it.</p>
<h2 id="Tiering-up-and-OSR"><a href="#Tiering-up-and-OSR" class="headerlink" title="Tiering up and OSR"></a>Tiering up and OSR</h2>
<p>V8 counts how much a function runs (invocations and loop iterations, weighted by bytecode size) and promotes it when budgets run out. The exact thresholds are internal heuristics that change between releases; do not design around numbers.</p>
<p>A long-running loop inside a function that is called only once would never tier up by call count, so V8 performs <strong>on-stack replacement (OSR)</strong>: it compiles an optimised version while the loop is running and jumps into it mid-loop.</p>
<blockquote>
<p><strong>Watch out:</strong> Node's defaults do not always match Chrome's. Chrome has enabled Maglev since M117, but at least one Node 22 release line ships with <code>--no-maglev</code> as the default. Check your own binary with <code>node --v8-options | grep -A1 ' --maglev '</code> before assuming a tier exists.</p>
</blockquote>
<h2 id="Speculation-is-the-whole-trick"><a href="#Speculation-is-the-whole-trick" class="headerlink" title="Speculation is the whole trick"></a>Speculation is the whole trick</h2>
<p>An optimising compiler for a dynamic language cannot know that <code>p.x</code> is a small integer. It <strong>speculates</strong> from feedback: &quot;every <code>p</code> seen so far had shape M1, and <code>p.x</code> was always a Smi&quot;. It emits a cheap check (a <em>guard</em>) followed by a fast path — a load at a fixed offset, an integer add. If the guard fails at run time, the optimised code cannot continue; it <strong>deoptimizes</strong> (Chapter 5). Fast JavaScript is JavaScript whose guards rarely fail.</p>
<hr>
<h1 id="Chapter-3-—-Hidden-classes-maps"><a href="#Chapter-3-—-Hidden-classes-maps" class="headerlink" title="Chapter 3 — Hidden classes (maps)"></a>Chapter 3 — Hidden classes (maps)</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Map</strong> (V8's term; &quot;hidden class&quot; or <strong>shape</strong> elsewhere) — a descriptor attached to every heap object that records its property names, their order, their attributes and where each value is stored.</li>
<li><strong>Transition</strong> — the edge from one map to another when a property is added. Maps form a <strong>transition tree</strong> rooted at the empty object's map.</li>
<li><strong>In-object property</strong> — a value stored directly inside the object's memory; the fastest kind of access.</li>
<li><strong>Properties backing store</strong> — an out-of-line array for properties that did not fit in-object.</li>
<li><strong>Dictionary mode</strong> (&quot;slow properties&quot;) — the object drops its map-based layout and stores properties in a hash table.</li>
</ul>
<h2 id="How-shapes-are-built"><a href="#How-shapes-are-built" class="headerlink" title="How shapes are built"></a>How shapes are built</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">Point</span>(<span class="hljs-params">x, y</span>) {</span><br><span class="line">  <span class="hljs-variable language_">this</span>.<span class="hljs-property">x</span> = x;   <span class="hljs-comment">// map M0 (empty) -&gt; M1 {x}</span></span><br><span class="line">  <span class="hljs-variable language_">this</span>.<span class="hljs-property">y</span> = y;   <span class="hljs-comment">// map M1 -&gt; M2 {x, y}</span></span><br><span class="line">}</span><br><span class="line"><span class="hljs-keyword">const</span> a = <span class="hljs-keyword">new</span> <span class="hljs-title class_">Point</span>(<span class="hljs-number">1</span>, <span class="hljs-number">2</span>);</span><br><span class="line"><span class="hljs-keyword">const</span> b = <span class="hljs-keyword">new</span> <span class="hljs-title class_">Point</span>(<span class="hljs-number">3</span>, <span class="hljs-number">4</span>);   <span class="hljs-comment">// follows the same transitions: same map M2</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>For constructors and classes, V8 uses <strong>slack tracking</strong>: the first objects created get extra in-object space, and after a number of constructions V8 shrinks the allocation to what was actually used. Properties added long after construction end up in the out-of-line backing store — still fast, one extra pointer hop.</p>
<h2 id="Rules-that-keep-shapes-stable"><a href="#Rules-that-keep-shapes-stable" class="headerlink" title="Rules that keep shapes stable"></a>Rules that keep shapes stable</h2>
<ol>
<li><strong>Initialise every field in the constructor (or as a class field), in the same order, even if the value is <code>null</code>.</strong> An object that gains <code>this.cache</code> later in some code paths splits the transition tree.</li>
<li><strong>Do not <code>delete</code> properties on hot objects.</strong> Set them to <code>undefined</code> or <code>null</code>. <code>delete</code> usually sends the object to dictionary mode for good (shown above).</li>
<li><strong>Use <code>Map</code> for dictionaries.</strong> An object used as a hash table with arbitrary keys will go to dictionary mode anyway, and then <code>Object.keys</code> and <code>for…in</code> are slower than <code>Map</code> iteration.</li>
<li><strong>Keep numeric field types consistent.</strong> A field that holds Smis in some objects and doubles in others forces the map to generalise the field's representation.</li>
<li><strong>Do not mutate prototypes of live objects</strong> (<code>Object.setPrototypeOf</code>, assigning <code>__proto__</code>). Prototype maps are special; changing them invalidates optimised code that depended on them.</li>
</ol>
<blockquote>
<p><strong>Common pitfall:</strong> &quot;optional&quot; fields added by spreading different objects: <code>{ ...base, ...(flag ? { extra: 1 } : {}) }</code> creates two shapes from one call site. In a hot path, write <code>{ ...base, extra: flag ? 1 : undefined }</code> so every result has the same keys in the same order.</p>
</blockquote>

<h2 id="Where-megamorphism-comes-from-in-real-code"><a href="#Where-megamorphism-comes-from-in-real-code" class="headerlink" title="Where megamorphism comes from in real code"></a>Where megamorphism comes from in real code</h2>
<ul>
<li><strong>Generic utilities</strong> — a <code>get(obj, path)</code> helper, a deep-equal, a serializer, a logger's <code>format(entry)</code> — see every shape in the program. They are megamorphic by design. That is acceptable if they are not your hot loop.</li>
<li><strong>Component frameworks</strong> — a renderer that reads <code>props.children</code> on thousands of different component prop objects. Framework authors work hard to keep internal objects (fibers, vnodes) one shape, and you should keep your own hot records the same way.</li>
<li><strong>Heterogeneous arrays</strong> — an array of events where each type is a differently shaped object. Consider a single shape with a <code>type</code> tag and the same fields (some <code>null</code>) for the hot processing path.</li>
<li><strong>Class hierarchies</strong> — instances of different subclasses have different maps. A loop over <code>Shape[]</code> calling <code>area()</code> is polymorphic in the call site; with more than four subclasses it goes megamorphic.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> normalise at the boundary. Parse external data (JSON, database rows) into objects created by one factory or class with a fixed field order. The rest of the program then sees one map.</p>
</blockquote>

<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">[bailout (kind: deopt-eager, reason: wrong map): begin. deoptimizing … &lt;JSFunction add …&gt;, … &lt;Code TURBOFAN&gt;, opt id 0, bytecode offset 0, …]</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The two fields to read are <strong>kind</strong> and <strong>reason</strong>. Common reasons: <code>wrong map</code> (shape changed), <code>not a Smi</code> / <code>lost precision</code> (number representation changed), <code>out of bounds</code> (array index past length), <code>wrong call target</code>, <code>Insufficient type feedback</code>.</p>
<h2 id="Failure-modes"><a href="#Failure-modes" class="headerlink" title="Failure modes"></a>Failure modes</h2>
<ul>
<li><strong>Deopt loops.</strong> A function optimises, deopts, re-optimises with slightly wider feedback, deopts again. Each round throws away compile work, and the function spends much of its life in the lower tiers. The symptom is a function that stays slow however hot it is. <code>--trace-opt --trace-deopt</code> shows the cycle.</li>
<li><strong>One-time deopts are normal.</strong> A few at startup cost microseconds. Chase deopts only when a profile shows the function is hot <em>and</em> the trace shows repetition.</li>
<li><strong>Stale advice.</strong> &quot;<code>try/catch</code> disables optimisation&quot; and &quot;never use <code>arguments</code>&quot; date from Crankshaft, the compiler TurboFan replaced in 2017. TurboFan optimises <code>try/catch</code>. Rest parameters are still clearer than <code>arguments</code>, but for readability, not speed.</li>
</ul>
<h2 id="Measuring-without-fooling-yourself"><a href="#Measuring-without-fooling-yourself" class="headerlink" title="Measuring without fooling yourself"></a>Measuring without fooling yourself</h2>
<p>Microbenchmarks in a JIT are hazardous:</p>
<ul>
<li><strong>Warm-up.</strong> The first iterations run in Ignition. Measure after warm-up, or measure a realistic workload end to end.</li>
<li><strong>Dead-code elimination.</strong> If the result is unused, TurboFan may delete the work. Always consume the result (the <code>sum &gt; 0</code> above).</li>
<li><strong>Constant folding.</strong> Inputs known at compile time can be folded away. Take inputs from <code>process.argv</code> or data.</li>
<li><strong>Feedback pollution.</strong> Covered above: separate processes per case.</li>
<li><strong>GC noise.</strong> An allocation-heavy loop measures the garbage collector as much as your code. Run several times and report the spread.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> use <code>%</code> natives only to <em>explain</em> a result you have already measured, never in shipped code. They are internal, unstable and disabled without <code>--allow-natives-syntax</code>.</p>
</blockquote>

<h1 id="Chapter-6-—-Numbers-and-elements-kinds"><a href="#Chapter-6-—-Numbers-and-elements-kinds" class="headerlink" title="Chapter 6 — Numbers and elements kinds"></a>Chapter 6 — Numbers and elements kinds</h1>
<h2 id="Smis-and-heap-numbers"><a href="#Smis-and-heap-numbers" class="headerlink" title="Smis and heap numbers"></a>Smis and heap numbers</h2>
<p>V8 represents small integers as <strong>Smis</strong> — tagged values stored directly in the pointer, with no allocation. With pointer compression (Chrome on 64-bit) a Smi is 31 bits (−2³⁰ to 2³⁰−1); builds without pointer compression, typical for Node, use 32-bit Smis on 64-bit platforms. Anything else — fractions, <code>-0</code>, <code>NaN</code>, <code>Infinity</code>, integers outside the Smi range — is a <strong>HeapNumber</strong> (a boxed double), unless the optimiser can keep it unboxed in a register or a double field.</p>
<h2 id="Elements-kinds"><a href="#Elements-kinds" class="headerlink" title="Elements kinds"></a>Elements kinds</h2>
<p>Array-indexed properties (the <em>elements</em>) are tracked separately from named properties, with their own &quot;kind&quot;. V8 distinguishes 21 elements kinds; the six you meet daily form a lattice:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="text"><span class="line">PACKED_SMI_ELEMENTS    →  PACKED_DOUBLE_ELEMENTS  →  PACKED_ELEMENTS</span><br><span class="line">        ↓                          ↓                        ↓</span><br><span class="line">HOLEY_SMI_ELEMENTS     →  HOLEY_DOUBLE_ELEMENTS   →  HOLEY_ELEMENTS</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Transitions only go <strong>right or down</strong>, towards more general kinds — never back:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> a = [<span class="hljs-number">1</span>, <span class="hljs-number">2</span>, <span class="hljs-number">3</span>];   <span class="hljs-comment">// PACKED_SMI_ELEMENTS</span></span><br><span class="line">a.<span class="hljs-title function_">push</span>(<span class="hljs-number">4.56</span>);          <span class="hljs-comment">// PACKED_DOUBLE_ELEMENTS</span></span><br><span class="line">a.<span class="hljs-title function_">push</span>(<span class="hljs-string">&#x27;x&#x27;</span>);           <span class="hljs-comment">// PACKED_ELEMENTS</span></span><br><span class="line">a[<span class="hljs-number">9</span>] = <span class="hljs-number">1</span>;              <span class="hljs-comment">// HOLEY_ELEMENTS (indices 5-8 are holes) - holey forever,</span></span><br><span class="line">                       <span class="hljs-comment">// even if you later fill every hole</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Why holes cost: reading a hole means &quot;not here — look up the prototype chain&quot;, so every holey read needs an extra check, and the engine must be sure nobody added indexed properties to <code>Array.prototype</code> or <code>Object.prototype</code>.</p>
<p>Practical rules (from the V8 team's own guidance):</p>
<ul>
<li>Prefer literals and <code>push</code> over <code>new Array(n)</code>, which creates a <strong>holey</strong> array. If you need a pre-sized numeric buffer, use a typed array (<code>new Float64Array(n)</code>), which has no holes and a fixed element type.</li>
<li>Keep <code>-0</code>, <code>NaN</code> and <code>Infinity</code> out of integer arrays unless they are real data; one such value turns a Smi array into a double array.</li>
<li>Do not read past <code>length</code> (<code>while (arr[i] != null)</code> style loops); an out-of-bounds read walks the prototype chain and can deopt.</li>
<li>Convert array-likes (<code>arguments</code>, <code>NodeList</code>) to real arrays once, then loop over the array.</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> <code>Array(n).fill(0)</code> is still HOLEY_SMI_ELEMENTS — <code>fill</code> puts values in the holes but the array stays holey (holey is permanent). <code>Array.from({ length: n }, () =&gt; 0)</code> builds a packed array. The difference only matters in genuinely hot numeric code; do not rewrite ordinary code for it.</p>
</blockquote>

<h1 id="Chapter-7-—-The-Orinoco-garbage-collector"><a href="#Chapter-7-—-The-Orinoco-garbage-collector" class="headerlink" title="Chapter 7 — The Orinoco garbage collector"></a>Chapter 7 — The Orinoco garbage collector</h1>
<h2 id="Terminology-2"><a href="#Terminology-2" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Generational hypothesis</strong> — most objects die young. A GC that collects young objects often and cheaply wins.</li>
<li><strong>Young generation</strong> — where new objects are allocated. In V8 it is split into a <strong>nursery</strong> and an <strong>intermediate</strong> generation.</li>
<li><strong>Old generation</strong> — objects that survived two young collections.</li>
<li><strong>Scavenge</strong> (minor GC) — copying collection of the young generation.</li>
<li><strong>Mark-Compact</strong> (major GC) — marking live objects in the whole heap, sweeping dead ones, compacting fragmented pages.</li>
<li><strong>Write barrier</strong> — a small piece of code the engine runs on every pointer store into the heap, so concurrent or incremental marking does not miss new references, and old-to-young pointers are remembered.</li>
<li><strong>Stop-the-world pause</strong> — time the main thread spends in GC instead of running JavaScript.</li>
</ul>
<h2 id="Young-generation-the-scavenger"><a href="#Young-generation-the-scavenger" class="headerlink" title="Young generation: the scavenger"></a>Young generation: the scavenger</h2>
<p>New objects go into the nursery with bump-pointer allocation (very cheap). When the young space fills, a <strong>scavenge</strong> copies live objects out: survivors of their first scavenge become <em>intermediate</em>; survivors of a second are <strong>promoted</strong> to the old generation. The young generation uses a <strong>semi-space</strong> design, so half of it is always empty to receive the copies. Cost is proportional to the number of <em>live</em> objects, not the garbage — dying young is nearly free.</p>
<p>The scavenger runs <strong>in parallel</strong> on helper threads; the V8 team measured a 20–50% reduction in main-thread young-generation GC time from parallel scavenging.</p>
<p>Node exposes the size knob: <code>--max-semi-space-size</code> (MiB). The Node docs note that the young generation is <strong>three times</strong> the semi-space size, so +1 MiB of semi-space adds 3 MiB of heap. Raising it can cut scavenges for allocation-heavy servers; benchmark before and after.</p>
<h2 id="Old-generation-concurrent-mark-compact"><a href="#Old-generation-concurrent-mark-compact" class="headerlink" title="Old generation: concurrent mark-compact"></a>Old generation: concurrent mark-compact</h2>
<ul>
<li><strong>Marking</strong> finds everything reachable from the roots (stack, globals, handles). V8 does most of it <strong>concurrently</strong> on background threads while JavaScript runs, plus <strong>incremental</strong> steps on the main thread. Write barriers keep it correct while your code mutates the heap.</li>
<li><strong>Sweeping</strong> frees dead objects' memory into free lists, concurrently.</li>
<li><strong>Compaction</strong> moves objects out of fragmented pages, in parallel, during a pause.</li>
<li><strong>Large objects</strong> (above a size threshold) live in a separate large-object space and are never moved.</li>
<li><strong>Idle-time GC</strong>: the browser tells V8 when a frame finished early, and V8 uses the idle slice for GC work.</li>
</ul>
<p>Concurrent marking and sweeping reduced pause times in heavy WebGL games by up to 50%, per the V8 team.</p>
<p>In Chrome, Blink's C++ DOM objects are managed by <strong>Oilpan</strong> (<code>cppgc</code>) and traced together with the JavaScript heap, so a cycle between a DOM node and a JavaScript closure is still collectable.</p>
<h2 id="Reading-trace-gc"><a href="#Reading-trace-gc" class="headerlink" title="Reading --trace-gc"></a>Reading <code>--trace-gc</code></h2>

<p>Healthy services show frequent sub-millisecond scavenges and rare mark-compacts. Warning signs: mark-compacts that free little memory (<code>232.8 -&gt; 200.3</code> after a 224 ms pause is a heap full of live data), <code>mu</code> trending down, and heap &quot;after&quot; values that climb from one major GC to the next — a leak, which Post 05 hunts with heap snapshots.</p>
<blockquote>
<p><strong>Watch out:</strong> <code>--max-old-space-size</code> is a ceiling, not a target. Setting it above the container's memory limit lets the heap grow until the kernel OOM-kills the process instead of V8 throwing a clean &quot;heap out of memory&quot;. Set it below the container limit, leaving room for buffers, native memory and the young generation.</p>
</blockquote>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Engine-or-host"><a href="#Exercise-1-—-Engine-or-host" class="headerlink" title="Exercise 1 — Engine or host?"></a>Exercise 1 — Engine or host?</h2>
<p>For each, say whether the engine or the host defines it: (a) <code>Array.prototype.map</code>, (b) <code>setTimeout</code>, (c) the order of promise <code>then</code> callbacks relative to each other, (d) when promise callbacks run relative to a <code>click</code> event, (e) <code>structuredClone</code>, (f) <code>import()</code> resolving a bare specifier like <code>&quot;react&quot;</code>.</p>
<details><summary>Solution</summary>
<p>(a) Engine — ECMAScript built-in. (b) Host — HTML / Node timers. (c) Engine — the spec requires promise jobs to run in the order they were enqueued. (d) Host — HTML decides when it performs a microtask checkpoint. (e) Host — defined by the HTML standard, adopted by server runtimes. (f) Both: <code>import()</code> syntax and module semantics are ECMAScript, but <em>resolving</em> a specifier to a file or URL is host-defined (Node's resolution algorithm, a browser import map).</p>
</details>
<h2 id="Exercise-2-—-Predict-the-maps"><a href="#Exercise-2-—-Predict-the-maps" class="headerlink" title="Exercise 2 — Predict the maps"></a>Exercise 2 — Predict the maps</h2>
<p>How many distinct maps end up in <code>list</code>?</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> list = [];</span><br><span class="line"><span class="hljs-keyword">for</span> (<span class="hljs-keyword">let</span> i = <span class="hljs-number">0</span>; i &lt; <span class="hljs-number">6</span>; i++) {</span><br><span class="line">  <span class="hljs-keyword">const</span> o = { <span class="hljs-attr">id</span>: i };</span><br><span class="line">  <span class="hljs-keyword">if</span> (i % <span class="hljs-number">2</span>) o.<span class="hljs-property">name</span> = <span class="hljs-string">&#x27;odd&#x27;</span>;</span><br><span class="line">  <span class="hljs-keyword">if</span> (i % <span class="hljs-number">3</span> === <span class="hljs-number">0</span>) o.<span class="hljs-property">tag</span> = <span class="hljs-string">&#x27;three&#x27;</span>;</span><br><span class="line">  list.<span class="hljs-title function_">push</span>(o);</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details><summary>Solution</summary>
<p>List the property sequences: i=0 <code>{id, tag}</code>, i=1 <code>{id, name}</code>, i=2 <code>{id}</code>, i=3 <code>{id, name, tag}</code>, i=4 <code>{id}</code>, i=5 <code>{id, name}</code>. Distinct: <code>{id}</code>, <code>{id, name}</code>, <code>{id, tag}</code>, <code>{id, name, tag}</code> — <strong>four maps</strong>. A function reading <code>o.id</code> across this list is polymorphic (4 maps, the limit). Add one more optional field and it goes megamorphic. Fix: <code>const o = { id: i, name: i % 2 ? 'odd' : null, tag: i % 3 === 0 ? 'three' : null };</code> gives one map.</p>
</details>
<h2 id="Exercise-3-—-Reproduce-the-megamorphic-step"><a href="#Exercise-3-—-Reproduce-the-megamorphic-step" class="headerlink" title="Exercise 3 — Reproduce the megamorphic step"></a>Exercise 3 — Reproduce the megamorphic step</h2>
<p>Run <code>poly.js</code> from Chapter 4 for n = 1, 2, 3, 4, 5, 6 on your machine. Where is the jump? Then change <code>getX</code> to read a property added <em>after</em> the varying one (<code>o.q = 1</code> after the loop line, read <code>o.q</code>). Does anything change?</p>
<details><summary>Solution</summary>
<p>The jump appears between 4 and 5 shapes, where the IC turns megamorphic. Reading <code>q</code> instead of <code>x</code> still sees n maps (the maps differ because of the earlier varying property), so the curve is the same. Map identity depends on the whole transition path, not just the property being read.</p>
</details>
<h2 id="Exercise-4-—-Read-a-deopt"><a href="#Exercise-4-—-Read-a-deopt" class="headerlink" title="Exercise 4 — Read a deopt"></a>Exercise 4 — Read a deopt</h2>
<p>A trace shows <code>kind: deopt-eager, reason: not a Smi</code> repeating every few seconds for <code>computeTotal</code>. What changed in the data, and what are two fixes?</p>
<details><summary>Solution</summary>
<p><code>computeTotal</code> was optimised on feedback that a value was always a small integer; now it periodically receives a fraction or a large integer (e.g. a price like <code>19.99</code>, or an ID above the Smi range). Fixes: (1) make the representation consistent from the start — e.g. keep money in integer cents, or ensure warm-up covers doubles so the optimiser plans for them; (2) stop mixing types — parse values to numbers once at the boundary instead of sometimes receiving strings. Repeating deopts point to a deopt loop; confirm with <code>--trace-opt --trace-deopt</code>.</p>
</details>
<h2 id="Exercise-5-—-Elements-kinds"><a href="#Exercise-5-—-Elements-kinds" class="headerlink" title="Exercise 5 — Elements kinds"></a>Exercise 5 — Elements kinds</h2>
<p>Give the elements kind after each line: <code>const a = new Array(3);</code> · <code>a[0] = 1; a[1] = 2; a[2] = 3;</code> · <code>const b = [1, 2, 3].map(x =&gt; x / 2);</code> · <code>const c = [1, 2, 3]; c.push(-0);</code></p>
<details><summary>Solution</summary>
<p><code>new Array(3)</code> → HOLEY_SMI_ELEMENTS. Filling all three slots → still HOLEY_SMI_ELEMENTS (holey is permanent). <code>b</code> → PACKED_DOUBLE_ELEMENTS (<code>map</code> builds a fresh packed array; 0.5 and 1.5 are doubles). <code>c.push(-0)</code> → PACKED_DOUBLE_ELEMENTS, because <code>-0</code> cannot be a Smi.</p>
</details>
<h2 id="Exercise-6-—-Diagnose-a-GC-trace"><a href="#Exercise-6-—-Diagnose-a-GC-trace" class="headerlink" title="Exercise 6 — Diagnose a GC trace"></a>Exercise 6 — Diagnose a GC trace</h2>
<p>A Node API in a 1 GiB container runs with <code>--max-old-space-size=4096</code>. Under load, <code>--trace-gc</code> shows Mark-Compact lines every few seconds, each pausing 300–600 ms and freeing under 5% of the heap; then the pod restarts with exit code 137. Explain and fix.</p>
<details><summary>Solution</summary>
<p>The heap is mostly live data (a leak or an unbounded cache), so each major GC works hard and frees little, and pauses grow with heap size. Because the V8 limit (4096 MiB) is above the container limit (1 GiB), V8 never throws &quot;heap out of memory&quot;; the kernel's OOM killer ends the process (137 = SIGKILL). Fix: set <code>--max-old-space-size</code> below the container limit (for example around 700–768 MiB for 1 GiB, leaving room for native memory) so failures are visible and diagnosable, then find the retained objects with heap snapshots (Post 05) — usually an unbounded <code>Map</code>, a listener that is never removed, or closures captured in a global.</p>
</details>
