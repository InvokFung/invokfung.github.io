<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>

<li><strong>Projection</strong> — the act of a kubelet rendering a ConfigMap or Secret into a Pod's filesystem.</li>
<li><strong>Hot reload</strong> — the application noticing a configuration change without being restarted.</li>
<li><strong>Immutable object</strong> — a ConfigMap or Secret marked <code>immutable: true</code>, which can never be updated, only replaced.</li>

<h2 id="The-propagation-delay"><a href="#The-propagation-delay" class="headerlink" title="The propagation delay"></a>The propagation delay</h2>
<p>Mounted files do not update instantly. The kubelet refreshes projected volumes on its periodic sync, using a locally cached copy of the object. The worst-case delay is therefore roughly the <strong>kubelet sync period</strong> (<code>--sync-frequency</code>, default 1 minute) <strong>plus the ConfigMap/Secret cache propagation delay</strong> (watch-based by default; the TTL-based strategy defaults to another minute). In practice, budget for changes appearing within about two minutes, not immediately.</p>
<p>Three further caveats:</p>
<ul>
<li>Updates are <strong>atomic per volume</strong>. The kubelet writes a new timestamped directory and swings a symlink, so an application never reads a half-updated set of files. Watch the <em>directory</em>, not the file inode — many file watchers miss the symlink swap.</li>
<li>The application still has to <em>do</em> something. A file changing on disk is not a reload; something must re-read it. Either implement a watcher, or accept a restart.</li>
<li><code>subPath</code> is the classic trap. It is used to drop a single file into a directory that already has other content (<code>/etc/nginx/conf.d/app.conf</code>), and it silently opts you out of updates entirely.</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> &quot;I edited the ConfigMap and nothing happened.&quot; Check which of the three consumption forms you used. If it is <code>env</code> or <code>subPath</code>, nothing <em>will</em> happen. Roll the Deployment.</p>
</blockquote>
<h2 id="Secrets-and-what-they-actually-protect"><a href="#Secrets-and-what-they-actually-protect" class="headerlink" title="Secrets, and what they actually protect"></a>Secrets, and what they actually protect</h2>
<p>A Secret looks exactly like a ConfigMap with a different <code>kind</code> and a <code>stringData</code> convenience field.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">apiVersion:</span> <span class="hljs-string">v1</span></span><br><span class="line"><span class="hljs-attr">kind:</span> <span class="hljs-string">Secret</span></span><br><span class="line"><span class="hljs-attr">metadata:</span> { <span class="hljs-attr">name:</span> <span class="hljs-string">db-credentials</span>, <span class="hljs-attr">namespace:</span> <span class="hljs-string">shop</span> }</span><br><span class="line"><span class="hljs-attr">type:</span> <span class="hljs-string">Opaque</span></span><br><span class="line"><span class="hljs-attr">stringData:</span>                <span class="hljs-comment"># written as plain text, stored base64-encoded</span></span><br><span class="line">  <span class="hljs-attr">DB_PASSWORD:</span> <span class="hljs-string">&quot;s3cr3t-do-not-commit&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h3 id="The-blunt-truth"><a href="#The-blunt-truth" class="headerlink" title="The blunt truth"></a>The blunt truth</h3>
<p><strong>A Secret is base64-encoded, not encrypted.</strong> Base64 is an encoding, not a cipher; <code>kubectl get secret db-credentials -o jsonpath='{.data.DB_PASSWORD}' | base64 -d</code> prints the password, and anyone with <code>get secrets</code> permission in that namespace can do it. By default the value also sits in <strong>etcd in plain text</strong>, which means an etcd backup, a stolen disk snapshot, or a compromised control-plane node exposes it.</p>
<p>What a Secret actually buys you over a ConfigMap:</p>
<ul>
<li>It is a distinct resource kind, so <strong>RBAC can be written against it separately</strong> (Post 07). This is the real benefit.</li>
<li>Its values are not printed by <code>kubectl describe</code>.</li>
<li>The kubelet stores projected Secret volumes in <code>tmpfs</code>, so they do not touch the node's disk.</li>
<li>It is only distributed to nodes running a Pod that requests it.</li>
</ul>
<p>What it does <strong>not</strong> buy you: encryption, audit of reads by the application, rotation, or safety from anyone who can <code>exec</code> into the Pod.</p>

<h1 id="Chapter-2-—-Forcing-a-rollout-when-configuration-changes"><a href="#Chapter-2-—-Forcing-a-rollout-when-configuration-changes" class="headerlink" title="Chapter 2 — Forcing a rollout when configuration changes"></a>Chapter 2 — Forcing a rollout when configuration changes</h1>
<p>Because <code>env</code>-injected values do not hot-reload, and because most applications cannot reload files anyway, the honest default is: <strong>treat a configuration change as a deployment</strong>. Two patterns make that reliable.</p>
<h2 id="Immutable-ConfigMaps-and-Secrets"><a href="#Immutable-ConfigMaps-and-Secrets" class="headerlink" title="Immutable ConfigMaps and Secrets"></a>Immutable ConfigMaps and Secrets</h2>
<p>Set <code>immutable: true</code> (stable since Kubernetes 1.21). The object can then never be edited — only deleted and recreated under a new name. This removes an entire class of &quot;someone edited the live ConfigMap and half the fleet is now on different config&quot;, and it also lets the kubelet stop watching the object, which measurably reduces API server load on large clusters.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">apiVersion:</span> <span class="hljs-string">v1</span></span><br><span class="line"><span class="hljs-attr">kind:</span> <span class="hljs-string">ConfigMap</span></span><br><span class="line"><span class="hljs-attr">metadata:</span> { <span class="hljs-attr">name:</span> <span class="hljs-string">web-config-7f3a91c</span> }   <span class="hljs-comment"># name carries a content hash</span></span><br><span class="line"><span class="hljs-attr">immutable:</span> <span class="hljs-literal">true</span></span><br><span class="line"><span class="hljs-attr">data:</span></span><br><span class="line">  <span class="hljs-attr">LOG_LEVEL:</span> <span class="hljs-string">&quot;info&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Kustomize's <code>configMapGenerator</code> and Helm both have idioms for hash-suffixed names; a new hash produces a new object name, the Deployment template references the new name, and the template change triggers a rollout automatically.</p>
<h2 id="The-checksum-annotation"><a href="#The-checksum-annotation" class="headerlink" title="The checksum annotation"></a>The checksum annotation</h2>
<p>When the ConfigMap name is fixed, put a hash of its content in the <strong>Pod template annotations</strong>. Changing an annotation on the <em>template</em> changes the template, which is exactly what makes the Deployment controller create a new ReplicaSet.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">spec:</span></span><br><span class="line">  <span class="hljs-attr">template:</span></span><br><span class="line">    <span class="hljs-attr">metadata:</span></span><br><span class="line">      <span class="hljs-attr">annotations:</span></span><br><span class="line">        <span class="hljs-attr">checksum/config:</span> <span class="hljs-string">&quot;<span class="hljs-template-variable">{{ include (print $.Template.BasePath \&quot;/configmap.yaml\&quot;) . | sha256sum }}</span>&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Outside Helm, compute it in CI:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">CFG_HASH=$(kubectl create configmap web-config --from-file=./config --dry-run=client -o yaml | <span class="hljs-built_in">sha256sum</span> | <span class="hljs-built_in">cut</span> -c1-16)</span><br><span class="line">yq -i <span class="hljs-string">&quot;.spec.template.metadata.annotations.\&quot;checksum/config\&quot; = \&quot;<span class="hljs-variable">$CFG_HASH</span>\&quot;&quot;</span> k8s/web-deployment.yaml</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Trick:</strong> annotate the <strong>Pod template</strong>, not the Deployment's own <code>metadata.annotations</code>. An annotation on the Deployment object changes nothing about the Pods and triggers no rollout. This is a very common and very confusing mistake.</p>
</blockquote>

<h1 id="Chapter-3-—-Storage"><a href="#Chapter-3-—-Storage" class="headerlink" title="Chapter 3 — Storage"></a>Chapter 3 — Storage</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Volume</strong> — a directory available to the containers in a Pod, with a lifetime tied to the <strong>Pod</strong>. <code>emptyDir</code> is scratch space that vanishes with the Pod; <code>configMap</code>, <code>secret</code>, <code>downwardAPI</code> and <code>projected</code> are read-only data sources.</li>
<li><strong>PersistentVolume (PV)</strong> — a cluster-scoped object representing a real piece of storage (an EBS volume, a Ceph RBD image, an NFS export).</li>
<li><strong>PersistentVolumeClaim (PVC)</strong> — a namespaced <em>request</em> for storage: size, access mode, class. Pods reference PVCs, never PVs.</li>
<li><strong>StorageClass</strong> — a named recipe describing how to provision a PV on demand: which provisioner, which parameters, which reclaim and binding policy.</li>
<li><strong>CSI (Container Storage Interface)</strong> — the standard gRPC contract between Kubernetes and a storage vendor's driver.</li>
</ul>
<p>The indirection exists so that a workload author can ask for &quot;20 GiB, fast, exclusive&quot; without knowing whether the cluster runs on AWS, on-prem Ceph, or a laptop.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="text"><span class="line">Pod ──uses──► PVC ──bound to──► PV ──backed by──► real disk</span><br><span class="line">                │                 ▲</span><br><span class="line">                └──requests a────►│ dynamically provisioned by</span><br><span class="line">                   StorageClass ──┘  the CSI driver</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Static-versus-dynamic-provisioning"><a href="#Static-versus-dynamic-provisioning" class="headerlink" title="Static versus dynamic provisioning"></a>Static versus dynamic provisioning</h2>
<p><strong>Static</strong>: an administrator creates PVs by hand and users claim them. Necessary for pre-existing storage (an NFS export, a restored snapshot). <strong>Dynamic</strong>: the user creates a PVC naming a StorageClass, and the CSI driver provisions a matching PV automatically. Dynamic is the default in every managed cloud and is what you should use unless you have a specific reason not to.</p>

<h2 id="Access-modes-—-and-the-mistake-everyone-makes"><a href="#Access-modes-—-and-the-mistake-everyone-makes" class="headerlink" title="Access modes — and the mistake everyone makes"></a>Access modes — and the mistake everyone makes</h2>
<table>
<thead>
<tr>
<th>Mode</th>
<th>Short</th>
<th>Meaning</th>
</tr>
</thead>
<tbody>
<tr>
<td>ReadWriteOnce</td>
<td>RWO</td>
<td>mounted read-write by <strong>one node</strong> (several Pods on that node may share it)</td>
</tr>
<tr>
<td>ReadOnlyMany</td>
<td>ROX</td>
<td>mounted read-only by many nodes</td>

<tr>
<td>ReadWriteMany</td>
<td>RWX</td>

<p>The mistake: assuming <strong>RWX is available</strong>. It usually is not. Block storage — EBS, GCE PD, Azure Disk, most on-prem SANs — is RWO only, because a block device cannot safely be mounted read-write on two machines at once. RWX requires a <em>file</em> protocol: NFS, EFS, Azure Files, CephFS, Filestore. If your design has three replicas of a Deployment all writing to one shared volume, either budget for a networked filesystem (slower, more expensive, another thing to operate) or redesign so each replica owns its own volume — which is what a StatefulSet gives you.</p>
<p>Note also that RWO is per <strong>node</strong>, not per Pod. Two Pods of the same Deployment that happen to land on the same node can both write to one RWO volume and corrupt each other. RWOP exists precisely to prevent that.</p>
<h2 id="Reclaim-policy"><a href="#Reclaim-policy" class="headerlink" title="Reclaim policy"></a>Reclaim policy</h2>
<p>Set on the StorageClass (inherited by dynamically provisioned PVs) or directly on a static PV:</p>
<ul>
<li><strong>Delete</strong> — deleting the PVC deletes the PV <em>and the underlying disk</em>. The default for dynamic provisioning. Convenient; also how data gets destroyed by a careless <code>kubectl delete -f</code>.</li>
<li><strong>Retain</strong> — the PV survives in <code>Released</code> state, the data stays, and an administrator must manually clean up or re-bind. The correct choice for anything you would be upset to lose.</li>
<li><strong>Recycle</strong> — deprecated, do not use.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> for production databases, either use <code>reclaimPolicy: Retain</code> or make sure the StorageClass's <code>Delete</code> behaviour is compensated by real, tested, off-cluster backups. &quot;The PVC was deleted&quot; should not be an unrecoverable event.</p>
</blockquote>
<h2 id="volumeBindingMode-and-the-zone-mismatch-bug"><a href="#volumeBindingMode-and-the-zone-mismatch-bug" class="headerlink" title="volumeBindingMode and the zone-mismatch bug"></a>volumeBindingMode and the zone-mismatch bug</h2>
<p>This setting fixes a failure that is baffling the first time you hit it.</p>
<ul>
<li><code>Immediate</code> — the PV is provisioned as soon as the PVC is created, before any Pod exists. In a multi-zone cluster the provisioner has to guess a zone. If the scheduler later places the Pod in a <em>different</em> zone, the Pod cannot mount the volume and stays <code>Pending</code> forever with a <code>node(s) had volume node affinity conflict</code> event. Zonal block storage cannot cross zones.</li>
<li><code>WaitForFirstConsumer</code> — provisioning is deferred until a Pod that uses the PVC is scheduled. The scheduler picks a node first, considering all its normal constraints, and <em>then</em> the volume is created in that node's zone.</li>
</ul>
<p>Use <code>WaitForFirstConsumer</code> on every zonal block-storage class. It is the default on modern managed clusters for exactly this reason.</p>
<h2 id="CSI-in-one-paragraph"><a href="#CSI-in-one-paragraph" class="headerlink" title="CSI in one paragraph"></a>CSI in one paragraph</h2>
<p>Every storage integration is now an out-of-tree <strong>CSI driver</strong>: a controller Deployment that handles create/delete/attach and a node DaemonSet that handles mount/unmount, both speaking a standard gRPC interface. The in-tree cloud provider volume plugins have been migrated to CSI and removed. Practical consequences: driver features arrive on the vendor's schedule rather than Kubernetes releases; snapshots (<code>VolumeSnapshot</code>, <code>VolumeSnapshotClass</code>), cloning, expansion (<code>allowVolumeExpansion: true</code>, then edit the PVC's requested size) and topology awareness are all standard CSI capabilities you can rely on if the driver advertises them.</p>

<h1 id="Chapter-4-—-StatefulSets"><a href="#Chapter-4-—-StatefulSets" class="headerlink" title="Chapter 4 — StatefulSets"></a>Chapter 4 — StatefulSets</h1>
<p>A Deployment's Pods are interchangeable and get random names. Some workloads cannot work that way: a Postgres replica must know it is the replica, a Kafka broker must keep its broker ID and its log directory, a Zookeeper ensemble must have stable peer addresses. <strong>StatefulSet</strong> provides four guarantees a Deployment does not.</p>

<thead>
<tr>

<th>Mechanism</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Stable identity</strong></td>
<td>Pods are named <code>&lt;statefulset&gt;-&lt;ordinal&gt;</code>: <code>pg-0</code>, <code>pg-1</code>, <code>pg-2</code>. A replacement Pod reuses the name</td>
</tr>
<tr>

<h2 id="The-PVCs-outlive-the-StatefulSet"><a href="#The-PVCs-outlive-the-StatefulSet" class="headerlink" title="The PVCs outlive the StatefulSet"></a>The PVCs outlive the StatefulSet</h2>
<p>This is deliberate and it surprises people. <code>kubectl delete statefulset pg</code> deletes the Pods and leaves <code>data-pg-0</code>, <code>data-pg-1</code>, <code>data-pg-2</code> in place. Recreate the StatefulSet with the same name and the same Pods re-attach to the same data. It is a safety feature: the workload controller is disposable, the data is not.</p>
<p>Since <strong>Kubernetes 1.32</strong> you can opt out explicitly:</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">spec:</span></span><br><span class="line">  <span class="hljs-attr">persistentVolumeClaimRetentionPolicy:</span></span><br><span class="line">    <span class="hljs-attr">whenDeleted:</span> <span class="hljs-string">Retain</span>     <span class="hljs-comment"># or Delete</span></span><br><span class="line">    <span class="hljs-attr">whenScaled:</span> <span class="hljs-string">Retain</span>      <span class="hljs-comment"># or Delete — applies when replicas are reduced</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>whenScaled: Delete</code> is useful for genuinely elastic stateful caches. For a database, keep both on <code>Retain</code> and delete PVCs deliberately.</p>
<blockquote>
<p><strong>Common pitfall:</strong> scaling a StatefulSet down and back up looks free but is not. Scaling <code>pg</code> from 3 to 2 removes <code>pg-2</code> and (with <code>whenScaled: Retain</code>) leaves its 50 GiB volume billing quietly forever. Audit orphaned PVCs: <code>kubectl get pvc -A</code> against <code>kubectl get pods -A -o jsonpath</code> is a five-minute script that regularly finds real money.</p>
</blockquote>
<p>Other honest caveats: <code>volumeClaimTemplates</code> is <strong>immutable</strong> — you cannot change the requested size in the template on an existing StatefulSet, only expand each PVC individually (and only if the class allows expansion). And a StatefulSet gives you identity and storage; it does <strong>not</strong> give you replication, leader election, backup, or failover. Those are the database's job, or an operator's.</p>

<h2 id="Job"><a href="#Job" class="headerlink" title="Job"></a>Job</h2>
<p>Runs Pods until a specified number complete successfully, then stops.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span <span class="hljs-string">batch/v1</span></span><br><span class="line"><span class="hljs-attr">kind:</span> <span class="hljs-string">Job</span></span><br><span class="line"><span <li><code>completions</code> + <code>parallelism</code> express a <strong>work queue</strong> or a <strong>fixed fan-out</strong>. With <code>completionMode: Indexed</code>, each Pod knows which slice of work is its own — the cleanest way to shard a batch job without an external queue.</li>
<li><code>backoffLimit</code> counts <strong>Pod</strong> failures, with exponential back-off between retries (10s, 20s, 40s, capped). Set it deliberately: <code>backoffLimit: 6</code> on a job that fails deterministically wastes six retries and twenty minutes.</li>
<li><code>ttlSecondsAfterFinished</code> is the difference between a tidy cluster and 4,000 <code>Completed</code> Pods.</li>

Use a native sidecar (<code>initContainers</code> with <code>restartPolicy: Always</code>, stable since 1.33 — Post 04): Kubernetes terminates it automatically once the main container finishes.</p>
</blockquote>
<h2 id="CronJob"><a href="#CronJob" class="headerlink" title="CronJob"></a>CronJob</h2>
<p>Creates a Job on a schedule.</p>

<p><code>concurrencyPolicy</code> matters more than it looks:</p>
<ul>
<li><strong>Allow</strong> (default) — a run that overruns its interval simply overlaps with the next one. Fine for idempotent work, catastrophic for a job that takes a lock or writes a shared file.</li>
<li><strong>Forbid</strong> — skip the new run if the previous one is still going. The safe default for most reporting and maintenance jobs.</li>
<li><strong>Replace</strong> — kill the running Job and start a fresh one.</li>
</ul>
<h2 id="The-missed-schedule-trap"><a href="#The-missed-schedule-trap" class="headerlink" title="The missed-schedule trap"></a>The missed-schedule trap</h2>
<p>The CronJob controller does not have perfect memory. When it wakes up, it counts the schedules it missed since it last ran. If it finds <strong>more than 100 missed schedules</strong>, it gives up entirely, schedules nothing, and records an event saying so — the CronJob then silently never fires again until it is edited or recreated. This happens after a long control-plane outage, after restoring an old cluster backup, or after a CronJob is created with a schedule in the past.</p>
<p><code>startingDeadlineSeconds</code> interacts with this: if set, the controller only counts misses within that window, which keeps the count small and avoids the lockout — but it also means a run more than that many seconds late is dropped rather than started. Setting it to a value shorter than the controller's own check interval can cause runs to be missed altogether.</p>
<blockquote>
<p><strong>Watch out:</strong> always alert on &quot;expected CronJob has not produced a successful Job in N intervals&quot;. Do not alert on the CronJob object being healthy — it looks perfectly healthy while firing nothing at all.</p>
</blockquote>

<p>Two details in there are load-bearing and routinely omitted:</p>
<ul>
<li><strong><code>PGDATA</code> points at a subdirectory</strong> of the mount, not the mount root. Many block-storage volumes arrive with a <code>lost+found</code> directory, and Postgres refuses to initialise into a non-empty directory.</li>
<li><strong><code>fsGroup</code></strong> makes the kubelet chown the volume so the non-root database user can write to it. Without it the container starts and immediately dies on a permission error.</li>
</ul>
<p>What this manifest still does not give you: replication between the three members, promotion of a new primary when <code>pg-0</code> dies, backups, or point-in-time recovery. Those need an operator (CloudNativePG, Zalando Postgres Operator, Percona, or the vendor's own) or a managed service. A StatefulSet is the <em>substrate</em>, not the database platform.</p>

<h1 id="Chapter-7-—-Should-the-database-be-on-Kubernetes-at-all"><a href="#Chapter-7-—-Should-the-database-be-on-Kubernetes-at-all" class="headerlink" title="Chapter 7 — Should the database be on Kubernetes at all?"></a>Chapter 7 — Should the database be on Kubernetes at all?</h1>
<p>The honest answer is &quot;sometimes&quot;, and the reasoning matters more than the verdict.</p>
<h2 id="The-case-against"><a href="#The-case-against" class="headerlink" title="The case against"></a>The case against</h2>
<ul>
<li><strong>The failure modes are unfamiliar.</strong> A node drain, a spot-instance reclaim, a memory limit hit, an eviction under disk pressure, a CNI hiccup — each is routine for a stateless service and each is a potential data event for a database.</li>
<li><strong>You are now operating two hard systems.</strong> Kubernetes upgrades every few months; the database has its own upgrade path. The intersection is where the incidents live.</li>
<li><strong>Managed services are genuinely good.</strong> RDS, Aurora, Cloud SQL, Atlas and their peers give you backups, PITR, failover, patching and a support contract for a price that is usually less than the engineer-time you would spend replicating them badly.</li>
<li><strong>Storage performance is a layer deeper.</strong> Network-attached block storage under a CSI driver under a container runtime has more moving parts and more tail latency than a local NVMe device.</li>
</ul>
<h2 id="The-case-for"><a href="#The-case-for" class="headerlink" title="The case for"></a>The case for</h2>
<ul>
<li><strong>You already run Kubernetes for everything else,</strong> and the operational uniformity — same deploy pipeline, same secrets, same observability, same RBAC — is worth real money.</li>
<li><strong>On-prem, sovereign or air-gapped requirements</strong> rule out managed services entirely.</li>
<li><strong>A mature operator exists for your database.</strong> This is the pivotal question. CloudNativePG for Postgres, Strimzi for Kafka, the MongoDB and Percona operators, Vitess for MySQL — these encode failover, backup and upgrade as controllers. Running a database on Kubernetes <em>with</em> a mature operator is a different activity from running one with a hand-written StatefulSet.</li>
<li><strong>Many identical database instances.</strong> Per-tenant or per-environment databases are exactly where declarative provisioning pays off.</li>
</ul>
<h2 id="A-decision-rule"><a href="#A-decision-rule" class="headerlink" title="A decision rule"></a>A decision rule</h2>
<table>
<thead>
<tr>
<th>Situation</th>
<th>Reasonable call</th>
</tr>
</thead>
<tbody>
<tr>
<td>Managed service available, no sovereignty constraint, small team</td>
<td><strong>Use the managed service.</strong></td>
</tr>
<tr>
<td>Already deep in Kubernetes, mature operator exists, platform team on call</td>
<td><strong>On Kubernetes, via the operator.</strong></td>
</tr>
<tr>
<td>On-prem or air-gapped</td>
<td><strong>On Kubernetes</strong> — it is likely the best option available</td>
</tr>
<tr>
<td>Small dataset, low QPS, one instance</td>
<td>plain VM or managed; the cluster adds cost without benefit</td>
</tr>
<tr>
<td>Hand-written StatefulSet, no operator, no runbook, production data</td>
<td><strong>Do not.</strong></td>
</tr>
</tbody>
</table>
<p>For a fuller treatment of this exact trade-off in one ecosystem — operator choice, production checklist, cost and compliance — see <code>content/posts/mongo_29_k8s_mongosync_cost_compliance.md</code>, which covers the same decision for MongoDB with the concrete numbers and the operator landscape spelled out.</p>
<p>Whatever you choose, the non-negotiables are the same: <strong>tested restores</strong> (not just backups), storage with a <code>Retain</code> reclaim policy or an equivalent guard, a PodDisruptionBudget so a node drain cannot take quorum (Post 06), anti-affinity so replicas are not co-located, and monitoring that alerts on replication lag rather than on Pod count.</p>

<h1 id="Cheat-sheet"><a href="#Cheat-sheet" class="headerlink" title="Cheat-sheet"></a>Cheat-sheet</h1>
<table>
<thead>
<tr>
<th>What</th>
<th>How</th>
</tr>
</thead>
<tbody>
<tr>
<td>Config as env vars</td>
<td><code>env.valueFrom.configMapKeyRef</code> / <code>envFrom</code> — <strong>never</strong> updates without a restart</td>

<tr>
<td>Config as files</td>
<td><code>volumes.configMap</code> + <code>volumeMounts</code> — updates in place, but not instantly</td>

<td>≈ kubelet sync period (1 min default) + ConfigMap cache propagation</td>
</tr>
<tr>

<td>base64, not encryption; plaintext in etcd unless encryption at rest is configured</td>
</tr>
<tr>

<td>KMS <code>EncryptionConfiguration</code> + tight RBAC + external store / workload identity</td>
</tr>
<tr>

<td>hash-suffixed immutable ConfigMap, or <code>checksum/config</code> on the <strong>Pod template</strong></td>

<td>Pod → PVC → PV → disk, provisioned by a StorageClass via CSI</td>

<td><code>volumeBindingMode: WaitForFirstConsumer</code> on zonal classes</td>
