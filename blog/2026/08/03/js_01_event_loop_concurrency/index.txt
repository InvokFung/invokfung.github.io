11:T12f40,<p>&quot;JavaScript is single-threaded&quot; is true of your code on one thread and false of everything around it. The browser runs networking, parsing, compositing and garbage collection on other threads; Node runs file-system work on a thread pool; and both let you start real parallel threads of JavaScript with workers. What <em>is</em> single-threaded is each agent's <strong>event loop</strong>: one call stack, fed by queues of tasks and microtasks, in an order that is precisely specified — by the HTML standard in browsers and by libuv plus Node's own rules on the server. This post makes that order exact: tasks vs microtasks, where rendering and <code>requestAnimationFrame</code> fit, the ordering puzzles that come out of it, Node's phases with <code>process.nextTick</code> and <code>setImmediate</code>, and then true parallelism with workers, structured clone, transferables, <code>SharedArrayBuffer</code> and <code>Atomics</code>. It ends with the production view: long tasks, INP and yielding with <code>scheduler.yield()</code>.</p>

<h1 id="Chapter-1-—-The-model"><a href="#Chapter-1-—-The-model" class="headerlink" title="Chapter 1 — The model"></a>Chapter 1 — The model</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Agent</strong> — a call stack, a set of queues and one event loop. A window (with its same-origin iframes), each worker, and each Node <code>worker_threads</code> worker are separate agents.</li>
<li><strong>Task</strong> (often &quot;macrotask&quot;) — a unit of work queued by the host: a timer firing, an input event, a network response, a <code>postMessage</code>. Browsers keep several task queues (by <em>task source</em>) and may choose which queue to serve next — this is how input can be prioritised over timers.</li>
<li><strong>Microtask</strong> — a smaller unit queued by promise reactions, <code>queueMicrotask</code>, and <code>MutationObserver</code>. There is one microtask queue per agent.</li>
<li><strong>Microtask checkpoint</strong> — the step that runs microtasks <strong>until the queue is empty</strong>, including microtasks queued by microtasks.</li>
<li><strong>Rendering opportunity</strong> — a moment when the browser can present a new frame, typically aligned with the display refresh (about every 16.7 ms at 60 Hz). Browsers may skip frames or throttle hidden pages.</li>
</ul>
<h2 id="One-turn-of-the-browser-loop"><a href="#One-turn-of-the-browser-loop" class="headerlink" title="One turn of the browser loop"></a>One turn of the browser loop</h2>
<ol>
<li>Pick the oldest task from a task queue the browser chooses, and run it to completion. The call stack empties.</li>
<li><strong>Perform a microtask checkpoint</strong>: run microtasks until none remain.</li>
<li>If this is a rendering opportunity and there is something to render, <strong>update the rendering</strong> (Chapter 3).</li>
<li>Repeat.</li>
</ol>
<p><img src="/blog/assets/js/diagram_01_event_loop.svg" alt="One turn of the event loop: a task, then all microtasks, then optional rendering; and Node's six libuv phases with nextTick and microtasks drained between callbacks"></p>
<p>Two rules produce nearly every &quot;surprising&quot; order:</p>
<ul>
<li><strong>Microtasks run whenever the JavaScript stack becomes empty</strong>, not only between tasks. The HTML spec's &quot;clean up after running script&quot; step performs a microtask checkpoint whenever the JavaScript execution context stack becomes empty — after a task, but also after each event listener the browser invokes and after each <code>requestAnimationFrame</code> callback.</li>
<li><strong>The checkpoint drains the queue completely.</strong> A microtask that queues another microtask keeps the loop in step 2. An infinite chain of microtasks freezes the page as surely as <code>while (true)</code> — rendering and input never get a turn.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> <code>setTimeout(fn, 0)</code> is not &quot;run next&quot;. HTML clamps the delay to at least 4 ms once timers are nested more than 5 levels deep, browsers throttle timers in background tabs heavily, and a timer is only a task — everything already queued, and the rendering step, can run first.</p>
</blockquote>

<h1 id="Chapter-3-—-Rendering-and-requestAnimationFrame"><a href="#Chapter-3-—-Rendering-and-requestAnimationFrame" class="headerlink" title="Chapter 3 — Rendering and requestAnimationFrame"></a>Chapter 3 — Rendering and <code>requestAnimationFrame</code></h1>
<p>When the loop decides to render, the HTML standard's <strong>update the rendering</strong> step runs, per document, in this order (abridged):</p>
<ol>
<li>Run the resize steps (fire <code>resize</code>), then the scroll steps (fire <code>scroll</code>).</li>
<li>Evaluate media queries; update animations and send animation events; fullscreen steps.</li>
<li><strong>Run the animation frame callbacks</strong> — every <code>requestAnimationFrame</code> callback registered <em>before</em> this frame began.</li>
<li><strong>Recalculate styles and update layout</strong>, then deliver <strong><code>ResizeObserver</code></strong> callbacks; if they changed layout, recalculate and deliver again (to a depth limit, after which the browser reports a &quot;ResizeObserver loop&quot; error).</li>
<li>Run the <strong><code>IntersectionObserver</code></strong> update steps.</li>
<li>Paint — &quot;update the rendering or user interface&quot;.</li>
</ol>
<p>Consequences for engineers:</p>
<ul>
<li><strong>rAF is the place for visual writes.</strong> Code in a rAF callback runs just before style and layout, so the frame shows its result. A <code>setTimeout(…, 16)</code> animation drifts against the display's refresh and may run twice or zero times per frame.</li>
<li><strong>A rAF callback that calls rAF schedules for the <em>next</em> frame</strong>, not the current one. That is what makes rAF loops work.</li>
<li><strong>Microtasks run between rAF callbacks</strong> (the stack empties after each one), so a promise resolved in one rAF callback settles before the next callback runs.</li>
<li><strong>Layout thrashing</strong>: reading layout (<code>offsetHeight</code>, <code>getBoundingClientRect()</code>) after writing styles forces the browser to do style and layout <em>synchronously</em>, in the middle of your task. Doing it in a loop — write, read, write, read — can force a layout per iteration. Batch all reads first, then all writes.</li>
</ul>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// Thrashes: forced synchronous layout on every iteration</span></span><br><span class="line"><span class="hljs-keyword">for</span> (<span class="hljs-keyword">const</span> el <span class="hljs-keyword">of</span> items) {</span><br><span class="line">  el.<span class="hljs-property">style</span>.<span class="hljs-property">width</span> = (el.<span class="hljs-property">offsetWidth</span> + <span class="hljs-number">10</span>) + <span class="hljs-string">&#x27;px&#x27;</span>;</span><br><span class="line">}</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// Reads first, then writes: at most one layout, done by the browser at the right time</span></span><br><span class="line"><span class="hljs-keyword">const</span> widths = items.<span class="hljs-title function_">map</span>(<span class="hljs-function"><span class="hljs-params">el</span> =&gt;</span> el.<span class="hljs-property">offsetWidth</span>);</span><br><span class="line"><span class="hljs-title function_">requestAnimationFrame</span>(<span class="hljs-function">() =&gt;</span> {</span><br><span class="line">  items.<span class="hljs-title function_">forEach</span>(<span class="hljs-function">(<span class="hljs-params">el, i</span>) =&gt;</span> { el.<span class="hljs-property">style</span>.<span class="hljs-property">width</span> = (widths[i] + <span class="hljs-number">10</span>) + <span class="hljs-string">&#x27;px&#x27;</span>; <blockquote>
<p><strong>Common pitfall:</strong> using rAF in a background tab to keep &quot;real-time&quot; work going. Browsers stop or heavily throttle rAF in hidden documents (the HTML spec removes hidden documents from rendering). Anything that must keep running — a WebSocket heartbeat, a timer for session expiry — belongs in a timer or a worker, not rAF.</p>
</blockquote>

<p>The Node documentation notes one change: starting with libuv 1.45.0 (Node 20), timers are run <strong>after</strong> the poll phase in each iteration; earlier versions ran them before polling.</p>
<p>On top of the phases:</p>
<ul>
<li><strong><code>process.nextTick</code> queue</strong> — drained after the current operation completes, <em>before</em> the loop moves on, regardless of phase.</li>
<li><strong>Microtask queue</strong> (promises, <code>queueMicrotask</code>) — drained right after the nextTick queue. Every time Node drains the nextTick queue, it drains the microtask queue immediately after.</li>
<li>Since Node 11, both queues are drained <strong>between every individual callback</strong> (after each timer, each immediate), matching browser behaviour. Older Node drained them only between phases.</li>
</ul>

<h2 id="What-runs-off-the-main-thread-in-Node"><a href="#What-runs-off-the-main-thread-in-Node" class="headerlink" title="What runs off the main thread in Node"></a>What runs off the main thread in Node</h2>
<p>The event loop is single-threaded, but libuv has a <strong>thread pool</strong> (default 4 threads, <code>UV_THREADPOOL_SIZE</code>) for work without a good asynchronous OS API: most <code>fs</code> operations, <code>dns.lookup</code>, and CPU-heavy <code>crypto</code> and <code>zlib</code> calls. Network sockets do not use the pool; they use the OS's readiness APIs (epoll, kqueue, IOCP). A burst of <code>fs</code> calls or <code>crypto.pbkdf2</code> calls can therefore queue behind four busy threads — a classic hidden bottleneck.</p>

<h1 id="Chapter-6-—-Shared-memory-and-Atomics"><a href="#Chapter-6-—-Shared-memory-and-Atomics" class="headerlink" title="Chapter 6 — Shared memory and Atomics"></a>Chapter 6 — Shared memory and <code>Atomics</code></h1>
<p>Message passing shares nothing, which is why it is safe. <code>SharedArrayBuffer</code> shares memory: both threads see the same bytes, with all the hazards of real threads.</p>
<h2 id="Why-browsers-require-cross-origin-isolation"><a href="#Why-browsers-require-cross-origin-isolation" class="headerlink" title="Why browsers require cross-origin isolation"></a>Why browsers require cross-origin isolation</h2>
<p>Shared memory plus a busy-loop counter gives a high-resolution timer, which is enough to mount Spectre-style side-channel attacks that read memory across origins. Browsers therefore expose <code>SharedArrayBuffer</code> only to <strong>cross-origin isolated</strong> documents, which requires two response headers on the top-level document:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line">Cross-Origin-Opener-Policy: same-origin</span><br><span class="line">Cross-Origin-Embedder-Policy: require-corp        (or: credentialless)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Check <code>crossOriginIsolated</code> at run time. <code>require-corp</code> blocks every cross-origin subresource that does not opt in with CORS or <code>Cross-Origin-Resource-Policy</code> — third-party scripts, images and iframes break — so adopting it is a project, not a header change. Without isolation, <code>postMessage</code> of a <code>SharedArrayBuffer</code> throws. Node has no such restriction.</p>

<h1 id="Chapter-7-—-Long-tasks-INP-and-yielding"><a href="#Chapter-7-—-Long-tasks-INP-and-yielding" class="headerlink" title="Chapter 7 — Long tasks, INP and yielding"></a>Chapter 7 — Long tasks, INP and yielding</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Long task</strong> — any task that occupies the main thread for more than <strong>50 ms</strong>. Input that arrives during it waits.</li>
<li><strong>INP (Interaction to Next Paint)</strong> — the Core Web Vital for responsiveness: roughly the worst latency from a user interaction to the next frame, across the page's life. Good is 200 ms or less; poor is above 500 ms.</li>
<li><strong>Yielding</strong> — ending the current task deliberately so the browser can handle input and render, then continuing in a new task.</li>
</ul>
<h2 id="Yielding-the-right-way"><a href="#Yielding-the-right-way" class="headerlink" title="Yielding the right way"></a>Yielding the right way</h2>
<p>Splitting work with <code>setTimeout(0)</code> works, but the continuation goes to the <strong>back</strong> of the task queue, behind every other queued task (and third-party scripts). <code>scheduler.yield()</code> returns a promise whose continuation is queued with <strong>priority above other tasks of the same priority</strong>, so your work resumes promptly after the browser has handled input and rendering:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">yieldToMain</span>(<span class="hljs-params"></span>) {</span><br><span class="line">  <span class="hljs-keyword">if</span> (globalThis.<span class="hljs-property">scheduler</span>?.<span class="hljs-property">yield</span>) <span class="hljs-keyword">return</span> scheduler.<span class="hljs-title function_">yield</span>();</span><br><span class="line">  <span class="hljs-keyword">return</span> <span class="hljs-keyword">new</span> <span class="hljs-title class_">Promise</span>(<span class="hljs-function"><span class="hljs-params">resolve</span> =&gt;</span> <span class="hljs-built_in">setTimeout</span>(resolve, <span class="hljs-number">0</span>)); <p><code>scheduler.yield()</code> shipped in Chrome 129 and Firefox 142; at the time of writing it is not Baseline, so always feature-detect. <code>scheduler.postTask(fn, { priority: 'user-blocking' | 'user-visible' | 'background' })</code> is the companion API for scheduling new work with a priority. Microtasks are <strong>not</strong> a way to yield: <code>await Promise.resolve()</code> resumes before the browser can render or handle input.</p>
<h2 id="Finding-the-long-tasks"><a href="#Finding-the-long-tasks" class="headerlink" title="Finding the long tasks"></a>Finding the long tasks</h2>
<ul>
<li><strong>DevTools Performance panel</strong>: long tasks are flagged with a red corner; the flame chart shows which function owns the time.</li>
<li><strong>Long Animation Frames API (LoAF)</strong>: <code>new PerformanceObserver(cb).observe({ type: 'long-animation-frame', buffered: true })</code> reports frames that took longer than 50 ms, with script attribution (source URL, function, invoker). It is the field-data tool for explaining a bad INP.</li>
<li><strong>Node</strong>: <code>perf_hooks.monitorEventLoopDelay()</code> gives a histogram of event-loop delay; a p99 in the hundreds of milliseconds means a synchronous hot spot (JSON parsing a huge body, a sync crypto call, a regex with catastrophic backtracking).</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> &quot;we moved it into a promise, so it's async now&quot;. Wrapping CPU-bound work in <code>new Promise(...)</code> or an <code>async</code> function changes nothing — the executor and the code before the first <code>await</code> run synchronously, and the rest runs in microtasks on the same thread. Only yielding (new tasks) or a worker (new thread) keeps the page responsive.</p>
</blockquote>

<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-built_in">setTimeout</span>(<span class="hljs-function">() =&gt;</span> <span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-string">&#x27;A&#x27;</span>), <span class="hljs-number">0</span>);</span><br><span class="line"><span class="hljs-title class_">Promise</span>.<span class="hljs-title function_">resolve</span>().<span class="hljs-title function_">then</span>(<span class="hljs-function">() =&gt;</span> {</span><br><span class="line">  <span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-string">&#x27;B&#x27;</span>);</span><br><span class="line">  <span class="hljs-built_in">setTimeout</span>(<span class="hljs-function">() =&gt;</span> <span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-string">&#x27;C&#x27;</span>), <span class="hljs-number">0</span>);</span><br><span class="line">  <span class="hljs-title function_">queueMicrotask</span>(<span class="hljs-function">() =&gt;</span> <span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-string">&#x27;D&#x27;</span>));</span><br><span class="line">});</span><br><span class="line"><span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-string">&#x27;E&#x27;</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details><summary>Solution</summary>
<p><code>E B D A C</code>. <code>E</code> is synchronous. The checkpoint runs <code>B</code>, which queues timer C (after timer A) and microtask D; the checkpoint keeps draining, so <code>D</code> runs before any task. Then the two timers in the order they were queued: <code>A</code>, <code>C</code>.</p>
</details>
<h2 id="Exercise-2-—-Starve-the-page"><a href="#Exercise-2-—-Starve-the-page" class="headerlink" title="Exercise 2 — Starve the page"></a>Exercise 2 — Starve the page</h2>
<p>Write a four-line snippet that freezes a page forever using only promises, and explain why rendering never happens. Then change one call so the page stays responsive.</p>
<details><summary>Solution</summary>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">spin</span>(<span class="hljs-params"></span>) { <span class="hljs-title class_">Promise</span>.<span class="hljs-title function_">resolve</span>().<span class="hljs-title function_">then</span>(spin); }</span><br><span class="line"><span class="hljs-title function_">spin</span>();</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Each microtask queues another, and the checkpoint only ends when the queue is empty, so the loop never reaches the rendering step or the next task. Replace <code>Promise.resolve().then(spin)</code> with <code>setTimeout(spin, 0)</code> (or <code>scheduler.postTask(spin)</code>): each iteration becomes a separate task, and rendering and input can happen between them.</p>
</details>

<h2 id="Exercise-4-—-The-module-format-bug"><a href="#Exercise-4-—-The-module-format-bug" class="headerlink" title="Exercise 4 — The module-format bug"></a>Exercise 4 — The module-format bug</h2>
<p>A library emits <code>'ready'</code> from its constructor with <code>process.nextTick</code>. The application attaches the listener one microtask later:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">class</span> <span class="hljs-title class_">Lib</span> <span class="hljs-keyword">extends</span> <span class="hljs-title class_ inherited__">EventEmitter</span> {</span><br><span class="line">  <span class="hljs-title function_">constructor</span>(<span class="hljs-params"></span>) { <span class="hljs-variable language_">super</span>(); process.<span class="hljs-title function_">nextTick</span>(<span class="hljs-function">() =&gt;</span> <span class="hljs-variable language_">this</span>.<span class="hljs-title function_">emit</span>(<span class="hljs-string">&#x27;ready&#x27;</span>)); }</span><br><span class="line">}</span><br><span class="line"><span class="hljs-keyword">const</span> lib = <span class="hljs-keyword">new</span> <span class="hljs-title class_">Lib</span>();</span><br><span class="line"><span class="hljs-title class_">Promise</span>.<span class="hljs-title function_">resolve</span>().<span class="hljs-title function_">then</span>(<span class="hljs-function">() =&gt;</span> lib.<span class="hljs-title function_">on</span>(<span class="hljs-string">&#x27;ready&#x27;</span>, <span class="hljs-function">() =&gt;</span> <span class="hljs-variable language_">console</span>.<span class="hljs-title function_">log</span>(<span class="hljs-string">&#x27;ready&#x27;</span>)));</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>In the ESM application this logs <code>ready</code>. The same code in the CommonJS test suite never does. Explain, and fix the library.</p>
<details><summary>Solution</summary>
<p>In a <code>.mjs</code> file the top-level code already runs inside the microtask queue, so the promise callback (which attaches the listener) runs before Node returns to the nextTick queue, and the event is caught. In a <code>.cjs</code> file the nextTick queue drains first: <code>'ready'</code> is emitted before anyone listens, and it is lost (both outputs checked in Node 22). The code only ever worked by accident of queue order. Fix the library so late listeners cannot miss the state: expose it (<code>lib.ready</code> as a promise that stays resolved, or an <code>isReady</code> flag the caller checks first), instead of a one-shot event fired on a timing guess.</p>
</details>
<h2 id="Exercise-5-—-Worker-or-not"><a href="#Exercise-5-—-Worker-or-not" class="headerlink" title="Exercise 5 — Worker or not?"></a>Exercise 5 — Worker or not?</h2>
<p>For each, choose main thread with yielding, a worker, or a worker with <code>SharedArrayBuffer</code>: (a) filtering a 5 000-row table as the user types; (b) parsing a 200 MB CSV upload; (c) a real-time audio effect exchanging samples with an <code>AudioWorklet</code>; (d) rendering 50 000 points to a canvas at 60 fps.</p>
<details><summary>Solution</summary>
<p>(a) Main thread; the work is small — debounce input and yield if it grows. (b) Worker: transfer the <code>ArrayBuffer</code> from <code>file.arrayBuffer()</code> in, stream results back in chunks. (c) <code>SharedArrayBuffer</code> + <code>Atomics</code> ring buffer: audio needs lock-free, copy-free exchange with hard deadlines (requires cross-origin isolation). (d) Worker with <code>OffscreenCanvas</code>, so drawing never blocks input.</p>
</details>
