11:T6971,<p>MongoDB's native time-series collections (Post 17 Ch 9) cover small-to-medium telemetry workloads beautifully — IoT fleets in the thousands of devices, observability for a single product, financial ticks for a few symbols. Past that, dedicated columnar / time-series engines pull ahead by an order of magnitude on price-performance. This post is the <strong>comparative guide</strong>: how Mongo time-series collections actually work internally, where their limits are, and how they compare to <strong>ClickHouse</strong>, <strong>TimescaleDB</strong>, <strong>InfluxDB</strong>, <strong>QuestDB</strong>, <strong>Druid</strong>. The goal — give you the decision matrix so you know when to stay on Mongo and when to add (or move to) something else.</p>
<blockquote>
<p>Series map: 26 OpenTelemetry → 27 Geo → <strong>28 Time-series extreme</strong> (this post) → 29 K8s + mongosync + cost.</p>

<ul>
<li>Explain how MongoDB time-series collections store + query data.</li>

<li>Pick a stack — pure Mongo / Mongo + hot analytics engine / replace Mongo for this workload.</li>

<h1 id="Chapter-1-—-How-Mongo-time-series-collections-work"><a href="#Chapter-1-—-How-Mongo-time-series-collections-work" class="headerlink" title="Chapter 1 — How Mongo time-series collections work"></a>Chapter 1 — How Mongo time-series collections work</h1>
<p>You create a TS collection with a <code>timeField</code>, optional <code>metaField</code>, and <code>granularity</code>:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-title function_">createCollection</span>(<span class="hljs-string">&quot;metrics&quot;</span>, {</span><br><span class="line">  <span class="hljs-attr">timeseries</span>: { <span class="hljs-attr">timeField</span>: <span class="hljs-string">&quot;ts&quot;</span>, <span class="hljs-attr">metaField</span>: <span class="hljs-string">&quot;host&quot;</span>, <span class="hljs-attr">granularity</span>: <span class="hljs-string">&quot;seconds&quot;</span> }</span><br><span class="line">})</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Under the hood:</p>
<ul>
<li>Documents you insert are <strong>invisibly bucketed</strong> by <code>metaField</code> + time window. The visible API is one-doc-per-event, but on disk it's many events per bucket document.</li>
<li>Buckets use <strong>columnar compression</strong> — much smaller than 1-doc-per-event.</li>
<li>Queries by time range + metaField are fast because they touch only matching buckets.</li>
</ul>
<p><img src="/blog/assets/mongo/diagram_28_ts_buckets.svg" alt="Time-series events grouped by host and time window into compressed bucket documents, and a query that reads only one bucket"></p>
<p>Trade-offs vs hand-rolled bucket pattern (Post 07 Ch 5):</p>
<ul>
<li>No manual schema to maintain.</li>
<li>Better compression than naive.</li>
<li>TTL works out of the box.</li>
</ul>
<p>Limits to be aware of:</p>
<ul>
<li><strong>No update / delete of individual events</strong> (you can re-create the doc or delete the bucket; old events were immutable).</li>
<li>Indexing limited (mostly <code>timeField</code> + <code>metaField</code>; partial multi-key support).</li>
<li>Aggregations work but cardinality-heavy <code>$group</code> is still RAM-bound.</li>
</ul>
<p>For most telemetry use cases this is fine. Workloads where Mongo TS starts to crack: 100k+ writes/sec sustained on a single node, deep aggregations over years of data, sub-100 ms query latency on billions of rows.</p>

<h1 id="Chapter-3-—-Where-Mongo-TS-struggles"><a href="#Chapter-3-—-Where-Mongo-TS-struggles" class="headerlink" title="Chapter 3 — Where Mongo TS struggles"></a>Chapter 3 — Where Mongo TS struggles</h1>
<ul>
<li><strong>Very high write throughput</strong> — single primary saturates around 50-100k writes/sec on a strong shard. Beyond that, sharding helps but costs grow.</li>
<li><strong>Very deep aggregations</strong> — averaging across billions of rows with cardinality-heavy <code>$group</code> is slower than columnar engines built for it.</li>
<li><strong>Sub-50ms p99 on huge ranges</strong> — columnar formats with vectorised execution win.</li>
<li><strong>Compression at extreme scale</strong> — ClickHouse / Parquet typically achieves 5-20× the compression ratio of Mongo TS for time-series-shape data.</li>
<li><strong>Cost per TB of cold data</strong> — Atlas hot storage isn't cheap; archive helps but specialist engines compress more aggressively.</li>
</ul>
<p>When the workload hits any of these, look at alternatives below.</p>

<td><strong>ClickHouse</strong></td>
<td>columnar, MergeTree variants</td>
<td>extreme analytics speed; great compression; SQL</td>
<td>append-mostly; weaker on point updates; ops complexity</td>
</tr>
<tr>
<td><strong>TimescaleDB</strong></td>
<td>Postgres extension; chunked time-partitioned tables</td>
<td>full SQL + Postgres tooling; PostGIS friends</td>
<td>not columnar core; scaling beyond 1 node harder</td>
</tr>
<tr>
<td><strong>InfluxDB v3</strong></td>
<td>Apache Arrow + Parquet</td>
<td>purpose-built for metrics; PromQL-like Flux/SQL</td>
<td>rewrite history; ecosystem smaller</td>
</tr>
<tr>
<td><strong>QuestDB</strong></td>
<td>columnar, SIMD-vectorised</td>
<td>very fast ingest + queries; small footprint</td>
<td>newer ecosystem; less feature coverage</td>
</tr>
<tr>
<td><strong>Apache Druid</strong></td>
<td>columnar, segment-based</td>
<td>sub-second on huge datasets + dashboards</td>
<td>heavy ops; complex schema</td>
</tr>
<tr>
<td><strong>Apache Pinot</strong></td>
<td>columnar, segment-based</td>
<td>sub-second; ad-tech / event use cases</td>
<td>heavy ops</td>
</tr>
<tr>
<td><strong>Prometheus + Mimir/Thanos</strong></td>
<td>TSDB</td>
<td>metrics monitoring</td>
<td>not for arbitrary analytical queries</td>
</tr>
</tbody>
</table>
<p>For pure analytics over time-series, <strong>ClickHouse</strong> is the dominant 2026 choice for new builds. Operational complexity dropped with managed offerings (Altinity Cloud, ClickHouse Cloud).</p>
<hr>
<h1 id="Chapter-5-—-ClickHouse-—-when-how"><a href="#Chapter-5-—-ClickHouse-—-when-how" class="headerlink" title="Chapter 5 — ClickHouse — when + how"></a>Chapter 5 — ClickHouse — when + how</h1>
<p>ClickHouse is a columnar OLAP database. Strengths for time-series:</p>
<ul>
<li>Sub-second aggregation over billions of rows.</li>
<li>10-50× compression vs row-store.</li>
<li>Materialized views update incrementally.</li>
<li>Native S3 + Parquet integration for cold storage.</li>
</ul>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span <p>Inserts: millions of rows / second per node.<br>
Queries: tens of milliseconds over millions of rows.</p>
<p>Trade-offs:</p>
<ul>
<li>Append-mostly; updates + deletes are expensive (mutations queue).</li>
<li>Schema is rigid (vs Mongo's flexibility).</li>
<li>Operational complexity higher than managed Mongo.</li>
</ul>
<p>Use ClickHouse when: pure analytical queries dominate; workload exceeds Mongo TS ceiling; you can devote eng time to running it or pay for managed.</p>
<hr>
<h1 id="Chapter-6-—-Hybrid-—-Mongo-for-OLTP-ClickHouse-for-OLAP"><a href="#Chapter-6-—-Hybrid-—-Mongo-for-OLTP-ClickHouse-for-OLAP" class="headerlink" title="Chapter 6 — Hybrid — Mongo for OLTP, ClickHouse for OLAP"></a>Chapter 6 — Hybrid — Mongo for OLTP, ClickHouse for OLAP</h1>
<p>The common 2026 pattern for serious scale:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="text"><span class="line">Application</span><br><span class="line">    │ writes (transactional)</span><br><span class="line">    ▼</span><br><span class="line">MongoDB (OLTP: orders, users, sessions, recent telemetry)</span><br><span class="line">    │ change stream / outbox / Kafka</span><br><span class="line">    ▼</span><br><span class="line">ClickHouse (OLAP: years of history, dashboards, BI)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Mongo handles user-facing reads + writes with rich queries on recent data. Events flow to ClickHouse via Kafka (Post 24) or a periodic batch (<code>$merge</code> + S3 → ClickHouse). Dashboards / BI hit ClickHouse for big analytics.</p>
<p>Each tool does what it's best at; you pay the cost of running two systems but neither is asked to do the other's job poorly.</p>
<hr>
<h1 id="Chapter-7-—-When-TimescaleDB-fits-better"><a href="#Chapter-7-—-When-TimescaleDB-fits-better" class="headerlink" title="Chapter 7 — When TimescaleDB fits better"></a>Chapter 7 — When TimescaleDB fits better</h1>
<p>If your team is already deep on Postgres + your analytical queries are still SQL-shape (joins, complex predicates, transactions over recent slices), <strong>TimescaleDB</strong> keeps you on one engine.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> metrics (</span><br><span class="line">  ts        TIMESTAMPTZ <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span>,</span><br><span class="line">  host      TEXT,</span><br><span class="line">  <span class="hljs-keyword">value</span>     <span class="hljs-type">DOUBLE PRECISION</span></span><br><span class="line">);</span><br><span class="line"><span class="hljs-keyword">SELECT</span> create_hypertable(<span class="hljs-string">&#x27;metrics&#x27;</span>, <span class="hljs-string">&#x27;ts&#x27;</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Strengths:</p>
<ul>
<li>Full Postgres feature set + PostGIS + extensions.</li>
<li>Multi-tier storage (recent on SSD, old compressed to columnar).</li>
<li>Familiar to SQL teams.</li>
</ul>
<p>Weaknesses:</p>
<ul>
<li>Not as fast as pure columnar for huge analytics.</li>
<li>Scaling horizontally still harder than Atlas + Mongo or ClickHouse.</li>
</ul>
<p>Pick when: SQL-first team, mixed transactional + analytical SQL workload, &lt; ~1 TB per dataset.</p>
<hr>
<h1 id="Chapter-8-—-InfluxDB-v3-—-metrics-focused"><a href="#Chapter-8-—-InfluxDB-v3-—-metrics-focused" class="headerlink" title="Chapter 8 — InfluxDB v3 — metrics-focused"></a>Chapter 8 — InfluxDB v3 — metrics-focused</h1>
<p>InfluxDB v3 (formerly IOx) is rebuilt on Apache Arrow + Parquet. Strengths for metrics:</p>
<ul>
<li>Native to monitoring workflows (Prometheus-compat ingest, Grafana plugin).</li>
<li>Fast on time-series math (rates, moving averages, derivatives).</li>
<li>Self-managed or cloud.</li>
</ul>
<p>Weaknesses:</p>
<ul>
<li>Less general-purpose than ClickHouse.</li>
<li>Schema evolution gotchas inherited from earlier versions.</li>
</ul>
<p>Pick when: pure monitoring workload + you want a metrics-first DB rather than a general analytical engine.</p>
<hr>
<h1 id="Chapter-9-—-QuestDB-—-fast-small"><a href="#Chapter-9-—-QuestDB-—-fast-small" class="headerlink" title="Chapter 9 — QuestDB — fast + small"></a>Chapter 9 — QuestDB — fast + small</h1>
<p>QuestDB is a young, fast columnar TS database. Strengths:</p>
<ul>
<li>Tiny footprint; runs on a laptop and on a server.</li>
<li>Very fast ingest + SQL queries.</li>
<li>Compatible with Postgres wire protocol.</li>
</ul>
<p>Weaknesses:</p>
<ul>
<li>Smaller community + ecosystem than ClickHouse.</li>
<li>Fewer enterprise features.</li>
</ul>
<p>Pick when: greenfield project, dev-friendliness &gt; ecosystem.</p>
<hr>
<h1 id="Chapter-10-—-Druid-Pinot-—-sub-second-dashboards-over-huge-data"><a href="#Chapter-10-—-Druid-Pinot-—-sub-second-dashboards-over-huge-data" class="headerlink" title="Chapter 10 — Druid / Pinot — sub-second dashboards over huge data"></a>Chapter 10 — Druid / Pinot — sub-second dashboards over huge data</h1>
<p>For ad-tech, real-time analytics, leaderboard-style dashboards over billions of rows with millisecond response:</p>
<ul>
<li><strong>Apache Druid</strong> — operational complexity high; sub-second analytical queries shine.</li>
<li><strong>Apache Pinot</strong> — similar story; LinkedIn / Uber heritage.</li>
</ul>
<p>Not the first choice for general workloads; reserve for when you genuinely need that latency at that scale.</p>
<hr>
<h1 id="Chapter-11-—-Decision-matrix"><a href="#Chapter-11-—-Decision-matrix" class="headerlink" title="Chapter 11 — Decision matrix"></a>Chapter 11 — Decision matrix</h1>

<p>The right answer is rarely &quot;one engine for everything&quot; past a certain scale.</p>
<hr>
<h1 id="Chapter-12-—-Migration-paths"><a href="#Chapter-12-—-Migration-paths" class="headerlink" title="Chapter 12 — Migration paths"></a>Chapter 12 — Migration paths</h1>
<h3 id="Mongo-TS-→-ClickHouse"><a href="#Mongo-TS-→-ClickHouse" class="headerlink" title="Mongo TS → ClickHouse"></a>Mongo TS → ClickHouse</h3>
<ol>
<li>Continue ingesting into Mongo.</li>
<li>Stream from Mongo to ClickHouse via Kafka (Post 24) or <code>$merge</code> to S3 → ClickHouse S3-table.</li>
<li>Switch dashboards + BI to ClickHouse.</li>
<li>Optionally cut writes to Mongo if it no longer serves a transactional purpose.</li>
</ol>
<h3 id="Atlas-Online-Archive-as-a-half-step"><a href="#Atlas-Online-Archive-as-a-half-step" class="headerlink" title="Atlas Online Archive as a half-step"></a>Atlas Online Archive as a half-step</h3>
<p>For &quot;old data costs too much in Mongo&quot;, <strong>Atlas Online Archive</strong> (Post 16) moves cold data to cheap S3-like storage, still queryable via federation. Cheaper than ClickHouse for archive-then-occasionally-query patterns. Faster path than a full migration.</p>

<h1 id="Chapter-13-—-Common-pitfalls"><a href="#Chapter-13-—-Common-pitfalls" class="headerlink" title="Chapter 13 — Common pitfalls"></a>Chapter 13 — Common pitfalls</h1>
<table>
<thead>
<tr>
<th>Pitfall</th>
<th>Cause</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>Started with Mongo TS, blew the ceiling</td>
<td>optimistic capacity planning</td>
<td>hybrid with ClickHouse for analytics</td>
</tr>
<tr>
<td>Adopted ClickHouse for OLTP</td>
<td>wrong tool</td>
<td>use it only for OLAP; keep Mongo for OLTP</td>
</tr>
<tr>
<td>Schema rigid in ClickHouse, painful to add columns</td>
<td>underestimated evolution cost</td>
<td>always design ALTER-friendly schemas</td>
</tr>
<tr>
<td>Big bills running both Mongo + ClickHouse</td>
<td>parallel storage of same data</td>
<td>smarter retention (raw in CH, summaries in Mongo)</td>
</tr>
<tr>
<td>TS collection updates rejected</td>
<td>by design — TS is append-only</td>
<td>re-architect to event-shape</td>
</tr>
<tr>
<td>Cross-engine joins required</td>
<td>one shouldn't be the source of truth for the other</td>
<td>sync via Kafka; or materialise into one</td>
</tr>
<tr>
<td>New DB before proving the need</td>
<td>premature optimisation</td>
<td>scale-test Mongo TS first</td>
</tr>
