<h1 id="Chapter-1-—-How-the-scheduler-works"><a href="#Chapter-1-—-How-the-scheduler-works" class="headerlink" title="Chapter 1 — How the scheduler works"></a>Chapter 1 — How the scheduler works</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Scheduling</strong> — assigning an unscheduled Pod to a node by writing <code>.spec.nodeName</code>. The kubelet on that node then starts it.</li>
<li><strong>Filter (predicate)</strong> — a check that eliminates nodes a Pod <em>cannot</em> run on.</li>
<li><strong>Score (priority)</strong> — a ranking of the surviving nodes by how <em>good</em> a fit they are.</li>
<li><strong>Binding</strong> — persisting the chosen node back to the API server.</li>
<li><strong>Feasible node</strong> — a node that survived every filter.</li>
</ul>
<h2 id="The-two-phases"><a href="#The-two-phases" class="headerlink" title="The two phases"></a>The two phases</h2>
<p>For each Pod in the scheduling queue, <code>kube-scheduler</code> runs a <strong>scheduling cycle</strong> and then a <strong>binding cycle</strong>. The scheduling cycle has two halves:</p>
<p><strong>1. Filter.</strong> Every node is tested against a series of predicates. Any failure removes the node from consideration:</p>
<ul>
<li>Does the node have enough <em>allocatable</em> CPU, memory and ephemeral storage to satisfy the Pod's <strong>requests</strong>?</li>
<li>Do the Pod's <code>nodeSelector</code> and required node affinity match the node's labels?</li>
<li>Are the node's taints tolerated by the Pod?</li>
<li>Are the requested host ports free?</li>
<li>Can the Pod's volumes be attached here (zone, node affinity of the PV, attach limits)?</li>
<li>Do required pod affinity and anti-affinity rules hold?</li>
<li>Is the node <code>Ready</code> and not under <code>MemoryPressure</code>, <code>DiskPressure</code> or <code>PIDPressure</code>?</li>
</ul>
<p>If zero nodes survive, the Pod stays <code>Pending</code> and the scheduler records an event naming the failing predicate — <code>0/12 nodes are available: 8 Insufficient cpu, 4 node(s) had untolerated taint</code>. That event is the answer to almost every &quot;why is my Pod Pending&quot; question.</p>
<p><strong>2. Score.</strong> Each feasible node is scored 0-100 by several plugins and the totals are weighted:</p>
<ul>
<li><code>NodeResourcesFit</code> — spread load (<code>LeastAllocated</code>, the default) or pack it tight (<code>MostAllocated</code>, better for autoscaler-driven cost savings).</li>
<li><code>ImageLocality</code> — prefer nodes that already have the image cached.</li>
<li><code>InterPodAffinity</code>, <code>PodTopologySpread</code>, <code>TaintToleration</code>, <code>NodeAffinity</code> — the preferred (soft) forms of each rule.</li>
</ul>
<p>The highest-scoring node wins; ties are broken at random. The scheduler then <strong>reserves</strong> the resources, runs any <code>Permit</code> plugins, and binds asynchronously.</p>
<p>Two properties matter operationally:</p>
<ul>
<li>The scheduler decides <strong>once</strong>, at admission. It does not move a running Pod because the cluster later became unbalanced. Rebalancing requires deleting Pods (the <code>descheduler</code> project automates this).</li>
<li>The scheduler reasons about <strong>requests</strong>, never about actual usage. A node can be 95 % idle and still reject a Pod because its requests are fully committed — and it can be 100 % CPU-saturated and happily accept more Pods whose requests fit.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> <code>kubectl describe node &lt;node&gt;</code> prints an &quot;Allocated resources&quot; table with requests and limits as a percentage of allocatable. That table, not <code>kubectl top</code>, is what the scheduler sees.</p>
</blockquote>

<p><strong>Common pitfall:</strong> hard <code>podAntiAffinity</code> on <code>kubernetes.io/hostname</code> caps your replica count at the node count. Scale to 10 replicas on a 6-node cluster and 4 Pods sit <code>Pending</code> forever. Use the <em>preferred</em> form, or topology spread constraints, unless the co-location really is unacceptable.</p>
</blockquote>
<p>Pod affinity is also computationally expensive — the scheduler must evaluate every Pod in the matched topology for every candidate node. On large clusters, prefer topology spread constraints.</p>
<h2 id="Taints-and-tolerations-—-the-inverse"><a href="#Taints-and-tolerations-—-the-inverse" class="headerlink" title="Taints and tolerations — the inverse"></a>Taints and tolerations — the inverse</h2>
<p>Affinity is a Pod attracting a node. A <strong>taint</strong> is a node repelling Pods. Only Pods with a matching <strong>toleration</strong> may land there.</p>

</blockquote>

<h1 id="Chapter-3-—-Requests-limits-and-QoS"><a href="#Chapter-3-—-Requests-limits-and-QoS" class="headerlink" title="Chapter 3 — Requests, limits and QoS"></a>Chapter 3 — Requests, limits and QoS</h1>
<h2 id="The-one-sentence-that-matters"><a href="#The-one-sentence-that-matters" class="headerlink" title="The one sentence that matters"></a>The one sentence that matters</h2>
<p><strong>Requests drive scheduling. Limits drive enforcement.</strong></p>
<ul>
<li>A <strong>request</strong> is a reservation. The scheduler subtracts it from the node's allocatable capacity and guarantees the Pod that much. It is also the number that decides whether the Pod fits at all.</li>
<li>A <strong>limit</strong> is a ceiling enforced at runtime by the kernel through cgroups. Exceed the CPU limit and you are throttled. Exceed the memory limit and you are killed.</li>
</ul>
<p>Everything else in this chapter follows from that distinction.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">resources:</span></span><br><span class="line">  <span class="hljs-attr">requests:</span></span><br><span class="line">    <span class="hljs-attr">cpu:</span> <span class="hljs-string">&quot;250m&quot;</span>        <span class="hljs-comment"># 0.25 of a core; the scheduler reserves this</span></span><br><span class="line">    <span class="hljs-attr">memory:</span> <span class="hljs-string">&quot;256Mi&quot;</span>    <span class="hljs-comment"># guaranteed; the basis of eviction ranking</span></span><br><span class="line">  <span class="hljs-attr">limits:</span></span><br><span class="line">    <span class="hljs-attr">memory:</span> <span class="hljs-string">&quot;512Mi&quot;</span>    <span class="hljs-comment"># exceed this and the kernel OOM-kills the container</span></span><br><span class="line">    <span class="hljs-comment"># cpu deliberately omitted — see below</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>CPU is <strong>compressible</strong>: exceeding your share means running slower. Memory is <strong>incompressible</strong>: there is no &quot;slower&quot;, only &quot;killed&quot;.</p>
<h2 id="QoS-classes"><a href="#QoS-classes" class="headerlink" title="QoS classes"></a>QoS classes</h2>
<p>The kubelet assigns each Pod a class based purely on how its requests and limits are written:</p>
<table>
<thead>
<tr>
<th>Class</th>
<th>Condition</th>
<th>Consequence</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Guaranteed</strong></td>
<td>every container sets both CPU <em>and</em> memory, and request == limit for each</td>
<td>evicted last; eligible for exclusive CPUs under the static CPU manager policy</td>
</tr>
<tr>
<td><strong>Burstable</strong></td>
<td>at least one request is set, but not the Guaranteed pattern</td>
<td>evicted after BestEffort, in order of how far usage exceeds requests</td>
</tr>
<tr>
<td><strong>BestEffort</strong></td>
<td>no requests or limits anywhere in the Pod</td>
<td>evicted first, always</td>
</tr>
</tbody>
</table>
<p>Under node memory pressure the kubelet evicts in that order: BestEffort first, then Burstable Pods that are using more than they requested (ranked by the excess), then Guaranteed. The kernel's own OOM killer uses a parallel mechanism, <code>oom_score_adj</code>, derived from the same classes.</p>
<blockquote>
<p><strong>Common pitfall:</strong> BestEffort Pods look thrifty and are actually hazardous. They are the first thing evicted when a node fills up, they contribute nothing to autoscaler capacity calculations, and they can starve neighbours. Set requests on everything, including the small &quot;unimportant&quot; jobs.</p>
</blockquote>
<h2 id="CPU-limits-and-CFS-throttling"><a href="#CPU-limits-and-CFS-throttling" class="headerlink" title="CPU limits and CFS throttling"></a>CPU limits and CFS throttling</h2>
<p>A CPU limit is implemented as a <strong>CFS quota</strong>: the cgroup is granted <em>quota</em> microseconds of CPU time per <em>period</em> (100 ms by default). A limit of <code>500m</code> means 50 ms of CPU per 100 ms window. When the quota is exhausted, every thread in the cgroup is <strong>stopped until the next period begins</strong>.</p>
<p>This produces a failure mode that is invisible in average CPU graphs. An application averaging 30 % of its limit can still be throttled hard, because the work is not spread evenly: a request arrives, several threads wake, the quota is consumed in 15 ms, and the container sleeps for the remaining 85 ms. The result is tail latency in whole multiples of 100 ms while the dashboard shows a comfortable average.</p>
<p>Multithreaded runtimes make it worse. A JVM or Go program that sees 32 host CPUs will happily run 32 threads, burning the quota 32× faster than a single thread would.</p>
<p>Measure it — do not guess:</p>
<pre><code class="language-promql"><figure class="highlight promql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="promql"><span class="line"><span class="hljs-comment"># Fraction of periods in which the container was throttled.</span></span><br><span class="line">rate(container_cpu_cfs_throttled_periods_total{<span class="hljs-attribute">pod</span>=~&quot;web-.*&quot;}[5m])</span><br><span class="line">  / rate(container_cpu_cfs_periods_total{<span class="hljs-attribute">pod</span>=~&quot;web-.*&quot;}[5m])</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Sustained values above roughly 5-10 % on a latency-sensitive service are worth acting on. Confirm on your own workload rather than trusting any published threshold.</p>
<h2 id="The-genuine-argument-for-omitting-CPU-limits"><a href="#The-genuine-argument-for-omitting-CPU-limits" class="headerlink" title="The genuine argument for omitting CPU limits"></a>The genuine argument for omitting CPU limits</h2>
<p>Set <strong>memory limits always; consider omitting CPU limits</strong> on latency-sensitive services.</p>
<p>The case for omitting: CPU is compressible and already fairly shared. When several containers on a node contend, the kernel divides CPU time in proportion to their <strong>requests</strong> (cgroup CPU shares) — so requests alone already provide isolation under contention. A limit adds nothing during contention and actively hurts when the node is <em>idle</em>, because it forbids a container from using spare capacity it could have had for free. Throttling a service that could have run faster, on a machine that is 60 % idle, is pure loss.</p>
<p>The case for keeping them: limits make behaviour reproducible and capacity predictable, they stop one runaway process from degrading its neighbours' latency (fair sharing is fair, but a busy neighbour still slows you down), some regulated or multi-tenant environments require hard ceilings, and Guaranteed QoS — which requires a CPU limit — is needed for exclusive CPU pinning.</p>
<p>A defensible policy: <strong>memory limit always set and equal to a measured peak plus headroom; CPU request set from measured usage; CPU limit omitted for latency-sensitive services, set generously (well above the request) for batch and untrusted workloads.</strong> Whatever you choose, also set <code>GOMAXPROCS</code> (Go) or the container-aware JVM flags so the runtime sizes its thread pools to the cgroup, not to the host.</p>
<h2 id="OOMKill-and-exit-code-137"><a href="#OOMKill-and-exit-code-137" class="headerlink" title="OOMKill and exit code 137"></a>OOMKill and exit code 137</h2>
<p>Exceed the memory limit and the kernel's OOM killer terminates the process with <code>SIGKILL</code>. The container exits with <strong>137</strong> — the shell convention of <code>128 + signal</code>, and <code>9</code> is SIGKILL.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="bash"><span class="line">kubectl describe pod web-6d4f-abcde</span><br><span class="line"><span class="hljs-comment"># Last State:     Terminated</span></span><br><span class="line"><span class="hljs-comment">#   Reason:       OOMKilled</span></span><br><span class="line"><span class="hljs-comment">#   Exit Code:    137</span></span><br><span class="line"><span class="hljs-comment"># Restart Count:  4</span></span><br><span class="line">kubectl get pod web-6d4f-abcde -o jsonpath=<span class="hljs-string">&#x27;{.status.containerStatuses[0].lastState}&#x27;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Diagnosis:</p>
<ul>
<li><strong>Exit 137 with <code>Reason: OOMKilled</code></strong> — the container exceeded its own memory limit. Raise the limit or fix the leak.</li>
<li><strong>Exit 137 without <code>OOMKilled</code></strong> — something sent SIGKILL: usually a grace period expiring during shutdown (Chapter 5), or a node-level OOM.</li>
<li><strong>Pod status <code>Evicted</code></strong> — the <em>node</em> ran out of memory and the kubelet chose this Pod by QoS ranking. Different problem: the node is over-committed.</li>
<li><strong>Exit 143</strong> is <code>128 + 15</code> (SIGTERM) — a normal, graceful termination.</li>
</ul>
<p>Note also that a <em>request</em> far below the real working set is what makes node-level OOM possible in the first place: the scheduler packed the node believing the Pods were small.</p>

<h2 id="The-classic-outage"><a href="#The-classic-outage" class="headerlink" title="The classic outage"></a>The classic outage</h2>
<p>A team writes one <code>/health</code> endpoint that checks the database, and wires it to <strong>both</strong> the readiness and the liveness probe. The database has a 30-second hiccup.</p>
<ol>
<li>Every replica's liveness probe fails.</li>
<li>The kubelet kills and restarts <strong>every replica simultaneously</strong>.</li>
<li>The database recovers — and is immediately hit by the full fleet reconnecting and re-warming caches at once.</li>
<li>The probes fail again. Restart storm. <code>CrashLoopBackOff</code>. The blast radius of a 30-second dependency blip is now a total outage that outlives it by many minutes.</li>
</ol>
<p>The rule that prevents it: <strong>a liveness probe must never test anything outside the process.</strong> If the dependency is down, restarting your container does not help — it makes recovery harder by discarding warm state and multiplying reconnection load.</p>
<ul>
<li><strong>Liveness</strong> → shallow. &quot;Is the event loop running, can I serve a trivial response?&quot; Many mature services are better off with <strong>no liveness probe at all</strong>; a process that crashes on a fatal fault is restarted by the Pod restart policy anyway.</li>
<li><strong>Readiness</strong> → may be deep. Failing readiness removes the Pod from load balancing and is <em>reversible with no state loss</em>. If every replica fails readiness the Service has no endpoints and clients get connection errors — bad, but strictly better than a restart storm, and it recovers the instant the dependency does.</li>
<li><strong>Startup</strong> → the correct tool for slow-starting applications. Without it you must inflate <code>initialDelaySeconds</code> or <code>failureThreshold</code> on liveness, which weakens liveness forever to accommodate one slow boot.</li>
</ul>

<h2 id="Rolling-updates"><a href="#Rolling-updates" class="headerlink" title="Rolling updates"></a>Rolling updates</h2>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">spec:</span></span><br><span class="line">  <span class="hljs-attr">strategy:</span></span><br><span class="line">    <span class="hljs-attr">type:</span> <span class="hljs-string">RollingUpdate</span></span><br><span class="line">    <span class="hljs-attr">rollingUpdate:</span></span><br><span class="line">      <span class="hljs-attr">maxSurge:</span> <span class="hljs-number">25</span><span class="hljs-string">%</span>          <span class="hljs-comment"># extra Pods allowed above `replicas` during the roll</span></span><br><span class="line">      <span class="hljs-attr">maxUnavailable:</span> <span class="hljs-number">0</span>      <span class="hljs-comment"># never drop below `replicas` ready Pods</span></span><br><span class="line">  <span class="hljs-attr">minReadySeconds:</span> <span class="hljs-number">10</span>        <span class="hljs-comment"># a new Pod must stay Ready this long before it counts</span></span><br><span class="line">  <span class="hljs-attr">progressDeadlineSeconds:</span> <span class="hljs-number">600</span></span><br><span class="line">  <span class="hljs-attr">revisionHistoryLimit:</span> <span class="hljs-number">5</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><code>maxSurge: 25%, maxUnavailable: 0</code> — the safe default. Capacity never dips; the rollout needs spare cluster capacity and is slightly slower.</li>
<li><code>maxSurge: 0, maxUnavailable: 1</code> — for workloads that cannot be over-provisioned (a licence limit, a singleton lock). Capacity dips during the roll.</li>
<li><code>minReadySeconds</code> is underused and valuable: it stops a rollout that passes readiness and then dies five seconds later from marching all the way through the fleet.</li>
<li><code>progressDeadlineSeconds</code> marks the Deployment <code>Progressing=False</code> when it stalls, which is what your alerting and your GitOps controller should watch. Note that it does <strong>not</strong> roll back automatically.</li>
</ul>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="bash"><span class="line">kubectl <span class="hljs-built_in">set</span> image deployment/web web=ghcr.io/example/web:1.4.3</span><br><span class="line">kubectl rollout status  deployment/web --<span class="hljs-built_in">timeout</span>=5m   <span class="hljs-comment"># the command that actually waits</span></span><br><span class="line">kubectl rollout <span class="hljs-built_in">history</span> deployment/web</span><br><span class="line">kubectl rollout undo    deployment/web                <span class="hljs-comment"># previous revision</span></span><br><span class="line">kubectl rollout pause   deployment/web                <span class="hljs-comment"># freeze mid-roll to inspect a canary</span></span><br><span class="line">kubectl rollout resume  deployment/web</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>A <strong>PodDisruptionBudget</strong> constrains only the voluntary column. It works by making the Eviction API refuse an eviction that would violate the budget; anything that does not go through that API — a node catching fire — is unaffected.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">apiVersion:</span> <span class="hljs-string">policy/v1</span></span><br><span class="line"><span class="hljs-attr">kind:</span> <span class="hljs-string">PodDisruptionBudget</span></span><br><span class="line"><span class="hljs-attr">metadata:</span> { <span class="hljs-attr">name:</span> <span class="hljs-string">web</span> }</span><br><span class="line"><span class="hljs-attr">spec:</span></span><br><span class="line">  <span class="hljs-attr">minAvailable:</span> <span class="hljs-number">2</span>          <span class="hljs-comment"># or: maxUnavailable: 1</span></span><br><span class="line">  <span class="hljs-attr">selector:</span></span><br><span class="line">    <span class="hljs-attr">matchLabels:</span> { <span class="hljs-attr">app.kubernetes.io/name:</span> <span class="hljs-string">web</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Guidance:</p>
<ul>
<li>Use <code>maxUnavailable: 1</code> for large stateless fleets — it scales with replica count without editing.</li>
<li>Use <code>minAvailable: &lt;quorum&gt;</code> for quorum systems (etcd, Zookeeper, a 3-member database): losing quorum during a routine node drain is a real and common outage.</li>
<li>A PDB that can never be satisfied <strong>blocks node drains indefinitely</strong>. <code>minAvailable: 3</code> on a Deployment with <code>replicas: 3</code> means no Pod may ever be evicted, and every cluster upgrade hangs. Always leave slack.</li>
<li>A PDB on a single-replica Deployment is a contradiction: you are asserting that the Pod is both critical and unreplicated.</li>
</ul>
<h2 id="Graceful-shutdown-and-the-endpoint-removal-race"><a href="#Graceful-shutdown-and-the-endpoint-removal-race" class="headerlink" title="Graceful shutdown and the endpoint-removal race"></a>Graceful shutdown and the endpoint-removal race</h2>
<p>When a Pod is deleted, two things happen <strong>concurrently</strong>, and this is the subtle part:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="text"><span class="line">  t=0   Pod marked Terminating</span><br><span class="line">        ├── path A: kubelet runs preStop, then sends SIGTERM to PID 1</span><br><span class="line">        └── path B: endpoints controller removes the Pod from the EndpointSlice</span><br><span class="line">                    → the API server notifies every node&#x27;s kube-proxy</span><br><span class="line">                    → each kube-proxy reprograms its own iptables/IPVS rules</span><br><span class="line">                    → any ingress controller or mesh updates its own view</span><br><span class="line">  t=grace  SIGKILL if the container has not exited</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Path B is a distributed propagation across every node in the cluster; path A is local and immediate. So a container can receive SIGTERM, stop accepting connections, and <strong>still be sent traffic</strong> for hundreds of milliseconds to several seconds afterwards, by proxies that have not yet heard the news. That is the source of the 502s and connection resets that appear during otherwise &quot;zero-downtime&quot; deploys.</p>
<p>The fix is to make the container keep serving for a moment after SIGTERM:</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">spec:</span></span><br><span class="line">  <span class="hljs-attr">terminationGracePeriodSeconds:</span> <span class="hljs-number">60</span></span><br><span class="line">  <span class="hljs-attr">containers:</span></span><br><span class="line">    <span class="hljs-bullet">-</span> <span class="hljs-attr">name:</span> <span class="hljs-string">web</span></span><br><span class="line">      <span class="hljs-attr">lifecycle:</span></span><br><span class="line">        <span class="hljs-attr">preStop:</span></span><br><span class="line">          <span class="hljs-attr">exec:</span></span><br><span class="line">            <span class="hljs-attr">command:</span> [<span class="hljs-string">&quot;sleep&quot;</span>, <span class="hljs-string">&quot;10&quot;</span>]     <span class="hljs-comment"># keep serving while endpoints propagate</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>preStop</code> runs <strong>before</strong> SIGTERM and the grace period clock covers both, so the grace period must exceed the sleep plus the real drain time. The sequence you want:</p>
<ol>
<li><code>preStop</code> sleeps ~5-15 s. The container is still healthy and still serving; meanwhile every proxy learns the Pod is gone.</li>
<li>SIGTERM. The application stops accepting <em>new</em> connections, finishes in-flight requests, closes pools, flushes buffers, and exits.</li>
<li>If it has not exited by <code>terminationGracePeriodSeconds</code> (default <strong>30</strong>), SIGKILL — exit code 137, in-flight work lost.</li>
</ol>
<p>Requirements that are easy to miss:</p>
<ul>
<li><strong>The application must actually handle SIGTERM.</strong> Many do not, and rely on being killed. Check.</li>
<li><strong>PID 1 must receive the signal.</strong> A container started via <code>sh -c &quot;app&quot;</code> makes the shell PID 1, and it does not forward signals. Use exec form (<code>CMD [&quot;app&quot;]</code>), an init such as <code>tini</code>, or <code>docker run --init</code> semantics. This was covered in Post 01 and it bites hardest here.</li>
<li><strong>Set the grace period from measurement.</strong> A worker draining 5-minute jobs needs a grace period longer than 5 minutes, or every deploy kills work in flight.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> if you cannot add a <code>sleep</code> binary to a distroless image, use <code>preStop: httpGet</code> against an endpoint that flips readiness to false and blocks, or add a <code>sleep</code> implementation to the image explicitly. The pattern matters more than the mechanism.</p>
</blockquote>

<li>The algorithm is <code>desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric)</code>, with a tolerance band (10 % by default) so small deviations do not cause churn.</li>
<li><code>Utilization</code> is a percentage <strong>of the CPU request</strong>, not of the node or the limit. A Pod requesting <code>100m</code> and using <code>90m</code> is at 90 % utilisation regardless of how idle the node is. <strong>An HPA on a workload with no CPU request cannot work at all.</strong></li>
<li><code>stabilizationWindowSeconds</code> makes the controller use the <em>maximum</em> recommendation over the window when scaling down (and the minimum when scaling up), which is what stops flapping. Asymmetric windows — scale up fast, scale down slowly — are almost always right.</li>
<li>Resource metrics need <strong>metrics-server</strong> installed. Custom and external metrics need an adapter (typically Prometheus Adapter or KEDA).</li>
<li><strong>Never point an HPA and a VPA at the same metric</strong> on the same workload. They fight: the VPA raises the request, which lowers utilisation, which makes the HPA scale in, which raises per-Pod load, which makes the VPA raise the request again.</li>
<li>The HPA cannot scale below 1 without the alpha/beta scale-to-zero feature; <strong>KEDA</strong> is the usual answer for event-driven scale-to-zero.</li>
</ul>
<h2 id="VerticalPodAutoscaler"><a href="#VerticalPodAutoscaler" class="headerlink" title="VerticalPodAutoscaler"></a>VerticalPodAutoscaler</h2>
<p>The VPA recommends — and optionally applies — better CPU and memory <em>requests</em>, learned from observed usage. Modes: <code>Off</code> (recommend only), <code>Initial</code> (apply at Pod creation), <code>Recreate</code>/<code>Auto</code> (evict and recreate Pods to apply new values).</p>
<p><code>Off</code> mode is genuinely useful on its own: run it across the cluster and read <code>kubectl describe vpa</code> as a free, continuously updated right-sizing report, without letting it touch anything. Historically <code>Auto</code> mode had to evict Pods to change resources, which made it disruptive; <strong>in-place Pod resize graduated to stable in Kubernetes 1.35</strong>, and pod-level in-place resize reached beta in <strong>1.36</strong>, so on current clusters resource changes can increasingly be applied without a restart. Check what your cluster version and your VPA release actually support before relying on it.</p>
<h2 id="Cluster-Autoscaler-and-Karpenter"><a href="#Cluster-Autoscaler-and-Karpenter" class="headerlink" title="Cluster Autoscaler and Karpenter"></a>Cluster Autoscaler and Karpenter</h2>
<p>The HPA adds Pods. Something has to add <strong>nodes</strong> when those Pods do not fit.</p>
<table>
<thead>
<tr>
<th></th>
<th>Cluster Autoscaler</th>
<th>Karpenter</th>
</tr>
</thead>
<tbody>
<tr>
<td>Model</td>
<td>scales pre-defined node groups / ASGs up and down</td>
<td>provisions individual nodes chosen to fit the pending Pods</td>
</tr>
<tr>
<td>Instance choice</td>
<td>fixed per node group</td>
<td>picks instance type, size, zone and capacity type per batch of Pods</td>
</tr>
<tr>
<td>Speed</td>
<td>minutes (ASG-mediated)</td>
<td>typically faster; talks to the cloud API directly</td>
</tr>
<tr>
<td>Consolidation</td>
<td>scale-down of under-used nodes</td>
<td>active consolidation and bin-packing; replaces nodes with cheaper ones</td>
</tr>
<tr>
<td>Availability</td>
<td>all major clouds</td>
<td>AWS-native origin, now with other providers</td>
</tr>
</tbody>

<p>Both react to <strong>unschedulable Pods</strong>, which means both depend entirely on your requests being accurate. Requests that are too high make the autoscaler buy capacity nobody uses; requests that are too low let it under-provision and then evict. Note also that Karpenter-style consolidation deliberately churns nodes, so PodDisruptionBudgets and correct graceful shutdown (Chapter 5) stop being optional.</p>
<h2 id="Right-sizing-methodology"><a href="#Right-sizing-methodology" class="headerlink" title="Right-sizing methodology"></a>Right-sizing methodology</h2>
<p>A repeatable procedure, in order:</p>
<ol>
<li><strong>Instrument first.</strong> Without <code>metrics-server</code> and a metrics store you are guessing. Collect at least two weeks, covering a weekly cycle and any peak event.</li>
<li><strong>Set memory request at ~P95 of observed working set; set the memory limit at the observed peak plus 25-50 %.</strong> Memory is incompressible, so the limit is a safety fuse, not a target.</li>
<li><strong>Set CPU request at ~P90 of observed usage.</strong> This is the scheduling reservation and the HPA's denominator, so it should reflect typical, not peak.</li>
<li><strong>Decide the CPU limit by policy</strong> (Chapter 3), then verify with the throttling ratio.</li>
<li><strong>Check the QoS class you ended up with</strong> — <code>kubectl get pod -o jsonpath='{.status.qosClass}'</code> — and confirm it matches the workload's importance.</li>
<li><strong>Compare requests against actual usage cluster-wide.</strong> The ratio of total requests to total usage is your headline waste number, and it is usually far worse than anyone expects.</li>
<li><strong>Re-measure after every significant release.</strong> Right-sizing is not a one-off project.</li>
</ol>

<h2 id="Exercise-7-—-Right-size-a-real-workload"><a href="#Exercise-7-—-Right-size-a-real-workload" class="headerlink" title="Exercise 7 — Right-size a real workload"></a>Exercise 7 — Right-size a real workload</h2>
<p>Pick one Deployment. Pull 7 days of CPU and memory usage. Compute P90 CPU and P95 memory, set requests accordingly, set the memory limit at peak + 30 %, and measure the throttling ratio before and after. Report the change in requested capacity and in p99 latency.</p>
