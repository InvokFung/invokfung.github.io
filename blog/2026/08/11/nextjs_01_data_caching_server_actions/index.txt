11:T14037,<p>Caching is the part of Next.js that changed the most between versions, and the part most likely to produce a production incident: a price page that serves yesterday's number, a dashboard that shows another tenant's data because a cached function closed over the wrong variable, or a Server Action that anyone on the internet can call because the page that renders it was protected and the action was not. This post covers how to fetch data in Server Components without waterfalls, the four caching layers of Next.js 14, what 15 changed, how Next.js 16 replaced implicit caching with the explicit <code>use cache</code> model (Cache Components), the revalidation APIs and their exact semantics, Server Actions (forms, progressive enhancement, the single-roundtrip response, the security model), and Route Handlers. Every behaviour is tagged with the version it applies to, because a blog post or Stack Overflow answer from 2024 is often wrong for a 2026 codebase.</p>

<h1 id="Chapter-1-—-Fetching-in-Server-Components"><a href="#Chapter-1-—-Fetching-in-Server-Components" class="headerlink" title="Chapter 1 — Fetching in Server Components"></a>Chapter 1 — Fetching in Server Components</h1>
<p>A Server Component can be <code>async</code> and <code>await</code> data directly: no <code>getServerSideProps</code>, no client-side loading state for the first render, and no API layer between the component and the data source unless you want one.</p>
<h2 id="Waterfalls-and-how-to-avoid-them"><a href="#Waterfalls-and-how-to-avoid-them" class="headerlink" title="Waterfalls and how to avoid them"></a>Waterfalls and how to avoid them</h2>
<p>Sequential <code>await</code>s in one component run one after another. Nested async components are worse: a child cannot start fetching until its parent has finished rendering.</p>

<h2 id="Deduplication-fetch-memoisation-and-Reactcache"><a href="#Deduplication-fetch-memoisation-and-Reactcache" class="headerlink" title="Deduplication: fetch memoisation and React.cache"></a>Deduplication: fetch memoisation and <code>React.cache</code></h2>
<p>Two different components often need the same data (the layout shows the user's name, the page shows the user's plan). You do not need to fetch once and drill props down.</p>
<ul>
<li><strong>Fetch memoisation.</strong> <code>fetch</code> requests using <code>GET</code> with the same URL and options are executed once per server render pass, across layouts, pages and other Server Components. Memoisation lasts only for that render pass. It does not apply in Route Handlers (they are not part of the React tree). Pass an <code>AbortController</code> signal to opt out.</li>
<li><strong><code>React.cache</code></strong> does the same for any function (a database query, an SDK call):</li>
</ul>
<pre><code class="language-ts"><figure class="highlight ts"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="ts"><span class="line"><span class="hljs-comment">// data/user.ts</span></span><br><span class="line"><span class="hljs-keyword">import</span> <span class="hljs-string">&#x27;server-only&#x27;</span></span><br><span class="line"><span class="hljs-keyword">import</span> { cache } <span class="hljs-keyword">from</span> <span class="hljs-string">&#x27;react&#x27;</span></span><br><span class="line"><span class="hljs-keyword">import</span> { db } <span class="hljs-keyword">from</span> <span class="hljs-string">&#x27;@/lib/db&#x27;</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">export</span> <span class="hljs-keyword">const</span> getUser = <span class="hljs-title function_">cache</span>(<span class="hljs-title function_">async</span> (<span class="hljs-attr">id</span>: <span class="hljs-built_in">string</span>) =&gt; {</span><br><span class="line">  <span class="hljs-keyword">return</span> db.<span class="hljs-property">user</span>.<span class="hljs-title function_">findUnique</span>({ <span class="hljs-attr">where</span>: { id }, <span class="hljs-attr">select</span>: { <span class="hljs-attr">id</span>: <span class="hljs-literal">true</span>, <span class="hljs-attr">name</span>: <span class="hljs-literal">true</span>, <span class="hljs-attr">plan</span>: <span class="hljs-literal">true</span> } })</span><br><span class="line">})</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

</blockquote>

<p>Next.js 14 (and 13.4+) had four layers, most of them <strong>on by default</strong>. A great deal of 2023-2024 content assumes this model.</p>

<p>In 14, a <code>fetch</code> was cached in the Data Cache unless something opted it out: <code>cache: 'no-store'</code>, <code>next: { revalidate: 0 }</code>, a <code>POST</code> Route Handler, reading <code>cookies()</code> or <code>headers()</code> before it, <code>export const dynamic = 'force-dynamic'</code>, and a few more heuristics. Non-<code>fetch</code> data (an ORM query) was cached through <code>unstable_cache</code>.</p>
<p>The model was fast by default and confusing by default. The typical incident: a developer adds a <code>fetch</code> to an external pricing API, it works in development, and production serves the build-time price for days because the Data Cache persisted the response and the route was prerendered as static.</p>

<h1 id="Chapter-3-—-What-Nextjs-15-changed"><a href="#Chapter-3-—-What-Nextjs-15-changed" class="headerlink" title="Chapter 3 — What Next.js 15 changed"></a>Chapter 3 — What Next.js 15 changed</h1>
<p>Next.js 15 (October 2024) flipped several defaults to &quot;uncached unless you ask&quot;:</p>

<p>&quot;<code>auto no cache</code>&quot; is subtle. The fetch is not stored in the Data Cache, but if the <strong>route</strong> is prerendered statically at build time, the fetch runs once during <code>next build</code> and its result is baked into the static HTML. If the route uses a request-time API (<code>cookies()</code>, <code>headers()</code>, <code>searchParams</code>, <code>connection()</code>), the fetch runs on every request. So &quot;15 does not cache fetch&quot; is only half true: a static route still freezes the data until the route is revalidated.</p>

<h2 id="The-new-default-dynamic-with-explicit-caching"><a href="#The-new-default-dynamic-with-explicit-caching" class="headerlink" title="The new default: dynamic, with explicit caching"></a>The new default: dynamic, with explicit caching</h2>
<p>Next.js 16 (October 2025) introduced <strong>Cache Components</strong>, enabled with one flag:</p>

<h2 id="What-goes-into-the-cache-key"><a href="#What-goes-into-the-cache-key" class="headerlink" title="What goes into the cache key"></a>What goes into the cache key</h2>
<p>A cache entry's key is built from:</p>
<ol>
<li><strong>Build ID</strong> (or <code>deploymentId</code> if configured). A new deploy invalidates every entry.</li>
<li><strong>Function ID</strong>: a secure hash of the function's location and signature.</li>
<li><strong>Serialisable arguments</strong>: props for components, arguments for functions.</li>
<li><strong>Closed-over variables</strong>: variables captured from an outer scope are bound as arguments automatically.</li>
<li>In development only, an HMR refresh hash.</li>
</ol>
<p>Point 4 is what makes nested cached functions safe:</p>

You may accept a non-serialisable value (such as <code>children</code> or a Server Action) only as <strong>pass-through</strong>: return it in JSX without reading it. That is how a cached layout can wrap uncached children: slots do not affect the cache entry.</p>

<p>Two rules that bite:</p>
<ul>
<li>A short lifetime (<code>revalidate</code> 0, or <code>expire</code> under 5 minutes, as with <code>seconds</code>) cannot be prerendered; the entry becomes a <strong>dynamic hole</strong> resolved at request time and needs a Suspense boundary.</li>
<li>Nesting a short-lived cache inside a <code>'use cache'</code> scope that has <strong>no explicit</strong> <code>cacheLife</code> fails the build, because the outer entry would silently become short-lived too. Always call <code>cacheLife</code> explicitly.</li>
</ul>
<h2 id="Where-entries-live-memory-remote-private"><a href="#Where-entries-live-memory-remote-private" class="headerlink" title="Where entries live: memory, remote, private"></a>Where entries live: memory, remote, private</h2>
<ul>
<li><strong><code>'use cache'</code></strong> stores entries through a cache handler, <strong>in memory (LRU) by default</strong>. Self-hosted, entries persist across requests in that process (size via <code>cacheMaxMemorySize</code>). On serverless, instances are ephemeral, so runtime entries often do not survive between requests; build-time entries work normally.</li>
<li><strong><code>'use cache: remote'</code></strong> lets the platform (or your <code>cacheHandlers</code> config) store entries in a shared store such as Redis. It costs a network round trip per lookup.</li>
<li><strong><code>'use cache: private'</code></strong> exists for the rare case where you cannot refactor runtime data out of the cached scope. Results are not stored in a server cache across production requests.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> neither <code>'use cache'</code> nor <code>'use cache: remote'</code> survives a deploy, because the build ID is in the key. The legacy <code>fetch</code> Data Cache and <code>unstable_cache</code> <strong>do</strong> persist across deploys. Migrating a slow upstream call from <code>unstable_cache</code> to <code>'use cache'</code> changes post-deploy load on that upstream.</p>
</blockquote>

<h1 id="Chapter-6-—-Server-Actions-and-Server-Functions"><a href="#Chapter-6-—-Server-Actions-and-Server-Functions" class="headerlink" title="Chapter 6 — Server Actions and Server Functions"></a>Chapter 6 — Server Actions and Server Functions</h1>
<h2 id="Vocabulary"><a href="#Vocabulary" class="headerlink" title="Vocabulary"></a>Vocabulary</h2>
<p>React calls any function marked <code>'use server'</code> a <strong>Server Function</strong>. When it is used through React's action mechanisms (<code>&lt;form action&gt;</code>, <code>&lt;button formAction&gt;</code>, or called inside <code>startTransition</code>), it is a <strong>Server Action</strong>. Next.js docs use both terms; they describe the same compiled artefact.</p>
<p>At build time, <code>'use server'</code> tells the compiler to replace the function in client bundles with a reference: an <strong>action ID</strong> plus a dispatcher that POSTs to the <strong>route of the page that invokes it</strong>. The implementation stays on the server. Since 15, IDs are unguessable and non-deterministic, rotated at most every 14 days, and actions that nothing imports are removed from the client bundle entirely (dead code elimination).</p>

<p>The form is a real HTML <code>&lt;form&gt;</code> posting to the page URL, so it can submit before JavaScript has loaded (progressive enhancement). <code>useActionState</code> replaced the earlier <code>useFormState</code> from React canaries (the name in Next.js 14 era code).</p>
<p>For instant feedback, <code>useOptimistic</code> shows the expected result while the action runs and rolls back automatically if it fails.</p>
<h2 id="One-round-trip-carries-data-and-UI"><a href="#One-round-trip-carries-data-and-UI" class="headerlink" title="One round trip carries data and UI"></a>One round trip carries data and UI</h2>
<p>When an action calls <code>updateTag</code>, <code>revalidatePath</code> or <code>refresh</code>, mutates cookies, or calls <code>redirect</code>, Next.js re-renders the current route (or the redirect target) in the <strong>same response</strong>. One Flight stream carries both the action's return value and the new RSC payload. No follow-up fetch is needed. <code>revalidateTag</code> with a profile is the exception: it only schedules a background refresh.</p>
<p>Put revalidation calls <strong>before</strong> <code>redirect</code>, because <code>redirect</code> throws.</p>
<p><strong>Actions are dispatched one at a time per client.</strong> <code>Promise.all([actionA(), actionB()])</code> from the browser does not run them in parallel; the second waits for the first. Parallel work belongs inside one action, in a Server Component, or in a Route Handler.</p>
<h2 id="Security-model-every-action-is-a-public-endpoint"><a href="#Security-model-every-action-is-a-public-endpoint" class="headerlink" title="Security model: every action is a public endpoint"></a>Security model: every action is a public endpoint</h2>
<p>The single most important fact: <strong>an exported Server Action is reachable by anyone who can send the same POST</strong>, whether or not your UI renders the form. A page-level auth check protects the page's HTML, not the action.</p>

<p>Checklist for every action:</p>
<ol>
<li><strong>Authenticate</strong> (is there a user?) and <strong>authorise</strong> (may this user touch this resource?). Missing authorisation is an IDOR bug.</li>
<li><strong>Validate input</strong> with a schema. Schema validation checks shape, not ownership.</li>
<li><strong>Return the minimum.</strong> Return values are serialised to the client; never return a raw database row.</li>
<li><strong>Keep it thin.</strong> Delegate to the <code>server-only</code> DAL so the checks live in one place.</li>
</ol>
<p>What the framework adds on top:</p>
<table>
<thead>
<tr>
<th>Protection</th>
<th>Detail</th>
</tr>
</thead>
<tbody>
<tr>
<td>CSRF check</td>
<td>Only <code>POST</code> invokes actions. The <code>Origin</code> header's host is compared with <code>Host</code> / <code>X-Forwarded-Host</code>; a mismatch is rejected. Extra hosts go in <code>experimental.serverActions.allowedOrigins</code> (<code>*</code> = one label, <code>**</code> = one or more). A request with no <code>Origin</code> header is allowed through with a warning.</td>
</tr>
<tr>
<td>Body size limit</td>
<td>1 MB by default; <code>experimental.serverActions.bodySizeLimit</code> (e.g. <code>'2mb'</code>).</td>
</tr>
<tr>
<td>Secure IDs + dead code elimination</td>
<td>Since 15; IDs rotate at most every 14 days.</td>
</tr>
<tr>
<td>Closure encryption</td>
<td>Variables captured by an inline action are encrypted before being sent to the client, with a new key per build. Set <code>NEXT_SERVER_ACTIONS_ENCRYPTION_KEY</code> (base64 AES key of 16, 24 or 32 bytes) on multi-instance deployments, or instances cannot decrypt each other's references.</td>
</tr>
</tbody>

<blockquote>
<p><strong>Watch out:</strong> closure encryption hides captured values from casual inspection, but Next.js explicitly says not to rely on it alone. Do not close over secrets; re-read sensitive values on the server inside the action.</p>
</blockquote>
<blockquote>
<p><strong>Common pitfall:</strong> a Proxy (<code>proxy.ts</code>, formerly <code>middleware.ts</code>) matcher that excludes a path also skips every Server Action posted to that path, because actions are POSTs to the page route. A refactor that moves an action can silently remove Proxy coverage. This is one more reason to check auth inside the action.</p>
</blockquote>
<p>The deserialiser that decodes Server Function arguments is itself attack surface: the critical React Server Components vulnerability of December 2025 (CVE-2025-55182, CVSS 10.0) was in exactly this code path. Post 03 covers it.</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Explain-the-stale-price"><a href="#Exercise-1-—-Explain-the-stale-price" class="headerlink" title="Exercise 1 — Explain the stale price"></a>Exercise 1 — Explain the stale price</h2>
<p>A Next.js 15 page does <code>await fetch('https://api.example.com/price')</code> with no options and uses no request-time APIs. In production the price never changes. Why, and give two fixes.</p>
<details>
<summary>Solution</summary>
<p>The route has no dynamic API, so it is prerendered at build time; under <code>auto no cache</code> the fetch runs once during <code>next build</code>, and the value is frozen in the static HTML. Fixes: <code>fetch(url, { next: { revalidate: 60 } })</code> (time-based ISR), or <code>{ cache: 'no-store' }</code> / <code>await connection()</code> to render per request. With Cache Components in 16, put the fetch in a <code>'use cache'</code> function with <code>cacheLife('minutes')</code>, or leave it uncached inside Suspense.</p>
</details>
<h2 id="Exercise-2-—-Cache-key-bug"><a href="#Exercise-2-—-Cache-key-bug" class="headerlink" title="Exercise 2 — Cache-key bug"></a>Exercise 2 — Cache-key bug</h2>
<p>A developer writes a <code>'use cache'</code> function <code>getDashboard()</code> that calls <code>getCurrentUser()</code> (which reads cookies) inside it. What happens, and what is the fix?</p>
<details>
<summary>Solution</summary>
<p>It fails with the <code>next-request-in-use-cache</code> error, because runtime APIs are forbidden inside cached scopes, including through helpers. Read the user outside and pass the id: <code>getDashboard(user.id)</code>. The id then becomes part of the key, so each user gets their own entry. Without that rule, one cached dashboard could be served to every user.</p>
</details>
<h2 id="Exercise-3-—-Pick-the-invalidation-API"><a href="#Exercise-3-—-Pick-the-invalidation-API" class="headerlink" title="Exercise 3 — Pick the invalidation API"></a>Exercise 3 — Pick the invalidation API</h2>
<p>For each case choose <code>updateTag</code>, <code>revalidateTag(tag, 'max')</code>, <code>revalidatePath</code> or <code>refresh</code>: (a) a user edits their display name and must see it immediately; (b) a CMS webhook says an article changed; (c) an action marks a notification read and the unread counter is uncached; (d) an admin action changes an untagged page.</p>
<details>
<summary>Solution</summary>
<p>(a) <code>updateTag</code> (read-your-own-writes, action only). (b) <code>revalidateTag(tag, 'max')</code> (Route Handler; <code>updateTag</code> is not allowed there). (c) <code>refresh()</code> (only uncached data changed). (d) <code>revalidatePath('/that/page')</code>.</p>
</details>
<h2 id="Exercise-4-—-Secure-the-action"><a href="#Exercise-4-—-Secure-the-action" class="headerlink" title="Exercise 4 — Secure the action"></a>Exercise 4 — Secure the action</h2>

<h2 id="Exercise-5-—-Multi-instance-failure"><a href="#Exercise-5-—-Multi-instance-failure" class="headerlink" title="Exercise 5 — Multi-instance failure"></a>Exercise 5 — Multi-instance failure</h2>
<p>Three containers behind a load balancer intermittently log &quot;Failed to find Server Action&quot;. Give two causes and the fixes.</p>
<details>
<summary>Solution</summary>
<p>(1) Each build generated its own closure-encryption key, or instances run different builds: set a shared <code>NEXT_SERVER_ACTIONS_ENCRYPTION_KEY</code> and deploy one build everywhere. (2) Version skew during a rolling deploy: a client from the old build calls an action ID the new build does not have. Configure <code>deploymentId</code>, prefer rolling deploys, and surface the error as a &quot;refresh and retry&quot; message.</p>
</details>
