11:Tc21a,<p>Every line in a text file ends with one or two invisible bytes. Windows usually writes two (CR LF); Linux and macOS write one (LF). Most of the time nobody notices. <h2 id="Where-they-came-from"><a href="#Where-they-came-from" class="headerlink" title="Where they came from"></a>Where they came from</h2>
<p>On a typewriter or an old teleprinter, two separate motions start a new line. The <strong>carriage return</strong> moves the print head back to the left margin. The <strong>line feed</strong> rolls the paper up one line. Teleprinters needed both codes, so early systems stored both.</p>
<p>The choice then split:</p>
<table>
<thead>
<tr>
<th>System</th>
<th>Line ending</th>
</tr>
</thead>
<tbody>
<tr>
<td>CP/M, MS-DOS, Windows</td>
<td>CRLF</td>
</tr>
<tr>
<td>Unix, Linux, macOS (since Mac OS X)</td>
<td>LF</td>
</tr>
<tr>
<td>Classic Mac OS (before Mac OS X)</td>
<td>CR</td>
</tr>
</tbody>
</table>
<p>Unix stores only LF in files and lets the terminal driver add the CR when printing. Windows kept the CP/M and MS-DOS habit of storing both.</p>
<p>Many internet protocols still use CRLF on the wire, whatever the operating system. HTTP/1.1 (RFC 9112) defines a message as <code>start-line CRLF *( field-line CRLF ) CRLF</code>, and CSV (RFC 4180) ends each record with CRLF. That is the protocol's business; your library handles it. This post is about <strong>files in your repository</strong>.</p>
<blockquote>
<p><strong>Watch out:</strong> Windows Notepad only understood CRLF until 2018. Microsoft then added support for LF and CR files. New files in Notepad still use CRLF by default.</p>
</blockquote>

<p>Line endings are invisible in an editor. Look at the bytes instead.</p>

<h2 id="Two-invisible-byte-problems"><a href="#Two-invisible-byte-problems" class="headerlink" title="Two invisible byte problems"></a>Two invisible byte problems</h2>
<p>Dev Essentials 01 · Text Encoding covered the BOM: three invisible bytes <code>EF BB BF</code> at the start of a file. CRLF is the same kind of problem: an invisible <code>0D</code> before every <code>0A</code>. One file can have both, and <code>file</code> reports both:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-built_in">printf</span> <span class="hljs-string">&#x27;\xef\xbb\xbfhi\r\n&#x27;</span> | file -</span><br><span class="line"><span class="hljs-comment"># /dev/stdin: Unicode text, UTF-8 (with BOM) text, with CRLF line terminators</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Both come from a tool that used a system default instead of a project rule. Both are fixed the same way: write the rule into the repository.</p>
<hr>
<h1 id="Chapter-3-—-How-line-endings-break-things"><a href="#Chapter-3-—-How-line-endings-break-things" class="headerlink" title="Chapter 3 — How line endings break things"></a>Chapter 3 — How line endings break things</h1>
<h2 id="1-Shell-scripts-in-Linux-containers-and-CI"><a href="#1-Shell-scripts-in-Linux-containers-and-CI" class="headerlink" title="1. Shell scripts in Linux, containers and CI"></a>1. Shell scripts in Linux, containers and CI</h2>
<p>A script saved with CRLF has a first line of <code>#!/bin/bash\r</code>. The system looks for an interpreter literally named <code>/bin/bash\r</code>, which does not exist.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-built_in">printf</span> <span class="hljs-string">&#x27;#!/bin/bash\r\necho hi\r\n&#x27;</span> &gt; crlf.sh &amp;&amp; <span class="hljs-built_in">chmod</span> +x crlf.sh</span><br><span class="line">./crlf.sh</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>What you see depends on where you run it:</p>
<table>
<thead>
<tr>
<th>Where</th>
<th>Message</th>
</tr>
</thead>
<tbody>
<tr>
<td>Ubuntu 24.04, bash 5.2 (tested)</td>
<td><code>bash: ./crlf.sh: cannot execute: required file not found</code></td>
</tr>
<tr>
<td>Older bash versions</td>
<td><code>bash: ./crlf.sh: /bin/bash^M: bad interpreter: No such file or directory</code></td>
</tr>
<tr>
<td>Git Bash on Windows (tested, bash 5.2 MSYS)</td>
<td>runs and prints <code>hi</code></td>
</tr>
</tbody>
</table>
<p>The last row is the trap. The script works on the Windows machine where it was written, then fails in Docker or on a Linux CI runner. Even when bash starts (for example <code>bash crlf2.sh</code>), the <code>\r</code> stays at the end of every command:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">crlf2.sh: line 3: cd: $&#x27;/tmp\r&#x27;: No such file or directory</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="2-Diffs-where-every-line-changed"><a href="#2-Diffs-where-every-line-changed" class="headerlink" title="2. Diffs where every line changed"></a>2. Diffs where every line changed</h2>
<p>If one person commits a file with LF and the next commits it with CRLF, Git sees a change on <strong>every line</strong>. The real one-line change is hidden, reviews become useless, and <code>git blame</code> now points every line at the wrong commit. <code>git diff --ignore-cr-at-eol</code> (or <code>-w</code>) hides CR-only changes so you can find the real one.</p>
<h2 id="3-Regex-split-and-CSV"><a href="#3-Regex-split-and-CSV" class="headerlink" title="3. Regex, split and CSV"></a>3. Regex, split and CSV</h2>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> re</span><br><span class="line"> </span><br><span class="line">text = <span class="hljs-string">&quot;abc\r\ndef\r\n&quot;</span>                         <span class="hljs-comment"># CRLF text read in binary mode or with newline=&quot;&quot;</span></span><br><span class="line"><span class="hljs-built_in">print</span>(text.split(<span class="hljs-string">&quot;\n&quot;</span>))                         <span class="hljs-comment"># [&#x27;abc\r&#x27;, &#x27;def\r&#x27;, &#x27;&#x27;]</span></span><br><span class="line"><span class="hljs-built_in">print</span>(text.splitlines())                        <span class="hljs-comment"># [&#x27;abc&#x27;, &#x27;def&#x27;]</span></span><br><span class="line"><span class="hljs-built_in">print</span>(re.findall(<span class="hljs-string">r&quot;(?m)^(\w+)$&quot;</span>, text))         <span class="hljs-comment"># []  ($ matches before \n, but \r is in the way)</span></span><br><span class="line"><span class="hljs-built_in">print</span>(re.findall(<span class="hljs-string">r&quot;(?m)^(.+)$&quot;</span>, text))          <span class="hljs-comment"># [&#x27;abc\r&#x27;, &#x27;def\r&#x27;]</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A value such as <code>&quot;def\r&quot;</code> then fails an equality check, a dictionary lookup or a hash comparison. The last field of each CSV row is the usual victim.</p>
<h2 id="4-Tests-and-checksums"><a href="#4-Tests-and-checksums" class="headerlink" title="4. Tests and checksums"></a>4. Tests and checksums</h2>
<p>A test that compares output with a saved &quot;golden&quot; file, or a checksum of a text file, passes on one OS and fails on another. The bytes differ even though the text looks the same.</p>
<blockquote>
<p><strong>Common pitfall:</strong> Python's text mode on Windows <strong>writes CRLF</strong> by default. The docs say: &quot;if newline is None, any '\n' characters written are translated to the system default line separator, os.linesep.&quot; Pass <code>newline=&quot;\n&quot;</code> when a file must have LF: <code>open(&quot;out.txt&quot;, &quot;w&quot;, encoding=&quot;utf-8&quot;, newline=&quot;\n&quot;)</code>.</p>
</blockquote>
<hr>
<h1 id="Chapter-4-—-Gits-conversion-coreautocrlf"><a href="#Chapter-4-—-Gits-conversion-coreautocrlf" class="headerlink" title="Chapter 4 — Git's conversion: core.autocrlf"></a>Chapter 4 — Git's conversion: <code>core.autocrlf</code></h1>
<p>Git keeps two copies of each file: the one <strong>in the repository</strong> (index and commits) and the one <strong>in your working tree</strong>. It can convert line endings when it moves a file between them.</p>
<table>
<thead>
<tr>
<th><code>core.autocrlf</code></th>
<th>On commit (working tree → repo)</th>
<th>On checkout (repo → working tree)</th>
<th>Typical use</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>true</code></td>
<td>CRLF → LF</td>
<td>LF → CRLF</td>
<td>Windows (GitHub's docs recommend it there)</td>
</tr>
<tr>
<td><code>input</code></td>
<td>CRLF → LF</td>
<td>no change</td>
<td>macOS / Linux (GitHub's recommendation)</td>
</tr>
<tr>
<td><code>false</code></td>
<td>no change</td>
<td>no change</td>
<td>You manage endings yourself, or with <code>.gitattributes</code></td>
</tr>
</tbody>
</table>
<p>The git-config docs describe <code>true</code> as &quot;the same as setting the <code>text</code> attribute to <code>auto</code> on all files and <code>core.eol</code> to <code>crlf</code>&quot;. So with <code>true</code>, the repository holds LF and your working tree holds CRLF.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git config --show-origin --get core.autocrlf    <span class="hljs-comment"># value, and which config file set it</span></span><br><span class="line">git config --global core.autocrlf <span class="hljs-literal">true</span>          <span class="hljs-comment"># set it for your user (Windows)</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The Git for Windows installer asks about this. Its option &quot;Checkout Windows-style, commit Unix-style line endings&quot; sets <code>core.autocrlf=true</code>, usually in the <strong>system</strong> config file. That is why <code>--show-origin</code> helps when you do not remember setting it.</p>
<h2 id="The-warning"><a href="#The-warning" class="headerlink" title="The warning"></a>The warning</h2>
<p>With <code>core.autocrlf=true</code>, adding a file that has LF endings prints:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">warning: in the working copy of &#x27;post.md&#x27;, LF will be replaced by CRLF the next time Git touches it</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>This is information, not an error. The file goes into the repository with LF, as intended; the next checkout will write it to your working tree with CRLF. (Older Git versions worded it as <code>warning: LF will be replaced by CRLF in post.md.</code>) The check is controlled by <code>core.safecrlf</code>, which defaults to <code>warn</code>. With <code>core.safecrlf=true</code>, Git refuses instead: <code>fatal: LF would be replaced by CRLF in post.md</code>.</p>
<h2 id="The-weakness-it-is-per-machine"><a href="#The-weakness-it-is-per-machine" class="headerlink" title="The weakness: it is per machine"></a>The weakness: it is per machine</h2>
<p><code>core.autocrlf</code> lives in each person's config, not in the repository. Every clone behaves the way its own machine is set up. One teammate with <code>false</code> on Windows can commit CRLF files, and the repository has no defence. The fix is to put the rule <strong>in the repository</strong>.</p>
<hr>
<h1 id="Chapter-5-—-gitattributes-rules-that-travel-with-the-repo"><a href="#Chapter-5-—-gitattributes-rules-that-travel-with-the-repo" class="headerlink" title="Chapter 5 — .gitattributes: rules that travel with the repo"></a>Chapter 5 — <code>.gitattributes</code>: rules that travel with the repo</h1>
<p>A <code>.gitattributes</code> file at the root of the repository sets per-path attributes. It is committed, so every clone follows it. GitHub's docs say: &quot;When you commit this file to a repository, it overrides the <code>core.autocrlf</code> setting for all repository contributors.&quot;</p>
<h2 id="A-good-default-for-most-projects"><a href="#A-good-default-for-most-projects" class="headerlink" title="A good default for most projects"></a>A good default for most projects</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span></pre></td><td class="code"><pre><code class="text"><span class="line"># .gitattributes</span><br><span class="line"> </span><br><span class="line"># Git decides text vs binary. <h2 id="LF-everywhere-or-native-endings"><a href="#LF-everywhere-or-native-endings" class="headerlink" title="LF everywhere, or native endings?"></a>LF everywhere, or native endings?</h2>
<ul>
<li><strong><code>* text=auto eol=lf</code></strong>: LF in the repository and in every working tree, Windows included. Best when the project has shell scripts or Docker files, or builds on Linux CI. Modern Windows editors (VS Code, Notepad since 2018) handle LF.</li>
<li><strong><code>* text=auto</code></strong> alone: LF in the repository, native endings in each working tree. The docs: if <code>text</code> is set but neither <code>core.autocrlf</code> nor <code>core.eol</code> is, &quot;the default is <code>eol=crlf</code> on Windows and <code>eol=lf</code> on all other platforms&quot;.</li>
</ul>
<p>Either way the <strong>repository</strong> content is LF and the same for everyone. That is what stops the whole-file diffs.</p>
<blockquote>
<p><strong>Trick:</strong> put per-type exceptions below the <code>*</code> line. When more than one line matches a path, the later line wins, one attribute at a time.</p>
</blockquote>
<hr>
<h1 id="Chapter-6-—-Fixing-an-existing-repository"><a href="#Chapter-6-—-Fixing-an-existing-repository" class="headerlink" title="Chapter 6 — Fixing an existing repository"></a>Chapter 6 — Fixing an existing repository</h1>
<p>Adding <code>.gitattributes</code> does not rewrite files already committed. To convert them, <strong>renormalize</strong>. Start from a clean working tree (commit or stash your work first; Dev Essentials 03 · Git Rescue Kit covers stashing safely).</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="bash"><span class="line">git status                                <span class="hljs-comment"># must be clean</span></span><br><span class="line"><span class="hljs-comment"># create .gitattributes as in Chapter 5, then:</span></span><br><span class="line">git add .gitattributes</span><br><span class="line">git add --renormalize .                   <span class="hljs-comment"># re-apply the rules to every tracked file</span></span><br><span class="line">git status                                <span class="hljs-comment"># lists files whose stored endings change</span></span><br><span class="line">git commit -m <span class="hljs-string">&quot;Normalize line endings&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>This is the sequence from the gitattributes docs and GitHub's line-ending guide. If a file that should not change shows up in <code>git status</code>, give it the <code>-text</code> or <code>binary</code> attribute and run the add again.</p>
<p>Two follow-ups:</p>
<ul>
<li><strong>Working copies.</strong> Files already on disk keep their old endings until Git writes them again. The simplest way to get a working tree that matches the new rules is a fresh clone.</li>
<li><strong>Blame noise.</strong> The normalize commit touches many lines. List its hash in a <code>.git-blame-ignore-revs</code> file at the repository root. GitHub's blame view reads that file, and locally you can run <code>git config blame.ignoreRevsFile .git-blame-ignore-revs</code>.</li>
</ul>

</tbody>
</table>
<p>The first line is what <code>core.autocrlf=true</code> with no <code>.gitattributes</code> looks like: LF in the repository, CRLF on disk, and no attribute. Any <code>i/crlf</code> or <code>i/mixed</code> on a text file is a file that was committed with CR bytes.</p>
<hr>
<h1 id="Chapter-7-—-Editors-editorconfig"><a href="#Chapter-7-—-Editors-editorconfig" class="headerlink" title="Chapter 7 — Editors: .editorconfig"></a>Chapter 7 — Editors: <code>.editorconfig</code></h1>
<p><code>.gitattributes</code> controls what Git stores and checks out. It does not stop your editor from saving CRLF into a new file before Git sees it. <strong>EditorConfig</strong> is a small, widely supported file that tells editors how to save:</p>
<pre><code class="language-ini"><figure class="highlight ini"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span></pre></td><td class="code"><pre><code class="ini"><span class="line"><span class="hljs-comment"># .editorconfig</span></span><br><span class="line"><span class="hljs-attr">root</span> = <span class="hljs-literal">true</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-section">[*]</span></span><br><span class="line"><span class="hljs-attr">charset</span> = utf-<span class="hljs-number">8</span></span><br><span class="line"><span class="hljs-attr">end_of_line</span> = lf</span><br><span class="line"><span class="hljs-attr">insert_final_newline</span> = <span class="hljs-literal">true</span></span><br><span class="line"><span class="hljs-attr">trim_trailing_whitespace</span> = <span class="hljs-literal">true</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-section">[*.{bat,cmd}]</span></span><br><span class="line"><span class="hljs-attr">end_of_line</span> = crlf</span><br><span class="line"> </span><br><span class="line"><span class="hljs-section">[*.md]</span></span><br><span class="line"><span class="hljs-attr">trim_trailing_whitespace</span> = <span class="hljs-literal">false</span>   <span class="hljs-comment"># two trailing spaces = a Markdown line break</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>From the EditorConfig spec: <code>end_of_line</code> accepts <code>lf</code>, <code>cr</code> or <code>crlf</code>; <code>charset</code> accepts <code>latin1</code>, <code>utf-8</code>, <code>utf-8-bom</code>, <code>utf-16be</code> or <code>utf-16le</code>; and <code>root = true</code> stops the search for more <code>.editorconfig</code> files in parent folders. Visual Studio and JetBrains IDEs read it with no plugin. VS Code needs the EditorConfig extension.</p>
<p>Note the <code>charset = utf-8</code> line: the same file also guards against the encoding problems of Dev Essentials 01.</p>
<hr>
<h1 id="Chapter-8-—-Converting-files-by-hand"><a href="#Chapter-8-—-Converting-files-by-hand" class="headerlink" title="Chapter 8 — Converting files by hand"></a>Chapter 8 — Converting files by hand</h1>
<p>Sometimes you just need to fix one file.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">dos2unix deploy.sh              <span class="hljs-comment"># CRLF -&gt; LF   (ships with Git for Windows)</span></span><br><span class="line">unix2dos run.bat                <span class="hljs-comment"># LF -&gt; CRLF</span></span><br><span class="line">sed -i <span class="hljs-string">&#x27;s/\r$//&#x27;</span> deploy.sh      <span class="hljs-comment"># CRLF -&gt; LF with plain sed</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>In Windows PowerShell 5.1, go through .NET so neither the encoding nor the endings change by accident:</p>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="powershell"><span class="line"><span class="hljs-variable">$p</span> = (<span class="hljs-built_in">Resolve-Path</span> .\deploy.sh).Path</span><br><span class="line"><span class="hljs-variable">$t</span> = [<span class="hljs-type">System.IO.File</span>]::ReadAllText(<span class="hljs-variable">$p</span>, [<span class="hljs-type">System.Text.Encoding</span>]::UTF8)</span><br><span class="line">[<span class="hljs-type">System.IO.File</span>]::WriteAllText(<span class="hljs-variable">$p</span>, (<span class="hljs-variable">$t</span> <span class="hljs-operator">-replace</span> <span class="hljs-string">&quot;`r`n&quot;</span>, <span class="hljs-string">&quot;`n&quot;</span>), (<span class="hljs-built_in">New-Object</span> System.Text.UTF8Encoding(<span class="hljs-variable">$false</span>)))</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Common pitfall:</strong> <code>(Get-Content file) | Set-Content file</code> in Windows PowerShell 5.1 changes two things at once. <code>Get-Content</code> splits the text into lines and drops the endings. <code>Set-Content</code> writes each line back followed by a Windows newline (CRLF), and by default in the ANSI code page. One harmless-looking line changes both the line endings and the encoding.</p>
</blockquote>
<p>In Python, work in bytes. Then there is no newline translation and no decoding step:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">from</span> pathlib <span class="hljs-keyword">import</span> Path</span><br><span class="line"> </span><br><span class="line">p = Path(<span class="hljs-string">&quot;deploy.sh&quot;</span>)</span><br><span class="line">p.write_bytes(p.read_bytes().replace(<span class="hljs-string">b&quot;\r\n&quot;</span>, <span class="hljs-string">b&quot;\n&quot;</span>))</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-9-—-Case-study-this-blogs-repository"><a href="#Chapter-9-—-Case-study-this-blogs-repository" class="headerlink" title="Chapter 9 — Case study: this blog's repository"></a>Chapter 9 — Case study: this blog's repository</h1>
<p>The facts:</p>
<ul>
<li>The author's Windows machine has <code>core.autocrlf=true</code>.</li>
<li>The blog repository has <strong>no <code>.gitattributes</code></strong> and no <code>.editorconfig</code>.</li>
</ul>
<p>What follows from the Git docs, and what <code>file</code> shows on the working copy:</p>
<ul>
<li><strong>The repository holds LF.</strong> With <code>autocrlf=true</code>, text files are normalized to LF when added. The Linux build on GitHub Actions checks out LF files.</li>
<li><strong>The working copy is mixed.</strong> A post checked out by Git shows &quot;with CRLF line terminators&quot; in <code>file</code>. A file written later by a tool that saves LF shows no CRLF. Both are fine locally, because Git converts them to LF on commit. Adding such an LF file prints the &quot;LF will be replaced by CRLF the next time Git touches it&quot; warning.</li>
<li><strong>The protection lives on one machine.</strong> A clone on another Windows machine with <code>core.autocrlf=false</code> would commit CRLF, and the next diff of that post would show every line changed. Nothing in the repository prevents it.</li>
</ul>
<p>A small change would move the rule into the repository:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="text"><span class="line"># .gitattributes (proposed)</span><br><span class="line">* text=auto eol=lf</span><br><span class="line">*.png binary</span><br><span class="line">*.jpg binary</span><br><span class="line">*.webp binary</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Add an <code>.editorconfig</code> with <code>end_of_line = lf</code> and <code>charset = utf-8</code>, then run <code>git add --renormalize .</code> in one dedicated commit.</p>
<p>The link to Dev Essentials 01 is direct. The encoding damage and the CRLF question have the same root: a tool used a machine default (the ANSI code page, the platform newline) where the project needed an explicit rule. The fix is the same too: write the rule down in the repository, where every tool and every machine can see it.</p>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Read-the-bytes"><a href="#Exercise-1-—-Read-the-bytes" class="headerlink" title="Exercise 1 — Read the bytes"></a>Exercise 1 — Read the bytes</h2>
<p><code>od -c notes.txt</code> prints <code>h  i  \r  \n  o  k  \n</code>. What does <code>file</code> report, and what does <code>cat -A</code> show?</p>
<details>
<summary>Solution</summary>
<p>The file is mixed: one CRLF line and one LF line. <code>file</code> reports <code>ASCII text, with CRLF, LF line terminators</code>. <code>cat -A</code> shows:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line">hi^M$</span><br><span class="line">ok$</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
</details>
<h2 id="Exercise-2-—-Works-on-my-machine"><a href="#Exercise-2-—-Works-on-my-machine" class="headerlink" title="Exercise 2 — Works on my machine"></a>Exercise 2 — Works on my machine</h2>
<p><code>./deploy.sh</code> runs in Git Bash on Windows but fails in a Linux Docker container with <code>cannot execute: required file not found</code>. Explain, and fix it twice: once now, once for good.</p>
<details>
<summary>Solution</summary>
<p>The file has CRLF endings, so the shebang names <code>/bin/bash\r</code>. Git Bash tolerated it; Linux does not.</p>
<p>Now: <code>dos2unix deploy.sh</code> (or <code>sed -i 's/\r$//' deploy.sh</code>), then commit.</p>
<p>For good: add <code>*.sh text eol=lf</code> (or <code>* text=auto eol=lf</code>) to <code>.gitattributes</code>, run <code>git add --renormalize .</code>, and commit. Every checkout, on every OS, then gets LF.</p>
</details>
<h2 id="Exercise-3-—-Write-the-attributes"><a href="#Exercise-3-—-Write-the-attributes" class="headerlink" title="Exercise 3 — Write the attributes"></a>Exercise 3 — Write the attributes</h2>
<p>A repository has <code>.sh</code>, <code>.ps1</code>, <code>.bat</code>, <code>.md</code> and <code>.png</code> files. The CI runs on Linux. Write its <code>.gitattributes</code>.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="text"><span class="line">* text=auto eol=lf</span><br><span class="line">*.bat text eol=crlf</span><br><span class="line">*.png binary</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>.sh</code>, <code>.ps1</code> and <code>.md</code> are covered by the first line; PowerShell reads LF scripts without trouble. Only <code>.bat</code> needs CRLF, and the later line wins for it.</p>
</details>
<h2 id="Exercise-4-—-Predict-coreautocrlf"><a href="#Exercise-4-—-Predict-coreautocrlf" class="headerlink" title="Exercise 4 — Predict core.autocrlf"></a>Exercise 4 — Predict <code>core.autocrlf</code></h2>
<p>A file is stored in the repository with LF. What line endings does the working tree get on Windows with <code>core.autocrlf</code> set to <code>true</code>, <code>input</code> and <code>false</code> (no <code>.gitattributes</code>)?</p>
<details>
<summary>Solution</summary>
<p><code>true</code>: CRLF (converted on checkout). <code>input</code>: LF (no conversion on checkout). <code>false</code>: LF (no conversion at all). Only <code>true</code> changes the working tree; <code>true</code> and <code>input</code> both convert CRLF to LF on commit.</p>
</details>
<h2 id="Exercise-5-—-LF-from-Python-on-Windows"><a href="#Exercise-5-—-LF-from-Python-on-Windows" class="headerlink" title="Exercise 5 — LF from Python on Windows"></a>Exercise 5 — LF from Python on Windows</h2>
<p>This code writes CRLF on Windows. Fix it so the file always has LF.</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">with</span> <span class="hljs-built_in">open</span>(<span class="hljs-string">&quot;out.txt&quot;</span>, <span class="hljs-string">&quot;w&quot;</span>, encoding=<span class="hljs-string">&quot;utf-8&quot;</span>) <span class="hljs-keyword">as</span> f:</span><br><span class="line">    f.write(<span class="hljs-string">&quot;line 1\nline 2\n&quot;</span>)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<details>
<summary>Solution</summary>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">with</span> <span class="hljs-built_in">open</span>(<span class="hljs-string">&quot;out.txt&quot;</span>, <span class="hljs-string">&quot;w&quot;</span>, encoding=<span class="hljs-string">&quot;utf-8&quot;</span>, newline=<span class="hljs-string">&quot;\n&quot;</span>) <span class="hljs-keyword">as</span> f:</span><br><span class="line">    f.write(<span class="hljs-string">&quot;line 1\nline 2\n&quot;</span>)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>With <code>newline=None</code> (the default), Python translates each <code>\n</code> to <code>os.linesep</code>, which is <code>\r\n</code> on Windows. <code>newline=&quot;\n&quot;</code> (or <code>newline=&quot;&quot;</code>) turns the translation off.</p>
</details>
<h2 id="Exercise-6-—-Read-ls-files-eol"><a href="#Exercise-6-—-Read-ls-files-eol" class="headerlink" title="Exercise 6 — Read ls-files --eol"></a>Exercise 6 — Read <code>ls-files --eol</code></h2>
<p>What does <code>i/crlf  w/crlf  attr/text=auto eol=lf  src/app.js</code> tell you, and what should you do?</p>
<details>
<summary>Solution</summary>
<p>The rules say LF (<code>attr/text=auto eol=lf</code>), but the file was committed with CRLF (<code>i/crlf</code>) before the rules existed, and the working copy is CRLF too. Run <code>git add --renormalize .</code> and commit. After a fresh checkout, the file shows <code>i/lf w/lf</code>.</p>
</details>
