<h2 id="Chapter-4-—-Production-checklist"><a href="#Chapter-4-—-Production-checklist" class="headerlink" title="Chapter 4 — Production checklist"></a>Chapter 4 — Production checklist</h2>
<ul>
<li><strong>Storage</strong>: SSD class, ReadWriteOnce, ≥ 3× working-set size.</li>
<li><strong>Node affinity</strong>: spread pods across nodes / zones (<code>podAntiAffinity</code>).</li>
<li><strong>Resource requests + limits</strong>: match instance sizing.</li>
<li><strong>PVC backup</strong>: Velero or CSI snapshots into S3.</li>
<li><strong>Monitoring</strong>: deploy <code>mongodb-prometheus-exporter</code> sidecar; scrape into Prometheus → Grafana.</li>
<li><strong>TLS</strong>: Operator creates cert-manager-backed certs; clients use them.</li>
<li><strong>Network policies</strong>: only app namespace reaches mongod ports.</li>
<li><strong>Backups</strong>: Percona Backup for MongoDB (PBM) sidecar, schedule + offsite S3.</li>
<li><strong>Updates</strong>: roll one member at a time via Operator-managed updates.</li>
</ul>
<h2 id="Chapter-5-—-When-NOT-to-run-Mongo-on-K8s"><a href="#Chapter-5-—-When-NOT-to-run-Mongo-on-K8s" class="headerlink" title="Chapter 5 — When NOT to run Mongo on K8s"></a>Chapter 5 — When NOT to run Mongo on K8s</h2>
<ul>
<li><strong>Atlas is available</strong> and you don't have a sovereignty / on-prem requirement → use Atlas. Saves enormous ops time.</li>
<li><strong>Team has no K8s expertise</strong> → managed first, K8s later.</li>
<li><strong>Small workloads</strong> (&lt; 100 GB, &lt; 1k QPS) → cheaper + simpler on plain VMs or managed.</li>
</ul>
<p>K8s pays off when: you already run K8s for everything else; you have multiple stateful workloads to operate; on-prem or sovereign cloud is required; you need infra-as-code for the DB itself.</p>

<h1 id="Part-2-—-mongosync"><a href="#Part-2-—-mongosync" class="headerlink" title="Part 2 — mongosync"></a>Part 2 — mongosync</h1>
<h2 id="Chapter-6-—-What-mongosync-does"><a href="#Chapter-6-—-What-mongosync-does" class="headerlink" title="Chapter 6 — What mongosync does"></a>Chapter 6 — What mongosync does</h2>
<p>Mongosync replicates data continuously from a source cluster to a destination cluster, with <strong>minimal downtime cut-over</strong>. Works between any combination of self-hosted + Atlas + clouds + regions.</p>
<p>Use cases:</p>
<ul>
<li>One-time migrations (on-prem → Atlas, AWS → GCP, cluster tier change).</li>
<li>Multi-region passive-standby — destination always current; failover updates DNS.</li>
<li>Pre-production environments — sync prod data nightly into staging (with PII scrubbing post-sync).</li>
<li>Reverse-sync for rollback.</li>
</ul>
<h2 id="Chapter-7-—-Mongosync-basics"><a href="#Chapter-7-—-Mongosync-basics" class="headerlink" title="Chapter 7 — Mongosync basics"></a>Chapter 7 — Mongosync basics</h2>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">mongosync \</span><br><span class="line">  --cluster0 <span class="hljs-string">&quot;mongodb+srv://srcuser:pw@src-cluster/&quot;</span> \</span><br><span class="line">  --cluster1 <span class="hljs-string">&quot;mongodb+srv://dstuser:pw@dst-cluster/&quot;</span> \</span><br><span class="line">  --logPath /var/log/mongosync/</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Then orchestrate via the REST API on <code>localhost:27182</code>:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># start initial sync</span></span><br><span class="line">curl -X POST localhost:27182/api/v1/start \</span><br><span class="line">  -d <span class="hljs-string">&#x27;{&quot;source&quot;: &quot;cluster0&quot;, &quot;destination&quot;: &quot;cluster1&quot;}&#x27;</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># track progress</span></span><br><span class="line">curl localhost:27182/api/v1/progress</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># commit (cut over)</span></span><br><span class="line">curl -X POST localhost:27182/api/v1/commit</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Phases:</p>
<ol>
<li><strong>Initial sync</strong> — bulk copy of every doc.</li>
<li><strong>Steady state</strong> — continuous oplog tailing.</li>
<li><strong>Commit</strong> — drain remaining oplog, freeze writes briefly, declare destination authoritative.</li>
</ol>
<p>Downtime for cut-over: seconds in normal cases.</p>
<p><img src="/blog/assets/mongo/diagram_29_mongosync.svg" alt="mongosync copies one cluster into another in three phases, then the app's writes move after a brief freeze"></p>
<h2 id="Chapter-8-—-Multi-region-active-passive"><a href="#Chapter-8-—-Multi-region-active-passive" class="headerlink" title="Chapter 8 — Multi-region active-passive"></a>Chapter 8 — Multi-region active-passive</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="text"><span class="line">Region A (primary writes)           Region B (passive standby)</span><br><span class="line">       │                                       ▲</span><br><span class="line">       │ writes                                │</span><br><span class="line">       ▼                                       │</span><br><span class="line">   Cluster A  ───── mongosync ──────────►  Cluster B</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>On region A outage:</p>
<ol>
<li>Stop the mongosync direction (or accept its catch-up lag).</li>
<li>Flip your app's connection string / DNS to cluster B.</li>
<li>Optionally start reverse mongosync (B → A) for when A recovers.</li>
</ol>
<p>Active-active (writes in both regions) is <strong>not natively supported</strong> — last-writer-wins conflict resolution would be needed; Mongo doesn't have it. For active-active you typically shard by region (each region writes only to its own shard); mongosync isn't the right tool.</p>
<h2 id="Chapter-9-—-Sharded-cluster-sync"><a href="#Chapter-9-—-Sharded-cluster-sync" class="headerlink" title="Chapter 9 — Sharded cluster sync"></a>Chapter 9 — Sharded cluster sync</h2>
<p>For sharded source + destination: run <strong>one mongosync per source shard</strong> to parallelise.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">mongosync --cluster0 <span class="hljs-string">&quot;mongodb://shard1/&quot;</span> --cluster1 <span class="hljs-string">&quot;mongodb://destShard1/&quot;</span> ...</span><br><span class="line">mongosync --cluster0 <span class="hljs-string">&quot;mongodb://shard2/&quot;</span> --cluster1 <span class="hljs-string">&quot;mongodb://destShard2/&quot;</span> ...</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Coordinated commit ensures consistency on cut-over.</p>

<h1 id="Part-3-—-Cost-optimisation"><a href="#Part-3-—-Cost-optimisation" class="headerlink" title="Part 3 — Cost optimisation"></a>Part 3 — Cost optimisation</h1>
<h2 id="Chapter-11-—-Atlas-tier-sizing"><a href="#Chapter-11-—-Atlas-tier-sizing" class="headerlink" title="Chapter 11 — Atlas tier sizing"></a>Chapter 11 — Atlas tier sizing</h2>
<p>Atlas pricing scales with tier (M0 free → M700+ enterprise). Cost levers:</p>
<ul>
<li><strong>Right-size the cluster</strong> by working set, not by RAM × N.</li>
<li><strong>Reduce non-essential indexes</strong> (write amplification + RAM bloat).</li>
<li><strong>Online Archive</strong> old data (Post 16) — 10× cheaper than hot tier.</li>
<li><strong>Search nodes</strong> sized separately; right-size for index size + traffic.</li>
<li><strong>Backup retention</strong> — long retention = more cost. Right-size to compliance need.</li>
<li><strong>Data transfer</strong> — cross-region replication / clients in different regions = egress fees. Co-locate.</li>
</ul>
<h2 id="Chapter-12-—-Index-pruning"><a href="#Chapter-12-—-Index-pruning" class="headerlink" title="Chapter 12 — Index pruning"></a>Chapter 12 — Index pruning</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">collection</span>.<span class="hljs-title function_">aggregate</span>([{ <span class="hljs-attr">$indexStats</span>: {} }])</span><br><span class="line"><span class="hljs-comment">// drop indexes with `ops: 0` over weeks</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Hidden index pattern (Post 03) lets you test removal safely. Quarterly index review on every production collection. Easy 10-30 % storage + RAM win.</p>
<h2 id="Chapter-13-—-Query-cost"><a href="#Chapter-13-—-Query-cost" class="headerlink" title="Chapter 13 — Query cost"></a>Chapter 13 — Query cost</h2>
<p>Each slow query = wasted CPU + IOPS. The profiler + Atlas Performance Advisor (Post 04) surface them. Fix top-N slowest queries every sprint.</p>
<p>A query halved is two queries worth of capacity reclaimed. Index investments scale your fleet without scaling your tier.</p>
<h2 id="Chapter-14-—-Storage-compression"><a href="#Chapter-14-—-Storage-compression" class="headerlink" title="Chapter 14 — Storage compression"></a>Chapter 14 — Storage compression</h2>
<ul>
<li>WiredTiger default is snappy. Switching new collections to <strong>zstd</strong> (Post 15) compresses ~25 % better at similar CPU.</li>
<li>Old collections can be re-collected (offline) to apply new compression.</li>
</ul>
<h2 id="Chapter-15-—-Connection-cost"><a href="#Chapter-15-—-Connection-cost" class="headerlink" title="Chapter 15 — Connection cost"></a>Chapter 15 — Connection cost</h2>
<p>Each pool connection costs server-side resources. Right-size client pools by Little's Law (Post 08). Big over-pools waste Atlas tier capacity.</p>
<h2 id="Chapter-16-—-Hot-vs-cold-tiers"><a href="#Chapter-16-—-Hot-vs-cold-tiers" class="headerlink" title="Chapter 16 — Hot vs cold tiers"></a>Chapter 16 — Hot vs cold tiers</h2>
<p>For data that's queried rarely:</p>
<ul>
<li>Atlas Online Archive → cheap S3-like storage; federated query.</li>
<li>Manual archive to S3 (Parquet, compressed) → cheapest, custom-query path.</li>
<li>For analytics, push old data to ClickHouse (Post 28).</li>
</ul>
<p>The two ratios that matter: hot/cold size + hot/cold cost. If 80 % of data is rarely queried, tier it; you'll cut cluster cost in half.</p>

<h2 id="Chapter-18-—-Self-hosted-cost-considerations"><a href="#Chapter-18-—-Self-hosted-cost-considerations" class="headerlink" title="Chapter 18 — Self-hosted cost considerations"></a>Chapter 18 — Self-hosted cost considerations</h2>
<p>Cost = hardware (or cloud VMs) + storage + network + people-ops.</p>
<p>Compared to Atlas:</p>
<ul>
<li>Self-hosted hardware is often cheaper per GB-RAM at large scale.</li>
<li>But operating cost (people, on-call, backup infra, monitoring) often exceeds the Atlas premium.</li>
<li>Most teams break even around ~50 nodes / multi-TB; below that, Atlas wins on TCO.</li>
</ul>
<p>The right answer depends on your ops headcount + cloud commit + sovereignty needs.</p>

<h2 id="Chapter-20-—-Atlas-HIPAA"><a href="#Chapter-20-—-Atlas-HIPAA" class="headerlink" title="Chapter 20 — Atlas + HIPAA"></a>Chapter 20 — Atlas + HIPAA</h2>

<li>Customer-managed KMS keys for encryption at rest.</li>
<li>Audit log enabled + shipped offsite.</li>
<li>TLS in transit (default).</li>
<li>VPC private endpoint; no public access.</li>
<li>MFA + SSO + RBAC for all users.</li>

<p>Document everything for the audit.</p>
<h2 id="Chapter-21-—-PCI-DSS"><a href="#Chapter-21-—-PCI-DSS" class="headerlink" title="Chapter 21 — PCI-DSS"></a>Chapter 21 — PCI-DSS</h2>
<p>For storing PAN (primary account number):</p>
<ul>
<li><strong>CSFLE</strong> or <strong>Queryable Encryption</strong> (Post 13) so PAN is unreadable to ops staff.</li>
<li>KMS-managed keys with rotation policy + access logs.</li>
<li>Network isolation; no internet egress from the DB host.</li>
<li>Audit log capturing every PAN access + every privileged op.</li>
<li>Quarterly external scanning; annual penetration test.</li>
<li>Vendor PCI attestation (Atlas has SAQ-D Service Provider).</li>
</ul>
<p>Better: don't store PAN at all. Use a tokenisation service (Stripe / Adyen / Spreedly); store tokens.</p>
<h2 id="Chapter-22-—-GDPR-—-right-to-be-forgotten"><a href="#Chapter-22-—-GDPR-—-right-to-be-forgotten" class="headerlink" title="Chapter 22 — GDPR — right to be forgotten"></a>Chapter 22 — GDPR — right to be forgotten</h2>
<p>Article 17 — data subjects can request deletion.</p>
<p>Patterns:</p>
<ul>
<li><strong>Hard delete</strong> via secondary key (email / customer_id). Find every collection referencing the subject; delete or anonymise. Mongo's lack of FK makes this app-side; document each collection's owner.</li>
<li><strong>Soft delete via anonymisation</strong> — replace PII with placeholders; keep aggregate analytics integrity.</li>
<li><strong>Backup considerations</strong> — backups also contain the subject's data. Most regulators accept &quot;purged on backup rotation&quot;; document the retention.</li>
<li><strong>Audit</strong> — log every deletion request + resolution.</li>
<li><strong>Data residency</strong> — Atlas regions match EU AWS / Azure / GCP regions to keep data in-EU.</li>
</ul>
<h2 id="Chapter-23-—-SOC-2-controls-—-common-requirements"><a href="#Chapter-23-—-SOC-2-controls-—-common-requirements" class="headerlink" title="Chapter 23 — SOC 2 controls — common requirements"></a>Chapter 23 — SOC 2 controls — common requirements</h2>
<ul>
<li>Documented security policies (you write; auditor reviews).</li>
<li>Access reviews — quarterly audit of who has what role.</li>
<li>Change management — every prod change reviewed + approved.</li>
<li>Vendor management — Atlas + every downstream vendor reviewed.</li>
<li>Incident response plan — written + practised.</li>
<li>Monitoring + alerts — proven via logs.</li>
<li>Backup + restore — tested (Post 14).</li>
</ul>
<p>The audit checks evidence over a 6 or 12 month observation period. Tooling (Vanta, Drata, Secureframe) automates most of the evidence collection.</p>
<h2 id="Chapter-24-—-Audit-logging-discipline"><a href="#Chapter-24-—-Audit-logging-discipline" class="headerlink" title="Chapter 24 — Audit logging discipline"></a>Chapter 24 — Audit logging discipline</h2>
<p>Every privileged operation + every data access on sensitive collections should be auditable:</p>
<ul>
<li>Atlas audit log → SIEM (Splunk, Datadog, ELK).</li>
<li>Self-hosted: Enterprise audit log feature, with filters for noise reduction.</li>
<li>App-level audit: every PII-touching endpoint logs <code>(user, action, target_id, at)</code> into an <code>audit_log</code> collection with TTL of regulator-required years.</li>
</ul>

<td>retention by regulator (often 7 years for HIPAA)</td>
</tr>
<tr>
<td>Backups not encrypted</td>
<td>self-hosted pipeline missed</td>
<td>encrypt every backup at rest</td>
</tr>
<tr>
<td>MFA only on humans, not service accounts</td>
<td>service accounts hijacked</td>
<td>use IAM auth where possible; rotate other secrets</td>
</tr>
<tr>
<td>Deletion request not honoured</td>
<td>backups still hold the data</td>
<td>document backup-rotation purge; honour as best-effort</td>
</tr>
<tr>
<td>Privileged role too broad</td>
<td>default <code>dbOwner</code> instead of custom</td>
<td>least-privilege custom roles</td>
</tr>
</tbody>
</table>

<h1 id="Course-complete"><a href="#Course-complete" class="headerlink" title="Course complete"></a>Course complete</h1>
<p>You've covered MongoDB from the document model through CRUD, indexes, aggregation, schema design, pool + concurrency, transactions, replication, sharding, change streams, security, backup, performance, Atlas (Search + Vector + Triggers + Stream Processing), drivers, modelling case studies, Mongoose, Beanie, the outbox pattern, CQRS + Event Sourcing, production RAG, SQL→Mongo migration, Kafka + Debezium CDC, testing, OpenTelemetry, geospatial, time-series at extreme scale, Kubernetes, mongosync, cost, and compliance.</p>
<p>That's the working knowledge of a senior MongoDB engineer + the architectural awareness of a platform engineer. Where you go from here:</p>
<ul>
<li>Read MongoDB Inc. release notes per major version — the engine evolves fast.</li>
<li>Build something real that exercises 5+ of these areas end-to-end.</li>
<li>Contribute to OSS — drivers, operators, ODMs all welcome patches.</li>
<li>Pair with a database that complements Mongo for your edge cases (ClickHouse for analytics, Redis for hot cache).</li>
</ul>
<p>The series will get future extensions (single-post deep dives on subtopics, case studies from real production migrations, performance benchmarks). The base + advanced you have today is enough to ship serious systems.</p>
