<h2 id="ASCII-Latin-1-and-Windows-1252"><a href="#ASCII-Latin-1-and-Windows-1252" class="headerlink" title="ASCII, Latin-1 and Windows-1252"></a>ASCII, Latin-1 and Windows-1252</h2>
<p><strong>ASCII</strong> defines 128 characters, codes <code>0x00</code>–<code>0x7F</code>: English letters, digits, punctuation and control codes such as <code>0x0A</code> (line feed). It uses only 7 bits, so the top bit of every ASCII byte is <code>0</code>. One byte can hold 256 values, so many &quot;8-bit&quot; encodings added 128 more characters on top of ASCII:</p>
<ul>
<li><strong>ISO-8859-1 (Latin-1)</strong> maps bytes <code>0x00</code>–<code>0xFF</code> straight to <code>U+0000</code>–<code>U+00FF</code>.</li>
<li><strong>Windows-1252</strong> is the same for most bytes, but fills <code>0x80</code>–<code>0x9F</code> with printable characters. For example, <code>0x80</code> is <code>€</code>.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> browsers treat the labels <code>iso-8859-1</code>, <code>latin1</code> and even <code>ascii</code> as <strong>windows-1252</strong>. The WHATWG Encoding Standard maps them that way on purpose, because real web pages labelled &quot;Latin-1&quot; were usually Windows-1252.</p>
</blockquote>
<h2 id="CP950-Big5-—-a-double-byte-encoding"><a href="#CP950-Big5-—-a-double-byte-encoding" class="headerlink" title="CP950 (Big5) — a double-byte encoding"></a>CP950 (Big5) — a double-byte encoding</h2>
<p>Chinese needs thousands of characters, so one byte is not enough. <strong>Big5</strong> uses one byte for ASCII and two bytes for each Chinese character. Microsoft's version is <strong>code page 950</strong> (CP950). Microsoft lists it as &quot;ANSI/OEM Traditional Chinese (Taiwan; Hong Kong SAR, PRC); Chinese Traditional (Big5)&quot;.</p>
<ul>
<li>A <strong>lead byte</strong> (<code>0x81</code>–<code>0xFE</code>) starts a two-byte character.</li>
<li>A <strong>trail byte</strong> (<code>0x40</code>–<code>0x7E</code> or <code>0xA1</code>–<code>0xFE</code>) finishes it.</li>
<li>A byte below <code>0x80</code> on its own is plain ASCII.</li>
</ul>
<p>For example, <code>&quot;中&quot;.encode(&quot;cp950&quot;)</code> gives <code>b'\xa4\xa4'</code> (2 bytes), while <code>&quot;中&quot;.encode(&quot;utf-8&quot;)</code> gives <code>b'\xe4\xb8\xad'</code> (3 bytes).</p>
<h2 id="The-Windows-ANSI-code-page"><a href="#The-Windows-ANSI-code-page" class="headerlink" title="The Windows &quot;ANSI code page&quot;"></a>The Windows &quot;ANSI code page&quot;</h2>
<p>Windows keeps a system-wide legacy code page. Microsoft calls it the &quot;ANSI code page&quot; (the name is historical). It depends on the system locale: 1252 on a US or Western European setup, 950 for Traditional Chinese, 936 for Simplified Chinese, 932 for Japanese. Programs that do not ask for a specific encoding often fall back to it. Check it on your own machine:</p>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="powershell"><span class="line"><span class="hljs-comment"># Windows PowerShell 5.1</span></span><br><span class="line">[<span class="hljs-type">System.Text.Encoding</span>]::Default.CodePage     <span class="hljs-comment"># e.g. 950</span></span><br><span class="line">(<span class="hljs-built_in">Get-Culture</span>).Name                           <span class="hljs-comment"># e.g. zh-HK</span></span><br><span class="line">python <span class="hljs-literal">-c</span> <span class="hljs-string">&quot;import locale; print(locale.getpreferredencoding(False))&quot;</span>   <span class="hljs-comment"># e.g. cp950</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> in PowerShell 7 (built on modern .NET), <code>[System.Text.Encoding]::Default</code> is always UTF-8. Only Windows PowerShell 5.1 reports the ANSI code page there. Microsoft's own docs warn: &quot;ANSI code pages can be different on different computers, or can be changed for a single computer, leading to data corruption.&quot;</p>
</blockquote>

<h1 id="Chapter-3-—-Unicode-and-UTF-8"><a href="#Chapter-3-—-Unicode-and-UTF-8" class="headerlink" title="Chapter 3 — Unicode and UTF-8"></a>Chapter 3 — Unicode and UTF-8</h1>
<p>Unicode gives one code point to every character in every script, plus symbols and emoji. The code space runs from <code>U+0000</code> to <code>U+10FFFF</code>, a 21-bit range. Unicode itself is only the numbering. UTF-8, UTF-16 and UTF-32 are the encodings that turn those numbers into bytes.</p>

<h2 id="Encode-中-by-hand"><a href="#Encode-中-by-hand" class="headerlink" title="Encode 中 by hand"></a>Encode <code>中</code> by hand</h2>
<p><img src="/blog/assets/dev/diagram_01_utf8_bits.svg" alt="The four UTF-8 bit patterns and how the bits of U+4E2D fill three bytes to give E4 B8 AD"></p>
<ol>
<li><code>U+4E2D</code> in binary is <code>0100 1110 0010 1101</code> (16 bits).</li>
<li>It is between <code>U+0800</code> and <code>U+FFFF</code>, so it needs 3 bytes: <code>1110xxxx 10xxxxxx 10xxxxxx</code>.</li>
<li>Split the 16 bits as 4 + 6 + 6: <code>0100</code> · <code>111000</code> · <code>101101</code>.</li>
<li>Fill the slots: <code>11100100</code> <code>10111000</code> <code>10101101</code> = <code>E4 B8 AD</code>. Check with <code>&quot; &quot;.join(f&quot;{b:08b}&quot; for b in &quot;中&quot;.encode(&quot;utf-8&quot;))</code>.</li>
</ol>
<h2 id="Why-UTF-8-won"><a href="#Why-UTF-8-won" class="headerlink" title="Why UTF-8 won"></a>Why UTF-8 won</h2>
<ul>
<li><strong>ASCII-compatible.</strong> Every ASCII file is already valid UTF-8, byte for byte. RFC 3629 also guarantees that ASCII byte values never appear inside a multi-byte character. So a <code>/</code> or <code>&quot;</code> byte always means <code>/</code> or <code>&quot;</code>, and old tools that split on ASCII still work.</li>
<li><strong>Self-synchronising.</strong> Continuation bytes always start with <code>10</code>. From any position you can step back to the start of a character.</li>
<li><strong>No byte-order problem.</strong> UTF-8 works in single bytes, so there is no big-endian vs little-endian question.</li>
<li><strong>Required for new formats.</strong> The WHATWG Encoding Standard says new protocols and formats &quot;must use the UTF-8 encoding exclusively&quot;.</li>
</ul>
<hr>
<h1 id="Chapter-4-—-UTF-16-surrogate-pairs-and-length"><a href="#Chapter-4-—-UTF-16-surrogate-pairs-and-length" class="headerlink" title="Chapter 4 — UTF-16, surrogate pairs and &quot;length&quot;"></a>Chapter 4 — UTF-16, surrogate pairs and &quot;length&quot;</h1>
<p>UTF-16 uses 16-bit code units. Code points up to <code>U+FFFF</code> (the Basic Multilingual Plane) take one unit. Anything above takes <strong>two</strong> units, called a <strong>surrogate pair</strong>:</p>
<ol>
<li>Subtract <code>0x10000</code> from the code point. You get a 20-bit number.</li>
<li>The top 10 bits plus <code>0xD800</code> give the <strong>high surrogate</strong> (<code>D800</code>–<code>DBFF</code>).</li>
<li>The low 10 bits plus <code>0xDC00</code> give the <strong>low surrogate</strong> (<code>DC00</code>–<code>DFFF</code>).</li>
</ol>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="python"><span class="line">v = <span class="hljs-number">0x1F600</span> - <span class="hljs-number">0x10000</span>                               <span class="hljs-comment"># 😀 is U+1F600</span></span><br><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-built_in">hex</span>(<span class="hljs-number">0xD800</span> + (v &gt;&gt; <span class="hljs-number">10</span>)), <span class="hljs-built_in">hex</span>(<span class="hljs-number">0xDC00</span> + (v &amp; <span class="hljs-number">0x3FF</span>)))  <span class="hljs-comment"># 0xd83d 0xde00</span></span><br><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-string">&quot;😀&quot;</span>.encode(<span class="hljs-string">&quot;utf-16-be&quot;</span>).<span class="hljs-built_in">hex</span>(<span class="hljs-string">&quot; &quot;</span>))             <span class="hljs-comment"># d8 3d de 00</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>JavaScript, Java, C# and the Windows API store strings as UTF-16. Their &quot;length&quot; counts code units, not characters:</p>
<pre><code class="language-javascript"><figure class="highlight javascript"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="javascript"><span class="line"><span class="hljs-string">&quot;😀&quot;</span>.<span class="hljs-property">length</span>;          <span class="hljs-comment">// 2  (two UTF-16 code units)</span></span><br><span class="line">[...<span class="hljs-string">&quot;😀&quot;</span>].<span class="hljs-property">length</span>;     <span class="hljs-comment">// 1  (the string iterator walks code points)</span></span><br><span class="line"><span class="hljs-string">&quot;😀&quot;</span>.<span class="hljs-title function_">slice</span>(<span class="hljs-number">0</span>, <span class="hljs-number">1</span>);     <span class="hljs-comment">// a lone high surrogate: broken text</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Python's <code>len(&quot;😀&quot;)</code> is 1, because a Python <code>str</code> counts code points. The UTF-8 form is 4 bytes. One emoji, three different &quot;lengths&quot;.</p>
<blockquote>
<p><strong>Common pitfall:</strong> cutting a JavaScript string with <code>.slice()</code> or <code>.substring()</code> to fit a length limit can split a surrogate pair. The result holds half an emoji and may show as <code>�</code>.</p>
</blockquote>

<h2 id="Grapheme-clusters"><a href="#Grapheme-clusters" class="headerlink" title="Grapheme clusters"></a>Grapheme clusters</h2>
<p>A <strong>grapheme cluster</strong> is what a person calls &quot;one character&quot;. Unicode Standard Annex #29 defines the rules. Many visible characters are several code points:</p>
<pre><code class="language-javascript"><figure class="highlight javascript"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="javascript"><span class="line"><span class="hljs-keyword">const</span> family = <span class="hljs-string">&quot;👨‍👩‍👧&quot;</span>;   <span class="hljs-comment">// man + ZWJ + woman + ZWJ + girl</span></span><br><span class="line">family.<span class="hljs-property">length</span>;                                    <span class="hljs-comment">// 8 UTF-16 units</span></span><br><span class="line">[...family].<span class="hljs-property">length</span>;                               <span class="hljs-comment">// 5 code points</span></span><br><span class="line"><span class="hljs-keyword">const</span> seg = <span class="hljs-keyword">new</span> <span class="hljs-title class_">Intl</span>.<span class="hljs-title class_">Segmenter</span>(<span class="hljs-string">&quot;en&quot;</span>, { <span class="hljs-attr">granularity</span>: <span class="hljs-string">&quot;grapheme&quot;</span> });</span><br><span class="line">[...seg.<span class="hljs-title function_">segment</span>(family)].<span class="hljs-property">length</span>;                  <span class="hljs-comment">// 1 grapheme</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<blockquote>
<p><strong>Watch out:</strong> a &quot;max 20 characters&quot; rule needs a definition. Bytes (database column size), code points, UTF-16 units (JavaScript <code>.length</code>), and graphemes (what the user sees) give four different answers.</p>
</blockquote>

<h1 id="Chapter-6-—-The-BOM-byte-order-mark"><a href="#Chapter-6-—-The-BOM-byte-order-mark" class="headerlink" title="Chapter 6 — The BOM (byte order mark)"></a>Chapter 6 — The BOM (byte order mark)</h1>
<p>The character <code>U+FEFF</code> at the very start of a file is a <strong>byte order mark</strong>. In UTF-16 it tells the reader the byte order. In UTF-8 it is only a signature.</p>
<table>
<thead>
<tr>
<th>Encoding</th>
<th>BOM bytes</th>
</tr>
</thead>
<tbody>
<tr>
<td>UTF-8</td>
<td><code>EF BB BF</code></td>
</tr>
<tr>
<td>UTF-16 big-endian</td>
<td><code>FE FF</code></td>
</tr>
<tr>
<td>UTF-16 little-endian</td>
<td><code>FF FE</code></td>
</tr>
</tbody>
</table>
<p>The Unicode FAQ warns that where UTF-8 is used in 8-bit environments, &quot;the use of a BOM will interfere with any protocol or file format that expects specific ASCII characters at the beginning&quot;. Real cases:</p>
<ul>
<li>A shell script must start with the bytes <code>#!</code>. With a BOM in front, the system does not see a shebang.</li>
<li>A CSV read without BOM handling gets a first column name that starts with an invisible <code>U+FEFF</code>, so <code>row[&quot;id&quot;]</code> fails.</li>
<li>RFC 8259 says a JSON text sent over a network must not start with a BOM.</li>
<li>Windows PowerShell 5.1 is the opposite case. Microsoft's docs say scripts with non-ASCII characters should be saved as UTF-8 <strong>with</strong> BOM, or 5.1 reads them in the ANSI code page.</li>
</ul>

</blockquote>

<h1 id="Chapter-7-—-Python-bytes-vs-str-and-always-pass-encoding"><a href="#Chapter-7-—-Python-bytes-vs-str-and-always-pass-encoding" class="headerlink" title="Chapter 7 — Python: bytes vs str, and always pass encoding="></a>Chapter 7 — Python: <code>bytes</code> vs <code>str</code>, and always pass <code>encoding=</code></h1>
<p>Python 3 keeps the two worlds apart. <code>str</code> is a sequence of code points. <code>bytes</code> is a sequence of numbers 0–255. You cross between them only with <code>.encode()</code> and <code>.decode()</code>.</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">from</span> pathlib <span class="hljs-keyword">import</span> Path</span><br><span class="line"> </span><br><span class="line">p = Path(<span class="hljs-string">&quot;note.txt&quot;</span>)</span><br><span class="line">p.write_text(<span class="hljs-string">&quot;Dev Essentials — 01 · Text Encoding\n&quot;</span>, encoding=<span class="hljs-string">&quot;utf-8&quot;</span>)</span><br><span class="line">text = p.read_text(encoding=<span class="hljs-string">&quot;utf-8&quot;</span>)   <span class="hljs-comment"># str</span></span><br><span class="line">raw = p.read_bytes()                   <span class="hljs-comment"># bytes: b&#x27;Dev Essentials \xe2\x80\x94 01 ...&#x27;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>With <code>open()</code>, the same rule applies: <code>open(p, encoding=&quot;utf-8&quot;)</code> in text mode, <code>open(p, &quot;rb&quot;)</code> for raw bytes.</p>
<h2 id="Why-encoding-matters"><a href="#Why-encoding-matters" class="headerlink" title="Why encoding= matters"></a>Why <code>encoding=</code> matters</h2>
<p>Without <code>encoding=</code>, <code>open()</code> uses the locale encoding. On a Windows machine with code page 950 that is <code>cp950</code>. The same script then reads UTF-8 files correctly on Linux and wrongly on that PC.</p>
<ul>
<li><strong>PEP 686</strong> turns on UTF-8 mode by default from <strong>Python 3.15</strong>, so text I/O without <code>encoding=</code> becomes UTF-8 everywhere. PEP 790 schedules 3.15.0 for 2026-10-01. You can opt out with <code>PYTHONUTF8=0</code> or <code>-X utf8=0</code>.</li>
<li>Your code will still meet Python 3.14 and older for years. Keep passing <code>encoding=&quot;utf-8&quot;</code>.</li>
<li>To find calls that forget it, run <code>python -X warn_default_encoding script.py</code> (Python 3.10+). It prints an <code>EncodingWarning</code> for each one.</li>
</ul>

<h1 id="Chapter-9-—-Mojibake-reversible-or-destroyed"><a href="#Chapter-9-—-Mojibake-reversible-or-destroyed" class="headerlink" title="Chapter 9 — Mojibake: reversible or destroyed?"></a>Chapter 9 — Mojibake: reversible or destroyed?</h1>
<p>Mojibake happens in one of two ways. The difference decides whether you can fix the file.</p>
<h2 id="Case-A-—-nothing-was-lost-reversible"><a href="#Case-A-—-nothing-was-lost-reversible" class="headerlink" title="Case A — nothing was lost (reversible)"></a>Case A — nothing was lost (reversible)</h2>
<p>The bytes were decoded with the wrong table, but every byte became <em>some</em> character. Walk the same steps backwards:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="python"><span class="line">good = <span class="hljs-string">&quot;café&quot;</span></span><br><span class="line">bad = good.encode(<span class="hljs-string">&quot;utf-8&quot;</span>).decode(<span class="hljs-string">&quot;cp1252&quot;</span>)</span><br><span class="line"><span class="hljs-built_in">print</span>(bad)                                   <span class="hljs-comment"># cafÃ©</span></span><br><span class="line"><span class="hljs-built_in">print</span>(bad.encode(<span class="hljs-string">&quot;cp1252&quot;</span>).decode(<span class="hljs-string">&quot;utf-8&quot;</span>))  <span class="hljs-comment"># café</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The library <strong>ftfy</strong> (<code>pip install ftfy</code>) automates this for common cases: <code>ftfy.fix_text(&quot;cafÃ©&quot;)</code> gives <code>café</code>. Its docs list the single-byte encodings it detects (Latin-1, Windows-125x, MacRoman, cp437 and others).</p>
<blockquote>
<p><strong>Watch out:</strong> ftfy's docs say it cannot handle the legacy Chinese, Japanese and Korean encodings. For CP950 mojibake, reverse it by hand: <code>s.encode(&quot;cp950&quot;).decode(&quot;utf-8&quot;)</code>.</p>
</blockquote>
<h2 id="Case-B-—-information-destroyed-not-reversible"><a href="#Case-B-—-information-destroyed-not-reversible" class="headerlink" title="Case B — information destroyed (not reversible)"></a>Case B — information destroyed (not reversible)</h2>
<p>If the decoder hit bytes it could not read and put in <code>?</code> or <code>U+FFFD</code>, the original bytes are gone. Many different inputs map to the same <code>?</code>, so no function can go back. The only fix is an older copy: a backup or version control.</p>
<h2 id="Why-detection-can-only-guess"><a href="#Why-detection-can-only-guess" class="headerlink" title="Why detection can only guess"></a>Why detection can only guess</h2>
<p>Tools such as <strong>charset-normalizer</strong> take unknown bytes and try many encodings. They throw away tables that cannot decode the bytes, then score the rest for &quot;mess&quot; and for how natural the letters look. That works well on long text. It cannot be certain, because the same bytes are often valid in more than one encoding:</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-keyword">import</span> unicodedata</span><br><span class="line">data = <span class="hljs-string">b&quot;\xc2\xb7&quot;</span></span><br><span class="line"><span class="hljs-keyword">for</span> enc <span class="hljs-keyword">in</span> (<span class="hljs-string">&quot;utf-8&quot;</span>, <span class="hljs-string">&quot;cp950&quot;</span>):</span><br><span class="line">    ch = data.decode(enc)</span><br><span class="line">    <span class="hljs-built_in">print</span>(enc, <span class="hljs-string">f&quot;U+<span class="hljs-subst">{<span class="hljs-built_in">ord</span>(ch):04X}</span>&quot;</span>, unicodedata.name(ch))</span><br><span class="line"><span class="hljs-comment"># utf-8 U+00B7 MIDDLE DOT</span></span><br><span class="line"><span class="hljs-comment"># cp950 U+7E5A CJK UNIFIED IDEOGRAPH-7E5A</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Both answers are &quot;valid&quot;. Only the writer knows which one was meant. The safe design is to <strong>not need detection</strong>: agree on UTF-8 and state it (the HTTP <code>charset</code>, <code>&lt;meta charset=&quot;utf-8&quot;&gt;</code>, <code>encoding=</code> in code).</p>

<h1 id="Chapter-10-—-Case-study-a-bulk-edit-that-damaged-44-posts"><a href="#Chapter-10-—-Case-study-a-bulk-edit-that-damaged-44-posts" class="headerlink" title="Chapter 10 — Case study: a bulk edit that damaged 44 posts"></a>Chapter 10 — Case study: a bulk edit that damaged 44 posts</h1>
<p>This blog stores posts as UTF-8 Markdown without a BOM. The post titles use <code>—</code> (em dash) and <code>·</code> (middle dot) as separators.</p>
<h2 id="What-happened"><a href="#What-happened" class="headerlink" title="What happened"></a>What happened</h2>
<p>A script updated the frontmatter of many posts at once, to add cover images. It rewrote <strong>44 posts</strong> and corrupted about <strong>2,700 characters</strong>. It ran in <strong>Windows PowerShell 5.1</strong> on a Windows machine with system ANSI code page <strong>950</strong> (Big5) and culture <code>zh-HK</code>.</p>
<p>Microsoft's docs for 5.1 explain the trap. When a file has no BOM, <code>Get-Content</code> &quot;uses the <code>Default</code> ANSI encoding&quot;. <code>Set-Content</code> also writes <code>Default</code> (ANSI) unless told otherwise. So on this machine, BOM-less UTF-8 is read as CP950.</p>

<p><strong>The repair.</strong> The dashes could not be recovered from the damaged files. So each file was <strong>restored from the parent Git commit</strong>, and the one intended frontmatter line was applied again. Version control turned an impossible repair into a routine one (see Dev Essentials 03 · Git Rescue Kit).</p>

<ul>
<li><code>UTF8Encoding($false)</code> means &quot;UTF-8, no BOM&quot;. In 5.1, <code>Set-Content -Encoding UTF8</code> writes UTF-8 <strong>with</strong> a BOM, and <code>Out-File</code> and the <code>&gt;</code> / <code>&gt;&gt;</code> operators write <strong>UTF-16LE</strong>. Do not redirect text into project files there.</li>
<li><strong>PowerShell 7+</strong> defaults to <code>utf8NoBOM</code> for all output. Using <code>pwsh</code> for scripts removes most of this risk. So does doing bulk edits in Python with <code>encoding=&quot;utf-8&quot;</code>.</li>
<li>Commit before any bulk edit. Then <code>git diff</code> shows the damage at once, and the old bytes are one command away.</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> .NET methods such as <code>ReadAllText</code> resolve relative paths against the process's working folder, which is not always PowerShell's current location. Pass a full path, as <code>Resolve-Path</code> does above.</p>
</blockquote>
<h2 id="The-system-wide-UTF-8-option"><a href="#The-system-wide-UTF-8-option" class="headerlink" title="The system-wide UTF-8 option"></a>The system-wide UTF-8 option</h2>
<p>Windows has a setting: <strong>Settings → Time &amp; language → Language &amp; region → Administrative language settings → Change system locale → &quot;Beta: Use Unicode UTF-8 for worldwide language support&quot;</strong>. It switches the system code page to 65001 (UTF-8) and needs a restart. Caveats before you turn it on:</p>
<ul>
<li>It is still labelled <strong>Beta</strong>.</li>
<li>It affects every program on the machine, not one project.</li>
<li>Older programs written for a double-byte code page such as 950 may show broken text.</li>
<li>Old files saved in the previous code page (Big5 text files, old CSV exports) will now be read as UTF-8 and look broken. The mismatch moves; it does not disappear.</li>
</ul>
<p>For your own programs, Microsoft offers a narrower switch. The <code>activeCodePage</code> manifest property (Windows 10 version 1903 and later) makes one process use UTF-8. Either way, an explicit encoding in code remains the reliable fix.</p>

<h2 id="Exercise-1-—-Bytes-by-hand"><a href="#Exercise-1-—-Bytes-by-hand" class="headerlink" title="Exercise 1 — Bytes by hand"></a>Exercise 1 — Bytes by hand</h2>
<p>Write the UTF-8 bytes of <code>€</code> (U+20AC) by hand, then check in Python.</p>
<details>
<summary>Solution</summary>
<p><code>U+20AC</code> is in the 3-byte range. Binary: <code>0010 0000 1010 1100</code>. Split 4 + 6 + 6: <code>0010</code> · <code>000010</code> · <code>101100</code>. Fill <code>1110xxxx 10xxxxxx 10xxxxxx</code>: <code>11100010 10000010 10101100</code> = <code>E2 82 AC</code>.</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-string">&quot;€&quot;</span>.encode(<span class="hljs-string">&quot;utf-8&quot;</span>).<span class="hljs-built_in">hex</span>(<span class="hljs-string">&quot; &quot;</span>))   <span class="hljs-comment"># e2 82 ac</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Exercise-2-—-Four-lengths"><a href="#Exercise-2-—-Four-lengths" class="headerlink" title="Exercise 2 — Four lengths"></a>Exercise 2 — Four lengths</h2>
<p>Take the string <code>&quot;e\N{COMBINING ACUTE ACCENT}\U0001F44D\U0001F3FD&quot;</code>: é written with a combining accent, then a thumbs-up with a skin tone. Predict the Python <code>len()</code>, the JavaScript <code>.length</code>, the UTF-8 byte count, and the number of graphemes.</p>
<details>
<summary>Solution</summary>
<p>Code points: <code>e</code>, <code>U+0301</code>, <code>U+1F44D</code>, <code>U+1F3FD</code>, so Python <code>len()</code> = <strong>4</strong>. UTF-16 units: 1 + 1 + 2 + 2 = <strong>6</strong>. UTF-8 bytes: 1 + 2 + 4 + 4 = <strong>11</strong>. Graphemes: <code>é</code> and the toned thumbs-up = <strong>2</strong>.</p>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="python"><span class="line">s = <span class="hljs-string">&quot;e\N{COMBINING ACUTE ACCENT}\U0001F44D\U0001F3FD&quot;</span></span><br><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-built_in">len</span>(s), <span class="hljs-built_in">len</span>(s.encode(<span class="hljs-string">&quot;utf-16-le&quot;</span>)) // <span class="hljs-number">2</span>, <span class="hljs-built_in">len</span>(s.encode(<span class="hljs-string">&quot;utf-8&quot;</span>)))  <span class="hljs-comment"># 4 6 11</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
</details>
<h2 id="Exercise-3-—-Fix-mojibake-of-both-kinds"><a href="#Exercise-3-—-Fix-mojibake-of-both-kinds" class="headerlink" title="Exercise 3 — Fix mojibake of both kinds"></a>Exercise 3 — Fix mojibake of both kinds</h2>
<p>A CSV shows <code>JosÃ© MÃ¼ller</code>. A Markdown line reads <code>Python Course — 03 X Functions</code>, where <code>X</code> is the character U+7E5A. Repair both. Can you repair everything in such files?</p>
<details>
<summary>Solution</summary>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-built_in">print</span>(<span class="hljs-string">&quot;JosÃ© MÃ¼ller&quot;</span>.encode(<span class="hljs-string">&quot;cp1252&quot;</span>).decode(<span class="hljs-string">&quot;utf-8&quot;</span>))   <span class="hljs-comment"># José Müller</span></span><br><span class="line"> </span><br><span class="line">MARK = <span class="hljs-built_in">chr</span>(<span class="hljs-number">0x7E5A</span>)</span><br><span class="line">line = <span class="hljs-string">f&quot;Python Course \N<span class="hljs-subst">{EM DASH}</span> 03 <span class="hljs-subst">{MARK}</span> Functions&quot;</span></span><br><span class="line"><span class="hljs-built_in">print</span>(line.replace(MARK, MARK.encode(<span class="hljs-string">&quot;cp950&quot;</span>).decode(<span class="hljs-string">&quot;utf-8&quot;</span>)))</span><br><span class="line"><span class="hljs-comment"># Python Course — 03 · Functions</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The CSV was UTF-8 decoded as Windows-1252; U+7E5A encodes back to <code>C2 B7</code> in CP950, which is <code>·</code> in UTF-8. Both are Case A. Any <code>—</code> that already became two <code>?</code> is Case B: it cannot be repaired from the file. Restore that file from Git.</p>
</details>
<h2 id="Exercise-4-—-Who-is-right"><a href="#Exercise-4-—-Who-is-right" class="headerlink" title="Exercise 4 — Who is right?"></a>Exercise 4 — Who is right?</h2>
<p>Two teammates open the same 2-byte file. One sees a middle dot, the other sees a Chinese character. Which one is right, and how would you settle it for good?</p>
<details>
<summary>Solution</summary>
<p>Neither can prove it from the bytes alone: <code>C2 B7</code> is valid UTF-8 (<code>·</code>) and valid CP950 (U+7E5A). Settle it by agreement, not detection. Declare UTF-8 for the project (<code>.editorconfig</code> <code>charset = utf-8</code>, <code>encoding=&quot;utf-8&quot;</code> in code, <code>&lt;meta charset=&quot;utf-8&quot;&gt;</code> on pages), and treat any tool that uses a system default as a bug.</p>
</details>
<h2 id="Exercise-5-—-Safe-bulk-edit-in-PowerShell-51"><a href="#Exercise-5-—-Safe-bulk-edit-in-PowerShell-51" class="headerlink" title="Exercise 5 — Safe bulk edit in PowerShell 5.1"></a>Exercise 5 — Safe bulk edit in PowerShell 5.1</h2>
<p>Change <code>katex: true</code> to <code>katex: false</code> in every <code>.md</code> file of a folder, without changing the encoding.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="powershell"><span class="line"><span class="hljs-variable">$utf8NoBom</span> = <span class="hljs-built_in">New-Object</span> System.Text.UTF8Encoding(<span class="hljs-variable">$false</span>)</span><br><span class="line"><span class="hljs-built_in">Get-ChildItem</span> <span class="hljs-literal">-Path</span> .\content\posts <span class="hljs-literal">-Filter</span> *.md | <span class="hljs-built_in">ForEach-Object</span> {</span><br><span class="line">    <span class="hljs-variable">$t</span> = [<span class="hljs-type">System.IO.File</span>]::ReadAllText(<span class="hljs-variable">$_</span>.FullName, [<span class="hljs-type">System.Text.Encoding</span>]::UTF8)</span><br><span class="line">    <span class="hljs-variable">$new</span> = <span class="hljs-variable">$t</span> <span class="hljs-operator">-replace</span> <span class="hljs-string">&#x27;(?m)^katex: true(?=\r?$)&#x27;</span>, <span class="hljs-string">&#x27;katex: false&#x27;</span></span><br><span class="line">    <span class="hljs-keyword">if</span> (<span class="hljs-variable">$new</span> <span class="hljs-operator">-ne</span> <span class="hljs-variable">$t</span>) {</span><br><span class="line">        [<span class="hljs-type">System.IO.File</span>]::WriteAllText(<span class="hljs-variable">$_</span>.FullName, <span class="hljs-variable">$new</span>, <span class="hljs-variable">$utf8NoBom</span>)</span><br><span class="line">    }</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>$_.FullName</code> is already a full path. The lookahead <code>(?=\r?$)</code> leaves any <code>\r</code> in place, so line endings do not change either (see Dev Essentials 04 · Line Endings). Then check in Git Bash: <code>grep -l $'\xe7\xb9\x9a' content/posts/*.md</code> should print nothing, and <code>git diff --stat</code> should list only the files you meant to change.</p>
</details>
