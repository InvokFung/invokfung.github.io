<h1 id="Chapter-1-—-Concurrent-rendering"><a href="#Chapter-1-—-Concurrent-rendering" class="headerlink" title="Chapter 1 — Concurrent rendering"></a>Chapter 1 — Concurrent rendering</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Blocking (urgent) update</strong> — must be shown right away: typing, clicking, pressing a key. Rendered synchronously to the end.</li>
<li><strong>Non-blocking update (Transition)</strong> — may take a moment: switching tabs, filtering a big list, navigating. Rendered in time slices and can be interrupted.</li>
<li><strong>Interruptible render</strong> — React can stop building the <code>workInProgress</code> tree (Post 00), handle something more urgent, then restart or resume.</li>
<li><strong>Tearing</strong> — part of the UI showing one version of the data and part another. Concurrent rendering must avoid it (Post 01's <code>useSyncExternalStore</code>).</li>
</ul>
<h2 id="What-concurrent-means"><a href="#What-concurrent-means" class="headerlink" title="What &quot;concurrent&quot; means"></a>What &quot;concurrent&quot; means</h2>
<p>JavaScript in the browser still runs on one main thread. React does not render in parallel. &quot;Concurrent&quot; means React can keep <strong>several versions of the UI in progress</strong> and choose which to work on:</p>
<ol>
<li>The user types in a search box while a large result list is being re-rendered as a Transition.</li>
<li>The keystroke arrives. React pauses (or abandons) the list render at the next yield point.</li>
<li>It renders and commits the input change synchronously, so the character appears at once.</li>
<li>It restarts the list render with the newest query.</li>
</ol>
<p>Without concurrent rendering, step 2 is impossible: a render that started must finish, and a 200 ms list render means 200 ms of input lag.</p>
<p>What concurrent rendering does <strong>not</strong> do: make a slow component faster. The total work is the same (or a little more, because of restarts). It only changes <em>which</em> work the user waits for.</p>
<p><strong>Opting in.</strong> There is no global switch. <code>createRoot</code> enables the concurrent renderer, but updates stay blocking unless you mark them: <code>startTransition</code>, <code>useDeferredValue</code>, or Suspense-related features. An app that uses none of these behaves much like React 17, plus automatic batching.</p>
<hr>
<h1 id="Chapter-2-—-Lanes-at-a-high-level"><a href="#Chapter-2-—-Lanes-at-a-high-level" class="headerlink" title="Chapter 2 — Lanes at a high level"></a>Chapter 2 — Lanes at a high level</h1>
<p>React tracks priority with <strong>lanes</strong>: bits in a 31-bit integer. Each update gets a lane; each fiber records the lanes of its pending updates (<code>lanes</code>, <code>childLanes</code> from Post 00). A bit mask makes it cheap to ask &quot;does this subtree have work at this priority?&quot; and to process several updates of the same priority together.</p>

<p>Three consequences worth knowing:</p>
<ul>
<li><strong>Higher lanes interrupt lower ones.</strong> A Transition render in progress is paused or thrown away when a Sync update arrives.</li>
<li><strong>Transitions are batched.</strong> As of React 19.2, when several Transitions are pending, React can render them together, so a slow Transition can delay a fast one.</li>
<li><strong>Starvation is prevented.</strong> A lower-priority lane that keeps being interrupted is eventually marked expired and rendered synchronously, so it cannot be delayed forever.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> the Performance panel in Chrome shows React's &quot;Scheduler&quot; and &quot;Components&quot; tracks (React 19.2 Performance Tracks), labelled with priorities such as blocking and transition. It is the quickest way to see lanes in a real trace.</p>
</blockquote>

<h2 id="Limits"><a href="#Limits" class="headerlink" title="Limits"></a>Limits</h2>
<ul>
<li><strong>Do not use a Transition for a controlled text input's own value.</strong> The input must update synchronously; put only the expensive consequence (the filtered list) behind the Transition, or use <code>useDeferredValue</code>.</li>
<li><strong>Only <code>set</code> calls made synchronously inside the callback (or inside nested <code>startTransition</code>) are marked.</strong> A <code>setTimeout</code> inside <code>startTransition</code> escapes it.</li>
<li><strong>Out-of-order responses are your problem</strong> with raw async Transitions: two quick submits can finish in the wrong order. <code>useActionState</code> (Chapter 6) queues actions and avoids this.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> a Transition does not make a slow component faster. If <code>Posts</code> takes 800 ms to render, the user still waits 800 ms for it; they just are not frozen while waiting. Pair Transitions with the performance work in Post 03.</p>
</blockquote>

<h1 id="Chapter-5-—-Suspense-for-code-and-data"><a href="#Chapter-5-—-Suspense-for-code-and-data" class="headerlink" title="Chapter 5 — Suspense for code and data"></a>Chapter 5 — Suspense for code and data</h1>
<h2 id="What-Suspense-does"><a href="#What-Suspense-does" class="headerlink" title="What Suspense does"></a>What Suspense does</h2>
<p>A <code>&lt;Suspense fallback={...}&gt;</code> boundary shows its fallback while something inside it is <strong>not ready</strong>. Children signal &quot;not ready&quot; by suspending. Supported sources:</p>
<ul>
<li><code>lazy()</code> components while their code loads (Post 03),</li>
<li><code>use(promise)</code> while the promise is pending,</li>
<li>Suspense-enabled data libraries and frameworks (TanStack Query's <code>useSuspenseQuery</code>, Relay, Next.js and other RSC frameworks).</li>
</ul>
<p>Suspense does <strong>not</strong> detect a fetch inside <code>useEffect</code>. The data source has to integrate with it.</p>
<pre><code class="language-jsx"><figure class="highlight jsx"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="jsx"><span class="line">&lt;<span class="hljs-title class_">Suspense</span> fallback={<span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">PageSkeleton</span> /&gt;</span></span>}&gt;</span><br><span class="line">  <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">ProfileHeader</span> <span class="hljs-attr">userId</span>=<span class="hljs-string">{id}</span> /&gt;</span></span></span><br><span class="line">  <span class="language-xml"><span class="hljs-tag">&lt;<span class="hljs-name">Suspense</span> <span class="hljs-attr">fallback</span>=<span class="hljs-string">{</span>&lt;<span class="hljs-attr">PostsSkeleton</span> /&gt;</span>}&gt;</span><br><span class="line">    <span class="hljs-tag">&lt;<span class="hljs-name">ProfilePosts</span> <span class="hljs-attr">userId</span>=<span class="hljs-string">{id}</span> /&gt;</span></span><br><span class="line">  <span class="hljs-tag">&lt;/<span class="hljs-name">Suspense</span>&gt;</span></span></span><br><span class="line">&lt;/<span class="hljs-title class_">Suspense</span>&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Nested boundaries define the <strong>loading sequence</strong>: the header can appear as soon as its data arrives, while the posts area keeps its own skeleton. Place boundaries where a designer would put a loading state, not around every component.</p>
<h2 id="Suspense-and-Transitions"><a href="#Suspense-and-Transitions" class="headerlink" title="Suspense and Transitions"></a>Suspense and Transitions</h2>
<p>When a component that is <strong>already showing</strong> suspends again (for example because a new <code>userId</code> needs new data), React has two choices: replace the content with the fallback, or keep the old content until the new content is ready.</p>
<ul>
<li>In a <strong>blocking</strong> update, React shows the nearest fallback. Existing content disappears — usually a bad experience.</li>
<li>In a <strong>Transition</strong>, React keeps the old UI on screen and waits; only <strong>new</strong> boundaries that have never shown content will show their fallback.</li>
</ul>
<p>That is why routers built for React 18+ wrap navigations in <code>startTransition</code>: clicking a link keeps the current page visible (with <code>isPending</code> for a progress bar) instead of flashing a skeleton.</p>
<p>To force a fresh fallback for a different entity, change the boundary's identity: <code>&lt;Suspense key={userId} fallback={...}&gt;</code>.</p>
<h2 id="React-19-changes"><a href="#React-19-changes" class="headerlink" title="React 19 changes"></a>React 19 changes</h2>
<ul>
<li><strong>Sibling pre-warming.</strong> When a component suspends, React 19 commits the nearest fallback immediately, without first rendering the rest of the siblings, and then renders the suspended siblings in the background to start their lazy requests.</li>
<li><strong>SSR reveal batching (19.2).</strong> Server-rendered Suspense boundaries that resolve close together are revealed in a short batch instead of one by one, which matches client behaviour and prepares for view-transition animations.</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> creating the promise during render: <code>use(fetch(url))</code> in a client component creates a new promise every render, so it never resolves from React's point of view. Promises passed to <code>use</code> must be cached — created by a framework, a data library, or a Server Component and passed down.</p>
</blockquote>

<h1 id="Chapter-6-—-Actions-useActionState-useFormStatus-useOptimistic"><a href="#Chapter-6-—-Actions-useActionState-useFormStatus-useOptimistic" class="headerlink" title="Chapter 6 — Actions: useActionState, useFormStatus, useOptimistic"></a>Chapter 6 — Actions: <code>useActionState</code>, <code>useFormStatus</code>, <code>useOptimistic</code></h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Action</strong> — a function, usually async, run inside a Transition. React tracks its pending state, errors and optimistic updates.</li>
<li><strong>Form action</strong> — a function passed to <code>&lt;form action={fn}&gt;</code> (or <code>&lt;button formAction={fn}&gt;</code>). React calls it with the <code>FormData</code> inside a Transition and, when it succeeds, resets uncontrolled fields.</li>
<li><strong>Server Function</strong> — an async function marked <code>&quot;use server&quot;</code> that runs on the server but can be called from the client (called &quot;Server Action&quot; when used as an action).</li>
</ul>

<p>When <code>mode=&quot;hidden&quot;</code>, React:</p>
<ul>
<li>hides the children with <code>display: none</code> — the DOM stays, so scroll position, input text and <code>&lt;video&gt;</code> elements are kept;</li>
<li><strong>keeps their state</strong>;</li>
<li><strong>cleans up their effects</strong> (subscriptions stop, timers clear);</li>
<li>keeps rendering them when their props change, but at a lower priority than visible content.</li>

<p>When the boundary becomes visible again, effects are set up again and the UI appears with its state intact. Compared with <code>{page === &quot;inbox&quot; &amp;&amp; &lt;Inbox /&gt;}</code>, switching back is instant and nothing is lost. <p>Things to check before using it:</p>
<ul>
<li>Effects must be written correctly (Post 01): hiding runs their cleanup, showing runs setup again. This is exactly what StrictMode's double effect run rehearses.</li>
<li>DOM side effects do not stop automatically. A playing <code>&lt;video&gt;</code> keeps playing when hidden unless an effect cleanup pauses it.</li>
<li>Hidden trees still cost memory. Do not keep dozens of large screens alive.</li>
</ul>

<h1 id="Chapter-9-—-React-Server-Components-an-overview"><a href="#Chapter-9-—-React-Server-Components-an-overview" class="headerlink" title="Chapter 9 — React Server Components: an overview"></a>Chapter 9 — React Server Components: an overview</h1>
<p>React Server Components (RSC) split the component tree between two environments. This chapter gives the React-level model; the Next.js Deep Dive series covers routing, caching and deployment.</p>
<h2 id="The-rules"><a href="#The-rules" class="headerlink" title="The rules"></a>The rules</h2>
<ul>
<li><strong>Server Components</strong> are the default in an RSC framework. They run on the server (at build time or per request), can be <code>async</code>, can read files and databases directly, and send <strong>no JavaScript</strong> for themselves to the browser. They cannot use state, effects, or browser APIs.</li>
<li><strong><code>&quot;use client&quot;</code></strong> at the top of a file marks a <strong>boundary</strong>: that module and everything it imports become part of the client bundle. Client Components render on the server for HTML (SSR) and then hydrate in the browser.</li>
<li><strong>Props from a Server Component to a Client Component must be serialisable</strong>: primitives, plain objects and arrays, <code>Date</code>, <code>Map</code>, <code>Set</code>, typed arrays, promises, JSX elements, and Server Functions. Ordinary functions and class instances cannot cross.</li>
<li><strong><code>&quot;use server&quot;</code></strong> marks <strong>Server Functions</strong>: async functions the client can call over the network (for example as a form action). Treat each one as a public API endpoint — validate input and check authorisation inside it.</li>
</ul>

<p>A Client Component can receive Server Components as <code>children</code> (the composition pattern from Post 00): the server renders them and the client only places the result. That is how interactive shells wrap server-rendered content without pulling it into the client bundle.</p>
<blockquote>
<p><strong>Common pitfall:</strong> putting <code>&quot;use client&quot;</code> at the top of a high-level layout &quot;to make things work&quot;. Everything imported below it becomes client code, and the bundle-size benefit of RSC is gone. Push the boundary down to the leaves that need interactivity.</p>
</blockquote>

<h1 id="Chapter-10-—-React-Compiler-10"><a href="#Chapter-10-—-React-Compiler-10" class="headerlink" title="Chapter 10 — React Compiler 1.0"></a>Chapter 10 — React Compiler 1.0</h1>
<p>React Compiler reached <strong>1.0 on 7 October 2025</strong>. It is a build-time tool (a Babel plugin, <code>babel-plugin-react-compiler</code>, with experimental SWC support) that adds <strong>automatic memoisation</strong> to components and hooks.</p>
<h2 id="What-it-does"><a href="#What-it-does" class="headerlink" title="What it does"></a>What it does</h2>
<p>The compiler analyses each component and hook, works out which values depend on which inputs, and caches JSX, objects, callbacks and computed values so they keep their identity until their inputs change. It can memoise in places where <code>useMemo</code> cannot be written, such as after an early return, and at a finer grain than most hand-written code.</p>
<p>The practical effect: the &quot;new object prop breaks <code>memo</code>&quot; and &quot;inline callback re-renders the child&quot; problems from Posts 00 and 01 mostly disappear, without writing <code>useMemo</code>, <code>useCallback</code> or <code>memo</code>.</p>
<h2 id="What-it-needs"><a href="#What-it-needs" class="headerlink" title="What it needs"></a>What it needs</h2>
<p>It assumes the <strong>Rules of React</strong>: pure render, no mutation of props or state, hooks at the top level, no reading refs during render. When it cannot prove a component follows the rules, it <strong>skips that component</strong> and leaves it as written. The compiler-powered rules in <code>eslint-plugin-react-hooks</code> (v6+, in the <code>recommended</code> preset) — <code>purity</code>, <code>refs</code>, <code>immutability</code>, <code>set-state-in-render</code>, <code>static-components</code> and others — report the code it would skip.</p>

<p>Framework support: Next.js 16 made the <code>reactCompiler: true</code> option stable (not on by default; builds get slower because it uses Babel), Expo SDK 54 enables it by default, and <code>create-vite</code> offers a compiler template.</p>
<p>A realistic rollout:</p>
<ol>
<li>Turn on the lint rules first and fix what they report.</li>
<li>Enable the compiler for one directory or with <code>annotation</code> mode.</li>
<li>Run the tests and profile key screens (Post 03).</li>
<li>Widen the scope.</li>
</ol>
<p>The React team's guidance on existing <code>useMemo</code> / <code>useCallback</code>: for new code, rely on the compiler and use them only where precise control is needed (for example, a value used as an effect dependency); for existing code, <strong>leave them in place</strong> or remove them carefully with tests, because removing them can change the compiled output.</p>
<blockquote>
<p><strong>Watch out:</strong> the compiler makes it easy to forget that memoisation is about identity. Code that <em>depends</em> on a value keeping its identity for correctness (an effect that must not re-run) should still say so explicitly, not rely on the compiler's current heuristics.</p>
</blockquote>

<h2 id="Exercise-1-—-No-skeleton-flash"><a href="#Exercise-1-—-No-skeleton-flash" class="headerlink" title="Exercise 1 — No skeleton flash"></a>Exercise 1 — No skeleton flash</h2>
<p>Clicking &quot;next user&quot; replaces the profile with a skeleton for 300 ms. Keep the old profile visible with a small pending indicator instead.</p>
<details>
<summary>Solution</summary>
<p>Make the navigation a Transition: <code>const [isPending, startTransition] = useTransition();</code> and <code>startTransition(() =&gt; setUserId(next))</code>. Already-revealed Suspense content is not replaced by the fallback during a Transition; show <code>isPending</code> as a spinner or reduced opacity.</p>
</details>

<h2 id="Exercise-3-—-Why-did-the-optimistic-item-vanish"><a href="#Exercise-3-—-Why-did-the-optimistic-item-vanish" class="headerlink" title="Exercise 3 — Why did the optimistic item vanish?"></a>Exercise 3 — Why did the optimistic item vanish?</h2>
<p>A &quot;like&quot; button uses <code>useOptimistic</code> to show <code>likes + 1</code>. After the request succeeds, the count goes back to the old number. Why?</p>
<details>
<summary>Solution</summary>
<p>The optimistic value only lives while the Action is pending. When it ends, React renders from the real <code>value</code> — which never changed, because nothing refetched or updated the like count after the save. Update the source state (set it from the response, invalidate the query, or refresh the server data) inside the Action.</p>
</details>
<h2 id="Exercise-4-—-Find-the-boundary"><a href="#Exercise-4-—-Find-the-boundary" class="headerlink" title="Exercise 4 — Find the boundary"></a>Exercise 4 — Find the boundary</h2>
<p>A Server Component page passes <code>onSelect={id =&gt; router.push(...)}</code> to a Client Component <code>ProductGrid</code>. The build fails. Explain and fix.</p>
<details>
<summary>Solution</summary>
<p>A plain function is not serialisable, so it cannot cross from server to client. Move the handler into the Client Component (it can call <code>useRouter()</code> itself), or, if the work belongs on the server, pass a Server Function marked <code>&quot;use server&quot;</code>.</p>
</details>
<h2 id="Exercise-5-—-Tabs-that-keep-their-state"><a href="#Exercise-5-—-Tabs-that-keep-their-state" class="headerlink" title="Exercise 5 — Tabs that keep their state"></a>Exercise 5 — Tabs that keep their state</h2>
<p>A settings screen has three tabs; switching tabs loses scroll position and half-filled inputs. Fix it with React 19.2, and name one thing to check in the tab components first.</p>
<details>
<summary>Solution</summary>
<p>Render all three inside <code>&lt;Activity mode={active === name ? &quot;visible&quot; : &quot;hidden&quot;}&gt;</code>. State and DOM are kept; effects are cleaned up while hidden. Check that each tab's effects have correct cleanups (and that nothing like a media element keeps running), because hiding runs cleanup and showing runs setup again.</p>
</details>
