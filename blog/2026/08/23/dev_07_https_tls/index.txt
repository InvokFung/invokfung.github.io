11:T10f9c,<p>You type <code>https://example.com</code> and press Enter. Half a second later the page is on screen. In that half second your computer found an IP address, opened a TCP connection, agreed on encryption keys with a server it has never met, and checked that server's identity against a chain of certificates. Only then did it send the first HTTP request. This post walks through each step and shows the commands that let you watch it happen, in Bash and PowerShell. It ends with a field guide to the HTTPS errors you will actually meet.</p>

<h1 id="Chapter-1-—-The-big-picture"><a href="#Chapter-1-—-The-big-picture" class="headerlink" title="Chapter 1 — The big picture"></a>Chapter 1 — The big picture</h1>
<p>The whole trip for <code>https://example.com/</code>:</p>
<ol>
<li><strong>Parse the URL.</strong> Scheme <code>https</code>, host <code>example.com</code>, default port <code>443</code>, path <code>/</code>.</li>
<li><strong>HSTS check.</strong> If the browser has a Strict-Transport-Security rule for this host, it never uses plain <code>http://</code> (Chapter 7).</li>
<li><strong>DNS.</strong> Turn <code>example.com</code> into an IP address (Chapter 2).</li>
<li><strong>TCP.</strong> Open a reliable connection to that IP on port 443 (Chapter 3).</li>
<li><strong>TLS.</strong> Agree on keys, check the certificate, switch to encryption (Chapters 4-5).</li>
<li><strong>HTTP.</strong> Send <code>GET /</code> inside the encrypted channel and read the response.</li>
</ol>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="text"><span class="line">client                                              server</span><br><span class="line">  |--- DNS &quot;example.com A?&quot; --&gt; resolver --&gt; 104.20.23.154 (TTL 247 s)</span><br><span class="line">  |--- TCP SYN --------------------------------------&gt;  |   1 round trip</span><br><span class="line">  |&lt;-- SYN-ACK ---------------------------------------  |</span><br><span class="line">  |--- ACK + TLS ClientHello (key share, SNI, ALPN) -&gt;  |   1 round trip</span><br><span class="line">  |&lt;-- ServerHello + cert + Finished (encrypted) -----  |</span><br><span class="line">  |--- Finished + HTTP GET / (encrypted) ------------&gt;  |</span><br><span class="line">  |&lt;-- HTTP 200 + page (encrypted) -------------------  |</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-2-—-DNS-from-name-to-IP-address"><a href="#Chapter-2-—-DNS-from-name-to-IP-address" class="headerlink" title="Chapter 2 — DNS: from name to IP address"></a>Chapter 2 — DNS: from name to IP address</h1>
<p>Packets are routed by IP address, not by name. DNS (RFC 1034/1035) is the distributed phone book that turns names into addresses.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line">your app ─► stub resolver (small client in the OS; cache hit? answer at once)</span><br><span class="line">               ▼</span><br><span class="line">            recursive resolver (ISP, router, 1.1.1.1, 8.8.8.8; does the walking, caches everything)</span><br><span class="line">               ├─► root server      &quot;who handles .com?&quot;         → the .com TLD servers</span><br><span class="line">               ├─► .com TLD server  &quot;who handles example.com?&quot;  → its authoritative servers</span><br><span class="line">               └─► authoritative    &quot;example.com A?&quot;            → 104.20.23.154, TTL 300</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>There are 13 named root server identities (<code>a.root-servers.net</code> to <code>m.root-servers.net</code>), each served from many sites by anycast. The <strong>authoritative</strong> server holds the real records, and is usually run by your DNS host or CDN.</p>
<p>Every answer carries a <strong>TTL (time to live)</strong> in seconds. Caches may reuse the answer until the TTL runs out. That is why a DNS change takes time to reach everyone: old answers live until their TTL ends.</p>
<blockquote>
<p><strong>Trick:</strong> before you move a site to a new IP, lower the TTL (for example to 300 s) a day ahead. After the move, raise it again.</p>
</blockquote>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># Linux / macOS (dig comes with BIND tools; Git Bash does not include it)</span></span><br><span class="line">dig example.com A +noall +answer</span><br><span class="line">dig example.com CAA +short      <span class="hljs-comment"># which CAs may issue certificates for this domain</span></span><br><span class="line">dig +trace example.com          <span class="hljs-comment"># walk root → TLD → authoritative yourself</span></span><br><span class="line">nslookup -<span class="hljs-built_in">type</span>=A example.com    <span class="hljs-comment"># works everywhere, including Git Bash on Windows</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="powershell"><span class="line"><span class="hljs-comment"># Windows PowerShell 5.1</span></span><br><span class="line"><span class="hljs-built_in">Resolve-DnsName</span> example.com <span class="hljs-literal">-Type</span> A</span><br><span class="line"><span class="hljs-built_in">Resolve-DnsName</span> example.com <span class="hljs-literal">-Type</span> NS                            <span class="hljs-comment"># the authoritative servers</span></span><br><span class="line">ipconfig /displaydns | <span class="hljs-built_in">Select-String</span> example.com <span class="hljs-literal">-Context</span> <span class="hljs-number">0</span>,<span class="hljs-number">5</span>   <span class="hljs-comment"># what the OS has cached</span></span><br><span class="line"><span class="hljs-built_in">Clear-DnsClientCache</span>                                            <span class="hljs-comment"># same as ipconfig /flushdns</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-3-—-TCP-the-three-way-handshake"><a href="#Chapter-3-—-TCP-the-three-way-handshake" class="headerlink" title="Chapter 3 — TCP: the three-way handshake"></a>Chapter 3 — TCP: the three-way handshake</h1>
<p>HTTP/1.1 and HTTP/2 run over TCP, which gives an ordered, reliable byte stream. Opening it takes three packets:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="text"><span class="line">client → server   SYN       &quot;I want to talk. My starting sequence number is x.&quot;</span><br><span class="line">server → client   SYN-ACK   &quot;OK. Mine is y. I got your x.&quot;</span><br><span class="line">client → server   ACK       &quot;I got your y.&quot;   (data can follow right away)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>That is one full round trip before any data flows. To test only the TCP step:</p>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="powershell"><span class="line"><span class="hljs-built_in">Test-NetConnection</span> example.com <span class="hljs-literal">-Port</span> <span class="hljs-number">443</span>        <span class="hljs-comment"># look for TcpTestSucceeded : True</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="bash"><span class="line">curl -sv telnet://example.com:443 --max-time 3  <span class="hljs-comment"># telnet:// opens TCP only, no TLS</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A <strong>timeout</strong> usually means a firewall, a wrong IP (stale DNS), or a server that is down. A fast <strong>connection refused</strong> means the host is reachable but nothing listens on that port. If TCP fails, TLS never starts.</p>

<h1 id="Chapter-4-—-The-TLS-13-handshake"><a href="#Chapter-4-—-The-TLS-13-handshake" class="headerlink" title="Chapter 4 — The TLS 1.3 handshake"></a>Chapter 4 — The TLS 1.3 handshake</h1>
<p>TLS (Transport Layer Security) gives three things: <strong>confidentiality</strong> (only the two ends can read), <strong>integrity</strong> (changes on the way are detected), and <strong>authentication</strong> (you reached the real <code>example.com</code>).</p>
<p>TLS 1.3 was defined in RFC 8446 (August 2018). In July 2026 the IETF published <strong>RFC 9846</strong>, which obsoletes RFC 8446. It calls itself a minor update that keeps the version number 1.3 and stays backward compatible. It also obsoletes RFC 5246, the TLS 1.2 spec.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span></pre></td><td class="code"><pre><code class="text"><span class="line">Client                                                  Server</span><br><span class="line">ClientHello</span><br><span class="line">  + supported_versions (1.3)   + key_share (ephemeral public key, e.g. X25519)</span><br><span class="line">  + server_name (SNI)          + ALPN (&quot;h2&quot;, &quot;http/1.1&quot;)   + signature_algorithms</span><br><span class="line">                         --------&gt;</span><br><span class="line">                                   ServerHello + key_share (server&#x27;s ephemeral public key)</span><br><span class="line">                                   ── everything below is encrypted ──</span><br><span class="line">                                   {EncryptedExtensions}  ALPN choice, ...</span><br><span class="line">                                   {Certificate}          leaf + intermediates</span><br><span class="line">                                   {CertificateVerify}    signature over the transcript</span><br><span class="line">                                   {Finished}             MAC over the transcript</span><br><span class="line">                         &lt;--------</span><br><span class="line">{Finished} + [HTTP request] -----&gt;</span><br><span class="line">                         &lt;--------  [HTTP response]</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ol>
<li><strong>ClientHello.</strong> The client guesses which key-exchange group the server accepts and sends a public key for it at once. This guess is what saves a round trip compared with TLS 1.2.</li>
<li><strong>ServerHello.</strong> The server sends its own public key. Both sides now run <strong>ECDHE</strong> (Elliptic-Curve Diffie-Hellman, Ephemeral): each mixes its private key with the other's public key and gets the same shared secret. Someone watching the wire cannot compute it.</li>
<li><strong>Keys are derived</strong> from that secret. Everything after ServerHello is encrypted, including the certificate.</li>
<li><strong>CertificateVerify.</strong> The server signs a hash of all handshake messages so far with the <strong>private key</strong> of its certificate. This proves it owns the certificate, not just a copy.</li>
<li><strong>Finished.</strong> Each side sends a MAC over the whole transcript. If an attacker changed any earlier message, the MACs do not match and the connection dies.</li>
<li>The client sends its HTTP request together with its Finished. <strong>Total: one round trip (1-RTT).</strong></li>
</ol>
<p>The key pairs are <strong>ephemeral</strong>: new for each connection, then thrown away. So stealing the server's certificate key later does not decrypt recorded old sessions. This is <strong>forward secrecy</strong>.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># Git Bash ships OpenSSL</span></span><br><span class="line">openssl s_client -connect example.com:443 -servername example.com -brief &lt; /dev/null</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line">CONNECTION ESTABLISHED</span><br><span class="line">Protocol version: TLSv1.3</span><br><span class="line">Ciphersuite: TLS_AES_256_GCM_SHA384</span><br><span class="line">Peer certificate: CN=example.com</span><br><span class="line">Verification: OK</span><br><span class="line">Server Temp Key: X25519, 253 bits</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>TLS_AES_256_GCM_SHA384</code> means AES-256 in GCM mode (an <strong>AEAD</strong> cipher: it encrypts and checks integrity in one step) with SHA-384 for key derivation. <code>Server Temp Key</code> is the ephemeral ECDHE group. That output came from OpenSSL 3.2. From OpenSSL 3.5 on, the default key shares offer the <strong>hybrid post-quantum</strong> group <code>X25519MLKEM768</code> (classic X25519 plus ML-KEM-768) as well as X25519, so you may see that name instead.</p>
<h2 id="Resumption-and-0-RTT"><a href="#Resumption-and-0-RTT" class="headerlink" title="Resumption and 0-RTT"></a>Resumption and 0-RTT</h2>
<p>After a handshake the server can send a <strong>session ticket</strong>. Next time the client presents it as a <strong>pre-shared key (PSK)</strong> and may send data in its very first flight: <strong>0-RTT early data</strong>.</p>
<blockquote>
<p><strong>Watch out:</strong> 0-RTT data can be <strong>replayed</strong>. An attacker who records the first flight can send it again, and the server may act on it twice. RFC 8446 says 0-RTT data has no non-replay guarantee between connections, and it is not forward secret either. Allow it only for safe, idempotent requests such as <code>GET</code>. RFC 8470 defines the <code>Early-Data: 1</code> header and the <code>425 Too Early</code> status for HTTP servers that want to refuse it.</p>
</blockquote>

<h1 id="Chapter-5-—-Certificates-and-the-chain-of-trust"><a href="#Chapter-5-—-Certificates-and-the-chain-of-trust" class="headerlink" title="Chapter 5 — Certificates and the chain of trust"></a>Chapter 5 — Certificates and the chain of trust</h1>
<p>Key exchange gives encryption, but encryption with whom? The <strong>certificate</strong> answers that. It is a statement, &quot;this public key belongs to <code>example.com</code>&quot;, signed by a <strong>Certificate Authority (CA)</strong>.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">openssl s_client -connect example.com:443 -servername example.com &lt; /dev/null 2&gt;/dev/null \</span><br><span class="line">  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line">subject=CN=example.com</span><br><span class="line">issuer=C=US, O=SSL Corporation, CN=Cloudflare TLS Issuing ECC CA 3</span><br><span class="line">notBefore=Jul 29 22:10:08 2026 GMT</span><br><span class="line">notAfter=Oct 27 22:17:21 2026 GMT</span><br><span class="line">X509v3 Subject Alternative Name:</span><br><span class="line">    DNS:example.com, DNS:*.example.com</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><strong>Subject Alternative Name (SAN)</strong> — the host names the certificate is valid for. Clients check the SAN, not the old Common Name.</li>
<li><strong>notBefore / notAfter</strong> — the validity window. Outside it, the certificate is rejected.</li>
<li><strong>Issuer</strong> — who signed it. The issuer has its own certificate, and so on up the chain.</li>
</ul>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="text"><span class="line">[root]          SSL.com TLS ECC Root CA 2022      ← already in your OS / browser trust store</span><br><span class="line">   │ signs</span><br><span class="line">[intermediate]  SSL.com TLS Transit ECC CA R2      ← sent by the server</span><br><span class="line">   │ signs</span><br><span class="line">[intermediate]  Cloudflare TLS Issuing ECC CA 3    ← sent by the server</span><br><span class="line">   │ signs</span><br><span class="line">[leaf]          CN=example.com                     ← sent by the server</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The server sends the <strong>leaf plus the intermediates</strong>. It does not send the root: the client must already have it in its <strong>trust store</strong>. The client builds a path from the leaf to a trusted root and checks every signature, the dates, the host name against the SAN, and key-usage limits. On Windows you can build the same chain with .NET (PowerShell 5.1):</p>
<pre><code class="language-powershell"><figure class="highlight powershell"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="powershell"><span class="line"><span class="hljs-variable">$h</span>   = <span class="hljs-string">&quot;example.com&quot;</span></span><br><span class="line"><span class="hljs-variable">$tcp</span> = <span class="hljs-built_in">New-Object</span> System.Net.Sockets.TcpClient(<span class="hljs-variable">$h</span>, <span class="hljs-number">443</span>)</span><br><span class="line"><span class="hljs-variable">$ssl</span> = <span <p>It prints <code>Tls13</code> and the same four names, leaf first. <strong>Trust stores differ by client:</strong> Windows and Chrome/Edge on Windows use the Windows certificate store (<code>Get-ChildItem Cert:\LocalMachine\Root</code>); macOS uses the keychain; Firefox has its own Mozilla store; Linux tools use a distro bundle; Python <code>requests</code> uses the <code>certifi</code> bundle. So one site can pass in one tool and fail in another.</p>
<h2 id="How-long-a-certificate-may-live-—-the-rules-today"><a href="#How-long-a-certificate-may-live-—-the-rules-today" class="headerlink" title="How long a certificate may live — the rules today"></a>How long a certificate may live — the rules today</h2>
<p>Public TLS certificates follow the CA/Browser Forum <strong>Baseline Requirements</strong>. Ballot <strong>SC-081v3</strong>, adopted on April 11, 2025, shrinks the maximum validity in steps (Baseline Requirements, section 6.3.2):</p>

<tbody>

<td>—</td>
<td>2026-03-15</td>
<td>398 days</td>
</tr>
<tr>
<td><strong>2026-03-15</strong></td>
<td><strong>2027-03-15</strong></td>
<td><strong>200 days</strong> ← applies now</td>

<tr>
<td>2027-03-15</td>
<td>2029-03-15</td>
<td>100 days</td>

<p>The same ballot cuts how long a CA may reuse a domain-validation result: 200 days from 2026-03-15, 100 days from 2027-03-15, 10 days from 2029-03-15. So a certificate issued today lives at most 200 days, and yearly manual renewal is already gone.</p>
<p><strong>Revocation.</strong> If a key leaks, the CA can revoke the certificate and publish that in a <strong>CRL</strong> (signed list of revoked serial numbers) or via <strong>OCSP</strong> (ask about one certificate). Let's Encrypt turned off its OCSP service on August 6, 2025, and now publishes revocation data only through CRLs. Short lifetimes also limit damage: a leaked short-lived certificate soon stops working anyway.</p>
<blockquote>
<p><strong>Trick:</strong> every publicly trusted certificate is recorded in public <strong>Certificate Transparency</strong> logs. Search your domain on a CT search site such as <a href="http://crt.sh" target="_blank" rel="noopener external nofollow noreferrer">crt.sh</a> to see every certificate ever issued for it.</p>
</blockquote>

<h1 id="Chapter-6-—-SNI-ECH-ALPN-HTTP2-and-HTTP3"><a href="#Chapter-6-—-SNI-ECH-ALPN-HTTP2-and-HTTP3" class="headerlink" title="Chapter 6 — SNI, ECH, ALPN, HTTP/2 and HTTP/3"></a>Chapter 6 — SNI, ECH, ALPN, HTTP/2 and HTTP/3</h1>
<p><strong>SNI.</strong> One IP often serves thousands of sites (think of a CDN). The server must pick a certificate before any HTTP <code>Host</code> header exists. So the client puts the host name in the ClientHello: the <strong>Server Name Indication</strong> extension (RFC 6066). That is why <code>openssl s_client</code> needs <code>-servername</code>. Without it you may get a default certificate for another name.</p>
<p><strong>ECH.</strong> SNI is plain text, so the network can see which site you visit. <strong>Encrypted Client Hello</strong> encrypts the real ClientHello under a public key the site publishes in its <code>HTTPS</code> DNS record.</p>
<ul>
<li><strong>RFC 9849</strong>, <em>TLS Encrypted Client Hello</em>, was published in March 2026 (Standards Track). <strong>RFC 9848</strong>, the same month, defines how ECH settings travel in SVCB/HTTPS DNS records.</li>
<li>Chrome Platform Status lists ECH as enabled by default since Chrome 117. Firefox 119 release notes say ECH &quot;is now available to Firefox users&quot;.</li>
<li>OpenSSL 4.0, released April 14, 2026, added ECH support.</li>
<li>The site's server or CDN must support it too. Where it does not, the connection falls back to normal SNI.</li>
</ul>
<p><strong>ALPN.</strong> Application-Layer Protocol Negotiation (RFC 7301) lets the client list protocols such as <code>h2</code> and <code>http/1.1</code> in the ClientHello. The server picks one in its reply, with no extra round trip.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">openssl s_client -connect example.com:443 -servername example.com -alpn h2,http/1.1 &lt; /dev/null 2&gt;/dev/null | grep ALPN</span><br><span class="line"><span class="hljs-comment"># ALPN protocol: h2</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>QUIC carries TLS 1.3 inside its own handshake (RFC 9001). A browser learns that a site speaks HTTP/3 from the <code>HTTPS</code> DNS record or from an <code>Alt-Svc</code> response header. The one from <a href="http://google.com" target="_blank" rel="noopener external nofollow noreferrer">google.com</a> begins with <code>Alt-Svc: h3=&quot;:443&quot;; ma=2592000</code> (&quot;HTTP/3 on port 443, remember this for 30 days&quot;).</p>
<blockquote>
<p><strong>Watch out:</strong> <code>curl --http3</code> works only if your curl build has HTTP/3. Check the Features line of <code>curl -V</code> for <code>HTTP3</code>. Neither the Git Bash curl nor the Windows <code>curl.exe</code> used for this post had it.</p>
</blockquote>

<h1 id="Chapter-7-—-HSTS-never-talk-plain-HTTP-again"><a href="#Chapter-7-—-HSTS-never-talk-plain-HTTP-again" class="headerlink" title="Chapter 7 — HSTS: never talk plain HTTP again"></a>Chapter 7 — HSTS: never talk plain HTTP again</h1>
<p>A user types <code>example.com</code> with no scheme. The browser tries <code>http://</code>, and the server redirects to <code>https://</code>. That first plain request can be intercepted. An attacker on public Wi-Fi can keep the user on HTTP (&quot;SSL stripping&quot;).</p>
<p><strong>HTTP Strict Transport Security</strong> (RFC 6797) closes the gap. The server sends, over HTTPS:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">Strict-Transport-Security: max-age=31536000; includeSubdomains; preload</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>(That exact header comes from <a href="http://github.com" target="_blank" rel="noopener external nofollow noreferrer">github.com</a>.) For <code>max-age</code> seconds (here one year) the browser turns every <code>http://</code> URL for the host into <code>https://</code> before sending anything. It also stops users from clicking through certificate errors. <code>includeSubDomains</code> applies the rule to every subdomain. <code>preload</code> agrees to be built into browsers' <strong>preload list</strong>, which also protects the very first visit. To join that list, <a href="http://hstspreload.org" target="_blank" rel="noopener external nofollow noreferrer">hstspreload.org</a> requires a valid certificate, an HTTP → HTTPS redirect, HTTPS on all subdomains, and a header with <code>max-age</code> of at least 31536000, <code>includeSubDomains</code> and <code>preload</code>.</p>
<blockquote>
<p><strong>Common pitfall:</strong> adding <code>includeSubDomains; preload</code> while some old subdomain (an intranet box, a printer page) only speaks HTTP. Browsers will refuse it. The preload site warns that removal takes months to reach users. Start with a short <code>max-age</code>, check every subdomain, then raise it.</p>
</blockquote>

<h1 id="Chapter-8-—-Lets-Encrypt-and-ACME"><a href="#Chapter-8-—-Lets-Encrypt-and-ACME" class="headerlink" title="Chapter 8 — Let's Encrypt and ACME"></a>Chapter 8 — Let's Encrypt and ACME</h1>
<p><strong>Let's Encrypt</strong> is a free, automated CA. Clients talk to it with <strong>ACME</strong> (Automatic Certificate Management Environment, RFC 8555):</p>
<ol>
<li>The client creates an <strong>account key</strong> and places an <strong>order</strong> for names, e.g. <code>example.com</code> and <code>www.example.com</code>.</li>
<li>For each name the CA sets a <strong>challenge</strong> to prove control:
<ul>
<li><code>http-01</code> — serve a token at <code>http://&lt;name&gt;/.well-known/acme-challenge/&lt;token&gt;</code>.</li>
<li><code>dns-01</code> — publish a <code>TXT</code> record at <code>_acme-challenge.&lt;name&gt;</code>. Needed for wildcard certificates.</li>
<li><code>tls-alpn-01</code> — answer a special TLS handshake on port 443 (RFC 8737).</li>
</ul>
</li>
<li>The client <strong>finalizes</strong> with a CSR (certificate signing request) holding its public key.</li>
<li>The CA issues the certificate; the client installs it and reloads the server.</li>
</ol>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-built_in">sudo</span> certbot --nginx -d example.com -d www.example.com   <span class="hljs-comment"># typical Linux + nginx</span></span><br><span class="line"><span class="hljs-built_in">sudo</span> certbot renew --dry-run                             <span class="hljs-comment"># prove that auto-renewal works</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>On Windows servers, win-acme does the same job. Caddy, and hosts such as GitHub Pages, Cloudflare and AWS Certificate Manager, run ACME for you.</p>

<p>The announced plan for the default: on <strong>February 10, 2027</strong>, <code>classic</code> moves to 64-day certificates with a 10-day authorization reuse period. On <strong>February 16, 2028</strong> it moves to 45 days with a 7-hour reuse period. That stays under the 47-day cap that starts March 15, 2029.</p>
<p><strong>ACME Renewal Information (ARI)</strong>, RFC 9773 (June 2025), lets the CA tell your client when to renew, for example early during an incident. Let's Encrypt recommends ARI and renewing about two-thirds of the way through a certificate's life.</p>

<p><strong>Why the missing intermediate is so confusing.</strong> <code>openssl</code> failed on <code>incomplete-chain</code>, but Python on Windows said OK, and so did the Windows <code>curl</code> (Schannel). Windows can download a missing intermediate itself, from the &quot;CA Issuers&quot; (AIA) URL inside the leaf, and it caches the result. Python on Windows loads certificates from the Windows stores, so it most likely found that cached copy. Many clients never do this: <code>openssl</code>, many Linux tools, Java, some mobile apps. So the site &quot;works on my machine&quot; and fails for others.</p>
<blockquote>
<p><strong>Common pitfall:</strong> testing only in your desktop browser. Always test the chain with <code>openssl s_client</code>, which does not fetch missing intermediates, or with an online SSL checker.</p>
</blockquote>
<p><strong>Clock skew.</strong> A certificate is valid only between <code>notBefore</code> and <code>notAfter</code>. A clock that is a year behind makes every new certificate &quot;not yet valid&quot;. A clock that is ahead makes them look expired. Suspects: dead CMOS battery, fresh VMs, devices without network time. Check with <code>w32tm /query /status</code> on Windows (<code>w32tm /resync</code> in an admin shell forces a sync) or <code>timedatectl status</code> on Linux (&quot;System clock synchronized: yes&quot;). More in Dev Essentials 02 · Dates &amp; Time Zones.</p>
<p><strong>In the browser.</strong> In Chrome or Edge, click the icon left of the address and open the connection details to view the certificate. DevTools has a <strong>Security</strong> panel (called &quot;Privacy and security&quot; in some recent versions) with the protocol, key exchange, cipher and a <strong>View certificate</strong> button. In Firefox: padlock → <em>Connection secure</em> → <em>More information</em> → <em>View Certificate</em>.</p>
<blockquote>
<p><strong>Watch out:</strong> never &quot;fix&quot; an error by turning verification off: <code>curl -k</code>, <code>requests.get(url, verify=False)</code>, <code>NODE_TLS_REJECT_UNAUTHORIZED=0</code>. That removes the authentication part of TLS, and any man-in-the-middle can then read and change your traffic. Fix the certificate, or add your private CA to the trust store on purpose.</p>
</blockquote>

<h2 id="Exercise-1-—-Time-each-phase"><a href="#Exercise-1-—-Time-each-phase" class="headerlink" title="Exercise 1 — Time each phase"></a>Exercise 1 — Time each phase</h2>
<p>Run <code>curl -w</code> against three sites: one near you, one far away, one behind a CDN. Work out DNS, TCP and TLS time separately. Which phases grow with distance?</p>
<details>
<summary>Solution</summary>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-keyword">for</span> u <span class="hljs-keyword">in</span> https://example.com https://www.gov.uk https://www.cloudflare.com; <span class="hljs-keyword">do</span></span><br><span class="line">  curl -s -o /dev/null -w <span class="hljs-string">&quot;<span class="hljs-variable">$u</span> dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect}\n&quot;</span> <span class="hljs-string">&quot;<span class="hljs-variable">$u</span>&quot;</span></span><br><span class="line"><span class="hljs-keyword">done</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>TCP time is <code>tcp - dns</code>, and TLS time is <code>tls - tcp</code>. Each costs about one RTT, so both grow with distance. DNS is often near zero after the first run because of caching. A CDN cuts TCP and TLS time because the handshake ends at an edge server near you.</p>
</details>

<summary>Solution</summary>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">openssl s_client -connect github.com:443 -servername github.com -showcerts &lt; /dev/null 2&gt;/dev/null \</span><br><span class="line">  | grep -E <span class="hljs-string">&quot;^ [0-9] s:|^   i:&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Exercise-3-—-Expiry-monitor"><a href="#Exercise-3-—-Expiry-monitor" class="headerlink" title="Exercise 3 — Expiry monitor"></a>Exercise 3 — Expiry monitor</h2>
<p>Change the Chapter 9 checker so it reads host names from a file and exits with code 1 if any certificate fails or has fewer than 30 days left. A scheduled task or CI job can then alert on it.</p>
<details>
<summary>Solution</summary>

<h2 id="Exercise-4-—-Design-an-HSTS-header"><a href="#Exercise-4-—-Design-an-HSTS-header" class="headerlink" title="Exercise 4 — Design an HSTS header"></a>Exercise 4 — Design an HSTS header</h2>
<p><code>shop.example</code> is fully HTTPS, except <code>legacy.shop.example</code>, an HTTP-only admin box that will be retired in three months. What HSTS header should <code>shop.example</code> send today?</p>
<details>
<summary>Solution</summary>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">Strict-Transport-Security: max-age=31536000</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Leave out <code>includeSubDomains</code> and <code>preload</code> until <code>legacy</code> is gone or on HTTPS. Otherwise browsers that visited <code>shop.example</code> would refuse plain HTTP to <code>legacy.shop.example</code>. After the retirement, add <code>includeSubDomains</code>, test, then think about <code>preload</code>.</p>
</details>
<h2 id="Exercise-5-—-0-RTT-risk"><a href="#Exercise-5-—-0-RTT-risk" class="headerlink" title="Exercise 5 — 0-RTT risk"></a>Exercise 5 — 0-RTT risk</h2>
<p>A banking API accepts 0-RTT early data. Why is <code>POST /transfer?to=alice&amp;amount=100</code> in early data dangerous, and what should the server do?</p>
<details>
<summary>Solution</summary>
<p>Early data can be replayed: an attacker who captured the first flight can send it again, and the transfer may run twice. The server should accept only idempotent requests (such as <code>GET</code>) as early data. For anything else it should refuse early data, for example with <code>425 Too Early</code> (RFC 8470), so the client retries after the full handshake. The request should also carry an idempotency key (see Dev Essentials 14 · API Reliability).</p>
</details>
