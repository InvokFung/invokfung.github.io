11:Tf878,<p>Vue's answer to &quot;virtual DOM is slow&quot; has always been the compiler. A template is not interpreted at run time: it is compiled into a render function that tells the runtime, node by node, which parts can ever change and how. That information — patch flags, cached static subtrees, blocks with flat lists of dynamic nodes — is why a Vue re-render usually skips most of the tree without comparing it. Vapor mode takes the idea to its end: compile the template straight to DOM operations and drop the virtual DOM entirely. This post reads real compiler output. It walks the SFC pipeline, decodes patch flags, explains static caching and the block tree, works through the keyed diff and its longest-increasing-subsequence step, shows what <code>v-once</code> and <code>v-memo</code> compile to, and compares a component compiled both ways. Every code sample marked as output was produced by <code>@vue/compiler-dom</code> / <code>@vue/compiler-sfc</code> <strong>3.5</strong>, or <strong>3.6.0-rc.8</strong> for Vapor.</p>

<h1 id="Chapter-1-—-The-SFC-pipeline"><a href="#Chapter-1-—-The-SFC-pipeline" class="headerlink" title="Chapter 1 — The SFC pipeline"></a>Chapter 1 — The SFC pipeline</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Descriptor</strong> — the parsed <code>.vue</code> file: <code>template</code>, <code>script</code>, <code>scriptSetup</code>, <code>styles[]</code>, <code>customBlocks[]</code>, each with its source and location.</li>
<li><strong>AST</strong> — the tree the template parser produces; transforms rewrite it before code generation.</li>
<li><strong>Transform</strong> — a compiler pass for one feature: <code>v-if</code>, <code>v-for</code>, <code>v-model</code>, slots, static analysis, patch flags.</li>
<li><strong>Codegen</strong> — turning the transformed AST into JavaScript source.</li>
<li><strong>Binding metadata</strong> — what <code>&lt;script setup&gt;</code> declares (<code>setup-ref</code>, <code>setup-const</code>, <code>props</code>, …). The template compiler uses it to emit <code>count.value</code> or <code>__props.x</code> instead of a generic <code>_ctx.count</code> lookup.</li>
<li><strong>Inline template</strong> — the template compiled into the <code>setup()</code> function as a closure, instead of as a separate <code>render</code> function.</li>
</ul>
<h2 id="The-stages"><a href="#The-stages" class="headerlink" title="The stages"></a>The stages</h2>
<ol>
<li><strong><code>parse()</code></strong> splits the file into a descriptor. Nothing is compiled yet.</li>
<li><strong><code>compileScript()</code></strong> processes <code>&lt;script setup&gt;</code>: removes macros (Post 01), resolves prop types, analyses bindings, and — in production — inlines the compiled template.</li>
<li><strong><code>compileTemplate()</code></strong> calls <code>@vue/compiler-dom</code>: parse → transforms → codegen, producing a render function.</li>
<li><strong><code>compileStyle()</code></strong> runs PostCSS for <code>scoped</code> styles (adds <code>data-v-&lt;hash&gt;</code> attribute selectors, <code>:deep()</code>, <code>:slotted()</code>), CSS modules, and <code>v-bind()</code> in CSS (compiled to CSS custom properties set from the component).</li>
</ol>
<p><code>@vitejs/plugin-vue</code> drives these stages. It uses the inline-template mode only when <strong>all</strong> of these hold: not the dev server, devtools support not enabled for production, the component has <code>&lt;script setup&gt;</code>, and the template is not loaded from <code>src</code>. Inline mode lets the render closure read <code>setup</code> bindings directly (<code>count.value</code>) without going through the <code>_ctx</code> proxy; the dev server keeps a separate render function so hot reload can swap the template alone.</p>
<blockquote>
<p><strong>Watch out:</strong> compiling templates at run time needs the full build (<code>vue/dist/vue.esm-bundler.js</code> with the compiler). The default <code>vue</code> import in a Vite app is the runtime-only build. A string <code>template:</code> option in a component object silently renders nothing and logs a warning in that setup.</p>
</blockquote>

<h1 id="Chapter-3-—-Patch-flags"><a href="#Chapter-3-—-Patch-flags" class="headerlink" title="Chapter 3 — Patch flags"></a>Chapter 3 — Patch flags</h1>
<p>A patch flag is a bitmask on a vnode that lists the <strong>only</strong> things that can differ between two renders of it. The runtime checks the flag and skips everything else. The values in 3.5 (<code>@vue/shared</code>):</p>
<table>
<thead>
<tr>
<th>Flag</th>
<th>Value</th>
<th>What the runtime patches</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>TEXT</code></td>
<td>1</td>
<td>Text children only</td>
</tr>
<tr>

<td>2</td>
<td><code>class</code> only</td>
</tr>

<blockquote>
<p><strong>Common pitfall:</strong> <code>&lt;Comp :options=&quot;{ dense: true }&quot; /&gt;</code> creates a <strong>new object on every parent render</strong>. <code>options</code> is dynamic (it is an expression), its identity always changes, and <code>Comp</code> re-renders every time its parent does. Hoist the literal into a constant in <code>&lt;script setup&gt;</code> or a <code>computed</code>.</p>
</blockquote>
<p>Hand-written render functions with <code>h()</code> get <strong>no</strong> patch flags: the runtime must diff them fully. That is one reason templates are the recommended default in Vue, not only a style preference.</p>

<h1 id="Chapter-4-—-Static-caching-and-stringification"><a href="#Chapter-4-—-Static-caching-and-stringification" class="headerlink" title="Chapter 4 — Static caching and stringification"></a>Chapter 4 — Static caching and stringification</h1>
<h2 id="Hoisting-became-caching-in-35"><a href="#Hoisting-became-caching-in-35" class="headerlink" title="Hoisting became caching in 3.5"></a>Hoisting became caching in 3.5</h2>
<p>The same <code>&lt;h2&gt;Title&lt;/h2&gt;</code> compiled by 3.4 and by 3.5:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// 3.4</span></span><br><span class="line"><span class="hljs-keyword">const</span> _hoisted_2 = <span class="hljs-comment">/*#__PURE__*/</span><span class="hljs-title function_">_createElementVNode</span>(<span class="hljs-string">&quot;h2&quot;</span>, <span class="hljs-literal">null</span>, <span class="hljs-string">&quot;Title&quot;</span>, -<span class="hljs-number">1</span> <span class="hljs-comment">/* HOISTED */</span>)</span><br><span class="line"><span class="hljs-comment">// … in render: _hoisted_2,</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// 3.5</span></span><br><span class="line">_cache[<span class="hljs-number">0</span>] || (_cache[<span class="hljs-number">0</span>] = <span class="hljs-title function_">_createElementVNode</span>(<span class="hljs-string">&quot;h2&quot;</span>, <span class="hljs-literal">null</span>, <span class="hljs-string">&quot;Title&quot;</span>, -<span class="hljs-number">1</span> <span class="hljs-comment">/* CACHED */</span>))</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>In 3.4 a static vnode was hoisted to <strong>module scope</strong> and shared by every instance of the component. In 3.5 it is created on first render and kept in the instance's <code>_cache</code> array. The flag name changed from <code>HOISTED</code> to <code>CACHED</code> with the same value (−1). Static <strong>props objects</strong> (<code>_hoisted_1 = { class: &quot;card&quot; }</code>) are still hoisted to module scope, because a plain object with no DOM reference is safe to share.</p>
<p>The practical effect is the same — static nodes are created once and skipped by the diff — but nothing is shared between instances any more. A hoisted vnode kept a reference (<code>el</code>) to the DOM element it was last mounted to, which was a known way to retain detached DOM trees (vuejs/core issue #5256). A per-instance cache avoids that shared state.</p>
<h2 id="Stringification"><a href="#Stringification" class="headerlink" title="Stringification"></a>Stringification</h2>
<p>When enough static content sits together, the compiler goes further and emits it as an HTML string that the runtime inserts with <code>innerHTML</code>:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">_cache[<span class="hljs-number">0</span>] || (_cache[<span class="hljs-number">0</span>] = <span class="hljs-title function_">_createStaticVNode</span>(</span><br><span class="line">  <span class="hljs-string">&quot;&lt;p class=\&quot;a\&quot;&gt;1&lt;/p&gt;&lt;p class=\&quot;a\&quot;&gt;2&lt;/p&gt;&lt;p class=\&quot;a\&quot;&gt;3&lt;/p&gt;&lt;p class=\&quot;a\&quot;&gt;4&lt;/p&gt;&lt;p class=\&quot;a\&quot;&gt;5&lt;/p&gt;&quot;</span>, <span class="hljs-number">5</span>))</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The threshold in <code>@vue/compiler-dom</code> 3.5 is <strong>20 or more consecutive static nodes, or 5 or more static elements with attributes</strong>. The same template with four <code>&lt;p class=&quot;a&quot;&gt;</code> elements instead of five produced four separate <code>CACHED</code> vnodes. Stringified chunks create no vnodes per element at all, which matters for large static sections such as documentation pages and legal text.</p>
<h2 id="What-is-never-static"><a href="#What-is-never-static" class="headerlink" title="What is never static"></a>What is never static</h2>
<p>Anything with a binding, a directive, a component, a <code>ref</code>, or a child that is dynamic. A single <code>{{ }}</code> inside a large block makes that element dynamic, but its static siblings and static descendants are still cached separately. Keep dynamic bits in small leaf elements and the static structure around them stays free.</p>
<hr>
<h1 id="Chapter-5-—-The-block-tree"><a href="#Chapter-5-—-The-block-tree" class="headerlink" title="Chapter 5 — The block tree"></a>Chapter 5 — The block tree</h1>
<h2 id="Blocks-collect-dynamic-descendants"><a href="#Blocks-collect-dynamic-descendants" class="headerlink" title="Blocks collect dynamic descendants"></a>Blocks collect dynamic descendants</h2>
<p><code>openBlock()</code> starts collecting; every vnode created with a patch flag while the block is open is pushed into the block's <strong><code>dynamicChildren</code></strong> array; <code>createElementBlock()</code> closes it. On update, the runtime calls <code>patchBlockChildren</code>, which walks this <strong>flat</strong> array and patches each dynamic node against its counterpart. The static structure between them is never visited.</p>
<p>For the Chapter 2 template, the root block's <code>dynamicChildren</code> holds the <code>&lt;span&gt;</code> (flag 3), the <code>v-for</code> fragment, and the <code>v-if</code> branch. The cached <code>&lt;h2&gt;</code> and <code>&lt;p&gt;</code>, the <code>&lt;button&gt;</code> with its cached handler, and the <code>&lt;ul&gt;</code> itself are not in it. A re-render after <code>msg</code> changes touches one text node's comparison, not the whole tree.</p>
<h2 id="Why-structural-directives-start-new-blocks"><a href="#Why-structural-directives-start-new-blocks" class="headerlink" title="Why structural directives start new blocks"></a>Why structural directives start new blocks</h2>
<p>A flat array works only if the set of dynamic nodes has a fixed shape. <code>v-if</code> and <code>v-for</code> change the shape: a branch may exist or not, a list may have 3 or 300 items. So each <code>v-if</code> branch is its own block (with a <code>key</code> so the runtime knows when the branch switched), and each <code>v-for</code> produces a fragment whose children are diffed as a list (Chapter 6), each child being a block of its own. Inside each block, the flat fast path applies again.</p>
<p><code>openBlock(true)</code> on the <code>v-for</code> fragment disables collection for that fragment: its children are diffed through the keyed algorithm, not through <code>dynamicChildren</code>.</p>
<hr>
<h1 id="Chapter-6-—-The-keyed-diff-and-the-longest-increasing-subsequence"><a href="#Chapter-6-—-The-keyed-diff-and-the-longest-increasing-subsequence" class="headerlink" title="Chapter 6 — The keyed diff and the longest increasing subsequence"></a>Chapter 6 — The keyed diff and the longest increasing subsequence</h1>
<h2 id="The-five-steps-of-patchKeyedChildren"><a href="#The-five-steps-of-patchKeyedChildren" class="headerlink" title="The five steps of patchKeyedChildren"></a>The five steps of <code>patchKeyedChildren</code></h2>
<p>Given old children <code>c1</code> and new children <code>c2</code>:</p>
<ol>
<li><strong>Sync from the start.</strong> While the heads have the same type and key, patch them and advance.</li>
<li><strong>Sync from the end.</strong> Same from the tails.</li>
<li><strong>Only new nodes left</strong> (old range exhausted): mount the remaining new nodes.</li>
<li><strong>Only old nodes left</strong> (new range exhausted): unmount the remaining old nodes.</li>
<li><strong>Unknown middle sequence:</strong>
<ol>
<li>Build <code>keyToNewIndexMap</code> from the new middle.</li>
<li>Walk the old middle. For each old node, find its new index by key. Not found: unmount it. Found: patch it, and record <code>newIndexToOldIndexMap[newIndex - start] = oldIndex + 1</code> (0 is reserved for &quot;new node&quot;). If a found new index is smaller than the largest seen so far, set <code>moved = true</code>.</li>
<li>If anything moved, compute the <strong>longest increasing subsequence</strong> (LIS) of <code>newIndexToOldIndexMap</code>. Nodes in the LIS are already in the right relative order and stay where they are. Walk the new middle <strong>backwards</strong>: a 0 entry is mounted, a node outside the LIS is moved, each before the node after it.</li>
</ol>
</li>
</ol>
<h2 id="A-worked-example"><a href="#A-worked-example" class="headerlink" title="A worked example"></a>A worked example</h2>
<p>Old: <code>a b c d e f g</code>. New: <code>a b e c d h f g</code>.</p>
<ul>
<li>Step 1 patches <code>a</code>, <code>b</code>. Step 2 patches <code>g</code>, <code>f</code>.</li>
<li>Middle: old <code>c d e</code> (old indices 2, 3, 4), new <code>e c d h</code> (new indices 2–5).</li>
<li>Step 5.2: <code>c</code> → new index 3, map slot 1 = 2 + 1 = <strong>3</strong>. <code>d</code> → new index 4, slot 2 = <strong>4</strong>. <code>e</code> → new index 2, which is smaller than 4, so <code>moved = true</code>; slot 0 = 4 + 1 = <strong>5</strong>. <code>h</code> is never found in the old list, so slot 3 stays <strong>0</strong>.</li>
<li>Map: <code>[5, 3, 4, 0]</code>. Its LIS, as positions, is <code>[1, 2]</code> — the values 3 and 4, i.e. <code>c</code> and <code>d</code>. (Checked by running Vue's own <code>getSequence([5, 3, 4, 0])</code>, which returns <code>[1, 2]</code>.)</li>
<li>Step 5.3, backwards: <code>h</code> (0) is <strong>mounted</strong> before <code>f</code>; <code>d</code> and <code>c</code> are in the LIS and <strong>stay</strong>; <code>e</code> is <strong>moved</strong> before <code>c</code>.</li>
</ul>
<p>Result: one insertion, one move, and no work at all for the six other nodes beyond patching them. The LIS is what makes the number of moves minimal: the nodes that can stay are exactly the longest run that is already in order. <code>getSequence</code> computes it in O(n log n) with patience sorting and binary search.</p>
<p><img src="/blog/assets/vue/diagram_02_keyed_diff.svg" alt="The keyed diff on old a b c d e f g and new a b e c d h f g: the common prefix a b and suffix f g are patched in place, the middle builds the map 5 3 4 0 from new position to old index plus one, its longest increasing subsequence 3 4 keeps c and d still, e is moved and h is mounted."></p>
<h2 id="Without-keys"><a href="#Without-keys" class="headerlink" title="Without keys"></a>Without keys</h2>
<p>A <code>v-for</code> without <code>:key</code> compiles to <code>UNKEYED_FRAGMENT</code> (256) and uses <code>patchUnkeyedChildren</code>: patch old and new <strong>by index</strong> for the common length, then mount or unmount the tail. Inserting at the front of an unkeyed list re-patches every item with its neighbour's data and moves no DOM, so component state and DOM state (focus, input values, animations) stay at their old positions while the data shifts.</p>
<blockquote>
<p><strong>Common pitfall:</strong> <code>:key=&quot;index&quot;</code> is the same as no key for this purpose. Keys must be stable identities from the data (<code>item.id</code>). Random keys (<code>Math.random()</code>) are worse: every render remounts every item.</p>
</blockquote>

<p>If the memo array is shallow-equal to last time, the previous vnode is returned and the whole subtree is skipped — no render, no diff. For a 1,000-row list where only the selected row changes, changing <code>selected</code> re-renders two rows (the old and the new selection) instead of all of them.</p>
<p>Rules and traps:</p>
<ul>
<li>Inside <code>v-for</code>, <code>v-memo</code> must be on the same element as the <code>v-for</code>, and the <code>v-for</code> needs a <code>key</code>.</li>
<li>The memo array must list <strong>everything</strong> the subtree reads that can change. In the example above, if <code>item.label</code> changes, the row does not update: <code>label</code> is not in the memo. That is the classic <code>v-memo</code> bug.</li>
<li>An empty array, <code>v-memo=&quot;[]&quot;</code>, is equivalent to <code>v-once</code>.</li>
<li><code>v-memo</code> is <strong>not supported in Vapor mode</strong> (Chapter 8).</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> before reaching for <code>v-memo</code>, check whether the list re-renders for a reactivity reason — a computed that returns a new array every time, an inline object prop (Chapter 3), a deep watcher. Fixing the cause is cheaper and cannot go stale.</p>
</blockquote>

<h1 id="Chapter-8-—-Vapor-mode"><a href="#Chapter-8-—-Vapor-mode" class="headerlink" title="Chapter 8 — Vapor mode"></a>Chapter 8 — Vapor mode</h1>
<h2 id="What-it-is"><a href="#What-it-is" class="headerlink" title="What it is"></a>What it is</h2>
<p>Vapor mode is an alternative compilation target for SFCs. Instead of a render function that creates vnodes, the component compiles to code that builds the DOM once from an HTML template and then binds the dynamic parts to small reactive effects. There is no virtual DOM, no diff and no patch flags. The 3.6 release notes describe it as &quot;100% opt-in&quot;, supporting &quot;a subset of existing Vue APIs with mostly identical behavior&quot;, and report the same level of performance as Solid and Svelte 5 in third-party benchmarks.</p>

<p>Read it top to bottom:</p>
<ul>
<li><code>_template()</code> holds static HTML as a string; calling it clones a prepared DOM fragment. All static structure is created in one browser-native operation.</li>
<li><code>_child</code> / <code>_next</code> / <code>_txt</code> walk to the nodes that have bindings, once.</li>
<li>Dynamic bindings are wrapped in small <code>_renderEffect</code>s. Bindings on the same element share one: <code>&lt;span :class=&quot;cls&quot;&gt;{{ msg }}&lt;/span&gt;</code> compiles (rc.8) to a single effect that calls <code>_setClass(n0, cls.value)</code> and <code>_setText(x0, …)</code>. When <code>count</code> changes, only the button's effect runs and sets one text node. No component re-render happens.</li>
<li><code>v-for</code> becomes <code>_createFor</code> with a source getter, a per-item render function and a key function. List reconciliation still exists, but at the level of DOM blocks, not vnodes.</li>
<li>The component definition carries <code>__vapor: true</code>.</li>
</ul>
<p>This is the reactivity graph from Post 00 wired directly to the DOM, which is what signal-based frameworks such as Solid do. It also leans much harder on the reactivity core — many small effects instead of one per component — which is why the 3.6 work on that core (alien-signals) matters for Vapor.</p>

<h2 id="What-it-does-not-support"><a href="#What-it-does-not-support" class="headerlink" title="What it does not support"></a>What it does not support</h2>
<p>The rc notes list: the <strong>Options API</strong>, <code>getCurrentInstance()</code>, <code>v-memo</code>, component template refs that expose <code>$el</code>, <code>$props</code>, <code>$attrs</code> and similar instance properties, and <code>@vue:xxx</code> per-element lifecycle events. Custom directives have a different interface in Vapor (the binding value arrives as a reactive getter). Libraries that reach into component instances are the most likely to break.</p>
<h2 id="Status-September-2026"><a href="#Status-September-2026" class="headerlink" title="Status (September 2026)"></a>Status (September 2026)</h2>
<ul>
<li><strong>3.6.0-alpha.1</strong> (July 2025) introduced Vapor mode and the alien-signals reactivity refactor; at that point SSR hydration, async components, Transition, KeepAlive and Suspense were not yet supported.</li>
<li><strong>3.6.0-rc.1</strong> (July 2026) declared the intended Vapor feature set complete. The rc changelogs since then are mostly Vapor fixes, including hydration, KeepAlive, Transition and Suspense.</li>
<li>At the time of writing the latest is <strong>3.6.0-rc.8</strong>, and <code>latest</code> on npm is still 3.5.x.</li>
</ul>
<p>The rc notes recommend two uses for now: <strong>performance-sensitive parts of existing apps</strong>, and <strong>small new apps built entirely in Vapor mode</strong>. For an existing app, the interop plugin allows adopting it one hot component at a time and measuring.</p>

<h1 id="Chapter-9-—-A-compiler-aware-performance-checklist"><a href="#Chapter-9-—-A-compiler-aware-performance-checklist" class="headerlink" title="Chapter 9 — A compiler-aware performance checklist"></a>Chapter 9 — A compiler-aware performance checklist</h1>
<ol>
<li><strong>Keep props stable.</strong> No inline object or array literals as component props. Stable props let the <code>PROPS</code> check skip child updates (Chapter 3).</li>
<li><strong>Keep computed values stable.</strong> A computed that returns an equal primitive stops propagation; one that returns a fresh array does not (Post 00, Chapter 4).</li>
<li><strong>Use <code>shallowRef</code> for large lists</strong> you replace, and virtualise long lists (only render visible rows). No compiler optimisation beats not rendering.</li>
<li><strong>Always key <code>v-for</code></strong> with a data identity.</li>
<li><strong>Split big components</strong> where a small part updates often. A component is the unit of re-render in the VDOM model; a ticking clock inside a 2,000-node page component re-renders the page's block.</li>
<li><strong><code>v-show</code> for frequent toggles, <code>v-if</code> for rare ones.</strong> <code>v-show</code> keeps the subtree mounted and flips <code>display</code>; <code>v-if</code> unmounts and remounts.</li>
<li><strong><code>v-memo</code> only for measured hot lists</strong>, with a complete memo array.</li>
<li><strong>Build flags.</strong> Set <code>__VUE_OPTIONS_API__: false</code> if no component uses the Options API (smaller bundle). Keep <code>__VUE_PROD_DEVTOOLS__</code> and <code>__VUE_PROD_HYDRATION_MISMATCH_DETAILS__</code> false in production unless you need them.</li>
<li><strong>Measure.</strong> Vue DevTools' performance timeline and <code>app.config.performance = true</code> (development only: component init, compile, render and patch timings in the browser's performance panel) come before any of the above.</li>
<li><strong>Consider Vapor for a hot subtree</strong> once it is stable enough for your risk appetite: a live dashboard or a data grid is the best-case workload.</li>
</ol>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Decode-the-flags"><a href="#Exercise-1-—-Decode-the-flags" class="headerlink" title="Exercise 1 — Decode the flags"></a>Exercise 1 — Decode the flags</h2>
<p>What do <code>9 /* TEXT, PROPS */, [&quot;id&quot;]</code>, <code>16</code>, <code>512</code> and <code>-1</code> tell the runtime?</p>
<details>
<summary>Solution</summary>
<p><code>9</code> = TEXT (1) | PROPS (8): compare the text child and only the <code>id</code> prop. <code>16</code> = FULL_PROPS: dynamic keys, diff all props. <code>512</code> = NEED_PATCH: nothing prop-related changes, but the vnode has a ref, directive or vnode hook that must run. <code>-1</code> = CACHED: a static vnode from <code>_cache</code>, never diffed, skippable during hydration.</p>
</details>
<h2 id="Exercise-2-—-Why-does-the-child-re-render"><a href="#Exercise-2-—-Why-does-the-child-re-render" class="headerlink" title="Exercise 2 — Why does the child re-render?"></a>Exercise 2 — Why does the child re-render?</h2>
<p><code>&lt;UserCard :user=&quot;user&quot; :style-opts=&quot;{ compact: true }&quot; @select=&quot;onSelect&quot; /&gt;</code> re-renders every time the parent does, though <code>user</code> did not change. Why, and what is the fix?</p>
<details>
<summary>Solution</summary>
<p><code>style-opts</code> is an expression that builds a new object on every parent render, so the <code>PROPS</code> comparison always finds a change. Move <code>{ compact: true }</code> into a constant in <code>&lt;script setup&gt;</code>. <code>@select=&quot;onSelect&quot;</code> is not the problem: the compiler caches handlers.</p>
</details>
<h2 id="Exercise-3-—-Run-the-diff"><a href="#Exercise-3-—-Run-the-diff" class="headerlink" title="Exercise 3 — Run the diff"></a>Exercise 3 — Run the diff</h2>
<p>Old <code>[a, b, c, d]</code>, new <code>[d, a, b, c]</code>, all keyed. Which nodes move?</p>
<details>
<summary>Solution</summary>
<p>No common prefix (<code>a</code> vs <code>d</code>) and no common suffix (<code>d</code> vs <code>c</code>), so the whole list is the middle. Walking the <strong>old</strong> list: <code>a</code> → new index 1, <code>b</code> → 2, <code>c</code> → 3, then <code>d</code> → 0, which is smaller than the largest index seen (3), so <code>moved = true</code>. The map from new position to old index + 1 is <code>[4, 1, 2, 3]</code>; <code>getSequence</code> returns positions <code>[1, 2, 3]</code> (<code>a b c</code>). Only <code>d</code> is outside the LIS: one DOM move, to the front.</p>
</details>
<h2 id="Exercise-4-—-The-stale-memo"><a href="#Exercise-4-—-The-stale-memo" class="headerlink" title="Exercise 4 — The stale memo"></a>Exercise 4 — The stale memo</h2>
<p>A list uses <code>v-memo=&quot;[item.id === selectedId]&quot;</code> and renders <code>{{ item.label }}</code> and <code>{{ item.price }}</code>. After a price update over WebSocket, prices on screen stay old. Fix it two ways.</p>
<details>
<summary>Solution</summary>
<p>The memo does not include <code>price</code>, so memoised rows are reused. Either add it: <code>v-memo=&quot;[item.id === selectedId, item.price, item.label]&quot;</code>, or remove <code>v-memo</code> and fix the real re-render cause (for example a <code>shallowRef</code> list replaced immutably, so unchanged rows keep their identity).</p>
</details>
<h2 id="Exercise-5-—-Hoisting-vs-caching"><a href="#Exercise-5-—-Hoisting-vs-caching" class="headerlink" title="Exercise 5 — Hoisting vs caching"></a>Exercise 5 — Hoisting vs caching</h2>
<p>Your library generates thousands of short-lived component instances. Explain what 3.5's change from hoisted to cached static vnodes costs and what it buys.</p>
<details>
<summary>Solution</summary>
<p>Cost: each instance creates its static vnodes once on its first render (in 3.4 they were created once per module), so first render does a little more work and each instance holds its own <code>_cache</code> entries. Buys: no vnode, and therefore no <code>el</code> reference, is shared across instances, which removes a known source of retained detached DOM. Static props objects are still hoisted and the diff still skips cached nodes, so update performance is unchanged.</p>
</details>
<h2 id="Exercise-6-—-Vapor-adoption-plan"><a href="#Exercise-6-—-Vapor-adoption-plan" class="headerlink" title="Exercise 6 — Vapor adoption plan"></a>Exercise 6 — Vapor adoption plan</h2>
<p>A large Options API app has one slow real-time table. Outline how to try Vapor mode on it and what could block you.</p>
<details>
<summary>Solution</summary>
<p>Rewrite the table (and its row component) with <code>&lt;script setup vapor&gt;</code>, install <code>vaporInteropPlugin</code> on the existing <code>createApp()</code>, and measure. Blockers from the rc notes: any Options API inside the Vapor components, <code>getCurrentInstance()</code>, <code>v-memo</code>, parent code that reads <code>$el</code> or <code>$props</code> through a template ref to the table, <code>@vue:mounted</code>-style vnode events, and custom directives written for the VDOM interface. Keep everything outside the table on the VDOM runtime.</p>
</details>
