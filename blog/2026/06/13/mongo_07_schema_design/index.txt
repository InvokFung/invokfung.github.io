11:Tc173,<p>The biggest leap from SQL to MongoDB is the way you model data. There's no &quot;right&quot; normalisation — schema is chosen per access pattern. Get it right and a single document satisfies the hot read with one disk seek. Get it wrong and you're stitching together with <code>$lookup</code> on every page load. This post covers the canonical design patterns: <strong>embed vs reference</strong>, <strong>1:1 / 1:few / 1:many / many:many</strong>, plus the named patterns the MongoDB community has codified — <strong>Polymorphic, Bucket, Computed, Extended Reference, Attribute, Tree (4 variants), Outlier, Schema Versioning</strong>.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Decide between embedding and referencing for each relationship.</li>
<li>Recognise the <strong>canonical access patterns</strong> for 1:1, 1:few, 1:many, many:many.</li>
<li>Apply the named patterns: Polymorphic, Bucket, Computed, Extended Reference, Attribute, Tree, Outlier, Schema Versioning.</li>
<li>Store hierarchies four ways (parent ref / child ref / array of ancestors / materialised path).</li>
<li>Plan schema evolution without downtime.</li>
</ul>

<h1 id="Chapter-1-—-The-mental-shift"><a href="#Chapter-1-—-The-mental-shift" class="headerlink" title="Chapter 1 — The mental shift"></a>Chapter 1 — The mental shift</h1>
<p>SQL: design schema first, query later.<br>
MongoDB: <strong>start from the queries you want to run</strong>, design schema to make them efficient.</p>
<p>Two principles:</p>
<ol>
<li><strong>Data that's accessed together should live together.</strong> Embed it.</li>
<li><strong>Data that grows unboundedly or is shared across many parents should be separated.</strong> Reference it.</li>
</ol>
<p>That's it. The named patterns below are corollaries.</p>
<hr>
<h1 id="Chapter-2-—-Embed-vs-reference"><a href="#Chapter-2-—-Embed-vs-reference" class="headerlink" title="Chapter 2 — Embed vs reference"></a>Chapter 2 — Embed vs reference</h1>
<h2 id="Embed-sub-document-or-array"><a href="#Embed-sub-document-or-array" class="headerlink" title="Embed (sub-document or array)"></a>Embed (sub-document or array)</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="js"><span class="line">{</span><br><span class="line">  <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span>,</span><br><span class="line">  <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Ada&quot;</span>,</span><br><span class="line">  <span class="hljs-attr">address</span>: {                          <span class="hljs-comment">// embedded sub-document</span></span><br><span class="line">    <span class="hljs-attr">city</span>: <span class="hljs-string">&quot;London&quot;</span>,</span><br><span class="line">    <span class="hljs-attr">country</span>: <span class="hljs-string">&quot;UK&quot;</span></span><br><span class="line">  },</span><br><span class="line">  <span class="hljs-attr">emails</span>: [<span class="hljs-string">&quot;ada@x&quot;</span>, <span class="hljs-string">&quot;ada@y&quot;</span>]          <span class="hljs-comment">// embedded array</span></span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Pros:</strong></p>
<ul>
<li>One document fetch returns the whole thing.</li>
<li>Atomic writes across the whole document.</li>
<li>No joins.</li>
</ul>
<p><strong>Cons:</strong></p>
<ul>
<li>Duplication if the same sub-document is shared by many parents.</li>
<li>Document size cap: <strong>16 MB</strong>.</li>
<li>Updating a deeply nested value can be awkward.</li>
</ul>
<h2 id="Reference-foreign-key-style"><a href="#Reference-foreign-key-style" class="headerlink" title="Reference (foreign key style)"></a>Reference (foreign key style)</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// users</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Ada&quot;</span> }</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// orders</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;o1&quot;</span>, <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">items</span>: [...] }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Pros:</strong></p>
<ul>
<li>Each entity is the single source of truth.</li>
<li>No size limit (each is its own document).</li>
<li>Many parents can reference the same entity.</li>
</ul>
<p><strong>Cons:</strong></p>
<ul>
<li>Reads need a join (<code>$lookup</code> or two round-trips).</li>
<li>No atomic writes across the reference unless using transactions.</li>
</ul>

<td>Item updated often, on its own</td>
<td></td>
<td>✓</td>
</tr>
<tr>
<td>Items rarely change once written</td>
<td>✓</td>
<td></td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>Trick:</strong> when undecided, <strong>embed first</strong>. Schema migration from embedded to referenced is mechanical. The reverse usually requires re-engineering query paths. Embedding is the cheap default.</p>
</blockquote>

<h2 id="11-—-always-embed"><a href="#11-—-always-embed" class="headerlink" title="1:1 — always embed"></a>1:1 — always embed</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Ada&quot;</span>, <span class="hljs-attr">profile</span>: { <span class="hljs-attr">bio</span>: <span class="hljs-string">&quot;...&quot;</span>, <span class="hljs-attr">avatar</span>: <span class="hljs-string">&quot;...&quot;</span> } }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="1few-—-embed-bounded-array"><a href="#1few-—-embed-bounded-array" class="headerlink" title="1:few — embed (bounded array)"></a>1:few — embed (bounded array)</h2>
<p>A user's emails (≤ ~10), a product's color variants (≤ ~20).</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Ada&quot;</span>, <span class="hljs-attr">emails</span>: [<span class="hljs-string">&quot;ada@x&quot;</span>, <span class="hljs-string">&quot;ada@y&quot;</span>, <span class="hljs-string">&quot;ada@z&quot;</span>] }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="1many-—-embed-if-bounded-reference-if-not"><a href="#1many-—-embed-if-bounded-reference-if-not" class="headerlink" title="1:many — embed if bounded, reference if not"></a>1:many — embed if bounded, reference if not</h2>
<p>A blog post's comments (could be 1 or 10,000) → reference.<br>
A user's purchase history (could be 1 or 10,000) → reference (separate <code>orders</code> collection).<br>
A book's chapters (10-50 typically) → embed.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// reference: each comment its own doc</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;c1&quot;</span>, <span class="hljs-attr">post_id</span>: <span class="hljs-string">&quot;p1&quot;</span>, <span class="hljs-attr">author</span>: <span class="hljs-string">&quot;Bob&quot;</span>, <span class="hljs-attr">text</span>: <span class="hljs-string">&quot;...&quot;</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Manymany-—-usually-reference-both-ways"><a href="#Manymany-—-usually-reference-both-ways" class="headerlink" title="Many:many — usually reference both ways"></a>Many:many — usually reference both ways</h2>
<p>Users and tags: tags as separate documents; user has <code>tag_ids: [...]</code>; tag has <code>user_count: N</code> (denormalised count).</p>
<p>For small membership lists (a user's roles), embed the IDs in the user doc.</p>
<h2 id="1-to-squillions-—-reference-parent-on-the-child"><a href="#1-to-squillions-—-reference-parent-on-the-child" class="headerlink" title="&quot;1 to squillions&quot; — reference parent on the child"></a>&quot;1 to squillions&quot; — reference parent on the child</h2>
<p>A device with millions of telemetry events.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// device</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;d1&quot;</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;sensor-foo&quot;</span> }</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// readings — bucket pattern (Chapter 6) often beats raw 1-per-doc</span></span><br><span class="line">{ <span class="hljs-attr">device_id</span>: <span class="hljs-string">&quot;d1&quot;</span>, <span class="hljs-attr">at</span>: <span class="hljs-title class_">ISODate</span>(...), <span class="hljs-attr">temp</span>: <span class="hljs-number">23.4</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Never try to embed millions of children into the parent — the 16 MB cap kicks in.</p>

<h1 id="Chapter-4-—-Polymorphic-pattern"><a href="#Chapter-4-—-Polymorphic-pattern" class="headerlink" title="Chapter 4 — Polymorphic pattern"></a>Chapter 4 — Polymorphic pattern</h1>
<p>When documents in the same collection have <strong>different shapes</strong> (different fields per type):</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// products collection</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;p1&quot;</span>, <span class="hljs-attr">type</span>: <span class="hljs-string">&quot;book&quot;</span>,    <span class="hljs-attr">title</span>: <span class="hljs-string">&quot;...&quot;</span>, <span class="hljs-attr">isbn</span>: <span class="hljs-string">&quot;...&quot;</span>, <span class="hljs-attr">pages</span>: <span class="hljs-number">320</span> }</span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;p2&quot;</span>, <span class="hljs-attr">type</span>: <span class="hljs-string">&quot;shirt&quot;</span>,   <span class="hljs-attr">title</span>: <span class="hljs-string">&quot;...&quot;</span>, <span class="hljs-attr">size</span>: <span class="hljs-string">&quot;M&quot;</span>,   <span class="hljs-attr">colour</span>: <span class="hljs-string">&quot;red&quot;</span> }</span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;p3&quot;</span>, <span class="hljs-attr">type</span>: <span class="hljs-string">&quot;course&quot;</span>,  <span class="hljs-attr">title</span>: <span class="hljs-string">&quot;...&quot;</span>, <span class="hljs-attr">duration_hours</span>: <span class="hljs-number">12</span>, <span class="hljs-attr">instructor</span>: <span class="hljs-string">&quot;...&quot;</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Common base fields (<code>title</code>, <code>price</code>, <code>category</code>) + a discriminator (<code>type</code>) + type-specific fields. Index <code>type</code> for filtering.</p>
<p>When to use: catalogue with many product kinds; events with type-specific payloads; logs with varied formats.</p>
<p>In code, a switch on <code>type</code> decides how to render / process. Trade richer schema for fewer collections + simpler queries.</p>

<p>Instead of one document per event, group events into &quot;buckets&quot; of N (by time or count):</p>

<h1 id="Chapter-6-—-Computed-pattern"><a href="#Chapter-6-—-Computed-pattern" class="headerlink" title="Chapter 6 — Computed pattern"></a>Chapter 6 — Computed pattern</h1>
<p>Pre-compute aggregates and store them on the parent document — avoid repeating expensive <code>$group</code> aggregations on every read.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line">{</span><br><span class="line">  <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span>,</span><br><span class="line">  <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Ada&quot;</span>,</span><br><span class="line">  <span class="hljs-attr">order_count</span>: <span class="hljs-number">42</span>,            <span class="hljs-comment">// computed</span></span><br><span class="line">  <span class="hljs-attr">total_spent</span>: <span class="hljs-number">1234.50</span>,       <span class="hljs-comment">// computed</span></span><br><span class="line">  <span class="hljs-attr">last_order_at</span>: <span class="hljs-title class_">ISODate</span>(...) <span class="hljs-comment">// computed</span></span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Update via the same write that creates the related event (transaction or <code>bulkWrite</code>) or via change-stream-driven background updates.</p>
<p>Trade-off: write amplification for read speed. Worth it when the read is hot and the computation expensive.</p>

<h1 id="Chapter-7-—-Extended-Reference-pattern"><a href="#Chapter-7-—-Extended-Reference-pattern" class="headerlink" title="Chapter 7 — Extended Reference pattern"></a>Chapter 7 — Extended Reference pattern</h1>
<p>Reference an entity by ID <strong>plus</strong> duplicate a few stable fields on the referencing side — saves the join for the most common read.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// orders</span></span><br><span class="line">{</span><br><span class="line">  <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;o1&quot;</span>,</span><br><span class="line">  <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>,</span><br><span class="line">  <span class="hljs-attr">user_name</span>: <span class="hljs-string">&quot;Ada&quot;</span>,           <span class="hljs-comment">// duplicated from users</span></span><br><span class="line">  <span class="hljs-attr">user_email</span>: <span class="hljs-string">&quot;ada@x&quot;</span>,        <span class="hljs-comment">// duplicated</span></span><br><span class="line">  <span class="hljs-attr">items</span>: [...]</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Reads listing orders don't need to <code>$lookup</code> users for name + email. Drawback: if the user changes their name, orders show stale.</p>
<p>Use when:</p>
<ul>
<li>The denormalised fields rarely change.</li>
<li>Read frequency &gt;&gt; write frequency.</li>
<li>Stale data for hours/days is acceptable until a background job catches up.</li>
</ul>

<p>When documents have many similar fields you need to query over arbitrary subsets:</p>

<h1 id="Chapter-9-—-Tree-patterns-4-ways-to-store-hierarchies"><a href="#Chapter-9-—-Tree-patterns-4-ways-to-store-hierarchies" class="headerlink" title="Chapter 9 — Tree patterns (4 ways to store hierarchies)"></a>Chapter 9 — Tree patterns (4 ways to store hierarchies)</h1>
<p>Hierarchies (org charts, comment threads, categories) have four canonical storage shapes. Pick by access pattern.</p>
<h2 id="1-Parent-reference"><a href="#1-Parent-reference" class="headerlink" title="1. Parent reference"></a>1. Parent reference</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;c1&quot;</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Electronics&quot;</span> }</span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;c2&quot;</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Laptops&quot;</span>, <span class="hljs-attr">parent</span>: <span class="hljs-string">&quot;c1&quot;</span> }</span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;c3&quot;</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Gaming&quot;</span>,  <span class="hljs-attr">parent</span>: <span class="hljs-string">&quot;c2&quot;</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li>Write: simple.</li>
<li>Find children: <code>find({ parent: &quot;c1&quot; })</code> — easy.</li>
<li>Find ancestors / whole subtree: <code>$graphLookup</code> or recursion.</li>
</ul>
<p>Default for hierarchies you don't traverse deeply.</p>
<h2 id="2-Child-references"><a href="#2-Child-references" class="headerlink" title="2. Child references"></a>2. Child references</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;c1&quot;</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Electronics&quot;</span>, <span class="hljs-attr">children</span>: [<span class="hljs-string">&quot;c2&quot;</span>, <span class="hljs-string">&quot;c5&quot;</span>] }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li>Find children: read the array.</li>
<li>Find parent: <code>find({ children: &quot;c2&quot; })</code>.</li>
<li>Move a node: update old + new parent.</li>
</ul>
<p>Useful when children are bounded + you list them often.</p>
<h2 id="3-Array-of-ancestors"><a href="#3-Array-of-ancestors" class="headerlink" title="3. Array of ancestors"></a>3. Array of ancestors</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;c3&quot;</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Gaming&quot;</span>, <span class="hljs-attr">ancestors</span>: [<span class="hljs-string">&quot;c1&quot;</span>, <span class="hljs-string">&quot;c2&quot;</span>], <span class="hljs-attr">parent</span>: <span class="hljs-string">&quot;c2&quot;</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li>Find ancestors: read the array (no join).</li>
<li>Find subtree: <code>find({ ancestors: &quot;c1&quot; })</code> — instant.</li>
<li>Move a node: update ancestors of node + all descendants.</li>
</ul>
<p>Best when you query &quot;all descendants&quot; frequently.</p>
<h2 id="4-Materialised-path"><a href="#4-Materialised-path" class="headerlink" title="4. Materialised path"></a>4. Materialised path</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;c3&quot;</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Gaming&quot;</span>, <span class="hljs-attr">path</span>: <span class="hljs-string">&quot;,c1,c2,&quot;</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li>Find subtree: <code>find({ path: /^,c1,/ })</code>.</li>
<li>Find ancestors: split the string.</li>
<li>Move: rewrite paths for node + descendants.</li>
</ul>
<p>Compact; regex-prefix index works (Post 02).</p>

<p>Mix is fine — store parent ref <strong>and</strong> ancestors for both kinds of query.</p>
<hr>
<h1 id="Chapter-10-—-Outlier-pattern"><a href="#Chapter-10-—-Outlier-pattern" class="headerlink" title="Chapter 10 — Outlier pattern"></a>Chapter 10 — Outlier pattern</h1>
<p>A few documents in a collection are atypically large (a celebrity user with 50k followers; a viral post with 1M comments). Embedding fails the 16 MB limit for them.</p>
<p><strong>Mark them as outliers + store the overflow elsewhere</strong>:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// most users</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Ada&quot;</span>, <span class="hljs-attr">followers</span>: [<span class="hljs-string">&quot;u2&quot;</span>, <span class="hljs-string">&quot;u3&quot;</span>] }     <span class="hljs-comment">// small array embedded</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// celebrity</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-number">99</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Famous&quot;</span>, <span class="hljs-attr">has_overflow</span>: <span class="hljs-literal">true</span> }</span><br><span class="line"><span class="hljs-comment">// followers in a separate collection</span></span><br><span class="line">{ <span class="hljs-attr">user_id</span>: <span class="hljs-number">99</span>, <span class="hljs-attr">followers_batch</span>: [...], <span class="hljs-attr">batch_index</span>: <span class="hljs-number">0</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>App reads check <code>has_overflow</code> and fetch from the side collection if true.</p>
<p>Avoids pathological queries on average users while still scaling for outliers.</p>
<hr>
<h1 id="Chapter-11-—-Schema-versioning-pattern"><a href="#Chapter-11-—-Schema-versioning-pattern" class="headerlink" title="Chapter 11 — Schema versioning pattern"></a>Chapter 11 — Schema versioning pattern</h1>
<p>MongoDB schema is flexible — apps must handle multiple versions during migrations. Make the version explicit:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">_schema_v</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Ada&quot;</span>, <span class="hljs-attr">emails</span>: [<span class="hljs-string">&quot;ada@x&quot;</span>] }</span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-number">2</span>, <span class="hljs-attr">_schema_v</span>: <span class="hljs-number">2</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;Bob&quot;</span>, <span class="hljs-attr">contact</span>: { <span class="hljs-attr">emails</span>: [<span class="hljs-string">&quot;bob@x&quot;</span>], <span class="hljs-attr">phone</span>: <span class="hljs-string">&quot;...&quot;</span> } }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>App-level:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">function</span> <span class="hljs-title function_">getUserContact</span>(<span class="hljs-params">doc</span>) {</span><br><span class="line">  <span class="hljs-keyword">switch</span> (doc.<span class="hljs-property">_schema_v</span>) {</span><br><span class="line">    <span class="hljs-keyword">case</span> <span class="hljs-number">1</span>: <span class="hljs-keyword">return</span> { <span class="hljs-attr">emails</span>: doc.<span class="hljs-property">emails</span> };</span><br><span class="line">    <span class="hljs-keyword">case</span> <span class="hljs-number">2</span>: <span class="hljs-keyword">return</span> doc.<span class="hljs-property">contact</span>;</span><br><span class="line">  }</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Migrate documents lazily (on read or via a background job) — never block the system for a big-bang migration. When all docs are at v2, drop the v1 code path.</p>
<hr>
<h1 id="Chapter-12-—-Schema-validation-optional-but-recommended"><a href="#Chapter-12-—-Schema-validation-optional-but-recommended" class="headerlink" title="Chapter 12 — Schema validation (optional but recommended)"></a>Chapter 12 — Schema validation (optional but recommended)</h1>
<p>MongoDB doesn't require a schema, but you can enforce one with <code>$jsonSchema</code>:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-title function_">createCollection</span>(<span class="hljs-string">&quot;users&quot;</span>, {</span><br><span class="line">  <span class="hljs-attr">validator</span>: {</span><br><span class="line">    <span class="hljs-attr">$jsonSchema</span>: {</span><br><span class="line">      <span class="hljs-attr">bsonType</span>: <span class="hljs-string">&quot;object&quot;</span>,</span><br><span class="line">      <span class="hljs-attr">required</span>: [<span class="hljs-string">&quot;name&quot;</span>, <span class="hljs-string">&quot;email&quot;</span>],</span><br><span class="line">      <span class="hljs-attr">properties</span>: {</span><br><span class="line">        <span class="hljs-attr">name</span>:  { <span class="hljs-attr">bsonType</span>: <span <span class="hljs-attr">maximum</span>: <span class="hljs-number">150</span> }</span><br><span class="line">      }</span><br><span class="line">    }</span><br><span class="line">  },</span><br><span <p><code>moderate</code> validates new docs + updated existing docs but allows old docs through. Good for gradual rollout.</p>
<p>Mongoose (Post 17) adds schema enforcement in the application layer with richer types + defaults + middleware.</p>
<hr>
<h1 id="Chapter-13-—-Avoiding-pathological-growth"><a href="#Chapter-13-—-Avoiding-pathological-growth" class="headerlink" title="Chapter 13 — Avoiding pathological growth"></a>Chapter 13 — Avoiding pathological growth</h1>
<p><strong>Unbounded arrays</strong> are the single biggest schema pitfall:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// danger: comments grow forever, may exceed 16 MB</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;p1&quot;</span>, <span class="hljs-attr">title</span>: <span class="hljs-string">&quot;...&quot;</span>, <span class="hljs-attr">comments</span>: [<span class="hljs-comment">/* could be 1M elements */</span>] }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Symptoms: slow updates (CoW on the whole doc), index bloat, eventual 16 MB cap.</p>
<p><strong>Fixes</strong> in priority order:</p>
<ol>
<li>Cap the array — <code>$push: { items: { $each: [x], $slice: -100 } }</code> keeps last 100.</li>
<li>Move to a child collection with <code>parent_id</code>.</li>
<li>Use the bucket pattern (Chapter 5) or time-series collection.</li>
</ol>

<h1 id="Chapter-15-—-Common-pitfalls"><a href="#Chapter-15-—-Common-pitfalls" class="headerlink" title="Chapter 15 — Common pitfalls"></a>Chapter 15 — Common pitfalls</h1>
<table>
<thead>
<tr>
<th>Pitfall</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>Embed unbounded array</td>
<td>cap with <code>$slice</code> or move to child collection</td>
</tr>
<tr>
<td>Reference everything by default</td>
<td>embed when always read together</td>
</tr>
<tr>
<td>Forget to denormalise stable fields</td>
<td>extended reference pattern</td>
</tr>
<tr>
<td>Sub-document mutation requires fetching whole doc</td>
<td>OK; just plan for it</td>
</tr>
<tr>
<td>Cross-collection consistency</td>
<td>use transactions (Post 09) or accept eventual</td>
</tr>
<tr>
<td>Schema changes break old code</td>
<td>schema versioning pattern</td>
</tr>
<tr>
<td>All-cases-in-one collection (sparse fields)</td>
<td>OK if polymorphic with discriminator</td>
</tr>
<tr>
<td>16 MB doc cap hit</td>
<td>outlier pattern + side collection</td>
</tr>
</tbody>
</table>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Embed-vs-reference-quiz"><a href="#Exercise-1-—-Embed-vs-reference-quiz" class="headerlink" title="Exercise 1 — Embed vs reference quiz"></a>Exercise 1 — Embed vs reference quiz</h2>
<p>For each, pick embed or reference and justify:</p>
<p>a) Blog post + author name + author bio (rarely changes).<br>
b) Blog post + comments (unbounded, paginated separately).<br>
c) Order + line items (typically 1-20 per order).<br>
d) User + login history (years of logins).</p>
<details>
<summary>Answers</summary>
<p>a) Extended reference — duplicate name + author_id; bio on the author doc (rare reads).<br>
b) Reference (separate <code>comments</code> collection).<br>
c) Embed line items.<br>
d) Reference (<code>logins</code> collection with TTL).</p>
</details>
<h2 id="Exercise-2-—-Build-a-category-tree"><a href="#Exercise-2-—-Build-a-category-tree" class="headerlink" title="Exercise 2 — Build a category tree"></a>Exercise 2 — Build a category tree</h2>
<p>Choose any approach from Chapter 9. Insert a 3-level tree (Electronics → Laptops → Gaming). Query for &quot;all categories under Electronics&quot;.</p>
<h2 id="Exercise-3-—-Computed-pattern"><a href="#Exercise-3-—-Computed-pattern" class="headerlink" title="Exercise 3 — Computed pattern"></a>Exercise 3 — Computed pattern</h2>
<p>Add <code>order_count</code> + <code>total_spent</code> to each user. Use change streams (Post 12 preview) or a one-time <code>aggregate</code> + <code>$merge</code> to populate.</p>
<h2 id="Exercise-4-—-Outlier"><a href="#Exercise-4-—-Outlier" class="headerlink" title="Exercise 4 — Outlier"></a>Exercise 4 — Outlier</h2>
<p>In <code>users</code>, give one user a <code>followers</code> array of 100k IDs. Profile insert time + read time. Refactor as outlier pattern.</p>
<h2 id="Exercise-5-—-Schema-validation"><a href="#Exercise-5-—-Schema-validation" class="headerlink" title="Exercise 5 — Schema validation"></a>Exercise 5 — Schema validation</h2>
<p>Apply <code>$jsonSchema</code> validation to <code>users</code>: name (string, required), email (matches regex, required), age (int 0-150). Try to insert an invalid doc.</p>
<h2 id="Exercise-6-—-Schema-versioning"><a href="#Exercise-6-—-Schema-versioning" class="headerlink" title="Exercise 6 — Schema versioning"></a>Exercise 6 — Schema versioning</h2>
<p>Migrate the <code>users</code> collection: rename <code>email</code> to <code>contact.email</code>. Use <code>_schema_v: 2</code> to distinguish; write app code that handles both versions.</p>

<h1 id="Cheat-sheet"><a href="#Cheat-sheet" class="headerlink" title="Cheat-sheet"></a>Cheat-sheet</h1>
<table>
<thead>
<tr>
<th>Pattern</th>
<th>When</th>
</tr>
</thead>
<tbody>
<tr>
<td>Embed</td>
<td>always read together; small + bounded</td>
</tr>
<tr>
<td>Reference</td>
<td>unbounded / shared / independent</td>
</tr>
<tr>
<td>Polymorphic</td>
<td>many types in one collection + discriminator field</td>
</tr>
<tr>
<td>Bucket</td>
<td>time-series before TSC; high-volume small events</td>
</tr>
<tr>
<td>Computed</td>
<td>pre-aggregate hot read on parent</td>
</tr>
<tr>
<td>Extended Reference</td>
<td>duplicate stable fields to skip join</td>
</tr>
<tr>
<td>Attribute</td>
<td>many sparse fields → array of <code>{k, v, unit}</code></td>
</tr>
<tr>
<td>Tree: parent ref</td>
<td>default; cheap writes</td>
</tr>
<tr>
<td>Tree: ancestors array</td>
<td>subtree queries</td>
</tr>
<tr>
<td>Tree: materialised path</td>
<td>small + regex-prefix friendly</td>
</tr>
<tr>
<td>Outlier</td>
<td>a few docs much larger than rest</td>
</tr>
<tr>
<td>Schema versioning</td>
<td>track <code>_schema_v</code> per doc; migrate lazily</td>
</tr>
<tr>
<td>Validation</td>
<td><code>$jsonSchema</code> in <code>createCollection</code></td>
</tr>
<tr>
<td>Default</td>
<td>embed first, refactor later if needed</td>
</tr>
<tr>
<td>16 MB cap</td>
<td>hard limit per document</td>
</tr>
<tr>
<td>Unbounded array</td>
<td>always cap or move out</td>
</tr>
