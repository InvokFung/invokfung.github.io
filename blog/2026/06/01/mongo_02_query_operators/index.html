MongoDB Course — 02 · Query Operators, Projections, Range Pagination

Created2026-06-01|Updated2026-06-01|Database > MongoDB
|Post View:

The CRUD operations from Post 01 take a filter as the first argument. The filter is where MongoDB's query expressiveness lives — comparison, logical, element-existence, array, regex, full-text, and geospatial operators all compose into one JSON-like predicate. This post covers every operator family, projection extras ($elemMatch, $slice, $), the right sort/limit/skip discipline, and the range pagination pattern that scales to millions of rows where .skip() collapses.

Series map: 00 Foundations → 01 CRUD → 02 Query Operators (this post) → 03 Indexes → 04 Query Optimization → 05 Aggregation Basics → … → 17 Drivers & Case Studies.

Learning Outcome

  • Use every comparison operator: $eq, $ne, $gt, $gte, $lt, $lte, $in, $nin.
  • Combine with logical operators: $and, $or, $nor, $not.
  • Use element operators: $exists, $type.
  • Match arrays correctly: $all, $elemMatch, $size.
  • Use $regex, $text, and $expr for advanced predicates.
  • Use projection extras: $elemMatch, $slice, the positional $.
  • Paginate with range queries instead of .skip() at scale.

Chapter 1 — Comparison operators

Operator Meaning
$eq equals
$ne not equals
$gt / $gte greater than / or equal
$lt / $lte less than / or equal
$in value in array of options
$nin value NOT in array

Equality on arrays

Subtle and important. The first form is "contains"; the second is "exactly equals this array". Use $all (Chapter 4) for "contains all of".

Operator Form

$or { $or: [ filterA, filterB ] }
$nor { $nor: [ filterA, filterB ] } (none match)
$not { field: { $not: { $gt: 10 } } } (negate a sub-expression)

Chapter 5 — Regex

$options flag Meaning
i case-insensitive
m multiline ^ / $
s . matches newlines
x ignore whitespace + allow # comments in pattern

Index use

A left-anchored regex (/^Ad/) can use a B-tree index on the field. Anything else does a scan within the index range or a full collection scan.

For substring + fuzzy + multi-language matching, prefer text indexes (next) or Atlas Search (Post 16).

Chapter 6 — Text search (built-in)

A text index enables $text queries:

Limits:

  • One text index per collection.
  • No phrase scoring nuance, no language-aware stemming beyond a basic set.
  • No autocomplete / fuzzy out of the box.

For serious search → Atlas Search (Lucene-based, faceted, autocomplete, fuzzy, multi-language) — Post 16.

Chapter 10 — Sort, limit, skip — and what doesn't scale

For small offsets this is fine. Cost of .skip(N): server scans N + limit documents in sort order, then discards the N. For N = 10,000 on a million-row collection that's painful even with an index.

Range pagination — the production pattern

Sort by a unique-enough field (often _id or a timestamp). Use the last seen value as a cursor for the next page.

Always O(limit) per page — independent of how deep into the list you've gone.

For non-unique sort keys (multiple rows with the same at), tiebreak on _id:

With a compound index on { at: -1, _id: -1 }, this stays O(limit).

Trick: any "Load more" / infinite-scroll UI must use range pagination. Server-side render-time pagination (offset for SEO) tolerates .skip() only up to a few hundred items.

Chapter 11 — Hint, comment, maxTimeMS

comment surfaces in db.currentOp() + the slow-query profiler — invaluable for tracking which app code issued a given query in production.

maxTimeMS is a safety net against runaway queries. Always set it in user-facing paths.

Chapter 12 — Distinct, count

distinct returns an array (max 16 MB BSON). For huge distinct sets, use the aggregation $group (Post 05).

Chapter 13 — Common pitfalls

Symptom Cause Fix
find({ tags: ["a"] }) returns nothing exact-array match use tags: "a" (contains) or $all: ["a"]
find slow on large collection no index Post 03
Multi-condition array filter matches wrong docs conditions applied independently use $elemMatch
Regex full-scan not left-anchored anchor /^…/ or use text/Atlas Search
.skip(50000) painfully slow offset cost range pagination
$or slow despite indexes each branch needs its own index create one index per branch
find returns sub-document with full fields no projection always project for big docs
App appears to ignore some results iterating cursor twice re-issue query or .toArray() once

Cheat-sheet

What How
Equals { field: value }
Range { field: { $gt: a, $lte: b } }
One of { field: { $in: [a, b] } }
Multi-cond OR { $or: [{ a: 1 }, { b: 2 }] }
Field present { field: { $exists: true } }
Array contains x { tags: "x" }
Array contains all { tags: { $all: ["x", "y"] } }
Array elem multi-cond { arr: { $elemMatch: { a: 1, b: { $gt: 2 } } } }
Array size N { arr: { $size: N } }
Regex (anchored, indexable) { s: /^prefix/ }
Cross-field compare { $expr: { $gt: ["$a", "$b"] } }
Project include { name: 1, email: 1, _id: 0 }
Project array slice { arr: { $slice: 5 } }
Project matched array elem { "arr.$": 1 } (with matched filter)
Pagination at scale range (< lastSeen) not .skip()
Force index .hint({ index })
Tag for profiler .comment("...")
Timeout safety .maxTimeMS(500)
Distinct db.c.distinct("field", filter?)
