MongoDB Course ??26 · OpenTelemetry Observability ??Traces, Metrics, Logs, Correlation

Created2026-06-01|Updated2026-06-01|Database > MongoDB
|Post View:

When a request is slow, "is it Mongo?" is the question that wastes the most production time. OpenTelemetry (OTel) makes the answer obvious ??every Mongo operation becomes a span attached to the request trace, with query shape, duration, target collection, and the surrounding service spans on the same timeline. Plus metrics (Mongo + driver pool + service) + logs (correlated by trace ID). This post covers wiring OTel into Node + Python services using the MongoDB drivers, picking a backend (Tempo / Datadog / Honeycomb / Atlas), instrumenting custom spans, and the dashboards + alerts worth building.

Series map: 24 Kafka + Debezium ??25 Testing ??26 OpenTelemetry (this post) ??27 Geo ??28 Time-series extreme ??29 K8s + mongosync + cost.

Learning Outcome

  • Wire OpenTelemetry into Node + Python services.
  • Auto-instrument the MongoDB driver (spans per operation).
  • Add custom spans + attributes for app-specific context.
  • Export traces to OTLP collector ??backend (Tempo / Datadog / Honeycomb / SigNoz / etc.).
  • Correlate Mongo slow-query log with trace IDs.
  • Pick the metrics + alerts that catch real production problems.

Chapter 1 ??The three signals

  • Traces ??per-request span tree. The "why is this endpoint slow?" answer.
  • Metrics ??aggregated counters / histograms. The "is the system healthy?" answer.
  • Logs ??discrete events. The "what exactly happened?" answer.

OTel unifies them with shared resource attributes (service.name, service.version) and trace context. A log line emitted inside a request carries the trace ID; click the trace ??see logs from every span.

For MongoDB specifically:

  • Each Mongo operation = a span (auto-instrumented). Includes operation name (find, aggregate), namespace (shop.orders), command summary, duration.
  • Driver pool metrics (connections active / idle / wait time).
  • Server-side: ship slow-query log to logs backend; correlate by comment field.

  • mongodb driver ??every command becomes a span.
  • mongoose ??additional spans for find / save / etc.
  • pg, mysql2, redis ??for polyglot services.

Chapter 4 ??Backend choice

Backend Hosted / Self Notes
Tempo + Grafana self-hosted OSS, scales, Grafana ecosystem
Jaeger self-hosted OSS classic; simpler than Tempo
Datadog hosted enterprise-grade, expensive
Honeycomb hosted strong query model, generous free tier
New Relic hosted broad APM
SigNoz self / hosted OSS-first, OTel native
Atlas hosted (Mongo Inc.) Atlas has its own performance + query insights ??pair, don't replace
AWS X-Ray hosted AWS native; OTel exporter exists

OpenTelemetry's value: write instrumentation once, swap backend by changing exporter URL. No vendor lock.

For new projects in 2026, Tempo + Grafana (self-hosted) or Honeycomb (hosted) are common picks.

Chapter 5 ??OTel Collector

The OTel Collector is a separate process (one per host or one per cluster) that receives OTLP from your services + exports to one or more backends. Decouples app from backend, allows sampling / filtering / batching centrally.

Apps point at the collector; collector handles fan-out. Easy to add a second backend, swap, or test.

Chapter 6 ??Metrics worth tracking

App-level (from your service):

  • request rate per endpoint
  • latency histogram per endpoint (p50 / p95 / p99)
  • error rate per endpoint
  • queue depth if you have a worker

MongoDB driver-side (auto-collected by recent OTel instrumentations):

  • command duration histogram (per operation, per collection)
  • connection pool ??connections.in_use, connections.idle, connections.wait_time_ms

MongoDB server-side (via Atlas metrics / Prometheus exporter on self-hosted):

  • ops per second (insert/query/update/delete)
  • connection count
  • replication lag
  • oplog window
  • cache hit ratio
  • ticket usage
  • queue depth

Alert on:

Metric Threshold
p99 latency on a key endpoint > 500 ms for 5 min
5xx error rate > 1 % for 5 min
Mongo command p99 > 200 ms for 10 min
Connection pool wait any > 0 sustained
Replication lag > 60 s
Atlas tier connection count > 80 % limit
OpsManager FTDC cursorTimeoutMs spikes

Chapter 7 ??Correlating with the slow-query log

Production trick: tag every query with the trace ID.

The query lands in the slow-query log (Post 14) with the trace ID. Atlas Query Insights surfaces both. Click a slow query ??search your traces backend for that ID ??see the full request context.

Bidirectional debugging:

  • Slow trace? ??drill into Mongo span ??see full command + duration.
  • Slow query in Atlas? ??look up the trace ID in your tracing backend ??see who called it + with what request.

Chapter 8 ??Sampling ??keep cost in check

Sending every span to a backend costs money + storage. Sample:

  • Head sampling: probability decision at the start of each trace (e.g., 10 %). Cheap, simple, loses interesting slow traces randomly.
  • Tail sampling (in the Collector): all spans buffered briefly; sample by outcome ??keep all errors + slow + a small % of normal. Cheaper + smarter.
  • Always sample errors + traces from /admin endpoints.

Hosted backends (Datadog, Honeycomb) have their own sampling controls.

Chapter 9 ??Logs correlated with traces

Every log line carries the current trace ID. Ship to Loki / Elasticsearch / Datadog. From a slow trace ??search logs for that trace_id ??see what the code was doing + any warnings.

OTel logs API (@opentelemetry/api-logs) is GA in 2026 ??even cleaner than Pino's trace fields. Pick whichever your stack uses.

Chapter 10 ??Atlas-specific signals

Atlas surfaces native:

  • Performance Advisor ??index suggestions from real slow queries.
  • Query Insights ??slow query shapes grouped + sampled.
  • Real-Time Performance Panel ??live ops + metrics.
  • Alerts ??configurable on every metric.
  • Cluster events log ??failovers, config changes.

Pair with OTel: app traces on your tracing backend; cluster-level metrics + slow queries on Atlas. Trace ID in query comment ties them together.

Atlas + Datadog integration ships pre-built dashboards if Datadog is your tracing backend ??saves dashboard-building time.

Chapter 11 ??Common pitfalls

Pitfall Cause Fix
Spans missing telemetry init AFTER app code starts init telemetry first
db.statement leaks sensitive data full command logged disable enhancedDatabaseReporting or scrub attributes
Trace context lost across setImmediate / queue manual async handoff loses context use context.with(ctx, fn)
Backend bill spike sampling 100 % at high QPS head + tail sample
Logs don't carry trace ID logger not enriched inject trace ID per log call
Slow query log + traces don't tie up no comment with trace ID add it on every query
Driver pool metric absent instrumentation version old upgrade
Cross-service trace breaks propagation header missing use auto-instrumented HTTP clients
OTel performance overhead always-on with no batching BatchSpanProcessor + reasonable export interval

Practice Exercises

Exercise 1 ??Hello OTel

In a Node or Python service, install OTel + run a local Jaeger / Tempo + see your first trace.

Exercise 2 ??Auto-instrument Mongo

Confirm every Mongo operation appears as its own span attached to your request trace.

Exercise 3 ??Custom span

Wrap a business operation (placeOrder) with a custom span + attributes. Verify in the trace UI.

Exercise 4 ??Trace ID in queries

Add a .comment(trace=${traceId}) to every Mongo query. Make a slow query; find it via Atlas slow-query log; follow the trace ID back to the trace.

Exercise 5 ??Sampling

Set head sampling to 10 %. Verify spans drop proportionally. Switch to tail sampling in the Collector keeping 100 % of errors.

Exercise 6 ??Logs correlation

Add Pino with trace ID enrichment. Confirm a log line written inside a request carries the right trace_id.
