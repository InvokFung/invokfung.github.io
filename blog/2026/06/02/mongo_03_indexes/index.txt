11:Ta489,<p>An index is a B-tree (or specialised structure) on one or more fields that lets MongoDB find documents without scanning the whole collection. Indexes turn a 60-second query into a 5-millisecond one — and turn an undertuned cluster into a poorly-running mess if used wrong (too many, too wide, wrong order). This post covers every index type, the <strong>ESR rule</strong> (Equality, Sort, Range) for compound-index ordering, partial / sparse / TTL / wildcard / hashed variants, index intersection, <strong>covered queries</strong>, and the build options (<code>background</code>, <code>unique</code>, <code>collation</code>).</p>
<blockquote>
<p>Series map: 00 Foundations → 01 CRUD → 02 Query Operators → <strong>03 Indexes</strong> (this post) → 04 Query Optimization → 05 Aggregation Basics → … → 17 Drivers &amp; Case Studies.</p>
</blockquote>

<h1 id="Chapter-1-—-Index-basics"><a href="#Chapter-1-—-Index-basics" class="headerlink" title="Chapter 1 — Index basics"></a>Chapter 1 — Index basics</h1>
<p>Every MongoDB collection has at least one index — on <code>_id</code> (unique, auto-created, can't drop). All others are user-created.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">email</span>: <span class="hljs-number">1</span> })          <span class="hljs-comment">// ascending B-tree</span></span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">created_at</span>: -<span class="hljs-number">1</span> })     <span class="hljs-comment">// descending</span></span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">getIndexes</span>()                        <span class="hljs-comment">// list</span></span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">dropIndex</span>(<span class="hljs-string">&quot;email_1&quot;</span>)                <span class="hljs-comment">// by name</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Naming: auto-generated as <code>&lt;field&gt;_&lt;dir&gt;</code> joined by <code>_</code>. Use <code>{ name: &quot;my_idx&quot; }</code> option for custom.</p>
<h2 id="Cost-trade-off"><a href="#Cost-trade-off" class="headerlink" title="Cost trade-off"></a>Cost trade-off</h2>
<ul>
<li>Indexes <strong>speed reads</strong> that filter / sort / project on indexed fields.</li>
<li>Indexes <strong>slow writes</strong> — every insert / update / delete must update every relevant index.</li>
<li>Indexes <strong>use RAM</strong> — frequently accessed parts of indexes must fit in the WiredTiger cache for speed (Post 15).</li>
<li>Indexes <strong>use disk</strong> — typically 10-30% of collection data size each.</li>
</ul>
<p>Rule: index for the <strong>queries you actually run</strong>, drop indexes never used (Post 04 covers <code>$indexStats</code> to find unused).</p>

<h1 id="Chapter-2-—-Single-field-index"><a href="#Chapter-2-—-Single-field-index" class="headerlink" title="Chapter 2 — Single-field index"></a>Chapter 2 — Single-field index</h1>
<p>The simplest:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">email</span>: <span class="hljs-number">1</span> })</span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">email</span>: <span class="hljs-string">&quot;ada@x&quot;</span> })           <span class="hljs-comment">// uses the index — O(log n)</span></span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">email</span>: <span class="hljs-regexp">/^ad/</span> })             <span class="hljs-comment">// uses the index (left-anchored regex)</span></span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">email</span>: <span class="hljs-regexp">/ad/</span> })              <span class="hljs-comment">// can&#x27;t use the index (no left anchor)</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Direction (<code>1</code> vs <code>-1</code>) doesn't matter for a single-field index — the B-tree can be walked either way. It matters for <strong>compound</strong> indexes when sorting on multiple fields.</p>
<hr>
<h1 id="Chapter-3-—-Compound-index-the-ESR-rule"><a href="#Chapter-3-—-Compound-index-the-ESR-rule" class="headerlink" title="Chapter 3 — Compound index + the ESR rule"></a>Chapter 3 — Compound index + the ESR rule</h1>
<p>A compound index is on multiple fields:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">status</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">at</span>: -<span class="hljs-number">1</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The order of fields in the index matters enormously. The <strong>ESR rule</strong>:</p>
<blockquote>
<p><strong>E</strong> — Equality fields first.<br>
<strong>S</strong> — Sort fields second.<br>
<strong>R</strong> — Range fields last.</p>
</blockquote>
<p>Why: B-trees can serve range scans only on the <strong>trailing</strong> indexed prefix once equality fields have been matched. Out-of-order indexes do partial work then full scans.</p>
<h2 id="Example"><a href="#Example" class="headerlink" title="Example"></a>Example</h2>
<p>Query: &quot;Most recent paid orders for user 1, sorted desc by date.&quot;</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">status</span>: <span class="hljs-string">&quot;paid&quot;</span> }).<span class="hljs-title function_">sort</span>({ <span class="hljs-attr">at</span>: -<span class="hljs-number">1</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Best index:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">status</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">at</span>: -<span class="hljs-number">1</span> })</span><br><span class="line"><span class="hljs-comment">//                       ^^^^^^^^^^^ equality first ^^^^ sort/range last</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The index serves:</p>
<ul>
<li><code>find({ user_id: 1 })</code> — uses prefix.</li>
<li><code>find({ user_id: 1, status: &quot;paid&quot; })</code> — uses prefix.</li>
<li><code>find({ user_id: 1 }).sort({ status: 1 })</code> — <code>status</code> comes right after the equality field, so the index order is already the sort order.</li>
<li><code>find({ user_id: 1, status: &quot;paid&quot;, at: { $gte: D } }).sort({ at: -1 })</code> — full use.</li>
</ul>
<p>Doesn't serve:</p>
<ul>
<li><code>find({ status: &quot;paid&quot; })</code> — <code>user_id</code> is the prefix; can't skip it.</li>
<li><code>find({ user_id: 1 }).sort({ at: -1 })</code> — the sort. <code>status</code> sits between <code>user_id</code> and <code>at</code> and is not in the filter, so the index finds the rows but MongoDB must still sort them in memory. Add <code>status</code> to the filter, or create <code>{ user_id: 1, at: -1 }</code>.</li>
</ul>
<h2 id="Prefix-rule"><a href="#Prefix-rule" class="headerlink" title="Prefix rule"></a>Prefix rule</h2>
<p>A compound index <code>{ a: 1, b: 1, c: 1 }</code> can serve:</p>
<ul>
<li><code>{ a }</code></li>
<li><code>{ a, b }</code></li>
<li><code>{ a, b, c }</code></li>
</ul>
<p>But not:</p>
<ul>
<li><code>{ b }</code> alone — <code>a</code> is the required prefix.</li>
</ul>
<p><strong>Trick:</strong> if you frequently query by <code>b</code> alone, you need a separate index <code>{ b: 1 }</code>. Don't try to make one mega-index do everything.</p>
<p><img src="/blog/assets/mongo/diagram_03_esr_rule.svg" alt="The ESR rule: a query mapped onto a compound index as equality, equality, sort, with example keys and the prefix rule"></p>
<h2 id="Direction-matters-for-sort"><a href="#Direction-matters-for-sort" class="headerlink" title="Direction matters for sort"></a>Direction matters for sort</h2>
<p>Index <code>{ at: 1, user_id: 1 }</code>:</p>
<ul>
<li><code>.sort({ at: 1, user_id: 1 })</code> — uses it directly.</li>
<li><code>.sort({ at: -1, user_id: -1 })</code> — uses it in <strong>reverse</strong> scan (also OK).</li>
<li><code>.sort({ at: 1, user_id: -1 })</code> — <strong>can't</strong> use it (mixed direction).</li>
</ul>
<p>Build the index to match your most common sort direction.</p>

<p>When indexed field is an array, MongoDB creates one index entry <strong>per array element</strong>. This is called a <strong>multikey index</strong> — automatic, no special syntax.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">tags</span>: <span class="hljs-number">1</span> })</span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">tags</span>: <span class="hljs-string">&quot;math&quot;</span> })             <span class="hljs-comment">// matches if &quot;math&quot; in array</span></span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">tags</span>: { <span class="hljs-attr">$all</span>: [<span class="hljs-string">&quot;math&quot;</span>, <span class="hljs-string">&quot;eng&quot;</span>] } })   <span class="hljs-comment">// can use the index</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">phone</span>: <span class="hljs-number">1</span> }, { <span class="hljs-attr">sparse</span>: <span class="hljs-literal">true</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-11-—-TTL-index-—-auto-delete-after-N-seconds"><a href="#Chapter-11-—-TTL-index-—-auto-delete-after-N-seconds" class="headerlink" title="Chapter 11 — TTL index — auto-delete after N seconds"></a>Chapter 11 — TTL index — auto-delete after N seconds</h1>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">sessions</span>.<span class="hljs-title function_">createIndex</span>(</span><br><span class="line">  { <span class="hljs-attr">last_active_at</span>: <span class="hljs-number">1</span> },</span><br><span class="line">  { <span class="hljs-attr">expireAfterSeconds</span>: <span class="hljs-number">3600</span> }     <span class="hljs-comment">// expire 1 hour after last_active_at</span></span><br><span class="line">)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A background thread deletes documents whose indexed date is older than <code>expireAfterSeconds</code> ago. Runs roughly every 60 s — TTL is approximate, not exact.</p>
<p>Field must be a <code>Date</code> (or array of Dates → uses earliest).</p>
<p>Common uses:</p>
<ul>
<li>Sessions, OTP codes, password-reset tokens.</li>
<li>Short-term caches.</li>
<li>Rate-limit counters.</li>
</ul>
<p>To expire at a specific instant: store the desired expiry timestamp directly, set <code>expireAfterSeconds: 0</code>:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">coupons</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">expires_at</span>: <span class="hljs-number">1</span> }, { <span class="hljs-attr">expireAfterSeconds</span>: <span class="hljs-number">0</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> TTL deletes generate write load + replication traffic — a large TTL cleanup spike can saturate a small instance.</p>
</blockquote>

<h1 id="Chapter-12-—-Wildcard-index-—-index-unknown-fields"><a href="#Chapter-12-—-Wildcard-index-—-index-unknown-fields" class="headerlink" title="Chapter 12 — Wildcard index — index unknown fields"></a>Chapter 12 — Wildcard index — index unknown fields</h1>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">docs</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-string">&quot;$**&quot;</span>: <span class="hljs-number">1</span> })                          <span class="hljs-comment">// every field</span></span><br><span class="line">db.<span class="hljs-property">docs</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-string">&quot;meta.$**&quot;</span>: <span class="hljs-number">1</span> })                     <span class="hljs-comment">// every subfield of meta</span></span><br><span class="line">db.<span class="hljs-property">docs</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-string">&quot;$**&quot;</span>: <span class="hljs-number">1</span> }, { <span class="hljs-attr">wildcardProjection</span>: { <span class="hljs-attr">name</span>: <span class="hljs-number">0</span> } })  <span class="hljs-comment">// exclude</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-13-—-Covered-queries"><a href="#Chapter-13-—-Covered-queries" class="headerlink" title="Chapter 13 — Covered queries"></a>Chapter 13 — Covered queries</h1>
<p>A query is <strong>covered</strong> when:</p>
<ol>
<li>Every queried field is in an index.</li>
<li>Every projected field is in the same index.</li>
<li>Query doesn't return <code>_id</code> unless <code>_id</code> is in the index.</li>
</ol>
<p>Covered queries return results <strong>straight from the index</strong> — no document fetch — extremely fast.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">email</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">name</span>: <span class="hljs-number">1</span> })</span><br><span class="line"> </span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">find</span>(</span><br><span class="line">  { <span class="hljs-attr">email</span>: <span class="hljs-string">&quot;ada@x&quot;</span> },</span><br><span class="line">  { <span class="hljs-attr">email</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">name</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">_id</span>: <span class="hljs-number">0</span> }    <span class="hljs-comment">// no _id, only indexed fields</span></span><br><span class="line">)</span><br><span class="line"><span class="hljs-comment">// covered query — no document fetch</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>explain()</code> (Post 04) shows <code>IXSCAN</code> with no following <code>FETCH</code> stage when a query is covered.</p>

<h1 id="Chapter-14-—-Index-intersection-use-sparingly"><a href="#Chapter-14-—-Index-intersection-use-sparingly" class="headerlink" title="Chapter 14 — Index intersection (use sparingly)"></a>Chapter 14 — Index intersection (use sparingly)</h1>
<p>MongoDB can intersect two single-field indexes to satisfy a multi-field query, but it's usually slower than a single compound index that matches the query.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// Two indexes</span></span><br><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span> })</span><br><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">status</span>: <span class="hljs-number">1</span> })</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// Query</span></span><br><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">status</span>: <span class="hljs-string">&quot;paid&quot;</span> })</span><br><span class="line"><span class="hljs-comment">// May use intersection — typically slower than a compound { user_id: 1, status: 1 }</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Rule: design <strong>compound indexes for the queries you run</strong>, not single-field per-column indexes.</p>

<h1 id="Chapter-15-—-Build-options"><a href="#Chapter-15-—-Build-options" class="headerlink" title="Chapter 15 — Build options"></a>Chapter 15 — Build options</h1>
<h2 id="Build-in-background-50-always"><a href="#Build-in-background-50-always" class="headerlink" title="Build in background (5.0+: always)"></a>Build in background (5.0+: always)</h2>
<p>Index builds since 5.0 use a hybrid foreground/background protocol that doesn't block writes. No special flag needed. (Older versions used <code>{ background: true }</code> — still accepted, no-op.)</p>
<h2 id="Collation-—-case-locale-aware"><a href="#Collation-—-case-locale-aware" class="headerlink" title="Collation — case + locale-aware"></a>Collation — case + locale-aware</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">createIndex</span>(</span><br><span class="line">  { <span class="hljs-attr">name</span>: <span class="hljs-number">1</span> },</span><br><span class="line">  { <span class="hljs-attr">collation</span>: { <span class="hljs-attr">locale</span>: <span class="hljs-string">&quot;en&quot;</span>, <span class="hljs-attr">strength</span>: <span class="hljs-number">2</span> } }     <span class="hljs-comment">// case-insensitive</span></span><br><span class="line">)</span><br><span class="line"> </span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;ada&quot;</span> }).<span class="hljs-title function_">collation</span>({ <span class="hljs-attr">locale</span>: <span class="hljs-string">&quot;en&quot;</span>, <span class="hljs-attr">strength</span>: <span class="hljs-number">2</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">hideIndex</span>(<span class="hljs-string">&quot;email_1&quot;</span>)            <span class="hljs-comment">// index still maintained but not used by planner</span></span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">unhideIndex</span>(<span class="hljs-string">&quot;email_1&quot;</span>)</span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">dropIndex</span>(<span class="hljs-string">&quot;email_1&quot;</span>)            <span class="hljs-comment">// permanent</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Safe pattern for &quot;is this index needed?&quot;: hide for a week, observe query performance, drop if no regression.</p>

<h1 id="Chapter-16-—-Production-rules-of-thumb"><a href="#Chapter-16-—-Production-rules-of-thumb" class="headerlink" title="Chapter 16 — Production rules of thumb"></a>Chapter 16 — Production rules of thumb</h1>
<ol>
<li><strong>Index every field used in a frequent filter, sort, or join.</strong> Not more.</li>
<li><strong>Compound indexes follow ESR.</strong></li>
<li><strong>Sort direction in the index matches your most common sort.</strong></li>
<li><strong>Use partial indexes</strong> to shrink indexes for filtered subsets (active users, open tickets).</li>
<li><strong>Use TTL</strong> for inherently temporary data.</li>
<li><strong>Index size + frequently-accessed entries should fit in RAM</strong> — Post 15.</li>
<li><strong>Drop unused indexes</strong> — <code>$indexStats</code> shows usage (Post 04).</li>
<li><strong>Build new indexes in off-peak windows</strong> for large collections, even with hybrid background builds — backfill is I/O heavy.</li>
<li><strong>Don't index every field &quot;just in case&quot;</strong> — write amplification + RAM waste.</li>
<li><strong>Test with <code>explain()</code></strong> before shipping any new query — Post 04.</li>
</ol>

<p>Given query <code>find({ user_id, status: &quot;paid&quot; }).sort({ at: -1 })</code>, design the compound index. Explain why each field is in its position.</p>
<details>
<summary>Answer</summary>
<p><code>{ user_id: 1, status: 1, at: -1 }</code>. <code>user_id</code> and <code>status</code> are equality → first two. <code>at</code> is sort + range candidate → last. Direction <code>-1</code> matches the desc sort.</p>
