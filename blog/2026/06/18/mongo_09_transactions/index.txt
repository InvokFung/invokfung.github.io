11:T8b31,<p>MongoDB has had <strong>multi-document ACID transactions</strong> since 4.0 (replica sets) and 4.2 (sharded clusters). They look like SQL transactions (<code>begin / commit / abort</code>), behave like SQL transactions (snapshot isolation), and carry SQL-like costs (locking, latency, contention). This post covers how to use them safely — sessions, retry on transient errors, abort vs commit, the limits — and the more important question: <strong>when NOT to reach for a transaction</strong> (in MongoDB, the answer is &quot;more often than you think&quot;).</p>
<blockquote>
<p>Series map: 00 Foundations → … → 08 Connection Pool &amp; Concurrency → <strong>09 Transactions</strong> (this post) → 10 Replica Sets → … → 17 Drivers &amp; Case Studies.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Start, commit, and abort a multi-document transaction.</li>
<li>Handle transient transaction errors with a retry loop.</li>
<li>Understand snapshot isolation + transaction limits (60 s, 16 MB).</li>
<li>Recognise when a transaction is the right tool — and when single-doc atomicity or schema redesign is better.</li>
</ul>

<h1 id="Chapter-1-—-Why-transactions-in-MongoDB"><a href="#Chapter-1-—-Why-transactions-in-MongoDB" class="headerlink" title="Chapter 1 — Why transactions in MongoDB"></a>Chapter 1 — Why transactions in MongoDB</h1>
<p>Single-document updates are <strong>already atomic</strong> in MongoDB — that's true for any update operator on one document, no transaction needed.</p>
<p>Transactions matter when you need atomicity <strong>across multiple documents</strong> (possibly across multiple collections, possibly across multiple shards):</p>
<ul>
<li>Transfer money between two accounts.</li>
<li>Decrement stock + insert an order line.</li>
<li>Update a parent + add to its children collection consistently.</li>
</ul>
<p>Before 4.0, the workaround was the <strong>two-phase commit pattern</strong> in application code — verbose and error-prone. Transactions replaced that for most use cases.</p>

<p>Key points:</p>
<ul>
<li><strong>Session</strong> — a transaction lives inside a session. <code>client.startSession()</code>.</li>
<li><strong><code>withTransaction(cb)</code></strong> — driver helper that begins, runs the callback, commits, and <strong>retries on transient errors automatically</strong>.</li>
<li><strong><code>{ session }</code></strong> option — must be passed to every operation that's part of the transaction. Forgetting it silently runs that op outside the transaction.</li>
<li><strong>Either commits all writes or none</strong> — snapshot isolation throughout.</li>
<li><strong><code>endSession</code></strong> in <code>finally</code> — always.</li>
</ul>

<hr>
<h1 id="Chapter-3-—-Read-concern-write-concern-inside-transactions"><a href="#Chapter-3-—-Read-concern-write-concern-inside-transactions" class="headerlink" title="Chapter 3 — Read concern + write concern inside transactions"></a>Chapter 3 — Read concern + write concern inside transactions</h1>
<p>Transactions default to:</p>
<ul>
<li><code>readConcern: 'snapshot'</code> — reads see a consistent point-in-time view; no torn reads.</li>
<li><code>writeConcern: 'majority'</code> — required for transactions on replica sets.</li>
<li><code>readPreference: 'primary'</code> — required.</li>
</ul>
<p>You can override per transaction. Stricter concerns are slower; the defaults are correct for most cases.</p>
<hr>
<h1 id="Chapter-4-—-Transient-errors-retry"><a href="#Chapter-4-—-Transient-errors-retry" class="headerlink" title="Chapter 4 — Transient errors + retry"></a>Chapter 4 — Transient errors + retry</h1>
<p>A transaction may fail with a <strong>transient transaction error</strong> for reasons unrelated to your code:</p>
<ul>
<li>Primary failover mid-transaction.</li>
<li>Lock conflict with another transaction.</li>
<li>Network blip.</li>
</ul>
<p><code>withTransaction</code> retries automatically when the error is marked <code>TransientTransactionError</code> or <code>UnknownTransactionCommitResult</code>. Most apps need no extra logic.</p>
<p>Manual retry pattern (for non-helper code):</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">async</span> <span class="hljs-keyword">function</span> <span class="hljs-title function_">runWithRetry</span>(<span class="hljs-params">txnFn</span>) {</span><br><span class="line">  <span class="hljs-keyword">while</span> (<span class="hljs-literal">true</span>) {</span><br><span class="line">    <span class="hljs-keyword">try</span> {</span><br><span class="line">      <span class="hljs-keyword">return</span> <span class="hljs-keyword">await</span> <span class="hljs-title function_">txnFn</span>();</span><br><span class="line">    } <span class="hljs-keyword">catch</span> (e) {</span><br><span class="line">      <span class="hljs-keyword">if</span> (e.<span class="hljs-property">hasErrorLabel</span>?.(<span class="hljs-string">&#x27;TransientTransactionError&#x27;</span>)) {</span><br><span class="line">        <span class="hljs-keyword">continue</span>;   <span class="hljs-comment">// retry</span></span><br><span class="line">      }</span><br><span class="line">      <span class="hljs-keyword">throw</span> e;</span><br><span class="line">    }</span><br><span class="line">  }</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Performance-impact"><a href="#Performance-impact" class="headerlink" title="Performance impact"></a>Performance impact</h2>
<p>A transaction holds locks for its duration. Other writers to the same documents queue or conflict. The longer the transaction, the worse the contention.</p>
<p>Rule of thumb:</p>
<ul>
<li>Sub-100 ms transactions are usually fine.</li>
<li>100 ms-1 s transactions add measurable lag at scale.</li>
<li>Multi-second transactions almost always indicate a design problem.</li>
</ul>
<hr>

<h1 id="Chapter-7-—-When-NOT-to-use-transactions"><a href="#Chapter-7-—-When-NOT-to-use-transactions" class="headerlink" title="Chapter 7 — When NOT to use transactions"></a>Chapter 7 — When NOT to use transactions</h1>
<p>Transactions are powerful + tempting, but expensive. Cheaper alternatives:</p>
<h2 id="Single-document-atomicity-free"><a href="#Single-document-atomicity-free" class="headerlink" title="Single-document atomicity (free)"></a>Single-document atomicity (free)</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">accounts</span>.<span class="hljs-title function_">updateOne</span>(</span><br><span class="line">  { <span class="hljs-attr">_id</span>: <span class="hljs-string">&#x27;A&#x27;</span>, <span class="hljs-attr">balance</span>: { <span class="hljs-attr">$gte</span>: <span class="hljs-number">100</span> } },</span><br><span class="line">  { <span class="hljs-attr">$inc</span>: { <span class="hljs-attr">balance</span>: -<span class="hljs-number">100</span> } }</span><br><span class="line">)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The whole update is atomic. If the filter doesn't match (balance &lt; 100), nothing changes. Most &quot;decrement counter, reject if would go negative&quot; problems collapse to this one statement.</p>
<h2 id="Embed-instead-of-reference"><a href="#Embed-instead-of-reference" class="headerlink" title="Embed instead of reference"></a>Embed instead of reference</h2>
<p>If you find yourself in a transaction across <code>parent</code> + <code>parent_children</code>, ask whether the children should be <strong>embedded</strong> in the parent (Post 07). A single update on an embedded array is atomic, no transaction needed.</p>
<h2 id="Idempotent-retries"><a href="#Idempotent-retries" class="headerlink" title="Idempotent retries"></a>Idempotent retries</h2>
<p>If the operation is idempotent, just retry on failure. No transaction needed — eventual consistency settles.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// idempotent upsert with a unique key</span></span><br><span class="line"><span class="hljs-keyword">await</span> db.<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;events&#x27;</span>).<span class="hljs-title function_">updateOne</span>(</span><br><span class="line">  { <span class="hljs-attr">event_id</span>: id },</span><br><span class="line">  { <span class="hljs-attr">$setOnInsert</span>: { ... } },</span><br><span class="line">  { <span class="hljs-attr">upsert</span>: <span class="hljs-literal">true</span> }</span><br><span class="line">)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Choreography-sagas-for-distributed-flows"><a href="#Choreography-sagas-for-distributed-flows" class="headerlink" title="Choreography (sagas) for distributed flows"></a>Choreography (sagas) for distributed flows</h2>
<p>For long-running cross-service flows (order → payment → shipping), use a saga / compensating action pattern. Transactions don't help across systems.</p>
<h2 id="Compute-materialise"><a href="#Compute-materialise" class="headerlink" title="Compute + materialise"></a>Compute + materialise</h2>
<p>Materialised views via <code>$merge</code> (Post 06) or change-stream-driven sync (Post 12) replace many &quot;update two collections at once&quot; cases.</p>
<blockquote>
<p><strong>Trick:</strong> before reaching for a transaction, ask: &quot;Can a single-document update with a filter condition serve this?&quot; Answer is yes 70-80 % of the time.</p>
</blockquote>
<hr>
<h1 id="Chapter-8-—-Sharded-transactions"><a href="#Chapter-8-—-Sharded-transactions" class="headerlink" title="Chapter 8 — Sharded transactions"></a>Chapter 8 — Sharded transactions</h1>
<p>Cross-shard transactions work since 4.2. They use a <strong>two-phase commit</strong> under the hood, so they're slower than single-shard.</p>
<p>Performance tips:</p>
<ul>
<li>Design schema so transactions hit one shard whenever possible.</li>
<li>Choose the shard key carefully — a transaction touching docs on the same shard key value stays single-shard.</li>
<li>Distributed transactions across many shards multiply latency by the number of shards.</li>
</ul>
<p>If your design requires frequent cross-shard transactions, the schema or shard-key choice may be wrong.</p>
<hr>

<h2 id="Exercise-5-—-Lifetime-limit"><a href="#Exercise-5-—-Lifetime-limit" class="headerlink" title="Exercise 5 — Lifetime limit"></a>Exercise 5 — Lifetime limit</h2>
<p>Inside a transaction, write 10k docs in a loop with no batching. Confirm it eventually fails when the 60s lifetime fires.</p>
<h2 id="Exercise-6-—-Retry-harness"><a href="#Exercise-6-—-Retry-harness" class="headerlink" title="Exercise 6 — Retry harness"></a>Exercise 6 — Retry harness</h2>
<p>Write your own retry-on-transient wrapper with a max-attempts cap of 3 and exponential backoff. Force a transient by aborting the transaction once during your callback.</p>

<h1 id="Cheat-sheet"><a href="#Cheat-sheet" class="headerlink" title="Cheat-sheet"></a>Cheat-sheet</h1>
<table>
<thead>
<tr>
<th>What</th>
<th>How</th>
</tr>
</thead>
<tbody>
<tr>
<td>Start session</td>
<td><code>const session = client.startSession()</code></td>
</tr>
<tr>
<td>Run transaction (helper)</td>
<td><code>await session.withTransaction(async () =&gt; { ... })</code></td>
</tr>
<tr>
<td>Pass session</td>
<td><code>{ session }</code> to <strong>every</strong> op inside the transaction</td>
</tr>
<tr>
<td>Default concerns</td>
<td>snapshot read, majority write, primary read pref</td>
</tr>
<tr>
<td>Lifetime cap</td>
<td>60 s; configure <code>transactionLifetimeLimitSeconds</code> cautiously</td>
</tr>
<tr>
<td>Oplog cap</td>
<td>16 MB per txn</td>
</tr>
<tr>
<td>Transient error</td>
<td><code>withTransaction</code> retries automatically</td>
</tr>
<tr>
<td>Snapshot isolation</td>
<td>reads see consistent point-in-time view</td>
</tr>
<tr>
<td>Single-doc atomic</td>
<td>already atomic; no transaction needed</td>
</tr>
<tr>
<td>Ask first</td>
<td>can single-doc + filter handle this? if yes, do that</td>
</tr>
<tr>
<td>Schema review</td>
<td>embed children → fewer transactions</td>
</tr>
<tr>
<td>Cross-shard</td>
<td>works (4.2+) but slower; align shard keys</td>
</tr>
<tr>
<td>Capped collection write</td>
<td>NOT supported in transaction</td>
</tr>
<tr>
<td>End session</td>
<td><code>finally { await session.endSession() }</code></td>
</tr>
