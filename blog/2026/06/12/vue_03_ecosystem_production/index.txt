11:T118af,<p>The first three posts in this series were about Vue itself. A production Vue application is Vue plus a store, a router, usually a meta-framework for server rendering, a test stack and a deployment target — and most production incidents happen at those seams: state that leaks between SSR requests, a navigation guard that loops, a hydration mismatch that only appears in one time zone, a page that fetches its data twice. This post covers the stack as it stands in September 2026: <strong>Pinia 4</strong> (setup stores, SSR state, testing), <strong>Vue Router 5</strong> (guards, lazy routes, and the typed file-based routing that moved into core), <strong>Nuxt 4.5</strong> (directory structure, rendering modes, hydration, <code>useFetch</code> / <code>useAsyncData</code>, Nitro), testing with <strong>Vitest</strong>, <strong>Vue Test Utils</strong> and <strong>Playwright</strong>, and deployment. Versions at the time of writing: Vue 3.5.43 (3.6 in release candidate), Pinia 4.0.3, Vue Router 5.3.1, Nuxt 4.5.2.</p>

<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Option store</strong> — <code>defineStore('id', { state, getters, actions })</code>, the Options API shape.</li>
<li><strong>Setup store</strong> — <code>defineStore('id', () =&gt; { … return { … } })</code>: <code>ref</code>s become state, <code>computed</code>s become getters, functions become actions.</li>
<li><strong>Pinia instance</strong> — the object created by <code>createPinia()</code> and installed with <code>app.use(pinia)</code>. It holds the state of every store in <code>pinia.state.value</code>.</li>
<li><strong>Hydration (of stores)</strong> — on the client, initialising <code>pinia.state.value</code> from the state the server serialised into the HTML.</li>
</ul>

<p>The rules that bite:</p>
<ul>
<li><strong>Return every piece of state.</strong> The Pinia docs are explicit: state that is not returned breaks SSR, devtools and plugins, because Pinia only knows about what it can see. You cannot have private state in a store; keep private values in a separate, internal store or in a closure that is not state.</li>
<li><strong><code>$reset()</code> is not generated for setup stores.</strong> Pinia cannot know the initial value of a <code>ref</code> you created; write your own, as above.</li>
<li><strong>Destructure with <code>storeToRefs</code>.</strong> A store is a <code>reactive</code> object, so <code>const { total } = useCartStore()</code> loses reactivity (Post 00, Chapter 8). <code>const { items, total } = storeToRefs(store)</code> keeps state and getters as refs; take actions directly from the store: <code>const { add } = store</code>.</li>
<li><strong><code>inject()</code> works inside setup stores</strong>, because Pinia runs them within the app's context. Use it for app-level provided values; do not return things such as the router or route from the store.</li>
</ul>
<p>Setup stores run inside an <code>effectScope</code> owned by Pinia, so <code>watch</code> and <code>computed</code> inside them live as long as the store. Composables from Post 01 that clean up with <code>onScopeDispose</code> behave correctly inside a store; composables that use <code>onUnmounted</code> do not.</p>
<h2 id="SSR-one-Pinia-per-request"><a href="#SSR-one-Pinia-per-request" class="headerlink" title="SSR: one Pinia per request"></a>SSR: one Pinia per request</h2>
<p>On the server, a module-scope <code>reactive</code> object is shared by every request (Post 00, Chapter 8). Pinia's design avoids that: stores are bound to the <code>pinia</code> instance, and you create <strong>one <code>pinia</code> per request</strong> together with the app. The per-request state is then serialised into the HTML and restored on the client before any store is used:</p>

<p>Nuxt's <code>@pinia/nuxt</code> module does all of this for you. Two SSR traps remain:</p>
<ul>
<li><strong>Calling <code>useStore()</code> outside setup on the server</strong> (in a plain module, or in a router guard defined outside <code>setup</code>) must receive the pinia instance: <code>useCartStore(pinia)</code>. Otherwise it may pick up the wrong request's pinia or none.</li>
<li><strong>Client-only values in state.</strong> A <code>ref</code> that reads <code>localStorage</code> (for example VueUse's <code>useLocalStorage</code>) must not be overwritten by the server's value during hydration. Wrap it: <code>const theme = skipHydrate(useLocalStorage('theme', 'light'))</code>.</li>
</ul>
<h2 id="Pinia-4"><a href="#Pinia-4" class="headerlink" title="Pinia 4"></a>Pinia 4</h2>
<p>Pinia 4.0 (July 2026) is a small major: the package is <strong>ESM-only</strong>, it requires Vue <code>^3.5.11</code> and TypeScript ≥ 5.6 for users who type-check, and <code>@vue/devtools-api</code> v8 is now a peer dependency. Its release notes also describe a rework of errors and development warnings. The store API above is unchanged from Pinia 2 and 3.</p>
<blockquote>
<p><strong>Trick:</strong> for server data (lists, details, anything with a cache lifetime) use a data-fetching layer — Nuxt's <code>useFetch</code>, TanStack Query, or Pinia Colada — and keep Pinia for <strong>client state</strong> (cart, UI preferences, wizard progress). Putting API caches in Pinia by hand means reimplementing deduplication, invalidation and staleness.</p>
</blockquote>

<p>A guard returns <code>false</code> to cancel, a route location to redirect, or nothing / <code>true</code> to continue. Throwing cancels and calls <code>router.onError</code>. Guards can be <code>async</code>. The older third argument, <code>next</code>, is still accepted, but the docs describe it as a common source of mistakes — calling it twice, or not at all on one branch — so new code should return values.</p>
<blockquote>
<p><strong>Common pitfall:</strong> a redirect guard that does not exclude its own target. <code>if (!user) return '/login'</code> on every route, including <code>/login</code>, loops; in development Vue Router aborts it with a &quot;possibly infinite redirection&quot; warning. Check <code>to.name !== 'login'</code> or mark public routes in <code>meta</code>.</p>
</blockquote>
<h2 id="The-full-resolution-order"><a href="#The-full-resolution-order" class="headerlink" title="The full resolution order"></a>The full resolution order</h2>
<ol>
<li>Navigation triggered.</li>
<li><code>beforeRouteLeave</code> in components being left.</li>
<li>Global <code>beforeEach</code>.</li>
<li><code>beforeRouteUpdate</code> in components being reused (same component, new params).</li>
<li><code>beforeEnter</code> in route records.</li>
<li>Async route components are resolved (lazy chunks downloaded).</li>
<li><code>beforeRouteEnter</code> in components being entered.</li>
<li>Global <code>beforeResolve</code>.</li>
<li>Navigation confirmed.</li>
<li>Global <code>afterEach</code>.</li>
<li>DOM updated.</li>
<li>Callbacks passed to <code>next</code> in <code>beforeRouteEnter</code> run with the new instance.</li>
</ol>
<p><code>beforeResolve</code> (step 8) is the right place for checks that need the <strong>resolved</strong> components, such as permissions stored in a page's <code>meta</code> or data that must exist before the page renders. <code>afterEach</code> cannot change the navigation; use it for analytics and document titles.</p>
<h2 id="Lazy-routes"><a href="#Lazy-routes" class="headerlink" title="Lazy routes"></a>Lazy routes</h2>
<pre><code class="language-ts"><figure class="highlight ts"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="ts"><span class="line"><span class="hljs-keyword">const</span> routes = [</span><br><span class="line">  { <span class="hljs-attr">path</span>: <span class="hljs-string">&#x27;/&#x27;</span>, <span class="hljs-attr">component</span>: <span class="hljs-title class_">Home</span> },                                   <span class="hljs-comment">// in the main bundle</span></span><br><span class="line">  { <span class="hljs-attr">path</span>: <span class="hljs-string">&#x27;/reports&#x27;</span>, <span class="hljs-attr">component</span>: <span class="hljs-function">() =&gt;</span> <span class="hljs-keyword">import</span>(<span class="hljs-string">&#x27;./pages/Reports.vue&#x27;</span>) },  <span class="hljs-comment">// own chunk</span></span><br><span class="line">]</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A function that returns a dynamic <code>import()</code> makes the route a separate chunk, downloaded at step 6. Do <strong>not</strong> use <code>defineAsyncComponent</code> for route components; the router handles the laziness itself. <h2 id="Hydration-mismatches"><a href="#Hydration-mismatches" class="headerlink" title="Hydration mismatches"></a>Hydration mismatches</h2>
<p>Hydration walks the server's DOM and attaches the client app to it, assuming both renders produced the same result. When they did not, Vue logs a mismatch warning in development and patches the difference, which costs time and can leave the page in a wrong state. The causes are few and always the same:</p>
<table>
<thead>
<tr>
<th>Cause</th>
<th>Example</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>Values that differ per environment</td>
<td><code>Date.now()</code>, <code>Math.random()</code>, <code>new Date().toLocaleString()</code> in the template</td>
<td>Compute once on the server and pass through state (<code>useState</code>), or render in <code>onMounted</code> / <code>&lt;ClientOnly&gt;</code></td>
</tr>
<tr>
<td>Time zone or locale differences</td>
<td>Server in UTC, user in Hong Kong</td>
<td>Format on the client, or format with an explicit time zone on both</td>
</tr>
<tr>
<td>Browser-only checks during render</td>
<td><code>typeof window !== 'undefined' ? … : …</code> in a template</td>
<td>Use <code>onMounted</code> to switch after hydration; <code>&lt;ClientOnly&gt;</code> with a fallback</td>
</tr>
<tr>
<td>Invalid HTML nesting</td>
<td><code>&lt;div&gt;</code> inside <code>&lt;p&gt;</code>, <code>&lt;a&gt;</code> inside <code>&lt;a&gt;</code></td>
<td>The browser's parser rewrites the server HTML before Vue sees it: fix the markup</td>
</tr>

<td>Counters for <code>aria-describedby</code></td>
<td><code>useId()</code> (Vue 3.5), stable across server and client</td>
</tr>
<tr>
<td>Genuinely unavoidable differences</td>
<td>A server-rendered timestamp</td>
<td><code>data-allow-mismatch=&quot;text&quot;</code> on that element (3.5)</td>
</tr>
</tbody>
</table>
<p>In production builds the mismatch details are compiled out. To debug one in production, set <code>__VUE_PROD_HYDRATION_MISMATCH_DETAILS__: true</code> in the build, reproduce, and turn it off again.</p>
<blockquote>
<p><strong>Watch out:</strong> browser extensions that inject markup (translators, password managers) cause mismatches you cannot fix. Reproduce in a clean profile before chasing one.</p>

<h1 id="Chapter-4-—-Data-fetching-in-Nuxt"><a href="#Chapter-4-—-Data-fetching-in-Nuxt" class="headerlink" title="Chapter 4 — Data fetching in Nuxt"></a>Chapter 4 — Data fetching in Nuxt</h1>
<h2 id="The-problem-fetching-twice"><a href="#The-problem-fetching-twice" class="headerlink" title="The problem: fetching twice"></a>The problem: fetching twice</h2>
<p>Code in a page's <code>setup</code> runs twice: on the server to produce HTML, then in the browser to hydrate. A bare <code>await $fetch('/api/products')</code> in setup therefore requests the data on the server <strong>and again</strong> in the browser, and if the two responses differ, the hydration check fails. <code>useFetch</code> and <code>useAsyncData</code> solve this: on the server they fetch and store the result in the <strong>payload</strong> (serialised into the HTML, available as <code>useNuxtApp().payload</code>); during hydration they read the payload instead of fetching.</p>
<pre><code class="language-vue"><figure class="highlight vue"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="vue"><span class="line"><span class="hljs-tag">&lt;<span class="hljs-name">script</span> <span class="hljs-attr">setup</span> <span class="hljs-attr">lang</span>=<span class="hljs-string">&quot;ts&quot;</span>&gt;</span><span class="language-javascript"></span><br><span class="line"><span class="hljs-keyword">const</span> route = <span class="hljs-title function_">useRoute</span>()</span><br><span class="line"><span class="hljs-keyword">const</span> { <span class="hljs-attr">data</span>: product, status, error, refresh } = <span class="hljs-keyword">await</span> <span class="hljs-title function_">useFetch</span>(</span><br><span class="line">  <span class="hljs-function">() =&gt;</span> <span class="hljs-string">`/api/products/<span class="hljs-subst">${route.params.id}</span>`</span>,</span><br><span class="line">  { <span class="hljs-attr">pick</span>: [<span class="hljs-string">&#x27;id&#x27;</span>, <span class="hljs-string">&#x27;name&#x27;</span>, <span class="hljs-string">&#x27;price&#x27;</span>] }           <span class="hljs-comment">// only these fields go into the payload</span></span><br><span class="line">)</span><br><span class="line"></span><span class="hljs-tag">&lt;/<span class="hljs-name">script</span>&gt;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>useFetch(url, opts)</code> is shorthand for <code>useAsyncData(key, () =&gt; $fetch(url, opts))</code> with a key generated from the URL and the call site.</p>
<h2 id="The-rules"><a href="#The-rules" class="headerlink" title="The rules"></a>The rules</h2>
<ul>
<li><strong><code>useFetch</code> / <code>useAsyncData</code> in setup, <code>$fetch</code> in event handlers.</strong> The Nuxt docs recommend <code>$fetch</code> for client-side, event-based interactions: a form submit or a button click has no server render to reuse.</li>
<li><strong><code>await</code> blocks navigation.</strong> Awaiting <code>useFetch</code> in a page uses Vue's <code>Suspense</code> under the hood (Post 01, Chapter 8), so the page renders with its data. <code>lazy: true</code> (or <code>useLazyFetch</code>) navigates immediately; show a state from <code>status</code> (<code>'idle' | 'pending' | 'success' | 'error'</code>).</li>
<li><strong><code>server: false</code></strong> fetches only in the browser — for data that depends on client-only state or does not matter for SEO.</li>
<li><strong>Reactive inputs refetch.</strong> A getter URL or reactive <code>query</code> values are watched; add <code>watch: [...]</code> for other sources.</li>
<li><strong>Keep payloads small.</strong> <code>pick</code> or <code>transform</code> before the data is serialised. A 2 MB API response copied into every HTML page is a performance bug.</li>
</ul>

<td><code>nuxt build</code> with a preset (often auto-detected; or <code>NITRO_PRESET</code>)</td>
<td>Platform-specific functions + static assets</td>
</tr>
</tbody>
</table>
<p>Before going live with SSR:</p>
<ol>
<li><strong>No per-user state at module scope</strong>, anywhere (Post 00, Chapter 8): stores via Pinia, shared composable state via <code>useState</code>.</li>
<li><strong>Runtime config from the environment</strong>, secrets outside <code>public</code>.</li>
<li><strong>Payload size</strong> checked on the heaviest pages (<code>pick</code>, <code>transform</code>).</li>
<li><strong><code>routeRules</code></strong> reviewed: which routes can be prerendered or cached with <code>swr</code> — every cached route is server CPU you do not spend.</li>
<li><strong>Hydration warnings</strong> at zero in development, and Playwright tests that wait for hydration.</li>
<li><strong>Error pages</strong>: <code>app/error.vue</code> for Nuxt, and <code>createError</code> with correct status codes in server routes so crawlers and monitors see real 404s and 500s.</li>
</ol>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-The-leaking-store"><a href="#Exercise-1-—-The-leaking-store" class="headerlink" title="Exercise 1 — The leaking store"></a>Exercise 1 — The leaking store</h2>
<p>An SSR app shows one user's cart to another user for a split second after deploys. The cart lives in <code>export const cart = reactive({ items: [] })</code>. Explain the bug and fix it with Pinia.</p>
<details>
<summary>Solution</summary>
<p>On the server the module is evaluated once per process, so every request shares <code>cart</code>. Move it into a Pinia setup store, create <code>pinia</code> per request with the app (Nuxt's <code>@pinia/nuxt</code> does this), and let the serialised state hydrate the client. Any code that runs outside <code>setup</code> on the server must call <code>useCartStore(pinia)</code> with that request's instance.</p>
</details>

<h2 id="Exercise-3-—-Nuxt-4-upgrade-bug"><a href="#Exercise-3-—-Nuxt-4-upgrade-bug" class="headerlink" title="Exercise 3 — Nuxt 4 upgrade bug"></a>Exercise 3 — Nuxt 4 upgrade bug</h2>
<p>After upgrading to Nuxt 4, <code>product.value.stock--</code> after a purchase no longer updates the page, and <code>if (data.value === null)</code> checks stopped working. Explain both and fix them.</p>
<details>
<summary>Solution</summary>
<p><code>data</code> from <code>useFetch</code> is now a <code>shallowRef</code>, so nested mutation is not tracked: replace the object (<code>product.value = { ...product.value, stock: product.value.stock - 1 }</code>) or pass <code>deep: true</code>. The default of <code>data</code> changed from <code>null</code> to <code>undefined</code>: test with <code>if (!data.value)</code> or <code>=== undefined</code>.</p>
</details>
<h2 id="Exercise-4-—-Find-the-mismatch"><a href="#Exercise-4-—-Find-the-mismatch" class="headerlink" title="Exercise 4 — Find the mismatch"></a>Exercise 4 — Find the mismatch</h2>
<p>A product page shows &quot;Offer ends in 2:59:59&quot; and logs a hydration text mismatch. Give two correct fixes.</p>
<details>
<summary>Solution</summary>
<p>The countdown is computed from <code>Date.now()</code> on the server and again, a moment later, on the client. Fix 1: render the countdown only after mount (<code>onMounted</code> sets a ref, or wrap it in <code>&lt;ClientOnly&gt;</code> with a placeholder of the same size). Fix 2: compute the end time once on the server, share it through <code>useState</code>, and render a static end time (&quot;Offer ends 18:00 HKT&quot;) during SSR, starting the ticking countdown in <code>onMounted</code>. <code>data-allow-mismatch=&quot;text&quot;</code> silences the warning but leaves a visible jump.</p>
</details>
<h2 id="Exercise-5-—-Payload-diet"><a href="#Exercise-5-—-Payload-diet" class="headerlink" title="Exercise 5 — Payload diet"></a>Exercise 5 — Payload diet</h2>
<p>A category page's HTML is 1.8 MB because of the <code>useFetch('/api/products')</code> payload, though the page shows name, price and thumbnail. Fix it without changing the API.</p>
<details>
<summary>Solution</summary>
<p><code>useFetch('/api/products', { transform: (list) =&gt; list.map(({ id, name, price, thumb }) =&gt; ({ id, name, price, thumb })) })</code>. For a single object, <code>pick: ['id', 'name', 'price']</code> does the same. Also consider pagination, and <code>swr</code> caching of the page in <code>routeRules</code>.</p>
</details>
<h2 id="Exercise-6-—-Flaky-e2e"><a href="#Exercise-6-—-Flaky-e2e" class="headerlink" title="Exercise 6 — Flaky e2e"></a>Exercise 6 — Flaky e2e</h2>
<p>A Playwright test clicks &quot;Add to cart&quot; right after <code>page.goto('/products/p1')</code> and fails about one run in ten. Explain and fix.</p>
<details>
<summary>Solution</summary>
<p>The server HTML shows the button before hydration attaches its listener; a click in that window does nothing. Use <code>goto('/products/p1', { waitUntil: 'hydration' })</code> from <code>@nuxt/test-utils/playwright</code>, or wait for an app-set signal after mount. Assert with web-first assertions (<code>await expect(locator).toHaveText(...)</code>), never fixed sleeps.</p>
</details>
