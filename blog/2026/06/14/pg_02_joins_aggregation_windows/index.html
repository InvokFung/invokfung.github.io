PostgreSQL Course — 02 · Joins, Aggregation and Window Functions

Created2026-06-14|Updated2026-06-14|Database > PostgreSQL
|Post View:

Everything in this post is what separates "can write SELECT" from "can answer the question the business actually asked". Joins combine rows across tables; aggregation collapses rows into summaries; window functions compute across a set of rows without collapsing them, which is the capability people most often reach for a reporting tool or an application loop to fake. Add CTEs and recursion and a very large class of problems that look like they need procedural code become a single declarative statement. Examples target PostgreSQL 17/18, with the version noted wherever behaviour changed.

Series map: 00 Foundations & Setup → 01 SQL Fundamentals & Data Types → 02 Joins, Aggregation & Window Functions (this post) → 03 Indexes & the Query Planner → 04 Query Optimization & Statistics → 05 Transactions, MVCC, Isolation & Locking → 06 Schema Design, Normalization & JSONB → 07 Operations, Backup, Replication & Security.

Learning Outcome

  • Predict the exact row output of INNER, LEFT, RIGHT, FULL, CROSS, and LATERAL joins on given inputs.
  • Write anti-joins correctly and explain why NOT IN is a NULL trap while NOT EXISTS is not.
  • Use GROUP BY, HAVING, the FILTER clause, and GROUPING SETS / ROLLUP / CUBE.
  • Solve greatest-n-per-group with DISTINCT ON and know when a window function is the better tool.
  • Use window functions in depth: PARTITION BY, ORDER BY, and frame clauses in ROWS, RANGE, and GROUPS mode.
  • Compute running totals, moving averages, rankings, and row-to-row deltas.
  • Write CTEs, control inlining with MATERIALIZED / NOT MATERIALIZED, and traverse trees with WITH RECURSIVE.

Chapter 1 — The join family, worked row by row

Terminology

  • Join — a combination of rows from two relations according to a predicate.
  • Join predicate — the ON condition. Distinct from the WHERE filter, and the distinction matters for outer joins.
  • Semi-join — returns rows of the left relation that have at least one match, with no duplication. EXISTS, IN.
  • Anti-join — returns rows of the left relation that have no match. NOT EXISTS.
  • Lateral — a subquery on the right of a join that may reference columns from the left.

The fixture

Every result in this chapter comes from these exact rows. Create them and follow along.

Four customers. Four orders, one of which belongs to nobody. Customers 3 and 4 have no orders. This shape exposes every join behaviour.

INNER JOIN — matches only

Three rows. Ada appears twice (one row per matching order — joins multiply). Kat and Alan vanish because they have no orders. Order 13 vanishes because NULL = c.id is never true.

LEFT JOIN — keep every left row

Five rows. Every customer survives; unmatched ones get NULL for all right-side columns. This is the workhorse join for "all X, with their Y if any".

RIGHT JOIN — keep every right row

RIGHT JOIN is LEFT JOIN with the tables written in the other order. Most codebases standardise on LEFT for readability; the one place RIGHT earns its keep is when a long chain of joins would otherwise need reordering.

FULL OUTER JOIN — keep everything

Six rows: the three matches, the two unmatched customers, the one unmatched order. FULL JOIN is the reconciliation tool — "which rows exist on one side but not the other" is a FULL JOIN with WHERE a.id IS NULL OR b.id IS NULL.

CROSS JOIN — every pairing

The legitimate use is generating a dense grid so that empty combinations appear as rows rather than going missing — every customer crossed with every calendar day, so zero-revenue days show up as zeroes instead of gaps:

Any accidental cross join is a missing ON clause, and shows up in EXPLAIN as a Nested Loop with no join condition and a wildly large row estimate.

ON vs WHERE in an outer join

The single most common outer-join bug:

ON decides what matches; WHERE decides what survives. In an outer join, any WHERE predicate on the nullable side removes the padded NULL rows and degrades the outer join to an inner one. For an inner join the two are interchangeable and the planner treats them identically.

USING and NATURAL

USING (col) is fine and produces one merged output column. NATURAL JOIN should be treated as forbidden: it silently changes meaning when someone adds a column named created_at to both tables.

Self-join

A table joined to itself — for hierarchies, adjacency, and pairwise comparison. Aliases become mandatory.

The a.id < b.id idiom is how you get unordered pairs exactly once instead of twice plus the self-pair.

LATERAL — a correlated subquery in the FROM clause

Normally a subquery in FROM cannot see the other FROM items. LATERAL (PostgreSQL 9.3+) lifts that restriction, which makes "top N per group" and "most recent per group" natural to express.

Use LEFT JOIN LATERAL (...) ON true instead of CROSS JOIN LATERAL if customers with no orders must still appear.

LATERAL is often the fastest greatest-n-per-group formulation when an index supports the inner ORDER BY … LIMIT, because it performs one small index scan per outer row rather than sorting the whole table. Set-returning functions in FROM are implicitly lateral:

Chapter 2 — Semi-joins, anti-joins, and the NOT IN trap

Semi-join: "has at least one"

Prefer EXISTS. It expresses the intent, never duplicates rows, and needs no DISTINCT to clean up afterwards. The JOIN … DISTINCT form is the one to avoid: it materialises the duplicates and then sorts them away.

Anti-join: "has none"

(a) and (b) both return Kat and Alan. (c) returns zero rows, because order 13 has customer_id IS NULL, so every NOT IN comparison evaluates to NULL rather than true, and WHERE keeps only true. No error, no warning — just an empty result that looks plausible.

The correctness argument is the important one, but there is a performance argument too: because NOT IN must preserve those NULL semantics, the planner cannot use a hash anti-join. It typically produces a Filter over a hashed SubPlan instead:

Form NULL-safe? Plans as anti-join? Verdict
NOT EXISTS (…) Yes Yes Default choice
LEFT JOIN … WHERE right.pk IS NULL Yes Yes Fine; slightly noisier to read
NOT IN (subquery) No No Avoid unless the column is provably NOT NULL
EXCEPT Yes (treats NULLs as equal) Sorts/hashes both sides Whole-row set difference only

Common pitfall: "the column is NOT NULL so NOT IN is safe" is true today. It survives until someone makes the column nullable, or the subquery grows a LEFT JOIN that introduces NULLs. Write NOT EXISTS and stop thinking about it.

Chapter 3 — Aggregation

GROUP BY and HAVING

The rule that explains most GROUP BY errors: every column in the select list must be either in the GROUP BY or inside an aggregate. PostgreSQL relaxes this in exactly one case — if you group by a table's primary key, every other column of that table is functionally dependent and may be selected bare:

WHERE filters rows before grouping; HAVING filters groups after. Putting a non-aggregate condition in HAVING works but forces the aggregation to process rows it will then discard — move it to WHERE.

The aggregate list worth knowing

Aggregate Returns
count(*) / count(col) All rows / non-NULL values
count(DISTINCT col) Distinct non-NULL values (expensive: sorts or hashes)
sum, avg, min, max The obvious; all skip NULL inputs
bool_and, bool_or Boolean conjunction / disjunction over a group
string_agg(col, ', ' ORDER BY col) Concatenated string
array_agg(col ORDER BY col) Array — keeps NULL elements
json_agg / jsonb_agg / jsonb_object_agg JSON aggregation
stddev_samp, var_samp, corr, regr_slope Statistics
percentile_cont(0.5) WITHIN GROUP (ORDER BY col) Interpolated median
percentile_disc(0.95) WITHIN GROUP (ORDER BY col) Actual value at the 95th percentile
mode() WITHIN GROUP (ORDER BY col) Most frequent value
range_agg, range_intersect_agg Range aggregation (PG 14+)

FILTER — conditional aggregation done properly

FILTER (SQL:2003, PostgreSQL 9.4+) replaces the sum(CASE WHEN … THEN … ELSE 0 END) idiom. It is clearer, and unlike the CASE form it produces NULL rather than 0 for an empty set — which is usually more honest. It composes with window functions too.

GROUPING SETS, ROLLUP, CUBE

One query, several grouping levels, one pass over the data.

Shorthands:

  • ROLLUP (a, b, c) = the hierarchical sets (a,b,c), (a,b), (a), () — for drill-down along a hierarchy such as country → region → city.
  • CUBE (a, b) = every combination: (a,b), (a), (b), () — for cross-tabulation.

The NULLs in subtotal rows are indistinguishable from genuine NULL data. GROUPING() disambiguates — it returns 1 when the column was aggregated away:

Chapter 4 — DISTINCT ON

PostgreSQL-specific, and one of the reasons people miss PostgreSQL on other databases. It keeps the first row of each group, where "first" is defined by ORDER BY.

Two hard rules:

  1. ORDER BY must begin with exactly the DISTINCT ON expressions. Otherwise PostgreSQL raises an error, because "first" would be undefined.
  2. The remaining ORDER BY terms choose which row within the group wins.

If the final output needs a different order, wrap it:

DISTINCT ON vs window function vs LATERAL

All three solve greatest-n-per-group:

Approach Best when
DISTINCT ON n = 1, concise, and a matching index makes the sort free
row_number() OVER (PARTITION BY … ORDER BY …) = n n > 1, or you need the rank value itself
LATERAL (SELECT … ORDER BY … LIMIT n) Few outer rows, many inner rows, and an index serves the inner ORDER BY … LIMIT

With an index on (customer_id, total DESC), DISTINCT ON can walk the index and skip within each group rather than sorting the table. With a small customers table and a huge orders table, LATERAL usually wins. Measure with EXPLAIN (ANALYZE, BUFFERS) — Post 03.

Chapter 5 — Window functions

An aggregate collapses many rows into one. A window function computes over a set of related rows and returns one value per input row, leaving the row count untouched. That single property solves running totals, rankings, row-to-row deltas, and percent-of-total without a self-join.

Anatomy

OVER () with nothing inside means "the whole result set as one partition" — the standard way to get a percent-of-total column.

Reuse a definition with the WINDOW clause:

The function catalogue

Function Returns
row_number() 1, 2, 3, 4 — no ties, arbitrary tiebreak
rank() 1, 2, 2, 4 — ties share a rank, then a gap
dense_rank() 1, 2, 2, 3 — ties share a rank, no gap
percent_rank() (rank - 1) / (rows - 1), in [0, 1]
cume_dist() Cumulative distribution, in (0, 1]
ntile(n) Bucket number, splitting the partition into n roughly equal parts
lag(expr, offset, default) Value from offset rows back (default 1)
lead(expr, offset, default) Value from offset rows forward
first_value(expr) First value in the frame
last_value(expr) Last value in the frame — see the trap below
nth_value(expr, n) The nth value in the frame
Any aggregate (sum, avg, count, array_agg, …) Aggregated over the frame

Frames: ROWS vs RANGE vs GROUPS

The frame decides which rows of the partition the function can see for the current row. This is where most window-function surprises live.

Mode n PRECEDING counts Use for
ROWS Physical rows Moving averages over the last N rows
RANGE A value offset in the ORDER BY column "Last 7 days" regardless of how many rows fall in it
GROUPS Peer groups (rows with equal ORDER BY values) "The previous 3 distinct dates"

RANGE with an offset and GROUPS mode, plus the EXCLUDE clauses, arrived in PostgreSQL 11. Before that only ROWS accepted offsets.

The default frame, and why it bites

  • With no ORDER BY: the frame is the entire partition. sum() gives the partition total for every row.
  • With an ORDER BY: the default frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — which in RANGE mode includes all peers of the current row, not just the rows up to it.

The two tied rows both see the full peer group under RANGE. If you want a strict row-by-row running total, say ROWS explicitly.

The last_value trap

first_value does not have this problem because the default frame starts at UNBOUNDED PRECEDING. An alternative that avoids the whole issue: first_value(total) OVER (… ORDER BY id DESC).

Running totals, moving averages, deltas

The ma7_calendar column is the reason RANGE with an interval offset exists: a ROWS BETWEEN 6 PRECEDING frame silently reaches further back than seven days whenever a day has no row.

Trick: the "gaps and islands" problem — grouping consecutive runs — is row_number() minus a second row_number(). SELECT grp, min(day), max(day) FROM (SELECT day, day - (row_number() OVER (ORDER BY day))::int AS grp FROM active_days) t GROUP BY grp; collapses consecutive dates into ranges. Worth memorising; it appears constantly in streak, session, and uptime calculations.

Chapter 6 — CTEs and recursion

Basic CTEs

CTEs make a long query readable by naming its stages, and they can be referenced multiple times. Data-modifying CTEs are a PostgreSQL strength:

All sub-statements of one query see the same snapshot and execute atomically.

The PostgreSQL 12 fencing change

Before PostgreSQL 12, every WITH clause was an optimisation fence: it was always materialised into a temporary result, and predicates from the outer query could never be pushed into it. That made CTEs a manual planner hint — sometimes helpful, often a performance trap.

From PostgreSQL 12, a CTE that is non-recursive, side-effect-free, and referenced exactly once is inlined by default, exactly like a subquery. Two keywords give explicit control:

Situation Choose
Expensive CTE referenced several times MATERIALIZED — compute once
CTE contains a volatile function you must call exactly once MATERIALIZED
Small CTE whose result you filter afterwards NOT MATERIALIZED or the default
Data-modifying CTE Always materialised; the keyword is irrelevant

Common pitfall: code written against PostgreSQL 11 or earlier sometimes uses a CTE deliberately as a fence, with a comment saying so or with no comment at all. Upgrading to 12+ inlines it and the plan changes. If a query regresses after a major upgrade, a CTE that lost its fence is a prime suspect — add MATERIALIZED to test the hypothesis.

Recursive CTEs

Execution is iterative, not truly recursive: run the seed, put its rows in a working table, repeatedly run the recursive term against the working table until it produces no rows.

Tree traversal

The path array does double duty: it produces correct depth-first ordering when used as the ORDER BY key, and it is the natural cycle guard.

A cycle in the data — employee A managing B managing A — makes a naive UNION ALL recursion run until it exhausts memory. Three defences:

PostgreSQL 14 also added SEARCH DEPTH FIRST BY id SET ord / SEARCH BREADTH FIRST BY id SET ord, which generates the ordering column for you instead of the manual path array.

Watch out: always put a bound on a recursive CTE running against user-supplied data — a WHERE depth < 100 in the recursive term, or the CYCLE clause. An unbounded recursion is a denial-of-service vector, and statement_timeout is a blunt second line of defence, not a first one.

Exercise 2 — The NOT IN trap, demonstrated

NOT IN returns 0 rows; the other two return Kat and Alan. Order 13 has customer_id IS NULL, so the NOT IN list contains NULL and every comparison yields NULL, which WHERE discards. After DELETE FROM orders WHERE id = 13, all three agree.

What How
Keep all left rows LEFT JOIN b ON …
Filter the nullable side Put the condition in ON, not WHERE
Reconcile two sets FULL OUTER JOIN … WHERE a.id IS NULL OR b.id IS NULL
Correlated subquery in FROM LEFT JOIN LATERAL (…) ON true
"Has at least one" WHERE EXISTS (SELECT 1 FROM … WHERE …)
"Has none" WHERE NOT EXISTS (…) — never NOT IN
Conditional aggregate count(*) FILTER (WHERE cond)
Median / p95 percentile_cont(0.5) WITHIN GROUP (ORDER BY x)
Concatenate a group string_agg(x, ', ' ORDER BY x)
Subtotals + grand total GROUP BY ROLLUP (a, b)
Top 1 per group SELECT DISTINCT ON (k) … ORDER BY k, sort_col DESC
Top N per group row_number() OVER (PARTITION BY k ORDER BY …) in a subquery
Percent of total x / sum(x) OVER ()
Running total sum(x) OVER (ORDER BY d ROWS UNBOUNDED PRECEDING)
Calendar moving average avg(x) OVER (ORDER BY d RANGE BETWEEN interval '6 days' PRECEDING AND CURRENT ROW)
Previous / next row lag(x) / lead(x)
Filter on a window result Wrap in a subquery or CTE
