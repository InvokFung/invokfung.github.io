MongoDB Course — 12 · Change Streams — Real-time CDC, Resume Tokens, Patterns

Created2026-06-25|Updated2026-06-25|Database > MongoDB
|Post View:

A change stream is a real-time feed of every document change in a collection, database, or whole cluster. It's MongoDB's built-in change data capture (CDC) — no Kafka Connect, no debezium, no polling. Subscribe, receive insert / update / delete / replace events as they happen, with resumable tokens for crash recovery. This post covers opening change streams at every scope, filtering with an aggregation pipeline, resume tokens, full-document options (including the new fullDocumentBeforeChange), and the canonical use cases: cache invalidation, audit logs, materialised-view refresh, cross-store sync.

Series map: 00 Foundations → … → 11 Sharding → 12 Change Streams (this post) → 13 Security → … → 17 Drivers & Case Studies.

Learning Outcome

  • Open a change stream on a collection, database, or cluster.
  • Filter events with an aggregation pipeline.
  • Resume after a crash using a resume token.
  • Use fullDocument and fullDocumentBeforeChange options.
  • Apply the standard patterns: cache invalidation, audit log, materialised view, sync.

Chapter 1 — Mechanics

Change streams are implemented over the same oplog that powers replication (Post 10). The server tails the oplog, applies your aggregation filter, transforms each event into a stable shape, and streams them to your client.

Requirements:

  • Replica set (or sharded cluster). Standalone mongod doesn't have an oplog.
  • Reads from the primary by default. Can be served from secondaries with read preference (less common).

Per-event latency: typically tens of milliseconds.

Chapter 4 — fullDocument options

fullDocument values:

Value Effect
"default" only present on insert, replace
"updateLookup" re-fetches the doc as it exists now after each update (may differ from the update time if more writes happened)
"whenAvailable" (7.0+, requires changeStreamPreAndPostImages) include post-image if recorded
"required" (7.0+) error if post-image unavailable

Pre-image (the change before)

Now every event includes both:

  • fullDocument — the doc as-of after the change.
  • fullDocumentBeforeChange — the doc as-of before.

Useful for: diff-based audit, before/after replication to another store, "what exactly changed".

Cost: storing pre-images increases write overhead; enable per collection only when needed.

Chapter 5 — Resume tokens

Every change event has _id = a resume token. If your consumer crashes, persist the last processed token, then resume:

  • resumeAfter — fails if the token is no longer in the oplog.
  • startAfter — like resumeAfter but tolerant of invalidate events (e.g., collection drop).
  • startAtOperationTime — start at a cluster time instead of a token.

Pattern:

If the consumer is down longer than the oplog window (Post 10), the token expires → must re-sync from scratch.

For exactly-once semantics, watch out: if your consumer crashes after applying but before persisting the resume token, you'll double-count on restart. Mitigations:

  1. Idempotent updates (e.g., use the order _id to dedupe).
  2. Transactional consumer (persist token + apply update in one transaction).
  3. Outbox table on the source side (the order is the source of truth; the view is rebuildable).

Chapter 9 — Use case: cross-store sync

Stream MongoDB changes into Elasticsearch / OpenSearch / Algolia for full-text search; into Redis for caching; into BigQuery / Snowflake for analytics; into another MongoDB cluster for cross-region replication.

Atlas does this natively via Atlas Triggers (Post 16) — a serverless function fires on every change event. No infra to run.

Chapter 10 — Operational concerns

Long-running consumers

A change stream client holds a cursor on the server. Treat it like a long-running connection:

  • Always wrap in error handling — network blips throw; reconnect with the last token.
  • On clean shutdown, persist the last token + close the cursor.
  • Use one consumer per collection per business purpose. Don't share streams across handlers.

Performance impact on the cluster

Change streams read from the oplog — extra reads, but typically cheap. Many streams = many oplog readers = some CPU + memory cost on the primary. Atlas handles thousands of streams comfortably.

Pre-image cost

Recording pre-images doubles per-update write work + storage. Enable only where the audit / before-image is needed.

Sharded clusters

Change streams on sharded clusters merge events from every shard, ordered by cluster time. Latency a touch higher than on a single replica set.

Chapter 11 — Limits

Limit Default
Single event size 16 MB (BSON)
Resume window depends on oplog window (Post 10)
Pipeline operators subset of full aggregation; basic $match, $project, $addFields, $replaceRoot, $replaceWith, $redact
Pre/post images per-collection opt-in; cost on writes

Large updates may produce events too big — adjust your pipeline to project only what consumers need.

Chapter 13 — Common pitfalls

Pitfall Cause Fix
Resume fails with "token expired" consumer down > oplog window enlarge oplog; or accept full re-sync from startAtOperationTime
Missing fullDocument on updates default mode use fullDocument: 'updateLookup' (or required pre-image)
Pre-image undefined collection not enabled collMod with changeStreamPreAndPostImages
Double-processed events on crash persisted token after apply but apply non-idempotent idempotent updates OR transactional consumer
Big event (> 16 MB) full-document mode + huge doc project subset before sending
Stream slow on busy collection lots of unrelated events; client filters them move filter to the pipeline ($match) — server side
invalidate event collection dropped or renamed use startAfter instead of resumeAfter
One consumer for everything bottleneck one consumer per use case

Practice Exercises

Exercise 1 — Print every change

Open a change stream on shop.orders. In another window insert + update + delete docs. Watch events print.

Exercise 2 — Resume token

Persist the last token to a JSON file after each event. Kill the consumer. Insert a few docs. Restart; confirm catch-up.

Exercise 3 — Cache invalidator

Run a Node consumer that pushes product changes into a Map (in-memory cache). Read from the cache in another script. Update a product; confirm the cache reflects the change in < 1 s.

Exercise 4 — Audit log

Enable pre-images on orders. Build the audit collection from Chapter 7. Update an order; inspect the audit doc.

Exercise 5 — Materialised view

Pipe paid-order events into daily_revenue. Insert a few paid orders for the same day; confirm daily_revenue totals match.

Exercise 6 — Stream-to-Elasticsearch (simulation)

Print to stdout in OpenSearch-bulk format every article change. Validate end-to-end pattern.
