11:Tac34,<p>A change stream is a real-time feed of every document change in a collection, database, or whole cluster. It's MongoDB's built-in <strong>change data capture (CDC)</strong> — no Kafka Connect, no debezium, no polling. Subscribe, receive <code>insert / update / delete / replace</code> events as they happen, with resumable tokens for crash recovery. This post covers opening change streams at every scope, filtering with an aggregation pipeline, resume tokens, full-document options (including the new <code>fullDocumentBeforeChange</code>), and the canonical use cases: cache invalidation, audit logs, materialised-view refresh, cross-store sync.</p>
<blockquote>
<p>Series map: 00 Foundations → … → 11 Sharding → <strong>12 Change Streams</strong> (this post) → 13 Security → … → 17 Drivers &amp; Case Studies.</p>
</blockquote>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Open a change stream on a collection, database, or cluster.</li>
<li>Filter events with an aggregation pipeline.</li>
<li>Resume after a crash using a resume token.</li>
<li>Use <code>fullDocument</code> and <code>fullDocumentBeforeChange</code> options.</li>
<li>Apply the standard patterns: cache invalidation, audit log, materialised view, sync.</li>
</ul>

<h1 id="Chapter-1-—-Mechanics"><a href="#Chapter-1-—-Mechanics" class="headerlink" title="Chapter 1 — Mechanics"></a>Chapter 1 — Mechanics</h1>
<p>Change streams are implemented over the same <strong>oplog</strong> that powers replication (Post 10). The server tails the oplog, applies your aggregation filter, transforms each event into a stable shape, and streams them to your client.</p>
<p>Requirements:</p>
<ul>
<li>Replica set (or sharded cluster). Standalone <code>mongod</code> doesn't have an oplog.</li>
<li>Reads from the <strong>primary</strong> by default. Can be served from secondaries with read preference (less common).</li>
</ul>
<p>Per-event latency: typically tens of milliseconds.</p>

<h1 id="Chapter-5-—-Resume-tokens"><a href="#Chapter-5-—-Resume-tokens" class="headerlink" title="Chapter 5 — Resume tokens"></a>Chapter 5 — Resume tokens</h1>
<p><img src="/blog/assets/mongo/diagram_12_change_streams.svg" alt="Change stream flow from writes to consumer, and resuming after a crash with the last saved resume token"></p>
<p>Every change event has <code>_id</code> = a <strong>resume token</strong>. If your consumer crashes, persist the last processed token, then resume:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> cs = db.<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;orders&#x27;</span>).<span class="hljs-title function_">watch</span>([], {</span><br><span class="line">  <span class="hljs-attr">resumeAfter</span>: lastToken     <span class="hljs-comment">// or startAfter: lastToken</span></span><br><span class="line">});</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><code>resumeAfter</code> — fails if the token is no longer in the oplog.</li>
<li><code>startAfter</code> — like resumeAfter but tolerant of <code>invalidate</code> events (e.g., collection drop).</li>
<li><code>startAtOperationTime</code> — start at a cluster time instead of a token.</li>
</ul>
<p>Pattern:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">let</span> lastToken = <span class="hljs-keyword">await</span> <span class="hljs-title function_">loadLastToken</span>();</span><br><span class="line"><span class="hljs-keyword">const</span> cs = db.<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;orders&#x27;</span>).<span class="hljs-title function_">watch</span>([], {</span><br><span class="line">  <span class="hljs-attr">resumeAfter</span>: lastToken,</span><br><span class="line">  <span class="hljs-attr">fullDocument</span>: <span class="hljs-string">&#x27;updateLookup&#x27;</span></span><br><span class="line">});</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">for</span> <span class="hljs-title function_">await</span> (<span class="hljs-keyword">const</span> change <span class="hljs-keyword">of</span> cs) {</span><br><span class="line">  <span class="hljs-keyword">await</span> <span class="hljs-title function_">processChange</span>(change);</span><br><span class="line">  <span class="hljs-keyword">await</span> <span class="hljs-title function_">saveLastToken</span>(change.<span class="hljs-property">_id</span>);</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If the consumer is down longer than the oplog window (Post 10), the token expires → must re-sync from scratch.</p>

<h1 id="Chapter-10-—-Operational-concerns"><a href="#Chapter-10-—-Operational-concerns" class="headerlink" title="Chapter 10 — Operational concerns"></a>Chapter 10 — Operational concerns</h1>
<h2 id="Long-running-consumers"><a href="#Long-running-consumers" class="headerlink" title="Long-running consumers"></a>Long-running consumers</h2>
<p>A change stream client holds a cursor on the server. Treat it like a long-running connection:</p>
<ul>
<li>Always wrap in error handling — network blips throw; reconnect with the last token.</li>
<li>On clean shutdown, persist the last token + close the cursor.</li>
<li>Use one consumer per collection per business purpose. Don't share streams across handlers.</li>
</ul>
<h2 id="Performance-impact-on-the-cluster"><a href="#Performance-impact-on-the-cluster" class="headerlink" title="Performance impact on the cluster"></a>Performance impact on the cluster</h2>
<p>Change streams read from the oplog — extra reads, but typically cheap. Many streams = many oplog readers = some CPU + memory cost on the primary. Atlas handles thousands of streams comfortably.</p>
<h2 id="Pre-image-cost"><a href="#Pre-image-cost" class="headerlink" title="Pre-image cost"></a>Pre-image cost</h2>
<p>Recording pre-images doubles per-update write work + storage. Enable only where the audit / before-image is needed.</p>
<h2 id="Sharded-clusters"><a href="#Sharded-clusters" class="headerlink" title="Sharded clusters"></a>Sharded clusters</h2>
<p>Change streams on sharded clusters merge events from every shard, ordered by cluster time. Latency a touch higher than on a single replica set.</p>

<h1 id="Chapter-13-—-Common-pitfalls"><a href="#Chapter-13-—-Common-pitfalls" class="headerlink" title="Chapter 13 — Common pitfalls"></a>Chapter 13 — Common pitfalls</h1>
<table>
<thead>
<tr>
<th>Pitfall</th>
<th>Cause</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>Resume fails with &quot;token expired&quot;</td>
<td>consumer down &gt; oplog window</td>
<td>enlarge oplog; or accept full re-sync from <code>startAtOperationTime</code></td>
</tr>
<tr>
<td>Missing <code>fullDocument</code> on updates</td>
<td>default mode</td>
<td>use <code>fullDocument: 'updateLookup'</code> (or required pre-image)</td>
</tr>
<tr>
<td>Pre-image undefined</td>
<td>collection not enabled</td>
<td><code>collMod</code> with <code>changeStreamPreAndPostImages</code></td>
</tr>
<tr>
<td>Double-processed events on crash</td>
<td>persisted token after apply but apply non-idempotent</td>
<td>idempotent updates OR transactional consumer</td>
</tr>
<tr>
<td>Big event (&gt; 16 MB)</td>
<td>full-document mode + huge doc</td>
<td>project subset before sending</td>
</tr>
<tr>
<td>Stream slow on busy collection</td>
<td>lots of unrelated events; client filters them</td>
<td>move filter to the pipeline (<code>$match</code>) — server side</td>
</tr>
<tr>
<td><code>invalidate</code> event</td>
<td>collection dropped or renamed</td>
<td>use <code>startAfter</code> instead of <code>resumeAfter</code></td>
</tr>
<tr>
<td>One consumer for everything</td>
<td>bottleneck</td>
<td>one consumer per use case</td>
</tr>
</tbody>
</table>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Print-every-change"><a href="#Exercise-1-—-Print-every-change" class="headerlink" title="Exercise 1 — Print every change"></a>Exercise 1 — Print every change</h2>
<p>Open a change stream on <code>shop.orders</code>. In another window insert + update + delete docs. Watch events print.</p>
<h2 id="Exercise-2-—-Resume-token"><a href="#Exercise-2-—-Resume-token" class="headerlink" title="Exercise 2 — Resume token"></a>Exercise 2 — Resume token</h2>
<p>Persist the last token to a JSON file after each event. Kill the consumer. Insert a few docs. Restart; confirm catch-up.</p>
<h2 id="Exercise-3-—-Cache-invalidator"><a href="#Exercise-3-—-Cache-invalidator" class="headerlink" title="Exercise 3 — Cache invalidator"></a>Exercise 3 — Cache invalidator</h2>
<p>Run a Node consumer that pushes product changes into a <code>Map</code> (in-memory cache). Read from the cache in another script. Update a product; confirm the cache reflects the change in &lt; 1 s.</p>
<h2 id="Exercise-4-—-Audit-log"><a href="#Exercise-4-—-Audit-log" class="headerlink" title="Exercise 4 — Audit log"></a>Exercise 4 — Audit log</h2>
<p>Enable pre-images on <code>orders</code>. Build the audit collection from Chapter 7. Update an order; inspect the audit doc.</p>
<h2 id="Exercise-5-—-Materialised-view"><a href="#Exercise-5-—-Materialised-view" class="headerlink" title="Exercise 5 — Materialised view"></a>Exercise 5 — Materialised view</h2>
<p>Pipe paid-order events into <code>daily_revenue</code>. Insert a few paid orders for the same day; confirm <code>daily_revenue</code> totals match.</p>
<h2 id="Exercise-6-—-Stream-to-Elasticsearch-simulation"><a href="#Exercise-6-—-Stream-to-Elasticsearch-simulation" class="headerlink" title="Exercise 6 — Stream-to-Elasticsearch (simulation)"></a>Exercise 6 — Stream-to-Elasticsearch (simulation)</h2>
<p>Print to stdout in OpenSearch-bulk format every article change. Validate end-to-end pattern.</p>
