11:T13448,<p>Post 03 covered index structures and how to read a basic <code>EXPLAIN</code> plan. This post goes one level down: <strong>why</strong> the planner picked that plan. PostgreSQL's planner is a cost-based optimizer — it enumerates plan shapes, prices each one using a handful of tunable constants plus the statistics collected by <code>ANALYZE</code>, and executes the cheapest. Almost every &quot;why is this query slow&quot; investigation ends at one of two answers: the cost constants do not describe your hardware, or the row estimates are wrong. Everything below is about finding out which.</p>

<h1 id="Chapter-1-—-How-the-planner-prices-a-plan"><a href="#Chapter-1-—-How-the-planner-prices-a-plan" class="headerlink" title="Chapter 1 — How the planner prices a plan"></a>Chapter 1 — How the planner prices a plan</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Path</strong> — one candidate way to produce a result set (a sequential scan, an index scan, a particular join order). The planner builds many, keeps the cheapest per useful sort order.</li>
<li><strong>Cost</strong> — an abstract number, not milliseconds. Only ratios between costs matter.</li>
<li><strong>Startup cost</strong> — cost paid before the first row can be returned. Shown as the first number in <code>cost=0.29..8.31</code>.</li>
<li><strong>Total cost</strong> — cost to return <em>all</em> rows. The second number.</li>
<li><strong>Selectivity</strong> — the estimated fraction of rows a predicate keeps, from <code>0.0</code> to <code>1.0</code>.</li>
<li><strong>Cardinality</strong> — the estimated number of rows a node emits, i.e. selectivity × input rows.</li>
</ul>

<p>A sequential scan of a 10 000-page table holding 1 000 000 rows costs roughly:</p>

<p>An index scan returning 1 % of that table pays <code>random_page_cost</code> per heap page it visits — and in the worst case (no correlation between index order and physical order) that is one page per row.</p>
<h2 id="Why-random_page_cost-4-is-wrong-on-SSDs"><a href="#Why-random_page_cost-4-is-wrong-on-SSDs" class="headerlink" title="Why random_page_cost = 4 is wrong on SSDs"></a>Why <code>random_page_cost = 4</code> is wrong on SSDs</h2>
<p>The default ratio of 4:1 encodes the physics of a 7 200 RPM spinning disk, where a random read costs a seek plus rotational latency and a sequential read costs almost nothing extra. On NVMe or SSD storage there is no seek; random reads are perhaps 1.0–1.5× the cost of sequential ones, and on a well-cached instance the difference is smaller still.</p>
<p>Leaving the default at <code>4.0</code> makes the planner systematically overprice index scans, so it falls back to sequential scans on queries where an index would win.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Cluster-wide, in postgresql.conf (needs reload):</span></span><br><span class="line"><span class="hljs-comment">--   random_page_cost = 1.1</span></span><br><span class="line"><span class="hljs-comment">--   effective_cache_size = &#x27;12GB&#x27;   -- ~50-75 % of RAM on a dedicated box</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- Session-level, for an experiment:</span></span><br><span class="line"><span class="hljs-keyword">SET</span> random_page_cost <span class="hljs-operator">=</span> <span class="hljs-number">1.1</span>;</span><br><span class="line">EXPLAIN (ANALYZE, BUFFERS) <span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> orders <span class="hljs-keyword">WHERE</span> customer_id <span class="hljs-operator">=</span> <span class="hljs-number">42</span>;</span><br><span class="line">RESET random_page_cost;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>effective_cache_size</code> is not an allocation — it tells the planner how much data it can <em>assume</em> is cached between the shared buffers and the OS page cache. Setting it too low is another way to scare the planner off index scans.</p>
<blockquote>
<p><strong>Trick:</strong> change one constant per session with <code>SET</code>, re-<code>EXPLAIN</code>, and compare. Never edit <code>postgresql.conf</code> first — prove the change helps on a real query before making it global.</p>
</blockquote>
<blockquote>
<p><strong>Watch out:</strong> cost is not time. A plan with half the cost can be slower if the row estimates feeding that cost are wrong. Always confirm with <code>EXPLAIN (ANALYZE, BUFFERS)</code>.</p>
</blockquote>

<h1 id="Chapter-2-—-Statistics-what-ANALYZE-actually-collects"><a href="#Chapter-2-—-Statistics-what-ANALYZE-actually-collects" class="headerlink" title="Chapter 2 — Statistics: what ANALYZE actually collects"></a>Chapter 2 — Statistics: what ANALYZE actually collects</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong><code>pg_statistic</code></strong> — the system catalogue holding per-column statistics. Read it through the <code>pg_stats</code> view, which is human-readable and permission-filtered.</li>
<li><strong>MCV list</strong> — most common values and their frequencies.</li>
<li><strong>Histogram</strong> — bucket boundaries describing the distribution of the non-MCV values.</li>
<li><strong><code>n_distinct</code></strong> — estimated number of distinct values. Negative values are a <em>ratio</em> to the table row count (<code>-1</code> means &quot;unique&quot;).</li>
<li><strong>Correlation</strong> — how closely the physical row order matches the logical order of the column, from <code>-1</code> to <code>1</code>. Drives the cost of an index scan's heap fetches.</li>
</ul>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="sql"><span class="line">ANALYZE orders;                    <span class="hljs-comment">-- one table</span></span><br><span class="line">ANALYZE;                           <span class="hljs-comment">-- whole database</span></span><br><span class="line">VACUUM (ANALYZE) orders;           <span class="hljs-comment">-- vacuum and re-analyze together</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> attname, n_distinct, correlation,</span><br><span class="line">       most_common_vals, most_common_freqs</span><br><span class="line"><span class="hljs-keyword">FROM</span> pg_stats</span><br><span class="line"><span class="hljs-keyword">WHERE</span> tablename <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;orders&#x27;</span> <span class="hljs-keyword">AND</span> attname <span class="hljs-keyword">IN</span> (<span class="hljs-string">&#x27;status&#x27;</span>, <span class="hljs-string">&#x27;created_at&#x27;</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Autovacuum runs <code>ANALYZE</code> automatically once roughly <code>autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × reltuples</code> rows have changed (defaults: 50 rows plus 10 %). Two situations defeat that:</p>
<ol>
<li>A bulk load followed immediately by queries — the statistics are still from before the load. Run <code>ANALYZE</code> explicitly at the end of any ETL job.</li>
<li>A restore from <code>pg_dump</code> — dumps do not carry statistics. <code>ANALYZE</code> is mandatory after a restore.</li>
</ol>
<h2 id="default_statistics_target"><a href="#default_statistics_target" class="headerlink" title="default_statistics_target"></a>default_statistics_target</h2>
<p>Default <code>100</code>: up to 100 MCV entries and 100 histogram buckets per column, sampled from roughly 300 × target rows. Raise it for columns with skewed distributions where the tail matters:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Per column (preferred - targeted, cheap):</span></span><br><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders <span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">COLUMN</span> status <span class="hljs-keyword">SET</span> STATISTICS <span class="hljs-number">500</span>;</span><br><span class="line">ANALYZE orders;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- Cluster-wide (blunt - raises ANALYZE cost everywhere):</span></span><br><span class="line"><span class="hljs-comment">-- default_statistics_target = 200</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The maximum is <code>10000</code>. Higher targets make <code>ANALYZE</code> slower and planning slower, so raise them per column, not globally.</p>

<h1 id="Chapter-3-—-Join-algorithms"><a href="#Chapter-3-—-Join-algorithms" class="headerlink" title="Chapter 3 — Join algorithms"></a>Chapter 3 — Join algorithms</h1>
<p>PostgreSQL has exactly three physical join strategies. Knowing when each wins tells you what a bad plan is missing.</p>
<table>
<thead>
<tr>
<th>Algorithm</th>
<th>Shape</th>
<th>Chosen when</th>
<th>Cost profile</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Nested Loop</strong></td>
<td>For each outer row, probe the inner relation</td>
<td>Outer side is small, inner side has an index on the join key</td>
<td>Low startup, cost grows linearly with outer rows</td>
</tr>
<tr>
<td><strong>Hash Join</strong></td>
<td>Build a hash table on the smaller side, stream the larger side through it</td>
<td>Both sides large, equality join, hash table fits in <code>work_mem × hash_mem_multiplier</code></td>
<td>High startup (build phase), cheap per probe</td>
</tr>
<tr>
<td><strong>Merge Join</strong></td>
<td>Sort both sides on the join key, walk them in lockstep</td>
<td>Both sides already sorted (index order), or sorting is cheap; also works for inequality merges</td>
<td>Startup dominated by the sorts</td>
</tr>
</tbody>
</table>

<p>Reading it:</p>
<ul>
<li><code>Batches: 1</code> means the hash table fit in memory. <code>Batches: 4</code> or more means it spilled to disk — a <code>work_mem</code> problem (Chapter 6).</li>
<li><code>loops=1</code> on the inner side of a hash join is normal. On a <strong>nested loop</strong> the inner node's <code>actual</code> numbers are <strong>per loop</strong>; multiply by <code>loops</code> to get the real total.</li>
<li>A nested loop with <code>loops=120000</code> and no index on the inner side is the classic accidental cross-product.</li>
</ul>
<h2 id="Forcing-a-strategy-for-diagnosis-only"><a href="#Forcing-a-strategy-for-diagnosis-only" class="headerlink" title="Forcing a strategy for diagnosis only"></a>Forcing a strategy for diagnosis only</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SET</span> enable_hashjoin <span class="hljs-operator">=</span> off;</span><br><span class="line">EXPLAIN ANALYZE <span class="hljs-keyword">SELECT</span> ...;      <span class="hljs-comment">-- what does it pick instead, and is it faster?</span></span><br><span class="line">RESET enable_hashjoin;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The <code>enable_*</code> flags (<code>enable_seqscan</code>, <code>enable_nestloop</code>, <code>enable_indexscan</code>, <code>enable_sort</code>, …) do not truly disable a strategy — they add a large penalty cost. They are diagnostic instruments. If disabling a join type makes the query dramatically faster, the real bug is an estimate, and that is what you fix.</p>

<h1 id="Chapter-4-—-Reading-a-nested-plan-and-finding-the-poisoned-estimate"><a href="#Chapter-4-—-Reading-a-nested-plan-and-finding-the-poisoned-estimate" class="headerlink" title="Chapter 4 — Reading a nested plan and finding the poisoned estimate"></a>Chapter 4 — Reading a nested plan and finding the poisoned estimate</h1>
<p>Plans are trees printed with the root at the top. Data flows <strong>bottom-up</strong>, but you read <strong>top-down</strong> to find where estimates first diverge, because a bad estimate low in the tree corrupts every decision above it.</p>
<p>The single most useful number is the ratio <code>actual rows / estimated rows</code> at each node. Walk down until you find the deepest node where that ratio is close to 1, then look at its parent — the first node where the ratio blows up is where the trouble starts.</p>
<pre><code><figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span></pre></td><td class="code"><pre><code class="plaintext"><span class="line">Nested Loop  (<span class="hljs-attribute">cost</span>=0.86..1420.11 <span class="hljs-attribute">rows</span>=12 <span class="hljs-attribute">width</span>=68)</span><br><span class="line">             (actual <span class="hljs-attribute">time</span>=0.098..4821.774 <span class="hljs-attribute">rows</span>=48211 <span class="hljs-attribute">loops</span>=1)   &lt;-- 4000x off</span><br><span class="line">  -&gt;  Index Scan using idx_events_type on events e</span><br><span class="line">        (<span class="hljs-attribute">cost</span>=0.43..612.02 <span class="hljs-attribute">rows</span>=12 <span class="hljs-attribute">width</span>=24)</span><br><span class="line">        (actual <span class="hljs-attribute">time</span>=0.041..38.902 <span class="hljs-attribute">rows</span>=48211 <span class="hljs-attribute">loops</span>=1)          &lt;-- 4000x off HERE</span><br><span class="line">        Index Cond: (event_type = <span class="hljs-string">&#x27;click&#x27;</span>)</span><br><span class="line">        Filter: (payload -&gt;&gt; <span class="hljs-string">&#x27;campaign&#x27;</span> = <span class="hljs-string">&#x27;summer&#x27;</span>)</span><br><span class="line">        Rows Removed by Filter: 3110</span><br><span class="line">  -&gt;  Index Scan using users_pkey on<span class="hljs-built_in"> users </span>u</span><br><span class="line">        (<span class="hljs-attribute">cost</span>=0.43..0.67 <span class="hljs-attribute">rows</span>=1 <span class="hljs-attribute">width</span>=48)</span><br><span class="line">        (actual <span class="hljs-attribute">time</span>=0.006..0.007 <span class="hljs-attribute">rows</span>=1 <span class="hljs-attribute">loops</span>=48211)            &lt;-- fine, but 48211 loops</span><br><span class="line">        Index Cond: (id = e.user_id)</span><br><span class="line">Planning Time: 0.312 ms</span><br><span class="line">Execution Time: 4839.610 ms</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Diagnosis: the planner believed the <code>events</code> scan returned 12 rows, so a nested loop looked free. It actually returned 48 211 rows, so the inner index scan ran 48 211 times. The join algorithm is not the bug; the estimate is. Two candidate fixes:</p>
<ol>
<li>Expression statistics on <code>payload -&gt;&gt; 'campaign'</code> so the planner stops guessing at the JSON predicate.</li>
<li>An index on <code>(event_type, (payload -&gt;&gt; 'campaign'))</code> so the filter becomes an index condition.</li>
</ol>
<p>Vocabulary that matters when reading plans:</p>
<ul>
<li><strong><code>Rows Removed by Filter</code></strong> — work the node did and threw away. Large values mean the predicate should move into the index condition.</li>
<li><strong><code>Heap Fetches</code></strong> on an Index Only Scan — pages visited because the visibility map was not all-visible. Large values mean the table needs a vacuum.</li>
<li><strong><code>Buffers: shared hit=… read=…</code></strong> — <code>hit</code> came from shared buffers, <code>read</code> came from the OS or disk. <code>BUFFERS</code> is on by default with <code>ANALYZE</code> from PostgreSQL 18; add it explicitly on earlier versions.</li>
<li><strong><code>Planning Time</code> vs <code>Execution Time</code></strong> — a planning time in the tens of milliseconds on a simple query points at too many partitions or a very high statistics target.</li>
</ul>
<blockquote>
<p><strong>Trick:</strong> <code>EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT TEXT)</code> prints any non-default planner settings alongside the plan, which makes &quot;works on my machine&quot; plan differences obvious.</p>
</blockquote>
<blockquote>
<p><strong>Watch out:</strong> <code>EXPLAIN ANALYZE</code> <em>runs</em> the statement. For <code>INSERT</code>/<code>UPDATE</code>/<code>DELETE</code>, wrap it: <code>BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;</code>.</p>
</blockquote>

<h2 id="Function-on-an-indexed-column"><a href="#Function-on-an-indexed-column" class="headerlink" title="Function on an indexed column"></a>Function on an indexed column</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Index on created_at is unusable: the planner cannot invert the function.</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> orders <span class="hljs-keyword">WHERE</span> date_trunc(<span class="hljs-string">&#x27;day&#x27;</span>, created_at) <span class="hljs-operator">=</span> <span class="hljs-type">DATE</span> <span class="hljs-string">&#x27;2026-05-01&#x27;</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- Sargable rewrite - a range that the btree can seek:</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> orders</span><br><span class="line"><span class="hljs-keyword">WHERE</span> created_at <span class="hljs-operator">&gt;=</span> <span class="hljs-type">DATE</span> <span class="hljs-string">&#x27;2026-05-01&#x27;</span></span><br><span class="line">  <span class="hljs-keyword">AND</span> created_at <span class="hljs-operator">&lt;</span>  <span class="hljs-type">DATE</span> <span class="hljs-string">&#x27;2026-05-02&#x27;</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- Or index the expression itself:</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_orders_day <span class="hljs-keyword">ON</span> orders (date_trunc(<span class="hljs-string">&#x27;day&#x27;</span>, created_at));</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The same applies to <code>LOWER(email) = 'a@b.com'</code> (index <code>LOWER(email)</code>, or use a <code>citext</code> column) and <code>id::text = '42'</code>.</p>
<h2 id="Implicit-casts"><a href="#Implicit-casts" class="headerlink" title="Implicit casts"></a>Implicit casts</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- account_no is varchar; the literal is numeric -&gt; cast, index skipped</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> accounts <span class="hljs-keyword">WHERE</span> account_no <span class="hljs-operator">=</span> <span class="hljs-number">12345</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- Match the type:</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> accounts <span class="hljs-keyword">WHERE</span> account_no <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;12345&#x27;</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The rule: a btree index on column <code>c</code> is usable only when the predicate is <code>c &lt;op&gt; &lt;constant expression&gt;</code>. Anything that wraps <code>c</code> in a cast or function breaks that shape. Casts on the <em>literal</em> side are fine.</p>
<h2 id="OR-chains-vs-UNION-ALL"><a href="#OR-chains-vs-UNION-ALL" class="headerlink" title="OR chains vs UNION ALL"></a>OR chains vs UNION ALL</h2>
<p>A disjunction across different columns often cannot use one index efficiently — the planner either seq-scans or builds a BitmapOr.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Often a seq scan:</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> contacts <span class="hljs-keyword">WHERE</span> email <span class="hljs-operator">=</span> $<span class="hljs-number">1</span> <span class="hljs-keyword">OR</span> phone <span class="hljs-operator">=</span> $<span class="hljs-number">1</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- Two index scans, deduplicated by the application&#x27;s own semantics:</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> contacts <span class="hljs-keyword">WHERE</span> email <span class="hljs-operator">=</span> $<span class="hljs-number">1</span></span><br><span class="line"><span class="hljs-keyword">UNION</span> <span class="hljs-keyword">ALL</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> contacts <span class="hljs-keyword">WHERE</span> phone <span class="hljs-operator">=</span> $<span class="hljs-number">1</span> <span class="hljs-keyword">AND</span> email <span class="hljs-keyword">IS</span> <span class="hljs-keyword">DISTINCT</span> <span class="hljs-keyword">FROM</span> $<span class="hljs-number">1</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Use <code>UNION</code> (not <code>UNION ALL</code>) if rows can genuinely satisfy both branches and duplicates are unacceptable — it costs a sort or hash for dedup. Check the plan: a <code>BitmapOr</code> over two bitmap index scans is already a good outcome and needs no rewrite.</p>
<h2 id="SELECT"><a href="#SELECT" class="headerlink" title="SELECT *"></a>SELECT *</h2>
<p><code>SELECT *</code> prevents <strong>index-only scans</strong>, inflates network transfer, and pulls TOASTed columns (large text/JSONB) off disk that you never look at. It also makes the query fragile — a later <code>ALTER TABLE ... ADD COLUMN</code> silently changes the result shape. Name your columns.</p>
<h2 id="OFFSET-pagination-vs-keyset-pagination"><a href="#OFFSET-pagination-vs-keyset-pagination" class="headerlink" title="OFFSET pagination vs keyset pagination"></a>OFFSET pagination vs keyset pagination</h2>
<p><code>OFFSET n</code> makes the server produce and discard <code>n</code> rows. Page 1 is instant; page 5 000 scans five thousand pages worth of rows before returning anything.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- O(offset): degrades linearly, and rows shift under concurrent inserts</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> id, title, created_at</span><br><span class="line"><span class="hljs-keyword">FROM</span> articles</span><br><span class="line"><span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> created_at <span class="hljs-keyword">DESC</span>, id <span class="hljs-keyword">DESC</span></span><br><span class="line">LIMIT <span class="hljs-number">20</span> <span class="hljs-keyword">OFFSET</span> <span class="hljs-number">100000</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Keyset (a.k.a. seek) pagination carries the last row's sort key forward and seeks straight to it:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span <p>Every page costs the same. The tuple comparison <code>(a, b) &lt; (x, y)</code> is a real row-value expression in PostgreSQL and it <em>does</em> use a matching multicolumn index — unlike the hand-expanded <code>a &lt; x OR (a = x AND b &lt; y)</code>, which frequently does not.</p>
<p>Trade-off: keyset pagination cannot jump to &quot;page 500&quot;. If the UI requires numbered pages, keep <code>OFFSET</code> but cap the reachable depth, or precompute page boundaries.</p>

<h1 id="Chapter-6-—-work_mem-sorts-and-spills"><a href="#Chapter-6-—-work_mem-sorts-and-spills" class="headerlink" title="Chapter 6 — work_mem, sorts, and spills"></a>Chapter 6 — work_mem, sorts, and spills</h1>
<p><code>work_mem</code> is the memory budget for <strong>one</strong> sort, hash, or bitmap operation — not per query and not per connection. A single query with three sorts and two hash joins running in three parallel workers can consume many multiples of it. That is why the default is a conservative <code>4MB</code>.</p>

<p>Rules that make partitioning pay off:</p>
<ul>
<li><strong>The partition key must appear in the predicate.</strong> A query filtering only on <code>event_type</code> touches every partition and is now <em>slower</em> than an unpartitioned table.</li>
<li><strong>Keep the partition count sane.</strong> Hundreds are fine; tens of thousands inflate planning time and lock counts.</li>
<li><strong>Detaching beats deleting.</strong> <code>ALTER TABLE events DETACH PARTITION events_2025_01;</code> retires a month in milliseconds where <code>DELETE</code> would generate millions of dead tuples.</li>
<li>Enable <code>enable_partitionwise_join</code> and <code>enable_partitionwise_aggregate</code> (both off by default) when joining two tables partitioned identically.</li>
</ul>

<h1 id="Chapter-9-—-Materialized-views"><a href="#Chapter-9-—-Materialized-views" class="headerlink" title="Chapter 9 — Materialized views"></a>Chapter 9 — Materialized views</h1>
<p>A materialized view stores the query result on disk. It is the right tool when an expensive aggregate is read far more often than the underlying data changes, and slightly stale results are acceptable.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> MATERIALIZED <span class="hljs-keyword">VIEW</span> daily_revenue <span class="hljs-keyword">AS</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> date_trunc(<span class="hljs-string">&#x27;day&#x27;</span>, created_at) <span class="hljs-keyword">AS</span> <span class="hljs-keyword">day</span>,</span><br><span class="line">       country,</span><br><span class="line">       <span class="hljs-built_in">sum</span>(total)  <span class="hljs-keyword">AS</span> revenue,</span><br><span class="line">       <span class="hljs-built_in">count</span>(<span class="hljs-operator">*</span>)    <span class="hljs-keyword">AS</span> orders</span><br><span class="line"><span class="hljs-keyword">FROM</span> orders</span><br><span class="line"><span class="hljs-keyword">GROUP</span> <span class="hljs-keyword">BY</span> <span class="hljs-number">1</span>, <span class="hljs-number">2</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- REQUIRED for the concurrent refresh below:</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">UNIQUE</span> INDEX daily_revenue_pk <span class="hljs-keyword">ON</span> daily_revenue (<span class="hljs-keyword">day</span>, country);</span><br><span class="line"> </span><br><span class="line">REFRESH MATERIALIZED <span class="hljs-keyword">VIEW</span> daily_revenue;              <span class="hljs-comment">-- ACCESS EXCLUSIVE lock</span></span><br><span class="line">REFRESH MATERIALIZED <span class="hljs-keyword">VIEW</span> CONCURRENTLY daily_revenue; <span class="hljs-comment">-- readers keep reading</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>CONCURRENTLY</code> computes the new contents into a temporary relation and applies the difference, so readers are never blocked. Its requirements: a <strong>unique index</strong> covering all rows, and a view that has already been populated once. It is slower in wall-clock terms than a plain refresh — it trades throughput for availability.</p>
<p>PostgreSQL has no built-in incremental view maintenance; if refresh cost becomes the bottleneck, the usual answer is a summary table updated by triggers or by a scheduled job that only recomputes recent partitions.</p>
<hr>
<h1 id="Chapter-10-—-Start-from-pg_stat_statements"><a href="#Chapter-10-—-Start-from-pg_stat_statements" class="headerlink" title="Chapter 10 — Start from pg_stat_statements"></a>Chapter 10 — Start from pg_stat_statements</h1>
<p>Tuning by intuition finds the query you <em>remember</em> being slow. <code>pg_stat_statements</code> finds the one that actually costs the most, which is usually a 3 ms query executed two million times an hour.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- postgresql.conf, requires a restart:</span></span><br><span class="line"><span class="hljs-comment">--   shared_preload_libraries = &#x27;pg_stat_statements&#x27;</span></span><br><span class="line"><span class="hljs-comment">--   pg_stat_statements.track = all</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> EXTENSION IF <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">EXISTS</span> pg_stat_statements;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Top 10 by total time - the ranking that matters</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> substr(query, <span class="hljs-number">1</span>, <span class="hljs-number">90</span>) <span class="hljs-keyword">AS</span> query,</span><br><span class="line">       calls,</span><br><span class="line">       round(total_exec_time::<span class="hljs-type">numeric</span>, <span class="hljs-number">1</span>)          <span class="hljs-keyword">AS</span> total_ms,</span><br><span class="line">       round(mean_exec_time::<span class="hljs-type">numeric</span>, <span class="hljs-number">3</span>)           <span class="hljs-keyword">AS</span> mean_ms,</span><br><span class="line">       <span class="hljs-keyword">rows</span>,</span><br><span class="line">       round(<span class="hljs-number">100.0</span> <span class="hljs-operator">*</span> shared_blks_hit</span><br><span class="line">             <span class="hljs-operator">/</span> <span class="hljs-built_in">nullif</span>(shared_blks_hit <span class="hljs-operator">+</span> shared_blks_read, <span class="hljs-number">0</span>), <span class="hljs-number">1</span>) <span class="hljs-keyword">AS</span> hit_pct</span><br><span class="line"><span class="hljs-keyword">FROM</span> pg_stat_statements</span><br><span class="line"><span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> total_exec_time <span class="hljs-keyword">DESC</span></span><br><span class="line">LIMIT <span class="hljs-number">10</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> pg_stat_statements_reset();   <span class="hljs-comment">-- baseline before a load test</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The workflow:</p>
<ol>
<li><code>pg_stat_statements</code> → pick the top consumer by <code>total_exec_time</code>, not <code>mean_exec_time</code>.</li>
<li><code>EXPLAIN (ANALYZE, BUFFERS)</code> that statement with realistic parameters.</li>
<li>Find the first node where <code>actual rows / estimated rows</code> diverges.</li>
<li>Fix the estimate (<code>ANALYZE</code>, statistics target, <code>CREATE STATISTICS</code>) or the access path (index, rewrite).</li>
<li>Re-measure. Reset the statistics and confirm the total time moved.</li>
</ol>
<p>Supporting views: <code>pg_stat_user_tables</code> (<code>seq_scan</code> vs <code>idx_scan</code>, <code>n_dead_tup</code>), <code>pg_stat_user_indexes</code> (<code>idx_scan = 0</code> means an unused index paying write cost for nothing), and <code>log_min_duration_statement</code> to capture individual slow executions with their parameters.</p>
<blockquote>
<p><strong>Common pitfall:</strong> <code>pg_stat_statements</code> normalises literals, so <code>WHERE id = 1</code> and <code>WHERE id = 2</code> collapse into one entry. That is what you want for ranking — but it means the recorded query text has <code>$1</code> placeholders and you must supply realistic values yourself when re-running <code>EXPLAIN</code>.</p>
</blockquote>
