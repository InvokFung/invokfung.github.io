PostgreSQL Course — 04 · Query Optimization and Statistics

Created2026-06-25|Updated2026-06-25|Database > PostgreSQL
|Post View:

Post 03 covered index structures and how to read a basic EXPLAIN plan. This post goes one level down: why the planner picked that plan. PostgreSQL's planner is a cost-based optimizer — it enumerates plan shapes, prices each one using a handful of tunable constants plus the statistics collected by ANALYZE, and executes the cheapest. Almost every "why is this query slow" investigation ends at one of two answers: the cost constants do not describe your hardware, or the row estimates are wrong. Everything below is about finding out which.

Series map: 00 Foundations & Setup → 01 SQL Fundamentals & Data Types → 02 Joins, Aggregation & Window Functions → 03 Indexes & the Query Planner → 04 Query Optimization & Statistics (this post) → 05 Transactions, MVCC, Isolation & Locking → 06 Schema Design, Normalization & JSONB → 07 Operations, Backup, Replication & Security.

Learning Outcome

  • Explain how the planner prices a plan using seq_page_cost, random_page_cost, and the CPU cost constants, and adjust them for SSD-backed storage.
  • Describe what ANALYZE stores in pg_statistic, when to raise default_statistics_target, and when to add extended statistics with CREATE STATISTICS.
  • Recognise nested loop, hash join, and merge join from a plan and say why each was chosen.
  • Read a nested EXPLAIN (ANALYZE, BUFFERS) plan top-down and locate the first bad row estimate.
  • Fix the classic anti-patterns: functions on indexed columns, implicit casts, OR chains, SELECT *, and OFFSET pagination.
  • Size work_mem from evidence instead of guesswork, and read spill/external-sort lines.
  • Use partitioning, parallel query, and materialized views as deliberate optimization tools.
  • Start any real tuning session from pg_stat_statements instead of from intuition.

Chapter 1 — How the planner prices a plan

Terminology

  • Path — one candidate way to produce a result set (a sequential scan, an index scan, a particular join order). The planner builds many, keeps the cheapest per useful sort order.
  • Cost — an abstract number, not milliseconds. Only ratios between costs matter.
  • Startup cost — cost paid before the first row can be returned. Shown as the first number in cost=0.29..8.31.
  • Total cost — cost to return all rows. The second number.
  • Selectivity — the estimated fraction of rows a predicate keeps, from 0.0 to 1.0.
  • Cardinality — the estimated number of rows a node emits, i.e. selectivity × input rows.

The cost constants

The planner converts work into cost with five main knobs:

Parameter Default Meaning
seq_page_cost 1.0 Reading one 8 KB page sequentially. The unit everything else is measured against.
random_page_cost 4.0 Reading one page at a random offset.
cpu_tuple_cost 0.01 Processing one row.
cpu_index_tuple_cost 0.005 Processing one index entry.
cpu_operator_cost 0.0025 Evaluating one operator or function call.

A sequential scan of a 10 000-page table holding 1 000 000 rows costs roughly:

An index scan returning 1 % of that table pays random_page_cost per heap page it visits — and in the worst case (no correlation between index order and physical order) that is one page per row.

Why random_page_cost = 4 is wrong on SSDs

The default ratio of 4:1 encodes the physics of a 7 200 RPM spinning disk, where a random read costs a seek plus rotational latency and a sequential read costs almost nothing extra. On NVMe or SSD storage there is no seek; random reads are perhaps 1.0–1.5× the cost of sequential ones, and on a well-cached instance the difference is smaller still.

Leaving the default at 4.0 makes the planner systematically overprice index scans, so it falls back to sequential scans on queries where an index would win.

effective_cache_size is not an allocation — it tells the planner how much data it can assume is cached between the shared buffers and the OS page cache. Setting it too low is another way to scare the planner off index scans.

Trick: change one constant per session with SET, re-EXPLAIN, and compare. Never edit postgresql.conf first — prove the change helps on a real query before making it global.

Watch out: cost is not time. A plan with half the cost can be slower if the row estimates feeding that cost are wrong. Always confirm with EXPLAIN (ANALYZE, BUFFERS).

Chapter 2 — Statistics: what ANALYZE actually collects

Terminology

  • pg_statistic — the system catalogue holding per-column statistics. Read it through the pg_stats view, which is human-readable and permission-filtered.
  • MCV list — most common values and their frequencies.
  • Histogram — bucket boundaries describing the distribution of the non-MCV values.
  • n_distinct — estimated number of distinct values. Negative values are a ratio to the table row count (-1 means "unique").
  • Correlation — how closely the physical row order matches the logical order of the column, from -1 to 1. Drives the cost of an index scan's heap fetches.

Autovacuum runs ANALYZE automatically once roughly autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × reltuples rows have changed (defaults: 50 rows plus 10 %). Two situations defeat that:

  1. A bulk load followed immediately by queries — the statistics are still from before the load. Run ANALYZE explicitly at the end of any ETL job.
  2. A restore from pg_dump — dumps do not carry statistics. ANALYZE is mandatory after a restore.

default_statistics_target

Default 100: up to 100 MCV entries and 100 histogram buckets per column, sampled from roughly 300 × target rows. Raise it for columns with skewed distributions where the tail matters:

The maximum is 10000. Higher targets make ANALYZE slower and planning slower, so raise them per column, not globally.

Extended statistics for correlated columns

The planner assumes predicates are independent: sel(A AND B) = sel(A) × sel(B). When columns are functionally related that is catastrophically wrong.

CREATE STATISTICS teaches it the relationship:

Kind Since Fixes
dependencies PostgreSQL 10 Functional dependency: knowing postal_code implies city. Helps equality predicates on both columns.
ndistinct PostgreSQL 10 Distinct count of a combination of columns. Helps GROUP BY a, b estimates.
mcv PostgreSQL 12 Multivariate most-common-values list. Helps non-equality and mixed predicates.

PostgreSQL 14 added statistics on expressions, which fixes estimates for functional indexes and expression predicates:

Common pitfall: extended statistics do not help across tables. A bad estimate on a join condition needs a different fix — usually better single-table estimates on the columns feeding the join.

Chapter 3 — Join algorithms

PostgreSQL has exactly three physical join strategies. Knowing when each wins tells you what a bad plan is missing.

Algorithm Shape Chosen when Cost profile
Nested Loop For each outer row, probe the inner relation Outer side is small, inner side has an index on the join key Low startup, cost grows linearly with outer rows
Hash Join Build a hash table on the smaller side, stream the larger side through it Both sides large, equality join, hash table fits in work_mem × hash_mem_multiplier High startup (build phase), cheap per probe
Merge Join Sort both sides on the join key, walk them in lockstep Both sides already sorted (index order), or sorting is cheap; also works for inequality merges Startup dominated by the sorts

Reading it:

  • Batches: 1 means the hash table fit in memory. Batches: 4 or more means it spilled to disk — a work_mem problem (Chapter 6).
  • loops=1 on the inner side of a hash join is normal. On a nested loop the inner node's actual numbers are per loop; multiply by loops to get the real total.
  • A nested loop with loops=120000 and no index on the inner side is the classic accidental cross-product.

Forcing a strategy for diagnosis only

The enable_* flags (enable_seqscan, enable_nestloop, enable_indexscan, enable_sort, …) do not truly disable a strategy — they add a large penalty cost. They are diagnostic instruments. If disabling a join type makes the query dramatically faster, the real bug is an estimate, and that is what you fix.

Chapter 4 — Reading a nested plan and finding the poisoned estimate

Plans are trees printed with the root at the top. Data flows bottom-up, but you read top-down to find where estimates first diverge, because a bad estimate low in the tree corrupts every decision above it.

The single most useful number is the ratio actual rows / estimated rows at each node. Walk down until you find the deepest node where that ratio is close to 1, then look at its parent — the first node where the ratio blows up is where the trouble starts.

Diagnosis: the planner believed the events scan returned 12 rows, so a nested loop looked free. It actually returned 48 211 rows, so the inner index scan ran 48 211 times. The join algorithm is not the bug; the estimate is. Two candidate fixes:

  1. Expression statistics on payload ->> 'campaign' so the planner stops guessing at the JSON predicate.
  2. An index on (event_type, (payload ->> 'campaign')) so the filter becomes an index condition.

Vocabulary that matters when reading plans:

  • Rows Removed by Filter — work the node did and threw away. Large values mean the predicate should move into the index condition.
  • Heap Fetches on an Index Only Scan — pages visited because the visibility map was not all-visible. Large values mean the table needs a vacuum.
  • Buffers: shared hit=… read=… — hit came from shared buffers, read came from the OS or disk. BUFFERS is on by default with ANALYZE from PostgreSQL 18; add it explicitly on earlier versions.
  • Planning Time vs Execution Time — a planning time in the tens of milliseconds on a simple query points at too many partitions or a very high statistics target.

Trick: EXPLAIN (ANALYZE, BUFFERS, SETTINGS, FORMAT TEXT) prints any non-default planner settings alongside the plan, which makes "works on my machine" plan differences obvious.

Watch out: EXPLAIN ANALYZE runs the statement. For INSERT/UPDATE/DELETE, wrap it: BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;.

Chapter 5 — Anti-patterns that defeat indexes

Function on an indexed column

The same applies to LOWER(email) = 'a@b.com' (index LOWER(email), or use a citext column) and id::text = '42'.

Implicit casts

The rule: a btree index on column c is usable only when the predicate is c <op> <constant expression>. Anything that wraps c in a cast or function breaks that shape. Casts on the literal side are fine.

OR chains vs UNION ALL

A disjunction across different columns often cannot use one index efficiently — the planner either seq-scans or builds a BitmapOr.

Use UNION (not UNION ALL) if rows can genuinely satisfy both branches and duplicates are unacceptable — it costs a sort or hash for dedup. Check the plan: a BitmapOr over two bitmap index scans is already a good outcome and needs no rewrite.

SELECT *

SELECT * prevents index-only scans, inflates network transfer, and pulls TOASTed columns (large text/JSONB) off disk that you never look at. It also makes the query fragile — a later ALTER TABLE ... ADD COLUMN silently changes the result shape. Name your columns.

OFFSET pagination vs keyset pagination

OFFSET n makes the server produce and discard n rows. Page 1 is instant; page 5 000 scans five thousand pages worth of rows before returning anything.

Keyset (a.k.a. seek) pagination carries the last row's sort key forward and seeks straight to it:

Every page costs the same. The tuple comparison (a, b) < (x, y) is a real row-value expression in PostgreSQL and it does use a matching multicolumn index — unlike the hand-expanded a < x OR (a = x AND b < y), which frequently does not.

Trade-off: keyset pagination cannot jump to "page 500". If the UI requires numbered pages, keep OFFSET but cap the reachable depth, or precompute page boundaries.

Chapter 6 — work_mem, sorts, and spills

work_mem is the memory budget for one sort, hash, or bitmap operation — not per query and not per connection. A single query with three sorts and two hash joins running in three parallel workers can consume many multiples of it. That is why the default is a conservative 4MB.

Sort Method Meaning
quicksort Fit entirely in work_mem. Good.
top-N heapsort ORDER BY ... LIMIT n kept only n rows in memory. Very good.
external merge Spilled to temporary files. The Disk: figure tells you how much memory it wanted.

Sizing from evidence: take the Disk: value, add headroom, and set work_mem for that statement or that role — not globally.

Hash nodes get work_mem × hash_mem_multiplier (default 2.0 since PostgreSQL 15). Watch Batches: on Hash nodes and Buckets: … Batches: … growth; more than one batch means spilling.

Turn on log_temp_files = 0 to log every temporary file created — the cheapest way to find spilling queries in production.

Watch out: raising global work_mem on a pooled server is a classic OOM route. max_connections × work_mem × nodes_per_query is the number to fear.

Chapter 7 — Parallel query

PostgreSQL parallelises sequential scans, index scans, joins, aggregates, and (since 11) hash joins and appends. A parallel plan shows a Gather or Gather Merge node with Workers Planned / Workers Launched beneath it.

Parameter Default Note
max_parallel_workers_per_gather 2 Per Gather node. Raising it to 4 is common on multi-core boxes.
max_parallel_workers 8 Pool shared by all queries.
max_worker_processes 8 Hard ceiling; max_parallel_workers cannot exceed it.
min_parallel_table_scan_size 8MB Tables smaller than this are never scanned in parallel.
parallel_setup_cost 1000 Fixed cost of starting workers — deliberately high.
parallel_tuple_cost 0.1 Cost of shipping one row from a worker to the leader.

Workers Launched: 0 when Workers Planned: 4 means the worker pool was exhausted — check max_parallel_workers and concurrent load. Parallel query helps analytical scans and hurts nothing else; it is not a fix for a missing index, because the cheapest parallel scan of a whole table still reads the whole table.

Chapter 8 — Partitioning as an optimization tool

Declarative partitioning (PostgreSQL 10+, mature from 12 onward) splits one logical table into physical child tables. Its value for query optimization is partition pruning: the planner discards partitions that cannot contain matching rows.

Strategy Use for
RANGE Time series, monotonically increasing keys. The overwhelmingly common case.
LIST A small closed set — region, tenant tier, country.
HASH Even spread when there is no natural range or list, e.g. sharding by customer_id.

Pruning happens at plan time when the predicate is a constant, and at execution time when it comes from a parameter or a join (enable_partition_pruning, on by default). Confirm in the plan: an Append node listing only the partitions actually needed.

Rules that make partitioning pay off:

  • The partition key must appear in the predicate. A query filtering only on event_type touches every partition and is now slower than an unpartitioned table.
  • Keep the partition count sane. Hundreds are fine; tens of thousands inflate planning time and lock counts.
  • Detaching beats deleting. ALTER TABLE events DETACH PARTITION events_2025_01; retires a month in milliseconds where DELETE would generate millions of dead tuples.
  • Enable enable_partitionwise_join and enable_partitionwise_aggregate (both off by default) when joining two tables partitioned identically.

Chapter 9 — Materialized views

A materialized view stores the query result on disk. It is the right tool when an expensive aggregate is read far more often than the underlying data changes, and slightly stale results are acceptable.

CONCURRENTLY computes the new contents into a temporary relation and applies the difference, so readers are never blocked. Its requirements: a unique index covering all rows, and a view that has already been populated once. It is slower in wall-clock terms than a plain refresh — it trades throughput for availability.

PostgreSQL has no built-in incremental view maintenance; if refresh cost becomes the bottleneck, the usual answer is a summary table updated by triggers or by a scheduled job that only recomputes recent partitions.

Chapter 10 — Start from pg_stat_statements

Tuning by intuition finds the query you remember being slow. pg_stat_statements finds the one that actually costs the most, which is usually a 3 ms query executed two million times an hour.

The workflow:

  1. pg_stat_statements → pick the top consumer by total_exec_time, not mean_exec_time.
  2. EXPLAIN (ANALYZE, BUFFERS) that statement with realistic parameters.
  3. Find the first node where actual rows / estimated rows diverges.
  4. Fix the estimate (ANALYZE, statistics target, CREATE STATISTICS) or the access path (index, rewrite).
  5. Re-measure. Reset the statistics and confirm the total time moved.

Supporting views: pg_stat_user_tables (seq_scan vs idx_scan, n_dead_tup), pg_stat_user_indexes (idx_scan = 0 means an unused index paying write cost for nothing), and log_min_duration_statement to capture individual slow executions with their parameters.

Common pitfall: pg_stat_statements normalises literals, so WHERE id = 1 and WHERE id = 2 collapse into one entry. That is what you want for ranking — but it means the recorded query text has $1 placeholders and you must supply realistic values yourself when re-running EXPLAIN.

Practice Exercises

Exercise 1 — Prove the cost constants matter

Create a 2-million-row table with an index. Find a selective query where the planner chooses a sequential scan at random_page_cost = 4. Re-run with SET random_page_cost = 1.1 and compare both the plan and the actual execution time.

Exercise 2 — Break and fix an estimate

Build a table where two columns are functionally dependent (e.g. country and country_code). Show the estimate error on a query filtering both, then correct it with CREATE STATISTICS.

Exercise 3 — Make an index unusable, then usable

Write a query with WHERE lower(email) = 'a@b.com' against a plain index on email. Confirm the sequential scan, then fix it two different ways (expression index; citext column) and compare.

Solution

Exercise 4 — Keyset pagination

Convert an OFFSET-based listing endpoint to keyset pagination. Measure page 1 and page 5 000 under both schemes with EXPLAIN (ANALYZE, BUFFERS).

Solution

Exercise 5 — Force a spill

Run a GROUP BY over a large table with work_mem = '1MB' and read the Sort Method: external merge Disk: line. Raise work_mem with SET LOCAL until the method becomes quicksort, and record the smallest value that works.

Exercise 6 — Partition pruning

Partition an events table by month. Write one query that prunes to a single partition and one that scans all of them. Show both plans and explain the difference in one sentence each.

Exercise 7 — Tuning session from evidence

Enable pg_stat_statements, run a mixed workload for ten minutes, then produce the top-5-by-total-time report. Pick one entry, EXPLAIN (ANALYZE, BUFFERS) it, apply one fix, reset the statistics, and re-measure.

Cheat-sheet

What How
Full plan with timings and I/O EXPLAIN (ANALYZE, BUFFERS) SELECT ...
Plan without executing EXPLAIN SELECT ...
Safe plan for a write BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;
Show non-default planner settings EXPLAIN (ANALYZE, SETTINGS) ...
SSD cost tuning random_page_cost = 1.1, raise effective_cache_size
Refresh statistics ANALYZE tablename;
Inspect statistics SELECT * FROM pg_stats WHERE tablename = '...'
Deeper histogram on one column ALTER TABLE t ALTER COLUMN c SET STATISTICS 500;
Correlated-column statistics CREATE STATISTICS s (dependencies, mcv) ON a, b FROM t;
Diagnose a join choice SET enable_hashjoin = off; then re-EXPLAIN
Nested-loop inner totals multiply actual rows by loops
Detect sort spilling Sort Method: external merge Disk: …
Per-statement memory SET LOCAL work_mem = '64MB';
Log all temp files log_temp_files = 0
Parallel worker count max_parallel_workers_per_gather
Prune partitions put the partition key in the WHERE clause
Non-blocking matview refresh REFRESH MATERIALIZED VIEW CONCURRENTLY v; (needs a unique index)
Rank slow queries ORDER BY total_exec_time DESC in pg_stat_statements
Find unused indexes pg_stat_user_indexes where idx_scan = 0
Capture slow statements log_min_duration_statement = 500
