<h1 id="Chapter-1-—-What-PostgreSQL-is-and-is-not"><a href="#Chapter-1-—-What-PostgreSQL-is-and-is-not" class="headerlink" title="Chapter 1 — What PostgreSQL is (and is not)"></a>Chapter 1 — What PostgreSQL is (and is not)</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>RDBMS</strong> — Relational Database Management System: data lives in tables of typed columns, related by keys, queried with SQL.</li>
<li><strong>Cluster</strong> — one PostgreSQL server instance and the set of databases it manages, all sharing one data directory, one port, and one set of processes. Nothing to do with a distributed cluster.</li>
<li><strong>Data directory (<code>PGDATA</code>)</strong> — the on-disk home of a cluster: table files, WAL, config, everything.</li>
<li><strong>WAL</strong> — Write-Ahead Log. Every change is written to the log <em>before</em> it is written to the data files. WAL is the foundation of crash recovery, replication, and point-in-time recovery.</li>
<li><strong>MVCC</strong> — Multi-Version Concurrency Control. Writers create new row versions instead of overwriting, so readers never block writers and writers never block readers. Covered in depth in Post 05.</li>
<li><strong>Extension</strong> — a packaged bundle of SQL objects, types, functions, or index methods loadable with <code>CREATE EXTENSION</code>. PostGIS, <code>pg_stat_statements</code>, and <code>pgvector</code> are extensions.</li>
<li><strong>psql</strong> — the official terminal client. Not just a query runner: it has its own meta-command language, scripting, and formatting.</li>
</ul>
<h2 id="Where-it-fits"><a href="#Where-it-fits" class="headerlink" title="Where it fits"></a>Where it fits</h2>
<p>PostgreSQL is an <em>object-relational</em> database: standard SQL plus a type system you can extend. The design bias is <strong>correctness first, then features, then raw speed</strong>. It will refuse to silently truncate your string, silently coerce <code>'abc'</code> to <code>0</code>, or silently accept February 30th.</p>

<h2 id="When-PostgreSQL-is-the-wrong-choice"><a href="#When-PostgreSQL-is-the-wrong-choice" class="headerlink" title="When PostgreSQL is the wrong choice"></a>When PostgreSQL is the wrong choice</h2>
<p>Being honest about this early saves grief:</p>
<ul>
<li><strong>Embedded / single-file / zero-admin.</strong> Use SQLite. A PostgreSQL cluster is a server with a lifecycle.</li>
<li><strong>Petabyte analytical scans.</strong> PostgreSQL is row-oriented. A columnar warehouse (ClickHouse, BigQuery, DuckDB for local work) will beat it by an order of magnitude on wide aggregate scans. Note the escape hatch: <code>pg_duckdb</code> and <code>citus</code> narrow the gap.</li>
<li><strong>Truly schema-free, per-tenant custom fields, high write fan-out.</strong> The document model may genuinely fit better — see the MongoDB course's <strong>SQL → MongoDB migration post</strong> for how that decision is actually made, including the honest note that most SQL workloads should stay on SQL.</li>
<li><strong>Extreme single-key throughput with no relational needs.</strong> A key-value store will win.</li>
</ul>
<p>Everything else — the overwhelming majority of application back-ends — is squarely PostgreSQL territory.</p>
<blockquote>
<p><strong>Trick:</strong> PostgreSQL's <code>jsonb</code> type covers a large fraction of &quot;we need flexible fields&quot; cases without leaving the relational model. Post 06 covers when the hybrid approach beats picking a side.</p>
</blockquote>

<h1 id="Chapter-4-—-Process-and-memory-architecture"><a href="#Chapter-4-—-Process-and-memory-architecture" class="headerlink" title="Chapter 4 — Process and memory architecture"></a>Chapter 4 — Process and memory architecture</h1>
<p>PostgreSQL is <strong>multi-process, not multi-threaded</strong>. Understanding the process map explains most of its operational behaviour: why connections are expensive, why <code>VACUUM</code> exists, why a checkpoint can cause an I/O spike.</p>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Postmaster</strong> — the supervisor process (<code>postgres -D $PGDATA</code>). It listens on the port, authenticates, and forks one child per connection. It never executes queries itself.</li>
<li><strong>Backend</strong> — one OS process serving exactly one client connection, for the lifetime of that connection.</li>
<li><strong>Shared buffers</strong> — the cluster-wide page cache in shared memory. All backends read and write pages here.</li>
<li><strong>Background worker</strong> — an auxiliary process: WAL writer, checkpointer, autovacuum, background writer, and (18+) I/O workers.</li>
</ul>

<h2 id="Why-connections-are-expensive"><a href="#Why-connections-are-expensive" class="headerlink" title="Why connections are expensive"></a>Why connections are expensive</h2>
<p>Each connection is a forked OS process with its own memory context — measurably heavier than a thread. A few hundred idle connections consume real RAM and add contention. The answer is a <strong>connection pooler</strong> (PgBouncer, pgcat, or a pool in your application driver), covered in Post 07. Rule of thumb: keep <code>max_connections</code> moderate (100–300) and pool in front of it rather than raising it to thousands.</p>

<h1 id="Chapter-5-—-Cluster-database-schema-table"><a href="#Chapter-5-—-Cluster-database-schema-table" class="headerlink" title="Chapter 5 — Cluster, database, schema, table"></a>Chapter 5 — Cluster, database, schema, table</h1>
<p>This four-level hierarchy is the single biggest source of confusion for people arriving from MySQL, where &quot;database&quot; and &quot;schema&quot; are synonyms.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="text"><span class="line">Cluster  (one server, one PGDATA, one port)</span><br><span class="line"> ├── database: postgres        ← maintenance database</span><br><span class="line"> ├── database: template0/1     ← templates for CREATE DATABASE</span><br><span class="line"> └── database: shop</span><br><span class="line">      ├── schema: public</span><br><span class="line">      │    ├── table: customers</span><br><span class="line">      │    └── table: orders</span><br><span class="line">      ├── schema: analytics</span><br><span class="line">      │    └── view: daily_revenue</span><br><span class="line">      └── schema: pg_catalog   ← system catalogs</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Two rules that follow from the picture:</p>
<ol>
<li><strong>A connection belongs to exactly one database.</strong> You cannot join <code>shop.customers</code> to <code>billing.invoices</code> in a single query if they are separate databases. In <code>psql</code>, <code>\c billing</code> closes the connection and opens a new one. Cross-database access requires <code>postgres_fdw</code> or <code>dblink</code>.</li>
<li><strong>Schemas are the real namespacing unit.</strong> If two subsystems need to live in one query's reach, make them schemas in one database, not two databases.</li>
</ol>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> DATABASE shop;</span><br><span class="line">\c shop</span><br><span class="line"><span class="hljs-keyword">CREATE</span> SCHEMA analytics;</span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> analytics.daily_revenue (<span class="hljs-keyword">day</span> <span class="hljs-type">date</span> <span class="hljs-keyword">primary</span> key, total <span class="hljs-type">numeric</span>(<span class="hljs-number">12</span>,<span class="hljs-number">2</span>));</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="search_path"><a href="#search_path" class="headerlink" title="search_path"></a><code>search_path</code></h2>
<p>Unqualified names are resolved against <code>search_path</code>, in order:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SHOW</span> search_path;              <span class="hljs-comment">-- &quot;$user&quot;, public</span></span><br><span class="line"><span class="hljs-keyword">SET</span> search_path <span class="hljs-keyword">TO</span> analytics, public;</span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> daily_revenue;   <span class="hljs-comment">-- resolves to analytics.daily_revenue</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- persist for a role or a database</span></span><br><span class="line"><span class="hljs-keyword">ALTER</span> ROLE app_user <span class="hljs-keyword">SET</span> search_path <span class="hljs-keyword">TO</span> app, public;</span><br><span class="line"><span class="hljs-keyword">ALTER</span> DATABASE shop <span class="hljs-keyword">SET</span> search_path <span class="hljs-keyword">TO</span> app, public;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>&quot;$user&quot;</code> expands to a schema named after the current role, if one exists — a tidy per-user sandbox pattern. <code>pg_catalog</code> is implicitly searched first, which is why <code>SELECT now()</code> works without qualification.</p>
<blockquote>
<p><strong>Watch out (PostgreSQL 15+):</strong> the <code>public</code> schema is no longer writable by every user. Since PG 15, <code>CREATE</code> on <code>public</code> is revoked from <code>PUBLIC</code> and the schema is owned by the database owner. Scripts written against PG 14 or earlier that create tables as a non-owner role will fail with <code>permission denied for schema public</code>. Grant explicitly: <code>GRANT CREATE ON SCHEMA public TO app_user;</code></p>
</blockquote>
<blockquote>
<p><strong>Common pitfall:</strong> a mutable <code>search_path</code> inside <code>SECURITY DEFINER</code> functions is a privilege-escalation vector. Always pin it: <code>CREATE FUNCTION ... SECURITY DEFINER SET search_path = pg_catalog, public</code>.</p>
</blockquote>
<h2 id="Roles-vs-users"><a href="#Roles-vs-users" class="headerlink" title="Roles vs users"></a>Roles vs users</h2>
<p>There is no separate &quot;user&quot; object. <code>CREATE USER</code> is literally an alias for <code>CREATE ROLE ... LOGIN</code>. A role is a single concept that can act as a login account, a group, or both.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> ROLE app_read; <p>Useful attributes: <code>SUPERUSER</code>, <code>CREATEDB</code>, <code>CREATEROLE</code>, <code>LOGIN</code>, <code>REPLICATION</code>, <code>BYPASSRLS</code>, <code>CONNECTION LIMIT n</code>, <code>VALID UNTIL 'ts'</code>.</p>
<p>PostgreSQL also ships <strong>predefined roles</strong> so you can avoid handing out superuser: <code>pg_read_all_data</code> and <code>pg_write_all_data</code> (14+), <code>pg_monitor</code>, <code>pg_read_all_settings</code>, <code>pg_signal_backend</code>, and <code>pg_maintain</code> (17+, allows <code>VACUUM</code>/<code>ANALYZE</code>/<code>REINDEX</code> without ownership).</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">GRANT</span> pg_monitor <span class="hljs-keyword">TO</span> observability;   <span class="hljs-comment">-- read all stats views, no data access needed</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The full security story — <code>pg_hba.conf</code>, row-level security, TLS — is Post 07.</p>

<p>Four choices in there worth naming now, each unpacked in Post 01:</p>
<ul>
<li><code>bigint GENERATED ALWAYS AS IDENTITY</code> rather than <code>serial</code> — identity is the SQL-standard form and avoids <code>serial</code>'s sequence-ownership surprises.</li>
<li><code>text</code> rather than <code>varchar(n)</code> — in PostgreSQL they perform identically, and <code>text</code> avoids arbitrary length limits that later require an <code>ALTER TABLE</code>.</li>
<li><code>numeric(12,2)</code> for money — never <code>float</code>. Binary floating point cannot represent <code>0.10</code> exactly.</li>
<li><code>timestamptz</code> rather than <code>timestamp</code> — it stores an absolute instant. <code>timestamp</code> stores a wall-clock reading with no timezone, which is almost never what you want.</li>
</ul>

<p><strong>Trick:</strong> <code>ALTER SYSTEM</code> is the right tool for infrastructure automation because it is transactional-ish, auditable, and survives config-management overwrites of <code>postgresql.conf</code>. </blockquote>
