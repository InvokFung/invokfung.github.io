PostgreSQL Course — 00 · Foundations and Setup

Created2026-06-05|Updated2026-06-05|Database > PostgreSQL
|Post View:

PostgreSQL is the default answer for "we need a relational database and we do not want to think about it again for ten years". It is ACID-compliant, MVCC-based, extensible down to custom types and index access methods, and — unusually for something this capable — genuinely free under a permissive licence with no enterprise edition holding features hostage. This post is the entry point of an eight-post course written as lecture notes: install it, drive psql, understand what the server processes actually do, and learn the cluster → database → schema → table hierarchy that trips up nearly everyone arriving from MySQL or MongoDB. Everything here targets PostgreSQL 17 and 18; where behaviour changed between versions, the version is stated.

Series map: 00 Foundations & Setup (this post) → 01 SQL Fundamentals & Data Types → 02 Joins, Aggregation & Window Functions → 03 Indexes & the Query Planner → 04 Query Optimization & Statistics → 05 Transactions, MVCC, Isolation & Locking → 06 Schema Design, Normalization & JSONB → 07 Operations, Backup, Replication & Security.

Learning Outcome

  • Explain what PostgreSQL is, where it sits against MySQL, SQLite, and document stores, and when it is the wrong choice.
  • Install a PostgreSQL 17/18 server on Windows, macOS, or Linux, or run one from a single Docker command.
  • Connect with psql and navigate using meta-commands (\l, \c, \dt, \d+, \du, \x, \timing).
  • Describe the process and memory architecture: postmaster, one backend per connection, shared_buffers, WAL writer, checkpointer, autovacuum.
  • Navigate the cluster → database → schema → table hierarchy and control resolution with search_path.
  • Distinguish roles from users and grant basic privileges.
  • Locate postgresql.conf / pg_hba.conf, read settings with SHOW, and change them with ALTER SYSTEM.

Chapter 1 — What PostgreSQL is (and is not)

Terminology

  • RDBMS — Relational Database Management System: data lives in tables of typed columns, related by keys, queried with SQL.
  • Cluster — one PostgreSQL server instance and the set of databases it manages, all sharing one data directory, one port, and one set of processes. Nothing to do with a distributed cluster.
  • Data directory (PGDATA) — the on-disk home of a cluster: table files, WAL, config, everything.
  • WAL — Write-Ahead Log. Every change is written to the log before it is written to the data files. WAL is the foundation of crash recovery, replication, and point-in-time recovery.
  • MVCC — Multi-Version Concurrency Control. Writers create new row versions instead of overwriting, so readers never block writers and writers never block readers. Covered in depth in Post 05.
  • Extension — a packaged bundle of SQL objects, types, functions, or index methods loadable with CREATE EXTENSION. PostGIS, pg_stat_statements, and pgvector are extensions.
  • psql — the official terminal client. Not just a query runner: it has its own meta-command language, scripting, and formatting.

Where it fits

PostgreSQL is an object-relational database: standard SQL plus a type system you can extend. The design bias is correctness first, then features, then raw speed. It will refuse to silently truncate your string, silently coerce 'abc' to 0, or silently accept February 30th.

Property PostgreSQL MySQL / MariaDB SQLite MongoDB
Model Relational + extensible types Relational Relational Document
Process model Process per connection Thread per connection In-process library Thread per connection
Concurrency MVCC, readers never block writers MVCC (InnoDB) File lock / WAL mode MVCC-ish, document-level
Strict typing Strong, will error on bad input Historically lenient Dynamic ("type affinity") Schema-optional
Window functions, CTEs Full, since 8.4 / 9.4 Since 8.0 Since 3.25 Aggregation framework
JSON jsonb with GIN indexing json column json1 extension Native
Extensibility Custom types, operators, index AMs Limited Limited N/A
Best at Anything relational, mixed workloads Simple high-read web workloads Embedded, single-file, tests Document-shaped, flexible schema

When PostgreSQL is the wrong choice

Being honest about this early saves grief:

  • Embedded / single-file / zero-admin. Use SQLite. A PostgreSQL cluster is a server with a lifecycle.
  • Petabyte analytical scans. PostgreSQL is row-oriented. A columnar warehouse (ClickHouse, BigQuery, DuckDB for local work) will beat it by an order of magnitude on wide aggregate scans. Note the escape hatch: pg_duckdb and citus narrow the gap.
  • Truly schema-free, per-tenant custom fields, high write fan-out. The document model may genuinely fit better — see the MongoDB course's SQL → MongoDB migration post for how that decision is actually made, including the honest note that most SQL workloads should stay on SQL.
  • Extreme single-key throughput with no relational needs. A key-value store will win.

Everything else — the overwhelming majority of application back-ends — is squarely PostgreSQL territory.

Trick: PostgreSQL's jsonb type covers a large fraction of "we need flexible fields" cases without leaving the relational model. Post 06 covers when the hybrid approach beats picking a side.

Chapter 2 — Installation

Version policy first: PostgreSQL ships a new major version every September and supports each major for five years. PostgreSQL 18 (released September 2025) is current; 17 is the safe choice if your tooling has not caught up. Minor releases (18.1, 18.2, …) are bug and security fixes only and are always safe to apply.

Windows

  1. Open postgresql.org/download/windows and take the EDB interactive installer.
  2. Run it. Accept the default data directory. Set a password for the postgres superuser and write it down — there is no recovery path that is less annoying than remembering it.
  3. Keep the default port 5432. Choose your locale (C or en_US are safe defaults).
  4. Stack Builder at the end is optional — skip it unless you need PostGIS today.

Meta-commands

Anything starting with a backslash is handled by the client, not the server. This is the actual reason psql beats a GUI for exploration.

Meta-command What it shows
\l List databases
\c dbname Connect to another database
\dt List tables in the search path

\dn List schemas

\df List functions
\du List roles and their attributes
\dx List installed extensions
\x Toggle expanded (one-column-per-line) output
\timing Toggle query timing
\e Open the last query in $EDITOR
\i file.sql Run a SQL file
\copy tbl FROM 'f.csv' CSV HEADER Client-side bulk load (no server file access needed)
\watch 2 Re-run the last query every 2 seconds
\conninfo Show current connection details
\h CREATE INDEX SQL syntax help
\? Meta-command help
\q Quit

A ~/.psqlrc worth having

\x auto alone is worth it: wide result rows flip to vertical layout automatically instead of wrapping into unreadable rubble.

Trick: \watch 2 turns any diagnostic query into a live dashboard. SELECT state, count(*) FROM pg_stat_activity GROUP BY 1; \watch 2 is a poor-person's connection monitor.

Chapter 4 — Process and memory architecture

PostgreSQL is multi-process, not multi-threaded. Understanding the process map explains most of its operational behaviour: why connections are expensive, why VACUUM exists, why a checkpoint can cause an I/O spike.

Terminology

  • Postmaster — the supervisor process (postgres -D $PGDATA). It listens on the port, authenticates, and forks one child per connection. It never executes queries itself.
  • Backend — one OS process serving exactly one client connection, for the lifetime of that connection.
  • Shared buffers — the cluster-wide page cache in shared memory. All backends read and write pages here.
  • Background worker — an auxiliary process: WAL writer, checkpointer, autovacuum, background writer, and (18+) I/O workers.

The map

What each auxiliary process does

Process Job Key settings
Checkpointer Periodically flushes all dirty shared buffers to disk and records a checkpoint in WAL, bounding crash-recovery time. checkpoint_timeout, max_wal_size, checkpoint_completion_target
Background writer Trickles dirty buffers out between checkpoints so backends rarely have to write a page themselves. bgwriter_delay, bgwriter_lru_maxpages
WAL writer Flushes WAL buffers to pg_wal/ so commits do not each pay the full write. wal_writer_delay, wal_buffers
Autovacuum launcher / workers Reclaim space from dead row versions produced by MVCC, and refresh planner statistics. Not optional. autovacuum_naptime, autovacuum_vacuum_scale_factor
Archiver Copies completed WAL segments to archive storage for PITR (Post 07). archive_mode, archive_command/archive_library
Logical replication launcher Starts apply workers for logical subscriptions. max_logical_replication_workers
I/O workers New in PostgreSQL 18: perform asynchronous reads on behalf of backends when io_method = worker (the default on most platforms). io_method, io_workers

Memory: shared vs per-backend

Setting Scope Rough starting point Notes
shared_buffers Cluster-wide 25% of RAM on a dedicated server Going far above 40% often loses to the OS page cache. Measure.
effective_cache_size Planner hint only 50–75% of RAM Allocates nothing; tells the planner how much caching to assume.
work_mem Per sort/hash node, per backend 4–64 MB, workload dependent This is the classic footgun: one query with several sorts and parallel workers can multiply it many times over.
maintenance_work_mem Per maintenance operation 256 MB – 2 GB Used by VACUUM, CREATE INDEX, ALTER TABLE. Raising it speeds index builds substantially.
temp_buffers Per backend 8 MB default Temporary table access only.
wal_buffers Cluster-wide -1 (auto = 1/32 of shared_buffers) Rarely needs manual tuning.

Common pitfall: treating work_mem as a global budget. It is granted per sort or hash operation. A plan with three hash joins running across four parallel workers can request roughly 3 × 4 × work_mem. Set it modestly at the cluster level and raise it per-session for known-heavy reporting queries.

Why connections are expensive

Each connection is a forked OS process with its own memory context — measurably heavier than a thread. A few hundred idle connections consume real RAM and add contention. The answer is a connection pooler (PgBouncer, pgcat, or a pool in your application driver), covered in Post 07. Rule of thumb: keep max_connections moderate (100–300) and pool in front of it rather than raising it to thousands.

Chapter 5 — Cluster, database, schema, table

This four-level hierarchy is the single biggest source of confusion for people arriving from MySQL, where "database" and "schema" are synonyms.

Two rules that follow from the picture:

  1. A connection belongs to exactly one database. You cannot join shop.customers to billing.invoices in a single query if they are separate databases. In psql, \c billing closes the connection and opens a new one. Cross-database access requires postgres_fdw or dblink.
  2. Schemas are the real namespacing unit. If two subsystems need to live in one query's reach, make them schemas in one database, not two databases.

search_path

Unqualified names are resolved against search_path, in order:

"$user" expands to a schema named after the current role, if one exists — a tidy per-user sandbox pattern. pg_catalog is implicitly searched first, which is why SELECT now() works without qualification.

Watch out (PostgreSQL 15+): the public schema is no longer writable by every user. Since PG 15, CREATE on public is revoked from PUBLIC and the schema is owned by the database owner. Scripts written against PG 14 or earlier that create tables as a non-owner role will fail with permission denied for schema public. Grant explicitly: GRANT CREATE ON SCHEMA public TO app_user;

Common pitfall: a mutable search_path inside SECURITY DEFINER functions is a privilege-escalation vector. Always pin it: CREATE FUNCTION ... SECURITY DEFINER SET search_path = pg_catalog, public.

Roles vs users

There is no separate "user" object. CREATE USER is literally an alias for CREATE ROLE ... LOGIN. A role is a single concept that can act as a login account, a group, or both.

Useful attributes: SUPERUSER, CREATEDB, CREATEROLE, LOGIN, REPLICATION, BYPASSRLS, CONNECTION LIMIT n, VALID UNTIL 'ts'.

PostgreSQL also ships predefined roles so you can avoid handing out superuser: pg_read_all_data and pg_write_all_data (14+), pg_monitor, pg_read_all_settings, pg_signal_backend, and pg_maintain (17+, allows VACUUM/ANALYZE/REINDEX without ownership).

The full security story — pg_hba.conf, row-level security, TLS — is Post 07.

Chapter 6 — First table, first query

Four choices in there worth naming now, each unpacked in Post 01:

  • bigint GENERATED ALWAYS AS IDENTITY rather than serial — identity is the SQL-standard form and avoids serial's sequence-ownership surprises.
  • text rather than varchar(n) — in PostgreSQL they perform identically, and text avoids arbitrary length limits that later require an ALTER TABLE.
  • numeric(12,2) for money — never float. Binary floating point cannot represent 0.10 exactly.
  • timestamptz rather than timestamp — it stores an absolute instant. timestamp stores a wall-clock reading with no timezone, which is almost never what you want.

Chapter 7 — Configuration

Where the files live

Ask the server rather than guessing — packaged installs put them in surprising places (Debian keeps config in /etc/postgresql/18/main/ while data lives in /var/lib/postgresql/18/main/):

File Purpose
postgresql.conf Main settings. Hand-edited.
postgresql.auto.conf Written by ALTER SYSTEM. Never hand-edit. Read last, so it overrides postgresql.conf.
pg_hba.conf Host-Based Authentication: who may connect, from where, over which method (scram-sha-256, peer, trust, …).
pg_ident.conf OS-user → database-role name mapping.

Reading settings

The context column tells you what a change costs:

context To apply a change
internal Fixed at initdb time — cannot change
postmaster Full server restart (shared_buffers, max_connections)
sighup Reload only (SELECT pg_reload_conf())
superuser / user SET it in the current session, immediately

Changing settings

Trick: ALTER SYSTEM is the right tool for infrastructure automation because it is transactional-ish, auditable, and survives config-management overwrites of postgresql.conf. But it is also the first place to look when a setting "mysteriously" ignores what postgresql.conf says — postgresql.auto.conf wins.
