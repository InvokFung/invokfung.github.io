<h2 id="The-selectivity-ratio"><a href="#The-selectivity-ratio" class="headerlink" title="The selectivity ratio"></a>The selectivity ratio</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line">totalKeysExamined / nReturned</span><br><span class="line">totalDocsExamined / nReturned</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Both should be close to <strong>1.0</strong>. If they balloon (10×, 100×), the index isn't selective enough — the query examined many entries to find a few matches.</p>
<p>Example:</p>
<ul>
<li><code>nReturned: 50</code>, <code>totalDocsExamined: 50</code> → perfect.</li>
<li><code>nReturned: 50</code>, <code>totalDocsExamined: 5000</code> → index returns too many candidates → wider compound index needed.</li>
<li><code>nReturned: 50</code>, <code>totalDocsExamined: 100000</code> → near-collection-scan; missing index.</li>
</ul>
<hr>
<h1 id="Chapter-3-—-IXSCAN-vs-COLLSCAN-—-the-binary-signal"><a href="#Chapter-3-—-IXSCAN-vs-COLLSCAN-—-the-binary-signal" class="headerlink" title="Chapter 3 — IXSCAN vs COLLSCAN — the binary signal"></a>Chapter 3 — IXSCAN vs COLLSCAN — the binary signal</h1>
<p><strong>IXSCAN</strong> = used an index. Cost: O(log n) for the seek + O(matches) for the scan.</p>
<p><strong>COLLSCAN</strong> = scanned every document. Cost: O(n) for n documents in the collection.</p>
<p>A COLLSCAN on a 10k-row collection is fast (a few ms). A COLLSCAN on a 10M-row collection is a multi-second outage.</p>
<pre><code class="language-json"><figure class="highlight json"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="json"><span class="line"><span class="hljs-attr">&quot;winningPlan&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span></span><br><span class="line">  <span class="hljs-attr">&quot;stage&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-string">&quot;COLLSCAN&quot;</span><span class="hljs-punctuation">,</span></span><br><span class="line">  <span class="hljs-attr">&quot;filter&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span> <span class="hljs-attr">&quot;status&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span> <span class="hljs-attr">&quot;$eq&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-string">&quot;paid&quot;</span> <span class="hljs-punctuation">}</span> <span class="hljs-punctuation">}</span></span><br><span class="line"><span class="hljs-punctuation">}</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Means: no index helped; the server read every document and filtered in memory. Add an index on <code>status</code> (or a compound covering this + other filters).</p>
<h2 id="Acceptable-COLLSCANs"><a href="#Acceptable-COLLSCANs" class="headerlink" title="Acceptable COLLSCANs"></a>Acceptable COLLSCANs</h2>
<ul>
<li>Tiny collections (&lt; few thousand docs).</li>
<li>Analytical jobs running off-peak.</li>
<li>One-time admin queries.</li>
</ul>
<p>For user-facing endpoints, never accept COLLSCAN.</p>
<hr>
<h1 id="Chapter-4-—-Sort-stage-—-the-silent-killer"><a href="#Chapter-4-—-Sort-stage-—-the-silent-killer" class="headerlink" title="Chapter 4 — Sort stage — the silent killer"></a>Chapter 4 — Sort stage — the silent killer</h1>
<pre><code class="language-json"><figure class="highlight json"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="json"><span class="line"><span class="hljs-attr">&quot;stage&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-string">&quot;SORT&quot;</span><span class="hljs-punctuation">,</span></span><br><span class="line"><span class="hljs-attr">&quot;sortPattern&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-punctuation">{</span> <span class="hljs-attr">&quot;at&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-number">-1</span> <span class="hljs-punctuation">}</span><span class="hljs-punctuation">,</span></span><br><span class="line"><span class="hljs-attr">&quot;memLimit&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-number">33554432</span><span class="hljs-punctuation">,</span></span><br><span class="line"><span class="hljs-attr">&quot;limitAmount&quot;</span><span class="hljs-punctuation">:</span> <span class="hljs-number">20</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A <code>SORT</code> stage means the documents came out in the wrong order, and the server is sorting them in RAM after retrieval. For large result sets:</p>
<ul>
<li>Slow (sort is O(n log n) on documents not index entries).</li>
<li>Fails entirely if sort exceeds 32 MB by default (<code>OperationFailed: Sort exceeded memory limit</code>).</li>
</ul>
<p>Fix: build an index that delivers documents in sort order.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">at</span>: -<span class="hljs-number">1</span> })</span><br><span class="line"> </span><br><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span> }).<span class="hljs-title function_">sort</span>({ <span class="hljs-attr">at</span>: -<span class="hljs-number">1</span> })       <span class="hljs-comment">// no SORT stage in plan</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For aggregations exceeding sort memory, pass <code>{ allowDiskUse: true }</code> (slower, uses disk).</p>

<h1 id="Chapter-6-—-Plan-cache"><a href="#Chapter-6-—-Plan-cache" class="headerlink" title="Chapter 6 — Plan cache"></a>Chapter 6 — Plan cache</h1>

<p>If data distribution changes (a field becomes much more selective), the cached plan may become wrong. The planner re-evaluates every ~1000 query executions; you can force it:</p>

<p>Inspect:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">aggregate</span>([{ <span class="hljs-attr">$planCacheStats</span>: {} }])</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

Confirm in production with the profiler / Atlas Performance Advisor.</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A &quot;slow query investigation&quot; rarely takes more than 10 minutes once you know the flow.</p>

<h1 id="Chapter-10-—-Atlas-Performance-Advisor"><a href="#Chapter-10-—-Atlas-Performance-Advisor" class="headerlink" title="Chapter 10 — Atlas Performance Advisor"></a>Chapter 10 — Atlas Performance Advisor</h1>
<p>Atlas surfaces:</p>
<ul>
<li><strong>Suggested indexes</strong> — based on actual slow queries observed.</li>
<li><strong>Suggested redundant indexes</strong> — overlap or unused.</li>
<li><strong>Query Insights</strong> — slow queries grouped by shape with sample explains.</li>
<li><strong>Real-time / historical performance</strong> — CPU, memory, query rate, ticket queue.</li>
</ul>
<p>Use it heavily in production. For local / self-hosted, the equivalent is the profiler + log aggregation.</p>
<hr>
<h1 id="Chapter-11-—-hint-maxTimeMS-comment-—-the-safety-trio"><a href="#Chapter-11-—-hint-maxTimeMS-comment-—-the-safety-trio" class="headerlink" title="Chapter 11 — .hint, .maxTimeMS, .comment — the safety trio"></a>Chapter 11 — <code>.hint</code>, <code>.maxTimeMS</code>, <code>.comment</code> — the safety trio</h1>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span> })</span><br><span class="line">  .<span class="hljs-title function_">hint</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">at</span>: -<span class="hljs-number">1</span> })</span><br><span class="line">  .<span class="hljs-title function_">maxTimeMS</span>(<span class="hljs-number">500</span>)</span><br><span class="line">  .<span class="hljs-title function_">comment</span>(<span class="hljs-string">&quot;dashboard-orders-list&quot;</span>)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><code>hint</code> — force index when the planner needs a nudge.</li>
<li><code>maxTimeMS</code> — abort runaway queries (always set for user-facing endpoints).</li>
<li><code>comment</code> — tag in the profiler / <code>currentOp</code> for traceability.</li>
</ul>
<p>Production endpoint pattern: always set <code>maxTimeMS</code>; add <code>comment</code> per endpoint; only <code>hint</code> after <code>explain</code> justifies.</p>

<h1 id="Chapter-12-—-Currentop-killop"><a href="#Chapter-12-—-Currentop-killop" class="headerlink" title="Chapter 12 — Currentop / killop"></a>Chapter 12 — Currentop / killop</h1>
<p>See in-flight operations:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-title function_">currentOp</span>()                                          <span class="hljs-comment">// all ops</span></span><br><span class="line">db.<span class="hljs-title function_">currentOp</span>({ <span class="hljs-string">&quot;secs_running&quot;</span>: { <span class="hljs-attr">$gt</span>: <span class="hljs-number">5</span> } })            <span class="hljs-comment">// long-running</span></span><br><span class="line">db.<span class="hljs-title function_">currentOp</span>({ <span class="hljs-string">&quot;command.comment&quot;</span>: <span class="hljs-string">&quot;dashboard-orders-list&quot;</span> })   <span class="hljs-comment">// your tagged ops</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Kill a runaway:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-title function_">killOp</span>(opid)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>(<code>opid</code> from <code>currentOp</code> output.) Reactive triage tool when something is consuming the cluster.</p>

<h1 id="Chapter-13-—-Common-pitfalls"><a href="#Chapter-13-—-Common-pitfalls" class="headerlink" title="Chapter 13 — Common pitfalls"></a>Chapter 13 — Common pitfalls</h1>
<table>
<thead>
<tr>
<th>Symptom</th>
<th>Cause</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>COLLSCAN on a key query</td>
<td>no index covering it</td>
<td>add compound index ESR-style</td>
</tr>
<tr>
<td>IXSCAN but <code>totalDocsExamined</code> huge</td>
<td>index not selective enough</td>
<td>add more fields to the compound</td>
</tr>
<tr>
<td>In-memory SORT stage</td>
<td>sort doesn't match any index</td>
<td>build index that matches sort order</td>
</tr>
<tr>
<td>Query fast in mongosh slow from app</td>
<td>different connection settings; or driver-side serialisation</td>
<td>profile the app path; check driver pool</td>
</tr>
<tr>
<td>Query slow only sometimes</td>
<td>plan flip-flop; data skew</td>
<td>check plan cache; analyse selectivity per parameter</td>
</tr>
<tr>
<td>New index &quot;doesn't help&quot;</td>
<td>wrong order (violates ESR); or planner chose old cached plan</td>
<td>check explain; clear plan cache</td>
</tr>
<tr>
<td>Sort exceeded memory</td>
<td>unindexed sort over big result</td>
<td>index; or <code>{ allowDiskUse: true }</code> for aggregation</td>
</tr>
<tr>
<td>Slow without obvious reason</td>
<td>hot collection lock or saturation elsewhere</td>
<td>check <code>currentOp</code> + server-status metrics</td>
</tr>
</tbody>
</table>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Force-COLLSCAN"><a href="#Exercise-1-—-Force-COLLSCAN" class="headerlink" title="Exercise 1 — Force COLLSCAN"></a>Exercise 1 — Force COLLSCAN</h2>
<p>Take any query on the seed <code>orders</code> collection (which has no extra indexes yet). Run <code>.explain(&quot;executionStats&quot;)</code>. Confirm COLLSCAN.</p>
<h2 id="Exercise-2-—-Add-verify"><a href="#Exercise-2-—-Add-verify" class="headerlink" title="Exercise 2 — Add + verify"></a>Exercise 2 — Add + verify</h2>
<p>Create <code>{ user_id: 1, at: -1 }</code> on orders. Repeat the query. Confirm IXSCAN, <code>totalDocsExamined</code> ≈ <code>nReturned</code>.</p>
<h2 id="Exercise-3-—-Sort-stage"><a href="#Exercise-3-—-Sort-stage" class="headerlink" title="Exercise 3 — Sort stage"></a>Exercise 3 — Sort stage</h2>
<p>Run <code>find({ user_id: 1 }).sort({ status: 1 })</code>. Check for a SORT stage. Build the compound <code>{ user_id: 1, status: 1 }</code>. Re-explain — no SORT.</p>
<h2 id="Exercise-4-—-Selectivity-ratio"><a href="#Exercise-4-—-Selectivity-ratio" class="headerlink" title="Exercise 4 — Selectivity ratio"></a>Exercise 4 — Selectivity ratio</h2>
<p>Insert 100k synthetic orders. Query <code>find({ status: &quot;paid&quot; })</code> without an index — note <code>totalDocsExamined</code>. With a <code>{ status: 1 }</code> index but <code>paid</code> is 80% of data — note the ratio is still close to 1 but <code>nReturned</code> is large (the index is correct but the query just matches a lot).</p>
<h2 id="Exercise-5-—-Find-unused"><a href="#Exercise-5-—-Find-unused" class="headerlink" title="Exercise 5 — Find unused"></a>Exercise 5 — Find unused</h2>
<p>Run <code>db.orders.aggregate([{ $indexStats: {} }])</code>. Hide any with <code>ops: 0</code>. Wait a few hours of normal traffic. Drop those without regression.</p>
<h2 id="Exercise-6-—-Profiler"><a href="#Exercise-6-—-Profiler" class="headerlink" title="Exercise 6 — Profiler"></a>Exercise 6 — Profiler</h2>
<p>Enable profiler at <code>slowms: 50</code> on the <code>shop</code> DB. Run various queries. Inspect <code>system.profile</code>. Identify the slowest query shapes.</p>

<th>What</th>
<th>How</th>

</tr>

<td><code>db.killOp(opid)</code></td>
</tr>
<tr>

<td><code>db.currentOp({ secs_running: { $gt: 5 } })</code></td>
</tr>
<tr>
<td>Tag a query</td>
<td><code>.comment(&quot;name&quot;)</code></td>
</tr>
<tr>
<td>Abort safety</td>

</tr>

</tr>

</tr>
<tr>

<td><code>aggregate([{ $planCacheStats: {} }])</code></td>
</tr>

</tr>
<tr>
<td>Slow log read</td>
<td><code>db.system.profile.find({ ... })</code></td>
</tr>
<tr>
<td>Atlas</td>
<td>Performance Advisor + Query Insights</td>
</tr>

<td>Diagnostic flow</td>
<td>reproduce → explain → IXSCAN? → ratio? → sort? → hint/index</td>
</tr>
