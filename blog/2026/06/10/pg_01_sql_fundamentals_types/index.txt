11:T1c6c6,<p>Type choices are the most expensive decisions in a schema. A wrong index costs a <code>CREATE INDEX</code>; a wrong column type costs a migration, a rewrite, a maintenance window, and — if the type was <code>float</code> for money or <code>timestamp</code> for an instant — a class of bugs that ships to production and only surfaces at quarter-end or the daylight-saving boundary. This post covers the DDL and DML you will write every day, then spends most of its length on the type system, <code>NULL</code> semantics, and constraints, because those are the parts you cannot cheaply change later. Examples target <strong>PostgreSQL 17/18</strong>; version-specific behaviour is called out inline.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Write DDL: <code>CREATE</code>, <code>ALTER</code>, and <code>DROP TABLE</code>, including the <code>ALTER</code> forms that avoid a full table rewrite.</li>
<li>Write DML confidently: <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code>, <code>RETURNING</code>, and upserts via <code>ON CONFLICT</code>.</li>
<li>Choose correctly among the integer family, <code>numeric</code> vs floating point, <code>text</code> vs <code>varchar</code>, enum vs lookup table.</li>
<li>Explain why <code>timestamptz</code> is the default correct answer and <code>timestamp</code> almost never is.</li>
<li>Predict the result of any expression involving <code>NULL</code> under three-valued logic.</li>
<li>Apply the six constraint types, including <code>EXCLUDE</code>, and add them to live tables without long locks.</li>
<li>Explain the difference between identity columns and <code>serial</code>, and why new work uses identity.</li>

<h1 id="Chapter-1-—-DDL-creating-and-evolving-tables"><a href="#Chapter-1-—-DDL-creating-and-evolving-tables" class="headerlink" title="Chapter 1 — DDL: creating and evolving tables"></a>Chapter 1 — DDL: creating and evolving tables</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>DDL</strong> — Data Definition Language: <code>CREATE</code>, <code>ALTER</code>, <code>DROP</code>. Changes the shape of the database.</li>
<li><strong>DML</strong> — Data Manipulation Language: <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code>, <code>SELECT</code>, <code>MERGE</code>. Changes or reads the contents.</li>
<li><strong>Table rewrite</strong> — an <code>ALTER TABLE</code> variant that must rebuild every row on disk. Holds an <code>ACCESS EXCLUSIVE</code> lock for the duration, which blocks <em>everything</em>, including reads.</li>
<li><strong>Catalog</strong> — the system tables (<code>pg_class</code>, <code>pg_attribute</code>, <code>pg_constraint</code>, …) describing the database to itself.</li>
<li><strong>Domain</strong> — a named, reusable type with constraints attached.</li>
</ul>

<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> IF <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">EXISTS</span> products (...);</span><br><span class="line"><span class="hljs-keyword">CREATE</span> TEMPORARY <span class="hljs-keyword">TABLE</span> scratch (...);            <span class="hljs-comment">-- dropped at session end</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> UNLOGGED <span class="hljs-keyword">TABLE</span> cache_rows (...);          <span class="hljs-comment">-- no WAL: fast, but lost on crash</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> archive_2025 (<span class="hljs-keyword">LIKE</span> orders INCLUDING <span class="hljs-keyword">ALL</span>);   <span class="hljs-comment">-- clone structure</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> paid_orders <span class="hljs-keyword">AS</span> <span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> orders <span class="hljs-keyword">WHERE</span> status <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;paid&#x27;</span>;  <span class="hljs-comment">-- CTAS</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

</blockquote>

<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">DROP</span> <span class="hljs-keyword">TABLE</span> products;</span><br><span class="line"><span class="hljs-keyword">DROP</span> <span class="hljs-keyword">TABLE</span> IF <span class="hljs-keyword">EXISTS</span> products CASCADE;   <span class="hljs-comment">-- CASCADE also drops dependent views, FKs</span></span><br><span class="line"><span class="hljs-keyword">TRUNCATE</span> products;                       <span class="hljs-comment">-- delete all rows, fast, resets nothing else</span></span><br><span class="line"><span class="hljs-keyword">TRUNCATE</span> products RESTART <span class="hljs-keyword">IDENTITY</span> CASCADE;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="RETURNING"><a href="#RETURNING" class="headerlink" title="RETURNING"></a><code>RETURNING</code></h2>
<p>Every one of <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code> (and <code>MERGE</code> since PostgreSQL 17) can return rows. This eliminates the read-after-write round trip that most ORMs would otherwise perform.</p>

<p>A pattern worth knowing — a transactional queue pop, using <code>RETURNING</code> with <code>FOR UPDATE SKIP LOCKED</code> (locking is Post 05):</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">DELETE</span> <span class="hljs-keyword">FROM</span> job_queue</span><br><span class="line"><span class="hljs-keyword">WHERE</span> id <span class="hljs-operator">=</span> (</span><br><span class="line">    <span class="hljs-keyword">SELECT</span> id <span class="hljs-keyword">FROM</span> job_queue</span><br><span class="line">    <span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> priority <span class="hljs-keyword">DESC</span>, id</span><br><span class="line">    <span class="hljs-keyword">FOR</span> <span class="hljs-keyword">UPDATE</span> <span class="hljs-keyword">SKIP</span> LOCKED</span><br><span class="line">    LIMIT <span class="hljs-number">1</span></span><br><span class="line">)</span><br><span class="line">RETURNING id, payload;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>PostgreSQL uses <code>FROM</code> / <code>USING</code> rather than the <code>UPDATE … JOIN</code> syntax of MySQL:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">UPDATE</span> orders o</span><br><span class="line"><span class="hljs-keyword">SET</span>    customer_country <span class="hljs-operator">=</span> c.country</span><br><span class="line"><span class="hljs-keyword">FROM</span>   customers c</span><br><span class="line"><span class="hljs-keyword">WHERE</span>  c.id <span class="hljs-operator">=</span> o.customer_id;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">DELETE</span> <span class="hljs-keyword">FROM</span> order_items oi</span><br><span class="line"><span class="hljs-keyword">USING</span>  orders o</span><br><span class="line"><span class="hljs-keyword">WHERE</span>  o.id <span class="hljs-operator">=</span> oi.order_id</span><br><span class="line">  <span class="hljs-keyword">AND</span>  o.status <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;cancelled&#x27;</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Upsert-ON-CONFLICT"><a href="#Upsert-ON-CONFLICT" class="headerlink" title="Upsert: ON CONFLICT"></a>Upsert: <code>ON CONFLICT</code></h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- ignore duplicates</span></span><br><span class="line"><span class="hljs-keyword">INSERT</span> <span class="hljs-keyword">INTO</span> products (sku, title, price)</span><br><span class="line"><span class="hljs-keyword">VALUES</span> (<span class="hljs-string">&#x27;A-1&#x27;</span>, <span class="hljs-string">&#x27;Widget&#x27;</span>, <span class="hljs-number">9.99</span>)</span><br><span class="line"><span class="hljs-keyword">ON</span> CONFLICT (sku) DO NOTHING;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- update on conflict; EXCLUDED is the row that would have been inserted</span></span><br><span class="line"><span class="hljs-keyword">INSERT</span> <span class="hljs-keyword">INTO</span> products (sku, title, price, updated_at)</span><br><span class="line"><span class="hljs-keyword">VALUES</span> (<span class="hljs-string">&#x27;A-1&#x27;</span>, <span class="hljs-string">&#x27;Widget Mk II&#x27;</span>, <span class="hljs-number">11.99</span>, now())</span><br><span class="line"><span class="hljs-keyword">ON</span> CONFLICT (sku) DO <span class="hljs-keyword">UPDATE</span></span><br><span class="line"><span class="hljs-keyword">SET</span> title      <span class="hljs-operator">=</span> EXCLUDED.title,</span><br><span class="line">    price      <span class="hljs-operator">=</span> EXCLUDED.price,</span><br><span class="line">    updated_at <span class="hljs-operator">=</span> EXCLUDED.updated_at</span><br><span class="line"><span class="hljs-keyword">WHERE</span> products.price <span class="hljs-keyword">IS</span> <span class="hljs-keyword">DISTINCT</span> <span class="hljs-keyword">FROM</span> EXCLUDED.price   <span class="hljs-comment">-- skip no-op updates</span></span><br><span class="line">RETURNING id, (xmax <span class="hljs-operator">=</span> <span class="hljs-number">0</span>) <span class="hljs-keyword">AS</span> was_inserted;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Rules that matter:</p>
<ul>
<li>The <strong>conflict target</strong> must be backed by a unique index or constraint. <code>ON CONFLICT DO UPDATE</code> requires a target; <code>DO NOTHING</code> may omit one (in which case it swallows <em>any</em> conflict).</li>
<li>Inside <code>DO UPDATE</code>, the proposed row is <code>EXCLUDED.*</code> and the existing row is <code>tablename.*</code>.</li>
<li>To target a <strong>partial</strong> unique index, repeat its predicate: <code>ON CONFLICT (email) WHERE deleted_at IS NULL DO UPDATE …</code>.</li>
<li><code>xmax = 0</code> in <code>RETURNING</code> distinguishes an insert from an update — a widely used idiom, though it relies on an implementation detail.</li>
<li>A single statement cannot update the same row twice: <code>ON CONFLICT DO UPDATE command cannot affect row a second time</code>. De-duplicate the input first.</li>
</ul>
<h2 id="MERGE"><a href="#MERGE" class="headerlink" title="MERGE"></a><code>MERGE</code></h2>
<p><code>MERGE</code> arrived in <strong>PostgreSQL 15</strong> and gained <code>RETURNING</code> in <strong>PostgreSQL 17</strong>. It is the SQL-standard multi-action form, and unlike <code>ON CONFLICT</code> it does not require a unique constraint — but it also gives no built-in concurrency guarantee, so concurrent <code>MERGE</code>s can raise serialization failures.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">MERGE</span> <span class="hljs-keyword">INTO</span> products p</span><br><span class="line"><span class="hljs-keyword">USING</span> staging_products s <span class="hljs-keyword">ON</span> p.sku <span class="hljs-operator">=</span> s.sku</span><br><span class="line"><span class="hljs-keyword">WHEN</span> MATCHED <span class="hljs-keyword">AND</span> s.price <span class="hljs-keyword">IS</span> <span class="hljs-keyword">DISTINCT</span> <span class="hljs-keyword">FROM</span> p.price <span class="hljs-keyword">THEN</span></span><br><span class="line">    <span class="hljs-keyword">UPDATE</span> <span class="hljs-keyword">SET</span> price <span class="hljs-operator">=</span> s.price, updated_at <span class="hljs-operator">=</span> now()</span><br><span class="line"><span class="hljs-keyword">WHEN</span> <span class="hljs-keyword">NOT</span> MATCHED <span class="hljs-keyword">THEN</span></span><br><span class="line">    <span class="hljs-keyword">INSERT</span> (sku, title, price) <span class="hljs-keyword">VALUES</span> (s.sku, s.title, s.price)</span><br><span class="line">RETURNING merge_action(), p.id;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Guidance: use <code>ON CONFLICT</code> for concurrent single-row upserts from application code; use <code>MERGE</code> for batch reconciliation against a staging table.</p>

<h3 id="bigint-for-keys-always"><a href="#bigint-for-keys-always" class="headerlink" title="bigint for keys, always"></a><code>bigint</code> for keys, always</h3>
<p><code>integer</code> exhausts at 2.1 billion. That sounds distant until you learn that a sequence advances on <strong>failed</strong> inserts too — every <code>ON CONFLICT DO NOTHING</code> that conflicts still burns an id. The <code>integer → bigint</code> migration on a hot table is a full rewrite with an <code>ACCESS EXCLUSIVE</code> lock. The four extra bytes per row are cheap by comparison.</p>
<h3 id="numeric-vs-floating-point-for-money"><a href="#numeric-vs-floating-point-for-money" class="headerlink" title="numeric vs floating point for money"></a><code>numeric</code> vs floating point for money</h3>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-number">0.1</span>::<span class="hljs-type">double precision</span> <span class="hljs-operator">+</span> <span class="hljs-number">0.2</span>::<span class="hljs-type">double precision</span>;   <span class="hljs-comment">-- 0.30000000000000004</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-number">0.1</span>::<span class="hljs-type">numeric</span> <span class="hljs-operator">+</span> <span class="hljs-number">0.2</span>::<span class="hljs-type">numeric</span>;                     <span class="hljs-comment">-- 0.3</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-built_in">sum</span>(x) <span class="hljs-keyword">FROM</span> (<span class="hljs-keyword">SELECT</span> <span class="hljs-number">0.1</span>::<span class="hljs-type">double precision</span> <span class="hljs-keyword">FROM</span> generate_series(<span class="hljs-number">1</span>,<span class="hljs-number">10</span>)) t(x);</span><br><span class="line"><span class="hljs-comment">-- 0.9999999999999999</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-built_in">sum</span>(x) <span class="hljs-keyword">FROM</span> (<span class="hljs-keyword">SELECT</span> <span class="hljs-number">0.1</span>::<span class="hljs-type">numeric</span> <span class="hljs-keyword">FROM</span> generate_series(<span class="hljs-number">1</span>,<span class="hljs-number">10</span>)) t(x);</span><br><span class="line"><span class="hljs-comment">-- 1.0</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Binary floating point cannot represent <code>0.1</code> exactly. Financial code that sums floats produces drift that accumulates silently and fails reconciliation. Use <code>numeric(12,2)</code> for currency amounts, or store integer minor units (cents) in a <code>bigint</code> if you need maximum arithmetic speed. <code>numeric</code> is slower — it is arbitrary-precision software arithmetic, not a CPU instruction — but the correctness is non-negotiable for money.</p>
<blockquote>
<p><strong>Watch out:</strong> <code>NaN</code> in <code>numeric</code> compares as <em>equal to itself and greater than all other values</em>, which differs from the IEEE 754 rule used for <code>double precision</code>, where <code>NaN = NaN</code> is false. This is documented and deliberate, so that <code>numeric</code> can be sorted and indexed.</p>
</blockquote>

<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line">sku text <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span> <span class="hljs-keyword">CHECK</span> (length(sku) <span class="hljs-keyword">BETWEEN</span> <span class="hljs-number">3</span> <span class="hljs-keyword">AND</span> <span class="hljs-number">32</span>)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h3 id="Why-timestamptz-is-almost-always-right"><a href="#Why-timestamptz-is-almost-always-right" class="headerlink" title="Why timestamptz is almost always right"></a>Why <code>timestamptz</code> is almost always right</h3>
<p>The name is misleading. <code>timestamptz</code> does <strong>not</strong> store a timezone. It stores an absolute point in time (microseconds from an epoch, in UTC). On input, a value is converted from the session's <code>TimeZone</code> to UTC; on output, from UTC back to the session's <code>TimeZone</code>. It is the type that answers &quot;when did this happen?&quot; unambiguously anywhere on Earth.</p>
<p><code>timestamp</code> (without time zone) stores a wall-clock reading with no anchor. Two servers in different regions will disagree about what instant it names, and it cannot represent the DST fall-back hour unambiguously.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SET</span> TimeZone <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;UTC&#x27;</span>;</span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-string">&#x27;2026-03-29 01:30:00+00&#x27;</span>::timestamptz;   <span class="hljs-comment">-- 2026-03-29 01:30:00+00</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SET</span> TimeZone <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;Europe/London&#x27;</span>;</span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-string">&#x27;2026-03-29 01:30:00+00&#x27;</span>::timestamptz;   <span class="hljs-comment">-- 2026-03-29 02:30:00+01</span></span><br><span class="line"><span class="hljs-comment">-- Same instant. Even then, store the IANA zone name alongside it in a separate column.</p>

<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> now() <span class="hljs-operator">+</span> <span class="hljs-type">interval</span> <span class="hljs-string">&#x27;1 month 3 days&#x27;</span>;</span><br><span class="line"><span class="hljs-keyword">SELECT</span> age(timestamptz <span class="hljs-string">&#x27;2026-06-02&#x27;</span>, timestamptz <span class="hljs-string">&#x27;1990-01-15&#x27;</span>);  <span class="hljs-comment">-- 36 years 4 mons 18 days</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> justify_interval(<span class="hljs-type">interval</span> <span class="hljs-string">&#x27;90 days&#x27;</span>);                     <span class="hljs-comment">-- 3 mons</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-built_in">extract</span>(epoch <span class="hljs-keyword">FROM</span> <span class="hljs-type">interval</span> <span class="hljs-string">&#x27;2 hours 30 minutes&#x27;</span>);        <span class="hljs-comment">-- 9000</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

This is correct calendar arithmetic, not a rounding bug.</p>
<h2 id="UUID"><a href="#UUID" class="headerlink" title="UUID"></a>UUID</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> events (id uuid <span class="hljs-keyword">PRIMARY</span> KEY <span class="hljs-keyword">DEFAULT</span> gen_random_uuid(), ...);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>16 bytes, stored binary. <code>gen_random_uuid()</code> (UUIDv4) is built in since <strong>PostgreSQL 13</strong> — no <code>pgcrypto</code> needed. <strong>PostgreSQL 18</strong> adds <code>uuidv4()</code> and <code>uuidv7()</code> as standard functions.</p>
<p>The trade-off against <code>bigint</code> identity:</p>
<ul>
<li>UUIDv4 is random, so inserts land at random points in the primary-key B-tree. That causes page splits, poor cache locality, and index bloat on high-insert tables.</li>
<li><strong>UUIDv7</strong> is time-ordered in its high bits, which restores the append-at-the-right-edge insert pattern of a sequence while keeping global uniqueness and non-guessability. On PG 18, <code>uuidv7()</code> is the right default when you want UUIDs.</li>
<li><code>bigint</code> identity remains smallest and fastest, at the cost of being guessable and requiring a central sequence.</li>
</ul>

<h2 id="bytea-and-other-types-worth-knowing"><a href="#bytea-and-other-types-worth-knowing" class="headerlink" title="bytea and other types worth knowing"></a><code>bytea</code> and other types worth knowing</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-string">&#x27;\x48656c6c6f&#x27;</span>::bytea;          <span class="hljs-comment">-- hex input/output format</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> encode(digest(<span class="hljs-string">&#x27;x&#x27;</span>,<span class="hljs-string">&#x27;sha256&#x27;</span>), <span class="hljs-string">&#x27;hex&#x27;</span>);   <span class="hljs-comment">-- needs pgcrypto</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>bytea</code> holds arbitrary binary. It is fine for small blobs (thumbnails, hashes, encrypted tokens); it is the wrong place for user-uploaded files — put those in object storage and keep the key in a <code>text</code> column.</p>
<p>Also in the standard distribution and worth remembering: <code>inet</code>/<code>cidr</code>/<code>macaddr</code> for networking, <code>tsvector</code>/<code>tsquery</code> for full-text search, <code>int4range</code>/<code>tstzrange</code>/<code>daterange</code> for ranges, <code>point</code>/<code>polygon</code> for basic geometry, <code>json</code>/<code>jsonb</code> (Post 06), and <code>xml</code>.</p>

<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> DOMAIN email <span class="hljs-keyword">AS</span> text</span><br><span class="line">  <span class="hljs-keyword">CHECK</span> (<span class="hljs-keyword">VALUE</span> <span class="hljs-operator">~</span> <span class="hljs-string">&#x27;^[^@\s]+@[^@\s]+\.[^@\s]+$&#x27;</span>);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">CREATE</span> DOMAIN positive_money <span class="hljs-keyword">AS</span> <span class="hljs-type">numeric</span>(<span class="hljs-number">12</span>,<span class="hljs-number">2</span>) <span class="hljs-keyword">CHECK</span> (<span class="hljs-keyword">VALUE</span> <span class="hljs-operator">&gt;=</span> <span class="hljs-number">0</span>);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> users (id <span class="hljs-type">bigint</span>, contact email <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span>, balance positive_money);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-4-—-NULL-and-three-valued-logic"><a href="#Chapter-4-—-NULL-and-three-valued-logic" class="headerlink" title="Chapter 4 — NULL and three-valued logic"></a>Chapter 4 — <code>NULL</code> and three-valued logic</h1>
<p><code>NULL</code> is not a value. It is a marker meaning <em>unknown</em>. Every comparison involving it yields <code>NULL</code> (neither true nor false), and SQL's <code>WHERE</code> clause keeps only rows where the predicate is <strong>true</strong> — so <code>NULL</code> behaves like false at filter time but not in any other context. This asymmetry is the source of an enormous share of production SQL bugs.</p>

<h2 id="The-NOT-IN-trap"><a href="#The-NOT-IN-trap" class="headerlink" title="The NOT IN trap"></a>The <code>NOT IN</code> trap</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Intent: customers with no orders</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> customers</span><br><span class="line"><span class="hljs-keyword">WHERE</span> id <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">IN</span> (<span class="hljs-keyword">SELECT</span> customer_id <span class="hljs-keyword">FROM</span> orders);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>Three safe rewrites, in order of preference:</p>

<h1 id="Chapter-5-—-Constraints"><a href="#Chapter-5-—-Constraints" class="headerlink" title="Chapter 5 — Constraints"></a>Chapter 5 — Constraints</h1>

<h3 id="PRIMARY-KEY"><a href="#PRIMARY-KEY" class="headerlink" title="PRIMARY KEY"></a><code>PRIMARY KEY</code></h3>
<p><code>NOT NULL</code> + <code>UNIQUE</code> + designated as the table's identity. One per table. Backed by a unique B-tree index automatically.</p>

<p><code>ON UPDATE</code> takes the same set. PostgreSQL 15+ allows column lists: <code>ON DELETE SET NULL (col_a)</code> for composite keys.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders</span><br><span class="line">  <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">CONSTRAINT</span> orders_customer_fk</span><br><span class="line">  <span class="hljs-keyword">FOREIGN</span> KEY (customer_id) <span class="hljs-keyword">REFERENCES</span> customers(id)</span><br><span class="line">  <span class="hljs-keyword">ON</span> <span class="hljs-keyword">DELETE</span> CASCADE <span class="hljs-keyword">ON</span> <span class="hljs-keyword">UPDATE</span> CASCADE</span><br><span class="line">  DEFERRABLE INITIALLY IMMEDIATE;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> PostgreSQL does <strong>not</strong> automatically index the referencing column. Every <code>DELETE</code> on the parent then triggers a sequential scan of the child to check the constraint. Index every foreign key column yourself — this is one of the most common causes of mysteriously slow deletes.</p>
</blockquote>
<blockquote>
<p><strong>Trick (zero-downtime FK):</strong> <code>ADD CONSTRAINT … FOREIGN KEY … NOT VALID</code> takes a <code>SHARE ROW EXCLUSIVE</code> lock and skips the existing-data scan; new rows are enforced immediately. Follow with <code>ALTER TABLE … VALIDATE CONSTRAINT …</code>, which scans under a lock that permits concurrent reads and writes.</p>
</blockquote>
<h3 id="UNIQUE"><a href="#UNIQUE" class="headerlink" title="UNIQUE"></a><code>UNIQUE</code></h3>
<p>Backed by a unique index. Multiple <code>NULL</code>s are permitted by default because <code>NULL</code>s are distinct. <strong>PostgreSQL 15+</strong> can change that:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> t (a <span class="hljs-type">int</span>, b <span class="hljs-type">int</span>, <span class="hljs-keyword">UNIQUE</span> NULLS <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">DISTINCT</span> (a, b));</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For conditional uniqueness — &quot;email unique among non-deleted users&quot; — use a <strong>partial unique index</strong> rather than a constraint, since constraints cannot carry a predicate:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">UNIQUE</span> INDEX users_email_active_uq</span><br><span class="line">  <span class="hljs-keyword">ON</span> users (email) <span class="hljs-keyword">WHERE</span> deleted_at <span class="hljs-keyword">IS</span> <span class="hljs-keyword">NULL</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h3 id="CHECK"><a href="#CHECK" class="headerlink" title="CHECK"></a><code>CHECK</code></h3>
<p>Any boolean expression over the row's own columns. It must be immutable and may not reference other tables or <code>now()</code>.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CHECK</span> (price <span class="hljs-operator">&gt;=</span> <span class="hljs-number">0</span>)</span><br><span class="line"><span class="hljs-keyword">CHECK</span> (status <span class="hljs-keyword">IN</span> (<span class="hljs-string">&#x27;pending&#x27;</span>,<span class="hljs-string">&#x27;paid&#x27;</span>,<span class="hljs-string">&#x27;shipped&#x27;</span>,<span class="hljs-string">&#x27;cancelled&#x27;</span>))</span><br><span class="line"><span class="hljs-keyword">CHECK</span> (ends_at <span class="hljs-operator">&gt;</span> starts_at)</span><br><span class="line"><span class="hljs-keyword">CHECK</span> (email <span class="hljs-operator">~</span> <span class="hljs-string">&#x27;^[^@]+@[^@]+$&#x27;</span>)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A <code>CHECK</code> that evaluates to <code>NULL</code> <strong>passes</strong>. <code>CHECK (price &gt; 0)</code> on a nullable <code>price</code> accepts <code>NULL</code>. Add <code>NOT NULL</code> if you mean it.</p>
<h3 id="EXCLUDE"><a href="#EXCLUDE" class="headerlink" title="EXCLUDE"></a><code>EXCLUDE</code></h3>
<p>The constraint type that has no equivalent in most other databases: &quot;no two rows may both satisfy these operator comparisons&quot;. The canonical use is preventing overlapping reservations.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> EXTENSION IF <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">EXISTS</span> btree_gist;   <span class="hljs-comment">-- needed to mix = with &amp;&amp; in one GiST index</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> bookings</span><br><span class="line">  <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">CONSTRAINT</span> no_double_booking</span><br><span class="line">  EXCLUDE <span class="hljs-keyword">USING</span> gist (room_id <span class="hljs-keyword">WITH</span> <span class="hljs-operator">=</span>, during <span class="hljs-keyword">WITH</span> <span class="hljs-operator">&amp;&amp;</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Now any attempt to insert a booking for the same room whose time range overlaps an existing one is rejected by the database, atomically, with no application-level locking. <code>UNIQUE</code> is in fact a special case of <code>EXCLUDE</code> where every operator is <code>=</code>.</p>
<p><strong>PostgreSQL 18</strong> generalises this further with temporal keys: <code>PRIMARY KEY (id, valid_at WITHOUT OVERLAPS)</code> and matching <code>FOREIGN KEY … PERIOD</code>.</p>
<h2 id="Deferrable-constraints"><a href="#Deferrable-constraints" class="headerlink" title="Deferrable constraints"></a>Deferrable constraints</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> ... <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">CONSTRAINT</span> c <span class="hljs-keyword">FOREIGN</span> KEY (...) <span class="hljs-keyword">REFERENCES</span> ...</span><br><span class="line">  DEFERRABLE INITIALLY DEFERRED;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">BEGIN</span>;</span><br><span class="line">  <span class="hljs-keyword">SET</span> CONSTRAINTS <span class="hljs-keyword">ALL</span> DEFERRED;   <span class="hljs-comment">-- check only at COMMIT</span></span><br><span class="line">  <span class="hljs-comment">-- circular inserts, swap two unique values, etc.</span></span><br><span class="line"><span class="hljs-keyword">COMMIT</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Deferring lets you write two rows that only jointly satisfy a constraint — swapping the <code>sort_order</code> of two rows under a unique index is the standard example. <code>NOT NULL</code> and <code>CHECK</code> cannot be deferred; <code>UNIQUE</code>, <code>PRIMARY KEY</code>, <code>EXCLUDE</code>, and <code>FOREIGN KEY</code> can.</p>

<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> conname, contype, convalidated, pg_get_constraintdef(oid)</span><br><span class="line"><span class="hljs-keyword">FROM</span> pg_constraint</span><br><span class="line"><span class="hljs-keyword">WHERE</span> conrelid <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;bookings&#x27;</span>::regclass;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="serial-is-a-macro-not-a-type"><a href="#serial-is-a-macro-not-a-type" class="headerlink" title="serial is a macro, not a type"></a><code>serial</code> is a macro, not a type</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> t (id serial <span class="hljs-keyword">PRIMARY</span> KEY);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>expands to:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> SEQUENCE t_id_seq;</span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> t (id <span class="hljs-type">integer</span> <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span> <span class="hljs-keyword">DEFAULT</span> nextval(<span class="hljs-string">&#x27;t_id_seq&#x27;</span>) <span class="hljs-keyword">PRIMARY</span> KEY);</span><br><span class="line"><span class="hljs-keyword">ALTER</span> SEQUENCE t_id_seq OWNED <span class="hljs-keyword">BY</span> t.id;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

If a business requires gapless invoice numbers, that is an application-level counter guarded by a lock, not a sequence.</p>

<h2 id="Casting"><a href="#Casting" class="headerlink" title="Casting"></a>Casting</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-string">&#x27;42&#x27;</span>::<span class="hljs-type">integer</span>;        <span class="hljs-comment">-- 3.5   the literal 2.0 is numeric</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-string">&#x27;2026-06-02&#x27;</span>::<span class="hljs-type">date</span> <span class="hljs-operator">+</span> <span class="hljs-number">30</span>;                <span class="hljs-comment">-- date + integer = date</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> now()::<span class="hljs-type">date</span>;                            <span class="hljs-comment">-- truncate to day</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-string">&#x27;{&quot;a&quot;:1}&#x27;</span>::jsonb <span class="hljs-operator">-</span><span class="hljs-operator">&gt;</span> <span class="hljs-string">&#x27;a&#x27;</span>;</span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-string">&#x27;a1b2c3&#x27;</span>::text <span class="hljs-operator">~</span> <span class="hljs-string">&#x27;^[a-z0-9]+$&#x27;</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>PostgreSQL recognises three cast strengths: <strong>implicit</strong> (applied automatically in any expression — deliberately rare, to prevent MySQL-style silent coercion), <strong>assignment</strong> (applied on <code>INSERT</code>/<code>UPDATE</code> into a column), and <strong>explicit</strong> (only with <code>::</code> or <code>CAST</code>). This strictness is why <code>SELECT 'abc' + 1</code> is an error rather than <code>1</code>.</p>
<p>Safe casting of untrusted text on <strong>PostgreSQL 16+</strong>:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> pg_input_is_valid(<span class="hljs-string">&#x27;abc&#x27;</span>, <span class="hljs-string">&#x27;integer&#x27;</span>);       <span class="hljs-comment">-- false, no exception raised</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> pg_input_error_info(<span class="hljs-string">&#x27;abc&#x27;</span>, <span class="hljs-string">&#x27;integer&#x27;</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Common pitfall:</strong> <code>::</code> binds more tightly than most operators. <code>-1::integer</code> parses as <code>-(1::integer)</code>, and <code>a || b::text</code> casts only <code>b</code>. Parenthesise when the intent is not obvious.</p>
</blockquote>

<h1 id="Cheat-sheet"><a href="#Cheat-sheet" class="headerlink" title="Cheat-sheet"></a>Cheat-sheet</h1>
<table>
<thead>
<tr>
<th>What</th>
<th>How</th>
</tr>
</thead>
<tbody>
<tr>
<td>Surrogate key</td>
<td><code>bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY</code></td>
</tr>
<tr>
<td>Money</td>
<td><code>numeric(12,2)</code> — never <code>float</code>, never <code>money</code></td>
</tr>
<tr>
<td>Strings</td>
<td><code>text</code> (+ a <code>CHECK</code> on length if needed)</td>
</tr>
<tr>
<td>Instant in time</td>
<td><code>timestamptz</code></td>
</tr>
<tr>
<td>Duration</td>
<td><code>interval</code></td>
</tr>
<tr>
<td>Random / sortable UUID</td>
<td><code>gen_random_uuid()</code> / <code>uuidv7()</code> (PG 18)</td>
</tr>
<tr>
<td>Add column with default</td>
<td><code>ADD COLUMN c type DEFAULT v</code> — no rewrite since PG 11</td>
</tr>
<tr>
<td>Safe <code>NOT NULL</code></td>
<td><code>CHECK (c IS NOT NULL) NOT VALID</code> → <code>VALIDATE</code> → <code>SET NOT NULL</code></td>
</tr>
<tr>
<td>Safe FK</td>
<td><code>ADD … FOREIGN KEY … NOT VALID</code> → <code>VALIDATE CONSTRAINT</code></td>
</tr>
<tr>
<td>Insert and get the id</td>
<td><code>INSERT … RETURNING id</code></td>
</tr>
<tr>
<td>Upsert</td>
<td><code>INSERT … ON CONFLICT (k) DO UPDATE SET c = EXCLUDED.c</code></td>
</tr>
<tr>
<td>Batch reconcile</td>
<td><code>MERGE INTO … USING … WHEN MATCHED/NOT MATCHED</code> (PG 15+)</td>
</tr>
<tr>
<td>Bulk load</td>
<td><code>COPY</code> / <code>\copy … CSV HEADER</code></td>
</tr>
<tr>
<td>Update from another table</td>
<td><code>UPDATE t SET … FROM u WHERE …</code></td>
</tr>
<tr>
<td>NULL-safe equality</td>
<td><code>IS NOT DISTINCT FROM</code></td>
</tr>
<tr>
<td>First non-NULL</td>
<td><code>coalesce(a, b, c)</code></td>
</tr>
<tr>
<td>Conditional uniqueness</td>
<td><code>CREATE UNIQUE INDEX … WHERE predicate</code></td>
</tr>
<tr>
<td>No overlapping ranges</td>
<td><code>EXCLUDE USING gist (k WITH =, range WITH &amp;&amp;)</code></td>
</tr>
<tr>
<td>Cast</td>
<td><code>expr::type</code> or <code>CAST(expr AS type)</code></td>
</tr>
<tr>
<td>Fix a desynced sequence</td>
<td><code>setval(pg_get_serial_sequence('t','id'), max(id))</code></td>
</tr>
</tbody>
</table>
