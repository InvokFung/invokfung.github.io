PostgreSQL Course — 01 · SQL Fundamentals and Data Types

Created2026-06-10|Updated2026-06-10|Database > PostgreSQL
|Post View:

Type choices are the most expensive decisions in a schema. A wrong index costs a CREATE INDEX; a wrong column type costs a migration, a rewrite, a maintenance window, and — if the type was float for money or timestamp for an instant — a class of bugs that ships to production and only surfaces at quarter-end or the daylight-saving boundary. This post covers the DDL and DML you will write every day, then spends most of its length on the type system, NULL semantics, and constraints, because those are the parts you cannot cheaply change later. Examples target PostgreSQL 17/18; version-specific behaviour is called out inline.

Series map: 00 Foundations & Setup → 01 SQL Fundamentals & Data Types (this post) → 02 Joins, Aggregation & Window Functions → 03 Indexes & the Query Planner → 04 Query Optimization & Statistics → 05 Transactions, MVCC, Isolation & Locking → 06 Schema Design, Normalization & JSONB → 07 Operations, Backup, Replication & Security.

Learning Outcome

  • Write DDL: CREATE, ALTER, and DROP TABLE, including the ALTER forms that avoid a full table rewrite.
  • Write DML confidently: INSERT, UPDATE, DELETE, RETURNING, and upserts via ON CONFLICT.
  • Choose correctly among the integer family, numeric vs floating point, text vs varchar, enum vs lookup table.
  • Explain why timestamptz is the default correct answer and timestamp almost never is.
  • Predict the result of any expression involving NULL under three-valued logic.
  • Apply the six constraint types, including EXCLUDE, and add them to live tables without long locks.
  • Explain the difference between identity columns and serial, and why new work uses identity.

Chapter 1 — DDL: creating and evolving tables

Terminology

  • DDL — Data Definition Language: CREATE, ALTER, DROP. Changes the shape of the database.
  • DML — Data Manipulation Language: INSERT, UPDATE, DELETE, SELECT, MERGE. Changes or reads the contents.
  • Table rewrite — an ALTER TABLE variant that must rebuild every row on disk. Holds an ACCESS EXCLUSIVE lock for the duration, which blocks everything, including reads.
  • Catalog — the system tables (pg_class, pg_attribute, pg_constraint, …) describing the database to itself.
  • Domain — a named, reusable type with constraints attached.

ALTER TABLE — the operations that are cheap and the ones that are not

This is the table to memorise, because the difference between a two-millisecond ALTER and a forty-minute outage is which row you land on.

Operation Rewrite? Lock Notes
ADD COLUMN c type (no default) No ACCESS EXCLUSIVE, brief Catalog-only
ADD COLUMN c type DEFAULT v No since PG 11 ACCESS EXCLUSIVE, brief Default stored in catalog, applied on read
ADD COLUMN c type DEFAULT <volatile fn> Yes Long e.g. DEFAULT gen_random_uuid() — each row needs a distinct value
DROP COLUMN No ACCESS EXCLUSIVE, brief Column is marked dead; space reclaimed by later rewrite
ALTER COLUMN … TYPE (binary-coercible, e.g. varchar(50)→text) No ACCESS EXCLUSIVE, brief
ALTER COLUMN … TYPE (integer→bigint) Yes Long The classic id-exhaustion migration
ALTER COLUMN … SET/DROP DEFAULT No Brief
ALTER COLUMN … SET NOT NULL No rewrite, but full scan ACCESS EXCLUSIVE for the scan See the trick below
ADD CONSTRAINT … CHECK … NOT VALID No Brief Then VALIDATE CONSTRAINT under a weaker lock
ADD FOREIGN KEY … NOT VALID No SHARE ROW EXCLUSIVE Then validate separately
SET LOGGED / SET UNLOGGED Yes Long

Trick (zero-downtime NOT NULL): adding NOT NULL directly scans the whole table under ACCESS EXCLUSIVE. Instead add an equivalent CHECK (c IS NOT NULL) NOT VALID, VALIDATE CONSTRAINT it (weaker lock, concurrent reads and writes continue), then SET NOT NULL — PostgreSQL 12+ recognises the validated check and skips the scan. PostgreSQL 18 simplifies this further by allowing ALTER TABLE … ADD CONSTRAINT … NOT NULL … NOT VALID directly.

Generated columns

The expression must be immutable — no now(), no other tables.

DROP

TRUNCATE is DDL, not DML: it takes an ACCESS EXCLUSIVE lock, does not fire row triggers, and does not produce dead tuples for VACUUM to clean. It is transactional in PostgreSQL — you can roll it back, unlike in some other engines.

Every one of INSERT, UPDATE, DELETE (and MERGE since PostgreSQL 17) can return rows. This eliminates the read-after-write round trip that most ORMs would otherwise perform.

UPDATE and DELETE with joins

PostgreSQL uses FROM / USING rather than the UPDATE … JOIN syntax of MySQL:

Common pitfall: an UPDATE … FROM where the FROM side matches multiple rows is not an error. PostgreSQL picks one arbitrarily and applies it. If the join is not guaranteed unique, aggregate it into a subquery first.

Upsert: ON CONFLICT

Rules that matter:

  • The conflict target must be backed by a unique index or constraint. ON CONFLICT DO UPDATE requires a target; DO NOTHING may omit one (in which case it swallows any conflict).
  • Inside DO UPDATE, the proposed row is EXCLUDED.* and the existing row is tablename.*.
  • To target a partial unique index, repeat its predicate: ON CONFLICT (email) WHERE deleted_at IS NULL DO UPDATE ….
  • xmax = 0 in RETURNING distinguishes an insert from an update — a widely used idiom, though it relies on an implementation detail.
  • A single statement cannot update the same row twice: ON CONFLICT DO UPDATE command cannot affect row a second time. De-duplicate the input first.

MERGE

MERGE arrived in PostgreSQL 15 and gained RETURNING in PostgreSQL 17. It is the SQL-standard multi-action form, and unlike ON CONFLICT it does not require a unique constraint — but it also gives no built-in concurrency guarantee, so concurrent MERGEs can raise serialization failures.

Guidance: use ON CONFLICT for concurrent single-row upserts from application code; use MERGE for batch reconciliation against a staging table.

Chapter 3 — The type system

Numbers

Type Bytes Range / precision Use for
smallint 2 ±32,767 Small enumerated counts. Rarely worth it.
integer / int 4 ±2,147,483,647 Default integer. Counts, small ids.
bigint 8 ±9.2 × 10¹⁸ All surrogate keys.
numeric(p,s) variable Exact, up to 131072 digits before the point Money, quantities, anything summed and compared for equality
real 4 ~6 decimal digits, IEEE 754 Sensor data, approximations
double precision 8 ~15 decimal digits, IEEE 754 Scientific computation
money 8 Locale-dependent Avoid. Its output format depends on lc_monetary.

bigint for keys, always

integer exhausts at 2.1 billion. That sounds distant until you learn that a sequence advances on failed inserts too — every ON CONFLICT DO NOTHING that conflicts still burns an id. The integer → bigint migration on a hot table is a full rewrite with an ACCESS EXCLUSIVE lock. The four extra bytes per row are cheap by comparison.

numeric vs floating point for money

Binary floating point cannot represent 0.1 exactly. Financial code that sums floats produces drift that accumulates silently and fails reconciliation. Use numeric(12,2) for currency amounts, or store integer minor units (cents) in a bigint if you need maximum arithmetic speed. numeric is slower — it is arbitrary-precision software arithmetic, not a CPU instruction — but the correctness is non-negotiable for money.

Watch out: NaN in numeric compares as equal to itself and greater than all other values, which differs from the IEEE 754 rule used for double precision, where NaN = NaN is false. This is documented and deliberate, so that numeric can be sorted and indexed.

Text

Type Behaviour
text Unlimited length. The default choice.
varchar(n) Same storage and performance as text, plus a length check
varchar (no n) Identical to text
char(n) Blank-padded to n on storage; comparison ignores trailing spaces. Avoid.

In PostgreSQL there is no performance difference between text and varchar(n) — both are varlena types with the same TOAST behaviour. varchar(n) is a CHECK (length(x) <= n) in disguise. Since a length limit is a business rule and business rules change, prefer text plus an explicit, alterable CHECK constraint:

Changing that check is a validate-only operation; changing varchar(32) to varchar(64) is cheap, but shrinking it requires a rewrite.

Values over roughly 2 KB are compressed and moved out-of-line into a TOAST table automatically. This is why a text column holding a megabyte of JSON does not bloat the main heap — but it does mean any query touching that column pays an extra fetch.

Boolean

boolean accepts true/false/NULL, and on input also 't', 'yes', 'on', '1'. One byte. Note that a nullable boolean is a three-state column — see Chapter 4.

Enum vs lookup table

enum Lookup table + FK text + CHECK
Storage 4 bytes 2–8 byte FK Full string per row
Sort order Declaration order Whatever column you add Alphabetical
Add a value ALTER TYPE … ADD VALUE INSERT ALTER the check constraint
Remove a value Not supported DELETE ALTER the check
Rename a value ALTER TYPE … RENAME VALUE (10+) UPDATE ALTER the check
Attach metadata (label, colour, sort key) No Yes No
Readable in raw dumps Yes Needs a join Yes

Decision rule: enum for a small, genuinely closed set with a meaningful order (pending < paid < shipped) that changes at most yearly. Lookup table whenever values carry metadata, are managed by non-engineers, or need deleting. text + CHECK as a light middle ground.

Watch out (PostgreSQL 12+): ALTER TYPE … ADD VALUE may run inside a transaction block, but the new value cannot be used in that same transaction. Migration frameworks that wrap everything in one transaction hit this constantly. Split it into two migrations.

Date and time

Type Stores Bytes
date Calendar day, no time 4
time Time of day, no date, no zone 8
timetz Time with zone offset 12 — avoid, semantically incoherent
timestamp Date + time, no zone 8
timestamptz An absolute instant 8
interval A duration 16

Why timestamptz is almost always right

The name is misleading. timestamptz does not store a timezone. It stores an absolute point in time (microseconds from an epoch, in UTC). On input, a value is converted from the session's TimeZone to UTC; on output, from UTC back to the session's TimeZone. It is the type that answers "when did this happen?" unambiguously anywhere on Earth.

timestamp (without time zone) stores a wall-clock reading with no anchor. Two servers in different regions will disagree about what instant it names, and it cannot represent the DST fall-back hour unambiguously.

The narrow legitimate uses of plain timestamp: a local wall-clock concept with no instant attached — "the shop opens at 09:00 in whatever timezone the shop is in", a recurring alarm, a birthday. Even then, store the IANA zone name alongside it in a separate column.

AT TIME ZONE flips between the two types in both directions — which direction depends on the input type. That asymmetry catches everyone once.

interval

An interval stores months, days, and microseconds separately, because a month is not a fixed number of days and a day is not always 24 hours across a DST boundary. interval '1 month' added to January 31 gives February 28 or 29. This is correct calendar arithmetic, not a rounding bug.

UUID

16 bytes, stored binary. gen_random_uuid() (UUIDv4) is built in since PostgreSQL 13 — no pgcrypto needed. PostgreSQL 18 adds uuidv4() and uuidv7() as standard functions.

The trade-off against bigint identity:

  • UUIDv4 is random, so inserts land at random points in the primary-key B-tree. That causes page splits, poor cache locality, and index bloat on high-insert tables.
  • UUIDv7 is time-ordered in its high bits, which restores the append-at-the-right-edge insert pattern of a sequence while keeping global uniqueness and non-guessability. On PG 18, uuidv7() is the right default when you want UUIDs.
  • bigint identity remains smallest and fastest, at the cost of being guessable and requiring a central sequence.

Arrays

Arrays are genuinely useful for small, fixed-cardinality, always-read-together sets (tags, permission flags, embedding dimensions). They are a poor substitute for a join table when you need per-element metadata, referential integrity, or per-element updates. Index with GIN (CREATE INDEX ON posts USING gin (tags)) if you filter with @> or && — see Post 03.

bytea and other types worth knowing

bytea holds arbitrary binary. It is fine for small blobs (thumbnails, hashes, encrypted tokens); it is the wrong place for user-uploaded files — put those in object storage and keep the key in a text column.

Also in the standard distribution and worth remembering: inet/cidr/macaddr for networking, tsvector/tsquery for full-text search, int4range/tstzrange/daterange for ranges, point/polygon for basic geometry, json/jsonb (Post 06), and xml.

Domains

A domain is a named type plus constraints, reusable across tables. Cheaper than a composite type, and it keeps validation in one place.

Migration note: when moving a relational schema to a document store, the type mapping is where fidelity is lost — numeric has no exact BSON equivalent, and array/jsonb columns collapse into the document naturally while enums do not. The SQL → MongoDB migration post walks through that mapping in both directions.

Chapter 4 — NULL and three-valued logic

NULL is not a value. It is a marker meaning unknown. Every comparison involving it yields NULL (neither true nor false), and SQL's WHERE clause keeps only rows where the predicate is true — so NULL behaves like false at filter time but not in any other context. This asymmetry is the source of an enormous share of production SQL bugs.

The surprising-results table

Expression Result Why
NULL = NULL NULL Unknown compared to unknown is unknown
NULL <> NULL NULL Same
NULL IS NULL true IS NULL is a test, not a comparison
NULL IS NOT DISTINCT FROM NULL true IS DISTINCT FROM treats NULL as a comparable value
1 + NULL NULL Arithmetic propagates
'abc' || NULL NULL || propagates
concat('abc', NULL) 'abc' concat() ignores NULL — unlike ||
NULL = '' NULL In PostgreSQL, '' and NULL are different (unlike Oracle)
true OR NULL true Result is determined regardless
false OR NULL NULL Undetermined
true AND NULL NULL Undetermined
false AND NULL false Result is determined regardless
NOT NULL (the operator) NULL
2 IN (1, NULL) NULL Not false — this is the NOT IN trap
2 NOT IN (1, NULL) NULL Row is filtered out. See below
count(*) on 3 rows, one NULL col 3 Counts rows
count(col) on the same 2 Aggregates skip NULL inputs
sum(col) where all values are NULL NULL Not 0
avg(col) Ignores NULLs in both numerator and denominator
array_agg(col) Keeps NULL elements Aggregates that build collections are the exception
SELECT DISTINCT over NULLs NULLs collapse to one DISTINCT treats them as equal
GROUP BY col with NULLs One NULL group Same
ORDER BY col ASC NULLs last NULL sorts as larger than everything
ORDER BY col DESC NULLs first Same rule, reversed
UNIQUE column with two NULLs Both allowed NULLs are distinct for uniqueness

The NOT IN trap

If any row in orders has a NULL customer_id, the subquery list contains NULL, every NOT IN test evaluates to NULL instead of true, and the query returns zero rows. Silently. No error.

Tools for handling NULL

Common pitfall: WHERE deleted_at != 'x' skips rows where deleted_at IS NULL. If "not equal to x" should include unknowns, write WHERE deleted_at IS DISTINCT FROM 'x'. This bug hides in soft-delete filters constantly.

Chapter 5 — Constraints

Constraints are the only guarantee that survives a buggy deployment, a rogue script, and the next developer. Application-level validation is a user-experience feature; a database constraint is the actual invariant.

The six types

PRIMARY KEY

NOT NULL + UNIQUE + designated as the table's identity. One per table. Backed by a unique B-tree index automatically.

FOREIGN KEY and the ON DELETE actions

Action Effect when the referenced row is deleted
NO ACTION (default) Error, checked at end of statement (deferrable)
RESTRICT Error, checked immediately (not deferrable)
CASCADE Delete the referencing rows too
SET NULL Set the FK column to NULL (column must be nullable)
SET DEFAULT Set it to the column default (which must itself satisfy the FK)

ON UPDATE takes the same set. PostgreSQL 15+ allows column lists: ON DELETE SET NULL (col_a) for composite keys.

Watch out: PostgreSQL does not automatically index the referencing column. Every DELETE on the parent then triggers a sequential scan of the child to check the constraint. Index every foreign key column yourself — this is one of the most common causes of mysteriously slow deletes.

Trick (zero-downtime FK): ADD CONSTRAINT … FOREIGN KEY … NOT VALID takes a SHARE ROW EXCLUSIVE lock and skips the existing-data scan; new rows are enforced immediately. Follow with ALTER TABLE … VALIDATE CONSTRAINT …, which scans under a lock that permits concurrent reads and writes.

UNIQUE

Backed by a unique index. Multiple NULLs are permitted by default because NULLs are distinct. PostgreSQL 15+ can change that:

For conditional uniqueness — "email unique among non-deleted users" — use a partial unique index rather than a constraint, since constraints cannot carry a predicate:

CHECK

Any boolean expression over the row's own columns. It must be immutable and may not reference other tables or now().

A CHECK that evaluates to NULL passes. CHECK (price > 0) on a nullable price accepts NULL. Add NOT NULL if you mean it.

EXCLUDE

The constraint type that has no equivalent in most other databases: "no two rows may both satisfy these operator comparisons". The canonical use is preventing overlapping reservations.

Now any attempt to insert a booking for the same room whose time range overlaps an existing one is rejected by the database, atomically, with no application-level locking. UNIQUE is in fact a special case of EXCLUDE where every operator is =.

PostgreSQL 18 generalises this further with temporal keys: PRIMARY KEY (id, valid_at WITHOUT OVERLAPS) and matching FOREIGN KEY … PERIOD.

Deferrable constraints

Deferring lets you write two rows that only jointly satisfy a constraint — swapping the sort_order of two rows under a unique index is the standard example. NOT NULL and CHECK cannot be deferred; UNIQUE, PRIMARY KEY, EXCLUDE, and FOREIGN KEY can.

Inspecting constraints

contype is p primary, f foreign, u unique, c check, x exclusion, n not-null (PG 18 records these in pg_constraint too).

Chapter 6 — Identity vs serial, and casting

Its problems: the column is only a DEFAULT, so anyone can insert an explicit id and desynchronise the sequence; the sequence is a separate object requiring separate GRANT USAGE for inserting roles; and it is a PostgreSQL-specific extension rather than standard SQL.

Recommended for new work No Yes

Watch out: sequences are not transactional for gap-freeness. A rolled-back transaction does not return its consumed values, and ON CONFLICT DO NOTHING burns an id per conflicting row. Identity and serial columns produce ordered, unique values, never gapless ones. If a business requires gapless invoice numbers, that is an application-level counter guarded by a lock, not a sequence.

Casting

PostgreSQL recognises three cast strengths: implicit (applied automatically in any expression — deliberately rare, to prevent MySQL-style silent coercion), assignment (applied on INSERT/UPDATE into a column), and explicit (only with :: or CAST). This strictness is why SELECT 'abc' + 1 is an error rather than 1.

Common pitfall: :: binds more tightly than most operators. -1::integer parses as -(1::integer), and a || b::text casts only b. Parenthesise when the intent is not obvious.
