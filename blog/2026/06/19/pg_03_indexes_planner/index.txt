11:T17aff,<p>An index is a redundant, automatically maintained data structure that lets the server find rows without reading the whole table. Adding the right one turns a forty-second query into a two-millisecond one; adding six wrong ones slows every write, wastes gigabytes, and leaves the slow query exactly as slow. The skill worth acquiring is not &quot;add an index&quot; — it is reading <code>EXPLAIN (ANALYZE, BUFFERS)</code> well enough to know <em>which</em> index, and to recognise the cases where the planner's sequential scan is genuinely the right answer. This post covers B-tree mechanics, all six index access methods, the leading-column rule, index-only scans, and the operational side: concurrent builds, bloat, and finding indexes nobody uses. Examples target <strong>PostgreSQL 17/18</strong>.</p>
<blockquote>
<p>Series map: 00 Foundations &amp; Setup → 01 SQL Fundamentals &amp; Data Types → 02 Joins, Aggregation &amp; Window Functions → <strong>03 Indexes &amp; the Query Planner</strong> (this post) → 04 Query Optimization &amp; Statistics → 05 Transactions, MVCC, Isolation &amp; Locking → 06 Schema Design, Normalization &amp; JSONB → 07 Operations, Backup, Replication &amp; Security.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Describe a B-tree index at a working level: pages, fanout, depth, and what a scan actually costs.</li>
<li>Choose among B-tree, Hash, GIN, GiST, SP-GiST, and BRIN using a decision table.</li>
<li>Order the columns of a multicolumn index correctly and apply the leading-column rule.</li>
<li>Build covering indexes with <code>INCLUDE</code> and get genuine index-only scans, including the visibility-map requirement.</li>
<li>Use partial and expression indexes, and explain why <code>WHERE lower(email) = …</code> needs one.</li>
<li>Distinguish unique indexes from unique constraints, and know when only the index will do.</li>
<li>Read <code>EXPLAIN (ANALYZE, BUFFERS)</code>: cost model, estimated vs actual rows, and the scan-node vocabulary.</li>
<li>Recognise when a sequential scan is correct and stop trying to index it away.</li>
<li>Build indexes on live tables with <code>CREATE INDEX CONCURRENTLY</code>, and find bloated or unused ones.</li>
</ul>

<h1 id="Chapter-1-—-B-tree-at-a-working-level"><a href="#Chapter-1-—-B-tree-at-a-working-level" class="headerlink" title="Chapter 1 — B-tree at a working level"></a>Chapter 1 — B-tree at a working level</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Access method</strong> — the algorithm behind an index type. PostgreSQL ships six for tables (<code>btree</code>, <code>hash</code>, <code>gin</code>, <code>gist</code>, <code>spgist</code>, <code>brin</code>) and lets extensions add more.</li>
<li><strong>Operator class (<code>opclass</code>)</strong> — the set of operators and support functions an index uses for a given data type, e.g. <code>text_pattern_ops</code>, <code>jsonb_path_ops</code>.</li>
<li><strong>Heap</strong> — the table's own storage. Distinct from the index.</li>
<li><strong>TID / ctid</strong> — a physical row pointer: <code>(block number, offset)</code>. Index entries point at TIDs.</li>
<li><strong>Visibility map (VM)</strong> — a per-table bitmap with two bits per heap page: all-visible and all-frozen. Maintained by <code>VACUUM</code>.</li>
<li><strong>Selectivity</strong> — the fraction of rows a predicate is expected to keep. The single most important number in the planner's decision.</li>
</ul>

<p>Numbers worth internalising:</p>
<ul>
<li>Each page holds on the order of a few hundred entries for typical key widths, so <strong>fanout</strong> is a few hundred.</li>
<li>Three levels therefore index roughly a hundred million rows; four levels index far more. Depth grows logarithmically and stays small.</li>
<li>A single-row lookup costs about <strong>depth + 1</strong> page reads: one per level down, plus one heap page fetch — and the upper levels are almost always cached.</li>
<li>The maximum index entry is about one third of a page (roughly 2704 bytes at the default 8 KB <code>BLCKSZ</code>). Indexing a long <code>text</code> column fails at insert time when a value exceeds it; index a hash or a truncation instead.</li>
<li>Leaf pages are doubly linked, which is why a range scan (<code>BETWEEN</code>, <code>&gt;</code>, <code>ORDER BY</code>) is cheap once positioned, and why a B-tree can also satisfy <code>ORDER BY</code> without a sort — in either direction, since it can be walked backwards.</li>
</ul>
<p>Two modern optimisations that matter operationally:</p>
<ul>
<li><strong>Deduplication</strong> (PostgreSQL 13+): repeated keys are stored once with a posting list of TIDs. Indexes on low-cardinality columns became dramatically smaller.</li>
<li><strong>Bottom-up index deletion</strong> (PostgreSQL 14+): before splitting a page, the index opportunistically removes entries pointing at dead tuples. This substantially slows bloat growth on tables with heavy non-<code>HOT</code> updates.</li>
</ul>

<h1 id="Chapter-2-—-The-six-index-types"><a href="#Chapter-2-—-The-six-index-types" class="headerlink" title="Chapter 2 — The six index types"></a>Chapter 2 — The six index types</h1>
<h2 id="B-tree"><a href="#B-tree" class="headerlink" title="B-tree"></a>B-tree</h2>
<p>The default and the right answer for perhaps 90% of indexes: any type with a total order, equality and range predicates, sorting, uniqueness.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_orders_placed_at <span class="hljs-keyword">ON</span> orders (placed_at);</span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_orders_placed_at_desc <span class="hljs-keyword">ON</span> orders (placed_at <span class="hljs-keyword">DESC</span> NULLS <span class="hljs-keyword">LAST</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Hash"><a href="#Hash" class="headerlink" title="Hash"></a>Hash</h2>
<p>Equality only. WAL-logged and crash-safe since <strong>PostgreSQL 10</strong> (before that they were not replicated and had to be rebuilt after a crash, which is why old advice says &quot;never use hash indexes&quot;).</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_sessions_token <span class="hljs-keyword">ON</span> sessions <span class="hljs-keyword">USING</span> hash (token);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Narrower than a B-tree for long keys, since it stores a 32-bit hash rather than the value. In exchange it cannot do ranges, cannot sort, cannot be unique, and cannot be multicolumn. The niche is genuinely narrow: very long keys, equality-only access, no ordering requirement. Benchmark against a B-tree on your own data before committing.</p>
<h2 id="GIN-—-Generalized-Inverted-Index"><a href="#GIN-—-Generalized-Inverted-Index" class="headerlink" title="GIN — Generalized Inverted Index"></a>GIN — Generalized Inverted Index</h2>
<p>For values that <strong>contain multiple searchable items</strong>: array elements, <code>jsonb</code> keys and values, full-text lexemes, trigrams.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_posts_tags   <span class="hljs-keyword">ON</span> posts <span class="hljs-keyword">USING</span> gin (tags);                 <span class="hljs-comment">-- text[]</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_docs_attrs   <span class="hljs-keyword">ON</span> docs  <span class="hljs-keyword">USING</span> gin (attributes);           <span class="hljs-comment">-- jsonb, @&gt; ? ?&amp; ?|</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_docs_attrs_p <span class="hljs-keyword">ON</span> docs  <span class="hljs-keyword">USING</span> gin (attributes jsonb_path_ops); <span class="hljs-comment">-- smaller, @&gt; only</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_articles_fts <span class="hljs-keyword">ON</span> articles <span class="hljs-keyword">USING</span> gin (to_tsvector(<span class="hljs-string">&#x27;english&#x27;</span>, body));</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">CREATE</span> EXTENSION pg_trgm;</span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_users_name_trgm <span class="hljs-keyword">ON</span> users <span class="hljs-keyword">USING</span> gin (name gin_trgm_ops);  <span class="hljs-comment">-- makes LIKE &#x27;%x%&#x27; indexable</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>GIN reads fast and writes slowly, because one row update can touch many index entries. The <code>fastupdate</code> mechanism buffers changes in a pending list and flushes them in batches — good for write throughput, but it means a query may have to scan the unflushed pending list, producing occasional latency spikes. Tune with <code>gin_pending_list_limit</code> or set <code>fastupdate = off</code> for read-latency-sensitive workloads.</p>
<h2 id="GiST-—-Generalized-Search-Tree"><a href="#GiST-—-Generalized-Search-Tree" class="headerlink" title="GiST — Generalized Search Tree"></a>GiST — Generalized Search Tree</h2>
<p>A framework for indexing things without a natural total order: geometry, ranges, nearest-neighbour search, and the exclusion constraints from Post 01.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_bookings_during <span class="hljs-keyword">ON</span> bookings <span class="hljs-keyword">USING</span> gist (during);         <span class="hljs-comment">-- tstzrange, &amp;&amp;</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_places_geom     <span class="hljs-keyword">ON</span> places   <span class="hljs-keyword">USING</span> gist (geom);           <span class="hljs-comment">-- PostGIS</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_users_name_gist <span class="hljs-keyword">ON</span> users    <span class="hljs-keyword">USING</span> gist (name gist_trgm_ops);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- K-nearest-neighbour: the 10 nearest places, using the index for ordering</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> places <span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> geom <span class="hljs-operator">&lt;</span><span class="hljs-operator">-</span><span class="hljs-operator">&gt;</span> ST_Point(<span class="hljs-number">-0.12</span>, <span class="hljs-number">51.50</span>) LIMIT <span class="hljs-number">10</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>GiST is lossy: it returns candidate rows that the executor must recheck. That is why a GiST plan shows a <code>Recheck Cond</code>.</p>
<h2 id="SP-GiST-—-Space-Partitioned-GiST"><a href="#SP-GiST-—-Space-Partitioned-GiST" class="headerlink" title="SP-GiST — Space-Partitioned GiST"></a>SP-GiST — Space-Partitioned GiST</h2>
<p>For naturally hierarchical, non-balanced partitionings: quadtrees, k-d trees, radix trees. In practice: <code>inet</code>/<code>cidr</code> containment, points, and text prefix search where a radix tree beats a B-tree on space.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_logs_ip     <span class="hljs-keyword">ON</span> logs  <span class="hljs-keyword">USING</span> spgist (client_ip inet_ops);</span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_words_radix <span class="hljs-keyword">ON</span> words <span class="hljs-keyword">USING</span> spgist (word);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="BRIN-—-Block-Range-INdex"><a href="#BRIN-—-Block-Range-INdex" class="headerlink" title="BRIN — Block Range INdex"></a>BRIN — Block Range INdex</h2>
<p>Stores a summary (by default min/max) for each <em>range of heap pages</em> — 128 pages by default. Consequently it is minuscule: an index over a billion-row table can be a few megabytes.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_events_at_brin <span class="hljs-keyword">ON</span> events <span class="hljs-keyword">USING</span> brin (occurred_at);</span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_events_at_brin2 <span class="hljs-keyword">ON</span> events <span class="hljs-keyword">USING</span> brin (occurred_at) <span class="hljs-keyword">WITH</span> (pages_per_range <span class="hljs-operator">=</span> <span class="hljs-number">32</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>BRIN only works when the <strong>physical row order correlates with the indexed value</strong> — append-only time-series data, log tables, tables loaded in key order. If rows are scattered, every block range spans the whole value domain and the index eliminates nothing. Check before building:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> attname, correlation <span class="hljs-keyword">FROM</span> pg_stats</span><br><span class="line"><span class="hljs-keyword">WHERE</span> tablename <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;events&#x27;</span> <span class="hljs-keyword">AND</span> attname <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;occurred_at&#x27;</span>;</span><br><span class="line"><span class="hljs-comment">-- |correlation| near 1.0 → BRIN is viable. Near 0 → useless.</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>PostgreSQL 14</strong> added <code>minmax_multi</code> opclasses (tolerant of a few outliers that would otherwise ruin a range's summary) and <code>bloom</code> opclasses (equality on uncorrelated columns).</p>

<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_orders_cust_status_placed</span><br><span class="line">  <span class="hljs-keyword">ON</span> orders (customer_id, status, placed_at <span class="hljs-keyword">DESC</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="The-leading-column-rule"><a href="#The-leading-column-rule" class="headerlink" title="The leading-column rule"></a>The leading-column rule</h2>
<p>A multicolumn B-tree is sorted by its first column, then by its second within ties, and so on. It efficiently serves any <strong>prefix</strong> of its column list:</p>
<table>
<thead>
<tr>
<th>Query predicate</th>
<th>Served by <code>(customer_id, status, placed_at)</code>?</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>customer_id = 1</code></td>
<td>Yes — prefix</td>
</tr>
<tr>
<td><code>customer_id = 1 AND status = 'paid'</code></td>
<td>Yes — prefix</td>
</tr>
<tr>
<td><code>customer_id = 1 AND status = 'paid' AND placed_at &gt; d</code></td>
<td>Yes — full use</td>
</tr>
<tr>
<td><code>customer_id = 1 ORDER BY placed_at DESC</code></td>
<td>Partially: <code>status</code> is skipped, so the sort is not free</td>
</tr>
<tr>
<td><code>status = 'paid'</code> alone</td>
<td><strong>No</strong> efficient use (but see skip scan below)</td>
</tr>
<tr>
<td><code>placed_at &gt; d</code> alone</td>
<td>No efficient use</td>
</tr>
</tbody>
</table>
<p>Two PostgreSQL-specific refinements that MongoDB does not have:</p>
<ol>
<li>Even when the leading column is missing, the planner may choose a <strong>full index scan</strong> of the multicolumn index if the index is much narrower than the table — slow, but sometimes still cheaper than a heap scan. You will see this as an <code>Index Scan</code> with a <code>Filter</code> and a large number of rows removed.</li>
<li><strong>PostgreSQL 18</strong> adds <strong>skip scan</strong> for multicolumn B-trees: when the leading column has few distinct values, the executor can iterate over those distinct values and perform a sub-scan for each, so a query constraining only <code>status</code> can still use the index. It is a genuine improvement, not a replacement for correct column ordering — with a high-cardinality leading column it does not help.</li>
</ol>
<h2 id="Ordering-the-columns"><a href="#Ordering-the-columns" class="headerlink" title="Ordering the columns"></a>Ordering the columns</h2>
<p>The rule PostgreSQL practitioners use is the same shape as MongoDB's:</p>
<blockquote>
<p><strong>Equality columns first, then the column you sort by, then the range column last.</strong></p>
</blockquote>
<p>That is exactly the <strong>ESR rule</strong> — Equality, Sort, Range — from the <strong>MongoDB indexes post</strong>. The reasoning is identical in both engines: a B-tree can only continue using subsequent columns while preceding ones are pinned to single values. Once a range predicate opens up a span of the tree, everything after it in the index is no longer in useful order.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Query: SELECT … WHERE customer_id = $1 AND status = $2 AND placed_at &gt;= $3</span></span><br><span class="line"><span class="hljs-comment">--        ORDER BY placed_at DESC LIMIT 20;</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> orders (customer_id, status, placed_at <span class="hljs-keyword">DESC</span>);</span><br><span class="line"><span class="hljs-comment">--                      ^^ equality ^^^^^^^  ^^ sort + range ^^</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Where PostgreSQL and MongoDB genuinely diverge:</p>
<table>
<thead>
<tr>
<th></th>
<th>PostgreSQL</th>
<th>MongoDB</th>
</tr>
</thead>
<tbody>
<tr>
<td>Column-order rule</td>
<td>Equality → Sort → Range</td>
<td>ESR — the same rule</td>
</tr>
<tr>
<td>Missing leading column</td>
<td>Full index scan possible; skip scan in PG 18</td>
<td>Index unusable, falls back to collection scan</td>
</tr>
<tr>
<td>Combining several indexes</td>
<td><strong>Bitmap</strong> <code>BitmapAnd</code> / <code>BitmapOr</code> — routine and effective</td>
<td>Index intersection exists but is rarely chosen and usually slower</td>
</tr>
<tr>
<td>Partial-order sorts</td>
<td><strong>Incremental Sort</strong> (PG 13+) can use a partially matching index and sort only within groups</td>
<td>No equivalent</td>
</tr>
<tr>
<td>Sort direction</td>
<td><code>(a ASC, b DESC)</code> also serves its exact reverse <code>(a DESC, b ASC)</code></td>
<td>Same rule</td>
</tr>
</tbody>
</table>
<p>The bitmap difference is the practical one. In MongoDB the guidance is firmly &quot;build the compound index that matches the query&quot;. In PostgreSQL, several single-column indexes combined with <code>BitmapAnd</code> are a legitimate design for tables queried on many unpredictable column combinations — an ad-hoc filtering UI, for example — because the planner can pick whichever subset the incoming query used. A dedicated multicolumn index is still faster for a known hot query.</p>
<h2 id="Sort-direction"><a href="#Sort-direction" class="headerlink" title="Sort direction"></a>Sort direction</h2>
<p>For a single column, direction is irrelevant: a B-tree scans backwards just as cheaply. For multiple columns it matters:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> orders (customer_id, placed_at <span class="hljs-keyword">DESC</span>);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> customer_id <span class="hljs-keyword">ASC</span>,  placed_at <span class="hljs-keyword">DESC</span>   <span class="hljs-comment">-- forward scan, free</span></span><br><span class="line"><span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> customer_id <span class="hljs-keyword">DESC</span>, placed_at <span class="hljs-keyword">ASC</span>    <span class="hljs-comment">-- backward scan, also free</span></span><br><span class="line"><span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> customer_id <span class="hljs-keyword">ASC</span>,  placed_at <span class="hljs-keyword">ASC</span>    <span class="hljs-comment">-- mixed: needs a sort</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Also worth knowing: <code>NULLS FIRST</code> / <code>NULLS LAST</code> is part of the index's sort order. An index created with the default (<code>ASC NULLS LAST</code>) will not provide a free sort for <code>ORDER BY col ASC NULLS FIRST</code>.</p>

<h1 id="Chapter-4-—-Covering-indexes-and-index-only-scans"><a href="#Chapter-4-—-Covering-indexes-and-index-only-scans" class="headerlink" title="Chapter 4 — Covering indexes and index-only scans"></a>Chapter 4 — Covering indexes and index-only scans</h1>
<h2 id="INCLUDE"><a href="#INCLUDE" class="headerlink" title="INCLUDE"></a><code>INCLUDE</code></h2>
<p><strong>PostgreSQL 11+</strong> allows non-key payload columns in a B-tree:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_orders_cover</span><br><span class="line">  <span class="hljs-keyword">ON</span> orders (customer_id, placed_at)</span><br><span class="line">  INCLUDE (status, total);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>INCLUDE</code> columns are stored <strong>only in leaf pages</strong>. They cannot be searched, cannot provide ordering, and do not participate in uniqueness — they exist purely so the query can be answered without visiting the heap. Compare:</p>
<table>
<thead>
<tr>
<th></th>
<th>Key columns <code>(a, b)</code></th>
<th><code>INCLUDE (c, d)</code></th>
</tr>
</thead>
<tbody>
<tr>
<td>Searchable</td>
<td>Yes</td>

<p>The last row is the sleeper feature: you can <code>INCLUDE</code> a column of a type that has no B-tree operator class at all.</p>
<h2 id="Index-only-scans-and-the-visibility-map"><a href="#Index-only-scans-and-the-visibility-map" class="headerlink" title="Index-only scans and the visibility map"></a>Index-only scans and the visibility map</h2>
<p>An <strong>Index Only Scan</strong> answers a query entirely from the index. Two conditions must hold:</p>
<ol>
<li>Every column the query needs — in <code>SELECT</code>, <code>WHERE</code>, <code>ORDER BY</code>, and <code>GROUP BY</code> — is in the index, as a key or an <code>INCLUDE</code> column.</li>
<li>The heap pages the matching entries point at are marked <strong>all-visible</strong> in the visibility map.</li>
</ol>
<p>Condition 2 exists because index entries carry no MVCC visibility information (Post 05). If the page is not known all-visible, the executor must fetch the heap tuple to check — a <strong>heap fetch</strong> — and the &quot;index-only&quot; scan degrades toward an ordinary index scan.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line">EXPLAIN (ANALYZE, BUFFERS)</span><br><span class="line"><span class="hljs-keyword">SELECT</span> customer_id, placed_at <span class="hljs-keyword">FROM</span> orders <span class="hljs-keyword">WHERE</span> customer_id <span class="hljs-operator">=</span> <span class="hljs-number">42</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="text"><span class="line"> Index Only Scan using idx_orders_cover on orders  (cost=0.43..8.45 rows=12 width=16)</span><br><span class="line">                                                   (actual time=0.021..0.038 rows=12 loops=1)</span><br><span class="line">   Index Cond: (customer_id = 42)</span><br><span class="line">   Heap Fetches: 0                        ← 0 is what you want</span><br><span class="line">   Buffers: shared hit=4</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A non-zero <strong><code>Heap Fetches</code></strong> means the visibility map is stale for those pages. The fix is <code>VACUUM</code> — either a manual <code>VACUUM orders;</code> or, for a table that keeps regressing, more aggressive autovacuum settings for that table:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders <span class="hljs-keyword">SET</span> (autovacuum_vacuum_scale_factor <span class="hljs-operator">=</span> <span class="hljs-number">0.02</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> an index-only scan on a table that is being updated constantly is unreliable by design. Heavily written tables are rarely all-visible for long. Index-only scans shine on read-mostly and append-mostly tables.</p>
</blockquote>

<h1 id="Chapter-5-—-Partial-expression-and-unique-indexes"><a href="#Chapter-5-—-Partial-expression-and-unique-indexes" class="headerlink" title="Chapter 5 — Partial, expression, and unique indexes"></a>Chapter 5 — Partial, expression, and unique indexes</h1>
<h2 id="Partial-indexes"><a href="#Partial-indexes" class="headerlink" title="Partial indexes"></a>Partial indexes</h2>
<p>An index with a <code>WHERE</code> clause, containing entries only for matching rows.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- 99% of orders are closed; only the open ones are ever queried by status</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_orders_open</span><br><span class="line">  <span class="hljs-keyword">ON</span> orders (placed_at)</span><br><span class="line">  <span class="hljs-keyword">WHERE</span> status <span class="hljs-keyword">IN</span> (<span class="hljs-string">&#x27;pending&#x27;</span>, <span class="hljs-string">&#x27;processing&#x27;</span>);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- exclude soft-deleted rows entirely</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_users_email_live <span class="hljs-keyword">ON</span> users (email) <span class="hljs-keyword">WHERE</span> deleted_at <span class="hljs-keyword">IS</span> <span class="hljs-keyword">NULL</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- index only the rare values; the common one is better served by a seq scan</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_jobs_failed <span class="hljs-keyword">ON</span> jobs (created_at) <span class="hljs-keyword">WHERE</span> state <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;failed&#x27;</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Benefits: a much smaller index, faster to build and scan, and — often more important — <strong>cheaper writes</strong>, because rows outside the predicate do not touch the index at all.</p>
<p>The requirement: the planner must be able to <em>prove</em> that the query's <code>WHERE</code> clause implies the index predicate. It performs this proof syntactically, so it is not clever. <code>WHERE status = 'pending'</code> matches the first index above. <code>WHERE status &lt;&gt; 'closed'</code> does not, even if the two are semantically equivalent on your data. Parameterised predicates (<code>WHERE status = $1</code>) also fail the proof, because the value is unknown at planning time under generic plans.</p>
<h2 id="Expression-indexes"><a href="#Expression-indexes" class="headerlink" title="Expression indexes"></a>Expression indexes</h2>
<p>The index is built on the result of an expression rather than a bare column.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_users_lower_email <span class="hljs-keyword">ON</span> users (<span class="hljs-built_in">lower</span>(email));</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> users <span class="hljs-keyword">WHERE</span> <span class="hljs-built_in">lower</span>(email) <span class="hljs-operator">=</span> <span class="hljs-built_in">lower</span>($<span class="hljs-number">1</span>);   <span class="hljs-comment">-- uses it</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> users <span class="hljs-keyword">WHERE</span> email <span class="hljs-operator">=</span> $<span class="hljs-number">1</span>;                 <span class="hljs-comment">-- does NOT use it</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>This is why case-insensitive lookup needs one. <code>lower(email)</code> is a <em>different value</em> from <code>email</code>; a plain index on <code>email</code> is sorted by the original strings and cannot answer questions about their lowercased forms. The query must repeat the expression <strong>exactly</strong> as indexed.</p>
<p>The expression must be <code>IMMUTABLE</code>. <code>now()</code>, <code>random()</code>, and anything depending on <code>TimeZone</code> or <code>lc_collate</code> are rejected. A frequent trap:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- fails: timestamptz → text depends on the session TimeZone, so it is STABLE, not IMMUTABLE</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> events (to_char(occurred_at, <span class="hljs-string">&#x27;YYYY-MM&#x27;</span>));</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- works: date_trunc(text, timestamptz) is immutable when given an explicit zone</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> events (date_trunc(<span class="hljs-string">&#x27;month&#x27;</span>, occurred_at <span class="hljs-keyword">AT</span> <span class="hljs-type">TIME</span> ZONE <span class="hljs-string">&#x27;UTC&#x27;</span>));</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>More expression-index patterns:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> orders ((attributes<span class="hljs-operator">-</span><span class="hljs-operator">&gt;&gt;</span><span class="hljs-string">&#x27;region&#x27;</span>));            <span class="hljs-comment">-- extract a jsonb field</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> users ((first_name <span class="hljs-operator">||</span> <span class="hljs-string">&#x27; &#x27;</span> <span class="hljs-operator">||</span> last_name));    <span class="hljs-comment">-- concatenated search key</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> events (md5(payload));                       <span class="hljs-comment">-- index a value too long for a B-tree</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Two alternatives to case-insensitive expression indexes worth knowing: the <code>citext</code> extension (a case-insensitive text type), and <strong>nondeterministic collations</strong> (PostgreSQL 12+), which make ordinary <code>=</code> case- or accent-insensitive at the column level:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">COLLATION</span> case_insensitive</span><br><span class="line">  (provider <span class="hljs-operator">=</span> icu, locale <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;und-u-ks-level2&#x27;</span>, <span class="hljs-keyword">deterministic</span> <span class="hljs-operator">=</span> <span class="hljs-literal">false</span>);</span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> users (email text <span class="hljs-keyword">COLLATE</span> case_insensitive);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Unique-indexes-vs-unique-constraints"><a href="#Unique-indexes-vs-unique-constraints" class="headerlink" title="Unique indexes vs unique constraints"></a>Unique indexes vs unique constraints</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- constraint: recorded in pg_constraint, backed by an automatically created unique index</span></span><br><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> users <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">CONSTRAINT</span> users_email_key <span class="hljs-keyword">UNIQUE</span> (email);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- index: recorded only in pg_index</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">UNIQUE</span> INDEX users_email_uq <span class="hljs-keyword">ON</span> users (email);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Both enforce uniqueness identically at runtime. The differences are in what else they can do:</p>
<table>
<thead>
<tr>

</tr>

<td><strong>Yes</strong></td>
<td>No</td>
</tr>
<tr>

<td>Yes</td>
<td>No (use <code>ON CONFLICT (cols)</code>)</td>

<p>So: conditional uniqueness and case-insensitive uniqueness are index-only territory.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">UNIQUE</span> INDEX users_email_active_uq</span><br><span class="line">  <span class="hljs-keyword">ON</span> users (<span class="hljs-built_in">lower</span>(email)) <span class="hljs-keyword">WHERE</span> deleted_at <span class="hljs-keyword">IS</span> <span class="hljs-keyword">NULL</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-6-—-Reading-EXPLAIN"><a href="#Chapter-6-—-Reading-EXPLAIN" class="headerlink" title="Chapter 6 — Reading EXPLAIN"></a>Chapter 6 — Reading <code>EXPLAIN</code></h1>
<h2 id="The-two-commands"><a href="#The-two-commands" class="headerlink" title="The two commands"></a>The two commands</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line">EXPLAIN <span class="hljs-keyword">SELECT</span> …;                          <span class="hljs-comment">-- plan only, does not execute</span></span><br><span class="line">EXPLAIN (ANALYZE, BUFFERS) <span class="hljs-keyword">SELECT</span> …;       <span class="hljs-comment">-- executes and reports real timings and I/O</span></span><br><span class="line">EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS, FORMAT TEXT) <span class="hljs-keyword">SELECT</span> …;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>PostgreSQL 18</strong> includes <code>BUFFERS</code> by default whenever <code>ANALYZE</code> is used, so <code>EXPLAIN (ANALYZE)</code> alone gives the I/O picture on 18; on 17 and earlier you must ask for it. <code>SETTINGS</code> reports any planner GUC that differs from its default — the first thing to check when a plan differs between two environments. <code>track_io_timing = on</code> (Post 00) adds real read/write times to the buffer lines.</p>
<blockquote>
<p><strong>Watch out:</strong> <code>EXPLAIN ANALYZE</code> <strong>runs the statement</strong>. For <code>UPDATE</code>/<code>DELETE</code>/<code>INSERT</code>, wrap it: <code>BEGIN; EXPLAIN (ANALYZE) DELETE …; ROLLBACK;</code></p>
</blockquote>
<h2 id="The-cost-model"><a href="#The-cost-model" class="headerlink" title="The cost model"></a>The cost model</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line">Seq Scan on orders  (cost=0.00..18334.00 rows=1000000 width=45)</span><br><span class="line">                    (actual time=0.011..84.219 rows=1000000 loops=1)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><code>cost=startup..total</code> — arbitrary units, <strong>not milliseconds</strong>. They are normalised so that reading one sequential page costs <code>1.0</code>. Their only purpose is to let the planner rank alternative plans against each other.</li>
<li><code>rows=</code> — the planner's <strong>estimate</strong>.</li>
<li><code>width=</code> — estimated average row width in bytes.</li>
<li><code>actual time=first_row..all_rows</code> in milliseconds, and <code>rows=</code> the <strong>actual</strong> count.</li>
<li><code>loops=N</code> — the node ran N times. <strong><code>actual rows</code> and <code>actual time</code> are per-loop averages</strong>; multiply by <code>loops</code> for the total. Missing this is the single most common <code>EXPLAIN</code> misreading.</li>
</ul>

<th>Notes</th>
</tr>

<td>1.0</td>

<h2 id="Estimated-vs-actual"><a href="#Estimated-vs-actual" class="headerlink" title="Estimated vs actual"></a>Estimated vs actual</h2>
<p>The gap between <code>rows=</code> and <code>actual rows=</code> is the primary diagnostic signal.</p>
<ul>
<li>Estimate within roughly an order of magnitude: fine.</li>
<li>Estimate off by 100× or more: the planner is choosing based on a fiction, and every join above that node inherits the error. Causes are stale statistics, correlated columns, and non-<code>IMMUTABLE</code> expressions the planner cannot estimate. Fixes — <code>ANALYZE</code>, <code>default_statistics_target</code>, and <code>CREATE STATISTICS</code> for correlated columns — are Post 04.</li>
</ul>

</table>
<p>A bitmap heap scan's extra lines are worth reading:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line"> Bitmap Heap Scan on orders  (actual rows=12043 loops=1)</span><br><span class="line">   Recheck Cond: (customer_id = 42)</span><br><span class="line">   Heap Blocks: exact=980 lossy=0</span><br><span class="line">   Buffers: shared hit=990</span><br><span class="line">   -&gt;  Bitmap Index Scan on idx_orders_customer  (actual rows=12043 loops=1)</span><br><span class="line">         Index Cond: (customer_id = 42)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>Heap Blocks: lossy=N</code> means the bitmap outgrew <code>work_mem</code> and degraded from per-row to per-page granularity, forcing a recheck of every row on those pages. A non-zero <code>lossy</code> count is a signal to raise <code>work_mem</code> for that query.</p>
<h2 id="Reading-BUFFERS"><a href="#Reading-BUFFERS" class="headerlink" title="Reading BUFFERS"></a>Reading <code>BUFFERS</code></h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">Buffers: shared hit=990 read=12045 dirtied=3 written=0</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><code>hit</code> — found in <code>shared_buffers</code>. Cheap.</li>
<li><code>read</code> — had to be requested from the OS (which may itself have cached it). This is the number to reduce.</li>
<li><code>dirtied</code> / <code>written</code> — pages modified / flushed by this query.</li>
<li><code>temp read/written</code> — spilled to temporary files: a sort or hash exceeded <code>work_mem</code>. Almost always worth fixing.</li>
</ul>
<p>Buffer counts are more stable than timings: they do not vary with cache warmth or machine load, which makes them the better metric when comparing two candidate plans.</p>
<h2 id="When-a-sequential-scan-is-correct"><a href="#When-a-sequential-scan-is-correct" class="headerlink" title="When a sequential scan is correct"></a>When a sequential scan is correct</h2>
<p>This bears stating plainly, because a great deal of wasted tuning effort comes from trying to force an index scan that would be slower.</p>
<p>A sequential scan is the right plan when:</p>
<ol>
<li><strong>The predicate matches a large fraction of the table</strong> — beyond roughly 5–10%, random heap fetches through an index exceed the cost of reading everything sequentially. The exact crossover depends on <code>random_page_cost</code> and physical correlation.</li>
<li><strong>The table is small.</strong> Under a few hundred pages, one sequential read beats index descent plus heap fetch. The planner knows this and is right.</li>
<li><strong>No index covers the predicate</strong>, and creating one is not justified by the query's frequency.</li>
<li><strong>The query is an aggregate over most of the table</strong> — <code>SELECT count(*) FROM orders</code> genuinely must look at everything (or at least at the whole visibility map, via a parallel index-only scan).</li>
<li><strong>Parallelism applies.</strong> A parallel sequential scan across four workers can beat a single-threaded index scan outright.</li>
</ol>
<p>To <em>diagnose</em> — never to fix in production code:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SET</span> enable_seqscan <span class="hljs-operator">=</span> off;         <span class="hljs-comment">-- session only; makes seq scans absurdly expensive, not impossible</span></span><br><span class="line">EXPLAIN (ANALYZE, BUFFERS) <span class="hljs-keyword">SELECT</span> …;</span><br><span class="line">RESET enable_seqscan;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If the forced index plan is slower, the planner was right and the investigation is over. If it is much faster, you have found a cost-model or statistics problem — which is Post 04's subject.</p>

<h1 id="Chapter-7-—-Building-and-maintaining-indexes-in-production"><a href="#Chapter-7-—-Building-and-maintaining-indexes-in-production" class="headerlink" title="Chapter 7 — Building and maintaining indexes in production"></a>Chapter 7 — Building and maintaining indexes in production</h1>
<h2 id="CREATE-INDEX-CONCURRENTLY"><a href="#CREATE-INDEX-CONCURRENTLY" class="headerlink" title="CREATE INDEX CONCURRENTLY"></a><code>CREATE INDEX CONCURRENTLY</code></h2>
<p>A plain <code>CREATE INDEX</code> takes a lock that blocks all writes to the table for the entire build. On a large busy table that is an outage.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX CONCURRENTLY idx_orders_placed_at <span class="hljs-keyword">ON</span> orders (placed_at);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>What it costs you:</p>
<ul>
<li><strong>Two</strong> table scans instead of one, plus a wait for all transactions that could see the table to finish. Substantially slower in wall-clock terms.</li>
<li>It <strong>cannot run inside a transaction block</strong> — which means migration frameworks that wrap each migration in a transaction need an explicit escape (Rails: <code>disable_ddl_transaction!</code>; Django: <code>atomic = False</code>; plain SQL: run it as its own statement).</li>
<li>If it fails — a deadlock, a unique violation discovered during the second pass, a cancelled session — it leaves behind an <strong>invalid</strong> index that is maintained on writes but never used by queries.</li>
</ul>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- find invalid indexes</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> c.relname</span><br><span class="line"><span class="hljs-keyword">FROM</span> pg_index i <span class="hljs-keyword">JOIN</span> pg_class c <span class="hljs-keyword">ON</span> c.oid <span class="hljs-operator">=</span> i.indexrelid</span><br><span class="line"><span class="hljs-keyword">WHERE</span> <span class="hljs-keyword">NOT</span> i.indisvalid;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">DROP</span> INDEX CONCURRENTLY idx_orders_placed_at;   <span class="hljs-comment">-- then retry</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>REINDEX INDEX CONCURRENTLY</code> (PostgreSQL 12+) rebuilds an existing index without blocking writes, and <code>DROP INDEX CONCURRENTLY</code> removes one the same way. On a replicated setup, build indexes on standbys first only if you are using logical replication — with physical streaming replication the index arrives automatically through WAL.</p>
<h2 id="Index-bloat"><a href="#Index-bloat" class="headerlink" title="Index bloat"></a>Index bloat</h2>
<p>MVCC leaves dead entries behind; <code>VACUUM</code> reclaims space for reuse but does not return it to the operating system, and a B-tree that has churned heavily can end up substantially larger than a freshly built equivalent. Bottom-up index deletion (PG 14+) reduced this markedly, but it did not eliminate it.</p>

<p>Four caveats before dropping anything:</p>
<ol>
<li><strong><code>idx_scan</code> is cumulative since the last statistics reset.</strong> Check <code>stats_reset</code> in <code>pg_stat_database</code>, and remember that <code>pg_upgrade</code> resets it. A &quot;never used&quot; index on a freshly upgraded cluster is meaningless. On <strong>PostgreSQL 16+</strong>, <code>pg_stat_user_indexes.last_idx_scan</code> gives you a timestamp instead of a bare counter, which is far more actionable.</li>
<li><strong>Statistics are per-node.</strong> An index unused on the primary may be the backbone of a report running on a read replica. Check every node.</li>
<li><strong>Quarterly and annual jobs exist.</strong> Observe across a period longer than your longest reporting cycle.</li>
<li><strong>Unique and primary indexes enforce correctness</strong> regardless of scan counts. Never drop one because it looks idle.</li>
</ol>
<p>PostgreSQL has no built-in equivalent of MongoDB's <code>hideIndex()</code> — the &quot;hide it for a week and watch&quot; pattern from the MongoDB course does not translate directly. A <code>UPDATE pg_index SET indisvalid = false</code> hack is widely circulated for this purpose; avoid it, because direct catalog manipulation is unsupported and interacts badly with cached plans. The honest procedure instead:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- 1. record the definition so recreating it is trivial</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> pg_get_indexdef(<span class="hljs-string">&#x27;idx_maybe_unused&#x27;</span>::regclass);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- 2. drop it online</span></span><br><span class="line"><span class="hljs-keyword">DROP</span> INDEX CONCURRENTLY idx_maybe_unused;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- 3. monitor. <h2 id="Related-indexes-worth-pruning"><a href="#Related-indexes-worth-pruning" class="headerlink" title="Related indexes worth pruning"></a>Related indexes worth pruning</h2>
<p>An index whose column list is a <strong>prefix</strong> of another index's is usually redundant: <code>(customer_id)</code> is covered by <code>(customer_id, status)</code>. The exceptions are worth checking — the narrower index is smaller and may be preferred for index-only scans, and a prefix index is not redundant if the wider index is partial or has a different opclass.</p>

<h2 id="Ten-rules-of-thumb"><a href="#Ten-rules-of-thumb" class="headerlink" title="Ten rules of thumb"></a>Ten rules of thumb</h2>
<ol>
<li>Index every column used in a <strong>frequent</strong> filter, join, or sort. Not more.</li>
<li><strong>Index every foreign-key column</strong> — PostgreSQL does not do it for you, and unindexed FKs make parent deletes scan the child table.</li>
<li>Order multicolumn indexes <strong>equality → sort → range</strong> (ESR).</li>
<li>Prefer one well-ordered multicolumn index for a known hot query; rely on bitmap combination for unpredictable ad-hoc filtering.</li>
<li>Use <strong>partial indexes</strong> whenever queries only ever touch a subset — the write saving is as valuable as the read saving.</li>
<li>Reach for <code>INCLUDE</code> when a hot query needs one or two extra columns, and confirm <code>Heap Fetches: 0</code>.</li>
<li>Set <code>random_page_cost</code> to something truthful for your storage before concluding the planner is wrong.</li>
<li>Always build on live tables with <code>CONCURRENTLY</code>, and check for invalid indexes afterwards.</li>
<li>Verify every new index with <code>EXPLAIN (ANALYZE, BUFFERS)</code> on realistic data volumes — an index that helps at 1,000 rows may be ignored at 10 million.</li>
<li>Review <code>pg_stat_user_indexes</code> periodically. Every index you keep is paid for on every write, forever.</li>
</ol>

<h2 id="Exercise-2-—-Column-order"><a href="#Exercise-2-—-Column-order" class="headerlink" title="Exercise 2 — Column order"></a>Exercise 2 — Column order</h2>
<p>For <code>WHERE customer_id = $1 AND status = 'paid' AND placed_at &gt;= $2 ORDER BY placed_at DESC LIMIT 20</code>, build the correct multicolumn index and justify each position. Then build a deliberately wrong one (<code>placed_at, customer_id, status</code>) and compare plans.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX idx_orders_esr <span class="hljs-keyword">ON</span> orders (customer_id, status, placed_at <span class="hljs-keyword">DESC</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>customer_id</code> and <code>status</code> are equality — they pin the scan to one contiguous span. <code>placed_at</code> is both the sort key and the range bound, so it goes last and carries <code>DESC</code> to match the query's sort, making the <code>ORDER BY</code> free and the <code>LIMIT 20</code> a partial scan. Leading with <code>placed_at</code> forces a range scan across all customers, and <code>customer_id</code>/<code>status</code> degrade to filters.</p>
</details>

<h2 id="Exercise-8-—-ESR-across-engines"><a href="#Exercise-8-—-ESR-across-engines" class="headerlink" title="Exercise 8 — ESR across engines"></a>Exercise 8 — ESR across engines</h2>
<p>Take the MongoDB compound index <code>{ user_id: 1, status: 1, at: -1 }</code> from the <strong>MongoDB indexes post</strong> and write the equivalent PostgreSQL index. List two things PostgreSQL can do with that index that MongoDB cannot, and one thing that is identical in both.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> orders (user_id, status, placed_at <span class="hljs-keyword">DESC</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>PostgreSQL-only: (1) <code>INCLUDE</code> extra payload columns for an index-only scan; (2) combine this index with others via <code>BitmapAnd</code>, or use it with <code>Incremental Sort</code> for a partially-matching <code>ORDER BY</code>; (3) on PG 18, a skip scan may still use it when <code>user_id</code> is unconstrained and low-cardinality. Identical in both: the leading-column/prefix rule and the equality-sort-range ordering principle, and the fact that mixed sort directions require the index to declare them.</p>

<h1 id="Cheat-sheet"><a href="#Cheat-sheet" class="headerlink" title="Cheat-sheet"></a>Cheat-sheet</h1>
<table>
<thead>
<tr>
<th>What</th>
<th>How</th>
</tr>
</thead>
<tbody>
<tr>
<td>Online build</td>
<td><code>CREATE INDEX CONCURRENTLY …</code> (not inside a transaction)</td>
</tr>
<tr>
<td>Multicolumn ordering</td>
<td>Equality → Sort → Range (ESR)</td>
</tr>
<tr>
<td>Covering index</td>
<td><code>CREATE INDEX … (a, b) INCLUDE (c, d)</code> (PG 11+)</td>
</tr>
<tr>
<td>Partial index</td>
<td><code>CREATE INDEX … WHERE predicate</code></td>
</tr>
<tr>
<td>Expression index</td>
<td><code>CREATE INDEX … (lower(email))</code> — query must repeat the expression</td>
</tr>
<tr>
<td>Array / jsonb / full text</td>
<td><code>USING gin (…)</code></td>
</tr>
<tr>
<td><code>LIKE '%x%'</code></td>
<td><code>CREATE EXTENSION pg_trgm; USING gin (col gin_trgm_ops)</code></td>
</tr>
<tr>
<td>Range overlap, geometry, KNN</td>
<td><code>USING gist (…)</code></td>
</tr>
<tr>
<td>Huge correlated append-only table</td>
<td><code>USING brin (…)</code> — check <code>pg_stats.correlation</code> first</td>
</tr>
<tr>
<td>Plan with real numbers</td>
<td><code>EXPLAIN (ANALYZE, BUFFERS) SELECT …</code></td>
</tr>
<tr>
<td>Explain a DML safely</td>
<td><code>BEGIN; EXPLAIN (ANALYZE) DELETE …; ROLLBACK;</code></td>
</tr>
<tr>
<td>Per-loop values</td>
<td><code>actual rows × loops</code> = total</td>
</tr>
<tr>
<td>Index-only scan is real</td>
<td><code>Heap Fetches: 0</code></td>
</tr>
<tr>
<td>Bitmap spilled <code>work_mem</code></td>
<td><code>Heap Blocks: lossy &gt; 0</code> → raise <code>work_mem</code></td>
</tr>
<tr>
<td>Sort spilled to disk</td>
<td><code>temp read/written</code> in <code>Buffers</code></td>
</tr>
<tr>
<td>SSD cost model</td>
<td><code>ALTER SYSTEM SET random_page_cost = 1.1;</code></td>
</tr>
<tr>
<td>Diagnose a seq scan</td>
<td><code>SET enable_seqscan = off;</code> (diagnosis only)</td>
</tr>

<td>Rebuild an index online</td>
<td><code>REINDEX INDEX CONCURRENTLY idx;</code></td>
</tr>
