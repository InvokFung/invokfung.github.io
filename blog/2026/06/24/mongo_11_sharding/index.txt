11:T85ba,<p>A single replica set scales reads (Post 10) and stores as much data as fits on one machine. To scale <strong>writes</strong> and store <strong>more data than one machine can hold</strong>, MongoDB <strong>shards</strong> — partitions a collection across multiple replica sets (&quot;shards&quot;) by a chosen <strong>shard key</strong>. Get the shard key right and the cluster scales linearly. Get it wrong and you get hot shards, jumbo chunks, scatter-gather queries, and an expensive resharding project. This post covers the architecture, the shard-key decision (the most important one), ranged vs hashed sharding, chunks + balancer, zones, <strong>resharding</strong> (5.0+), and query targeting vs scatter-gather.</p>

<h1 id="Chapter-3-—-Shard-key-—-the-most-important-decision"><a href="#Chapter-3-—-Shard-key-—-the-most-important-decision" class="headerlink" title="Chapter 3 — Shard key — the most important decision"></a>Chapter 3 — Shard key — the most important decision</h1>
<p>A shard key is one or more fields whose <strong>value</strong> decides which shard each document lives on.</p>
<h3 id="Three-properties-to-evaluate"><a href="#Three-properties-to-evaluate" class="headerlink" title="Three properties to evaluate"></a>Three properties to evaluate</h3>
<table>
<thead>
<tr>
<th>Property</th>
<th>Good</th>
<th>Bad</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Cardinality</strong></td>
<td>many distinct values</td>
<td>few values</td>
</tr>
<tr>
<td><strong>Frequency</strong></td>
<td>values appear with similar frequency</td>
<td>one value dominates</td>
</tr>
<tr>
<td><strong>Monotonicity</strong></td>
<td>random-looking distribution</td>
<td>always-increasing (<code>_id</code>, timestamps)</td>
</tr>
</tbody>
</table>
<h3 id="Why-each-matters"><a href="#Why-each-matters" class="headerlink" title="Why each matters"></a>Why each matters</h3>
<ul>
<li><strong>Low cardinality</strong> — too few values to spread across many shards. A <code>{ status: 1 }</code> shard key over <code>[&quot;open&quot;, &quot;closed&quot;]</code> gives 2 chunks max; can't scale beyond 2 shards.</li>
<li><strong>Skewed frequency</strong> — one tenant or one product dominates → one shard takes all writes (hot shard).</li>
<li><strong>Monotonic key</strong> (auto-increment ID, timestamp) → all new writes hit the chunk holding the max value → that chunk's shard becomes hot.</li>
</ul>
<h3 id="The-ideal"><a href="#The-ideal" class="headerlink" title="The ideal"></a>The ideal</h3>
<p>A field that's:</p>
<ul>
<li>many distinct values,</li>
<li>writes spread evenly,</li>
<li>frequently appears in queries' filters so <code>mongos</code> can route to one shard.</li>
</ul>
<h3 id="Common-shard-key-choices"><a href="#Common-shard-key-choices" class="headerlink" title="Common shard-key choices"></a>Common shard-key choices</h3>
<table>
<thead>
<tr>
<th>Workload</th>
<th>Good shard key</th>
</tr>
</thead>
<tbody>
<tr>
<td>Multi-tenant SaaS</td>
<td><code>{ tenant_id: 1, _id: 1 }</code> (tenant-aware queries route to one shard)</td>
</tr>
<tr>
<td>User-centric (orders per user)</td>
<td><code>{ user_id: 1, _id: 1 }</code></td>
</tr>
<tr>
<td>IoT telemetry, write-heavy</td>
<td><code>{ device_id: &quot;hashed&quot; }</code> (even distribution)</td>
</tr>
<tr>
<td>Time-series append</td>
<td>hashed on <code>device_id</code> + ranged on time secondary; OR native time-series collection</td>
</tr>
<tr>
<td>Geo-partitioned</td>
<td><code>{ region: 1, _id: 1 }</code> + zone sharding</td>
</tr>
</tbody>
</table>
<p>A <strong>compound shard key</strong> (<code>{ tenant_id: 1, _id: 1 }</code>) gives tenant-aware routing (tenant_id used by queries) while keeping cardinality high (via <code>_id</code> tiebreaker).</p>

<h1 id="Chapter-4-—-Ranged-vs-hashed-sharding"><a href="#Chapter-4-—-Ranged-vs-hashed-sharding" class="headerlink" title="Chapter 4 — Ranged vs hashed sharding"></a>Chapter 4 — Ranged vs hashed sharding</h1>
<h2 id="Ranged-default"><a href="#Ranged-default" class="headerlink" title="Ranged (default)"></a>Ranged (default)</h2>
<p>Documents with shard-key values in a range live on the same chunk.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">sh.<span class="hljs-title function_">shardCollection</span>(<span class="hljs-string">&quot;shop.orders&quot;</span>, { <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li>Pro: range queries on the shard key only hit shards in that range.</li>
<li>Con: monotonic inserts hot-spot the max-range chunk.</li>
</ul>
<h2 id="Hashed"><a href="#Hashed" class="headerlink" title="Hashed"></a>Hashed</h2>
<p>The shard key is hashed before placement.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">events</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">device_id</span>: <span class="hljs-string">&quot;hashed&quot;</span> })</span><br><span class="line">sh.<span class="hljs-title function_">shardCollection</span>(<span class="hljs-string">&quot;shop.events&quot;</span>, { <span class="hljs-attr">device_id</span>: <span class="hljs-string">&quot;hashed&quot;</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li>Pro: writes always spread evenly across shards, even for monotonic / sequential keys.</li>
<li>Con: range queries on the shard key become <strong>scatter-gather</strong> (visit every shard).</li>
</ul>
<p>Modern compound hashed (4.4+):</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">sh.<span class="hljs-title function_">shardCollection</span>(<span class="hljs-string">&quot;shop.events&quot;</span>, { <span class="hljs-attr">device_id</span>: <span class="hljs-string">&quot;hashed&quot;</span>, <span class="hljs-attr">at</span>: <span class="hljs-number">1</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Hashed on <code>device_id</code>, ranged on <code>at</code> as secondary — combines distribution + time-range-by-device queries.</p>
<hr>
<h1 id="Chapter-5-—-Chunks-the-balancer"><a href="#Chapter-5-—-Chunks-the-balancer" class="headerlink" title="Chapter 5 — Chunks + the balancer"></a>Chapter 5 — Chunks + the balancer</h1>
<p>A <strong>chunk</strong> is a range of shard-key values. Each chunk lives entirely on one shard. Chunk size defaults to <strong>128 MB</strong> in modern versions.</p>
<p>The <strong>balancer</strong> is a background process on the primary config server that moves chunks between shards to keep distribution roughly even. Runs continuously; can be scheduled to a window:</p>

<p>Inspect chunk distribution:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">sh.<span class="hljs-title function_">status</span>()</span><br><span class="line">db.<span class="hljs-title function_">adminCommand</span>({ <span class="hljs-attr">getShardMap</span>: <span class="hljs-number">1</span> })</span><br><span class="line">db.<span class="hljs-title function_">printShardingStatus</span>()</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Jumbo-chunks"><a href="#Jumbo-chunks" class="headerlink" title="Jumbo chunks"></a>Jumbo chunks</h2>
<p>A chunk exceeding the chunk size that <strong>can't be split</strong> (because all its documents have the same shard-key value) is called <strong>jumbo</strong> and is marked unmovable. The balancer skips it.</p>
<p>Cause: too few distinct values for the shard key (low cardinality) — usually a sign the shard key was wrong.</p>
<p>Fix: re-shard the collection (Chapter 7); or pre-split with care.</p>

<li><strong>Region pinning</strong> — APAC users on APAC shards (low-latency reads + compliance).</li>
<li><strong>Tiered storage</strong> — recent data on SSD shards, archive on cheap shards.</li>
</ul>

<h1 id="Chapter-7-—-Resharding-50"><a href="#Chapter-7-—-Resharding-50" class="headerlink" title="Chapter 7 — Resharding (5.0+)"></a>Chapter 7 — Resharding (5.0+)</h1>
<p>Pre-5.0, changing a shard key meant dumping the collection, dropping, and reinserting under a new shard key — multi-hour outage for big collections.</p>
<p>5.0+ introduced <strong>online resharding</strong>:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">sh.<span class="hljs-title function_">reshardCollection</span>(<span class="hljs-string">&quot;shop.orders&quot;</span>, { <span class="hljs-attr">tenant_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The new shard key is computed; chunks rebalance in the background; clients keep reading + writing throughout. Final cutover is brief.</p>
<p>Constraints:</p>
<ul>
<li>Disk + I/O cost is high; plan for a slower-than-usual period.</li>
<li>Some prerequisites on indexes + collection size.</li>
<li>The new shard key must have an index.</li>
</ul>
<p>This dramatically lowered the cost of &quot;I chose the wrong shard key&quot; — but a good initial choice still saves time + money.</p>
<hr>
<h1 id="Chapter-8-—-Query-targeting-vs-scatter-gather"><a href="#Chapter-8-—-Query-targeting-vs-scatter-gather" class="headerlink" title="Chapter 8 — Query targeting vs scatter-gather"></a>Chapter 8 — Query targeting vs scatter-gather</h1>
<p><img src="/blog/assets/mongo/diagram_11_sharding.svg" alt="A targeted query that reaches one shard next to a scatter-gather query that reaches every shard"></p>
<p>When a query includes the shard key, <code>mongos</code> can route to one (or few) specific shards. Otherwise it has to ask <strong>every</strong> shard (&quot;scatter&quot;) and merge results (&quot;gather&quot;).</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// includes shard key → routed to one shard</span></span><br><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">user_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">status</span>: <span class="hljs-string">&quot;paid&quot;</span> })</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// no shard key → scatter-gather to ALL shards</span></span><br><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">find</span>({ <span class="hljs-attr">status</span>: <span class="hljs-string">&quot;paid&quot;</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Scatter-gather scales <strong>poorly</strong> as the cluster grows — adding a shard makes scatter-gather queries <em>slower</em>, not faster.</p>
<p>Check with explain (sharded version):</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">find</span>({ ... }).<span class="hljs-title function_">explain</span>(<span class="hljs-string">&quot;executionStats&quot;</span>)</span><br><span class="line"><span class="hljs-comment">// look at &quot;shards&quot; array; one entry per shard visited</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Trick:</strong> the hot path of every endpoint should include the shard key in its filter. Reports + admin queries can scatter-gather. Plan your access patterns accordingly when picking a shard key.</p>
</blockquote>
<hr>
<h1 id="Chapter-9-—-Aggregation-sharding"><a href="#Chapter-9-—-Aggregation-sharding" class="headerlink" title="Chapter 9 — Aggregation + sharding"></a>Chapter 9 — Aggregation + sharding</h1>
<p>Most aggregation stages run per shard, then <code>mongos</code> merges. Some stages must run after the merge (<code>$group</code>, final <code>$sort</code>, <code>$lookup</code> against an unsharded collection).</p>
<p>Implications:</p>
<ul>
<li><code>$match</code> early — lets shards drop docs before pulling them to mongos.</li>
<li><code>$lookup</code> foreign collection should be unsharded (sharded <code>$lookup</code> works but is slower).</li>
<li><code>$out</code> / <code>$merge</code> to a sharded target — supported since 4.4 / 5.0.</li>
</ul>
<p><code>explain</code> shows the split between <code>$shards</code> stages and <code>$mergerPart</code> stages.</p>

<p>Atlas surfaces sharding as a cluster tier upgrade. You pick a shard key in the UI; resharding is a one-click operation. Connection string remains <code>mongodb+srv://</code> — <code>mongos</code> routing is invisible to clients.</p>

<h1 id="Chapter-11-—-When-to-shard-and-when-not"><a href="#Chapter-11-—-When-to-shard-and-when-not" class="headerlink" title="Chapter 11 — When to shard (and when not)"></a>Chapter 11 — When to shard (and when not)</h1>
<h3 id="Shard-when"><a href="#Shard-when" class="headerlink" title="Shard when"></a>Shard when</h3>
<ul>
<li>Single replica set's CPU / disk / RAM is the bottleneck and vertical scaling is exhausted.</li>
<li>Working-set (hot indexes + frequently-accessed docs) exceeds RAM, even at maximum instance size.</li>
<li>Write throughput needed exceeds what one primary can sustain.</li>
<li>Data set exceeds biggest available single-instance storage.</li>
<li>Regulatory / latency requirement to keep data in specific regions.</li>
</ul>
<h3 id="Dont-shard-when"><a href="#Dont-shard-when" class="headerlink" title="Don't shard when"></a>Don't shard when</h3>
<ul>
<li>Single replica set still handles your load (most apps' entire lifecycle).</li>
<li>Working-set fits in RAM on a larger instance.</li>
<li>Sharding overhead (extra hops via <code>mongos</code>, complexity, cost) doesn't pay back.</li>
</ul>
<p><strong>Vertical scaling beats horizontal scaling until you have no choice</strong> — modern Atlas tiers go to many TB of RAM. Most apps never shard.</p>

<h2 id="Exercise-6-—-Reshard"><a href="#Exercise-6-—-Reshard" class="headerlink" title="Exercise 6 — Reshard"></a>Exercise 6 — Reshard</h2>
<p>(Atlas / 5.0+ only.) Initiate a resharding from <code>{ user_id: 1 }</code> to <code>{ tenant_id: 1, user_id: 1 }</code>. Watch the operation progress.</p>
