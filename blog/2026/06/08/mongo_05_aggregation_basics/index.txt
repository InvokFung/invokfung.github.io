11:Td845,<p>The aggregation framework is MongoDB's &quot;everything beyond CRUD&quot; engine. A <strong>pipeline</strong> is a sequence of stages, each transforming the stream of documents flowing through it — filter, group, project, sort, join, unwind, compute. This post covers the core stages every project uses: <code>$match</code>, <code>$project</code>, <code>$addFields</code>, <code>$group</code>, <code>$sort</code>, <code>$limit</code>, <code>$skip</code>, <code>$count</code>, <code>$unwind</code>, <code>$lookup</code>. Post 06 follows with advanced stages (<code>$facet</code>, <code>$bucket</code>, <code>$graphLookup</code>, <code>$merge</code>, window functions).</p>
<blockquote>
<p>Series map: 00 Foundations → 01 CRUD → 02 Query Operators → 03 Indexes → 04 Query Optimization → <strong>05 Aggregation Basics</strong> (this post) → 06 Aggregation Advanced → … → 17 Drivers &amp; Case Studies.</p>
</blockquote>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Write an aggregation pipeline composed of stages.</li>
<li>Use <code>$match</code> early to leverage indexes.</li>
<li>Group + reduce with <code>$group</code> and accumulators (<code>$sum</code>, <code>$avg</code>, <code>$first</code>, <code>$last</code>, <code>$push</code>, <code>$addToSet</code>, <code>$min</code>, <code>$max</code>).</li>
<li>Reshape with <code>$project</code>, <code>$addFields</code>, <code>$set</code>, <code>$unset</code>.</li>
<li>Sort, limit, skip, count results.</li>
<li>Flatten arrays with <code>$unwind</code>.</li>
<li>Join collections with <code>$lookup</code> (left outer join).</li>
</ul>

<h1 id="Chapter-1-—-Pipeline-basics"><a href="#Chapter-1-—-Pipeline-basics" class="headerlink" title="Chapter 1 — Pipeline basics"></a>Chapter 1 — Pipeline basics</h1>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">aggregate</span>([</span><br><span class="line">  { <span class="hljs-attr">$match</span>: { <span class="hljs-attr">status</span>: <span class="hljs-string">&quot;paid&quot;</span> } },</span><br><span class="line">  { <span class="hljs-attr">$group</span>: { <span class="hljs-attr">_id</span>: <span class="hljs-string">&quot;$user_id&quot;</span>, <span class="hljs-attr">total</span>: { <span class="hljs-attr">$sum</span>: <span class="hljs-string">&quot;$total&quot;</span> } } },</span><br><span class="line">  { <span class="hljs-attr">$sort</span>: { <span class="hljs-attr">total</span>: -<span class="hljs-number">1</span> } },</span><br><span class="line">  { <span class="hljs-attr">$limit</span>: <span class="hljs-number">10</span> }</span><br><span class="line">])</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A pipeline is an <strong>array of stage objects</strong>. Each stage takes the previous stage's output documents as input and emits its own. Order matters.</p>
<p>Mental model:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">collection → [stage 1] → docs → [stage 2] → docs → ... → results</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Field-references"><a href="#Field-references" class="headerlink" title="Field references"></a>Field references</h2>
<p>Inside aggregation stages, prefix field names with <code>$</code> to reference document values:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">$project</span>: { <span class="hljs-attr">full</span>: { <span class="hljs-attr">$concat</span>: [<span class="hljs-string">&quot;$first&quot;</span>, <span class="hljs-string">&quot; &quot;</span>, <span class="hljs-string">&quot;$last&quot;</span>] } } }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A double-dollar <code>$$variable</code> references a named variable (<code>NOW</code>, <code>ROOT</code>, <code>CURRENT</code>, or pipeline-defined).</p>

<h1 id="Chapter-2-—-match-—-filter"><a href="#Chapter-2-—-match-—-filter" class="headerlink" title="Chapter 2 — $match — filter"></a>Chapter 2 — <code>$match</code> — filter</h1>
<p>Same syntax as <code>find</code> filter:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">{ <span class="hljs-attr">$match</span>: { <span class="hljs-attr">status</span>: <span class="hljs-string">&quot;paid&quot;</span>, <span class="hljs-attr">total</span>: { <span class="hljs-attr">$gte</span>: <span class="hljs-number">50</span> } } }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>Always put <code>$match</code> as early as possible</strong> in the pipeline. When <code>$match</code> is the first stage, MongoDB can use indexes to skip non-matching documents entirely. Later in the pipeline it can't.</p>

<p>The pipeline form lets you filter/sort/limit the joined documents — far more efficient than fetching all then dropping.</p>
<h2 id="Performance"><a href="#Performance" class="headerlink" title="Performance"></a>Performance</h2>
<ul>
<li><code>$lookup</code> is <strong>not free</strong> — for every input doc, it queries the foreign collection.</li>
<li>The foreign-collection field (the <code>foreignField</code>) should be indexed.</li>
<li>Avoid <code>$lookup</code> in hot user-facing paths; prefer embedded documents (Post 07).</li>
<li>Acceptable for reporting / dashboards where latency is less critical.</li>
</ul>
<h2 id="lookup-limits"><a href="#lookup-limits" class="headerlink" title="$lookup limits"></a>$lookup limits</h2>
<ul>
<li>Result document size capped at 16 MB (the BSON doc limit).</li>
<li>For huge joins, consider denormalisation or pre-aggregation into a materialised view (<code>$merge</code>, Post 06).</li>
</ul>

<h1 id="Chapter-10-—-Performance-indexing-for-aggregations"><a href="#Chapter-10-—-Performance-indexing-for-aggregations" class="headerlink" title="Chapter 10 — Performance + indexing for aggregations"></a>Chapter 10 — Performance + indexing for aggregations</h1>
<ul>
<li>The first <code>$match</code> and the first <code>$sort</code> (if both at the top) can use indexes.</li>
<li><code>$lookup</code>'s <code>foreignField</code> should be indexed.</li>
<li>Large <code>$group</code> results consume memory; pass <code>{ allowDiskUse: true }</code> for big aggregations.</li>
<li>Avoid expensive transformations before <code>$match</code> reduces the dataset.</li>
<li>Use <code>.explain(&quot;executionStats&quot;)</code> on aggregations (Post 04).</li>
</ul>
<p>Aggregation result size cap: 16 MB per document. For huge outputs, write to a collection with <code>$out</code> / <code>$merge</code> and query separately.</p>
<blockquote>
<p><strong>Trick:</strong> <strong><code>$count</code> is faster than <code>$group: { _id: null, c: { $sum: 1 } }</code></strong>. The dedicated stage is optimised internally.</p>
</blockquote>

<p>Compute daily revenue with <code>$out</code> to a <code>daily_revenue</code> collection. Then change to <code>$merge</code> so subsequent runs update incrementally.</p>
