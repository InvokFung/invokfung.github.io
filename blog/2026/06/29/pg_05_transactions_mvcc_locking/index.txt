11:T14b5d,<p>A transaction is the unit in which a database promises to be correct. PostgreSQL implements that promise with <strong>MVCC</strong> — multi-version concurrency control — where writers never block readers and readers never block writers, because every row can exist in several versions at once. That design explains almost everything else in this post: why an <code>UPDATE</code> writes a new row instead of editing one, why <code>VACUUM</code> exists at all, why an idle transaction can quietly break your cluster, and why <code>SERIALIZABLE</code> hands you an error instead of a lock. This post covers the mechanics, the four isolation levels as PostgreSQL actually implements them, explicit locking, deadlocks, and the vacuum consequences.</p>

<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Atomicity</strong> — a transaction's effects are all applied or none are. PostgreSQL gets this from the commit record in the WAL: until the commit record is durable, the transaction's tuples are simply invisible.</li>
<li><strong>Consistency</strong> — the database moves from one state satisfying all declared constraints to another. This is the <em>application's and the schema's</em> property; the database enforces it through constraints, not by magic.</li>
<li><strong>Isolation</strong> — concurrent transactions produce a result consistent with some acceptable ordering. How strong that guarantee is depends on the isolation level (Chapter 3).</li>
<li><strong>Durability</strong> — once <code>COMMIT</code> returns, the effects survive a crash. Provided by write-ahead logging plus <code>fsync</code>; weakened deliberately by <code>synchronous_commit = off</code>.</li>
<li><strong>Anomaly</strong> — a concurrency outcome that a given isolation level permits: dirty read, non-repeatable read, phantom read, lost update, write skew.</li>
</ul>

<p><strong>Watch out:</strong> after any error inside a transaction block, PostgreSQL puts the session into the aborted state — every subsequent statement fails with &quot;current transaction is aborted&quot; until you <code>ROLLBACK</code> or <code>ROLLBACK TO SAVEPOINT</code>. Drivers that wrap each statement in an implicit savepoint hide this and pay for it in overhead.</p>
</blockquote>

<h1 id="Chapter-2-—-MVCC-mechanics"><a href="#Chapter-2-—-MVCC-mechanics" class="headerlink" title="Chapter 2 — MVCC mechanics"></a>Chapter 2 — MVCC mechanics</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Tuple</strong> — one physical row version on a heap page. A logical row is a chain of tuples.</li>
<li><strong><code>xmin</code></strong> — the transaction ID that inserted this tuple version.</li>
<li><strong><code>xmax</code></strong> — the transaction ID that deleted or superseded it; <code>0</code> while the version is live.</li>
<li><strong><code>ctid</code></strong> — the physical location <code>(page, offset)</code> of a tuple. Changes on every update.</li>
<li><strong>Snapshot</strong> — the set of transactions considered committed at a point in time. Determines which tuple versions a statement can see.</li>
<li><strong>Dead tuple</strong> — a version no snapshot in the system can still see. Reclaimable by vacuum.</li>
</ul>
<p>Every table has these hidden system columns. Select them directly:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> t (id <span class="hljs-type">int</span> <span class="hljs-keyword">PRIMARY</span> KEY, v text);</span><br><span class="line"><span class="hljs-keyword">INSERT</span> <span class="hljs-keyword">INTO</span> t <span class="hljs-keyword">VALUES</span> (<span class="hljs-number">1</span>, <span class="hljs-string">&#x27;a&#x27;</span>);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> ctid, xmin, xmax, id, v <span class="hljs-keyword">FROM</span> t;</span><br><span class="line"><span class="hljs-comment">--  (0,1) | 812 | 0 | 1 | a</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">UPDATE</span> t <span class="hljs-keyword">SET</span> v <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;b&#x27;</span> <span class="hljs-keyword">WHERE</span> id <span class="hljs-operator">=</span> <span class="hljs-number">1</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> ctid, xmin, xmax, id, v <span class="hljs-keyword">FROM</span> t;</span><br><span class="line"><span class="hljs-comment">--  (0,2) | 813 | 0 | 1 | b       &lt;- a NEW tuple at a new ctid</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The old tuple at <code>(0,1)</code> is still on the page with <code>xmax = 813</code>. It stays there, invisible, until vacuum reclaims it.</p>
<h2 id="Why-UPDATE-writes-a-new-version"><a href="#Why-UPDATE-writes-a-new-version" class="headerlink" title="Why UPDATE writes a new version"></a>Why UPDATE writes a new version</h2>
<p>Overwriting in place would destroy the version that concurrent readers are still entitled to see. Instead:</p>
<ol>
<li>The new version is written (usually on the same page if there is room).</li>
<li>The old version's <code>xmax</code> is set to the updating transaction's ID.</li>
<li>Readers with older snapshots continue to see the old version; readers with newer snapshots see the new one.</li>
<li>Vacuum removes the old version once no snapshot needs it.</li>
</ol>
<p>Consequences you have to live with:</p>
<ul>
<li>An <code>UPDATE</code> costs roughly as much as a <code>DELETE</code> plus an <code>INSERT</code>.</li>
<li>Every index entry pointing at the row must be updated too — <strong>unless</strong> the update is a <strong>HOT</strong> (Heap-Only Tuple) update, which requires that no indexed column changed and that the new version fits on the same page. HOT updates are why <code>fillfactor</code> below 100 can help write-heavy tables.</li>
<li>Tables grow under update load. Reclaiming the space is vacuum's job (Chapter 8).</li>
</ul>
<h2 id="Snapshots-and-visibility"><a href="#Snapshots-and-visibility" class="headerlink" title="Snapshots and visibility"></a>Snapshots and visibility</h2>
<p>A snapshot records: the next unassigned transaction ID, and the list of transactions in flight. A tuple is visible if its <code>xmin</code> committed before the snapshot and its <code>xmax</code> either is zero or belongs to a transaction that had not committed at snapshot time.</p>
<ul>
<li><strong>READ COMMITTED</strong> takes a <strong>new snapshot at the start of each statement</strong>. Two identical <code>SELECT</code>s in one transaction can return different data.</li>
<li><strong>REPEATABLE READ</strong> and <strong>SERIALIZABLE</strong> take <strong>one snapshot at the first statement</strong> and keep it for the whole transaction.</li>
</ul>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> txid_current();               <span class="hljs-comment">-- current XID (assigns one if none yet)</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> pg_current_xact_id();         <span class="hljs-comment">-- PostgreSQL 13+ name, 64-bit &quot;full&quot; XID</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> pg_current_snapshot(); <span class="hljs-comment">-- xmin:xmax:in-progress list</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>Two facts that trip people coming from other databases:</p>
<ol>
<li><strong><code>READ UNCOMMITTED</code> behaves exactly like <code>READ COMMITTED</code>.</strong> It is accepted for standards compliance but there is no dirty-read mode in PostgreSQL. MVCC never exposes uncommitted tuple versions, so dirty reads are structurally impossible.</li>
<li><strong><code>REPEATABLE READ</code> also prevents phantom reads</strong>, which the standard permits at that level. Because the whole transaction runs off one snapshot, a range query re-executed later returns exactly the same rows. PostgreSQL's <code>REPEATABLE READ</code> is snapshot isolation.</li>
</ol>
<p>What <code>REPEATABLE READ</code> still allows is <strong>write skew</strong>: two transactions each read a set of rows, each decides its write is safe based on what it read, and the combined result violates an invariant that neither transaction alone broke.</p>

<h2 id="SERIALIZABLE-and-SSI"><a href="#SERIALIZABLE-and-SSI" class="headerlink" title="SERIALIZABLE and SSI"></a>SERIALIZABLE and SSI</h2>
<p>PostgreSQL 9.1 and later implement <code>SERIALIZABLE</code> with <strong>Serializable Snapshot Isolation (SSI)</strong>. It runs on top of snapshot isolation and tracks read/write dependencies between concurrent transactions with predicate locks (SIREAD locks). When it detects a dependency cycle that could not occur in any serial ordering, it aborts one of the transactions with SQLSTATE <code>40001</code>.</p>
<p>Properties worth internalising:</p>
<ul>
<li>It does <strong>not</strong> block. There is no extra waiting; the cost is aborts and the memory used for predicate locks.</li>
<li>The guarantee is real: if every transaction runs at <code>SERIALIZABLE</code> and every serialization failure is retried, the outcome is equivalent to some serial execution. No hand-written locking required.</li>
<li>It is <strong>all-or-nothing per workload</strong>. A transaction at <code>READ COMMITTED</code> running alongside serializable ones is not protected and can break their guarantee.</li>
<li>Read-only transactions can be marked to reduce false positives: <code>BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE, READ ONLY, DEFERRABLE;</code> waits until a safe snapshot exists, then never aborts.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> the same rewritten SSI example above, run at <code>SERIALIZABLE</code>, aborts one session with <code>could not serialize access due to read/write dependencies among transactions</code>. That abort <em>is</em> the feature.</p>
</blockquote>

<p>Rules for the retry body:</p>
<ul>
<li><strong>Retry the whole transaction</strong>, not the failing statement. The snapshot is gone; re-reading is the point.</li>
<li><strong>Never leave side effects outside the transaction inside the retried block</strong> — no emails, no queue publishes, no HTTP calls. Collect them and fire after commit.</li>
<li><strong>Cap the attempts</strong> and back off with jitter, or a hot row turns into a retry storm.</li>
<li><strong>Instrument it.</strong> A rising 40001 rate is a real signal about contention.</li>
</ul>
<p>MongoDB's driver-level <code>withTransaction</code> helper does the equivalent retry automatically for <code>TransientTransactionError</code> — see the MongoDB course post <code>mongo_09_transactions</code> for the contrast. PostgreSQL's drivers deliberately do <em>not</em> retry for you, because only the application knows whether the transaction body is safe to re-execute.</p>

<h2 id="NOWAIT"><a href="#NOWAIT" class="headerlink" title="NOWAIT"></a>NOWAIT</h2>
<p><code>FOR UPDATE NOWAIT</code> raises <code>lock_not_available</code> (SQLSTATE <code>55P03</code>) immediately instead of waiting. Use it when a fast failure is better than an unbounded wait — an interactive &quot;edit this record&quot; screen, for example.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> documents <span class="hljs-keyword">WHERE</span> id <span class="hljs-operator">=</span> <span class="hljs-number">9</span> <span class="hljs-keyword">FOR</span> <span class="hljs-keyword">UPDATE</span> NOWAIT;</span><br><span class="line"><span class="hljs-comment">-- ERROR: could not obtain lock on row in relation &quot;documents&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Between them: <code>NOWAIT</code> = &quot;fail if busy&quot;, <code>SKIP LOCKED</code> = &quot;give me whatever is free&quot;, default = &quot;wait your turn&quot;.</p>

<h1 id="Chapter-5-—-Deadlocks"><a href="#Chapter-5-—-Deadlocks" class="headerlink" title="Chapter 5 — Deadlocks"></a>Chapter 5 — Deadlocks</h1>
<p>A deadlock is a cycle in the wait-for graph: A holds a lock B wants and B holds a lock A wants. PostgreSQL detects it after <code>deadlock_timeout</code> (default <code>1s</code>) and aborts one transaction with SQLSTATE <code>40P01</code>.</p>

<p>Deadlocks come from two transactions acquiring the same set of locks in different orders. Impose a global order — sorting by primary key is the standard choice — and the cycle becomes impossible.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Always touch the lower id first, whatever the business direction of the transfer.</span></span><br><span class="line"><span class="hljs-keyword">BEGIN</span>;</span><br><span class="line"><span class="hljs-keyword">SELECT</span> id <span class="hljs-keyword">FROM</span> accounts</span><br><span class="line"><span class="hljs-keyword">WHERE</span> id <span class="hljs-keyword">IN</span> (:from_id, :to_id)</span><br><span class="line"><span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> id</span><br><span class="line"><span class="hljs-keyword">FOR</span> <span class="hljs-keyword">UPDATE</span>; <p>Other reliable mitigations: keep transactions short, do not interleave user think-time inside a transaction, and touch tables in the same order everywhere in the codebase. And keep the retry loop from Chapter 3 — a deadlock abort is retryable by definition.</p>

<h1 id="Chapter-6-—-Advisory-locks"><a href="#Chapter-6-—-Advisory-locks" class="headerlink" title="Chapter 6 — Advisory locks"></a>Chapter 6 — Advisory locks</h1>
<p>Advisory locks are application-defined mutexes stored in PostgreSQL's lock manager. The database attaches no meaning to them; you choose the key.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Session-scoped: held until unlocked or the session ends</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> pg_advisory_lock(<span class="hljs-number">42</span>);</span><br><span class="line"><span class="hljs-keyword">SELECT</span> pg_advisory_unlock(<span class="hljs-number">42</span>);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- Non-blocking variant: returns true/false immediately</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> pg_try_advisory_lock(hashtext(<span class="hljs-string">&#x27;nightly-report&#x27;</span>));</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- Transaction-scoped: released automatically at COMMIT or ROLLBACK - prefer these</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> pg_advisory_xact_lock(<span class="hljs-number">42</span>);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> pg_locks <span class="hljs-keyword">WHERE</span> locktype <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;advisory&#x27;</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Typical uses: making a cron job single-instance across many app servers, serialising a migration, or guarding a per-tenant critical section keyed by tenant ID.</p>
<blockquote>
<p><strong>Trick:</strong> prefer <code>pg_advisory_xact_lock</code> over <code>pg_advisory_lock</code>. Transaction-scoped locks cannot be leaked by a crashed code path — they disappear at the end of the transaction.</p>
</blockquote>
<blockquote>
<p><strong>Common pitfall:</strong> advisory locks are per <em>session</em>, and PgBouncer in transaction pooling mode hands your session to someone else between statements. Session-scoped advisory locks are unusable there; transaction-scoped ones are fine. Post 07 covers this.</p>
</blockquote>

<h1 id="Chapter-7-—-Long-transactions-wraparound-and-idle-in-transaction"><a href="#Chapter-7-—-Long-transactions-wraparound-and-idle-in-transaction" class="headerlink" title="Chapter 7 — Long transactions, wraparound, and &quot;idle in transaction&quot;"></a>Chapter 7 — Long transactions, wraparound, and &quot;idle in transaction&quot;</h1>
<h2 id="Why-long-transactions-are-expensive"><a href="#Why-long-transactions-are-expensive" class="headerlink" title="Why long transactions are expensive"></a>Why long transactions are expensive</h2>
<p>Vacuum can only remove a dead tuple if <strong>no snapshot in the entire cluster</strong> could still see it. One transaction that started an hour ago and is still open pins the global horizon at its own snapshot. For that hour, no dead tuple newer than it can be removed anywhere in the database — even in tables that transaction has never touched.</p>
<p>The result is bloat everywhere, slowly, invisibly, until someone notices the disk.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- The offenders, worst first</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> pid, state, now() <span class="hljs-operator">-</span> xact_start <span class="hljs-keyword">AS</span> xact_age,</span><br><span class="line">       now() <span class="hljs-operator">-</span> state_change <span class="hljs-keyword">AS</span> in_state, wait_event_type, <span class="hljs-keyword">left</span>(query, <span class="hljs-number">60</span>) <span class="hljs-keyword">AS</span> query</span><br><span class="line"><span class="hljs-keyword">FROM</span> pg_stat_activity</span><br><span class="line"><span class="hljs-keyword">WHERE</span> state <span class="hljs-operator">&lt;&gt;</span> <span class="hljs-string">&#x27;idle&#x27;</span> <span class="hljs-keyword">OR</span> state <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;idle in transaction&#x27;</span></span><br><span class="line"><span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> xact_start NULLS <span class="hljs-keyword">LAST</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>idle in transaction</code> is the worst state on that list: the client issued <code>BEGIN</code>, did some work, and then went off to call an external API or wait on a user. It holds its snapshot, holds any locks it took, and consumes a connection slot, while doing nothing.</p>
<p>Defences, all of which should be set in production:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- postgresql.conf or ALTER ROLE / ALTER DATABASE</span></span><br><span class="line">idle_in_transaction_session_timeout <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;60s&#x27;</span>   <span class="hljs-comment">-- kill idle transactions</span></span><br><span class="line">statement_timeout <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;30s&#x27;</span>                     <span class="hljs-comment">-- kill runaway statements</span></span><br><span class="line">lock_timeout <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;5s&#x27;</span>                           <span class="hljs-comment">-- do not queue forever on a lock</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Set them per role rather than globally when a reporting user legitimately needs longer.</p>
<h2 id="Transaction-ID-wraparound"><a href="#Transaction-ID-wraparound" class="headerlink" title="Transaction ID wraparound"></a>Transaction ID wraparound</h2>
<p>Transaction IDs are 32-bit. PostgreSQL treats them as a circle: from any XID, roughly 2 billion are &quot;in the past&quot; and 2 billion are &quot;in the future&quot;. A tuple whose <code>xmin</code> fell more than 2 billion transactions behind would suddenly appear to be from the future — invisible. To prevent that, old tuples are <strong>frozen</strong>: marked as unconditionally visible, so their <code>xmin</code> no longer matters.</p>
<p>Freezing is vacuum's other job.</p>
<table>
<thead>
<tr>
<th>Parameter</th>
<th>Default</th>
<th>Meaning</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>vacuum_freeze_min_age</code></td>
<td>50 million</td>
<td>Age at which a tuple becomes eligible for freezing during a normal vacuum</td>
</tr>
<tr>
<td><code>autovacuum_freeze_max_age</code></td>
<td>200 million</td>
<td>Age at which an <strong>anti-wraparound</strong> autovacuum is forced, even on a table nothing writes to</td>
</tr>
<tr>
<td><code>vacuum_freeze_table_age</code></td>
<td>150 million</td>
<td>Age at which vacuum scans the whole table rather than only unfrozen pages</td>

</tbody>
</table>
<p>If freezing never catches up, PostgreSQL first warns loudly in the log, then refuses new write transactions to protect the data:</p>

<h1 id="Chapter-8-—-VACUUM-autovacuum-and-bloat"><a href="#Chapter-8-—-VACUUM-autovacuum-and-bloat" class="headerlink" title="Chapter 8 — VACUUM, autovacuum, and bloat"></a>Chapter 8 — VACUUM, autovacuum, and bloat</h1>
<h2 id="Terminology-2"><a href="#Terminology-2" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Bloat</strong> — space occupied by dead tuples and free space that has not been returned to the OS.</li>
<li><strong><code>VACUUM</code></strong> — reclaims dead tuples <em>for reuse within the table</em>, updates the visibility map, freezes old tuples. Takes only <code>SHARE UPDATE EXCLUSIVE</code>; runs concurrently with reads and writes.</li>
<li><strong><code>VACUUM FULL</code></strong> — rewrites the table into a new file, returning space to the OS. Takes <code>ACCESS EXCLUSIVE</code> for the whole rewrite and needs disk for a second copy.</li>
<li><strong>Autovacuum</strong> — the background daemon that runs <code>VACUUM</code> and <code>ANALYZE</code> on a threshold.</li>
<li><strong>Visibility map</strong> — per-page bits recording &quot;all tuples on this page are visible to everyone&quot;, which is what makes index-only scans possible.</li>
</ul>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line">VACUUM (VERBOSE, ANALYZE) orders;</span><br><span class="line">VACUUM (FREEZE) orders;</span><br><span class="line">VACUUM <span class="hljs-keyword">FULL</span> orders;          <span class="hljs-comment">-- only in a maintenance window; consider pg_repack instead</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Autovacuum-thresholds"><a href="#Autovacuum-thresholds" class="headerlink" title="Autovacuum thresholds"></a>Autovacuum thresholds</h2>
<p>A table is vacuumed when dead tuples exceed <code>autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples</code> — by default 50 rows plus 20 % of the table. On a 100-million-row table that is 20 million dead tuples before anything happens, which is far too lenient. Tune the big tables individually:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders <span class="hljs-keyword">SET</span> (</span><br><span class="line">    autovacuum_vacuum_scale_factor  <span class="hljs-operator">=</span> <span class="hljs-number">0.01</span>,   <span class="hljs-comment">-- 1 % instead of 20 %</span></span><br><span class="line">    autovacuum_vacuum_threshold     <span class="hljs-operator">=</span> <span class="hljs-number">1000</span>,</span><br><span class="line">    autovacuum_analyze_scale_factor <span class="hljs-operator">=</span> <span class="hljs-number">0.005</span>,</span><br><span class="line">    autovacuum_vacuum_cost_limit    <span class="hljs-operator">=</span> <span class="hljs-number">2000</span>    <span class="hljs-comment">-- let it work faster on this table</span></span><br><span class="line">);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>PostgreSQL 13 added <code>autovacuum_vacuum_insert_threshold</code> (default 1000), which triggers vacuum on insert-only tables so their visibility map and freeze state keep up — a real fix for append-only time-series tables that previously never got vacuumed at all.</p>
<h2 id="Measuring-dead-tuples-and-bloat"><a href="#Measuring-dead-tuples-and-bloat" class="headerlink" title="Measuring dead tuples and bloat"></a>Measuring dead tuples and bloat</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> relname,</span><br><span class="line">       n_live_tup, n_dead_tup,</span><br><span class="line">       round(<span class="hljs-number">100.0</span> <span class="hljs-operator">*</span> n_dead_tup <span class="hljs-operator">/</span> <span class="hljs-built_in">nullif</span>(n_live_tup <span class="hljs-operator">+</span> n_dead_tup, <span class="hljs-number">0</span>), <span class="hljs-number">1</span>) <span class="hljs-keyword">AS</span> dead_pct,</span><br><span class="line">       last_vacuum, last_autovacuum, last_analyze</span><br><span class="line"><span class="hljs-keyword">FROM</span> pg_stat_user_tables</span><br><span class="line"><span class="hljs-keyword">ORDER</span> <span class="hljs-keyword">BY</span> n_dead_tup <span class="hljs-keyword">DESC</span></span><br><span class="line">LIMIT <span class="hljs-number">20</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">SELECT</span> pg_size_pretty(pg_total_relation_size(<span class="hljs-string">&#x27;orders&#x27;</span>)) <span class="hljs-keyword">AS</span> total,</span><br><span class="line">       pg_size_pretty(pg_relation_size(<span class="hljs-string">&#x27;orders&#x27;</span>))       <span class="hljs-keyword">AS</span> heap;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For a precise bloat figure install the <code>pgstattuple</code> extension: <code>SELECT * FROM pgstattuple('orders');</code> gives exact dead-tuple percentage at the cost of a full scan.</p>
<p>Steady state is a dead-tuple percentage that oscillates and comes back down. A percentage that only climbs means autovacuum is not keeping up: either it is being blocked by long transactions, or its cost limits are throttling it, or the table's thresholds are too lenient.</p>
<blockquote>
<p><strong>Watch out:</strong> <code>VACUUM FULL</code> is not a routine maintenance command. It locks the table completely, and if the table is bloated because of a long-transaction problem, the bloat comes straight back. Fix the cause; use <code>pg_repack</code> when you need an online rewrite.</p>
</blockquote>

<h1 id="Chapter-9-—-Contrast-with-MongoDB"><a href="#Chapter-9-—-Contrast-with-MongoDB" class="headerlink" title="Chapter 9 — Contrast with MongoDB"></a>Chapter 9 — Contrast with MongoDB</h1>
<p>Worth holding both models in mind, especially if you work across the two.</p>
<table>
<thead>
<tr>
<th>Aspect</th>
<th>PostgreSQL</th>
<th>MongoDB</th>
</tr>
</thead>
<tbody>
<tr>
<td>Default unit of atomicity</td>
<td>The statement (autocommit), extendable with <code>BEGIN</code></td>
<td>The single document</td>
</tr>
<tr>
<td>Multi-record transactions</td>
<td>Native since forever; the normal way to work</td>
<td>Available since 4.0 / 4.2, deliberately used sparingly</td>
</tr>
<tr>
<td>Isolation inside a transaction</td>
<td>Choice of four levels, <code>READ COMMITTED</code> default</td>
<td>Snapshot isolation</td>
</tr>
<tr>
<td>Concurrency control</td>
<td>MVCC with row versions on the heap</td>
<td>MVCC in WiredTiger with document-level locking</td>
</tr>
<tr>
<td>Retry on conflict</td>
<td>Application must retry <code>40001</code> / <code>40P01</code></td>
<td>Driver <code>withTransaction</code> retries transient errors automatically</td>
</tr>
<tr>
<td>Time limit</td>
<td>None by default; bounded with <code>statement_timeout</code></td>
<td>60 s default <code>transactionLifetimeLimitSeconds</code></td>
</tr>
<tr>
<td>Reclaiming dead versions</td>
<td><code>VACUUM</code> / autovacuum, visible in operations</td>
<td>Handled inside the storage engine</td>
</tr>
</tbody>
</table>
<p>The design advice rhymes: in MongoDB you ask &quot;can single-document atomicity do this?&quot; before reaching for a transaction; in PostgreSQL you ask &quot;can one statement do this?&quot; before reaching for <code>SELECT ... FOR UPDATE</code> and a read-modify-write round trip. <code>UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance &gt;= 100</code> needs no explicit lock and no retry at <code>READ COMMITTED</code>; check the row count to detect the insufficient-funds case. See <code>mongo_09_transactions</code> in the MongoDB course for that side in full.</p>
