11:T8f35,<p>You write to the database. You also need to publish an event (&quot;order placed → send confirmation email&quot;). If those two steps aren't atomic, you'll either lose events (DB committed, queue publish failed) or send duplicates (publish succeeded, DB rolled back). The <strong>outbox pattern</strong> solves this by treating the event as part of the same DB transaction, then publishing from the outbox to your message bus asynchronously. With MongoDB <strong>change streams</strong> (Post 12), the publisher is one process tailing the outbox collection — no Kafka Connect, no extra infrastructure. This post covers the full pattern, retry + idempotency + ordering, and the deduplication strategies downstream consumers need.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Recognise the dual-write problem.</li>
<li>Build an outbox collection alongside business writes inside one transaction.</li>
<li>Build a change-stream-driven publisher with resume tokens.</li>
<li>Handle at-least-once delivery + downstream idempotency.</li>
<li>Pick between outbox + change streams vs Debezium / Kafka Connect.</li>
</ul>

<h1 id="Chapter-1-—-The-dual-write-problem"><a href="#Chapter-1-—-The-dual-write-problem" class="headerlink" title="Chapter 1 — The dual-write problem"></a>Chapter 1 — The dual-write problem</h1>
<pre><code class="language-python"><figure class="highlight python"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="python"><span class="line"><span class="hljs-comment"># WRONG — not atomic</span></span><br><span class="line"><span class="hljs-keyword">await</span> db.orders.insert_one(order)</span><br><span class="line"><span class="hljs-keyword">await</span> kafka.publish(<span class="hljs-string">&quot;orders.created&quot;</span>, order)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Two failure modes:</p>
<ul>
<li>DB insert succeeds, Kafka publish fails → <strong>lost event</strong>.</li>
<li>Kafka publish succeeds, DB insert fails → <strong>phantom event</strong> (consumers act on data that doesn't exist).</li>
</ul>
<p>Neither is acceptable for systems that need consistency between their database state + downstream consumers.</p>
<h2 id="Naive-fixes-that-dont-work"><a href="#Naive-fixes-that-dont-work" class="headerlink" title="Naive fixes that don't work"></a>Naive fixes that don't work</h2>
<ul>
<li>Try-catch + retry: same race, just longer odds.</li>
<li>2-phase commit across MongoDB + Kafka: not supported across systems.</li>
<li>Eventual consistency + reconciliation: complex; high latency.</li>
</ul>
<h2 id="The-outbox"><a href="#The-outbox" class="headerlink" title="The outbox"></a>The outbox</h2>
<p>Write the event as a row in the <strong>same database, same transaction</strong> as the business mutation. A separate process publishes from the outbox to Kafka / RabbitMQ / SQS / SNS, marking each event as published (or deleting it).</p>
<p>Because the business write + outbox write are in one transaction, they're atomic. The publisher is async + retryable; downstream consumers handle duplicates idempotently.</p>

<h1 id="Chapter-6-—-At-least-once-→-consumer-must-be-idempotent"><a href="#Chapter-6-—-At-least-once-→-consumer-must-be-idempotent" class="headerlink" title="Chapter 6 — At-least-once → consumer must be idempotent"></a>Chapter 6 — At-least-once → consumer must be idempotent</h1>
<p>Once a publisher delivers at-least-once, consumers will eventually see duplicates (publisher crashed mid-ack, network duplicate, replay after rebuild).</p>
<p>Idempotency patterns:</p>
<h2 id="1-Event-ID-dedup"><a href="#1-Event-ID-dedup" class="headerlink" title="1. Event ID dedup"></a>1. Event ID dedup</h2>
<p>Every outbox event has a unique <code>_id</code>. Consumers track processed IDs (in a &quot;consumed_events&quot; collection, Redis set, etc.). Skip if already processed.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">const</span> r = <span class="hljs-keyword">await</span> db.<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;consumed_events&#x27;</span>).<span class="hljs-title function_">updateOne</span>(</span><br><span class="line">  { <span class="hljs-attr">_id</span>: event.<span class="hljs-property">_id</span> },</span><br><span class="line">  { <span class="hljs-attr">$setOnInsert</span>: { <span class="hljs-attr">processed_at</span>: <span class="hljs-keyword">new</span> <span class="hljs-title class_">Date</span>() } },</span><br><span class="line">  { <span class="hljs-attr">upsert</span>: <span class="hljs-literal">true</span> }</span><br><span class="line">);</span><br><span class="line"><span class="hljs-keyword">if</span> (r.<span class="hljs-property">upsertedCount</span> === <span class="hljs-number">0</span>) <span class="hljs-keyword">return</span>;          <span class="hljs-comment">// already processed; skip</span></span><br><span class="line"><span class="hljs-keyword">await</span> <span class="hljs-title function_">applyEvent</span>(event);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="2-Idempotent-operations"><a href="#2-Idempotent-operations" class="headerlink" title="2. Idempotent operations"></a>2. Idempotent operations</h2>
<p>Make the consumer's side-effect itself idempotent: <code>INSERT ... ON CONFLICT DO NOTHING</code>, upsert by key, &quot;set status to X&quot; rather than increment.</p>
<h2 id="3-Optimistic-versioning"><a href="#3-Optimistic-versioning" class="headerlink" title="3. Optimistic versioning"></a>3. Optimistic versioning</h2>
<p>Event carries <code>version</code>; consumer rejects updates with <code>version &lt;= current_version</code>.</p>
<p>Combine 1 + 2 for belt-and-braces.</p>
<hr>
<h1 id="Chapter-7-—-Ordering-guarantees"><a href="#Chapter-7-—-Ordering-guarantees" class="headerlink" title="Chapter 7 — Ordering guarantees"></a>Chapter 7 — Ordering guarantees</h1>
<p>Kafka topics + partitions preserve order <strong>within a partition</strong>. Choose your partition key to match the ordering you need.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">await</span> kafka.<span class="hljs-title function_">send</span>({</span><br><span class="line">  <span class="hljs-attr">topic</span>: event.<span class="hljs-property">event_type</span>,</span><br><span class="line">  <span class="hljs-attr">key</span>:   event.<span class="hljs-property">aggregate_id</span>,          <span class="hljs-comment">// events for the same order land on same partition → ordered</span></span><br><span class="line">  <span class="hljs-attr">value</span>: ...</span><br><span class="line">});</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For &quot;all events on this order, in order&quot; → key on <code>aggregate_id</code>.<br>
For &quot;every event in occurrence order globally&quot; → single-partition topic (low throughput).</p>
<p>Most outbox usage cares about per-aggregate ordering — keying by <code>aggregate_id</code> is the right default.</p>
<h2 id="What-if-you-dont-have-Kafka"><a href="#What-if-you-dont-have-Kafka" class="headerlink" title="What if you don't have Kafka?"></a>What if you don't have Kafka?</h2>
<p>SQS doesn't preserve order across the queue (unless FIFO with <code>MessageGroupId</code>). SNS doesn't (FIFO topics do). RabbitMQ exchanges + queues do preserve order per queue.</p>
<p>Match destination to the ordering requirement.</p>
<hr>
<h1 id="Chapter-8-—-Backpressure-DLQ"><a href="#Chapter-8-—-Backpressure-DLQ" class="headerlink" title="Chapter 8 — Backpressure + DLQ"></a>Chapter 8 — Backpressure + DLQ</h1>
<p>When the downstream is down for hours:</p>
<ul>
<li>Outbox grows. Disk usage climbs.</li>
<li>If you have TTL on <code>published_at: null</code>, you'll lose unpublished events — <strong>don't TTL the unpublished portion</strong>.</li>
<li>The publisher must implement exponential backoff to avoid hammering a downed downstream.</li>
</ul>
<p>Dead Letter Queue pattern:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">if</span> (event.<span class="hljs-property">attempts</span> &gt; <span class="hljs-number">10</span>) {</span><br><span class="line">  <span class="hljs-keyword">await</span> db.<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;outbox_dlq&#x27;</span>).<span class="hljs-title function_">insertOne</span>({ ...event, <span class="hljs-attr">dlq_at</span>: <span class="hljs-keyword">new</span> <span class="hljs-title class_">Date</span>() });</span><br><span class="line">  <span class="hljs-keyword">await</span> db.<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;outbox&#x27;</span>).<span class="hljs-title function_">deleteOne</span>({ <span class="hljs-attr">_id</span>: event.<span class="hljs-property">_id</span> });</span><br><span class="line">  <span class="hljs-title function_">alert</span>(<span class="hljs-string">&quot;outbox event moved to DLQ&quot;</span>, event);</span><br><span class="line">}</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Alert + investigate. Don't silently drop.</p>
<hr>
<h1 id="Chapter-9-—-Outbox-sagas-cross-service-workflows"><a href="#Chapter-9-—-Outbox-sagas-cross-service-workflows" class="headerlink" title="Chapter 9 — Outbox + sagas (cross-service workflows)"></a>Chapter 9 — Outbox + sagas (cross-service workflows)</h1>
<p>For workflows spanning services (order → payment → inventory → shipping), combine outbox events with a saga orchestrator. Each step is one service's local transaction + outbox publication. The next service's consumer triggers its step.</p>
<p>If a step fails, the orchestrator publishes a <strong>compensating action</strong> event → previous services undo.</p>
<p>Outbox makes each step atomic + reliable. The saga adds the cross-step orchestration. Together they're the standard pattern for distributed workflows on document databases.</p>

<td>no resume token persistence</td>
<td>save token after each ack</td>
</tr>
<tr>
<td>Outbox bloats</td>
<td>publisher down for long</td>
<td>alert on size; DLQ chronic failures; back-pressure</td>
</tr>
<tr>
<td>Wrong partition ordering</td>
<td>random key</td>
<td>partition by aggregate_id</td>
</tr>
<tr>
<td>Outbox writes blocked by transaction lifetime cap</td>
<td>huge transactions</td>
<td>smaller business transactions</td>
</tr>
<tr>
<td>Forgot to mark published</td>
<td>infinite loop re-publishing</td>
<td>always <code>$set: published_at</code> post-ack</td>
</tr>
</tbody>
</table>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Build-the-outbox"><a href="#Exercise-1-—-Build-the-outbox" class="headerlink" title="Exercise 1 — Build the outbox"></a>Exercise 1 — Build the outbox</h2>
<p>Implement <code>placeOrder</code> from Post 09 that also writes an <code>outbox</code> entry inside the transaction. Confirm both rows appear or neither.</p>
<h2 id="Exercise-2-—-Build-the-publisher"><a href="#Exercise-2-—-Build-the-publisher" class="headerlink" title="Exercise 2 — Build the publisher"></a>Exercise 2 — Build the publisher</h2>
<p>A Node script that change-streams the outbox + prints events to stdout (simulating Kafka). Mark them published.</p>
<h2 id="Exercise-3-—-Idempotent-consumer"><a href="#Exercise-3-—-Idempotent-consumer" class="headerlink" title="Exercise 3 — Idempotent consumer"></a>Exercise 3 — Idempotent consumer</h2>
<p>A second script consuming &quot;Kafka&quot; (file or stdin) that dedupes by event <code>_id</code> against a <code>consumed_events</code> collection. Replay the same events twice; confirm the side effect runs once.</p>
<h2 id="Exercise-4-—-Crash-recovery"><a href="#Exercise-4-—-Crash-recovery" class="headerlink" title="Exercise 4 — Crash recovery"></a>Exercise 4 — Crash recovery</h2>
<p>Kill the publisher mid-batch. Restart. Confirm no event is lost (you may see duplicates — the consumer dedups them).</p>
<h2 id="Exercise-5-—-DLQ"><a href="#Exercise-5-—-DLQ" class="headerlink" title="Exercise 5 — DLQ"></a>Exercise 5 — DLQ</h2>
<p>Make the consumer fail for a specific event_type. After 10 attempts, move to <code>outbox_dlq</code>. Confirm.</p>
<h2 id="Exercise-6-—-Compare-to-Debezium"><a href="#Exercise-6-—-Compare-to-Debezium" class="headerlink" title="Exercise 6 — Compare to Debezium"></a>Exercise 6 — Compare to Debezium</h2>
<p>(If Kafka available.) Set up Debezium MongoDB source on the same <code>outbox</code> collection. Compare event shape + ordering + ops surface.</p>
