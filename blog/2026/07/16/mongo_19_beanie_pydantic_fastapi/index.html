MongoDB Course — 19 · Beanie + Pydantic v2 + FastAPI — Async Python ODM

Created2026-07-16|Updated2026-07-16|Database > MongoDB
|Post View:

The Python equivalent of Mongoose in 2026 is Beanie — an async ODM built on Motor + Pydantic. It fits naturally into FastAPI (which is also Pydantic-based) and gives type-safe models, async I/O, validation, indexes, hooks, links (relations), aggregations, and migrations in one package. This post covers the working set: models, CRUD, indexes, links + back-links, hooks, projections, aggregations, transactions, integration patterns with FastAPI.

Series map: 17 base course → 18 Mongoose deep → 19 Beanie + FastAPI (this post) → 20 Outbox → ... → 29 K8s + mongosync + cost.

Learning Outcome

  • Set up Beanie + Motor with FastAPI lifespan.
  • Define models with Pydantic v2 + Indexed + relations (Link).
  • CRUD with type-safe queries.
  • Use projections + aggregations + bulk writes.
  • Hook into events (before_save, after_event).
  • Use transactions inside Beanie.
  • Integrate with FastAPI dependency injection.

Chapter 1 — Install + connect

init_beanie registers your models against the database and creates declared indexes. One call per process.

Chapter 2 — Models

Key elements:

  • Inherit Document. _id auto-managed as ObjectId.
  • Annotated[Type, Indexed(...)] for index declarations.
  • Settings inner class for collection name + index definitions.
  • @before_event / @after_event hooks similar to Mongoose middleware.
  • Pydantic v2 validators (Field(ge=0)) run on construction + assignment.

Chapter 3 — CRUD

Query expressions use the Python operators on model fields — fully type-checked.

Chapter 4 — Indexes

Indexes created at init_beanie. For production, disable + create via migrations (same advice as Mongoose Post 18).

Chapter 5 — Links (relations)

Beanie supports linked documents — equivalent to Mongoose populate:

Multi-level fetch supported. Like Mongoose populate, this issues additional queries — for hot endpoints prefer aggregation $lookup.

BackLink[T] for reverse references (also fetched on demand).

Chapter 6 — Projections

Use for list endpoints — server returns only projected fields + Pydantic constructs the typed slim object.

Chapter 7 — Aggregations

Returns raw dicts. To get typed results, pass a projection_model:

For aggregation builders + type-safe pipeline construction, the community pyodmongo and helpers exist. Most teams just use dict pipelines as in mongosh.

Chapter 8 — Hooks (events)

Events: Insert, Replace, Update, Delete, Save, Validate. Multiple events per decorator. Async or sync function bodies.

Chapter 9 — Transactions

Or with retry helper from Motor (Post 09 patterns apply).

session= must be passed to every op — same rule as Mongoose + the official driver.

Chapter 10 — Bulk writes

Batches the operations into a single bulkWrite call — much faster than per-doc round-trips.

Chapter 11 — FastAPI integration patterns

Separation of concerns:

  • UserCreate — request body.
  • User (Beanie) — database document.
  • UserOut — response body (no internal fields).

Helps avoid leaking server-side fields (__v, internal_flag, etc.) into responses.

Dependency injection for repositories

Useful when you want to mock the repository in tests.

Chapter 12 — Migrations

Beanie has beanie migrate CLI:

Migration files apply schema-evolution + index changes idempotently. State stored in migrations_log collection.

For complex schema versioning (Post 07), pair with _schema_v on documents + lazy migration in app code.

Chapter 13 — Common pitfalls

Pitfall Cause Fix
init_beanie called per request overhead, leak risk call once in lifespan
Links populate causing N+1 many docs each fetch_links aggregation $lookup
Projection model field name mismatch aliases needed use Field(alias="_id")
EmailStr install error missing optional dep pip install pydantic[email]
Auto-index blocks on production startup huge collection disable + migrate manually
Mixed sync + async code accidental blocking call wrap with asyncio.to_thread
Old Pydantic v1 examples breaking changes always use Pydantic v2
id vs _id confusion Beanie exposes .id (the str-friendly view) match docs

Practice Exercises

Exercise 1 — Hello Beanie + FastAPI

Build the FastAPI skeleton in Chapter 1 + 2. Create User model. POST + GET endpoint. Test with curl.

Exercise 2 — Aggregation

Build an endpoint /stats/users-per-country that returns count per country via an aggregation projected to a Pydantic model.

Exercise 3 — Links

Create Order linking to User. Insert a few. Endpoint /orders/{id} returns the order with the linked user fetched.

Exercise 4 — Hooks

Add a before_event(Insert) hook to Order that sets created_at and validates total > 0.

Exercise 5 — Bulk + transaction

Endpoint that inserts a batch of 100 users in a single bulkWrite. Wrap in a transaction (overkill for inserts; just to practice).

Exercise 6 — Migration

Add an email_index migration. Run beanie migrate. Verify getIndexes() from mongosh shows it.

Cheat-sheet

What How
Install pip install beanie motor fastapi
Init await init_beanie(db, document_models=[...])
Model class X(Document): ...
Index Annotated[T, Indexed(unique=True)] or Settings.indexes
Query Model.find(Model.field == v) (type-safe)
Insert await m.insert() or Model.insert_one(m)
Update await m.save() (state-managed) or find(...).update({$set: ...})
Delete await m.delete()
Project find().project(SlimModel)
Aggregate Model.aggregate([...], projection_model=Out)
Link Link[User] field; fetch_links=True
Hook @before_event(Insert) / @after_event(...)
Transaction session.start_transaction()
Bulk async with BulkWriter() as bulk: m.insert(bulk_writer=bulk)
FastAPI lifespan to init/close; Pydantic models for request/response
Migration beanie new-migration / beanie migrate
Async only use Motor under the hood
