11:T194b8,<p>Schema design is the decision with the longest half-life in any system. Indexes can be added, queries can be rewritten, hardware can be replaced — but a wrong key choice or a wrong normalization decision propagates into every query, every migration, and every downstream consumer for years. This post covers the formal part (normal forms, keys, constraints), the pragmatic part (when denormalization is correct, how to model hierarchies and temporal data), the PostgreSQL-specific part (JSONB and when it is the right answer), and the operational part (how to change a schema without locking production out of its own database).</p>
<blockquote>
<p>Series map: 00 Foundations &amp; Setup → 01 SQL Fundamentals &amp; Data Types → 02 Joins, Aggregation &amp; Window Functions → 03 Indexes &amp; the Query Planner → 04 Query Optimization &amp; Statistics → 05 Transactions, MVCC, Isolation &amp; Locking → <strong>06 Schema Design, Normalization &amp; JSONB</strong> (this post) → 07 Operations, Backup, Replication &amp; Security.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Decompose a table through 1NF, 2NF, 3NF and BCNF, and state what each step eliminates.</li>
<li>Make an informed, reversible decision to denormalize, and name the cost you accepted.</li>
<li>Choose between natural keys, <code>bigint</code> identity, UUIDv4 and UUIDv7 with index locality as the deciding factor.</li>
<li>Model one-to-many, many-to-many, inheritance, and hierarchies with the standard patterns and their trade-offs.</li>
<li>Represent temporal data with range types and forbid overlaps with an <code>EXCLUDE</code> constraint.</li>
<li>Apply a clear rule for when a value belongs in JSONB and when it belongs in a real column, and index JSONB correctly.</li>
<li>Run schema migrations with expand/contract so no deployment needs a maintenance window.</li>
</ul>

<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Functional dependency</strong> — <code>A → B</code> means every value of <code>A</code> determines exactly one value of <code>B</code>.</li>
<li><strong>Candidate key</strong> — a minimal set of columns that functionally determines every other column.</li>
<li><strong>Primary key</strong> — the candidate key you chose to designate.</li>
<li><strong>Partial dependency</strong> — a non-key column depending on only <em>part</em> of a composite key.</li>
<li><strong>Transitive dependency</strong> — a non-key column depending on another non-key column.</li>
<li><strong>Update anomaly</strong> — one logical fact stored in many rows, so changing it requires changing many rows and can leave them inconsistent.</li>
</ul>

<p>Normalization optimises for <em>write correctness</em>. It costs joins on read. Denormalize when you can state, in one sentence, which read you are buying and which write cost you are paying.</p>
<p>Defensible denormalizations:</p>

<h1 id="Chapter-3-—-Keys-natural-surrogate-and-index-locality"><a href="#Chapter-3-—-Keys-natural-surrogate-and-index-locality" class="headerlink" title="Chapter 3 — Keys: natural, surrogate, and index locality"></a>Chapter 3 — Keys: natural, surrogate, and index locality</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Natural key</strong> — a key drawn from the data itself: ISBN, ISO country code, email address.</li>
<li><strong>Surrogate key</strong> — a meaningless generated identifier: a sequence or a UUID.</li>
<li><strong>Index locality</strong> — how close together in the btree consecutive inserts land. High locality means new entries pack into the same few rightmost pages.</li>
</ul>
<p>Natural keys are excellent when the value is genuinely immutable, short, and externally defined — <code>char(2)</code> ISO country codes, currency codes, ISBNs. They are dangerous when the &quot;obviously stable&quot; value turns out to be mutable: email addresses change, national ID formats get reissued, SKUs get renumbered in an acquisition. A natural key that changes forces a cascading update across every referencing table.</p>
<p>Default to a surrogate primary key and a <code>UNIQUE</code> constraint on the natural key. You get stable references <em>and</em> enforced uniqueness.</p>

<td>Creation timestamp only</td>
</tr>
<tr>
<td>Merging data from multiple sources</td>
<td>Collides</td>
<td>Safe</td>
<td>Safe</td>
</tr>
</tbody>
</table>
<p><strong>Index locality is the real issue, not the extra 8 bytes.</strong> With random UUIDv4 primary keys, every insert dirties a different btree leaf page. Once the index exceeds the shared buffer cache, each insert becomes a random read plus a random write, write amplification rises through full-page writes in the WAL, and the index fragments. This is the reason UUIDv4 primary keys develop a reputation for &quot;getting slow at scale&quot; — and the reason UUIDv7, which puts a millisecond timestamp in the high bits, fixes most of it while keeping client-side generation.</p>
<p>Practical guidance:</p>
<ul>
<li>Single database, ids never leave the system → <code>bigint GENERATED ALWAYS AS IDENTITY</code>.</li>
<li>Ids exposed in URLs, generated on the client, or merged across services → UUIDv7.</li>
<li>UUIDv4 → only when unpredictability of ordering is itself a requirement.</li>
<li>Never store a UUID as <code>text</code>. The <code>uuid</code> type is 16 bytes; the text form is 36 plus overhead and compares slower.</li>
</ul>

<h2 id="One-to-many"><a href="#One-to-many" class="headerlink" title="One-to-many"></a>One-to-many</h2>
<p>A foreign key on the <em>many</em> side. Decide the delete behaviour explicitly — the default <code>NO ACTION</code> is a good default precisely because it forces the conversation.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> invoice_lines (</span><br><span class="line">    invoice_id <span class="hljs-type">bigint</span> <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span> <span class="hljs-keyword">REFERENCES</span> invoices <span class="hljs-keyword">ON</span> <span class="hljs-keyword">DELETE</span> CASCADE,</span><br><span class="line">    ...</span><br><span class="line">);</span><br><span class="line"><span class="hljs-keyword">CREATE</span> INDEX <span class="hljs-keyword">ON</span> invoice_lines (invoice_id);   <span class="hljs-comment">-- FKs are NOT indexed automatically</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Common pitfall:</strong> PostgreSQL indexes the <em>referenced</em> side (it must be unique) but never the <em>referencing</em> side. A missing index on the child's foreign key column makes every parent delete or update do a sequential scan of the child table, and makes the child hold locks longer.</p>
</blockquote>

<h2 id="Soft-deletes-and-what-they-cost"><a href="#Soft-deletes-and-what-they-cost" class="headerlink" title="Soft deletes and what they cost"></a>Soft deletes and what they cost</h2>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> users <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">COLUMN</span> deleted_at timestamptz;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The costs are real and cumulative:</p>
<ul>
<li><strong>Every query must remember the filter.</strong> One forgotten <code>WHERE deleted_at IS NULL</code> is a data leak.</li>
<li><strong>Unique constraints stop working.</strong> <code>UNIQUE (email)</code> now blocks re-registering an address whose owner &quot;deleted&quot; their account.</li>
<li><strong>Foreign keys stop meaning what they say.</strong> A child can reference a soft-deleted parent.</li>
<li><strong>The table never shrinks</strong>, and indexes carry dead weight forever.</li>
</ul>
<p>Mitigations, in order of preference:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- 1. Partial unique index: uniqueness applies only among live rows</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">UNIQUE</span> INDEX users_email_live <span class="hljs-keyword">ON</span> users (email) <span class="hljs-keyword">WHERE</span> deleted_at <span class="hljs-keyword">IS</span> <span class="hljs-keyword">NULL</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- 2. A view that carries the filter, so application code cannot forget it</span></span><br><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">VIEW</span> active_users <span class="hljs-keyword">AS</span> <span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> users <span class="hljs-keyword">WHERE</span> deleted_at <span class="hljs-keyword">IS</span> <span class="hljs-keyword">NULL</span>;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- 3. <p>An <code>EXCLUDE</code> constraint is the generalisation of <code>UNIQUE</code>: instead of &quot;no two rows are equal on these columns&quot;, it says &quot;no two rows satisfy these operators pairwise&quot;. <code>UNIQUE (a)</code> is exactly <code>EXCLUDE (a WITH =)</code>.</p>
<p>Useful range operators: <code>&amp;&amp;</code> overlaps, <code>@&gt;</code> contains, <code>&lt;@</code> contained by, <code>-|-</code> adjacent, <code>+</code> union, <code>*</code> intersection. Always use the half-open <code>'[)'</code> bound convention for time — it makes back-to-back intervals adjacent rather than overlapping, and it composes correctly.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> room_bookings <span class="hljs-keyword">WHERE</span> during @<span class="hljs-operator">&gt;</span> now();                    <span class="hljs-comment">-- current bookings</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> room_bookings <span class="hljs-keyword">WHERE</span> during <span class="hljs-operator">&amp;&amp;</span> tstzrange(now(), now() <span class="hljs-operator">+</span> <span class="hljs-type">interval</span> <span class="hljs-string">&#x27;7 days&#x27;</span>);</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For a full history table, <code>daterange</code>/<code>tstzrange</code> plus an exclusion constraint on <code>(entity_id WITH =, valid WITH &amp;&amp;)</code> gives a non-overlapping, gap-tolerant slowly-changing-dimension table that the database itself keeps consistent.</p>

<h1 id="Chapter-6-—-JSON-vs-JSONB"><a href="#Chapter-6-—-JSON-vs-JSONB" class="headerlink" title="Chapter 6 — JSON vs JSONB"></a>Chapter 6 — JSON vs JSONB</h1>
<h2 id="Terminology-2"><a href="#Terminology-2" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong><code>json</code></strong> — stores the exact input text. Preserves whitespace, key order, and duplicate keys. Re-parsed on every access.</li>
<li><strong><code>jsonb</code></strong> — stores a decomposed binary representation. Loses whitespace, key order, and duplicates (last wins). Parsed once on input; indexable.</li>
<li><strong><code>jsonpath</code></strong> — the SQL/JSON path language, available through <code>jsonb_path_query</code> and the <code>@?</code> / <code>@@</code> operators.</li>
</ul>
<p><strong>Use <code>jsonb</code>.</strong> <code>json</code> is appropriate only when you must reproduce the input byte-for-byte, which is an audit-log requirement, not a data-modelling one.</p>

If you query <em>arbitrary</em> keys with containment, use GIN — <code>jsonb_path_ops</code> when <code>@&gt;</code> is all you need, default <code>jsonb_ops</code> when you also need key-existence operators.</p>
<blockquote>
<p><strong>Common pitfall:</strong> <code>payload -&gt;&gt; 'total' &gt; '100'</code> compares <em>text</em>, so <code>'99' &gt; '100'</code> is true. Cast explicitly — <code>(payload -&gt;&gt; 'total')::numeric &gt; 100</code> — and make sure your index uses the identical expression, cast included, or it will not be used.</p>
</blockquote>
<h2 id="The-rule-for-JSONB-vs-a-real-column"><a href="#The-rule-for-JSONB-vs-a-real-column" class="headerlink" title="The rule for JSONB vs a real column"></a>The rule for JSONB vs a real column</h2>
<p>Make it a <strong>real column</strong> when any of these is true:</p>
<ul>
<li>You filter, sort, join, or group by it regularly.</li>
<li>It must be <code>NOT NULL</code>, unique, checked, or a foreign key.</li>
<li>Every row has it.</li>
<li>Its type matters (dates, money, booleans).</li>
</ul>
<p>Make it <strong>JSONB</strong> when all of these are true:</p>
<ul>
<li>The shape is genuinely open-ended or supplied by an external system you do not control.</li>
<li>It is read as a whole blob far more often than it is queried by an inner field.</li>
<li>The set of keys varies by row and enumerating them would produce a wide sparse table.</li>
</ul>
<p>Typical correct shapes: webhook payloads as received, third-party API responses, per-tenant custom fields, feature flags, sparse product attributes that differ by category, and event payloads whose schema evolves faster than your migration cadence.</p>
<p>The failure mode is &quot;the whole row is one JSONB column&quot;. You lose constraints, statistics quality, and type safety, and you gain nothing PostgreSQL was not already better at. If you find yourself writing <code>WHERE data-&gt;&gt;'user_id' = ...</code> on every query, that key wanted to be a column. The hybrid — a normalized core with a JSONB sidecar for genuinely variable attributes — is the design that ages well.</p>
<p>For the document-database perspective on the same modelling questions (embed vs reference, and how those map back to relational tables), see the MongoDB course posts <code>mongo_07_schema_design</code> and <code>mongo_23_sql_to_mongo_migration</code>. The mapping is close: MongoDB's &quot;embed&quot; corresponds to JSONB or a composite type here, and its &quot;reference&quot; corresponds to a foreign key — with the difference that PostgreSQL will actually enforce the reference.</p>

<h1 id="Chapter-8-—-Migration-discipline"><a href="#Chapter-8-—-Migration-discipline" class="headerlink" title="Chapter 8 — Migration discipline"></a>Chapter 8 — Migration discipline</h1>
<p>Every schema change happens against a running system. The rule is that a migration must never require the application and the database to change at the same instant.</p>
<h2 id="Expand-contract"><a href="#Expand-contract" class="headerlink" title="Expand / contract"></a>Expand / contract</h2>
<p>Split every breaking change into phases that are individually backwards-compatible:</p>
<ol>
<li><strong>Expand</strong> — add the new structure. Nullable column, new table, new index built <code>CONCURRENTLY</code>. Old code keeps working.</li>
<li><strong>Backfill</strong> — populate the new structure in batches, committing as you go so no single transaction holds a snapshot for hours.</li>
<li><strong>Dual-write</strong> — deploy application code that writes both old and new. Reads still come from old.</li>
<li><strong>Migrate reads</strong> — deploy code that reads from new. Verify.</li>
<li><strong>Contract</strong> — stop writing the old structure, then drop it, once you are certain no rollback will need it.</li>
</ol>
<p>Renaming a column becomes: add <code>new_name</code> → backfill → dual-write → switch reads → drop <code>old_name</code>. Five deployments instead of one, and zero downtime at every step.</p>

<h2 id="Adding-a-NOT-NULL-column-safely"><a href="#Adding-a-NOT-NULL-column-safely" class="headerlink" title="Adding a NOT NULL column safely"></a>Adding a NOT NULL column safely</h2>
<p>Adding a plain column with a default has been non-rewriting since <strong>PostgreSQL 11</strong> — the default is recorded in the catalogue and materialised lazily. That makes this fast even on a huge table:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">COLUMN</span> currency <span class="hljs-type">char</span>(<span class="hljs-number">3</span>) <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span> <span class="hljs-keyword">DEFAULT</span> <span class="hljs-string">&#x27;JPY&#x27;</span>;   <span class="hljs-comment">-- PG 11+: no rewrite</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A <strong>volatile</strong> default still rewrites the whole table:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">COLUMN</span> token uuid <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span> <span class="hljs-keyword">DEFAULT</span> gen_random_uuid();  <span class="hljs-comment">-- FULL REWRITE</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For that case, and for adding <code>NOT NULL</code> to an existing column, use the constraint-first route:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- 1. Add nullable, no default. Instant.</span></span><br><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">COLUMN</span> token uuid;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- 2. Backfill in batches (see above), and have the application populate new rows.</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- 3. Add a NOT VALID check: takes a brief lock, validates nothing yet.</span></span><br><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">CONSTRAINT</span> orders_token_nn <span class="hljs-keyword">CHECK</span> (token <span class="hljs-keyword">IS</span> <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span>) <span class="hljs-keyword">NOT</span> VALID;</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">-- 4. <p>The same <code>NOT VALID</code> → <code>VALIDATE CONSTRAINT</code> two-step works for foreign keys, and it is the only sane way to add one to a large table.</p>
<h2 id="Why-a-careless-ALTER-TABLE-is-dangerous"><a href="#Why-a-careless-ALTER-TABLE-is-dangerous" class="headerlink" title="Why a careless ALTER TABLE is dangerous"></a>Why a careless ALTER TABLE is dangerous</h2>
<p>Most <code>ALTER TABLE</code> forms take an <strong><code>ACCESS EXCLUSIVE</code></strong> lock — the mode that conflicts with everything, including plain <code>SELECT</code>. Two things make that far worse than it sounds:</p>
<ol>
<li>The lock request must <strong>wait</strong> for existing conflicting locks to be released. One long-running <code>SELECT</code> or an open <code>idle in transaction</code> session (post 05) delays it indefinitely.</li>
<li>While it waits, <strong>every subsequent query queues behind it</strong>. PostgreSQL's lock queue is ordered. A migration blocked for 30 seconds behind one slow report takes the whole table offline for those 30 seconds — for everyone.</li>
</ol>
<p>The discipline:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">SET</span> lock_timeout <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;3s&#x27;</span>;          <span class="hljs-comment">-- fail fast; retry in a loop rather than queueing</span></span><br><span class="line"><span class="hljs-keyword">SET</span> statement_timeout <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;30s&#x27;</span>;</span><br><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> orders <span class="hljs-keyword">ADD</span> <span class="hljs-keyword">COLUMN</span> promo_code text;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Wrap DDL in a retry loop with <code>lock_timeout</code>, and check <code>pg_stat_activity</code> for long transactions before you start. Also remember:</p>
<ul>
<li><code>CREATE INDEX CONCURRENTLY</code> and <code>DROP INDEX CONCURRENTLY</code> avoid the exclusive lock (at the cost of two table passes and the possibility of leaving an <code>INVALID</code> index behind if they fail — check <code>pg_index.indisvalid</code> and re-run).</li>
<li><code>CREATE INDEX CONCURRENTLY</code> cannot run inside a transaction block, which means most migration frameworks need an explicit &quot;no transaction&quot; flag for that step.</li>
<li>Changing a column's type generally rewrites the table. Widening <code>varchar(50)</code> to <code>varchar(100)</code> or to <code>text</code> does not; narrowing does.</li>
<li>Adding a column is cheap; <strong>dropping</strong> one is also cheap (the column is only marked dropped), but the space is not reclaimed until the rows are rewritten.</li>
</ul>
