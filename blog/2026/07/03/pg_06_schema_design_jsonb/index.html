PostgreSQL Course — 06 · Schema Design, Normalization and JSONB

Created2026-07-03|Updated2026-07-03|Database > PostgreSQL
|Post View:

Schema design is the decision with the longest half-life in any system. Indexes can be added, queries can be rewritten, hardware can be replaced — but a wrong key choice or a wrong normalization decision propagates into every query, every migration, and every downstream consumer for years. This post covers the formal part (normal forms, keys, constraints), the pragmatic part (when denormalization is correct, how to model hierarchies and temporal data), the PostgreSQL-specific part (JSONB and when it is the right answer), and the operational part (how to change a schema without locking production out of its own database).

Series map: 00 Foundations & Setup → 01 SQL Fundamentals & Data Types → 02 Joins, Aggregation & Window Functions → 03 Indexes & the Query Planner → 04 Query Optimization & Statistics → 05 Transactions, MVCC, Isolation & Locking → 06 Schema Design, Normalization & JSONB (this post) → 07 Operations, Backup, Replication & Security.

Learning Outcome

  • Decompose a table through 1NF, 2NF, 3NF and BCNF, and state what each step eliminates.
  • Make an informed, reversible decision to denormalize, and name the cost you accepted.
  • Choose between natural keys, bigint identity, UUIDv4 and UUIDv7 with index locality as the deciding factor.
  • Model one-to-many, many-to-many, inheritance, and hierarchies with the standard patterns and their trade-offs.
  • Represent temporal data with range types and forbid overlaps with an EXCLUDE constraint.
  • Apply a clear rule for when a value belongs in JSONB and when it belongs in a real column, and index JSONB correctly.
  • Run schema migrations with expand/contract so no deployment needs a maintenance window.

Chapter 1 — Normalization, worked

Terminology

  • Functional dependency — A → B means every value of A determines exactly one value of B.
  • Candidate key — a minimal set of columns that functionally determines every other column.
  • Primary key — the candidate key you chose to designate.
  • Partial dependency — a non-key column depending on only part of a composite key.
  • Transitive dependency — a non-key column depending on another non-key column.
  • Update anomaly — one logical fact stored in many rows, so changing it requires changing many rows and can leave them inconsistent.

Start with the classic denormalized order sheet, one row per line item:

1NF — atomic values, no repeating groups

products and qty hold lists. Split them into rows; every cell now holds a single value.

1NF eliminates: parsing strings in WHERE clauses, and the impossibility of indexing or constraining an individual product.

2NF — no partial dependencies on a composite key

The key is (order_id, line_no). But order_date, customer, cust_email, cust_city depend on order_id alone. Split.

2NF eliminates: repeating the customer's email once per line item.

3NF — no transitive dependencies

In orders_2nf, cust_email → customer, cust_city, cust_country: those depend on the customer, not on the order. In order_lines_2nf, supplier → supplier_tel. Both are non-key columns determining other non-key columns.

3NF eliminates: the update anomaly where changing a supplier's phone number requires touching every order line they ever appeared on.

Note unit_price stays on order_lines even though products have prices. That is not a normalization failure — the price at the time of sale is a genuinely different fact from the current catalogue price. Ask "does this value depend on the key, or on the moment?" before deleting a column that looks redundant.

BCNF — every determinant is a candidate key

3NF still permits an anomaly when a table has overlapping candidate keys. Classic example: a course scheduling table where each course is taught by one instructor, and each instructor teaches one course.

BCNF decomposition:

In practice 3NF is the working target and BCNF violations are rare; they show up mostly where two natural keys overlap.

Chapter 2 — The honest case for denormalization

Normalization optimises for write correctness. It costs joins on read. Denormalize when you can state, in one sentence, which read you are buying and which write cost you are paying.

Defensible denormalizations:

Pattern Buys Costs Keep correct with
Cached counter (post.comment_count) Removing a count(*) from every page render Drift if the write path is missed Trigger, or a scheduled reconciliation job
Copied immutable value (order_lines.unit_price) Historical accuracy, not just speed Nothing — this is not really denormalization Nothing needed
Denormalized read table / summary table A dashboard query that would otherwise join six tables Staleness, extra storage, refresh cost Materialized view or incremental refresh (post 04)
Duplicated tenant_id on child tables Row-level security and partition pruning without joins An extra column to keep consistent Foreign key on the composite (tenant_id, parent_id)

Indefensible ones: duplicating a mutable attribute with no trigger and no reconciliation, or "we might need to join later so let's flatten now". The test is whether you can describe how the copy stays correct. If you cannot, you have not denormalized — you have introduced a bug with a schedule.

Watch out: this trigger serialises all comment inserts for a single hot post onto one row lock. For a viral post that is a contention bottleneck. The alternative is an append-only delta table summed periodically — a trade of freshness for throughput.

Chapter 3 — Keys: natural, surrogate, and index locality

Terminology

  • Natural key — a key drawn from the data itself: ISBN, ISO country code, email address.
  • Surrogate key — a meaningless generated identifier: a sequence or a UUID.
  • Index locality — how close together in the btree consecutive inserts land. High locality means new entries pack into the same few rightmost pages.

Natural keys are excellent when the value is genuinely immutable, short, and externally defined — char(2) ISO country codes, currency codes, ISBNs. They are dangerous when the "obviously stable" value turns out to be mutable: email addresses change, national ID formats get reissued, SKUs get renumbered in an acquisition. A natural key that changes forces a cascading update across every referencing table.

Default to a surrogate primary key and a UNIQUE constraint on the natural key. You get stable references and enforced uniqueness.

bigint identity vs UUIDv4 vs UUIDv7

bigint identity UUIDv4 UUIDv7
Size 8 bytes 16 bytes 16 bytes
Insert locality in a btree Perfect — always the rightmost page Terrible — every insert lands on a random page Good — time-prefixed, so near-sequential
Generatable client-side No (needs a round trip or a sequence cache) Yes Yes
Leaks information Yes — row counts and creation order are guessable No Creation timestamp only
Merging data from multiple sources Collides Safe Safe

Index locality is the real issue, not the extra 8 bytes. With random UUIDv4 primary keys, every insert dirties a different btree leaf page. Once the index exceeds the shared buffer cache, each insert becomes a random read plus a random write, write amplification rises through full-page writes in the WAL, and the index fragments. This is the reason UUIDv4 primary keys develop a reputation for "getting slow at scale" — and the reason UUIDv7, which puts a millisecond timestamp in the high bits, fixes most of it while keeping client-side generation.

Practical guidance:

  • Single database, ids never leave the system → bigint GENERATED ALWAYS AS IDENTITY.
  • Ids exposed in URLs, generated on the client, or merged across services → UUIDv7.
  • UUIDv4 → only when unpredictability of ordering is itself a requirement.
  • Never store a UUID as text. The uuid type is 16 bytes; the text form is 36 plus overhead and compares slower.

Chapter 4 — Modelling patterns

One-to-many

A foreign key on the many side. Decide the delete behaviour explicitly — the default NO ACTION is a good default precisely because it forces the conversation.

Common pitfall: PostgreSQL indexes the referenced side (it must be unique) but never the referencing side. A missing index on the child's foreign key column makes every parent delete or update do a sequential scan of the child table, and makes the child hold locks longer.

Many-to-many with a composite primary key

The composite primary key does double duty: it enforces "a tag can only be applied once" and serves as the access path from post to tags. The second index serves tag to posts. Add a surrogate key to a join table only when something else must reference the relationship itself.

Inheritance: single table vs class table

For a hierarchy of related entities — say vehicle with car and truck subtypes:

Approach Shape Good Bad
Single table One table, a type discriminator, all subtype columns nullable One query returns everything; no joins Cannot enforce NOT NULL per subtype without CHECK gymnastics; wide sparse rows
Class table vehicle + car + truck, each subtype table referencing the parent Proper constraints per subtype; narrow tables Every read joins; enforcing "exactly one subtype" needs work
Concrete table car and truck fully independent, no parent Simplest per-type queries No way to reference "a vehicle" generically; duplicated columns

Single table with CHECK constraints is the usual pragmatic answer for two or three subtypes with mostly shared columns:

PostgreSQL's own INHERITS table inheritance exists but is largely a legacy feature — it does not propagate unique or foreign key constraints to children. Use the patterns above instead.

Hierarchies: adjacency list, closure table, ltree

Pattern Storage Read a subtree Move a subtree Notes
Adjacency list (parent_id) 1 column Recursive CTE Update one row Simple, correct, the default choice
Closure table One row per ancestor/descendant pair Single indexed join Delete + reinsert the subtree's pairs Fast reads, expensive writes, exact
ltree One ltree path column path <@ 'root.a' with a GiST index Rewrite paths of all descendants Elegant for shallow, rarely-moved trees

Start with the adjacency list. Move to a closure table or ltree only when subtree reads are measurably the bottleneck.

Soft deletes and what they cost

The costs are real and cumulative:

  • Every query must remember the filter. One forgotten WHERE deleted_at IS NULL is a data leak.
  • Unique constraints stop working. UNIQUE (email) now blocks re-registering an address whose owner "deleted" their account.
  • Foreign keys stop meaning what they say. A child can reference a soft-deleted parent.
  • The table never shrinks, and indexes carry dead weight forever.

Option 3 keeps the live table clean, the constraints honest, and the history intact. Prefer it unless the row must remain referenceable.

Chapter 5 — Temporal data and exclusion constraints

Two different time concepts are often conflated:

  • Transaction time — when the database learned the fact (created_at, updated_at).
  • Valid time — when the fact is true in the real world (valid_from, valid_to).

A price that takes effect next Monday has a valid time in the future and a transaction time of now. Model them separately when both matter.

Range types make valid-time intervals a first-class value and let the database forbid overlaps outright:

An EXCLUDE constraint is the generalisation of UNIQUE: instead of "no two rows are equal on these columns", it says "no two rows satisfy these operators pairwise". UNIQUE (a) is exactly EXCLUDE (a WITH =).

Useful range operators: && overlaps, @> contains, <@ contained by, -|- adjacent, + union, * intersection. Always use the half-open '[)' bound convention for time — it makes back-to-back intervals adjacent rather than overlapping, and it composes correctly.

For a full history table, daterange/tstzrange plus an exclusion constraint on (entity_id WITH =, valid WITH &&) gives a non-overlapping, gap-tolerant slowly-changing-dimension table that the database itself keeps consistent.

Chapter 6 — JSON vs JSONB

Terminology

  • json — stores the exact input text. Preserves whitespace, key order, and duplicate keys. Re-parsed on every access.
  • jsonb — stores a decomposed binary representation. Loses whitespace, key order, and duplicates (last wins). Parsed once on input; indexable.
  • jsonpath — the SQL/JSON path language, available through jsonb_path_query and the @? / @@ operators.

Use jsonb. json is appropriate only when you must reproduce the input byte-for-byte, which is an audit-log requirement, not a data-modelling one.

Operators

Operator Returns Example
-> jsonb data -> 'address'
->> text data ->> 'name'
#> jsonb at a path data #> '{address,city}'
#>> text at a path data #>> '{address,city}'
@> boolean, containment data @> '{"status":"active"}'
? boolean, key exists data ? 'email'
`? /?&` any / all keys exist
@? boolean, jsonpath matches data @? '$.items[*] ? (@.qty > 5)'
@@ boolean, jsonpath predicate data @@ '$.total > 100'
jsonb_path_query set of jsonb SELECT jsonb_path_query(data, '$.items[*].sku')

Indexing JSONB

Choosing: if you query a known key with equality or range, use an expression btree index. If you query arbitrary keys with containment, use GIN — jsonb_path_ops when @> is all you need, default jsonb_ops when you also need key-existence operators.

Common pitfall: payload ->> 'total' > '100' compares text, so '99' > '100' is true. Cast explicitly — (payload ->> 'total')::numeric > 100 — and make sure your index uses the identical expression, cast included, or it will not be used.

The rule for JSONB vs a real column

Make it a real column when any of these is true:

  • You filter, sort, join, or group by it regularly.
  • It must be NOT NULL, unique, checked, or a foreign key.
  • Every row has it.
  • Its type matters (dates, money, booleans).

Make it JSONB when all of these are true:

  • The shape is genuinely open-ended or supplied by an external system you do not control.
  • It is read as a whole blob far more often than it is queried by an inner field.
  • The set of keys varies by row and enumerating them would produce a wide sparse table.

Typical correct shapes: webhook payloads as received, third-party API responses, per-tenant custom fields, feature flags, sparse product attributes that differ by category, and event payloads whose schema evolves faster than your migration cadence.

The failure mode is "the whole row is one JSONB column". You lose constraints, statistics quality, and type safety, and you gain nothing PostgreSQL was not already better at. If you find yourself writing WHERE data->>'user_id' = ... on every query, that key wanted to be a column. The hybrid — a normalized core with a JSONB sidecar for genuinely variable attributes — is the design that ages well.

For the document-database perspective on the same modelling questions (embed vs reference, and how those map back to relational tables), see the MongoDB course posts mongo_07_schema_design and mongo_23_sql_to_mongo_migration. The mapping is close: MongoDB's "embed" corresponds to JSONB or a composite type here, and its "reference" corresponds to a foreign key — with the difference that PostgreSQL will actually enforce the reference.

Chapter 7 — Enum vs lookup table, revisited

Enum type Lookup table Text + CHECK
Storage 4 bytes Text or a small FK Text
Add a value ALTER TYPE ... ADD VALUE — cannot run inside a transaction block in older versions, and cannot be used in the same transaction that adds it INSERT — ordinary DML ALTER TABLE ... DROP CONSTRAINT + add — takes a lock and validates
Remove or rename a value Rename since PostgreSQL 10; removal requires recreating the type DELETE (FK protects in-use values) Constraint swap
Attach metadata (label, ordering, flags) No Yes No
Ordering Declaration order, built in sort_order column Alphabetical only

Rule of thumb: an enum for a closed set that genuinely never changes ('left' / 'right', weekday names) and where the 4-byte storage matters. A lookup table for anything a product manager might want to add to, or that needs a human-readable label, an ordering, or extra attributes — which in practice is most status columns.

Chapter 8 — Migration discipline

Every schema change happens against a running system. The rule is that a migration must never require the application and the database to change at the same instant.

Expand / contract

Split every breaking change into phases that are individually backwards-compatible:

  1. Expand — add the new structure. Nullable column, new table, new index built CONCURRENTLY. Old code keeps working.
  2. Backfill — populate the new structure in batches, committing as you go so no single transaction holds a snapshot for hours.
  3. Dual-write — deploy application code that writes both old and new. Reads still come from old.
  4. Migrate reads — deploy code that reads from new. Verify.
  5. Contract — stop writing the old structure, then drop it, once you are certain no rollback will need it.

Renaming a column becomes: add new_name → backfill → dual-write → switch reads → drop old_name. Five deployments instead of one, and zero downtime at every step.

Adding a NOT NULL column safely

Adding a plain column with a default has been non-rewriting since PostgreSQL 11 — the default is recorded in the catalogue and materialised lazily. That makes this fast even on a huge table:

The same NOT VALID → VALIDATE CONSTRAINT two-step works for foreign keys, and it is the only sane way to add one to a large table.

Why a careless ALTER TABLE is dangerous

Most ALTER TABLE forms take an ACCESS EXCLUSIVE lock — the mode that conflicts with everything, including plain SELECT. Two things make that far worse than it sounds:

  1. The lock request must wait for existing conflicting locks to be released. One long-running SELECT or an open idle in transaction session (post 05) delays it indefinitely.
  2. While it waits, every subsequent query queues behind it. PostgreSQL's lock queue is ordered. A migration blocked for 30 seconds behind one slow report takes the whole table offline for those 30 seconds — for everyone.

The discipline:

Wrap DDL in a retry loop with lock_timeout, and check pg_stat_activity for long transactions before you start. Also remember:

  • CREATE INDEX CONCURRENTLY and DROP INDEX CONCURRENTLY avoid the exclusive lock (at the cost of two table passes and the possibility of leaving an INVALID index behind if they fail — check pg_index.indisvalid and re-run).
  • CREATE INDEX CONCURRENTLY cannot run inside a transaction block, which means most migration frameworks need an explicit "no transaction" flag for that step.
  • Changing a column's type generally rewrites the table. Widening varchar(50) to varchar(100) or to text does not; narrowing does.
  • Adding a column is cheap; dropping one is also cheap (the column is only marked dropped), but the space is not reclaimed until the rows are rewritten.
