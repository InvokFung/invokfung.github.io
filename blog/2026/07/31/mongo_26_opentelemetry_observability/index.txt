11:Tad68,<p>When a request is slow, &quot;is it Mongo?&quot; is the question that wastes the most production time. <strong>OpenTelemetry</strong> (OTel) makes the answer obvious — every Mongo operation becomes a span attached to the request trace, with query shape, duration, target collection, and the surrounding service spans on the same timeline. Plus metrics (Mongo + driver pool + service) + logs (correlated by trace ID). This post covers wiring OTel into Node + Python services using the MongoDB drivers, picking a backend (Tempo / Datadog / Honeycomb / Atlas), instrumenting custom spans, and the dashboards + alerts worth building.</p>

<p>Series map: 24 Kafka + Debezium → 25 Testing → <strong>26 OpenTelemetry</strong> (this post) → 27 Geo → 28 Time-series extreme → 29 K8s + mongosync + cost.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Wire OpenTelemetry into Node + Python services.</li>
<li>Auto-instrument the MongoDB driver (spans per operation).</li>
<li>Add custom spans + attributes for app-specific context.</li>
<li>Export traces to OTLP collector → backend (Tempo / Datadog / Honeycomb / SigNoz / etc.).</li>
<li>Correlate Mongo slow-query log with trace IDs.</li>
<li>Pick the metrics + alerts that catch real production problems.</li>
</ul>

<h1 id="Chapter-1-—-The-three-signals"><a href="#Chapter-1-—-The-three-signals" class="headerlink" title="Chapter 1 — The three signals"></a>Chapter 1 — The three signals</h1>
<ul>
<li><strong>Traces</strong> — per-request span tree. The &quot;why is this endpoint slow?&quot; answer.</li>
<li><strong>Metrics</strong> — aggregated counters / histograms. The &quot;is the system healthy?&quot; answer.</li>
<li><strong>Logs</strong> — discrete events. The &quot;what exactly happened?&quot; answer.</li>
</ul>
<p>OTel unifies them with shared resource attributes (<code>service.name</code>, <code>service.version</code>) and trace context. A log line emitted inside a request carries the trace ID; click the trace → see logs from every span.</p>
<p>For MongoDB specifically:</p>
<ul>
<li>Each Mongo operation = a span (auto-instrumented). Includes operation name (<code>find</code>, <code>aggregate</code>), namespace (<code>shop.orders</code>), command summary, duration.</li>
<li>Driver pool metrics (connections active / idle / wait time).</li>
<li>Server-side: ship slow-query log to logs backend; correlate by <code>comment</code> field.</li>
</ul>

<ul>

<h1 id="Chapter-8-—-Sampling-—-keep-cost-in-check"><a href="#Chapter-8-—-Sampling-—-keep-cost-in-check" class="headerlink" title="Chapter 8 — Sampling — keep cost in check"></a>Chapter 8 — Sampling — keep cost in check</h1>
<p>Sending every span to a backend costs money + storage. Sample:</p>
<ul>
<li><strong>Head sampling</strong>: probability decision at the start of each trace (e.g., 10 %). Cheap, simple, loses interesting slow traces randomly.</li>
<li><strong>Tail sampling</strong> (in the Collector): all spans buffered briefly; sample by outcome — keep all errors + slow + a small % of normal. Cheaper + smarter.</li>
<li><strong>Always sample</strong> errors + traces from <code>/admin</code> endpoints.</li>
</ul>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span <h1 id="Chapter-10-—-Atlas-specific-signals"><a href="#Chapter-10-—-Atlas-specific-signals" class="headerlink" title="Chapter 10 — Atlas-specific signals"></a>Chapter 10 — Atlas-specific signals</h1>
<p>Atlas surfaces native:</p>
<ul>
<li>Performance Advisor — index suggestions from real slow queries.</li>
<li>Query Insights — slow query shapes grouped + sampled.</li>
<li>Real-Time Performance Panel — live ops + metrics.</li>
<li>Alerts — configurable on every metric.</li>
<li>Cluster events log — failovers, config changes.</li>
</ul>
<p>Pair with OTel: app traces on your tracing backend; cluster-level metrics + slow queries on Atlas. Trace ID in query comment ties them together.</p>
<p>Atlas + Datadog integration ships pre-built dashboards if Datadog is your tracing backend — saves dashboard-building time.</p>

<h1 id="Chapter-11-—-Common-pitfalls"><a href="#Chapter-11-—-Common-pitfalls" class="headerlink" title="Chapter 11 — Common pitfalls"></a>Chapter 11 — Common pitfalls</h1>
<table>
<thead>
<tr>
<th>Pitfall</th>
<th>Cause</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>Spans missing</td>
<td>telemetry init AFTER app code starts</td>
<td>init telemetry first</td>
</tr>
<tr>
<td><code>db.statement</code> leaks sensitive data</td>
<td>full command logged</td>
<td>disable <code>enhancedDatabaseReporting</code> or scrub attributes</td>
</tr>
<tr>
<td>Trace context lost across <code>setImmediate</code> / queue</td>
<td>manual async handoff loses context</td>
<td>use <code>context.with(ctx, fn)</code></td>
</tr>
<tr>
<td>Backend bill spike</td>
<td>sampling 100 % at high QPS</td>
<td>head + tail sample</td>
</tr>
<tr>
<td>Logs don't carry trace ID</td>
<td>logger not enriched</td>
<td>inject trace ID per log call</td>
</tr>
<tr>
<td>Slow query log + traces don't tie up</td>
<td>no <code>comment</code> with trace ID</td>
<td>add it on every query</td>
</tr>
<tr>
<td>Driver pool metric absent</td>
<td>instrumentation version old</td>
<td>upgrade</td>
</tr>
<tr>
<td>Cross-service trace breaks</td>
<td>propagation header missing</td>
<td>use auto-instrumented HTTP clients</td>
</tr>
<tr>
<td>OTel performance overhead</td>
<td>always-on with no batching</td>
<td><code>BatchSpanProcessor</code> + reasonable export interval</td>
</tr>
</tbody>
</table>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Hello-OTel"><a href="#Exercise-1-—-Hello-OTel" class="headerlink" title="Exercise 1 — Hello OTel"></a>Exercise 1 — Hello OTel</h2>

<h2 id="Exercise-2-—-Auto-instrument-Mongo"><a href="#Exercise-2-—-Auto-instrument-Mongo" class="headerlink" title="Exercise 2 — Auto-instrument Mongo"></a>Exercise 2 — Auto-instrument Mongo</h2>
<p>Confirm every Mongo operation appears as its own span attached to your request trace.</p>
<h2 id="Exercise-3-—-Custom-span"><a href="#Exercise-3-—-Custom-span" class="headerlink" title="Exercise 3 — Custom span"></a>Exercise 3 — Custom span</h2>

<h2 id="Exercise-4-—-Trace-ID-in-queries"><a href="#Exercise-4-—-Trace-ID-in-queries" class="headerlink" title="Exercise 4 — Trace ID in queries"></a>Exercise 4 — Trace ID in queries</h2>
<p>Add a <code>.comment(trace=${traceId})</code> to every Mongo query. Make a slow query; find it via Atlas slow-query log; follow the trace ID back to the trace.</p>
<h2 id="Exercise-5-—-Sampling"><a href="#Exercise-5-—-Sampling" class="headerlink" title="Exercise 5 — Sampling"></a>Exercise 5 — Sampling</h2>
<p>Set head sampling to 10 %. Verify spans drop proportionally. Switch to tail sampling in the Collector keeping 100 % of errors.</p>
<h2 id="Exercise-6-—-Logs-correlation"><a href="#Exercise-6-—-Logs-correlation" class="headerlink" title="Exercise 6 — Logs correlation"></a>Exercise 6 — Logs correlation</h2>
