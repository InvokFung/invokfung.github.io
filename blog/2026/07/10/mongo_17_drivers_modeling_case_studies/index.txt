<p>Mongoose adds:</p>
<ul>
<li>Schemas + types + validation at the app layer.</li>
<li>Pre/post hooks (lifecycle middleware).</li>
<li>Population (<code>ref</code> + <code>populate</code> — <code>$lookup</code> from the app side).</li>

<p>Inserts look like a normal collection. Internally documents are bucketed by <code>metaField</code> + time, compressed columnarly. Reads use the same query API, with optimisations for time ranges.</p>
<p>Pros:</p>
<ul>
<li>70-90 % storage reduction vs naive 1-doc-per-event.</li>
<li>Faster time-range queries.</li>
<li>Built-in TTL.</li>
<li>Works with <code>$setWindowFields</code>, <code>$densify</code>, <code>$fill</code>.</li>
</ul>
<p>Limits:</p>
<ul>
<li>No updates of individual events (delete + insert if needed).</li>
<li>No unique indexes on data fields (other than <code>timeField</code> + <code>metaField</code>).</li>
<li>Schema-on-insert is strict for the meta + time fields.</li>
</ul>
<p>For high-volume telemetry (IoT, observability, finance), time-series collections beat hand-rolled bucket patterns (Post 07 Ch 5) in storage + performance + simplicity.</p>

<p>Trade-offs:</p>
<ul>
<li><strong>Read fan-out</strong> — cheap writes, expensive reads (especially for users following thousands). Good for small networks.</li>
<li><strong>Write fan-out</strong> — cheap reads, expensive writes (a celebrity's post inserts millions of rows). Good for read-heavy feeds.</li>
<li><strong>Hybrid</strong> — fan-out on write for normal users; fan-out on read for celebrities (mark with <code>is_high_fanout: true</code>, query separately).</li>
</ul>
<p>This is the Twitter/Mastodon problem. There's no one-size-fits-all answer.</p>

<h1 id="Chapter-13-—-Case-study-E-multi-tenant-SaaS"><a href="#Chapter-13-—-Case-study-E-multi-tenant-SaaS" class="headerlink" title="Chapter 13 — Case study E: multi-tenant SaaS"></a>Chapter 13 — Case study E: multi-tenant SaaS</h1>
<p>Three patterns. Pick by tenant count + isolation needs + per-tenant size.</p>
<h2 id="Pattern-1-—-Shared-collection-tenant-field"><a href="#Pattern-1-—-Shared-collection-tenant-field" class="headerlink" title="Pattern 1 — Shared collection, tenant field"></a>Pattern 1 — Shared collection, tenant field</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// users collection holds users for all tenants</span></span><br><span class="line">{ <span class="hljs-attr">_id</span>: <span class="hljs-title class_">ObjectId</span>, <span class="hljs-attr">tenant_id</span>: <span class="hljs-string">&quot;acme&quot;</span>, <span class="hljs-attr">name</span>: <span class="hljs-string">&quot;...&quot;</span> }</span><br><span class="line"> </span><br><span class="line">db.<span class="hljs-property">users</span>.<span class="hljs-title function_">createIndex</span>({ <span class="hljs-attr">tenant_id</span>: <span class="hljs-number">1</span>, <span class="hljs-attr">_id</span>: <span class="hljs-number">1</span> })</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Every query includes <code>tenant_id: X</code>. Compound indexes start with <code>tenant_id</code>.</p>
<p>Pros: minimal overhead; easy to add a tenant; queries simple.<br>
Cons: noisy-neighbour effects; per-tenant operations (drop) are app-side; less isolation.</p>
<p>Best for: thousands of small tenants.</p>
<h2 id="Pattern-2-—-Collection-per-tenant"><a href="#Pattern-2-—-Collection-per-tenant" class="headerlink" title="Pattern 2 — Collection per tenant"></a>Pattern 2 — Collection per tenant</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">db[<span class="hljs-string">&#x27;users_acme&#x27;</span>].<span class="hljs-title function_">find</span>({})</span><br><span class="line">db[<span class="hljs-string">&#x27;users_globex&#x27;</span>].<span class="hljs-title function_">find</span>({})</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Pros: per-tenant indexes + backup + drop possible.<br>
Cons: many collections per database (limit: a few thousand before metadata strain); harder to query across tenants.</p>
<p>Best for: dozens of medium tenants needing some isolation.</p>
<h2 id="Pattern-3-—-Database-per-tenant"><a href="#Pattern-3-—-Database-per-tenant" class="headerlink" title="Pattern 3 — Database per tenant"></a>Pattern 3 — Database per tenant</h2>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">client.<span class="hljs-title function_">db</span>(<span class="hljs-string">&#x27;shop_acme&#x27;</span>).<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;users&#x27;</span>)</span><br><span class="line">client.<span class="hljs-title function_">db</span>(<span class="hljs-string">&#x27;shop_globex&#x27;</span>).<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;users&#x27;</span>)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Pros: full isolation; per-tenant backup, restore, IAM; easy to off-board.<br>
Cons: connection per DB; metadata overhead at hundreds of DBs; harder cross-tenant analytics.</p>
<p>Best for: a few large tenants; regulatory isolation; on-premise hosting per customer.</p>
<h2 id="Sharding-tie-in"><a href="#Sharding-tie-in" class="headerlink" title="Sharding tie-in"></a>Sharding tie-in</h2>
<p>In Pattern 1, sharding the collection on <code>{ tenant_id: 1, _id: 1 }</code> keeps each tenant's data on one shard (with <code>tagSets</code> you can pin specific tenants to specific shards or regions).</p>

<h1 id="Chapter-15-—-Common-pitfalls-in-driver-code"><a href="#Chapter-15-—-Common-pitfalls-in-driver-code" class="headerlink" title="Chapter 15 — Common pitfalls in driver code"></a>Chapter 15 — Common pitfalls in driver code</h1>
<table>

<th>Pitfall</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>Connecting per request</td>
<td>one client per process</td>
</tr>
<tr>
<td>Mongoose <code>lean()</code> not used</td>

<td>Promise leaks; lint with <code>no-floating-promises</code></td>

</tr>
<tr>

<td><code>EJSON.stringify</code> for safe serialisation</td>
</tr>
<tr>
<td>Missing index in dev → slow query in prod</td>
<td>run <code>.explain</code> in CI</td>
</tr>
