MongoDB Course — 17 · Drivers + Modeling Case Studies (Time-Series, IoT, E-commerce, Social, Multi-Tenant)

Created2026-07-10|Updated2026-07-10|Database > MongoDB
|Post View:

The final base post wraps up the series with two practical halves. First — a quick tour of the major drivers (Node official + Mongoose vs Prisma, Python pymongo + Motor, Go, Rust, .NET) so you can match idioms to the language you actually ship in. Second — end-to-end modelling case studies for the five workloads that show up most often: native time-series collections, IoT telemetry, e-commerce catalogue + orders, social feed, and multi-tenant SaaS.

Series map: 00 Foundations → … → 16 Atlas → 17 Drivers & Case Studies (this post — final base).

Learning Outcome

  • Use the official Node driver + know when to layer Mongoose vs Prisma.
  • Switch idioms between pymongo / Motor for sync vs async Python.
  • Recognise driver patterns in Go, Rust, .NET.
  • Apply native time-series collections correctly.
  • Model IoT telemetry, e-commerce, social feed, multi-tenant SaaS end to end.

Chapter 1 — Node.js — official driver

Strengths:

  • Thin, no opinion.
  • TypeScript first-class.
  • Fastest driver in the JS ecosystem.

Combine with zod / valibot for runtime schema validation if you want types without a heavier ORM/ODM.

Chapter 2 — Node.js — Mongoose ODM

Mongoose adds:

  • Schemas + types + validation at the app layer.
  • Pre/post hooks (lifecycle middleware).
  • Population (ref + populate — $lookup from the app side).
  • Virtuals + getters/setters.
  • Methods + statics.

Trade-off: extra abstraction, ~30 % slower than the raw driver, sometimes opaque. Many teams pick the official driver + Zod for new projects in 2026 — leaner.

Chapter 3 — Node.js — Prisma + MongoDB

Prisma (originally Postgres-only) has supported MongoDB since 2022. Schema-first ORM with TypeScript types generated for you.

Strengths: type-safe queries (compile-time errors on wrong fields), excellent DX.

Weaknesses (vs Postgres Prisma):

  • Relations on MongoDB use references-with-IDs (not native foreign keys). Joins via include are app-side.
  • Some Prisma features are SQL-only.

Choose Prisma if the rest of your stack uses Prisma + you value the TypeScript ergonomics. Choose the official driver if you want raw control or you write a lot of aggregation pipelines (Prisma's aggregation API is less expressive).

Chapter 4 — Python — pymongo + Motor

pymongo (synchronous)

Motor (async)

ODMs

  • Beanie — async ODM on top of Motor + Pydantic. Excellent if you're on FastAPI + Pydantic.
  • MongoEngine — older, sync, less popular in 2026.
  • ODMantic — modern Pydantic-based.

For new FastAPI projects, Beanie is the modern choice. For scripts + ETL, raw pymongo.

Chapter 5 — Go

Idiomatic Go: pass context.Context to every op; use struct tags for marshalling.

Chapter 6 — Rust

Async via Tokio. For typed collections, derive Serialize + Deserialize from serde on your struct + collection::<MyType>(...).

Chapter 7 — .NET / C#

Builders<T>.Filter provides typed query construction. LINQ also supported for queries + aggregations.

Chapter 8 — Driver picking rules of thumb

Project Pick
TypeScript backend, type-safety priority Prisma OR official driver + Zod
Node.js with traditional ODM/hooks expectations Mongoose
FastAPI + Pydantic Beanie
Python scripts + ETL raw pymongo
Async Python service Motor (with or without Beanie)
Go service official driver + struct tags
Rust service official driver + serde
.NET / Unity official driver

All drivers use the same wire protocol. Pool, write/read concern, retryability options are identical across — Post 08 applies everywhere.

Chapter 9 — Case study A: time-series collections

For metrics, IoT telemetry, financial ticks: MongoDB 5.0+ ships native time-series collections that auto-bucket + columnar-compress data.

Inserts look like a normal collection. Internally documents are bucketed by metaField + time, compressed columnarly. Reads use the same query API, with optimisations for time ranges.

Pros:

  • 70-90 % storage reduction vs naive 1-doc-per-event.
  • Faster time-range queries.
  • Built-in TTL.
  • Works with $setWindowFields, $densify, $fill.

Limits:

  • No updates of individual events (delete + insert if needed).
  • No unique indexes on data fields (other than timeField + metaField).
  • Schema-on-insert is strict for the meta + time fields.

For high-volume telemetry (IoT, observability, finance), time-series collections beat hand-rolled bucket patterns (Post 07 Ch 5) in storage + performance + simplicity.

Chapter 10 — Case study B: IoT device telemetry

End-to-end model:

Ingest path: device → MQTT broker → ingest service → telemetry.insertMany([...]) in batches.

Rollup: scheduled aggregation every 5 minutes, $merge into telemetry_5m. Old raw data drops at TTL; rollups persist a year.

Real-time queries: vector dashboard reads telemetry_5m for the chart, drills into raw telemetry only when investigating an incident.

Alerting: change stream on telemetry triggers a function when temp > threshold.

This pattern (raw TS + pre-aggregated rollups + dashboards on rollups) is the canonical IoT architecture in 2026.

Chapter 11 — Case study C: e-commerce

Collections + relationships:

Hot paths:

  • Catalogue search → Atlas Search index on products.
  • Personalised recommendations → Atlas Vector Search over product embeddings.
  • Cart updates → single-doc atomic $inc on stock + push to cart.
  • Order placement → single-doc transaction (Post 09) covering stock decrement + order insert.
  • Reporting → $merge materialised views (daily_revenue, top_products).

Chapter 12 — Case study D: social feed

Trade-offs:

  • Read fan-out — cheap writes, expensive reads (especially for users following thousands). Good for small networks.
  • Write fan-out — cheap reads, expensive writes (a celebrity's post inserts millions of rows). Good for read-heavy feeds.
  • Hybrid — fan-out on write for normal users; fan-out on read for celebrities (mark with is_high_fanout: true, query separately).

This is the Twitter/Mastodon problem. There's no one-size-fits-all answer.

Chapter 13 — Case study E: multi-tenant SaaS

Three patterns. Pick by tenant count + isolation needs + per-tenant size.

Pattern 1 — Shared collection, tenant field

Every query includes tenant_id: X. Compound indexes start with tenant_id.

Pros: minimal overhead; easy to add a tenant; queries simple.
Cons: noisy-neighbour effects; per-tenant operations (drop) are app-side; less isolation.

Best for: thousands of small tenants.

Pattern 2 — Collection per tenant

Pros: per-tenant indexes + backup + drop possible.
Cons: many collections per database (limit: a few thousand before metadata strain); harder to query across tenants.

Best for: dozens of medium tenants needing some isolation.

Pattern 3 — Database per tenant

Pros: full isolation; per-tenant backup, restore, IAM; easy to off-board.
Cons: connection per DB; metadata overhead at hundreds of DBs; harder cross-tenant analytics.

Best for: a few large tenants; regulatory isolation; on-premise hosting per customer.

Sharding tie-in

In Pattern 1, sharding the collection on { tenant_id: 1, _id: 1 } keeps each tenant's data on one shard (with tagSets you can pin specific tenants to specific shards or regions).

Chapter 14 — Production-ready service skeleton (Node TypeScript + official driver)

Recipe summary:

  • One client per process; explicit pool + concerns + appName.
  • Validate at the app boundary (Zod) — runtime + types.
  • .maxTimeMS() on user-facing queries.
  • Graceful shutdown.

Drop into a Fastify / Express / Hono handler — done.

Chapter 15 — Common pitfalls in driver code

Pitfall Fix
Connecting per request one client per process
Mongoose lean() not used reads return heavy documents; use .lean() for plain JS objects
Forgetting await on .toArray() Promise leaks; lint with no-floating-promises
ObjectId vs string mismatch in filter careful: new ObjectId(str) when querying
No appName tag hard to debug which service issued a query
BSON types lost in JSON EJSON.stringify for safe serialisation
Missing index in dev → slow query in prod run .explain in CI
Pool stress under bursty workload add waitQueueTimeoutMS; rightsize pool

Practice Exercises

Exercise 1 — Pick a driver

For the shop application throughout the series, pick a driver + ODM in your preferred language. Build createOrder, findRecent, cancelOrder.

Exercise 2 — Time-series collection

Create a sensor_readings time-series collection. Bulk-insert 100k synthetic readings across 10 devices over 1 hour. Query last-hour avg per device.

Exercise 3 — IoT rollup

Build a scheduled aggregation that rolls sensor_readings into a 5-minute summary collection via $merge. Confirm subsequent runs only touch new buckets.

Exercise 4 — E-commerce checkout

Implement placeOrder(userId, cartId) that atomically decrements stock for each item + inserts the order. Test concurrent runs for the same user shouldn't double-charge.

Exercise 5 — Social feed

For the social model, implement both read-fan-out and write-fan-out timelines. Benchmark each at 1k follows, 100k follows.

Exercise 6 — Multi-tenant

Implement all three multi-tenant patterns for a tasks collection. Discuss when each is right for your team.
