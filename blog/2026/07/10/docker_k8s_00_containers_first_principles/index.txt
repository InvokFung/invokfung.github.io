11:Te8e4,<p>Containers are the packaging and isolation unit that most modern deployment runs on: CI pipelines, Kubernetes clusters, serverless container platforms, and local development environments all assume them. The trouble is that the popular one-line explanation — &quot;a container is a lightweight VM&quot; — is wrong in a way that produces bad decisions later, especially around security and state. This first post builds the correct model from the Linux primitives upward: a container is an ordinary process whose view of the system has been narrowed by namespaces, whose resource usage has been capped by cgroups, and whose root filesystem has been swapped for an image. Everything else in this course — Dockerfiles, Compose, registries, Kubernetes pods — is machinery layered on top of that one sentence.</p>

<h1 id="Chapter-1-—-What-a-container-actually-is"><a href="#Chapter-1-—-What-a-container-actually-is" class="headerlink" title="Chapter 1 — What a container actually is"></a>Chapter 1 — What a container actually is</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Container</strong> — a process (or small process tree) running on the host kernel with a restricted view of the system: its own namespaces, a cgroup limiting its resources, and a root filesystem taken from an image.</li>
<li><strong>Image</strong> — a read-only, layered filesystem plus metadata (entrypoint, environment, exposed ports). The template.</li>
<li><strong>Namespace</strong> — a kernel feature that gives a process a private instance of a global resource (process IDs, mounts, network stack, hostname, …).</li>
<li><strong>cgroup (control group)</strong> — a kernel mechanism that accounts for and limits a group of processes' CPU, memory, I/O, and process count.</li>
<li><strong>Container runtime</strong> — the software that turns an image plus a config into a running process. Low-level: <code>runc</code>, <code>crun</code>. High-level: <code>containerd</code>, <code>CRI-O</code>.</li>
<li><strong>Host kernel</strong> — the single Linux kernel that every container on a machine shares. There is no second kernel.</li>
</ul>
<h2 id="The-one-sentence-definition"><a href="#The-one-sentence-definition" class="headerlink" title="The one-sentence definition"></a>The one-sentence definition</h2>
<p>On Linux, this is a container:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="text"><span class="line">a normal process</span><br><span class="line">  + namespaces      (it sees a private PID space, mounts, network, hostname, …)</span><br><span class="line">  + cgroup limits   (it may use at most N CPUs, M bytes of RAM)</span><br><span class="line">  + a root filesystem unpacked from an image (chroot-like, via overlayfs)</span><br><span class="line">  + a security profile (dropped capabilities, seccomp filter, LSM labels)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Where-lightweight-VM-fails"><a href="#Where-lightweight-VM-fails" class="headerlink" title="Where &quot;lightweight VM&quot; fails"></a>Where &quot;lightweight VM&quot; fails</h2>
<p>The analogy is seductive because both give you &quot;a box that looks like its own machine&quot;. It fails on four concrete points, and every one of them bites in production:</p>
<ol>
<li><strong>There is no guest kernel.</strong> A VM boots its own kernel on virtual hardware. A container calls the host's kernel directly. A kernel panic, a kernel CVE, or a <code>sysctl</code> that must differ per workload is therefore <em>not</em> isolated by a container.</li>
<li><strong>There is no boot.</strong> A VM boots firmware → bootloader → kernel → init → services, in seconds to a minute. A container is <code>clone()</code> + <code>execve()</code> in milliseconds. That is why &quot;one container per process&quot; is normal and &quot;one VM per process&quot; is absurd.</li>
<li><strong>The isolation boundary is a kernel API surface, not a hardware boundary.</strong> A VM escape requires defeating the hypervisor's narrow virtual-device interface. A container escape requires defeating one of 300-plus syscalls, plus every cgroup, namespace, and filesystem interface the kernel exposes. The attack surface is orders of magnitude wider.</li>
<li><strong>The filesystem is layered and disposable by default.</strong> A VM has a disk that persists. A container's writable layer is thrown away with <code>docker rm</code> unless you explicitly mount a volume. Treating a container like a small server — SSH in, edit a config, restart — loses your edit the moment the container is replaced.</li>
</ol>
<blockquote>
<p><strong>Watch out:</strong> the fourth point is the most common beginner failure. Anything a container writes that is not on a mounted volume is <em>temporary storage attached to that container instance</em>, not to the image and not to the service.</p>
</blockquote>

<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong><code>clone(2)</code></strong> — the syscall that creates a process; namespace flags such as <code>CLONE_NEWPID</code> decide which namespaces the child gets fresh.</li>
<li><strong><code>unshare(1)</code>/<code>unshare(2)</code></strong> — move the current process into new namespaces without creating a container runtime.</li>
<li><strong>Copy-on-write (CoW)</strong> — a write to a shared read-only file first copies it into a private layer, then modifies the copy.</li>
<li><strong>Capability</strong> — one slice of root's power (e.g. <code>CAP_NET_BIND_SERVICE</code> = bind ports below 1024), grantable independently.</li>
<li><strong>seccomp</strong> — a kernel filter that decides, per syscall, whether a process may make that call.</li>
</ul>

<p>Read the limits from <em>inside</em> a container — with cgroup namespaces the container sees its own cgroup root:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker run --<span class="hljs-built_in">rm</span> --memory=256m --cpus=0.5 alpine \</span><br><span class="line">  sh -c <span class="hljs-string">&#x27;cat /sys/fs/cgroup/memory.max; cat /sys/fs/cgroup/cpu.max&#x27;</span></span><br><span class="line"><span class="hljs-comment"># 268435456</span></span><br><span class="line"><span class="hljs-comment"># 50000 100000      → 50 ms of CPU per 100 ms period = 0.5 CPU</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Two behaviours to internalise now, because they reappear in Kubernetes (Post 06):</p>
<ul>
<li><strong>Memory over the limit = the kernel OOM-kills the process</strong> (exit code 137). It is not paged out, it is not throttled, it is killed.</li>
<li><strong>CPU over the limit = throttling, not killing.</strong> The process is simply not scheduled for the rest of the period, which shows up as latency, not as a crash.</li>
</ul>
<blockquote>
<p><strong>Common pitfall:</strong> language runtimes that read <code>/proc/cpuinfo</code> or host memory instead of the cgroup limit will size their thread pools and heaps for the whole machine. Modern JVMs (<code>UseContainerSupport</code>, on by default since JDK 10) and Go 1.25's cgroup-aware <code>GOMAXPROCS</code> handle this; older runtimes and many libraries do not.</p>
</blockquote>
<h2 id="overlayfs-and-copy-on-write-layers"><a href="#overlayfs-and-copy-on-write-layers" class="headerlink" title="overlayfs and copy-on-write layers"></a>overlayfs and copy-on-write layers</h2>
<p>An image is a stack of read-only directories. <code>overlayfs</code> presents them, plus one writable directory, as a single tree:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line">merged/   ← what the container sees as /</span><br><span class="line">  ▲</span><br><span class="line">  ├── upperdir/   writable layer (this container only)</span><br><span class="line">  ├── lowerdir/   image layer N     (read-only, shared)</span><br><span class="line">  ├── lowerdir/   image layer N-1   (read-only, shared)</span><br><span class="line">  └── lowerdir/   image layer 0     (read-only, shared)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Rules that follow directly from that structure:</p>
<ul>
<li><strong>Reading</strong> a file finds the topmost layer that contains it.</li>
<li><strong>Writing</strong> an existing file triggers a <em>copy-up</em>: the whole file is copied into <code>upperdir</code> first. Editing one byte of a 2 GB file copies 2 GB.</li>
<li><strong>Deleting</strong> a file from a lower layer creates a <em>whiteout</em> entry in <code>upperdir</code>. The bytes remain in the image layer — which is exactly why a secret added in one Dockerfile layer and <code>rm</code>'d in the next is still in the image (Post 03).</li>
<li><strong><code>docker rm</code></strong> deletes <code>upperdir</code>. All container-local writes vanish.</li>
</ul>
<p>Inspect the layer chain of a running container:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker inspect -f <span class="hljs-string">&#x27;{{json .GraphDriver.Data}}&#x27;</span> web | <span class="hljs-built_in">tr</span> <span class="hljs-string">&#x27;,&#x27;</span> <span class="hljs-string">&#x27;\n&#x27;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Trick:</strong> because copy-up is per-file and whole-file, databases and other write-heavy workloads should always write to a volume, not to the writable layer. You get both better performance and persistence. Post 02 covers volumes properly.</p>
</blockquote>
<h2 id="Capabilities-and-seccomp-—-the-introductory-version"><a href="#Capabilities-and-seccomp-—-the-introductory-version" class="headerlink" title="Capabilities and seccomp — the introductory version"></a>Capabilities and seccomp — the introductory version</h2>
<p>Traditional UNIX has a binary answer to &quot;are you root?&quot;. Linux splits root's power into ~40 <strong>capabilities</strong>, so a process can bind port 80 (<code>CAP_NET_BIND_SERVICE</code>) without also being able to load kernel modules (<code>CAP_SYS_MODULE</code>).</p>
<p>A container started by Docker does <em>not</em> get full root even when it runs as UID 0. The daemon drops all but a small default set (<code>CHOWN</code>, <code>DAC_OVERRIDE</code>, <code>FOWNER</code>, <code>FSETID</code>, <code>KILL</code>, <code>SETGID</code>, <code>SETUID</code>, <code>SETPCAP</code>, <code>NET_BIND_SERVICE</code>, <code>NET_RAW</code>, <code>SYS_CHROOT</code>, <code>MKNOD</code>, <code>AUDIT_WRITE</code>, <code>SETFCAP</code>). Tighten it:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># drop everything, add back only what the app needs</span></span><br><span class="line">docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE nginx:1.27-alpine</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>seccomp</strong> filters syscalls. Docker applies a default profile that blocks roughly 40 of the 300-plus syscalls — things like <code>mount</code>, <code>reboot</code>, <code>kexec_load</code>, and old <code>clone</code> flags — with no measurable cost for typical applications.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># see what happens without it (do NOT do this in production)</span></span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> --security-opt seccomp=unconfined alpine <span class="hljs-built_in">echo</span> hi</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Add <strong>AppArmor</strong> (Debian/Ubuntu) or <strong>SELinux</strong> (Fedora/RHEL) labels on top, and you have the four layers of the runtime sandbox: namespaces (what you can see), cgroups (how much you can use), capabilities + seccomp (what you can ask the kernel to do), LSM (what the policy engine permits). Post 03 turns all of this into a hardening checklist.</p>

<h2 id="The-security-caveat-stated-plainly"><a href="#The-security-caveat-stated-plainly" class="headerlink" title="The security caveat, stated plainly"></a>The security caveat, stated plainly</h2>
<p><strong>A shared kernel is a shared attack surface.</strong> Container isolation is enforced by the same kernel that a compromised container is talking to. A kernel privilege-escalation bug that a container can reach is, in the worst case, a host compromise — and from the host, every other container on that machine. VM escapes exist too, but the interface an attacker must break is far narrower.</p>
<p>Practical consequences:</p>
<ul>
<li>Do not treat containers as a hard multi-tenant boundary for untrusted code. Running arbitrary customer code? Put a VM or a sandboxed runtime (gVisor, Kata Containers, Firecracker microVMs) around it.</li>
<li><code>--privileged</code> disables almost every layer described above (capabilities, device restrictions, and typically seccomp). It converts &quot;isolated process&quot; into &quot;root on the host with extra steps&quot;. Post 03 covers the alternatives.</li>
<li>Mounting <code>/var/run/docker.sock</code> into a container is equivalent to granting root on the host: whoever can talk to the daemon can start a privileged container mounting <code>/</code>.</li>
<li>Patch the <em>host</em> kernel. No amount of rebuilding your images fixes a host kernel CVE.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> &quot;containers are more secure than VMs&quot; and &quot;containers are insecure&quot; are both marketing. The accurate statement is: containers give strong <em>workload</em> isolation with a wide kernel attack surface; use them for your own code, and add a VM boundary when the tenant is untrusted.</p>
</blockquote>

<h1 id="Chapter-4-—-OCI-specs-and-the-runtime-stack"><a href="#Chapter-4-—-OCI-specs-and-the-runtime-stack" class="headerlink" title="Chapter 4 — OCI specs and the runtime stack"></a>Chapter 4 — OCI specs and the runtime stack</h1>
<h2 id="Terminology-2"><a href="#Terminology-2" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>OCI (Open Container Initiative)</strong> — the Linux Foundation body that standardised container formats, so images are not a Docker-only artifact.</li>
<li><strong>Image spec</strong> — how an image is laid out: a manifest, a config JSON, and content-addressed layer blobs.</li>
<li><strong>Runtime spec</strong> — how a runtime turns an unpacked <em>filesystem bundle</em> plus a <code>config.json</code> into a running process.</li>
<li><strong>Distribution spec</strong> — the HTTP API registries speak (<code>/v2/...</code>) for pushing and pulling those blobs.</li>
<li><strong>CRI (Container Runtime Interface)</strong> — the gRPC API Kubernetes uses to talk to a runtime. Not an OCI spec; it sits above one.</li>
</ul>
<p>Because of these specs, an image built by Docker's BuildKit runs unchanged under containerd, CRI-O, or Podman, and can be stored in Docker Hub, GHCR, ECR, Harbor, or a plain object store fronted by a registry.</p>
<h2 id="The-stack-top-to-bottom"><a href="#The-stack-top-to-bottom" class="headerlink" title="The stack, top to bottom"></a>The stack, top to bottom</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="text"><span class="line">docker CLI            you type `docker run`</span><br><span class="line">   │  REST over /var/run/docker.sock</span><br><span class="line">dockerd               Docker Engine daemon: builds, networks, volumes, API</span><br><span class="line">   │  gRPC</span><br><span class="line">containerd            image pull, snapshot (overlayfs) management, container lifecycle</span><br><span class="line">   │  fork/exec</span><br><span class="line">containerd-shim       one per container; keeps it alive across daemon restarts, reaps exit codes</span><br><span class="line">   │  exec</span><br><span class="line">runc                  sets up namespaces/cgroups/seccomp, then execve()s your process</span><br><span class="line">   │</span><br><span class="line">your process          PID 1 inside the container</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>Kubernetes (Post 04) removes the top two layers entirely: the kubelet talks CRI to <code>containerd</code> (or CRI-O) directly. This is the whole content of the 2021 &quot;Kubernetes deprecates Docker&quot; story — the <em>image format never changed</em>, only the shim Kubernetes used to reach the runtime.</p>

<h2 id="macOS-and-Windows-—-there-is-a-Linux-VM-under-there"><a href="#macOS-and-Windows-—-there-is-a-Linux-VM-under-there" class="headerlink" title="macOS and Windows — there is a Linux VM under there"></a>macOS and Windows — there is a Linux VM under there</h2>
<p>Linux containers need a Linux kernel. macOS and Windows do not have one, so Docker Desktop ships a small Linux VM and runs the engine inside it:</p>
<table>
<thead>
<tr>
<th>Host</th>
<th>Mechanism</th>
<th>Notes</th>
</tr>
</thead>
<tbody>
<tr>
<td>macOS</td>
<td>Apple Virtualization framework (or the older HyperKit) running a Linux VM</td>
<td>file sharing via VirtioFS by default in current Desktop versions</td>
</tr>
<tr>
<td>Windows (recommended)</td>
<td><strong>WSL2</strong> — a real Linux kernel in a lightweight utility VM</td>
<td>Docker Desktop integrates with your WSL2 distros</td>
</tr>
<tr>
<td>Windows (legacy)</td>
<td>Hyper-V backend</td>
<td>slower start, more memory pinned</td>
</tr>
<tr>
<td>Windows containers</td>
<td>native Windows kernel isolation, on Windows hosts only</td>
<td>separate image ecosystem (<code>mcr.microsoft.com/windows/...</code>)</td>
</tr>
</tbody>
</table>
<p>Consequences you will feel every day:</p>
<ol>
<li><strong>The &quot;host&quot; your container sees is the VM, not your laptop.</strong> A port published with <code>-p 8080:80</code> is forwarded by Docker Desktop from the VM to your machine, which is why it still works — but a container reaching your laptop's other services must use <code>host.docker.internal</code>, not <code>localhost</code> (Post 02).</li>
<li><strong>Bind mounts cross a filesystem boundary and are slow.</strong> Every <code>read()</code> on a mounted source tree traverses VirtioFS/9p into the VM. Node's <code>node_modules</code>, Python's site-packages, and large monorepo builds are the usual victims. Keeping dependencies in a named volume or inside the image instead of a bind mount typically restores most of the speed.</li>
<li><strong>On Windows, keep your code inside the WSL2 filesystem</strong> (<code>\\wsl$\Ubuntu\home\you\project</code>), not on <code>C:\</code>. Crossing the Windows/Linux filesystem boundary is the single largest performance cliff in the WSL2 setup.</li>
<li><strong>CPU/memory are the VM's, not the machine's.</strong> Docker Desktop's resource sliders cap what any container can use.</li>
</ol>
<p>Measure it on your own machine rather than trusting a number from a blog post:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># rough bind-mount read throughput vs image-internal read throughput</span></span><br><span class="line"><span class="hljs-built_in">mkdir</span> -p /tmp/bmtest &amp;&amp; <span class="hljs-built_in">dd</span> <span class="hljs-keyword">if</span>=/dev/urandom of=/tmp/bmtest/blob bs=1M count=256</span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> -v /tmp/bmtest:/data alpine sh -c <span class="hljs-string">&#x27;time cat /data/blob &gt; /dev/null&#x27;</span></span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> -v bmvol:/data alpine sh -c \</span><br><span class="line">  <span class="hljs-string">&#x27;dd if=/dev/urandom of=/data/blob bs=1M count=256 &gt;/dev/null 2&gt;&amp;1; time cat /data/blob &gt; /dev/null&#x27;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>On a native Linux host the two numbers are close. On macOS or Windows with a bind mount they usually are not.</p>
