MongoDB Course — 22 · Production RAG Build — Atlas Vector + LangChain + OpenAI

Created2026-07-22|Updated2026-07-22|Database > MongoDB
|Post View:

Post 16 introduced Atlas Vector Search. This post builds an end-to-end production-shaped RAG (Retrieval-Augmented Generation) app on top of it: chunking + embedding the corpus, indexing into Atlas, querying with hybrid (lexical + semantic) retrieval, optional reranking, prompt assembly, streaming the LLM response, observability + cost tracking, and the production guardrails (rate limits, citation, evaluation). The framework is LangChain (Python); the embedder is OpenAI text-embedding-3-large; the LLM is GPT-4o (any equivalent works).

Series map: 19 Beanie+FastAPI → 20 Outbox → 21 CQRS + ES → 22 RAG Production Build (this post) → 23 SQL→Mongo migration → … → 29 K8s + mongosync + cost.

Learning Outcome

  • Chunk + embed + index a document corpus into Atlas Vector Search.
  • Retrieve with vector + lexical + filter (hybrid).
  • Rerank with a cross-encoder when needed.
  • Assemble prompts with citations.
  • Stream the LLM response back to clients.
  • Track cost + latency + relevance per query.
  • Evaluate retrieval quality with a small offline eval set.

Chapter 1 — Why MongoDB for RAG

The naïve RAG stack is:

Mongo + Atlas Vector Search replaces a separate vector DB:

  • Documents + their embeddings + their metadata live in one collection in one database.
  • Hybrid search (lexical + vector) is one pipeline (Post 16 Ch 2).
  • Filter on metadata (tenant, recency, category) alongside vector search.
  • Same backup / monitoring / connection-pool patterns as the rest of your Mongo workload.
  • No data sync between document store + vector store.

Trade-off vs Pinecone / Weaviate / pgvector: Atlas Vector Search is HNSW only (no IVF or hybrid index types in 2026); cluster cost scales with index size. For < a few hundred million vectors, Atlas wins on operational simplicity.

Chapter 2 — Ingest pipeline — chunk + embed + insert

Chunking guidelines:

  • 800-1200 tokens per chunk for general documents. Smaller for FAQs (200-400); larger for narrative text (1500-2000).
  • Overlap of 10-15 % to preserve context across boundaries.
  • For code / structured docs, split at structural boundaries (functions, sections).

Embedding batch size: OpenAI accepts up to ~2048 inputs per call; tune to your rate limit. Batch dramatically reduces cost + latency.

Index the embedding (Atlas UI or API)

Also create an Atlas Search lexical index on text for hybrid (Chapter 4).

Chapter 3 — Retrieval — vector

Knobs:

  • numCandidates: HNSW search width. Higher = better recall + slower. Start 200; raise to 500-1000 if recall is bad.
  • limit: top-k to return.
  • filter: pre-filters narrow the search space. Big wins for multi-tenant or category-scoped queries.

Chapter 4 — Hybrid retrieval (lexical + vector)

Vector search misses exact-keyword hits; lexical misses semantic paraphrases. Combine for best recall.

The weights (0.6 / 0.4) are workload-dependent — tune with an eval set (Chapter 8).

A better scoring approach is Reciprocal Rank Fusion (RRF) — combine ranks, not raw scores:

Atlas + the LangChain integration provide hybrid retriever helpers that do this for you.

Chapter 5 — Optional reranking

Hybrid retrieval typically returns 20-50 candidates. A cross-encoder reranker scores each candidate against the query more accurately (slow per pair, fast on small batches).

When to add reranking:

  • Quality matters more than 50-100 ms latency.
  • You're already calling Cohere / OpenAI / Jina for embeddings.
  • Hybrid alone isn't returning the right doc top-1.

Skip when latency matters more than relevance lift.

Chapter 6 — Prompt assembly with citations

Key rules baked into the prompt:

  • Use only context.
  • Cite numerically (cheap to render in UI).
  • Refuse when context is insufficient (mitigates hallucination).

The UI then maps [1][3] to the actual source_id URLs from chunks.

Chapter 8 — Evaluation

A small eval set is the difference between "I think it's good" and "I know it's improving".

Build 50-200 queries with the expected source(s). Run retrieval; measure:

  • Recall@k — was the right doc in the top-k?
  • MRR — mean reciprocal rank of the first correct doc.
  • End-to-end accuracy — manually + via LLM-judge on a sample.

Run on every PR that touches retrieval. CI gate on regression > X %.

LangChain ships an eval module; LangSmith provides hosted eval + traces; ragas is a popular OSS framework for RAG-specific metrics.

Chapter 9 — Observability + cost

Track per request:

  • Query string + tenant + filters.
  • Embedding tokens (input length).
  • Retrieved chunk IDs + scores (for offline replay).
  • Reranker latency.
  • LLM input + output tokens.
  • End-to-end latency.

Persist to a traces collection or use LangSmith / Helicone / Langfuse. Use this data to:

  • Identify slow queries.
  • Estimate per-query cost (embedding tokens × embedding price + LLM tokens × LLM price).
  • Find queries with low retrieval quality (no high-score matches).

Atlas Charts on the traces collection gives quick dashboards.

Chapter 10 — Production guardrails

Guardrail Why
Rate limit per user / tenant LLM calls are slow + expensive
Max input length validation refuses crafted huge inputs
PII / secret scrubbing in inputs + outputs privacy + compliance
Citation enforcement hallucination mitigation; user trust
Refusal on low-confidence retrieval "I don't have the information" beats wrong answers
Logging with masking debug without leaking
Eval-gated deploys CI on RAG quality
A/B test retrieval strategies data-driven tuning
Cost alerts per tenant catch runaway usage
Streaming better UX, lower perceived latency
Cache identical question answers per tenant (with TTL) cost saver

Chapter 11 — Common pitfalls

Pitfall Cause Fix
Embeddings dimension mismatch swapped model didn't rebuild index rebuild index when changing embedder
Low recall with high limit numCandidates too small raise to 500-1000
Mixed tenants in results no filter on metadata add filter to $vectorSearch
LLM ignores context, hallucinates weak system prompt strengthen "USE ONLY context"; refusal instruction; eval
Latency spikes reranker on every query rerank top-20 only; or skip when not needed
Cost spike one user spamming rate-limit + cache identical Qs
Stale answers after document update embeddings not updated change-stream-driven re-embed (Post 12)
Long context blowing token limit too many chunks in prompt smaller top_n; smaller chunks
Reranker different lang than docs language mismatch use multilingual rerank model
Eval set drift new feature areas not covered grow eval set quarterly

Practice Exercises

Exercise 1 — Ingest a small corpus

Download ~50 markdown docs (your repo's docs / Wikipedia subset). Chunk + embed + insert. Build the vector index.

Exercise 2 — Vector-only retrieval

Endpoint that takes a query, runs $vectorSearch, returns top-5 chunks + scores. Test 10 questions; rate manually.

Exercise 3 — Hybrid retrieval

Add lexical ($search text) to the pipeline. Compare top-5 across vector / lexical / hybrid for the same 10 questions.

Exercise 4 — Reranker

Add Cohere rerank step after hybrid. Confirm top-1 quality improves on questions where exact keywords matter.

Exercise 5 — Streaming endpoint

Wire the streaming pipeline into FastAPI SSE. Render in a small HTML page that progressively displays tokens.

Exercise 6 — Eval harness

Build a 20-question eval set with known gold chunks. Run recall@1 / recall@5 / MRR. Tune numCandidates, chunk size, reranker on/off; track which combination wins.
