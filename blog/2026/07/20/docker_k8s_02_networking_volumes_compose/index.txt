<h1 id="Chapter-1-—-Docker-networking"><a href="#Chapter-1-—-Docker-networking" class="headerlink" title="Chapter 1 — Docker networking"></a>Chapter 1 — Docker networking</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Network driver</strong> — the mechanism implementing a Docker network: <code>bridge</code>, <code>host</code>, <code>none</code>, <code>overlay</code>, <code>macvlan</code>, <code>ipvlan</code>.</li>
<li><strong>Default bridge</strong> — the <code>bridge</code> network (<code>docker0</code> on the host) containers join when you specify nothing; a <strong>user-defined bridge</strong> is one you create with <code>docker network create</code>, and it behaves better in every way.</li>
<li><strong>Embedded DNS</strong> — Docker's resolver at <code>127.0.0.11</code> inside containers on user-defined networks; resolves container names and <strong>network aliases</strong> (extra names set with <code>--network-alias</code> or <code>networks.&lt;net&gt;.aliases</code>).</li>
<li><strong>Publishing</strong> — mapping a container port onto a host port with <code>-p</code>.</li>
</ul>

<h2 id="Default-bridge-vs-user-defined-bridge"><a href="#Default-bridge-vs-user-defined-bridge" class="headerlink" title="Default bridge vs user-defined bridge"></a>Default bridge vs user-defined bridge</h2>
<p>This is the single most useful networking fact in Docker:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker run -d --name db redis:7-alpine          <span class="hljs-comment"># default bridge</span></span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> alpine ping -c1 db              <span class="hljs-comment"># ping: bad address &#x27;db&#x27;</span></span><br><span class="line"> </span><br><span class="line">docker network create appnet                    <span class="hljs-comment"># user-defined bridge</span></span><br><span class="line">docker run -d --name db2 --network appnet redis:7-alpine</span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> --network appnet alpine ping -c1 db2   <span class="hljs-comment"># 64 bytes from 172.19.0.2 ...</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Why: on a user-defined network the container's <code>/etc/resolv.conf</code> points at Docker's embedded DNS server (<code>127.0.0.11</code>), which knows every container name and alias on that network and updates as containers come and go. The default bridge has no such service — the old <code>--link</code> flag filled that gap and is legacy today.</p>
<p>Other differences follow: user-defined networks are isolated from each other (a container on <code>frontend</code> cannot reach one on <code>backend</code> unless attached to both), containers can be attached and detached while running (<code>docker network connect/disconnect appnet web</code>), and every container on the network can reach every other on <strong>all ports</strong> without any publishing.</p>
<blockquote>
<p><strong>Trick:</strong> the correct mental default is &quot;one user-defined network per application stack&quot;. Compose does this for you automatically: every project gets a network named <code>&lt;project&gt;_default</code>, and every service is reachable from every other by its <strong>service name</strong>.</p>
</blockquote>
<h2 id="Inter-container-communication"><a href="#Inter-container-communication" class="headerlink" title="Inter-container communication"></a>Inter-container communication</h2>
<p>Within one user-defined network, address peers by service/container name and the container's <em>own</em> port — not the published host port:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="text"><span class="line">web → postgres:5432      ✓  container-to-container, on the container&#x27;s own port</span><br><span class="line">web → localhost:5432     ✗  localhost inside `web` is `web` itself (same for 127.0.0.1)</span><br><span class="line">web → host-ip:15432      ✗  works, but hairpins out to the host and back</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong><code>localhost</code> inside a container means that container.</strong> This one line prevents most first-week networking bugs.</p>
<h2 id="Publishing-ports"><a href="#Publishing-ports" class="headerlink" title="Publishing ports"></a>Publishing ports</h2>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker run -d -p 8080:80           nginx     <span class="hljs-comment"># 0.0.0.0:8080 on the host → :80 in the container</span></span><br><span class="line">docker run -d -p 127.0.0.1:8080:80 nginx     <span class="hljs-comment"># loopback only — not reachable from the LAN</span></span><br><span class="line">docker run -d -P nginx; docker port web      <span class="hljs-comment"># every EXPOSEd port on a random high port; show mappings</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Format: <code>[host-ip:]host-port:container-port[/protocol]</code>. Omitting the host IP binds <strong>all interfaces</strong>, which on a machine with a public IP means the port is on the internet.</p>
<blockquote>
<p><strong>Watch out:</strong> on Linux, Docker publishes ports by writing <code>iptables</code> rules in the <code>nat</code> table's <code>DOCKER</code> chain, which are consulted <em>before</em> the <code>INPUT</code> rules that host firewalls like <code>ufw</code> manage. A <code>ufw deny 8080</code> therefore does <strong>not</strong> block a published container port. The fixes: publish to <code>127.0.0.1</code> explicitly, put the container behind a reverse proxy, or configure Docker with <code>iptables</code> integration adjusted per the official networking documentation.</p>
</blockquote>

<h1 id="Chapter-2-—-Storage"><a href="#Chapter-2-—-Storage" class="headerlink" title="Chapter 2 — Storage"></a>Chapter 2 — Storage</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Named volume</strong> — storage managed by Docker, referenced by name, under the daemon's data root (<code>/var/lib/docker/volumes/&lt;name&gt;/_data</code> on Linux). An <strong>anonymous volume</strong> is the same thing with a generated name, created when an image <code>VOLUME</code> path has nothing mounted on it.</li>
<li><strong>Bind mount</strong> — a host path mounted into the container. Not managed by Docker; the host's permissions and inode semantics apply.</li>
<li><strong>tmpfs mount</strong> — an in-memory filesystem inside the container, never written to disk (Linux only). The container's <strong>writable layer</strong> (Post 00) is not storage at all: it dies with the container.</li>
</ul>

<h2 id="Volume-lifecycle-and-what-docker-rm-v-destroys"><a href="#Volume-lifecycle-and-what-docker-rm-v-destroys" class="headerlink" title="Volume lifecycle and what docker rm -v destroys"></a>Volume lifecycle and what <code>docker rm -v</code> destroys</h2>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker volume <span class="hljs-built_in">ls</span>; docker volume inspect pgdata   <span class="hljs-comment"># what exists, and where</span></span><br><span class="line">docker volume <span class="hljs-built_in">rm</span> pgdata      <span class="hljs-comment"># refuses while a container still references it</span></span><br><span class="line">docker volume prune          <span class="hljs-comment"># deletes ALL volumes no container uses</span></span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> -v pgdata:/d alpine <span class="hljs-built_in">du</span> -sh /d      <span class="hljs-comment"># size on disk</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The rules, precisely:</p>
<ul>
<li><code>docker rm &lt;container&gt;</code> — removes the container and its writable layer; named volumes are untouched. <code>docker rm -v</code> additionally removes the <strong>anonymous</strong> volumes attached to it, and still leaves named ones alone.</li>
<li><code>docker volume prune</code> — removes every volume no container currently references. It deletes real data with no summary of contents; a stopped container counts as a reference, one you already removed does not.</li>
<li><code>docker compose down</code> — removes containers and the project network, <strong>keeps</strong> named volumes. <code>docker compose down -v</code> also removes the named volumes declared in the file — the command that wipes your development database.</li>
</ul>
<blockquote>
<p><strong>Watch out:</strong> <code>docker system prune -a --volumes</code> is the most destructive command in everyday Docker use. Read the confirmation prompt before typing <code>y</code>.</p>
</blockquote>
<p>Back up a volume without knowing anything about its internals by mounting it into a throwaway container and tarring it out: <code>docker run --rm -v pgdata:/data:ro -v &quot;$PWD&quot;:/backup alpine tar czf /backup/pgdata.tar.gz -C /data .</code>. For a database, prefer its own dump tool (<code>pg_dump</code>, <code>mongodump</code>) over a filesystem tar of a <em>running</em> instance — a raw copy of live data files is not guaranteed to be consistent.</p>
<h2 id="The-bind-mount-permission-problem"><a href="#The-bind-mount-permission-problem" class="headerlink" title="The bind-mount permission problem"></a>The bind-mount permission problem</h2>
<p>A bind mount carries the host's numeric UIDs and GIDs straight through. The kernel compares numbers, not names; it does not care that UID 1000 is <code>alice</code> on the host and <code>node</code> in the image.</p>
<p>Both directions hurt: a non-root container cannot write into a host-owned directory, and a root container writes files the host user then cannot edit.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker run --<span class="hljs-built_in">rm</span> -u 10001:10001 -v <span class="hljs-string">&quot;<span class="hljs-variable">$PWD</span>&quot;</span>:/app -w /app alpine <span class="hljs-built_in">touch</span> out.txt</span><br><span class="line"><span class="hljs-comment"># touch: out.txt: Permission denied</span></span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> -v <span class="hljs-string">&quot;<span class="hljs-variable">$PWD</span>&quot;</span>:/app -w /app node:22-alpine npm install</span><br><span class="line"><span class="hljs-built_in">ls</span> -l node_modules   <span class="hljs-comment"># owned by root:root — your editor cannot delete it</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Fixes, best first:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># 1. run as your host user (in Compose: user: &quot;${UID:-1000}:${GID:-1000}&quot;)</span></span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> -u <span class="hljs-string">&quot;<span class="hljs-subst">$(id -u)</span>:<span class="hljs-subst">$(id -g)</span>&quot;</span> -v <span class="hljs-string">&quot;<span class="hljs-variable">$PWD</span>&quot;</span>:/app -w /app node:22-alpine npm ci</span><br><span class="line"><span class="hljs-comment"># 2. align ownership on the host once</span></span><br><span class="line"><span class="hljs-built_in">sudo</span> <span class="hljs-built_in">chown</span> -R <span class="hljs-string">&quot;<span class="hljs-subst">$(id -u)</span>:<span class="hljs-subst">$(id -g)</span>&quot;</span> .</span><br><span class="line"><span class="hljs-comment"># 3. keep generated directories out of the bind mount (also the performance fix)</span></span><br><span class="line">docker run --<span class="hljs-built_in">rm</span> -v <span class="hljs-string">&quot;<span class="hljs-variable">$PWD</span>&quot;</span>:/app -v node_modules_vol:/app/node_modules -w /app node:22-alpine npm ci</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A fourth option belongs in the image: create the user and the writable directories at build time (<code>RUN adduser -u 10001 -D app &amp;&amp; chown -R 10001:10001 /app</code>, then <code>USER 10001:10001</code>) so the container's UID is stable and known.</p>
<p>On macOS and Windows Docker Desktop remaps ownership for you in most cases, which is why the problem often appears only when a colleague on Linux (or CI) runs the same stack. Rootless Docker and Podman add another layer: with user namespaces, container UID 0 maps to your host UID, so files land owned by <em>you</em>.</p>
<h2 id="Bind-mount-performance-on-macOS-and-Windows"><a href="#Bind-mount-performance-on-macOS-and-Windows" class="headerlink" title="Bind-mount performance on macOS and Windows"></a>Bind-mount performance on macOS and Windows</h2>
<p>Every I/O operation on a bind mount crosses from the container into the Linux VM's file-sharing layer and out to the host filesystem (VirtioFS on current Docker Desktop for Mac; the 9p/<code>drvfs</code> path for Windows files accessed from WSL2). Directories with tens of thousands of small files — <code>node_modules</code>, <code>.venv</code>, <code>vendor</code>, <code>target</code> — are worst affected.</p>
<p>Mitigations, in order of effect: keep dependency directories in a <strong>named volume</strong> or inside the image and bind-mount only your source; on Windows keep the project <strong>inside the WSL2 filesystem</strong> (<code>~/project</code> in the distro), not on <code>/mnt/c</code>; use <code>:cached</code>/<code>:delegated</code> consistency flags where your Desktop version still honours them; and for large builds, build inside the container or in CI rather than bind-mounting a host build tree.</p>
<p>Measure your own numbers rather than trusting a blog figure: <code>docker run --rm -v &quot;$PWD&quot;:/m alpine sh -c 'time find /m -type f | wc -l'</code>, then the same against a named volume.</p>

<h1 id="Chapter-3-—-Docker-Compose"><a href="#Chapter-3-—-Docker-Compose" class="headerlink" title="Chapter 3 — Docker Compose"></a>Chapter 3 — Docker Compose</h1>
<h2 id="Terminology-2"><a href="#Terminology-2" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Compose file</strong> — <code>compose.yaml</code> (or <code>docker-compose.yml</code>), declaring the services of one application, grouped into a <strong>project</strong> whose name defaults to the directory and prefixes every container, network, and volume.</li>

<p><code>build</code> and <code>image</code> together mean &quot;build it and tag the result with that name&quot; (so <code>docker compose push</code> works); <code>image</code> alone means &quot;pull it&quot;.</p>
<h2 id="depends_on-—-the-trap"><a href="#depends_on-—-the-trap" class="headerlink" title="depends_on — the trap"></a><code>depends_on</code> — the trap</h2>
<p>Plain <code>depends_on</code> only orders <strong>container start</strong>. It does not wait for the process inside to be ready. A PostgreSQL container is &quot;started&quot; milliseconds after <code>docker run</code>, and is not accepting connections for several seconds after that — so a plain <code>depends_on: [db]</code> reliably produces <code>connection refused</code> on the first application boot.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">depends_on:</span>                        <span class="hljs-comment"># ✗ starts db first; says nothing about readiness</span></span><br><span class="line">  <span class="hljs-bullet">-</span> <span class="hljs-string">db</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-attr">depends_on:</span>                        <span class="hljs-comment"># ✓ waits for db&#x27;s healthcheck, and for a migration job to finish</span></span><br><span class="line">  <span class="hljs-attr">db:</span> { <span class="hljs-attr">condition:</span> <span class="hljs-string">service_healthy</span> }</span><br><span class="line">  <span class="hljs-attr">migrate:</span> { <span class="hljs-attr">condition:</span> <span class="hljs-string">service_completed_successfully</span> }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>The dependency must therefore <em>have</em> a health check. Add <code>restart: true</code> under the dependency to have Compose restart the dependent service when the dependency is restarted.</p>
<blockquote>
<p><strong>Common pitfall:</strong> health-gated startup makes local runs pleasant, but it is not a substitute for application-level retry. Kubernetes has no <code>depends_on</code> at all (Post 06), so any service that cannot survive its database being briefly unavailable will fail there. Write the reconnect loop anyway.</p>
</blockquote>
<h2 id="Configuration-through-the-environment"><a href="#Configuration-through-the-environment" class="headerlink" title="Configuration through the environment"></a>Configuration through the environment</h2>
<p>The discipline, which carries directly into Kubernetes ConfigMaps and Secrets (Post 05): <strong>the image is identical in every environment</strong> (nothing environment-specific baked in at build time); <strong>all configuration arrives as environment variables</strong> or mounted files at run time; <strong>secrets come from a secret store</strong>, never from a committed file and never from <code>ARG</code>/<code>ENV</code> at build time (Post 03); and <strong>defaults are sensible while failures are explicit</strong> — missing optional config falls back, missing required config aborts at startup with a clear message.</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">environment:</span></span><br><span class="line">  <span class="hljs-comment"># ${VAR} from the shell or the .env file beside compose.yaml; ${VAR:-default} falls back;</span></span><br><span class="line">  <span class="hljs-comment"># ${VAR:?message} fails the `up` with that message when unset</span></span><br><span class="line">  <span class="hljs-attr">DATABASE_URL:</span> <span class="hljs-string">postgresql://app:${POSTGRES_PASSWORD:?set</span> <span class="hljs-string">POSTGRES_PASSWORD}@db:5432/app</span></span><br><span class="line">  <span class="hljs-attr">LOG_LEVEL:</span> <span class="hljs-string">${LOG_LEVEL:-info}</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>environment</code> (inline) beats <code>env_file</code> for a handful of values; <code>env_file</code> is right for longer sets and keeps the file out of version control. Note that Compose's own <code>${…}</code> interpolation reads the <code>.env</code> file <em>beside the Compose file</em>, which is a different mechanism from <code>env_file:</code> (which is passed to the container). Both exist; do not confuse them.</p>

<p>Things to notice in that file, because each is a deliberate choice:</p>
<ul>
<li><code>db</code> and <code>cache</code> publish <strong>no ports</strong> — they are reachable at <code>db:5432</code> and <code>cache:6379</code> from inside the project network only, and <code>web</code> addresses them by <strong>service name</strong>, never by IP or <code>localhost</code>.</li>
<li><code>condition: service_healthy</code> means the first request after <code>up</code> works instead of racing PostgreSQL's startup. The data volumes are <strong>named</strong>, so <code>docker compose down</code> is safe and <code>down -v</code> is the explicit reset, and every password comes from the environment rather than the image.</li>
<li><code>/healthz</code> is local and cheap while <code>/readyz</code> checks dependencies — the distinction Kubernetes formalises as liveness vs readiness probes (Post 06).</li>
</ul>
