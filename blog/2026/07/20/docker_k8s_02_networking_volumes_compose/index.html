Containers Course — 02 · Networking, Volumes and Compose

Created2026-07-20|Updated2026-07-20|Infrastructure > Containers
|Post View:

A single container is rarely the whole system. Real services talk to a database, cache things in Redis, and need their data to survive a redeploy — which means two subjects that beginners consistently get wrong: networking (why one container cannot reach another by name, why localhost inside a container is not your laptop) and storage (why the database was empty after docker rm, why a bind-mounted directory is suddenly owned by root). This post covers both from the mechanics upward, then assembles everything into a Docker Compose stack — web application, PostgreSQL, and Redis — that starts in the right order, waits for dependencies to be genuinely ready, and can be run end to end from the file listings here.

Series map: 00 Containers from First Principles → 01 Images and Dockerfiles → 02 Networking, Volumes and Compose (this post) → 03 Registries, Supply Chain and Security → 04 Kubernetes Architecture and Core Objects → 05 Config, Storage and Stateful Workloads → 06 Scheduling, Resources, Probes and Rollouts → 07 Ingress, Observability, RBAC and GitOps.

Learning Outcome

  • Explain Docker's network drivers, why only a user-defined bridge provides DNS by container name, and what publishing a port does to the host's firewall rules.
  • Use host.docker.internal with the right platform-specific caveats.
  • Choose between named volumes, bind mounts, and tmpfs using a decision table, and know exactly what docker rm -v destroys.
  • Diagnose and fix UID/permission mismatches on bind mounts, and know why they are slow on macOS and Windows.
  • Write a modern Compose file (v2 spec, no version: key) with health-gated depends_on, env files, named volumes, profiles, and resource limits.
  • Run, inspect, log, and tear down a multi-service stack, with log rotation configured so it cannot fill the disk.

Chapter 1 — Docker networking

Terminology

  • Network driver — the mechanism implementing a Docker network: bridge, host, none, overlay, macvlan, ipvlan.
  • Default bridge — the bridge network (docker0 on the host) containers join when you specify nothing; a user-defined bridge is one you create with docker network create, and it behaves better in every way.
  • Embedded DNS — Docker's resolver at 127.0.0.11 inside containers on user-defined networks; resolves container names and network aliases (extra names set with --network-alias or networks.<net>.aliases).
  • Publishing — mapping a container port onto a host port with -p.

The drivers

Driver Isolation Reaching other containers Reaching the host network Typical use
bridge (default) own netns, NAT to host by IP only — no DNS by name via published ports legacy default; avoid for multi-container work
user-defined bridge own netns, NAT to host by container name and alias via published ports the normal choice; what Compose creates
host / none shares the host netns / only lo direct on localhost / nothing direct, no NAT / nothing latency-sensitive workloads (Linux) / offline batch jobs
overlay multi-host, VXLAN across hosts by name — Swarm; Kubernetes uses its own CNI plugins instead
macvlan / ipvlan own MAC/IP on the physical LAN as a LAN peer as a LAN peer legacy apps that need a real LAN address

Default bridge vs user-defined bridge

This is the single most useful networking fact in Docker:

Why: on a user-defined network the container's /etc/resolv.conf points at Docker's embedded DNS server (127.0.0.11), which knows every container name and alias on that network and updates as containers come and go. The default bridge has no such service — the old --link flag filled that gap and is legacy today.

Other differences follow: user-defined networks are isolated from each other (a container on frontend cannot reach one on backend unless attached to both), containers can be attached and detached while running (docker network connect/disconnect appnet web), and every container on the network can reach every other on all ports without any publishing.

Trick: the correct mental default is "one user-defined network per application stack". Compose does this for you automatically: every project gets a network named <project>_default, and every service is reachable from every other by its service name.

Inter-container communication

Within one user-defined network, address peers by service/container name and the container's own port — not the published host port:

localhost inside a container means that container. This one line prevents most first-week networking bugs.

Publishing ports

Format: [host-ip:]host-port:container-port[/protocol]. Omitting the host IP binds all interfaces, which on a machine with a public IP means the port is on the internet.

Watch out: on Linux, Docker publishes ports by writing iptables rules in the nat table's DOCKER chain, which are consulted before the INPUT rules that host firewalls like ufw manage. A ufw deny 8080 therefore does not block a published container port. The fixes: publish to 127.0.0.1 explicitly, put the container behind a reverse proxy, or configure Docker with iptables integration adjusted per the official networking documentation.

Reaching the host from a container

Platform How Notes
Docker Desktop (macOS, Windows) host.docker.internal provided automatically by Desktop
Docker Engine on Linux --add-host=host.docker.internal:host-gateway, or extra_hosts: in Compose not present unless you add it (Engine 20.10+)

host networking itself has a platform caveat: it is native on Linux, whereas on Docker Desktop the "host" is the Linux VM, so support arrived only in recent Desktop versions and behaves differently. For portable stacks, do not depend on --network host.

Debugging a network

The last line attaches a debug container to another container's network namespace — the same relationship every container in a Kubernetes Pod has with its peers (Post 04).

Chapter 2 — Storage

Terminology

  • Named volume — storage managed by Docker, referenced by name, under the daemon's data root (/var/lib/docker/volumes/<name>/_data on Linux). An anonymous volume is the same thing with a generated name, created when an image VOLUME path has nothing mounted on it.
  • Bind mount — a host path mounted into the container. Not managed by Docker; the host's permissions and inode semantics apply.
  • tmpfs mount — an in-memory filesystem inside the container, never written to disk (Linux only). The container's writable layer (Post 00) is not storage at all: it dies with the container.

Decision table

Named volume Bind mount tmpfs
Lives where Docker's data root anywhere on the host RAM
Managed by Docker yes (docker volume …) no yes
Survives docker rm yes yes (it is host data) no
Survives docker rm -v only if named and still referenced elsewhere; anonymous ones are deleted yes no
Host UID/permission surprises few — Docker seeds ownership from the image on first use many none
Performance on macOS/Windows good poor (crosses the VM boundary) good
Editable live from the host not conveniently yes — the point of it no
Right for databases, uploads, caches, any production data source code in development, config files, host sockets secrets in memory, scratch space, read-only-rootfs writable paths

Trick: -v ./typo:/app silently creates a directory when the source does not exist; --mount type=bind,source=./typo,target=/app errors instead. Prefer --mount in anything you intend to keep.

Volume lifecycle and what docker rm -v destroys

The rules, precisely:

  • docker rm <container> — removes the container and its writable layer; named volumes are untouched. docker rm -v additionally removes the anonymous volumes attached to it, and still leaves named ones alone.
  • docker volume prune — removes every volume no container currently references. It deletes real data with no summary of contents; a stopped container counts as a reference, one you already removed does not.
  • docker compose down — removes containers and the project network, keeps named volumes. docker compose down -v also removes the named volumes declared in the file — the command that wipes your development database.

Watch out: docker system prune -a --volumes is the most destructive command in everyday Docker use. Read the confirmation prompt before typing y.

Back up a volume without knowing anything about its internals by mounting it into a throwaway container and tarring it out: docker run --rm -v pgdata:/data:ro -v "$PWD":/backup alpine tar czf /backup/pgdata.tar.gz -C /data .. For a database, prefer its own dump tool (pg_dump, mongodump) over a filesystem tar of a running instance — a raw copy of live data files is not guaranteed to be consistent.

The bind-mount permission problem

A bind mount carries the host's numeric UIDs and GIDs straight through. The kernel compares numbers, not names; it does not care that UID 1000 is alice on the host and node in the image.

Both directions hurt: a non-root container cannot write into a host-owned directory, and a root container writes files the host user then cannot edit.

Fixes, best first:

A fourth option belongs in the image: create the user and the writable directories at build time (RUN adduser -u 10001 -D app && chown -R 10001:10001 /app, then USER 10001:10001) so the container's UID is stable and known.

On macOS and Windows Docker Desktop remaps ownership for you in most cases, which is why the problem often appears only when a colleague on Linux (or CI) runs the same stack. Rootless Docker and Podman add another layer: with user namespaces, container UID 0 maps to your host UID, so files land owned by you.

Bind-mount performance on macOS and Windows

Every I/O operation on a bind mount crosses from the container into the Linux VM's file-sharing layer and out to the host filesystem (VirtioFS on current Docker Desktop for Mac; the 9p/drvfs path for Windows files accessed from WSL2). Directories with tens of thousands of small files — node_modules, .venv, vendor, target — are worst affected.

Mitigations, in order of effect: keep dependency directories in a named volume or inside the image and bind-mount only your source; on Windows keep the project inside the WSL2 filesystem (~/project in the distro), not on /mnt/c; use :cached/:delegated consistency flags where your Desktop version still honours them; and for large builds, build inside the container or in CI rather than bind-mounting a host build tree.

Measure your own numbers rather than trusting a blog figure: docker run --rm -v "$PWD":/m alpine sh -c 'time find /m -type f | wc -l', then the same against a named volume.

Chapter 3 — Docker Compose

Terminology

  • Compose file — compose.yaml (or docker-compose.yml), declaring the services of one application, grouped into a project whose name defaults to the directory and prefixes every container, network, and volume.
  • Service — one container specification, scalable to several replicas. A profile is a label that keeps optional services out of the default up.

Compose v2 is a Go plugin invoked as docker compose (no hyphen); the Python docker-compose v1 is end-of-life. The Compose Specification made the top-level version: key obsolete — current versions warn if you include it. Modern files start straight with services:.

Service keys you will actually use

build and image together mean "build it and tag the result with that name" (so docker compose push works); image alone means "pull it".

depends_on — the trap

Plain depends_on only orders container start. It does not wait for the process inside to be ready. A PostgreSQL container is "started" milliseconds after docker run, and is not accepting connections for several seconds after that — so a plain depends_on: [db] reliably produces connection refused on the first application boot.

Condition Meaning
service_started the container has been started (the old default behaviour)
service_healthy its healthcheck reports healthy
service_completed_successfully it ran and exited with code 0 (migrations, seeders)

The dependency must therefore have a health check. Add restart: true under the dependency to have Compose restart the dependent service when the dependency is restarted.

Common pitfall: health-gated startup makes local runs pleasant, but it is not a substitute for application-level retry. Kubernetes has no depends_on at all (Post 06), so any service that cannot survive its database being briefly unavailable will fail there. Write the reconnect loop anyway.

Configuration through the environment

The discipline, which carries directly into Kubernetes ConfigMaps and Secrets (Post 05): the image is identical in every environment (nothing environment-specific baked in at build time); all configuration arrives as environment variables or mounted files at run time; secrets come from a secret store, never from a committed file and never from ARG/ENV at build time (Post 03); and defaults are sensible while failures are explicit — missing optional config falls back, missing required config aborts at startup with a clear message.

environment (inline) beats env_file for a handful of values; env_file is right for longer sets and keeps the file out of version control. Note that Compose's own ${…} interpolation reads the .env file beside the Compose file, which is a different mechanism from env_file: (which is passed to the container). Both exist; do not confuse them.

Logging

Container stdout/stderr go to the daemon's logging driver — json-file by default, which grows without bound. A chatty service can fill a disk in days.

Set the same as a daemon-wide default in /etc/docker/daemon.json so it applies to everything:

Reading logs:

The rule your application must follow: log to stdout/stderr, one event per line, no log files inside the container. Log files in a container's writable layer are invisible to docker logs, invisible to Kubernetes (Post 07), and deleted with the container.

Chapter 4 — A complete worked stack

A FastAPI web service, PostgreSQL, and Redis, with health-gated startup, named volumes for the data, and a debug profile. Create these four files in an empty directory and run it.

compose.yaml

Dockerfile

requirements.txt — fastapi==0.115.*, uvicorn[standard]==0.32.*, psycopg[binary]==3.2.*, redis==5.2.*, one per line.

app.py

.env — POSTGRES_PASSWORD=devpassword and LOG_LEVEL=debug. Never commit it; add it to .gitignore and .dockerignore.

Run it:

Things to notice in that file, because each is a deliberate choice:

  • db and cache publish no ports — they are reachable at db:5432 and cache:6379 from inside the project network only, and web addresses them by service name, never by IP or localhost.
  • condition: service_healthy means the first request after up works instead of racing PostgreSQL's startup. The data volumes are named, so docker compose down is safe and down -v is the explicit reset, and every password comes from the environment rather than the image.
  • /healthz is local and cheap while /readyz checks dependencies — the distinction Kubernetes formalises as liveness vs readiness probes (Post 06).

Compose command reference

Trick: docker compose config prints the file after interpolation, profile resolution, and merging of override files. When a variable "isn't being picked up", this is the command that tells you what Compose actually sees.

Exercise 1 — Prove the DNS difference

Exercise 2 — Publishing and exposure

Publish nginx on 8080 twice: once on all interfaces, once on loopback only. From another machine (or from ip addr's address on the same machine) confirm which is reachable. State the security implication in one sentence.

Exercise 3 — Destroy your data on purpose

Run PostgreSQL with a named volume, create a table, then in turn: docker rm -f the container, docker compose down, and docker compose down -v. Record after each step whether the table still exists.

Solution

Only -v removes the named volume.

Cheat-sheet

What How
Create a network / attach a container docker network create appnet / docker network connect appnet web
DNS by container name requires a user-defined network (embedded DNS at 127.0.0.11)
Publish a port / show mappings -p 8080:80 (-p 127.0.0.1:8080:80 for loopback only) / docker port web
Reach the host host.docker.internal (Desktop); --add-host=host.docker.internal:host-gateway (Linux)
Inside a container, localhost means that container — use the service name for peers
Named volume / bind mount / tmpfs -v pgdata:/data; --mount type=bind,source="$PWD",target=/app; --tmpfs /tmp:rw,size=64m
Volume commands docker volume inspect / prune; docker rm -v removes anonymous volumes only; docker compose down -v removes the project's named volumes
Bind-mount UID fix -u "$(id -u):$(id -g)", or user: in Compose
Compose file compose.yaml, no version: key, docker compose (v2)
Readiness / one-shot dependency depends_on: {db: {condition: service_healthy}}; service_completed_successfully
