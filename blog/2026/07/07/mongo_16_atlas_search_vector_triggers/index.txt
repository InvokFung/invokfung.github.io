11:Tae7e,<p>Atlas is MongoDB Inc.'s managed cloud service. Beyond hosting Mongo for you, Atlas ships features the open-source core doesn't have: <strong>Atlas Search</strong> (Lucene-based full-text), <strong>Atlas Vector Search</strong> (k-NN over embeddings — the building block of every RAG system in 2026), <strong>Atlas Triggers</strong> (serverless functions on database events / schedules / HTTP), <strong>Atlas Stream Processing</strong> (real-time pipelines over Kafka streams + Mongo collections), <strong>Atlas Online Archive</strong> (tier old data to cheap storage), and <strong>Data Federation</strong> (one query over Mongo + S3 + more). This post covers all of them with the patterns that show up in production.</p>

<h1 id="Chapter-5-—-Online-Archive"><a href="#Chapter-5-—-Online-Archive" class="headerlink" title="Chapter 5 — Online Archive"></a>Chapter 5 — Online Archive</h1>
<p>Move old documents to cheap blob storage, queryable via the same connection.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="text"><span class="line">Cluster policy:</span><br><span class="line">- Archive orders older than 1 year → S3-style storage</span><br><span class="line">- Still queryable transparently via federated query</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Set up via Atlas UI: pick a collection, define a date-based filter, choose retention. After archive, documents are gone from the primary collection but reachable via the <strong>federated database</strong>.</p>
<p>Cost: archived data is ~10× cheaper than hot tier.</p>
<p>Use cases: compliance retention; lifecycle management; right-sizing the hot cluster.</p>
<hr>
<h1 id="Chapter-6-—-Data-Federation"><a href="#Chapter-6-—-Data-Federation" class="headerlink" title="Chapter 6 — Data Federation"></a>Chapter 6 — Data Federation</h1>
<p>Run one query across <strong>Atlas clusters + S3 + other federated sources</strong>:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="text"><span class="line">Federated database = virtual DB</span><br><span class="line">  - Source 1: Atlas cluster A</span><br><span class="line">  - Source 2: Atlas cluster B</span><br><span class="line">  - Source 3: S3 bucket of Parquet files</span><br><span class="line">  - Source 4: Online Archive</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// queries from any driver — the federation layer routes + merges</span></span><br><span class="line">db.<span class="hljs-property">federated_db</span>.<span class="hljs-property">federated_orders</span>.<span class="hljs-title function_">aggregate</span>([</span><br><span class="line">  { <span class="hljs-attr">$match</span>: { <span class="hljs-attr">at</span>: { <span class="hljs-attr">$gte</span>: <span class="hljs-title class_">ISODate</span>(<span class="hljs-string">&quot;2020-01-01&quot;</span>) } } },   <span class="hljs-comment">// covers archived + live</span></span><br><span class="line">  { <span class="hljs-attr">$group</span>: { <span class="hljs-attr">_id</span>: { <span class="hljs-attr">$year</span>: <span class="hljs-string">&quot;$at&quot;</span> }, <span class="hljs-attr">revenue</span>: { <span class="hljs-attr">$sum</span>: <span class="hljs-string">&quot;$total&quot;</span> } } }</span><br><span class="line">])</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For analytics over years of mixed-tier data, much simpler than ETL + a warehouse.</p>
<hr>
<h1 id="Chapter-7-—-Atlas-Charts"><a href="#Chapter-7-—-Atlas-Charts" class="headerlink" title="Chapter 7 — Atlas Charts"></a>Chapter 7 — Atlas Charts</h1>
<p>A built-in BI tool for visualising MongoDB data. Drag fields, build dashboards, embed via iframe / API. Skips the need for a separate BI tool for small to medium projects.</p>
<p>Pair with <code>$merge</code>-built materialised views (Post 06) for fast dashboard reads.</p>
<hr>
<h1 id="Chapter-8-—-Atlas-App-Services-formerly-Realm"><a href="#Chapter-8-—-Atlas-App-Services-formerly-Realm" class="headerlink" title="Chapter 8 — Atlas App Services (formerly Realm)"></a>Chapter 8 — Atlas App Services (formerly Realm)</h1>
<p>A serverless backend platform: auth, functions, GraphQL endpoint, HTTPS rules. Pairs naturally with Atlas Triggers + Mongo for full-stack apps without managing servers.</p>
<p>In 2026 the focus shifted toward leaner primitives (Triggers + Functions + HTTPS endpoints) rather than the full Realm stack. Check current docs for the supported feature set.</p>
<hr>
<h1 id="Chapter-9-—-When-to-lean-on-Atlas-vs-DIY"><a href="#Chapter-9-—-When-to-lean-on-Atlas-vs-DIY" class="headerlink" title="Chapter 9 — When to lean on Atlas vs DIY"></a>Chapter 9 — When to lean on Atlas vs DIY</h1>
<p>Lean on Atlas when:</p>
<ul>
<li>Search + vector + serverless triggers + monitoring are all needed.</li>
<li>Small / medium ops team — managed &gt; self-hosted.</li>
<li>Multi-region HA + automatic backups + PITR are required.</li>
<li>Workloads benefit from one provider (less integration).</li>
</ul>
<p>DIY (self-hosted Mongo + Elasticsearch + Kafka + cron + S3) when:</p>
<ul>
<li>Existing infra investment.</li>
<li>On-prem or sovereign cloud requirement.</li>
<li>Cost optimisation at very large scale.</li>
</ul>
<p>Most teams below 100-engineer scale benefit from Atlas. Most teams above can justify either way.</p>

<h1 id="Chapter-11-—-Common-pitfalls"><a href="#Chapter-11-—-Common-pitfalls" class="headerlink" title="Chapter 11 — Common pitfalls"></a>Chapter 11 — Common pitfalls</h1>
<table>

<th>Pitfall</th>
<th>Cause</th>
<th>Fix</th>
</tr>
</thead>

<td><code>$search</code> returns 0 — fresh index</td>
<td>indexing in progress</td>
<td>wait + check index status</td>
</tr>
<tr>
<td>Vector dim mismatch</td>
<td>model changed; index didn't</td>
<td>rebuild index for new dim</td>

<td><code>numCandidates</code> too small</td>
<td>raise (cost trade-off)</td>

<td>exception in function</td>
<td>check Atlas Function logs</td>
</tr>

<td>sink slow / window too big</td>
<td>profile sink; smaller windows</td>
</tr>

<td>large S3 scan</td>
<td>partition source data by date / key</td>
</tr>

<td>querying raw events</td>
<td>precompute via <code>$merge</code> materialised view</td>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Search-index"><a href="#Exercise-1-—-Search-index" class="headerlink" title="Exercise 1 — Search index"></a>Exercise 1 — Search index</h2>
<p>On a sample <code>articles</code> collection, create an Atlas Search index. Query for &quot;mongodb&quot; with fuzzy + autocomplete.</p>
<h2 id="Exercise-2-—-Vector-search-RAG"><a href="#Exercise-2-—-Vector-search-RAG" class="headerlink" title="Exercise 2 — Vector search RAG"></a>Exercise 2 — Vector search RAG</h2>
<p>Generate embeddings (OpenAI / Cohere / local model) for a handful of documents. Store in Mongo. Build a vector index. Run k-NN for a user query embedding. Confirm relevant docs returned.</p>
<h2 id="Exercise-3-—-Trigger-on-insert"><a href="#Exercise-3-—-Trigger-on-insert" class="headerlink" title="Exercise 3 — Trigger on insert"></a>Exercise 3 — Trigger on insert</h2>
<p>Write an Atlas Database trigger on <code>orders</code> that posts a webhook with the new order. Test by inserting; confirm webhook receives the payload.</p>
<h2 id="Exercise-4-—-Scheduled-refresh"><a href="#Exercise-4-—-Scheduled-refresh" class="headerlink" title="Exercise 4 — Scheduled refresh"></a>Exercise 4 — Scheduled refresh</h2>

<h2 id="Exercise-5-—-Hybrid-search"><a href="#Exercise-5-—-Hybrid-search" class="headerlink" title="Exercise 5 — Hybrid search"></a>Exercise 5 — Hybrid search</h2>
<p>Combine lexical search + vector search with <code>$unionWith</code> (Chapter 2). Compare top 10 results vs lexical-only vs vector-only.</p>
<h2 id="Exercise-6-—-Online-Archive"><a href="#Exercise-6-—-Online-Archive" class="headerlink" title="Exercise 6 — Online Archive"></a>Exercise 6 — Online Archive</h2>
