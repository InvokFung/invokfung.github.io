11:T101a2,<p>An image that only exists on your laptop is not deployable. Getting it somewhere a cluster can pull it — and being able to prove <em>which</em> bytes you deployed, what is inside them, and who built them — is the subject of this post. It is also where container practice stops being about convenience and starts being about security: a registry is a distribution channel, and anything you pull runs on your infrastructure. This post covers how a registry actually stores things, why tags lie and digests do not, how to publish to Docker Hub, GHCR, and ECR, how to scan for vulnerabilities without drowning in CVE noise, what SBOMs and signatures buy you, how to harden a container at run time, and the secret-leak patterns that survive inside image layers forever.</p>

<h1 id="Chapter-1-—-How-a-registry-actually-works"><a href="#Chapter-1-—-How-a-registry-actually-works" class="headerlink" title="Chapter 1 — How a registry actually works"></a>Chapter 1 — How a registry actually works</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Registry</strong> — an HTTP service implementing the OCI distribution spec (Docker Hub, GHCR, ECR, Harbor, Artifactory, or <code>registry:2</code> run yourself).</li>
<li><strong>Repository</strong> — a named collection of images inside a registry: <code>ghcr.io/acme/api</code>.</li>
<li><strong>Blob</strong> — an immutable content-addressed object: a layer tar or a config JSON, stored under its <code>sha256:</code> digest.</li>
<li><strong>Manifest</strong> — a JSON document listing one image's config blob and layer blobs, for one platform.</li>
<li><strong>Index (manifest list)</strong> — a JSON document listing several manifests, one per platform, plus optional attestations.</li>
<li><strong>Tag</strong> — a mutable, human-readable pointer to a manifest or index within a repository.</li>
<li><strong>Digest</strong> — the SHA-256 of the manifest or blob bytes. Immutable by construction.</li>
</ul>
<h2 id="The-data-model"><a href="#The-data-model" class="headerlink" title="The data model"></a>The data model</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="text"><span class="line">registry</span><br><span class="line"> └── repository  ghcr.io/acme/api</span><br><span class="line">      ├── tag &quot;1.4.0&quot;  ──┐</span><br><span class="line">      ├── tag &quot;latest&quot; ──┼──► index (sha256:aaa…)</span><br><span class="line">      │                  │     ├── manifest linux/amd64 (sha256:bbb…) ─► config blob + layer blobs</span><br><span class="line">      │                  │     ├── manifest linux/arm64 (sha256:ccc…) ─► config blob + layer blobs</span><br><span class="line">      │                  │     └── attestation manifests (SBOM, provenance)</span><br><span class="line">      └── blobs/  sha256:… (layers and configs, shared across every tag that references them)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker run -d -p 5000:5000 --name reg registry:2</span><br><span class="line">docker pull alpine:3.20</span><br><span class="line">docker tag alpine:3.20 localhost:5000/alpine:3.20</span><br><span class="line">docker push localhost:5000/alpine:3.20</span><br><span class="line"> </span><br><span class="line">curl -s localhost:5000/v2/_catalog</span><br><span class="line">curl -s localhost:5000/v2/alpine/tags/list</span><br><span class="line">curl -sI -H <span class="hljs-string">&#x27;Accept: application/vnd.oci.image.manifest.v1+json&#x27;</span> \</span><br><span class="line">     localhost:5000/v2/alpine/manifests/3.20 | grep -i docker-content-digest</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>That <code>Docker-Content-Digest</code> header is the digest of the manifest — the identity you should be deploying by.</p>

<p><strong>Trick:</strong> <code>crane</code> and <code>skopeo</code> talk to registries without a container runtime. <code>skopeo copy docker://src docker://dst</code> moves an image between registries without pulling it to disk — the cleanest way to mirror images into an air-gapped environment.</p>
</blockquote>

<h1 id="Chapter-2-—-Tags-lie-digests-do-not"><a href="#Chapter-2-—-Tags-lie-digests-do-not" class="headerlink" title="Chapter 2 — Tags lie, digests do not"></a>Chapter 2 — Tags lie, digests do not</h1>
<p>A tag is a mutable pointer. Anyone with push access can move <code>1.4.0</code>, and upstream maintainers routinely move <code>latest</code>, <code>3.12</code>, and even patch tags to new builds. Two machines pulling <code>myapp:1.4.0</code> an hour apart can therefore run different code, with no error anywhere.</p>
<p>A digest is the hash of the manifest bytes. <code>myapp@sha256:9f2e…</code> is either the exact image you tested or a failed pull. There is no third outcome.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker pull ghcr.io/acme/api:1.4.0</span><br><span class="line">docker inspect --format <span class="hljs-string">&#x27;{{index .RepoDigests 0}}&#x27;</span> ghcr.io/acme/api:1.4.0</span><br><span class="line"><span class="hljs-comment"># ghcr.io/acme/api@sha256:9f2e...</span></span><br><span class="line"> </span><br><span class="line">docker pull ghcr.io/acme/api@sha256:9f2e...     <span class="hljs-comment"># exactly those bytes, forever</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>The rule: tags for humans, digests for machines.</strong></p>
<table>
<thead>
<tr>
<th>Context</th>
<th>Reference by</th>
</tr>
</thead>
<tbody>
<tr>
<td>A person reading a README or <code>docker run</code> in a tutorial</td>
<td>tag</td>
</tr>
<tr>
<td><code>FROM</code> in a Dockerfile you must rebuild identically</td>
<td>tag <strong>+</strong> digest</td>
</tr>
<tr>
<td>A Kubernetes manifest or Compose file in production</td>
<td>digest (or a tag pinned by your GitOps tooling, Post 07)</td>
</tr>
<tr>
<td>A rollback</td>
<td>the previous digest — tags may have moved</td>
</tr>
<tr>
<td>An audit trail (&quot;what was running at 03:00?&quot;)</td>
<td>digest, recorded at deploy time</td>
</tr>
</tbody>
</table>
<p>Practical middle ground: keep readable tags in the repository <em>and</em> record the digest at deploy time. Kubernetes writes the resolved digest into the Pod status (<code>imageID</code>), and an admission policy can require digest references outright (Post 07).</p>
<blockquote>
<p><strong>Common pitfall:</strong> <code>imagePullPolicy: IfNotPresent</code> with a moving tag means nodes keep whatever they cached first. Half the fleet runs the old bytes, half the new, and both report the same tag. Digests remove the class of bug entirely.</p>
</blockquote>
<h2 id="Multi-arch-images-and-the-index"><a href="#Multi-arch-images-and-the-index" class="headerlink" title="Multi-arch images and the index"></a>Multi-arch images and the index</h2>
<p>A modern public image tag usually resolves to an <strong>index</strong> rather than a manifest. The client picks the manifest matching its platform.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker buildx imagetools inspect alpine:3.20</span><br><span class="line"><span class="hljs-comment"># Name:      docker.io/library/alpine:3.20</span></span><br><span class="line"><span class="hljs-comment"># MediaType: application/vnd.oci.image.index.v1+json   Digest: sha256:...</span></span><br><span class="line"><span class="hljs-comment"># Manifests:</span></span><br><span class="line"><span class="hljs-comment">#   Platform: linux/amd64   Digest: sha256:...</span></span><br><span class="line"><span class="hljs-comment">#   Platform: linux/arm64   Digest: sha256:...   (and the other supported platforms)</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Build one yourself (Post 01 covered <code>buildx</code>):</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker buildx build --platform linux/amd64,linux/arm64 -t ghcr.io/acme/api:1.4.0 --push .</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Two consequences worth remembering:</p>
<ol>
<li><strong><code>docker pull image@sha256:…</code> of an index digest still works on every architecture</strong> — the index digest is platform-independent, while a per-platform manifest digest is not. Pin the index digest.</li>
<li>Build attestations (SBOM, provenance) are stored as extra manifests inside that same index, which is how <code>cosign</code> and <code>docker buildx imagetools inspect</code> find them later.</li>
</ol>

<h2 id="Docker-Hub"><a href="#Docker-Hub" class="headerlink" title="Docker Hub"></a>Docker Hub</h2>

<p>ECR issues a short-lived token rather than accepting a long-lived password. The AWS series covers the IAM model this depends on (AWS Course Post 00) and the Terraform that provisions repositories (AWS Course Post 08).</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span></pre></td><td class="code"><pre><code class="bash"><span class="line">ACCOUNT=123456789012; REGION=ap-east-1</span><br><span class="line">aws ecr create-repository --repository-name myapp --region <span class="hljs-variable">$REGION</span> \</span><br><span class="line">  --image-tag-mutability IMMUTABLE --image-scanning-configuration scanOnPush=<span class="hljs-literal">true</span></span><br><span class="line"> </span><br><span class="line">aws ecr get-login-password --region <span class="hljs-variable">$REGION</span> \</span><br><span class="line">  | docker login --username AWS --password-stdin <span class="hljs-variable">$ACCOUNT</span>.dkr.ecr.<span class="hljs-variable">$REGION</span>.amazonaws.com</span><br><span class="line"> </span><br><span class="line">docker tag myapp:1.4.0 <span class="hljs-variable">$ACCOUNT</span>.dkr.ecr.<span class="hljs-variable">$REGION</span>.amazonaws.com/myapp:1.4.0</span><br><span class="line">docker push <span class="hljs-variable">$ACCOUNT</span>.dkr.ecr.<span class="hljs-variable">$REGION</span>.amazonaws.com/myapp:1.4.0</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p>Nodes need credentials of their own — your laptop's <code>docker login</code> is irrelevant to them. In Kubernetes that is an <strong>image pull secret</strong>:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">kubectl create secret docker-registry ghcr-pull \</span><br><span class="line">  --docker-server=ghcr.io --docker-username=&lt;user&gt; --docker-password=&lt;token&gt;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-4-—-Vulnerability-scanning-without-drowning"><a href="#Chapter-4-—-Vulnerability-scanning-without-drowning" class="headerlink" title="Chapter 4 — Vulnerability scanning without drowning"></a>Chapter 4 — Vulnerability scanning without drowning</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>CVE</strong> — a public identifier for one vulnerability (<code>CVE-2025-12345</code>).</li>
<li><strong>Scanner</strong> — a tool that inventories the packages in an image and matches them against vulnerability databases.</li>
<li><strong>Fixed / unfixed</strong> — whether the distribution has published a patched version yet.</li>
<li><strong>VEX</strong> — a machine-readable statement that a given CVE is <em>not exploitable</em> in your product, so scanners can suppress it with a documented reason.</li>
</ul>
<h2 id="Running-a-scan"><a href="#Running-a-scan" class="headerlink" title="Running a scan"></a>Running a scan</h2>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># Trivy</span></span><br><span class="line">trivy image myapp:1.4.0</span><br><span class="line">trivy image --severity HIGH,CRITICAL --ignore-unfixed myapp:1.4.0</span><br><span class="line">trivy image --exit-code 1 --severity CRITICAL myapp:1.4.0     <span class="hljs-comment"># gate a CI pipeline</span></span><br><span class="line">trivy image --format json -o report.json myapp:1.4.0</span><br><span class="line">trivy fs .                                                    <span class="hljs-comment"># scan source and lockfiles</span></span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># Grype (Anchore)</span></span><br><span class="line">grype myapp:1.4.0</span><br><span class="line">grype myapp:1.4.0 --fail-on high</span><br><span class="line">grype sbom:./sbom.spdx.json                                   <span class="hljs-comment"># scan an SBOM instead of an image</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Registries also scan: ECR (<code>scanOnPush</code>, with the deeper Amazon Inspector integration), GHCR/Dependabot for some ecosystems, Docker Scout for Hub.</p>
<h2 id="Reading-the-output-without-drowning"><a href="#Reading-the-output-without-drowning" class="headerlink" title="Reading the output without drowning"></a>Reading the output without drowning</h2>
<p>A first scan of a <code>python:3.12</code> image can report hundreds of findings. Most of them are not action items. Triage in this order:</p>
<ol>
<li><strong>Severity and fix availability first.</strong> <code>--severity HIGH,CRITICAL --ignore-unfixed</code> collapses the list to what you can actually act on today.</li>
<li><strong>Is the vulnerable component reachable?</strong> A CVE in a CLI tool your service never invokes is real but low-priority; a CVE in your TLS library is not.</li>
<li><strong>Is it in the base image or in your dependencies?</strong> Base-image CVEs are fixed by rebuilding on a newer base; dependency CVEs are fixed by bumping a lockfile.</li>
<li><strong>Suppress with a reason, never silently.</strong> <code>.trivyignore</code> (with an expiry date and a comment) or a VEX document records <em>why</em> something was accepted.</li>
<li><strong>Gate on a policy you can hold to.</strong> &quot;No CRITICAL with a fix available&quot; is enforceable; &quot;zero CVEs&quot; is not, and a gate everyone bypasses protects nothing.</li>
</ol>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line"># .trivyignore — every line needs a reason and a review date</span><br><span class="line">CVE-2025-11111  # not reachable: /usr/bin/git is not invoked at runtime. Review 2026-09-01.</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="The-base-image-strategy-that-actually-reduces-CVE-count"><a href="#The-base-image-strategy-that-actually-reduces-CVE-count" class="headerlink" title="The base-image strategy that actually reduces CVE count"></a>The base-image strategy that actually reduces CVE count</h2>
<p>Scanning does not fix anything. What reduces findings, in order of effect:</p>
<table>
<thead>
<tr>
<th>Action</th>
<th>Effect</th>
</tr>
</thead>
<tbody>
<tr>
<td><strong>Rebuild regularly on a fresh base</strong></td>
<td>most OS-package CVEs disappear because the base was patched upstream</td>
</tr>
<tr>
<td><strong>Ship a smaller base</strong> (slim, distroless, <code>scratch</code>)</td>
<td>fewer packages, fewer CVEs, less to patch — often a large drop</td>
</tr>
<tr>
<td><strong>Remove build tooling from the runtime stage</strong> (Post 01)</td>
<td>compilers and headers stop counting toward your attack surface</td>
</tr>
<tr>
<td><strong>Automate base bumps</strong> (Renovate/Dependabot on the <code>FROM</code> digest)</td>
<td>the pin stays current without a human remembering</td>
</tr>
<tr>
<td><strong>Track your own dependency lockfiles</strong></td>
<td>application-level CVEs, which no base change fixes</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>Trick:</strong> a weekly scheduled rebuild-and-scan of the <em>unchanged</em> source is one of the highest-value pipelines you can add. Your code did not change; your base image did, and so did the vulnerability database.</p>
</blockquote>

<h1 id="Chapter-5-—-SBOMs-provenance-and-signing"><a href="#Chapter-5-—-SBOMs-provenance-and-signing" class="headerlink" title="Chapter 5 — SBOMs, provenance, and signing"></a>Chapter 5 — SBOMs, provenance, and signing</h1>
<h2 id="SBOM"><a href="#SBOM" class="headerlink" title="SBOM"></a>SBOM</h2>
<p>A <strong>Software Bill of Materials</strong> lists every component in an artifact — OS packages, language dependencies, versions, licences. Two mainstream formats: <strong>SPDX</strong> (ISO standard, licence-focused) and <strong>CycloneDX</strong> (OWASP, security-focused). Either is fine; pick one and be consistent.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="bash"><span class="line">syft myapp:1.4.0 -o spdx-json=sbom.spdx.json</span><br><span class="line">syft myapp:1.4.0 -o cyclonedx-json=sbom.cdx.json</span><br><span class="line">trivy image --format cyclonedx -o sbom.cdx.json myapp:1.4.0</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># BuildKit can attach SBOM and provenance as attestations at build time</span></span><br><span class="line">docker buildx build --sbom=<span class="hljs-literal">true</span> --provenance=mode=max -t ghcr.io/acme/api:1.4.0 --push .</span><br><span class="line">docker buildx imagetools inspect ghcr.io/acme/api:1.4.0 --format <span class="hljs-string">&#x27;{{json .SBOM}}&#x27;</span> | <span class="hljs-built_in">head</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Why it matters: when the next widely-exploited library CVE lands, the question &quot;are we affected, and where?&quot; becomes a query over stored SBOMs instead of a week of archaeology. It is also increasingly a procurement and compliance requirement.</p>
<h2 id="Provenance"><a href="#Provenance" class="headerlink" title="Provenance"></a>Provenance</h2>
<p><strong>Provenance</strong> answers <em>how</em> the artifact was built: which source commit, which builder, which parameters. BuildKit emits it as an in-toto attestation (<code>--provenance=mode=max</code>), and the SLSA framework defines levels for how tamper-resistant that claim is. Provenance produced by your CI, signed by your CI's identity, is what lets a policy say &quot;only images built by this pipeline from this repository may run&quot;.</p>
<h2 id="Signing-with-cosign"><a href="#Signing-with-cosign" class="headerlink" title="Signing with cosign"></a>Signing with cosign</h2>
<p>Classic key-based signing works, but key management is the hard part. <strong>Keyless</strong> signing (Sigstore) removes the long-lived key: your CI job authenticates with an OIDC token, Fulcio issues a short-lived certificate bound to that identity, the signature is recorded in the Rekor transparency log, and the certificate expires minutes later.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># sign by digest, never by tag — a tag can move after signing</span></span><br><span class="line">cosign sign --<span class="hljs-built_in">yes</span> ghcr.io/acme/api@sha256:9f2e...</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># verify, asserting WHO signed it and via which OIDC issuer</span></span><br><span class="line">cosign verify \</span><br><span class="line">  --certificate-identity-regexp <span class="hljs-string">&#x27;^https://github.com/acme/api/\.github/workflows/.+&#x27;</span> \</span><br><span class="line">  --certificate-oidc-issuer https://token.actions.githubusercontent.com \</span><br><span class="line">  ghcr.io/acme/api@sha256:9f2e... | python3 -m json.tool</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># attach an SBOM as a signed attestation</span></span><br><span class="line">cosign attest --<span class="hljs-built_in">yes</span> --<span class="hljs-built_in">type</span> cyclonedx --predicate sbom.cdx.json ghcr.io/acme/api@sha256:9f2e...</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> <code>cosign verify</code> with no identity flags checks only that <em>a</em> signature exists. The security comes from asserting the expected identity and issuer. A verification step that accepts any signer is theatre.</p>
</blockquote>
<p>Enforcement belongs at admission time in the cluster — an admission controller (Kyverno, Sigstore Policy Controller, Gatekeeper) that rejects Pods whose images are unsigned, unscanned, or not from an allowed registry. That is Post 07 material; the point here is that signing is only useful if something checks it.</p>

<h2 id="Image-lifecycle-and-retention"><a href="#Image-lifecycle-and-retention" class="headerlink" title="Image lifecycle and retention"></a>Image lifecycle and retention</h2>
<p>Registries grow without bound unless told otherwise. Every CI run of every branch pushes a tag; six months later the repository is thousands of images and a large bill.</p>
<p>A workable policy:</p>
<ul>
<li><strong>Immutable release tags</strong> (<code>1.4.0</code>) — never reused. ECR enforces this with <code>IMMUTABLE</code>; other registries have equivalents.</li>
<li><strong>Semantic tags for humans, digests for deploys</strong>, as in Chapter 2.</li>
<li><strong>Expire ephemeral tags</strong>: PR/branch/commit-SHA tags after 14–30 days.</li>
<li><strong>Keep the last N releases</strong> (say 10) plus anything currently deployed, forever.</li>
<li><strong>Delete untagged manifests</strong> older than a few days — these accumulate every time a tag moves.</li>
<li><strong>Verify nothing running references what you delete</strong> before enabling any rule; a deleted digest breaks a Pod restart, not just a new deploy.</li>
</ul>

<h2 id="Exercise-4-—-Scan-and-triage"><a href="#Exercise-4-—-Scan-and-triage" class="headerlink" title="Exercise 4 — Scan and triage"></a>Exercise 4 — Scan and triage</h2>
<p>Scan <code>python:3.12</code> and <code>python:3.12-slim</code> with Trivy. Record the total findings and the HIGH/CRITICAL-with-fix counts for each. Then scan your own application image and write a one-paragraph triage: what you would fix this week, what you would suppress with a reason, and why.</p>
<h2 id="Exercise-5-—-Harden-a-container"><a href="#Exercise-5-—-Harden-a-container" class="headerlink" title="Exercise 5 — Harden a container"></a>Exercise 5 — Harden a container</h2>
<p>Take any image you run and add, one flag at a time: <code>--user</code>, <code>--read-only</code> (plus the <code>--tmpfs</code> paths it turns out to need), <code>--cap-drop=ALL</code>, and <code>--security-opt no-new-privileges:true</code>. Record which flag first breaks the app and what the minimum capability set turned out to be.</p>
<h2 id="Exercise-6-—-SBOM-and-signature"><a href="#Exercise-6-—-SBOM-and-signature" class="headerlink" title="Exercise 6 — SBOM and signature"></a>Exercise 6 — SBOM and signature</h2>
<p>Generate an SBOM for one of your images in both SPDX and CycloneDX form, and check whether the same image (or a public one you depend on) carries a cosign signature. If you have a GitHub Actions pipeline, add keyless signing of the pushed digest and verify it locally with an identity assertion.</p>
