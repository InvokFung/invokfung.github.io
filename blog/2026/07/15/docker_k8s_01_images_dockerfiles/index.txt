11:T1029e,<p>Post 00 established what a container is at runtime. This post covers the artifact it runs from: the <strong>image</strong>. An image is not a tarball of a machine — it is an ordered stack of filesystem layers plus two small JSON documents, and almost every practical skill (fast rebuilds, small images, no leaked secrets, reproducible deploys) follows from understanding that structure. The Dockerfile is the build script that produces it, and its instructions have exact semantics that are easy to use wrongly: <code>ADD</code> where <code>COPY</code> was meant, <code>ENV</code> where <code>ARG</code> was meant, shell-form <code>CMD</code> that silently breaks signal handling. This post goes through all of it, then builds working multi-stage Node and Python images and measures the size difference.</p>
<blockquote>
<p>Series map: 00 Containers from First Principles → <strong>01 Images and Dockerfiles</strong> (this post) → 02 Networking, Volumes and Compose → 03 Registries, Supply Chain and Security → 04 Kubernetes Architecture and Core Objects → 05 Config, Storage and Stateful Workloads → 06 Scheduling, Resources, Probes and Rollouts → 07 Ingress, Observability, RBAC and GitOps.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Describe an image as layers + manifest + config, and use every meaningful Dockerfile instruction with correct semantics — including the <code>COPY</code>/<code>ADD</code>, <code>ENV</code>/<code>ARG</code>, and <code>CMD</code>/<code>ENTRYPOINT</code> distinctions.</li>
<li>Predict exactly which layers a change invalidates, and order instructions so dependency installs stay cached.</li>
<li>Write a <code>.dockerignore</code> that keeps the build context small and the cache stable.</li>
<li>Build multi-stage images for a Node service and a Python service, running as a non-root user.</li>
<li>Choose between <code>distroless</code>, <code>alpine</code>, <code>slim</code>, and full base images with the musl/glibc trade-offs in mind.</li>
<li>Use BuildKit cache mounts, secret mounts, and <code>buildx</code> multi-platform builds.</li>
<li>Measure your own before/after image sizes and pin base images by digest for reproducibility.</li>
</ul>

<h1 id="Chapter-1-—-What-an-image-is-made-of"><a href="#Chapter-1-—-What-an-image-is-made-of" class="headerlink" title="Chapter 1 — What an image is made of"></a>Chapter 1 — What an image is made of</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Layer</strong> — a tar archive of filesystem changes (added, modified, and whiteout entries), stored as a content-addressed blob. Its <code>diff_id</code> is the SHA-256 of the <em>uncompressed</em> tar.</li>
<li><strong>Digest</strong> — the SHA-256 of a <em>stored blob or manifest</em> as the registry holds it. What <code>image@sha256:…</code> refers to.</li>
<li><strong>Manifest</strong> — a small JSON listing the config blob and the layer blobs for one platform.</li>
<li><strong>Index / manifest list</strong> — a JSON listing several manifests, one per platform (Post 03).</li>
<li><strong>Image config</strong> — JSON holding <code>Env</code>, <code>Cmd</code>, <code>Entrypoint</code>, <code>WorkingDir</code>, <code>User</code>, <code>ExposedPorts</code>, <code>Labels</code>, the <code>rootfs.diff_ids</code>, and a <code>history</code> array.</li>
<li><strong>Build context</strong> — the set of files sent to the builder, from which <code>COPY</code> may read.</li>
</ul>

<p>Three facts worth internalising immediately:</p>
<ol>
<li><strong>Layers are shared.</strong> Ten images built <code>FROM python:3.12-slim</code> store that base once. Pulls only fetch blobs the host lacks.</li>
<li><strong>Layers are additive.</strong> Deleting a file in layer 3 does not shrink layers 0–2; it writes a whiteout. <code>RUN apt-get install …</code> in one instruction and <code>RUN rm -rf /var/lib/apt/lists/*</code> in the next leaves the package lists inside the image.</li>
<li><strong>The config is the runtime contract.</strong> <code>ENTRYPOINT</code>, <code>CMD</code>, <code>USER</code>, <code>ENV</code>, and <code>WORKDIR</code> live there — not in the filesystem — which is why <code>docker run --entrypoint</code> can override them without touching a layer.</li>
</ol>

<h1 id="Chapter-2-—-The-Dockerfile-instruction-set"><a href="#Chapter-2-—-The-Dockerfile-instruction-set" class="headerlink" title="Chapter 2 — The Dockerfile instruction set"></a>Chapter 2 — The Dockerfile instruction set</h1>
<h2 id="FROM"><a href="#FROM" class="headerlink" title="FROM"></a><code>FROM</code></h2>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">FROM</span> python:<span class="hljs-number">3.12</span>-slim              <span class="hljs-comment"># tag: mutable, readable</span></span><br><span class="line"><span class="hljs-keyword">FROM</span> python:<span class="hljs-number">3.12</span>-slim@sha256:...   <span class="hljs-comment"># tag + digest: reproducible (Post 03)</span></span><br><span class="line"><span class="hljs-keyword">FROM</span> node:<span class="hljs-number">22</span>-alpine AS builder     <span class="hljs-comment"># names a stage for multi-stage builds</span></span><br><span class="line"><span class="hljs-keyword">FROM</span> scratch                       <span class="hljs-comment"># the empty image: for static binaries</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Every <code>FROM</code> starts a new stage and resets the filesystem; only <code>ARG</code>s declared before the first <code>FROM</code> survive across stage boundaries, and then only for use in <code>FROM</code> lines unless redeclared.</p>
<h2 id="RUN"><a href="#RUN" class="headerlink" title="RUN"></a><code>RUN</code></h2>
<p>Runs a command in a new layer on top of the current image.</p>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-comment"># shell form → /bin/sh -c &quot;...&quot;; pipes, &amp;&amp;, and variable expansion available</span></span><br><span class="line"><span class="hljs-keyword">RUN</span><span class="language-bash"> apt-get update &amp;&amp; apt-get install -y --no-install-recommends curl \</span><br><span class="line"> &amp;&amp; <span class="hljs-built_in">rm</span> -rf /var/lib/apt/lists/*</span></span><br><span class="line"><span class="hljs-keyword">RUN</span><span class="language-bash"> [<span class="hljs-string">&quot;/usr/local/bin/setup.sh&quot;</span>, <span class="hljs-string">&quot;--fast&quot;</span>]   <span class="hljs-comment"># exec form: no shell, no expansion</span></span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Chain related commands with <code>&amp;&amp;</code> in one <code>RUN</code> so cleanup happens <em>in the same layer</em> as the thing it cleans up. A separate cleanup instruction removes nothing from the image.</p>
<h2 id="COPY-vs-ADD"><a href="#COPY-vs-ADD" class="headerlink" title="COPY vs ADD"></a><code>COPY</code> vs <code>ADD</code></h2>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">COPY</span><span class="language-bash"> package.json package-lock.json ./     <span class="hljs-comment"># explicit, predictable</span></span></span><br><span class="line"><span class="hljs-keyword">COPY</span><span class="language-bash"> --<span class="hljs-built_in">chown</span>=10001:10001 src/ /app/src/    <span class="hljs-comment"># set ownership as you copy</span></span></span><br><span class="line"><span class="hljs-keyword">COPY</span><span class="language-bash"> --from=builder /app/dist /app/dist    <span class="hljs-comment"># copy from another stage</span></span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>ADD</code> does everything <code>COPY</code> does <em>plus</em> two magic behaviours: it auto-extracts local tar archives into the destination, and it can fetch remote URLs (and, with current BuildKit, Git repositories).</p>
<table>
<thead>
<tr>
<th>Situation</th>
<th>Use</th>
</tr>
</thead>
<tbody>
<tr>
<td>Copying files or directories from the context</td>
<td><code>COPY</code></td>
</tr>
<tr>
<td>Copying from a previous build stage</td>
<td><code>COPY --from=</code></td>
</tr>
<tr>
<td>Extracting a local <code>.tar.gz</code> you control</td>
<td><code>ADD</code> (this is its one clear win)</td>
</tr>
<tr>
<td>Downloading a remote file</td>
<td>prefer <code>RUN curl -fsSL … &amp;&amp; checksum-verify</code>, or <code>ADD --checksum=sha256:…</code></td>
</tr>
</tbody>
</table>
<p><strong>Why <code>ADD</code> is usually wrong:</strong> the tar auto-extraction is implicit, so <code>ADD release.tgz /opt/</code> behaves completely differently from <code>ADD release.bin /opt/</code>; a plain <code>ADD &lt;url&gt;</code> historically performed no integrity check and produced an un-cacheable layer that could not be validated. <code>COPY</code> has one behaviour and it is the one you expected. The Docker docs' own best-practices guide says the same: prefer <code>COPY</code>.</p>
<h2 id="WORKDIR"><a href="#WORKDIR" class="headerlink" title="WORKDIR"></a><code>WORKDIR</code></h2>
<p><code>WORKDIR /app</code> creates the directory if missing and persists for later instructions and at run time. Always use it rather than <code>RUN cd /app</code> — a <code>cd</code> inside a <code>RUN</code> affects only that shell, which is a common source of &quot;why is my file in <code>/</code>?&quot;.</p>

<p>If both are defined with the same name, <code>ENV</code> wins for the rest of the build. Neither is a secret store: <code>docker history --no-trunc</code> prints build args, and <code>docker inspect</code> prints env vars. Post 03 goes into the leak in detail; the fix is BuildKit secret mounts, in Chapter 6 below.</p>
<h2 id="EXPOSE"><a href="#EXPOSE" class="headerlink" title="EXPOSE"></a><code>EXPOSE</code></h2>
<p><code>EXPOSE 8080</code> publishes nothing. It is metadata: documentation for humans, a hint for tooling, and the list <code>docker run -P</code> uses when assigning random host ports. Actual publishing is <code>-p 8080:8080</code> at run time (Post 02). Leaving <code>EXPOSE</code> out does not prevent anything from working.</p>
<h2 id="CMD-vs-ENTRYPOINT"><a href="#CMD-vs-ENTRYPOINT" class="headerlink" title="CMD vs ENTRYPOINT"></a><code>CMD</code> vs <code>ENTRYPOINT</code></h2>
<ul>
<li><code>ENTRYPOINT</code> — the executable. Not overridden by trailing <code>docker run</code> arguments.</li>
<li><code>CMD</code> — default arguments (or the default command when there is no <code>ENTRYPOINT</code>). Replaced by trailing <code>docker run</code> arguments.</li>
</ul>
<p>The canonical combination:</p>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">ENTRYPOINT</span><span class="language-bash"> [<span class="hljs-string">&quot;/usr/local/bin/myapp&quot;</span>]</span></span><br><span class="line"><span class="hljs-keyword">CMD</span><span class="language-bash"> [<span class="hljs-string">&quot;--config&quot;</span>, <span class="hljs-string">&quot;/etc/myapp/prod.yaml&quot;</span>]</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ul>
<li><code>docker run myapp</code> → <code>myapp --config /etc/myapp/prod.yaml</code></li>
<li><code>docker run myapp --config /etc/myapp/dev.yaml</code> → the <code>CMD</code> is replaced</li>
<li><code>docker run --entrypoint sh -it myapp</code> → drops you into a shell</li>
</ul>
<h3 id="Exec-form-vs-shell-form"><a href="#Exec-form-vs-shell-form" class="headerlink" title="Exec form vs shell form"></a>Exec form vs shell form</h3>
<table>
<thead>
<tr>
<th></th>
<th>Exec form <code>[&quot;a&quot;,&quot;b&quot;]</code></th>
<th>Shell form <code>a b</code></th>
</tr>
</thead>
<tbody>
<tr>
<td>What runs as PID 1</td>
<td>your program</td>
<td><code>/bin/sh</code></td>
</tr>
<tr>
<td>Variable expansion (<code>$HOME</code>)</td>
<td>no</td>
<td>yes</td>
</tr>
<tr>
<td>Pipes, <code>&amp;&amp;</code>, redirection</td>
<td>no</td>
<td>yes</td>
</tr>
<tr>
<td>Receives <code>SIGTERM</code> from <code>docker stop</code></td>
<td><strong>yes</strong></td>
<td><strong>usually not</strong></td>
</tr>
<tr>
<td>Requires a shell in the image</td>
<td>no (works on <code>distroless</code>/<code>scratch</code>)</td>
<td>yes</td>
</tr>
</tbody>
</table>
<p><strong>The signal problem, precisely:</strong> with shell form, PID 1 is <code>/bin/sh -c &quot;myapp&quot;</code> and your app is a child. <code>docker stop</code> sends <code>SIGTERM</code> to PID 1. A minimal <code>sh</code> does not forward signals to children, so your app never learns it should shut down; after the grace period (10 s by default) the kernel <code>SIGKILL</code>s everything. In-flight requests are dropped, buffers are not flushed, and in Kubernetes this shows up as failed rolling updates (Post 06).</p>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">CMD</span><span class="language-bash"> [<span class="hljs-string">&quot;node&quot;</span>, <span class="hljs-string">&quot;server.js&quot;</span>]        <span class="hljs-comment"># correct: node is PID 1, gets SIGTERM</span></span></span><br><span class="line"><span class="hljs-keyword">CMD</span><span class="language-bash"> node server.js               <span class="hljs-comment"># broken shutdowns</span></span></span><br><span class="line"><span class="hljs-keyword">CMD</span><span class="language-bash"> [<span class="hljs-string">&quot;sh&quot;</span>, <span class="hljs-string">&quot;-c&quot;</span>, <span class="hljs-string">&quot;exec node server.js&quot;</span>]   <span class="hljs-comment"># if you truly need shell expansion, `exec` replaces the shell</span></span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Common pitfall:</strong> applications that spawn children (a shell wrapper, a supervisor, a <code>npm start</code> chain) also need to reap zombies. Use <code>docker run --init</code> (or <code>tini</code> as the entrypoint) when your PID 1 is not a real init.</p>
</blockquote>
<h2 id="USER"><a href="#USER" class="headerlink" title="USER"></a><code>USER</code></h2>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">RUN</span><span class="language-bash"> addgroup -g 10001 app &amp;&amp; adduser -u 10001 -G app -D app</span></span><br><span class="line"><span class="hljs-keyword">USER</span> <span class="hljs-number">10001</span>:<span class="hljs-number">10001</span>            <span class="hljs-comment"># numeric: Kubernetes `runAsNonRoot` can verify it</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Applies to every subsequent <code>RUN</code> and to the container at run time. Prefer a numeric UID: a name resolves only if <code>/etc/passwd</code> in that image maps it, which <code>distroless</code> and <code>scratch</code> may not.</p>
<h2 id="HEALTHCHECK"><a href="#HEALTHCHECK" class="headerlink" title="HEALTHCHECK"></a><code>HEALTHCHECK</code></h2>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">HEALTHCHECK</span><span class="language-bash"> --interval=30s --<span class="hljs-built_in">timeout</span>=3s --start-period=10s --retries=3 \</span><br><span class="line">  CMD wget -qO- http://localhost:8080/healthz || <span class="hljs-built_in">exit</span> 1</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Exit 0 = healthy, 1 = unhealthy; <code>docker ps</code> shows the state and Compose's <code>condition: service_healthy</code> uses it (Post 02). <strong>Kubernetes ignores <code>HEALTHCHECK</code> entirely</strong> — it has its own probes (Post 06). Keep the check cheap and local: one that queries a database turns a dependency outage into a self-inflicted restart loop.</p>
<h2 id="LABEL"><a href="#LABEL" class="headerlink" title="LABEL"></a><code>LABEL</code></h2>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">LABEL</span><span class="language-bash"> org.opencontainers.image.source=<span class="hljs-string">&quot;https://github.com/acme/myapp&quot;</span> \</span><br><span class="line">      org.opencontainers.image.revision=<span class="hljs-string">&quot;<span class="hljs-variable">${BUILD_REV}</span>&quot;</span></span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Use the standard <code>org.opencontainers.image.*</code> keys — registries and scanners read them, and <code>image.source</code> links a package on GHCR back to its repository.</p>
<h2 id="VOLUME"><a href="#VOLUME" class="headerlink" title="VOLUME"></a><code>VOLUME</code></h2>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">VOLUME</span><span class="language-bash"> /var/lib/postgresql/data</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Declares that a path should be backed by a volume; without one mounted there, Docker creates an <strong>anonymous</strong> volume. Caveats: any <code>RUN</code> writing to that path <em>after</em> the <code>VOLUME</code> instruction is discarded, and every <code>docker run</code> leaves another anonymous volume behind. In application images, document the path instead and let Compose or Kubernetes mount it.</p>
<h1 id="Chapter-3-—-Build-cache-mechanics"><a href="#Chapter-3-—-Build-cache-mechanics" class="headerlink" title="Chapter 3 — Build cache mechanics"></a>Chapter 3 — Build cache mechanics</h1>
<h2 id="How-the-cache-decides"><a href="#How-the-cache-decides" class="headerlink" title="How the cache decides"></a>How the cache decides</h2>
<p>For each instruction the builder computes a cache key and looks for a matching existing layer:</p>
<ul>
<li><code>RUN</code> — the key is the <strong>command string</strong> (plus the parent layer). BuildKit does not know or care what the command actually did. <code>RUN apt-get update</code> will happily reuse a six-month-old package index.</li>
<li><code>COPY</code> / <code>ADD</code> — the key includes a <strong>checksum of the copied file contents and metadata</strong>. Change one byte of one copied file and this layer and every layer after it rebuild.</li>
<li>Metadata instructions — the key is the instruction text.</li>
</ul>
<p><strong>A cache miss cascades.</strong> Once one instruction misses, everything below it rebuilds, regardless of whether it would have hit on its own.</p>
<h2 id="The-canonical-ordering"><a href="#The-canonical-ordering" class="headerlink" title="The canonical ordering"></a>The canonical ordering</h2>
<p>Dependencies change rarely; source code changes constantly. So copy the dependency manifest first, install, and only then copy the source.</p>
<p><strong>Before — every code edit reinstalls every dependency:</strong></p>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">FROM</span> node:<span class="hljs-number">22</span>-alpine</span><br><span class="line"><span class="hljs-keyword">WORKDIR</span><span class="language-bash"> /app</span></span><br><span class="line"><span class="hljs-keyword">COPY</span><span class="language-bash"> . .                 <span class="hljs-comment"># ← any file change invalidates here</span></span></span><br><span class="line"><span class="hljs-keyword">RUN</span><span class="language-bash"> npm ci</span></span><br><span class="line"><span class="hljs-keyword">CMD</span><span class="language-bash"> [<span class="hljs-string">&quot;node&quot;</span>, <span class="hljs-string">&quot;server.js&quot;</span>]</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><strong>After — code edits reuse the install layer:</strong></p>
<pre><code class="language-dockerfile"><figure class="highlight dockerfile"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="dockerfile"><span class="line"><span class="hljs-keyword">FROM</span> node:<span class="hljs-number">22</span>-alpine</span><br><span class="line"><span class="hljs-keyword">WORKDIR</span><span class="language-bash"> /app</span></span><br><span class="line"><span class="hljs-keyword">COPY</span><span class="language-bash"> package.json package-lock.json ./   <span class="hljs-comment"># ← changes only when deps change</span></span></span><br><span class="line"><span class="hljs-keyword">RUN</span><span class="language-bash"> npm ci</span></span><br><span class="line"><span class="hljs-keyword">COPY</span><span class="language-bash"> . .                                 <span class="hljs-comment"># ← code changes land here, cheaply</span></span></span><br><span class="line"><span class="hljs-keyword">CMD</span><span class="language-bash"> [<span class="hljs-string">&quot;node&quot;</span>, <span class="hljs-string">&quot;server.js&quot;</span>]</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Measure the difference on your own project:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker build -t demo:before -f Dockerfile.before . &amp;&amp; <span class="hljs-built_in">touch</span> src/index.js</span><br><span class="line">time docker build -t demo:before -f Dockerfile.before .   <span class="hljs-comment"># full reinstall</span></span><br><span class="line">docker build -t demo:after  -f Dockerfile.after  . &amp;&amp; <span class="hljs-built_in">touch</span> src/index.js</span><br><span class="line">time docker build -t demo:after  -f Dockerfile.after  .   <span class="hljs-comment"># install layer CACHED</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Watch the build output: the reused steps print <code>CACHED</code>. On a dependency-heavy project the second rebuild typically drops from tens of seconds (or minutes) to a couple of seconds — the exact figures depend on your dependency tree, so record your own.</p>
<p>The same pattern elsewhere: copy <code>requirements.txt</code> before <code>pip install -r</code>; <code>pyproject.toml</code> + <code>poetry.lock</code>/<code>uv.lock</code> before <code>poetry install --no-root</code> or <code>uv sync --frozen</code>; <code>go.mod</code> + <code>go.sum</code> before <code>go mod download</code>; <code>Cargo.toml</code> + <code>Cargo.lock</code> before <code>cargo fetch</code>; <code>pom.xml</code> before <code>mvn -B dependency:go-offline</code>.</p>
<blockquote>
<p><strong>Trick:</strong> <code>npm ci</code> (not <code>npm install</code>) and <code>pip install --require-hashes</code> where possible. They fail loudly when the lockfile and the manifest disagree instead of silently resolving a different tree — which is what makes the cached layer trustworthy.</p>
</blockquote>

<h1 id="Chapter-4-—-dockerignore"><a href="#Chapter-4-—-dockerignore" class="headerlink" title="Chapter 4 — .dockerignore"></a>Chapter 4 — <code>.dockerignore</code></h1>
<p>The build context is everything the CLI hands to the builder. Without a <code>.dockerignore</code>, that includes <code>.git</code>, <code>node_modules</code>, build outputs, virtualenvs, and any stray database dump in the directory.</p>
<p>Three separate costs: <strong>transfer time</strong> (the context is packed and sent before instruction one runs), <strong>cache poisoning</strong> (<code>COPY . .</code> hashes everything in the context, so a <code>.git/index</code> that changes on every commit invalidates the copy layer and everything below it — the usual cause of builds that &quot;randomly&quot; stop hitting cache), and <strong>accidental inclusion</strong> (<code>.env</code>, <code>*.pem</code>, and full <code>.git</code> history shipped inside the image, readable by anyone who pulls it).</p>
<p>A workable starting point:</p>
<pre><code class="language-gitignore"><figure class="highlight gitignore"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span></pre></td><td class="code"><pre><code class="gitignore"><span class="line"><span class="hljs-comment"># .dockerignore</span></span><br><span class="line"><span class="hljs-string">.git</span></span><br><span class="line">node_modules</span><br><span class="line">dist</span><br><span class="line">build</span><br><span class="line">__pycache__</span><br><span class="line">*<span class="hljs-string">.pyc</span></span><br><span class="line"><span class="hljs-string">.venv</span></span><br><span class="line"><span class="hljs-string">.env</span></span><br><span class="line"><span class="hljs-string">.env.</span>*</span><br><span class="line">*<span class="hljs-string">.log</span></span><br><span class="line">coverage</span><br><span class="line"><span class="hljs-string">.pytest_cache</span></span><br><span class="line">Dockerfile*</span><br><span class="line">compose*<span class="hljs-string">.yaml</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Check the size of what you are actually sending:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-built_in">du</span> -sh .                                    <span class="hljs-comment"># everything on disk</span></span><br><span class="line">docker build -t ctx-test . 2&gt;&amp;1 | <span class="hljs-built_in">head</span> -2   <span class="hljs-comment"># BuildKit prints &quot;transferring context: … B&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Watch out:</strong> <code>.dockerignore</code> is not <code>.gitignore</code>. Files that git ignores are still in the build context unless <code>.dockerignore</code> also lists them. Keeping the two in sync is worth a moment of attention every time you add a build output directory.</p>

<h3 id="The-Alpine-caveats"><a href="#The-Alpine-caveats" class="headerlink" title="The Alpine caveats"></a>The Alpine caveats</h3>
<p>Alpine uses <strong>musl</strong> libc rather than glibc, which produces real differences:</p>
<ul>
<li><strong>Python</strong> wheels target <code>manylinux</code> (glibc), so on Alpine pip often compiles from source: slower builds, a toolchain dragged in, and frequently a <em>larger</em> image than <code>python:3.12-slim</code>. <code>musllinux</code> wheels exist but coverage is thinner.</li>
<li><strong>DNS resolution</strong> differs: musl's resolver has diverged from glibc on search-domain handling and parallel A/AAAA queries, and TCP fallback for large responses only arrived in musl 1.2.4. In Kubernetes, where discovery leans on <code>ndots</code> and search domains (Post 07), this is the classic &quot;works on Debian, flaky on Alpine&quot; bug.</li>
<li><strong>Native modules</strong> built against glibc will not run; anything with <code>CGO_ENABLED=1</code> or prebuilt <code>.so</code> files must be rebuilt.</li>
</ul>
<p>Alpine is excellent for statically linked Go and Rust binaries and for small utility images. For Python and for Node projects with native modules, <code>-slim</code> is usually the better default and distroless the better production endpoint.</p>

<h2 id="Reproducibility-and-digest-pinning"><a href="#Reproducibility-and-digest-pinning" class="headerlink" title="Reproducibility and digest pinning"></a>Reproducibility and digest pinning</h2>
<p>A tag is a mutable pointer. <code>python:3.12-slim</code> today and next month are different images. For anything you must be able to rebuild identically:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker pull python:3.12-slim</span><br><span class="line">docker inspect --format <span class="hljs-string">&#x27;{{index .RepoDigests 0}}&#x27;</span> python:3.12-slim</span><br><span class="line"><span class="hljs-comment"># python@sha256:1f2c…</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>FROM python:3.12-slim@sha256:1f2c...</code> then pins the exact bytes, forever.</p>
<p>Pair digest pinning with an automated updater (Dependabot, Renovate) so the pin is refreshed deliberately rather than drifting silently, and add lockfiles for language dependencies. The rule Post 03 formalises: <strong>tags for humans, digests for machines.</strong></p>

<h2 id="Exercise-1-—-Read-an-image"><a href="#Exercise-1-—-Read-an-image" class="headerlink" title="Exercise 1 — Read an image"></a>Exercise 1 — Read an image</h2>
<h2 id="Exercise-2-—-Fix-the-cache"><a href="#Exercise-2-—-Fix-the-cache" class="headerlink" title="Exercise 2 — Fix the cache"></a>Exercise 2 — Fix the cache</h2>
<p>Take the &quot;before&quot; Dockerfile from Chapter 3, rebuild after touching a source file, and record the time. Reorder it, rebuild the same way, and record again. Report both numbers and which steps printed <code>CACHED</code>.</p>
<details>
<summary>Solution</summary>
<p>Move <code>COPY package.json package-lock.json ./</code> + <code>RUN npm ci</code> above <code>COPY . .</code>, then:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">time docker build -t demo:after .          <span class="hljs-comment"># first build: full</span></span><br><span class="line"><span class="hljs-built_in">touch</span> src/index.js &amp;&amp; time docker build -t demo:after .</span><br><span class="line"><span class="hljs-comment"># the second build prints CACHED for COPY package*.json and RUN npm ci</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
</details>
<h2 id="Exercise-3-—-Signal-handling"><a href="#Exercise-3-—-Signal-handling" class="headerlink" title="Exercise 3 — Signal handling"></a>Exercise 3 — Signal handling</h2>
<p>Build two images from the same trivial Node/Python server, one with shell-form <code>CMD</code> and one with exec form. Start each, run <code>docker stop</code>, and time how long the stop takes. Explain the difference.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">time docker stop shellform     <span class="hljs-comment"># ≈ 10 s: SIGTERM never reaches the app, then SIGKILL</span></span><br><span class="line">time docker stop execform      <span class="hljs-comment"># sub-second, clean shutdown; exit code 0 rather than 137</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Fix: <code>CMD [&quot;node&quot;, &quot;server.js&quot;]</code>, or <code>CMD [&quot;sh&quot;,&quot;-c&quot;,&quot;exec node server.js&quot;]</code> if shell expansion is genuinely required.</p>
</details>
<h2 id="Exercise-4-—-Multi-stage-conversion"><a href="#Exercise-4-—-Multi-stage-conversion" class="headerlink" title="Exercise 4 — Multi-stage conversion"></a>Exercise 4 — Multi-stage conversion</h2>
<p>Convert a single-stage image of your own to multi-stage and record <code>docker images</code> sizes before and after. Confirm the runtime image ships no compiler: <code>docker run --rm &lt;image&gt; which gcc</code> should fail.</p>
<h2 id="Exercise-5-—-Secret-that-does-not-leak"><a href="#Exercise-5-—-Secret-that-does-not-leak" class="headerlink" title="Exercise 5 — Secret that does not leak"></a>Exercise 5 — Secret that does not leak</h2>
<p>Build an image that needs a token during <code>npm ci</code> (or <code>pip install</code> from a private index). Do it once with <code>ARG</code> and once with a BuildKit secret mount. Then try to recover the token from each image.</p>
<details>
<summary>Solution</summary>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="bash"><span class="line">docker build --build-arg TOKEN=hunter2 -t leaky .</span><br><span class="line">docker <span class="hljs-built_in">history</span> --no-trunc leaky | grep -i hunter2      <span class="hljs-comment"># found</span></span><br><span class="line"> </span><br><span class="line">docker build --secret <span class="hljs-built_in">id</span>=token,src=./token.txt -t safe .</span><br><span class="line">docker <span class="hljs-built_in">history</span> --no-trunc safe | grep -i hunter2       <span class="hljs-comment"># nothing</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
</details>
<h2 id="Exercise-6-—-Non-root-and-pinned"><a href="#Exercise-6-—-Non-root-and-pinned" class="headerlink" title="Exercise 6 — Non-root and pinned"></a>Exercise 6 — Non-root and pinned</h2>
<p>Rewrite one of your images to run as UID 10001 with <code>COPY --chown</code>, verify with <code>docker run --rm &lt;image&gt; id</code>, then pin its base by digest and confirm that <code>docker build --pull</code> no longer changes the base layer.</p>
