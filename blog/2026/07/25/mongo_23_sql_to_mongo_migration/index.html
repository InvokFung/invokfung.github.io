MongoDB Course — 23 · Migrating from SQL / Postgres to MongoDB

Created2026-07-25|Updated2026-07-25|Database > MongoDB
|Post View:

You have a Postgres / MySQL / Oracle workload. You want to move it to MongoDB — perhaps because the access pattern is document-shaped, the schema is changing too fast for migrations, or scaling write throughput requires sharding. The migration is half schema redesign, half data movement, half cut-over choreography. This post is the playbook: schema-mapping principles, data-load tooling (mongoimport, AWS DMS, Striim, custom ETL), dual-write strategies, staged cut-over, rollback plan, and the common traps.

Series map: 20 Outbox → 21 CQRS+ES → 22 RAG → 23 SQL→Mongo migration (this post) → 24 Kafka + Debezium → … → 29 K8s + mongosync + cost.

Learning Outcome

  • Decide whether the workload should move at all (and which parts).
  • Map relational schema to document model using Post 07's patterns.
  • Choose a data-movement strategy (full reload, dual-write, change-data-capture).
  • Implement the staged cut-over with rollback gates.
  • Avoid the 6 most common migration disasters.

Chapter 1 — Should you migrate?

Honest answer first: most SQL workloads should stay on SQL. Migration is expensive + risky. Strong reasons to move:

  • Schema flexibility required (per-tenant custom fields, fast product iteration, polymorphic items).
  • Write throughput beyond what Postgres can vertical-scale.
  • Hierarchical / document-shaped data (forms, content, configs, complex products) that's painful to join.
  • Horizontal scaling + multi-region + sharding required.
  • Operational simplicity at low ops headcount (Atlas managed > self-hosted Postgres cluster).

Weak reasons:

  • "NoSQL is modern."
  • "We want to avoid joins" (you'll write joins as $lookup either way).
  • "We need higher performance" (often a Postgres index would have fixed it).

Often the right answer is migrate a subset — the parts where the document model genuinely fits — and keep the rest in Postgres. The two coexist via outbox / CDC / app-side composition.

Chapter 3 — Data movement strategies

Pick by downtime tolerance + data size + complexity tolerance.

Strategy A — Full reload (hours of downtime)

  1. Freeze writes to source.
  2. Extract source → transform → load into Mongo.
  3. Cut DNS / connection string over.
  4. Resume writes against Mongo.

OK for: < 100 GB and you can take a maintenance window.

Strategy B — Dual-write at app layer (low downtime)

  1. App writes to both Postgres + Mongo for new operations.
  2. Backfill historical data via ETL.
  3. Read-shadow: in parallel with reads from Postgres, fetch from Mongo + log differences.
  4. Switch reads to Mongo when shadow shows parity.
  5. Stop writes to Postgres.

OK for: medium-size apps where you control the write path.

Strategy C — CDC-driven (best for large, can't-downtime)

  1. Tail Postgres WAL via Debezium (or AWS DMS, Striim, Estuary, Airbyte).
  2. Transform + write to Mongo continuously.
  3. After sync catches up + remains in sync for a while, cut reads over.
  4. After cut-over, drain Postgres writes; flip back-flow off.

OK for: large databases, strict uptime requirements, polyglot teams.

Strategy D — Strangler fig

  • New features write to Mongo only.
  • Old features stay on Postgres.
  • Migrate one feature at a time over months.

OK for: legacy systems where a big-bang move is too risky.

AWS DMS (Database Migration Service)

Continuously replicates Postgres / MySQL / Oracle / SQL Server → MongoDB Atlas. Configurable transformations (rename columns, denormalise child rows into arrays via "JSON-encoded selectors").

Pros: managed; one of the easiest CDC paths to Atlas. Cons: AWS-only; transformations limited.

Debezium + Kafka + Mongo Kafka Sink Connector

Debezium reads Postgres WAL → Kafka → MongoDB Kafka Connector applies events to Atlas. Most flexible (any transformations via Kafka Streams). More moving parts.

Chapter 5 — Dual-write strategy walk-through

Properties:

  • Postgres is still source of truth — Mongo failures don't break the user request.
  • Mongo writes are idempotent (linked by pg_id) — re-runnable.
  • Backfill script picks up rows in Postgres not yet in Mongo.

Read-shadow phase

Run for days/weeks until diffs are rare + understood. Then flip reads to Mongo for some endpoints; eventually all.

Chapter 6 — Staged cut-over (CDC strategy)

Gates between steps: error budget; latency budget; data-parity assertions. Don't proceed without crossing them.

Rollback plan at each gate:

  • T3-T4: trivial — route reads back to Postgres.
  • T5: still possible — Postgres data is fresh until T6.
  • T6+: harder — need reverse CDC or accept the cut.

Chapter 7 — Validation

After load (or continuously during CDC):

Automate. Run in CI. Alert on regressions.

For large collections use statistical sampling + checksums per shard / per day rather than full equality.

Chapter 8 — Application-layer changes

The migration isn't just data movement — your code changes too.

SQL idiom MongoDB equivalent
JOIN embed first; $lookup only when must
WHERE x IN (subquery) $lookup + $match or 2-step query
GROUP BY + window functions $group + $setWindowFields
ORDER BY + LIMIT + OFFSET sort + skip (small) or range pagination (big)
Transactions across many tables rethink with single-doc atomicity + embedded data first
Stored procedures service-layer code
Triggers change streams
Views aggregation pipelines + $merge materialised views
LIKE '%x%' text index, regex (left-anchored), Atlas Search
ORMs Mongoose / Beanie / Prisma / official driver

Plan the code refactor in parallel with the data move. Don't try to make Mongo behave like Postgres — you'll get worst of both.

Chapter 9 — Common pitfalls

Pitfall Cause Fix
Lift-and-shift schema one Mongo collection per SQL table redesign for document shape
50 $lookups per request over-normalised denormalise / embed
ObjectId vs numeric ID mismatch app expects integer keep numeric IDs during transition
Date type conversion fails timezone / format inconsistencies normalise to ISO 8601 UTC
Foreign-key constraints lost silently Mongo doesn't enforce app-layer validation + tests
Sequence ID gaps new ObjectIds vs SERIAL use new sequence or rely on ObjectId ordering
Migration script OOM on big tables not batching chunk + checkpoint
Forgot indexes on Mongo full collection scans in prod create indexes BEFORE traffic
CDC lag during big writes undersized destination scale Atlas tier before cut-over
No rollback plan got stuck after T6 dual-write until you're 100% sure
Bigger bill than expected wrong tier sizing benchmark + size with safety margin

Chapter 10 — Rollback patterns

If Mongo turns out wrong (worse perf, missing feature, business decision change):

  • During dual-write window: trivial. Switch back, drop Mongo data.
  • After cut-over but Mongo still has CDC back to Postgres: route reads back to Postgres, stop write CDC, keep Mongo as warm standby until decision.
  • After full cut: you need a reverse migration. Same playbook, opposite direction. Cost as much as the original.

Plan rollback explicitly before T0. Document the decision points.

Practice Exercises

Exercise 1 — Schema mapping

Take a Postgres schema you know (e.g., from a previous project). Map to Mongo collections following Post 07. Note which tables embed and which stay as references.

Exercise 2 — mongoimport

Export one table to CSV from Postgres. mongoimport into Mongo. Verify counts + spot-check.

Exercise 3 — Dual-write

Implement Chapter 5's create_order dual-write. Insert 1000 orders; confirm both DBs have them. Kill Mongo connectivity mid-test; confirm Postgres still works + Mongo is backfillable.

Exercise 4 — Read-shadow

Implement the shadow comparator. Run 1000 reads; surface diffs. Fix any.

Exercise 5 — CDC PoC

Set up Debezium reading from a local Postgres into Kafka. Configure a Mongo sink. Insert into Postgres; see in Mongo within seconds. (Detailed walkthrough in Post 24.)
