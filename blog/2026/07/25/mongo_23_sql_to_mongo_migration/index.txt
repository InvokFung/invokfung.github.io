You want to move it to MongoDB — perhaps because the access pattern is document-shaped, the schema is changing too fast for migrations, or scaling write throughput requires sharding. This post is the playbook: schema-mapping principles, data-load tooling (mongoimport, AWS DMS, Striim, custom ETL), dual-write strategies, staged cut-over, rollback plan, and the common traps.</p>

<h1 id="Chapter-1-—-Should-you-migrate"><a href="#Chapter-1-—-Should-you-migrate" class="headerlink" title="Chapter 1 — Should you migrate?"></a>Chapter 1 — Should you migrate?</h1>
<p>Honest answer first: most SQL workloads should stay on SQL. Migration is expensive + risky. Strong reasons to move:</p>
<ul>
<li><strong>Schema flexibility</strong> required (per-tenant custom fields, fast product iteration, polymorphic items).</li>
<li><strong>Write throughput</strong> beyond what Postgres can vertical-scale.</li>
<li><strong>Hierarchical / document-shaped data</strong> (forms, content, configs, complex products) that's painful to join.</li>
<li><strong>Horizontal scaling</strong> + multi-region + sharding required.</li>
<li><strong>Operational simplicity</strong> at low ops headcount (Atlas managed &gt; self-hosted Postgres cluster).</li>
</ul>
<p>Weak reasons:</p>
<ul>
<li>&quot;NoSQL is modern.&quot;</li>
<li>&quot;We want to avoid joins&quot; (you'll write joins as <code>$lookup</code> either way).</li>
<li>&quot;We need higher performance&quot; (often a Postgres index would have fixed it).</li>
</ul>
<p>Often the right answer is <strong>migrate a subset</strong> — the parts where the document model genuinely fits — and keep the rest in Postgres. The two coexist via outbox / CDC / app-side composition.</p>

<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// one collection, denormalised</span></span><br><span class="line">orders {</span><br><span class="line">  _id, user_id,</span><br><span class="line">  <span class="hljs-attr">user_email_at_order</span>: <span class="hljs-string">&quot;...&quot;</span>,          <span class="hljs-comment">// extended reference</span></span><br><span class="line">  status, total, created_at,</span><br><span class="line">  <span class="hljs-attr">items</span>: [</span><br><span class="line">    { <span class="hljs-attr">p</span>: product_id, <span class="hljs-attr">name_at_order</span>: <span class="hljs-string">&quot;...&quot;</span>, <span class="hljs-attr">price_at_order</span>: ..., <span class="hljs-attr">qty</span>: ... }</span><br><span class="line">  ]</span><br><span class="line">}</span><br><span class="line">users { _id, name, email }</span><br><span class="line">products { _id, name, sku, price }</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Chapter-3-—-Data-movement-strategies"><a href="#Chapter-3-—-Data-movement-strategies" class="headerlink" title="Chapter 3 — Data movement strategies"></a>Chapter 3 — Data movement strategies</h1>
<p>Pick by downtime tolerance + data size + complexity tolerance.</p>
<h3 id="Strategy-A-—-Full-reload-hours-of-downtime"><a href="#Strategy-A-—-Full-reload-hours-of-downtime" class="headerlink" title="Strategy A — Full reload (hours of downtime)"></a>Strategy A — Full reload (hours of downtime)</h3>
<ol>
<li>Freeze writes to source.</li>
<li>Extract source → transform → load into Mongo.</li>
<li>Cut DNS / connection string over.</li>
<li>Resume writes against Mongo.</li>
</ol>
<p>OK for: &lt; 100 GB and you can take a maintenance window.</p>
<h3 id="Strategy-B-—-Dual-write-at-app-layer-low-downtime"><a href="#Strategy-B-—-Dual-write-at-app-layer-low-downtime" class="headerlink" title="Strategy B — Dual-write at app layer (low downtime)"></a>Strategy B — Dual-write at app layer (low downtime)</h3>
<ol>
<li>App writes to <strong>both</strong> Postgres + Mongo for new operations.</li>
<li>Backfill historical data via ETL.</li>
<li>Read-shadow: in parallel with reads from Postgres, fetch from Mongo + log differences.</li>
<li>Switch reads to Mongo when shadow shows parity.</li>
<li>Stop writes to Postgres.</li>
</ol>
<p>OK for: medium-size apps where you control the write path.</p>
<h3 id="Strategy-C-—-CDC-driven-best-for-large-cant-downtime"><a href="#Strategy-C-—-CDC-driven-best-for-large-cant-downtime" class="headerlink" title="Strategy C — CDC-driven (best for large, can't-downtime)"></a>Strategy C — CDC-driven (best for large, can't-downtime)</h3>
<ol>
<li>Tail Postgres WAL via <strong>Debezium</strong> (or AWS DMS, Striim, Estuary, Airbyte).</li>
<li>Transform + write to Mongo continuously.</li>
<li>After sync catches up + remains in sync for a while, cut reads over.</li>
<li>After cut-over, drain Postgres writes; flip back-flow off.</li>
</ol>
<p>OK for: large databases, strict uptime requirements, polyglot teams.</p>
<h3 id="Strategy-D-—-Strangler-fig"><a href="#Strategy-D-—-Strangler-fig" class="headerlink" title="Strategy D — Strangler fig"></a>Strategy D — Strangler fig</h3>
<ul>
<li>New features write to Mongo only.</li>
<li>Old features stay on Postgres.</li>
<li>Migrate one feature at a time over months.</li>
</ul>
<p>OK for: legacy systems where a big-bang move is too risky.</p>

<h1 id="Chapter-6-—-Staged-cut-over-CDC-strategy"><a href="#Chapter-6-—-Staged-cut-over-CDC-strategy" class="headerlink" title="Chapter 6 — Staged cut-over (CDC strategy)"></a>Chapter 6 — Staged cut-over (CDC strategy)</h1>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="text"><span class="line">T0  — CDC pipeline live; replicating writes from Postgres to Mongo</span><br><span class="line">T1  — Backfill historical data complete (script ran once)</span><br><span class="line">T2  — Validate parity (row counts + sampled deep-equals + queries return same answers)</span><br><span class="line">T3  — Read traffic split: 1% → Mongo, 99% → Postgres</span><br><span class="line">T4  — Slowly raise % to Mongo; watch error rates + latency</span><br><span class="line">T5  — 100% reads on Mongo; still dual-writing (or CDC still active)</span><br><span class="line">T6  — Stop writes to Postgres; CDC drained; cut over</span><br><span class="line">T7  — Postgres becomes read-only / archive</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Gates between steps: error budget; latency budget; data-parity assertions. Don't proceed without crossing them.</p>
<p>Rollback plan at each gate:</p>
<ul>
<li>T3-T4: trivial — route reads back to Postgres.</li>
<li>T5: still possible — Postgres data is fresh until T6.</li>
<li>T6+: harder — need reverse CDC or accept the cut.</li>
</ul>

<h1 id="Chapter-10-—-Rollback-patterns"><a href="#Chapter-10-—-Rollback-patterns" class="headerlink" title="Chapter 10 — Rollback patterns"></a>Chapter 10 — Rollback patterns</h1>
<p>If Mongo turns out wrong (worse perf, missing feature, business decision change):</p>
<ul>
<li><strong>During dual-write window</strong>: trivial. Switch back, drop Mongo data.</li>
<li><strong>After cut-over but Mongo still has CDC back to Postgres</strong>: route reads back to Postgres, stop write CDC, keep Mongo as warm standby until decision.</li>
<li><strong>After full cut</strong>: you need a reverse migration. Same playbook, opposite direction. Cost as much as the original.</li>
</ul>
<p><strong>Plan rollback explicitly</strong> before T0. Document the decision points.</p>

<p>Implement the shadow comparator. Run 1000 reads; surface diffs. Fix any.</p>
<h2 id="Exercise-5-—-CDC-PoC"><a href="#Exercise-5-—-CDC-PoC" class="headerlink" title="Exercise 5 — CDC PoC"></a>Exercise 5 — CDC PoC</h2>
<p>Set up Debezium reading from a local Postgres into Kafka. Configure a Mongo sink. Insert into Postgres; see in Mongo within seconds. (Detailed walkthrough in Post 24.)</p>
