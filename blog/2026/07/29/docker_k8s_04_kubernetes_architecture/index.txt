11:T11c60,<p>Posts 00-03 covered a single machine: how a container is built out of namespaces and cgroups, how images are layered, how Compose wires a handful of containers together on one host, and how the supply chain around images is secured. This post crosses the boundary from <strong>one host</strong> to <strong>a fleet</strong>. <h1 id="Chapter-1-—-The-problem-Kubernetes-solves-and-when-you-do-not-need-it"><a href="#Chapter-1-—-The-problem-Kubernetes-solves-and-when-you-do-not-need-it" class="headerlink" title="Chapter 1 — The problem Kubernetes solves (and when you do not need it)"></a>Chapter 1 — The problem Kubernetes solves (and when you do not need it)</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Orchestrator</strong> — a system that decides <em>which</em> container runs <em>where</em>, restarts it when it dies, and keeps its identity on the network stable while the underlying process moves.</li>
<li><strong>Desired state</strong> — a declaration of what the cluster should look like, stored in the API server. <strong>Actual state</strong> — what is really running, as reported by the nodes.</li>
<li><strong>Reconciliation</strong> — the continuous work of shrinking the gap between the two.</li>
<li><strong>Controller</strong> — a process whose entire job is one reconciliation loop for one kind of object.</li>
<li><strong>Node</strong> — a machine that runs workloads. <strong>Control plane</strong> — the components that store desired state and drive reconciliation.</li>
</ul>
<h2 id="What-breaks-at-fleet-scale"><a href="#What-breaks-at-fleet-scale" class="headerlink" title="What breaks at fleet scale"></a>What breaks at fleet scale</h2>
<p>Compose (Post 02) works beautifully on a single host and stops working the moment you need any of the following:</p>

<p>The common thread is <strong>convergence</strong>. Every one of those is &quot;keep reality matching a description&quot;, which is exactly the loop Kubernetes implements once and reuses for everything.</p>
<h2 id="When-you-do-not-need-Kubernetes"><a href="#When-you-do-not-need-Kubernetes" class="headerlink" title="When you do not need Kubernetes"></a>When you do not need Kubernetes</h2>
<p>This deserves to be said plainly, because the cost of Kubernetes is real: a control plane to run or pay for, a YAML surface area to learn, an upgrade treadmill roughly every four months, and an on-call rotation that now has to understand a distributed system underneath the application.</p>
<p>Do <strong>not</strong> reach for Kubernetes when:</p>
<ul>
<li>You run <strong>one or two services on one or two machines</strong> and a few minutes of downtime is acceptable. Compose plus a systemd unit and a restart policy is genuinely simpler and genuinely reliable.</li>
<li>Your workload is <strong>bursty and stateless</strong> — a managed serverless or PaaS runtime (Cloud Run, Fargate, App Runner, Fly, Render) removes the entire operational tier.</li>
<li>You have <strong>no platform owner</strong>. Kubernetes without someone responsible for it degrades into an unpatched cluster running a version nobody dares upgrade.</li>
<li>The team is <strong>three engineers shipping a product</strong>. The orchestration you save is smaller than the orchestration you acquire.</li>
</ul>
<p>Reach for Kubernetes when you have many services, more than one team deploying, an existing cluster to piggyback on, an on-prem or sovereign requirement, or a genuine need for the ecosystem (operators, service mesh, policy engines) built on its API.</p>
<blockquote>
<p><strong>Watch out:</strong> &quot;we might need to scale later&quot; is not a reason to adopt Kubernetes today. Migrating a containerised app onto Kubernetes later is a bounded, well-trodden project. Running a cluster you do not need for two years is not.</p>
</blockquote>

<h1 id="Chapter-2-—-The-declarative-model-and-the-control-loop"><a href="#Chapter-2-—-The-declarative-model-and-the-control-loop" class="headerlink" title="Chapter 2 — The declarative model and the control loop"></a>Chapter 2 — The declarative model and the control loop</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Declarative</strong> — you describe the end state; the system works out the transitions.</li>
<li><strong>Imperative</strong> — you issue the transitions yourself.</li>
<li><strong>Level-triggered</strong> — the loop acts on the <em>current</em> difference between desired and actual, not on the <em>event</em> that caused it.</li>
<li><strong>Idempotent</strong> — applying the same declaration twice has the same effect as applying it once.</li>
</ul>
<h2 id="The-loop"><a href="#The-loop" class="headerlink" title="The loop"></a>The loop</h2>
<p>Every controller in Kubernetes runs, conceptually, this:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="text"><span class="line">loop forever:</span><br><span class="line">    desired  = read objects from the API server</span><br><span class="line">    actual   = observe the world</span><br><span class="line">    diff     = desired − actual</span><br><span class="line">    if diff is non-empty:</span><br><span class="line">        take one step to shrink diff</span><br><span class="line">        record what happened in .status</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>That is the whole idea. The Deployment controller does it for &quot;how many Pods of this template exist&quot;. The Node controller does it for &quot;which nodes are healthy&quot;. A cert-manager controller does it for &quot;does a valid certificate exist for this hostname&quot;. Your own operator, if you write one, does it for whatever domain object you invent.</p>
<p>Two consequences fall out of this, and both matter daily:</p>
<ol>
<li><strong><code>kubectl apply</code> is a statement of intent, not a command.</strong> It writes your desired state into etcd and returns. It does <em>not</em> mean the thing happened. <code>kubectl apply</code> succeeding tells you the API server accepted and persisted a valid object. Whether a Pod ever actually started is a separate question answered by <code>.status</code>, by events, and by <code>kubectl rollout status</code>. Beginners read &quot;deployment.apps/web configured&quot; as success and are then baffled that nothing runs. It is a receipt for a <em>request</em>, not a <em>result</em>.</li>
<li><strong>The loop is level-triggered, so it self-heals.</strong> Delete a Pod that a Deployment owns and a new one appears, because the controller does not remember that it created three Pods — it counts and finds two. Miss a webhook event, restart a controller, lose a message: the next pass recomputes from scratch. This is why Kubernetes tolerates its own components crashing.</li>
</ol>
<h2 id="Spec-versus-status"><a href="#Spec-versus-status" class="headerlink" title="Spec versus status"></a>Spec versus status</h2>
<p><code>spec</code> is written by you and holds the intent. <code>status</code> is written by the controller and holds the observation (<code>replicas</code>, <code>readyReplicas</code>, <code>observedGeneration</code>, <code>conditions</code>). Never write <code>status</code> by hand; read it constantly.</p>
<blockquote>
<p><strong>Trick:</strong> <code>kubectl get &lt;kind&gt; &lt;name&gt; -o yaml</code> and read <code>.status</code> before you open any dashboard. It is the controller telling you, in its own words, what it thinks is true.</p>
</blockquote>

<h1 id="Chapter-5-—-Pods-ReplicaSets-and-Deployments"><a href="#Chapter-5-—-Pods-ReplicaSets-and-Deployments" class="headerlink" title="Chapter 5 — Pods, ReplicaSets and Deployments"></a>Chapter 5 — Pods, ReplicaSets and Deployments</h1>
<h2 id="Why-the-Pod-not-the-container"><a href="#Why-the-Pod-not-the-container" class="headerlink" title="Why the Pod, not the container"></a>Why the Pod, not the container</h2>
<p>A <strong>Pod</strong> is one or more containers that are scheduled together, share a network namespace and an IP address, can share volumes, and live and die as a unit. It is the smallest thing Kubernetes schedules.</p>
<p>The reason for the extra layer is that some containers are genuinely useless alone. A log shipper that tails <code>/var/log/app</code> must be on the same filesystem as the app. A proxy that terminates mTLS for the app must be on the same network stack as the app. Making the <em>group</em> the schedulable unit means those helpers can be separate images with separate lifecycles and still be guaranteed co-location.</p>
<h2 id="What-is-shared"><a href="#What-is-shared" class="headerlink" title="What is shared"></a>What is shared</h2>
<ul>
<li><strong>Network namespace</strong> — every container in the Pod sees the same interfaces and the same IP. They reach each other over <code>localhost</code>, and they <strong>must not</strong> bind the same port. This is the most common Pod authoring bug: two containers both listening on 8080.</li>
<li><strong>IPC namespace and hostname.</strong></li>
<li><strong>Volumes</strong> — declared at Pod level, mounted independently in each container.</li>
</ul>
<p>Not shared by default: the <strong>filesystem</strong> (each container keeps its own image root) and the <strong>PID namespace</strong> (opt in with <code>shareProcessNamespace: true</code>).</p>

<h2 id="Sidecars-—-including-the-native-kind"><a href="#Sidecars-—-including-the-native-kind" class="headerlink" title="Sidecars — including the native kind"></a>Sidecars — including the native kind</h2>
<p>Historically a &quot;sidecar&quot; was just a second entry in <code>containers:</code>, and it had two well-known defects: it could start <em>after</em> the app container needed it, and in a Job it would keep running forever after the main container exited, so the Job never completed.</p>
<p>Kubernetes solved this by giving init containers a <code>restartPolicy: Always</code>, which turns them into <strong>native sidecars</strong>: they start in init order (so before the app), they keep running alongside it, and they are terminated automatically after the app containers exit. The feature was alpha in <strong>1.28</strong>, beta and on by default in <strong>1.29</strong>, and graduated to <strong>stable in Kubernetes 1.33</strong>.</p>

<h2 id="You-almost-never-write-a-bare-Pod"><a href="#You-almost-never-write-a-bare-Pod" class="headerlink" title="You almost never write a bare Pod"></a>You almost never write a bare Pod</h2>
<p>A Pod on its own is not rescheduled if its node dies. Write a Deployment, StatefulSet, DaemonSet, or Job — all of which manage Pods for you. Bare Pods are for debugging (<code>kubectl run -it --rm debug --image=busybox -- sh</code>).</p>
<h2 id="ReplicaSet"><a href="#ReplicaSet" class="headerlink" title="ReplicaSet"></a>ReplicaSet</h2>
<p>A ReplicaSet has exactly one job: <em>ensure N Pods matching this selector exist</em>. It counts, and it creates or deletes to close the gap. You rarely write one directly.</p>
<h2 id="Deployment"><a href="#Deployment" class="headerlink" title="Deployment"></a>Deployment</h2>
<p>A Deployment manages ReplicaSets to provide <strong>versioned, controlled rollouts</strong>. Change the Pod template and the Deployment controller creates a <em>new</em> ReplicaSet, scales it up while scaling the old one down, and keeps the old one around at zero replicas so you can roll back.</p>

<h1 id="Chapter-6-—-Services-kube-proxy-and-DNS"><a href="#Chapter-6-—-Services-kube-proxy-and-DNS" class="headerlink" title="Chapter 6 — Services, kube-proxy and DNS"></a>Chapter 6 — Services, kube-proxy and DNS</h1>
<p>Pods are mortal and their IPs are ephemeral. A <strong>Service</strong> is a stable virtual IP plus a DNS name in front of a label-selected set of Pods.</p>
<h2 id="The-four-types"><a href="#The-four-types" class="headerlink" title="The four types"></a>The four types</h2>

<h2 id="How-kube-proxy-implements-it"><a href="#How-kube-proxy-implements-it" class="headerlink" title="How kube-proxy implements it"></a>How kube-proxy implements it</h2>
<p>A Service IP is not owned by any interface — nothing is listening on it. kube-proxy watches Services and EndpointSlices and programs the node's networking so that packets addressed to the virtual IP are rewritten to a real Pod IP:</p>
<ul>
<li><strong>iptables mode</strong> (long-standing default) — NAT rules with probabilistic jumps. Simple and robust, but rule count grows with Service × endpoint count, so very large clusters see slow reprogramming.</li>
<li><strong>IPVS mode</strong> — kernel load balancing with hash tables: better at scale, real scheduling algorithms.</li>
<li><strong>nftables mode</strong> — the modern replacement for the iptables backend, fixing its scaling behaviour; the direction of travel.</li>
<li><strong>eBPF datapaths</strong> (Cilium and friends) can replace kube-proxy entirely.</li>
</ul>
<p>The decision is made <strong>per connection</strong>, in the kernel, on the client's node — no hop through a central box. It is also L4 only, so long-lived HTTP/2 or gRPC connections pin to one backend and will <em>not</em> rebalance. For L7 balancing you need an Ingress, a Gateway, or a mesh (Post 07).</p>
<h2 id="Headless-Services-and-DNS"><a href="#Headless-Services-and-DNS" class="headerlink" title="Headless Services and DNS"></a>Headless Services and DNS</h2>
<p>Set <code>clusterIP: None</code> and you get a <strong>headless Service</strong>: no virtual IP, no kube-proxy rules. DNS instead returns the <strong>A/AAAA records of every ready Pod</strong>. This is how clients that want to see individual members — database replica sets, Kafka, anything doing its own peer discovery — find them, and it is the backbone of StatefulSets (Post 05).</p>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">apiVersion:</span> <span class="hljs-string">v1</span></span><br><span class="line"><span class="hljs-attr">kind:</span> <span class="hljs-string">Service</span></span><br><span class="line"><span class="hljs-attr">metadata:</span> { <span class="hljs-attr">name:</span> <span class="hljs-string">pg</span> }</span><br><span class="line"><span class="hljs-attr">spec:</span></span><br><span class="line">  <span class="hljs-attr">clusterIP:</span> <span class="hljs-string">None</span></span><br><span class="line">  <span class="hljs-attr">selector:</span> { <span class="hljs-attr">app:</span> <span class="hljs-string">pg</span> }</span><br><span class="line">  <span class="hljs-attr">ports:</span> [{ <span class="hljs-attr">port:</span> <span class="hljs-number">5432</span>, <span class="hljs-attr">name:</span> <span class="hljs-string">postgres</span> }]</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="text"><span class="line">&lt;service&gt;.&lt;namespace&gt;.svc.cluster.local          # Service</span><br><span class="line">web.shop.svc.cluster.local</span><br><span class="line"> </span><br><span class="line">&lt;pod-hostname&gt;.&lt;service&gt;.&lt;namespace&gt;.svc.cluster.local   # headless Service member</span><br><span class="line">pg-0.pg.shop.svc.cluster.local</span><br><span class="line"> </span><br><span class="line">_&lt;port-name&gt;._&lt;protocol&gt;.&lt;service&gt;.&lt;namespace&gt;.svc.cluster.local   # SRV record</span><br><span class="line">_postgres._tcp.pg.shop.svc.cluster.local</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

Prefer <code>web.shop</code> in configuration — the bare name silently changes meaning when the manifest is applied to a different namespace. Check any of it with <code>kubectl run -it --rm dns --image=busybox:1.36 --restart=Never -- nslookup web.shop.svc.cluster.local</code>.</p>

<h2 id="Namespaces"><a href="#Namespaces" class="headerlink" title="Namespaces"></a>Namespaces</h2>
<p>A namespace is a scope for names, plus a natural attachment point for quotas (ResourceQuota, LimitRange) and permissions (RBAC, Post 07). It is a <strong>soft</strong> boundary: by default all Pods in all namespaces can reach each other over the Pod network. Real isolation needs NetworkPolicy (Post 07).</p>

<h2 id="Imperative-to-declarative-—-the-workflow-that-actually-works"><a href="#Imperative-to-declarative-—-the-workflow-that-actually-works" class="headerlink" title="Imperative to declarative — the workflow that actually works"></a>Imperative to declarative — the workflow that actually works</h2>
<p>Writing YAML from memory is slow and error-prone. Generate it, then own it.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># Generate a Deployment manifest without touching the cluster:</span></span><br><span class="line">kubectl create deployment web --image=ghcr.io/example/web:1.4.2 \</span><br><span class="line">  --replicas=3 --dry-run=client -o yaml &gt; k8s/web-deployment.yaml</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># Generate the matching Service:</span></span><br><span class="line">kubectl create service clusterip web --tcp=80:8080 \</span><br><span class="line">  --dry-run=client -o yaml &gt; k8s/web-service.yaml</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment"># Edit, commit, then apply the directory:</span></span><br><span class="line">kubectl apply -f k8s/ -R</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>--dry-run=client</code> renders locally and never contacts the API server. <code>--dry-run=server</code> sends the object through authentication, admission control and validation but does not persist it — that is the one to use when you want to know whether a policy engine (Post 07) will reject your manifest.</p>
<blockquote>
<p><strong>Common pitfall:</strong> <code>kubectl edit</code> and <code>kubectl scale</code> change the live cluster and nothing else. The next <code>kubectl apply</code> from your repository silently reverts them, and with GitOps (Post 07) the reversal happens within seconds. Treat imperative commands as debugging tools, and put every intentional change in the repository.</p>
</blockquote>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Stand-up-a-cluster-and-read-it"><a href="#Exercise-1-—-Stand-up-a-cluster-and-read-it" class="headerlink" title="Exercise 1 — Stand up a cluster and read it"></a>Exercise 1 — Stand up a cluster and read it</h2>

<p>Deploy three replicas of any image. Then delete one Pod by name and time how long a replacement takes to become Ready. Then delete the ReplicaSet with <code>--cascade=orphan</code> and observe what happens to the Pods and what the Deployment controller does next.</p>

<h2 id="Exercise-4-—-Selector-surgery"><a href="#Exercise-4-—-Selector-surgery" class="headerlink" title="Exercise 4 — Selector surgery"></a>Exercise 4 — Selector surgery</h2>
<p>Create a Deployment <code>web</code> (label <code>app=web</code>) and a ClusterIP Service selecting <code>app=web</code>. Then:</p>
<ol>
<li>Add a second, unrelated Pod with the label <code>app=web</code> and confirm the Service starts sending traffic to it.</li>
<li>Change one Pod's label to <code>app=web-canary</code> and watch it leave the Service's EndpointSlice.</li>
<li>Explain what this implies about labels as a security boundary.</li>
</ol>
<h2 id="Exercise-5-—-DNS-tour"><a href="#Exercise-5-—-DNS-tour" class="headerlink" title="Exercise 5 — DNS tour"></a>Exercise 5 — DNS tour</h2>
<p>From a debug Pod in namespace <code>a</code>, resolve a Service in namespace <code>b</code> by short name, by <code>&lt;svc&gt;.&lt;ns&gt;</code> and by FQDN. Then create a headless Service in front of a 3-replica Deployment and compare <code>nslookup</code> output against the ClusterIP version. Record which form returns one address and which returns many.</p>
<h2 id="Exercise-6-—-Imperative-to-declarative"><a href="#Exercise-6-—-Imperative-to-declarative" class="headerlink" title="Exercise 6 — Imperative to declarative"></a>Exercise 6 — Imperative to declarative</h2>
<p>Build the following with imperative commands only, using <code>--dry-run=client -o yaml</code> to capture each object into <code>k8s/</code>: a Deployment of 2 replicas, a ClusterIP Service, and a namespace. Then delete the namespace entirely and rebuild the whole thing with a single <code>kubectl apply -f k8s/ -R</code>. Diff the recreated objects against the originals and explain every field that differs.</p>
<h2 id="Exercise-7-—-Failure-injection-on-the-control-plane"><a href="#Exercise-7-—-Failure-injection-on-the-control-plane" class="headerlink" title="Exercise 7 — Failure injection on the control plane"></a>Exercise 7 — Failure injection on the control plane</h2>
<p>On a kind cluster, stop the <code>kube-scheduler</code> container on the control-plane node, create a Deployment, and observe the Pods. Restart the scheduler. Record what state the Pods sat in and whether existing workloads were affected.</p>

<h1 id="Cheat-sheet"><a href="#Cheat-sheet" class="headerlink" title="Cheat-sheet"></a>Cheat-sheet</h1>

<th>What</th>
<th>How</th>

<td>many services, multiple teams, existing cluster, on-prem requirement — otherwise probably not</td>

<td>declarative desired state + level-triggered reconciliation loops</td>

<td><code>kubectl apply</code> means</td>

</tr>

<td><code>apiVersion</code>, <code>kind</code>, <code>metadata</code>, <code>spec</code> (yours), <code>status</code> (the controller's)</td>

</tr>

<td><code>initContainers</code> (run to completion, in order)</td>
