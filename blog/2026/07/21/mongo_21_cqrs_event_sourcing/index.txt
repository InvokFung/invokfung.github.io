11:Tc016,<p><strong>CQRS</strong> (Command Query Responsibility Segregation) separates write models from read models. <strong>Event Sourcing</strong> treats the immutable event log as the source of truth — current state is a projection of replayed events. Both are architectural patterns, not Mongo features — but MongoDB fits them especially well: change streams as the projection bus (Post 12), <code>$merge</code> for materialised views (Post 06), aggregation for replaying events, transactions for atomic event-store appends (Post 09). This post covers when each pays off, the canonical models, the trade-offs vs CRUD, and a worked order-management example end-to-end.</p>

<p>Series map: 19 Beanie+FastAPI → 20 Outbox → <strong>21 CQRS + Event Sourcing</strong> (this post) → 22 RAG → ... → 29 K8s + mongosync + cost.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Define CQRS and recognise when it earns its complexity.</li>
<li>Define Event Sourcing and the event-store schema in MongoDB.</li>
<li>Project events into read models via change streams.</li>
<li>Replay history for new projections + bug fixes.</li>
<li>Handle snapshots + projection rebuilds.</li>
<li>Combine outbox + CQRS + ES into a clean architecture.</li>
</ul>
<hr>
<h1 id="Chapter-1-—-CQRS-in-one-paragraph"><a href="#Chapter-1-—-CQRS-in-one-paragraph" class="headerlink" title="Chapter 1 — CQRS in one paragraph"></a>Chapter 1 — CQRS in one paragraph</h1>
<p>A normal CRUD app uses <strong>one model</strong> for reads and writes — same schema, same indexes, same database. CQRS splits them: <strong>command side</strong> handles writes (often normalised, validated, transactional), <strong>query side</strong> holds one or more <strong>read models</strong> optimised per use case (denormalised, fast). The read models are updated by <strong>events</strong> the command side publishes — usually asynchronously.</p>
<p>Benefit:</p>
<ul>
<li>Read models match exactly the queries they serve → simple + fast.</li>
<li>Read + write scale independently.</li>
<li>Multiple read models per command model (one for search, one for analytics, one for a mobile API).</li>
</ul>
<p>Cost:</p>
<ul>
<li>More moving parts.</li>
<li>Read-after-write delay (eventual consistency).</li>
<li>Operational complexity.</li>
</ul>
<p>Use CQRS when one of: read volume &gt;&gt; write volume; queries diverge wildly from write shape; you already need an outbox + projections.</p>
<hr>
<h1 id="Chapter-2-—-Event-Sourcing-in-one-paragraph"><a href="#Chapter-2-—-Event-Sourcing-in-one-paragraph" class="headerlink" title="Chapter 2 — Event Sourcing in one paragraph"></a>Chapter 2 — Event Sourcing in one paragraph</h1>
<p>Instead of storing <strong>current state</strong>, store <strong>every change as an immutable event</strong>. Current state is computed by replaying events. Events are append-only — the most reliable storage primitive in databases.</p>
<p>Benefits:</p>
<ul>
<li>Full audit trail for free.</li>
<li>New projections retroactively built from history.</li>
<li>Bug fixes can replay events through corrected code.</li>
<li>Time-travel debugging.</li>
</ul>
<p>Costs:</p>
<ul>
<li>Reads must aggregate events (use snapshots + projections).</li>
<li>Schema evolution of events is forever — versioning matters.</li>
<li>Higher mental + ops load than CRUD.</li>
</ul>
<p>Use ES when one of: regulatory audit trail mandatory; the domain is genuinely event-shaped (orders, payments, IoT, ledger systems); you need to replay history for new analytics or bug correction.</p>
<p>ES + CQRS combine naturally — ES is the command-side event log, CQRS is the read-side projections.</p>
<hr>
<h1 id="Chapter-3-—-When-NOT-to-use-CQRS-ES"><a href="#Chapter-3-—-When-NOT-to-use-CQRS-ES" class="headerlink" title="Chapter 3 — When NOT to use CQRS / ES"></a>Chapter 3 — When NOT to use CQRS / ES</h1>
<ul>
<li>A CRUD app with simple reads + writes — KISS.</li>
<li>Small team / small product — overhead &gt; benefit.</li>
<li>Tight read-after-write requirements with no tolerance for eventual consistency.</li>
<li>&quot;Because it sounds modern&quot; — biggest reason teams regret it.</li>
</ul>
<p>Default = CRUD. Add CQRS only when reads + writes genuinely diverge. Add ES only when the audit-or-replay property is mandatory.</p>

<h2 id="Multiple-projections"><a href="#Multiple-projections" class="headerlink" title="Multiple projections"></a>Multiple projections</h2>
<p>Add a <code>customer_orders_view</code> keyed by <code>user_id</code>, an <code>analytics_daily_revenue</code> view, a <code>search_index</code> Atlas Search index — each is a different consumer of the event stream.</p>
<p>To add a new view: write the projection code, replay events from the beginning (no resume token), let it catch up, switch reads over.</p>

<p>Snapshots are derived data — disposable. Wipe + rebuild from events if your apply logic changes.</p>

<h1 id="Chapter-8-—-Rebuilding-projections"><a href="#Chapter-8-—-Rebuilding-projections" class="headerlink" title="Chapter 8 — Rebuilding projections"></a>Chapter 8 — Rebuilding projections</h1>
<p>Bug in projection code? Wrote bad state? Rebuild from scratch:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// drop projection</span></span><br><span class="line"><span class="hljs-keyword">await</span> db.<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;orders_view&#x27;</span>).<span class="hljs-title function_">drop</span>();</span><br><span class="line"> </span><br><span class="line"><span class="hljs-comment">// replay all events from beginning</span></span><br><span class="line"><span class="hljs-keyword">const</span> cs = db.<span class="hljs-title function_">collection</span>(<span class="hljs-string">&#x27;events&#x27;</span>).<span class="hljs-title function_">watch</span>([{ <span class="hljs-attr">$match</span>: { <span class="hljs-attr">operationType</span>: <span class="hljs-string">&#x27;insert&#x27;</span> } }], {</span><br><span class="line">  <span class="hljs-attr">startAtOperationTime</span>: <span class="hljs-title class_">Timestamp</span>(<span class="hljs-number">0</span>, <span class="hljs-number">0</span>)    <span class="hljs-comment">// from the start of the cluster</span></span><br><span class="line">});</span><br><span class="line"><span class="hljs-comment">// ... feed every event through the projection logic</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Or use <code>find</code> + sort by <code>_id</code> (events sorted naturally by ObjectId time) instead of change stream for a one-shot rebuild.</p>
<p>This <strong>retroactive correctness</strong> is one of the headline benefits of ES — no other persistence model lets you &quot;just rerun history with the new code&quot;.</p>
<hr>
<h1 id="Chapter-9-—-Event-versioning"><a href="#Chapter-9-—-Event-versioning" class="headerlink" title="Chapter 9 — Event versioning"></a>Chapter 9 — Event versioning</h1>
<p>Events live forever. Their schema must evolve gracefully.</p>
<p>Patterns:</p>
<ol>
<li><strong>Add a <code>version</code> field per event type</strong> + handle each version in the projection.</li>
<li><strong>Upcast</strong> old events to the new shape at read time.</li>
<li><strong>Migration events</strong> — emit a new event (&quot;schema migrated to v2&quot;) rather than mutating history.</li>
</ol>
<p>Never mutate old events. The event log is sacred — modifying it breaks every projection's correctness.</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-keyword">case</span> <span class="hljs-string">&#x27;order.created&#x27;</span>:</span><br><span class="line">  <span class="hljs-keyword">if</span> (e.<span class="hljs-property">version</span> === <span class="hljs-number">1</span>) state.<span class="hljs-property">items</span> = e.<span class="hljs-property">payload</span>.<span class="hljs-property">items</span>;</span><br><span class="line">  <span class="hljs-keyword">else</span> <span class="hljs-keyword">if</span> (e.<span class="hljs-property">version</span> === <span class="hljs-number">2</span>) {</span><br><span class="line">    state.<span class="hljs-property">items</span> = e.<span class="hljs-property">payload</span>.<span class="hljs-property">line_items</span>.<span class="hljs-title function_">map</span>(<span class="hljs-function"><span class="hljs-params">li</span> =&gt;</span> ({ <span class="hljs-attr">p</span>: li.<span class="hljs-property">product_id</span>, <span class="hljs-attr">qty</span>: li.<span class="hljs-property">quantity</span> }));</span><br><span class="line">  }</span><br><span class="line">  <span class="hljs-keyword">break</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span><br><span class="line">17</span><br><span class="line">18</span><br><span class="line">19</span><br><span class="line">20</span><br><span class="line">21</span><br><span class="line">22</span><br><span class="line">23</span><br><span class="line">24</span><br><span class="line">25</span><br><span class="line">26</span><br><span class="line">27</span><br><span class="line">28</span><br><span class="line">29</span><br><span class="line">30</span><br><span class="line">31</span></pre></td><td class="code"><pre><code class="text"><span class="line">┌─────────────────────────────────────────────────────────────────────┐</span><br><span class="line">│   Client (UI / API caller)                                          │</span><br><span class="line">└─────────┬────────────────────────────────────────┬──────────────────┘</span><br><span class="line">          │ POST /commands                          │ GET /queries</span><br><span class="line">          ▼                                          ▼</span><br><span class="line">  ┌─────────────────┐                       ┌────────────────────────┐</span><br><span class="line">  │ Command Service │                       │  Query Service          │</span><br><span class="line">  │  - one per projection    │</span><br><span class="line">   │  - updates view collection│</span><br><span class="line">   └──────────────────────────┘</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Three deployables:</p>
<ol>
<li><strong>Command service</strong> — accepts commands, validates against loaded aggregate, appends events.</li>
<li><strong>Query service</strong> — reads from projection collections.</li>
<li><strong>Projection workers</strong> — one or many, each tail change stream + update one view.</li>
</ol>
<p>Optional: outbox alongside events for publishing to Kafka (Post 20) — events going to external systems.</p>

<h1 id="Chapter-11-—-Trade-offs-vs-CRUD"><a href="#Chapter-11-—-Trade-offs-vs-CRUD" class="headerlink" title="Chapter 11 — Trade-offs vs CRUD"></a>Chapter 11 — Trade-offs vs CRUD</h1>
<table>

<tr>
<th></th>
<th>CRUD</th>
<th>CQRS</th>
<th>CQRS + ES</th>

<h1 id="Chapter-12-—-Common-pitfalls"><a href="#Chapter-12-—-Common-pitfalls" class="headerlink" title="Chapter 12 — Common pitfalls"></a>Chapter 12 — Common pitfalls</h1>
<table>
<thead>
<tr>
<th>Pitfall</th>
<th>Cause</th>
<th>Fix</th>
</tr>
</thead>
<tbody>
<tr>
<td>Eventual consistency surprises in UI</td>
<td>read immediately after write</td>
<td>optimistic UI; or read-from-command-side fallback for the actor's own writes</td>
</tr>
<tr>
<td>Projection stuck on a bug</td>
<td>one bad event halts the worker</td>
<td>log + skip the bad one + alert; never panic-mutate the event log</td>
</tr>
<tr>
<td>Aggregate load slow</td>
<td>thousands of events</td>
<td>snapshots every N events</td>
</tr>
<tr>
<td>Lost data on schema migration</td>
<td>upcasting bug or missed event version</td>
<td>exhaustive tests on every event type version</td>
</tr>
<tr>
<td>Sharded <code>events</code> cross-shard transaction</td>
<td>aggregate scattered across shards</td>
<td>shard key starts with <code>aggregate_id</code></td>
</tr>
<tr>
<td>Projection worker DLQ overflowing</td>
<td>downstream issue</td>
<td>back-pressure; alert; never silently drop</td>
</tr>
<tr>
<td>Wrong projection idempotency</td>
<td>duplicates inflate counts</td>
<td>dedupe by event <code>_id</code></td>
</tr>
<tr>
<td>ES adopted on a CRUD-friendly domain</td>
<td>overengineering</td>
<td>rollback to CRUD; lessons learned</td>
</tr>
</tbody>
</table>

<h1 id="Practice-Exercises"><a href="#Practice-Exercises" class="headerlink" title="Practice Exercises"></a>Practice Exercises</h1>
<h2 id="Exercise-1-—-Event-store"><a href="#Exercise-1-—-Event-store" class="headerlink" title="Exercise 1 — Event store"></a>Exercise 1 — Event store</h2>
<p>Build the <code>events</code> collection from Chapter 4 with the unique index. Append 3 events for one aggregate. Try to append a duplicate <code>version</code> — confirm it fails.</p>
<h2 id="Exercise-2-—-Command-handler"><a href="#Exercise-2-—-Command-handler" class="headerlink" title="Exercise 2 — Command handler"></a>Exercise 2 — Command handler</h2>
<p>Implement <code>payOrder</code> and <code>shipOrder</code>. Load the aggregate, validate, emit the event. Confirm a <code>payOrder</code> against an already-paid order is rejected.</p>
<h2 id="Exercise-3-—-Projection"><a href="#Exercise-3-—-Projection" class="headerlink" title="Exercise 3 — Projection"></a>Exercise 3 — Projection</h2>
<p>Build the <code>orders_view</code> projection (Chapter 6). Start the projection worker; run a few commands; confirm the view stays in sync.</p>
<h2 id="Exercise-4-—-Snapshot"><a href="#Exercise-4-—-Snapshot" class="headerlink" title="Exercise 4 — Snapshot"></a>Exercise 4 — Snapshot</h2>
<p>After 100 simulated events for one aggregate, write a snapshot. Time the load-aggregate function before + after snapshot — confirm speedup.</p>
<h2 id="Exercise-5-—-Rebuild"><a href="#Exercise-5-—-Rebuild" class="headerlink" title="Exercise 5 — Rebuild"></a>Exercise 5 — Rebuild</h2>
<p>Drop <code>orders_view</code>. Replay from the start (single-pass aggregate). Confirm final state matches what was there before.</p>
<h2 id="Exercise-6-—-Schema-versioning"><a href="#Exercise-6-—-Schema-versioning" class="headerlink" title="Exercise 6 — Schema versioning"></a>Exercise 6 — Schema versioning</h2>
<p>Introduce a v2 of <code>order.created</code> that renames <code>items</code> → <code>line_items</code>. Update the apply function to handle both versions. Replay history; confirm same final state.</p>
