PostgreSQL Course — 07 · Operations, Backup, Replication and Security

Created2026-07-08|Updated2026-07-08|Database > PostgreSQL
|Post View:

Everything in the previous six posts assumed a database that is up, reachable, and holding correct data. This post is about keeping that true. It covers the write-ahead log that underpins both durability and replication, backup strategies from a logical dump to point-in-time recovery, streaming and logical replication with the failover hazards they bring, why PostgreSQL's process-per-connection model makes a pooler near-mandatory, the security surface from pg_hba.conf to row-level security, and the monitoring that tells you any of this is going wrong before a user does. It closes the base PostgreSQL course.

Series map: 00 Foundations & Setup → 01 SQL Fundamentals & Data Types → 02 Joins, Aggregation & Window Functions → 03 Indexes & the Query Planner → 04 Query Optimization & Statistics → 05 Transactions, MVCC, Isolation & Locking → 06 Schema Design, Normalization & JSONB → 07 Operations, Backup, Replication & Security (this post) → (future: extensions, full-text search, pgvector, partitioning at scale, tuning, PL/pgSQL, ORMs, managed PostgreSQL).

Learning Outcome

  • Explain what the WAL is, why full page writes exist, and what a checkpoint does.
  • Choose between logical dumps, physical base backups, and continuous archiving, and perform a point-in-time recovery.
  • Set up streaming replication with a replication slot, and monitor lag correctly.
  • Explain the split-brain hazard and why automatic failover needs fencing.
  • Use logical replication, including for a near-zero-downtime major version upgrade.
  • Configure PgBouncer in transaction mode and list exactly what breaks there.
  • Grant privileges correctly, write a row-level security policy, and configure pg_hba.conf with scram-sha-256 and TLS.
  • Name the handful of PostgreSQL metrics worth alerting on and where each comes from.

Chapter 1 — The write-ahead log

Terminology

  • WAL — the write-ahead log. Every change to a data page is described in a WAL record that is flushed to durable storage before the page itself is written.
  • LSN — Log Sequence Number, a monotonically increasing byte position in the WAL stream (0/16B3748). The universal currency of replication and recovery.
  • WAL segment — a WAL file, 16 MB by default.
  • Checkpoint — a point at which all dirty shared buffers are flushed to the data files, allowing WAL before that point to be recycled.
  • Full page write — the first change to a page after a checkpoint writes the entire 8 KB page into the WAL, not just the delta.

The write-ahead rule is what makes crash recovery possible: after a crash, PostgreSQL replays WAL from the last checkpoint forward, reconstructing every committed change. COMMIT returns only once the commit record is durably flushed — this is exactly the D in ACID, and it is why fsync = off is a data-loss setting, not a performance setting.

Full page writes

Operating systems and storage do not guarantee that an 8 KB page write is atomic. A crash mid-write can leave a torn page: half old, half new — a page WAL deltas cannot be applied to, because the base is corrupt. full_page_writes = on (the default) solves this by writing a complete image of the page the first time it is modified after each checkpoint, giving recovery a known-good base to replay from.

The cost is WAL volume, and it is the reason WAL generation spikes immediately after every checkpoint. It is also the reason random-write workloads (see UUIDv4 keys in post 06) generate far more WAL than sequential ones: they touch more distinct pages, so more of them need full images.

Checkpoints

Parameter Default Effect
checkpoint_timeout 5min Maximum time between checkpoints. Commonly raised to 15min–30min.
max_wal_size 1GB Soft ceiling on WAL between checkpoints; exceeding it triggers one early.
min_wal_size 80MB WAL kept preallocated for recycling.
checkpoint_completion_target 0.9 Fraction of the interval over which the flush is spread.
wal_compression off Compresses full-page images. Often a clear win on modern CPUs.

Longer intervals mean fewer full page writes and less total I/O, but a longer crash-recovery time and larger I/O bursts. Set log_checkpoints = on (default since PostgreSQL 15) and watch for the phrase checkpoints are occurring too frequently in the log — that means max_wal_size is too small for the write rate.

synchronous_commit controls how much durability you pay for per transaction:

Value Guarantee Risk on crash
on (default) WAL flushed locally before COMMIT returns None
remote_apply Flushed and applied on a synchronous standby None; highest latency
remote_write Written (not flushed) on the standby Standby OS crash could lose it
local Local flush only, ignoring synchronous standbys Loss only if the primary is lost
off COMMIT returns before the flush Up to wal_writer_delay × 3 of committed transactions lost — but never corruption

synchronous_commit = off is a legitimate choice for a bulk load or an analytics table where losing the last 600 ms of transactions is acceptable. fsync = off never is.

Chapter 2 — Backups

Three families, and you probably want two of them.

Method Granularity Restore target Cross-version Cost
pg_dump / pg_dumpall Logical (SQL or archive) Any point you took a dump Yes — restores into a newer major version Slow on large databases; restore is slower still
pg_basebackup Physical (whole cluster) The moment the backup ended No — same major version, same architecture Fast; size of the data directory
Base backup + WAL archive Physical + continuous Any moment covered by the archive No Base backup plus ongoing WAL storage

Logical dumps

Properties to internalise: a pg_dump is a consistent snapshot (it runs in a REPEATABLE READ transaction), it does not block writers, but it does hold that snapshot for the whole run — which pins the vacuum horizon (post 05). It does not include statistics, so ANALYZE after restoring. And -Fc lets you restore one table out of a full dump, which plain SQL output does not.

Physical base backups

-X stream streams the WAL generated during the backup alongside it, so the result is self-consistent and immediately restorable. In PostgreSQL 15 the old exclusive backup mode was removed; the low-level API is now pg_backup_start() / pg_backup_stop() (renamed from pg_start_backup / pg_stop_backup).

Continuous archiving and point-in-time recovery

Configure the primary to hand every completed WAL segment to an archive:

The archive_command must return non-zero if it fails — PostgreSQL retries and keeps the segment until it succeeds. A command that silently succeeds while writing nowhere is the most common way a PITR setup turns out to be fiction.

Watch out: a failing archive_command makes WAL accumulate in pg_wal until the disk fills and the primary shuts down. Alert on pg_stat_archiver.last_failed_time and on pg_wal directory size.

Worked restore to a specific moment:

Recovery targets available: recovery_target_time, recovery_target_lsn, recovery_target_xid, recovery_target_name (set beforehand with pg_create_restore_point('before_migration')), and recovery_target = 'immediate'. recovery_target_action = 'pause' is the safe default — it gives you a chance to check before the timeline advances irreversibly.

In production, use a purpose-built tool rather than hand-rolled scripts: pgBackRest, Barman, or WAL-G all handle retention, parallel compression, encryption, incremental backups, and — critically — verification.

An untested backup is not a backup

The only evidence a backup works is a restore that produced a working database. Practices worth enforcing:

  • A scheduled automated restore into a scratch environment, at least weekly, that runs a real query afterwards and fails loudly if it does not.
  • Record and track the restore time, not just the backup time. Your RTO is a measured number or it is a hope.
  • Keep at least one copy off the machine, off the account, and immutable. Backups on the same volume protect against nothing that actually happens.
  • Practise the restore under time pressure once, with the runbook, before you need it.

Chapter 3 — Streaming replication

A standby connects to the primary over the replication protocol, receives WAL as it is generated, and replays it continuously. It is physical, byte-for-byte identical replication of the whole cluster.

Replication slots

A slot makes the primary retain WAL until the standby has confirmed consuming it. That removes the classic failure where a standby falls behind, the primary recycles the WAL it still needed, and the standby is permanently broken.

The slot's danger is symmetrical: a forgotten or dropped standby leaves an active slot, the primary retains WAL forever, and pg_wal fills the disk. Bound it:

Synchronous vs asynchronous

Asynchronous (the default) means COMMIT returns as soon as the primary has flushed locally. A primary failure can lose the last few transactions. Synchronous replication waits for a standby:

The trade is unambiguous: synchronous replication buys zero data loss on failover and costs one network round trip on every commit. Configure ANY 1 (a, b) rather than a single named standby — with one synchronous standby and no alternative, losing that standby stalls every commit on the primary.

Hot standby and read scaling

hot_standby = on lets the standby serve read-only queries. Two conflicts follow:

  • A long query on the standby can be cancelled when WAL replay needs to remove rows it is reading (max_standby_streaming_delay, default 30 s, controls how long replay waits first).
  • hot_standby_feedback = on tells the primary to hold back vacuum for the standby's oldest snapshot, which prevents those cancellations — and reintroduces the long-transaction bloat problem from post 05, now caused remotely.

Pick one deliberately. Analytics standby: hot_standby_feedback = on and accept the bloat. Failover-only standby: leave it off.

Monitoring lag

Alert on replay lag in bytes, not on the time figure alone: on an idle primary, now() - pg_last_xact_replay_timestamp() grows simply because nothing has been committed, which produces false alarms.

Failover and split brain

Promotion itself is trivial:

The danger is split brain: the old primary is not actually dead — it was unreachable — and it keeps accepting writes while the new primary also accepts writes. Two divergent timelines, both containing real customer data, and no automatic way to merge them.

Automatic failover therefore requires more than a health check:

  • Fencing / STONITH — make certain the old primary cannot accept writes: kill the instance, revoke its network path, or detach its storage.
  • Quorum — the decision to promote must be made by a majority of an odd-numbered set of observers, not by one watcher that may itself be the partitioned party.
  • A single write endpoint — clients must reach the primary through a VIP, a proxy, or target_session_attrs=read-write in a multi-host connection string, so promotion actually redirects them.

Use Patroni (with etcd/Consul/Kubernetes for consensus) or repmgr. Hand-rolled failover scripts are the classic source of split-brain incidents, and pg_rewind — which can resynchronise a diverged old primary — only helps if the divergence is small and wal_log_hints or data checksums were enabled beforehand.

Chapter 4 — Logical replication

Streaming replication copies bytes. Logical replication decodes the WAL into row-level changes and applies them as ordinary inserts, updates and deletes on the subscriber. That makes it selective and cross-version.

What it can do that physical replication cannot: replicate a subset of tables, replicate between different major versions, replicate into a differently-indexed target, filter rows (WHERE clauses on publications, PostgreSQL 15+) and columns (15+), and support two-way or many-to-one topologies.

What it does not do, and these bite:

  • DDL is not replicated. Schema changes must be applied on both sides, subscriber first for additive changes.
  • Sequence values are not replicated (through PostgreSQL 17). At cutover you must advance every sequence on the subscriber manually with setval().
  • Every replicated table needs a replica identity — a primary key, or REPLICA IDENTITY FULL (which makes updates and deletes far more expensive), otherwise updates and deletes cannot be applied.
  • Large objects are not replicated. Truncate is (11+), but only for tables in the publication.

Major-version upgrade via logical replication

This is logical replication's most valuable use, because it reduces the downtime of a major upgrade from "however long pg_upgrade takes" to "however long a DNS or proxy switch takes".

  1. Build a new cluster on the target major version, restore the schema only (pg_dump --schema-only).
  2. Create a publication on the old cluster and a subscription on the new one. Initial data sync copies existing rows, then streaming catches up.
  3. Wait until pg_stat_subscription shows negligible lag. Verify row counts on both sides.
  4. Stop application writes (this is the entire downtime window).
  5. Confirm zero lag, advance all sequences with setval(), then repoint the application at the new cluster.
  6. Drop the subscription. Keep the old cluster shut down but intact for a rollback window.

Compare with pg_upgrade:

pg_upgrade Logical replication
Downtime Minutes to hours; --link/--clone makes it minutes Seconds — the cutover only
Extra disk None with --link A full second copy of the data
Rollback Hard once --link has been used Easy — the old cluster is untouched and still running
Complexity One command plus a post-upgrade ANALYZE Sequences, DDL freeze, and verification to manage
Extension/index caveats Statistics are not carried over; ANALYZE immediately Target can even be re-indexed differently

pg_upgrade --link is right for a small database with an acceptable maintenance window. Logical replication is right when downtime is measured in seconds and you want a live rollback path.

Chapter 5 — Connection pooling

PostgreSQL forks one operating-system process per connection. Each backend carries its own memory (work_mem allocations, catalogue caches, prepared statement plans), typically several megabytes at rest and much more under load. Consequences:

  • Establishing a connection costs a fork() plus catalogue loading — milliseconds, which is enormous compared to a 0.3 ms query.
  • Idle connections are not free; they hold memory and appear in every snapshot computation.
  • Throughput peaks at a fairly small number of active backends — roughly in the neighbourhood of the core count plus effective spindle count — and declines beyond it as lock contention and context switching dominate. Raising max_connections to 2000 does not raise throughput; it lowers it.

This is why a pooler is near-mandatory for any application with more than a handful of application servers, and why serverless platforms that open a connection per request need one absolutely.

PgBouncer modes

Mode A server connection is returned to the pool Multiplexing Use for
session When the client disconnects None — 1:1 while connected Legacy apps that depend on session state
transaction At the end of each transaction High — the reason to use PgBouncer Almost all web applications
statement After every statement Highest Only for autocommit-only, single-statement workloads

What breaks in transaction mode

Your session may be a different backend for every transaction. Anything that lives in a session rather than a transaction is therefore unsafe:

Feature Status in transaction mode
SET / SET SESSION outside a transaction Broken — lands on an arbitrary backend. Use SET LOCAL inside the transaction.
Session-level advisory locks (pg_advisory_lock) Broken — the unlock may run on a different backend. Use pg_advisory_xact_lock.
LISTEN / NOTIFY Broken — LISTEN needs a persistent session. Keep a direct connection for it.
Session-level prepared statements Historically broken. PgBouncer 1.21+ supports protocol-level prepared statements in transaction mode via max_prepared_statements; enable it and match the driver's behaviour.
WITH HOLD cursors Broken — they outlive the transaction.
Temporary tables Broken — session-scoped.
Sequence currval() across transactions Broken. Use RETURNING instead.
SET ROLE for row-level security Only safe as SET LOCAL ROLE inside the transaction.

Common pitfall: ORMs and drivers frequently use server-side prepared statements by default (psycopg3's prepare threshold, JDBC's prepareThreshold, Prisma's behaviour). Either enable max_prepared_statements in PgBouncer or turn prepared statements off in the driver. Silently mismatched configuration produces intermittent prepared statement "S_1" does not exist errors under load and nowhere else.

Sizing: total server connections across all poolers should stay comfortably under max_connections. A common shape is max_connections = 200 on the server, default_pool_size = 20 per pooler instance, and thousands of client connections above that. Alternatives worth knowing: Odyssey (multi-threaded), pgcat (pooling plus load balancing and sharding), and the pooler built into most managed platforms.

Chapter 6 — Security

Roles and privileges

PostgreSQL has one concept — the role — that plays the part of both user and group. LOGIN is just an attribute.

ALTER DEFAULT PRIVILEGES applies to objects created by the role that runs it. Run it as the role that owns your migrations, or specify FOR ROLE migrator, or the next table created will silently be inaccessible.

Baseline hardening:

  • The application never connects as a superuser, and never as the schema owner. A compromised application should not be able to DROP TABLE.
  • Revoke the default public access: since PostgreSQL 15 the public schema no longer grants CREATE to PUBLIC, but on older clusters run REVOKE CREATE ON SCHEMA public FROM PUBLIC;.
  • REVOKE ALL ON DATABASE shop FROM PUBLIC; then grant CONNECT explicitly.
  • Separate roles for migrations (DDL), the application (DML), read replicas/analytics (SELECT only), and backups (pg_read_all_data, a predefined role since PostgreSQL 14).

Row-level security

RLS makes the database itself filter rows per user — the multi-tenancy control that cannot be forgotten by an application developer.

The application sets the tenant at the start of each transaction:

Three things to get right:

  • USING filters what is visible; WITH CHECK constrains what may be written. Omit WITH CHECK and a tenant can insert rows belonging to another tenant that it then cannot see.
  • Without FORCE ROW LEVEL SECURITY, the table owner bypasses all policies. Superusers and roles with BYPASSRLS always bypass them.
  • Use SET LOCAL, never SET, when a pooler is in front (Chapter 5). A leaked app.tenant_id on a reused backend is a cross-tenant data leak.
  • Index the policy column. Every query now carries tenant_id = ..., so (tenant_id, ...) should lead your indexes.

pg_hba.conf and authentication

pg_hba.conf is evaluated top to bottom, first match wins. The most common misconfiguration is a broad early rule shadowing the strict rule below it.

Method Verdict
scram-sha-256 The correct default. Set password_encryption = 'scram-sha-256' (the default since PostgreSQL 14) and reset every password so the stored verifier is upgraded.
md5 Deprecated and weak. Migrate off it.
trust No authentication at all. Never outside a throwaway container.
peer / ident OS-user based; fine for local admin access.
cert TLS client certificates. Strong, operationally heavy.
ldap / gss / sspi Enterprise directory integration.

Reload after editing: SELECT pg_reload_conf(); — no restart needed. Inspect the effective rules with SELECT * FROM pg_hba_file_rules;, which also reports parse errors.

TLS

Server-side ssl = on only permits TLS. The client decides whether to require it, and the default (sslmode=prefer) silently falls back to plaintext. Force it from the client, and use verify-full so the certificate is actually checked against the hostname:

Use hostssl (not host) lines in pg_hba.conf for anything crossing a network boundary, so the server rejects plaintext rather than trusting the client to ask.

Secrets

  • Never in the repository, never in a connection string in application source, never in a shell history.
  • Use the platform's secret manager (AWS Secrets Manager, GCP Secret Manager, Vault, Kubernetes secrets with encryption at rest) and inject at runtime.
  • Prefer short-lived credentials where the platform offers them — IAM authentication on RDS/Cloud SQL issues a token valid for minutes rather than a static password.
  • ~/.pgpass (mode 0600) for operator tooling; environment variables for containers; never a command-line -W password argument, which lands in the process list.
  • Rotate on a schedule, and make the rotation a tested procedure rather than a theoretical one.

Chapter 7 — Monitoring and alerting

The views that matter

View Tells you
pg_stat_activity What every backend is doing right now: state, wait_event_type, xact_start, query
pg_stat_database Per database: commits, rollbacks, blks_hit/blks_read, deadlocks, temp_files, conflicts
pg_stat_user_tables Per table: seq vs index scans, n_dead_tup, last (auto)vacuum and analyze
pg_stat_user_indexes Per index: idx_scan — zero means an unused index costing write throughput
pg_stat_statements Query-level aggregate cost. The starting point of tuning (post 04)
pg_stat_replication Per-standby lag at each stage
pg_stat_archiver WAL archiving success and failure counts
pg_stat_bgwriter Checkpoint counts — a high checkpoints_req vs checkpoints_timed ratio means max_wal_size is too small
pg_stat_io Per-backend-type I/O breakdown (PostgreSQL 16+)
pg_locks Lock waits and blocking chains

Logging

log_min_duration_statement complements pg_stat_statements rather than duplicating it: pg_stat_statements gives aggregates with normalised text, the log gives individual slow executions with their actual parameter values — which is what you need to reproduce a plan.

For heavier sampling use auto_explain with auto_explain.log_min_duration and auto_explain.log_analyze (understanding that log_analyze adds real overhead), which captures the actual plan of slow statements as they happen.

What to alert on

Signal Source Why it wakes someone
Replication replay lag over threshold (bytes) pg_stat_replication Failover would lose data; read replicas serve stale results
Inactive replication slot with growing retention pg_replication_slots Primary's pg_wal will fill the disk
WAL archiver failures pg_stat_archiver.last_failed_time PITR is silently broken and disk will fill
Transaction ID age approaching autovacuum_freeze_max_age age(datfrozenxid) Cluster will refuse writes (post 05)
Disk usage on the data and WAL volumes OS A full volume shuts PostgreSQL down
Connections near max_connections pg_stat_activity count New connections will be refused
Longest transaction / longest idle in transaction pg_stat_activity Blocks vacuum cluster-wide; blocks DDL
Deadlocks per interval pg_stat_database.deadlocks A lock-ordering bug shipped
Cache hit ratio falling sharply pg_stat_database Working set outgrew memory; investigate, do not alert on a fixed number
p99 query latency, and error rate by SQLSTATE Application / pg_stat_statements The signal your users actually feel
Backup job success, and last successful restore test Backup tool The only proof the backup exists

Alert on things that are actionable and that precede user-visible failure. Cache hit ratio, transactions per second and index counts are dashboard metrics, not pager metrics.

Practice Exercises

Exercise 1 — Full PITR drill

Set up continuous archiving on a scratch cluster. Take a base backup, insert recognisable data, note the wall-clock time, then DROP TABLE something important. Restore to one minute before the drop and prove the table is back.

Solution

Exercise 2 — Streaming replication with a slot

Build a primary and one standby with a physical replication slot. Write continuously on the primary and read on the standby. Then stop the standby for ten minutes and show, from pg_replication_slots, exactly how much WAL the primary retained on its behalf.

Exercise 3 — Break the slot deliberately

Set max_slot_wal_keep_size to a small value, stop the standby, and generate enough WAL to exceed it. Observe the slot becoming lost and the standby failing to resume. Explain in two sentences why this outcome is preferable to the primary filling its disk.

Exercise 4 — Transaction pooling failures

Put PgBouncer in pool_mode = transaction in front of a test database. Reproduce three distinct failures: a SET outside a transaction that does not stick, a session advisory lock that is never released, and a prepared-statement error. Then fix each one.

Solution

Exercise 5 — Row-level security

Create a two-tenant documents table with RLS. Show that a query with app.tenant_id = '1' cannot see tenant 2's rows, that FORCE ROW LEVEL SECURITY also constrains the owner, and that omitting WITH CHECK lets a tenant insert a row it then cannot read back.

Solution

Exercise 6 — Audit pg_hba.conf

Take a default pg_hba.conf and harden it: no trust, scram-sha-256 everywhere, hostssl for anything non-local, a dedicated replication line, and an explicit reject at the end. Verify with pg_hba_file_rules and confirm a plaintext connection is refused.

Exercise 7 — Design the alert set

For a two-node cluster with nightly base backups and continuous archiving, write out every alert you would configure: the metric, its source query, the threshold, and the first three steps of the runbook for each. Deliberately include no alert that is not actionable.
