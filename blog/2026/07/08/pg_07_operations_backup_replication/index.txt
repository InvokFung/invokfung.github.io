<h1 id="Chapter-1-—-The-write-ahead-log"><a href="#Chapter-1-—-The-write-ahead-log" class="headerlink" title="Chapter 1 — The write-ahead log"></a>Chapter 1 — The write-ahead log</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>WAL</strong> — the write-ahead log. Every change to a data page is described in a WAL record that is flushed to durable storage <em>before</em> the page itself is written.</li>
<li><strong>LSN</strong> — Log Sequence Number, a monotonically increasing byte position in the WAL stream (<code>0/16B3748</code>). The universal currency of replication and recovery.</li>
<li><strong>WAL segment</strong> — a WAL file, 16 MB by default.</li>
<li><strong>Checkpoint</strong> — a point at which all dirty shared buffers are flushed to the data files, allowing WAL before that point to be recycled.</li>
<li><strong>Full page write</strong> — the first change to a page after a checkpoint writes the <em>entire</em> 8 KB page into the WAL, not just the delta.</li>
</ul>
<p>The write-ahead rule is what makes crash recovery possible: after a crash, PostgreSQL replays WAL from the last checkpoint forward, reconstructing every committed change. <code>COMMIT</code> returns only once the commit record is durably flushed — this is exactly the D in ACID, and it is why <code>fsync = off</code> is a data-loss setting, not a performance setting.</p>
<h2 id="Full-page-writes"><a href="#Full-page-writes" class="headerlink" title="Full page writes"></a>Full page writes</h2>
<p>Operating systems and storage do not guarantee that an 8 KB page write is atomic. A crash mid-write can leave a <em>torn page</em>: half old, half new — a page WAL deltas cannot be applied to, because the base is corrupt. <code>full_page_writes = on</code> (the default) solves this by writing a complete image of the page the first time it is modified after each checkpoint, giving recovery a known-good base to replay from.</p>
<p>The cost is WAL volume, and it is the reason WAL generation spikes immediately after every checkpoint. It is also the reason random-write workloads (see UUIDv4 keys in post 06) generate far more WAL than sequential ones: they touch more distinct pages, so more of them need full images.</p>

<p><code>synchronous_commit = off</code> is a legitimate choice for a bulk load or an analytics table where losing the last 600 ms of transactions is acceptable. <code>fsync = off</code> never is.</p>

<p>Properties to internalise: a <code>pg_dump</code> is a <strong>consistent snapshot</strong> (it runs in a <code>REPEATABLE READ</code> transaction), it does <strong>not</strong> block writers, but it <em>does</em> hold that snapshot for the whole run — which pins the vacuum horizon (post 05). It does not include statistics, so <code>ANALYZE</code> after restoring. And <code>-Fc</code> lets you restore one table out of a full dump, which plain SQL output does not.</p>
<h2 id="Physical-base-backups"><a href="#Physical-base-backups" class="headerlink" title="Physical base backups"></a>Physical base backups</h2>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">pg_basebackup -h primary.internal -U replicator \</span><br><span class="line">    -D /var/lib/postgresql/backup \</span><br><span class="line">    -X stream -c fast -P --checkpoint=fast</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>-X stream</code> streams the WAL generated during the backup alongside it, so the result is self-consistent and immediately restorable. In PostgreSQL 15 the old exclusive backup mode was removed; the low-level API is now <code>pg_backup_start()</code> / <code>pg_backup_stop()</code> (renamed from <code>pg_start_backup</code> / <code>pg_stop_backup</code>).</p>
<h2 id="Continuous-archiving-and-point-in-time-recovery"><a href="#Continuous-archiving-and-point-in-time-recovery" class="headerlink" title="Continuous archiving and point-in-time recovery"></a>Continuous archiving and point-in-time recovery</h2>
<p>Configure the primary to hand every completed WAL segment to an archive:</p>
<pre><code class="language-ini"><figure class="highlight ini"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="ini"><span class="line"><span class="hljs-comment"># postgresql.conf</span></span><br><span class="line"><span class="hljs-attr">wal_level</span> = replica</span><br><span class="line"><span class="hljs-attr">archive_mode</span> = <span class="hljs-literal">on</span></span><br><span class="line"><span class="hljs-attr">archive_command</span> = <span class="hljs-string">&#x27;test ! -f /wal_archive/%f &amp;&amp; cp %p /wal_archive/%f&#x27;</span></span><br><span class="line"><span class="hljs-attr">archive_timeout</span> = <span class="hljs-string">&#x27;5min&#x27;</span>      <span class="hljs-comment"># force a segment switch so low-traffic gaps are bounded</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The <code>archive_command</code> must return non-zero if it fails — PostgreSQL retries and keeps the segment until it succeeds. A command that silently succeeds while writing nowhere is the most common way a PITR setup turns out to be fiction.</p>
<blockquote>
<p><strong>Watch out:</strong> a failing <code>archive_command</code> makes WAL accumulate in <code>pg_wal</code> until the disk fills and the primary shuts down. Alert on <code>pg_stat_archiver.last_failed_time</code> and on <code>pg_wal</code> directory size.</p>
</blockquote>
<p>Worked restore to a specific moment:</p>

<p>Recovery targets available: <code>recovery_target_time</code>, <code>recovery_target_lsn</code>, <code>recovery_target_xid</code>, <code>recovery_target_name</code> (set beforehand with <code>pg_create_restore_point('before_migration')</code>), and <code>recovery_target = 'immediate'</code>. <code>recovery_target_action = 'pause'</code> is the safe default — it gives you a chance to check before the timeline advances irreversibly.</p>
<p>In production, use a purpose-built tool rather than hand-rolled scripts: <strong>pgBackRest</strong>, <strong>Barman</strong>, or <strong>WAL-G</strong> all handle retention, parallel compression, encryption, incremental backups, and — critically — verification.</p>
<h2 id="An-untested-backup-is-not-a-backup"><a href="#An-untested-backup-is-not-a-backup" class="headerlink" title="An untested backup is not a backup"></a>An untested backup is not a backup</h2>
<p>The only evidence a backup works is a restore that produced a working database. Practices worth enforcing:</p>
<ul>
<li>A scheduled automated restore into a scratch environment, at least weekly, that runs a real query afterwards and fails loudly if it does not.</li>
<li>Record and track the <strong>restore time</strong>, not just the backup time. Your RTO is a measured number or it is a hope.</li>
<li>Keep at least one copy off the machine, off the account, and immutable. Backups on the same volume protect against nothing that actually happens.</li>
<li>Practise the restore under time pressure once, with the runbook, before you need it.</li>
</ul>

<h1 id="Chapter-3-—-Streaming-replication"><a href="#Chapter-3-—-Streaming-replication" class="headerlink" title="Chapter 3 — Streaming replication"></a>Chapter 3 — Streaming replication</h1>
<p>A standby connects to the primary over the replication protocol, receives WAL as it is generated, and replays it continuously. It is physical, byte-for-byte identical replication of the whole cluster.</p>
<h2 id="Setup"><a href="#Setup" class="headerlink" title="Setup"></a>Setup</h2>

<h2 id="Replication-slots"><a href="#Replication-slots" class="headerlink" title="Replication slots"></a>Replication slots</h2>
<p>A slot makes the primary retain WAL until the standby has confirmed consuming it. That removes the classic failure where a standby falls behind, the primary recycles the WAL it still needed, and the standby is permanently broken.</p>
<p>The slot's danger is symmetrical: a <strong>forgotten or dropped standby leaves an active slot</strong>, the primary retains WAL forever, and <code>pg_wal</code> fills the disk. Bound it:</p>
<pre><code class="language-ini"><figure class="highlight ini"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="ini"><span class="line"><span class="hljs-attr">max_slot_wal_keep_size</span> = <span class="hljs-string">&#x27;64GB&#x27;</span>    <span class="hljs-comment"># PostgreSQL 13+: invalidate the slot rather than die</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-comment">-- Audit slots regularly; anything inactive with a growing lag is a disk-space incident</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> slot_name, slot_type, active,</span><br><span class="line">       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) <span class="hljs-keyword">AS</span> retained</span><br><span class="line"><span class="hljs-keyword">FROM</span> pg_replication_slots;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<h2 id="Synchronous-vs-asynchronous"><a href="#Synchronous-vs-asynchronous" class="headerlink" title="Synchronous vs asynchronous"></a>Synchronous vs asynchronous</h2>
<p>Asynchronous (the default) means <code>COMMIT</code> returns as soon as the primary has flushed locally. A primary failure can lose the last few transactions. Synchronous replication waits for a standby:</p>
<pre><code class="language-ini"><figure class="highlight ini"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="ini"><span class="line"><span class="hljs-attr">synchronous_standby_names</span> = <span class="hljs-string">&#x27;ANY 1 (standby_1, standby_2)&#x27;</span></span><br><span class="line"><span class="hljs-attr">synchronous_commit</span> = <span class="hljs-literal">on</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The trade is unambiguous: synchronous replication buys zero data loss on failover and costs one network round trip on every commit. Configure <code>ANY 1 (a, b)</code> rather than a single named standby — with one synchronous standby and no alternative, losing that standby stalls every commit on the primary.</p>
<h2 id="Hot-standby-and-read-scaling"><a href="#Hot-standby-and-read-scaling" class="headerlink" title="Hot standby and read scaling"></a>Hot standby and read scaling</h2>
<p><code>hot_standby = on</code> lets the standby serve read-only queries. Two conflicts follow:</p>
<ul>
<li>A long query on the standby can be <strong>cancelled</strong> when WAL replay needs to remove rows it is reading (<code>max_standby_streaming_delay</code>, default 30 s, controls how long replay waits first).</li>
<li><code>hot_standby_feedback = on</code> tells the primary to hold back vacuum for the standby's oldest snapshot, which prevents those cancellations — and reintroduces the long-transaction bloat problem from post 05, now caused remotely.</li>
</ul>
<p>Pick one deliberately. Analytics standby: <code>hot_standby_feedback = on</code> and accept the bloat. Failover-only standby: leave it off.</p>

<h2 id="Failover-and-split-brain"><a href="#Failover-and-split-brain" class="headerlink" title="Failover and split brain"></a>Failover and split brain</h2>
<p>Promotion itself is trivial:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line">pg_ctl promote -D /var/lib/postgresql/17/main</span><br><span class="line"><span class="hljs-comment"># or: SELECT pg_promote();</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The danger is <strong>split brain</strong>: the old primary is not actually dead — it was unreachable — and it keeps accepting writes while the new primary also accepts writes. Two divergent timelines, both containing real customer data, and no automatic way to merge them.</p>
<p>Automatic failover therefore requires more than a health check:</p>
<ul>
<li><strong>Fencing / STONITH</strong> — make certain the old primary cannot accept writes: kill the instance, revoke its network path, or detach its storage.</li>
<li><strong>Quorum</strong> — the decision to promote must be made by a majority of an odd-numbered set of observers, not by one watcher that may itself be the partitioned party.</li>
<li><strong>A single write endpoint</strong> — clients must reach the primary through a VIP, a proxy, or <code>target_session_attrs=read-write</code> in a multi-host connection string, so promotion actually redirects them.</li>
</ul>
<p>Use <strong>Patroni</strong> (with etcd/Consul/Kubernetes for consensus) or <strong>repmgr</strong>. Hand-rolled failover scripts are the classic source of split-brain incidents, and <code>pg_rewind</code> — which can resynchronise a diverged old primary — only helps if the divergence is small and <code>wal_log_hints</code> or data checksums were enabled beforehand.</p>

<span class="hljs-keyword">FROM</span> pg_replication_slots <span class="hljs-keyword">WHERE</span> slot_type <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;logical&#x27;</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>What it can do that physical replication cannot: replicate a subset of tables, replicate between different major versions, replicate into a differently-indexed target, filter rows (<code>WHERE</code> clauses on publications, PostgreSQL 15+) and columns (15+), and support two-way or many-to-one topologies.</p>
<p>What it does <strong>not</strong> do, and these bite:</p>
<ul>
<li><strong>DDL is not replicated.</strong> Schema changes must be applied on both sides, subscriber first for additive changes.</li>
<li><strong>Sequence values are not replicated</strong> (through PostgreSQL 17). At cutover you must advance every sequence on the subscriber manually with <code>setval()</code>.</li>
<li><strong>Every replicated table needs a replica identity</strong> — a primary key, or <code>REPLICA IDENTITY FULL</code> (which makes updates and deletes far more expensive), otherwise updates and deletes cannot be applied.</li>
<li>Large objects are not replicated. Truncate is (11+), but only for tables in the publication.</li>
</ul>
<h2 id="Major-version-upgrade-via-logical-replication"><a href="#Major-version-upgrade-via-logical-replication" class="headerlink" title="Major-version upgrade via logical replication"></a>Major-version upgrade via logical replication</h2>
<p>This is logical replication's most valuable use, because it reduces the downtime of a major upgrade from &quot;however long <code>pg_upgrade</code> takes&quot; to &quot;however long a DNS or proxy switch takes&quot;.</p>
<ol>
<li>Build a new cluster on the target major version, restore the schema only (<code>pg_dump --schema-only</code>).</li>
<li>Create a publication on the old cluster and a subscription on the new one. Initial data sync copies existing rows, then streaming catches up.</li>
<li>Wait until <code>pg_stat_subscription</code> shows negligible lag. Verify row counts on both sides.</li>
<li>Stop application writes (this is the entire downtime window).</li>
<li>Confirm zero lag, advance all sequences with <code>setval()</code>, then repoint the application at the new cluster.</li>
<li>Drop the subscription. Keep the old cluster shut down but intact for a rollback window.</li>
</ol>
<p>Compare with <code>pg_upgrade</code>:</p>

<h1 id="Chapter-5-—-Connection-pooling"><a href="#Chapter-5-—-Connection-pooling" class="headerlink" title="Chapter 5 — Connection pooling"></a>Chapter 5 — Connection pooling</h1>
<p>PostgreSQL forks <strong>one operating-system process per connection</strong>. Each backend carries its own memory (<code>work_mem</code> allocations, catalogue caches, prepared statement plans), typically several megabytes at rest and much more under load. Consequences:</p>
<ul>
<li>Establishing a connection costs a <code>fork()</code> plus catalogue loading — milliseconds, which is enormous compared to a 0.3 ms query.</li>
<li>Idle connections are not free; they hold memory and appear in every snapshot computation.</li>
<li>Throughput peaks at a fairly small number of <em>active</em> backends — roughly in the neighbourhood of the core count plus effective spindle count — and <strong>declines</strong> beyond it as lock contention and context switching dominate. Raising <code>max_connections</code> to 2000 does not raise throughput; it lowers it.</li>
</ul>
<p>This is why a pooler is near-mandatory for any application with more than a handful of application servers, and why serverless platforms that open a connection per request need one absolutely.</p>

<h2 id="What-breaks-in-transaction-mode"><a href="#What-breaks-in-transaction-mode" class="headerlink" title="What breaks in transaction mode"></a>What breaks in transaction mode</h2>
<p>Your session may be a different backend for every transaction. Anything that lives in a <em>session</em> rather than a <em>transaction</em> is therefore unsafe:</p>
<table>
<thead>
<tr>
<th>Feature</th>
<th>Status in transaction mode</th>
</tr>
</thead>
<tbody>
<tr>
<td><code>SET</code> / <code>SET SESSION</code> outside a transaction</td>
<td>Broken — lands on an arbitrary backend. Use <code>SET LOCAL</code> inside the transaction.</td>
</tr>
<tr>
<td>Session-level advisory locks (<code>pg_advisory_lock</code>)</td>
<td>Broken — the unlock may run on a different backend. Use <code>pg_advisory_xact_lock</code>.</td>
</tr>
<tr>
<td><code>LISTEN</code> / <code>NOTIFY</code></td>
<td>Broken — <code>LISTEN</code> needs a persistent session. Keep a direct connection for it.</td>
</tr>
<tr>
<td>Session-level prepared statements</td>
<td>Historically broken. PgBouncer 1.21+ supports protocol-level prepared statements in transaction mode via <code>max_prepared_statements</code>; enable it and match the driver's behaviour.</td>
</tr>
<tr>
<td><code>WITH HOLD</code> cursors</td>
<td>Broken — they outlive the transaction.</td>
</tr>
<tr>
<td>Temporary tables</td>
<td>Broken — session-scoped.</td>
</tr>
<tr>
<td>Sequence <code>currval()</code> across transactions</td>
<td>Broken. Use <code>RETURNING</code> instead.</td>
</tr>
<tr>
<td><code>SET ROLE</code> for row-level security</td>
<td>Only safe as <code>SET LOCAL ROLE</code> inside the transaction.</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>Common pitfall:</strong> ORMs and drivers frequently use server-side prepared statements by default (psycopg3's prepare threshold, JDBC's <code>prepareThreshold</code>, Prisma's behaviour). Either enable <code>max_prepared_statements</code> in PgBouncer or turn prepared statements off in the driver. Silently mismatched configuration produces intermittent <code>prepared statement &quot;S_1&quot; does not exist</code> errors under load and nowhere else.</p>
</blockquote>
<p>Sizing: total server connections across all poolers should stay comfortably under <code>max_connections</code>. A common shape is <code>max_connections = 200</code> on the server, <code>default_pool_size = 20</code> per pooler instance, and thousands of client connections above that. Alternatives worth knowing: <strong>Odyssey</strong> (multi-threaded), <strong>pgcat</strong> (pooling plus load balancing and sharding), and the pooler built into most managed platforms.</p>

<h2 id="Roles-and-privileges"><a href="#Roles-and-privileges" class="headerlink" title="Roles and privileges"></a>Roles and privileges</h2>
<p>PostgreSQL has one concept — the <strong>role</strong> — that plays the part of both user and group. <code>LOGIN</code> is just an attribute.</p>

<p><code>ALTER DEFAULT PRIVILEGES</code> applies to objects created <strong>by the role that runs it</strong>. Run it as the role that owns your migrations, or specify <code>FOR ROLE migrator</code>, or the next table created will silently be inaccessible.</p>
<p>Baseline hardening:</p>
<ul>
<li>The application never connects as a superuser, and never as the schema owner. A compromised application should not be able to <code>DROP TABLE</code>.</li>
<li>Revoke the default public access: since PostgreSQL 15 the <code>public</code> schema no longer grants <code>CREATE</code> to <code>PUBLIC</code>, but on older clusters run <code>REVOKE CREATE ON SCHEMA public FROM PUBLIC;</code>.</li>
<li><code>REVOKE ALL ON DATABASE shop FROM PUBLIC;</code> then grant <code>CONNECT</code> explicitly.</li>
<li>Separate roles for migrations (DDL), the application (DML), read replicas/analytics (<code>SELECT</code> only), and backups (<code>pg_read_all_data</code>, a predefined role since PostgreSQL 14).</li>
</ul>
<h2 id="Row-level-security"><a href="#Row-level-security" class="headerlink" title="Row-level security"></a>Row-level security</h2>
<p>RLS makes the database itself filter rows per user — the multi-tenancy control that cannot be forgotten by an application developer.</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span><br><span class="line">15</span><br><span class="line">16</span><br><span class="line">17</span><br><span class="line">18</span><br><span class="line">19</span><br><span class="line">20</span><br><span class="line">21</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">CREATE</span> <span class="hljs-keyword">TABLE</span> documents (</span><br><span class="line">    id         <span class="hljs-type">bigint</span> GENERATED ALWAYS <span class="hljs-keyword">AS</span> <span class="hljs-keyword">IDENTITY</span> <span class="hljs-keyword">PRIMARY</span> KEY,</span><br><span class="line">    tenant_id  <span class="hljs-type">bigint</span> <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span>,</span><br><span class="line">    owner      text   <span class="hljs-keyword">NOT</span> <span class="hljs-keyword">NULL</span>,</span><br><span class="line">    body       text</span><br><span class="line">);</span><br><span class="line"> </span><br><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> documents ENABLE <span class="hljs-type">ROW</span> LEVEL SECURITY;</span><br><span class="line"><span class="hljs-keyword">ALTER</span> <span class="hljs-keyword">TABLE</span> documents FORCE <span class="hljs-type">ROW</span> LEVEL SECURITY; <p>The application sets the tenant at the start of each transaction:</p>
<pre><code class="language-sql"><figure class="highlight sql"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="sql"><span class="line"><span class="hljs-keyword">BEGIN</span>;</span><br><span class="line"><span class="hljs-keyword">SET</span> <span class="hljs-keyword">LOCAL</span> app.tenant_id <span class="hljs-operator">=</span> <span class="hljs-string">&#x27;4711&#x27;</span>;     <span class="hljs-comment">-- LOCAL: reverts at commit, pooler-safe</span></span><br><span class="line"><span class="hljs-keyword">SELECT</span> <span class="hljs-operator">*</span> <span class="hljs-keyword">FROM</span> documents;              <span class="hljs-comment">-- only tenant 4711&#x27;s rows exist, as far as this query knows</span></span><br><span class="line"><span class="hljs-keyword">COMMIT</span>;</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Three things to get right:</p>
<ul>
<li><code>USING</code> filters what is <strong>visible</strong>; <code>WITH CHECK</code> constrains what may be <strong>written</strong>. Omit <code>WITH CHECK</code> and a tenant can insert rows belonging to another tenant that it then cannot see.</li>
<li>Without <code>FORCE ROW LEVEL SECURITY</code>, the table owner bypasses all policies. Superusers and roles with <code>BYPASSRLS</code> always bypass them.</li>
<li>Use <code>SET LOCAL</code>, never <code>SET</code>, when a pooler is in front (Chapter 5). A leaked <code>app.tenant_id</code> on a reused backend is a cross-tenant data leak.</li>
<li>Index the policy column. Every query now carries <code>tenant_id = ...</code>, so <code>(tenant_id, ...)</code> should lead your indexes.</li>
</ul>

<h2 id="TLS"><a href="#TLS" class="headerlink" title="TLS"></a>TLS</h2>
<pre><code class="language-ini"><figure class="highlight ini"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="ini"><span class="line"><span class="hljs-attr">ssl</span> = <span class="hljs-literal">on</span></span><br><span class="line"><span class="hljs-attr">ssl_cert_file</span> = <span class="hljs-string">&#x27;/etc/ssl/certs/server.crt&#x27;</span></span><br><span class="line"><span class="hljs-attr">ssl_key_file</span>  = <span class="hljs-string">&#x27;/etc/ssl/private/server.key&#x27;</span></span><br><span class="line"><span class="hljs-attr">ssl_min_protocol_version</span> = <span class="hljs-string">&#x27;TLSv1.2&#x27;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Server-side <code>ssl = on</code> only <em>permits</em> TLS. The client decides whether to require it, and the default (<code>sslmode=prefer</code>) silently falls back to plaintext. Force it from the client, and use <code>verify-full</code> so the certificate is actually checked against the hostname:</p>
<pre><code><figure class="highlight plaintext"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="plaintext"><span class="line">postgresql:<span class="hljs-regexp">//</span>app_svc@db.internal:<span class="hljs-number">5432</span><span class="hljs-regexp">/shop?sslmode=verify-full&amp;sslrootcert=/</span>etc<span class="hljs-regexp">/ssl/</span>ca.pem</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Use <code>hostssl</code> (not <code>host</code>) lines in <code>pg_hba.conf</code> for anything crossing a network boundary, so the server rejects plaintext rather than trusting the client to ask.</p>
<h2 id="Secrets"><a href="#Secrets" class="headerlink" title="Secrets"></a>Secrets</h2>
<ul>
<li>Never in the repository, never in a connection string in application source, never in a shell history.</li>
<li>Use the platform's secret manager (AWS Secrets Manager, GCP Secret Manager, Vault, Kubernetes secrets with encryption at rest) and inject at runtime.</li>
<li>Prefer short-lived credentials where the platform offers them — IAM authentication on RDS/Cloud SQL issues a token valid for minutes rather than a static password.</li>
<li><code>~/.pgpass</code> (mode <code>0600</code>) for operator tooling; environment variables for containers; never a command-line <code>-W</code> password argument, which lands in the process list.</li>
<li>Rotate on a schedule, and make the rotation a tested procedure rather than a theoretical one.</li>
</ul>

<h1 id="Course-base-complete-—-whats-next"><a href="#Course-base-complete-—-whats-next" class="headerlink" title="Course base complete — what's next"></a>Course base complete — what's next</h1>
<p>You now have the base PostgreSQL course end to end: installation and the client, SQL and the type system, joins and window functions, indexes and the planner, cost-based optimization and statistics, MVCC and concurrency control, schema design and JSONB, and the operational layer that keeps all of it running. That is the working knowledge behind most day-to-day PostgreSQL engineering, and enough to be the person on a team who can answer &quot;why is this slow&quot; and &quot;can we restore that&quot;.</p>
<p>The remaining posts go deeper into specialisations, each of which is a topic in its own right.</p>
<p><strong>Planned future posts (extensions):</strong></p>
