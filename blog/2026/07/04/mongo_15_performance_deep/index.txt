<h1 id="Chapter-1-—-WiredTiger-cache"><a href="#Chapter-1-—-WiredTiger-cache" class="headerlink" title="Chapter 1 — WiredTiger cache"></a>Chapter 1 — WiredTiger cache</h1>
<p>WiredTiger is MongoDB's default storage engine (since 3.2). It keeps recently-accessed B-tree pages + index entries in an in-memory <strong>cache</strong>:</p>
<ul>
<li>Default size: <code>max(50% of RAM - 1 GB, 256 MB)</code>.</li>
<li>Tunable: <code>storage.wiredTiger.engineConfig.cacheSizeGB</code>.</li>
</ul>
<pre><code class="language-yaml"><figure class="highlight yaml"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="yaml"><span class="line"><span class="hljs-attr">storage:</span></span><br><span class="line">  <span class="hljs-attr">wiredTiger:</span></span><br><span class="line">    <span class="hljs-attr">engineConfig:</span></span><br><span class="line">      <span class="hljs-attr">cacheSizeGB:</span> <span class="hljs-number">32</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Cache holds:</p>
<ul>
<li>Indexes pages (priority).</li>
<li>Recently-read document pages.</li>
<li>Active write buffers.</li>
</ul>
<p><strong>Cache hit rate</strong> matters more than absolute RAM. A query touching an index page already in cache is microseconds. Touching one from disk is milliseconds (SSD) or tens of ms (slow disk).</p>
<p>Inspect:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-title function_">serverStatus</span>().<span class="hljs-property">wiredTiger</span>.<span class="hljs-property">cache</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Key fields:</p>
<ul>
<li><code>bytes currently in the cache</code></li>
<li><code>tracked dirty bytes in the cache</code> (modified, not yet checkpointed)</li>
<li><code>pages evicted by application threads</code> — bad sign; app waited for eviction</li>
<li><code>unmodified pages evicted</code> — fine</li>
<li><code>modified pages evicted</code> — fine; happens periodically</li>
</ul>
<p>If <code>pages evicted by application threads</code> is climbing fast, the cache is undersized for your working set.</p>
<hr>
<h1 id="Chapter-2-—-Working-set-sizing-—-the-most-important-number"><a href="#Chapter-2-—-Working-set-sizing-—-the-most-important-number" class="headerlink" title="Chapter 2 — Working set sizing — the most important number"></a>Chapter 2 — Working set sizing — the most important number</h1>
<p>The <strong>working set</strong> is &quot;data + indexes you actually touch frequently&quot;. For read-heavy workloads, working set should fit in the WiredTiger cache.</p>
<p>Rough estimate:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">working_set ≈ (active indexes&#x27; size) + (5-10% of frequently-accessed docs&#x27; size)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>You can measure:</p>
<ul>
<li><code>db.collection.stats()</code> → <code>size</code>, <code>totalIndexSize</code>.</li>
<li><code>$indexStats</code> → which indexes are actually used.</li>
</ul>
<p>If working set &gt; cache:</p>
<ul>
<li>Cache thrashes — every query causes evictions.</li>
<li>Queries that should be &lt; 1 ms become 10-50 ms.</li>
<li>Latency p99 spikes.</li>
</ul>
<p>Fix priority:</p>
<ol>
<li>Drop unused indexes.</li>
<li>Reduce document size (don't store unused fields; compress text outside Mongo).</li>
<li>Archive old data (Atlas Online Archive or manual move).</li>
<li>Scale up to a bigger RAM tier.</li>
<li>Last resort: shard (Post 11) — distributes working set across multiple machines.</li>
</ol>

<td>none</td>
<td>1×</td>
<td>rarely useful</td>
</tr>
</tbody>
</table>
<p>Per-collection at creation:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-title function_">createCollection</span>(<span class="hljs-string">&quot;orders&quot;</span>, {</span><br><span class="line">  <span class="hljs-attr">storageEngine</span>: { <span class="hljs-attr">wiredTiger</span>: { <span class="hljs-attr">configString</span>: <span class="hljs-string">&quot;block_compressor=zstd&quot;</span> } }</span><br><span class="line">})</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>For most new collections in 2026, <code>zstd</code> beats snappy: similar speed, better compression → smaller cache footprint → higher hit rate.</p>
<p>Indexes are compressed by prefix compression separately (always on).</p>
<blockquote>
<p><strong>Trick:</strong> if your working set barely fits in RAM, switching from snappy → zstd often gives you 25 % more effective cache for free. Test under load before flipping in production.</p>
</blockquote>
<hr>
<h1 id="Chapter-4-—-Document-level-locking-MVCC"><a href="#Chapter-4-—-Document-level-locking-MVCC" class="headerlink" title="Chapter 4 — Document-level locking + MVCC"></a>Chapter 4 — Document-level locking + MVCC</h1>
<p>WiredTiger uses <strong>multi-version concurrency control (MVCC)</strong>:</p>
<ul>
<li>Readers see a consistent snapshot at their start time.</li>
<li>Writers create new versions; old versions linger until no reader needs them.</li>
<li>Locking is at the <strong>document</strong> level — different documents in the same collection don't block each other.</li>
</ul>
<p>Practical implications:</p>
<ul>
<li>High concurrency on different documents = fine.</li>
<li>High concurrency on the SAME document = serialised (hot-key problem, next).</li>
<li>Long readers force old versions to linger → memory pressure.</li>
</ul>
<p><strong>No collection-level lock</strong> during ordinary CRUD. DDL (createIndex, drop, collMod) still locks the collection briefly.</p>
<hr>
<h1 id="Chapter-5-—-Hot-keys-write-hotspots"><a href="#Chapter-5-—-Hot-keys-write-hotspots" class="headerlink" title="Chapter 5 — Hot keys + write hotspots"></a>Chapter 5 — Hot keys + write hotspots</h1>
<p>Symptom: a small subset of documents (one user, one product, one counter) receives most writes. WiredTiger serialises writes per document. The cluster has spare capacity but that one document caps throughput.</p>
<p>Examples:</p>
<ul>
<li>A &quot;global stats&quot; doc incremented on every event.</li>
<li>A celebrity user's profile updated by every fan's like.</li>
<li>An auto-increment sequence counter.</li>
</ul>
<p>Fixes:</p>
<ol>
<li><strong>Sharded counter pattern</strong> — split one counter into N shards, increment a random one, sum on read:</li>
</ol>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span><br><span class="line">10</span><br><span class="line">11</span><br><span class="line">12</span><br><span class="line">13</span><br><span class="line">14</span></pre></td><td class="code"><pre><code class="js"><span class="line"><span class="hljs-comment">// write</span></span><br><span class="line"><span class="hljs-keyword">const</span> shardId = <span class="hljs-title class_">Math</span>.<span class="hljs-title function_">floor</span>(<span class="hljs-title class_">Math</span>.<span class="hljs-title function_">random</span>() * <span class="hljs-number">16</span>);</span><br><span class="line">db.<span class="hljs-property">counters</span>.<span class="hljs-title function_">updateOne</span>(</span><br><span class="line">  { <span class="hljs-attr">_id</span>: <span class="hljs-string">`pageviews:<span class="hljs-subst">${shardId}</span>`</span> },</span><br><span class="line">  { <span class="hljs-attr">$inc</span>: { <span class="hljs-attr">count</span>: <span class="hljs-number">1</span> } },</span><br><span class="line">  { <span class="hljs-attr">upsert</span>: <span class="hljs-literal">true</span> }</span><br><span class="hljs-title function_">aggregate</span>([</span><br><span class="line">  { <span class="hljs-attr">$match</span>: { <span class="hljs-attr">_id</span>: { <span class="hljs-attr">$regex</span>: <span class="hljs-string">&quot;^pageviews:&quot;</span> } } },</span><br><span class="line">  { <span class="hljs-attr">$group</span>: { <span class="hljs-attr">_id</span>: <span class="hljs-literal">null</span>, <span class="hljs-attr">total</span>: { <span class="hljs-attr">$sum</span>: <span class="hljs-string">&quot;$count&quot;</span> } } }</span><br><span class="line">])</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<ol start="2">
<li>
<p><strong>Move to per-event docs</strong> — instead of incrementing a counter, insert one doc per event; aggregate on read. Trade write hotspot for storage + aggregation cost. Use TTL to bound storage.</p>
</li>
<li>
<p><strong>Async aggregation</strong> — log raw events; a background job rolls them up periodically (change stream + <code>$merge</code>).</p>
</li>
</ol>
<hr>
<h1 id="Chapter-6-—-Large-document-anti-pattern"><a href="#Chapter-6-—-Large-document-anti-pattern" class="headerlink" title="Chapter 6 — Large-document anti-pattern"></a>Chapter 6 — Large-document anti-pattern</h1>
<p>Documents have a <strong>16 MB BSON ceiling</strong>. Approaching it brings problems even earlier:</p>
<ul>
<li>Every update rewrites (copy-on-write) the whole document — slow.</li>
<li>Indexes on fields inside huge docs are inefficient.</li>
<li>Network + WiredTiger cost grows.</li>
</ul>
<p>Practical limit: <strong>keep docs under ~1 MB</strong> for hot writes.</p>
<p>Causes of bloat:</p>
<ul>
<li><strong>Unbounded arrays</strong> — comments, followers, history.</li>
<li><strong>Embedded binary data</strong> — images, PDFs.</li>
<li><strong>Schema drift</strong> — old fields accumulating.</li>
</ul>
<p>Fixes:</p>
<ol>
<li>Cap arrays: <code>$push: { items: { $each: [x], $slice: -100 } }</code>.</li>
<li>Move to child collection.</li>
<li><strong>GridFS</strong> for large binary (Chapter 7).</li>
<li>Compress before storing (gzip text), decompress on read.</li>
</ol>
<p>For files that need to live in MongoDB, GridFS is the safer answer.</p>
<hr>
<h1 id="Chapter-7-—-GridFS"><a href="#Chapter-7-—-GridFS" class="headerlink" title="Chapter 7 — GridFS"></a>Chapter 7 — GridFS</h1>
<p>GridFS splits large files into chunks (default 255 KB) stored across two collections (<code>&lt;bucket&gt;.files</code> + <code>&lt;bucket&gt;.chunks</code>).</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span <p>Use GridFS when:</p>
<ul>
<li>Files &gt; 16 MB.</li>
<li>You want metadata + access control alongside the file in one system.</li>
<li>Replication + sharding of the files for free.</li>
</ul>
<p>Better alternatives (in 2026):</p>
<ul>
<li><strong>S3 (or other object storage)</strong> + store URL + metadata in MongoDB. Cheaper, faster, scales further.</li>
<li>GridFS is convenient for small projects; object storage wins at scale.</li>
</ul>
<hr>
<h1 id="Chapter-8-—-Concurrency-tickets-recap-from-Post-08"><a href="#Chapter-8-—-Concurrency-tickets-recap-from-Post-08" class="headerlink" title="Chapter 8 — Concurrency tickets (recap from Post 08)"></a>Chapter 8 — Concurrency tickets (recap from Post 08)</h1>
<p>WiredTiger limits concurrent storage-engine operations via <strong>read + write tickets</strong> (default 128 each).</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-title function_">serverStatus</span>().<span class="hljs-property">wiredTiger</span>.<span class="hljs-property">concurrentTransactions</span></span><br><span class="line"><span class="hljs-comment">// { write: { out: 12, available: 116, totalTickets: 128 }, read: { ... } }</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p><code>available</code> near 0 = exhaustion → operations queue → latency spikes.</p>
<p>Causes:</p>
<ul>
<li>Slow queries holding tickets too long (most common).</li>
<li>Sudden write storm exceeding capacity.</li>
<li>Bad index plans.</li>
</ul>
<p>Fix order:</p>
<ol>
<li>Find + fix slow queries (Post 04).</li>
<li>Reduce app-side concurrency (smaller pool).</li>
<li>Scale up.</li>
</ol>
<p>Tickets aren't directly tunable in modern versions — they're sized by the storage engine.</p>
<hr>
<h1 id="Chapter-9-—-Long-readers-MVCC-pressure"><a href="#Chapter-9-—-Long-readers-MVCC-pressure" class="headerlink" title="Chapter 9 — Long readers + MVCC pressure"></a>Chapter 9 — Long readers + MVCC pressure</h1>
<p>A long-running read holds an MVCC snapshot. Old document versions can't be reclaimed until the reader is done. Long readers + heavy writers = memory pressure (cache fills with version chains).</p>
<p>Symptoms: <code>transactions.transaction store</code> growing, cache evictions climbing during long-running aggregations.</p>
<p>Mitigations:</p>
<ul>
<li>Set <code>maxTimeMS</code> on every user-facing query (Post 02).</li>
<li>Run heavy aggregations on a secondary (with <code>secondaryPreferred</code>) to isolate.</li>
<li>Break long aggregations into chunked stages writing to a <code>$merge</code> target.</li>
</ul>
<hr>
<h1 id="Chapter-10-—-Index-pages-in-RAM-math"><a href="#Chapter-10-—-Index-pages-in-RAM-math" class="headerlink" title="Chapter 10 — Index-pages-in-RAM math"></a>Chapter 10 — Index-pages-in-RAM math</h1>
<p>A useful sanity check:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line">hot_index_size = sum(index sizes used in hot queries)</span><br><span class="line">ratio = hot_index_size / wiredtiger_cache</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>If <code>ratio &gt; 1</code>, you can't keep indexes in RAM — queries that should be index-only will spill to disk.</p>
<p>Get sizes:</p>
<pre><code class="language-js"><figure class="highlight js"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="js"><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">totalIndexSize</span>()</span><br><span class="line">db.<span class="hljs-property">orders</span>.<span class="hljs-title function_">stats</span>().<span class="hljs-property">indexSizes</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Add up the ones from <code>$indexStats</code> (Post 04) with non-trivial <code>ops</code>. That's your hot index footprint.</p>
<hr>
<h1 id="Chapter-11-—-FTDC-diagnostic-data"><a href="#Chapter-11-—-FTDC-diagnostic-data" class="headerlink" title="Chapter 11 — FTDC + diagnostic data"></a>Chapter 11 — FTDC + diagnostic data</h1>
<p>MongoDB writes Full-Time Diagnostic Data Capture files to <code>dbpath/diagnostic.data/</code>. Continuous metrics, queryable after the fact with tools like <code>mongo-profiler</code> + Atlas's built-in analyzer.</p>
<p>For self-hosted root-cause analysis:</p>
<ul>
<li>Capture FTDC during an incident; share with MongoDB support or analyse via OSS tools.</li>
<li>Combine with mongod logs (slow ops, election events, ticket waits).</li>
</ul>
<p>Atlas: FTDC is collected automatically; the Atlas team can access it for support cases.</p>
<hr>
<h1 id="Chapter-12-—-Sample-production-tuning-checklist"><a href="#Chapter-12-—-Sample-production-tuning-checklist" class="headerlink" title="Chapter 12 — Sample production tuning checklist"></a>Chapter 12 — Sample production tuning checklist</h1>
<p>For a new self-hosted production cluster:</p>
<ul>
<li>[ ] WiredTiger cache sized to fit working set + headroom.</li>
<li>[ ] <code>zstd</code> compression for cold-ish collections.</li>
<li>[ ] Indexes audited; unused dropped.</li>
<li>[ ] Hot-counter pattern uses sharded counters.</li>
<li>[ ] No collection-level arrays growing unbounded.</li>
<li>[ ] Large binaries in GridFS or S3, not embedded.</li>
<li>[ ] <code>maxTimeMS</code> on user-facing queries.</li>
<li>[ ] Profiler at <code>slowms: 100</code>.</li>
<li>[ ] FTDC retained for 30 days.</li>
<li>[ ] Prometheus + Grafana dashboard alerting on the Post 14 metrics.</li>
<li>[ ] Restore drill scheduled monthly.</li>
</ul>
