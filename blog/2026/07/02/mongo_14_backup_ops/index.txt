<p>For self-hosted production with bigger volumes, snapshot the data volume:</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="bash"><span class="line"><span class="hljs-comment"># AWS EBS — snapshot the data volume</span></span><br><span class="line">aws ec2 create-snapshot --volume-id vol-XXXX --description <span class="hljs-string">&quot;mongod nightly&quot;</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Steps for consistency:</p>
<ol>
<li>Ensure journaling enabled (default — yes).</li>
<li>Take the snapshot while <code>mongod</code> is running (the journal ensures consistency on restore).</li>
<li>Restore: attach snapshot to new instance, <code>mongod --dbpath /new-data</code>.</li>
</ol>
<p>For replica sets, snapshot a <strong>secondary</strong> to avoid impacting primary I/O. To get a strictly-consistent point-in-time, run <code>db.fsyncLock()</code> on the secondary first → snapshot → <code>db.fsyncUnlock()</code>.</p>
<p>Throughput: snapshots are fast (block-level); restore time = mount + replication catch-up.</p>
<hr>
<h1 id="Chapter-4-—-Point-in-Time-Recovery-PITR"><a href="#Chapter-4-—-Point-in-Time-Recovery-PITR" class="headerlink" title="Chapter 4 — Point-in-Time Recovery (PITR)"></a>Chapter 4 — Point-in-Time Recovery (PITR)</h1>
<p>Snapshots give you &quot;the state as of snapshot time&quot;. PITR lets you restore to <strong>any second</strong> within a retention window — recover from &quot;we accidentally dropped this collection 22 minutes ago&quot;.</p>
<h2 id="How-it-works"><a href="#How-it-works" class="headerlink" title="How it works"></a>How it works</h2>
<ul>
<li>A periodic base snapshot.</li>
<li>Continuous oplog archiving between snapshots.</li>
<li>Restore = base snapshot + replay oplog to the target second.</li>
</ul>
<h2 id="Atlas"><a href="#Atlas" class="headerlink" title="Atlas"></a>Atlas</h2>
<p>Atlas continuous backup ships PITR by default on dedicated tiers. Restore via UI: pick a point in time, choose target (new cluster, in-place, or download).</p>
<p>Retention configurable (typical: 7-30 days continuous + monthly snapshots for longer retention).</p>
<h2 id="Self-hosted"><a href="#Self-hosted" class="headerlink" title="Self-hosted"></a>Self-hosted</h2>
<p>Use <strong>Percona Backup for MongoDB</strong> (PBM) or <strong>MongoDB Cloud Manager</strong> for PITR. Configure base snapshot + oplog archive to S3 / GCS / Azure Blob.</p>
<hr>
<h1 id="Chapter-5-—-Restore-drills"><a href="#Chapter-5-—-Restore-drills" class="headerlink" title="Chapter 5 — Restore drills"></a>Chapter 5 — Restore drills</h1>
<p>A backup is meaningless if you've never tested it. Schedule:</p>
<ul>
<li><strong>Monthly</strong>: pick a random recent backup; restore to a temporary cluster; verify a small sanity-check query returns expected data. Record RTO (time taken).</li>
<li><strong>Quarterly</strong>: full PITR drill — restore a DB to a specific past second.</li>
<li><strong>Annually</strong>: tabletop disaster scenario (region down). Walk through your runbook.</li>
</ul>
<p>Track:</p>
<ul>
<li><strong>RTO</strong> (Recovery Time Objective) — how long restore takes.</li>
<li><strong>RPO</strong> (Recovery Point Objective) — how much data you'd lose (depends on backup frequency + oplog window).</li>
</ul>
<p>Common surprises in first drills:</p>
<ul>
<li>Restored cluster's IAM / users are missing.</li>
<li>App connection string still points at the old cluster.</li>
<li>Restore is slower than expected because IOPS is limited on the target tier.</li>
<li>Indexes rebuild in the background, performance is poor for hours.</li>
</ul>
<p>Fix during the drill, not during an actual outage.</p>

<h1 id="Chapter-9-—-Capacity-planning"><a href="#Chapter-9-—-Capacity-planning" class="headerlink" title="Chapter 9 — Capacity planning"></a>Chapter 9 — Capacity planning</h1>
<p>Plan four dimensions:</p>
<h3 id="1-Working-set-vs-RAM"><a href="#1-Working-set-vs-RAM" class="headerlink" title="1. Working set vs RAM"></a>1. Working set vs RAM</h3>
<p>The <strong>working set</strong> = hot indexes + frequently-accessed docs. Must fit in WiredTiger cache (default 50 % of RAM - 1 GB) for fast reads. If it doesn't, every query touches disk → latency 10-100× worse.</p>
<p>Estimate working set: cumulative size of indexes used in hot queries + ~5-10 % of frequently-accessed documents. If RAM &lt; working set, scale up.</p>
<h3 id="2-Storage-IOPS"><a href="#2-Storage-IOPS" class="headerlink" title="2. Storage IOPS"></a>2. Storage IOPS</h3>
<p>Random read IOPS = how many &quot;miss the cache&quot; queries per second you can serve.</p>
<ul>
<li>Atlas tiers have provisioned IOPS per disk type.</li>
<li>AWS gp3: configurable up to 16k IOPS per volume.</li>
<li>NVMe instance-store: 100k+ IOPS but ephemeral.</li>
</ul>
<p>If IOPS is the bottleneck (visible as high disk queue depth + slow queries despite indexes), scale storage tier.</p>
<h3 id="3-CPU"><a href="#3-CPU" class="headerlink" title="3. CPU"></a>3. CPU</h3>
<p>For pipelines + aggregations + many concurrent queries, CPU matters. Aggregation-heavy workloads peg CPU before disk.</p>
<h3 id="4-Connections"><a href="#4-Connections" class="headerlink" title="4. Connections"></a>4. Connections</h3>
<p>App fleet × <code>maxPoolSize</code> ≤ tier connection limit (Post 08). Plan headroom for failover bursts.</p>
<h2 id="Sizing-decision-tree"><a href="#Sizing-decision-tree" class="headerlink" title="Sizing decision tree"></a>Sizing decision tree</h2>
