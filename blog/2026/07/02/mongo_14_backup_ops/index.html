MongoDB Course — 14 · Backup, Restore, Ops Monitoring, Capacity Planning

Created2026-07-02|Updated2026-07-02|Database > MongoDB
|Post View:

A backup you never restored is a hope, not a backup. This post covers the operational reality of running MongoDB in production: backup mechanisms (mongodump, file-system snapshots, Atlas continuous backup), point-in-time recovery (PITR), the slow-query profiler + currentOp + killOp, the server-status metrics worth alerting on, the restore drill that turns hopes into backups, and capacity planning.

Series map: 00 Foundations → … → 13 Security → 14 Backup & Ops (this post) → 15 Performance Deep → 16 Atlas → 17 Drivers & Case Studies.

Learning Outcome

  • Use mongodump / mongorestore correctly + their limits.
  • Take consistent file-system snapshots (LVM, EBS, ZFS).
  • Configure Atlas continuous backup + point-in-time recovery.
  • Run a restore drill monthly + automate it.
  • Use the profiler + slow-query log + currentOp + killOp.
  • Monitor the metrics that matter + alert thresholds.
  • Plan capacity by working-set + IOPS + connections.

Chapter 1 — Backup approaches

Approach What Best for
mongodump / mongorestore logical export of BSON small DBs (< ~100 GB), dev exports, migrations
File-system snapshot (LVM, EBS, ZFS) block-level snapshot of --dbpath medium-large DBs; consistent if journal included
Atlas Continuous Backup Atlas-managed snapshot + oplog tailing Atlas users; PITR included
Percona Backup for MongoDB open-source PITR self-hosted production

Pick by scale + ops staff + Atlas vs self-hosted.

Chapter 2 — mongodump / mongorestore

Pros: works against any version + cloud; portable file.

Cons:

  • Slow for big DBs — serialises every doc through the driver.
  • Not consistent across collections without --oplog (replica-set source only).
  • No PITR by itself.

Use for: dev datasets, migrations between accounts/regions, ad-hoc collection-level export.

Consistent dump from a replica set

--oplog captures oplog events during the dump; --oplogReplay applies them on restore — gives a consistent snapshot across the whole DB.

Chapter 3 — File-system snapshots

For self-hosted production with bigger volumes, snapshot the data volume:

Steps for consistency:

  1. Ensure journaling enabled (default — yes).
  2. Take the snapshot while mongod is running (the journal ensures consistency on restore).
  3. Restore: attach snapshot to new instance, mongod --dbpath /new-data.

For replica sets, snapshot a secondary to avoid impacting primary I/O. To get a strictly-consistent point-in-time, run db.fsyncLock() on the secondary first → snapshot → db.fsyncUnlock().

Throughput: snapshots are fast (block-level); restore time = mount + replication catch-up.

Chapter 4 — Point-in-Time Recovery (PITR)

Snapshots give you "the state as of snapshot time". PITR lets you restore to any second within a retention window — recover from "we accidentally dropped this collection 22 minutes ago".

How it works

  • A periodic base snapshot.
  • Continuous oplog archiving between snapshots.
  • Restore = base snapshot + replay oplog to the target second.

Atlas

Atlas continuous backup ships PITR by default on dedicated tiers. Restore via UI: pick a point in time, choose target (new cluster, in-place, or download).

Retention configurable (typical: 7-30 days continuous + monthly snapshots for longer retention).

Self-hosted

Use Percona Backup for MongoDB (PBM) or MongoDB Cloud Manager for PITR. Configure base snapshot + oplog archive to S3 / GCS / Azure Blob.

Chapter 5 — Restore drills

A backup is meaningless if you've never tested it. Schedule:

  • Monthly: pick a random recent backup; restore to a temporary cluster; verify a small sanity-check query returns expected data. Record RTO (time taken).
  • Quarterly: full PITR drill — restore a DB to a specific past second.
  • Annually: tabletop disaster scenario (region down). Walk through your runbook.

Track:

  • RTO (Recovery Time Objective) — how long restore takes.
  • RPO (Recovery Point Objective) — how much data you'd lose (depends on backup frequency + oplog window).

Common surprises in first drills:

  • Restored cluster's IAM / users are missing.
  • App connection string still points at the old cluster.
  • Restore is slower than expected because IOPS is limited on the target tier.
  • Indexes rebuild in the background, performance is poor for hours.

Fix during the drill, not during an actual outage.

Chapter 7 — currentOp + killOp

Reactive triage during incidents. Tag every endpoint with .comment() (Post 02) so you can find its ops quickly.

For chronic offenders, find their query shape via profiler + fix the index (Post 04).

Chapter 8 — Server status — metrics that matter

A massive JSON blob. Key metrics worth alerting on:

Metric Alert when Why
connections.current / max > 80 % pool exhaustion incoming
connections.totalCreated rate growing fast possible client misuse
opcounters.{insert,query,update,delete} rate sudden anomaly traffic spike or stuck loop
wiredTiger.cache.bytes currently in the cache vs configured near max + evictions high working set > cache (Post 15)
wiredTiger.concurrentTransactions.read/write.available near 0 ticket exhaustion
globalLock.activeClients.{readers,writers} sustained high contention
metrics.queryExecutor.scanned / scannedObjects growing per op indexes not used well
Replication lag > 60 s secondary falling behind
Oplog window < 4 h resync risk if a secondary falls behind
Disk free < 20 % running out
CPU sustained > 80 % undersized or runaway query

Atlas dashboards surface all of these out of the box. Self-hosted: Prometheus + the MongoDB Prometheus exporter + Grafana is the standard stack.

Chapter 9 — Capacity planning

Plan four dimensions:

1. Working set vs RAM

The working set = hot indexes + frequently-accessed docs. Must fit in WiredTiger cache (default 50 % of RAM - 1 GB) for fast reads. If it doesn't, every query touches disk → latency 10-100× worse.

Estimate working set: cumulative size of indexes used in hot queries + ~5-10 % of frequently-accessed documents. If RAM < working set, scale up.

2. Storage IOPS

Random read IOPS = how many "miss the cache" queries per second you can serve.

  • Atlas tiers have provisioned IOPS per disk type.
  • AWS gp3: configurable up to 16k IOPS per volume.
  • NVMe instance-store: 100k+ IOPS but ephemeral.

If IOPS is the bottleneck (visible as high disk queue depth + slow queries despite indexes), scale storage tier.

3. CPU

For pipelines + aggregations + many concurrent queries, CPU matters. Aggregation-heavy workloads peg CPU before disk.

4. Connections

App fleet × maxPoolSize ≤ tier connection limit (Post 08). Plan headroom for failover bursts.

Chapter 11 — Disaster recovery patterns

Scenario Strategy
Accidental drop restore from snapshot or PITR to the second before
Region outage Atlas multi-region cluster auto-fails over to surviving region
Logical corruption (bug wrote bad data for hours) PITR to before the bad write
Ransomware on self-hosted offsite, immutable, encrypted backups
Account compromise (Atlas) MFA + SSO + delete-protected backup snapshots + IAM-only access

Test these scenarios — RTO + RPO aren't real until you've measured them.

Chapter 12 — Common pitfalls

Pitfall Cause Fix
Backup never restored "we have backups" complacency monthly restore drill
mongodump chosen for huge DB slow + no PITR use Atlas backup or PBM
Snapshot taken without journal inconsistent restore journaling on (default); snapshot while running OK
Lost the connection string after restore restored cluster has new IDs scripted restore including app reconfig
Profiler off in production "performance overhead" myth enable with slowms: 100, overhead is minor
Metrics not alerted reactive ops dashboards + alerts on the table in Ch 8
Working set > RAM growth wasn't planned scale tier; add indexes; archive old data
Atlas tier connection limit hit client leaks Post 08
Restore is super slow restore tier too small provision IOPS on restore target
Backups not encrypted at rest self-hosted pipeline encrypt the backup bucket

Practice Exercises

Exercise 1 — mongodump round-trip

Dump shop to an archive. Restore into a fresh local instance. Verify document counts match.

Exercise 2 — Filtered dump

Dump only orders with status: "paid". Restore as orders_paid_only in a fresh DB.

Exercise 3 — Atlas restore drill

(Atlas user.) Take a snapshot. Restore to a new cluster. Document RTO + verify a sanity-check query.

Exercise 4 — Profiler

Enable profiler at slowms: 100. Run various queries. Find top 5 slowest by shape via system.profile.

Exercise 5 — Alerts

In Atlas (or self-hosted Prometheus), configure alerts for: connection limit 80 %, replication lag > 60 s, oplog window < 4 h.

Exercise 6 — Capacity audit

For your cluster, estimate working-set size, check it against RAM, check connection usage vs limit. Document one action item to address the tightest constraint.
