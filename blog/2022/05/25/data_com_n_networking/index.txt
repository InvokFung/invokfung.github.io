11:T1db87,<p>Networking is the part of computing that stays true the longest. Frameworks are replaced every few years; the fact that a packet is a bounded chunk of bytes travelling between two addresses, that it may be dropped, duplicated or delayed, and that everything above it is an attempt to hide those facts, has held since the 1970s and will outlive whatever runtime you are using this year. This post is a single self-contained pass over data communication and networking: the switching reality at the bottom, the layered abstractions built over it, the addressing and subnetting arithmetic you have to be able to do by hand, the transport and application protocols that carry the modern web, the delivery machinery that makes it fast at scale, and the diagnostic ladder that turns &quot;the site is slow&quot; into a specific, provable fault. Security is not a separate chapter here — firewalls, TLS and the common attack classes appear at the layer where each actually lives.</p>
<p>Where a cloud provider gives these concepts a branded name — a VPC, a security group, a NAT gateway — the mapping is pointed out, because a VPC is not a new idea: it is subnetting, routing tables and stateful firewalls with a control plane bolted on. The companion post <strong>AWS Course — 01 · Network First</strong> is the applied version of Chapters 3 and 4.</p>

<h1 id="Learning-Outcome"><a href="#Learning-Outcome" class="headerlink" title="Learning Outcome"></a>Learning Outcome</h1>
<ul>
<li>Explain what a network is in switching terms, distinguish bandwidth, throughput, latency and jitter, and use the bandwidth-delay product to explain why it caps a single connection.</li>
<li>Map OSI's seven layers onto TCP/IP's four, walk one real packet through encapsulation header by header, and read an Ethernet frame — including what a switch learns and how ARP, VLANs and MTU interact.</li>
<li>Subnet IPv4 by hand: derive network address, broadcast, usable host range and host count from any prefix, and build a VLSM plan that does not overlap.</li>
<li>Explain NAT and its real costs, read an IPv6 address, describe SLAAC and dual stack, and defend why IPv6 adoption matters.</li>

<li>Explain TCP's handshake, retransmission, flow control and congestion control, know when UDP is the better answer, and say what QUIC and TLS 1.3 fixed above it.</li>
<li>Trace one DNS name to its answer, compare HTTP/1.1, HTTP/2 and HTTP/3, and diagnose a broken or slow connection from layer 1 upward.</li>

<h1 id="Chapter-1-—-Fundamentals"><a href="#Chapter-1-—-Fundamentals" class="headerlink" title="Chapter 1 — Fundamentals"></a>Chapter 1 — Fundamentals</h1>
<h2 id="Terminology"><a href="#Terminology" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Network</strong> — nodes plus links, arranged so any node can deliver bytes to any other, directly or via intermediaries.</li>
<li><strong>Node</strong> — anything terminating or forwarding traffic: host, switch, router, firewall, load balancer.</li>
<li><strong>Protocol</strong> — an agreed message format and set of rules; the contract that lets independently written programs interoperate.</li>
<li><strong>Bandwidth</strong> — capacity of a link in bits per second. A property of the link, not of your transfer.</li>
<li><strong>Throughput</strong> — the rate your transfer actually achieves. Always ≤ bandwidth, usually well below. <strong>Goodput</strong> counts only useful application bytes, excluding headers and retransmissions.</li>
<li><strong>Latency</strong> — one-way delay. <strong>RTT</strong> is the there-and-back figure, which is what most tools measure.</li>
<li><strong>Jitter</strong> — variation in latency between successive packets. Fatal for real-time media, irrelevant for file transfer.</li>
<li><strong>Packet loss</strong> — the fraction of packets that never arrive. Networks are allowed to drop; reliability is built above.</li>
</ul>

<p>The internet chose packet switching because data traffic is <strong>bursty</strong>: a browser idles for seconds, then wants everything at once, and reserving capacity for an idle conversation is waste. The price is that delay is no longer constant, congestion is possible, and every layer above must cope with loss and reordering. Essentially all of Chapter 5 exists to pay that price.</p>
<h2 id="Bandwidth-is-not-speed"><a href="#Bandwidth-is-not-speed" class="headerlink" title="Bandwidth is not speed"></a>Bandwidth is not speed</h2>
<p>These four terms are routinely conflated, and the conflation causes most bad network decisions.</p>
<p>A 1 Gbit/s link does not make a packet arrive sooner; it makes more packets fit per second. Bandwidth is a truck's capacity, latency is how long the drive takes. And latency has a floor you cannot buy past: light in fibre travels at roughly two-thirds of <em>c</em>, about 200,000 km/s, so London to New York (~5,600 km) has a one-way minimum near 28 ms and an RTT floor near 56 ms. Real paths are not straight, so 70–80 ms is the production figure. No money reduces this; only moving the data closer does (Chapter 7). Throughput is the <em>outcome</em>, determined jointly by bandwidth, latency, loss, window sizes, the far end's capacity and every queue in between.</p>
<blockquote>
<p><strong>Watch out:</strong> &quot;the network is slow&quot; almost never means bandwidth is exhausted. Far more often it is latency, loss driving retransmission, an undersized window, a DNS stall, or a slow server. Measure before upgrading a link.</p>
</blockquote>
<h2 id="Bandwidth-delay-product"><a href="#Bandwidth-delay-product" class="headerlink" title="Bandwidth-delay product"></a>Bandwidth-delay product</h2>
<p>The <strong>BDP</strong> is how much data fits &quot;in flight&quot; on a path: <code>bandwidth (bits/s) × RTT (seconds)</code>. It matters because a reliable protocol can only have as much unacknowledged data outstanding as its window allows; if the window is smaller than the BDP, the sender stalls waiting for acknowledgements and the link runs empty.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line">100 Mbit/s, RTT 20 ms → 100,000,000 × 0.020 = 2,000,000 bits =    250,000 bytes ≈ 244 KiB</span><br><span class="line">1 Gbit/s,   RTT 80 ms → 1,000,000,000 × 0.080 = 80,000,000 bits = 10,000,000 bytes ≈ 9.54 MiB</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Now the classic consequence. TCP's receive-window field is 16 bits, so without window scaling the maximum window is 65,535 bytes. On that 80 ms transatlantic path:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span></pre></td><td class="code"><pre><code class="text"><span class="line">65,535 bytes × 8 bits ÷ 0.080 s = 524,280 ÷ 0.080 ≈ 6,553,500 bits/s ≈ 6.55 Mbit/s</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>A 1 Gbit/s link delivering 6.5 Mbit/s per connection — a 150× shortfall — purely because of a header field sized in 1981. Window scaling (RFC 7323) is the fix and is default everywhere now, but the shape recurs constantly: <strong>on long paths the window, not the link, is the limit.</strong></p>
<blockquote>
<p><strong>Trick:</strong> when one transfer is slow over a long path but many parallel transfers saturate the link, the bottleneck is per-connection windowing or congestion control, not capacity. That is exactly why <code>aria2 -x</code>, download accelerators and multipart S3 uploads exist.</p>
</blockquote>
<h2 id="Why-layers"><a href="#Why-layers" class="headerlink" title="Why layers"></a>Why layers</h2>
<p>Each layer solves one problem using only the service beneath it and offers one service above. The payoff is substitutability: HTTP does not know whether it runs over Ethernet, Wi-Fi or LTE. Each layer adds a header going down and strips it coming up — encapsulation, the subject of Chapter 2.</p>
<p>The cost is worth naming: layering hides information the layer above sometimes needs. TCP cannot tell wireless loss from congestion loss and slows down for both. HTTP/1.1 could not see it was sharing one connection. Most protocol progress of the last decade — QUIC especially — is layer boundaries being renegotiated because the old ones hid too much.</p>

<h1 id="Chapter-2-—-OSI-and-TCPIP"><a href="#Chapter-2-—-OSI-and-TCPIP" class="headerlink" title="Chapter 2 — OSI and TCP/IP"></a>Chapter 2 — OSI and TCP/IP</h1>
<h2 id="Terminology-1"><a href="#Terminology-1" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>PDU</strong> — the unit of data at a layer. Layer 2 calls it a <em>frame</em>, layer 3 a <em>packet</em>, TCP a <em>segment</em>, UDP a <em>datagram</em>.</li>
<li><strong>Encapsulation</strong> — wrapping a higher layer's PDU as the payload of a lower one by prepending a header.</li>
<li><strong>Trailer</strong> — metadata appended rather than prepended; Ethernet's frame check sequence is the example.</li>
<li><strong>MTU</strong> — the largest payload one link carries in a single frame. <strong>MSS</strong> — the largest TCP payload that fits in one packet without fragmenting.</li>
</ul>
<h2 id="The-two-models"><a href="#The-two-models" class="headerlink" title="The two models"></a>The two models</h2>

<p>A browser sending an HTTPS request over IPv4 and Ethernet, using documentation addresses from RFC 5737:</p>

<p>Two things cause real bugs. <strong>The destination MAC is the gateway's, not the server's</strong> — layer 2 addressing is hop-by-hop, layer 3 is end-to-end. IP addresses stay the same across the path (absent NAT); MAC addresses are rewritten at every router. This is the single most useful mental model in networking.</p>
<p><strong>Header sizes determine the MSS.</strong> On a 1500-byte MTU: <code>1500 − 20 (IPv4) − 20 (TCP) = 1460</code>. With IPv6's fixed 40-byte header, <code>1500 − 40 − 20 = 1440</code>. With the TCP timestamp option (common on Linux, 12 bytes padded), 1448. Over PPPoE at MTU 1492, 1452. Every VPN or overlay subtracts more.</p>
<h2 id="OSI-is-a-teaching-tool-TCPIP-is-what-runs"><a href="#OSI-is-a-teaching-tool-TCPIP-is-what-runs" class="headerlink" title="OSI is a teaching tool; TCP/IP is what runs"></a>OSI is a teaching tool; TCP/IP is what runs</h2>
<p>OSI was a complete protocol suite that lost; what survived is its vocabulary. Seven layers are useful for talking (&quot;that is a layer 7 load balancer&quot;) and misleading taken literally, because real protocols refuse to sit in one box. <strong>TLS</strong> runs over TCP, presents a byte stream, and does key exchange — it has no OSI home. <strong>QUIC</strong> is transport, session and security at once, in user space over UDP. <strong>MPLS</strong> is routinely called &quot;layer 2.5&quot; because it fits nowhere. <strong>VXLAN</strong> (RFC 7348) carries Ethernet inside UDP inside IP inside Ethernet, which the model forbids and every data centre does. <strong>ICMP</strong> rides inside IP but controls IP itself.</p>
<p>Use OSI numbers as shorthand; reason about the four TCP/IP layers when you need to be right.</p>
<hr>
<h1 id="Chapter-3-—-Link-layer"><a href="#Chapter-3-—-Link-layer" class="headerlink" title="Chapter 3 — Link layer"></a>Chapter 3 — Link layer</h1>
<h2 id="Terminology-2"><a href="#Terminology-2" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Frame</strong> — the link layer's PDU: header, payload, frame check sequence.</li>
<li><strong>MAC address</strong> — a 48-bit link-layer identifier burned into or configured on a NIC.</li>
<li><strong>Broadcast domain</strong> — the set of interfaces a broadcast frame reaches. One VLAN is one broadcast domain.</li>
<li><strong>Trunk port</strong> — a switch port carrying multiple VLANs, distinguished by 802.1Q tags; an <strong>access port</strong> carries one, untagged.</li>
</ul>
<h2 id="The-Ethernet-frame"><a href="#The-Ethernet-frame" class="headerlink" title="The Ethernet frame"></a>The Ethernet frame</h2>
<p>IEEE 802.3, in ubiquitous Ethernet II framing: preamble + SFD (7 + 1 bytes, not part of the frame proper), destination MAC (6), source MAC (6), EtherType (2 — <code>0x0800</code> IPv4, <code>0x86DD</code> IPv6, <code>0x0806</code> ARP, <code>0x8100</code> 802.1Q), payload (46–1500), FCS (4, CRC-32; a failing frame is silently discarded), then a 12-byte interframe gap. The 46-byte payload minimum makes the smallest legal frame 64 bytes. The 1500-byte maximum is the origin of the MTU number everyone quotes.</p>
<h2 id="MAC-addresses"><a href="#MAC-addresses" class="headerlink" title="MAC addresses"></a>MAC addresses</h2>
<p>Six hex octets. The first 24 bits are the <strong>OUI</strong>, assigned to a vendor by the IEEE. Two flag bits live in octet 1: the <strong>I/G bit</strong> (least significant) is 0 for unicast, 1 for multicast, with <code>ff:ff:ff:ff:ff:ff</code> as broadcast; the <strong>U/L bit</strong> (second least significant) is 1 for locally administered, which every virtual NIC, container veth and randomised phone MAC sets.</p>
<blockquote>
<p><strong>Watch out:</strong> modern phones and laptops randomise their MAC per network by default as an anti-tracking measure. Any access control, DHCP reservation or licence check keyed on MAC address is now unreliable by design. Use 802.1X or certificates.</p>
</blockquote>
<h2 id="What-a-switch-actually-does"><a href="#What-a-switch-actually-does" class="headerlink" title="What a switch actually does"></a>What a switch actually does</h2>
<p>One table, three rules. A frame arrives on port 3 with source MAC <code>aa:bb:cc:00:00:01</code>, so the switch <strong>learns</strong> that MAC is reachable via port 3 (entries age out, typically after 300 s). It looks up the destination MAC: found means forward out that one port, not found means <strong>flood</strong> out every port except the arrival port. Broadcast and multicast are flooded within the VLAN.</p>
<p>Two consequences. <strong>Unknown-unicast flooding is normal, briefly</strong> — a quiet server whose entry aged out receives VLAN-wide flooded traffic until it replies once. And <strong>loops are catastrophic</strong>, because Ethernet has no TTL: a frame in a physical loop circulates forever and broadcasts multiply at every switch, saturating the segment in seconds. Spanning Tree (802.1D, and the faster RSTP 802.1w and MSTP 802.1s) exists solely to block redundant links so the active topology is loop-free.</p>
<h2 id="ARP"><a href="#ARP" class="headerlink" title="ARP"></a>ARP</h2>
<p>To send an IP packet on the local link, a host needs the destination's MAC. ARP (RFC 826) supplies it:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="text"><span class="line">→ broadcast (dest ff:ff:ff:ff:ff:ff):  &quot;Who has 192.0.2.1? Tell 192.0.2.15&quot;</span><br><span class="line">← unicast:                             &quot;192.0.2.1 is at 00:1a:2b:00:00:01&quot;</span><br><span class="line">  cached in the neighbour table for a few minutes</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span></pre></td><td class="code"><pre><code class="bash"><span class="line">ip neigh show                 <span class="hljs-comment"># Linux neighbour/ARP table</span></span><br><span class="line">arp -a                        <span class="hljs-comment"># macOS / BSD / Windows</span></span><br><span class="line">ip neigh flush dev eth0       <span class="hljs-comment"># force re-resolution</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>ARP has <strong>no authentication whatsoever</strong>: any host on the segment can answer for any IP. That is ARP spoofing, and it turns a shared LAN into an on-path attack surface — the attacker becomes the gateway and sees all victim traffic. Mitigations are switch features, not host features: Dynamic ARP Inspection, DHCP snooping, port security, and 802.1X to authenticate devices before they get a port at all. IPv6 replaces ARP with Neighbor Discovery (RFC 4861) over ICMPv6, which has the same trust problem and the same class of switch-side defences (RA Guard, ND inspection).</p>
<h2 id="VLANs"><a href="#VLANs" class="headerlink" title="VLANs"></a>VLANs</h2>
<p>A VLAN partitions one physical fabric into independent broadcast domains. IEEE 802.1Q inserts a 4-byte tag after the source MAC: TPID (16 bits, <code>0x8100</code>), PCP (3 bits, 802.1p priority), DEI (1 bit), and VID (12 bits, VLAN 1–4094; 0 and 4095 reserved). Traffic between VLANs must be routed — which is exactly where firewall policy gets applied, and why &quot;put it in its own VLAN&quot; is a security statement, not just a topology one.</p>
<blockquote>
<p><strong>Common pitfall:</strong> the <em>native VLAN</em> on a trunk is carried untagged. If user traffic uses the native VLAN, a double-tagged frame can hop VLANs. Set the native VLAN to an unused ID and tag everything that matters.</p>
</blockquote>
<p>The 12-bit VID caps a fabric at 4094 segments, which is why multi-tenant data centres moved to VXLAN and its 24-bit VNI — roughly 16 million segments, carried as Ethernet-in-UDP so it routes across an IP fabric.</p>
<h2 id="MTU-and-why-1500"><a href="#MTU-and-why-1500" class="headerlink" title="MTU, and why 1500"></a>MTU, and why 1500</h2>
<p>1500 is the Ethernet payload maximum, and because Ethernet is everywhere it became the default assumption for the whole internet. <strong>Jumbo frames</strong> (typically 9000) cut per-packet overhead but require every device on the path to agree, so they are a data-centre feature, never an internet one. <strong>Tunnels shrink the usable MTU</strong>: PPPoE takes 8 bytes, and IPsec, WireGuard, GRE and VXLAN each take their own bite. An endpoint that ignores this produces the classic symptom — pings fine, DNS fine, small pages fine, large transfers hang forever.</p>
<p><strong>Path MTU Discovery</strong> (RFC 1191) is meant to solve it: the sender sets the IPv4 Don't Fragment bit and a router that cannot forward returns ICMP &quot;Fragmentation Needed&quot; (type 3, code 4) naming the smaller MTU. A firewall that blindly drops all ICMP turns the path into a <strong>PMTUD black hole</strong>. IPv6 raises the stakes — routers must never fragment (RFC 8200), so the source depends entirely on ICMPv6 Packet Too Big.</p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">ping -M <span class="hljs-keyword">do</span> -s 1472 203.0.113.80   <span class="hljs-comment"># 1472 + 8 (ICMP) + 20 (IPv4) = 1500; bisect downward on failure</span></span><br><span class="line">ip <span class="hljs-built_in">link</span> show eth0 | grep mtu      <span class="hljs-comment"># local interface MTU</span></span><br><span class="line"><span class="hljs-comment"># last-resort fix on a router: clamp TCP MSS to the real path MTU</span></span><br><span class="line">iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Trick:</strong> &quot;small requests fine, large uploads hang&quot; is an MTU problem until proven otherwise. It is the highest-yield guess in all of network troubleshooting.</p>
</blockquote>

<h1 id="Chapter-4-—-Network-layer"><a href="#Chapter-4-—-Network-layer" class="headerlink" title="Chapter 4 — Network layer"></a>Chapter 4 — Network layer</h1>
<h2 id="Terminology-3"><a href="#Terminology-3" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Prefix / CIDR block</strong> — a range of addresses sharing a leading bit pattern, written <code>address/length</code>. The <strong>subnet mask</strong> is the same idea as a dotted quad.</li>
<li><strong>Network address</strong> — all-zeros host portion; names the subnet. <strong>Broadcast address</strong> — all-ones host portion (IPv4 only).</li>
<li><strong>Default gateway</strong> — the next hop for any destination not on a directly connected subnet.</li>
<li><strong>Autonomous System (AS)</strong> — a network under one routing policy, identified by an AS number.</li>
</ul>
<h2 id="IPv4-addressing-and-CIDR"><a href="#IPv4-addressing-and-CIDR" class="headerlink" title="IPv4 addressing and CIDR"></a>IPv4 addressing and CIDR</h2>
<p>Thirty-two bits in four decimal octets; the prefix length says how many leading bits identify the network.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line">192.168.10.77/26 → mask 255.255.255.192 = 11111111.11111111.11111111.11000000</span><br><span class="line">                 → 26 network bits, 6 host bits</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h2 id="Subnetting-step-by-step"><a href="#Subnetting-step-by-step" class="headerlink" title="Subnetting, step by step"></a>Subnetting, step by step</h2>
<ol>
<li>Convert the prefix to a mask and find the <strong>interesting octet</strong> — the one that is neither 255 nor 0.</li>
<li>Compute the <strong>block size</strong>: <code>256 − (mask value in that octet)</code>.</li>
<li>Boundaries in that octet are multiples of the block size, starting at 0.</li>
<li><strong>Network address</strong> = the boundary at or below the given address; octets to its right become 0.</li>
<li><strong>Broadcast</strong> = next boundary − 1; octets to its right become 255.</li>
<li><strong>Usable range</strong> = network + 1 through broadcast − 1. <strong>Hosts</strong> = <code>2^(32 − prefix) − 2</code>.</li>
</ol>
<h3 id="Worked-example-1-—-192168107726"><a href="#Worked-example-1-—-192168107726" class="headerlink" title="Worked example 1 — 192.168.10.77/26"></a>Worked example 1 — <code>192.168.10.77/26</code></h3>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line">mask 255.255.255.192, interesting octet = 4th, block = 256 − 192 = 64</span><br><span class="line">boundaries: 0, 64, 128, 192   →  77 lies in 64…127</span><br><span class="line">network   192.168.10.64</span><br><span class="line">broadcast 192.168.10.127</span><br><span class="line">usable    192.168.10.65 – 192.168.10.126</span><br><span class="line">hosts     2^(32−26) − 2 = 64 − 2 = 62</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Verify by ANDing: 77 is <code>01001101</code>, mask octet 192 is <code>11000000</code>, AND gives <code>01000000</code> = 64. Correct.</p>
<h3 id="Worked-example-2-—-10132004521"><a href="#Worked-example-2-—-10132004521" class="headerlink" title="Worked example 2 — 10.13.200.45/21"></a>Worked example 2 — <code>10.13.200.45/21</code></h3>
<p>Here the interesting octet is the third, which is where most people slip.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span></pre></td><td class="code"><pre><code class="text"><span class="line">mask 255.255.248.0, interesting octet = 3rd, block = 256 − 248 = 8</span><br><span class="line">boundaries in octet 3: 0, 8, 16, …, 192, 200, 208   →  200 is itself a multiple of 8</span><br><span class="line">network   10.13.200.0</span><br><span class="line">broadcast 10.13.207.255      (next boundary 208, minus 1 → 207; octets right → 255)</span><br><span class="line">usable    10.13.200.1 – 10.13.207.254</span><br><span class="line">hosts     2^(32−21) − 2 = 2048 − 2 = 2046</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The subnet spans exactly eight /24s, <code>10.13.200.0</code> through <code>10.13.207.0</code>. When the interesting octet is the third, remember the fourth octet runs its full 0–255 range in every row.</p>
<h3 id="Worked-example-3-—-VLSM-allocation"><a href="#Worked-example-3-—-VLSM-allocation" class="headerlink" title="Worked example 3 — VLSM allocation"></a>Worked example 3 — VLSM allocation</h3>
<p>Given <code>172.16.4.0/22</code> (1,024 addresses, <code>172.16.4.0</code>–<code>172.16.7.255</code>), serve Engineering (500 hosts), Sales (200), Ops (100), Guest Wi-Fi (50) and two point-to-point router links. Round each up to a power of two, then <strong>allocate largest first</strong> so every block lands on its own natural boundary:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="text"><span class="line">172.16.4.0/23    Engineering  510 usable   172.16.4.0   – 172.16.5.255</span><br><span class="line">172.16.6.0/24    Sales        254 usable   172.16.6.0   – 172.16.6.255</span><br><span class="line">172.16.7.0/25    Ops          126 usable   172.16.7.0   – 172.16.7.127</span><br><span class="line">172.16.7.128/26  Guest         62 usable   172.16.7.128 – 172.16.7.191</span><br><span class="line">172.16.7.192/30  Link A         2 usable   172.16.7.192 – 172.16.7.195</span><br><span class="line">172.16.7.196/30  Link B         2 usable   172.16.7.196 – 172.16.7.199</span><br><span class="line">                 free                      172.16.7.200 – 172.16.7.255  (56 spare)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<blockquote>
<p><strong>Common pitfall:</strong> allocating smallest first produces blocks that are not aligned to their own size, which is illegal. A /23 must start on an even /24 boundary; a /26 must start at .0, .64, .128 or .192. If a block does not begin at a multiple of its size, the plan is wrong.</p>
</blockquote>
<p><strong>Summarisation</strong> is the reverse: <code>192.168.8.0/24</code> through <code>192.168.11.0/24</code> are contiguous and 8 is a multiple of 4, so they aggregate to <code>192.168.8.0/22</code>. This is how the global routing table stays finite — providers announce aggregates, not the thousands of customer prefixes inside them.</p>

<h2 id="NAT-and-what-it-costs"><a href="#NAT-and-what-it-costs" class="headerlink" title="NAT and what it costs"></a>NAT and what it costs</h2>
<p>NAPT (also called PAT) lets many private hosts share one public IPv4 address; the router keeps a mapping table and rewrites addresses and ports both ways.</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span></pre></td><td class="code"><pre><code class="text"><span class="line">192.168.1.10:51000  ↔  203.0.113.7:61001  ──►  93.184.x.x:443</span><br><span class="line">192.168.1.11:51000  ↔  203.0.113.7:61002  ──►  93.184.x.x:443</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>NAT bought the IPv4 internet two extra decades. The bill:</p>
<ul>
<li><strong>End-to-end addressing is gone.</strong> Inbound connections require port forwarding, UPnP/NAT-PMP, or a rendezvous server.</li>
<li><strong>Peer-to-peer becomes hard.</strong> Two NATed hosts cannot connect directly without hole punching — hence STUN, TURN, ICE, and most of WebRTC's machinery.</li>
<li><strong>Protocols that embed addresses break.</strong> Active FTP and SIP carry IPs in their payloads, so the NAT must deep-inspect and rewrite them (&quot;ALGs&quot;) — fragile, and a recurring source of bizarre bugs.</li>
<li><strong>State is finite and mortal.</strong> Idle mappings are reclaimed, often within minutes for UDP; long-lived idle TCP connections die silently unless keepalives are shorter than the NAT's timeout.</li>
<li><strong>CGNAT destroys the IP as identity.</strong> Thousands of subscribers share one address, so rate limiting, geolocation, abuse blocking and audit logging all become coarse and unfair — and ports run out, producing failures that look like packet loss.</li>
</ul>
<p>A NAT is not a firewall, though it accidentally behaves like one inbound. Say what you mean and configure a stateful firewall explicitly. In cloud terms, a NAT gateway is precisely this device, and the reason private-subnet instances reach the internet but cannot be reached from it.</p>

<h3 id="SLAAC"><a href="#SLAAC" class="headerlink" title="SLAAC"></a>SLAAC</h3>
<p>Stateless Address Autoconfiguration (RFC 4862) lets a host configure itself with no server:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span></pre></td><td class="code"><pre><code class="text"><span class="line">1. Host generates a link-local address: fe80::/64 + interface identifier.</span><br><span class="line">2. Duplicate Address Detection — a Neighbor Solicitation for its own address; silence means free.</span><br><span class="line">3. Host sends a Router Solicitation to ff02::2.</span><br><span class="line">4. Router Advertisement returns the /64 prefix, default route, lifetimes, and the M/O flags.</span><br><span class="line">5. <p>The interface identifier was originally derived from the MAC via EUI-64, leaking a stable hardware identity onto every network you joined. Modern stacks default to temporary privacy addresses (RFC 8981) plus a stable-but-opaque per-network identifier (RFC 7217), so a host typically holds several IPv6 addresses at once. The RA's <strong>M</strong> flag means &quot;also use DHCPv6 for addresses&quot;, <strong>O</strong> means &quot;use DHCPv6 for DNS and other information&quot;; DHCPv6 itself is RFC 8415.</p>
<h3 id="Dual-stack-and-why-adoption-matters"><a href="#Dual-stack-and-why-adoption-matters" class="headerlink" title="Dual stack and why adoption matters"></a>Dual stack and why adoption matters</h3>
<p>A dual-stack host prefers IPv6 when a AAAA resolves. <strong>Happy Eyeballs v2</strong> (RFC 8305) makes that safe: start the IPv6 connection, give it a short head start, race IPv4 behind it — so a broken IPv6 path costs milliseconds rather than a timeout. On IPv6-only networks, NAT64 (RFC 6146) with DNS64 (RFC 6147) synthesises addresses for IPv4-only destinations and translates at the edge.</p>
<p>Adoption matters for economic reasons before technical ones. The IANA free pool exhausted in 2011 and addresses now trade on a secondary market at real cost. Networks without enough IPv4 deploy CGNAT, which is expensive to run, degrades the user experience, and destroys the address as a unit of accountability. Large mobile operators run IPv6-only cores with 464XLAT because it is simply cheaper. Meanwhile IPv6 restores the end-to-end model, quietly removing whole categories of workaround. The pragmatic position is not &quot;IPv6 or IPv4&quot; — it is dual stack now, IPv6-primary as soon as dependencies allow, and never designing anything new that assumes 32-bit addresses.</p>

<h3 id="Static-vs-dynamic"><a href="#Static-vs-dynamic" class="headerlink" title="Static vs dynamic"></a>Static vs dynamic</h3>
<p>Static routes are configured by a human or by IaC, do not react to failure, and scale to a handful of entries — right for stub networks, cloud route tables and default routes. Dynamic routing is a protocol between routers that reconverges around failures and scales to a million prefixes — right for anything with redundant paths.</p>
<h3 id="Interior-OSPF"><a href="#Interior-OSPF" class="headerlink" title="Interior: OSPF"></a>Interior: OSPF</h3>
<p><strong>OSPF</strong> (OSPFv2 is RFC 2328; OSPFv3 carries IPv6) is a link-state IGP. Every router floods link-state advertisements describing its own links, so every router builds an identical map of the area and independently runs Dijkstra over it, with cost derived from bandwidth. Large deployments split into <strong>areas</strong> joined by a backbone (area 0) so flooding and SPF computation stay bounded. Convergence is fast — sub-second with tuned timers — because everyone sees the same topology. IS-IS occupies the same slot in large carriers; EIGRP is Cisco's distance-vector alternative.</p>
<h3 id="Exterior-BGP"><a href="#Exterior-BGP" class="headerlink" title="Exterior: BGP"></a>Exterior: BGP</h3>
<p><strong>BGP-4</strong> (RFC 4271) is the protocol that makes the internet one network. It is <strong>path-vector</strong>, running between Autonomous Systems: each AS advertises which prefixes it can reach and the AS path to get there, and each applies its own <strong>policy</strong> to decide what to accept, prefer and re-advertise. Policy, not shortest path, is the point — best-path selection walks a fixed list:</p>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span></pre></td><td class="code"><pre><code class="text"><span class="line">1. highest LOCAL_PREF     ← &quot;which exit do I want to use&quot;       (local policy)</span><br><span class="line">2. shortest AS_PATH       ← fewest ASes traversed</span><br><span class="line">3. lowest ORIGIN type</span><br><span class="line">4. lowest MED             ← &quot;which entrance do you want me to use&quot;</span><br><span class="line">5. eBGP preferred over iBGP</span><br><span class="line">6. lowest IGP metric to the next hop</span><br><span class="line">7. deterministic tiebreakers (oldest route, lowest router ID)</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>Step 1 comes first for a reason: money. LOCAL_PREF is where &quot;prefer settlement-free peering over paid transit&quot; is expressed. The default-free zone currently holds on the order of a million IPv4 prefixes and keeps growing — check the CIDR Report for the live figure rather than trusting a number in a blog post.</p>
<h3 id="Hijacks-and-route-leaks"><a href="#Hijacks-and-route-leaks" class="headerlink" title="Hijacks and route leaks"></a>Hijacks and route leaks</h3>
<p>BGP was designed among mutually trusting operators and authenticates nothing about who may announce what.</p>
<ul>
<li><strong>Prefix hijack</strong> — an AS announces a prefix it does not hold. Because a more specific announcement wins under longest-prefix match, announcing a /24 out of someone's /16 pulls their traffic globally. In 2008 Pakistan Telecom announced a more specific YouTube prefix intending a domestic block and removed YouTube from much of the internet for roughly two hours. In 2018 an announcement covering Amazon Route 53 address space redirected DNS for a cryptocurrency wallet and enabled real theft.</li>
<li><strong>Route leak</strong> — an AS re-advertises routes learned from one peer or provider to another, violating the intended relationship. Usually misconfiguration rather than attack, it typically funnels a large share of internet traffic through a network far too small to carry it, producing global congestion. RFC 7908 classifies six distinct leak types.</li>
</ul>
<p>Defences, none complete: <strong>RPKI ROAs</strong> record which AS may originate a prefix and <strong>Route Origin Validation</strong> (RFC 6811) lets routers drop RPKI-invalid announcements — this stops naive origin hijacks but not path forgery or most leaks; <strong>prefix filters and IRR data</strong> on customer sessions, with <strong>max-prefix limits</strong> to shut a session that suddenly announces 500,000 routes; and <strong>MANRS</strong> as the industry norms package. The honest summary: the routing layer is held together by filtering discipline and mutual reputation, incrementally reinforced by cryptography. Treat global reachability as best-effort.</p>

<h1 id="Chapter-5-—-Transport-layer"><a href="#Chapter-5-—-Transport-layer" class="headerlink" title="Chapter 5 — Transport layer"></a>Chapter 5 — Transport layer</h1>
<h2 id="Terminology-4"><a href="#Terminology-4" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Port</strong> — a 16-bit endpoint number within a host. <code>0–1023</code> well-known, <code>1024–49151</code> registered, above that dynamic (Linux defaults to <code>32768–60999</code>, see <code>net.ipv4.ip_local_port_range</code>).</li>
<li><strong>Socket</strong> — one endpoint. A TCP connection is identified by the 4-tuple: source IP, source port, destination IP, destination port.</li>
<li><strong>cwnd</strong> — congestion window: what the <em>sender</em> believes the network can absorb. <strong>rwnd</strong> — receive window: what the <em>receiver</em> says it can buffer.</li>
<li><strong>RTO</strong> — retransmission timeout: how long to wait for an ACK before resending.</li>
</ul>

<h2 id="Handshake-and-teardown"><a href="#Handshake-and-teardown" class="headerlink" title="Handshake and teardown"></a>Handshake and teardown</h2>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="text"><span class="line">Client                                   Server        Teardown (each direction closes</span><br><span class="line">  | SYN         seq=x                       |          independently, so half-close is legal)</span><br><span class="line">  |----------------------------------------&gt;|            | FIN ----------------&gt;|</span><br><span class="line">  |         SYN,ACK  seq=y, ack=x+1         |            |&lt;--------------- ACK  |</span><br><span class="line">  |&lt;----------------------------------------|            |&lt;--------------- FIN  |</span><br><span class="line">  | ACK         seq=x+1, ack=y+1            |            | ACK ----------------&gt;|</span><br><span class="line">  |----------------------------------------&gt;|            | … TIME_WAIT (2×MSL) …|</span><br><span class="line">  |            ESTABLISHED                   |</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The handshake costs one full RTT before any application byte moves — which is why connection reuse matters so much and why TLS 1.3 and QUIC work so hard to collapse round trips. Both sides pick a random <strong>Initial Sequence Number</strong>; randomising it is a security requirement, since predictable ISNs allow off-path connection spoofing.</p>
<p>A half-open connection consumes server state, so flooding SYNs from spoofed sources fills the accept queue — the classic <strong>SYN flood</strong>. <strong>SYN cookies</strong> are the standard defence: the server encodes the connection state into the ISN it returns and keeps no state until the client's ACK proves receipt (<code>net.ipv4.tcp_syncookies</code>).</p>
<p><strong>TIME_WAIT</strong> holds the closer for twice the maximum segment lifetime (60 s on Linux) so stray delayed segments cannot be mistaken for part of a new connection reusing the same 4-tuple.</p>
<blockquote>
<p><strong>Common pitfall:</strong> thousands of sockets in <code>TIME-WAIT</code> on a busy client is normal and healthy, not a leak. Thousands in <code>CLOSE-WAIT</code> <em>is</em> a bug — the application received a FIN and never called <code>close()</code>.</p>
</blockquote>
<h2 id="Sequence-numbers-and-retransmission"><a href="#Sequence-numbers-and-retransmission" class="headerlink" title="Sequence numbers and retransmission"></a>Sequence numbers and retransmission</h2>
<p>TCP numbers <strong>bytes</strong>, not packets. The ACK field carries the next byte expected, acknowledging everything before it cumulatively; <strong>SACK</strong> lets the receiver additionally report non-contiguous blocks it holds, so the sender resends only what is actually missing.</p>
<p>Loss is detected two ways. <strong>Fast retransmit</strong> treats three duplicate ACKs as a gap and resends immediately; modern Linux adds RACK-TLP (RFC 8985), which infers loss from transmit timestamps and probes the tail of a flight, greatly reducing costly timeouts. <strong>Timeout (RTO)</strong> is computed from a smoothed RTT estimate and its variance (RFC 6298): <code>RTO = SRTT + max(G, 4 × RTTVAR)</code>, initial value 1 second, exponential backoff on repeated failure. An RTO is expensive — it stalls the flow and resets the congestion window to its minimum.</p>
<h2 id="Flow-control"><a href="#Flow-control" class="headerlink" title="Flow control"></a>Flow control</h2>
<p>The receiver advertises <strong>rwnd</strong> in every ACK; the sender may never have more unacknowledged data outstanding than that. This protects a slow receiver from a fast sender — purely end-to-end, unrelated to network capacity. The field is 16 bits, capping the window at 65,535 bytes, which Chapter 1 showed is far below the BDP of any long fast path. The <strong>window scale option</strong> (RFC 7323) multiplies it by a negotiated power of two, up to a gigabyte. It is negotiated <em>only in the SYN</em>, so a middlebox that strips unknown TCP options from SYNs silently caps every connection through it at 6 Mbit/s on a transatlantic path.</p>
<h2 id="Congestion-control"><a href="#Congestion-control" class="headerlink" title="Congestion control"></a>Congestion control</h2>
<p>Flow control protects the receiver; congestion control protects the <em>network</em>, whose capacity nobody advertises. The sender may have at most <code>min(cwnd, rwnd)</code> bytes in flight. The classic algorithm (RFC 5681):</p>
<ul>
<li><strong>Slow start</strong> — begin small (10 segments is the common initial window) and <em>double</em> cwnd every RTT. Despite the name it is the aggressive phase; it is &quot;slow&quot; only relative to blasting at line rate immediately.</li>
<li><strong>Congestion avoidance</strong> — past <code>ssthresh</code>, switch to additive increase: roughly one MSS per RTT, linear.</li>
<li><strong>On loss</strong> — multiplicative decrease. Reno halves cwnd on fast retransmit; a full timeout collapses it to the initial window.</li>
</ul>
<p>This AIMD shape is why loss hurts far more on long paths: recovery is one segment per RTT, so an 80 ms path recovers eight times more slowly than a 10 ms one.</p>

<h2 id="Head-of-line-blocking"><a href="#Head-of-line-blocking" class="headerlink" title="Head-of-line blocking"></a>Head-of-line blocking</h2>
<p>TCP delivers bytes <strong>in order</strong>. If segment 5 of 10 is lost, segments 6–10 sit in the receiver's buffer, already arrived and undeliverable, until the retransmission lands. For a single file that is correct. For HTTP/2, which multiplexes many independent streams over one TCP connection, it is a serious flaw: loss affecting one image stalls every other response on the connection. This is the single biggest reason HTTP/3 abandoned TCP.</p>

Conversely a <em>client</em> opening many connections to one destination is limited by its ephemeral port range for that destination, around 28,000 on default Linux settings, and the cause of &quot;cannot assign requested address&quot; under load testing.</p>

<h1 id="Chapter-6-—-Application-layer"><a href="#Chapter-6-—-Application-layer" class="headerlink" title="Chapter 6 — Application layer"></a>Chapter 6 — Application layer</h1>
<h2 id="Terminology-5"><a href="#Terminology-5" class="headerlink" title="Terminology"></a>Terminology</h2>
<ul>
<li><strong>Resolver</strong> — the client-side component turning names into addresses. A <strong>stub</strong> resolver asks; a <strong>recursive</strong> resolver does the work.</li>
<li><strong>Authoritative server</strong> — holds the real published data for a <strong>zone</strong>, a contiguous portion of the namespace under one administration.</li>
<li><strong>TTL</strong> — how long a record may be cached, in seconds.</li>
<li><strong>SNI</strong> — Server Name Indication: the hostname sent in the TLS handshake so a shared IP can select the right certificate.</li>
</ul>
<h2 id="DNS"><a href="#DNS" class="headerlink" title="DNS"></a>DNS</h2>
<p>DNS (RFC 1034, RFC 1035) is a distributed, hierarchical, aggressively cached database on UDP port 53, falling back to TCP port 53 for large responses, with EDNS(0) (RFC 6891) negotiating larger UDP payloads. A <strong>stub resolver</strong> knows almost nothing and expects a final answer; a <strong>recursive resolver</strong> (your ISP's, or <code>1.1.1.1</code>) does the walking and caches; an <strong>authoritative server</strong> answers only for its own zones and otherwise returns a referral one level down.</p>

<h3 id="Records-worth-knowing"><a href="#Records-worth-knowing" class="headerlink" title="Records worth knowing"></a>Records worth knowing</h3>
<p><code>A</code>/<code>AAAA</code> are addresses. <code>CNAME</code> is an alias and cannot coexist with other records at the same name, so never at a zone apex. <code>MX</code> lists mail exchangers with preferences. <code>TXT</code> carries SPF, DKIM, DMARC and ownership proofs. <code>NS</code> names a zone's authoritative servers, <code>SOA</code> carries the serial, refresh/retry/expire timers and the negative-caching TTL (RFC 2308). <code>PTR</code> is reverse lookup, <code>SRV</code> gives host, port, priority and weight, <code>CAA</code> restricts which CAs may issue. <code>DS</code>, <code>DNSKEY</code>, <code>RRSIG</code> and <code>NSEC</code>/<code>NSEC3</code> are DNSSEC material, and <code>HTTPS</code>/<code>SVCB</code> deliver service parameters — ALPN, port, address hints — in one lookup.</p>
<h3 id="TTL-and-caching"><a href="#TTL-and-caching" class="headerlink" title="TTL and caching"></a>TTL and caching</h3>
<p>TTL is the contract that makes DNS scale and the trap that makes migrations painful. A record with <code>TTL 86400</code> may be cached for a day by every resolver worldwide and <strong>you cannot recall it</strong>. The discipline is non-negotiable: lower the TTL to 60–300 seconds at least one full old-TTL period <em>before</em> a planned change, make the change, verify, then raise it again. Negative answers are cached too, governed by the SOA minimum — which is why a typo'd record can look broken for a while after you fix it.</p>
<h3 id="DNSSEC-and-encrypted-transports"><a href="#DNSSEC-and-encrypted-transports" class="headerlink" title="DNSSEC and encrypted transports"></a>DNSSEC and encrypted transports</h3>
<p>DNS answers are unauthenticated by default, which historically enabled <strong>cache poisoning</strong>: race a forged answer to a resolver and pollute it for the whole TTL. Source-port randomisation and query-name mixing (RFC 5452 and successors) raised the cost but authenticate nothing. DNSSEC (RFC 4033/4034/4035) signs record sets, publishes the public key as <code>DNSKEY</code>, and has the parent zone publish a <code>DS</code> hash of it — a chain of trust from the root down, letting a validating resolver prove an answer is genuine or that a name genuinely does not exist. It provides <strong>authenticity and integrity, not confidentiality</strong>, and its cost is operational: key rollovers and expired signatures fail closed.</p>

<h2 id="QUIC"><a href="#QUIC" class="headerlink" title="QUIC"></a>QUIC</h2>
<p>QUIC (RFC 9000, TLS integration in RFC 9001, loss recovery in RFC 9002) is a transport built on UDP, in user space, with TLS 1.3 fused into it. Moving to UDP was not a preference for datagrams; it was the only way to deploy a new transport at all, because middleboxes everywhere inspect and mangle TCP and will not pass an unknown IP protocol number. UDP is the escape hatch, and user-space implementation lets the protocol evolve at application release cadence rather than kernel upgrade cadence.</p>
<p>What it fixes: <strong>no transport head-of-line blocking</strong>, since QUIC streams are independent and a lost packet stalls only its own stream; <strong>connection migration</strong>, because a QUIC connection is identified by a <strong>connection ID</strong> rather than the 4-tuple, so moving from Wi-Fi to cellular changes the IP but not the connection and the session survives with no reconnect and no lost upload; <strong>fewer round trips</strong>, with transport and cryptographic handshakes combined into 1-RTT for a new connection and 0-RTT on resumption; <strong>encryption by default including most of the transport header</strong>, so middleboxes cannot ossify it the way they ossified TCP; and <strong>unambiguous packet numbers</strong> that are never reused for retransmissions, removing TCP's retransmission ambiguity.</p>
<p>Costs, stated plainly: higher CPU per byte than kernel TCP (improving with offload), some networks block or throttle UDP, and 0-RTT data is replayable so it must carry only idempotent requests. Discovery is via the <code>Alt-Svc</code> header or an <code>HTTPS</code> DNS record — the client starts on TCP and upgrades.</p>
<h2 id="TLS-13"><a href="#TLS-13" class="headerlink" title="TLS 1.3"></a>TLS 1.3</h2>
<p>TLS 1.3 (RFC 8446) is both faster and smaller than TLS 1.2 (RFC 5246), and both properties come from the same decision: delete the insecure options rather than negotiate them.</p>

<td>sample two at random, pick the less loaded</td>
<td>large fleets; near least-connections quality, far less state</td>
</tr>
</tbody>
</table>
<blockquote>
<p><strong>Trick:</strong> plain round robin plus a slow endpoint equals a queue on every backend. Least-connections is the safer default whenever request cost is not uniform, because it naturally routes away from anything that has become slow.</p>
</blockquote>
<h2 id="Health-checks-and-affinity"><a href="#Health-checks-and-affinity" class="headerlink" title="Health checks and affinity"></a>Health checks and affinity</h2>
<p><strong>Active</strong> checks probe each backend on an interval — cheap, predictable, the standard. <strong>Passive</strong> checks observe real traffic and eject a backend after N consecutive errors — faster to react, but needs traffic to learn. A TCP connect proves the process is listening; an HTTP <code>/healthz</code> that touches the database proves it can actually serve.</p>
<p>Design the endpoint carefully. A deep check that fails when a shared dependency degrades marks <strong>every</strong> backend unhealthy at once and takes the service fully down — a self-inflicted outage worse than degraded service. The usual compromise is a shallow <strong>liveness</strong> check deciding restarts and a deeper <strong>readiness</strong> check deciding traffic, with a floor guaranteeing the balancer never removes the last healthy backends.</p>
<p><strong>Session affinity</strong> pins a client to one backend via a balancer-set cookie or a source-IP hash. It is a workaround for server-side state and it costs real properties: uneven load, lost sessions when a backend dies, and much harder deploys. Prefer stateless backends with session state in a shared store; use affinity only where an in-memory cache or a stateful long-lived connection genuinely requires it.</p>
<h2 id="Reverse-proxies-CDNs-anycast"><a href="#Reverse-proxies-CDNs-anycast" class="headerlink" title="Reverse proxies, CDNs, anycast"></a>Reverse proxies, CDNs, anycast</h2>
<p>A reverse proxy (nginx, HAProxy, Envoy, Caddy) is the load balancer's more general sibling, typically also handling TLS termination, HTTP version translation (HTTP/3 to the client, HTTP/1.1 to a legacy backend), compression, buffering, timeouts, retries, circuit breaking and access control. Concentrating these in one tier means applications do not reimplement them per service.</p>
<blockquote>
<p><strong>Watch out:</strong> behind a proxy the backend sees the <em>proxy's</em> address as the client. Propagate the real one with <code>X-Forwarded-For</code> / <code>Forwarded</code> (RFC 7239) — and trust it <strong>only</strong> from known proxy addresses. A blindly trusted <code>X-Forwarded-For</code> is a client-controlled header, and it will be used to bypass your IP allowlists and rate limits.</p>
</blockquote>
<p>A <strong>CDN</strong> is a global fleet of reverse-proxy caches. A client resolves your hostname to a nearby PoP, which serves from cache or fetches from the origin, often via an <strong>origin shield</strong> that collapses many PoPs' misses into one origin request. You gain latency (bytes start closer), origin offload (the origin serves misses only), and DDoS absorption (the attack lands on distributed edge capacity). You must manage invalidation and cache-key correctness — anything cached wrongly is now wrong in hundreds of places at once.</p>
<p><strong>Anycast</strong> announces the same prefix from many locations and lets BGP deliver each client to the routing-closest instance. It is how the DNS root servers, public resolvers and every CDN's edge addresses work: no DNS TTL delay when steering traffic, automatic failover when a site withdraws its announcement, and DDoS split across sites by the routing system itself. The limits: &quot;closest&quot; means shortest AS path, not lowest latency, and a route change mid-connection can move a client to a different site and break a long-lived TCP connection. That last problem is exactly what QUIC's connection migration is designed to survive, which is one reason CDNs adopted HTTP/3 early.</p>
<h2 id="Cache-Control-decides-whether-any-of-this-helps"><a href="#Cache-Control-decides-whether-any-of-this-helps" class="headerlink" title="Cache-Control decides whether any of this helps"></a>Cache-Control decides whether any of this helps</h2>

<p>Two rules govern all of them. <strong>Symmetry is not guaranteed</strong> — forward and return paths may differ, so a one-way problem is normal and traceroute shows one direction only. <h2 id="The-troubleshooting-ladder"><a href="#The-troubleshooting-ladder" class="headerlink" title="The troubleshooting ladder"></a>The troubleshooting ladder</h2>
<p>Work upward; each rung assumes the ones below passed. Stopping at the first failure is the entire technique, and most wasted debugging time comes from starting at layer 7.</p>
<p><strong>1 — Physical and link.</strong> <code>ip -br link</code> (is it UP with carrier?), <code>ethtool eth0 | grep -E 'Speed|Duplex|Link detected'</code>, <code>iw dev wlan0 link</code> for Wi-Fi signal and rate. Down or no carrier means cable, port, driver or radio, and nothing above can work.</p>
<p><strong>2 — Layer 2 neighbours.</strong> <code>ip neigh show</code>. A gateway stuck <code>INCOMPLETE</code> means ARP is not being answered: wrong VLAN, wrong subnet mask, port security, or the gateway is genuinely down.</p>
<p><strong>3 — Layer 3 addressing and routing.</strong></p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">ip addr show          <span class="hljs-comment"># address and prefix — is the mask right?</span></span><br><span class="line">ip route show         <span class="hljs-comment"># is there a default route?</span></span><br><span class="line">ping -c3 192.0.2.1    <span class="hljs-comment"># the gateway</span></span><br><span class="line">ping -c3 1.1.1.1      <span class="hljs-comment"># the internet by IP, bypassing DNS entirely</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>
<p>The critical split: <strong>if <code>ping 1.1.1.1</code> works but names fail, it is DNS</strong> — skip to rung 4. If it fails, stay at layer 3.</p>
<p><strong>4 — DNS.</strong></p>
<pre><code class="language-bash"><figure class="highlight bash"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span></pre></td><td class="code"><pre><code class="bash"><span class="line">dig example.com A +short           <span class="hljs-comment"># via the system resolver</span></span><br><span class="line">dig @1.1.1.1 example.com A +short  <span class="hljs-comment"># via a known-good public resolver</span></span><br><span class="line">resolvectl status                  <span class="hljs-comment"># which resolver is the system actually using?</span></span><br><span class="line">grep -v <span class="hljs-string">&#x27;^#&#x27;</span> /etc/hosts            <span class="hljs-comment"># a stale override here explains many mysteries</span></span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<p><strong>5 — Layer 4 reachability.</strong> <code>nc -vz example.com 443</code>, <code>curl -v --connect-timeout 5 https://example.com</code>. Read the failure mode, because it names the cause:</p>

<tr>

</tr>

<td>Connection timed out</td>
<td>SYN silently dropped: firewall, security group, or a black-holed route</td>

<h2 id="Exercise-4-—-Bandwidth-delay-product"><a href="#Exercise-4-—-Bandwidth-delay-product" class="headerlink" title="Exercise 4 — Bandwidth-delay product"></a>Exercise 4 — Bandwidth-delay product</h2>
<p>A 10 Gbit/s path has an RTT of 120 ms. (a) What is the BDP in bytes? (b) What window is needed to fill it? (c) What is the maximum single-connection throughput without window scaling?</p>
<details>
<summary>Solution</summary>
<pre><code class="language-text"><figure class="highlight text"><table><tr><td class="gutter"><pre><span class="line">1</span><br><span class="line">2</span><br><span class="line">3</span><br><span class="line">4</span><br><span class="line">5</span><br><span class="line">6</span><br><span class="line">7</span><br><span class="line">8</span><br><span class="line">9</span></pre></td><td class="code"><pre><code class="text"><span class="line">(a) 10,000,000,000 × 0.120 = 1,200,000,000 bits = 150,000,000 bytes ≈ 143 MiB</span><br><span class="line"> </span><br><span class="line">(b) The window must be at least the BDP — ~150 MB in flight. The 16-bit field maxes at</span><br><span class="line">    65,535, so a window scale factor of at least 2^12 is required</span><br><span class="line">    (65,535 × 4096 ≈ 268 MB of headroom).</span><br><span class="line"> </span><br><span class="line">(c) 65,535 × 8 ÷ 0.120 = 524,280 ÷ 0.120 ≈ 4,369,000 bits/s ≈ 4.37 Mbit/s</span><br><span class="line">    A 10 Gbit/s path delivering 4.4 Mbit/s per connection — a ~2,300× shortfall.</span><br><span class="line"> </span></code></pre></td></tr></table></figure></code></pre>

<h1 id="Where-to-go-deeper"><a href="#Where-to-go-deeper" class="headerlink" title="Where to go deeper"></a>Where to go deeper</h1>
<ul>
<li><strong>Apply Chapters 3 and 4 in a cloud</strong> — <strong>AWS Course — 01 · Network First</strong> is this material with a control plane: VPC CIDRs are RFC 1918 planning, subnets are the subnetting arithmetic above, route tables are longest-prefix match, security groups are stateful firewalls, NACLs are stateless ones, and NAT gateways are Chapter 4's NAT.</li>
<li><strong>Build a lab.</strong> Three Linux network namespaces joined by veth pairs, plus <code>ip route</code> and <code>iptables</code>, teach more in an afternoon than any diagram. Add FRRouting to run real OSPF and BGP between them.</li>
<li><strong>Read one capture properly.</strong> Load a single HTTPS page load into Wireshark and account for every packet: handshake, TLS, HTTP/2 frames, ACK pattern, FIN. Doing this once changes how you read everything else.</li>
<li><strong>Follow the specs.</strong> RFC 9293 (TCP), RFC 9000 (QUIC), RFC 8446 (TLS 1.3) and RFC 9110/9111 (HTTP semantics and caching) are unusually readable modern documents.</li>
<li><strong>Watch routing live.</strong> RIPE RIS and RouteViews publish real BGP data; RIPE Atlas lets you run measurements from thousands of vantage points for free.</li>
</ul>
