Part 2 — mongosync

Chapter 6 — What mongosync does

Mongosync replicates data continuously from a source cluster to a destination cluster, with minimal downtime cut-over. Works between any combination of self-hosted + Atlas + clouds + regions.

Use cases:

- One-time migrations (on-prem → Atlas, AWS → GCP, cluster tier change).- Multi-region passive-standby — destination always current; failover updates DNS.- Pre-production environments — sync prod data nightly into staging (with PII scrubbing post-sync).- Reverse-sync for rollback.

Phases:

Downtime for cut-over: seconds in normal cases.

Chapter 8 — Multi-region active-passive

On region A outage:

1. Stop the mongosync direction (or accept its catch-up lag).2. Flip your app's connection string / DNS to cluster B.3. Optionally start reverse mongosync (B → A) for when A recovers.

Active-active (writes in both regions) is not natively supported — last-writer-wins conflict resolution would be needed; Mongo doesn't have it. For active-active you typically shard by region (each region writes only to its own shard); mongosync isn't the right tool.

Chapter 9 — Sharded cluster sync

For sharded source + destination: run one mongosync per source shard to parallelise.

Coordinated commit ensures consistency on cut-over.

Part 3 — Cost optimisation

Chapter 11 — Atlas tier sizing

Atlas pricing scales with tier (M0 free → M700+ enterprise). Cost levers:

- Right-size the cluster by working set, not by RAM × N.- Reduce non-essential indexes (write amplification + RAM bloat).- Online Archive old data (Post 16) — 10× cheaper than hot tier.- Search nodes sized separately; right-size for index size + traffic.- Backup retention — long retention = more cost. Right-size to compliance need.- Data transfer — cross-region replication / clients in different regions = egress fees. Co-locate.

Chapter 12 — Index pruning

Hidden index pattern (Post 03) lets you test removal safely. Quarterly index review on every production collection. Easy 10-30 % storage + RAM win.

Chapter 13 — Query cost

Each slow query = wasted CPU + IOPS. The profiler + Atlas Performance Advisor (Post 04) surface them. Fix top-N slowest queries every sprint.

A query halved is two queries worth of capacity reclaimed. Index investments scale your fleet without scaling your tier.

Chapter 14 — Storage compression

- WiredTiger default is snappy. Switching new collections to zstd (Post 15) compresses 25 % better at similar CPU.- Old collections can be re-collected (offline) to apply new compression.

Chapter 15 — Connection cost

Each pool connection costs server-side resources. Right-size client pools by Little's Law (Post 08). Big over-pools waste Atlas tier capacity.

Chapter 16 — Hot vs cold tiers

For data that's queried rarely:

- Atlas Online Archive → cheap S3-like storage; federated query.- Manual archive to S3 (Parquet, compressed) → cheapest, custom-query path.- For analytics, push old data to ClickHouse (Post 28).

The two ratios that matter: hot/cold size + hot/cold cost. If 80 % of data is rarely queried, tier it; you'll cut cluster cost in half.

Chapter 17 — Atlas cost-control tactics

| Tactic | Saving ||--------|--------|| Right-size tier | up to 50 % if over-provisioned || Drop unused indexes | 10-30 % RAM || Online Archive cold data | 50 %+ on cold-heavy workloads || Switch to zstd | 20-30 % storage || Co-locate clients + cluster | data-transfer egress reduction || Annual commit / reserved pricing | 20-40 % discount || Stop dev / staging clusters off-hours | tier-hour reduction || Audit + cancel forgotten resources | varies; can be huge |

Chapter 18 — Self-hosted cost considerations

Cost = hardware (or cloud VMs) + storage + network + people-ops.

Compared to Atlas:

- Self-hosted hardware is often cheaper per GB-RAM at large scale.- But operating cost (people, on-call, backup infra, monitoring) often exceeds the Atlas premium.- Most teams break even around 50 nodes / multi-TB; below that, Atlas wins on TCO.

The right answer depends on your ops headcount + cloud commit + sovereignty needs.

Chapter 21 — PCI-DSS

For storing PAN (primary account number):

Chapter 22 — GDPR — right to be forgotten

Article 17 — data subjects can request deletion.

Patterns:

- Hard delete via secondary key (email / customerid). Find every collection referencing the subject; delete or anonymise. Chapter 4 ??Alternatives ??quick reference

| System | Storage model | Strengths | Weaknesses ||--------|----------------|-----------|------------|| MongoDB TS | document buckets w/ columnar compression | flexible schema, mixed workload, one DB | scale ceiling, slower deep analytics || ClickHouse | columnar, MergeTree variants | extreme analytics speed; great compression; SQL | append-mostly; weaker on point updates; ops complexity || TimescaleDB | Postgres extension; chunked time-partitioned tables | full SQL + Postgres tooling; PostGIS friends | not columnar core; scaling beyond 1 node harder || InfluxDB v3 | Apache Arrow + Parquet | purpose-built for metrics; PromQL-like Flux/SQL | rewrite history; ecosystem smaller || QuestDB | columnar, SIMD-vectorised | very fast ingest + queries; small footprint | newer ecosystem; less feature coverage || Apache Druid | columnar, segment-based | sub-second on huge datasets + dashboards | heavy ops; complex schema || Apache Pinot | columnar, segment-based | sub-second; ad-tech / event use cases | heavy ops || Prometheus + Mimir/Thanos | TSDB | metrics monitoring | not for arbitrary analytical queries |

For pure analytics over time-series, ClickHouse is the dominant 2026 choice for new builds. Operational complexity dropped with managed offerings (Altinity Cloud, ClickHouse Cloud).

Chapter 5 ??ClickHouse ??when + how

ClickHouse is a columnar OLAP database. Strengths for time-series:

- Sub-second aggregation over billions of rows.- 10-50? compression vs row-store.- Materialized views update incrementally.- Native S3 + Parquet integration for cold storage.

Inserts: millions of rows / second per node.Queries: tens of milliseconds over millions of rows.

Trade-offs:

- Append-mostly; updates + deletes are expensive (mutations queue).- Schema is rigid (vs Mongo's flexibility).- Operational complexity higher than managed Mongo.

Use ClickHouse when: pure analytical queries dominate; workload exceeds Mongo TS ceiling; you can devote eng time to running it or pay for managed.

Chapter 6 ??Hybrid ??Mongo for OLTP, ClickHouse for OLAP

The common 2026 pattern for serious scale:

Mongo handles user-facing reads + writes with rich queries on recent data. Events flow to ClickHouse via Kafka (Post 24) or a periodic batch ( + S3 ??ClickHouse). Dashboards / BI hit ClickHouse for big analytics.

Each tool does what it's best at; you pay the cost of running two systems but neither is asked to do the other's job poorly.

Chapter 7 ??When TimescaleDB fits better

If your team is already deep on Postgres + your analytical queries are still SQL-shape (joins, complex predicates, transactions over recent slices), TimescaleDB keeps you on one engine.

Strengths:

- Full Postgres feature set + PostGIS + extensions.- Multi-tier storage (recent on SSD, old compressed to columnar).- Familiar to SQL teams.

Weaknesses:

- Not as fast as pure columnar for huge analytics.- Scaling horizontally still harder than Atlas + Mongo or ClickHouse.

Pick when: SQL-first team, mixed transactional + analytical SQL workload, < 1 TB per dataset.

Chapter 8 ??InfluxDB v3 ??metrics-focused

InfluxDB v3 (formerly IOx) is rebuilt on Apache Arrow + Parquet. Strengths for metrics:

- Native to monitoring workflows (Prometheus-compat ingest, Grafana plugin).- Fast on time-series math (rates, moving averages, derivatives).- Self-managed or cloud.

Weaknesses:

- Less general-purpose than ClickHouse.- Schema evolution gotchas inherited from earlier versions.

Pick when: pure monitoring workload + you want a metrics-first DB rather than a general analytical engine.

Chapter 9 ??QuestDB ??fast + small

QuestDB is a young, fast columnar TS database. Strengths:

- Tiny footprint; runs on a laptop and on a server.- Very fast ingest + SQL queries.- Compatible with Postgres wire protocol.

Weaknesses:

- Smaller community + ecosystem than ClickHouse.- Fewer enterprise features.

Pick when: greenfield project, dev-friendliness > ecosystem.

Chapter 10 ??Druid / Pinot ??sub-second dashboards over huge data

For ad-tech, real-time analytics, leaderboard-style dashboards over billions of rows with millisecond response:

- Apache Druid ??operational complexity high; sub-second analytical queries shine.- Apache Pinot ??similar story; LinkedIn / Uber heritage.

Not the first choice for general workloads; reserve for when you genuinely need that latency at that scale.

Chapter 11 ??Decision matrix

The right answer is rarely "one engine for everything" past a certain scale.

Chapter 1 ??Should you migrate?

Honest answer first: most SQL workloads should stay on SQL. Migration is expensive + risky. Strong reasons to move:

- Schema flexibility required (per-tenant custom fields, fast product iteration, polymorphic items).- Write throughput beyond what Postgres can vertical-scale.- Hierarchical / document-shaped data (forms, content, configs, complex products) that's painful to join.- Horizontal scaling + multi-region + sharding required.- Operational simplicity at low ops headcount (Atlas managed > self-hosted Postgres cluster).

Weak reasons:

- "NoSQL is modern."- "We want to avoid joins" (you'll write joins as  either way).- "We need higher performance" (often a Postgres index would have fixed it).

Often the right answer is migrate a subset ??the parts where the document model genuinely fits ??and keep the rest in Postgres. The two coexist via outbox / CDC / app-side composition.

Chapter 3 ??Data movement strategies

Pick by downtime tolerance + data size + complexity tolerance.

Strategy A ??Full reload (hours of downtime)

1. Freeze writes to source.2. Extract source ??transform ??load into Mongo.3. Cut DNS / connection string over.4. Resume writes against Mongo.

OK for: < 100 GB and you can take a maintenance window.

Strategy B ??Dual-write at app layer (low downtime)

1. App writes to both Postgres + Mongo for new operations.2. Backfill historical data via ETL.3. Read-shadow: in parallel with reads from Postgres, fetch from Mongo + log differences.4. Switch reads to Mongo when shadow shows parity.5. Stop writes to Postgres.

OK for: medium-size apps where you control the write path.

Strategy C ??CDC-driven (best for large, can't-downtime)

1. Tail Postgres WAL via Debezium (or AWS DMS, Striim, Estuary, Airbyte).2. Transform + write to Mongo continuously.3. After sync catches up + remains in sync for a while, cut reads over.4. After cut-over, drain Postgres writes; flip back-flow off.

OK for: large databases, strict uptime requirements, polyglot teams.

Strategy D ??Strangler fig

- New features write to Mongo only.- Old features stay on Postgres.- Migrate one feature at a time over months.

OK for: legacy systems where a big-bang move is too risky.

Chapter 10 ??Rollback patterns

If Mongo turns out wrong (worse perf, missing feature, business decision change):

- During dual-write window: trivial. Switch back, drop Mongo data.- After cut-over but Mongo still has CDC back to Postgres: route reads back to Postgres, stop write CDC, keep Mongo as warm standby until decision.- After full cut: you need a reverse migration. Same playbook, opposite direction. Cost as much as the original.

Plan rollback explicitly before T0. Document the decision points.

Chapter 1 ??CQRS in one paragraph

A normal CRUD app uses one model for reads and writes ??same schema, same indexes, same database. CQRS splits them: command side handles writes (often normalised, validated, transactional), query side holds one or more read models optimised per use case (denormalised, fast). The read models are updated by events the command side publishes ??usually asynchronously.

Benefit:

- Read models match exactly the queries they serve ??simple + fast.- Read + write scale independently.- Multiple read models per command model (one for search, one for analytics, one for a mobile API).

Cost:

- More moving parts.- Read-after-write delay (eventual consistency).- Operational complexity.

Use CQRS when one of: read volume >> write volume; queries diverge wildly from write shape; you already need an outbox + projections.

Chapter 2 ??Event Sourcing in one paragraph

Instead of storing current state, store every change as an immutable event. Current state is computed by replaying events. Events are append-only ??the most reliable storage primitive in databases.

Benefits:

- Full audit trail for free.- New projections retroactively built from history.- Bug fixes can replay events through corrected code.- Time-travel debugging.

Costs:

- Reads must aggregate events (use snapshots + projections).- Schema evolution of events is forever ??versioning matters.- Higher mental + ops load than CRUD.

Use ES when one of: regulatory audit trail mandatory; the domain is genuinely event-shaped (orders, payments, IoT, ledger systems); you need to replay history for new analytics or bug correction.

ES + CQRS combine naturally ??ES is the command-side event log, CQRS is the read-side projections.

Chapter 3 ??When NOT to use CQRS / ES

- A CRUD app with simple reads + writes ??KISS.- Small team / small product ??overhead > benefit.- Tight read-after-write requirements with no tolerance for eventual consistency.- "Because it sounds modern" ??biggest reason teams regret it.

Default = CRUD. Add CQRS only when reads + writes genuinely diverge. Add ES only when the audit-or-replay property is mandatory.

Chapter 1 ??The dual-write problem

Two failure modes:

- DB insert succeeds, Kafka publish fails ??lost event.- Kafka publish succeeds, DB insert fails ??phantom event (consumers act on data that doesn't exist).

Neither is acceptable for systems that need consistency between their database state + downstream consumers.

Naive fixes that don't work

- Try-catch + retry: same race, just longer odds.- 2-phase commit across MongoDB + Kafka: not supported across systems.- Eventual consistency + reconciliation: complex; high latency.

The outbox

Write the event as a row in the same database, same transaction as the business mutation. A separate process publishes from the outbox to Kafka / RabbitMQ / SQS / SNS, marking each event as published (or deleting it).

Because the business write + outbox write are in one transaction, they're atomic. The publisher is async + retryable; downstream consumers handle duplicates idempotently.

Chapter 2 ??Outbox schema

means unprocessed. The publisher claims, processes, marks.

Chapter 3 ??Producer side ??transactional write

Both writes commit together or neither does. The business state and the to-be-published event are forever consistent.

Chapter 4 ??Publisher ??change-stream-driven (the cheap option)

Properties:

- At-least-once delivery ??on crash before token persist, we replay.- Resume token persisted after successful publish + mark.- Network blip ??retried with backoff, attempts incremented.

This pattern needs no external infrastructure beyond your existing MongoDB. The publisher can run anywhere ??a sidecar, a long-running container, a dedicated tiny pod.

Chapter 5 ??Publisher ??polling fallback

If change streams aren't available (standalone Mongo, very old versions, or a multi-region setup with restricted secondary access):

Higher latency (poll interval) + more DB queries; rock-solid. Use change streams when available, polling as fallback.

Chapter 6 ??At-least-once ??consumer must be idempotent

Once a publisher delivers at-least-once, consumers will eventually see duplicates (publisher crashed mid-ack, network duplicate, replay after rebuild).

Idempotency patterns:

1. Event ID dedup

Every outbox event has a unique . Consumers track processed IDs (in a "consumedevents" collection, Redis set, etc.). Skip if already processed.

2. Idempotent operations

Make the consumer's side-effect itself idempotent: , upsert by key, "set status to X" rather than increment.

3. Optimistic versioning

Event carries ; consumer rejects updates with .

Combine 1 + 2 for belt-and-braces.

Chapter 7 ??Ordering guarantees

Kafka topics + partitions preserve order within a partition. Choose your partition key to match the ordering you need.

For "all events on this order, in order" ??key on .For "every event in occurrence order globally" ??single-partition topic (low throughput).

Most outbox usage cares about per-aggregate ordering ??keying by  is the right default.

What if you don't have Kafka?

SQS doesn't preserve order across the queue (unless FIFO with ). SNS doesn't (FIFO topics do). RabbitMQ exchanges + queues do preserve order per queue.

Match destination to the ordering requirement.

Chapter 8 ??Backpressure + DLQ

When the downstream is down for hours:

- Outbox grows. Disk usage climbs.- If you have TTL on , you'll lose unpublished events ??don't TTL the unpublished portion.- The publisher must implement exponential backoff to avoid hammering a downed downstream.

Dead Letter Queue pattern:

Alert + investigate. Don't silently drop.

Chapter 9 ??Outbox + sagas (cross-service workflows)

For workflows spanning services (order ??payment ??inventory ??shipping), combine outbox events with a saga orchestrator. Each step is one service's local transaction + outbox publication. The next service's consumer triggers its step.

If a step fails, the orchestrator publishes a compensating action event ??previous services undo.

Outbox makes each step atomic + reliable. The saga adds the cross-step orchestration. Together they're the standard pattern for distributed workflows on document databases.

Chapter 10 ??When to use outbox + change streams vs Debezium

| | Outbox + change streams | Debezium MongoDB connector ||---|---|---|| Sync vs async | async publisher process | Kafka Connect cluster || Infrastructure | minimal (just Mongo) | Kafka + Connect || At-least-once | yes | yes || Event format | yours | Debezium envelope (uniform across DBs) || Schema migrations | app-aware | DB-shape only || Best for | one service, simple ops | many services, polyglot DBs into Kafka |

If you already run Kafka + Connect, Debezium is a thin add. If you don't, outbox + change-stream publisher is a cheap, self-contained pattern that scales to many millions of events/day.

Chapter 11 ??Common pitfalls

| Pitfall | Cause | Fix ||---------|-------|-----|| Lost events | non-transactional dual-write | use outbox || Phantom events on rollback | publish before commit | publish only from outbox post-commit || Duplicates downstream | at-least-once delivery | idempotent consumers || Publisher process crash ??unbounded replay | no resume token persistence | save token after each ack || Outbox bloats | publisher down for long | alert on size; DLQ chronic failures; back-pressure || Wrong partition ordering | random key | partition by aggregateid || Outbox writes blocked by transaction lifetime cap | huge transactions | smaller business transactions || Forgot to mark published | infinite loop re-publishing | always  post-ack |
